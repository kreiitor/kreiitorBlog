# 后记：回到 Agent = LLM + 上下文 + 工具

> 本笔记对应原书《深入理解AI Agent：设计原理与工程实践》后记：回到 Agent = LLM + 上下文 + 工具，原书印刷页码 303–305 页（PDF 第 311–313 页）。
> 笔记结构：先给“本章地图”，再逐节精读，最后是术语速查、原文要点汇编与自测题。

## 本章地图

- **这一部分要解决什么问题**：正文十章各自讲了一种构建或改进 Agent 的手段，但手段之间是什么关系？本部分是全书的总收束，它做三件事：① 用一条线把十章重新串回第 1 章的公式 `Agent = LLM + 上下文 + 工具`，并交代十章分别落在公式的哪个位置；② 给出作者认为今天 Agent 还没解决的两件大事——“两朵乌云”（实时交互、经验积累），并说清它们各自的现状、两条（两种）可能解法、以及为什么“是不是真问题”本身还有争议；③ 说明模型与 Agent（更准确地说，是模型与 Harness）之间那条自我强化的飞轮，回答第 1 章悬下的“模型会不会最终吃掉 Harness”，并落到对两类从业者的具体建议。
- **它在全书中的位置**：这是全书正文之后的收尾篇，没有下一章。它不引入新技术，只做“回收”：把第 1 章的公式、第 2–6 章的构建能力、第 7–9 章的评估与进化、第 10 章的协作重新摆成一张地图，再指出地图之外还没走通的两块地方。读它的正确姿势是“回头对照”——每读到一个判断，就回去想它对应第几章的哪一节结论。
- **本部分的层次**：后记开篇（原文无小标题，印刷 p.303）是“全书十章回顾”，把十章按“构建—评估与进化—协作”三组重排，并点出第九章是全书从“怎样构建 Agent”转向“怎样让 Agent 长期变好”的汇合点；随后「两朵乌云」（印刷 p.303 起）指出未来要打的两场硬仗；「模型与 Agent 的共同演进」（印刷 p.304）回答这两朵乌云靠什么被吹散、你该站在飞轮的哪一端；最后一页（印刷 p.305）是一段没有小标题的全书结语。换句话说，本部分的行文顺序是“回顾 → 展望（问题）→ 机制（飞轮）→ 寄语”。
- **读完你应该能做到**：
  1. 说出十章分别属于“构建”还是“提升能力”，以及后记给每一章留下的一句话结论；
  2. 复述两朵乌云各自讲的是什么问题：第一朵是“Agent 如何流式地、实时地与环境交互”，第二朵是“Agent 如何像人一样，从与环境交互的成功与失败中持续积累经验”；
  3. 讲清第一朵乌云的两条路（架构上快慢分离、把推理本身做快），并解释为什么“decode 够快”会让 turn-by-turn 与“实时”的界限模糊；
  4. 讲清第二朵乌云背后的“小世界假设”与“大世界假设”之争，以及原文更看重哪一边（此为笔记判断，原文未明说）；
  5. 画出模型与 Harness 互相喂养的飞轮，说出“Harness 会被一层一层吃掉、但没有吃完的那一天”的三个理由；
  6. 用“不换模型、只改 harness，准确率从 52.8% 跳到 66.5%”这个数字说明 harness 的杠杆从哪来、什么时候会失效。

## 后记开篇：全书十章都在公式的三个词里展开（原文无小标题，印刷 p.303）

**原文要点**

- 后记第一句就是回收第 1 章的公式：**本书开篇提出了一个公式：Agent = LLM + 上下文 + 工具。全书十章，都在这三个词里展开。**
- **第一章**建立公式的**三层理解**——实现层、直觉层、学术层，并给出**从工作流到自主 Agent 的编排光谱**。
- 随后的章节沿 **“构建—评估与进化—协作”** 逐步展开：
  - **构建 Agent（第二至六章）**：上下文工程决定 Agent 在一次任务中**看到什么**，记忆与知识库把信息扩展到**多次会话**；工具定义它**能做什么**，代码生成则提供**创造新工具与新系统的元能力**；交互一章再把观察与动作空间从**文本回合制**推向**语音、GUI 与物理世界**。
  - **评估与进化（第七至九章）**：评估把表现变成**可信信号**，后训练把高维能力写入**模型参数**，持续进化再把生产经验转化为**知识、指令、程序或参数**的**受控更新**。
  - **协作（第十章）**：多 Agent 协作进一步改变**上下文、工具与责任**的组织方式。
- 作者特别强调：**这三个层次并不是相互独立的书架。** 第九章尤其依赖前文的全部基础——没有**轨迹和知识系统**，经验无处保存；没有**代码能力**，Agent 无法修改工具与 Harness；没有**评估**，系统更无法判断一次修改究竟是进步还是退化。第九章由此成为全书**从“怎样构建 Agent”转向“怎样让 Agent 长期变好”的汇合点**。

**辅导讲解**

- 把这三组词和一串问题对起来记，最省力。整本书其实一直在回答三个问题：
  1. **看到什么？**——由**上下文**决定（第 2 章上下文工程管一次任务、第 3 章记忆与知识库管多次会话）；
  2. **能做什么？**——由**工具**决定（第 4 章工具，第 5 章代码把“工具”从既有的接口变成可随时新造的东西，第 6 章把工具/观察的载体从文本扩到语音、GUI、物理世界）；
  3. **做得对不对？怎么才能越做越好？**——这才是第 7–9 章的主线：评估先给出可度量的反馈，后训练把能力写进参数，持续进化把运行经验沉淀成知识/指令/程序/参数。
  第三组问题里“怎么才能越做越好”不属于第 1 章那条公式的三个词，但它是公式之外的第四个动作：**验证与改进**。后记末尾把“**如何验证做得对不对**”和“看到什么、能做什么”并列为三个不会过时的问题，正好对应这个分工。
- **为什么第九章是“汇合点”，而不是普通的一章**：可以把它想成一条装配线——第 3 章（记忆与知识库）生产并保管“原料”（运行轨迹、知识文档），第 5 章（代码能力）提供“机床”（Agent 能自己改工具、改 Harness），第 7 章（评估）提供“量具”（判断改完是进步还是退化），第 9 章才可能把原料、机床、量具接成一条闭环。少了任何一件，闭环都转不起来：没有量具，Agent 会把“碰巧跑通”当成“能力提升”；没有机床，它就只能改提示词，改不动工具与 Harness 这两层真正决定上下限的东西。
- **怎么用这张表**：把它当索引。以后遇到“某个功能/某个报错该归到哪里”的问题，先问它在三个词里是哪一个——是“模型没看到”（上下文问题）、还是“模型看不到能做这件事的手段”（工具问题）、还是“模型做了但没人告诉它做错了”（评估与进化问题）。这三个问句能覆盖全书绝大多数故障定位。
- 关于“构建 / 提升能力”这个两分法（笔记补充的读法）：如果按原书引言的两分法读，第 1–6 章是“**如何构建 Agent**”（把 Agent 造出来），第 7–10 章是“**如何提升 Agent 能力**”（让它更强、更可靠、更能协同）；引言还把这四章再细分了三个层面——第 8 章扩展**模型参数**层面的能力，第 9 章扩展**单体系统**层面的能力，第 10 章扩展**群体系统**层面的能力。后记则拆得更细，把第 7–9 章合成“评估与进化”、第 10 章单列“协作”。两种划法的内容一致，只是分组粒度不同。

**一句话记住**

> 全书十章不是十个并列技巧，而是同一条公式的三层展开：上下文决定看到什么，工具决定能做什么，评估与持续进化决定改得对不对；第九章把“造出来”和“越用越好”接成了闭环。

## 两朵乌云

**原文要点（总起）**

- 作者用物理学史上的典故开题：**1900 年，开尔文说物理学晴朗的天空上还飘着两朵乌云——后来，一朵变成了相对论，另一朵变成了量子力学。今天 Agent 的天空同样称不上晴朗，我也看到两朵乌云。**
- 这一节的收束句先给出基调：**这两朵乌云，都不是靠某一次模型升级就能凭空吹散的。要理解它们最终会怎样被跨越，得先看清一件事：模型和 Agent，从来不是上下游，而是一起往前走的。**

**原文要点 · 第一朵乌云：Agent 如何流式地、实时地与环境交互**

- **现状**：今天绝大多数 Agent 仍是按轮次（turn-by-turn）的“**请求—应答**”模式——**你说完一句，它想一整段，再一次性吐出结果**。
- **为什么这不够**：**真实世界不会停下来等它想完**——话会被打断，画面在持续变化，邮件在不断到达。
- **作者的判断**：一个真正“**活着**”的 Agent，应该能**边听边想、边说边想**，能在你**话说到一半时就开始规划**，也能在**没人吩咐时主动发现“这封邮件该处理了”**。
- **走向实时性的两条路，往往并行推进**：
  1. **架构上做快慢分离**：**实时与智能几乎是两条正交的轴**，单一模型难以兼顾，于是让**前台快模型维持对话节奏、后台慢模型负责深度思考**；
  2. **把推理本身做快**：**当 decode 速度足够高，按轮次的等待就短到近乎消失，turn-by-turn 与“实时”的界限也随之模糊**。这条路正被**芯片与推理引擎**快速推进，原文给了两个证据：
     - **小米 MiMo** 已让一个 **1T 参数模型**在**单个 8 卡节点**上把生成速度推过 **1000 token/s**（脚注 17）；
     - **把整个模型直接固化进芯片的专用方案（如 Taalas HC1）** 更是把 **80 亿参数模型**推到约 **17000 token/s**、**响应低于 100 毫秒**（脚注 18）。
- **结论句**：**当模型每秒能吐出上千个字，“想完再说”和“边想边说”的体验差距就被抹平了。**

**第一朵乌云的两条脚注（原文照录）**

- **脚注 17**：小米 **MiMo-V2.5-Pro-UltraSpeed** 通过 **FP4 量化、DFlash 并行推测解码**与 **TileRT 推理系统**的**模型—系统协同设计**，在**单个通用 8-GPU 节点**上**首次**把 **1T 参数模型**的生成速度推过 **1000 token/s**。见小米 MiMo 官方技术博客 “Pushing 1T-Parameter Model Generation Speed to 1000 TPS”, 2026. <https://mimo.xiaomi.com/blog/mimo-tilert-1000tps>
- **脚注 18**：**Taalas HC1** 将 **Llama 3.1 8B** 整个模型固化进 **6nm 芯片**，实现约 **17000 token/s**、**响应低于 100 毫秒**；代价是**芯片只能运行被固化的那个模型，模型更新需重新流片**。见 Karl Freund, “Taalas Launches Hardcore Chip With ‘Insane’ AI Inference Performance,” Forbes, 2026. <https://www.forbes.com/sites/karlfreund/2026/02/19/taalas-launches-hardcore-chip-with-insane-ai-inference-performance/>

**辅导讲解**

- **为什么“请求—应答”会成为默认形态**：LLM 的生成（decode）是自回归的——一次只吐一个 token，而且这一回合的“想”必须写完，才能作为一个完整回复交给用户。所以“你说完一句，它想一整段，再一次性吐出结果”不是设计者偷懒，而是当前推理范式落到产品上的自然结果。原文要攻的正是这个默认形态。
- **“实时”和“智能”为什么是两条正交的轴**（笔记补充的展开）：实时性约束的是“**多久之内必须给出反应**”（延迟预算），智能约束的是“**这一步要想多深**”（思考/搜索预算）。在同一时刻，算力只能花在一边：把预算堆到深度思考上，首个 token 就出得慢；为了抢延迟而砍掉思考，答案质量就掉下去。两者不是同一个刻度上的两端，而是两个独立的坐标轴，这就是原文说“单一模型难以兼顾”的原因，也是“快慢分离”这个解法的出发点。
- **快慢分离怎么工作**（笔记补充的类比）：像医院的分诊台和专家门诊。分诊台（前台快模型）必须立刻回应、维持队伍流动，负责接话、应答、察觉打断；专家（慢模型）可以慢慢看，负责真正的推理与判断，结论最后由他给。前台不必等后台想完就能继续对话，用户体验到的“节奏”由快模型保证，“质量”由慢模型保证。**需要补一句诚实的话：原文只交代了这个分工思路，并没有展开后台结论怎样、何时插回前台的机制（原文此处未展开）。**
- **第二条路为什么有效**：这条路绕开了架构，直接压时间去换体验。只要 decode 足够快，“它在想”这段等待就短到用户察觉不到，交互观感就和“边说边想”接近了。原文的两个数字可以换算成体感（以下为**笔记补充的估算**）：1000 token/s 按英文约 0.75 词/token 折算约 750 词/秒，而人类正常朗读约 150 词/分钟（约 2.5 词/秒），也就是说 1000 token/s 已经比人说话快**两个数量级以上**；17000 token/s 再快一个数量级。原文那句“当模型每秒能吐出上千个字”，说的就是这段等待被压到体感阈值以下。
- **固化芯片为什么能这么快、代价又是什么**（笔记补充的机制解释）：在 GPU 上做 decode，每生成一个 token 通常都要把（未命中缓存的）权重从显存搬到计算单元，很多情况下瓶颈在**显存带宽**而不是算力；把整个模型固化进芯片，等于把这部分搬移从“每次都要做”变成“电路本身就是权重”，速度自然上台阶。代价原文写得很清楚：**芯片只能运行被固化的那个模型，模型更新需重新流片**——模型迭代一次要重新做一版芯片，这条路买到的是速度，付出的是灵活性。
- **“FP4 量化 / DFlash 并行推测解码 / TileRT”三个词怎么理解**（笔记补充，原文只把它们并列成“模型—系统协同设计”）：**FP4 量化**是把权重压到 4 位精度，直接决定显存占用与带宽需求；**并行推测解码**（speculative decoding）是先用便宜的“草稿”一次猜出多个 token，再让大模型批量校验，把串行的逐步生成改成“猜—验”批量执行；**TileRT** 是配套的推理系统。三者合起来才让 1T 模型在 8 卡节点上过 1000 token/s。**再补一个算术感受**（笔记补充估算）：1T 参数在 FP4 下约 $1\times10^{12}\times0.5\ \text{byte}=500\ \text{GB}$，要塞进**单个通用 8-GPU 节点**，平均每卡要背 60 GB 以上——这也解释了“FP4 量化”为什么是这套方案的前提。
- **别把“速度”当成万能药**（笔记补充的判断，注意这条是笔记的补充，不是原文结论）：速度解决的是“**等多久**”，而“**要不要主动开口**”“**能不能被打断**”“**没人吩咐时自己发现该处理邮件**”属于**触发时机与控制流**问题，不是延迟问题。原文因此只说 turn-by-turn 与“实时”的**界限模糊**，没有说按轮次的模式会消失。第 6 章讲异步与事件驱动，处理的正是后一类问题。

**易混点**

- **流式（streaming）≠ 实时（real-time）**：流式说的是**输出方式**——token 一个个吐出来、边生成边显示；按轮次的 Agent 一样可以流式输出。实时说的是**交互时序**——能不能在对方话没说完时就开始规划、能不能被打断、能不能主动触发。原文这朵乌云指的是后者，别用“我们已经是流式返回了”来回答它。
- **快慢分离 ≠ 语音里的级联流水线**：快慢分离是**两个模型并行分工**（前台保节奏、后台想深度）；级联是**一条串行流水线**（前一级的输出喂给后一级）。第 6 章的语音交互会把这两类结构都摆出来（原书目录 6.3.2 级联流水线与 6.3.5 认知时序：实时交互与深度思考），但它们解决的问题不同。
- **把模型固化进芯片 ≠ 把模型量化**：量化是**压数值精度**，模型仍然可以替换；固化是把权重变成**电路**，快得多但把模型锁死（更新要重新流片）。原文把这两件事分别放在脚注 17 和脚注 18，正是两条不同的技术路线。

**原文要点 · 第二朵乌云：Agent 如何像人一样，从与环境交互的成功与失败中持续积累经验**

- **现状与比喻**：**今天的模型更像一个记性极好、却学不会新东西的天才**——训练时把人类知识背得滚瓜烂熟，上岗后却几乎不再成长；**每次任务结束，那些踩过的坑、试出来的窍门，大多随着上下文一起被丢掉**。
- **作者先声明了一个前提**：这究竟是不是一个真问题，**取决于两种针锋相对的假设**。
- **假设一：“小世界假设”**——一个**足够大的模型（比如几万亿参数）本就装得下物理世界里几乎所有重要的通用知识，学一次就够**。持这种看法的人（**不乏 OpenAI、Anthropic 的研究者**）指出：
  - AI 今天**唯独在编程上最强**，并不是因为代码对模型有什么特殊，而是因为**编程是人类最开放的领域**：海量开源代码摆在那里，可供学习；
  - 而**大多数行业压根没有公开的信息与数据**。于是前沿实验室真正在做的，是**一家家去与各行各业合作，把各自的专业能力“蒸馏”进同一个大模型**；
  - 按这种观点，**瓶颈既不在模型的容量、也不在它学不学得会，而在数据够不够**。**把数据喂进去、训练一次，问题就解决了。**
- **假设二：“大世界假设”**——它指向了**单靠“训练一次”补不上的一层**：**属于某个具体用户、某家具体公司的知识**。
  - 例证：**特定公司的代码规范、做 PPT 的口味、某个客户特有的脾气**，这些**不在任何训练语料里，而且时时在变**；
  - 结论：要贴合这个**由无数具体情境拼成的“大世界”**，模型**只能在上岗之后持续学习，没法指望出厂时一次配齐**。
- **作者紧接着指出这正是正文在摸索的方向**：**这正是第三章的记忆与第九章的持续进化在摸索的方向：把经验写成知识文档、指令或程序，还是经过筛选后用于更新模型参数？**
- **再往前一步**：**“RSI”（递归自我进化）和“AI for Science”都在推动 Agent 走到没有现成答案的前沿**；在那里，它**只能从一次次实验的成败中自主学习，而不是事事回头问人**。
- **这一朵乌云的结论句**：**所以，模型最强的能力，终将不是记住，而是学习与适应。**

**辅导讲解**

- **两套假设真正在争什么**：它们争的不是“大模型行不行”，而是**知识的分布长什么样**。小世界假设把世界看成一个**相对稳定、可以被一次性覆盖的总体**：只要数据足够多、模型足够大，通用知识就装得下，剩下的缺口是“还没喂进去的数据”。大世界假设把世界看成**无数具体情境拼起来的集合**：其中有一部分知识（某个用户的脾气、某家公司的规范、某个客户的偏好）**样本量极小（甚至只有一个人/一家公司）、而且时时在变**，因此它**不可能在训练时就存在**——训练集里没有，就算有也会过期。这就是“训练一次补不上的一层”的确切含义（这一段是笔记补充的解释）。
- **哪种假设会赢，决定了完全不同的工程投入**（笔记补充的推演）：如果小世界假设成立，投在“造更大模型 + 收更多数据”上的钱回报最高，Agent 侧的持续学习只是锦上添花；如果大世界假设成立，那么**围绕“上岗后如何学”的基础设施就是必需品**——第 3 章解决“经验存在哪儿、下次怎么找回来”，第 7 章解决“怎么知道这次做得好不好”，第 9 章解决“怎么把确认有效的经验变成受控更新”。原文虽然没有明说作者站哪一边，但它用“终将不是记住，而是学习与适应”作结，并把这个方向挂在第 3 章与第 9 章名下，立场是偏后者的（此为**笔记判断**）。
- **“把经验写成知识文档、指令或程序，还是更新模型参数”这句话为什么值得背下来**：它是整条“持续进化”路线的**选项清单**，而且顺序几乎是按“代价从小到大”排的（以下成本对比是**笔记补充**，原文只列出了四种形态）：
  - **知识文档**：写进记忆或知识库，最轻、可读可审、随时可回滚；代价是**每次都要占用上下文**、检索可能失败；
  - **指令**：写进系统提示词或 Skill，能直接改变行为，仍然属于上下文层，因此**受上下文长度与缓存策略约束**；
  - **程序**：写成代码，等于把经验固化成**可执行、可测试、可复用**的工具——这正是第 5 章“代码是元能力”的用处；
  - **参数**：更新模型权重，推理时**不占上下文开销**，但更新慢、难审计，而且可能带来灾难性遗忘。
  这四种形态对应第 9 章讲持续进化时逐节展开的四种方法（“将经验沉淀为知识 / 将经验写成指令 / 将经验写成程序 / 将经验写入参数”，见原书目录；原书另有一节讨论“从更新产物到更新‘更新方法’”）。**后记没有展开这四种形态各自的机制，只在问句里点了名。**
- **为什么“RSI”和“AI for Science”被一起提到**：这两个场景有一个共同特征——**没有现成答案，也没有人能随时给出正确答案**。在既有业务里，Agent 出错还可以回头问人；在“实验科学”和“自我改进”这两类前沿任务里，人类自己也不知道下一步该怎么做，**唯一的监督信号就是实验的成败**。所以它们对“经验积累”这件事的要求最高：必须能从失败里学，而不是每件事都等人来纠。原文对 RSI 与 AI for Science 本身**没有展开定义和机制**（原文此处未展开）。
- **和第 8 章的边界在哪**（笔记补充）：第 8 章讲的是**训练侧**怎么把能力写进参数（SFT、RL、奖励设计），它需要“数据/环境/奖励”这些外部条件齐备；第二朵乌云问的是**运行侧**：在没有专人标注、没有人给你造训练环境、数据只属于某一个用户的时候，Agent 能不能自己攒出可用的学习信号。所以这朵乌云落在第 3 章（记忆）与第 9 章（持续进化）上，而不是第 8 章。

**易混点**

- **“训练一次”≠“持续学习”**：前者假设知识是一个**静态分布**，把数据喂进去就行；后者要处理的是**分布本身随时在变**、且样本只属于极少数用户/公司（长尾到 $n=1$）的情况。两者的工程投入方向完全不同。
- **记忆（第 3 章）≠ 持续进化（第 9 章）**：记忆是**把信息存下来、下次能查**，不改模型；持续进化是**把经验变成受控更新**，可能改知识、改指令、改程序，也可能改参数。原文把两者并列为“摸索的方向”，说明它们要配着用：记忆负责“留得住”，进化负责“变得了”。
- **“记住”≠“学习与适应”**：这正是原文结论句里的对立面。记住是**静态存储**能力（背得多），学习与适应是**分布外适应**能力（换了环境还能变好）。小世界假设押注前者够用，大世界假设认为后者才是关键。
- **第二朵乌云 ≠ 第 8 章要解决的问题**：第 8 章是把已有数据/反馈变成参数更新的技术；第二朵乌云问的是**信号从哪来、谁来判好坏、怎么不忘记**。前者是方法，后者是闭环。

**一句话记住**

> 两朵乌云都不是“再训一版更强的模型”就能吹散的：一朵是**交互时序**（能不能边说边想、被打断、主动触发），一朵是**经验积累**（能不能在用中学）；作者把它押在“模型最强的能力，终将不是记住，而是学习与适应”上。

## 模型与 Agent 的共同演进

**原文要点**

- **先回头看 harness**：那些层层叠叠的兜底逻辑——**多级上下文压缩、失败数千次才熔断的重试、悲观地默认“不安全”的权限判断**——**每一段看似丑陋的“屎山”，记录的都是模型此刻还做不稳的地方。**
- **内化与删除是一体两面**：**当下一代模型把这些约束内化，对应的代码就可以删掉**；而模型之所以能内化，**又正是因为 Agent 早已在真实业务里替它把这些坑趟了一遍，沉淀成了下一轮训练的信号。**
- **飞轮的完整链条**：**用户提出真实的难题 → 应用层用 harness 把模型暂时做不好的事补上 → 这些补救再反过来变成模型下一次迭代的训练信号。这是一个自我强化的飞轮。**
- **回答第 1 章悬下的问题**（模型会不会最终吃掉 Harness？）：**本书的观点是：会，但不是一次性吃掉，而是一层一层地吃，并且没有吃完的那一天。**
  - **机制**：**模型每稳定内化一种能力，对应的 Harness 层就可以删掉。**
  - **已发生的例子**：**第六章的交互模型就是这样一个例子——打断、插话这些曾经要靠外挂 harness 才能拼出的行为，如今被直接做进了模型内部。**
  - **但“吃”永远不会完结，原文给了三个理由**：① **训练以月计，模型等得起，业务等不起**；② **模型无法内化真实业务中所有的约束与偏好，总有一层最新的边界需要外部逻辑兜底**；③ **每一代模型都会打开新的能力前沿，而前沿处恰恰是模型最做不稳的地方**。
  - **结论**：**所以 Harness 不会消失，它只是随着模型，不断向新的前沿迁移。**
  - **这也是《苦涩的教训》在 Agent 时代的读法**：**通用方法终将胜出，但“终将”二字里的每一段路，都是 Harness 铺出来的。**
- **飞轮转得最快的地方，是同时握住两端的人**：**Anthropic 用 Claude Code 做的，正是让自家模型和自家 harness 互相喂养、共同进化**——**模型知道 harness 会怎样调用它，harness 也清楚模型的边界在哪，两端的每一次改动都能立刻反馈给对方。**
- **一个关键实验数字**：**曾有人做过一个实验，不换模型、只改 harness，任务准确率就从 52.8% 跳到 66.5%。****这既说明 harness 今天的杠杆有多大，也提醒你：它之所以有这么大杠杆，恰恰是因为模型还没走到那一步。**
- **护城河的判断**：**这条飞轮本身，就是这个时代最深的一条护城河：真实业务、反馈数据与模型迭代咬合得越紧，别人越难从外部追上。**
- **对两类从业者的建议**（**这对你意味着什么，取决于你站在飞轮的哪一端**）：
  - **如果你在造模型**：**护城河就是把这条飞轮转起来——让真实场景的反馈尽快回流到训练里。**
  - **如果你在模型之上造应用**：**harness 是你短期最锋利的技术杠杆，但要清醒：模型每内化一层约束，就会顺手抹平一批只靠 harness 建立的优势。****应用层真正长久的护城河，往往在技术之外**——**独占的数据、稳固的渠道、用户的信任、网络效应，以及必须由人与 Agent 协作的物理世界场景等。****把 harness 用来争取时间，把这段时间用来构筑技术之外的壁垒，才是稳妥的打法。**
- **最后给出的“不会过时”清单**：**不必焦虑手里的框架会不会过时。****模型每几个月迭代一次，具体的 API、产品和榜单都会翻篇，但“看到什么、能做什么、如何验证做得对不对”这三个问题不会过时**——**它们描述的不是某个模型的用法，而是一个智能系统与世界交互的基本方式。****掌握了它们，无论下一代模型带来什么新能力，你都知道该把它放进公式的哪个位置，也能一眼看出，它离吹散那两朵乌云还有多远。**

**辅导讲解**

- **把“屎山”读成“能力的负片”**（笔记补充的视角）：多级上下文压缩、失败数千次才熔断的重试、默认“不安全”的权限判断，这三段代码有一个共同点——它们**不是业务需要，而是模型的缺陷留下的化石**。判断一段 harness 代码的寿命，可以用一个很实用的问句：**它是因为“模型现在做不到”才存在，还是因为“业务/制度要求如此”才存在？** 属于前者的，会随模型迭代被删；属于后者的，模型再强也吃不掉（比如“谁签字、谁负责、出事怎么回滚”）。
- **飞轮的因果链走一遍**（把原文的一句话拆成六步，**笔记补充的展开**）：
  1. 用户提出一个真实难题（难题的难度决定了后面所有环节的含金量）；
  2. 生产 harness 承接它，暴露出模型在这一类任务上的失败点；
  3. 外部逻辑兜底：压缩上下文、重试、默认拒绝危险操作……任务勉强完成；
  4. 这一整条轨迹（含失败与补救）被记录下来，成为训练信号；
  5. 下一代模型把这一类失败内化，对应的 harness 层被删掉；
  6. 模型的能力边界前移，于是**更难的业务被接了进来**，回到第 1 步。
  注意这个循环里同时产出两种资产，它们的性质完全相反：**被删掉的 harness 代码是消耗品**（它的价值随模型迭代归零），**沉淀下来的真实轨迹与反馈是资本**（它的价值随积累上升，且别人拿不到）。原文说“飞轮本身是最深的护城河”，护的其实就是后者。
- **为什么“没有吃完的那一天”（三个理由的机制）**：
  - **理由① 节奏差**：训练以月计，业务等不起。哪怕模型最终一定能学会，业务当下就得跑，所以**永远存在一段“模型还没学会、业务已经在跑”的窗口**，这段窗口里必须有人用外部逻辑顶上。
  - **理由② 私有约束与偏好无穷**：这与第二朵乌云的“大世界假设”是同一个道理。只要还要求“贴合这家公司的规范、这个客户的口味”，就总有一层属于特定组织的外部逻辑，而它不在任何训练语料里。
  - **理由③ 新前沿不断出现**：模型越强，被推上去做的任务越难，而“越难的任务”恰好落在它最不稳的地方。于是**删掉的层数多，新长出来的层数也不少**——harness 的总量不一定缩小，但它的**位置**一直在向新前沿迁移。这正是原文那句“不是一次性吃掉，而是一层一层地吃”的确切含义。
- **52.8% → 66.5% 该怎么读**：这是一个**控制变量**的实验——模型不动，只动 harness，所以提升只能归因于 harness。作者对这个数字给了**双向解读**：一方面，harness 今天的杠杆确实很大（13.7 个百分点的绝对提升）；另一方面，**它之所以有这么大杠杆，恰恰是因为模型还没走到那一步**。工程含义是：harness 的收益属于一种**时间窗口收益**——模型每次迭代都会侵蚀一部分。所以“今天 harness 能加 10 分”不能读成“harness 永远值 10 分”，更不能读成“harness 可以当长期壁垒”。（这段解读属于**笔记补充**，原文只给了数字和方向性提醒。）
- **“同时握住两端”为什么快**（笔记补充的机制解释）：如果模型团队和应用团队是两个组织，反馈回路的每一跳都要过需求、排期和口径对齐，周期以季度计；**Anthropic 用 Claude Code 把两端放在同一家公司里**，模型知道 harness 会怎样调用它，harness 也清楚模型的边界在哪，**每一次改动都能立刻反馈给对方**，回路缩短到天甚至小时级。原文没有写具体的数据指标，只说这是“互相喂养、共同进化”。
- **和全书其他章节的呼应**：这一节里的“内化并删除”，第 1 章的 Harness 五要素就是它的账本——每一条要素（上下文管理、工具接口、约束、验证、纠正）都可能整块被模型吃进去；第 6 章的交互模型是**已经发生过的实例**（打断、插话从外挂 harness 变成模型内置）；第 8 章讲的是“内化”在训练侧怎么做；第 9 章讲的是“把业务里趟出来的坑变成信号”这条链路的受控版本。
- **最后那三个问题**（“看到什么、能做什么、如何验证做得对不对”）**为什么被作者当作全书最值得带走的东西**：因为它们的答案会随模型换代而改变，**问题本身不会**。第 1 章那条公式给了前两个问题的位置（上下文 → 看到什么，工具 → 能做什么），第 7–9 章给了第三个问题的位置（评估 → 验证做得对不对）。学到这个层次，新技术来了你不需要重新学一遍框架，只需要把它**放进公式的对应格子里**。

**易混点**

- **“模型吃掉 Harness”≠“Harness 不再重要”**：吃掉说的是**能力替换**（某一层外部约束被内化进模型），重要性说的是**相对价值**。恰恰因为剩下的层是模型最做不稳的地方，它才更值钱、更前沿。原文的结论是“Harness 不会消失，它只是随着模型，不断向新的前沿迁移”。
- **“Harness 层被删掉”≠“Harness 工作消失”**：被删的是**因为模型暂时做不到而存在**的那部分代码；工作的重心随模型边界一起迁移。把“我写的代码被删了”读成“我的岗位没价值了”，是对这一节最常见的误读。
- **“harness 是护城河”≠“harness 是长期护城河”**：原文的态度是分层的——**飞轮**是护城河（真实业务 + 反馈数据 + 模型迭代的咬合），**harness 代码**只是短期杠杆。混淆这两者，就会得出“把 harness 做得足够好就安全了”的错误结论。
- **“通用方法终将胜出”≠“专用方法现在没用”**：原文的完整表述是“通用方法终将胜出，但‘终将’二字里的每一段路，都是 Harness 铺出来的”——**时间维度上的必然**和**当下的工程现实**是两件事，第 1 章 Harness 工程的意义就在这后半句里。

**一句话记住**

> Harness 记录的是模型此刻的短板，模型的内化又来自 harness 趟过的坑；这个飞轮会一层一层吃掉 harness，但因为训练以月计、业务约束私有、新前沿不断出现，它永远吃不完——所以把 harness 当**买时间的杠杆**，把买到的时间用来筑技术之外的壁垒。

- **这段结语在回答“读一本会过时的书有什么用”**（笔记补充的解读）：技术书的具体 API 一定会过时——原文自己说“模型每几个月迭代一次，具体的 API、产品和榜单都会翻篇”。作者要留下的因此不是操作手册，而是**一套判断力**：知道一个新能力该放进公式的哪个位置、知道它离吹散两朵乌云还有多远。这与上一节末尾那三个问题（看到什么、能做什么、如何验证做得对不对）是同一件事的两种说法。
- **“创造的原则”具体指什么**（笔记补充的归纳，不是原文原话）：按本部分的逻辑，它至少包含三层——① 用`Agent = LLM + 上下文 + 工具`把任何新系统拆成可动手的三块；② 用“看到什么 / 能做什么 / 验证做得对不对”给任何系统做体检；③ 认准模型与 harness 的飞轮，把自己的位置放在飞轮上而不是某段代码上。作者说“你已经握住了‘创造’的原则”，指的正是这种**可迁移的结构认识**，而不是某个框架的用法。
- **为什么结尾落在“写代码创造新能力，甚至改进自己”**：这正是第 5 章“代码：通用 Agent 的元能力”（代码创造代码、Agent 自举）与第 9 章“持续进化”的合流，也是第二朵乌云里“RSI（递归自我进化）”的日常版本。作者把全书最后一句话留给“去造点什么”，等于把这条链的起点交回给读者：**真实的难题由你做出来，飞轮才转得起来。**
- **一个可执行的读法**（笔记补充）：把配套实验跑一遍的价值不只是验证结论，而是**亲手体验一次“模型做不稳的地方”**——那些你在跑实验时想加的重试、想加的压缩、想加的权限判断，就是原文说的“Harness 铺出来的路”。

**一句话记住**

> 这本书要你带走的不是 API 用法，而是一套能在技术浪潮里保持清醒的判断力；公式、三个问题与那条飞轮都在你手上了，接下来去造点什么。
