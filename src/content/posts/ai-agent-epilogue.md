## 本章地图

全书十章各自讲了一种构建或改进 Agent 的手段，后记要做的是把这些手段重新摆成一张地图。它把十章收回到第 1 章那条公式 `Agent = LLM + 上下文 + 工具` 上，交代每一章落在公式的哪个位置；然后点出今天 Agent 还没解决的两件大事，也就是「两朵乌云」：实时交互与经验积累，并说清它们各自的现状、可能的解法，以及连「这算不算真问题」本身都还有争议；最后讲模型与 Agent（更准确地说，是模型与 Harness）之间那条自我强化的飞轮，回答第 1 章悬下的「模型会不会最终吃掉 Harness」，并落到对两类从业者的具体建议上。后记不引入新技术，只做回收，所以读它的正确姿势是回头对照：每读到一个判断，就回去想它对应第几章的哪一节结论。行文顺序是回顾、展望（问题）、机制（飞轮）、寄语：开篇到「两朵乌云」是一段，随后是「模型与 Agent 的共同演进」，最后一页是一段没有小标题的全书结语。

## 后记开篇：全书十章都在公式的三个词里展开

后记第一句就把第 1 章的公式捡了回来：这里开篇提出了一个公式，Agent = LLM + 上下文 + 工具，全书十章都在这三个词里展开。第 1 章自己负责建立公式的三层理解，实现层、直觉层、学术层，并给出从工作流到自主 Agent 的编排光谱。后面九章沿着「构建—评估与进化—协作」展开：构建 Agent 这部分是第二至六章，上下文工程决定 Agent 在一次任务中看到什么，记忆与知识库把信息扩展到多次会话，工具定义它能做什么，代码生成则提供创造新工具与新系统的元能力，交互一章再把观察与动作空间从文本回合制推向语音、GUI 与物理世界；评估与进化是第七至九章，评估把表现变成可信信号，后训练把高维能力写入模型参数，持续进化再把生产经验转化为知识、指令、程序或参数的受控更新；协作是第十章，多 Agent 协作进一步改变上下文、工具与责任的组织方式。

这三个层次并不是相互独立的书架。第九章尤其依赖前文的全部基础：没有轨迹和知识系统，经验无处保存；没有代码能力，Agent 无法修改工具与 Harness；没有评估，系统更无法判断一次修改究竟是进步还是退化。第九章由此成为全书从「怎样构建 Agent」转向「怎样让 Agent 长期变好」的汇合点。

这三组词可以和三个问题对起来记。上下文回答「看到什么」，第 2 章管一次任务，第 3 章的记忆与知识库管多次会话。工具回答「能做什么」，第 4 章是工具本身，第 5 章的代码把「工具」从既有接口变成可以随时新造的东西，第 6 章再把工具与观察的载体从文本扩到语音、GUI、物理世界。第 7 至 9 章的主线是「做得对不对、怎么才能越做越好」：评估先给出可度量的反馈，后训练把能力写进参数，持续进化把运行经验沉淀成知识、指令、程序或参数。最后一个问题其实不在公式的三个词里，它是公式之外的第四个动作，验证与改进。后记末尾把「如何验证做得对不对」和「看到什么、能做什么」并列为三个不会过时的问题，正好对应这个分工。

第九章为什么是汇合点，而不是普通的一章，可以把它想成一条装配线。第 3 章的记忆与知识库生产并保管原料，也就是运行轨迹和知识文档；第 5 章的代码能力提供机床，Agent 能自己改工具、改 Harness；第 7 章的评估提供量具，判断改完是进步还是退化；到第 9 章，原料、机床、量具才可能接成一条闭环。少了任何一件，闭环都转不起来。没有量具，Agent 会把「碰巧跑通」当成「能力提升」；没有机床，它就只能改提示词，改不动工具与 Harness 这两层真正决定上下限的东西。

这张表还可以当索引用。以后遇到「某个功能该归到哪里」「某个报错该找哪一章」的问题，先问它在三个词里是哪一个：是模型没看到，那是上下文问题；是模型看不到能做这件事的手段，那是工具问题；是模型做了但没人告诉它做错了，那是评估与进化问题。这三个问句能覆盖全书绝大多数故障定位。

关于「构建 / 提升能力」这个两分法，两种切法其实没有冲突。按引言读，第 1–6 章是把 Agent 造出来，第 7–10 章是让它更强、更可靠、更能协同；引言还把这四章再分成三个层面，第 8 章扩展模型参数层面的能力，第 9 章扩展单体系统层面，第 10 章扩展群体系统层面。后记拆得更细，把第 7–9 章合成「评估与进化」、第 10 章单列「协作」。内容一致，只是分组粒度不同。

全书十章更像同一条公式的三层展开，谈不上十个并列技巧：上下文决定看到什么，工具决定能做什么，评估与持续进化决定改得对不对；第九章把「造出来」和「越用越好」接成了闭环。

## 两朵乌云

用物理学史上的典故开题。1900 年，开尔文说物理学晴朗的天空上还飘着两朵乌云，后来一朵变成了相对论，另一朵变成了量子力学。今天 Agent 的天空同样称不上晴朗，也看到两朵乌云。这一节的基调定得很清楚：这两朵乌云都不是靠某一次模型升级就能凭空吹散的。要理解它们最终会怎样被跨越，得先看清一件事：模型和 Agent 一直是一起往前走的，谈不上谁在上游谁在下游。

### 第一朵乌云：Agent 如何流式地、实时地与环境交互

今天绝大多数 Agent 仍是按轮次（turn-by-turn）的「请求—应答」模式：你说完一句，它想一整段，再一次性吐出结果。麻烦在于真实世界不会停下来等它想完，话会被打断，画面在持续变化，邮件在不断到达。判断一个真正「活着」的 Agent 应该能边听边想、边说边想，能在你话说到一半时就开始规划，也能在没人吩咐时主动发现「这封邮件该处理了」。

走向实时性的两条路往往并行推进。一条是架构上做快慢分离：实时与智能几乎是两条正交的轴，单一模型难以兼顾，于是让前台快模型维持对话节奏、后台慢模型负责深度思考。另一条是把推理本身做快：当 decode 速度足够高，按轮次的等待就短到近乎消失，turn-by-turn 与「实时」的界限也随之模糊。

请求—应答之所以成为默认形态，是因为 LLM 的生成（decode）是自回归的，一次只吐一个 token，而且这一回合的「想」必须写完，才能作为一个完整回复交给用户。你说完一句、它想一整段、再一次性吐出结果，这是当前推理范式落到产品上的自然结果，只是这里要攻的正是这个默认形态。

实时与智能为什么是两条正交的轴，值得多说一句。实时性约束的是「多久之内必须给出反应」，也就是延迟预算；智能约束的是「这一步要想多深」，也就是思考或搜索预算。在同一时刻，算力只能花在一边：把预算堆到深度思考上，首个 token 就出得慢；为了抢延迟而砍掉思考，答案质量就掉下去。两者处在两个独立的坐标轴上，谈不上同一个刻度上的两端，这就是「单一模型难以兼顾」的原因，也是快慢分离这个解法的出发点。

快慢分离具体怎么工作，可以借医院的分诊台和专家门诊来理解。分诊台必须立刻回应、维持队伍流动，负责接话、应答、察觉打断；专家可以慢慢看，负责真正的推理与判断，结论最后由他给。前台不必等后台想完就能继续对话，用户体验到的节奏由快模型保证，质量由慢模型保证。这里要补一句诚实的话：本节只交代了这个分工思路，并没有展开后台结论怎样、何时插回前台的机制（此处未展开）。

第二条路为什么有效，因为它绕开了架构，直接压时间去换体验。只要 decode 足够快，「它在想」这段等待就短到用户察觉不到，交互观感就和「边说边想」接近了。这里的两个数字可以换算成体感，下面这两个估值是我按公开数字自己算的，本节只给了结论。1000 token/s 按英文约 0.75 词/token 折算约 750 词/秒，而人类正常朗读约 150 词/分钟，也就是 2.5 词/秒左右，所以 1000 token/s 已经比人说话快两个数量级以上；17000 token/s 再快一个数量级。那句「当模型每秒能吐出上千个字」，说的就是这段等待被压到体感阈值以下。

这条路上这里给了两个证据。小米 MiMo 已让一个 1T 参数模型在单个 8 卡节点上把生成速度推过 1000 token/s（脚注 17）；把整个模型直接固化进芯片的专用方案，比如 Taalas HC1，更是把 80 亿参数模型推到约 17000 token/s、响应低于 100 毫秒（脚注 18）。

> 脚注 17（按说明）：小米 **MiMo-V2.5-Pro-UltraSpeed** 通过 **FP4 量化、DFlash 并行推测解码**与 **TileRT 推理系统**的**模型—系统协同设计**，在**单个通用 8-GPU 节点**上**首次**把 **1T 参数模型**的生成速度推过 **1000 token/s**。见小米 MiMo 官方技术博客 “Pushing 1T-Parameter Model Generation Speed to 1000 TPS”, 2026. <https://mimo.xiaomi.com/blog/mimo-tilert-1000tps>
>
> 脚注 18（按说明）：**Taalas HC1** 将 **Llama 3.1 8B** 整个模型固化进 **6nm 芯片**，实现约 **17000 token/s**、**响应低于 100 毫秒**；代价是芯片只能运行被固化的那个模型，模型更新需重新流片。见 Karl Freund, “Taalas Launches Hardcore Chip With ‘Insane’ AI Inference Performance,” Forbes, 2026. <https://www.forbes.com/sites/karlfreund/2026/02/19/taalas-launches-hardcore-chip-with-insane-ai-inference-performance/>

固化芯片为什么能这么快，以及代价是什么，机制其实不复杂。在 GPU 上做 decode，每生成一个 token 通常都要把未命中缓存的权重从显存搬到计算单元，很多情况下瓶颈在显存带宽而不是算力；把整个模型固化进芯片，等于把这部分搬移从「每次都要做」变成「电路本身就是权重」，速度自然上台阶。代价这里写得很清楚：芯片只能运行被固化的那个模型，模型更新需重新流片。模型迭代一次要重新做一版芯片，这条路买到的是速度，付出的是灵活性。

FP4 量化、DFlash 并行推测解码、TileRT 这三个词，本节只把它们并列成「模型—系统协同设计」，没有逐个解释，这里补一下理解方式。FP4 量化是把权重压到 4 位精度，直接决定显存占用与带宽需求；并行推测解码（speculative decoding）是先用便宜的「草稿」一次猜出多个 token，再让大模型批量校验，把串行的逐步生成改成「猜—验」批量执行；TileRT 是配套的推理系统。三者合起来才让 1T 模型在 8 卡节点上过 1000 token/s。再算一笔算术：1T 参数在 FP4 下约 $1\times10^{12}\times0.5\ \text{byte}=500\ \text{GB}$，要塞进单个通用 8-GPU 节点，平均每卡要背 60 GB 以上，这也解释了 FP4 量化为什么是这套方案的前提（这个数同样是我按上面的口径算的）。

最后一件事得提醒：别把速度当成万能药。速度解决的是「等多久」，而「要不要主动开口」「能不能被打断」「没人吩咐时自己发现该处理邮件」属于触发时机与控制流问题，不是延迟问题。这里因此只说 turn-by-turn 与「实时」的界限模糊，没有说按轮次的模式会消失。第 6 章讲异步与事件驱动，处理的正是后一类问题。这一条是笔记的补充判断，不是上述结论。

这朵乌云里有两处最容易划错。流式（streaming）不等于实时（real-time）：流式说的是输出方式，token 一个个吐出来、边生成边显示，按轮次的 Agent 一样可以流式输出；实时说的是交互时序，能不能在对方话没说完时就开始规划、能不能被打断、能不能主动触发。这里这朵乌云指的是后者，别用「我们已经是流式返回了」来回答它。快慢分离也不等于语音里的级联流水线：快慢分离是两个模型并行分工，前台保节奏、后台想深度；级联是一条串行流水线，前一级的输出喂给后一级。第 6 章的语音交互会把这两类结构都摆出来，这里目录里是 6.3.2 级联流水线与 6.3.5 认知时序：实时交互与深度思考，但它们解决的问题不同。还有一条：把模型固化进芯片不等于把模型量化。量化是压数值精度，模型仍然可以替换；固化是把权重变成电路，快得多但把模型锁死，更新要重新流片。把这两件事分别放在脚注 17 和脚注 18，正是两条不同的技术路线。

### 第二朵乌云：Agent 如何像人一样，从与环境交互的成功与失败中持续积累经验

第二朵乌云换了个方向。先给一个比喻：今天的模型更像一个记性极好、却学不会新东西的天才，训练时把人类知识背得滚瓜烂熟，上岗后却几乎不再成长；每次任务结束，那些踩过的坑、试出来的窍门，大多随着上下文一起被丢掉。这究竟是不是一个真问题，取决于两种针锋相对的假设。

小世界假设认为，一个足够大的模型（比如几万亿参数）本就装得下物理世界里几乎所有重要的通用知识，学一次就够。持这种看法的不乏 OpenAI、Anthropic 的研究者，他们的论证大致是这样：AI 今天唯独在编程上最强，这跟代码本身有没有特殊之处无关，原因在于编程是人类最开放的领域，海量开源代码摆在那里可供学习；而大多数行业压根没有公开的信息与数据，于是前沿实验室真正在做的，是一家家去与各行各业合作，把各自的专业能力「蒸馏」进同一个大模型。按这种观点，瓶颈既不在模型的容量、也不在它学不学得会，而在数据够不够，把数据喂进去、训练一次，问题就解决了。

大世界假设指向了单靠「训练一次」补不上的一层：属于某个具体用户、某家具体公司的知识。特定公司的代码规范、做 PPT 的口味、某个客户特有的脾气，这些不在任何训练语料里，而且时时在变。要贴合这个由无数具体情境拼成的「大世界」，模型只能在上岗之后持续学习，没法指望出厂时一次配齐。

紧接着，这正是第 3 章的记忆与第 9 章的持续进化在摸索的方向，并且把问题提得更具体：把经验写成知识文档、指令或程序，还是经过筛选后用于更新模型参数？再往前一步，「RSI」（递归自我进化）和「AI for Science」都在推动 Agent 走到没有现成答案的前沿，在那里它只能从一次次实验的成败中自主学习，没法事事回头问人。这一朵乌云的结论句是：所以，模型最强的能力，终将是学习与适应，不是记住。

| 核心命题 | 一个足够大的模型（比如几万亿参数）本就装得下物理世界里几乎所有重要的通用知识，学一次就够 | 单靠“训练一次”补不上属于某个具体用户、某家具体公司的知识，模型只能在上岗之后持续学习 |
| 瓶颈在哪 | **数据够不够：既不在模型的容量，也不在它学不学得会 | 情境**：具体用户/公司的知识不在训练语料里，而且时时在变 |
| 主要论据 | AI 今天唯独在编程上最强，是因为编程是人类最开放的领域（海量开源代码可供学习）；而大多数行业压根没有公开的信息与数据，所以前沿实验室是一家家与各行各业合作，把专业能力“蒸馏”进同一个大模型 | 特定公司的代码规范、做 PPT 的口味、某个客户特有的脾气不在任何训练语料里，而且时时在变 |
| 给出的解法 | 把数据喂进去、训练一次，问题就解决了 | 上岗之后持续学习，没法指望出厂时一次配齐 |
| 谁在持这种看法 | 不乏 OpenAI、Anthropic 的研究者（这里如此） | 未点名持论者；把它与第三章的记忆、第九章的持续进化联系起来 |
| 对“模型是否还要成长”的回答 | 出厂即够用，成长主要是补数据 | 出厂只是起点，成长是常态 |

两套假设真正在争的，其实是知识的分布长什么样，跟「大模型行不行」关系不大。小世界假设把世界看成一个相对稳定、可以被一次性覆盖的总体：只要数据足够多、模型足够大，通用知识就装得下，剩下的缺口是「还没喂进去的数据」。大世界假设把世界看成无数具体情境拼起来的集合，其中有一部分知识（某个用户的脾气、某家公司的规范、某个客户的偏好）样本量极小，甚至只有一个人或一家公司，而且时时在变，因此它不可能在训练时就存在：训练集里没有，就算有也会过期。这就是「训练一次补不上的一层」的确切含义。这一段是补充的解释。

哪种假设会赢，决定了完全不同的工程投入方向。如果小世界假设成立，投在「造更大模型 + 收更多数据」上的钱回报最高，Agent 侧的持续学习只是锦上添花；如果大世界假设成立，围绕「上岗后如何学」的基础设施就是必需品：第 3 章解决经验存在哪儿、下次怎么找回来，第 7 章解决怎么知道这次做得好不好，第 9 章解决怎么把确认有效的经验变成受控更新。这里虽然没有明说立场偏向哪一边，但它特意把落点放在「学习与适应」上，并把这个方向挂在第 3 章与第 9 章名下，立场是偏后者的。这是我的判断，本节没有点破。

「把经验写成知识文档、指令或程序，还是更新模型参数」这句话值得背下来，它是整条持续进化路线的选项清单。四种形态的顺序大体就是按代价从小到大排的，下面这段成本对比是补充，本节只列出了四种形态。知识文档写进记忆或知识库，最轻、可读可审、随时可回滚，代价是每次都要占用上下文、检索可能失败；指令写进系统提示词或 Skill，能直接改变行为，仍然属于上下文层，因此受上下文长度与缓存策略约束；程序写成代码，等于把经验固化成可执行、可测试、可复用的工具，这正是第 5 章「代码是元能力」的用处；参数更新模型权重，推理时不占上下文开销，但更新慢、难审计，而且可能带来灾难性遗忘。这四种形态对应第 9 章讲持续进化时逐节展开的四种方法，也就是「将经验沉淀为知识 / 将经验写成指令 / 将经验写成程序 / 将经验写入参数」（见本章目录；另有一节讨论「从更新产物到更新‘更新方法’」）。后记没有展开这四种形态各自的机制，只在问句里点了名。

RSI 和 AI for Science 被一起提到，是因为这两个场景有一个共同特征：没有现成答案，也没有人能随时给出正确答案。在既有业务里，Agent 出错还可以回头问人；在实验科学和自我改进这两类前沿任务里，人类自己也不知道下一步该怎么做，唯一的监督信号就是实验的成败。所以它们对经验积累的要求最高，必须能从失败里学。这里对 RSI 与 AI for Science 本身没有展开定义和机制（此处未展开）。

和第 8 章的边界也值得划一下。第 8 章讲的是训练侧怎么把能力写进参数，SFT、RL、奖励设计，它需要数据、环境、奖励这些外部条件齐备；第二朵乌云问的是运行侧：在没有专人标注、没有人给你造训练环境、数据只属于某一个用户的时候，Agent 能不能自己攒出可用的学习信号。所以这朵乌云落在第 3 章记忆与第 9 章持续进化上，而不是第 8 章。

几组容易混的说法，分开看就清楚了。「训练一次」假设知识是一个静态分布，把数据喂进去就行；持续学习要处理的是分布本身随时在变、且样本只属于极少数用户或公司（长尾到 $n=1$）的情况，两者的工程投入方向完全不同。记忆（第 3 章）是把信息存下来、下次能查，不改模型；持续进化（第 9 章）是把经验变成受控更新，可能改知识、改指令、改程序，也可能改参数。把两者并列为「摸索的方向」，说明它们要配着用：记忆负责「留得住」，进化负责「变得了」。记住是静态存储能力，比的是背得多；学习与适应是分布外适应能力，比的是换了环境还能变好。小世界假设押注前者够用，大世界假设认为后者才是关键。第二朵乌云也不等于第 8 章要解决的问题：第 8 章是把已有数据或反馈变成参数更新的技术，第二朵乌云问的是信号从哪来、谁来判好坏、怎么不忘记。前者是方法，后者是闭环。

两朵乌云都不是「再训一版更强的模型」就能吹散的：一朵是交互时序，能不能边说边想、被打断、主动触发，另一朵是经验积累，能不能在用中学。后者才是这里押注的方向，落点是「学习与适应」，而不是「记住」。

## 模型与 Agent 的共同演进

先回头看 harness。那些层层叠叠的兜底逻辑，多级上下文压缩、失败数千次才熔断的重试、悲观地默认「不安全」的权限判断，每一段看似丑陋的代码记录的都是模型此刻还做不稳的地方。内化与删除是一体两面：当下一代模型把这些约束内化，对应的代码就可以删掉；而模型之所以能内化，又正是因为 Agent 早已在真实业务里替它把这些坑趟了一遍，沉淀成了下一轮训练的信号。

飞轮的完整链条是这样：用户提出真实的难题，应用层用 harness 把模型暂时做不好的事补上，这些补救再反过来变成模型下一次迭代的训练信号。这是一个自我强化的飞轮。

第 1 章悬下的问题是模型会不会最终吃掉 Harness。这里的观点是会，只是这个过程一层一层来，并且没有吃完的那一天。机制很直白：模型每稳定内化一种能力，对应的 Harness 层就可以删掉。已经发生的例子是第 6 章的交互模型，打断、插话这些曾经要靠外挂 harness 才能拼出的行为，如今被直接做进了模型内部。但「吃」永远不会完结，这里给了三个理由：训练以月计，模型等得起，业务等不起；模型无法内化真实业务中所有的约束与偏好，总有一层最新的边界需要外部逻辑兜底；每一代模型都会打开新的能力前沿，而前沿处恰恰是模型最做不稳的地方。所以 Harness 不会消失，它只是随着模型，不断向新的前沿迁移。这也是《苦涩的教训》在 Agent 时代的读法：通用方法终将胜出，但「终将」二字里的每一段路，都是 Harness 铺出来的。

飞轮转得最快的地方，是同时握住两端的人。Anthropic 用 Claude Code 做的，正是让自家模型和自家 harness 互相喂养、共同进化：模型知道 harness 会怎样调用它，harness 也清楚模型的边界在哪，两端的每一次改动都能立刻反馈给对方。还有一个关键实验数字，不换模型、只改 harness，任务准确率就从 52.8% 跳到 66.5%。这既说明 harness 今天的杠杆有多大，也提醒你它之所以有这么大杠杆，恰恰是因为模型还没走到那一步。至于护城河，这条飞轮本身就是这个时代最深的一条：真实业务、反馈数据与模型迭代咬合得越紧，别人越难从外部追上。

对两类从业者的建议取决于你站在飞轮的哪一端。如果你在造模型，护城河就是把这条飞轮转起来，让真实场景的反馈尽快回流到训练里。如果你在模型之上造应用，harness 是你短期最锋利的技术杠杆，但要清醒：模型每内化一层约束，就会顺手抹平一批只靠 harness 建立的优势。应用层真正长久的护城河往往在技术之外，独占的数据、稳固的渠道、用户的信任、网络效应，以及必须由人与 Agent 协作的物理世界场景等。把 harness 用来争取时间，把这段时间用来构筑技术之外的壁垒，才是稳妥的打法。

还留了一份「不会过时」的清单。不必焦虑手里的框架会不会过时，模型每几个月迭代一次，具体的 API、产品和榜单都会翻篇，但「看到什么、能做什么、如何验证做得对不对」这三个问题不会过时，它们跟某个具体模型的用法无关，描述的是一套基本方式：一个智能系统怎样与世界交互。掌握了它们，无论下一代模型带来什么新能力，你都知道该把它放进公式的哪个位置，也能一眼看出，它离吹散那两朵乌云还有多远。

把「屎山」读成「能力的负片」，是补充的一个视角。多级上下文压缩、失败数千次才熔断的重试、默认「不安全」的权限判断，这三段代码有一个共同点：它们跟业务需要无关，是模型的缺陷留下的化石。判断一段 harness 代码的寿命，可以用一个很实用的问句：它是因为「模型现在做不到」才存在，还是因为「业务或制度要求如此」才存在？属于前者的，会随模型迭代被删；属于后者的，模型再强也吃不掉，比如谁签字、谁负责、出事怎么回滚。

飞轮的因果链可以拆成六步走一遍，这段是补充的展开。用户提出一个真实难题，难题的难度决定了后面所有环节的含金量；生产 harness 承接它，暴露出模型在这一类任务上的失败点；外部逻辑兜底，压缩上下文、重试、默认拒绝危险操作，任务勉强完成；这一整条轨迹连同失败与补救被记录下来，成为训练信号；下一代模型把这一类失败内化，对应的 harness 层被删掉；模型的能力边界前移，于是更难的业务被接了进来，循环回到第一步。这个循环里同时产出两种资产，它们的性质完全相反：被删掉的 harness 代码是消耗品，它的价值随模型迭代归零；沉淀下来的真实轨迹与反馈是资本，它的价值随积累上升，且别人拿不到。「飞轮本身是最深的护城河」，护的其实就是后者。

「没有吃完的那一天」，三个理由背后各有一套机制。节奏差这条说的是，训练以月计，业务等不起，哪怕模型最终一定能学会，业务当下就得跑，所以永远存在一段「模型还没学会、业务已经在跑」的窗口，这段窗口里必须有人用外部逻辑顶上。私有约束与偏好无穷这条，与第二朵乌云的「大世界假设」是同一个道理，只要还要求贴合这家公司的规范、这个客户的口味，就总有一层属于特定组织的外部逻辑，而它不在任何训练语料里。新前沿不断出现这条，说的是模型越强，被推上去做的任务越难，而越难的任务恰好落在它最不稳的地方，于是删掉的层数多，新长出来的层数也不少。harness 的总量不一定缩小，但它的位置一直在向新前沿迁移，这正是「一层一层地吃」的确切含义。

52.8% 到 66.5% 是一个控制变量的实验，模型不动，只动 harness，所以提升只能归因于 harness。对这个数字给了双向解读：harness 今天的杠杆确实大，13.7 个百分点的绝对提升；可它之所以有这么大杠杆，恰恰因为模型还没走到那一步。落到工程上，harness 的收益属于一种时间窗口收益，模型每次迭代都会侵蚀一部分。所以「今天 harness 能加 10 分」不能读成「harness 永远值 10 分」，更不能读成「harness 可以当长期壁垒」。这段解读同样属于补充，本节只给了数字和方向性提醒。

「同时握住两端」为什么快，可以这样理解。如果模型团队和应用团队是两个组织，反馈回路的每一跳都要过需求、排期和口径对齐，周期以季度计；Anthropic 用 Claude Code 把两端放在同一家公司里，模型知道 harness 会怎样调用它，harness 也清楚模型的边界在哪，每一次改动都能立刻反馈给对方，回路缩短到天甚至小时级。本节没有写具体的数据指标，只说这是「互相喂养、共同进化」。

这一节和全书其他章节还有几处呼应。这里的「内化并删除」，第 1 章的 Harness 五要素就是它的账本，每一条要素（上下文管理、工具接口、约束、验证、纠正）都可能整块被模型吃进去；第 6 章的交互模型是已经发生过的实例，打断、插话从外挂 harness 变成模型内置；第 8 章讲的是「内化」在训练侧怎么做；第 9 章讲的是把业务里趟出来的坑变成信号这条链路的受控版本。

最后那三个问题为什么被被当作全书最值得带走的东西，因为它们的答案会随模型换代而改变，问题本身不会。第 1 章那条公式给了前两个问题的位置，上下文对应看到什么，工具对应能做什么；第 7–9 章给了第三个问题的位置，评估对应验证做得对不对。学到这个层次，新技术来了你不需要重新学一遍框架，只需要把它放进公式的对应格子里。

这一节也有几处措辞需要分清。「模型吃掉 Harness」说的是能力替换，某一层外部约束被内化进模型；「Harness 不再重要」说的是相对价值。恰恰因为剩下的层是模型最做不稳的地方，它才更值钱、更前沿，这里的结论是「Harness 不会消失，它只是随着模型，不断向新的前沿迁移」。「Harness 层被删掉」对应的是那部分因为模型暂时做不到而存在的代码，工作的重心随模型边界一起迁移，把「我写的代码被删了」读成「我的岗位没价值了」，是对这一节最常见的误读。「harness 是护城河」和「harness 是长期护城河」也要分层看：飞轮是护城河，真实业务加反馈数据加模型迭代的咬合；harness 代码只是短期杠杆。混淆这两者，就会得出「把 harness 做得足够好就安全了」的错误结论。「通用方法终将胜出」也不等于「专用方法现在没用」，这里的完整表述是「通用方法终将胜出，但‘终将’二字里的每一段路，都是 Harness 铺出来的」，时间维度上的必然和当下的工程现实是两件事，第 1 章 Harness 工程的意义就在这后半句里。

Harness 记录的是模型此刻的短板，模型的内化又来自 harness 趟过的坑；这个飞轮会一层一层吃掉 harness，但因为训练以月计、业务约束私有、新前沿不断出现，它永远吃不完。所以把 harness 当买时间的杠杆，把买到的时间用来筑技术之外的壁垒。

## 结语段：去造点什么

Agent 技术仍在飞速演进，任何一份材料都追不上所有变化。这份材料的成败标准：如果这份材料交给你的是一套能在技术浪潮里保持清醒的判断力，某个 API 的具体用法反倒是次要的，那它就完成了使命。这里全部内容与配套实验代码都是开源的，欢迎你去仓库里把实验亲手跑一遍、提 issue 和 PR。收尾的一句是：Agent 最迷人的地方，正在于它能通过写代码创造新的能力，甚至改进自己；走到这里，你已经握住了「创造」的原则。接下来，去造点什么吧。

这段结语其实在回答「读一本会过时的书有什么用」。技术书的具体 API 一定会过时，这里自己就说「模型每几个月迭代一次，具体的 API、产品和榜单都会翻篇」。这里要留下的因此是一套判断力，操作手册式的具体用法不在其中：知道一个新能力该放进公式的哪个位置、知道它离吹散两朵乌云还有多远。这与上一节末尾那三个问题是同一件事的两种说法。

「创造的原则」具体指什么，这一段是笔记的归纳，不是逐字引用。按本部分的逻辑，它至少包含三层：用 `Agent = LLM + 上下文 + 工具` 把任何新系统拆成可动手的三块；用「看到什么 / 能做什么 / 验证做得对不对」给任何系统做体检；认准模型与 harness 的飞轮，把自己的位置放在飞轮上而不是某段代码上。「你已经握住了‘创造’的原则」，指的正是这种可迁移的结构认识，而不是某个框架的用法。

结尾落在「写代码创造新能力，甚至改进自己」上，是因为这正是第 5 章「代码：通用 Agent 的元能力」（代码创造代码、Agent 自举）与第 9 章「持续进化」的合流，也是第二朵乌云里「RSI（递归自我进化）」的日常版本。把全书最后一句话留给「去造点什么」，等于把这条链的起点交回给读者：真实的难题由你做出来，飞轮才转得起来。此外还有一个可执行的读法，把配套实验跑一遍，价值不限于验证结论，你会亲手体验一次「模型做不稳的地方」。那些你在跑实验时想加的重试、想加的压缩、想加的权限判断，就是「Harness 铺出来的路」。

这里想让你带走的，说到底是一套能在技术浪潮里保持清醒的判断力，API 的具体用法过几个月就会翻篇；公式、三个问题与那条飞轮都在你手上了，接下来去造点什么。
