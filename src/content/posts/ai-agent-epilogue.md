## 回到公式

前面十章讨论的所有设计，都可以放回同一个结构：

```text
Agent = LLM + 上下文 + 工具
```

- 模型决定推理能力与行动选择的上限。
- 上下文决定模型在具体任务中能看到什么。
- 工具决定 Agent 能对环境做什么。
- Harness 把三者组织成可运行、可验证、可纠错的系统。

一个常见误区是把能力提升全部归因于模型升级。模型升级当然重要，但如果没有稳定的上下文组织、清晰的工具边界和可靠的验证机制，更强的模型仍然会在真实任务里失控。

## 两个待解问题

### 流式交互

当前多数 Agent 仍然是“请求—等待—响应”的轮次结构。真实环境是连续变化的：用户会打断，工具会异步返回，外部事件会在模型生成过程中发生。如何在不破坏消息格式和因果顺序的前提下，让 Agent 实时观察、打断和恢复，是一个开放的工程问题。

### 持续学习

Agent 可以从单次任务的成功与失败中修正行为，但如何把跨任务的经验稳定地保留下来，仍然没有统一答案。把经验写进参数、写进记忆、写进工具，还是写进 Harness 的策略，各自有不同的代价。

## 一条工程判断

模型与 Harness 不是上下游关系，而是一起演进的。模型每稳定内化一种能力，Harness 就可以少做一层补偿；但新的模型能力也会带来新的失败模式，需要新的约束和验证。

因此，设计 Agent 时不要只问“用哪个模型”，还要问：

1. 这个任务需要哪些观察与行动接口？
2. 哪些信息必须进入上下文，哪些应该留在外部存储？
3. 哪些错误可以由 Harness 检测和纠正？
4. 哪些能力应该交给模型，哪些应该写成确定性代码？

把这些问题回答清楚，比追逐某一种框架或某一次模型升级更可靠。
