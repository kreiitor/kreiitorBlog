## 编程抽象上移：从操作系统到模型上下文

模型再能推理，也得跑在什么东西上面。要开发好基于模型的应用，除了理解模型本身，还需要理解这类应用赖以运行的基础设施。这些基础设施分两个方面：一方面是模型本身，它怎样处理输入、生成输出，并根据上下文与环境交互；另一方面是模型的运行系统，参数和上下文状态存在哪里，计算怎样执行，多个加速器怎样协作，模型调用又怎样与工具程序衔接。这里讨论的就是支撑模型训练与推理的这套东西，也就是 AI Infra。

应用开发者为什么需要这些底层知识，这里给的类比是软件工程师的常识：大多数软件工程师不需要亲自开发操作系统、编译器和芯片，但仍然需要学习操作系统、编译原理和计算机体系结构，因为这些知识帮助人们理解程序所依赖的抽象，以及抽象背后的实现。抽象背后的实现是有代价的，申请一块内存、读取一个文件、调用一个函数，看起来只是简单的操作，却各有资源和时间上的代价；理解这些代价，才能解释程序为什么慢，以及怎样改进。基于模型开发应用是同一个道理，选择多大的模型、保留多长的上下文、允许多少条请求同时执行、把任务放在本地还是云端，每一个选择都会改变系统需要完成的工作。

理解 AI Infra 的一个自然入口，是操作系统、编译器和硬件的分工。这一领域的两大顶级会议 SOSP（操作系统原理研讨会）和 OSDI（操作系统设计与实现），名字里都包括「OS」。传统体系里的分工是有来由的：操作系统要支撑多种多样的应用，编译器和硬件则为事先未知的程序提供通用能力，所以以往做系统优化时，总要考虑可编程性与性能的权衡取舍。这个问题上态度明确，为了极致性能牺牲可编程性往往不是好的选择。

变化出现在 LLM 时代。如今 LLM 就是最重要的应用，在 AI 推理和训练系统中，从算子执行到分布式调度都可以为特定的模型和加速器架构优化，从而为跨层联合优化打开了新的空间。第一个核心判断是：编程抽象从操作系统到模型上下文的迁移，是计算机系统领域数十年来最重要的变化之一。一句话概括就是：模型成了 LLM 时代的操作系统，而 AI Infra 成了 LLM 时代的计算机体系结构。这也解释了这份材料的动机，《计算机体系结构：量化研究方法》是在体系结构领域的入门书，而目前 AI Infra 领域还缺少一本从硬件约束和模型架构出发、量化推导系统设计的书。

「上移」这个词要落到实处。编程抽象（programming abstraction）指的是程序员用来描述「我要算什么」的那一层接口：写 C 的时候是函数、指针和文件描述符，写分布式服务时是 RPC 和消息队列，写 LLM 应用时，最主要的接口变成了上下文（context）。往上下文里放什么，提示词、历史消息、检索回来的片段、工具的定义与返回值，模型就据此生成什么。应用的核心逻辑从「我怎么算」变成「我给它看什么、让它据此生成什么」，最关键的那一层抽象便从操作系统挪到了模型上下文。

优化空间为什么会跟着变？传统系统栈里，操作系统、编译器和硬件面对的是事先未知的程序，只能用通用机制换取适用范围：多级缓存对谁都一样，调度器并不知道下一个进程要干什么，代价就是可编程性和性能之间的权衡取舍，想更快往往要牺牲通用性。而一旦最重要的应用固定成 LLM 推理与训练，待优化的对象也就固定下来了，模型结构已知、算子已知、加速器架构已知，于是可以在算子层、运行时层、互联层为这一族特定负载做专门优化。数据库领域在关系模型出现、负载形态稳定之后，才敢为特定查询模式设计索引与执行计划；JIT 编译器也是在运行期看清热路径之后，才敢为它专门生成机器码。LLM 推理系统今天站在类似的位置：负载可见，所以可以专门化。

这一节对读者真正有用的地方，是它给了一种向下追责的思维。应用层的每个选择都会在底层变成具体的工作量：上下文留得越长，需要保存和反复读取的状态就越多；并发开得越大，每个人的等待时间就可能越长；把任务放本地还是放云端，决定了要走多少网络、花多少成本。你能不能在下笔写这几行配置时就知道下面要多干多少活，就是这一节想让你具备的能力。专门化本身也有代价，为特定模型和加速器做跨层优化意味着系统与模型互相耦合，模型换代或换芯片时优化可能失效；前言后文反复强调「条件改变以后应该如何重新选择」，配套材料要随书稿继续补充和修订，原因都在这里。这份材料关心的是模型应用跑在什么之上、代价从哪来，采用的也是同一套「抽象与代价」的眼光。

两个词最容易混。中文里都叫「上下文」，模型上下文（context）指的是一次推理的输入序列以及与之绑定的状态（如 KV 缓存），操作系统「上下文切换」里的上下文指的是 CPU 寄存器、页表等被保存和恢复的机器状态，标题里「从操作系统到模型上下文」说的是抽象层位置的迁移，跟这两类上下文之间的技术继承没有关系。另一组是 AI Infra 与 AI Agent：前者是支撑训练与推理的运行系统，就是「参数和上下文状态存在哪里，计算怎样执行，多个加速器怎样协作，以及模型调用怎样与工具程序衔接」，后者是基于模型搭出来的应用的架构与工程实践。这里对 AI Infra 的那四个问句可以直接当试纸，用来判断一个话题算不算 Infra 问题。

还有一处措辞要读准。「通用性」与「可编程性」是在「可编程性与性能的权衡取舍」这个语境里出现的，这里做出的选择是「为了极致性能牺牲可编程性往往不是好的选择」，意思是牺牲可编程性去换性能通常不划算，别读成通用性不重要。LLM 时代的跨层优化之所以有新空间，是因为待优化的对象已经确定为 LLM 推理与训练，系统可以直接为特定的模型和加速器架构优化，不必再为事先未知的程序保留全部通用性；专门化要付的耦合代价，就是前面说的那条。

## 从数量级估算到系统设计

在数据中心加速的场景里，无论面对模型推理、网络处理还是存储访问，都可以先做一遍数量级估算。这一步被拆成几个问句：一项任务要完成多少计算，读写多少数据？需要驻留的数据，显存装得下吗？存储和互联带宽能否满足数据供给需求？计算、读写和必须串行执行的步骤，分别给出了怎样的耗时下界？这套做法有出处，就是 Jeff Dean 所倡导的 back-of-the-envelope estimation，用纸笔做粗略估算。对它的评价是，几步计算往往就能帮助我们判断一个方向是否值得继续，以及应该先解决哪个问题。信封背面估算靠的是有约束的算术，用两三个乘法把「工作量」和「资源能力」放到同一量纲上比大小，产出通常是一句结论，比如「这套配置的瓶颈在显存容量，不在算力」。

还有一层更直接的原因。不少熟悉模型和框架的从业者，还没有形成对容量、带宽、算力和延迟的数量级直觉。把能力分成两种：面对一个设计，能够说出所用的技术，与能够判断它是否可行、性能大致能达到什么水平。前者是名词性知识，知道有 KV 缓存、有流水并行、有 FP8；后者是建模能力，知道这些名词各自对应多少字节、多少次通信、多少时间。名词性知识可以靠读文档获得，建模能力只能靠自己动手估，而且要清楚自己漏了什么。这里希望帮助读者建立的是后一种能力。

在数量级估算这件事上，AI 的表现也不比人可靠。用 GPT-6 Astra、Claude Fable 5.1 等模型帮忙估算模型推理或训练系统，或者新芯片架构的性能，这些模型能列出公式，算出看似精确的数字，却仍会漏掉决定结果的基本约束。把这些常见的漏算逐一列了出来，它们是全书反复提醒的清单：

- 有时只算权重读取，忘了注意力还要读取 KV 缓存；
- 有时估算了读取时间，却没有检查权重、KV 缓存和运行时工作区合计是否放得进显存；
- 有时按峰值算力推算速度，却没有检查存储带宽能否持续供给数据；
- 有时把工作量平均分给多张卡，却遗漏卡间通信；
- 还有时算出了很高的吞吐量，却没有考虑串行依赖与通信往返的延迟。

漏掉其中任何一项，结论都可能偏离几倍甚至几个数量级。把这份清单按「漏掉了哪个约束」重排一遍会看得更清楚（下表是整理的对照，括号里是这里的表述要点）：

| 这里描述的漏算 | 漏掉的约束类别 | 检查动作（补充） |
| --- | --- | --- |
| 只算权重读取，忘了注意力还要读取 KV 缓存 | 数据量算少了 | 把一次解码要读的字节列全：权重 + KV 缓存（+ 其他状态） |
| 估算了读取时间，却没检查合计是否放得进显存 | 容量约束 | 权重 + KV 缓存 + 运行时工作区的总和与显存容量比大小 |
| 按峰值算力推算速度，却没检查存储带宽能否持续供给 | 带宽约束 | 用「数据量 ÷ 带宽」和「计算量 ÷ 算力」两个时间取大者 |
| 把工作量平均分给多张卡，却遗漏卡间通信 | 通信约束 | 并行度提高后，通信量与时延一并纳入时间下界 |
| 算出很高吞吐，却没考虑串行依赖与通信往返延迟 | 依赖/延迟约束 | 找出无法重叠的串行段与往返次数，单独算它们的时间 |

「耗时下界」（lower bound）这个词要单独拎出来。下界的意思是，在最优情况下也不可能比这更快，算出的时间是一条不可逾越的底线，别把它当成预测值。它最大的用处是快速否掉方案：如果某个方案的乐观下界已经是业务允许延迟的好几倍，那它就不用再细调了。真实系统只会比下界更慢，两者的差距就是「离上限还有多远」的度量。

因此，贯穿这里的方法是**从约束推导设计**。完整流程可以记成五步：先明确任务与质量要求，比如延迟目标、成本上限、精度要求；再列出计算、存储、通信和依赖关系；然后逐条检查显存等存储资源的容量是否足够、存储和互联带宽是否满足计算的数据需求、哪些依赖造成的等待无法消除；据此讨论模型怎样分工、状态放在哪里、执行如何组织；末尾用测量校正前面的假设。这套流程先把已知的基本约束逐一纳入，用来排除明显不可能的方案，实际系统中的开销和变化则要继续用测量来校正。这一节的收尾是对估算态度的概括：「估算不必一开始就精确，但必须知道自己算进了什么，还有什么没有算进去。」这句话实际上要求你维护一张假设清单：每个数字是从哪来的、忽略了哪些开销、什么条件下结论会翻转。这也是为什么把「条件改变以后应该如何重新选择」当成一个正式环节。

四个指标的单位要分清。容量（capacity）是「能装多少」，单位是字节（GB）；带宽（bandwidth）是「每秒能搬多少」，单位是字节/秒（GB/s）；算力是「每秒能做多少次运算」，单位常用 TFLOP/s（注意斜杠：带「/s」的 TFLOP/s、GFLOP/s 是速率，也就是算力，不带「/s」的 TFLOPs、GFLOPs 是运算总量）；延迟（latency）是「一次操作要等多久」，单位是秒或毫秒。这里要求形成对容量、带宽、算力和延迟的数量级直觉，这四者必须分开形成，因为瓶颈落在哪一个上，解法完全不同：容量不够要减少驻留或换存储层次，带宽不够要减少搬移量或提高复用，算力不够要换更快的计算单元或合并算子，延迟太高则要减少串行依赖、增加并行或流水。

「平均分给多张卡」这条错误的关键，在于默认卡间通信免费。真实情况是卡越多，单卡工作量越小，但通信次数、通信量与同步等待往往变大，存在一个收益递减甚至反转的点。加卡就要加一笔通信账，这个习惯越早养成越好。和它相邻的还有吞吐与延迟的分野：算出很高的吞吐量，只说明单位时间能处理多少请求，不代表单个请求等得短，批处理与流水正是用延迟换吞吐的典型手段，判断可行性时这两个指标要分别对照业务要求。另外，估算和实测有出入并不算失败，差多少不重要，差在哪个约束上才重要；如果实测比估算慢很多，通常说明漏了一整项，比如通信、排队或内存搬运，很少是某个系数取错。数量级估算与精确建模属于两个阶段，前者用来判断方向、排优先级，后者是随后用测量校正结论的阶段，估算不必一开始就精确。

## 从算子加速到万卡互联

这一节用四个案例说明「约束是设计之源」：先找出什么不够用，再选择技术手段。四个案例的尺度逐级放大，分析方法相同。

**案例一：FPGA 加速搜索排序（2016 年）。** 目标是加速搜索排序所用的深度神经网络。瓶颈在于模型权重反复从片外内存搬进芯片，计算单元经常等数据。应对方式是把模型拆到多块 FPGA，让各部分权重留在各自的片上存储中，只通过高速网络传递中间结果。这种切分后来被称为「模型并行」。案例留下的习惯是：先按第一性原理算出硬件允许的上限，再看系统离上限还有多远；如果离上限只有很小的比例，就不值得再投入大工程。

**案例二：AKG 自动算子生成（2019 年）。** 这项工作把模型计算转换为适合昇腾 NPU 执行的程序，由编译器安排数据分块、存储和执行顺序。为了融合 softmax 算子，团队需要找到一种不需要把整行数据读两遍、也不把中间结果写回片外存储的算法。2018 年 NVIDIA 的在线 softmax 研究提供了这个思路：在一趟遍历里边读边维护 running max 与 running sum，最后一次性归一化。把这个技巧与分块、融合结合起来，就得到后来的 FlashAttention 的一条核心思路：减少注意力矩阵中间结果的显存读写。案例说明，算子融合的关键往往不是写出更复杂的公式，而是重新安排数据的读写顺序。

**案例三：Unified Bus 统一互联（2020 年起）。** 这一步把问题扩大到上万处理器的协作：怎样让成千上万个处理器高效地共同完成一项计算？当时常见的训练规模只有八卡，万卡互联看起来离需求很远。推动立项的证据是趋势：2019 年有人把 AI 算力需求画成散点图，发现需求增长远快于单芯片能力提升；2020 年 GPT-3 的发表又强化了这一判断。由于互联架构的研究和实现周期很长，等需求完全显现再开始往往来不及。阶段性结果是 UB 已用于昇腾 910C 和 950 系统，基于 UB 的 NPU 训练集群架构支持万卡以上规模。案例留下的方法是：系统设计要同时看眼前的负载和正在变化的条件，并把趋势、资源与代价讲清楚，才能说服别人提前投入。

**案例四：实时语音交互（2023 年起）。** 这个案例把尺度从集群拉回端到端应用。实时语音要回答两个问题：用户说完一句话要等多久才能听到回答，一通电话持续半小时的服务成本是多少。2024 年，团队在 GPT-4o 发布之前推出实时语音交互，后来与基于 GPT-4o 的实时语音 API 比较，运行成本约为调用它的百分之一。2023 年底第一个语音电话演示的延迟高达 5 秒；团队把整条交互管线拆开，先估算模型一次推理需要多少计算、读取多少数据，再逐段优化网络传输、数据库访问等，延迟从 5 秒降到 2.5 秒、1 秒，后来做到约 500—600 毫秒。案例说明，应用开发与基础设施之间有直接联系：延迟相差几倍，产品体验可能完全不同；成本相差一个数量级，能够支持的商业模式也会改变。

四个案例的尺度逐级放大，分析方法完全同构，可以归纳为下表：

| 案例 | 系统尺度 | 瓶颈（约束） | 应对 |
| --- | --- | --- | --- |
| FPGA 加速搜索排序（2016 年） | 单芯片 → 多块 FPGA | 模型权重反复从片外内存搬进芯片，限制计算速度 | 把模型拆到多块 FPGA，各部分权重留在各自片上存储，只通过高速网络传中间结果（模型并行） |
| AKG 自动算子生成（2019 年） | 单个算子 / 编译层 | 中间结果的存储和读写开销 | 借鉴在线 softmax 研究实现算子融合；把在线归约与分块、融合结合 |
| UB 统一互联（2020 年起） | 万卡级加速器协作 | 单芯片能力提升赶不上 AI 算力需求增长 | 推动面向上万张卡的高性能互联；UB 已用于昇腾 910C 和 950 系统 |
| 实时语音交互（2023 年起） | 端到端交互管线 | 端到端延迟（首个演示 5 秒）与服务成本 | 拆开交互管线，先估模型一次推理的计算量与读取量，再优化网络传输、数据库访问等；延迟降至约 500—600 毫秒 |

「约束是设计之源」这句话要连起来读：先找出什么不够用，再挑技术。片外内存带宽不够，就把权重留在片上；中间结果读写太多，就把算子融合；单芯片算力增长跟不上，就把规模做大、把互联做好；端到端延迟太长，就把管线拆开逐段算。四段工作里技术手段完全不同，「先定位瓶颈、再选手段」的顺序是一样的。

「模型并行」的直觉值得补一句。单块芯片的片外内存带宽是硬上限，权重又必须每步都读；如果不改变「权重必须从片外读进来」这件事，算得再快也没用。把模型切分到多块 FPGA 上，让各自的权重常驻在各自片上存储里，就只需要在卡间传递中间结果，搬移量从「整个模型的权重」降到「一层或几层之间的中间结果」。这正是全书反复出现的「提高复用、减少搬移」思路的最早形态。

「先算出物理上限，再看系统离上限还有多远」这个习惯值得单独记下来，它有两个好处：给出乐观下界，让你知道还有多少空间可挖，如果离上限只有 20%，就不值得再投入大工程；给出否证依据，如果某个方案号称突破了上限，那一定是漏算了某项约束。后面分析加速器、算子、超节点、网络时，都会先给资源的上限，再讨论实现能到哪。

在线 softmax 与 FlashAttention 的关系要说清楚，不要拔高。在线归约（online normalizer）解决的是一个数值计算问题：算 softmax 需要先知道所有元素的指数和，甚至需要减去最大值以保证数值稳定，但如果不允许把整行数据读两遍、或者不允许把中间结果写回片外存储，就要在一趟遍历里边读边维护 running max 与 running sum，最后再一次性归一化。把这个技巧和分块（tiling）、融合（fusion）结合起来，就能避免把注意力矩阵的中间结果写回显存再读回来。两件事的关系是思路上相通，不应读成「AKG 实现了 FlashAttention」；从在线 softmax 走到完整的 FlashAttention，还需要把后续与 $V$ 的加权求和也纳入在线更新，并围绕完整注意力安排片内存储和数据搬移。

万卡互联那一段真正值得学的是决策方法，而不只是结论。把两种东西分得很清楚：八张卡能够完成任务是实际经验，更大的计算需求会推动更大规模协作是对未来的判断。做系统设计的难点在于，硬件与互联架构的建设周期很长，所以必须提前按趋势下注；而下注要能说服别人，就得把趋势、资源和代价讲清楚。趋势是算力需求的增速快于单芯片能力提升，2019 年的散点图呈现了这一点；资源是建设集群与互联需要什么；代价是投入与风险。

实时语音那一段，是「估算—改进—再估算」闭环最完整的一个例子。关键数是 2023 年底 5 秒 → 2.5 秒 → 1 秒 → 约 500—600 毫秒，成本约为调用基于 GPT-4o 的实时语音 API 的百分之一。这里没有给出各个管线段落的耗时明细，所以不要替它编一份分段账。能学到的方法是：先拆管线，再对每一段做估算，然后逐段优化，而且优化对象不限于模型，还包括网络传输、数据库访问等。这段经历被放在方法论小节里，是因为它演示了延迟差几倍、成本差一个数量级会直接改变产品与商业可行性；基础设施本身也因此成了决定应用能否成立的条件。

这一节里出现的术语只有「模型并行」一个，用来描述把模型拆到多块 FPGA 的想法，这里并没有展开介绍其他并行方式。想系统了解多种并行方式，要到这里第 6 章「超节点」的 6.2「六种并行方式」。不要把这一节的「拆模型」理解成模型并行概念的完整定义。在线 softmax 与 FlashAttention 也不是同一件事：前者是一个数值计算技巧，不预先取到全部元素也能完成归一化，便于一趟完成、便于融合；后者是一整套注意力算法与显存管理方案。AKG 那一段属于编译器/算子层，处理的是数据分块、存储与执行顺序；UB 那一段属于系统互联层，处理的是上万处理器协作。这些工作跨越了不同的尺度，相通的问题是数据搬移开销，读的时候要抓住共性，别把它们当成互不相干的两件事。

## 我希望这份材料讲清楚什么

上一节说的是应用与基础设施的联系，这种联系在模型研发内部同样存在。优秀的基础模型团队里，越来越常见一种跨越分工的工作方式，可以概括为三句话：最懂 Infra 的人做算法，最懂算法的人做数据，最懂数据的人做 Infra。这句话表达的是一种相互理解的深度，并分别解释了原因：算法设计者知道硬件的容量、带宽和通信限制，才能在模型结构中利用这些条件；数据工作者理解模型怎样学习，才能判断哪些样本和训练任务最有价值；Infra 工程师了解数据的组织、长度和使用过程，才能把系统资源真正用在有效的训练与推理上。这三句不要读成转岗建议，它真正的意思是，只在自己那一层做最优化，很容易做出全局上的次优解。

近年来的模型设计中已经出现了这种跨层配合，这里举的例子是 DeepSeek V4 和 V4.1。V4 在模型架构中就充分考虑了 Infra 的效率，将局部窗口、上下文压缩和稀疏选择结合起来，减少长上下文需要保存的状态和反复读取的数据，这里的结论是显存容量、存储带宽与计算之间的约束，直接影响了模型怎样表示和使用上下文。V4.1 Flash 更进一步，用非对称的因果编码器—解码器（Causal Encoder-Decoder，CED）架构重新划分理解与生成的职责，针对 Agent 输入多、输出相对少的负载重新安排计算投入。往下一层拆开看（以下解读是补充，本节只给了架构要点与结论）：把长上下文当成本项，两笔大开销就显出来了，一是要保存的状态占用的容量，二是反复读取的数据占用的带宽，于是局部窗口把注意力限制在最近的一段以降低状态增长、上下文压缩把历史压成更短的表示、稀疏选择只挑一部分参与计算，这三处都是模型结构上的改动，动因却是显存容量和存储带宽这样的硬件约束。V4.1 Flash 的例子说明，系统效率的要求能够推动模型架构本身的创新。

建立这种跨层理解有两个方向：看到一种模型结构时，能想到它要求加速器做哪些工作；看到一种硬件能力时，能判断怎样改变模型与执行方式，才能真正把它用起来。

贯穿这些分析的一条线索，是数据搬移。这里描述的场景是，计算单元需要取得权重和中间结果，多个加速器需要交换各自算出的数据，远端服务需要接收输入并返回结果。我们看到的表象是模型在生成答案，底层发生的却是一次次读取、计算、保存和交接。影响执行效率的因素有四个：数据放在哪里、重复使用多少次、需要经过哪些接口、后续工作是否必须等待。数据搬移之所以值得当主线，是因为在一个计算单元里，做一次乘加很便宜，把参与计算的数据搬到计算单元旁边很贵，而层层存储的容量越大离得越远、越远就越慢。系统优化大多归结为两件事：让每个搬来的字节被复用更多次，或者让必须搬的字节更少。

用了「厕所」这个类比：可以把处理器和存储器想象成一座大楼，把数据访问点想象成厕所。如果所有厕所都集中在一楼，楼上的人每次使用都要下楼，距离和拥堵会限制整座大楼的效率；如果每层都建厕所，访问距离缩短，却要占用更多面积，还要安排管道、维护和容量。逐项对应到硬件上，楼层是存储层次的位置，厕所数量是容量，下楼的距离与拥堵是长距离访问的延迟与带宽占用，每层建厕所占的面积、铺的管道和维护是芯片面积与成本、布线和管理复杂度（比如一致性、容量分配）。寄存器、缓存、片上缓冲像「每层都建厕所」，容量小但近；显存、主存像「一楼的大厕所」，容量大但远。

计算机体系结构也在做同样的取舍：把容量较大的存储放在较远位置，把高频使用的数据放进寄存器、缓存或片上缓冲，再通过总线和互联安排数据的移动。AI 加速器的许多设计，都是在回答同一个问题：哪些数据值得放得更近，应该准备多少，何时搬入，何时释放。从顺序纸带式的计算模型，到冯·诺依曼计算机的可寻址存储器，再到 CPU 的多级缓存、GPU 的共享内存和 AI 加速器的片上缓冲，体系结构一直在改变数据与计算单元之间的距离，真正延续下来的问题是，如何在通用性、容量、带宽、延迟和硬件成本之间安排数据路径。进一步指出，Transformer 同时产生权重、激活、KV 状态和专家输入等不同访问模式，单靠一套自动缓存策略很难覆盖全部情况，因此需要分块、融合、流水和专用互联共同参与。

于是这里反复追问五个问题：搬什么、搬多少、搬几次、经过哪里、谁必须等它。明了这五个问题的适用范围，从芯片上的存储层次，到超节点（这里括注：通过高带宽互联紧密协作的一组加速器）和数据中心网络，再到终端、边缘与云（端边云）之间的任务分工，都能帮助我们找到需要计算的量。以一次矩阵乘法走一遍这五问（以下是补充的举例，本节没有这个例子）：搬什么对应权重和激活，搬多少是它们的字节数，搬几次是一批 token 里每个权重被用了几次，经过哪里是从显存经片上缓冲到计算单元的哪条路径、要不要跨卡跨节点，谁必须等它是下一层算子必须等这一层的输出、跨卡还要等通信完成。这样一套问下来，「需要计算的量」就自然浮现了。

这里同时列出三组权衡，可以直接当口诀记：保留数据可以减少重复计算，却会占用容量；扩大并行规模可以分担工作，却会增加通信；减少传输可能需要更多本地计算，也可能改变结果质量。这三条是后面各章「为什么不能一味优化某一项」的统一解释。第三组权衡的后半句尤其要注意，这里承认有些系统改动会影响结果本身（质量），所以系统设计与质量要求不能分开谈。

要回答这五个问题，就需要把每个量都算出来，这也是这里采用「量化分析与系统设计」作为副标题的原因。《计算机体系结构：量化研究方法》为这种分析方式提供了很好的示范，这里希望把前面所说的估算习惯落实到每一层设计中：从模型的工作量出发，对照资源约束，解释为什么选择一种执行方式，以及条件改变以后应该如何重新选择。读者从这里拿到的是一套能随条件变化重新推导的方法，参数表反而只是副产品。

四类数据的访问特征要分清。 Transformer「同时产生」权重、激活、KV 状态和专家输入这几类不同访问模式，正因如此「单靠一套自动缓存策略很难覆盖全部情况」。展开一点看（这是笔记对「访问模式」的解释）：权重是只读且会被反复使用的，复用度高、容量需求大；激活是算出来就被下一层读走、多数情况下不必长期保留；KV 状态随上下文长度持续增长，既要保存又要反复读取；专家输入取决于路由结果，其访问是动态、不规则的。四类数据的最优放置位置不同，这正是需要分块、融合、流水和专用互联共同参与的原因。

超节点、数据中心网络、端边云这三个词在这里是并列出现的三个尺度：超节点是「通过高带宽互联紧密协作的一组加速器」，数据中心网络是更大范围的集群互联，端边云是终端、边缘与云之间的任务分工。说这五个问题「都能帮助我们找到需要计算的量」，也就是说换尺度不换问题。超节点不要理解成一种机柜形态，这里的界定是功能性的（一组加速器靠高带宽互联紧密协作）。另外，「把容量较大的存储放在较远位置」讲的是取舍，判断标准是「值不值得放得更近」，代价是面积、成本与复杂度，不是越远越好。

还有一组容易混的：五问是「搬什么、搬多少、搬几次、经过哪里、谁必须等它」，用于找工作量；四因素是「数据放在哪里、重复使用多少次、需要经过哪些接口、后续工作是否必须等待」，用于判断什么影响执行效率。两者内容相近，但五问是要你自己逐条去问的清单，四因素是这里直接给出的判断依据，把它们分别用在不同段落里。

三个部分的划分方式本身就是一种解题顺序：先算账，要干多少活；再看家底，有什么资源、怎么被用起来；末尾排班，把请求、状态、训练过程组织起来。只关心某个具体问题也可以直接跳，比如「为什么我的服务扩了卡反而更慢」可以去第 9 章找，但前面的建议是回头看前面的章节为它提供了哪些基础，因为答案通常在第 6 章（并行与通信）和第 7 章（网络拥塞与交接）里。把「章→问题」清单当索引用，是这一节最实用的读法，这里自己给了用法：「你可以先在这里找到自己关心的问题，再看看前面的章节为它提供了哪些基础。」这里因此更像一张有依赖关系的问题图，每章回答一个问题，而回答它又需要前面若干章的结论当输入，不必从头顺读。

三个部分之间是单向依赖加回环修正的关系（这层解读是笔记根据图注后半句所作的）：前面的部分为后面提供分析依据和资源基础，阅读顺序由此确定；但真实系统是迭代的，服务与部署阶段会拿到新的实测数据（任务质量、完成时间、成本），据此回头修改模型与资源选择。这里那段「最初只考虑权重容量，后来还要计算上下文状态……回头检查自己在前面作出的判断」，讲的是增量式建模的教学设计。它提示读者，这里每个结论都带着自己的条件，读到后面发现条件变了，正确动作是回去看第一个结论在什么条件下成立、现在为什么不成立，记住第二个结论解决不了问题，这跟第二节「必须知道自己算进了什么、还有什么没有算进去」是同一条原则。读到任何一章时，还可以用前言给的五个问题去问这一章的方案，如果某一问得不到答案，说明还没抓住这一章的关键约束。

「全书结构」与「如何阅读这份材料」的分工不同：这一节回答内容由什么组成，包括部分划分、各章要回答的问题、部分之间的依赖顺序；下一节回答该怎么读，包括三类读者的路线、先自己估算的习惯、练习与配套材料。两节不要混着记。图 0-1 这个编号也说明了它的位置：前言是第 0 章性质的部分，所以插图编号从 0 开头，第 1 章起按章编号。第 1 章「初识 AI Infra」属于「模型与负载」，任务是「认识系统全景，并用几个关键数字估算一次模型执行」，也就是把前言第二节的估算方法第一次落到实处；它不是可以跳过的导论，推荐的阅读路线正是从第 1—3 章开始。

## 如何阅读这份材料

如果希望从头建立系统认识，前面的建议是先读第 1—3 章，学会估算一次执行，弄清模型与负载提出了哪些需求，再依次阅读后面两部分；不同背景的读者，可以在这个共同基础上选择自己的重点。下面按读者背景给出三条路线：模型与应用开发者可以重点阅读第 8、9 章的推理服务，以及第 11、12 章的任务环境和部署，遇到容量、算子或通信问题时，再回到第 4—7 章追踪原因；系统与网络工程师可以重点阅读第 5—7 章的执行与加速器协作，再看第 9、10 章，检查这些机制如何影响分布式推理和训练；芯片与体系结构工程师可以重点阅读第 4—7 章，并结合后续章节的任务算例，检查自己熟悉的硬件指标如何转化为实际的服务能力。整理成一张速查表就是这样（章节号与「重点／回头追踪」的区分都取自本节）：

| 读者背景 | 重点阅读 | 遇到问题时回看 | 这条路线想让你获得什么（笔记归纳） |
| --- | --- | --- | --- |
| 模型与应用开发者 | 第 8、9 章（推理服务）；第 11、12 章（任务环境和部署） | 容量、算子或通信问题 → 第 4—7 章 | 把自己的服务配置与服务成本，对应到底层容量、算子与通信上 |
| 系统与网络工程师 | 第 5—7 章（执行与加速器协作） | 再看第 9、10 章，检查这些机制如何影响分布式推理和训练 | 把熟悉的执行/互联机制，接到真实推理与训练负载上 |
| 芯片与体系结构工程师 | 第 4—7 章，并结合后续章节的任务算例 | 未另给回看路径，要求结合后续章节的任务算例 | 把熟悉的硬件指标，换算成实际的服务能力 |

三条路线有一个共同前提，就是那句「不同背景的读者，也可以在这一共同基础上选择自己的重点」，这个基础就是第 1—3 章。第 1—3 章是所有人都要读的，之后才分岔。

对所有人通用的一条建议是：无论选择哪条阅读路径，都尤其建议你在看答案之前，先自己估一下。具体做法是「拿一张纸，写下数据量、处理能力和必须等待的步骤，通常就能发现一些值得追问的地方」。这三栏其实正是前言第二节估算框架的压缩版：数据量对应「读写多少数据」，处理能力对应「计算与带宽能提供多少」，必须等待的步骤对应「必须串行执行的步骤给出的耗时下界」。你只要把这三栏写出来，就已经在做从约束推导设计了。如果自己的结果与这里不同，给出的排查顺序是先检查双方是否使用了相同的条件，条件相同，就继续寻找漏算或重复计算的工作。这个次序不能颠倒，先怀疑条件（模型规模、精度、硬件规格、批次大小是否一致），条件对齐之后才去查自己漏算了一整项（例如通信），或者把某一项算了两遍。这里评价这种来回检查往往比直接记住一个结论更有收获。

关于练习，这里的练习分为核心与延伸，核心练习帮助完成本章的主要推导，延伸练习可按兴趣和项目需要选择。核心练习属于必须过一遍的部分，延伸练习适合做实际项目时回头挑；前言没有给出具体练习编号，具体练习在各章末，这里末尾的索引栏目也会说明前言部分没有练习。

仓库里有三类材料，建议与这里配合使用。实验与计算按章节组织，提供运行说明、输入条件和结果记录，配套计算工具可以帮助你复算这里的数字，或者换一组条件观察结论怎样变化。论文与技术资料是相关论文、开源软件和官方技术文档的索引与来源记录，便于沿着这里的问题继续阅读，并核对具体论据。芯片与模型参数表汇集调研中整理的硬件规格与模型配置，包括算力、存储容量与带宽、互联能力，以及模型层数、维度、混合专家模型的专家配置和上下文状态等估算所需的信息，参数表与来源、计算工具配合使用，帮助你检查数字的适用条件，再把它们代入自己的分析。三类材料配上一条工作流就顺了：参数表提供输入，计算工具做复算，实验做校验，论文与技术资料用来核对论据、沿着问题继续读。

使用方式上，可以从仓库首页进入实验、量化计算和参考资料目录，按各项目的说明运行。需要特定加速器的实验会注明环境和加速器条件，没有相应加速器时，也可以先分析已有记录，再改变输入重新计算。这条提示很实用，复现不一定要有同样的硬件，改条件重算同样有效。这里提醒，模型和硬件不断更新，这些材料也会随书稿继续补充和修订，所以仓库里的参数表应当被当作带来源与适用条件的输入，而不是长期有效的常量，用之前要检查数字的适用条件。

这里收尾的建议是，读这份材料时也可以带着自己的模型、机器和业务问题，把材料里的输入替换掉，看看结论是否改变，再决定下一步值得测什么；这些例子能够成为读者分析自己问题的起点。

核心练习与延伸练习的定位不同：前者是完成本章主要推导所必需的，后者按兴趣与项目需要选择，不要把延伸练习当成「更难的核心练习」。实验与计算工具也不是一类东西：实验是按章节组织、提供运行说明、输入条件和结果记录的实操，用来验证机制；计算工具用来复算给出的数字或换一组条件观察结论怎样变化，做的是参数敏感性分析。「回看第 4—7 章」对模型与应用开发者来说同样不是可选项，这里的表述是「遇到容量、算子或通信问题时，再回到第 4—7 章追踪原因」，也就是说第 4—7 章是排查工具书，不属于背景阅读；同理，系统与网络工程师要「再看第 9、10 章」，是为了检查机制对真实负载的影响。另外，「带着自己的问题读」不等于随意跳读，这里仍然要求在共同基础（第 1—3 章）之上选择重点，跳读的前提是先会估算一次执行。

## 前置知识

这里面向有编程经验、希望理解模型执行与系统设计的读者，下面几项基础会帮助你跟上这里的推导和实验。编程与工具方面，能读懂和修改简单的 Python 程序，熟悉命令行和基本的依赖安装；基础练习从手算、小脚本和已有实验记录开始，使用特定加速器的实验会另行说明条件。数学方面，理解向量、矩阵乘法和基本代数，会做单位换算；平均值与概率的基本知识有助于分析负载和等待，导数与梯度的直觉有助于阅读训练章节。计算机系统方面，了解进程、内存、文件与网络通信的基本用途；模型结构、并行方式和专用硬件机制会随问题逐步介绍，不需要提前学。三项基础各自的用途可以按服务对象来记（下表的分工是笔记归纳，三项基础本身照这里）：

| 基础 | 这里要求 | 它在这里服务于什么 |
| --- | --- | --- |
| 编程与工具 | 读懂并修改简单 Python 程序；熟悉命令行和基本依赖安装 | 跑基础练习（手算、小脚本、已有实验记录）与配套实验 |
| 数学 | 向量、矩阵乘法和基本代数；会做单位换算；平均值与概率；导数与梯度的直觉 | 矩阵乘法与基本代数提供估算的算术功；平均值与概率用于分析负载与等待；导数与梯度用于读训练章节 |
| 计算机系统 | 了解进程、内存、文件与网络通信的基本用途 | 理解执行与搬移机制；模型结构、并行方式、专用硬件机制随问题逐步介绍 |

三项里最容易被低估的是「会做单位换算」。数量级估算的绝大多数错误都发生在换算这一步：字节和比特、十进制前缀与二进制前缀、每秒与每次、毫秒与秒。把它列为数学基础的一项，说明它算不上细枝末节，本身就是估算能力的一部分；结合上一节的排查建议「先检查双方是否使用了相同的条件」，单位与口径不一致正是最常见的一类条件不同。矩阵乘法与基本代数的用途不一样，它用来理解模型的计算量构成，单位换算则是把不同来源的数字放进同一个量纲里比较。

这里还给了一类「经验型」的起点：如果你已经调用过模型 API，或者在自己的机器上运行过一个模型，可以把这些经验带进这里的算例，并提出了三个问题：为什么长上下文变慢，为什么增加并发后每个人等得更久，为什么换了加速器却没有得到预期的加速？这里评价这些都是很好的阅读起点，但没有指明它们将在哪一章得到解答，读者可以带着这三问往后读，每读完一部分就试着回答一次。「增加并发后每个人等得更久」正是排队效应的典型表现，分析负载时只看平均到达率不够，还要看分布的波动与排队行为，这也是把「平均值与概率」与「负载和等待」直接挂钩的原因。

关于学习方式，这里的态度是不必等到熟悉所有层次才开始阅读。做系统研究和工程实践时，自己一直需要围绕具体问题，学习相邻层次的知识；遇到陌生的概念，可以先抓住它要解决的问题，再回来看实现细节。这与全书从约束推导设计的顺序一致，也解释了为什么模型结构、并行方式和专用硬件机制会随问题逐步介绍，这里并不要求你先补完一门课。读完之后的目标可以拆成四步动作：画出执行过程，算出几个关键数字，指出最需要验证的假设，并根据观察修改自己的选择。第三步就是前言第二节说的「知道自己算进了什么、还有什么没有算进去」，第四步是用测量校正。这里收尾时强调，你的结论可以与这里不同，能够说明差异来自哪里，本身就是理解系统的表现。

「会做单位换算」与「会算矩阵乘法」都属数学基础，用途却不同：矩阵乘法与基本代数用于理解模型的计算量构成，单位换算用于把不同来源的数字放进同一个量纲里比较，后者是估算的关键一步。「熟悉命令行」的要求只是熟悉命令行和基本的依赖安装，目的是能按说明跑起练习与实验，并不要求读者会部署生产系统。计算机系统基础与模型、并行、专用硬件知识也要分开：前者是前置要求，指的是进程、内存、文件与网络通信的基本用途；后者说「会随问题逐步介绍」，属于这里内容，不要因为不熟悉 NPU 或并行策略而推迟开始阅读。
