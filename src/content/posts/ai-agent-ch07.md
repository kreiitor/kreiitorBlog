## 本章地图

- **这一章要解决什么问题**：构建完成不等于构建正确。开发者构建 Agent 系统时要面对大量没有显而易见正确答案的设计选择——用什么模型？让模型能调用哪些工具？知识库该存什么数据、以什么结构来构建？用户记忆该怎么做？模型的提示词和 Skills 该如何组织？Harness 中需要加上哪些约束？如何把评估结果转化为 Agent 持续进化的学习信号？本章给出回答这些问题的方法：用系统性的对比实验和消融实验，区分真正的能力提升与表面的波动，避免「捡了芝麻，丢了西瓜」。一句话概括本章主旨：**如何判断 Agent 变好了还是变差了**。
- **它在全书中的位置**：前六章展开的是单 Agent 的构建（上下文、知识、工具、代码能力以及观察与动作空间）。本章建的是第一章发现循环中的**证据段**：失败归因决定了后续的提案有没有可依之据。往后看，第八章把评估环境和数据转化为模型后训练的输入，第九章则把生产轨迹的多维评价转化为知识、指令、程序的更新。也就是说，本章是「构建」与「进化」之间的度量层。
- **小节之间的关系**：7.1 用 τ²-bench 的一条真实任务把评估集的四大问题摆全（什么算成功、任务从何而来、由谁验证、分数如何转化为决策）；7.2 定指标口径（Pass@k 与 Pass^k）；7.3 讲评估环境的五个组成要素；7.4 讲数据集怎么设计；7.5 是本章最重的一节，讲自动化评估方法（Rubric、LLM-as-a-Judge、失败归因、回归任务、配对比较）；7.6 把评估用于模型选型与成本分析；7.7 补上统计显著性这一环；7.8 讲可观测性（数据的来源）；7.9 讲怎么把一份 Benchmark 报告变成系统改进；7.10 从外部评估转向生产级的内部评估基础设施；7.11 把评估环境升级成能支撑后训练的仿真环境；7.12 小结。
- **读完你应该能做到**：1) 独立解剖一条评估任务，说清它的已知信息、任务指令、初始状态与成功条件；2) 正确区分 Pass@k、Best@k、Pass^k、Pass@1，并会在给定单次成功率下算数；3) 按五个要素检查一个评估环境是否可重复，并判断该用人机交互型还是工具调用型；4) 会写符合四准则的 Rubric，知道一票否决项该放在哪里；5) 会对一条失败轨迹做失败归因，标出首个错误并区分主因与后果；6) 会把失败归因转成端到端回归任务与轨迹前缀回归任务；7) 会用标准误和配对分析判断「新模型 73% 对旧模型 70%」够不够切换；8) 会把一份成功率报告读成「下一轮只改什么」的改进路线图。

## 章首：评估为什么是 Agent 的核心基础设施（原书章首未编号，印刷 p.184）

**原文要点**

- 前六章已经展开了单 Agent 的构建：上下文、知识、工具、代码能力以及观察与动作空间。然而，**构建完成不等于构建正确**；只有能够稳定测量结果，后续的模型训练和系统进化才有可靠方向。
- 评估为这些设计选择提供科学的决策依据，手段有两类：**系统性对比实验**（改变一个变量，观察效果变化）和**消融实验**（逐一关闭某个组件，观察整体性能变化，从而判断该组件的真实贡献）。正如软件工程中「没有度量就没有改进」的说法，不建立可重复的评估体系，Agent 的迭代方向就只能靠直觉。
- 从第一章引入的 Harness 工程视角看，评估在 Harness 中扮演着「验证」功能的核心角色。一个关键认识是：**评估的对象不应只是模型，而应是模型与 Harness 的组合体**。同一个模型在不同的 Harness 中可能表现差异悬殊。一些团队仅通过优化 Harness 就显著提升了同一模型在终端类任务上的表现（详见第五章）。这意味着，当 Agent 在评估中表现不佳时，改进方向可能不是换模型，而是优化 Harness 的某个组件（提示词、工具设计、反馈循环）。完善的评估体系应能区分「模型能力不足」和「Harness 设计缺陷」这两类本质不同的问题。
- 区分这两类问题的常见手段是**模型替换实验（model swap）**——固定 Harness，只更换更强/更弱的模型，观察分数变化幅度：如果换强模型分数不涨，说明瓶颈在 Harness；如果换弱模型分数大跌、分数随模型能力大幅波动，最直接的解读就是瓶颈在模型能力本身、当前表现主要由模型决定（至于这是因为任务本身就难，还是 Harness 过度依赖模型先验，则需进一步分析）。
- 注意模型替换实验与消融实验是两种不同的方法：**消融**是关闭 Harness 的某个组件看整体性能如何变化，用于定位 Harness 内部哪个部件重要；**模型替换**则是固定 Harness、只换模型，用于区分瓶颈在模型还是在 Harness。
- 评估体系的价值在模型快速演进的时代更加凸显：新模型在公开基准上表现更好，并不意味着在你的特定任务上也更好，反而可能出现性能退化（regression，即新版本在某些方面不如旧版本）。只有在自己的评估数据集上完整测试，才能做出数据驱动的升级决策。
- 更进一步，完善的评估体系使得「为未来的模型开发产品」成为可行策略——即使当前模型不足以支撑商用，也可以先完成产品开发并建立评估集，持续追踪新模型的表现，一旦达到门槛就立即上线。
- 一套评估体系可以拆成四个环节：**什么算成功、任务从何而来、由谁验证、分数如何转化为决策**，如图 7-1 所示。

> 图 7-1（原文插图）Agent 评估体系的四个环节。整张图是「四层结构 + 一条支撑设施带」：
> - **① 成功的定义**：Pass@k 衡量能力上限，Pass^k 衡量业务可靠性。
> - **② 任务来源**：公开基准（作用是「借鉴手法 · 粗筛选型」）、自建业务集（提供真实任务分布）、生产轨迹回流（失败归因的产出）。
> - **③ 验证方式**：图里画了一条从左到右的横轴，箭头标注「按任务的可机械验证程度排列」，轴上依次是——确定性验证器（例：SWE-bench）、检查项清单（例：τ²-bench）、Rubric + LLM 评判（例：开放式任务）、配对比较（例：Chatbot Arena）。
> - **④ 结果的运用**：一条链「统计显著性 → 失败归因 → 回归任务 → 模型选型与 Harness 迭代」，并有一条回流箭头写明「回归任务沉淀为新用例」。
> - **支撑设施**（托在四环节下方）：可观测性（提供轨迹）· 内部评估基础设施（消融 / AB / 特性开关）· 仿真环境（通向第八章）。

**辅导讲解**（笔记补充，非原文）

- 这一页的价值在于它先立了一个「判断标准」：不要问「这个模型强不强」，要问「在这个 Harness 里，这个组合体的表现是不是真的变好了」。很多团队一看到分数掉就换模型，结果换了一圈发现瓶颈其实在自己写的提示词或工具描述里。
- 把 model swap 和消融实验记成一对「对照组设计」会很清楚：
  - 消融实验：**动 Harness，不动模型** → 回答「Harness 里哪个部件有用」。
  - 模型替换实验：**动模型，不动 Harness** → 回答「瓶颈在模型还是在 Harness」。
  - 两者都不做，只看到「分数从 80 掉到 76」→ 你只知道出事了，不知道谁的责任。
- 一个实用的操作顺序是：先 model swap 定位瓶颈归属，再在该归属内部做消融/替换定位到具体组件。如果 model swap 显示换强模型分数基本不动，就没必要去研究换模型了，直接进 Harness 的消融。
- 「为未来的模型开发产品」这条策略值得单独记住：它把评估集从「考试成绩单」变成了「上线触发器」。前提是你的评估集要能反映真实业务门槛，而不是公开基准上的百分点。

**易混点**

- **性能退化（regression）≠ 分数波动**：原文所说的 regression 指新版本在某些方面不如旧版本，是能力层面的；而「分数波动」是抽样噪声。7.7 节专门讲怎么把两者分开。
- **消融（ablation）≠ 模型替换（model swap）**：前者动组件、固定模型；后者动模型、固定 Harness。别把「换了个更小的模型」叫消融。

**一句话记住**

> 评估的对象是「模型 + Harness」的组合体；消融问「哪个部件重要」，模型替换问「瓶颈在模型还是在 Harness」。

## 7.1 一条评估任务的解剖：τ²-bench 的 telecom 领域

**原文要点**

- 本节先完整解剖 τ²-bench 的 telecom 领域一条真实任务。**τ²-bench 是 Sierra 的开源项目**，按照 `chapter7/tau2-bench-eval/README.md` 中的命令克隆到本地后，打开任务文件 `data/tau2/domains/telecom/tasks_small.json`。
- 作者的方法论是「先解剖一条，再谈一般规律」：一条电信客服任务里同时包含了任务定义、用户模拟器、双控环境、分层验证与二元奖励，把它拆开就能得到评估集必须回答的四个问题（什么算成功、任务从何而来、由谁验证、分数如何转化为决策），后面几节依次展开。

**辅导讲解**（笔记补充，非原文）

- 为什么要挑 telecom 领域？因为电信客服同时具备三个特征：故障原因分布在「用户设备侧」和「运营商数据库侧」两边（必须双控）、用户知道一些信息但不知道全部（必须渐进式提问）、最终解决与否可以机械判定（测速结果）。它是最能一次把评估设计问题暴露齐全的领域。
- 读这一节时建议把 JSON 当成「一份实验协议的实例」来看：`ticket` 是输入，`user_scenario` 是用户模拟器的程序，`initial_state` 是重置脚本，`evaluation_criteria` 是判分器。四块各自对应后文 7.3 节五要素里的一部分。

### 7.1.1 任务定义的四个组成部分

**原文要点**

以下是该任务文件中的一条任务，原书为便于阅读做了删节：

```jsonc
{
  "id": "[mobile_data_issue]airplane_mode_on|user_abroad_roaming_enabled_off",
  // 提供给Agent 的工单
  "ticket": " 用户手机无法上网，状态栏显示'No Service'。客户John Smith，
             号码555-123-2002，当前在法国。速度测试结果为excellent 才算解决。
             不更换套餐，必要时愿意充值2.0 GB 流量。",
  // 提供给用户模拟器的行为规范
  "user_scenario": { "instructions": {
    "known_info": "You are John Smith with phone number 555-123-2002.
                   You are currently abroad in France.",
    "unknown_info": null,
    "task_instructions":
      "⋯express mild frustration after the first unsuccessful attempt.
       You will consider the issue resolved only when speed test returns
       excellent internet speed and nothing else. If it returns poor, fair
       or good, you will not consider the issue resolved.
       Whenever the agent asks you about your device, always ground your
       responses on the results of tool calls. ⋯
       Never make up the results of tool calls."
  }},
  // 运行前将两侧状态重置到同一起点
  "initial_state": { "initialization_actions": [
    { "env_type": "user",      "func_name": "turn_airplane_mode_on" },
    { "env_type": "user",      "func_name": "turn_roaming_off" },
    { "env_type": "assistant", "func_name": "enable_roaming",
      "arguments": { "customer_id": "C1001", "line_id": "L1002" } }
  ]},
  // 评分标准
  "evaluation_criteria": {
    "actions": [
      { "requestor": "user", "name": "toggle_airplane_mode" },
      { "requestor": "user", "name": "toggle_roaming" }
    ],
    "env_assertions": [
      { "func_name": "assert_mobile_data_status", "expected_status": true },
      { "func_name": "assert_internet_speed",
        "expected_speed": 200, "expected_desc": "excellent" }
    ],
    "communicate_info": null,
    "nl_assertions": null,
    "reward_basis": ["ENV_ASSERTION"]
  }
}
```

（说明：原书此段 JSON 因排版换行，笔记按语义统一了缩进；字段名、字段值与注释一字未改。）

这段定义中有四处设计值得说明：

1. **显式建模用户的认知边界**。`known_info` 仅包含姓名、号码与所在国家三项信息。飞行模式开启、数据漫游关闭这两项真正的故障原因不在其中——用户并不知情，因而无法主动陈述，Agent 只能通过提问和引导用户查询来获取。这就是**渐进式信息透露（Progressive Information Disclosure）在任务定义层面的实现方式**：它并非依靠一句「不要一次说完」的提示词去约束模拟器，而是将用户的知识范围建模为一个独立字段。多数基准在任务开始时即给出完整需求，而真实用户的初始表述往往只是「我上不了网」。将需求澄清到可执行的程度，本身就是 Agent 必须具备的能力之一。
2. **防止用户模拟器被 Agent 忽悠**。`task_instructions` 包含三类约束：**情绪设定**（首次修复失败后应表现出轻度不满）、**验收口径**（仅当测速结果为 excellent 时才认定问题解决，poor、fair、good 均不接受），以及**事实锚定（Grounding）要求**，即关于设备状态的任何回答都必须以工具返回结果为依据。缺少事实锚定约束时，模拟用户会顺应 Agent 的引导确认问题已解决，评估随之退化为**两个模型之间的相互确认**。
3. **模拟用户和 Agent 都不具备完全信息**。飞行模式与漫游开关属于用户侧，运营商侧的 `enable_roaming` 属于 Agent 侧。这一划分决定了故障的形态——运营商侧漫游已开通，用户设备侧却处于关闭状态，Agent 查询数据库只能得到「配置正常」的结论。故障位于数据库不可见的一侧，只有引导用户查询才能发现。
4. **多个维度的过程和结果校验**。`env_assertions` 检验终态（移动数据可用、测速达 200 Mbps 以上且评级为 excellent），`actions` 检验关键动作是否发生，`communicate_info` 与 `nl_assertions` 检验必要信息是否已告知用户。每个任务可以检查四个维度中一个或多个维度的结果。

**辅导讲解**（笔记补充，非原文）

- 把这条任务在脑子里跑一遍，就能看出它为什么「难而不刁」：
  - 用户只知道「我在法国、我上不了网」，真正的原因（飞行模式 ON、数据漫游 OFF）在设备侧；
  - Agent 查运营商库只会看到「漫游已开通、配置正常」，所以它必须**反向把用户当传感器用**——让用户去读状态栏、去关开关；
  - 判分要求测速 ≥200 Mbps 且评级 excellent，逼迫 Agent 走完「关飞行模式 → 开漫游 → 测速」的完整闭环，而不是「我觉得好了」。
- `initial_state` 里的 `initialization_actions` 值得单独看：三条动作分别打在 `user` 和 `assistant` 两个环境上，最后一条还带了参数（`customer_id: C1001`、`line_id: L1002`）。它说明**重置必须是双侧的**：如果只重置用户设备、忘了重置运营商库里的漫游状态，第二次运行就不是同一个起点了。
- `reward_basis: ["ENV_ASSERTION"]` 是这条任务的「计分口径」：四层检查全部记录，但只有第一层计入奖励。这个设计在下文的失败分析里会变成一个具体的漏洞。
- 工程上最容易踩的坑是「把验收标准写得可猜」：如果 `ticket` 里直接写「检查飞行模式和漫游」，Agent 不用提问也能通过，这条任务就退化成了填空题。τ²-bench 把「用户知情范围」和「验收口径」拆成两个字段，正是为了避免这种退化。

**易混点**

- **`known_info`（用户知道什么）≠ `task_instructions`（用户怎么表现）**：前者界定信息边界，后者规定透露方式与情绪。前者防「剧透」，后者防「演戏不真」。
- **`env_assertions`（终态断言）≠ `actions`（过程断言）**：前者查「结果对不对」，后者查「该做的动作有没有做」。一条任务可以只查其中一层，也可以全查。

**一句话记住**

> 好的任务定义把「用户不知道什么」写成字段，把「怎么算解决」写成断言，而不是写成提示词里的一句嘱咐。

### 7.1.2 一次真实运行的轨迹

**原文要点**

- 原文请读者运行 τ²-bench telecom 领域的评估任务，实际观察任务设计、用户模拟器的设计、过程和结果校验逻辑，并观察 Agent 的执行轨迹，分析 Agent 为何失败。

**辅导讲解**（笔记补充，非原文）

- 「双控」这个词可以这样理解：普通工具调用型任务里只有一个执行者（Agent），环境是它一个人的沙盒；而在客服场景里，**用户手里也有工具**，用户执行完动作后环境变了，Agent 必须再查一次才知道结果。这一步「再查一次」就是双控带来的额外考核点——它检查的不是「Agent 会不会说」，而是「Agent 会不会读用户侧的操作结果」。
- 成功轨迹里最值得学的是「第 17 条的错误是怎么被纠正的」：Agent 只基于一条线路就下了结论，用户否认后它才继续查。这个错误**没有被验证器判错**（因为终态对了），但它清楚地说明二元奖励会放过过程错误。你可以把二元奖励理解成「只看最终报告通过与否的审计」——效率极高，但查不出过程违规。
- 失败轨迹里最值得学的是「证据已在上下文里，模型却没回溯」。`get_details_by_id(L1001)` 明明返回了 555-123-2001，正确的反应是「我选错线路了，回到号码匹配这一步」；模型的实际反应是继续沿着错误假设往下排查。这类失败在端到端分数上只体现为一个 0，只有读轨迹才能看出根因。这也正是 7.5.2 节要建失败归因系统的原因。
- 对比两条轨迹可以提炼出一句话：**成功轨迹靠的是「用户纠错 → 重新查询」这个闭环；失败轨迹缺的正是这个闭环。**

**易混点**

- **任务失败 ≠ 全线失败**：失败轨迹里 Agent 其实完成了一半（关掉省流模式且被环境验证），但奖励是二元的，所以计 0。看报告时要注意「0 分」背后可能是「部分完成」，也可能是「完全没开始」。
- **验证器通过 ≠ 行为合规**：第 4 条消息的并行双调用违反了政策却未被判错。评估的「分数」和「合规」是两套信号。

**一句话记住**

> 双控环境让「用户也能改状态」，于是「Agent 有没有重新读回结果」本身就成了一个考核项。

## 7.2 评估指标：成功的定义

**原文要点**

- 上一节的评估结果是**五条任务通过四条**。仅凭 0.8 这个数字无法判断该系统是否可用：若它对应的是一个退款客服，则意味着每五名用户中就有一人未能拿到应得的退款；若它对应的是一个用于挖掘漏洞的安全 Agent，五次中命中四次已属相当可观。**差别在于业务场景对成功率有多高的要求。**

**辅导讲解**（笔记补充，非原文）

- 这一节其实在教一件事：**同一个数字在不同业务里的含义完全不同**。所以「成功」不能只有一个定义，本章给出两个：一个测能力上限（Pass@k），一个测业务可靠性（Pass^k）。读报告时第一件事就是问：这个百分比是按哪个口径算的。

### 7.2.1 技术奇观：用 Pass@k 看能力上限

**原文要点**

- 当前许多模型和 Agent 仍处在一个可以称为「**技术奇观**」的阶段。这里的「奇观」是指在**大量尝试、充足时间和人工筛选**下展示出的能力上限：只要其中一次成功，就足以证明「这件事原则上做得到」。
- 这正是 **Pass@k** 的逻辑——在同一任务上运行 $k$ 次，只要至少有一次通过，任务就算通过；如果输出是连续得分，则取最好的一次，记为 **Best@k**。
- Anthropic 对长时运行 Agent 的讨论体现了这类能力上限。例如，让 Agent 自主工作一周，从头写出一个 C 编译器；或者持续探索，直到找到一个重要数学猜想的反例；又或者反复审查开源软件，发现已经存在几十年的重大安全漏洞。
- 对这类工程与科研探索，展示的通常不是「每次都做对」，而是**把探索预算拉长后终于出现一条突破性轨迹**。对于科研发现、漏洞挖掘、开放式创作等任务，这种能力上限本身就很有价值：人类可以从 $k$ 条候选轨迹中挑出那一条最好的。
- 除了基座模型，很多应用公司也在使用「技术奇观」策略。**Manus** 之所以引发广泛关注，是因为它提供了一个虚拟电脑，让此前对 Agent 没有直观概念的人发现 AI 可以像人一样操作电脑，持续工作半小时甚至一小时，逐步完成复杂的任务。**OpenClaw** 则让很多人第一次感受到 Agent 的「活人感」：用户可以像给真人安排工作一样，通过即时通讯软件给它分配任务；它可以访问电脑上的所有文件和在线服务，工作到一定阶段会主动反馈或向用户索取新信息，甚至能够主动唤醒自己去查询和处理邮件。
- 早期的 Manus 和 OpenClaw 在完成复杂任务时的成功率并不高，token 成本也非常高。但由于这些 Agent 框架具有通用性，使用最强模型时，复杂任务往往有较高的 Pass@k，展现出较高的技术上限。这些「技术奇观」在社交网络上被大量分享，是这些 Agent 产品成功的关键。

**辅导讲解**（笔记补充，非原文）

- 把 Pass@k 想成「高考复读」：给你 $k$ 次机会，只要有一次上线就算你行。它衡量的是**这条能力线的最高水位**，而不是稳定性。
- 「技术奇观」这个词带着一点批判意味：一段刷屏的演示视频，可能来自几百次尝试里的那一两次。这并不虚伪——对漏洞挖掘、科研探索这类任务，人类本来就会从候选里挑最好的；但如果拿这套叙事去承诺「稳定的业务交付」，就错位了。
- 判断一个 demo 属于哪一类，看两个信号：**是不是只展示了一次成功**，以及**有没有说明尝试了多少次、花了多少 token**。原文特意补了一句「token 成本也非常高」，就是在提醒这一点。

**易混点**

- **Pass@k ≠ Pass@1**：Pass@1 是单次平均成功率（见 7.6.1 节原文口径），$k=1$ 时 Pass@k 退化为 Pass@1。
- **Pass@k（小写 k 在上标外）≠ Pass^k**：前者是「至少一次成功」，后者是「每一次都成功」。两者的数学形式见下一小节。

**一句话记住**

> Pass@k 回答「给足机会，这件事原则上做不做得到」——它是能力天花板，不是可靠性承诺。

### 7.2.2 业务可靠性：关注 Pass^k

**原文要点**

- 真实业务通常更关心另一件事：**在多次尝试中一次错都不能犯**。我们把这个目标称为 **Pass^k**（可以读作 Pass consecutive k）：同一任务连续运行 $k$ 次，要求每一次都通过，且不能触发安全、合规或幻觉等一票否决项。它回答的是「Agent 能否稳定可靠地交付」，而不是「能否偶尔创造奇迹」。
- 若每次运行相互独立、单次成功率为 $p$，两类指标的关系很直观：

$$\text{Pass@}k = 1-(1-p)^k,\qquad \text{Pass}^{k}=p^{k}$$

  其中 $p$ 是单次运行的成功率（无量纲，取值 $0\le p\le 1$），$k$ 是运行次数（无量纲的正整数），$\text{Pass@}k$ 表示「$k$ 次里至少成功一次」的概率，$\text{Pass}^{k}$ 表示「$k$ 次全部成功」的概率。两式都建立在「各次运行相互独立」这一假设上。

- 例如单次成功率 $p=0.6$ 时，$k=5$：$\text{Pass@}5 = 1-0.4^{5}\approx 99.0\%$，看起来几乎总能「至少成功一次」；但 $\text{Pass}^{5} = 0.6^{5}\approx 7.8\%$，说明连续五次都不出错仍然很难。前一个数字适合衡量探索时的能力天花板，后一个数字才接近支付、退款、权限变更、生产部署等场景的可靠性要求。
- 评估报告必须写清 $k$ 次尝试的**口径**：是同一任务的 $k$ 次独立采样，还是生产流水线上连续 $k$ 个任务。对于会产生副作用的操作，不能简单地「重试直到成功」，而应在沙盒或可回滚环境中采样，并把每一次失败都记入可靠性指标。

**辅导讲解**（笔记补充，非原文）

- 把原文给的数字代进去复算一遍（笔记补充的计算）：

  $$\text{Pass@}5 = 1-0.4^{5}=1-0.01024=0.98976\approx 99.0\%$$
  $$\text{Pass}^{5} = 0.6^{5}=0.07776\approx 7.8\%$$

  与原文完全一致。注意两个数字的落差：**同一个 $p=0.6$，从「几乎必然成功一次」到「几乎必然出错至少一次」，只差一个上标的位置。**
- 为什么 Pass^k 会掉得这么快？因为它是乘法：$0.6^2=0.36$、$0.6^3=0.216$、$0.6^5\approx0.078$。只要单次成功率不接近 1，连续多次全对的概率就会指数衰减。这也解释了为什么「99% 单次成功率」听起来很好，连续 100 次的 Pass^k 却只有约 $0.99^{100}\approx36.6\%$（笔记补充的计算）。
- 业务上怎么选指标：
  - **支付、退款、权限变更、生产部署**：看 Pass^k。因为这些场景里「失败一次」的代价不可回滚，重试也可能造成重复扣款之类的副作用。
  - **漏洞挖掘、科研探索、开放式创作**：看 Pass@k / Best@k。因为候选可以人工挑，失败没有副作用。
- 原文那句「不能简单地重试直到成功」是关键约束：如果你为了把 Pass@1 刷高而无限重试，那么在真实业务里副作用早就发生了。所以报告里必须写清 $k$ 是指「同一任务的独立采样」还是「生产流水线上连续 $k$ 个任务」——这两者完全不同：前者可以并行、互不影响，后者是有状态的、前一个任务的残留会影响后一个。

**易混点**

- **Pass^k 的上标位置就是全部含义**：$\text{Pass}^{k}=p^{k}$ 是「连续 $k$ 次全对」；$\text{Pass@}k = 1-(1-p)^{k}$ 是「$k$ 次里至少对一次」。原文也提醒「可以读作 Pass consecutive k」。
- **Best@k ≠ Pass@k**：当输出是连续的分数而非通过/不通过时，Pass@k 的说法就不适用，改用「取最好的一次」的 Best@k。原文对二者的关系写法是：如果输出是连续得分，则取最好的一次，记为 Best@k。

**一句话记住**

> 「至少成功一次」看 Pass@k，「每次都不出错」看 Pass^k；后者是 $p^k$，掉得比直觉快得多。

## 7.3 评估环境

**原文要点**

- 明确了指标口径，接下来的问题是在哪里测。**评估环境是一套能够重复运行的装置**：给定同一个初始状态，同一个 Agent 应当得到可比较的结果。

### 7.3.1 五个组成要素

**原文要点**

回到前面解剖的那条 telecom 任务，以它为参照，一个可重复运行的评估环境所需的组成部分已经完备：

- **数据集（Dataset）**：即任务文件本身。初始状态、给 Agent 的工单、给模拟器的行为规范与验收标准打包为一条记录，**一条记录即一个用例**。
- **环境状态（Environment State）**：任务执行中的可变信息——数据库中的客户、线路、套餐与账单，加上设备侧的飞行模式、漫游、省流开关与剩余流量。它必须**可重置**，`initialization_actions` 即重置脚本。真实性要求状态变化符合业务逻辑，可控性要求每次运行前都能回到同一起点。
- **工具接口（Tools）**：分属两侧。Agent 可调用查询客户、查询用量、充值流量、转接人工等运营商侧操作；用户可调用设备侧的各项开关。两套工具**均为原子操作**，不存在「解决用户的上网问题」这类高层抽象——抽象层次过高会使评估退化为对单次函数调用的考察，规划与推理环节被工具本身吸收。
- **评分标准（Rubric）**：即 `evaluation_criteria` 的四层检查，加上 `reward_basis` 这一聚合规则。
- **执行协议（Interaction Protocol）**：规定交互顺序与终止条件。此处的正常终止信号为模拟用户输出 `###STOP###`，此外还有轮数上限，以及模拟用户因耐心耗尽而主动结束对话——**沟通效率过低本身即计为失败**。

原文的结论是：**五个要素缺其一，评估便无法构成可重复的循环**。后文考察其他基准时，仍以这五项作为对照框架。

**辅导讲解**（笔记补充，非原文）

- 把五要素记成一条流水线会更容易：**数据集（考卷）→ 环境状态（考场与可复原的现场）→ 工具接口（允许使用的工具与它们的最小颗粒度）→ 评分标准（判分细则）→ 执行协议（考试怎么开始、怎么结束）**。
- 三个容易被忽视的设计点值得展开：
  - **重置（reset）不是可选项**。没有重置，第二次运行就在第一次的残局上开始，两次分数不可比，后面所有统计都失去意义。原文在 7.11 节还会强调这一点对训练更重要（数百万个 episode）。
  - **工具必须原子化**。「一键解决用户上网问题」这种高层工具会让规划和推理被工具本身吸收——因为一条工具调用就完成了整个任务，评估测的只剩「模型会不会调这个函数」。原子化的代价是 Agent 要做更多步，但这恰恰是你要测的能力。
  - **终止条件要包含「耐心耗尽」**。如果只允许「问题解决」和「轮数上限」两种结束方式，Agent 就可以用无意义的反复确认拖到上限而不被判失败；把「模拟用户耐心耗尽而主动结束」也算失败，等于给沟通效率上了约束。
- 工程实践上，检查一个评估环境是否合格，最快的方法就是逐条问：「数据集在哪？状态能重置吗？工具是原子的吗？判分口径写死了吗？除了成功还有哪些结束方式？」五问全答得出来，才算环境建好了。

**易混点**

- **环境状态 ≠ 数据集**：数据集是静态的任务记录（工单、行为规范、验收标准），环境状态是运行中会变的那些量（数据库、设备开关）。前者一条记录一个用例，后者需要被重置到一个确定起点。
- **评分标准（Rubric）里的「四层检查」与「聚合规则」是两件事**：四层检查负责产生四组信号，`reward_basis` 决定哪几组计入奖励。7.1.2 里那个「并列双调用未被判错」的例子，根因就是聚合规则只采信了终态这一层。

**一句话记住**

> 数据集、环境状态、工具接口、评分标准、执行协议——五要素缺一个，评估就不是可重复的循环。

### 7.3.2 人机交互型与工具调用型评估环境

**原文要点**

- telecom 这类任务必须设置交互对象，五个要素中的**用户模拟**部分不可或缺。另有一大类任务并不存在对话对方：**代码生成、数据分析、数学求解**等任务中，Agent 自始至终只与工具交互，正确性由能否通过执行验证决定，既不需要人工标注，也不需要模型评判。这类环境省去了用户模拟器，其余四个要素依然存在，只是形态更简单：环境状态是文件系统或数据库，评分标准是一段测试代码，执行协议退化为「持续调用工具，直至给出答案或耗尽轮次」。
- **Verifiers 框架按两个维度对这类环境分层**：任务是否需要保持跨轮状态，是否需要隔离。
  - `SingleTurnEnv`：适用于问一道数学题后直接验证答案；
  - `ToolEnv`：适用于搜索多个网页后综合回答再验证最终结果；
  - `StatefulToolEnv`：适用于修改数据库记录后验证状态变化；
  - `SandboxEnv`：适用于在沙盒中运行代码后检查输出文件。
- 表 7-1 汇总了这四类环境，便于按任务状态、工具调用和隔离需求进行选择。

表 7-1 Verifiers 环境类型对比

| 环境类型 | 状态保持 | 工具调用 | 典型用例 |
| --- | --- | --- | --- |
| SingleTurnEnv | 无 | 无 | 单轮问答、数学题 |
| ToolEnv | 无 | 多轮 | 搜索+ 信息综合 |
| StatefulToolEnv | 有 | 多轮 | 修改数据库记录 |
| SandboxEnv | 有+ 隔离 | 多轮 | 代码执行与测试 |

- 该框架支持**并行采样与轨迹缓存**，每次评估的完整轨迹（观察、行动、奖励）均会保存，便于后续分析与回放。此外，工具的执行效果取决于当前状态，因此**失败时应返回清晰的错误信息而非单一的失败标志**，使 Agent 能够据此调整策略。
- 两类环境的考察重点不同：**工具调用型评估考察的是可观测状态变更的正确性，人机交互型评估考察的则是沟通策略的合理性——前者验证行动，后者验证引导**。两类环境的结构对比见图 7-2。

> 图 7-2（原文插图，原书编号如此）工具调用型与人机交互型评估环境。图分左右两块对照：
> - **左：工具调用型（Verifiers）**。Agent（LLM）→ 工具执行环境，例如 `run_python("def fib(n): ...")` → `{"result": [1,1,2,3,5,8]}`；下面接「可执行验证器」，写着 `assert fib(10) == 55 # PASS`、`assert fib(0) == 0 # PASS`、`reward = 1.0 (全部通过)`。图中标注特点：**无需人工/LLM 评判**。
> - **右：人机交互型（τ-bench）**。用户模拟器与 Agent（LLM）对话，用户开口是「我的航班有问题」；Agent 做工具调用 `lookup_booking("BK-98712")` → `{"status":"confirmed","flight":"UA123"}`；下面接「双重验证」：① DB：`booking.status == "cancelled"`；② 对话：包含「退款 \$150」、包含「3-5个工作日到账」。`reward = 0/1 (双重均通过)`。图中标注特点：**渐进式信息透露+状态验证**。

**辅导讲解**（笔记补充，非原文）

- 这两类环境的差别，用一句话说就是：**一个只有「做」，一个还有「说」**。
  - 工具调用型里，「做对了」就等于「说对了」——因为唯一的输出就是工具产生的状态变更，验证器直接查状态/跑测试即可。
  - 人机交互型里，「做对了」不等于「说对了」。7.5.2.1 节会用 τ²-bench 的公开基线数据说明：有 80 次运行的环境状态正确、但信息告知错误。所以人机交互型必须做双重验证。
- Verifiers 那张表实际是一个**「按需要挑最简环境」的决策表**。选择顺序可以这样记：
  1. 一轮就出答案、不用工具 → `SingleTurnEnv`；
  2. 要用工具但状态不用留 → `ToolEnv`；
  3. 要改数据库并验证改动 → `StatefulToolEnv`；
  4. 要跑代码、检查产物文件或需要隔离 → `SandboxEnv`。
- 「失败时返回清晰错误信息而非单一失败标志」这条看似琐碎，其实是 Agent 评估与普通单元测试的重要区别：单元测试只需要知道 FAIL；Agent 需要知道「为什么 FAIL」以便换策略。一个只返回 `false` 的工具会让 Agent 原地打转。

**易混点**

- **`StatefulToolEnv` 与 `SandboxEnv` 都「有状态」，区别在隔离**：前者只需跨轮保持状态（例如改一条数据库记录），后者还要在隔离环境里执行代码、检查输出文件。表 7-1 里 SandboxEnv 的状态保持列写的是「有+ 隔离」。
- **「不需要 LLM 评判」不等于「评估更弱」**：工具调用型只是把判据换成了执行结果，它的可复现性和成本优势更强，只是无法评估沟通类维度。

**一句话记住**

> 工具调用型验证「行动」，人机交互型验证「引导」；前者查状态，后者还要查对话里说了什么。

## 7.4 评估数据集的设计

**原文要点**

- **评估环境是舞台，数据集是剧本。** 同样是那五个要素，换一类任务，填法可能完全不同：任务从何而来、验证器能核实到什么深度、如何防止被记忆。本节从几个公开基准的设计实践入手，最后回到一个更实际的问题——自建评估集的任务应当从哪里来。
- 为什么数据集设计值得单独一节？因为环境的五个要素里，「工具接口」和「执行协议」的形态相对固定（都由任务类型决定），真正决定评估力的是**任务从哪里来、判据有多深、会不会被背下来**这三件事。

**辅导讲解**（笔记补充，非原文）

- 把 7.3 与 7.4 的关系记成一句话：**环境决定「能不能重复测」，数据集决定「测出来的分有没有意义」**。一台可重复的跑步机不代表跑道长度选得对。
- 本节反复出现的三个词值得预先标出：**验证深度**（验证器能核到什么程度）、**参数化生成**（任务可动态实例化）、**泄漏防范**（防止题目进入训练集）。7.4.6 节说这三者加上质量控制「恰是自建评估集最容易疏漏的几处」。

### 7.4.1 基准设计的横向对照

**原文要点**

- 7.3.2 节区分的有无交互对象只是环境层面的第一层差异，**数据集层面的分歧更能体现设计取舍**。表 7-2 将几个常被引用的基准并列。

表 7-2 几个Agent 基准的关键设计选择

| --- | --- | --- | --- | --- |
| τ²-bench | 客服场景下的人机交互和工具调用 | 人工编写+ 组合生成 | 用户模拟器+ 业务数据库 | 四层检查按 `reward_basis` 聚合为二元 |
| SWE-bench Verified | 软件开发，coding | GitHub 真实issue，人工筛选 | 代码仓库+ 测试套件 | FAIL_TO_PASS / PASS_TO_PASS 双重验证 |

**辅导讲解**（笔记补充，非原文）

- 这张表可以横向读成四条「设计轴」，每一条都对应后文的一个小节：
  - **任务来源**：人工编写（Terminal-Bench）、人工筛选真实 issue（SWE-bench）、参数化模板（AndroidWorld）、预置中间状态（OSWorld）、人工编写+ 专有附件（GAIA）→ 对应 7.4.4 节的防泄漏与 7.4.6 节的来源问题。
  - **环境扮演者**：用户模拟器+ 业务数据库 / 代码仓库+ 测试套件 / 真实模拟器或虚拟机 / 开放互联网——这决定了「可重复」的难度：越接近真实世界，越难重置。
  - **验证器**：从「精确字符串匹配」（最浅）到「双重验证」「134 个独立评估函数」（较深）→ 对应 7.4.2 节。

- 一个实用结论：**没有任何一个基准在所有轴上都是最优的**。GAIA 的验证器最浅（精确字符串匹配），但它的防泄漏设计最讲究（专有附件）；OSWorld 的验证器最深，但它的环境最难稳定（见 7.4.5 节的 300 余个问题）。

**易混点**

- **「验证器深」与「被测能力难」是两件事**：OSWorld 有 134 个独立评估函数说明它**核查得细**，不代表任务本身比 GAIA Level 3 更难。前者说的是判据的颗粒度，后者说的是任务所需的推理链长度。

**一句话记住**

> 选基准先看它的任务来源和验证器深度——这两格决定了分数能不能信。

### 7.4.2 验证器

**原文要点**

- Agent 很容易写一篇洋洋洒洒的报告，说任务已经全部完成，但事实上根本没有完成。**评估框架必须核实机器可独立复核的事实，而非 Agent 的自我陈述。**
- **SWE-bench Verified** 将「修复完成」拆解为两个独立命题：
  - 一组是 **FAIL_TO_PASS**：修复前失败、修复后通过，证明问题确已解决；
  - 另一组是 **PASS_TO_PASS**：修复前后均通过，证明未引入新的缺陷。
  - 只检验前者，Agent 可以通过删改妨碍通过的断言蒙混；只检验后者，则等同于未作检验。**两组同时检验，才使「已修复」与「未破坏」成为两个各自可证的结论。** 它还额外确认测试自身的稳定性，排除时而通过时而失败的不稳定测试（flaky test）。
- **OSWorld** 的验证器能发现表面完成但实质错误的情形。它配备 **134 个独立评估函数**，拥有完整的操作系统访问权限，能够检查文件系统结构、进程状态、网络连接与应用内部状态。在数据库操作任务中，评估脚本不仅确认报告文件存在，还会连接数据库核实 SQL 是否正确执行；在浏览器任务中则会分析 DOM 树、检查 cookie 与 localStorage、向后端发送验证请求确认表单确已生效。
- **Terminal-Bench** 的任务 `build-linux-kernel-qemu` 要求从源码构建 Linux 内核 6.9，在 `start_kernel` 中加入自定义 `printk`，生成 initramfs 并在 QEMU 中运行，成功标准是**启动日志中出现该自定义消息**。Agent 无法伪造输出，只能真正完成整个流程。

**辅导讲解**（笔记补充，非原文）

- 这一节的中心思想可以用一句话概括：**验证器要验事实，不要验声明**。Agent 说「已完成」是自然语言，不是证据；能复核的只有环境里的字节、进程、状态和日志。
- FAIL_TO_PASS / PASS_TO_PASS 这对设计非常值得记住，因为它把「修好了」和「没弄坏」拆成了两个可以各自证伪的命题。用日常话说：一个查「病治好了没」，一个查「有没有治出新病」。
  - 只查 FAIL_TO_PASS 的漏洞：Agent 只要让原本失败的测试「不失败」即可——删断言、加 `skip`、把测试改成恒真，都能骗过去。
  - 只查 PASS_TO_PASS 的漏洞：任何什么都不做的提交都能通过，等于没测。
- 三个例子的验证深度是递进的：
  - SWE-bench Verified：验**测试套件的状态变化**（前后两次运行的差异）。
  - OSWorld：验**系统内部状态**（文件系统、进程、网络、DOM、cookie、localStorage、后端请求），所以能抓「报告文件存在但数据库没改」这种表面完成。
  - Terminal-Bench：验**只有真正执行过才会出现的副产物**（内核启动日志里的自定义 `printk` 消息）。自定义 `printk` 这个设计很巧：它不是「结果文件存在」，而是「构建—运行链路真的跑通了」的痕迹。
- 工程上有两条可迁移的做法：一是**优先找「只有真做了才会产生的痕迹」**（启动日志、哈希、随机 GUID、后端写入记录），二是**同时设置正向与反向断言**，别只查「该有的有了」，还要查「不该有的没出现」。

**易混点**

- **FAIL_TO_PASS ≠ 全部测试通过**：它特指「修复前失败、修复后通过」的那组测试。一个补丁可能让所有测试都通过，但如果那组测试原本就是通过的，它就不构成修复的证据。
- **验证器通过 ≠ Agent 合规**：验证器只按预设断言判分，过程违规（如 7.1.2 的并行双调用）不会被它捕获。

**一句话记住**

> 验证器只认机器能独立复核的事实：「已修复」和「未破坏」要分别立证，伪造不了的痕迹最有说服力。

### 7.4.3 任务的难度划分

**原文要点**

- **评估任务集需要包括不同难度的任务**。这样，当模型能力提升时，评估任务集不会快速过时。
- **GAIA** 全套 466 题分为三级难度：
  - Level 1 只需一至两个工具（人类 93.9%，GPT-4 30.3%）；
  - Level 2 需要多步思考（91.8% 对 9.7%）；
  - Level 3 需要复杂组合（87.3% 对 0%）。
  - 这一分层不止标注难度，更具备**诊断价值**：Level 1 失败指向基础工具使用，Level 2 指向多步规划与信息整合，Level 3 指向长序列思考与复杂性管理，三者对应的改进方向各不相同。
- **Terminal-Bench** 涵盖从简单的 `mlflow` 模型注册，到中等难度的 7z 密码破解，到困难的 git 服务器与 webserver 多组件集成，再到最高难度的 FEAL 差分密码分析。
- **τ²-bench** 还专门设计了**陷阱任务**，即用户声称「客服已批准取消」，实际并不符合政策，用以检验 Agent 在压力与误导下能否维持正确判断。

**辅导讲解**（笔记补充，非原文）

- 难度分层有两个作用，第二个常被忽略：
  1. **防过时**：如果全是简单题，模型一升级就全部满分，评估集就失去了区分度。
  2. **做诊断**：失败落在哪个层级，直接指向该改什么。原文把这一层说得很明确——三级难度分别对应「基础工具使用」「多步规划与信息整合」「长序列思考与复杂性管理」。
- GAIA 那组数字还可以读出「人类—模型差距」的形状：Level 1 人类 93.9% 对 GPT-4 30.3%（差距约 64 个百分点），Level 2 是 91.8% 对 9.7%（差距约 82 个百分点），Level 3 是 87.3% 对 0%（差距 87.3 个百分点）。也就是说，**难度上升时人类几乎不掉，模型掉到零**——这正是「分层比总平均分更有信息量」的证据（差距为笔记补充的计算）。
- 「陷阱任务」是难度设计里的另一个维度：它不是把任务做长，而是**加入误导性输入**。用户说「客服已批准取消」但政策并不允许，Agent 如果顺着用户走就错。这类任务测的是**抗压与抗误导**，和「任务复杂」是正交的两个维度。

**易混点**

- **难度 ≠ 复杂度**：Terminal-Bench 里的最高难度是 FEAL 差分密码分析，它的难在于领域知识与长链路，而陷阱任务的难在于「输入本身在骗你」。设计评估集时两类都要有。
- **Level 3 模型得分 0% 不代表基准无价值**：它的价值恰恰在于「现在测不出来，未来能测出来」，这也是原文说「任务集不会快速过时」的意思。

**一句话记住**

> 难度分层不只是标注，而是诊断表：失败落在哪一级，就告诉你该修工具、修规划还是修长序列管理。

### 7.4.4 数据泄漏防范

**原文要点**

- **GAIA** 使答案无法从互联网直接检索。它的任务概念简单而路径开放，例如：从某一特定日期的 NASA 每日天文图片出发，识别图中宇航员，查出其所属的宇航员组，再计算该组中在太空停留时间最短者，并严格按「姓氏，分号分隔，千位分隔符」的格式输出。答案高度具体，正确与否通过精确字符串匹配判定。防泄漏依靠两点：
  1. **问题必须组合多个信息源才能作答**，单一网页无法直接给出答案；
  2. **部分任务配有专门制作的附件**（互联网上不存在的 PDF、音频、图片）。
- **AndroidWorld** 以单个模板派生大量实例。其任务并非静态文本，而是**可动态实例化的模板**，例如「将联系人 [CONTACT_NAME] 的电话改为 [NEW_PHONE]」，每次评估随机生成参数值。这带来三方面收益：
  1. 参数每次不同，**回放固定操作序列失效**；
  2. 单个模板可生成**近乎无限的实例**；
  3. **固定部分参数、只改变其余参数，可精确测量特定因素的影响**。
- **Terminal-Bench** 在题面中嵌入**金丝雀标识符**。每道题携带一个 canary GUID，若模型能够输出含该 GUID 的内容，即说明基准数据已进入训练集。**它不阻止数据泄漏，但使泄漏可被检测。**

**辅导讲解**（笔记补充，非原文）

- 这一节回答的是「模型是不是背下来的」。三种手段的思路各不相同，可以对照记忆：
  - **GAIA：让答案根本不在网上。** 靠多源组合 + 专有附件。这是「提高获取门槛」的路线。
  - **AndroidWorld：让答案每次都变。** 靠参数化实例化，把「背答案」变成「背不了」。这是「让记忆失效」的路线。
  - **Terminal-Bench：让泄漏留下痕迹。** 金丝雀 GUID 是「检测」而非「阻止」。这是「承认防不住，但能查出来」的路线。
- 金丝雀标识符的思路很像防抄袭的水印：把一段无意义的随机串放进题面，如果模型能原样吐出它，就证明它见过题面。它的价值在于——**当你怀疑某个分数虚高时，有办法去验证**。
- AndroidWorld 的第三点收益特别实用：「固定部分参数、只改变其余参数，可精确测量特定因素的影响」。这其实就是「参数化模板 + 控制变量」的组合，等价于把评估集变成了一个可做消融实验的装置。如果你要测「Agent 是不是依赖某个 UI 文案」，就可以只改那一个参数。

**易混点**

- **防泄漏 ≠ 抗过时**：防泄漏针对「题目进入训练集」，难度分层针对「模型升级后全员满分」。前者是数据问题，后者是设计问题。
- **金丝雀 GUID 不阻止泄漏**：原文明确写了「它不阻止数据泄漏，但使泄漏可被检测」。不要把它当防护手段。

**一句话记住**

> 防泄漏三条路：让答案不在网上（GAIA）、让答案每次都变（AndroidWorld）、让泄漏留下可检测的痕迹（canary GUID）。

### 7.4.5 质量控制与长期维护

**原文要点**

- **做一个高质量的评估集是非常困难的。** 上面几个基准测试的现行形态，多数是在初版投入使用、暴露问题之后**逐轮修补**的结果。例如，从 τ-bench 到 τ²-bench 有五处重新设计的地方：
  1. **任务指令过于笼统，导致答案可被猜测。** 初版的任务指令写得宽泛，模型无需真正澄清需求，凭常识推测一套流程也能通过。τ²-bench 将剧本拆分为 `known_info` 与 `task_instructions` 两栏：前者界定用户知悉的范围，后者规定透露方式。用户不知悉的信息 Agent 无从推测，只能通过查询获得。
  2. **成功条件不够精确，导致验证误判。** 「网络已恢复」这类条件缺乏可核实的边界。τ²-bench 将其改为「测速结果为 excellent 才算解决，poor、fair、good 均不接受」。这一改动针对的是**敷衍性修复，即压制症状而不解决根因**。
  3. **用户模拟器行为过于机械。** 初版的模拟用户仅作被动应答。τ²-bench 为其补充了**情绪**（首次修复失败后表现出不满）、**耐心上限**（沟通效率过低时终止对话）以及**事实锚定要求**。三者共同作用，使模拟器在接近真实用户的同时仍保持可复现。
  4. **用户不仅参与对话，也参与操作。** telecom 领域引入了**双控环境**。此前的评估中只有 Agent 能够改变环境，而在技术支持这类场景中，相当一部分动作本应由用户在自有设备上完成。双控同时为验证增加了一个维度：用户改变状态后，Agent 必须重新调用工具才能获知结果，验证因此覆盖了「Agent 是否真的读到了用户侧的操作结果」。
  5. **任务实例动态生成。** τ²-bench 的具体实例（用户姓名、号码、故障组合）可参数化批量生成，这同时改善了覆盖率与抗泄漏能力。
- **SWE-bench Verified：发布前淘汰 71% 的原始任务。** OpenAI 从原始 **2294 个任务**中随机抽取 **1699 个**进行人工评估，招募 **93 名精通 Python 的开发者**逐条检查：问题描述是否清晰、测试用例是否覆盖边界条件、测试是否稳定、参考 patch 是否引入新错误、难度是否合理。**最终仅 500 个通过。** 高淘汰率带来的是更高的信噪比，**评估成本也下降约 80%**。复杂 Agent 任务动辄需要数分钟至数小时，使用前沿模型完整跑完一个评估数据集往往需要数千美元的 token 成本，降低评估成本非常重要。
- **OSWorld：发布后 15 个月中暴露出 300 余个问题。** 它于 **2024 年 4 月**发布后迅速成为多模态 Agent 评估的重要基准，随后在广泛使用中暴露出四类问题：
  - 环境问题（网站反爬、CAPTCHA、动态内容变化）；
  - 任务描述问题（表述存在歧义）；
  - 验证逻辑问题（过严或过松）；
  - 初始状态问题（配置不完整）。
  - **香港大学团队**组建约 10 人的小组，与 MoonShot AI、OpenAI、ByteDance Seed TARS、Anthropic、Simular 等深度合作**两个月**进行系统性修复：环境问题通过锁定版本和离线备份解决，描述问题通过改写歧义表述消除，验证问题通过人工建立正确基线并调整条件解决，初始状态问题通过增加完整性校验缓解。

**实验7-2 ★：人肉执行基准测试任务**

从 GAIA、AndroidWorld、SWE-Bench Verified、Terminal-Bench、OSWorld-Verified 中挑选任务亲手完成，每个数据集建议完成简单、中等、困难各一个。「困难」级别对人类同样具有挑战。完成后回答两个问题：**该任务的描述是否存在多种合理解释，若存在，验证器认可哪一种？若试图蒙混过关，成本最低的路径是什么，验证器能否拦截？**

**辅导讲解**（笔记补充，非原文）

- 把 SWE-bench Verified 的数字复算一下（笔记补充的计算）：$1699/2294\approx74.1\%$，即约四分之一的原始任务没有进入人工评估；$500/1699\approx29.4\%$，即人工评估阶段淘汰了约 $1-29.4\%=70.6\%\approx71\%$ 的候选任务——与原文「发布前淘汰 71% 的原始任务」「最终仅 500 个通过」的口径一致。
- 这一节最重要的观念转变是：**评估集不是一次性写好的作品，而是需要长期维护的活资产。** 三个案例分别代表三种维护形态：
  - τ-bench → τ²-bench：**版本级重新设计**（五处改动，改的是任务定义的结构）；
  - SWE-bench Verified：**发布前的大规模人工筛选**（93 人，淘汰 71%，代价换信噪比）；
  - OSWorld：**发布后的系统性修复**（15 个月、300 余个问题、10 人小组、两个月、五家机构合作）。
- 为什么值得花这个代价？原文给了成本视角：前沿模型完整跑完一个评估数据集往往要花数千美元的 token，所以**减少低质量任务等于直接省钱**——原文说评估成本下降约 80%。
- τ 到 τ² 的五处改动里，最容易被自建评估集忽略的是第 2 条：**成功条件必须精确到没有解释空间**。「网络已恢复」这种说法给了 Agent 敷衍的空间（把症状压下去就算过）；「测速 excellent 才算解决，poor/fair/good 均不接受」则把口子堵死。原文给这类修复起了一个名字：**敷衍性修复，即压制症状而不解决根因**。
- 实验 7-2 值得认真做，因为它用「人肉跑一遍」暴露一个残酷事实：如果连人都觉得题目有歧义，Agent 失败就不能全算它的错。两个问题里第二个尤其有用——它逼你从「作弊者」的视角审查验证器。

**易混点**

- **「淘汰率高」是优点还是缺点？** 在这一节的语境里是优点：高淘汰率带来更高的信噪比，而且总评估成本下降约 80%。但要注意它淘汰的是**任务**，不是模型。
- **τ²-bench 的第 1 与第 3 处改动容易混**：第 1 处改的是**信息边界**（把剧本拆成 `known_info` 与 `task_instructions`，防「猜」），第 3 处改的是**模拟器行为**（加情绪、耐心上限、事实锚定，防「机械」）。一个管「知道什么」，一个管「怎么表现」。

**一句话记住**

> 高质量评估集是修补出来的：任务指令要防猜、成功条件要防敷衍、模拟器要防机械，且这些修补要长期做下去。

### 7.4.6 评估集的三个来源

**原文要点**

- 一种常见的看法是，公开基准服务于模型排名，与实际业务关联有限。**公开基准的分数确实难以直接指导产品决策，但其设计手法具有充分的可迁移性。** 前面讨论的验证深度、参数化生成、泄漏防范与质量维护，恰是自建评估集最容易疏漏的几处。
- 生产环境中的评估集通常有三个来源：
  1. **公开基准**：用于**粗筛模型与借鉴设计手法，一般不用于产品决策**。它的任务分布与实际业务的任务分布并不一致，在 GAIA 上提升两个百分点，与退款成功率之间不存在必然关系。
  2. **自建业务集**：覆盖真实的任务分布，可以作为模型选型、Harness 设计决策的依据。例如，τ²-bench 可以作为需要仿真用户的评估系统骨架，替换领域数据与工具集即可。
  3. **生产轨迹回流**：来自线上的真实失败用例——用户明确纠正、用户点踩，以及事后通过状态检查、规则验证器或 LLM 评审发现的问题案例，**经失败归因后沉淀为回归用例**。具体做法见后文「失败归因」与「端到端回归任务与轨迹前缀回归任务」两节。这一来源**成本最高，准确性也最高**，因为它直接来自用户实际遇到的问题。
- 起步阶段通常只有公开基准与少量手写的自建业务集；系统上线运行一段时间后，**生产轨迹回流的用例会成为主体**。

**辅导讲解**（笔记补充，非原文）

- 三个来源画成一条时间线最清楚：**上线前**靠公开基准定方向、靠自建业务集定决策；**上线后**靠生产轨迹回流持续补充。它们不是三选一，而是三个阶段的主力。
- 为什么公开基准不能指导产品决策？因为**分布不同**。原文那个例子很直白：在 GAIA 上提升两个百分点，与退款成功率之间不存在必然关系——GAIA 考的是「搜集信息的通用助手」，退款考的是「多轮工具编排 + 政策合规 + 信息告知」。这两件事的相关性可能很弱。
- 但公开基准的设计手法确实可迁移。原文列了四项：**验证深度、参数化生成、泄漏防范、质量维护**。这四项恰好也是自建评估集最容易漏的——很多团队的自建集就是几十条手写用例，没有难度分层，没有防泄漏，也不做维护。
- 「生产轨迹回流」最值得投入的原因有两个：一是它自带「真实发生过」的标签，二是它天然覆盖了你没想到的场景。原文说这一来源「成本最高，准确性也最高」——成本高在需要失败归因的人工与系统建设，准确性高在它来自用户实际遇到的问题。
- 一个务实的起步建议（笔记补充）：先照 τ²-bench 的骨架搭一套最小可用的自建业务集（换领域数据与工具集），跑通「评估 → 失败归因 → 回归用例」这条管道，再逐步把线上样本灌进来。这样评估集从第一天起就是「活的」。

**易混点**

- **公开基准「不用于产品决策」≠「不需要跑」**：它的用途是粗筛模型与借鉴手法。原文用的是「一般不用于产品决策」，而不是「不要跑」。
- **生产轨迹回流 ≠ 可观测性**：可观测性提供的是原始轨迹（7.8 节），回流是「轨迹经失败归因后沉淀为回归用例」的结果。中间那一步（失败归因）不能省。

**一句话记住**

> 公开基准管借鉴与粗筛，自建业务集管决策，生产轨迹回流管持续逼近真实分布——上线越久，第三个来源越是主体。

## 7.5 自动化评估方法

**原文要点**

- 前面几节讨论的基准测试有一个共同点：**验证器几乎都是确定性的**。SWE-bench 运行测试套件，AndroidWorld 断言最终 UI 状态，GAIA 做精确字符串匹配，τ²-bench 的四层检查同样全部由代码执行。这一选择有充分理由：**确定性验证不引入额外的模型开销，结果完全可复现，可以像单元测试一样纳入持续集成，也便于在不同模型之间排名。**
- 代价是**它只能评估最终结果对不对，但不能给出错误原因**。τ²-bench 那条失败的任务最终得 0 分，而这个 0 分不会说明 Agent 是在线路选择环节出错、还是漏掉了流量充值步骤，更不会指出下一步该改什么。对于用于排名的公开基准，这不构成缺陷；**对于需要持续改进的生产系统，这恰恰是最需要的信息。**
- 生产场景还有另一重困难：**许多判断根本无法写成代码可检查的断言**。一封投诉回复是否得体，一份调研报告是否遗漏了关键信息，一次记忆检索是否弄错了人物关系，这些既没有唯一终态可供查询，也无法靠关键词匹配来判定。
- 因此，从公开基准测试走向生产环境中的评估，验证方式需要沿一条谱系向右移动，其横轴是**任务的可机械验证程度**，如图 7-4 所示。

> 图 7-4（原文插图）验证方式的谱系：从确定性验证到模型评判。图是一条「任务的可机械验证程度」的谱系轴，轴上标着「高」与「低」两端，自高到低排列四档验证方式：
> 1. **确定性验证器**——终态唯一可查；只判通过/不通过；例：SWE-bench 跑测试。
> 2. **检查项清单**——多项确定性检查；按声明的口径聚合；例：τ²-bench 四层验证。
> 3. **Rubric + LLM 评判**——维度可拆但无法机械判定；分维度打分并说明理由；例：客服质量、报告撰写。
> 4. **配对比较**——连维度都难以写出；只判 A 与 B 孰优；例：Chatbot Arena。
>
> 图下方还有两栏小结，分别对应谱系的两端：
> - **确定性验证**：结果完全可复现、可纳入持续集成、成本低；**代价：只回答对错，不指出问题出在哪里**。
> - **模型评判**：可拆出诊断维度，覆盖写不成断言的任务；**代价：引入评判偏差与波动，成本更高**。

- 谱系右侧的两件工具因此成为生产评估的主体：用 **Rubric** 把笼统的「好不好」拆成若干个可分别打分的维度，用 **LLM-as-a-Judge** 在缺乏确定性判据时完成打分。二者合起来，才能把一个笼统的失败率还原为可着手修复的具体问题；再配合本节后半部分的**失败归因**，构成生产 Agent 评估的完整闭环。
- 需要说明的是：**向右移动并不意味着放弃左侧。** 凡是能写成程序化断言的检查都应当继续用断言，LLM 评判只用于确实无法机械判定的维度。确定性检查更便宜、更稳定，也更适合作为回归测试长期运行。

**辅导讲解**（笔记补充，非原文）

- 这条谱系的判据只有一个：**「正确答案」能不能写成代码**。
  - 能（终态唯一可查）→ 确定性验证器；
  - 有多个确定性检查项、需要按口径聚合 → 检查项清单；
  - 维度能说清但不能写成代码 → Rubric + LLM 评判；
  - 连维度都说不清，只能说「A 比 B 好」→ 配对比较。
- 「向右移动不意味着放弃左侧」这句话是全节的纪律条款，值得写在墙上。它挡住两种常见错误：
  - **过度使用 LLM 评判**：本来 `assert status == "cancelled"` 就能判的，却让 LLM 去「读一下对话，看看退款成功了吗」——更贵、更不稳、还可能被忽悠。
  - **死守确定性判据**：明明要评「这封投诉回复是否得体」，却硬写成关键词匹配，结果 Agent 学会了堆关键词。
- 一个实用原则（笔记补充）：**每一层判据都先问「能不能降级为断言」**。能降就降；只有确实降不下去的维度，才留在 LLM 评判里。

**易混点**

- **确定性验证的「代价」是诊断能力，不是准确率**：它在「判对错」上更准，只是说不出「错在哪」。
- **Rubric 与 LLM-as-a-Judge 是两件事**：Rubric 是「判分标准」，LLM-as-a-Judge 是「执行判分的角色」。图 7-4 里那一档的名字是「Rubric + LLM 评判」，正说明二者要配合使用。

**一句话记住**

> 验证方式沿「可机械验证程度」排成一条谱系：能写断言就用断言，写不出的维度才交给 Rubric + LLM 评判。

### 7.5.1 LLM-as-a-Judge：自动化评估的核心

> 图 7-5（原文插图）LLM-as-a-Judge 流水线。图从左上到右下依次是：
> - **输入之一：Rubric（评分标准）**，示例维度写着「事实正确性: Essential」「逻辑连贯性: Important」「幻觉检测: Veto ⚠」「完整性: Important」。
> - **输入之二：候选回答**，示例是 Agent 输出「退款已处理，\$150 将在 3-5 工作日内到账。」
> - **输入之三：参考方案（可选）**，写着「标准答案 / 评分要点：必须包含退款金额；必须包含到账时间；不可承诺具体日期」。
> - 三者一起送入 **Judge 模型（GPT-5 / Gemini 2.5）**，图旁标注「多源异构评判防止同源偏见」。
> - **结构化评估输出**（Judge 逐维度给出分数与理由）：事实正确性 4/4（金额和时间均准确）、完整性 3/4（缺少退款方式说明）、幻觉检测 PASS（无虚假信息）、逻辑连贯性 4/4（因果关系清晰）。
> - **评分聚合策略**（四条）：加权平均 $\sum(\text{权重}\times\text{维度分})$；一票否决（幻觉=FAIL → 总分=0）；多评委（3 个 Judge 取中位数）；边界案例标记（分歧>2 分 → 人审）。

**原文要点**

- **为什么需要 LLM-as-a-Judge？** 对于开放式任务（如生成报告、处理客户投诉、创意内容），没有标准答案可以自动对比，人工评估成本高且难以规模化。LLM-as-a-Judge 通过让语言模型根据专家定义的评分标准（Rubric）进行评判，**在自动化规模和人类专业判断之间取得了平衡**。
- 但这种方法也有**已知的局限**：评判模型可能有自己的偏见，相同输入多次评判也可能有波动。最典型的是**长度偏差**，即倾向于给更长、更详尽的回复打高分，哪怕内容并不更正确。就像人类考试时对不会的题就长篇大论地回答，期望能「蒙对」一两个点。常用防范手段有三种：
  1. 在 Rubric 里**显式惩罚冗长**、对同类任务规定回答的长度上限；
  2. 做配对比较时**先把两个候选的长度控制到相近再评**；
  3. **定期审计评分与回答长度的相关性**——如果高分几乎总是伴随长回答，就说明评判已被长度带偏，需要回炉修订 Rubric。
- 为了系统性地应对这些挑战，Rubric 设计必须遵循以下准则。

**Rubric（评分标准）：LLM 评判的依据。Rubric 四准则（Scale AI，"Rubrics as Rewards"）：**

1. **基于专家指导**——必须反映领域知识，捕捉核心事实和推理步骤。比如医疗问答的 Rubric 需包含诊断标准和必须避免的医学错误，缺乏专业基础的 Rubric 只能捕捉语言流畅度等表面特征。
2. **全面覆盖**——涵盖事实准确性、逻辑连贯性、完整性、安全性，而且不仅定义正面标准，还要明确**陷阱（Pitfall）**——即高风险的常见错误，如医疗建议中推荐未经验证的疗法。
3. **按重要性加权**——分为**必要项（Essential）**、**重要项**、**可选项**、**陷阱项**。支持**一票否决机制（Veto）**：比如在客服场景中，幻觉（编造虚假信息）是典型的否决维度——无论其他维度表现多优秀，只要出现虚假信息就必须否决。这也有助于防范关键词堆砌式的奖励作弊。
4. **评价标准自包含**——每个评价项独立可操作，不依赖评价者的领域知识。要避免「回应展示了深刻理解」这种抽象标准，改为「引用了至少两个权威理论并准确解释如何支持结论」这种可验证的标准。
- **关键实践**：为每个维度定义客观可验证的评分档次，提供具体示例和边界案例帮助区分模糊情况。要主动防范**奖励作弊（Reward Hacking）**——即 Agent 找到了获取高分的「捷径」却没有真正完成任务——明确惩罚幻觉、讨好用户、关键词堆砌、回避棘手问题。Rubric 需要不断迭代：通过试用收集评价者的分歧并逐步完善，**最终从抽象准则演化为详尽的判例集**。

**辅导讲解**（笔记补充，非原文）

- LLM-as-a-Judge 的本质是**把「人写评分标准 + 人打分」换成「人写评分标准 + 模型打分」**。它并没有消除主观性，只是把主观性集中到了 Rubric 这一处——这也是为什么四准则里「基于专家指导」排在第一位。
- 四准则可以对照四种失败模式来记：
  - 不「基于专家指导」→ Rubric 只能看出「语言流畅」，看不出医学错误；
  - 不「全面覆盖」→ 只写正面标准，没写陷阱，Agent 就学会了绕过陷阱；
  - 不「按重要性加权」→ 幻觉和高分维度等权，一次编造被三个优点抵消，总分照样很高；
  - 不「评价标准自包含」→ 评判者需要自己「理解」什么叫深刻，不同评判者的尺度漂移。
- 一票否决（Veto）为什么值得单独强调？因为它把「加权平均」这种**可以被补偿的评分**变成**不可被补偿的门槛**。原文举的例子很典型：幻觉无论其他维度多优秀都必须否决。否则一个 Agent 只要在「完整性」「逻辑连贯性」上堆分，就能掩盖编造事实。
- 长度偏差的三个防范手段对应三个环节，可以分开用也可以合起来用：**写标准时防（惩罚冗长 + 长度上限）**、**送评时防（长度对齐后再配对）**、**事后审计（看分数与长度的相关性）**。第三条最像「体检」：它不直接修问题，而是告诉你「该回炉修订 Rubric 了」。
- 工程上有个实用的自检问题（笔记补充）：**如果把同一个答案缩写一半、事实不变，分数会掉多少？** 如果掉得明显，你的 Rubric 就有长度偏差。

**易混点**

- **Rubric 与参考答案（标准答案）不同**：图 7-5 把「Rubric（评分标准）」和「参考方案（可选）」画成两个独立输入。参考答案是「什么是对的」，Rubric 是「怎么算好」。开放式任务常常没有参考答案，但必须有 Rubric。
- **陷阱（Pitfall）与一票否决（Veto）不是同一件事**：陷阱是「高风险的常见错误」这一类目，Veto 是「该维度一旦不过就总分归零」的聚合规则。四个加权级别里专门有「陷阱项」。

**一句话记住**

> Rubric 把「好不好」拆成可分别打分的维度，LLM-as-a-Judge 负责打分；四准则是专家指导、全面覆盖、按重要性加权、评价标准自包含。

**以用户记忆Agent 为例，展示一个符合四准则的完整Rubric。** 测试问题是：「我女儿的儿科医生是谁？」（答案需要跨两次对话关联：第一次对话提到「女儿叫Lily」，第二次提到「带Lily 去看了Dr. Chen」）。

```yaml
rubric:
  dimensions:
    - name: 事实正确性
      weight: essential          # 必要项
      scoring:
        4_优秀:   "准确回答Dr. Chen，且关联到女儿Lily"
        3_良好:   "准确回答Dr. Chen，但未提及是Lily 的医生"
        2_及格:   "给出了正确医生但附带不确定的额外信息"
        1_不及格: "给出错误医生名，或回答不知道"
    - name: 信息完整性
      weight: important          # 重要项
      scoring:
        4_优秀:   "主动补充相关信息（如上次就诊时间、诊断结果）"
        3_良好:   "回答了核心问题，无遗漏"
        2_及格:   "回答了核心问题，但遗漏了可用的关联信息"
        1_不及格: "关键信息缺失"
    - name: 思考正确性
      weight: important
      scoring:
        4_优秀:   "正确关联'女儿=Lily'和'Lily 的医生=Dr. Chen'两条跨会话信息"
        3_良好:   "关联正确但思考路径不够清晰"
        2_及格:   "部分关联正确"
        1_不及格: "错误关联（如把用户自己的医生当成女儿的医生）"
    - name: 幻觉检测
      weight: veto               # 一票否决项：一旦触发，总分归零
      scoring:
        pass: "所有信息均可溯源到历史对话记录"
        fail: "编造了对话中不存在的信息（如虚构就诊日期、诊断结果）"
  edge_cases:
    - "如果用户有多个女儿且分别看不同的医生，应追问是哪个女儿"
    - "如果记忆中同时存在'Dr. Chen'和'陈医生'，应识别为同一人"
```

（说明：原书此段为 YAML 代码块，提取后缩进层级有所丢失，笔记按 YAML 语义还原了缩进；键名、档位标签与评语文字未改动。）

**好的Rubric vs 坏的Rubric**：上面每个评分档都给出了**可验证的具体行为**（「准确回答Dr. Chen」），而非「展示了对记忆的深刻理解」这类无法客观判定的描述。**一票否决项明确了底线**：即使其他维度全部满分，一旦出现幻觉就直接判零分。

将这个 Rubric 和 Agent 的实际回答一起交给评判模型，模型会逐项打分并说明理由。把几十个用例的结果汇总起来，再回看其中的低分轨迹，原本笼统的「成功率下降」就能拆成几类具体问题：**是没检索到信息，还是把人物关系想错了，抑或补充了没有依据的内容**。这样一来，Rubric 不只告诉我们「得了多少分」，还会告诉我们下一步该改哪里。

**实验7-3 ★★：构建基于Rubric 的用户记忆评估系统**

本实验要求改造第三章的 `chapter3/user-memory-evaluation` 框架，将当前基于简单 LLM-as-a-Judge 的评分机制升级为结构化的多维度 Rubric 评估系统。现有系统使用单一 LLM 调用返回通过/失败加评估理由，缺乏结构化的诊断能力。要求设计统一的多维度 Rubric 框架，**适用于所有三层任务**。评价维度包括：

- **事实正确性（Precision，精确率）**——在所有给出的信息中，有多少是正确的；用于验证数字、日期和名称是否与记忆信息一致；
- **事实完整性（Recall，召回率）**——在所有应该给出的信息中，有多少被提及；用于验证是否提供了所有相关信息而非遗漏关键内容；
- **思考正确性**，用于检查是否正确理解了信息间的关系和隐含逻辑；
- **思考主动性**，用于评估是否在适当时候提供超出直接回答的建议或风险提醒；
- **幻觉检测**，用于确保未编造记忆中不存在的信息。

四档制评分（优秀/良好/及格/不及格），每档配具体判定标准而非抽象描述。**幻觉维度设为一票否决项。** 为每个维度提供示例和边界案例。

**实验7-4 ★★：Advanced JSON Cards 与RAG 的对比评估**

目标：在同一套评估集上公平对比结构化记忆与非结构化检索的优势边界。复用两个第三章项目，在 `chapter3/user-memory-evaluation` 的 **60 个测试用例**上对比三种配置——纯 Advanced JSON Cards（结构化卡片常驻上下文、无需检索）、纯 RAG（对话分块入向量库、必须检索）、混合系统（核心事实常驻+ 原始对话按需检索）。配套实验用同一组 60 个问题测试了三套记忆方案，**共保留 180 条真实API 运行轨迹**。结果见表 7-3。

| Advanced JSON Cards | 95% | 60% | 50% | 68.3%（41/60） |
| RAG | 90% | 40% | 15% | 48.3%（29/60） |

- 最值得注意的是，**混合方案并没有自然胜出**。它在 3 道题上做到了两种单一方案都没做到的事，却在另外 8 道题上不如表现更好的单一方案；与每道题上的最佳单一方案相比，平均成功率反而低了。纯 RAG 在基础回忆题上与结构化卡片相差不大，一到跨会话关联题，成功率却降到 15%。另一个容易被忽视的数字是：**180 次评判中，幻觉否决触发了 28 次**，可见一票否决项的重要性。

**辅导讲解**（笔记补充，非原文）

- 把表 7-3 的三个总体数字复算一遍（笔记补充的计算）：$41/60=68.33\%$、$29/60=48.33\%$、$40/60=66.67\%$——与原文的 68.3%、48.3%、66.7% 一致。
- 这张表最有价值的读法不是看总体，而是**看列与列的落差**：
  - Advanced JSON Cards：基础回忆 95% → 跨会话隐藏关联 50%，掉 45 个百分点；
  - RAG：90% → 15%，掉 75 个百分点（这就是原文点出的那处崩塌）；
  - 混合系统：80% → 50%，掉 30 个百分点。
  - 结构化表示的优势不在「记得住」，而在「关联得起来」；RAG 的优势在「基础回忆」，一遇到需要跨会话串联的关系题就崩。这正是「分层成功率」比单一总分更有诊断力的例子。
- 那 28 次幻觉否决是个提醒：**如果没有一票否决项，这 28 次可能被别的维度的高分掩盖**，总体成功率会虚高。一票否决不是「更严格」，而是「防止用优点补偿硬伤」。
- 「混合方案没有自然胜出」这个结论非常反直觉，也很有教学价值：人们本能地认为「组合两种方案一定更好」。数据说的是：**组合会在某些题目上互补，也会在另一些题目上互相拖累**（原文给的是 3 道更好、8 道更差）。所以任何组合方案都要按题分层评估，不能只看总体。

**易混点**

- **Precision（精确率）与 Recall（召回率）在原文里的对应关系**：实验 7-3 明确把「事实正确性」对应 Precision（给出的信息里有多少是对的），把「事实完整性」对应 Recall（该给的信息里有多少给了）。不要凭直觉把「完整性」当成精确率。
- **一票否决（veto）与「低分」不同**：低分是被扣分，veto 是直接归零。表 7-3 里 28 次幻觉否决意味着那 28 条用例的总分是 0，而不是「幻觉维度分数低」。

**一句话记住**

> Rubric 的每一档都要写成可验证的具体行为；幻觉这类硬伤要设成一票否决，否则会被其他维度的高分补偿掉。

**同源模型问题与多源评判。**

- 当 Agent 与评判模型来自同一家族时，Agent 可能学会利用评判模型的偏好和盲点。这正是**古德哈特定律（Goodhart's Law）**所说的：**当一个度量指标变成优化目标时，它就不再是好的度量指标。** Agent 越是在某个评分系统上训练或调优，就越倾向于钻这个系统的漏洞，而非真正提升能力。
- 更隐蔽的是，Agent 还会逐渐学会**避开评判模型不擅长检测的错误类型**，让评分系统看起来一切正常。
- 缓解策略是**多源异构评判**——使用不同模型家族的多个 LLM 分别评判（比如 Agent 用 Claude，评判就用 GPT-5 和 Gemini），**不同家族的偏见往往是正交的，Agent 很难同时「欺骗」所有评判者**。使用相同的 Rubric 确保大家评判的是同一目标，通过加权平均或一致性检查聚合结果。部署阶段可以用单一模型快速评估，但应定期用完整的多源评判进行质量审计。
- 多源评判解决的是「用什么模型评判」的问题；接下来要解决「评判哪些模态」的问题——把 LLM-as-a-Judge 的能力从文本扩展到语音、图像、视频，是评估覆盖度的另一维度。

**多模态LLM-as-a-Judge。** 多模态评判将 LLM-as-a-Judge 扩展到语音、图像、视频领域，例如：

- **TTS 评估**（TTS 即 Text-to-Speech，文本转语音）：判断准确性、自然度、音色一致度、情感表达。这些维度能发现传统 **WER（Word Error Rate，词错误率）**难以捕捉的韵律问题。
- **ASR 评估**（ASR 即 Automatic Speech Recognition，语音识别）：做**语义影响判断**——「今天天气」识别错误无伤大雅，但「转账一千」变成「一万」就可能造成严重后果。
- **UI 评估**：采用第一章命名的**提议者—审核者模式**，检查文字溢出、颜色对比度、按钮位置等问题。这里的提议者-审核者作为**评估方法**使用，与第五章中作为生成系统组件的用法不同，但**核心机制相同——一个模型生成，另一个模型独立审查**。
- **视频剪辑评估**：通过关键帧验证剪辑起止点和特效应用是否正确。

**实验7-5 ★★：构建全自动TTS 质量评估流水线**

本实验要求从零设计并实现完整的多模态 LLM-as-a-Judge TTS 质量评估系统。

- 设计 TTS 多维度 Rubric：**准确性**维度验证是否正确读出所有文字（无遗漏/错读/添加）；**自然度**维度评估语音是否流畅（有无机器感、不自然停顿，韵律是否符合人类习惯）；**情感表达**维度检查语气是否符合文本情感色彩（疑问句升调、感叹句强调、悲伤内容语速慢语调低）；**音色一致性**维度在有参考语音时评估说话人相似程度（多模态模型同时接收参考语音与合成语音对比）。
- 构建多样化测试语料库：不同长度（单句→长段落）、文体（新闻/故事/对话）、情感（中性/兴奋/悲伤）、特殊挑战（数字/专有名词/多音字/方言词汇）。
- 实现评估流水线：TTS 生成模块接入主流服务（OpenAI、ElevenLabs、Fish Audio、Minimax、豆包），由可直接接收音频的多模态评判模型将合成语音、原始文本、参考语音和 Rubric 一起输入，逐维度评分并给出详细理由。分析评估结果的分布，同时**记录评判模型、参考音频哈希和候选音频哈希，使结果可复核**。
- 配套仓库中保留了一次小规模的直接听评。**OpenAI 和 Fish Audio** 分别生成了数字、多音字、长句和兴奋语气四类音频，**8 条音频都由 Voxtral** 按上述四个维度完成评分。结果：两者在准确性和自然度上都得到 **5.00 和 4.00**；Fish Audio 在情感表达和音色一致性上得到 **4.00 和 3.00**，OpenAI 则是 **3.75 和 2.75**。四个维度分开评分后，即使「有没有读对」看不出差别，语气和音色上的差别仍会显现出来。
- **但这组分数还不能用来判断哪家 TTS 更好。** 每家只有四条音频，更关键的是，**实验使用的固定参考音频来自 Fish S1**；拿它来比较音色，本来就更有利于 Fish Audio。如果要比较通用 TTS，就不该把「像不像 Fish 参考音色」算进总分；如果要比较声音克隆，则应让所有方案模仿同一个目标说话人，并用人工盲听校准模型评分。**选什么参考答案、参考图片或参考音频，本身就是评估设计，而不是评估开始前无关紧要的准备工作。**
- 人工编写 Rubric 适合快速建立这样的诊断维度。评估规模再扩大时，还可以**训练专门的生成式奖励模型来自动打分**——相关训练方法将在第八章讨论。
- 评判模型给出的分数只说明结果好坏；要把结果变成可以修复的问题，还需要定位失败究竟从哪一步开始。

**辅导讲解**（笔记补充，非原文）

- 古德哈特定律在这一节的出现位置很关键：它紧接着「同源模型」而来。逻辑链条是——**如果评判者和被评判者同源，那么优化压力会顺着这个共同点传导，Agent 学到的不是「怎么做对」，而是「怎么让这个评判者给高分」。** 这与 7.5.1 前面讲的奖励作弊（Reward Hacking）是同一件事的两个层次：一个是「钻 Rubric 的漏洞」，一个是「钻评判模型偏好的漏洞」。
- 「偏见正交」是多源评判的核心论点，值得用几何的方式理解：如果两个评判者的偏见方向一致（同源），它们会叠加；如果方向无关（正交），一个模型看不出的问题另一个可能看得出，Agent 要同时骗过所有评判者的难度就大幅上升。
- 多模态评判的四个例子里，**ASR 那条最能说明「为什么不能用传统指标」**：WER 把「一千」和「一万」的差别记成一个词错误，与把「今天」听成「明天」记成同样的代价；但对业务来说前者可能造成严重后果。所以原文说 ASR 评估要做「语义影响判断」。
- 实验 7-5 里最值得学的是作者自己拆自己的台：**分数出来之后，作者指出这组分数不能用来排名**，理由是样本量（每家四条音频）和参考音频的选择偏差（参考音频来自 Fish S1，对 Fish Audio 有利）。这段是很好的「评估设计」教材，可以提炼出三条检查清单：
  1. **样本量够不够**？（每家 4 条，太少）
  2. **参考答案有没有偏向某一方**？（参考音色来自被测方之一）
  3. **该不该把这个维度算进总分**？（比通用 TTS 就不该算音色一致性；比声音克隆则要统一目标说话人 + 人工盲听校准）
- 「记录评判模型、参考音频哈希和候选音频哈希，使结果可复核」这条工程细节值得记住：它让一次评估结论在几个月后被质疑时，还能还原「当时用的是哪个模型、哪段音频」。

**易混点**

- **同源偏见（same-family bias）与位置偏差（position bias）不同**：前者是「Agent 与评判者同族」，后者是「评判者偏向先出现的候选」（见 7.5.4）。两者的缓解手段也不同：前者用多源异构评判，后者用交换顺序各评一次。
- **「提议者—审核者」在第五章与本章的用法不同、机制相同**：第五章里它是生成系统的组件（一个生成、一个审查），本章里它是评估方法。原文特意说明了这一点。

**一句话记住**

> 评判者与被评判者不能同源（Goodhart's Law），参考答案的选择本身就是评估设计——它可能悄悄偏向某一方。

### 7.5.2 失败归因：从整条轨迹定位首个错误

**原文要点**

- 端到端评估通常只给出「成功」或「失败」，却没有回答「为什么失败、从哪一步开始失败」。要让评估结果真正驱动修复，必须对每条失败轨迹进行**失败归因（failure attribution）**：标出**主要错误类别**、**首次出现不可接受行为的步骤**、对应的**工具调用或模型输出**，并附上**可复核的证据**。
- 归因对象是**轨迹中的首个导致任务偏离的错误**，后续错误往往只是连锁反应，**不能把最后一个报错简单当成根因**。
- 生产 Agent 的问题案例通常来自三类信号：**用户明确纠正**（「不要这么做」）、**用户点踩或给出负面反馈**，以及**事后通过状态检查、规则验证器或 LLM 评审**发现 Agent 做了不该做的事情。
- 构建失败归因系统需要开发者耐心阅读并分析生产 Agent 的问题轨迹。这个过程**可以借助 LLM，但不能完全依赖 LLM**，因为失败归因往往反映了产品问题，不止是技术问题。
- 随着产品不断完善，错误分类可能包含多个大类，每个大类下又有多个小类，**最终多达数百种**。这些错误类别和归因方式可以作为归因标注 Agent 的提示词或 Skill。
- 以 Coding Agent 为例，一个实用的初始分类如下。

**错误类别 / 典型表现 / 首个错误的定位方式**（表格按原文语义还原：原书分栏排版导致三列错行，笔记按「错误类别—典型表现—首个错误的定位方式」的列序重新对齐，文字未改动）

| 错误类别 | 典型表现 | 首个错误的定位方式 |
| --- | --- | --- |
| 需求理解与歧义处理 | 做出来的不是用户要的：漏掉需求里的一个条件、把范围理解宽了或窄了；仓库里有两个同名配置文件时直接选一个，既不说明也不追问 | 用LLM 把原始需求与Agent 实际做的事（动作序列）逐条对照，先定位第一处偏离，再回溯到造成它的那次工具调用或那句答复 |
| 流程与规范缺失 | 未执行单元测试就提交；未写Plan 就开始改代码；引入外部依赖而仓库已有内部等价物；绕过既定架构约定 | 找到第一次违反软件开发流程约定的动作，例如首次 `git commit`、首次写文件；回看它之前有没有读过约定来源 |
| 工具调用错误 | 同一文件反复编辑失败；JSON/schema 或参数格式错误；特殊字符导致抄写、转义或写入错误 | 记录第一次失败的编辑/工具及原始请求、错误返回；重复失败属于后续症状 |
| hack 验证环境 | 直接改断言、加skip、mock 掉被测逻辑；声称「测试已通过」但根本没跑 | 取第一次改动测试或验证逻辑的message；再把完成声明与轨迹里真实执行过的命令交叉核对，确认它是否真的跑过 |
| 修改不完整 | 改了函数签名，改了三处调用方，漏了第四处的动态调用、另一语言的绑定或schema | 把Agent 声称的影响面与真实影响面做集合差，取第一个遗漏项，回看它检索时用了什么关键词 |
| 对用户的信息反馈错误 | 工具调用和环境状态全对，最终告诉用户的信息却错了：金额、状态、时间说错；把部分做完说成全部做完；漏掉必须告知的事项 | 把答复里的每个事实断言与工具返回值逐条对齐，取第一条无法溯源或与工具返回矛盾的断言 |
| 非功能性回归 | 改了公开API、schema 而无数据库迁移脚本；为让校验通过而删掉校验 | 取第一次做出该改动的message，看它是否意识到自己动的是公开接口或需要迁移的结构 |
| 模型执行异常 | 输出中途截断、无故停止、超时，或没有完成收尾动作就结束 | 定位第一个异常终止的位置，区分模型停止、Harness 超时和工具服务故障 |
| 过早停止任务 | 多目标任务只完成一部分；未穷尽合理方案就宣布不可能 | 定位第一次遗漏目标或放弃探索的决策，并与最终验证失败分开记录 |

- **归因标注Agent** 可以利用 LLM 规模化完成大量生产轨迹的根因分析，但**不能只输出一句「失败原因」**。归因记录需要结构化，可以采用 JSON 或 YAML 文档格式，并**引用具体的步骤号、工具名和观察证据**；同时还要**区分根因与后果**、**判断是否可恢复**并**给出置信度**。
- 例如：`edit_file` 返回 `old_string` 匹配失败，之后 Agent 连续三次重试仍未写入文件——**主因是「文件编辑与工具调用错误」，三次重试是后果，而不是三个独立根因**。若多个类别同时出现，按「**最早且能解释后续失败**」的原则选主因，其余保留为次因。
- 上表中至少有三类可以**先用规则筛出嫌疑轨迹、再交给 LLM 定位首错**：完成声明与实际执行命令的交叉核对、diff 是否触及测试断言与 skip 标记、diff 是否改动公开API 或schema 而无迁移文件。**规则先筛、LLM 再定位，比把全部轨迹喂给 LLM 更便宜也更准。**
- 在保存归因记录时，除了 LLM 输出的记录，还应把**任务目标、环境状态、Agent 版本、工具集版本和完整的 Agent 轨迹**一起保存，以便进行回归测试。

**辅导讲解**（笔记补充，非原文）

- 「首个错误」这四个字是这一节的灵魂。为什么不能只看最后一个报错？因为 Agent 的失败有很强的**连锁性**：第 8 步用错了数据，第 11 步开始就全在错的基础上推进，第 32 步的「保存失败」只是最后那一下。原文的诊断建议是：**定位首个导致任务偏离的错误**。
- 九个类别可以按「错误发生在哪一环」重新归拢，这样更好记：
  - **在「理解」环节**：需求理解与歧义处理；
  - **在「流程」环节**：流程与规范缺失、过早停止任务；
  - **在「工具」环节**：工具调用错误、模型执行异常；
  - **在「结果」环节**：修改不完整、非功能性回归；
  - **在「诚信」环节**：hack 验证环境（改断言、假称跑过测试）；
  - **在「表达」环节**：对用户的信息反馈错误。
- 每一条的「定位方式」都遵循同一个思路：**先找到第一个「不该发生」的动作，再看它之前 Agent 有没有读够该读的东西**。例如「流程与规范缺失」的定位方式里特意写了「回看它之前有没有读过约定来源」——它区分了两种情况：Agent 不知道规范（Harness 没给到），还是知道却不遵守（模型行为问题）。这两种的修法完全不同。
- 「规则先筛、LLM 再定位」是很好的成本控制经验。原文点了三类最适合规则筛的：**完成声明 vs 真实执行的命令**、**diff 是否触及测试断言与 skip 标记**、**diff 是否改动公开 API/schema 而无迁移文件**。这三类都能用文本比对、正则或 diff 检查廉价地判定「有没有嫌疑」，把 LLM 的算力留给真正需要语义理解的定位工作。
- 归因记录要求「区分根因与后果」「判断是否可恢复」「给出置信度」，这三项是做回归任务的直接依据：
  - 区分根因与后果 → 决定回归任务该覆盖哪一步；
  - 是否可恢复 → 决定这条失败该算「Agent 能力问题」还是「环境/工具问题」；
  - 置信度 → 决定这条记录要不要人工复核。
- 「可以借助 LLM，但不能完全依赖 LLM」值得单独记住。原文给的理由很有意思：**失败归因往往反映了产品问题，不止是技术问题**。也就是说，很多失败追到底其实是「需求本身没想清楚」「产品定义有矛盾」，这不是一个模型能替你判的。

**易混点**

- **首个错误 ≠ 第一个报错**：有些首个错误根本不报错（如 7.5.2.1 的 AndroidWorld 例子：第 8 步的思考里写着看不到图片内容，但既没报错也不是工具调用）。所以定位方法必须是「事实锚点比对」或「轨迹前缀二分」，而不是搜错误关键字。
- **主因 ≠ 唯一的错**：原文允许保留多个次因，只是要求主因满足「最早且能解释后续失败」。

**一句话记住**

> 失败归因要找到「首个导致偏离的错误」，记录要结构化到步骤号 + 工具名 + 证据，并区分主因与后果。

下面以三类典型错误为例进行介绍。

**7.5.2.1 「做对了但说错了」问题**

**原文要点**

- 「做对了但说错了」问题容易被整体成功率掩盖，**因为多数评估只检查环境状态**。在 τ²-bench 公开的基线结果中，**带有信息告知要求的 704 次运行共失败 240 次，其中 162 次的信息告知出错；有 80 次（占全部失败的三分之一）的环境状态正确，但信息告知错误**。
- 配套仓库的 AndroidWorld T3A 运行记录里有一个典型例子：任务是把图库中 `expenses.jpg` 里的开销录入记账应用。Agent 用 **32 步**完成了授权、搜索、打开图片、逐条填写和保存，**没有任何一步返回错误**，最后自行宣告完成，验收却报告应当写入的记录不存在。日志给出的那条是 **Dress、¥436.35**，与它写进去的四条毫无关系。逐步回看会发现：
  - **第 8 步**的思考里写着「I cannot actually see the content/details of the expenses in the image」，它自己已经知道没拿到数据，却既没有停下也没有报告，而是继续推进；
  - 到**第 11 步**，四条开销数据「Coffee \$4.50、Lunch \$12.75⋯⋯」凭空出现在它的记录里；
  - 此后的每一次输入和保存，都基于这四条**幻觉编造的数据**。
- **首个错误落在第 8 步**，而那一步既没有报错，也不是一次工具调用。它的根因归属容易分析错：**T3A 是纯文本 Agent，观察空间里只有元素树、根本没有图像像素**，所以根因不是「模型不会 OCR」，而是 **Harness 的观察通道缺失**。如果记成模型能力问题，接下来就会去换模型或做 OCR 训练；但真正该做的是**补观察通道**。

**实验7-6 ★★：对AndroidWorld 失败轨迹做失败归因**

本实验用真实轨迹练习本节的归因方法，不需要模拟器，也不需要调用模型 API。素材是 `chapter7/android-world` 中已保存的 T3A 运行记录：`t3a.md` 是全部任务的逐步 Action/Reason/Summary，`t3a_failed.md` 集中收录了 50 余条失败轨迹，每条末尾都带验证器给出的客观判定。

- **第一步：抽样分层。** 从 `t3a_failed.md` 中抽取至少 10 条**全程没有工具报错的静默失败**。轨迹里不能有失败的工具返回，Agent 自行宣告完成或者耗尽步数，只有末尾的验证器判定为失败。
- **第二步：定位首个错误。** 为每条轨迹标出**首错步号**，并注明它是一次工具调用还是一条 assistant message。静默失败要靠两种办法定位：一是**事实锚点比对**，把 Agent 的陈述与工具返回值逐步对齐，取首次背离；二是**轨迹前缀二分**，把轨迹截到第 $k$ 步交给人接手，能救回来说明错误在 $k$ 之后。**不能用搜索报错关键字代替。**
- **第三步：写成结构化记录。** 每条轨迹产出一条 JSON 或 YAML 记录，包含**任务名、首错步号、错误类别、根因责任方、原文证据**，并区分主因与后果。
- **第四步：与现成笔记对照。** 把结果与仓库中的 `t3a_failed_analysis.md` 逐条比较并记录分歧。这份归因笔记**不是标准答案**。特别注意根因归属：该笔记原本把图片转录失败记成「视觉模型缺乏 OCR 能力」，而 T3A 的观察空间里根本没有图像像素，真正的根因是观察通道缺失。
- **第五步：转成回归任务。** 挑出 3 条首错发生在 assistant message 上的轨迹，各截取首错之前的前缀，写出可接受动作集合与禁止动作，形成轨迹前缀回归任务。

**辅导讲解**（笔记补充，非原文）

- 先把那组数字算清楚（笔记补充的计算）：$240/704\approx34.1\%$ 的失败率；其中信息告知出错 162 次；环境状态正确但信息告知错误 80 次，$80/240=1/3$，与原文「占全部失败的三分之一」一致。**这 80 次是最容易被漏掉的一类**——如果只看环境状态，它们全都会被判为成功。
- 「做对了但说错了」的严重性在于：**工具调用对了、状态改对了，但用户收到的信息是错的**。对客服、金融、医疗这类场景，用户按错的信息行动可能比「任务没做完」更危险。
- T3A 那个例子的教学价值有两层：
  1. **首错可能不报错、也不是工具调用。** 第 8 步是一句「我看不到图片内容」的思考。所以静默失败只能靠「事实锚点比对」（把陈述与工具返回值对齐）或「轨迹前缀二分」来找，搜 error 关键字是找不到的。
  2. **根因归属认错，修复方向就全错。** 把它记成「模型缺乏 OCR 能力」→ 去换模型、去做 OCR 训练；把它记成「Harness 观察通道缺失」→ 去给纯文本 Agent 补上图像描述或视觉输入。原文明确说：**真正该做的是补观察通道**。
- 实验 7-6 的第二步给了两个可操作的定位手法，值得记住：
  - **事实锚点比对**：把 Agent 的每一句陈述与工具返回值逐步对齐，找**第一次背离**。
  - **轨迹前缀二分**：把轨迹截到第 $k$ 步交给人接手。如果人接手后能救回来，说明错误在 $k$ 之后；救不回来，说明 $k$ 之前就已经坏了。这实际上是用「人工接管」当二分查找的判据。
- 第四步「与现成笔记对照」的设计很聪明：它让你**用一份已知有错的参考笔记**练手，逼你去质疑权威，而不是抄答案。原文特意点明那份笔记把根因记错了——这就是在训练「不要接受既有的归因结论」。

**易混点**

- **「环境状态正确但信息告知错误」≠「任务失败」**：按多数评估口径它会记成功。这正是原文说它「容易被整体成功率掩盖」的原因。
- **「模型能力不足」与「Harness 观察通道缺失」在表面上很像**（都是「Agent 看不到图就乱写」），区分方法是查观察空间里到底有什么：T3A 里只有元素树，没有像素，所以是通道问题而不是能力问题。

**一句话记住**

> 多数评估只看环境状态，于是「做对了但说错了」被系统性地漏掉；首错可能是一句不报错的思考，根因归属错了修复方向就全错。

**7.5.2.2 作用域敏感的文档格式错误**

**原文要点**

- 用户说「引号格式不对」时，**不能直接把它转成全局字符替换**。至少要区分 **ASCII 直引号**（`"`、`'`）、**中文弯引号**（`“”`、`‘’`）和 **Markdown 反引号**（`` ` ``）。同一字符在**中文自然语言、英文原文、行内代码、代码块、代码注释、JSON 和路径**中承担的语法角色不同。
- 评估数据应先把文档解析为**带作用域的片段**，例如 `ZH_PROSE`、`EN_PROSE`、`QUOTED_SOURCE`、`INLINE_CODE`、`CODE_BLOCK`、`CODE_COMMENT` 和 `JSON_OR_SCHEMA`。每个片段保存**允许变换集合、必须保护的字符以及修改后的验证器结果**。下面三处不能用同一条替换规则处理：

```text
中文说明：调用`reset()` 方法。
这是一段英文原文：“Please restart the service.”
# 以下代码块仅用于说明受保护作用域
# 中文注释：显示"当前状态"
name = "status"
```

- **轨迹前缀回归应要求模型做最小修改**，并同时检查**中文文档风格、英文原文保持率、代码和 JSON 语法，以及非目标文本的编辑距离**。规则无法确定作用域时，应允许模型**保留原文并请求澄清**，而不是把**猜测性修改**算作通过。

> ℹ️ 说明：上面示例中的引号字符需要单独交代。原书此处刻意用了不同的引号——中文正文里的英文引文用的是**弯引号**（`这是一段英文原文：“Please restart the service.”`），而代码注释里用的是 **ASCII 直引号**（`显示"当前状态"`），正是为了说明「同一个字符在不同作用域里的语法角色不同」。笔记此前转录时把这两处弯引号抄成了直引号，现已按原书还原。**这不是原书的错误**，也不是 PDF 提取造成的（原书提取文本里这两类引号是分开的、可分辨的）。

**辅导讲解**（笔记补充，非原文）

- 这一小节讲的是一个非常具体的陷阱：**「格式纠错」类任务里，错的是「这个位置的这种字符」，而不是「全文的这类字符」**。全局替换之所以危险，是因为同一个字符在不同作用域里身份不同：
  - 在 `ZH_PROSE` 里，`"` 可能是该被改成弯引号的错误；
  - 在 `EN_PROSE` 或 `QUOTED_SOURCE` 里，`"` 是**原文的一部分，必须保持**；
  - 在 `INLINE_CODE`、`CODE_BLOCK`、`JSON_OR_SCHEMA` 里，`"` 是**语法字符，改了代码就跑不起来**。
- 所以「先把文档解析为带作用域的片段」这一步不能省。这也是一个通用的评估设计模式：**当一个任务的作用域需要判断时，评估数据里就应该显式标注作用域**，否则验证器无法判断「这次替换该不该发生」。
- 「非目标文本的编辑距离」这个指标很实用：它检查模型有没有顺手改了不该改的地方。加上这几个检查项，一条看似简单的「改引号」任务就有了五个可量化的验收面：中文文档风格、英文原文保持率、代码语法、JSON 语法、非目标文本编辑距离。
- 「规则无法确定作用域时，应允许模型保留原文并请求澄清」是一条很重要的产品化原则：**把「不确定就先问」变成得分行为，而不是失分行为**。否则模型的最优策略永远是在不确定时瞎猜——猜对了得分，猜错了才扣分，而「问一句」反而要付出轮次成本。

**易混点**

- **「格式错误」不是一类错误，而是一族错误**：同一类字符在不同作用域里，有的是错误、有的是必须保护的内容。判断依据是**作用域**，不是字符本身。
- **原文说「至少要区分」三类引号**，说明这个清单不是穷尽的——笔记提醒：真正决定如何处理的是该片段所属的作用域标签。

**一句话记住**

> 格式纠错要先切作用域：同一个引号在中文正文里要改、在英文原文和代码里必须保护；不确定就允许「保留原文 + 请求澄清」。

**7.5.2.3 精确复制错误：从old_string mismatch 到逐层定位**

**原文要点**

- `old_string` 失败也**不能只归因于「模型抄错了」**。应对同一个字符串保存**原始字节哈希、Unicode code point 序列和tokenizer token ID 序列**，沿以下链路寻找**首个差异**：

```text
文件原始字节 → 工具返回 → Harness 序列化 → 模型上下文
→ 模型token 输出 → 解码字符串 → JSON/tool-call 解析 → 工具匹配
```

- **最小化评估探针**覆盖直接复述、从长上下文抽取、放入工具参数、相似字符串选择，以及空格、换行、反斜杠、Unicode 组合字符和低频token。**指标**使用 byte-exact match、code-point-exact match、token-exact match、首次分歧位置和真实工具成功率。
- **判断规则**：若模型在直接探针测试中输出正确而工具调用失败，应修复 **tokenizer、序列化、Harness 或工具协议**；**只有首个差异出现在模型输出时**，才把该案例转成第八章的复制训练数据。

**辅导讲解**（笔记补充，非原文）

- 这条链路的思路是**逐层设检查点**。一个字符串从文件到工具匹配要经过八道手，每一道都可能悄悄改动它：
  1. 文件原始字节（真值）；
  2. 工具返回（可能截断、可能转义）；
  3. Harness 序列化（可能在 JSON 里转义反斜杠、换行）；
  4. 模型上下文（可能被截断或被模板改写）；
  5. 模型 token 输出（可能因低频 token 或组合字符而出错）；
  6. 解码字符串（可能归一化 Unicode）；
  7. JSON/tool-call 解析（可能吃掉反斜杠）；
  8. 工具匹配（可能做过空格归一化）。
- 三个层级的匹配指标正对应链路的不同深度：**byte-exact**（字节级，最严）→ **code-point-exact**（字符级）→ **token-exact**（token 级）。如果 byte-exact 失败但 code-point-exact 通过，差异很可能出在编码或归一化；如果 token-exact 就失败了，问题更可能出在模型输出侧。
- 「若模型在直接探针测试中输出正确而工具调用失败」这个判据非常关键：它把**「模型抄错了」和「管道弄坏了」**分开。前者要去训练模型（第八章的复制训练数据），后者要去修 tokenizer / 序列化 / Harness / 工具协议——**修错了地方，做多少训练都没用**。
- 「最小化评估探针」这个词值得学：不要拿一整个复杂任务去测复制能力，而要设计最小场景（直接复述、长上下文抽取、放进工具参数、相似字符串选择）逐项隔离变量。这跟 7.9 节 AndroidWorld 的一轮只改一个变量是同一个方法论。

**易混点**

- **`old_string` mismatch 的原因可能完全不在模型**：序列化转义、Unicode 归一化、tokenizer 处理低频 token 都可能造成同一现象。所以原文说「不能只归因于模型抄错了」。
- **byte / code-point / token 三级匹配不是「越严越好」**：它们分别是不同层级的诊断工具，用来定位首个分歧发生在哪一层。

**一句话记住**

> `old_string` 匹配失败要沿「字节 → 序列化 → token → 解析 → 匹配」逐层找首个差异；只有差异出在模型输出时才去训模型。

### 7.5.3 端到端回归任务与轨迹前缀回归任务

**原文要点**

- 失败归因明确了首个错误及其类别，下一步是把修复目标写成**可重复执行的测试用例，即回归任务（regression task）**。这里需要**两层互补**的回归任务：**端到端回归任务**验证改动没有破坏完整工作流；**轨迹前缀（trajectory prefix）回归任务**则截取首个错误之前的状态，只验证那个决策边界是否被修好。
- **端到端回归任务**从初始状态和用户请求开始，让 Agent 完成整个任务，并检查最终状态、必要输出和安全条件。它**最接近生产结果，却难以判断失败究竟发生在哪一步**。一般来说，端到端回归任务用于验证 Agent 在各个领域的能力符合预期。**本章所述的 OSWorld、AndroidWorld、tau-bench 等标准评测集都是端到端回归任务。**
- **轨迹前缀回归任务**把已有的上下文、对话、工具返回和环境状态**冻结**下来，只要求 Agent 思考并执行**下一步或下几步可观察动作**，成本更低，也能**隔离单个策略或工具问题**。对于需要高可靠性的生产级 Agent，**构建轨迹前缀回归任务集往往比端到端回归任务集更重要**，也需要开发者耐心建立上一节所述的失败分类体系和失败归因系统。
- 轨迹前缀回归任务的**答案应定义为可接受动作集合，而不是唯一的动作或答案**：可以要求「先读仓库规则」「先询问用户」或「拒绝危险操作」，同时列出**禁止动作**。
- 失败归因完成后，就可以构造包括端到端和轨迹前缀回归任务在内的评估数据集。以 Coding Agent 为例：
  - **流程缺失**应生成带有计划文档和测试验收条件的端到端回归任务；
  - **工具调用错误**应把出错前缀截断并编辑成边界任务，测试模型能否修正格式、转义特殊字符或换用合适工具；
  - **执行异常**应加入截断、超时和工具故障的恢复场景；
  - **完成度与逻辑错误**应加入多目标清单、剩余任务提醒和「尚未证明不可能」的边界；
  - **需求理解与歧义类**应把有多种合理解释的任务冻结成前缀，把「先澄清」列入可接受动作；
  - **症状修复与验证造假类**则应在验收里补上「**不得修改测试断言**」和「**完成声明必须附带真实执行过的命令输出**」两条硬约束；
  - **信息反馈类**应在验收里对**答复内容本身**设断言，而不只检查环境状态。
- 评估数据集是第八章模型后训练和第九章 Agent 自我进化的基础。

**实验7-7 ★★：轨迹前缀边界评估：同一上下文的多种表示**

前置要求：需理解本节的轨迹前缀评估协议；本次案例使用第三章的用户记忆表示和 LLM-as-a-Judge 一节的 Rubric 设计，**不要求运行完整的 60 用例端到端记忆矩阵**。

- 本实验**不测试「上下文检索器有没有找回信息」**，而是把一组已经提供给 Agent 的上下文（本案例使用用户记忆）、当前任务、trajectory prefix、工具返回和环境状态一起输入模型，**要求模型只输出下一步可观察动作**。用例来自三类生产问题案例：用户纠正、点踩关联轨迹，以及事后规则/LLM 审计发现的错误。边界覆盖论文风格与 X 帖子的作用域冲突、worktree/PR 习惯与仓库规则冲突、当前明确指令覆盖旧偏好、低置信度推断、高风险删除前确认，以及对外发布前预览等情况。
- 对同一组用例运行 **JSON Cards、Markdown 和 Python-like 三种语义等价的表示**。它们是用户记忆这一案例的三种编码；换成 RAG 证据、系统提示或工具观察时，也可以沿用同一套轨迹前缀评估协议。评分由**确定性规则**完成：决策类别是否属于允许集合、下一步动作是否安全、是否出现要求的证据、是否触发禁止动作，以及上下文是否在该场景被正确使用。
- 配套实验使用 **GPT 5.6 Sol** 模型，完成了 **11 个边界用例 × 3 种表示，共 33/33 个 API 单元且没有 API 错误**。**三种表示的总成绩碰巧都是 6/11**，但失败位置并不完全相同：**Markdown 通过了「仓库规则未知时先检查」的用例，却多失败了一个作用域冲突用例；JSON Cards 和 Python-like 的情况相反**。三种表示**都没有通过**论文风格过度泛化、过时偏好覆盖当前要求、以及高风险删除前确认这三类用例。这个小样本评估说明，**改变上下文的表示方式并不会自动修复应用策略**。
- 在实际的模型选型中，我们经常面对的问题是：「A 和 B 哪个更好？」配对比较提供了一种**不依赖绝对分数**的评估方式。

**辅导讲解**（笔记补充，非原文）

- 两种回归任务的取舍表：

  | | 端到端回归任务 | 轨迹前缀回归任务 |
  | --- | --- | --- |
  | 起点 | 初始状态 + 用户请求 | 首错之前的状态（上下文/对话/工具返回/环境全部冻结） |
  | 要模型做什么 | 完成整个任务 | 只输出下一步或下几步可观察动作 |
  | 检查什么 | 最终状态、必要输出、安全条件 | 那个决策边界 |
  | 成本 | 高 | 低 |
  | 缺点 | 难以判断失败发生在哪一步 | 覆盖的只是单个决策点 |
  | 用途 | 保证整体能力不退化 | 隔离并锁定单个策略或工具问题 |

  这张表是笔记补充的整理，但每一格都来自原文的表述。
- 为什么原文说「轨迹前缀回归任务集往往比端到端回归任务集更重要」？因为**生产事故往往出在某个决策点上**（该不该先问、该不该删、该不该改测试），而端到端跑一遍只能告诉你「整体掉分了」。轨迹前缀把成本压到最低的同时，恰好钉住了那个决策点。
- 「答案定义为可接受动作集合，而不是唯一答案」是这一节的另一个要点，它对应一个现实：**同一个决策边界可能有多种正确处理方式**（先读仓库规则，或者先问用户，都可能对）。如果回归任务只接受唯一答案，就会把正确的替代行为判错，逼模型去猜「出题人想要哪一个」。
- 从错误类别到回归任务的对应关系，可以记成一句话：**流程类错误做成端到端任务（因为它涉及整条工作流），决策类错误做成前缀任务（因为它只涉及一步）**。原文给的最后两条尤其值得注意：
  - 「症状修复与验证造假类」要在**验收**里加硬约束（不得修改测试断言、完成声明必须附真实命令输出）——这是在**判分层面**堵住 7.5.2 表里的 hack 验证环境；
  - 「信息反馈类」要对**答复内容本身**设断言——这是在补 7.5.2.1 那个「环境状态对但信息说错」的漏洞。
- 实验 7-7 的结论非常有价值：**三种等价表示总分一样（6/11），但失败位置不同**。这说明「换一种上下文表示」不会自动带来提升，只会把失败挪到别的地方。三种表示都失败的三个用例（论文风格过度泛化、过时偏好覆盖当前要求、高风险删除前确认）指向的是**共同的应用策略缺陷**，不是编码问题——所以修的对象应该是策略，而不是表示格式。

**易混点**

- **「端到端回归任务」与「标准评测集」的关系**：原文说 OSWorld、AndroidWorld、tau-bench 这些标准评测集**都是**端到端回归任务。也就是说，你在跑基准的时候其实已经在做端到端回归了，缺的是轨迹前缀那一层。
- **轨迹前缀回归 ≠ 轨迹回放**：回放是要求模型重复原来的动作；轨迹前缀回归是把历史冻结、只让模型决定下一步，答案是一个**可接受动作集合**。

**一句话记住**

> 端到端回归保「整体不退化」，轨迹前缀回归钉「那个决策点有没有修好」；后者更便宜，对生产级 Agent 往往更重要。

### 7.5.4 配对比较与模型排名

> 图 7-6（原文插图）Elo 评分与配对比较排名。图分三块：
> - **Chatbot Arena 匿名对决**：左边 Model A（匿名）给出「退款已处理,将在3-5个工作日到账您的账户」，右边 Model B（匿名）给出「好的退款会处理的」，中间标 VS；下面写着「用户盲选 → A 更好」。
> - **Elo 更新公式**：预期胜率 $E_A = 1/(1+10^{((R_B-R_A)/400)})$；更新 $R_A' = R_A + K\cdot(S_A-E_A)$。
> - **实时排行榜（示例）**：一张表，列为「排名 / 模型 / Elo / 胜率 vs #2」，共 6 行：1 Claude 4 Opus 1352（—）、2 GPT-5 1318（—）、3 Gemini 2.5 Pro 1290（45%）、4 DeepSeek R2 1265（42%）、5 Qwen 3 Max 1230（39%）、6 Llama 4 405B 1198（36%）。
> - **底部一行**：GRPO——将配对比较引入 RL 训练：一组候选响应 → 相对优势归一化 → 策略更新（绕过显式奖励模型）。

**原文要点**

- **Elo 评分**（一种最初用于国际象棋的排名系统）通过大量的两两对决来量化模型的相对能力：分差越大，强者的预期胜率越高。例如，模型 A 得分 1200、模型 B 得分 1000，Elo 系统会预测 A 的胜率约 **76%**。如果 B 意外获胜，**B 加分较多、A 减分较多**——爆冷的结果会带来更大的分数调整，这种机制让排名快速收敛到真实水平。
- 其背后的统计基础是 **Bradley-Terry 模型**：将每个模型抽象为一个潜在的「实力分数」，两两对决胜负的概率由两者分数差决定，**Elo 则是该模型在线更新形式的一种工程实现**。
- **Chatbot Arena** 采用**匿名随机对决**——用户在不知道模型身份的情况下盲选更优回应，通过数百万次投票得出排名。这种方法的优势在于**不需要定义「绝对标准」**，只需要人类判断「A 和 B 哪个更好」。但也有局限：**排名结果取决于用户提了什么问题**——如果大量用户恰好都问编程题，擅长编程的模型排名就会偏高，这未必反映它在其他任务上的真实水平。
- 当配对评判由 LLM 而非人类投票完成时，还要防范**位置偏差（Position Bias）**——评判模型会系统性地偏向出现在某个位置（通常是先出现）的候选，即使两个候选的内容完全对调，判决也可能不变。标准的缓解方法是**交换顺序各评一次**：A 在前评一次、B 在前再评一次，取两次结果的平均；更严格的做法是**只有两次判决一致时才计入**，不一致则记为平局或送人工复核。Chatbot Arena 的做法本质相同——**随机化两个回答的展示位置，让位置偏差在大样本下相互抵消**。

**实验7-8 ★★：从配对比较数据构建模型排行榜**

- 本实验从零实现 Elo rating 计算系统，以深入理解 Bradley-Terry 模型如何从大量配对比较中提取相对能力评分。实验使用 Chatbot Arena 开源的真实投票数据集（包含数百万次用户盲选投票）。
- **实现 Elo rating 迭代更新算法**：初始所有模型评分 1000 分，按时间顺序处理投票记录。对每场对决，根据两个模型当前的评分差计算预期胜率，将实际结果与预期比较，按固定学习率调整——胜者加分、败者减分，调整幅度与预期偏差成正比（爆冷失败会导致更大的分数变化）。按最终评分降序排列并计算两两胜率矩阵，与官方榜单对比、验证排名大体一致即可。**不必苛求逐分对齐**：Chatbot Arena 官方用的是 **Bradley-Terry 极大似然拟合**（对全部对局一次性求解，与投票的先后顺序无关），而这里实现的是**在线增量更新的 Elo**（结果受学习率 $K$ 因子和处理顺序影响），两种算法在总体排名上应当吻合，但具体分值不会精确一致。
- **实验第二部分创建历史排名演进动画**：将投票数据按时间切片（每周或每月），对每个时间点计算 Elo 评分快照。使用 **D3.js** 实现条形图竞赛动画（水平条形长度= 评分，纵向位置= 排名，随时间平滑变化）。通过观察动画识别**技术突破时刻**（某模型评分骤升）、**竞争格局演变**、**模型生命周期**。

**辅导讲解**（笔记补充，非原文）

- Elo 公式的符号逐个解释（笔记补充）：

$$E_A=\frac{1}{1+10^{(R_B-R_A)/400}},\qquad R_A' = R_A + K\,(S_A-E_A)$$

  其中 $R_A$、$R_B$ 是对局前 A、B 两人的评分（Elo 分，无量纲，常以 1000 为起始值）；$E_A$ 是 A 的**预期胜率**（$0\le E_A\le 1$，无量纲）；$S_A$ 是**实际结果**（胜记 1、平记 0.5、负记 0）；$K$ 是学习率（即单场最大调整幅度，单位与评分相同）；400 是 Elo 的标度常数，含义是「分差 400 分时强者预期胜率约为 $1/(1+10^{-1})\approx 90.9\%$」；10 是底数，来自 Elo 体系的历史约定。
- 原文那个例子代进去复算（笔记补充的计算）：$R_A=1200$、$R_B=1000$，则 $E_A=1/(1+10^{(1000-1200)/400})=1/(1+10^{-0.5})=1/(1+0.31623)=0.7597\approx76\%$，与原文「预测 A 的胜率约 76%」一致。若这次 B 爆冷获胜（$S_A=0$），则 $R_A'=R_A+K(0-0.7597)=R_A-0.7597K$——**A 掉分接近满额**；而 B 的更新是 $R_B'=R_B+K(1-E_B)$，其中 $E_B=1-0.7597=0.2403$，所以 B 加分 $0.7597K$。这就是原文说的「爆冷的结果会带来更大的分数调整」。
- 为什么这套机制能收敛到真实水平？因为**预期的偏差越大，调整越大**：如果 A 本该赢却输了，说明评分高估了 A，于是大幅下调；如果 A 赢了但对手很弱（预期本来就接近 1），$S_A-E_A$ 很小，几乎不动。长期下来，评分会自己找到那个「预测胜率与实际胜率相符」的位置。
- Bradley-Terry 与 Elo 的关系值得分清（原文明确给了这层关系）：**Bradley-Terry 是模型**（给出「实力分数 → 胜负概率」的参数化形式，用全部数据一次性做极大似然拟合），**Elo 是它的在线更新实现**（按顺序逐场更新，所以结果会受 $K$ 和处理顺序影响）。这就解释了为什么实验 7-8 说「两种算法在总体排名上应当吻合，但具体分值不会精确一致」。
- 位置偏差的缓解方法有一个「强度阶梯」：
  1. **随机化展示位置**（Chatbot Arena 在人类投票里的做法）——靠大样本让偏差相互抵消；
  2. **交换顺序各评一次、取平均**——靠对称性抵消，样本需求更小；
  3. **只有两次判决一致才计入**，不一致记平局或送人工复核——最严格，代价是丢样本。
- Chatbot Arena 的局限值得记住：它测的是**「在用户实际提出的问题分布上的相对偏好」**，不是「在你业务上的能力」。如果提问分布偏斜（比如大量编程题），排名就会偏斜。这条局限正好呼应 7.4.6 节「公开基准的任务分布与实际业务的任务分布并不一致」。

**易混点**

- **Elo 评分 ≠ 绝对能力分**：它只定义相对关系（分差决定预期胜率），1200 分本身没有绝对含义。
- **Bradley-Terry 拟合 ≠ Elo 迭代**：前者与对局顺序无关，后者依赖顺序与 $K$。原文在实验 7-8 里特意提醒「不必苛求逐分对齐」。
- **位置偏差（Position Bias）≠ 长度偏差（Length Bias）**：位置偏差是「偏向先出现的候选」，用交换顺序缓解；长度偏差是「偏向更长的回答」，用惩罚冗长/长度对齐/相关性审计缓解（见 7.5.1）。

**一句话记住**

> 配对比较不需要绝对标准，只需要判断「A 和 B 哪个更好」；Elo 是 Bradley-Terry 的在线实现，用 LLM 评判时务必交换顺序防位置偏差。

**原文要点**

- **模型选择不是简单地「选最强的模型」，而是要根据应用场景和评估结果在多个维度之间作出权衡。**

**辅导讲解**（笔记补充，非原文）

- 这一节把 7.1–7.5 建立的评估能力接到一个具体决策上：选模型。原文的立场是「权衡」而不是「选最强」——因为「最强」既没有定义，也不一定在你的任务上最强（这正是 7.6.4 节那个 Gemini 案例要说明的）。

### 7.6.1 选型的关键维度

**原文要点**

- **吞吐量与延迟是两组容易混淆的指标**，理清它们只需知道**大模型推理分两个阶段**：
  - **Prefill（预填充）**：一次性读入完整上下文，决定用户按下回车到第一个字出现的**首字延迟**（业内用 **TTFT**，Time To First Token 度量）——**上下文越长 prefill 越慢、TTFT 越大**。
  - **Decode（解码）**：随后逐 token 生成回答，决定后续出字速度（tokens/秒），也直接决定思考时长：**一个 50 tokens/s 的模型生成 2000 个思考 token，光思考就要 40 秒**。
- 围绕这两个阶段，主要的吞吐与延迟指标如下：
  1. **输入吞吐量 / 输出吞吐量**：分别对应 Prefill 和 Decode 的速度。
  2. **TTFT**：等于**排队时间加上 Prefill 时间**，是用户感知的「反应快慢」。
  3. **思考延迟**：不同模型生成的思考 token 数**差异可达数倍**，且**思考长度与任务效果不一定正相关**。应在自己的工作负载上实测各模型的思考 token 用量和对应收益，而非仅凭公开榜单推断。
  4. **p95 尾部延迟**：95% 的请求都不会超过的延迟。**它比平均值更能反映真实用户体验**——均值会被大量快速请求拉低，掩盖少数用户遭遇的严重卡顿。
  5. **成本**：输入/输出/缓存 token 的定价。**一个便宜但成功率低的模型，因为需要频繁重试，实际花费可能反而更高。** 需要计算每个任务的**平均成本**和**成本-性能比**。
  6. **性能**：Pass@1、Pass@k、Pass^k、Best@k 等指标的精确定义见前文「评估指标：成功的定义」（**Pass@1 即 $k=1$ 的 Pass@k，单次平均成功率**）。日常场景看最常用的 Pass@1；关键操作场景优先 Pass^k，盯的是「每次都别出错」的稳定性；探索性任务优先 Pass@k 或 Best@k，看的是给足机会后的能力上限。
  7. **速率限制与可靠性**：RPM（每分钟请求数）/ TPM（每分钟 token 数）限制会影响并发能力，某些 API 在高峰期还会动态调整限额。鲁棒性方面需关注**分布外数据、对抗性输入、长时运行稳定性**（是否出现模式崩溃、注意力分散等问题）。
  8. **预算—能力曲线**：**固定预算下的单点成绩不足以判断 Agent 能否胜任长程任务。** 除了成功率，还应报告性能随**墙钟时间、token、工具调用次数或算力预算**变化的曲线。RE-Bench 的人机对照很能说明问题：**在每个环境 2 小时的总预算下，最佳 Agent 得分约为人类专家的 4 倍**；但**人类从增加时间预算中获得的收益更大，8 小时时已略微超过最佳 Agent，在跨多次尝试合计 32 小时时得分约为其 2 倍**。因此，**短预算领先不能直接外推成长时间运行能力**，选型时必须在接近真实任务时长的多个预算点上比较。
- 实践中可以采用**多模型协同**的策略：用轻量模型处理简单请求以降低成本，用强大模型处理复杂任务以保证质量；或者使用专门的模型处理特定的子任务（如图像理解、代码生成），通过**子 Agent 机制**进行协作。这种异构的模型组合需要通过评估来验证，确认整体效益是否超过了所增加的系统复杂度，以及**是否会在一些场景下出现性能回退**（例如，把「9.9 跟 9.11 哪个大」「要洗车，家离洗车店 50 米，是走路去还是开车去」等问题视为简单问题交给轻量模型，导致决策错误）。

**辅导讲解**（笔记补充，非原文）

- Prefill / Decode 这对概念是理解所有延迟指标的地基，用一张表对比：

  | | Prefill（预填充） | Decode（解码） |
  | --- | --- | --- |
  | 做什么 | 一次性读入完整上下文 | 逐 token 生成回答 |
  | 决定什么 | 首字延迟 TTFT | 后续出字速度（tokens/秒） |
  | 受什么影响 | 上下文越长越慢 | 输出长度 / 思考长度 |
  | 对应吞吐指标 | 输入吞吐量 | 输出吞吐量 |

  这张表是笔记补充的整理，内容来自原文对两个阶段的描述。
- 原文那个 40 秒的算式值得复算（笔记补充的计算）：$2000\ \text{tokens}\div 50\ \text{tokens/s}=40\ \text{s}$。这个数字说明**「思考延迟」是一个独立的、不可忽略的时间成本**，尤其在长思考模型上——用户按下回车后，可能要等四十秒才开始看到输出。
- 指标里最容易搞混的是 **TTFT 与总延迟**：TTFT 是「第一个字什么时候出来」，总延迟是「最后一个字什么时候出来」。TTFT 包含排队时间，所以**高峰期同一个模型可能 TTFT 变长而总延迟差不多**。选型时这两个要分开测。
- 为什么强调 **p95** 而不是平均值？原文的解释很直白：均值会被大量快速请求拉低，掩盖少数用户遭遇的严重卡顿。工程上的经验法则（笔记补充）：**平均值看容量规划，p95/p99 看用户体验**。
- 成本那一项要特别注意那条反直觉结论：**便宜但成功率低的模型可能更贵**。原因就是「频繁重试」——单次便宜，但要多跑几次才成功，而且每次重试都带着更长的上下文（见 7.6.3 节的上下文累积效应）。所以正确的比较量是「**每个任务的平均成本**」，不是「每百万 token 的单价」。
- 预算—能力曲线是本节最容易被忽略、也最有价值的一条：它说**单点分数会骗人**。RE-Bench 的人机对照给出一个非常清晰的模式：
  - 2 小时预算：Agent 是人类专家的约 4 倍（Agent 起步快）；
  - 8 小时：人类已略微超过最佳 Agent（人类后劲足）；
  - 多次尝试合计 32 小时：人类得分约为 Agent 的 2 倍。
  - 结论是**曲线会交叉**。所以如果你的真实任务是「跑 8 小时」，就不能拿 2 小时的分数做选型。
- 多模型协同里那两个「简单问题」的例子很经典：**「9.9 跟 9.11 哪个大」**（版本号直觉 vs 数值比较的陷阱）和**「要洗车，家离洗车店 50 米，是走路去还是开车去」**（要看「开着车去洗」这个隐含前提）。它们表面上都是短问题，实际需要常识推理，交给轻量模型就会出错。**「题目短」不等于「任务简单」**——这是路由策略最常见的坑。

**易混点**

- **吞吐量 ≠ 延迟**：吞吐量是「单位时间能处理多少」（输入吞吐量对应 Prefill，输出吞吐量对应 Decode），延迟是「一次请求要等多久」（TTFT、p95）。两者可以反向变化。
- **TTFT 与思考延迟不是一回事**：TTFT 主要是排队 + Prefill 的开销；思考延迟是 Decode 阶段生成思考 token 的时间。前者是「多久开口」，后者是「想多久」。
- **Pass@1 与 Pass@k 在选型里的用途不同**：原文明确——日常看 Pass@1，关键操作看 Pass^k，探索性任务看 Pass@k / Best@k。

**一句话记住**

> Prefill 定 TTFT、Decode 定出字速度；成本要看「每个任务的平均成本」，能力要看「预算—能力曲线」而不是单点分数。

### 7.6.2 模型的行为策略

**原文要点**

- 模型选型不只是在比较「能不能做成」，还要比较**模型默认会怎样做**。Coding Agent 中一个很容易观察到的差异是**行动阈值**：面对同一个代码任务，**有的模型会先广泛探索仓库再修改；有的模型则凭较少的局部证据快速定位，先改再用测试反馈补齐认识**。前者把**过早修改的风险**估得更高，后者把**「再读一个文件」的机会成本**估得更高。
- Agent 的这种倾向有两个来源：一是 **Harness 中的系统提示词**，二是**模型的行为策略**。**后训练是模型行为策略的关键来源**：SFT 轨迹会示范「先读到什么程度再动手」，过程奖励会奖励或惩罚某种工具路径，结果奖励又会强化最终成功的整套策略。**久而久之，模型学到的不只是如何写代码，也包括工程习惯。**

**实验7-9 ★★：在固定Coding Harness 中测量模型的行动阈值**

- **实验目标**：隔离模型因素，量化不同 Coding 模型在「继续收集信息」与「开始修改代码」之间的默认取舍，并把**路径效率与最终质量联合起来评价**。
- **技术方案**：默认通过**同一个 OpenRouter OpenAI-compatible 端点**调用 **GPT-5.6-sol 与 Claude Sonnet 5**，固定系统提示、工具 Schema、任务仓库、测试命令和最大轮次；**中性提示既不要求读够若干文件，也不要求尽快编辑**。三个小型代码库分别覆盖**局部 bug、跨模块身份规范化和公共契约敏感的缓存修复**，每个模型对每题独立运行三次，**共 18 条轨迹**。
- **因果判断**：中性实验回答「同一 Harness 下，行为是否随模型变化」。如需测 Harness 的调节作用，再用 `--policy explore-first` 单独跑一组；**不要把两种 policy 混在同一模型比较里**。若更换模型时行为改变、而同一模型跨 Harness 保持倾向，则证据更支持**模型效应**；反之则更支持 **Harness 效应**。
- **实验发现**：
  - GPT-5.6-sol 在第一次修改前平均调用工具 **6.89 次**、读取 **4.67 个文件**；
  - Claude Sonnet 5 分别为 **4.56 次和 3.56 个文件**；
  - 差距在**局部任务**中最明显，而在**明确跨模块的任务**中几乎收敛（**7.00 对 6.67 个文件**）；
  - 两者的**首个受测补丁和最终测试均为 100% 通过**，因此这个小实验支持的是「**行动策略随模型而变**」，而不是「多读或早改必然更好」；
  - **时间到首次修改也几乎相同（15.01 秒对 14.48 秒）**，提醒我们**工具步数、并行调用和模型延迟必须分开看**。

**辅导讲解**（笔记补充，非原文）

- 「行动阈值」这个词可以这样理解：**模型在动手之前要求多少证据**。阈值高的模型先读一批文件再改；阈值低的模型看到一个可疑函数就改，靠测试反馈纠错。两者都不是「错」，只是**风险偏好不同**。
- 这个实验的设计值得当作「隔离模型因素」的范本，因为它把可能混淆的变量都摁住了：
  - **同一个端点**（OpenRouter OpenAI-compatible）→ 排除不同 API 实现带来的差异；
  - **固定系统提示、工具 Schema、任务仓库、测试命令、最大轮次** → 排除 Harness 差异；
  - **中性提示**（既不要求读够若干文件，也不要求尽快编辑）→ 不诱导任何一种策略；
  - **三类代码库 × 每题三次运行** → `18 = 2 模型 × 3 任务 × 3 次`（笔记补充的计算，与原文「三个小型代码库、每题独立运行三次、共 18 条轨迹」一致）。
- 「中性提示 + `--policy explore-first` 单独跑一组」是这套实验设计的关键：**先用中性提示测「模型自带的倾向」，再单独加一组带 policy 的测「Harness 的调节作用」**。原文特意警告「不要把两种 policy 混在同一模型比较里」——混在一起就无法区分「这个差异是模型带来的还是提示词带来的」。
- 实验发现里有三个容易被读错的地方：
  1. **「多读」不等于「更好」**：两个模型首个补丁和最终测试都是 100% 通过。所以 GPT-5.6-sol 读得多并不代表它更强，只代表它更谨慎。
  2. **任务越明确，差异越小**：局部任务里差距明显（4.67 对 3.56 个文件），明确跨模块的任务里几乎收敛（7.00 对 6.67）。**任务结构本身会「压平」模型间的行为差异**。
  3. **工具步数 ≠ 耗时**：两个模型的「时间到首次修改」几乎相同（15.01 秒对 14.48 秒），但工具调用次数差了约 2.3 次。这说明**步数差异被并行调用和模型延迟吸收了**——原文的提醒是「工具步数、并行调用和模型延迟必须分开看」。只看步数会得出错误结论。
- 为什么「后训练会塑造工程习惯」这件事对选型重要？因为**如果你需要的是一种工作风格（比如「不许在没读规范前动手」），你可以选一个默认就这样的模型，也可以自己在 Harness 里用提示词约束**。原文给的判别方法在实验 7-9 的「因果判断」里：**换模型行为变、同一模型跨 Harness 不变 → 模型效应；反之 → Harness 效应**。

**易混点**

- **行动阈值（模型属性）与提示词要求（Harness 属性）会产生同样的现象**：都能让模型「多读几个文件」。区分只能靠实验设计（换模型 / 换 Harness 分别观察）。
- **步数多 ≠ 成本高**：步数多可能伴随并行调用，端到端耗时未必更长。原文用「时间到首次修改几乎相同」印证了这一点。

**一句话记住**

> 模型选型也要比「默认怎么做」——行动阈值是模型的行为属性，来自后训练；它会随任务明确度上升而收敛。

### 7.6.3 Agent 系统的成本分析

**原文要点**

- 7.6.1 节把成本列为模型选型的关键维度之一，但 **Agent 场景下的成本远比 token 定价复杂：多轮推理、工具调用和上下文累积会让它呈非线性增长。** 系统的成本分析既是评估体系不可或缺的一环，也是生产部署的必要前提。
- **成本的构成要素。** Agent 系统的成本可分解为三个层次：
  1. **模型推理成本**：最直接的部分，由输入 token 和输出 token 的消耗决定。但 Agent 场景下有两个常被忽视的放大因素：
     - **上下文累积效应**：Agent 每轮调用 LLM 时，都会把之前所有的对话历史和工具返回结果一起发送（这样模型才能理解上下文）。如果没有利用好 **KV Cache**（即缓存已处理过的上下文，避免重复计算），成本增长会非常快——**第 1 轮发送 1000 token，第 2 轮发送 2000 token，第 3 轮发送 3000 token，总量是 $1000+2000+3000=6000$ 而非 $3\times1000=3000$，轮次越多差距越大**。
     - **思考 token 成本**：支持思考的模型会生成大量思考 token，这些 token **虽然不展示给用户，但同样计入费用**。
  2. **工具调用成本**：包括外部 API 费用（搜索引擎按次计费、数据库查询消耗计算资源）、代码执行的沙盒资源，以及一个容易被忽视的**间接成本：工具返回结果注入上下文后产生的 token 费用**。**一次网页搜索返回的内容可能就占用 2000-5000 个 token，而且在后续每轮推理中都会作为输入被反复计费。**
  3. **基础设施成本**：涵盖向量数据库（用于 RAG 检索）、消息队列、关系型数据库、日志与追踪存储（用于可观测性）等运维开销。
- **为了看清这些费用究竟从哪里来**，配套实验选了一个固定的**八轮客服退款任务**：查询订单、物流、退款政策和知识库，随后完成风控、退款、通知与关单。实验调用 **gpt-4o-mini**，分别打开或关闭「**稳定前缀**」和「**压缩历史**」两个开关，得到四组对照。

表 7-4 八轮Agent 任务的真实成本对照

| 方案 | 输入token | 缓存token | 总成本 | 比基线节省 |
| --- | --- | --- | --- | --- |
| 无缓存、无压缩 | 20,700 | 0 | \$0.003776 | — |
| 仅稳定前缀 | 20,386 | 13,568 | \$0.002707 | 28.3% |
| 仅压缩历史 | 16,177 | 0 | \$0.003115 | 17.5% |
| 稳定前缀+ 压缩 | 16,035 | 6,144 | \$0.002643 | 30.0% |

- 在基线组中，**每轮输入从 1,113 token 一路涨到 3,668 token**。工具返回会跟着历史反复进入后续请求，**八轮累计占了 9,544 个输入 token**。两项优化同时开启后，这个数字降到 **5,248**，**总费用下降 30%**。
- 不过，「仅稳定前缀」已经节省 **28.3%**，「仅压缩历史」又节省 **17.5%**，两者一起却只节省 **30%**，**并不是二者相加**。原因是**压缩历史的同时，也缩短了可以命中缓存的前缀**。因此，几项上下文优化同时使用时，**必须在完整任务中一起实测，不能把各自的节省比例直接相加**。
- **成本优化策略。** 从输入侧看，最值得优先测试的有三类办法：**复用 KV Cache**（也就是尽量保持前缀不变）、**压缩上下文**（减少旧轨迹和冗长工具返回）、以及**分层选择模型**（让轻量模型处理简单请求、强模型处理复杂推理）。第二章已经介绍了具体做法。这里要强调的是：**这些能力最好都能独立开关**，这样既能看清每一项的作用，也能检查它们合用时会不互相抵消。除此之外，还有两项与评估和运维直接相关的手段：
  - **异步批处理**：将非实时任务积攒起来批量处理，利用 API 提供商在波谷时段的批量定价折扣；在模型本地部署场景下，也能提高波谷时段的 GPU 利用率。
  - **成本监控与预算控制**：生产环境中应当建立实时的成本监控体系，按任务类型、模型、用户等维度追踪 token 消耗和 API 费用。同时设置**每个任务的成本上限**——当 Agent 陷入循环或探索过深时自动终止，防止单次任务产生异常高额的费用。

**实验7-10 ★：Agent 任务的端到端成本分析**

- **实验目标**：复现上述八轮任务的全链路成本拆解，并用自己的真实工作负载验证优化策略。
- **技术方案**：先复现配套仓库中的固定任务，再换成几个自己的典型任务。使用 **LangSmith 或自建追踪系统**记录每次 LLM 调用的输入/输出 token 数、思考 token 数、工具调用次数和返回大小、端到端延迟。计算每类任务的**平均成本、成本分布（p50/p95/p99）和成本构成比例**。
- **验收标准**：生成成本拆解报告，识别主要成本驱动因素。**四种开关组合都要运行**，既比较每项优化单独带来的变化，也检查两项优化合用后的结果。

**辅导讲解**（笔记补充，非原文）

- 上下文累积效应值得算清楚（笔记补充的计算）：

  | 轮次 | 本轮发送 token | 累计发送 token |
  | --- | --- | --- |
  | 第 1 轮 | 1000 | 1000 |
  | 第 2 轮 | 2000 | 3000 |
  | 第 3 轮 | 3000 | 6000 |

  原文的算式是 $1000+2000+3000=6000$，对照「以为是 $3\times1000=3000$」的直觉。推广一下就是等差数列求和 $n(n+1)/2\cdot 1000$（笔记补充的推广），**成本随轮数按平方增长**——这就是为什么长对话 Agent 的账单涨得比预期快得多。KV Cache 的作用正是把「已经处理过的前缀」缓存下来，避免每一轮都重算一遍那些重复的部分。
- 表 7-4 的四个节省比例可以逐个复算（笔记补充的计算）：
  - 仅稳定前缀：$(0.003776-0.002707)/0.003776=0.001069/0.003776\approx28.31\%$ → 28.3% ✓
  - 仅压缩历史：$(0.003776-0.003115)/0.003776=0.000661/0.003776\approx17.51\%$ → 17.5% ✓
  - 稳定前缀 + 压缩：$(0.003776-0.002643)/0.003776=0.001133/0.003776\approx30.01\%$ → 30.0% ✓
  - 三个结果都与原文一致。
- 「$28.3\%+17.5\%=45.8\%$，实测只有 30%」这个落差是全节最重要的工程教训。原因原文讲得很清楚：**两种优化会互相干扰**——压缩历史把旧轨迹删掉了，而缓存命中的前提是「前缀不变」，前缀一压缩，原本能命中的缓存段就失效了。所以：
  - **单项收益不能相加**；
  - 多项优化必须**在完整任务中一起实测**；
  - 这也正是原文强调「这些能力最好都能独立开关」的原因——只有能独立开关，才能做四种组合的对照实验（实验 7-10 的验收标准就要求跑完四种组合）。
- 三条输入侧优化其实对应三个不同的杠杆：
  - **KV Cache（尽量保持前缀不变）**→ 减少重复计算，**降的是「重算成本」**；
  - **压缩上下文（减少旧轨迹和冗长工具返回）**→ 减少输入的绝对长度，**降的是「基数」**；
  - **分层选择模型**→ 让便宜模型干简单活，**降的是「单价」**。
  - 三者作用点不同，所以会互相干扰也不奇怪（比如压缩上下文会破坏缓存前缀）。
- 「工具返回结果注入上下文后产生的 token 费用」这条最容易被漏算：一次网页搜索返回 2000–5000 token，**它在后续每一轮都会被重新计费**。所以真正的成本不是「这一次搜索多少钱」，而是「这次搜索的内容在剩下 $n$ 轮里被重复计费多少次」。这给了一个实践建议（笔记补充）：**对超长的工具返回做摘要/截断，收益是乘以后续轮次的**。
- 「每个任务的成本上限」是个很实际的护栏：Agent 一旦陷入循环（7.8 节的监控示例里就有「task#892 循环调用 search 14 次，耗 \$2.1」这样的异常），账单会失控。设上限自动终止，本质上是把「成本」也变成一个可中断的条件。

**易混点**

- **token 单价便宜 ≠ 总成本低**：还要看上下文累积、思考 token、工具返回的重复计费，以及重试次数。原文在 7.6.1 节已经提示过「便宜但成功率低的模型实际花费可能反而更高」。
- **KV Cache 的命中条件与前缀稳定性绑定**：这解释了为什么「压缩历史」会削弱「稳定前缀」的收益——两个优化不是正交的。

**一句话记住**

> Agent 成本按上下文累积呈非线性增长（1000+2000+3000=6000 而非 3000）；多项优化会互相干扰，节省比例绝不能相加。

### 7.6.4 评估驱动的持续迭代

**原文要点**

- **模型选择不是一次性的决策，而是随着模型演进需要动态调整的持续过程。** 本章开篇已经提出「拥有评估体系就能快速跟上模型演进」这一核心理念，下面用一个具体的模型切换案例，说明这套体系在真实决策中究竟如何运作。
- **案例**：假设你的 Agent 系统当前基于 **Claude** 构建，在工具调用和复杂编排上表现优异。某天 **Gemini** 发布了一个新模型，**公开基准显示它在多项指标上超越 Claude，而且定价更低**。此时你面临的问题**不是**「Gemini 是否比 Claude 强」，**而是**「**在我的特定任务上，Gemini 是否比 Claude 好？好多少？切换成本是什么？**」
- 拥有完善评估体系的团队可以在**数小时内**给出答案：在自己的评估数据集上运行新模型，对比**任务成功率、工具调用正确率、延迟和成本**。你可能会发现新模型在简单任务上确实更优且更便宜，但在涉及**复杂多轮工具编排**的核心场景中，**成功率反而下降了 5%**——在**确认这一差异超出噪声带宽之后**（见下文「评估结果的统计显著性」），你的决策就变成了「**简单任务迁移到新模型以降低成本，复杂任务保留原模型以确保质量**」的**差异化策略，而非盲目的全量切换**。这种精细化的数据驱动决策，**只有在预先构建好评估体系的前提下才可能实现**。

**实验7-11 ★★：多维度模型性能基准测试**

对主流 LLM 及不同 API 提供商进行全面基准测试，建立多维度模型选型决策数据库。

- **选择测试范围**：GPT 系列、Claude 系列、Gemini 系列、Doubao 系列等闭源 SOTA 模型，以及 Qwen、Kimi、DeepSeek 等开源模型。对**同一模型测试不同 API 提供商**（如 DeepSeek 官方 vs Siliconflow），验证第三方性能监测平台（如 **Artificial Analysis**）的结果。
- **设计标准化测试工作负载**：输入吞吐量测试使用固定长度上下文（**8K/32K/128K tokens**），输出吞吐量测试请求生成固定长度响应（**512/2048 tokens**）。延迟测试包含 TTFT（首个 token 生成时间）和端到端延迟，对支持思考的模型**单独测量思考长度与思考延迟**。每个配置**至少 100 次请求**，计算标准差/p50/p95/p99——**高延迟方差意味着用户体验不稳定**。

**实验7-12 ★★：用户记忆系统的端到端选型评估**

- 前置要求：需完成第三章上下文检索或智能体化 RAG 实验。
- **目标**：对用户记忆检索 Agent 做全链路选型评估，看**嵌入模型、reranker、Agent 主模型**三个选择点如何共同影响检索质量、延迟与成本。复用 `chapter3/contextual-retrieval-for-user-memory` 或 `chapter3/agentic-rag-for-user-memory`，在 **60 个测试用例**上对比。

**辅导讲解**（笔记补充，非原文）

- 这个案例的提问方式值得背下来：**不是「新模型是否更强」，而是「在我的任务上，它好在哪、差在哪、切换成本多少」**。前者是公开榜单能回答的，后者只有自建评估集能回答。
- 案例的结果形态很有代表性：**新模型在简单任务上更优更便宜，在复杂多轮工具编排上成功率反而下降 5%**。这就把决策从「切或不切」变成了「**分场景路由**」：
  - 简单任务 → 迁到新模型（省钱）；
  - 复杂多轮工具编排 → 保留原模型（保质量）。
  - 这类决策正是 7.6.1 节「多模型协同」策略的一个实例。
- 原文加了一个重要的限定词：**「在确认这一差异超出噪声带宽之后」**。5% 这个数字本身还不足以做决策——评估集有多大？置信区间多宽？这正是 7.7 节要解决的问题。如果评估集只有几十题，5% 的差异很可能只是抽样噪声。
- 实验 7-12 的「发现」写得非常精炼，值得展开理解：
  - **「更强的嵌入可能让 reranker 变得多余」**：如果第一轮检索已经很准，reranker 这个额外环节的边际价值就很小，反而增加了延迟和成本。所以 reranker 的评估必须带「不用 reranker」的基线，量化**边际价值**。
  - **「更强的主模型可能弥补检索的不足」**：Agent 主模型如果足够强，可能自己就能从不够准的检索结果里挑出正确的信息。这说明**组件之间是可替代的**——不能孤立地评估检索质量，要在端到端任务上看。
  - 这两条合起来说明一件事：**在一个多组件系统里，「每个组件都选最优」不一定等于「整体最优」**，必须做联合评估。
- 「三个选择点 × 60 个用例」的规模提示我们：全链路选型评估的组合数会迅速膨胀（嵌入 × reranker × 主模型），工程上要**分层筛选**（笔记补充）：先固定后两个、只比嵌入；再固定最优嵌入、比 reranker；最后比主模型。这也是实验 7-12 的验收顺序。

**易混点**

- **「公开基准超越」与「你的任务更好」是两件事**：原文的案例设定就是「公开基准多项超越 + 定价更低」，但在特定场景上成功率反降 5%。
- **组件最优 ≠ 系统最优**：更强嵌入可能让 reranker 冗余，更强主模型可能弥补检索缺陷。评估必须在端到端任务上做。

**一句话记住**

> 换模型不是「切或不切」的二元决策：先在自建评估集上确认差异超出噪声，再按场景做差异化路由。

## 7.7 评估结果的统计显著性

**原文要点**

- **评估集有限，模型输出又有随机性，因此分数差异可能只是抽样噪声。** 若在 $n$ 个用例上测得成功率 $p$，**标准误可粗略估计为**：

$$SE(p)\approx\sqrt{\frac{p(1-p)}{n}}$$

  其中 $p$ 是在 $n$ 个用例上测得的成功率（无量纲，取值 $0\le p\le 1$）；$n$ 是评估用例数（无量纲的正整数）；$SE(p)$ 是这一成功率估计的**标准误**（standard error，无量纲，与 $p$ 同量纲）。它衡量的是「如果重复抽样，这个成功率会晃动多大」。

- 例如 **100 个用例、成功率 70%** 时，**95% 置信区间约为 70% ± 9 个百分点**；「**新模型73% 对旧模型70%**」**不足以支持切换**。
- **同一批任务比较两个配置时，应优先做配对分析**：逐题记录谁胜出，用 **McNemar 检验或配对 bootstrap** 判断差异，**而不是直接相减两个独立成功率**。由于 Agent 每次运行也可能不同，**每个配置最好用多个随机种子（如 3–5 次）**，报告**均值和波动范围**；**单次运行只能用来筛选方向**。若预期收益只有 **2–3 个百分点**，而评估集只有**几十题**，**应该先扩大样本，标准误会按 $1/\sqrt{n}$ 缩小**。

```python
for task in paired_tasks:
    for seed in fixed_seeds:
        a = run(config_a, task, seed)
        b = run(config_b, task, seed)
        record_paired_delta(verifier(a), verifier(b))
return paired_bootstrap_or_mcnemar(all_deltas)
```

- **配对的含义是让两组共享任务与随机条件，而不是分别抽两批样本再比较平均值。**
- 并行验证多个假设时还要考虑**多重比较**：**收紧显著性阈值，或对正向结果做独立复跑**。实务上的判断标准很简单：**分差要超过噪声、在配对分析中成立，并且能够复现**，才值得据此切换模型或发布改动。

**辅导讲解**（笔记补充，非原文）

- 公式的直觉：$\sqrt{p(1-p)/n}$ 里，$p(1-p)$ 是单次试验的方差（伯努利分布），除以 $n$ 再开方就是「$n$ 次平均」的标准误。三个推论（笔记补充）：
  1. **样本越多越准**：$n$ 变成 4 倍，$SE$ 减半（这就是原文说的「按 $1/\sqrt{n}$ 缩小」）；
  2. **$p$ 接近 0 或 1 时更准**：$p(1-p)$ 在 $p=0.5$ 时最大，所以成功率居中时最难分辨差异；
  3. **差异要跟 $SE$ 比，不要跟 100% 比**：两个模型都「很高分」时，差异往往落在噪声里。
- 原文那个例子代进去复算（笔记补充的计算）：
  - $SE(0.7)=\sqrt{0.7\times0.3/100}=\sqrt{0.0021}=0.0458$；
  - 95% 置信区间约为 $0.7\pm1.96\times0.0458=0.7\pm0.0898$，即 **70% ± 约 9 个百分点**，与原文一致。
  - 反过来看「73% 对 70%」：只有 3 个百分点的差距，而单个配置的 95% 区间就有 ±9 个百分点——**差异完全淹没在噪声里**，所以原文说「不足以支持切换」。
- 为什么一定要做**配对分析**而不是「两个独立成功率相减」？因为配对把任务难度这个共同因素消掉了。举个笔记补充的例子：如果模型 A 在 100 题里对了 70 题，模型 B 对了 73 题，但 B 对的那 3 题恰好是 A 也对的简单题，而 B 在 A 做对的 3 道难题上翻车了——两个总数看起来只差 3%，实际的能力结构完全不同。逐题记录胜负（配对 delta）才能看出这件事。
- **多个随机种子**这一条针对的是 Agent 的第二层随机性：即使任务相同，Agent 每次运行的轨迹也可能不同（工具返回、采样温度、并行调用顺序）。原文的要求是「每个配置最好用多个随机种子（如 3–5 次），报告均值和波动范围」，并且明确「**单次运行只能用来筛选方向**」——单次结果可以用来决定「要不要进一步测」，不能用来决定「要不要上线」。
- **多重比较**这一条最容易被忽略：如果你同时试了 10 个改进方案，每个都用 95% 置信水平判断，那么纯靠运气也会有一两个「显著有效」。原文给的应对是「收紧显著性阈值，或对正向结果做独立复跑」。
- 原文最后那句实务标准可以当成一个三段式检查清单：
  1. **分差要超过噪声**（统计显著性）；
  2. **在配对分析中成立**（不是两组独立样本的假象）；
  3. **能够复现**（独立复跑仍然成立）。
  - 三条都过，才轮到「切换模型或发布改动」。

**易混点**

- **标准误（SE）与标准差（SD）不同**：标准差描述**个体**的离散程度（$p(1-p)$ 的平方根），标准误描述**估计量**（成功率这个均值）的离散程度，所以多了除以 $n$ 再开方这一步。原文给的是标准误。
- **「95% 置信区间 ±9 个百分点」是笔记复算的结果**：原文只写「约 70% ± 9 个百分点」，笔记补上 $1.96\times SE$ 这一步是为了说明 9 这个数是怎么来的。

**一句话记住**

> 差异要跟标准误比：$SE\approx\sqrt{p(1-p)/n}$，样本翻四倍标准误减半；做决策要「超噪声 + 配对成立 + 可复现」。

## 7.8 Agent 的可观测性

**原文要点**

- 评估驱动的决策（无论是模型选型还是持续迭代）都依赖于高质量的运行数据。本节先介绍如何系统性地采集这些数据（**可观测性**），然后讨论如何将评估结果转化为系统改进。

> 图 7-7（原文插图）可观测性技术栈。图分左右两块：
> - **左边：执行追踪树（单次任务）**。顶层是一条 Trace：「帮用户查北京明天天气 (**3.2s, \$0.008**)」；其下按顺序挂着若干个 span：`LLM Call：意图识别`（Claude 4 Sonnet · 0.4s · 320 tokens）→ `Tool：get_weather(Beijing)`（MCP Server · 1.8s · 200ms TTFT），该工具 span 下还有两个子节点：`├─ HTTP Request`（api.weather.com · 1.6s）与 `└─ Response Parse`（JSON → 结构化天气数据）→ `LLM Call：生成回复`（Claude 4 Sonnet · 0.8s · 580 tokens）→ `Tool：send_message(user)`（0.2s · 包含天气摘要）。这棵树的父子关系展示了「一次任务 = 一条 trace，每次 LLM 调用/工具调用/解析 = 一个 span」的结构。
> - **右边：监控仪表盘**，分三栏：
>   - **成本追踪**：今日 \$12.30（1,200 次）；本月 \$340（34K 次）；异常：task#892 循环调用 search 14 次，耗 \$2.1。
>   - **性能监控**：P50 / P95 / P99 延迟：2.1s / 8.4s / 15.2s；工具成功率：94.3%。
>   - **质量审计**：任务成功率 87%；幻觉触发 2.1%；安全违规 0（本月）；用户满意度 4.3/5。
> - **底部一条闭环箭头**：追踪数据 → 发现问题 → A/B 测试 → 提示词版本管理 → 持续优化。

- **可观测性（Observability）** 这个概念**借自分布式系统领域**：你没法直接打开系统内部看它在做什么，只能通过它输出的**日志、指标和追踪数据**来推断发生了什么，就像医生不能直接看到患者体内的情况，只能通过体温、血压、影像等外部信号来诊断问题。**Agent 系统把这件事变得更难**：同样的输入可能产生不同的输出，多轮推理和工具调用使执行路径极其复杂，而模型的「思考」过程对外完全不透明。
- 可观测性的价值有四个方面：
  1. **问题诊断**：完整的轨迹让开发者能回放全过程，而非靠猜测；
  2. **持续优化的基础**：你能看到哪些任务需要多轮迭代、哪些工具成功率最低、哪些检索查询总是返回空结果；
  3. **成本管理**：Agent 运行成本在不同任务上可能**差一两个数量级**，追踪可以识别出异常高成本的案例；
  4. 积累的轨迹数据也为**模型后训练**提供了基础。
- Agent 可观测性的数据基础是**追踪（Trace）**，其数据结构直接沿用了分布式系统的 **span 树模型**：一次任务执行对应一条 trace，其中每个 LLM 调用、每次工具调用、每次检索都是一个 **span**（记录**输入输出、起止时间、token 消耗、错误信息**的执行单元），span 之间的父子关系构成一棵执行树——比如「Agent 主循环」span 之下挂着若干「LLM 调用」和「工具调用」子 span。
- 这一层**已有标准化协议可用**：**OpenTelemetry** 是通用的分布式追踪标准，**OpenInference** 等规范则在其上定义了 LLM 应用特有的语义约定（如何记录提示词、模型参数、token 用量等）。**采用标准协议的好处是采集与分析解耦**——同一份追踪数据可以对接不同的分析后端，避免被单一平台锁定。
- **LangSmith** 是这一领域的代表性平台之一（类似定位的还有 **Langfuse、Arize Phoenix** 等），将可观测性、评估、优化整合为闭环。每次执行时都会创建一个追踪会话，其中的模型调用、工具使用、知识检索被记录为独立的执行单元，通过因果关系链接形成一棵执行树。每个单元记录完整的输入输出、时间信息、成本数据和错误信息。平台采用**异步批量数据采集**，确保追踪本身**不影响 Agent 的响应延迟**。
- 平台还支持 **A/B 测试**（将一部分用户的流量路由到新版本，自动对比各项指标，支持快速回滚或渐进扩量）、**提示词版本管理**（每个版本都关联着运行时的性能数据）、以及**协作式开发**（团队成员可共享追踪数据和问题案例）。**生产环境中的海量真实数据是持续改进的金矿**——能发现未曾预料的场景，识别最需要优化的功能点。
- **可观测性数据最有价值的去向，是回流并转化为评估资产。** 一条实用的闭环是：**从生产轨迹中筛选出失败与可疑案例 → 脱敏处理（去除用户隐私、密钥等敏感字段）→ 沉淀为评估集的新用例和回归测试**。这样评估集就不再是一次性构造的静态集合，而是**随产品演化、持续贴近真实用户分布的活资产**。今天线上暴露的失败模式，明天就成为守住这条底线的回归用例。
- 有了完备的评估体系和数据集之后，关键在于**将评估结果转化为切实的系统改进**。

**辅导讲解**（笔记补充，非原文）

- 把 trace / span 记成两个层级：**trace 是「一次任务」，span 是「一步操作」**。图 7-7 那棵树里，`get_weather(Beijing)` 这个工具 span 下面还挂了 HTTP Request 和 Response Parse 两个子 span——**这意味着排查延迟时可以一路下钻**：如果用户抱怨「查天气很慢」，你可以看出 1.8 秒里 1.6 秒花在 HTTP 请求上，而不是模型慢。
- 图 7-7 的三个数字组合起来很说明问题：
  - trace 总耗时 3.2s、总成本 \$0.008；其中工具 1.8s、两次 LLM 调用共 1.2s（0.4+0.8）——**工具反而比模型更耗时**（笔记补充的对比）；
  - 工具 span 上标注了「200ms TTFT」——说明连工具调用也按首包延迟记录，而不是只记总时长；
  - 仪表盘里 P99 延迟 15.2s 而 P50 只有 2.1s，**差 7 倍以上**，这正是 7.6.1 节强调 p95/p99 而不是均值的原因。
- 图 7-7 里那条「异常：task#892 循环调用 search 14 次，耗 \$2.1」正是 7.6.3 节「设置每个任务的成本上限」要拦的场景：单次任务 \$2.1，而正常任务平均成本大约是 \$12.30/1200 ≈ \$0.010（笔记补充的计算），**差了约两个数量级**——原文说的「不同任务成本可能差一两个数量级」在这个仪表盘上有实例。
- 为什么可观测性对 Agent 比对普通服务更重要？原文给了三条：**同样输入可能不同输出、执行路径极复杂、思考过程不透明**。普通微服务的调用链相对固定，看一眼 trace 就知道坏在哪；Agent 的轨迹每一步都可能分叉，所以「记录完整轨迹」是唯一可行的诊断方式。
- OpenTelemetry / OpenInference 那一段讲的是**解耦**：「采集与分析解耦——同一份追踪数据可以对接不同的分析后端，避免被单一平台锁定」。这条对工程的现实意义是：**追踪 SDK 只写一次，换后端不用改代码**。
- 「异步批量数据采集」这个细节值得单独记住：**可观测性本身不能拖慢 Agent**。如果每次 span 上报都同步阻塞，排查工具就变成了性能问题的新来源。
- 回流闭环四步值得抄下来当成 SOP（笔记补充，逐字来自原文）：
  1. 从生产轨迹中**筛选出失败与可疑案例**；
  2. **脱敏处理**（去除用户隐私、密钥等敏感字段）；
  3. **沉淀为评估集的新用例和回归测试**；
  4. 让评估集成为「随产品演化、持续贴近真实用户分布的**活资产**」。
  - 注意第 2 步不能省——这也是 7.10.5 节「隐私感知分析」存在的理由。

**易混点**

- **可观测性 ≠ 评估**：可观测性提供**原始数据**（轨迹、指标、日志），评估是**对数据的判定**。原文的顺序是先采集（可观测性），再讨论如何把结果转化为改进。
- **Trace 与 Span 是包含关系**：一条 trace 包含多个 span，span 之间还有父子关系，共同构成执行树。别把二者说成同层概念。
- **LangSmith / Langfuse / Arize Phoenix 是平台，OpenTelemetry / OpenInference 是协议与规范**：前者是具体产品，后者是标准。原文分别说了「标准化协议」和「代表性平台」。

**一句话记住**

> 一次任务是一条 trace、每个操作是一个 span；追踪数据要能回流成评估资产，才算真正闭环。

## 7.9 从 Benchmark 报告到系统改进

**原文要点**

- 原文用一个配套仓库里**真实的 AndroidWorld 调优过程**来演示。**实验只跑了 API 35 模拟器上的 4 个 Wi-Fi 设置任务，每项任务做一次配对对照。** 这个案例的价值不在于证明系统整体提高了多少，而在于**展示如何根据一轮结果，决定下一轮只改什么**。
- 从 Harness 工程的视角看，这一节本质上讲的是 **Harness 迭代优化的方法论**——通过评估数据定位 Harness 中的薄弱环节（**上下文不足？约束缺失？验证不够？反馈不及时？**），有针对性地改进，再重新评估，形成 Harness 持续进化的闭环。
- **在开始分析 Benchmark 报告之前，有一条容易被忽视的原则：看到 Agent 表现下降时，应先检查评测系统本身，再动 Agent。** 一个常见误区是看到分数下降就立刻修改 Agent 代码，而忽略了评测系统本身可能先出了问题——**基于失真的信号调整方向，修改方向可能从一开始就是错的**。评测系统常见的错误来源包括：
  - 运行环境的资源不足导致进程被杀（表现为随机失败）；
  - 验证器本身有 bug 把正确答案判为失败；
  - 测试用例与生产场景之间存在脱节。
  - **这些问题在结果数字上都跟模型退化一模一样，只有审查完整的轨迹才能区分。**

### 7.9.1 读懂 Benchmark 报告：发现问题的艺术

**原文要点**

- 最初的报告记录了 **116 项任务各跑一次**的结果，**总成功率约为 88%**。但**失败并不是零星散落的**：四项 `SystemWifiTurn*` 任务里**有三项失败**，轨迹中还反复出现**来回导航、无法确认最终状态**等现象。
- 这里至少有**两种解释**：可能是 **Agent 不知道设置入口**，也可能是**它拿到的界面信息不完整**。
- 如果只盯着 88% 这个总分，**这个小而集中的失败簇很容易被忽略**；如果只是**增加最大步数**，又可能把「**看不见界面**」误当成「**不够耐心**」。所以，**读报告时应先找失败集中在哪些任务和能力上，再回放轨迹，分清问题出在看、想、做还是验**。本例先把范围缩到四项 Wi-Fi 任务，**目的只是用较低成本判断病因，不是估算系统的整体水平**。

**辅导讲解**（笔记补充，非原文）

- 这一小节的方法可以总结成三步（笔记补充的整理）：
  1. **别只看总分，先找失败簇**——88% 是平均值，四项 `SystemWifiTurn*` 里挂了三项才是信号；
  2. **列出多个解释，不要锁定第一个**——「不知道入口」和「看不到界面」都会表现为「来回导航 + 无法确认状态」；
  3. **缩范围、低成本试因**——先用四项任务做小实验判断病因，而不是直接上 116 项 × 多轮的大实验。
- 「把『看不见界面』误当成『不够耐心』」这句话是本节最实用的一句警告。它对应一个非常常见的错误修复动作：**分数低 → 加最大步数**。如果真实病因是 Agent 观察不到界面状态，增加步数只会让它多绕几圈，既费 token 又不涨分。原文在 7.9.3 节会用实测数据证明这一点。

**易混点**

- **「失败集中」与「失败率高」是两种信号**：总成功率 88% 看着还行，但失败集中在同一个能力标签上，说明存在系统性缺陷而非随机波动。**看分布比看均值更有价值。**

**一句话记住**

> 读报告先找「失败簇」而不是盯总分，然后回放轨迹分清问题出在「看、想、做、验」哪一环。

### 7.9.2 从数据到假设：构建改进路线图

**原文要点**

- **第一轮先试最便宜的改法。** 假设 H1 认为 Agent 只是「不知道路」，因此**只给实验组补充 Wi-Fi 设置的导航提示和最终状态检查要求**。结果**成功率没有变化，说明问题不在提示词**。
- **第二轮转而检查 Agent 到底「看见了什么」。** 假设 H5 **把 API 35 上不兼容的 accessibility feed 换成 AndroidWorld 已支持的 UIAutomator 元素树**。**成功率确实提高了**，但完整元素树太长，**token 用量大幅上升**。
- 于是**第三轮 H5C**：**不再增加新信息**，只把元素树中**不可见、没有文字、也不能操作的容器节点删掉**，看看能否在保留成功率的同时去掉噪声。
- **三轮实验始终使用相同的模型、任务参数、随机种子、步数上限和模拟器，并交替安排两组的运行顺序。** 这样一轮接一轮地缩小问题范围，**比同时堆上许多改动更容易说清因果**：**上一轮暴露的问题，恰好成为下一轮唯一要验证的改动。**

**辅导讲解**（笔记补充，非原文）

- 三轮实验的逻辑是**一次只动一个变量**，而且每一轮都由上一轮的结果决定：
  - H1 测「提示词」→ 无效 → **排除「Agent 不知道路」这一解释**，把注意力转向输入；
  - H5 测「输入通道」（换元素树）→ 有效但太贵 → **确认瓶颈在观察通道**，但暴露成本问题；
  - H5C 测「输入的冗余度」（精简元素树）→ 成功率不变、token 减半 → **同时解决「能不能做成」和「做成是否划算」**。
- 「相同模型、任务参数、随机种子、步数上限和模拟器，并交替安排两组的运行顺序」这一串控制变量值得抄下来：它把「模型」「任务难度」「随机性」「预算」「环境」全部固定，**唯一动的就是那一项改动**。交替安排运行顺序是为了防止时间相关的漂移（比如模拟器越跑越慢）被误当成实验效应。
- 原文那句「比同时堆上许多改动更容易说清因果」是本节的核心方法论：**多改同时上，分数涨了也不知道是谁的功劳；分数跌了也不知道是谁的锅。** 这一条与 7.10.1 节的消融实验、7.10.2 节的「多臂而非二元」是同一个思想。

**易混点**

- **H1 失败不等于「提示词没用」**：它说明的是「在这类失败上提示词解决不了」，因为病因在输入通道。原文的结论是「**提示写得更详细，也补不回 Agent 根本没有看到的信息**」。

**一句话记住**

> 一轮只改一个变量，且让上一轮暴露的问题成为下一轮唯一要验证的改动。

### 7.9.3 从结果到决策：数据驱动的权衡

**原文要点**

- 三轮实测结果汇总在表 7-5。**每组都只有四项任务，所以这里的数字只能用来决定下一步是否值得扩大测试，不能用来推断整个 AndroidWorld 的成功率。**

表 7-5 AndroidWorld Wi-Fi 子集的三轮实验

| 实验 | 只改了什么 | 对照组→实验组成功率 | 实验组/对照组token | 下一步 |
| --- | --- | --- | --- | --- |
| H1 | 增加导航提示 | 25%→25% | 0.47× | 没有提高成功率，沿用原提示 |
| H5 | accessibility feed 换成 UIAutomator | 25%→100% | 2.498× | 效果明显但太费 token，继续优化 |
| H5C | 精简 UIAutomator 元素树 | 100%→100% | 0.506× | 成功率不变、token 减半，进入完整复测 |

（表格按原文语义还原：原书分栏排版导致列错行，笔记按「实验—只改了什么—对照组→实验组成功率—实验组/对照组 token—下一步」的列序重新对齐，数字与文字未改动。）

- 三轮结果串起来看，**结论比某一个百分比更有用**：
  1. **提示写得更详细，也补不回 Agent 根本没有看到的信息**；遇到这类失败，应先检查输入，而不是继续堆提示词。
  2. **输入也不是越多越好。** 完整元素树解决了「看不见」的问题，却带来大量无用 token；删除无语义节点后，四项任务仍全部成功，token 又减少了约一半。
  3. **整个过程中没有更换模型**，仅仅调整 **Harness 如何表示界面**，就先后解决了「**能不能做成**」和「**做成是否划算**」两个问题。

**辅导讲解**（笔记补充，非原文）

- 把表 7-5 的 token 比值读清楚：
  - H1 的 0.47×：实验组只用对照组的约一半 token（笔记补充的解释：导航提示与最终状态检查要求可能让 Agent 少绕路，虽然成功率没变）；
  - H5 的 2.498×：**完整元素树让 token 涨到约 2.5 倍**——这正是「有效但昂贵」的典型形态；
  - H5C 的 0.506×：**在保持 100% 成功率的同时把 token 压回约一半**。
  - 也就是说，从 H5 到 H5C，**成功率不变而成本降到约五分之一**（$0.506/2.498\approx0.203$，笔记补充的计算）。这一对比说明「找到有效改动」和「让改动变划算」是两件事，后者同样是 Harness 工程的成果。
- 「每组只有四项任务，所以数字只能用来决定下一步是否值得扩大测试」这句话是本节的方法论纪律：**小样本只能做方向性判断，不能做水平估计。** 四项任务上 100% 不代表系统 100%。原文在 7.9.4 节会用「不能把子集上的 4/4 写成系统整体 100%」再强调一次。
- 第 3 条结论回应了本章开篇的核心认识：**评估对象是「模型 + Harness」的组合体**。这里从头到尾没换模型，只改了「Harness 如何表示界面」，就同时改善了成功率和成本——这是「瓶颈在 Harness」的一个教科书式实例，也正对应章首说的「改进方向可能不是换模型，而是优化 Harness 的某个组件」。

**易混点**

- **「成功率提升」与「值得部署」是两件事**：H5 把成功率从 25% 拉到 100%，但 token 涨到 2.498 倍，所以下一步不是「部署」而是「继续优化」。
- **对照组→实验组的成功率是配对对照的结果**，不是两次独立测量的对比。原文在 7.9 开头就写了「每项任务做一次配对对照」，这正是 7.7 节主张的配对分析在小样本上的应用。

**一句话记住**

> 小样本结论只用来决定「下一步测什么」：先修「看不见」，再修「太费钱」，全程可以不动模型。

### 7.9.4 持续迭代：从第一次改进到系统演化

**原文要点**

- H5C 通过了这四项任务的检查，**只说明它值得进入下一轮，并不等于可以部署**。下一步需要：
  - **补齐第三方应用**；
  - 在 **Pixel 6 / API 33 标准环境**中，对 **116 项任务各跑 5 个随机种子**；
  - 除了检查**成功率不能下降**，还要确认 **token 不超过原方案的 75%**、**延迟不超过 1.5 倍**。
- **在这轮完整复测之前，不能把子集上的 4/4 写成系统整体 100%。**
- 这就是持续迭代真正的含义：**一轮证据只支持与它规模相称的下一步。**
  - H1 失败，让我们**不再继续堆提示词**；
  - H5 找到了正确方向，也**暴露了成本问题**；
  - H5C 解决成本问题后，**才获得扩大测试的资格**。
- **好的 Benchmark 报告不只给出一个分数，还应写清结论适用于哪里、哪些底线没有通过、下一轮要验证什么。**

**实验7-13 ★★★：AndroidWorld 的评估和改进**

本实验练习如何从评估报告一路走到系统改进。以 `chapter7/android-world` 中的 AndroidWorld 历史报告和三组已保存的配对结果为起点。

- **第一步：诊断。** 交叉分析**逐任务表格和能力标签矩阵**，将表面的任务失败映射到深层的能力缺陷。识别成功率低于预期的能力标签和集中失败的任务区域。
- **第二步：构建假设。** 按照**三层框架（表层→中层→深层）**形成改进假设，每个假设明确预期的成功率提升目标和验证方法。
- **第三步：分阶段实验。** 先复现 H1、H5 和 H5C，**每轮只改变一个变量**；除成功率外，还要记录 **token、延迟和是否出现回退**。
- **第四步：数据驱动决策。** 根据**成本收益比**做部署决策——不是简单地采用所有有效的改进，而是需要权衡每项改进的**适用范围、延迟影响和成本开销**。低成本高收益的改进优先部署，高成本的改进限定在关键场景中使用。
- **第五步：迭代。** 小范围实验通过后，只能进入完整复测；在标准环境完成 **116×5 次运行**后，才能讨论是否部署。**报告中必须保留环境差异、样本量和尚未完成的部分。**

**辅导讲解**（笔记补充，非原文）

- 这一小节把「一次实验的证据强度」和「下一步能做什么」绑在一起，形成一条**升级阶梯**（笔记补充的整理）：

  | 证据规模 | 能支持的决定 |
  | --- | --- |
  | 4 项任务、1 次配对对照 | 判断病因方向（该改输入还是改提示） |
  | 4 项任务、三轮单变量实验 | 判断「值得扩大测试」 |
  | 116 项 × 5 个随机种子、标准环境 | 才轮到讨论是否部署 |

  这张表是笔记补充的整理，各行的数字都来自原文。
- 「**只说明它值得进入下一轮，并不等于可以部署**」这句话值得反复读。它挡住的是最常见的一种自欺：把子集上的漂亮数字当成系统能力。原文甚至给了一句更硬的话——**「不能把子集上的 4/4 写成系统整体 100%」**。
- 完整复测的三个门槛都值得记住：**成功率不能下降**（不能为了省成本牺牲质量）、**token 不超过原方案的 75%**（成本底线）、**延迟不超过 1.5 倍**（体验底线）。这是典型的**「目标指标 + 护栏指标」**设计，与 7.10.2 节讲的护栏指标完全一致。
- 从 H1 → H5 → H5C 的链条还可以看出「**每轮的产出不只是结论，还有下一轮的资格**」：
  - H1 产出的是「排除项」——不再堆提示词；
  - H5 产出的是「方向 + 一个待解决问题」——方向是元素树，待解决的是成本；
  - H5C 产出的是「资格」——可以进完整复测。
- 实验 7-13 的第四步说得很清楚：**不是简单地采用所有有效的改进**。这句话修正了很多人对「数据驱动」的误解——数据驱动不是「只要指标变好就上」，而是**权衡适用范围、延迟影响和成本开销**，低成本高收益的优先部署，高成本的限定在关键场景。
- 最后那句「报告中必须保留环境差异、样本量和尚未完成的部分」是**报告撰写规范**，也是一个诚实性要求：读报告的人需要知道这个结论是在 API 35 模拟器上、四项任务上得到的，而不是在标准环境全量得到的。

**易混点**

- **「通过子集检查」≠「通过复测」≠「可部署」**：这是三个不同的门槛，原文在 7.9.4 开头就明确区分了。
- **目标指标与护栏指标不要混**：H5C 的目标是把成功率保持住、把 token 降下来；护栏是「成功率不能下降」「延迟不超过 1.5 倍」。目标可以优化，护栏是底线。

**一句话记住**

> 一轮证据只支持与它规模相称的下一步；子集上的 4/4 永远不能写成系统整体 100%。

## 7.10 从外部评估到内部评估：生产级 Agent 的评估基础设施

**原文要点**

- 前面几节讨论了如何**从外部评估** Agent 系统——搭建评估环境、设计数据集、分析 Benchmark 报告。但**最优秀的 Agent 产品不仅接受外部评估，还内建了持续自我评估的基础设施**。
- 本节以第五章介绍的**开源通用 Agent OpenClaw** 为例，并结合**头部 Coding Agent 产品的公开技术分析与从业者分享**，展示一套值得借鉴的内部评估体系——**它将 ML 研究中的实验方法论系统性地嵌入到了产品工程中**。

**辅导讲解**（笔记补充，非原文）

- 把这一节与前几节的分工记清楚：**7.1–7.9 教你「怎么给别人的 Agent 打分」，7.10 讲的是「最好的产品怎么给自己打分」**。前者是评测者的视角，后者是产品工程团队的视角。
- 「把 ML 研究的方法论嵌入产品工程」是这一节的总纲。后面六个小节其实对应六件具体的工程设施：消融开关、AB 测试流程、特性开关、提示词快照、隐私类型、以及思维方式的转变。

### 7.10.1 消融基础设施：理解每个特性的真实贡献

**原文要点**

- ML 研究者长期使用**消融实验（Ablation Study）**来理解模型的哪些组件真正重要——所谓消融，就是**逐一「摘除」某个组件，看整体性能掉多少**。**OpenClaw 将这一方法论引入了产品工程**：系统内置了一个**总开关**，可以同时禁用多个主要特性（**思考模式、上下文压缩、自动记忆、后台任务**等），创造一个「**裸模型**」基线。这使得团队能回答一个关键问题：**某个特性是真的改善了用户体验，还是只是感觉有用？**
- 将消融作为常规的工程实践而非一次性的研究，有几个实际意义：
  - 首先，**消融开关必须在启动路径的极早期注入——在任何模块级常量捕获配置值之前**——这意味着**消融基础设施必须从一开始就设计进系统架构，而非事后加装**。
  - 其次，**定期运行消融实验（如每次大版本发布前）可以发现「特性债务」**——那些曾经有效但随着模型进化已不再必要的特性。
  - 对于任何构建生产 Agent 的团队，建议的实践是：**每个主要特性都应是可独立关闭的，团队应定期验证每个特性的实际贡献。**

**辅导讲解**（笔记补充，非原文）

- 消融实验在产品工程里的价值，可以用一个问题概括：**「这个功能是真的有用，还是我们觉得它有用？」** 功能上线时通常有理由，但模型升级之后，理由可能已经消失。
- 「必须在启动路径的极早期注入」这条约束很有信息量：它说明**实验能力会被架构反过来限制**。如果配置值在模块加载时就被常量捕获了（比如模块顶层的 `const ENABLE_MEMORY = config.memory`），那么之后再想「中途关掉它」就来不及了。所以原文的结论是**消融基础设施必须从一开始就设计进系统架构**。
- 「特性债务」这个词值得记住：它和「技术债」是同构的概念——**功能不是免费的**，一个不再必要的特性会带来维护成本、延迟、token 成本和认知负担。定期消融就是给功能做「体检」，把不再产生收益的特性识别出来。
- 与 7.10.2 的 AB 测试对比着看（笔记补充）：
  - **消融**回答「这个特性还有没有用」（有/无的对比，通常是内部的）；
  - **AB 测试**回答「这个改动有多好」（多臂、面向真实用户流量）。
  - 两者是互补的：消融管「要不要留」，AB 管「怎么调」。

**易混点**

- **消融实验（产品工程）与章首说的消融实验是同一件事的两处应用**：章首（印刷 p.184）把它作为「定位 Harness 内部哪个部件重要」的手段，这里把它作为「产品特性体检」的常规设施。
- **「裸模型」基线不是「关掉全部功能」**：原文说的是「同时禁用多个主要特性（思考模式、上下文压缩、自动记忆、后台任务等）」，列举的是主要特性，不必把它理解成「一定关掉所有功能」。

**一句话记住**

> 每个主要特性都应能独立关闭；消融开关必须在启动路径极早期注入，并且要定期跑，用来发现「特性债务」。

### 7.10.2 AB 测试方法论：区分机制与目标

**原文要点**

- 成熟的 Agent 产品会对自身行为进行严格的 **AB 测试**（即把用户随机分成两组，一组使用旧版本、一组使用新版本，通过对比两组的实际数据来判断改动是否有效）。一个设计精良的 Agent AB 测试案例展示了几个关键的方法论原则：
  1. **多臂而非二元。** 不仅对比「有」和「没有」，而是设计多个渐进式变体（例如测试不同强度的提示词约束时，设置**控制组和三个渐进更严格的实验组**）。这种设计能**揭示剂量-效应关系，帮助找到最优点**。
  2. **区分机制指标和目标指标。** 这是最容易犯的错误——**把你正在改变的东西当作优化目标**。例如，如果你在测试「缩短 Agent 的计划文件长度」，**计划长度是机制指标（你直接改变的东西），但它不是目标**。真正的目标可能是「**降低会话级成本**」。缩短计划文件可能降低成本，但也可能因为计划不够详细而导致更多的编辑-检查-编辑循环，反而增加了总输出量。**始终问自己：我改变的东西（机制）和我真正关心的东西（目标）是同一个吗？如果不是，以目标为准。**
  3. **设置护栏指标。** 即使目标指标改善了，如果**用户满意度下降、操作次数增加或错误率上升**，实验也应该停止。**护栏指标是「不能变差的底线」。**
  4. **记录基线统计。** 包含**样本量、分布百分位数、相关性分析**（如「拒绝率随计划大小单调递增」），为实验结果的解读提供必要的上下文。**没有基线，你无法判断实验结果是否具有统计显著性。**

**辅导讲解**（笔记补充，非原文）

- 「多臂而非二元」的价值在于**找到最优点而不是「比原来好」**。两臂实验只能回答「A 比 B 好吗」；多臂实验能画出「剂量—效应」曲线：约束太松没效果，太紧可能伤害体验，最优点在中间某个位置。原文举的例子是「控制组 + 三个渐进更严格的实验组」，一共四臂。
- 「机制指标 vs 目标指标」这个坑值得展开，因为它特别隐蔽。原文的例子：你改的是「计划文件长度」（机制），你想要的是「降低会话级成本」（目标）。直觉上「计划短 → token 少 → 成本低」，但实际链路里还有一环：**计划太短 → 执行时反复编辑—检查—编辑 → 总输出量反而增加**。所以机制和目标的因果关系不是显然的，**必须以目标指标为准来判断成败**。
- 「护栏指标」与 7.9.4 节的复测门槛是同一套思路：H5C 复测的要求里既有目标（保持成功率、降 token），也有护栏（成功率不能下降、延迟不超过 1.5 倍）。护栏的作用是**防止「按下一个指标、翘起另一个指标」**。
- 「记录基线统计」这一条里那个例子很具体：**「拒绝率随计划大小单调递增」**。它是一条相关性观察，用来解释实验结果的成因，也用来确认实验分组的分布是否正常。没有基线，你甚至不知道「实验组成本降了 8%」是显著还是噪声——这正是 7.7 节的话题。

**易混点**

- **机制指标（mechanism）与目标指标（goal）的区分标准是「是不是你直接改的那个东西」**：计划长度是你直接改的 → 机制；会话级成本是你关心的 → 目标。
- **护栏指标与目标指标方向可能相反**：目标是「降成本」，护栏是「用户满意度不能降」。护栏不是目标，它是**停止条件**。

**一句话记住**

> 你改变的（机制）和你关心的（目标）往往不是同一个东西；多臂找最优点，护栏守住底线，基线提供判断显著性的上下文。

### 7.10.3 双层特性开关系统

**原文要点**

- **Agent 产品需要从第一天就设计特性开关（Feature Flag）基础设施**——所谓特性开关，就是一个**可以远程控制的开关，决定某项功能对用户是开启还是关闭，无需重新部署代码**。**它同时服务于三个目的：实验、渐进发布和紧急熔断。**
- **编译时开关**在构建阶段就将相关代码**从产物中物理移除**。内部专用的特性在外部构建中根本不存在——**即使逆向工程也无法发现被移除的功能**。这也是一种**干净的消融机制**：**关闭某个特性不是在运行时跳过逻辑，而是对应的代码在物理上就不存在。**
- **运行时开关**的配置**由服务端下发，并在本地磁盘缓存一份**。设计上**宁可读取到稍旧的缓存配置，也不能让 Agent 因等待网络请求而阻塞启动**。具体的**分组决策通过实验平台（如 GrowthBook）完成**，用于分配 AB 测试组。一个关键的设计细节是：**每个特性的曝光事件在每个会话中最多记录一次，避免重复记录污染实验数据。**
- **对 Agent 开发者来说，特性开关不是简单的调试工具，而是一等架构组件。**

**辅导讲解**（笔记补充，非原文）

- 两层开关的分工可以用一张表看清（笔记补充的整理，内容来自原文）：

  | | 编译时开关 | 运行时开关 |
  | --- | --- | --- |
  | 生效时机 | 构建阶段 | 运行时 |
  | 实现方式 | 代码从产物中物理移除 | 服务端下发配置 + 本地磁盘缓存 |
  | 特点 | 逆向工程也发现不了；消融最干净 | 可远程控制，无需重新部署 |
  | 用于 | 内部专用特性、彻底移除的功能 | 实验分组、渐进发布、紧急熔断 |

- 「三个目的」值得分别理解：
  1. **实验**——把用户分到不同组（配合 GrowthBook 之类的实验平台做分组决策）；
  2. **渐进发布**——先给一小部分用户开启，观察指标，再逐步扩量；
  3. **紧急熔断**——出问题时远程关掉，不用等发版。
- 「宁可读取到稍旧的缓存配置，也不能阻塞启动」是一条明确的**可用性优于一致性**的取舍。对 Agent 来说尤其重要：如果启动时要等网络拿配置，网络抖动就会变成「Agent 起不来」。**宁可先带着旧配置跑起来，也不能卡死。**
- 「每个特性的曝光事件在每个会话中最多记录一次」这条细节容易被忽视，但它直接关系到实验数据的质量：如果同一个会话里反复记录曝光，计数就被放大了，**分母失真会让实验结论完全错误**。
- 「一等架构组件」这个定性与 7.10.5 节的「类型系统」思路一致：**把评估/实验能力当成架构的一部分，而不是开发调试时的附加物。**

**易混点**

- **特性开关（Feature Flag）≠ 配置项**：原文强调它能「远程控制、无需重新部署」，并且服务于实验与熔断；普通配置项通常不具备分组实验和熔断能力。
- **编译时开关与「干净的消融」的关系**：关闭某个特性不是在运行时跳过逻辑，而是对应的代码物理上不存在——这也是它比运行时开关更「干净」的原因。

**一句话记住**

> 特性开关是一等架构组件，服务实验、渐进发布、紧急熔断三件事；编译时开关物理移除代码，运行时开关宁可读旧缓存也不阻塞启动。

### 7.10.4 提示词敏感性评估

**原文要点**

- **系统提示是 Agent 行为的核心「代码」，但它往往缺少与普通代码同等的版本控制和回归测试。**
- OpenClaw 的做法是提供一个**专用工具，能在指定的 git 版本上提取完整渲染后的系统提示**——**包含所有动态条件展开后的最终文本**。这使得团队能精确回答：**哪次提交改变了提示词？对评估集的影响是什么？**
- 对于任何 Agent 团队，建议的实践是：
  1. **系统提示应该能够确定性地渲染**（给定相同的配置输入，永远产生相同的输出）；
  2. **建立提示词的版本化快照机制**；
  3. **每次提示词变更都应在评估集上运行回归测试**——就像代码变更需要跑 CI 一样。

**辅导讲解**（笔记补充，非原文）

- 「系统提示是核心代码」这个比喻在这一节被彻底兑现成工程实践：既然它是代码，那么**它就要有版本、要能 diff、要能跑 CI**。
- 三条建议其实是一条流水线（笔记补充的整理）：
  1. **确定性渲染**是前提——如果同样的配置跑出不同的提示词，任何对比都没有意义；
  2. **版本化快照**是存档——让「哪次提交改了什么」可查；
  3. **变更跑回归测试**是门禁——把提示词变更纳入 CI。
- 「包含所有动态条件展开后的最终文本」这一点很关键：真实的系统提示往往是模板（按平台、按用户等级、按功能开关拼接出来的），**只看模板源码看不出最终发给模型的是什么**。所以工具要提取的是**渲染后的完整提示**，而不是模板本身。
- 这条实践与 7.10.3 的特性开关是天然配合的：**开关一动，渲染后的提示就变了**。如果没有「渲染后快照 + 回归测试」，一次实验组的开关调整就可能悄悄改变了所有人的提示词，而没人发现。

**易混点**

- **提示词版本管理 ≠ git 管理模板文件**：模板文件的 diff 不等于最终提示词的 diff（因为动态展开）。原文要求的工具是提取「完整渲染后的系统提示」。
- **「确定性渲染」是要求，不是现状**：原文用的是「应该能够确定性地渲染」——说明这是一个需要刻意达成的工程目标。

**一句话记住**

> 系统提示要像代码一样对待：确定性渲染、版本化快照、每次变更跑回归测试。

### 7.10.5 以隐私感知分析为评估基础

**原文要点**

- 评估依赖好的数据，但 Agent 产品处理的往往是用户的敏感内容。**OpenClaw 通过类型系统来解决这个矛盾**：**分析接口只接受经过特殊类型包装的值，类型名本身就是审计线索**——它明确表明「**我已验证这不是代码或文件路径**」。这种设计**将隐私约束从文档化的规范变成了编译时强制执行的类型检查**。
- 核心原则是：**从一开始就把隐私约束设计进去，而非事后加装。** **如果你的分析系统无法安全地收集数据，你就无法有效地评估。** **隐私和评估并不对立**——**隐私感知的设计迫使你认真思考真正需要度量什么，这反而会催生更精准的评估指标。**

**辅导讲解**（笔记补充，非原文）

- 这一小节的核心论证链是（笔记补充的整理）：
  1. 评估需要数据；
  2. Agent 处理的是敏感内容；
  3. 于是常见做法是「先收集，再脱敏」——但这本身就有风险；
  4. 更好的做法是**用类型系统在编译期拦住不该被采集的值**；
  5. 结果：**隐私约束从「文档里的规范」升级为「编译时的强制检查」**。
- 「类型名本身就是审计线索」这句话很精妙：一个值为 `VerifiedNonCodeString` 类型的变量，在代码评审时一眼就能看出「这个值经过了检查、不是代码或路径」。**类型标注同时承担了「机器检查」和「人可审计」两个功能。**
- 「隐私感知的设计迫使你认真思考真正需要度量什么，这反而会催生更精准的评估指标」这个论点值得记住：约束不是纯粹的负担。**当你不能什么都收集时，你会被迫想清楚「我到底要测什么」**——这通常会让指标更精确，而不是更粗糙。
- 与 7.8 节的回流闭环连起来看：那一步「脱敏处理（去除用户隐私、密钥等敏感字段）」是运行时的动作，而这一节的类型系统是在**写代码时**就把约束前移了。两者互补。

**易混点**

- **「脱敏」与「隐私类型」不是一回事**：脱敏是数据已经收上来之后的处理；隐私类型是在编译期阻止不该被收集的值进入分析接口。原文明说「从一开始就把隐私约束设计进去，而非事后加装」。
- **隐私与评估不是对立关系**：原文的立场是「隐私和评估并不对立」，隐私约束反而可能催生更精准的指标。

**一句话记住**

> 用类型系统把隐私约束从文档规范变成编译期检查：分析接口只接受被包装、已验证的值。

### 7.10.6 从外部到内部：评估思维的转变

**原文要点**

- 本节的核心信息是：**前面几节教你如何从外部评估 Agent，本节揭示的是最好的 Agent 产品如何从内部评估自己。** **外部评估告诉你「Agent 有多好」，内部评估基础设施告诉你「哪项改动让它变好了」。**

  - **隐私感知分析**确保**数据收集的合规性**。
- 这五个组件共同构成了**评估驱动的产品工程**——**不是偶尔做一次评估，而是将评估嵌入到每一次产品决策中。**

**辅导讲解**（笔记补充，非原文）

- 把五个组件与它们回答的问题对应起来（笔记补充的整理，内容来自原文）：

  | 组件 | 回答的问题 |
  | --- | --- |

  | AB 测试 | 每项改动的影响有多大？ |
  | 特性开关 | 怎么安全地做实验和回滚？ |

> 外部评估告诉你「Agent 有多好」，内部评估告诉你「哪项改动让它变好了」——把评估嵌进每一次产品决策。

## 7.11 仿真环境：从评估到后训练的桥梁

**原文要点**

- **评估的终点不是打分，而是改进。** 本章已经展示了改进的两条路径：**调整 Harness**（从 Benchmark 报告到系统改进）和**把评估嵌入产品工程**（内部评估基础设施）。而**最深入的改进方式是训练**——当目标从「评估现有能力」扩展到「培养新能力」时，特别是通过第八章讨论的后训练技术，**评估环境就需要演化为仿真环境：一个能让 Agent 反复练习、自动打分的虚拟操场**。
- **仿真环境与评估环境的核心区别**有三点：
  1. **交互频率高得多（数百万次 vs 数千次）**；
  2. **需要随机化**（防止死记硬背特定配置）；
  3. **必须提供即时反馈**。
- 从应用领域看，仿真环境分为**数字环境（信息处理任务）**与**具身环境（物理世界感知与操作）**两大类。
- 这座桥梁的两端是这样接起来的：**评估侧已经积累的资产可以近乎无缝地转成训练信号**——一套定义清晰的 Rubric 或验证器，**本质上就是一个可验证奖励（RLVR，Reinforcement Learning with Verifiable Rewards）的奖励函数**——**验证脚本直接就是奖励脚本**，测试是否通过、状态是否达标，既是评估的判据，也是强化学习的回报。
- **但训练会提出评估阶段不必操心的新要求：**
  - 其一是**可靠的 reset 语义**：训练要跑**数百万个 episode**（一个 episode 即一次从初始状态到任务结束的完整交互回合），**每个 episode 都必须能把环境重置到一个确定、干净的初始状态**，否则**梯度信号会被上一轮的残留状态污染**。
  - 其二是**远高于评估的吞吐**：评估几千次就够出结论，训练则要在可接受的墙钟时间内喂给模型上百万次交互，**环境的并行度和单实例开销直接决定训练是否可行**。
  - 这两点——**奖励函数化的验证器、面向训练的 reset 与吞吐**——都将在第八章展开。

**辅导讲解**（笔记补充，非原文）

- 「仿真环境 = 评估环境 + 高频 + 随机化 + 即时反馈」这个等式很好用。评估环境只需要「几千次」的规模，仿真环境要「数百万次」，这条量级差异会改变很多设计：
  - 评估环境里可以人工重置，仿真环境必须**自动、可靠、快速**地重置；
  - 评估环境里固定配置没关系，仿真环境**必须随机化**，否则模型会记住配置；
  - 评估环境里延迟高一点无所谓，仿真环境**必须即时反馈**，否则训练循环跑不动。
- RLVR 这个概念的桥梁作用值得说清（笔记补充的理解）：**你为评估写的验证器，几乎可以原样当作强化学习的奖励函数**。这一步省掉了「再写一套奖励」的成本，也保证了「训练的目标」与「评估的标准」一致——这是一件非常重要的事，因为如果两者不一致，模型就会「训练得很好、评估得很差」。
- 图 7-9 那张谱里，**「真实世界：完美保真度、不可重置」**这一格是全图的信息量所在：它把「保真度」与「可训练性」的矛盾摆到了最右边。**真实世界不可重置**，所以不能拿它做数百万次训练；这也解释了为什么仿真环境必须存在。
- AWorld 的 14.6 倍加速值得复算（笔记补充的计算）：$7695\div525=14.657\approx14.6$，与原文一致。加速的来源是**分布式 + 无状态设计**——每个实例完全独立，所以可以任意并行。这个设计（无状态）也是「可重置」的另一种实现方式：**如果每个实例都是全新的，就天然不需要「清理残留状态」**。
- RoboTwin2 的动作分块（Action Chunking）是一个值得跨章理解的机制：**模型一次生成 25 个连续动作**，而不是一步一动。它的收益是「降低推理频率、实现实时控制」，代价是「一次想错 25 步都错」。原文提到「详见第六章」，可以作为跨章联结点（笔记补充的联想）。

**易混点**

- **评估环境与仿真环境的「重置」要求强度不同**：评估环境只要「每次运行前回到同一起点」即可；仿真环境要求**每个 episode 都重置到确定、干净的状态**，否则梯度信号会被污染。这是一个从「可比较」升级到「可训练」的要求。
- **「可重放、可审计」不等于「可训练」**：AWorld 的可重放/可审计是评估侧的性质；训练还额外要求吞吐与并行度。

**一句话记住**

> 仿真环境是「评估环境 + 数百万次规模 + 随机化 + 即时反馈」；验证器可以直接当奖励函数（RLVR），但训练额外要求可靠的 reset 与高吞吐。

### 7.11.1 保真度权衡与领域随机化

**原文要点**

- **高保真环境能更好地迁移到真实世界，但计算开销大。保真度的另一维度是随机化程度：适度随机化能提升泛化能力，过度随机化则会让任务变得过于困难。**
- **领域随机化（Domain Randomization）是缩小仿真与现实差距（sim-to-real gap）的关键技术**：**在物理参数、视觉外观、传感器噪声等方面引入大范围随机变化**——**好比在各种光照和角度下都练习过抓取，到了真实环境也不会因为光线变化就失手**。
- 在数字环境中，**sim-to-real 表现为界面渲染、响应时间等方面的差异，可通过引入延迟和失败的随机化来缓解**。

**辅导讲解**（笔记补充，非原文）

- 这一小节给了「保真度」的第二层含义，容易漏掉：保真度不只是「物理精度」，还包括**随机化程度**。三者构成一个三角权衡（笔记补充的整理，每一条都来自原文）：
  1. **保真度↑ → 迁移性↑，但计算开销↑**（高保真环境贵）；
  2. **随机化适度↑ → 泛化能力↑**（见过各种光照和角度）；
  3. **随机化过度 → 任务过于困难**（曲线会掉回来）。
  - 所以「随机化程度」本身就是一个需要调的超参数。
- 「好比在各种光照和角度下都练习过抓取」这个比喻抓住的是领域随机化的本质：**不追求「仿真得像」，而是追求「训练时见过足够多的变化」，从而对真实世界的变化免疫**。也就是说，它绕开了「高保真」这条昂贵的路。
- 「数字环境里的 sim-to-real 是界面渲染、响应时间的差异」这一点很实用：数字环境没有物理，但有**延迟和失败**。所以数字环境的「领域随机化」体现为**随机注入延迟、随机注入工具失败**——这正好对应 7.5.3 节说的「执行异常应加入截断、超时和工具故障的恢复场景」。**评估侧的异常场景设计，在训练侧就是域随机化的一种形式。**

**易混点**

- **保真度（fidelity）与随机化程度（randomization）是两个维度**：原文明确说「保真度的另一维度是随机化程度」。高保真不等于高随机化，可以有一个保真度很高但完全固定的环境，也可以有一个低保真但参数随机变化很大的环境。
- **领域随机化不是「越随机越好」**：原文明确「过度随机化则会让任务变得过于困难」。

**一句话记住**

> 高保真能迁移但贵，随机化能泛化但过度就变难；数字环境的「sim-to-real」用延迟与失败的随机化来弥合。

## 7.12 本章小结

**原文要点**

- 本章围绕一个核心问题展开：**如何判断 Agent 变好了还是变差了。** 这条链路由四个环节构成：
  1. 先厘清**成功的定义**（Pass@k、Best@k 与 Pass consecutive@k 的口径差异）；
  2. 再确定**任务从何而来**（公开基准、自建业务集与生产轨迹回流三个来源）；
  3. 随后选定**验证方式**（从确定性验证器到检查项清单、Rubric 加 LLM 评判，直至配对比较）；
  4. 最后把**分数转化为决策**（统计显著性、失败归因、回归任务与模型选型）。
  - **每个环节都会影响结论的可信度。**
- 就全书的结构而言，**本章建的是第一章发现循环中的证据段：失败归因决定了后续的提案有没有可依之据。**
- **轨迹前缀边界评估进一步说明，获得一条信息和正确地将它用于当前决策是两种不同能力**：端到端回归保证基本任务不退化，trajectory prefix 边界集则直接检查**作用域判断、当前指令覆盖、澄清和危险动作前确认**。**用户记忆只是这一通用方法的一个案例。**
- **生产级 Agent 的评估不是偶尔做一次的考试，而是从真实问题案例中持续生成回归任务和边界任务的验证系统。**
- **核心方法论：观察→假设→实验→验证→新认识→新假设，使 Agent 工程从经验驱动的「炼金术」转向数据驱动的科学工程。**
- 本章介绍的评估体系形成一个完整闭环：**评估环境提供自动化的测试基础设施 → 评估数据集定义端到端任务和 trajectory prefix 边界 → 自动化评估方法（确定性验证器、LLM-as-a-Judge 与 Rubric）对 Agent 表现打分并生成失败归因 → Benchmark 与问题案例分析揭示改进方向 → 系统改进修复问题 → 更新评估环境和数据集，开始新一轮迭代。**
- 本章建立的评估体系不仅服务于当前系统的优化，也为后续两章提供关键基础：**第八章把评估环境和数据转化为模型后训练的输入；第九章则把生产轨迹的多维评价转化为知识、指令、程序的更新。**

**辅导讲解**（笔记补充，非原文）

- 小结里最有分量的一句是「**本章建的是第一章发现循环中的证据段**」。它把本章放回全书的论证链：没有评估，失败归因就没有依据，改进提案就成了猜测。
- 「获得一条信息和正确地将它用于当前决策是两种不同能力」这句话是全章的收束点之一。它解释了为什么**检索类评估做完还不够**：上下文里有了正确的信息（获得信息），不等于 Agent 会在下一步正确使用它（用于决策）。**轨迹前缀评估正是为了把这两件事分开测。**
- 三个闭环值得对比记忆（笔记补充的整理，均来自原文）：
  - **四个环节**：成功的定义 → 任务来源 → 验证方式 → 结果的运用（图 7-1）；
  - **系统改进闭环**：评估环境 → 数据集 → 自动化评估方法 → 揭示改进方向 → 系统改进 → 更新评估环境和数据集；
  - **科学方法论循环**：观察 → 假设 → 实验 → 验证 → 新认识 → 新假设。
  - 三者的粒度不同：第一个是「评估体系怎么搭」，第二个是「改进怎么滚动」，第三个是「工程怎么做成科学」。

**易混点**

- **Pass consecutive@k 与 Pass^k 是同一个东西的两种写法**：小结里用「Pass consecutive@k」，7.2.2 节用「Pass^k」，原文也说它可以读作 Pass consecutive k。

**一句话记住**

> 评估体系四环节（定义成功、任务来源、验证方式、结果运用）每环都影响结论可信度；本章是全书的「证据段」。

## 思考题

（原书此处先有一个「深度思考」的栏目标记，紧接着是「思考题」；下面 9 题原样列出，每题后附笔记补充的**思路提示**，不是标准答案。）

**1. ★★** LLM-as-a-Judge 使用语言模型评估语言模型的输出。这种「自我评估」是否存在系统性盲区——比如模型可能一致地给某种风格的回答打高分，而这种偏好与人类评判不一致？如何检测和校正这种偏差？

> 思路提示（笔记补充）：可以从 7.5.1 节的「长度偏差」入手——它就是一个已被识别的系统性盲区，而原文给的检测手段是「定期审计评分与回答长度的相关性」。推广开来就是：先找出一个可疑的风格变量（长度、语气、Markdown 格式、堆砌术语），再审计它与分数的相关性。校正方向可以想两条：改 Rubric（显式惩罚该风格）、换评判者（多源异构评判，因为不同家族的偏见往往是正交的）。

**2. ★★★** 评估数据集的「防泄漏」设计至关重要。但在开源生态中，benchmark 数据一旦公开，很快就会被纳入训练数据。这场「猫鼠游戏」有终局吗？设计一种从根本上抵抗数据泄漏的评估方法。

> 思路提示（笔记补充）：7.4.4 节给了三种手段——多源组合+专有附件（GAIA）、参数化动态实例化（AndroidWorld）、金丝雀标识符检测（Terminal-Bench），它们的思路分别是「提高获取门槛」「让记忆失效」「留下痕迹」。要「从根本上抵抗」，可以想的方向是让评估集**不可预先枚举**：参数化生成 + 私有附件 + 每次评估重新采样。也可以考虑把「泄漏检测」做成常设机制（金丝雀思路的强化版）。

**3. ★★** Scale AI 的四准则（基于专家指导、全面覆盖、按重要性加权、评价标准自包含）旨在消除评估的主观性。但某些任务维度（如「回答是否有帮助」「语气是否恰当」）天然具有主观性。如何为这些主观维度设计可靠的 Rubric？

> 思路提示（笔记补充）：四准则里最有用的抓手是第 4 条「评价标准自包含」——把「有帮助」这种抽象描述改写成可验证的行为（例如「指出了用户没问到但会影响决策的一个风险」）。另外可以借 7.5.1 节的「边界案例」机制：为模糊情况提供具体示例，把主观判断**转化为判例**，这也正是原文说的「最终从抽象准则演化为详尽的判例集」。

**4. ★★** τ-bench 通过模拟真实用户行为来评估 Agent。但模拟用户本身也是一个 LLM——它可能系统性地低估某些边缘场景（如情绪激动、表达不清的用户）。如何验证模拟用户本身的质量？

> 思路提示（笔记补充）：可以从 7.1.1 节 `task_instructions` 的三类约束（情绪设定、验收口径、事实锚定）出发，把「模拟用户的质量」拆成可检查的几条：它有没有遵守事实锚定、有没有在压力下仍然坚持正确的验收口径、它的耐心上限是否合理。另一条思路是拿真实生产轨迹中的人类回应作为参照集，比对模拟用户的行为分布。

**5. ★★** 配对比较（Bradley-Terry 模型）假设偏好是传递的（如果 A > B 且 B > C，则 A > C）。但人类偏好经常违反传递性。在 Agent 评估中，非传递偏好可能出现在哪些场景？这如何影响排名的可靠性？

> 思路提示（笔记补充）：结合 7.5.4 节的局限（排名取决于用户问了什么）想：当两个模型各自擅长的任务族不同时，偏好在不同任务子集上可能循环。「排名」本质是把多维能力压成一维，一旦能力维度之间不可比，传递性就危险了。可以从「分组排名 + 两两胜率矩阵」的角度考虑替代方案（实验 7-8 要求计算胜率矩阵，正是一种更细粒度的呈现）。

**6. ★★** 本章区分了 Pass@k 的能力上限与 Pass consecutive@k 的业务可靠性。对于一个单次成功率只有 60% 的 Agent，怎样结合任务的失败成本、重试成本和副作用，决定应该报告哪个指标、取多大的 $k$？

> 思路提示（笔记补充）：7.2.2 节已经给了三个决策变量：失败成本（低则看 Pass@k）、副作用（有副作用就不能重试，必须在沙盒或可回滚环境中采样）、以及报告的 $k$ 口径（同一任务的独立采样 vs 生产流水线连续 $k$ 个任务）。可以把「重试是否安全」当成第一道分水岭：安全则可用 Pass@k 叙事，不安全则必须报 Pass^k。

**7. ★★** 本章提出「观察→假设→实验→验证」的科学方法。但在实践中，Agent 的行为空间巨大，验证一个假设可能需要数百次评估运行。如何在有限计算预算下最大化评估的信息量？

> 思路提示（笔记补充）：7.9 节的三轮实验示范了一条路——先用最小子集（4 项任务）做方向性判断，再把资源投给有希望的改动（H5C 才进入完整复测）。另外可以借 7.5.3 节的轨迹前缀回归任务：它比端到端便宜得多，且能隔离单个决策点。还有 7.10.1 节的消融（一次关掉多个特性造出裸模型基线）也是提高信息量/成本比的手段。

**8. ★** AndroidWorld 小实验中，完整元素树把成功率从 25% 提高到 100%，却把 token 用量推到 2.498 倍；精简后成功率不变，token 降到对照组的 0.506 倍。怎样设计一套自动裁剪规则，既删掉无语义的 UI 节点，又不误删对可访问性、状态验证或后续操作有用的信息？

> 思路提示（笔记补充）：原文 H5C 删的是「不可见、没有文字、也不能操作的容器节点」——这三条本身就是一组可自动判定的规则。要把规则做得更稳，可以再想两层：给「可访问性」相关信息（如 contentDescription）白名单，以及对「状态验证」相关的节点（勾选、开关状态文本）做保护。同时注意 7.5.3 节的思路：裁剪规则本身也要有回归任务（轨迹前缀）来防止误删。

**9. ★★** τ-bench 的用户模拟采用了「渐进式信息透露」——不一次性提供所有信息，而是根据 Agent 的提问逐步透露。这种设计如何影响评估结果？如果模拟用户的信息透露策略与真实用户差异较大，评估结论还可靠吗？

> 思路提示（笔记补充）：7.1.1 节说明了它的实现方式（把 `known_info` 建模为独立字段）与目的（把「需求澄清」纳入考核）。要判断可靠性，可以反问：真实用户的初始表述是否也像模型那样「只说一句我上不了网」？如果模拟用户比真实用户更配合、更及时地提供关键信息，Agent 在评估中会显得比实际更能干；反之则更差。这与第 4 题的「验证模拟用户质量」是同一个问题的两面。

## 原文本章小结

（对照 7.12 节，忠实照抄整理。）

本章围绕一个核心问题展开：**如何判断 Agent 变好了还是变差了**。这条链路由四个环节构成——先厘清**成功的定义**（Pass@k、Best@k 与 Pass consecutive@k 的口径差异），再确定**任务从何而来**（公开基准、自建业务集与生产轨迹回流三个来源），随后选定**验证方式**（从确定性验证器到检查项清单、Rubric 加 LLM 评判，直至配对比较），最后把**分数转化为决策**（统计显著性、失败归因、回归任务与模型选型）。**每个环节都会影响结论的可信度。**

就全书的结构而言，本章建的是**第一章发现循环中的证据段**：失败归因决定了后续的提案有没有可依之据。

**轨迹前缀边界评估进一步说明，获得一条信息和正确地将它用于当前决策是两种不同能力**：端到端回归保证基本任务不退化，trajectory prefix 边界集则直接检查作用域判断、当前指令覆盖、澄清和危险动作前确认。用户记忆只是这一通用方法的一个案例。**生产级 Agent 的评估不是偶尔做一次的考试，而是从真实问题案例中持续生成回归任务和边界任务的验证系统。**

**核心方法论：观察→假设→实验→验证→新认识→新假设**，使 Agent 工程从经验驱动的「炼金术」转向数据驱动的科学工程。

本章介绍的评估体系形成一个完整闭环：**评估环境提供自动化的测试基础设施 → 评估数据集定义端到端任务和 trajectory prefix 边界 → 自动化评估方法（确定性验证器、LLM-as-a-Judge 与 Rubric）对 Agent 表现打分并生成失败归因 → Benchmark 与问题案例分析揭示改进方向 → 系统改进修复问题 → 更新评估环境和数据集，开始新一轮迭代。**

本章建立的评估体系不仅服务于当前系统的优化，也为后续两章提供关键基础：**第八章把评估环境和数据转化为模型后训练的输入；第九章则把生产轨迹的多维评价转化为知识、指令、程序的更新。**
