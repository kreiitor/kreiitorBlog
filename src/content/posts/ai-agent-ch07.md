## 本章地图

本章依次讨论：章首：评估为什么是 Agent 的核心基础设施；7.1 一条评估任务的解剖：τ²-bench 的 telecom 领域；7.2 评估指标：成功的定义；7.3 评估环境；7.4 评估数据集的设计；7.4.4 数据泄漏防范。

评估要回答的问题只有一个：这个 Agent 到底变好了还是变差了。构建完成不等于构建正确，开发者面前堆着一串没有显而易见答案的选择：用哪个模型、让模型能调用哪些工具、知识库里存什么数据、用户记忆怎么做、提示词和 Skills 怎么组织、Harness 里还要加哪些约束，以及评估结果怎样转化成持续进化的学习信号。本章给的是方法，用系统性的对比实验和消融实验，把真正的能力提升从表面的波动里择出来，免得「捡了芝麻，丢了西瓜」。它在全书的位置也很清楚：前六章展开的是单 Agent 的构建，第八章把评估环境和数据变成模型后训练的输入，第九章把生产轨迹的多维评价变成知识、指令、程序的更新，本章正好是「构建」与「进化」之间的度量层。往下走，7.1 用 τ²-bench 的一条真实任务把评估集的四大问题摆全，7.2 定指标口径（Pass@k 与 Pass^k），7.3 讲评估环境的五个组成要素，7.4 讲数据集怎么设计，7.5 是本章最重的一节，覆盖 Rubric、LLM-as-a-Judge、失败归因、回归任务与配对比较，7.6 把评估用于模型选型与成本分析，7.7 补上统计显著性这一环，7.8 讲可观测性，7.9 讲怎么把一份 Benchmark 报告变成系统改进，7.10 从外部评估转向生产级的内部评估基础设施，7.11 把评估环境升级成能支撑后训练的仿真环境，7.12 小结。

读完这一章，你应该能独立解剖一条评估任务并说清它的已知信息、任务指令、初始状态与成功条件，能算清 Pass@k、Best@k、Pass^k、Pass@1 的区别，能按五个要素判断一个评估环境是否可重复、该用人机交互型还是工具调用型，能写出符合四准则的 Rubric 并知道一票否决项放哪里，能给一条失败轨迹标出首个错误、区分主因与后果，能把失败归因转成端到端与轨迹前缀回归任务，能用标准误和配对分析判断「新模型 73% 对旧模型 70%」够不够切换，也能把一份成功率报告读成「下一轮只改什么」的路线图。

## 章首：评估为什么是 Agent 的核心基础设施

前六章把单 Agent 该有的部件都铺开了：上下文、知识、工具、代码能力，以及观察与动作空间。这些部件拼起来能跑，不代表拼对了。只有结果能被稳定测量，后续的模型训练和系统进化才有可靠方向，这正是评估在 Harness 里承担「验证」职能的原因。它给设计选择提供两类证据：系统性对比实验改变一个变量、看效果怎么动，消融实验逐一关掉某个组件、看整体性能掉多少，从而判断这个组件的真实贡献。软件工程里那句「没有度量就没有改进」在这里同样成立，缺一套可重复的评估体系，Agent 的迭代方向就只能靠直觉。

这里有一个容易被跳过的前提：评估的对象是模型与 Harness 的组合体，单看模型不够。同一个模型换个 Harness，表现可能差出一大截，有团队光靠优化 Harness 就把同一模型在终端类任务上的成绩显著拉高（第五章有详细展开）。所以 Agent 分数难看的时候，别急着换模型，先问是提示词、工具设计还是反馈循环拖了后腿。完善的评估体系必须能区分「模型能力不足」和「Harness 设计缺陷」这两类性质完全不同的问题。

区分的手段通常是**模型替换实验**（model swap）：固定 Harness，只把模型换成更强或更弱的，看分数怎么变。换强模型分数不涨，瓶颈在 Harness；换弱模型分数大跌、成绩随模型能力大幅波动，最直接的解读是瓶颈在模型能力本身、当前表现主要由模型决定（至于这是因为任务本身就难，还是 Harness 过度依赖模型先验，还得进一步分析）。这一对手法各自回答不同的问题：消融实验动 Harness、不动模型，用来定位 Harness 内部哪个部件重要；模型替换实验动模型、不动 Harness，用来判断瓶颈在哪一侧。两个都不做，只看到分数从 80 掉到 76，你只知道出事了，不知道是谁的责任。顺序上先做 model swap 定归属，再在归属内部做消融或替换定位到具体组件；如果 model swap 显示换强模型分数基本不动，就完全没必要再研究换模型，直接进 Harness 的消融。

术语上还有一处常被弄错：把「换了个更小的模型」叫消融是错的，消融一定是动组件、固定模型。

另外两个概念也要分开这里的性能退化（regression）指新版本在某些方面不如旧版本，属于能力层面的问题；而日常说的「分数波动」是抽样噪声，两者的处置方式完全不同，7.7 节专门讲怎么把它们分开。

评估体系的价值在模型快速演进的时代更突出。新模型在公开基准上更强，不保证在你的特定任务上也更强，甚至可能出现性能退化，只有在自己的评估数据集上完整测试过，升级决策才算数据驱动。再往前一步，「为未来的模型开发产品」就成了可行策略：当前模型撑不起商用，也可以先把产品做完、把评估集建起来，持续追踪新模型，一旦越过门槛立即上线。这相当于把评估集从一张考试成绩单变成上线触发器，前提是它反映的是真实业务门槛，公开基准上的几个百分点不算数。

## 7.1 一条评估任务的解剖：τ²-bench 的 telecom 领域

本节先完整解剖 τ²-bench 的 telecom 领域里一条真实任务。τ²-bench 是 Sierra 的开源项目，按 `chapter7/tau2-bench-eval/README.md` 中的命令克隆到本地后，打开文件 `data/tau2/domains/telecom/tasks_small.json` 就能看到。用的方法是「先解剖一条，再谈一般规律」：一条电信客服任务里同时包含了任务定义、用户模拟器、双控环境、分层验证与二元奖励，把它拆开就能得到评估集必须回答的四个问题，也就是什么算成功、任务从何而来、由谁验证、分数如何转化为决策，后面几节依次展开。

为什么挑 telecom 领域？电信客服同时具备三个特征：故障原因分布在「用户设备侧」和「运营商数据库侧」两边，必须双控；用户知道一些信息但不知道全部，必须渐进式提问；最终解决与否可以机械判定，看测速结果。它是最能一次把评估设计问题暴露齐全的领域。读这一节时，把这段 JSON 当成一份实验协议的实例来看会更顺：`ticket` 是输入，`user_scenario` 是用户模拟器的程序，`initial_state` 是重置脚本，`evaluation_criteria` 是判分器，四块各自对应后文 7.3 节五要素里的一部分。

> 检索确认：外部资料中确实存在一篇题为「τ²-Bench: Evaluating Conversational Agents in a Dual-Control Environment」的论文（arXiv:2506.07982），并被 ICML 收录为 poster；这与这里所说的「τ²-bench」「双控（Dual-Control）」命名一致。（来源：[τ²-Bench: Evaluating Conversational Agents in a Dual-Control Environment](https://ar5iv.labs.arxiv.org/html/2506.07982)、[ICML poster 页](https://icml.cc/virtual/2026/poster/64377)）

### 7.1.1 任务定义的四个组成部分

以下是该文件中的一条任务，这里为便于阅读做了删节：

```jsonc
{
  "id": "[mobile_data_issue]airplane_mode_on|user_abroad_roaming_enabled_off",
  // 提供给Agent 的工单
  "ticket": " 用户手机无法上网，状态栏显示'No Service'。客户John Smith，
             号码555-123-2002，当前在法国。速度测试结果为excellent 才算解决。
             不更换套餐，必要时愿意充值2.0 GB 流量。",
  // 提供给用户模拟器的行为规范
  "user_scenario": { "instructions": {
    "known_info": "You are John Smith with phone number 555-123-2002.
                   You are currently abroad in France.",
    "unknown_info": null,
    "task_instructions":
      "⋯express mild frustration after the first unsuccessful attempt.
       You will consider the issue resolved only when speed test returns
       excellent internet speed and nothing else. If it returns poor, fair
       or good, you will not consider the issue resolved.
       Whenever the agent asks you about your device, always ground your
       responses on the results of tool calls. ⋯
       Never make up the results of tool calls."
  }},
  // 运行前将两侧状态重置到同一起点
  "initial_state": { "initialization_actions": [
    { "env_type": "user",      "func_name": "turn_airplane_mode_on" },
    { "env_type": "user",      "func_name": "turn_roaming_off" },
    { "env_type": "assistant", "func_name": "enable_roaming",
      "arguments": { "customer_id": "C1001", "line_id": "L1002" } }
  ]},
  // 评分标准
  "evaluation_criteria": {
    "actions": [
      { "requestor": "user", "name": "toggle_airplane_mode" },
      { "requestor": "user", "name": "toggle_roaming" }
    ],
    "env_assertions": [
      { "func_name": "assert_mobile_data_status", "expected_status": true },
      { "func_name": "assert_internet_speed",
        "expected_speed": 200, "expected_desc": "excellent" }
    ],
    "communicate_info": null,
    "nl_assertions": null,
    "reward_basis": ["ENV_ASSERTION"]
  }
}
```

（说明：这里此段 JSON 因排版换行，按语义统一了缩进；字段名、字段值与注释一字未改。）

这段定义中有四处设计值得说明。`known_info` 这一项做的是显式建模用户的认知边界：它只包含姓名、号码与所在国家三项信息，飞行模式开启、数据漫游关闭这两项真正的故障原因不在其中，用户并不知情，也就无法主动陈述，Agent 只能通过提问和引导用户查询来获取。这是**渐进式信息透露**（Progressive Information Disclosure）在任务定义层面的实现方式，它把用户的知识范围建模成一个独立字段，没有停留在「不要一次说完」这种提示词层面的约束。多数基准在任务开始时即给出完整需求，而真实用户的初始表述往往只是「我上不了网」，把需求澄清到可执行的程度，本身就是 Agent 必须具备的能力之一。

`task_instructions` 管的是另一件事：防止用户模拟器被 Agent 忽悠。它包含三类约束，情绪设定要求首次修复失败后表现出轻度不满，验收口径规定仅当测速结果为 excellent 时才认定问题解决、poor 与 fair 与 good 均不接受，还有事实锚定（Grounding）要求，即关于设备状态的任何回答都必须以工具返回结果为依据。缺少事实锚定约束时，模拟用户会顺应 Agent 的引导确认问题已解决，评估随之退化为两个模型之间的相互确认。

模拟用户和 Agent 也都不具备完全信息。飞行模式与漫游开关属于用户侧，运营商侧的 `enable_roaming` 属于 Agent 侧。这一划分决定了故障的形态：运营商侧漫游已开通，用户设备侧却处于关闭状态，Agent 查询数据库只能得到「配置正常」的结论。故障位于数据库不可见的一侧，只有引导用户查询才能发现。

剩下的一处是多个维度的过程和结果校验。`env_assertions` 检验终态（移动数据可用、测速达 200 Mbps 以上且评级为 excellent），`actions` 检验关键动作是否发生，`communicate_info` 与 `nl_assertions` 检验必要信息是否已告知用户。每个任务可以检查四个维度中一个或多个维度的结果。

把这条任务在脑子里跑一遍，就能看出它为什么「难而不刁」。用户只知道「我在法国、我上不了网」，真正的原因（飞行模式 ON、数据漫游 OFF）在设备侧；Agent 查运营商库只会看到「漫游已开通、配置正常」，所以它必须反过来把用户当传感器用，让用户去读状态栏、去关开关；判分要求测速 ≥200 Mbps 且评级 excellent，逼着 Agent 走完「关飞行模式 → 开漫游 → 测速」的完整闭环，中途说一句「我觉得好了」是过不了的。

`initial_state` 里的 `initialization_actions` 值得单独看。三条动作分别打在 `user` 和 `assistant` 两个环境上，第三条还带了参数（`customer_id: C1001`、`line_id: L1002`）。它说明重置必须是双侧的：如果只重置用户设备、忘了重置运营商库里的漫游状态，第二次运行就不是同一个起点了。而 `reward_basis: ["ENV_ASSERTION"]` 是这条任务的计分口径，四层检查全部记录，只有第一层计入奖励，这个设计在下文的失败分析里会变成一个具体的漏洞。

工程上最容易踩的坑是把验收标准写得可猜。如果 `ticket` 里直接写「检查飞行模式和漫游」，Agent 不用提问也能通过，这条任务就退化成了填空题。τ²-bench 把「用户知情范围」和「验收口径」拆成两个字段，正是为了避免这种退化。`known_info` 界定信息边界，`task_instructions` 规定透露方式与情绪，前者防「剧透」，后者防「演戏不真」；`env_assertions` 查结果对不对，`actions` 查该做的动作有没有做，一条任务可以只查其中一层，也可以全查。

### 7.1.2 一次真实运行的轨迹

这里请读者运行 τ²-bench telecom 领域的评估任务，实际观察任务设计、用户模拟器的设计、过程和结果校验逻辑，以及 Agent 的执行轨迹，分析 Agent 为何失败。

#### 实验7-1 ★：运行τ²-bench 并对比τ-bench 的演进

本实验通过运行 τ²-bench 评估框架，理解人机交互型评估环境的设计要点。先按本节的路径通读任务定义文件，每条任务包含已知信息、任务指令、初始状态与成功条件四个部分；随后运行完整评估流程，观察用户模拟器与 Agent 的多轮对话，分析典型失败模式（政策违规、信息遗漏、过度转接人工等）。

> **图 7-3：τ²-bench 的双控环境与分层验证**
>
> τ²-bench 的双控环境与分层验证。图分三大块：
> - 上半部分是两个参与方加一条对话通道。左侧「用户模拟器（LLM）」框内写着：`known_info`：John Smith / 555-123-2002 / 在法国；`task_instructions`：渐进透露 · 情绪 · 事实锚定；验收口径：仅 excellent 算解决。右侧「Agent（待评估）」框内写着：输入：工单 + 领域政策；不可见：用户设备的真实状态；只能引导用户操作，无法代其执行。两者之间是「多轮对话」，旁边标注「渐进式信息透露」。
> - 中间是共享环境（双控：两侧都能改写状态），分成两栏。左栏「设备侧状态」：飞行模式 ON · 数据漫游 OFF · 省流模式 · 剩余流量；用户工具：`toggle_airplane_mode` / `toggle_roaming` / `check_status_bar` / `run_speed_test`。右栏「运营商侧数据库」：客户 C1001 · 线路 L1001/L1002/L1003 · 套餐 · 账单；Agent 工具：`get_customer_by_phone` / `get_data_usage` / `enable_roaming` / `refuel_data`。图旁有一句关键说明：用户执行 `toggle_roaming` 后环境已改变，Agent 必须重新调用工具才能获知结果，验证因此覆盖「是否读到了用户侧的操作结果」。
> - 下半部分是任务结束后：四层检查 + 聚合规则。`env_assertions`（移动数据可用；测速 ≥ 200 / excellent）、`actions`（`toggle_airplane_mode`，且 `requestor` 必须为 user）、`communicate_info`（必要信息是否告知，本题为 null）、`nl_assertions`（自然语言层判定，本题为 null）；最后一行写着 `reward_basis = ["ENV_ASSERTION"]` → 仅采信第一层；其余各层照常记录但不计入奖励。

配套仓库保留了一次运行记录（`chapter7/tau2-bench-eval`），这里分析了其中一条成功的运行记录。前十余轮是账户识别阶段：Agent 依据号码查得客户 C1001，随后逐一查询 L1001、L1002、L1003 三条线路的流量，又回头询问用户在法国实际使用的号码。第 17 条消息中它给出了一个错误结论：

> Agent（17）：号码555-123-2002 不在您的活跃线路中，最接近的是555-123-2001⋯⋯

这个结论仅基于 L1001 一条线路的查询结果。用户坚持号码无误后，Agent 继续查询 L1002，方才对应上。关键转折出现在第 30 条：

> 用户（30）→调用 `check_network_status()`、`check_status_bar()`
> 工具返回（31）：`Airplane Mode: ON | Cellular Connection: no_service | Mobile Data Enabled: Yes | Data Roaming Enabled: No`
> 用户（33）：我看到手机当前处于飞行模式，因此没有信号。移动数据是开启的，但数据漫游是关闭的。需要我关掉飞行模式试一下吗？

注意这里发出工具调用的是用户而非 Agent，这就是**双控**（Dual-Control）机制：模拟用户拥有一套独立的工具集，如 `check_status_bar`、`toggle_airplane_mode`、`reseat_sim_card`、`run_speed_test` 等。它的含义可以这样理解：普通工具调用型任务里只有一个执行者，环境是 Agent 一个人的沙盒；客服场景里用户手里也有工具，用户执行完动作后环境变了，Agent 必须再查一次才知道结果。这一步「再查一次」就是双控带来的额外考核点，它检查的是「Agent 会不会读用户侧的操作结果」，「Agent 会不会说」在这一层不算考核项。

其后的排查较为顺利：Agent 要求用户关闭飞行模式并开启漫游，用户执行相应操作（35、37），状态栏转为 5G 满格；Agent 要求测速，返回 275 Mbps、评级 Excellent（46），用户确认问题解决。两条 `env_assertions` 均通过，reward = 1.0。

这条满分轨迹中还包含一处未被验证器捕获的问题。telecom 的 Agent 政策首段即规定「You should only make one tool call at a time」，而第 4 条消息中 Agent 一次发出了 `get_customer_by_phone` 与 `get_customer_by_name` 两个调用。验证器没有因此判定出错，原因在于本题的 `reward_basis` 只考虑最终状态。这算不上 τ²-bench 的疏漏，它是二元奖励的固有代价：以过程细节换取跨模型可比的单一数字。生产环境中的评估系统往往需要更多，不仅要判定对错，还要指出问题出在哪里。

失败的那条任务同样具有分析价值。用户号码为 555-123-2002，Agent 却选定 L1001 线路，并以其 3.2/5 GB 的用量为依据继续推进。期间 `get_details_by_id(L1001)` 明确返回该线路号码为 555-123-2001，Agent 读取了这一结果却未修正判断，此后在无关排查上消耗数十条消息，最终转接人工。它实际完成了任务的一半，引导用户关闭了省流模式，该用户侧动作真实发生并被环境验证；但线路选择错误导致所需的 2 GB 流量充值未执行，三条终态断言全部失败。这一失败形态与后文「失败归因」一节讨论的 AndroidWorld 案例高度相似：修正判断所需的证据已进入上下文，Agent 未据此回溯。

成功轨迹里那个错误值得再多看一眼。Agent 只基于一条线路就下了结论，用户否认后它才继续查；这个错误没有被验证器判错，因为终态对了，但二元奖励会放过过程错误，它像一份只看最终报告通过与否的审计，效率极高，却查不出过程违规。失败轨迹里则是另一副样子：证据明明在上下文里，模型却没有回溯，`get_details_by_id(L1001)` 返回 555-123-2001 之后，正确的反应是「我选错线路了，回到号码匹配这一步」，实际反应却是沿着错误假设继续往下排查。这类失败在端到端分数上只体现为一个 0，只有读轨迹才能看出根因，7.5.2 节要建的失败归因系统就是为了这个。把两条轨迹放在一起看，成功的那条靠的是「用户纠错 → 重新查询」这个闭环，失败的那条缺的正是它。

读数时还有两点容易忽略。任务失败不等于全线失败：上面那条失败轨迹里 Agent 其实完成了一半，关掉省流模式且被环境验证过，但奖励是二元的，所以计 0，看到「0 分」时要留意它背后可能是部分完成，也可能是完全没开始。验证器通过也不等于行为合规：第 4 条消息的并行双调用违反了政策却未被判错。评估的「分数」和「合规」是两套信号。

这条任务已经把一个评估集必须回答的问题摆全了：什么算成功、任务从何而来、由谁验证、分数如何转化为决策。

## 7.2 评估指标：成功的定义

上一节的评估结果是五条任务通过四条。仅凭 0.8 这个数字无法判断该系统是否可用：若它对应的是一个退款客服，则意味着每五名用户中就有一人未能拿到应得的退款；若它对应的是一个用于挖掘漏洞的安全 Agent，五次中命中四次已属相当可观。差别在于业务场景对成功率有多高的要求。同一个数字在不同业务里的含义完全不同，所以「成功」不能只有一个定义，本章给出两个：一个测能力上限（Pass@k），一个测业务可靠性（Pass^k）。读报告时第一件事就是问，这个百分比是按哪个口径算的。

### 7.2.1 技术奇观：用 Pass@k 看能力上限

当前许多模型和 Agent 仍处在一个可以称为**技术奇观**的阶段。这里的「奇观」是指在大量尝试、充足时间和人工筛选下展示出的能力上限：只要其中一次成功，就足以证明「这件事原则上做得到」。这正是 Pass@k 的逻辑，在同一任务上运行 $k$ 次，只要至少有一次通过，任务就算通过；如果输出是连续得分，则取最好的一次，记为 Best@k。

Anthropic 对长时运行 Agent 的讨论体现了这类能力上限。例如，让 Agent 自主工作一周，从头写出一个 C 编译器；或者持续探索，直到找到一个重要数学猜想的反例；又或者反复审查开源软件，发现已经存在几十年的重大安全漏洞。对这类工程与科研探索来说，值得展示的是把探索预算拉长后终于出现的那一条突破性轨迹，要求每次都做对是另一回事。对于科研发现、漏洞挖掘、开放式创作等任务，这种能力上限本身就很有价值：人类可以从 $k$ 条候选轨迹中挑出那一条最好的。

除了基座模型，很多应用公司也在使用「技术奇观」策略。Manus 之所以引发广泛关注，是因为它提供了一个虚拟电脑，让此前对 Agent 没有直观概念的人发现 AI 可以像人一样操作电脑，持续工作半小时甚至一小时，逐步完成复杂的任务。OpenClaw 则让很多人第一次感受到 Agent 的「活人感」：用户可以像给真人安排工作一样，通过即时通讯软件给它分配任务；它可以访问电脑上的所有文件和在线服务，工作到一定阶段会主动反馈或向用户索取新信息，甚至能够主动唤醒自己去查询和处理邮件。早期的 Manus 和 OpenClaw 在完成复杂任务时的成功率并不高，token 成本也非常高。但由于这些 Agent 框架具有通用性，使用最强模型时，复杂任务往往有较高的 Pass@k，展现出较高的技术上限。这些「技术奇观」在社交网络上被大量分享，是这些 Agent 产品成功的关键。

把 Pass@k 想成「高考复读」就好理解：给你 $k$ 次机会，只要有一次上线就算你行，它衡量的是这条能力线的最高水位，稳定性不在其中。「技术奇观」这个词带着一点批判意味：一段刷屏的演示视频，可能来自几百次尝试里的那一两次。这并不虚伪，对漏洞挖掘、科研探索这类任务，人类本来就会从候选里挑最好的；但拿这套叙事去承诺「稳定的业务交付」，就错位了。判断一个 demo 属于哪一类，看两个信号即可：是不是只展示了一次成功，有没有说明尝试了多少次、花了多少 token。补的那句「token 成本也非常高」，提醒的正是这一点。

Pass@k 与 Pass@1 要分开：Pass@1 是单次平均成功率（见 7.6.1 节这里口径），$k=1$ 时 Pass@k 退化为 Pass@1。写法上也要留意，Pass@k 的小写 $k$ 在上标外，含义是「至少一次成功」；Pass^k 是「每一次都成功」，两者的数学形式见下一小节。

### 7.2.2 业务可靠性：关注 Pass^k

真实业务通常更关心另一件事：在多次尝试中一次错都不能犯。我们把这个目标称为 Pass^k（可以读作 Pass consecutive k）：同一任务连续运行 $k$ 次，要求每一次都通过，且不能触发安全、合规或幻觉等一票否决项。它回答的是「Agent 能否稳定可靠地交付」，「能否偶尔创造奇迹」不在这个指标的考察范围内。

若每次运行相互独立、单次成功率为 $p$，两类指标的关系很直观：

$$
\text{Pass@}k = 1-(1-p)^k,\qquad \text{Pass}^{k}=p^{k}
$$

其中 $p$ 是单次运行的成功率（无量纲，取值 $0\le p\le 1$），$k$ 是运行次数（无量纲的正整数），$\text{Pass@}k$ 表示「$k$ 次里至少成功一次」的概率，$\text{Pass}^{k}$ 表示「$k$ 次全部成功」的概率。两式都建立在「各次运行相互独立」这一假设上。

例如单次成功率 $p=0.6$ 时，$k=5$：$\text{Pass@}5 = 1-0.4^{5}\approx 99.0\%$，看起来几乎总能「至少成功一次」；但 $\text{Pass}^{5} = 0.6^{5}\approx 7.8\%$，说明连续五次都不出错仍然很难。前一个数字适合衡量探索时的能力天花板，后一个数字才接近支付、退款、权限变更、生产部署等场景的可靠性要求。我把这两个数代进去复算了一遍（补充的计算）：$\text{Pass@}5 = 1-0.4^{5}=1-0.01024=0.98976\approx 99.0\%$，$\text{Pass}^{5} = 0.6^{5}=0.07776\approx 7.8\%$，与这里完全一致。两个数字的落差很说明问题：同一个 $p=0.6$，从「几乎必然成功一次」到「几乎必然出错至少一次」，只差一个上标的位置。

Pass^k 掉得这么快，是因为它是乘法：$0.6^2=0.36$、$0.6^3=0.216$、$0.6^5\approx0.078$。只要单次成功率不接近 1，连续多次全对的概率就会指数衰减。这也解释了为什么「99% 单次成功率」听起来很好，连续 100 次的 Pass^k 却只有约 $0.99^{100}\approx36.6\%$（补充的计算）。

指标怎么选，取决于失败的代价。支付、退款、权限变更、生产部署这些场景看 Pass^k，因为「失败一次」的代价不可回滚，重试也可能造成重复扣款之类的副作用；漏洞挖掘、科研探索、开放式创作则看 Pass@k 或 Best@k，因为候选可以人工挑，失败没有副作用。那句「不能简单地重试直到成功」是关键约束：如果你为了把 Pass@1 刷高而无限重试，那么在真实业务里副作用早就发生了。所以报告里必须写清 $k$ 的口径，是同一任务的 $k$ 次独立采样，还是生产流水线上连续 $k$ 个任务，这两者完全不同，前者可以并行、互不影响，后者是有状态的，前一个任务的残留会影响后一个。对于会产生副作用的操作，采样要在沙盒或可回滚环境中做，并把每一次失败都记入可靠性指标。

Best@k 与 Pass@k 也别混：当输出是连续的分数而非通过/不通过时，Pass@k 的说法就不适用，改用「取最好的一次」的 Best@k。这里对二者关系的写法是：如果输出是连续得分，则取最好的一次，记为 Best@k。

## 7.3 评估环境

明确了指标口径，接下来的问题是在哪里测。评估环境是一套能够重复运行的装置：给定同一个初始状态，同一个 Agent 应当得到可比较的结果。

### 7.3.1 五个组成要素

回到前面解剖的那条 telecom 任务，以它为参照，一个可重复运行的评估环境所需的组成部分已经完备。

数据集（Dataset）即文件本身。初始状态、给 Agent 的工单、给模拟器的行为规范与验收标准打包为一条记录，一条记录即一个用例。环境状态（Environment State）是任务执行中的可变信息：数据库中的客户、线路、套餐与账单，加上设备侧的飞行模式、漫游、省流开关与剩余流量。它必须可重置，`initialization_actions` 即重置脚本；真实性要求状态变化符合业务逻辑，可控性要求每次运行前都能回到同一起点。工具接口（Tools）分属两侧，Agent 可调用查询客户、查询用量、充值流量、转接人工等运营商侧操作，用户可调用设备侧的各项开关，两套工具均为原子操作，不存在「解决用户的上网问题」这类高层抽象：抽象层次过高会使评估退化为对单次函数调用的考察，规划与推理环节被工具本身吸收。评分标准（Rubric）即 `evaluation_criteria` 的四层检查，加上 `reward_basis` 这一聚合规则。执行协议（Interaction Protocol）规定交互顺序与终止条件，此处的正常终止信号为模拟用户输出 `###STOP###`，此外还有轮数上限，以及模拟用户因耐心耗尽而主动结束对话，沟通效率过低本身即计为失败。这里的结论是，五个要素缺其一，评估便无法构成可重复的循环；后文考察其他基准时，仍以这五项作为对照框架。

把五要素记成一条流水线会更容易：数据集是考卷，环境状态是考场与可复原的现场，工具接口是允许使用的工具与它们的最小单位，评分标准是判分细则，执行协议管考试怎么开始、怎么结束。其中三个设计点容易被忽视。重置不是可选项，没有重置，第二次运行就在第一次的残局上开始，两次分数不可比，后面所有统计都失去意义，7.11 节还会强调这一点对训练更重要（数百万个 episode）。工具必须原子化，「一键解决用户上网问题」这种高层工具会让规划和推理被工具本身吸收，因为一条工具调用就完成了整个任务，评估测的只剩「模型会不会调这个函数」；原子化的代价是 Agent 要做更多步，而这恰恰是你要测的能力。终止条件要包含「耐心耗尽」，如果只允许「问题解决」和「轮数上限」两种结束方式，Agent 就可以用无意义的反复确认拖到上限而不被判失败，把「模拟用户耐心耗尽而主动结束」也算失败，等于给沟通效率上了约束。工程实践上，检查一个评估环境是否合格，最快的方法就是逐条问：数据集在哪？状态能重置吗？工具是原子的吗？判分口径写死了吗？除了成功还有哪些结束方式？五问全答得出来，才算环境建好了。

环境状态与数据集不是同一件东西：数据集是静态的任务记录（工单、行为规范、验收标准），环境状态是运行中会变的那些量（数据库、设备开关），前者一条记录一个用例，后者需要被重置到一个确定起点。评分标准里的「四层检查」与「聚合规则」也是两件事，四层检查负责产生四组信号，`reward_basis` 决定哪几组计入奖励，7.1.2 里那个「并列双调用未被判错」的例子，根因就是聚合规则只采信了终态这一层。

### 7.3.2 人机交互型与工具调用型评估环境

telecom 这类任务必须设置交互对象，五个要素中的用户模拟部分不可或缺。另有一大类任务并不存在对话对方：代码生成、数据分析、数学求解等任务中，Agent 自始至终只与工具交互，正确性由能否通过执行验证决定，既不需要人工标注，也不需要模型评判。这类环境省去了用户模拟器，其余四个要素依然存在，只是形态更简单：环境状态是文件系统或数据库，评分标准是一段测试代码，执行协议退化为「持续调用工具，直至给出答案或耗尽轮次」。

Verifiers 框架按两个维度对这类环境分层：任务是否需要保持跨轮状态，是否需要隔离。`SingleTurnEnv` 适用于问一道数学题后直接验证答案；`ToolEnv` 适用于搜索多个网页后综合回答再验证最终结果；`StatefulToolEnv` 适用于修改数据库记录后验证状态变化；`SandboxEnv` 适用于在沙盒中运行代码后检查输出文件。表 7-1 汇总了这四类环境，便于按任务状态、工具调用和隔离需求进行选择。

表 7-1 Verifiers 环境类型对比

| 环境类型 | 状态保持 | 工具调用 | 典型用例 |
| --- | --- | --- | --- |
| SingleTurnEnv | 无 | 无 | 单轮问答、数学题 |
| ToolEnv | 无 | 多轮 | 搜索+ 信息综合 |
| StatefulToolEnv | 有 | 多轮 | 修改数据库记录 |
| SandboxEnv | 有+ 隔离 | 多轮 | 代码执行与测试 |

该框架支持并行采样与轨迹缓存，每次评估的完整轨迹（观察、行动、奖励）均会保存，便于后续分析与回放。此外，工具的执行效果取决于当前状态，因此失败时应返回清晰的错误信息，只给一个失败标志并不够用，Agent 才能据此调整策略。这一条看着琐碎，其实是 Agent 评估与普通单元测试的重要区别：单元测试只需要知道 FAIL，Agent 需要知道「为什么 FAIL」以便换策略，一个只返回 `false` 的工具会让 Agent 原地打转。

两类环境的考察重点不同：工具调用型评估考察的是可观测状态变更的正确性，人机交互型评估考察的则是沟通策略的合理性，前者验证行动，后者验证引导。两类环境的结构对比见图 7-2。

> - 左：工具调用型（Verifiers）。Agent（LLM）→ 工具执行环境，例如 `run_python("def fib(n): ...")` → `{"result": [1,1,2,3,5,8]}`；下面接「可执行验证器」，写着 `assert fib(10) == 55 # PASS`、`assert fib(0) == 0 # PASS`、`reward = 1.0 (全部通过)`。图中标注特点：无需人工/LLM 评判。
> - 右：人机交互型（τ-bench）。用户模拟器与 Agent（LLM）对话，用户开口是「我的航班有问题」；Agent 做工具调用 `lookup_booking("BK-98712")` → `{"status":"confirmed","flight":"UA123"}`；下面接「双重验证」：① DB：`booking.status == "cancelled"`；② 对话：包含「退款 \$150」、包含「3-5个工作日到账」。`reward = 0/1 (双重均通过)`。图中标注特点：渐进式信息透露+状态验证。

这两类环境的差别，用一句话说就是：一个只有「做」，一个还有「说」。工具调用型里，「做对了」就等于「说对了」，因为唯一的输出就是工具产生的状态变更，验证器直接查状态/跑测试即可；人机交互型里，「做对了」不等于「说对了」，7.5.2.1 节会用 τ²-bench 的公开基线数据说明：有 80 次运行的环境状态正确、但信息告知错误。所以人机交互型必须做双重验证。

Verifiers 那张表实际是一张「按需要挑最简环境」的决策表，选择顺序可以这样记：一轮就出答案、不用工具，选 `SingleTurnEnv`；要用工具但状态不用留，选 `ToolEnv`；要改数据库并验证改动，选 `StatefulToolEnv`；要跑代码、检查产物文件或需要隔离，选 `SandboxEnv`。

`StatefulToolEnv` 与 `SandboxEnv` 都「有状态」，区别在隔离：前者只需跨轮保持状态（例如改一条数据库记录），后者还要在隔离环境里执行代码、检查输出文件，表 7-1 里 SandboxEnv 的状态保持列写的是「有+ 隔离」。「不需要 LLM 评判」也不等于「评估更弱」，工具调用型只是把判据换成了执行结果，它的可复现性和成本优势更强，只是无法评估沟通类维度。

## 7.4 评估数据集的设计

评估环境是舞台，数据集是剧本。同样是那五个要素，换一类任务，填法可能完全不同：任务从何而来、验证器能核实到什么深度、如何防止被记忆。本节从几个公开基准的设计实践入手，最后回到一个更实际的问题，自建评估集的任务应当从哪里来。数据集设计值得单独一节，是因为环境的五个要素里，「工具接口」和「执行协议」的形态相对固定（都由任务类型决定），真正决定评估力的是任务从哪里来、判据有多深、会不会被背下来这三件事。

7.3 与 7.4 的关系可以记成一句话：环境决定「能不能重复测」，数据集决定「测出来的分有没有意义」。一台可重复的跑步机不代表跑道长度选得对。本节反复出现的三个词值得预先标出：**验证深度**（验证器能核到什么程度）、**参数化生成**（任务可动态实例化）、**泄漏防范**（防止题目进入训练集）。7.4.6 节说这三者加上质量控制，「恰是自建评估集最容易疏漏的几处」。

7.3.2 节区分的有无交互对象只是环境层面的第一层差异，数据集层面的分歧更能体现设计取舍。表 7-2 将几个常被引用的基准并列。

### 7.4.2 验证器

Agent 很容易写一篇洋洋洒洒的报告，说任务已经全部完成，但事实上根本没有完成。评估框架必须核实机器可独立复核的事实，Agent 的自我陈述不算数。

SWE-bench Verified 将「修复完成」拆解为两个独立命题。一组是 **FAIL_TO_PASS：修复前失败、修复后通过，证明问题确已解决；另一组是 PASS_TO_PASS**：修复前后均通过，证明未引入新的缺陷。只检验前者，Agent 可以通过删改妨碍通过的断言蒙混；只检验后者，则等同于未作检验。两组同时检验，才使「已修复」与「未破坏」成为两个各自可证的结论。它还额外确认测试自身的稳定性，排除时而通过时而失败的不稳定测试（flaky test）。这对设计很值得记住，因为它把「修好了」和「没弄坏」拆成了两个可以各自证伪的命题，用日常话说，一个查「病治好了没」，一个查「有没有治出新病」。

OSWorld 的验证器能发现表面完成但实质错误的情形。它配备 134 个独立评估函数，拥有完整的操作系统访问权限，能够检查文件系统结构、进程状态、网络连接与应用内部状态。在数据库操作任务中，评估脚本不仅确认报告文件存在，还会连接数据库核实 SQL 是否正确执行；在浏览器任务中则会分析 DOM 树、检查 cookie 与 localStorage、向后端发送验证请求确认表单确已生效。

Terminal-Bench 的任务 `build-linux-kernel-qemu` 要求从源码构建 Linux 内核 6.9，在 `start_kernel` 中加入自定义 `printk`，生成 initramfs 并在 QEMU 中运行，成功标准是启动日志中出现该自定义消息。Agent 无法伪造输出，只能真正完成整个流程。

三个例子的验证深度是递进的。SWE-bench Verified 验的是测试套件的状态变化，也就是前后两次运行的差异；OSWorld 验系统内部状态，涵盖文件系统、进程、网络、DOM、cookie、localStorage、后端请求，所以能抓出「报告文件存在但数据库没改」这种表面完成；Terminal-Bench 验的是只有真正执行过才会出现的副产物，也就是内核启动日志里那条自定义 `printk` 消息。自定义 `printk` 这个设计很巧，结果文件存在这类证据它不看，它要的是构建与运行链路真的跑通以后留下的痕迹。

工程上有两条可迁移的做法：优先找「只有真做了才会产生的痕迹」，比如启动日志、哈希、随机 GUID、后端写入记录；同时设置正向与反向断言，别只查「该有的有了」，还要查「不该有的没出现」。这里还有一组容易混的说法。FAIL_TO_PASS 不等于全部测试通过，它特指「修复前失败、修复后通过」的那组测试，一个补丁可能让所有测试都通过，但如果那组测试原本就是通过的，它就不构成修复的证据。验证器通过也不等于 Agent 合规，验证器只按预设断言判分，过程违规（如 7.1.2 的并行双调用）不会被它捕获。说到底，验证器只认机器能独立复核的事实：「已修复」和「未破坏」要分别立证，伪造不了的痕迹最有说服力。

## 7.4.3 任务的难度划分

评估任务集里得放不同难度的任务。原因很直接：全挑简单题，模型一升级就全员满分，这套题立刻失去区分度。难度分层还有第二个作用，经常被忽略，就是失败落在哪一级，直接告诉你该修什么。

GAIA 把全套 466 题切成三级。Level 1 只需一至两个工具，人类通过率 93.9%，GPT-4 是 30.3%；Level 2 需要多步思考，91.8% 对 9.7%；Level 3 需要复杂组合，87.3% 对 0%。三级对应的改进方向并不一样：Level 1 失手说明基础工具使用有问题，Level 2 失手说明多步规划与信息整合不到位，Level 3 失手则是长序列思考与复杂性管理跟不上。

把这组数字的差距算出来，形状会更清楚。Level 1 差约 64 个百分点，Level 2 约 82 个百分点，Level 3 是 87.3 个百分点（这三个差值是我按这里的百分比相减得到的，本节只给了两侧的通过率）。难度每上一级，人类几乎不掉，模型掉到零。分层比一个总平均分更有信息量，说的就是这件事。

其他基准的难度梯度长得不一样。Terminal-Bench 从简单的 `mlflow` 模型注册起步，到中等难度的 7z 密码破解，再到困难的 git 服务器与 webserver 多组件集成，最高一档是 FEAL 差分密码分析。τ²-bench 另开了一路，专门设计陷阱任务：用户声称「客服已批准取消」，实际上并不符合政策，看 Agent 在压力与误导下还能不能守住判断。

这里有两处容易混。难度与复杂度不是一回事，FEAL 差分密码分析的难，难在领域知识与长链路；陷阱任务的难，难在输入本身在骗你。两类任务考的能力不同，设计评估集时都要有。另一处是 Level 3 上模型得 0% 不说明这个基准没价值，它的价值恰恰在于现在测不出来、将来能测出来，这跟这里「任务集不会快速过时」是同一层意思。

## 7.4.4 数据泄漏防范

这一节回答的是另一个问题：模型是不是把答案背下来了。三种手段各走一条路。

GAIA 的思路是让答案根本不在网上。它的任务概念简单而路径开放，例如从某一特定日期的 NASA 每日天文图片出发，识别图中宇航员，查出他所属的宇航员组，再算出这个组里在太空停留时间最短的那个人，并严格按「姓氏，分号分隔，千位分隔符」的格式输出。答案高度具体，判分靠精确字符串匹配。防泄漏依靠两点：问题必须组合多个信息源才能作答，单一网页给不出答案；部分任务还配有专门制作的附件，也就是互联网上不存在的 PDF、音频、图片。

AndroidWorld 换个方向，让答案每次都变。它的任务是可动态实例化的模板，例如「将联系人 [CONTACT_NAME] 的电话改为 [NEW_PHONE]」，每次评估随机生成参数值。这带来三方面收益：参数每次不同，回放固定操作序列就失效了；单个模板能生成近乎无限的实例；固定一部分参数、只改其余参数，还能精确测量某个特定因素的影响。AndroidWorld 那第三点收益在工程上特别实用，参数化模板加控制变量，等于把评估集变成了一个能做消融实验的装置。想测 Agent 是不是依赖某句 UI 文案，只改那一个参数就行。

Terminal-Bench 走第三条路，让泄漏留下痕迹。它在题面里嵌金丝雀标识符，每道题带一个 canary GUID，模型如果能输出含这个 GUID 的内容，就说明基准数据已经进了训练集。这里对它的定位写得很明确：不阻止数据泄漏，但使泄漏可被检测。这跟防抄袭的水印是一个意思，往题面里放一段无意义的随机串，模型能原样吐出来就说明它见过。它的用处在于，当你怀疑某个分数虚高时，有办法去验证。

还有一处别混。防泄漏针对的是题目进入训练集，难度分层针对的是模型升级后全员满分，前者是数据问题，后者是设计问题。金丝雀 GUID 也不该当成防护手段，它只管检测。

### 7.4.5 质量控制与长期维护

做一个高质量的评估集非常困难。前面几个基准的现行形态，多数是在初版投入使用、暴露问题之后逐轮修补出来的。τ-bench 走到 τ²-bench，就有五处重新设计。

初版的**任务指令**写得笼统，答案可以被猜。模型不用真正澄清需求，凭常识推测一套流程也能通过。τ²-bench 把剧本拆成 `known_info` 与 `task_instructions` 两栏，前者界定用户知悉的范围，后者规定透露方式，用户不知悉的信息 Agent 无从推测，只能去查。

成功条件则不够精确，导致验证误判。「网络已恢复」这种说法缺一个可核实的边界。τ²-bench 改成测速结果为 excellent 才算解决，poor、fair、good 都不接受。这一条针对的是**敷衍性修复**，也就是把症状压下去而不解决根因。

初版的模拟用户只作被动应答，行为过于机械。τ²-bench 给它补上情绪，首次修复失败后表现出不满；加上耐心上限，沟通效率过低就终止对话；还要求事实锚定。三样东西一起作用，模拟器既接近真实用户，又保持可复现。

用户的位置也变了，不再只参与对话，还参与操作。telecom 领域因此引入**双控环境**。从前只有 Agent 能改变环境，而技术支持这类场景里，相当一部分动作本应由用户在自有设备上完成。双控还给验证添了一个维度：用户改变状态之后，Agent 必须重新调用工具才能知道结果，于是验证覆盖到了「Agent 是否真的读到了用户侧的操作结果」。

另一处是任务实例动态生成。τ²-bench 的具体实例，用户姓名、号码、故障组合，都可以参数化批量生成，覆盖率与抗泄漏能力一起改善。

这五处里，自建评估集最容易漏的是第二条：成功条件要精确到没有解释空间。「网络已恢复」给了 Agent 敷衍的余地，「测速 excellent 才算解决」把口子堵死。

SWE-bench Verified 是另一种维护形态，发布前做大规模人工筛选。OpenAI 从原始 2294 个任务中随机抽 1699 个，招 93 名精通 Python 的开发者逐条检查：问题描述是否清晰、测试用例是否覆盖边界条件、测试是否稳定、参考 patch 是否引入新错误、难度是否合理。最终只有 500 个通过。按这几个数复算，$1699/2294\approx74.1\%$，约四分之一的原始任务没进入人工评估；$500/1699\approx29.4\%$，人工评估阶段淘汰了 $1-29.4\%=70.6\%\approx71\%$（这几个比例是我按这些数字算的），跟这里「发布前淘汰 71% 的原始任务」「最终仅 500 个通过」的口径对得上。高淘汰率换来更高的信噪比，评估成本也下降约 80%。这笔账值得算：复杂 Agent 任务动辄要几分钟至几小时，用前沿模型完整跑完一个评估数据集往往要花数千美元的 token，把低质量任务筛掉等于直接省钱。

OSWorld 是发布后维护的例子。它 2024 年 4 月发布，很快成为多模态 Agent 评估的重要基准，随后 15 个月里暴露出 300 余个问题，分四类：环境问题，比如网站反爬、CAPTCHA、动态内容变化；任务描述问题，表述存在歧义；验证逻辑问题，过严或过松；初始状态问题，配置不完整。香港大学团队组了约 10 人的小组，与 MoonShot AI、OpenAI、ByteDance Seed TARS、Anthropic、Simular 等深度合作两个月做系统修复：环境问题靠锁定版本和离线备份解决，描述问题靠改写歧义表述，验证问题靠人工建立正确基线并调整条件，初始状态问题靠增加完整性校验缓解。

三个案例放在一起，正好是三种维护形态：τ-bench 到 τ²-bench 属于版本级重新设计，动的是任务定义的结构；SWE-bench Verified 属于发布前的大规模人工筛选，用 93 人和 71% 的淘汰率换信噪比；OSWorld 属于发布后的系统性修复，15 个月、300 余个问题、10 人小组、两个月、五家机构合作。观念上要转过来的是，评估集属于需要长期维护的活资产，这里给的成本视角也很直接，减少低质量任务本身就是省钱。

**实验7-2 ★：人肉执行基准测试任务**

从 GAIA、AndroidWorld、SWE-Bench Verified、Terminal-Bench、OSWorld-Verified 里挑任务亲手做，每个数据集建议简单、中等、困难各一个。「困难」级别对人类同样有挑战。做完回答两个问题：该任务的描述是否存在多种合理解释，若存在，验证器认可哪一种？若试图蒙混过关，成本最低的路径是什么，验证器能否拦截？

这个实验值得认真做，因为它用「人肉跑一遍」暴露一个事实：连人都觉得题目有歧义，Agent 失败就不能全算它的错。第二个问题尤其有用，它逼你从作弊者的视角审查验证器。

另有两处容易记岔。「淘汰率高」在这一节的语境里是优点，高淘汰率带来更高信噪比，总评估成本还降了约 80%，不过要注意淘汰的是任务，不是模型。τ²-bench 的第 1 处与第 3 处改动也容易混：第 1 处改的是信息边界，防「猜」；第 3 处改的是模拟器行为，防「机械」。一个管知道什么，一个管怎么表现。

### 7.4.6 评估集的三个来源

有一种常见看法，说公开基准只服务于模型排名，跟实际业务关系不大。公开基准的分数确实难以直接指导产品决策，因为它的任务分布与业务的任务分布并不一致。GAIA 上提升两个百分点，跟退款成功率之间没有必然关系：GAIA 考的是搜集信息的通用助手，退款考的是多轮工具编排、政策合规加信息告知，两件事的相关性可能很弱。但公开基准的设计手法可以迁移，前面讲过的验证深度、参数化生成、泄漏防范、质量维护四项，恰好是自建评估集最容易疏漏的几处。很多团队的自建集就是几十条手写用例，没有难度分层，没有防泄漏，也不做维护。

生产环境里的评估集通常来自三处。公开基准用于粗筛模型与借鉴设计手法，一般不用于产品决策，这里别误读成「不需要跑」，用的词是「一般不用于产品决策」。自建业务集覆盖真实的任务分布，可以作为模型选型、Harness 设计决策的依据，τ²-bench 就能当需要仿真用户的评估系统骨架，替换领域数据与工具集即可。生产轨迹回流来自线上的真实失败用例，包括用户明确纠正、用户点踩，以及事后通过状态检查、规则验证器或 LLM 评审发现的问题案例，经失败归因后沉淀为回归用例，具体做法见后文「失败归因」与「端到端回归任务与轨迹前缀回归任务」两节。这一来源成本最高，准确性也最高，因为它直接来自用户实际遇到的问题。

把三者放到时间线上看最清楚：上线前靠公开基准定方向、靠自建业务集定决策，上线后靠生产轨迹回流持续补充，它们各是不同阶段的主力。起步阶段通常只有公开基准和少量手写的自建业务集，系统跑一段时间之后，生产轨迹回流的用例才会成为主体。想让这条路径早点转起来，可以照 τ²-bench 的骨架先搭一套最小可用的自建业务集，换掉领域数据与工具集，跑通「评估 → 失败归因 → 回归用例」这条管道，再逐步把线上样本灌进来。这样评估集从第一天起就是活的。

生产轨迹回流值得投入的原因有两个：它自带「真实发生过」的标签，也天然覆盖了你没想到的场景。成本高在失败归因需要人工与系统建设，准确性高在它来自用户实际遇到的问题。还有一处别混，生产轨迹回流与可观测性不是同一件事。可观测性提供的是原始轨迹（7.8 节），回流是轨迹经失败归因后沉淀下来的回归用例，中间那一步不能省。

## 7.5 自动化评估方法

前面几节讨论的基准测试有一个共同点：验证器几乎都是确定性的。SWE-bench 跑测试套件，AndroidWorld 断言最终 UI 状态，GAIA 做精确字符串匹配，τ²-bench 的四层检查也全部由代码执行。这样选有充分理由：确定性验证不引入额外的模型开销，结果完全可复现，可以像单元测试一样纳入持续集成，也便于在不同模型之间排名。

代价落在诊断能力上。它只评估最终结果对不对，给不出错误原因。τ²-bench 那条失败的任务最终得 0 分，而这个 0 分不会说明 Agent 是在线路选择环节出错，还是漏掉了流量充值步骤，更不会指出下一步该改什么。对用于排名的公开基准，这不构成缺陷；对需要持续改进的生产系统，这恰恰是最缺的信息。

生产场景还有一重困难：许多判断根本写不成代码可检查的断言。一封投诉回复是否得体，一份调研报告是否遗漏了关键信息，一次记忆检索是否弄错了人物关系，这些都既没有唯一终态可供查询，也靠不住关键词匹配。

从公开基准走向生产环境中的评估，验证方式就得沿一条谱系向右移动，横轴是任务的可机械验证程度，如图 7-4。

> **图 7-4：验证方式的谱系**
>
> 验证方式的谱系：从确定性验证到模型评判。图是一条「任务的可机械验证程度」的谱系轴，轴上标着「高」与「低」两端，自高到低排列四档验证方式：

| 读图顺序 | 内容 |
| --- | --- |
| 1 | 验证方式的谱系：从确定性验证到模型评判 |
| 2 | 图是一条「任务的可机械验证程度」的谱系轴，轴上标着「高」与「低」两端，自高到低排列四档验证方式 |
> 1. 确定性验证器：终态唯一可查；只判通过/不通过；例：SWE-bench 跑测试。
> 2. 检查项清单：多项确定性检查；按声明的口径聚合；例：τ²-bench 四层验证。
> 3. Rubric + LLM 评判：维度可拆但无法机械判定；分维度打分并说明理由；例：客服质量、报告撰写。
> 4. 配对比较：连维度都难以写出；只判 A 与 B 孰优；例：Chatbot Arena。

> 图下方还有两栏小结，对应谱系的两端：
> - 确定性验证：结果完全可复现、可纳入持续集成、成本低；代价是只回答对错，不指出问题出在哪里。
> - 模型评判：可拆出诊断维度，覆盖写不成断言的任务；代价是引入评判偏差与波动，成本更高。

谱系右侧的两件工具因此成为生产评估的主体。用 Rubric 把笼统的「好不好」拆成若干个可分别打分的维度，用 LLM-as-a-Judge 在缺乏确定性判据时完成打分。两者合起来，才能把一个笼统的失败率还原成可着手修复的具体问题；再配合后面的失败归因，构成生产 Agent 评估的完整闭环。

这里有一条纪律：向右移动不意味着放弃左侧。凡是能写成程序化断言的检查都应当继续用断言，LLM 评判只用于确实无法机械判定的维度。确定性检查更便宜、更稳定，也更适合作为回归测试长期运行。

判据其实只有一个：「正确答案」能不能写成代码。能写成代码、终态唯一可查的，用确定性验证器；有多个确定性检查项、需要按声明口径聚合的，用检查项清单；维度能说清但不能写成代码的，用 Rubric 加 LLM 评判；连维度都说不清的，只剩配对比较。

「向右移动不意味着放弃左侧」这句话值得写在墙上，它挡住两种常见错误。一种是过度使用 LLM 评判：本来 `assert status == "cancelled"` 就能判的，却让 LLM 去「读一下对话，看看退款成功了吗」，更贵、更不稳，还可能被忽悠。另一种是死守确定性判据：明明要评「这封投诉回复是否得体」，却硬写成关键词匹配，结果 Agent 学会了堆关键词。

所以每一层判据都先问一句「能不能降级为断言」。能降就降，只有确实降不下去的维度，才留在 LLM 评判里。

还有两处容易混。确定性验证的代价在诊断能力上，跟准确率无关，它在判对错上反而更准，只是说不出错在哪。Rubric 与 LLM-as-a-Judge 也是两件事：Rubric 是判分标准，LLM-as-a-Judge 是执行判分的角色。图 7-4 里那一档的名字写作「Rubric + LLM 评判」，正说明二者要配合使用。

这条谱系记住一句话就够了：能写断言就用断言，写不出的维度才交给 Rubric 加 LLM 评判。

## 7.5.1 LLM-as-a-Judge：自动化评估的核心

> **图 7-5：LLM-as-a-Judge 流水线**
>
> LLM-as-a-Judge 流水线。图从左上到右下依次是：

| 读图顺序 | 内容 |
| --- | --- |
| 1 | LLM-as-a-Judge 流水线 |
| 2 | 图从左上到右下依次是 |
> - 输入之一：Rubric（评分标准），示例维度写着「事实正确性: Essential」「逻辑连贯性: Important」「幻觉检测: Veto ⚠」「完整性: Important」。
> - 输入之二：候选回答，示例是 Agent 输出「退款已处理，\$150 将在 3-5 工作日内到账。」
> - 输入之三：参考方案（可选），写着「标准答案 / 评分要点：必须包含退款金额；必须包含到账时间；不可承诺具体日期」。
> - 三者一起送入 Judge 模型（GPT-5 / Gemini 2.5），图旁标注「多源异构评判防止同源偏见」。
> - 结构化评估输出（Judge 逐维度给出分数与理由）：事实正确性 4/4（金额和时间均准确）、完整性 3/4（缺少退款方式说明）、幻觉检测 PASS（无虚假信息）、逻辑连贯性 4/4（因果关系清晰）。
> - 评分聚合策略（四条）：加权平均 $\sum(\text{权重}\times\text{维度分})$；一票否决（幻觉=FAIL → 总分=0）；多评委（3 个 Judge 取中位数）；边界案例标记（分歧>2 分 → 人审）。

开放式任务没有标准答案可以自动对比，比如生成报告、处理客户投诉、创意内容，人工评估成本高且难以规模化。LLM-as-a-Judge 让语言模型根据专家定义的评分标准（Rubric）来评判，在自动化规模和人类专业判断之间取得平衡。它的问题也很实在：评判模型有自己的偏见，相同输入多次评判还会波动。最典型的是长度偏差，评判者倾向于给更长、更详尽的回复打高分，哪怕内容并不更正确。这有点像人类考试时对不会的题长篇大论，指望能蒙对一两个点。

对付长度偏差有三种常用手段。在 Rubric 里显式惩罚冗长，对同类任务规定回答的长度上限；做配对比较时先把两个候选的长度控制到相近再评；定期审计评分与回答长度的相关性，如果高分几乎总是伴随长回答，就说明评判已经被长度带偏，需要回炉修订 Rubric。

Rubric 是 LLM 评判的依据。Scale AI 在 "Rubrics as Rewards" 里给出四准则。

1. 基于专家指导。Rubric 必须反映领域知识，捕捉核心事实和推理步骤。医疗问答的 Rubric 要包含诊断标准和必须避免的医学错误；缺乏专业基础的 Rubric 只能捕捉语言流畅度这类表面特征。
2. 全面覆盖。涵盖事实准确性、逻辑连贯性、完整性、安全性，而且不仅定义正面标准，还要明确陷阱（Pitfall），也就是高风险的常见错误，比如医疗建议里推荐未经验证的疗法。
3. 按重要性加权。分必要项（Essential）、重要项、可选项、陷阱项，并支持一票否决机制（Veto）。客服场景里幻觉就是典型的否决维度，编造虚假信息，无论其他维度多优秀都必须否决。这一条同时有助于防范关键词堆砌式的奖励作弊。
4. 评价标准自包含。每个评价项独立可操作，不依赖评价者的领域知识。要避免「回应展示了深刻理解」这种抽象标准，改成「引用了至少两个权威理论并准确解释如何支持结论」这种可验证的表述。

关键实践是给每个维度定义客观可验证的评分档次，配具体示例和边界案例来区分模糊情况，同时主动防范奖励作弊（Reward Hacking）：Agent 找到了拿高分的捷径，却没有真正完成任务。幻觉、讨好用户、关键词堆砌、回避棘手问题都要明确惩罚。Rubric 还需要不断迭代，通过试用收集评价者的分歧逐步完善，最终从抽象准则演化为详尽的判例集。

LLM-as-a-Judge 的本质，是把「人写评分标准 + 人打分」换成「人写评分标准 + 模型打分」。主观性并没有被消除，只是被集中到了 Rubric 这一处，这也是四准则把「基于专家指导」排在第一位的理由。四条准则可以对照四种失败模式来记：不基于专家指导，Rubric 只能看出语言流畅，看不出医学错误；不全面覆盖，只写正面标准不写陷阱，Agent 就学会了绕过陷阱；不按重要性加权，幻觉和高分维度等权，一次编造被三个优点抵消，总分照样很高；不做到评价标准自包含，评判者得自己去理解什么叫深刻，不同评判者的尺度就会漂移。

一票否决值得单独强调，因为它把加权平均这种可以被补偿的评分，变成了不可被补偿的门槛。这里举的例子很典型：幻觉无论其他维度多优秀都必须否决。否则一个 Agent 只要在完整性、逻辑连贯性上堆分，就能掩盖编造事实。

长度偏差的三个防范手段分别落在三个环节，可以分开用也可以合起来用：写标准时防（惩罚冗长加长度上限）、送评时防（长度对齐后再配对）、事后审计（看分数与长度的相关性）。第三条最像体检，它不直接修问题，只是告诉你该回炉修订 Rubric 了。工程上有个实用的自检问题：把同一个答案缩写一半、事实不变，分数会掉多少？掉得明显，说明你的 Rubric 沾上了长度偏差。

Rubric 与参考答案不一样。图 7-5 把「Rubric（评分标准）」和「参考方案（可选）」画成两个独立输入。参考答案回答的是「什么是对的」，Rubric 回答的是「怎么算好」。开放式任务常常没有参考答案，但必须有 Rubric。陷阱（Pitfall）与一票否决（Veto）也不是同一件事：陷阱是「高风险的常见错误」这一类目，Veto 是「该维度一旦不过就总分归零」的聚合规则，四个加权级别里专门有陷阱项。

拿用户记忆 Agent 举例，一个符合四准则的完整 Rubric 长这样。测试问题是「我女儿的儿科医生是谁？」，答案需要跨两次对话关联：第一次对话提到「女儿叫 Lily」，第二次提到「带 Lily 去看了 Dr. Chen」。

```yaml
rubric:
  dimensions:
    - name: 事实正确性
      weight: essential          # 必要项
      scoring:
        4_优秀:   "准确回答Dr. Chen，且关联到女儿Lily"
        3_良好:   "准确回答Dr. Chen，但未提及是Lily 的医生"
        2_及格:   "给出了正确医生但附带不确定的额外信息"
        1_不及格: "给出错误医生名，或回答不知道"
    - name: 信息完整性
      weight: important          # 重要项
      scoring:
        4_优秀:   "主动补充相关信息（如上次就诊时间、诊断结果）"
        3_良好:   "回答了核心问题，无遗漏"
        2_及格:   "回答了核心问题，但遗漏了可用的关联信息"
        1_不及格: "关键信息缺失"
    - name: 思考正确性
      weight: important
      scoring:
        4_优秀:   "正确关联'女儿=Lily'和'Lily 的医生=Dr. Chen'两条跨会话信息"
        3_良好:   "关联正确但思考路径不够清晰"
        2_及格:   "部分关联正确"
        1_不及格: "错误关联（如把用户自己的医生当成女儿的医生）"
    - name: 幻觉检测
      weight: veto               # 一票否决项：一旦触发，总分归零
      scoring:
        pass: "所有信息均可溯源到历史对话记录"
        fail: "编造了对话中不存在的信息（如虚构就诊日期、诊断结果）"
  edge_cases:
    - "如果用户有多个女儿且分别看不同的医生，应追问是哪个女儿"
    - "如果记忆中同时存在'Dr. Chen'和'陈医生'，应识别为同一人"
```

（说明：这里此段为 YAML 代码块，提取后缩进层级有所丢失，按 YAML 语义还原了缩进；键名、档位标签与评语文字未改动。）

好的 Rubric 与坏的 Rubric 差别就在档位描述上。上面每一档给的都是可验证的具体行为，比如「准确回答Dr. Chen」，而「展示了对记忆的深刻理解」这类描述无法客观判定。一票否决项则明确了底线：即使其他维度全部满分，一旦出现幻觉就直接判零分。

把这个 Rubric 和 Agent 的实际回答一起交给评判模型，模型会逐项打分并说明理由。几十个用例的结果汇总起来，再回看其中的低分轨迹，原本笼统的「成功率下降」就能拆成几类具体问题：是没检索到信息，还是把人物关系想错了，抑或补充了没有依据的内容。Rubric 不只告诉我们得了多少分，还告诉我们下一步该改哪里。

### 实验7-3 ★★：构建基于Rubric 的用户记忆评估系统

本实验要求改造第三章的 `chapter3/user-memory-evaluation` 框架，把当前基于简单 LLM-as-a-Judge 的评分机制升级为结构化的多维度 Rubric 评估系统。现有系统用单一 LLM 调用返回通过/失败加评估理由，缺乏结构化的诊断能力。要求设计统一的多维度 Rubric 框架，适用于所有三层任务。评价维度包括：

- 事实正确性（Precision，精确率）：在所有给出的信息中，有多少是正确的；用于验证数字、日期和名称是否与记忆信息一致；
- 事实完整性（Recall，召回率）：在所有应该给出的信息中，有多少被提及；用于验证是否提供了所有相关信息、有没有遗漏关键内容；
- 思考正确性：检查是否正确理解了信息间的关系和隐含逻辑；
- 思考主动性：评估是否在适当时候提供超出直接回答的建议或风险提醒；
- 幻觉检测：确保未编造记忆中不存在的信息。

评分用四档制（优秀/良好/及格/不及格），每档配具体判定标准，不停留在抽象描述。幻觉维度设为一票否决项，每个维度都要提供示例和边界案例。

#### 实验7-4 ★★：Advanced JSON Cards 与RAG 的对比评估

目标是在同一套评估集上公平对比结构化记忆与非结构化检索的优势边界。复用两个第三章项目，在 `chapter3/user-memory-evaluation` 的 60 个测试用例上对比三种配置：纯 Advanced JSON Cards（结构化卡片常驻上下文、无需检索）、纯 RAG（对话分块入向量库、必须检索）、混合系统（核心事实常驻 + 原始对话按需检索）。配套实验用同一组 60 个问题测试了三套记忆方案，共保留 180 条真实 API 运行轨迹。结果见表 7-3。

表 7-3 三种用户记忆系统的分层成功率

| 系统 | 基础回忆 | 多会话消歧 | 跨会话隐藏关联 | 总体 |
| --- | --- | --- | --- | --- |
| Advanced JSON Cards | 95% | 60% | 50% | 68.3%（41/60） |
| RAG | 90% | 40% | 15% | 48.3%（29/60） |
| 混合系统 | 80% | 70% | 50% | 66.7%（40/60） |

（表格按语义整理：这里分栏排版导致表头与单元格错行，按「系统—基础回忆—多会话消歧—跨会话隐藏关联—总体」的列序重新对齐，数字未改动。）

最扎眼的一点是混合方案并没有自然胜出。它在 3 道题上做到了两种单一方案都没做到的事，却在另外 8 道题上不如表现更好的单一方案，与每道题上的最佳单一方案相比，平均成功率反而更低。纯 RAG 在基础回忆题上与结构化卡片相差不大，一到跨会话关联题，成功率降到 15%。另一个容易被忽视的数字是：180 次评判中，幻觉否决触发了 28 次。这个数字本身就说明一票否决项有多要紧。

把表 7-3 的三个总体数字复算一遍（这几个数是我按给出的分母算的）：$41/60=68.33\%$、$29/60=48.33\%$、$40/60=66.67\%$，与这里的 68.3%、48.3%、66.7% 一致。

这张表更值得看的是列与列之间的落差，而不是总体。Advanced JSON Cards 从基础回忆的 95% 掉到跨会话隐藏关联的 50%，掉 45 个百分点；RAG 从 90% 掉到 15%，掉 75 个百分点，这就是这里点出的那处崩塌；混合系统从 80% 掉到 50%，掉 30 个百分点。结构化表示的优势在「关联得起来」，不在「记得住」；RAG 的优势在基础回忆，一遇到需要跨会话串联的关系题就崩。分层成功率比单一总分更有诊断力，这个例子讲得很清楚。

那 28 次幻觉否决是个提醒：如果没有一票否决项，这 28 次很可能被别的高分维度掩盖，总体成功率会虚高。一票否决的作用是防止用优点补偿硬伤。

混合方案没有自然胜出这个结论相当反直觉。人们本能地认为组合两种方案一定更好，数据说的是：组合会在某些题目上互补，也会在另一些题目上互相拖累（这里给的是 3 道更好、8 道更差）。所以任何组合方案都要按题分层评估，不能只看总体。

还有两处容易记反。实验 7-3 明确把「事实正确性」对应 Precision（给出的信息里有多少是对的），把「事实完整性」对应 Recall（该给的信息里有多少给了），别凭直觉把完整性当成精确率。另外，一票否决与低分不同：低分是被扣分，veto 是直接归零。表 7-3 里那 28 次幻觉否决意味着 28 条用例的总分是 0，而不是幻觉维度分数偏低。

Rubric 的每一档都要写成可验证的具体行为；幻觉这类硬伤要设成一票否决，否则会被其他维度的高分补偿掉。

#### 同源模型问题与多源评判

当 Agent 与评判模型来自同一家族，Agent 可能学会利用评判模型的偏好和盲点。这正是古德哈特定律（Goodhart's Law）说的：当一个度量指标变成优化目标时，它就不再是好的度量指标。Agent 越是在某个评分系统上训练或调优，就越倾向于钻这个系统的漏洞，能力提升反而被放到一边。更隐蔽的是，Agent 还会逐渐学会避开评判模型不擅长检测的错误类型，让评分系统看起来一切正常。

缓解策略是多源异构评判：用不同模型家族的多个 LLM 分别评判，比如 Agent 用 Claude，评判就用 GPT-5 和 Gemini。不同家族的偏见往往是正交的，Agent 很难同时欺骗所有评判者。评判时使用相同的 Rubric，确保大家评的是同一目标，再通过加权平均或一致性检查聚合结果。部署阶段可以用单一模型快速评估，但要定期用完整的多源评判做质量审计。

多源评判解决的是「用什么模型评判」，往下还有个「评判哪些模态」的问题。把 LLM-as-a-Judge 的能力从文本扩展到语音、图像、视频，是评估覆盖度的另一维度。

古德哈特定律出现在这里的位置很关键，它紧接着「同源模型」而来。逻辑链条是这样的：评判者和被评判者同源，优化压力就会顺着这个共同点传导，Agent 学到的手法变成了「怎么讨好这个评判者」，真正该提升的能力反而没人管。这跟前面讲的奖励作弊是同一件事的两个层次，一个钻 Rubric 的漏洞，一个钻评判模型偏好的漏洞。

「偏见正交」是多源评判的核心论点，用几何的方式理解很直观：两个评判者的偏见方向一致（同源），它们会叠加；方向无关（正交），一个模型看不出的问题另一个可能看得出，Agent 要同时骗过所有评判者的难度就大幅上升。

#### 多模态 LLM-as-a-Judge

多模态评判把 LLM-as-a-Judge 扩展到语音、图像、视频领域，例如：

- TTS 评估（TTS 即 Text-to-Speech，文本转语音）：判断准确性、自然度、音色一致度、情感表达。这些维度能发现传统 WER（Word Error Rate，词错误率）难以捕捉的韵律问题。
- ASR 评估（ASR 即 Automatic Speech Recognition，语音识别）：做语义影响判断。「今天天气」识别错误无伤大雅，但「转账一千」变成「一万」就可能造成严重后果。
- UI 评估：采用第一章命名的提议者—审核者模式，检查文字溢出、颜色对比度、按钮位置等问题。这里的提议者—审核者作为评估方法使用，与第五章中作为生成系统组件的用法不同，核心机制相同：一个模型生成，另一个模型独立审查。
- 视频剪辑评估：通过关键帧验证剪辑起止点和特效应用是否正确。

四个例子里，ASR 那条最能说明为什么不能用传统指标。WER 把「一千」和「一万」的差别记成一个词错误，与把「今天」听成「明天」代价相同；但对业务来说前者可能造成严重后果。这里因此说 ASR 评估要做「语义影响判断」。

#### 实验7-5 ★★：构建全自动TTS 质量评估流水线

本实验要求从零设计并实现完整的多模态 LLM-as-a-Judge TTS 质量评估系统。

- 设计 TTS 多维度 Rubric：准确性维度验证是否正确读出所有文字（无遗漏/错读/添加）；自然度维度评估语音是否流畅（有无机器感、不自然停顿，韵律是否符合人类习惯）；情感表达维度检查语气是否符合文本情感色彩（疑问句升调、感叹句强调、悲伤内容语速慢语调低）；音色一致性维度在有参考语音时评估说话人相似程度（多模态模型同时接收参考语音与合成语音对比）。
- 构建多样化测试语料库：不同长度（单句→长段落）、文体（新闻/故事/对话）、情感（中性/兴奋/悲伤）、特殊挑战（数字/专有名词/多音字/方言词汇）。
- 实现评估流水线：TTS 生成模块接入主流服务（OpenAI、ElevenLabs、Fish Audio、Minimax、豆包），由可直接接收音频的多模态评判模型将合成语音、原始文本、参考语音和 Rubric 一起输入，逐维度评分并给出详细理由。分析评估结果的分布，同时记录评判模型、参考音频哈希和候选音频哈希，使结果可复核。
- 配套仓库中保留了一次小规模的直接听评。OpenAI 和 Fish Audio 分别生成了数字、多音字、长句和兴奋语气四类音频，8 条音频都由 Voxtral 按上述四个维度完成评分。结果：两者在准确性和自然度上都得到 5.00 和 4.00；Fish Audio 在情感表达和音色一致性上得到 4.00 和 3.00，OpenAI 则是 3.75 和 2.75。四个维度分开评分后，即使「有没有读对」看不出差别，语气和音色上的差别仍会显现出来。
- 但这组分数还不能用来判断哪家 TTS 更好。每家只有四条音频，更关键的是，实验使用的固定参考音频来自 Fish S1，拿它来比较音色，本来就更有利于 Fish Audio。如果要比较通用 TTS，就不该把「像不像 Fish 参考音色」算进总分；如果要比较声音克隆，则应让所有方案模仿同一个目标说话人，并用人工盲听校准模型评分。选什么参考答案、参考图片或参考音频，这件事本身就属于评估设计，跟评估开始前的杂务无关。

人工编写 Rubric 适合快速建立这样的诊断维度。评估规模再扩大时，还可以训练专门的生成式奖励模型来自动打分，相关训练方法在第八章讨论。评判模型给出的分数只说明结果好坏；要把结果变成可以修复的问题，还得定位失败从哪一步开始。

实验 7-5 里最值得学的是这里值得学的是自我拆台：分数出来之后，这组分数不能用来排名，理由有两条，样本量太小（每家四条音频），参考音频的选择有偏差（参考音频来自 Fish S1，对 Fish Audio 有利）。这段是很好的评估设计教材，可以提炼成三个检查：样本量够不够？参考答案有没有偏向某一方？该不该把这个维度算进总分？比通用 TTS 就不该算音色一致性，比声音克隆则要统一目标说话人再加人工盲听校准。

记录评判模型、参考音频哈希和候选音频哈希这条工程细节值得记住，它让一次评估结论在几个月后被质疑时，还能还原当时用的是哪个模型、哪段音频。

同源偏见（same-family bias）与位置偏差（position bias）是两回事：前者是「Agent 与评判者同族」，后者是「评判者偏向先出现的候选」（见 7.5.4）。缓解手段也不同，前者用多源异构评判，后者用交换顺序各评一次。提议者—审核者在第五章与本章的用法也不同、机制相同：第五章里它是生成系统的组件（一个生成、一个审查），本章里它是评估方法，说明了这一点。

评判者与被评判者不能同源（Goodhart's Law）；参考答案的选择本身就是评估设计，它可能悄悄偏向某一方。

### 7.5.2 失败归因：从整条轨迹定位首个错误

端到端评估通常只给出「成功」或「失败」，却不回答为什么失败、从哪一步开始失败。要让评估结果真正驱动修复，必须对每条失败轨迹做失败归因（failure attribution）：标出主要错误类别、首次出现不可接受行为的步骤、对应的工具调用或模型输出，并附上可复核的证据。

归因对象是轨迹中首个导致任务偏离的错误。后续错误往往只是连锁反应，不能把最后一个报错简单当成根因。

生产 Agent 的问题案例通常来自三类信号：用户明确纠正（「不要这么做」）、用户点踩或给出负面反馈，以及事后通过状态检查、规则验证器或 LLM 评审发现 Agent 做了不该做的事。

构建失败归因系统需要开发者耐心阅读并分析生产 Agent 的问题轨迹。这个过程可以借助 LLM，但不能完全依赖 LLM，因为失败归因往往反映的是产品问题，不止是技术问题。随着产品不断完善，错误分类可能包含多个大类，每个大类下又有多个小类，最终多达数百种。这些错误类别和归因方式，可以作为归因标注 Agent 的提示词或 Skill。

以 Coding Agent 为例，一个实用的初始分类如下（表格按语义整理：这里分栏排版导致三列错行，按「错误类别—典型表现—首个错误的定位方式」的列序重新对齐，文字未改动）。

| 错误类别 | 典型表现 | 首个错误的定位方式 |
| --- | --- | --- |
| 需求理解与歧义处理 | 做出来的不是用户要的：漏掉需求里的一个条件、把范围理解宽了或窄了；仓库里有两个同名配置文件时直接选一个，既不说明也不追问 | 用LLM 把原始需求与Agent 实际做的事（动作序列）逐条对照，先定位第一处偏离，再回溯到造成它的那次工具调用或那句答复 |
| 流程与规范缺失 | 未执行单元测试就提交；未写Plan 就开始改代码；引入外部依赖而仓库已有内部等价物；绕过既定架构约定 | 找到第一次违反软件开发流程约定的动作，例如首次 `git commit`、首次写文件；回看它之前有没有读过约定来源 |
| 工具调用错误 | 同一文件反复编辑失败；JSON/schema 或参数格式错误；特殊字符导致抄写、转义或写入错误 | 记录第一次失败的编辑/工具及原始请求、错误返回；重复失败属于后续症状 |
| hack 验证环境 | 直接改断言、加skip、mock 掉被测逻辑；声称「测试已通过」但根本没跑 | 取第一次改动测试或验证逻辑的message；再把完成声明与轨迹里真实执行过的命令交叉核对，确认它是否真的跑过 |
| 修改不完整 | 改了函数签名，改了三处调用方，漏了第四处的动态调用、另一语言的绑定或schema | 把Agent 声称的影响面与真实影响面做集合差，取第一个遗漏项，回看它检索时用了什么关键词 |
| 对用户的信息反馈错误 | 工具调用和环境状态全对，最终告诉用户的信息却错了：金额、状态、时间说错；把部分做完说成全部做完；漏掉必须告知的事项 | 把答复里的每个事实断言与工具返回值逐条对齐，取第一条无法溯源或与工具返回矛盾的断言 |
| 非功能性回归 | 改了公开API、schema 而无数据库迁移脚本；为让校验通过而删掉校验 | 取第一次做出该改动的message，看它是否意识到自己动的是公开接口或需要迁移的结构 |
| 模型执行异常 | 输出中途截断、无故停止、超时，或没有完成收尾动作就结束 | 定位第一个异常终止的位置，区分模型停止、Harness 超时和工具服务故障 |
| 过早停止任务 | 多目标任务只完成一部分；未穷尽合理方案就宣布不可能 | 定位第一次遗漏目标或放弃探索的决策，并与最终验证失败分开记录 |

归因标注 Agent 可以利用 LLM 规模化完成大量生产轨迹的根因分析，但不能只输出一句「失败原因」。归因记录需要结构化，可以采用 JSON 或 YAML 文档格式，引用具体的步骤号、工具名和观察证据，同时区分根因与后果、判断是否可恢复，并给出置信度。

举个例子：`edit_file` 返回 `old_string` 匹配失败，之后 Agent 连续三次重试仍未写入文件。主因是「文件编辑与工具调用错误」，三次重试是后果，算不上三个独立根因。若多个类别同时出现，按「最早且能解释后续失败」的原则选主因，其余保留为次因。

上表里至少有三类可以先用规则筛出嫌疑轨迹、再交给 LLM 定位首错：完成声明与实际执行命令的交叉核对、diff 是否触及测试断言与 skip 标记、diff 是否改动公开 API 或 schema 而无迁移文件。规则先筛、LLM 再定位，比把全部轨迹喂给 LLM 更便宜也更准。

保存归因记录时，除了 LLM 输出的记录，还应把任务目标、环境状态、Agent 版本、工具集版本和完整的 Agent 轨迹一起保存，以便做回归测试。

「首个错误」这四个字是这一节的灵魂。为什么不能只看最后一个报错？因为 Agent 的失败有很强的连锁性：第 8 步用错了数据，第 11 步开始就全在错的基础上推进，第 32 步的「保存失败」只是最后那一下。这里的诊断建议是定位首个导致任务偏离的错误。

九个类别可以按「错误发生在哪一环」重新归拢，这样更好记。理解环节是需求理解与歧义处理；流程环节是流程与规范缺失、过早停止任务；工具环节是工具调用错误、模型执行异常；结果环节是修改不完整、非功能性回归；诚信环节是 hack 验证环境（改断言、假称跑过测试）；表达环节是对用户的信息反馈错误。

每一条的定位方式都遵循同一个思路：先找到第一个「不该发生」的动作，再看它之前 Agent 有没有读够该读的东西。「流程与规范缺失」的定位方式里特意写了「回看它之前有没有读过约定来源」，它区分了两种情况：Agent 不知道规范（Harness 没给到），还是知道却不遵守（模型行为问题）。这两种的修法完全不同。

规则先筛、LLM 再定位是很好的成本控制经验。这里点的三类最适合规则筛的是完成声明与真实执行的命令、diff 是否触及测试断言与 skip 标记、diff 是否改动公开 API 或 schema 而无迁移文件。这三类都能用文本比对、正则或 diff 检查廉价地判定有没有嫌疑，把 LLM 的算力留给真正需要语义理解的定位工作。

归因记录要求区分根因与后果、判断是否可恢复、给出置信度，这三项是做回归任务的直接依据：区分根因与后果决定回归任务该覆盖哪一步；是否可恢复决定这条失败算 Agent 能力问题还是环境与工具问题；置信度决定这条记录要不要人工复核。

「可以借助 LLM，但不能完全依赖 LLM」值得单独记住，这里给的理由很有意思：失败归因往往反映了产品问题，不止是技术问题。很多失败追到底其实是「需求本身没想清楚」「产品定义有矛盾」，这不是一个模型能替你判的。

首个错误不等于第一个报错。有些首个错误根本不报错，比如下面 AndroidWorld 那个例子：第 8 步的思考里写着看不到图片内容，但既没报错，也不是工具调用。所以定位方法必须是「事实锚点比对」或「轨迹前缀二分」，不能靠搜错误关键字。另外，主因也不是唯一的错，这里允许保留多个次因，只要求主因满足「最早且能解释后续失败」。

失败归因要找到首个导致偏离的错误，记录要结构化到步骤号加工具名加证据，并区分主因与后果。

下面拿三类典型错误展开。

#### 7.5.2.1 「做对了但说错了」问题

「做对了但说错了」这类问题容易被整体成功率掩盖，因为多数评估只检查环境状态。在 τ²-bench 公开的基线结果中，带有信息告知要求的 704 次运行共失败 240 次，其中 162 次的信息告知出错；有 80 次（占全部失败的三分之一）的环境状态正确，但信息告知错误。

配套仓库的 AndroidWorld T3A 运行记录里有一个典型例子。任务是把图库中 `expenses.jpg` 里的开销录入记账应用。Agent 用 32 步完成了授权、搜索、打开图片、逐条填写和保存，没有任何一步返回错误，最后自行宣告完成，验收却报告应当写入的记录不存在。日志给出的那条是 Dress、¥436.35，与它写进去的四条毫无关系。逐步回看会发现：第 8 步的思考里写着「I cannot actually see the content/details of the expenses in the image」，它自己已经知道没拿到数据，却没有停下，也没有报告，继续往下推进；到第 11 步，四条开销数据「Coffee \$4.50、Lunch \$12.75⋯⋯」凭空出现在它的记录里；此后的每一次输入和保存，都基于这四条幻觉编造的数据。

首个错误落在第 8 步，而那一步既没有报错，也不是一次工具调用。它的根因归属容易分析错：T3A 是纯文本 Agent，观察空间里只有元素树、根本没有图像像素，所以根因在 Harness 的观察通道缺失，跟「模型不会 OCR」无关。如果记成模型能力问题，接下来就会去换模型或做 OCR 训练；真正该做的是补观察通道。

#### 实验7-6 ★★：对AndroidWorld 失败轨迹做失败归因

本实验用真实轨迹练习这一节的归因方法，不需要模拟器，也不需要调用模型 API。素材是 `chapter7/android-world` 中已保存的 T3A 运行记录：`t3a.md` 是全部任务的逐步 Action/Reason/Summary，`t3a_failed.md` 集中收录了 50 余条失败轨迹，每条末尾都带验证器给出的客观判定。

- 第一步：抽样分层。从 `t3a_failed.md` 中抽取至少 10 条全程没有工具报错的静默失败。轨迹里不能有失败的工具返回，Agent 自行宣告完成或者耗尽步数，只有末尾的验证器判定为失败。
- 第二步：定位首个错误。为每条轨迹标出首错步号，并注明它是一次工具调用还是一条 assistant message。静默失败要靠两种办法定位：一是事实锚点比对，把 Agent 的陈述与工具返回值逐步对齐，取首次背离；二是轨迹前缀二分，把轨迹截到第 $k$ 步交给人接手，能救回来说明错误在 $k$ 之后。不能用搜索报错关键字代替。
- 第三步：写成结构化记录。每条轨迹产出一条 JSON 或 YAML 记录，包含任务名、首错步号、错误类别、根因责任方、这里证据，并区分主因与后果。
- 第四步：与现成笔记对照。把结果与仓库中的 `t3a_failed_analysis.md` 逐条比较并记录分歧。这份归因笔记不是标准答案。特别注意根因归属：该笔记原本把图片转录失败记成「视觉模型缺乏 OCR 能力」，而 T3A 的观察空间里根本没有图像像素，真正的根因是观察通道缺失。
- 第五步：转成回归任务。挑出 3 条首错发生在 assistant message 上的轨迹，各截取首错之前的前缀，写出可接受动作集合与禁止动作，形成轨迹前缀回归任务。

先把那组数字算清楚（补充的计算）：$240/704\approx34.1\%$ 的失败率；其中信息告知出错 162 次；环境状态正确但信息告知错误 80 次，$80/240=1/3$，与「占全部失败的三分之一」一致。这 80 次是最容易被漏掉的一类，如果只看环境状态，它们全都会被判为成功。

「做对了但说错了」的严重性在于：工具调用对了、状态改对了，用户收到的信息却是错的。对客服、金融、医疗这类场景，用户按错的信息行动，可能比任务没做完更危险。

T3A 那个例子的教学价值有两层。首错可能不报错，也不是工具调用，第 8 步只是一句「我看不到图片内容」的思考，所以静默失败只能靠事实锚点比对（把陈述与工具返回值对齐）或轨迹前缀二分来找，搜 error 关键字是找不到的。根因归属认错，修复方向就全错：记成「模型缺乏 OCR 能力」，就会去换模型、做 OCR 训练；记成「Harness 观察通道缺失」，才会去给纯文本 Agent 补上图像描述或视觉输入。真正该做的是补观察通道。

实验 7-6 第二步给的两个定位手法值得记住。事实锚点比对是把 Agent 的每一句陈述与工具返回值逐步对齐，找第一次背离；轨迹前缀二分是把轨迹截到第 $k$ 步交给人接手，能救回来说明错误在 $k$ 之后，救不回来说明 $k$ 之前就已经坏了。这实际上是用人工接管当二分查找的判据。

第四步「与现成笔记对照」的设计很聪明：它让你用一份已知有错的参考笔记练手，逼你去质疑权威，抄答案会直接踩坑。

「环境状态正确但信息告知错误」按多数评估口径会记成功，这正是它容易被整体成功率掩盖的原因。另外，「模型能力不足」与「Harness 观察通道缺失」表面上很像，都是「Agent 看不到图就乱写」，区分方法是查观察空间里到底有什么：T3A 里只有元素树，没有像素，所以问题在通道上。

多数评估只看环境状态，于是「做对了但说错了」被系统性地漏掉；首错可能是一句不报错的思考，根因归属错了修复方向就全错。

#### 7.5.2.2 作用域敏感的文档格式错误

用户说「引号格式不对」时，不能直接把它转成全局字符替换。至少要区分 ASCII 直引号（`"`、`'`）、中文弯引号（`“”`、`‘’`）和 Markdown 反引号（`` ` ``）。同一字符在中文自然语言、英文引文、行内代码、代码块、代码注释、JSON 和路径中承担的语法角色不同。

评估数据应先把文档解析为带作用域的片段，例如 `ZH_PROSE`、`EN_PROSE`、`QUOTED_SOURCE`、`INLINE_CODE`、`CODE_BLOCK`、`CODE_COMMENT` 和 `JSON_OR_SCHEMA`。每个片段保存允许变换集合、必须保护的字符以及修改后的验证器结果。下面三处不能用同一条替换规则处理：

```text
中文说明：调用`reset()` 方法。
这是一段英文原句：“Please restart the service.”
# 以下代码块仅用于说明受保护作用域
# 中文注释：显示"当前状态"
name = "status"
```

轨迹前缀回归应要求模型做最小修改，并同时检查中文文档风格、英文引文保持率、代码和 JSON 语法，以及非目标文本的编辑距离。规则无法确定作用域时，应允许模型保留这里并请求澄清；把猜测性修改算作通过是不合适的。

> 说明：上面的示例刻意使用了不同的引号：中文引文用弯引号（`这是一段英文引文：“Please restart the service.”`），代码注释用 ASCII 直引号（`显示"当前状态"`），用来说明同一个字符在不同作用域里的语法角色不同。

这一小节讲的陷阱很具体：在「格式纠错」类任务里，错的是「这个位置的这种字符」，全文同类字符未必都错。全局替换之所以危险，是因为同一个字符在不同作用域里身份不同。在 `ZH_PROSE` 里，`"` 可能是该被改成弯引号的错误；在 `EN_PROSE` 或 `QUOTED_SOURCE` 里，`"` 是这里的一部分，必须保持；在 `INLINE_CODE`、`CODE_BLOCK`、`JSON_OR_SCHEMA` 里，`"` 是语法字符，改了代码就跑不起来。

先把文档解析为带作用域的片段这一步不能省。这也是一个通用的评估设计模式：当一个任务的作用域需要判断时，评估数据里就应该显式标注作用域，否则验证器无法判断这次替换该不该发生。

非目标文本的编辑距离这个指标很实用，它检查模型有没有顺手改了不该改的地方。加上这几个检查项，一条看似简单的「改引号」任务就有了五个可量化的验收面：中文文档风格、英文引文保持率、代码语法、JSON 语法、非目标文本编辑距离。

「规则无法确定作用域时，应允许模型保留这里并请求澄清」是一条很重要的产品化原则：把「不确定就先问」变成得分行为。否则模型的最优策略永远是在不确定时瞎猜，猜对了得分，猜错了才扣分，而问一句反而要付出轮次成本。

「格式错误」是一族错误，不是一个类别。同一类字符在不同作用域里，有的是错误、有的是必须保护的内容，判断依据是作用域。「至少要区分」三类引号，说明这个清单并不穷尽，真正决定怎么处理的是该片段所属的作用域标签。

格式纠错要先切作用域：同一个引号在中文这里要改，在英文引文和代码里必须保护；不确定就允许「保留这里 + 请求澄清」。

#### 7.5.2.3 精确复制错误：从old_string mismatch 到逐层定位

`old_string` 失败也不能只归因于「模型抄错了」。应对同一个字符串保存原始字节哈希、Unicode code point 序列和 tokenizer token ID 序列，沿下面这条链路寻找首个差异：

```text
文件原始字节 → 工具返回 → Harness 序列化 → 模型上下文
→ 模型token 输出 → 解码字符串 → JSON/tool-call 解析 → 工具匹配
```

最小化评估探针要覆盖直接复述、从长上下文抽取、放入工具参数、相似字符串选择，以及空格、换行、反斜杠、Unicode 组合字符和低频 token。指标用 byte-exact match、code-point-exact match、token-exact match、首次分歧位置和真实工具成功率。

判断规则：若模型在直接探针测试中输出正确而工具调用失败，应修复 tokenizer、序列化、Harness 或工具协议；只有首个差异出现在模型输出时，才把该案例转成第八章的复制训练数据。

这条链路的思路是逐层设检查点。一个字符串从文件到工具匹配要经过八道手，每一道都可能悄悄改动它：文件原始字节（真值）；工具返回（可能截断、可能转义）；Harness 序列化（可能在 JSON 里转义反斜杠、换行）；模型上下文（可能被截断或被模板改写）；模型 token 输出（可能因低频 token 或组合字符而出错）；解码字符串（可能归一化 Unicode）；JSON/tool-call 解析（可能吃掉反斜杠）；工具匹配（可能做过空格归一化）。

三个层级的匹配指标对应链路的不同深度：byte-exact 是字节级，最严；code-point-exact 是字符级；token-exact 是 token 级。如果 byte-exact 失败但 code-point-exact 通过，差异很可能出在编码或归一化；如果 token-exact 就失败了，问题更可能出在模型输出侧。

「若模型在直接探针测试中输出正确而工具调用失败」这个判据非常关键，它把「模型抄错了」和「管道弄坏了」分开。前者要去训练模型（第八章的复制训练数据），后者要去修 tokenizer、序列化、Harness 或工具协议；修错了地方，做多少训练都没用。

「最小化评估探针」这个词值得学：不要拿一整个复杂任务去测复制能力，而要设计最小场景（直接复述、长上下文抽取、放进工具参数、相似字符串选择）逐项隔离变量。这跟 7.9 节 AndroidWorld 的一轮只改一个变量是同一个方法论。

`old_string` mismatch 的原因可能完全不在模型，序列化转义、Unicode 归一化、tokenizer 处理低频 token 都可能造成同一现象，所以不能只归因于模型抄错了。另外，byte / code-point / token 三级匹配并非「越严越好」，它们分别是不同层级的诊断工具，用来定位首个分歧发生在哪一层。

`old_string` 匹配失败要沿「字节 → 序列化 → token → 解析 → 匹配」逐层找首个差异；只有差异出在模型输出时才去训模型。

### 7.5.3 端到端回归任务与轨迹前缀回归任务

失败归因明确了首个错误及其类别，下一步是把修复目标写成可重复执行的测试用例，即回归任务（regression task）。这里需要两层互补的回归任务：端到端回归任务验证改动没有破坏完整工作流；轨迹前缀（trajectory prefix）回归任务截取首个错误之前的状态，只验证那个决策边界是否被修好。

端到端回归任务从初始状态和用户请求开始，让 Agent 完成整个任务，并检查最终状态、必要输出和安全条件。它最接近生产结果，却难以判断失败究竟发生在哪一步。一般来说，端到端回归任务用于验证 Agent 在各个领域的能力符合预期。本章所述的 OSWorld、AndroidWorld、tau-bench 等标准评测集都是端到端回归任务。

轨迹前缀回归任务把已有的上下文、对话、工具返回和环境状态冻结下来，只要求 Agent 思考并执行下一步或下几步可观察动作，成本更低，也能隔离单个策略或工具问题。对于需要高可靠性的生产级 Agent，构建轨迹前缀回归任务集往往比端到端回归任务集更重要，也需要开发者耐心建立上一节所述的失败分类体系和失败归因系统。

轨迹前缀回归任务的答案应定义为一个可接受动作集合，不必是唯一的动作或答案：可以要求「先读仓库规则」「先询问用户」或「拒绝危险操作」，同时列出禁止动作。

失败归因完成后，就可以构造包括端到端和轨迹前缀回归任务在内的评估数据集。以 Coding Agent 为例：流程缺失应生成带有计划文档和测试验收条件的端到端回归任务；工具调用错误应把出错前缀截断并编辑成边界任务，测试模型能否修正格式、转义特殊字符或换用合适工具；执行异常应加入截断、超时和工具故障的恢复场景；完成度与逻辑错误应加入多目标清单、剩余任务提醒和「尚未证明不可能」的边界；需求理解与歧义类应把有多种合理解释的任务冻结成前缀，把「先澄清」列入可接受动作；症状修复与验证造假类则应在验收里补上「不得修改测试断言」和「完成声明必须附带真实执行过的命令输出」两条硬约束；信息反馈类应在验收里对答复内容本身设断言，不能只检查环境状态。

评估数据集是第八章模型后训练和第九章 Agent 自我进化的基础。

#### 实验7-7 ★★：轨迹前缀边界评估：同一上下文的多种表示

前置要求：需理解这一节的轨迹前缀评估协议；本次案例使用第三章的用户记忆表示和 LLM-as-a-Judge 一节的 Rubric 设计，不要求运行完整的 60 用例端到端记忆矩阵。

- 本实验关心的不是「上下文检索器有没有找回信息」。它把一组已经提供给 Agent 的上下文（本案例使用用户记忆）、当前任务、trajectory prefix、工具返回和环境状态一起输入模型，要求模型只输出下一步可观察动作。用例来自三类生产问题案例：用户纠正、点踩关联轨迹，以及事后规则/LLM 审计发现的错误。边界覆盖论文风格与 X 帖子的作用域冲突、worktree/PR 习惯与仓库规则冲突、当前明确指令覆盖旧偏好、低置信度推断、高风险删除前确认，以及对外发布前预览等情况。
- 对同一组用例运行 JSON Cards、Markdown 和 Python-like 三种语义等价的表示。它们是用户记忆这一案例的三种编码；换成 RAG 证据、系统提示或工具观察时，也可以沿用同一套轨迹前缀评估协议。评分由确定性规则完成：决策类别是否属于允许集合、下一步动作是否安全、是否出现要求的证据、是否触发禁止动作，以及上下文是否在该场景被正确使用。
- 配套实验使用 GPT 5.6 Sol 模型，完成了 11 个边界用例 × 3 种表示，共 33/33 个 API 单元且没有 API 错误。三种表示的总成绩碰巧都是 6/11，但失败位置并不完全相同：Markdown 通过了「仓库规则未知时先检查」的用例，却多失败了一个作用域冲突用例；JSON Cards 和 Python-like 的情况相反。三种表示都没有通过论文风格过度泛化、过时偏好覆盖当前要求、以及高风险删除前确认这三类用例。这个小样本评估说明，改变上下文的表示方式并不会自动修复应用策略。
- 模型选型时经常遇到的问题就是「A 和 B 哪个更好」，配对比较给了一种不依赖绝对分数的评估方式。

两种回归任务的取舍可以列成一张表：

| | 端到端回归任务 | 轨迹前缀回归任务 |
| --- | --- | --- |
| 起点 | 初始状态 + 用户请求 | 首错之前的状态（上下文/对话/工具返回/环境全部冻结） |
| 要模型做什么 | 完成整个任务 | 只输出下一步或下几步可观察动作 |
| 检查什么 | 最终状态、必要输出、安全条件 | 那个决策边界 |
| 成本 | 高 | 低 |
| 缺点 | 难以判断失败发生在哪一步 | 覆盖的只是单个决策点 |
| 用途 | 保证整体能力不退化 | 隔离并锁定单个策略或工具问题 |

这张表是补充的整理，但每一格都来自资料的表述。

为什么轨迹前缀回归任务集往往比端到端回归任务集更重要？因为生产事故往往出在某个决策点上（该不该先问、该不该删、该不该改测试），而端到端跑一遍只能告诉你整体掉分了。轨迹前缀把成本压到最低的同时，恰好钉住了那个决策点。

「答案定义为一个可接受动作集合」对应一个现实：同一个决策边界可能有多种正确处理方式，先读仓库规则，或者先问用户，都可能对。如果回归任务只接受唯一答案，就会把正确的替代行为判错，逼模型去猜出题人想要哪一个。

从错误类别到回归任务的对应关系可以记成一句话：流程类错误做成端到端任务，它涉及整条工作流；决策类错误做成前缀任务，它只涉及一步。这里给的最后两条尤其值得注意：「症状修复与验证造假类」要在验收里加硬约束（不得修改测试断言、完成声明必须附真实命令输出），这是在判分层面堵住 7.5.2 表里的 hack 验证环境；「信息反馈类」要对答复内容本身设断言，这是在补 7.5.2.1 那个「环境状态对但信息说错」的漏洞。

实验 7-7 的结论很有价值：三种等价表示总分一样（6/11），但失败位置不同。这说明换一种上下文表示不会自动带来提升，只会把失败挪到别的地方。三种表示都失败的三个用例（论文风格过度泛化、过时偏好覆盖当前要求、高风险删除前确认）指向的是共同的应用策略缺陷，跟编码格式无关，所以修的对象应该是策略。

「端到端回归任务」与「标准评测集」的关系也要理清： OSWorld、AndroidWorld、tau-bench 这些标准评测集都是端到端回归任务。也就是说，跑基准的时候其实已经在做端到端回归了，缺的是轨迹前缀那一层。另外，轨迹前缀回归不等于轨迹回放：回放是要求模型重复原来的动作；轨迹前缀回归是把历史冻结、只让模型决定下一步，答案是一个可接受动作集合。

端到端回归保「整体不退化」，轨迹前缀回归钉「那个决策点有没有修好」；后者更便宜，对生产级 Agent 往往更重要。

Elo 评分最初用于国际象棋，它通过大量的两两对决量化模型的相对能力：分差越大，强者的预期胜率越高。模型 A 得 1200 分、模型 B 得 1000 分时，Elo 系统会预测 A 的胜率约 76%。如果 B 意外获胜，B 加分较多、A 减分较多，爆冷的结果会带来更大的分数调整，这种机制让排名快速收敛到真实水平。

背后的统计基础是 Bradley-Terry 模型：把每个模型抽象为一个潜在的实力分数，两两对决的胜负概率由两者分数差决定；Elo 是该模型在线更新形式的一种工程实现。

Chatbot Arena 采用匿名随机对决，用户在不知道模型身份的情况下盲选更优回应，通过数百万次投票得出排名。这种方法的优势在于不需要定义绝对标准，只需要人类判断「A 和 B 哪个更好」。局限也很明确：排名结果取决于用户提了什么问题。如果大量用户恰好都问编程题，擅长编程的模型排名就会偏高，这未必反映它在其他任务上的真实水平。

当配对评判由 LLM 执行时，还要防范位置偏差（Position Bias）：评判模型会系统性地偏向出现在某个位置（通常是先出现）的候选，即使两个候选的内容完全对调，判决也可能不变。标准的缓解方法是交换顺序各评一次，A 在前评一次、B 在前再评一次，取两次结果的平均；更严格的做法是只有两次判决一致时才计入，不一致则记为平局或送人工复核。Chatbot Arena 的做法本质相同，随机化两个回答的展示位置，让位置偏差在大样本下相互抵消。

#### 实验7-8 ★★：从配对比较数据构建模型排行榜

- 本实验从零实现 Elo rating 计算系统，以深入理解 Bradley-Terry 模型如何从大量配对比较中提取相对能力评分。实验使用 Chatbot Arena 开源的真实投票数据集（包含数百万次用户盲选投票）。
- 实现 Elo rating 迭代更新算法：初始所有模型评分 1000 分，按时间顺序处理投票记录。对每场对决，根据两个模型当前的评分差计算预期胜率，将实际结果与预期比较，按固定学习率调整，胜者加分、败者减分，调整幅度与预期偏差成正比（爆冷失败会导致更大的分数变化）。按最终评分降序排列并计算两两胜率矩阵，与官方榜单对比，验证排名大体一致即可。不必苛求逐分对齐：Chatbot Arena 官方用的是 Bradley-Terry 极大似然拟合（对全部对局一次性求解，与投票的先后顺序无关），而这里实现的是在线增量更新的 Elo（结果受学习率 $K$ 因子和处理顺序影响），两种算法在总体排名上应当吻合，但具体分值不会精确一致。
- 实验第二部分创建历史排名演进动画：将投票数据按时间切片（每周或每月），对每个时间点计算 Elo 评分快照。使用 D3.js 实现条形图竞赛动画（水平条形长度 = 评分，纵向位置 = 排名，随时间平滑变化）。通过观察动画识别技术突破时刻（某模型评分骤升）、竞争格局演变、模型生命周期。

Elo 公式的符号逐个解释一下（补充）：

$$
E_A=\frac{1}{1+10^{(R_B-R_A)/400}},\qquad R_A' = R_A + K\,(S_A-E_A)
$$

其中 $R_A$、$R_B$ 是对局前 A、B 两人的评分（Elo 分，无量纲，常以 1000 为起始值）；$E_A$ 是 A 的预期胜率（$0\le E_A\le 1$，无量纲）；$S_A$ 是实际结果（胜记 1、平记 0.5、负记 0）；$K$ 是学习率，即单场最大调整幅度，单位与评分相同；400 是 Elo 的标度常数，含义是分差 400 分时强者预期胜率约为 $1/(1+10^{-1})\approx 90.9\%$；10 是底数，来自 Elo 体系的历史约定。

把那个例子代进去复算（补充的计算）：$R_A=1200$、$R_B=1000$，则 $E_A=1/(1+10^{(1000-1200)/400})=1/(1+10^{-0.5})=1/(1+0.31623)=0.7597\approx76\%$，与「预测 A 的胜率约 76%」一致。若这次 B 爆冷获胜（$S_A=0$），则 $R_A'=R_A+K(0-0.7597)=R_A-0.7597K$，A 掉分接近满额；而 B 的更新是 $R_B'=R_B+K(1-E_B)$，其中 $E_B=1-0.7597=0.2403$，所以 B 加分 $0.7597K$。这就是「爆冷的结果会带来更大的分数调整」。

为什么这套机制能收敛到真实水平？因为预期的偏差越大，调整越大。如果 A 本该赢却输了，说明评分高估了 A，于是大幅下调；如果 A 赢了但对手很弱（预期本来就接近 1），$S_A-E_A$ 很小，几乎不动。长期下来，评分会自己找到那个「预测胜率与实际胜率相符」的位置。

Bradley-Terry 与 Elo 的关系值得分清（给了这层关系）：Bradley-Terry 是模型，给出「实力分数 → 胜负概率」的参数化形式，用全部数据一次性做极大似然拟合；Elo 是它的在线更新实现，按顺序逐场更新，所以结果会受 $K$ 和处理顺序影响。这可以解释为什么实验 7-8 说两种算法在总体排名上应当吻合，但具体分值不会精确一致。

位置偏差的缓解方法有一个强度阶梯：随机化展示位置（Chatbot Arena 在人类投票里的做法），靠大样本让偏差相互抵消；交换顺序各评一次、取平均，靠对称性抵消，样本需求更小；只有两次判决一致才计入，不一致记平局或送人工复核，最严格，代价是丢样本。

Chatbot Arena 的局限值得记住：它测的是「在用户实际提出的问题分布上的相对偏好」，跟「在你业务上的能力」是两回事。如果提问分布偏斜（比如大量编程题），排名就会偏斜。这条局限正好呼应 7.4.6 节「公开基准的任务分布与实际业务的任务分布并不一致」。

Elo 评分不是绝对能力分，它只定义相对关系（分差决定预期胜率），1200 分本身没有绝对含义。Bradley-Terry 拟合与 Elo 迭代也不同：前者与对局顺序无关，后者依赖顺序与 $K$，实验 7-8 里特意提醒「不必苛求逐分对齐」。位置偏差（Position Bias）与长度偏差（Length Bias）同样要分清：位置偏差是偏向先出现的候选，用交换顺序缓解；长度偏差是偏向更长的回答，用惩罚冗长、长度对齐、相关性审计缓解（见 7.5.1）。

配对比较不需要绝对标准，只需要判断「A 和 B 哪个更好」；Elo 是 Bradley-Terry 的在线实现，用 LLM 评判时务必交换顺序防位置偏差。

## 7.6 评估驱动的模型选型

挑模型的第一反应是选榜单上最强的那个。这里对这个做法有明确态度：「模型选择是要根据应用场景和评估结果在多个维度之间作出权衡，不是简单地『选最强的模型』。」「最强」既没有统一定义，也不一定在你的任务上最强，7.6.4 节那个 Gemini 换 Claude 的案例就是为这件事准备的。这一节要做的，是把 7.1 到 7.5 建立起来的评估能力接到一个具体决策上。

## 7.6.1 选型的关键维度

吞吐量和延迟是两组容易混淆的指标，理清它们只需要知道大模型推理分两个阶段。Prefill（预填充）一次性读入完整上下文，决定用户按下回车到第一个字出现之间的等待，业内用 TTFT（Time To First Token）度量：上下文越长 prefill 越慢、TTFT 越大。Decode（解码）随后逐 token 生成回答，决定后续出字速度（tokens/秒），也直接决定思考时长。这里有个容易低估的数：一个 50 tokens/s 的模型生成 2000 个思考 token，光思考就要 40 秒。

围绕这两个阶段，主要的吞吐与延迟指标有八项。

1. 输入吞吐量 / 输出吞吐量：分别对应 Prefill 和 Decode 的速度。
2. TTFT：等于排队时间加上 Prefill 时间，是用户感知的「反应快慢」。
3. 思考延迟：不同模型生成的思考 token 数差异可达数倍，而且思考长度与任务效果不一定正相关。要在自己的工作负载上实测各模型的思考 token 用量和对应收益，不能只凭公开榜单推断。
4. p95 尾部延迟：95% 的请求都不会超过的延迟。它比平均值更能反映真实用户体验，均值会被大量快速请求拉低，掩盖少数用户遭遇的严重卡顿。
5. 成本：输入/输出/缓存 token 的定价。一个便宜但成功率低的模型，因为需要频繁重试，实际花费可能反而更高。要算的是每个任务的平均成本和成本-性能比。
6. 性能：Pass@1、Pass@k、Pass^k、Best@k 的精确定义见前文「评估指标：成功的定义」，其中 Pass@1 就是 $k=1$ 的 Pass@k，即单次平均成功率。日常场景看最常用的 Pass@1；关键操作场景优先 Pass^k，盯的是每次都别出错的稳定性；探索性任务优先 Pass@k 或 Best@k，看的是给足机会后的能力上限。
7. 速率限制与可靠性：RPM（每分钟请求数）/ TPM（每分钟 token 数）限制会影响并发能力，某些 API 在高峰期还会动态调整限额。鲁棒性方面要关注分布外数据、对抗性输入和长时运行稳定性，比如是否出现模式崩溃、注意力分散。
8. 预算—能力曲线：固定预算下的单点成绩不足以判断 Agent 能否胜任长程任务。除了成功率，还应该报告性能随墙钟时间、token、工具调用次数或算力预算变化的曲线。RE-Bench 的人机对照很能说明问题：在每个环境 2 小时的总预算下，最佳 Agent 得分约为人类专家的 4 倍；但人类从增加时间预算中获得的收益更大，8 小时时已略微超过最佳 Agent，在跨多次尝试合计 32 小时时得分约为其 2 倍。短预算领先不能直接外推成长时间运行能力，选型必须在接近真实任务时长的多个预算点上比较。

实践中还可以采用多模型协同的策略：轻量模型处理简单请求以降低成本，强大模型处理复杂任务以保证质量；或者用专门的模型处理特定子任务，如图像理解、代码生成，通过子 Agent 机制协作。这种异构的模型组合同样要靠评估来验证，确认整体效益是否超过了所增加的系统复杂度，以及是否会在某些场景下出现性能回退。这里举的例子很具体：把「9.9 跟 9.11 哪个大」或者「要洗车，家离洗车店 50 米，是走路去还是开车去」当成简单问题交给轻量模型，就会直接导致决策错误。

这里那个 40 秒的算式值得复算：$2000\ \text{tokens}\div 50\ \text{tokens/s}=40\ \text{s}$。它说明思考延迟是一个独立的、不可忽略的时间成本，长思考模型上尤其明显，用户按下回车之后可能要等四十秒才开始看到输出。

指标里最容易搞混的是 TTFT 与总延迟。TTFT 是第一个字什么时候出来，总延迟是最后一个字什么时候出来。TTFT 包含排队时间，高峰期同一个模型可能 TTFT 变长而总延迟差不多，所以选型时这两项要分开测。至于为什么强调 p95 而不是平均值，这里的解释是均值会被大量快速请求拉低，掩盖少数用户遭遇的严重卡顿；工程上的经验法则可以记成平均值看容量规划，p95/p99 看用户体验。

成本那一项有个反直觉结论：便宜但成功率低的模型可能更贵。原因是频繁重试，单次便宜但要多跑几次才成功，而且每次重试都带着更长的上下文（7.6.3 节讲上下文累积效应时会展开）。正确的比较量是每个任务的平均成本，不是每百万 token 的单价。

预算—能力曲线是这一节最容易被忽略、也最有价值的一条，它说的其实是单点分数会骗人。RE-Bench 的人机对照给出了一个很清晰的模式：2 小时预算下 Agent 是人类专家的约 4 倍，Agent 起步快；8 小时人类已略微超过最佳 Agent，人类后劲足；跨多次尝试合计 32 小时，人类得分约为 Agent 的 2 倍。曲线会交叉。如果你的真实任务是「跑 8 小时」，就不能拿 2 小时的分数做选型。

多模型协同里那两个例子很经典。「9.9 跟 9.11 哪个大」是版本号直觉与数值比较的陷阱；「要洗车，家离洗车店 50 米，是走路去还是开车去」则要看「开着车去洗」这个隐含前提。它们表面上都是短问题，实际需要常识推理，交给轻量模型就会出错。题目短不等于任务简单，这是路由策略最常见的坑。

还有三组概念别搅在一起。吞吐量是单位时间能处理多少，输入吞吐量对应 Prefill、输出吞吐量对应 Decode；延迟是一次请求要等多久，比如 TTFT 和 p95，两者可以反向变化。TTFT 与思考延迟也不是一回事：前者主要是排队加 Prefill 的开销，回答的是「多久开口」；后者是 Decode 阶段生成思考 token 的时间，回答的是「想多久」。Pass@1 与 Pass@k 在选型里的用途同样不同，得很明确，日常看 Pass@1，关键操作看 Pass^k，探索性任务看 Pass@k / Best@k。

### 7.6.2 模型的行为策略

选型不只是在比较「能不能做成」，还要比较模型默认会怎样做。Coding Agent 上有一个很容易观察到的差异，叫行动阈值：面对同一个代码任务，有的模型会先广泛探索仓库再动手修改；有的模型凭较少的局部证据快速定位，先改再用测试反馈补齐认识。前者把过早修改的风险估得更高，后者把「再读一个文件」的机会成本估得更高。

这种倾向有两个来源：Harness 中的系统提示词，以及模型自身的行为策略。后训练是行为策略的关键来源。SFT 轨迹会示范「先读到什么程度再动手」，过程奖励会奖励或惩罚某种工具路径，结果奖励又会强化最终成功的整套策略。久而久之，模型学到的不只是如何写代码，也包括工程习惯。

#### 实验7-9 ★★：在固定Coding Harness 中测量模型的行动阈值

- 实验目标：隔离模型因素，量化不同 Coding 模型在「继续收集信息」与「开始修改代码」之间的默认取舍，并把路径效率与最终质量联合起来评价。
- 技术方案：默认通过同一个 OpenRouter OpenAI-compatible 端点调用 GPT-5.6-sol 与 Claude Sonnet 5，固定系统提示、工具 Schema、任务仓库、测试命令和最大轮次；中性提示既不要求读够若干文件，也不要求尽快编辑。三个小型代码库分别覆盖局部 bug、跨模块身份规范化和公共契约敏感的缓存修复，每个模型对每题独立运行三次，共 18 条轨迹。
- 因果判断：中性实验回答「同一 Harness 下，行为是否随模型变化」。如需测 Harness 的调节作用，再用 `--policy explore-first` 单独跑一组；不要把两种 policy 混在同一模型比较里。若更换模型时行为改变、而同一模型跨 Harness 保持倾向，则证据更支持模型效应；反之则更支持 Harness 效应。
- 实验发现：
 - GPT-5.6-sol 在第一次修改前平均调用工具 6.89 次、读取 4.67 个文件；
 - Claude Sonnet 5 分别为 4.56 次和 3.56 个文件；
 - 差距在局部任务中最明显，而在明确跨模块的任务中几乎收敛（7.00 对 6.67 个文件）；
 - 两者的首个受测补丁和最终测试均为 100% 通过，因此这个小实验支持的是「行动策略随模型而变」，而不是「多读或早改必然更好」；
 - 时间到首次修改也几乎相同（15.01 秒对 14.48 秒），提醒我们工具步数、并行调用和模型延迟必须分开看。

「行动阈值」可以这样理解：模型在动手之前要求多少证据。阈值高的模型先读一批文件再改，阈值低的模型看到一个可疑函数就改，靠测试反馈纠错。两者都算不上错，只是风险偏好不同。

这个实验的设计值得当作「隔离模型因素」的范本，因为它把可能混淆的变量都摁住了。同一个端点（OpenRouter OpenAI-compatible）排除了不同 API 实现带来的差异；系统提示、工具 Schema、任务仓库、测试命令、最大轮次全部固定，排除了 Harness 差异；中性提示既不要求读够若干文件，也不要求尽快编辑，不诱导任何一种策略；三类代码库乘以每题三次运行，`18 = 2 模型 × 3 任务 × 3 次`（这个数是按「三个小型代码库、每题独立运行三次、共 18 条轨迹」算出来的）。

「中性提示 + `--policy explore-first` 单独跑一组」是这套设计的关键：先用中性提示测模型自带的倾向，再单独加一组带 policy 的测 Harness 的调节作用。警告不要把两种 policy 混在同一模型比较里，混在一起就无法区分这个差异是模型带来的还是提示词带来的。

实验发现里有三个地方容易被读错。一是「多读」不等于「更好」，两个模型首个补丁和最终测试都是 100% 通过，GPT-5.6-sol 读得多只说明它更谨慎。二是任务越明确差异越小，局部任务里 4.67 对 3.56 个文件差得明显，明确跨模块的任务里几乎收敛到 7.00 对 6.67，任务结构本身会「压平」模型间的行为差异。三是工具步数不等于耗时，两个模型的时间到首次修改几乎相同（15.01 秒对 14.48 秒），工具调用次数却差了约 2.3 次，说明步数差异被并行调用和模型延迟吸收了。这里的提醒正是工具步数、并行调用和模型延迟必须分开看，只看步数会得出错误结论。

「后训练会塑造工程习惯」这件事对选型重要在哪里？如果你需要的是一种工作风格，比如「不许在没读规范前动手」，你可以选一个默认就这样的模型，也可以在 Harness 里用提示词约束。判别方法在实验 7-9 的因果判断里：换模型行为变、同一模型跨 Harness 不变，是模型效应；反之是 Harness 效应。

这里有两组容易混淆的东西。行动阈值是模型属性，提示词要求是 Harness 属性，两者会产生同样的现象，都能让模型「多读几个文件」，要区分只能靠实验设计，也就是换模型和换 Harness 分别观察。另外，步数多不等于成本高，步数多可能伴随并行调用，端到端耗时未必更长，用「时间到首次修改几乎相同」印证了这一点。

选型也要比模型默认怎么做。行动阈值是模型的行为属性，来自后训练，它会随任务明确度上升而收敛。

### 7.6.3 Agent 系统的成本分析

7.6.1 节把成本列为选型维度之一，但在 Agent 场景下，成本远比 token 定价复杂：多轮推理、工具调用和上下文累积会让它呈非线性增长。系统的成本分析既是评估体系不可或缺的一环，也是生产部署的必要前提。

成本可以分解成三个层次。第一层是模型推理成本，也是最直接的部分，由输入 token 和输出 token 的消耗决定，但 Agent 场景下有两个常被忽视的放大因素。一个是上下文累积效应：Agent 每轮调用 LLM 时都会把之前所有的对话历史和工具返回结果一起发送，模型才能理解上下文；如果没有利用好 KV Cache（缓存已处理过的上下文，避免重复计算），成本增长会非常快。第 1 轮发送 1000 token，第 2 轮 2000 token，第 3 轮 3000 token，总量是 $1000+2000+3000=6000$ 而非 $3\times1000=3000$，轮次越多差距越大。另一个是思考 token 成本，支持思考的模型会生成大量思考 token，这些 token 虽然不展示给用户，但同样计入费用。

第二层是工具调用成本，包括外部 API 费用（搜索引擎按次计费、数据库查询消耗计算资源）、代码执行的沙盒资源，以及一个容易被忽视的间接成本：工具返回结果注入上下文后产生的 token 费用。一次网页搜索返回的内容可能就占用 2000-5000 个 token，而且在后续每轮推理中都会作为输入被反复计费。第三层是基础设施成本，涵盖向量数据库（用于 RAG 检索）、消息队列、关系型数据库、日志与追踪存储（用于可观测性）等运维开销。

为了看清这些费用究竟从哪里来，配套实验选了一个固定的八轮客服退款任务：查询订单、物流、退款政策和知识库，随后完成风控、退款、通知与关单。实验调用 gpt-4o-mini，分别打开或关闭「稳定前缀」和「压缩历史」两个开关，得到四组对照。

表 7-4 八轮Agent 任务的真实成本对照

| 方案 | 输入token | 缓存token | 总成本 | 比基线节省 |
| --- | --- | --- | --- | --- |
| 无缓存、无压缩 | 20,700 | 0 | \$0.003776 | — |
| 仅稳定前缀 | 20,386 | 13,568 | \$0.002707 | 28.3% |
| 仅压缩历史 | 16,177 | 0 | \$0.003115 | 17.5% |
| 稳定前缀+ 压缩 | 16,035 | 6,144 | \$0.002643 | 30.0% |

基线组里每轮输入从 1,113 token 一路涨到 3,668 token。工具返回会跟着历史反复进入后续请求，八轮累计占了 9,544 个输入 token。两项优化同时开启后，这个数字降到 5,248，总费用下降 30%。

有意思的是这三档节省并不能相加。「仅稳定前缀」已经节省 28.3%，「仅压缩历史」又节省 17.5%，两者一起却只节省 30%。原因是压缩历史的同时，也缩短了可以命中缓存的前缀。几项上下文优化同时使用时，必须在完整任务中一起实测，不能把各自的节省比例直接相加。

再看成本优化策略。从输入侧看，最值得优先测试的有三类办法：复用 KV Cache（尽量保持前缀不变）、压缩上下文（减少旧轨迹和冗长工具返回）、分层选择模型（让轻量模型处理简单请求、强模型处理复杂推理）。第二章已经介绍了具体做法，这里要强调的是这些能力最好都能独立开关，既能看清每一项的作用，也能检查它们合用时会不互相抵消。除此之外，还有两项与评估和运维直接相关的手段。异步批处理把非实时任务积攒起来批量处理，利用 API 提供商在波谷时段的批量定价折扣；在模型本地部署场景下，也能提高波谷时段的 GPU 利用率。成本监控与预算控制则要求生产环境中建立实时的成本监控体系，按任务类型、模型、用户等维度追踪 token 消耗和 API 费用，同时设置每个任务的成本上限，当 Agent 陷入循环或探索过深时自动终止，防止单次任务产生异常高额的费用。

#### 实验7-10 ★：Agent 任务的端到端成本分析

- 实验目标：复现上述八轮任务的全链路成本拆解，并用自己的真实工作负载验证优化策略。
- 技术方案：先复现配套仓库中的固定任务，再换成几个自己的典型任务。使用 LangSmith 或自建追踪系统记录每次 LLM 调用的输入/输出 token 数、思考 token 数、工具调用次数和返回大小、端到端延迟。计算每类任务的平均成本、成本分布（p50/p95/p99）和成本构成比例。
- 验收标准：生成成本拆解报告，识别主要成本驱动因素。四种开关组合都要运行，既比较每项优化单独带来的变化，也检查两项优化合用后的结果。

上下文累积效应值得自己算一遍：

| 轮次 | 本轮发送 token | 累计发送 token |
| --- | --- | --- |
| 第 1 轮 | 1000 | 1000 |
| 第 2 轮 | 2000 | 3000 |
| 第 3 轮 | 3000 | 6000 |

这里的算式是 $1000+2000+3000=6000$，正好用来对照「以为是 $3\times1000=3000$」的直觉。推广到 $n$ 轮就是等差数列求和 $n(n+1)/2\cdot 1000$，成本随轮数按平方增长，所以长对话 Agent 的账单涨得比预期快得多。KV Cache 的作用正是把已经处理过的前缀缓存下来，避免每一轮都重算那些重复的部分。

表 7-4 的四个节省比例可以逐个复算。仅稳定前缀：$(0.003776-0.002707)/0.003776=0.001069/0.003776\approx28.31\%$，对应 28.3%。仅压缩历史：$(0.003776-0.003115)/0.003776=0.000661/0.003776\approx17.51\%$，对应 17.5%。稳定前缀加压缩：$(0.003776-0.002643)/0.003776=0.001133/0.003776\approx30.01\%$，对应 30.0%。三个结果都与前面一致。

「$28.3\%+17.5\%=45.8\%$，实测只有 30%」这个落差是全节最重要的工程教训。原因这里讲得很清楚，两种优化会互相干扰：压缩历史把旧轨迹删掉了，而缓存命中的前提是前缀不变，前缀一压缩，原本能命中的缓存段就失效了。所以单项收益不能相加，多项优化必须在完整任务中一起实测；这也正是这里强调这些能力最好都能独立开关的原因，只有能独立开关，才能做四种组合的对照实验，实验 7-10 的验收标准要求跑完四种组合。

三条输入侧优化其实对应三个不同的杠杆。KV Cache 尽量保持前缀不变，减少重复计算，降的是重算成本；压缩上下文减少旧轨迹和冗长工具返回，降的是输入的绝对长度，也就是基数；分层选择模型让便宜模型干简单活，降的是单价。三者作用点不同，会互相干扰也不奇怪，比如压缩上下文就会破坏缓存前缀。

工具返回结果注入上下文后产生的 token 费用最容易漏算。一次网页搜索返回 2000 到 5000 token，它在后续每一轮都会被重新计费。真正的成本在于这次搜索的内容在剩下 $n$ 轮里被重复计费多少次，而这一次搜索本身花掉的钱只是零头。实践上的建议是对超长的工具返回做摘要或截断，收益会乘以后续轮次。

每个任务的成本上限是个很实际的护栏。Agent 一旦陷入循环，账单会失控，7.8 节的监控示例里就有「task#892 循环调用 search 14 次，耗 \$2.1」这样的异常。设上限自动终止，本质上是把成本也变成一个可中断的条件。

这里还有两组容易混的对照。token 单价便宜不等于总成本低，还要看上下文累积、思考 token、工具返回的重复计费，以及重试次数，7.6.1 节已经提示过「便宜但成功率低的模型实际花费可能反而更高」。KV Cache 的命中条件与前缀稳定性绑定，这也解释了为什么压缩历史会削弱稳定前缀的收益，两个优化并不正交。

Agent 成本按上下文累积呈非线性增长（1000+2000+3000=6000 而非 3000），多项优化会互相干扰，节省比例绝不能相加。

### 7.6.4 评估驱动的持续迭代

模型选择需要随着模型演进动态调整，一次定下来是不行的。本章开篇已经提出「拥有评估体系就能快速跟上模型演进」这一核心理念，下面用一个具体的模型切换案例，说明这套体系在真实决策中如何运作。

假设你的 Agent 系统当前基于 Claude 构建，在工具调用和复杂编排上表现优异。某天 Gemini 发布了一个新模型，公开基准显示它在多项指标上超越 Claude，而且定价更低。此时真正要问的是：在我的特定任务上，Gemini 是否比 Claude 好？好多少？切换成本是什么？「Gemini 是否比 Claude 强」这种问题榜单已经回答过了，但它回答不了上面这三问。

拥有完善评估体系的团队可以在数小时内给出答案：在自己的评估数据集上运行新模型，对比任务成功率、工具调用正确率、延迟和成本。你可能会发现新模型在简单任务上确实更优且更便宜，但在涉及复杂多轮工具编排的核心场景中，成功率反而下降了 5%。在确认这一差异超出噪声带宽之后（见下文「评估结果的统计显著性」），决策就变成了「简单任务迁移到新模型以降低成本，复杂任务保留原模型以确保质量」的差异化策略，而不是盲目的全量切换。这种精细化的数据驱动决策，只有在预先构建好评估体系的前提下才可能实现。

#### 实验7-11 ★★：多维度模型性能基准测试

对主流 LLM 及不同 API 提供商进行全面基准测试，建立多维度模型选型决策数据库。

- 选择测试范围：GPT 系列、Claude 系列、Gemini 系列、Doubao 系列等闭源 SOTA 模型，以及 Qwen、Kimi、DeepSeek 等开源模型。对同一模型测试不同 API 提供商（如 DeepSeek 官方 vs Siliconflow），验证第三方性能监测平台（如 Artificial Analysis）的结果。
- 设计标准化测试工作负载：输入吞吐量测试使用固定长度上下文（8K/32K/128K tokens），输出吞吐量测试请求生成固定长度响应（512/2048 tokens）。延迟测试包含 TTFT（首个 token 生成时间）和端到端延迟，对支持思考的模型单独测量思考长度与思考延迟。每个配置至少 100 次请求，计算标准差/p50/p95/p99。高延迟方差意味着用户体验不稳定。
- 评估 API 的可用性与稳定性：在一周内每小时探测一次，记录成功率、错误类型和故障时长。计算故障率、MTTR（平均恢复时间）和最长连续可用时间。测试速率限制的实际阈值，通过逐步提升并发量来找到限流点，记录 RPM/TPM 上限。计算综合成本：收集定价信息（输入/输出/缓存 token 的单价），考虑 KV Cache 的影响，计算典型多轮 Agent 任务的平均成本。

#### 实验7-12 ★★：用户记忆系统的端到端选型评估

- 前置要求：需完成第三章上下文检索或智能体化 RAG 实验。
- 目标：对用户记忆检索 Agent 做全链路选型评估，看嵌入模型、reranker、Agent 主模型三个选择点如何共同影响检索质量、延迟与成本。复用 `chapter3/contextual-retrieval-for-user-memory` 或 `chapter3/agentic-rag-for-user-memory`，在 60 个测试用例上对比。
- 验收：遍历三个选择点。嵌入模型（BGE-M3 / OpenAI / 豆包等，记 top-5 检索准确率、延迟、成本）；reranker（含「不用 reranker」基线，量化其边际价值）；主模型（相同检索配置下比成功率与工具使用效率）。
- 发现：更强的嵌入可能让 reranker 变得多余，更强的主模型可能弥补检索的不足。

这个案例的提问方式值得背下来。公开榜单能回答的是「谁更强」，只有自建评估集能回答「在我的任务上，它好在哪、差在哪、切换成本多少」。

案例的结果形态也很有代表性：新模型在简单任务上更优更便宜，在复杂多轮工具编排上成功率反而下降 5%。这就把决策从「切或不切」变成了分场景路由。简单任务迁到新模型省钱，复杂多轮工具编排保留原模型保质量，这类决策正是 7.6.1 节「多模型协同」策略的一个实例。

这一点上加了一个重要的限定词：「在确认这一差异超出噪声带宽之后」。5% 这个数字本身还不足以做决策，评估集有多大？置信区间多宽？这是 7.7 节要解决的问题。如果评估集只有几十题，5% 的差异很可能只是抽样噪声。

实验 7-12 的「发现」写得非常精炼，值得展开理解。「更强的嵌入可能让 reranker 变得多余」说的是：如果第一轮检索已经很准，reranker 这个额外环节的边际价值就很小，反而增加了延迟和成本；所以 reranker 的评估必须带「不用 reranker」的基线，量化边际价值。「更强的主模型可能弥补检索的不足」说的是：Agent 主模型如果足够强，可能自己就能从不够准的检索结果里挑出正确的信息，这意味着组件之间是可替代的，不能孤立地评估检索质量，要在端到端任务上看。两条合起来说明，在一个多组件系统里，每个组件都选最优不一定等于整体最优，必须做联合评估。

「三个选择点 × 60 个用例」的规模也提示我们，全链路选型评估的组合数会迅速膨胀（嵌入 × reranker × 主模型），工程上要分层筛选：先固定后两个、只比嵌入；再固定最优嵌入、比 reranker；把这两个选择点定下来之后，才轮到比主模型。这也是实验 7-12 的验收顺序。

两组概念在这里要分开。公开基准超越与在你的任务上更好是两件事，这里的案例设定就是「公开基准多项超越 + 定价更低」，但在特定场景上成功率反降 5%。组件最优也不等于系统最优，更强的嵌入可能让 reranker 冗余，更强的主模型可能弥补检索缺陷，评估必须在端到端任务上做。

换模型不是「切或不切」的二元决策，先在自建评估集上确认差异超出噪声，再按场景做差异化路由。

## 7.7 评估结果的统计显著性

评估集有限，模型输出又有随机性，分数差异完全可能只是抽样噪声。若在 $n$ 个用例上测得成功率 $p$，标准误可以粗略估计为：

$$
SE(p)\approx\sqrt{\frac{p(1-p)}{n}}
$$

其中 $p$ 是在 $n$ 个用例上测得的成功率（无量纲，取值 $0\le p\le 1$）；$n$ 是评估用例数（无量纲的正整数）；$SE(p)$ 是这一成功率估计的标准误（standard error，无量纲，与 $p$ 同量纲）。它衡量的是「如果重复抽样，这个成功率会晃动多大」。

举个具体的例子：100 个用例、成功率 70% 时，95% 置信区间约为 70% ± 9 个百分点。「新模型 73% 对旧模型 70%」这样的结果不足以支持切换。

同一批任务上比较两个配置时，应该优先做配对分析：逐题记录谁胜出，用 McNemar 检验或配对 bootstrap 判断差异，而不是直接相减两个独立成功率。由于 Agent 每次运行也可能不同，每个配置最好用多个随机种子（如 3–5 次），报告均值和波动范围；单次运行只能用来筛选方向。如果预期收益只有 2–3 个百分点，而评估集只有几十题，应该先扩大样本，标准误会按 $1/\sqrt{n}$ 缩小。

```python
for task in paired_tasks:
    for seed in fixed_seeds:
        a = run(config_a, task, seed)
        b = run(config_b, task, seed)
        record_paired_delta(verifier(a), verifier(b))
return paired_bootstrap_or_mcnemar(all_deltas)
```

配对的含义是让两组共享任务与随机条件，而不是分别抽两批样本再比较平均值。

并行验证多个假设时还要考虑多重比较：收紧显著性阈值，或对正向结果做独立复跑。实务上的判断标准很简单，分差要超过噪声、在配对分析中成立，并且能够复现，才值得据此切换模型或发布改动。

公式的直觉可以拆开看。$\sqrt{p(1-p)/n}$ 里，$p(1-p)$ 是单次试验的方差（伯努利分布），除以 $n$ 再开方，就是「$n$ 次平均」的标准误。由它出发有三个推论。样本越多越准，$n$ 变成 4 倍，$SE$ 减半，这就是「按 $1/\sqrt{n}$ 缩小」。$p$ 接近 0 或 1 时更准，因为 $p(1-p)$ 在 $p=0.5$ 时最大，成功率居中时最难分辨差异。差异要跟 $SE$ 比，不要跟 100% 比，两个模型都「很高分」时，差异往往落在噪声里。

把那个例子代进去复算一遍：$SE(0.7)=\sqrt{0.7\times0.3/100}=\sqrt{0.0021}=0.0458$；95% 置信区间约为 $0.7\pm1.96\times0.0458=0.7\pm0.0898$，即 70% ± 约 9 个百分点，与前面一致。反过来看「73% 对 70%」，只有 3 个百分点的差距，而单个配置的 95% 区间就有 ±9 个百分点，差异完全淹没在噪声里，所以不足以支持切换。

为什么要强调配对分析，而不是把两个独立成功率相减？因为配对把任务难度这个共同因素消掉了。举个补充的例子：模型 A 在 100 题里对了 70 题，模型 B 对了 73 题，但 B 对的那 3 题恰好是 A 也对的简单题，而 B 在 A 做对的 3 道难题上翻了车。两个总数看起来只差 3%，实际的能力结构完全不同。逐题记录胜负（配对 delta）才能看出这件事。

多个随机种子这一条，针对的是 Agent 的第二层随机性：即使任务相同，Agent 每次运行的轨迹也可能不同，工具返回、采样温度、并行调用顺序都会有影响。这里的要求是每个配置最好用多个随机种子（如 3–5 次），报告均值和波动范围，并且把单次运行的用途限定在筛选方向上。单次结果可以决定要不要进一步测，不能决定要不要上线。

多重比较这一条最容易被忽略。如果你同时试了 10 个改进方案，每个都用 95% 置信水平判断，那么纯靠运气也会有一两个看起来「显著有效」。这里给的应对是收紧显著性阈值，或对正向结果做独立复跑。

这里最后那句实务标准可以当成三段式检查清单：分差要超过噪声（统计显著性）；在配对分析中成立（不是两组独立样本的假象）；能够复现（独立复跑仍然成立）。三条都过，才轮到切换模型或发布改动。

还有两组概念要分清。标准误（SE）与标准差（SD）不同，标准差描述个体的离散程度（$p(1-p)$ 的平方根），标准误描述估计量也就是成功率这个均值的离散程度，所以多了除以 $n$ 再开方这一步；这里给的是标准误。另外，「95% 置信区间 ±9 个百分点」是笔记复算的结果，本节只写了「约 70% ± 9 个百分点」，笔记补上 $1.96\times SE$ 这一步，是为了说明 9 这个数是怎么来的。

差异要跟标准误比：$SE\approx\sqrt{p(1-p)/n}$，样本翻四倍标准误减半；做决策要满足「超噪声 + 配对成立 + 可复现」。

## 7.8 Agent 的可观测性

评估驱动的决策，无论是模型选型还是持续迭代，都依赖高质量的运行数据。这一节先讲如何系统性地采集这些数据，也就是可观测性，再讨论如何把评估结果转化为系统改进。

> **图 7-7：可观测性技术栈**
>
> 可观测性技术栈。图分左右两块：
> - **左边：执行追踪树（单次任务）。顶层是一条 Trace：「帮用户查北京明天天气 (3.2s, \$0.008**)」；其下按顺序挂着若干个 span：`LLM Call：意图识别`（Claude 4 Sonnet · 0.4s · 320 tokens）→ `Tool：get_weather(Beijing)`（MCP Server · 1.8s · 200ms TTFT），该工具 span 下还有两个子节点：`├─ HTTP Request`（api.weather.com · 1.6s）与 `└─ Response Parse`（JSON → 结构化天气数据）→ `LLM Call：生成回复`（Claude 4 Sonnet · 0.8s · 580 tokens）→ `Tool：send_message(user)`（0.2s · 包含天气摘要）。这棵树的父子关系展示了「一次任务 = 一条 trace，每次 LLM 调用/工具调用/解析 = 一个 span」的结构。
> - **右边：监控仪表盘**，分三栏：
> - **成本追踪**：今日 \$12.30（1,200 次）；本月 \$340（34K 次）；异常：task#892 循环调用 search 14 次，耗 \$2.1。
> - **性能监控**：P50 / P95 / P99 延迟：2.1s / 8.4s / 15.2s；工具成功率：94.3%。
> - **质量审计**：任务成功率 87%；幻觉触发 2.1%；安全违规 0（本月）；用户满意度 4.3/5。
> - **底部一条闭环箭头**：追踪数据 → 发现问题 → A/B 测试 → 提示词版本管理 → 持续优化。

可观测性（Observability）这个概念借自分布式系统领域。你没法直接打开系统内部看它在做什么，只能通过它输出的日志、指标和追踪数据来推断发生了什么，就像医生不能直接看到患者体内的情况，只能通过体温、血压、影像等外部信号来诊断问题。Agent 系统把这件事变得更难：同样的输入可能产生不同的输出，多轮推理和工具调用使执行路径极其复杂，而模型的「思考」过程对外完全不透明。

它的价值有四个方面。问题诊断上，完整的轨迹让开发者能回放全过程，而非靠猜测。它也是持续优化的基础，你能看到哪些任务需要多轮迭代、哪些工具成功率最低、哪些检索查询总是返回空结果。成本管理上，Agent 运行成本在不同任务上可能差一两个数量级，追踪可以识别出异常高成本的案例。积累下来的轨迹数据同样为模型后训练提供了基础。

Agent 可观测性的数据基础是追踪（Trace），其数据结构直接沿用了分布式系统的 span 树模型：一次任务执行对应一条 trace，其中每个 LLM 调用、每次工具调用、每次检索都是一个 span，也就是记录输入输出、起止时间、token 消耗、错误信息的执行单元。span 之间的父子关系构成一棵执行树，比如「Agent 主循环」span 之下挂着若干「LLM 调用」和「工具调用」子 span。

这一层已经有标准化协议可用。OpenTelemetry 是通用的分布式追踪标准，OpenInference 等规范则在其上定义了 LLM 应用特有的语义约定，比如如何记录提示词、模型参数、token 用量。采用标准协议的好处是采集与分析解耦：同一份追踪数据可以对接不同的分析后端，避免被单一平台锁定。

LangSmith 是这一领域的代表性平台之一，类似定位的还有 Langfuse、Arize Phoenix 等，它们把可观测性、评估、优化整合为闭环。每次执行时都会创建一个追踪会话，其中的模型调用、工具使用、知识检索被记录为独立的执行单元，通过因果关系链接形成一棵执行树，每个单元记录完整的输入输出、时间信息、成本数据和错误信息。平台采用异步批量数据采集，确保追踪本身不影响 Agent 的响应延迟。它还支持 A/B 测试（将一部分用户的流量路由到新版本，自动对比各项指标，支持快速回滚或渐进扩量）、提示词版本管理（每个版本都关联着运行时的性能数据），以及协作式开发（团队成员可共享追踪数据和问题案例）。生产环境中的海量真实数据是持续改进的金矿，能发现未曾预料的场景，识别最需要优化的功能点。

可观测性数据最有价值的去向，是回流并转化为评估资产。一条实用的闭环是：从生产轨迹中筛选出失败与可疑案例，做脱敏处理（去除用户隐私、密钥等敏感字段），再沉淀为评估集的新用例和回归测试。这样评估集就不再是一次性构造的静态集合，而成了随产品演化、持续贴近真实用户分布的活资产。今天线上暴露的失败模式，明天就成为守住这条底线的回归用例。

有了完备的评估体系和数据集，关键就在于把评估结果转化为切实的系统改进。

trace 和 span 的关系可以记成两个层级：trace 是「一次任务」，span 是「一步操作」。图 7-7 那棵树里，`get_weather(Beijing)` 这个工具 span 下面还挂了 HTTP Request 和 Response Parse 两个子 span，这意味着排查延迟时可以一路下钻。用户抱怨「查天气很慢」，你可以看出 1.8 秒里有 1.6 秒花在 HTTP 请求上，问题出在网络而不是模型。

图 7-7 的三个数字组合起来很说明问题。trace 总耗时 3.2s、总成本 \$0.008，其中工具 1.8s，两次 LLM 调用共 1.2s（0.4+0.8），工具反而比模型更耗时。工具 span 上还标了「200ms TTFT」，说明连工具调用也按首包延迟记录，不只记总时长。仪表盘里 P99 延迟 15.2s 而 P50 只有 2.1s，差了 7 倍以上，这正是 7.6.1 节强调 p95/p99 而不是均值的原因。

那条「异常：task#892 循环调用 search 14 次，耗 \$2.1」正是 7.6.3 节「设置每个任务的成本上限」要拦的场景。单次任务 \$2.1，而正常任务平均成本大约是 \$12.30/1200 ≈ \$0.010（这个数是笔记拿仪表盘上的今日费用除以今日次数算的），差了约两个数量级。不同任务成本可能差一两个数量级，在这个仪表盘上就有现成的实例。

可观测性对 Agent 比对普通服务更重要，这里给了三条理由：同样输入可能不同输出、执行路径极复杂、思考过程不透明。普通微服务的调用链相对固定，看一眼 trace 就知道坏在哪；Agent 的轨迹每一步都可能分叉，所以记录完整轨迹是唯一可行的诊断方式。

OpenTelemetry 与 OpenInference 那一段讲的是解耦，落到工程上就是追踪 SDK 只写一次，换后端不用改代码。异步批量数据采集这个细节值得单独记住：可观测性本身不能拖慢 Agent，如果每次 span 上报都同步阻塞，排查工具就变成了性能问题的新来源。

回流闭环的四步可以抄下来当 SOP，这四步的措辞逐字来自资料：从生产轨迹中筛选出失败与可疑案例；脱敏处理，去除用户隐私、密钥等敏感字段；沉淀为评估集的新用例和回归测试；让评估集成为随产品演化、持续贴近真实用户分布的活资产。其中第二步不能省，这也是 7.10.5 节「隐私感知分析」存在的理由。

这里有三组容易混的对照。可观测性提供的是原始数据（轨迹、指标、日志），评估是对数据的判定，这里的顺序也是先采集再讨论如何把结果转化为改进。Trace 与 Span 是包含关系，一条 trace 包含多个 span，span 之间还有父子关系，共同构成执行树，不能把二者说成同层概念。LangSmith、Langfuse、Arize Phoenix 是平台，OpenTelemetry、OpenInference 是协议与规范，前者是具体产品，后者是标准，这里分别用了「标准化协议」和「代表性平台」两种说法。

一次任务是一条 trace、每个操作是一个 span；追踪数据要能回流成评估资产，才算真正闭环。

## 7.9 从 Benchmark 报告到系统改进

用一个配套仓库里真实的 AndroidWorld 调优过程来演示。实验只跑了 API 35 模拟器上的 4 个 Wi-Fi 设置任务，每项任务做一次配对对照。这个案例的价值不在于证明系统整体提高了多少，而在于展示如何根据一轮结果，决定下一轮只改什么。

从 Harness 工程的视角看，这一节讲的是 Harness 迭代优化的方法论：通过评估数据定位 Harness 中的薄弱环节（上下文不足？约束缺失？验证不够？反馈不及时？），有针对性地改进，再重新评估，形成 Harness 持续进化的闭环。

在开始分析 Benchmark 报告之前，有一条容易被忽视的原则：看到 Agent 表现下降时，应先检查评测系统本身，再动 Agent。一个常见误区是看到分数下降就立刻修改 Agent 代码，而忽略了评测系统本身可能先出了问题。基于失真的信号调整方向，修改方向可能从一开始就是错的。评测系统常见的错误来源有三种：运行环境的资源不足导致进程被杀，表现为随机失败；验证器本身有 bug，把正确答案判为失败；测试用例与生产场景之间存在脱节。这些问题在结果数字上都跟模型退化一模一样，只有审查完整的轨迹才能区分。

### 7.9.1 读懂 Benchmark 报告：发现问题的艺术

最初的报告记录了 116 项任务各跑一次的结果，总成功率约为 88%。但失败并不是零星散落的：四项 `SystemWifiTurn*` 任务里有三项失败，轨迹中还反复出现来回导航、无法确认最终状态等现象。

这里至少有两种解释：可能是 Agent 不知道设置入口，也可能是它拿到的界面信息不完整。如果只盯着 88% 这个总分，这个小而集中的失败簇很容易被忽略；如果只是增加最大步数，又可能把「看不见界面」误当成「不够耐心」。所以读报告时应先找失败集中在哪些任务和能力上，再回放轨迹，分清问题出在看、想、做还是验。本例先把范围缩到四项 Wi-Fi 任务，目的只是用较低成本判断病因，不是估算系统的整体水平。

这一小节的方法可以整理成三步。别只看总分，去找失败簇，88% 是平均值，四项 `SystemWifiTurn*` 里挂了三项才是信号。也别锁定第一个解释，「不知道入口」和「看不到界面」都会表现为来回导航加无法确认状态。范围则要缩下来，用四项任务做小实验判断病因，而不是直接上 116 项乘以多轮的大实验。

「把『看不见界面』误当成『不够耐心』」是这一节最实用的一句警告。它对应一个非常常见的错误修复动作：分数低就加最大步数。如果真实病因是 Agent 观察不到界面状态，增加步数只会让它多绕几圈，既费 token 又不涨分。7.9.3 节会用实测数据证明这一点。

「失败集中」和「失败率高」是两种信号。总成功率 88% 看着还行，但失败集中在同一个能力标签上，说明存在系统性缺陷，而不是随机波动。看分布比看均值更有价值。

读报告先找失败簇，不要盯总分，然后回放轨迹分清问题出在「看、想、做、验」哪一环。

### 7.9.2 从数据到假设：构建改进路线图

第一轮先试最便宜的改法。假设 H1 认为 Agent 只是「不知道路」，因此只给实验组补充 Wi-Fi 设置的导航提示和最终状态检查要求。结果成功率没有变化，说明问题不在提示词。

第二轮转而检查 Agent 到底「看见了什么」。假设 H5 把 API 35 上不兼容的 accessibility feed 换成 AndroidWorld 已支持的 UIAutomator 元素树。成功率确实提高了，但完整元素树太长，token 用量大幅上升。

于是第三轮 H5C：不再增加新信息，只把元素树中不可见、没有文字、也不能操作的容器节点删掉，看看能否在保留成功率的同时去掉噪声。

三轮实验始终使用相同的模型、任务参数、随机种子、步数上限和模拟器，并交替安排两组的运行顺序。这样一轮接一轮地缩小问题范围，比同时堆上许多改动更容易说清因果：上一轮暴露的问题，恰好成为下一轮唯一要验证的改动。

三轮实验的逻辑是一次只动一个变量，而且每一轮都由上一轮的结果决定。H1 测提示词，无效，于是排除了「Agent 不知道路」这一解释，把注意力转向输入；H5 测输入通道，换元素树，有效但太贵，于是确认瓶颈在观察通道，同时暴露了成本问题；H5C 测输入的冗余度，精简元素树，成功率不变而 token 减半，把「能不能做成」和「做成是否划算」一起解决了。

那一串控制变量值得抄下来：相同模型、任务参数、随机种子、步数上限和模拟器，并交替安排两组的运行顺序。它把模型、任务难度、随机性、预算、环境全部固定，唯一动的就是那一项改动。交替安排运行顺序是为了防止时间相关的漂移被误当成实验效应，比如模拟器越跑越慢。

那句「比同时堆上许多改动更容易说清因果」是这一节的核心方法论。多改同时上，分数涨了也不知道是谁的功劳，分数跌了也不知道是谁的锅。这一条与 7.10.1 节的消融实验、7.10.2 节的「多臂而非二元」是同一个思想。

H1 失败不等于「提示词没用」，它说明的是在这类失败上提示词解决不了，因为病因在输入通道。这里的结论是「提示写得更详细，也补不回 Agent 根本没有看到的信息」。

一轮只改一个变量，且让上一轮暴露的问题成为下一轮唯一要验证的改动。

### 7.9.3 从结果到决策：数据驱动的权衡

三轮实测结果汇总在表 7-5。每组都只有四项任务，所以这里的数字只能用来决定下一步是否值得扩大测试，不能用来推断整个 AndroidWorld 的成功率。

表 7-5 AndroidWorld Wi-Fi 子集的三轮实验

| 实验 | 只改了什么 | 对照组→实验组成功率 | 实验组/对照组token | 下一步 |
| --- | --- | --- | --- | --- |
| H1 | 增加导航提示 | 25%→25% | 0.47× | 没有提高成功率，沿用原提示 |
| H5 | accessibility feed 换成 UIAutomator | 25%→100% | 2.498× | 效果明显但太费 token，继续优化 |
| H5C | 精简 UIAutomator 元素树 | 100%→100% | 0.506× | 成功率不变、token 减半，进入完整复测 |

（表格按语义整理：这里分栏排版导致列错行，按「实验—只改了什么—对照组→实验组成功率—实验组/对照组 token—下一步」的列序重新对齐，数字与文字未改动。）

三轮结果串起来看，结论比某一个百分比更有用。提示写得更详细，也补不回 Agent 根本没有看到的信息；遇到这类失败，应先检查输入，而不是继续堆提示词。输入也不是越多越好，完整元素树解决了「看不见」的问题，却带来大量无用 token，删除无语义节点后，四项任务仍全部成功，token 又减少了约一半。整个过程中没有更换模型，仅仅调整 Harness 如何表示界面，就先后解决了「能不能做成」和「做成是否划算」两个问题。

表 7-5 的 token 比值值得逐个读清楚。H1 的 0.47× 表示实验组只用对照组的约一半 token，导航提示与最终状态检查要求可能让 Agent 少绕路，虽然成功率没变。H5 的 2.498× 表示完整元素树让 token 涨到约 2.5 倍，这正是「有效但昂贵」的典型形态。H5C 的 0.506× 则在保持 100% 成功率的同时把 token 压回约一半。也就是说，从 H5 到 H5C，成功率不变而成本降到约五分之一（$0.506/2.498\approx0.203$），这一对比说明「找到有效改动」和「让改动变划算」是两件事，后者同样是 Harness 工程的成果。

「每组只有四项任务，所以数字只能用来决定下一步是否值得扩大测试」这句话是本节的方法论纪律：小样本只能做方向性判断，不能做水平估计。四项任务上 100% 不代表系统 100%。7.9.4 节会用「不能把子集上的 4/4 写成系统整体 100%」再强调一次。

第三条结论回应了本章开篇的核心认识：评估对象是「模型 + Harness」的组合体。这里从头到尾没换模型，只改了 Harness 如何表示界面，就同时改善了成功率和成本，这是「瓶颈在 Harness」的一个教科书式实例，也正对应章首说的「改进方向可能是优化 Harness 的某个组件」，不是换模型。

有两组概念在这里要分开。「成功率提升」与「值得部署」是两件事，H5 把成功率从 25% 拉到 100%，代价是 token 涨到 2.498 倍，所以它的下一步是继续优化，还谈不上部署。另外，对照组到实验组的成功率是配对对照的结果，不是两次独立测量的对比；7.9 开头就写了「每项任务做一次配对对照」，这正是 7.7 节主张的配对分析在小样本上的应用。

小样本结论只用来决定下一步测什么：先修「看不见」，再修「太费钱」，全程可以不动模型。

## 7.9.4 持续迭代：从第一次改进到系统演化

H5C 在四项任务上全部通过检查，能说明的事情其实有限：它值得进入下一轮，离可以部署还差得远。下一轮要补的功课有三件。第三方应用先补齐；然后在 Pixel 6 / API 33 标准环境里，让 116 项任务各跑 5 个随机种子；验收时除了确认成功率不能下降，还要看 token 有没有压在原方案的 75% 以内，延迟有没有控制在 1.5 倍以内。在这轮完整复测跑完之前，子集上的 4/4 不能写成系统整体的 100%。

这就是持续迭代的实际含义：一轮证据只支持与它规模相称的下一步。H1 失败，产出的是一个排除项，从此不再继续堆提示词；H5 找到了正确方向，同时把成本问题摆到台面上；H5C 把成本压下去之后，才换来扩大测试的资格。所以一份好的 Benchmark 报告不会只丢一个分数出来，它要写清结论适用于哪里、哪些底线没有通过、下一轮准备验证什么。

**实验7-13 ★★★：AndroidWorld 的评估和改进**

这个实验练的是从评估报告一路走到系统改进。起点是 `chapter7/android-world` 里的 AndroidWorld 历史报告，以及三组已经保存好的配对结果。

第一步是诊断。交叉分析逐任务表格和能力标签矩阵，把表面的任务失败映射回深层的能力缺陷，找出成功率低于预期的能力标签，以及集中翻车的任务区域。第二步是构建假设，按表层→中层→深层这三层框架把改进假设写出来，每个假设都要有明确的预期成功率提升目标和验证方法。第三步进入分阶段实验，先把 H1、H5、H5C 复现一遍，每轮只改一个变量；除了成功率，token、延迟和是否出现回退都要记下来。第四步做数据驱动决策，按成本收益比决定部署，适用范围、延迟影响和成本开销都要权衡，低成本高收益的改进优先上，高成本的限定在关键场景里用。第五步是迭代，小范围实验过了只能进完整复测，等标准环境里的 116×5 次运行跑完，才谈得上部署。报告里必须保留环境差异、样本量和尚未完成的部分。

「只说明它值得进入下一轮，并不等于可以部署」这句值得反复读，它挡住的是最常见的一种自欺：把子集上的漂亮数字当成系统能力。这里后面还有一句更硬的，不能把子集上的 4/4 写成系统整体 100%。

把「一轮实验的证据强度」和「下一步能做什么」摆在一起，就是一条升级阶梯（下面这张表是我按资料整理的，每行的数字都来自资料）：

| 证据规模 | 能支持的决定 |
| --- | --- |
| 4 项任务、1 次配对对照 | 判断病因方向（该改输入还是改提示） |
| 4 项任务、三轮单变量实验 | 判断「值得扩大测试」 |
| 116 项 × 5 个随机种子、标准环境 | 才轮到讨论是否部署 |

完整复测的三个门槛值得单独记。成功率不能下降是质量底线，token 不超过原方案的 75% 是成本底线，延迟不超过 1.5 倍是体验底线。这种「目标指标 + 护栏指标」的搭配，和 7.10.2 节讲的护栏指标是同一套设计，只是把护栏写成了硬数字。

H1 到 H5C 的链条还说明另一件事：每轮的产出除了结论，还有下一轮的资格。H1 交出来的是排除项，H5 交出来的是方向加一个待解决的问题，方向是元素树，待解决的是成本，H5C 交出来的是资格，可以进完整复测。

实验第四步那句「不是简单地采用所有有效的改进」值得单独读，它修正了不少人对「数据驱动」的误解。在这里，数据驱动意味着按成本收益比去权衡适用范围、延迟影响和成本开销，指标变好只是入场券。

最后那句「报告中必须保留环境差异、样本量和尚未完成的部分」既是撰写规范，也是诚实性要求。读报告的人需要知道，这个结论是在四项任务上、API 35 模拟器上得到的，标准环境的全量复测还没做完（这里 7.9.4 的复测要求写的是 Pixel 6 / API 33 标准环境，两处环境标注并不一致，下面按原样各自保留）。

还有两处容易混的地方要盯住。「通过子集检查」「通过复测」「可以部署」是三个不同的门槛，7.9.4 开头就把它们分开了。目标指标和护栏指标也不要混：H5C 的目标是把成功率保持住、把 token 降下来，护栏是成功率不能下降、延迟不超过 1.5 倍。目标可以继续优化，护栏是底线。

## 7.10 从外部评估到内部评估：生产级 Agent 的评估基础设施

前面几节讲的是怎么从外部给一个 Agent 打分：搭评估环境、设计数据集、分析 Benchmark 报告。真正做得好的 Agent 产品会再往前一步，把持续自我评估的基础设施建进产品里。

本节拿第五章介绍过的开源通用 Agent OpenClaw 当例子，再结合头部 Coding Agent 产品公开的技术分析与从业者分享，看一套值得借鉴的内部评估体系。它做的事情说穿了，就是把 ML 研究里的实验方法论系统性地嵌入产品工程。分工上可以这样记：7.1 到 7.9 是评测者的视角，教你怎么给别人的 Agent 打分；7.10 是产品工程团队的视角，看最好的产品怎么给自己打分。后面六个小节对应六件具体的工程设施：消融开关、AB 测试流程、特性开关、提示词快照、隐私类型，以及思维方式的转变。

### 7.10.1 消融基础设施：理解每个特性的真实贡献

ML 研究者用消融实验（Ablation Study）用了很久，做法是逐一「摘除」某个组件，看整体性能掉多少，由此判断哪些组件真正重要。OpenClaw 把这套方法搬进了产品工程：系统内置一个总开关，可以一次禁用多个主要特性（思考模式、上下文压缩、自动记忆、后台任务等），造出一个「裸模型」基线。有了这个基线，团队就能回答一个关键问题：某个特性是真的改善了用户体验，还是只是感觉有用？

消融如果只在研究阶段做一次就收工，价值有限。做成常规工程实践之后，有两处约束会立刻显出来。

一层是架构约束。消融开关必须在启动路径的极早期注入，要早于任何模块级常量捕获配置值。这句话反过来给出一个结论：消融基础设施得从一开始就设计进系统架构，事后加装已经来不及。

另一层是节奏。定期跑消融实验，比如每次大版本发布之前跑一轮，可以把「特性债务」挖出来，也就是那些曾经有效、但随着模型进化已经不再必要的特性。

对任何在做生产 Agent 的团队，这里的实践建议很直接：每个主要特性都应该可以独立关闭，团队要定期验证每个特性的实际贡献。

消融在产品工程里的价值，用一个问题就能概括：这个功能是真的有用，还是我们觉得它有用？功能上线时通常有理由，可模型升级之后，那个理由可能已经消失。

「必须在启动路径的极早期注入」这条约束信息量不小，它说明实验能力会被架构反过来限制。配置值如果在模块加载时就被常量捕获了（比如模块顶层的 `const ENABLE_MEMORY = config.memory`），之后再想中途关掉它就来不及。这正是把「从一开始就设计进架构」说成硬要求的原因。

「特性债务」这个词值得记住，它和技术债是同构的：功能不是免费的，一个不再必要的特性会持续带来维护成本、延迟、token 成本和认知负担。定期消融等于给功能做体检，把不再产生收益的特性挑出来。

把它和 7.10.2 的 AB 测试放在一起看，分工很清楚。消融回答「这个特性还有没有用」，做的是有/无对比，通常发生在内部；AB 测试回答「这个改动有多好」，多臂，面向真实用户流量。两者互补，消融管要不要留，AB 管怎么调。

产品工程里的消融实验和章首说的消融是同一件事的两处应用：章首把它当成定位 Harness 内部哪个部件重要的手段，把它当成产品特性的常规体检设施。

「裸模型」基线也不等于「关掉全部功能」。这里的措辞是「同时禁用多个主要特性（思考模式、上下文压缩、自动记忆、后台任务等）」，列的是一批主要特性，不必理解成一定关掉所有功能。

### 7.10.2 AB 测试方法论：区分机制与目标

成熟的 Agent 产品会对自己做严格的 AB 测试：把用户随机分成两组，一组跑旧版本，一组跑新版本，用两组的实际数据判断改动是否有效。这里给了一个设计得比较精良的 AB 测试案例，从中可以读出几条方法论原则。

多臂对比比二元更有用。别只摆「有」和「没有」两组，可以设计多个渐进式变体；这里的例子是测提示词约束强度，控制组之外再设三个渐进更严格的实验组，四臂一起跑。价值落在找最优点上：两臂只能回答「A 比 B 好吗」，多臂能画出剂量-效应曲线，约束太松没效果，太紧伤体验，最优点在中间某处。

区分机制指标和目标指标，这是最容易犯的一个错，说白了就是把你正在改变的东西当成了优化目标。这里的例子是测「缩短 Agent 的计划文件长度」：计划长度是机制指标，是你直接动手改的东西，它本身不构成目标，真正的目标可能是降低会话级成本。直觉上计划短就 token 少就成本低，可链路里还夹着一环，计划太短会让执行阶段反复编辑-检查-编辑，总输出量反而增加。机制和目标的因果关系并不显然，所以每次都该自问一句，我改的东西和我关心的东西是不是同一个，不是的话以目标为准。

设置护栏指标。目标指标改善了也不算数，一旦用户满意度下降、操作次数增加或者错误率上升，实验同样应该停下。护栏指标是不能变差的底线，它和目标的方向可能正好相反：这里目标是降成本，护栏是用户满意度不能降。护栏不参与优化，它是停止条件。这套思路和 7.9.4 的复测门槛一致，H5C 的复测里既有目标（保持成功率、把 token 降下来），也有护栏（成功率不能下降、延迟不超过 1.5 倍），作用就是防止按下这个指标、翘起那个指标。

记录基线统计，包括样本量、分布百分位数和相关性分析，这里举的例子是「拒绝率随计划大小单调递增」。这是一条相关性观察，用来解释实验结果的成因，也用来确认实验分组的分布是否正常。没有基线，你甚至说不清「实验组成本降了 8%」是显著还是噪声，这正是 7.7 节讨论的话题。

区分机制和目标的判断标准只有一条：它是不是你直接改的那个东西。计划长度是你直接改的，算机制；会话级成本是你关心的，算目标。

### 7.10.3 双层特性开关系统

Agent 产品要从第一天就把特性开关（Feature Flag）基础设施设计进去。特性开关是一个可以远程控制的开关，决定某项功能对用户开着还是关着，不需要重新部署代码。它同时服务三件事：实验、渐进发布、紧急熔断。

编译时开关在构建阶段就把相关代码从产物里物理移除。内部专用的特性在外部构建里根本不存在，即使逆向工程也发现不了被移除的功能。它同时也是最干净的消融机制：关掉一个特性，产物里就没有这段代码，运行时不存在一段被跳过的分支。

运行时开关的配置由服务端下发，并在本地磁盘缓存一份。设计取舍写得很明确，宁可读到稍旧的缓存配置，也不能让 Agent 因为等网络请求而阻塞启动。分组决策交给实验平台（比如 GrowthBook）完成，用来分配 AB 测试组。还有个容易忽略的细节：每个特性的曝光事件在每个会话里最多记录一次，避免重复记录污染实验数据。

对 Agent 开发者来说，特性开关不只是一件顺手用的调试工具，它是一等架构组件。

两层开关的分工看一张表最清楚（表是我按资料整理的）：

| | 编译时开关 | 运行时开关 |
| --- | --- | --- |
| 生效时机 | 构建阶段 | 运行时 |
| 实现方式 | 代码从产物中物理移除 | 服务端下发配置 + 本地磁盘缓存 |
| 特点 | 逆向工程也发现不了；消融最干净 | 可远程控制，无需重新部署 |
| 用于 | 内部专用特性、彻底移除的功能 | 实验分组、渐进发布、紧急熔断 |

三个目的值得分开理解。实验是把用户分到不同组，配合 GrowthBook 之类的平台做分组决策；渐进发布是先给一小部分用户开启，盯住指标再逐步扩量；紧急熔断是出问题时远程关掉，不用等发版。

「宁可读取到稍旧的缓存配置，也不能阻塞启动」是一条明确的取舍，可用性优先于一致性。对 Agent 尤其重要，启动时要等网络拿配置的话，网络一抖就变成 Agent 起不来。先带着旧配置跑起来，比卡死强。

「每个特性的曝光事件在每个会话中最多记录一次」这条细节容易被忽视，它直接关系实验数据质量。同一个会话里反复记曝光，计数就被放大，分母失真会让结论完全错误。

「一等架构组件」这个定性，和 7.10.5 的类型系统思路一致：把评估和实验能力算进架构，别当成开发调试时外挂上去的东西。

特性开关不等于配置项。这里强调它「远程控制、无需重新部署」，而且要服务实验与熔断；普通配置项通常不具备分组实验和熔断能力。

编译时开关和「干净的消融」的关系，在于代码物理上不存在。关掉一个特性时，产物里少的是那段代码本身，运行时并没有多一次判断。

### 7.10.4 提示词敏感性评估

系统提示是 Agent 行为的核心「代码」，可它往往拿不到普通代码那样的版本控制和回归测试待遇。

OpenClaw 的做法是提供一个专用工具，能在指定的 git 版本上提取完整渲染后的系统提示，包含所有动态条件展开后的最终文本。有了它，团队就能精确回答两个问题：哪次提交改变了提示词，以及对评估集的影响是什么。

对任何 Agent 团队，这里给了三条实践建议。系统提示应该能够确定性地渲染，也就是给定相同的配置输入，永远产生相同的输出；要建立提示词的版本化快照机制；每次提示词变更都应该在评估集上跑回归测试，就像代码变更要跑 CI 一样。

「系统提示是核心代码」这个比喻在这一节被兑现成了工程实践：既然它是代码，它就要有版本、要能 diff、要能跑 CI。三条建议连起来是一条流水线。确定性渲染是前提，同样的配置如果跑出不同的提示词，任何对比都没有意义；版本化快照是存档，让「哪次提交改了什么」可查；变更跑回归测试是门禁，把提示词变更纳入 CI。

「包含所有动态条件展开后的最终文本」这点关键。真实的系统提示往往是模板，按平台、按用户等级、按功能开关拼接出来，只看模板源码看不出最终发给模型的是什么。工具要提取的是渲染后的完整提示，模板本身不够。

这条实践和 7.10.3 的特性开关天生配合：开关一动，渲染后的提示就变了。缺了「渲染后快照 + 回归测试」，一次实验组的开关调整就可能悄悄改掉所有人的提示词，还没人发现。

提示词版本管理不等于用 git 管理模板文件，模板文件的 diff 不等于最终提示词的 diff，中间隔着一层动态展开。这里要求的工具提取的是完整渲染后的系统提示。另外，「确定性渲染」是要求，不是现状，用的是「应该能够确定性地渲染」，说明这是一个需要刻意达成的工程目标。

### 7.10.5 以隐私感知分析为评估基础

评估依赖好的数据，而 Agent 产品处理的又往往是用户的敏感内容。OpenClaw 用类型系统来解决这个矛盾：分析接口只接受经过特殊类型包装的值，类型名本身就是审计线索，它明确表明「我已验证这不是代码或文件路径」。这么做的效果，是把隐私约束从文档化的规范变成了编译时强制执行的类型检查。

核心原则是从一开始就把隐私约束设计进去，而非事后加装。这里还有两句判断：如果你的分析系统无法安全地收集数据，你就无法有效地评估；隐私和评估并不对立，隐私感知的设计迫使你认真思考真正需要度量什么，这反而会催生更精准的评估指标。

这条论证链是一步步推出来的。评估需要数据；Agent 处理的是敏感内容；于是常见做法变成「先收集，再脱敏」，可这本身就带风险；更好的做法是用类型系统在编译期拦住不该被采集的值；结果就是隐私约束从文档里的规范升级成编译时的强制检查。

「类型名本身就是审计线索」这句很精妙。一个类型为 `VerifiedNonCodeString` 的变量，代码评审时一眼就能看出这个值经过检查、不是代码或路径。类型标注同时承担了机器检查和人工可审计两个功能。

约束不全是负担，这一点值得记住。当你不能什么都收集的时候，你会被迫想清楚到底要测什么，指标通常因此更精确，而不是更粗糙。和 7.8 节的回流闭环连起来看，那边「脱敏处理（去除用户隐私、密钥等敏感字段）」是运行时的动作，这一节的类型系统把约束前移到了写代码的时候，两者互补。

「脱敏」和「隐私类型」不是一回事。脱敏是数据已经收上来之后的处理；隐私类型是在编译期阻止不该被收集的值进入分析接口。这里明说「从一开始就把隐私约束设计进去，而非事后加装」。隐私和评估也不对立，这里的立场是「隐私和评估并不对立」，隐私约束反而可能催生更精准的指标。

### 7.10.6 从外部到内部：评估思维的转变

这一节的核心信息可以压成一句话：前面几节教的是怎么从外部评估 Agent，这里揭示的是最好的 Agent 产品怎么从内部评估自己。外部评估告诉你「Agent 有多好」，内部评估基础设施告诉你「哪项改动让它变好了」。

五个组件各管一段：消融实验发现哪些特性真正重要；AB 测试量化每项改动的影响；特性开关提供实验和回滚的基础设施；提示词敏感性评估把系统提示纳入 CI 体系；隐私感知分析保证数据收集的合规性。这五个组件合起来构成评估驱动的产品工程，评估被嵌进每一次产品决策，而不是隔一段时间做一次。

把它们和各自回答的问题对应起来最清楚（表是我按资料整理的）：

| 组件 | 回答的问题 |
| --- | --- |
| 消融实验 | 哪些特性真正重要？ |
| AB 测试 | 每项改动的影响有多大？ |
| 特性开关 | 怎么安全地做实验和回滚？ |
| 提示词敏感性评估 | 这次提示词改动带来了什么变化？ |
| 隐私感知分析 | 数据收集合规吗？ |

「外部评估」和「内部评估」的差别可以这样说：外部评估给的是一份体检报告，内部评估给的是病因分析能力。前者是某个时间点上的一个数字，后者是随时可以问「如果我改这里会怎样」的能力。

把评估嵌进每一次产品决策，这个落点与 7.9.4 那句「一轮证据只支持与它规模相称的下一步」并不冲突：内部评估基础设施的意义，正是让每轮证据来得够快、够便宜，才撑得起高频决策。

内部评估里的消融实验和 AB 测试回答的问题不同：消融问「这个特性还有用吗」，做有/无对比；AB 问「这个改动有多好」，多臂，面向真实流量。

## 7.11 仿真环境：从评估到后训练的桥梁

评估走到终点并不是为了拿到一个分数，分数只是中间产物。本章前面已经给出两条改进路径：调整 Harness（从 Benchmark 报告走到系统改进），以及把评估嵌进产品工程（内部评估基础设施）。还有一条更彻底的路径是训练。当目标从「评估已有能力」扩到「培养新能力」，尤其是第八章会展开的后训练技术，评估环境就得演化成另一种东西：一个能让 Agent 反复练习、自动打分的虚拟操场，也就是**仿真环境**。

它跟评估环境的差别集中在三点：交互频率高得多（数百万次对数千次）、需要随机化（否则模型会记住特定配置）、必须提供即时反馈。

按应用领域分，仿真环境有两大类，数字环境对应信息处理任务，具身环境对应物理世界的感知与操作。

这座桥的两端接得很顺：评估侧攒下来的资产几乎能无缝转成训练信号。一套定义清晰的 Rubric 或验证器，是一个可验证奖励（RLVR，Reinforcement Learning with Verifiable Rewards）的奖励函数，验证脚本直接就是奖励脚本。测试是否通过、状态是否达标，放在评估里是判据，放到强化学习里就是回报。

麻烦在于训练会提出评估阶段不必操心的新要求。一是**可靠的 reset 语义**：训练要跑数百万个 episode（一个 episode 是一次从初始状态到任务结束的完整交互回合），每个 episode 都必须把环境重置到一个确定、干净的初始状态，否则梯度信号会被上一轮的残留状态污染。二是远高于评估的吞吐：评估几千次就够出结论，训练得在可接受的墙钟时间内喂给模型上百万次交互，环境的并行度和单实例开销直接决定训练这件事做不做得成。奖励函数化的验证器、面向训练的 reset 与吞吐，这两条都留到第八章展开。

具身环境这一侧，RoboTwin2 基于物理引擎构建双臂操作任务，随机化物体的位置、朝向和外观来提升泛化能力。观测空间包括多相机视觉和关节状态，靠动作分块（Action Chunking，模型一次规划多个连续动作）实现实时控制，细节在第六章。OSWorld 通过虚拟机快照实现可重置性，AndroidWorld 聚焦移动应用自动化。两类环境都同样需要第四章讨论的隔离执行环境与虚拟身份机制，也就是 VM/容器隔离、住宅代理、Human-in-the-Loop 认证、共享文件系统，这里不再重复。

「仿真环境 = 评估环境 + 高频 + 随机化 + 即时反馈」这个等式挺好用，规模从几千次跳到数百万次，会连带改掉很多设计。评估环境里人工重置可以接受，仿真环境必须自动、可靠、快速；评估环境里配置固定没关系，仿真环境必须随机化，不然模型会背下那套配置；评估环境里延迟高一点无所谓，仿真环境必须即时反馈，否则训练循环根本转不动。

RLVR 这个概念的桥梁作用值得讲透（这层理解是笔记补的）：你为评估写的验证器，几乎可以原样当作强化学习的奖励函数。省掉「再写一套奖励」的成本只是顺手的好处，真正的价值是让训练的目标与评估的标准保持一致。这两者一旦分家，就会出现模型训练得分很高、评估表现很差的结果。

回到图 7-9，信息量最大的其实是「真实世界：完美保真度、不可重置」这一格。它把保真度与可训练性的矛盾摆到了谱的最右边：真实世界不可重置，所以没法拿它跑数百万次训练，仿真环境的存在理由就在这里。

AWorld 那个 14.6 倍可以复算一遍：$7695\div525=14.657\approx14.6$（这个数是我按这两个秒数算的，本节只给了倍率结论）。加速来自分布式加无状态设计，每个实例完全独立，想并行多少都行。无状态同时也是「可重置」的另一种实现方式，每个实例都是全新的，天然不需要清理残留状态。

动作分块值得跨章理解：模型一次生成 25 个连续动作，而不是一步一动。收益是降低推理频率、撑住实时控制，代价是一次想错就是连续 25 步一起错，错误被放大。这一点上回指第六章，可以顺着这条线把两章连起来看。

还有两个容易混的地方。评估环境与仿真环境对「重置」的要求强度并不一样：前者只要每次运行前回到同一起跑线即可，后者要求每个 episode 都重置到确定、干净的状态，否则梯度信号被污染，性质上是从「可比较」升级到了「可训练」。另外，AWorld 的「可重放、可审计」是评估侧的性质，别拿它当训练就绪的证明，训练还额外要吞吐和并行度。

> 仿真环境是「评估环境 + 数百万次规模 + 随机化 + 即时反馈」；验证器可以直接当奖励函数（RLVR），但训练额外要求可靠的 reset 与高吞吐。

## 7.11.1 保真度权衡与领域随机化

高保真环境更容易迁移到真实世界，代价是计算开销大。保真度还有第二个维度，就是随机化程度：适度随机化能提升泛化能力，随机化过了头，任务本身会变得过于困难。

**领域随机化**（Domain Randomization）是缩小仿真与现实差距（sim-to-real gap）的关键技术，做法是在物理参数、视觉外观、传感器噪声这些地方引入大范围随机变化。这里的比喻很好懂：好比在各种光照和角度下都练习过抓取，到了真实环境也不会因为光线变化就失手。

数字环境里的 sim-to-real 表现不一样，它落在界面渲染、响应时间的差异上，靠引入延迟和失败的随机化来缓解。

保真度的第二层含义很容易漏掉，它不只指物理精度，还包括随机化程度。把三条放在一起看就是一个三角权衡（这三条都出自这里，整理是笔记做的）：保真度上去，迁移性变好但计算开销跟着涨；随机化适度提高，泛化能力变好，因为模型见过各种光照和角度；随机化过度，任务过于困难，曲线会掉回来。随机化程度本身就是个要调的超参数。

「在各种光照和角度下都练习过抓取」这个比喻抓住的是领域随机化的本质：它不追求仿真得像，而追求训练时见过足够多的变化，于是对真实世界的变化免疫。这条路绕开了高保真那条昂贵的路线。

数字环境那条说法很实用。数字环境没有物理，但有延迟和失败，所以它的领域随机化就体现为随机注入延迟、随机注入工具失败。这正好接上 7.5.3 节讲的「执行异常应加入截断、超时和工具故障的恢复场景」：评估侧的异常场景设计，换到训练侧就是域随机化的一种形式。

两个容易混的点。保真度（fidelity）与随机化程度（randomization）是两个维度，说「保真度的另一维度是随机化程度」，所以高保真不等于高随机化，既可以有保真度很高但完全固定的环境，也可以有低保真而参数随机变化很大的环境。领域随机化也不是越随机越好，写了「过度随机化则会让任务变得过于困难」。

> 高保真能迁移但贵，随机化能泛化但过度就变难；数字环境的「sim-to-real」用延迟与失败的随机化来弥合。

## 7.12 本章小结

本章围绕一个问题转：如何判断 Agent 变好了还是变差了。这条链路由四个环节构成，先厘清成功的定义（Pass@k、Best@k 与 Pass consecutive@k 的口径差异），再确定任务从何而来（公开基准、自建业务集与生产轨迹回流三个来源），随后选定验证方式（从确定性验证器到检查项清单、Rubric 加 LLM 评判，直至配对比较），最后把分数转化为决策（统计显著性、失败归因、回归任务与模型选型）。每个环节都会影响结论的可信度。

放回全书结构，本章建的是第一章发现循环中的证据段：失败归因决定了后续的提案有没有可依之据。

用户记忆那一节其实是一个更大的结论的案例。轨迹前缀边界评估说明，获得一条信息和正确地将它用于当前决策是两种不同的能力。前者是上下文里有没有正确内容，后者是 Agent 下一步会不会照着做。端到端回归的任务是保证基本任务不退化，trajectory prefix 边界集则直接去查作用域判断、当前指令覆盖、澄清和危险动作前确认这几件事，用户记忆只是这套通用方法应用到的一个场景。

生产级 Agent 的评估因此是一套从真实问题案例中持续生成回归任务和边界任务的验证系统，不是偶尔做一次的考试。背后的方法论是观察→假设→实验→验证→新认识→新假设，它让 Agent 工程从经验驱动的「炼金术」转向数据驱动的科学工程。

本章描述的评估体系构成一个闭环：评估环境提供自动化的测试基础设施，评估数据集定义端到端任务和 trajectory prefix 边界，自动化评估方法（确定性验证器、LLM-as-a-Judge 与 Rubric）对表现打分并生成失败归因，Benchmark 与问题案例分析指出改进方向，系统改进修掉问题，然后更新评估环境和数据集，进入下一轮。这套体系不只服务当前系统的优化，也是后两章的地基：第八章把评估环境和数据转成模型后训练的输入，第九章把生产轨迹的多维评价转成知识、指令、程序的更新。

小结里最有分量的一句是「本章建的是第一章发现循环中的证据段」。它把本章钉回全书的论证链：没有评估，失败归因就没有依据，改进提案就成了猜。

三个闭环可以放在一起对比（整理是笔记做的，条目都来自资料）。四个环节指的是成功的定义 → 任务来源 → 验证方式 → 结果的运用，对应图 7-1，讲的是评估体系怎么搭。系统改进闭环是评估环境 → 数据集 → 自动化评估方法 → 揭示改进方向 → 系统改进 → 更新评估环境和数据集，讲的是改进怎么滚动。科学方法论循环是观察 → 假设 → 实验 → 验证 → 新认识 → 新假设，讲的是工程怎么做成科学。三者的粒度明显不同。

最后一处易混：Pass consecutive@k 与 Pass^k 是同一个东西的两种写法。小结里用前一种，7.2.2 节用后一种，这里也说它读作 Pass consecutive k。

> 评估体系四环节（定义成功、任务来源、验证方式、结果运用）每环都影响结论可信度；本章是全书的「证据段」。

## 思考题

（此处先有一个「深度思考」的栏目标记，紧接着是「思考题」；下面 9 题原样列出，每题后附补充的**思路提示**，不是标准答案。）

**1. ★★** LLM-as-a-Judge 使用语言模型评估语言模型的输出。这种「自我评估」是否存在系统性盲区——比如模型可能一致地给某种风格的回答打高分，而这种偏好与人类评判不一致？如何检测和校正这种偏差？

> 思路提示（补充）：可以从 7.5.1 节的「长度偏差」入手，它就是一个已被识别的系统性盲区，而这里给的检测手段是「定期审计评分与回答长度的相关性」。推广开来就是：先找出一个可疑的风格变量（长度、语气、Markdown 格式、堆砌术语），再审计它与分数的相关性。校正方向可以想两条：改 Rubric（显式惩罚该风格）、换评判者（多源异构评判，因为不同家族的偏见往往是正交的）。

**2. ★★★** 评估数据集的「防泄漏」设计至关重要。但在开源生态中，benchmark 数据一旦公开，很快就会被纳入训练数据。这场「猫鼠游戏」有终局吗？设计一种从根本上抵抗数据泄漏的评估方法。

> 思路提示（补充）：7.4.4 节给了三种手段，多源组合+专有附件（GAIA）、参数化动态实例化（AndroidWorld）、金丝雀标识符检测（Terminal-Bench），它们的思路分别是「提高获取门槛」「让记忆失效」「留下痕迹」。要「从根本上抵抗」，可以想的方向是让评估集**不可预先枚举**：参数化生成 + 私有附件 + 每次评估重新采样。也可以考虑把「泄漏检测」做成常设机制（金丝雀思路的强化版）。

**3. ★★** Scale AI 的四准则（基于专家指导、全面覆盖、按重要性加权、评价标准自包含）旨在消除评估的主观性。但某些任务维度（如「回答是否有帮助」「语气是否恰当」）天然具有主观性。如何为这些主观维度设计可靠的 Rubric？

> 思路提示（补充）：四准则里最有用的判断是第 4 条「评价标准自包含」，把「有帮助」这种抽象描述改写成可验证的行为（例如「指出了用户没问到但会影响决策的一个风险」）。另外可以借 7.5.1 节的「边界案例」机制：为模糊情况提供具体示例，把主观判断**转化为判例**，这也正是的「最终从抽象准则演化为详尽的判例集」。

**4. ★★** τ-bench 通过模拟真实用户行为来评估 Agent。但模拟用户本身也是一个 LLM——它可能系统性地低估某些边缘场景（如情绪激动、表达不清的用户）。如何验证模拟用户本身的质量？

> 思路提示（补充）：可以从 7.1.1 节 `task_instructions` 的三类约束（情绪设定、验收口径、事实锚定）出发，把「模拟用户的质量」拆成可检查的几条：它有没有遵守事实锚定、有没有在压力下仍然坚持正确的验收口径、它的耐心上限是否合理。另一条思路是拿真实生产轨迹中的人类回应作为参照集，比对模拟用户的行为分布。

**5. ★★** 配对比较（Bradley-Terry 模型）假设偏好是传递的（如果 A > B 且 B > C，则 A > C）。但人类偏好经常违反传递性。在 Agent 评估中，非传递偏好可能出现在哪些场景？这如何影响排名的可靠性？

> 思路提示（补充）：结合 7.5.4 节的局限（排名取决于用户问了什么）想：当两个模型各自擅长的任务族不同时，偏好在不同任务子集上可能循环。「排名」本质是把多维能力压成一维，一旦能力维度之间不可比，传递性就危险了。可以从「分组排名 + 两两胜率矩阵」的角度考虑替代方案（实验 7-8 要求计算胜率矩阵，正是一种更细粒度的呈现）。

**6. ★★** 本章区分了 Pass@k 的能力上限与 Pass consecutive@k 的业务可靠性。对于一个单次成功率只有 60% 的 Agent，怎样结合任务的失败成本、重试成本和副作用，决定应该报告哪个指标、取多大的 $k$？

> 思路提示（补充）：7.2.2 节已经给了三个决策变量：失败成本（低则看 Pass@k）、副作用（有副作用就不能重试，必须在沙盒或可回滚环境中采样）、以及报告的 $k$ 口径（同一任务的独立采样 vs 生产流水线连续 $k$ 个任务）。可以把「重试是否安全」当成第一道分水岭：安全则可用 Pass@k 叙事，不安全则必须报 Pass^k。

**7. ★★** 本章提出「观察→假设→实验→验证」的科学方法。但在实践中，Agent 的行为空间巨大，验证一个假设可能需要数百次评估运行。如何在有限计算预算下最大化评估的信息量？

> 思路提示（补充）：7.9 节的三轮实验示范了一条路，先用最小子集（4 项任务）做方向性判断，再把资源投给有希望的改动（H5C 才进入完整复测）。另外可以借 7.5.3 节的轨迹前缀回归任务：它比端到端便宜得多，且能隔离单个决策点。还有 7.10.1 节的消融（一次关掉多个特性造出裸模型基线）也是提高信息量/成本比的手段。

**8. ★** AndroidWorld 小实验中，完整元素树把成功率从 25% 提高到 100%，却把 token 用量推到 2.498 倍；精简后成功率不变，token 降到对照组的 0.506 倍。怎样设计一套自动裁剪规则，既删掉无语义的 UI 节点，又不误删对可访问性、状态验证或后续操作有用的信息？

> 思路提示（补充）：这里 H5C 删的是「不可见、没有文字、也不能操作的容器节点」，这三条本身就是一组可自动判定的规则。要把规则做得更稳，可以再想两层：给「可访问性」相关信息（如 contentDescription）白名单，以及对「状态验证」相关的节点（勾选、开关状态文本）做保护。同时注意 7.5.3 节的思路：裁剪规则本身也要有回归任务（轨迹前缀）来防止误删。

**9. ★★** τ-bench 的用户模拟采用了「渐进式信息透露」——不一次性提供所有信息，而是根据 Agent 的提问逐步透露。这种设计如何影响评估结果？如果模拟用户的信息透露策略与真实用户差异较大，评估结论还可靠吗？

> 思路提示（补充）：7.1.1 节说明了它的实现方式（把 `known_info` 建模为独立字段）与目的（把「需求澄清」纳入考核）。要判断可靠性，可以反问：真实用户的初始表述是否也像模型那样「只说一句我上不了网」？如果模拟用户比真实用户更配合、更及时地提供关键信息，Agent 在评估中会显得比实际更能干；反之则更差。这与第 4 题的「验证模拟用户质量」是同一个问题的两面。
