# 第1章 AI Agent 入门

> 本笔记对应原书《深入理解AI Agent：设计原理与工程实践》第1章 AI Agent 入门，原书印刷页码 7–29 页（PDF 第 15–37 页）。
> 笔记结构：先给“本章地图”，再逐节精读，最后是术语速查、原文小结与自测题。

## 本章地图

- **这一章要解决什么问题**：回答两个问题。第一，“Agent 是什么”——用一个能落地的最小工程公式 `Agent = LLM + 上下文 + 工具` 把 Agent 拆开，并划清 Agent 与 Environment（环境）的边界；第二，“Agent 如何在生产环境中可靠运行”——引出 Harness 工程，说明为什么模型之外的约束、验证、纠正才是产品化的胜负手。作者在开篇明确写了本章的定位：**本章是全书的概念地图**，会快速引入 Agent 的核心公式、运行循环、工程框架和设计模式，为后续章节提供统一的术语和参照坐标。因此原书还给了阅读提示：初次阅读不必逐一记住所有概念，先建立整体印象即可，后续每一章都会展开讲解本章提到的某一个方面。
- **它在全书中的位置**：本章是全书第一章，没有上一章。它是“概念地图”，向后提供统一的术语和坐标：第二至六章讨论“构建”（对应 Harness 五要素），第七至九章讨论评估与进化，第十章讨论多 Agent 协作。原书结尾也说明：关于 Agent 概念在强化学习中的学术渊源、以及传统 RL 与现代 LLM Agent 的深入对比，将在第八章系统展开；下一章将深入 Harness 中最核心的组件——上下文工程。作者还专门交代了本章与第 1.2.6 节的关系：**全书的结构骨架只有一个**，就是引言和后记反复使用的 `Agent = LLM + 上下文 + 工具`；`Agent = Model + Harness` 不是与它并列的另一套划分，而是同一事物在生产形态下的展开。
- **小节之间的关系**：1.1 是“Agent 是什么”，按“先具体后抽象”的顺序推进——先讲**工具**（手脚，最具体），再深入**大脑**（LLM）和**眼睛**（上下文），最后用 **ReAct 循环** 把三者串起来（1.1.1 先给出观察空间/动作空间这个接口层视角，1.1.2–1.1.4 依次展开工具、LLM、上下文，1.1.5 讲它们如何协同运转）。1.2 是“Agent 怎么可靠地跑”，先给 `Agent = Model + Harness` 与 Harness 五要素（上下文管理、工具接口、约束、验证、纠正），再展开三个“不属于五要素但绕不开”的决策主题：模型选型、编排模式、护栏与安全性，最后用 1.2.6 把五要素对回全书章节。1.3 一次性命名并定义贯穿全书的五个设计模式。1.4 收束全章。**思考题**（共 10 题，标注了 ★/★★/★★★ 难度）用于引导深入思考，原书明确声明不设标准答案。
- **读完你应该能做到**：
  1. 用自己的话解释 `Agent = LLM + 上下文 + 工具`，说清为什么这个公式不包含 Environment，以及为什么加号表示工程组件的组合而不是强化学习中的形式化定义；
  2. 画/讲出 Agent 与 Environment 的闭环交互，以及 Agent 内部的 Model–Harness 结构；
  3. 说清观察空间与动作空间为什么是“底层模型固定时最主要的系统工程杠杆”；
  4. 完整复述 ReAct 循环，并写出 `上下文 = 静态前缀 + 轨迹` 这个分解；
  5. 理解 Harness 五要素的分工与相互关系，知道五要素分别对应第二至六章的哪些章节（第二、三、四、五、六章各承担了什么）；
  6. 判断一个场景该用工作流还是自主 Agent，并说清两类护栏（三层防线 + 人工干预）各自挡什么。

## 1.1 现代Agent = LLM + 上下文+ 工具

**原文要点**

- 现代 Agent 的**最小工程实现**可以用一个简洁的公式表达：`Agent = LLM（大语言模型，Large Language Model）+ 上下文 + 工具`。原文对公式里的加号做了两点限定：一是“加号表示工程组件的组合，而不是强化学习中的形式化定义”；二是“这个公式只描述 Agent **边界之内**的实现，**不包含** Agent 与之交互的 Environment（环境）”。
- 公式中每个词都要做“广义但边界清楚”的理解：
  - **LLM 是 Agent 的大脑**：它不只是一组模型参数，而是 Agent 的整个决策内核——理解意图、思考规划、做出判断。就像人类大脑不只是神经元的集合，还包括通过经验塑造的思维方式，LLM 的能力也来自两部分：**预训练**所积累的世界知识与语言能力，以及**后训练**所固化的决策策略。后者的具体技术（如监督微调与强化学习）将在第八章展开。
  - **上下文是 Agent 的眼睛**：它不只是输入给模型的那段文本，而是 Agent 在**每个决策点**收到并保留的信息表示——来自环境的观察、用户记忆、领域知识、自身状态和任务进展。
  - **工具是 Agent 的手脚**：这里的“工具”指 Agent 用来**感知或改变外部世界**的接口，包括工具定义、调用协议和适配器——从预定义的工具调用到动态生成代码，从委托子 Agent 协作到主动与用户沟通。
- 换一种更直观的说法：`Agent = 大脑 + 眼睛 + 手脚`。大脑负责思考和决策，眼睛接收环境提供的观察，手脚将决策转化为作用于环境的行动。
- 在经典的**强化学习和控制论视角**下，Agent 与 Environment 是**闭环交互的两方，而不是彼此的组成部分**。环境不断向 Agent 返回当前观察，Agent 根据已有上下文选择下一步行动；行动改变环境状态，新的状态再产生下一次观察，循环由此继续。原文称这是“理解所有 Agent 交互的最小结构”。
- **图 1-1 同时给出了两个抽象层次**（原文原话）：
  - **外层**是 Agent 与 Environment 的交互关系：环境包含文件、数据库、网页、用户、其他 Agent 以及物理或仿真世界，Agent 只能通过观察和行动接口与它交互。
  - **内层**是 Agent 的 **Model–Harness 结构**：Model 负责策略决策；Harness 是 Agent 边界内环绕模型的运行与治理层，负责构造上下文、暴露工具接口、维护循环和状态，并实施权限、验证与纠正。Harness 可以创建、隔离或代理一个环境，**却不因此包含环境自身的状态与转移规律**。
- 本节开头的工程公式可以据此重新展开：**LLM 对应 Model，“上下文 + 工具”构成最小 Harness**；生产系统还会在 Harness 中加入**约束、验证和纠正**。原文强调：“后文所有架构都遵循这条边界。”
- 这三个工程组件可以映射到 RL（强化学习，详见第八章）的**策略与交互接口**，但**不是严格的一一等同关系**：上下文是具体观察和历史在 Agent 内部的表示，**并不等于整个观察空间**；工具则定义 Agent 可使用的观察与行动接口，**工具背后的对象仍属于环境**。
- 原书用一张表给出“直觉理解—实现组件—学术概念”的三列对应（见下表）。

> 图 1-1（原文插图）：这张图把两层抽象画在同一幅图里。**外层**是一个闭环：左侧是标记为“Agent（智能体）”的大框，右侧是标记为“Environment（环境）”的框；环境框里列出了它包含的东西——“状态与转移规律”“当前状态”“执行行动后产生新状态”，以及具体的载体“文件系统 · 数据库 / 网页 · API · 应用程序 / 用户 · 其他 Agent / 仿真或物理世界”。Agent 框与 Environment 框之间有两条方向相反的箭头：Environment 指向 Agent 的那条标注为“**观察**”，Agent 指向 Environment 的那条标注为“**行动**”，构成“观察 → 决策 → 行动 → 新状态 → 新观察”的循环。**内层**是 Agent 框内部的三段结构：上方是“Harness（模型运行与交互层）”，框内注明其职责为“循环 · 状态管理 · 权限 · 验证 · 纠正”；中部是“上下文”，括注“观察 · 历史 · 记忆 · 任务状态”；下部是“Model”，括注“理解 · 推理 · 选择下一步行动”；最下面是“工具与动作接口”。也就是说：Environment 只通过观察/行动两条边跟 Agent 打交道，而 Agent 内部再分成 Model（做决策）与 Harness（构造上下文、暴露工具、跑循环、做治理）两半。注意图中 Harness 被画在 Agent 边界**之内**、Environment 被画在边界**之外**，这正是原书反复强调的边界。

**1.1 小节内的对应表**（表格按原文语义还原）

| 直觉理解 | 实现组件 | 学术概念 | 含义 |
| --- | --- | --- | --- |
| 大脑 | LLM | 策略（Policy） | Agent 决定“下一步做什么”的决策逻辑——面对当前看到的信息，从所有可选行动中挑出最合适的一个 |
| 眼睛 | 上下文构造 | 观察与历史 | 将环境返回的观察与已有历史组织成当前决策所需的信息 |
| 手脚 | 工具与适配器 | 观察/行动接口 | 规定 Agent 可以读取哪些观察、发出哪些行动，以及接口采用什么格式 |

**辅导讲解**

- **为什么公式里没有 Environment？** 这是初学者最容易忽略、也最容易被考试/面试抓住的一点。如果写成 `Agent = LLM + 上下文 + 工具 + 环境`，那这句话就变成了同义反复——因为“环境”根本不归 Agent 所有，Agent 既不能构造它也不能修改它，只能观察它、对它施加行动。原书的说法是 Agent 与 Environment 是“闭环交互的两方”。你可以这样理解：Agent 是你写的程序，Environment 是程序外面的世界（文件系统、数据库、网页、用户、传感器……）。你的程序可以定义“我怎么看世界”（观察通道）和“我怎么动手”（动作接口），但你不能在代码里“定义”世界本身。所以公式只列 Agent 边界之内的三样东西。
- **“加号”到底是什么意思？** 原文特意澄清“加号表示工程组件的组合，而不是强化学习中的形式化定义”。原因是：在 RL 里，“Agent”是一个被精确定义过的概念（一个策略函数 + 一套交互协议），而 LLM Agent 的 `LLM + 上下文 + 工具` 只是工程上的“三块拼起来”。作者不希望读者把它当成一个数学定义去推导。读懂这个限定，后面看到 `Agent = Model + Harness` 时就不会困惑“怎么又来一个公式”——它同样是工程视角的展开，不是另一套理论。
- **从“三大组件”到“Model–Harness 两分”这条思路链**：先有 `Agent = LLM + 上下文 + 工具`，然后图 1-1 指出“上下文 + 工具”总是在**同一侧**（都在 Agent 边界内、都围绕模型服务），于是把它们打包成 Harness，得到 `LLM → Model`、`上下文 + 工具 → 最小 Harness`。这一步打包的收益是：**“围绕模型的那层工程外壳”从此有了名字**，可以被单独讨论、单独优化。第 1.2 节整节就在讲它，第 1.2.6 节再把 Harness 拆细了跟章节对上。
- **脑/眼/手这个类比的边界**：类比好用，但别推过头。“眼睛”不是相机——上下文不等于“屏幕上的一切”；原文明确说上下文“**并不等于整个观察空间**”。“手脚”也不是末端执行器——按原书的说法，工具定义的是**观察与行动接口**，工具背后的对象（那个真实的数据库、那个真人用户）仍然属于环境。所以准确的说法是：**上下文和工具是接口层，不是被接口连接的东西**。这一点在后面 1.1.1 节会变成一条核心论点。
- **工程上的用法**：这三个组件正好对应三条可独立优化的杠杆——换更强的模型、把信息更好地组织进上下文、给模型更多/更好的工具。本章 1.1.1 节说得很直接：在**底层模型固定**时，最有效的系统工程手段往往就是后两条。这给排优先级提供了依据：如果预算只能动一项，先动最有瓶颈的那一项，而不是本能地“换模型”。

**易混点**

- **“上下文” vs “上下文窗口”**：上下文是“Agent 在每个决策点能看到的全部信息”，是一个**信息集合**；上下文窗口是模型/API 层面能容纳这段信息的**容量上限**（原书在实验 1-2 里提到 Kimi K3 拥有“100 万 token 的上下文窗口”）。前者讲内容，后者讲容量。
- **“工具” vs “工具背后的对象”**：工具是接口（名称、描述、参数格式、调用协议、适配器）；被工具操作的东西（数据库、网页、用户）属于 Environment。原文用一句“工具背后的对象仍属于环境”划开了这条线。
- **`Agent = LLM + 上下文 + 工具` vs `Agent = Model + Harness`**：不是两套并列的划分。前者是全书从头到尾的结构骨架，后者是**同一事物在生产形态下的展开**，“上下文 + 工具”被细分成上下文管理、工具接口、约束、验证、纠正五项职责。记住：**只有一个骨架，Model + Harness 只是它在“构建”部分内部的一个观察视角**。
- **RL 的 Agent vs 本书的 Agent**：可以映射（大脑↔策略、眼睛↔观察与历史、手脚↔观察/行动接口），但**不是严格的一一等同**。原书反对把二者画等号。

**一句话记住**

> Agent 边界之内只有三样东西——大脑（LLM）、眼睛（上下文）、手脚（工具）；环境在边界之外，只通过“观察”和“行动”两条边进出。

### 1.1.1 观察空间与动作空间：模型与世界的接口

**原文要点**

- **观察通道与动作接口共同构成了 Agent 与外部环境之间的边界。** Harness 做两次转换：把环境返回的**观察**转换为模型能够处理的**上下文**；再把模型选择的**行动**转换为对环境的**工具调用**。
- 原文给出两条“不存在”的判据：
  - **没有通过观察通道进入上下文的信息，对模型来说就像不存在；**
  - **没有被动作接口允许的操作，模型即使知道该怎么做，也只能停留在文字建议上。**
- 由此推出本节的核心论断：**在底层模型固定时，提升 Agent 任务表现最主要的系统工程手段，往往就是重新定义或扩展观察空间与动作空间。** 用本书的术语说，就是**扩展上下文和工具**。原文进一步说：“许多看似需要‘更聪明模型’的问题，其实只是接口问题：把任务所需的数据纳入上下文，或把完成任务所需的操作封装成工具，原本不可解的任务就可能变得可解。”
- **案例一：Manus——合并原本分离的空间。** 在 Manus 出现之前，生产级 Agent 大多沿着三条相对独立的路线发展：**Deep Research（深度调研）、Coding（代码生成）、Computer Use（电脑操控）**。Manus 的突破在于“率先把三者放进同一个有广泛影响力的生产级 Agent”：**虚拟浏览器扩大了观察空间；文件系统、代码执行与命令行执行扩大了动作空间**。原文的判断是：它**没有仅靠替换一个更强的模型**来成为通用 Agent，而是**取三类 Agent 观察空间与动作空间的并集**，使同一个 Agent 能跨越原有产品边界完成任务。
- **案例二：OpenClaw——把接口延伸到用户的数字生活。** 它“又把这两个空间向外推进了一层”：
  - 通过用户已经在使用的 **WhatsApp、Telegram、Slack、Discord、iMessage** 等消息渠道接收任务和返回结果，让 Agent 可以**随时随地**被触达；
  - 同时采用**本地 Gateway**，连接 **Google Drive、Notion** 等云应用以及**本地文件系统**。
  - 结果是：分散在不同账号与设备中的数字文件，都可以在**用户明确授权后**进入同一个 Agent 的观察空间，并被其工具处理。
  - 原文的对比：相较于早期 Manus 以**隔离云端沙盒**为中心、往往需要上传文件或另行配置连接器的形态，**本地优先**的 OpenClaw 跨越了更大的数据边界。
  - 原文补了一句点睛的话：**Manus 后来也加入了 Google Drive 连接器和桌面端本地访问**，这恰好再次说明——**产品能力的演进往往就是观察空间和动作空间的演进。**
- 原文交代了后续的展开顺序：理解这三者（工具、LLM、上下文）的作用及其相互关系，是构建有效 Agent 系统的基础；介绍顺序是**从最具体的手脚（工具）开始**，再逐步深入到大脑（LLM）和眼睛（上下文）。
- 原书随后给出五个真实 Agent 产品在“眼睛/手脚/策略”三个维度上的对照表（见下表），并总结出这些系统的**共同特征**：它们都使用**开放式的动作空间**（不是从有限的几个按钮中选择，而是能生成任意自然语言和代码）；它们都能**内部思考**（在采取行动前先思考和规划）；它们都能**持续交互**（根据环境反馈不断调整策略）。原文的结论是：这些能力正是来自**大脑、眼睛和手脚——即 LLM、上下文和工具——的协同作用**。

**Agent 产品三维度对照表**（表格按原文语义还原）

| Agent 产品 | 眼睛（感知） | 手脚（行动） | 策略 |
| --- | --- | --- | --- |
| Cursor 等 Coding Agent | 需求、读取到的代码片段、目录列表、终端输出 | 开放式（代码搜索、文件读写、执行命令等） | 增量开发：理解需求→搜索相关代码→编辑代码→测试验证→调试修复 |
| Deep Research 等搜索 Agent | 搜索结果、网页内容、论文摘要与引用 | 开放式（搜索查询、网页读取、生成报告等） | 迭代深化：根据已有信息调整搜索方向，逐步综合出完整报告 |
| Browser Use 等电脑操控 Agent | 屏幕截图、DOM 或无障碍树、操作结果 | 开放式（点击、输入、滚动、截图、执行代码等） | 视觉感知+操作：观察屏幕→识别目标元素→执行操作→验证结果 |
| 豆包等手机助手 Agent | 手机截图、App 界面状态、系统反馈 | 开放式（点击、滑动、输入、打开 App 等） | 意图理解+App 操控：理解用户需求→定位目标 App→执行操作→确认完成 |
| Pine AI 等个人办事 Agent | 经授权读取的账户记录、账单结果、服务商资料 | 开放式（打电话、发邮件、填表单、与用户确认） | 多步骤任务执行：收集信息→制定协商策略→联系服务商→谈判→汇报结果 |

> 脚注 1（印刷 p.9）：Manus 的官方资料将其原始 Sandbox 描述为隔离的云端虚拟机；后来发布 Google Drive Connector 时也明确回顾了此前需要在 Drive、桌面与 Manus 之间手工下载和上传文件的割裂流程。2026 年 3 月发布 My Computer 时，Manus 又把“重要工作位于本地而非云端”称为云沙盒的根本局限。OpenClaw 的官方 README 则将其描述为运行在用户自己设备上的本地优先、常驻个人助手，并列出二十余种消息渠道；其工具和插件机制可继续接入云服务与本地能力。参见 <https://manus.im/blog/manus-sandbox>、<https://manus.im/blog/manus-google-drive-connector>、<https://manus.im/blog/manus-my-computer-desktop>、<https://github.com/openclaw/openclaw>、<https://docs.openclaw.ai/tools>。

**辅导讲解**

- **“像不存在”这三个字是整个 1.1.1 节的题眼。** 模型的决策完全基于它当次调用看到的上下文。你没把某个数据放进上下文，模型就只能靠参数里的记忆去猜——它不会知道“我看不到这个数据”，反而很可能给出一个语气笃定的答案（这一点在 1.1.4 节的实验 1-1 里被明确验证）。反过来，动作接口也一样：模型知道该删文件，但你没给它 `delete_file` 工具，它就只能写一句“你可以这样删除……”。所以**接口设计的本质，是在决定模型的能力上限**，而不是在决定模型“能不能表达”。
- **为什么说“很多问题只是接口问题”？** 举个笔记补充的例子（非原文）：一个 Agent 要算“这批订单里有多少是重复下单”。如果它的上下文里只有订单号的文本列表、动作空间里只有“生成一段自然语言”，它会写出一段看着很有道理的估算。把订单表通过一个查询工具接进来（观察空间 +），再给一个代码解释器（动作空间 +），同一个模型就能精确算出来。模型一点没变，任务从“不可解”变成“可解”。这正是原书那句话的字面意思。
- **观察空间 / 动作空间与“上下文 / 工具”的换算关系**：观察空间 ↔ 上下文（进入边界的信息），动作空间 ↔ 工具（能发出的操作）。注意不完全等同：原书在 1.1 里就说过，上下文“并不等于整个观察空间”——上下文是观察在 Agent 内部**被组织后的表示**；同理工具定义的是**接口**，工具背后的对象仍在环境里。
- **Manus 案例的读法：这是“并集”，不是“更强的模型”。** 如果把 Manus 的成功归因于“模型更强”，就会得出错误的产品结论——去卷模型选型。原文特意强调“没有仅靠替换一个更强的模型”，因为它取的是三类 Agent 空间的**并集**。并集带来的效果是**跨越原有产品边界**：Deep Research 的 Agent 到了写代码那一步就停下，Coding Agent 到了要上网查资料那一步就停下，而并集 Agent 可以一路走到底。这也是为什么原书后面反复说“通用性很大程度上来自接口边界的扩大”（见 1.4 本章小结）。
- **OpenClaw 案例的读法：边界向外推一层，触达方式和数据边界同时扩大。** 这里有两件独立的事，别混：一是**触达渠道**（WhatsApp/Telegram/Slack/Discord/iMessage，解决“用户在哪里找到 Agent”），二是**数据接入**（本地 Gateway 连 Google Drive、Notion 和本地文件系统，解决“Agent 能看到哪些数据”）。前者属于交互时机（第六章），后者属于观察空间的扩大。原文把“本地优先”当成关键对比点：云端沙盒意味着数据得先上传才能被看见，本地优先则意味着“数据不动、Agent 动”。
- **“Manus 后来也加了 Google Drive 连接器和桌面端本地访问”这个细节为什么值得写进书里？** 因为它是一个**可观察的行业证据**：如果“产品能力 = 观察空间 + 动作空间”这个判断对，那么一个最初以云沙盒为中心的产品，就应该会逐步把边界往用户数据所在地推。原文的措辞是“这恰好再次说明”，即它把该案例当作论据而非趣味轶事。读者读到这里应该意识到：**看一个 Agent 产品的路线图，可以看它在扩哪一侧的空间。**
- **读那张 Agent 产品表的方法**：不要只当清单看，要横向比“眼睛”那一列。五个产品的**手脚**一栏全都写着“开放式”，差异几乎全在**眼睛**和**策略**上：Coding Agent 看代码与终端输出，Browser Use 看截图与 DOM/无障碍树，豆包看手机截图与 App 界面状态，Pine AI 看的是“经授权读取的账户记录、账单结果、服务商资料”。也就是说，这些产品的差异**主要是观察空间和策略的差异**，而“策略”一栏恰恰是“眼睛 + 手脚 + 模型”三者协同出来的行为模式（原文用的词就是“策略”）。另外注意 Pine AI 那一行里的“**经授权**”三个字——原书在这里就埋下了权限/授权是观察空间前提的伏笔，后面 1.2.5 的“故障安全默认值”与此呼应。
- **“开放式动作空间”到底开放在哪？** 原文给的定义很精确：“不是从有限的几个按钮中选择，而是**能生成任意自然语言和代码**”。这解释了为什么 LLM Agent 与传统 GUI 自动化脚本有本质区别：脚本的动作集合是有限的（点击坐标、按键），LLM Agent 的动作集合是**生成式**的——理论上它可以写出一段谁也没预先写过的代码。好处是通用，代价是**出错和攻击面也随之扩大**（1.1.2 节马上就会讲这个话题）。
- **工程上的坑**：扩大观察空间不是免费的。把更多数据放进上下文会挤占上下文窗口、拉高成本、还会引入“上下文污染”和“提示注入”的风险面；扩大动作空间则放大了误操作、越权与不可逆操作的风险。所以原文在本章小结里补了一句关键限定：**“这种扩大必须按需进行，并配合权限控制和验证。”** 也就是说，“接口就是能力杠杆”不等于“接口越宽越好”。
- **不适用的情况**：当瓶颈确实在模型的推理/泛化能力上（例如需要高维语义判断、需要多步严密逻辑），再怎么扩接口也补不上；这时只能等模型变强或做后训练。原文的说法是“在**底层模型固定时**”这个手段才叫“最主要”，反过来说，模型本身是短板时，接口不是主要矛盾。

> 🔎 检索确认：Manus 在 2026 年发布的 My Computer / 桌面端确实把“重要工作位于本地而非云端”作为云沙盒的局限来陈述，与原文脚注 1 的描述方向一致。（来源：[Manus 官方博客](https://manus.im/blog/manus-my-computer-desktop)）

**易混点**

- **观察空间 vs 上下文**：观察空间是“环境能提供给 Agent 的全部观察”；上下文是“某一次决策时，Agent 内部实际组织好的那部分信息表示”。上下文是观察空间的一个子集（还可能掺入记忆、领域知识等非观察来源）。
- **动作空间 vs 工具**：动作空间是“允许发出的操作集合”；工具是“这些操作的接口封装（定义、协议、适配器）”。工具是动作空间的实现形态。
- **“接口问题” vs “模型问题”**：判断方法是问一句“把数据/操作给到这个模型，它做得对吗？”如果答案是“对”，那原来的失败就是接口问题；如果还是“不对”，才是模型问题。这个问法（笔记补充）是本节论断最实用的操作化形式。
- **Manus 的“合并” vs OpenClaw 的“延伸”**：Manus 是**在云端把三条产品线的空间取并集**（横向合流），OpenClaw 是**把接口推到用户已有的渠道和本地数据上**（纵向外扩）。两者的共同点是都靠扩空间而非换模型。

**一句话记住**

> 模型固定时，Agent 的能力上限由“它能看到什么”和“它能做什么”决定——扩观察空间（上下文）与动作空间（工具），常比换一个更聪明的模型更管用。

### 1.1.2 工具：Agent 的手脚

**原文要点**

- **工具是 Agent 与外部世界交互的桥梁**：**感知类工具**承载“环境到 Agent”的观察，**执行类工具**承载“Agent 到环境”的行动。原文的判据很直接：“没有工具，Agent 只能‘纸上谈兵’；有了工具，它才能真正读取或改变世界。”
- 原文按 **Agent 与外界互动的方向**把工具分为**五类**（先快速过一遍，建立整体印象，后续章节逐一展开）：
  1. **感知工具**：让 Agent 能**访问信息**——搜索引擎提供实时网络数据，文件系统读取本地文档，API 和数据库则对接外部服务和企业核心数据。
  2. **执行工具**：让 Agent **改变世界**——代码执行、文件操作、系统命令、外部 API 调用，决策由此变成实际行动。
  3. **协作工具**：让 Agent 与其他 Agent **分工合作**——委托子 Agent 完成专项任务，在关键决策点请求人类确认，或在多 Agent 系统中协调行动。
  4. **事件触发工具**：与前三类在**调用方式上有本质的区别**——它们**不是 Agent 主动调用的**，而是作为**外部输入**来驱动 Agent 开始执行任务。例如收到一封新邮件、到了某个预定时间点、或另一个系统发出了 Webhook 回调；这些事件会激活 Agent，让它开始后续的思考和行动。原文补充了它的归类理由：**事件适配器同样是 Environment 向 Agent 提供观察的通道，因此本书把它归入广义的工具体系**。
  5. **用户沟通工具**：Agent **主动**与用户建立连接、传递信息的渠道。与执行工具改变外部世界不同，用户沟通工具**专注于信息的传递和交互**——通过文字消息、语音通话、邮件等方式，将 Agent 的执行进展或主动关怀传达给用户。
- 原文注明：以上五类工具的**完整分类体系和设计原则将在第四章展开讨论**。
- **工具设计的质量直接决定 Agent 能走多远**，原文给出三个失败模式：
  - **接口定义不清晰 → 模型就会乱用工具**；
  - **错误处理不到位 → 工具一旦调用失败，Agent 就可能陷入死锁**；
  - **权限控制太宽泛 → Agent 一旦出错，后果就难以挽回**。
- 原文提到生态进展：**MCP（Model Context Protocol，模型上下文协议）标准的推广，正在让工具接入变得更容易。**
- **工具调用（Tool Calling，也称 Function Calling）** 是现代 LLM Agent 的一项**核心能力**，它让模型能通过**结构化**的方式调用外部工具。这种能力“将 LLM 从一个纯粹的文本生成器转变为能够执行实际操作的智能系统”。原文声明：**本书后续统一使用“工具调用”这一术语。**
- **工具调用的流程分为四步**：
  1. 首先，在上下文里告诉模型**有哪些工具可用**（包括名称、用途和参数）；
  2. 然后，模型**自主判断**要不要调用工具、调用哪个、传什么参数；
  3. 接着，工具执行完毕后，**结果被追加到上下文中**；
  4. 最后，模型**据此决定下一步行动**。
  - 原文明确说：**“这个循环就是后文要介绍的 ReAct 的基础。”**
- 原文还说：**开发者只需要定义工具和执行工具调用，模型自主完成“要不要调用、调哪个、传什么参数”的决策。** 第二章将详细展开这个 API 结构。
- **工具粒度的取舍原则**（原文的核心工程建议）：
  - 为 Agent 设计工具时，**先从任务所需的最窄能力起步，再随任务复杂度提升逐步扩展**。
  - 例：如果任务只是做**四则运算**，一个参数清晰的计算器就足够了；当任务升级为**读取表格、清洗缺失值、计算统计量并绘图**时，**受限的 Python 代码解释器**就比不断叠加专用工具更容易组合和探索。
  - 但**通用性也扩大了出错和攻击面**：代码必须在**隔离沙盒**中运行，默认**不能访问网络**，也不能读取**授权工作目录以外**的文件，并对**执行时间、CPU、内存和输出大小**设置上限。
  - 例（长程任务）：**单一日志工具**适合记录一段执行过程；对于需要**数小时甚至数天**的长程任务，**受控的虚拟工作目录**则可以同时保存**计划、中间结果、运行日志和最终产物**，让 Agent 能在**多次执行之间接续工作**。这个目录也应限定**可读写的路径、容量和文件类型**，并防止**路径越界**，而不是把宿主文件系统全部暴露给 Agent。
  - **通用工具并不总是优于专用工具。** 支付、删除数据、发送邮件和生产部署等**高风险或强业务约束操作**，仍应封装为**参数明确、权限受限且全程可审计**的专用工具，必要时再加上**预览和人工确认**。
  - 因此，**工具设计的核心原则是：通用基础能力用于组合与探索；专用工具用于约束高风险和强业务规则操作。**

**四步工具调用流程的 API 简化表示**（原文代码因分栏排版逐行交错，笔记按语义还原为左右两列的顺序）

```text
# 第一步：声明工具
tools: [{
  name: "get_weather",
  parameters: {
    city: "string"
  }
}]

# 第二步：模型决定调用
assistant: {
  tool_calls: [{
    function: "get_weather",
    arguments: {city: "北京"}
  }]
}

# 第三步：结果追加到上下文
tool: {
  tool_call_id: "call_1",
  content: '{"temp":28,"sky":"晴"}'
}

# 第四步：模型基于结果回复
assistant: {
  content: "北京今天28°C，晴。"
}
```

**这段代码在干什么**：第一步 `tools` 数组是**开发者**写给模型的“能力清单”，只包含 `get_weather` 的名字和参数 schema（参数 `city` 是字符串）；第二步 `assistant.tool_calls` 是**模型**自己产出的调用请求，它填好了 `function: "get_weather"` 与 `arguments: {city: "北京"}`——“要不要调、调哪个、传什么”这三件事全部由模型决定；第三步 `tool` 消息是**框架**执行完工具后追加回上下文的返回值，用 `tool_call_id` 与第二步的调用配对，内容是结构化的 JSON（`temp: 28`、`sky: "晴"`）；第四步 `assistant.content` 是模型看到工具结果后给出的自然语言答复“北京今天 28°C，晴。”。**四步走完，正好是一轮 ReAct 循环的骨架**——第二步是“行动”，第三步是“观察”，第一步和第四步分别对应“可用的工具定义”和“基于观察的再思考”。注意原文的用词是“API 层面的**简化**表示”：真实 API 的字段层级比这更细（第二章展开）。

**辅导讲解**

- **五类工具的“方向”这条分类轴好在哪里？** 你不需要背五个孤立的名字，只要问两个问题就能定位：**信息往哪边走？谁发起？**
  - 环境 → Agent 且由 Agent 主动取：**感知工具**；
  - Agent → 环境且由 Agent 主动做：**执行工具**；
  - Agent ↔ 其他 Agent / 人，且由 Agent 主动发起：**协作工具**；
  - 环境 → Agent，但**由外部事件发起**（不是 Agent 拉的，是被推的）：**事件触发工具**；
  - Agent → 用户，传的是**信息而非世界状态**：**用户沟通工具**。
  这样“事件触发工具”为什么跟另外四类不一样就一目了然了：**前三类是“Agent 调用工具”，第四类是“工具调用 Agent”**。原文用的词是“在调用方式上有本质的区别”。
- **为什么“用户沟通工具”要单列，而不是塞进执行工具？** 因为它的效果**不改变外部世界的状态**。发一条“任务已完成”的消息不会让数据库多一行记录，它的作用是**让人类知道发生了什么**（原书用了“主动关怀”这个说法）。把它单列，工程上的好处是：它的风险等级天然很低，可以和高风险的执行工具分开管控——这一点会直接连接到 1.2.5 节“执行层护栏按操作是否可逆、权限等级、财务影响做工具风险评级”。
- **四步流程里的分工线在哪？** 这是本节最该记住的工程事实：**“定义工具”和“执行工具”是开发者的活，“要不要调、调哪个、传什么”是模型的活**。原文把这句写在四步流程下面。对比一下 1.2.4.2 节的自主 Agent——它之所以叫“自主”，就是在这一点上跟工作流分道扬镳：工作流里连“下一步走哪个节点”都是代码写死的，而工具调用把这一步交给了模型。
- **“最窄能力起步，逐步扩展”背后的机制**：工具数量越多，模型选错工具的概率越高（要在更多选项里挑）；专用工具越细，工具之间的组合路径越复杂。而一个通用工具（比如受限 Python 解释器）把“读表、清洗、统计、绘图”四件事压缩成**一次调用 + 一段模型自己写的代码**，组合和探索的成本都低。代价是它在语义上是“开放”的——模型能写任意代码，所以你**必须在沙盒边界上把风险关掉**：不能联网、不能越出授权工作目录、时间/CPU/内存/输出大小都要有上限。原文列这几条限制时用的是“必须”和“默认”，说明这不是可选项。
- **长程任务为什么要“受控虚拟工作目录”？** 因为长程任务的真正难点不是“某一步做不对”，而是“上一次执行的结果带不到下一次”。受控虚拟工作目录相当于给 Agent 一个**跨会话的落盘介质**：计划、中间结果、运行日志、最终产物都放在里面，于是“续接工作”变成“读回自己写下的文件”。这与 1.1.3.2 节讲的“外部产物更新（artifact）”是同一件事的两个视角——一个从工具角度看（工作目录是个工具），一个从学习机制角度看（artifact 是跨任务持久的行为改变载体）。原文对它的限制也很具体：**限定可读写的路径、容量和文件类型，并防止路径越界**——“不要暴露宿主文件系统”。
- **通用 vs 专用不是“先进 vs 落后”，而是按风险分域**：低风险、需要探索 → 通用（代码解释器）；高风险、强规则 → 专用（支付/删除/发信/部署），并配“参数明确 + 权限受限 + 全程可审计 + 预览 + 人工确认”。这套组合之所以必要，是因为**通用工具把决策权交给了模型**，而模型的判断在涉及钱、数据删除、对外通信和生产变更时不可依赖。原文把这条上升为“工具设计的核心原则”，值得逐字记住。
- **MCP 为什么出现在这里？** 原文只说了一句“MCP 标准的推广，正在让工具接入变得更容易”（完整讨论在第四章）。读者应理解它的定位：它解决的是**工具的接入与互操作**问题，让“给 Agent 加一个工具”从每个框架各自实现变成统一协议——也就是把观察/动作接口的**扩展成本**降下来。这与 1.1.1 节“扩空间是主要杠杆”的判断是配套的：杠杆好用，前提是扩起来便宜。
- **“工具调用”/“Function Calling”术语提示**：原文明确“本书后续统一使用‘工具调用’这一术语”。所以后面看到 Function Calling，直接读成工具调用即可。

**易混点**

- **感知工具 vs 事件触发工具**：都在“环境 → Agent”的方向上。区别在**发起方**：感知工具是 Agent 主动去取（调搜索引擎、读文件）；事件触发工具是外部推过来的（新邮件、定时点、Webhook），Agent 是被唤醒的一方。
- **执行工具 vs 用户沟通工具**：都在“Agent → 外部”的方向上。区别在**是否改变世界状态**：执行工具改变状态（写文件、扣款），用户沟通工具只传递信息。
- **“工具” vs “工具调用”**：工具是**被定义出来的能力**（名称 + 用途 + 参数 + 执行实现）；工具调用是**模型在某一轮做出的结构化动作**（`tool_calls`）。四步流程里，第一步是“声明工具”，第二步才是“工具调用”。
- **通用工具 vs 专用工具**：不是能力高低之分，而是**风险与控制力**之分。原文的判据是“高风险或强业务约束操作”→ 专用；“用于组合与探索”→ 通用。别把“通用”当成“更好”。
- **沙盒 vs 虚拟工作目录**：沙盒是**隔离与限制**的边界（不联网、越权即拒）；虚拟工作目录是**持久化与接续**的介质（存计划、中间结果、日志、产物）。两者常一起用，但解决的问题不同。

**一句话记住**

> 工具就是 Agent 的手脚：按“信息往哪边走、谁发起”分成五类；四步调用流程里模型决定“调不调、调哪个、传什么”，开发者只管定义与执行——而通用工具用于探索、专用工具用于约束风险。

### 1.1.3 LLM：Agent 的大脑

**原文要点**

- **大语言模型（Large Language Model, LLM）是 Agent 的决策核心。** 收到用户的请求后，它要完成三类工作：
  1. **先解析真实意图**——原文特意加了一个括号说明：“用户说的往往不是他真正想要的”；
  2. **再将模糊或复杂的任务拆解成可执行的步骤**；
  3. **执行过程中持续做出判断**：下一步该做什么、要不要调用工具、调哪个工具、传什么参数。
- 原文把上面这套能力称为**“理解-规划-执行”**的能力，它**来自预训练所积累的知识**，并且是**工作流和自主 Agent 都依赖的基础**（注意：不只是自主 Agent 依赖它，工作流里每个节点内部的“理解和生成”（见 1.2.4.1）同样依赖它）。
- **LLM Agent 的一个独特能力是内部思考**——在采取实际行动之前，Agent 可以先进行**规划与推演**。这一过程**不改变外部环境**，却能**显著提升后续行动的质量**。
- LLM 之所以能进行有效的内部推演，得益于**预训练（Pre-training，即在海量互联网文本上进行初始训练，让模型学会语言规律和世界知识）** 阶段习得的能力——模型在推演时所遵循的是**人类知识中已经沉淀下来的逻辑规则**，包括**数学定律、因果关系、问题分解策略**等。
- 由此得出与传统 RL Agent 的对比：**与传统强化学习 Agent 不同，今天基于 LLM 的 Agent 不是盲目的随机探索，而是在结构化的知识体系上展开。**

#### 1.1.3.1 模型即Agent：当模型本身成为产品

**原文要点**

- **“模型即 Agent”（Model as Agent）这一新范式代表了 AI Agent 发展的最新方向。** 先进模型通过**后训练（特别是强化学习）** 将**工具调用能力内化为原生能力**：何时调用工具、调哪个、传什么参数，**都由模型自己决定，无需人工编排**。
- **但这并不意味着框架层变得不重要了。恰恰相反，模型越强大，围绕模型构建的 Harness 就越关键。**
- 原文用一个词源类比解释 Harness：**Harness 这个词原指马具，即套在马身上的缰绳与挽具，不是为了限制马的奔跑能力，而是把这种力量引导到正确的方向上。** 换到 Agent 语境里：**模型是那匹强大但不可预测的马，Harness 则是把它的能力引导成可靠任务执行的工程外壳。**
- 在 Agent 中，**Harness 包括上下文管理、工具接口、安全约束、验证与纠正等基础设施（详见本章末节，即 1.2.6）**。
- **模型自主决策的空间越大，出错时的影响面也越大**，因此需要**更精细的约束、验证和纠正机制**来确保可靠性。
- 原文对模型厂商的判断：**模型厂商的真正优势不是“让框架变薄”，而是能对模型与外围 Harness 进行协同优化，持续迭代。**
- **《苦涩的教训》之问**：Rich Sutton 在《苦涩的教训》（The Bitter Lesson）中回顾了 AI 研究**七十年**间反复上演的一幕——研究者一次次把自己对领域的理解编码进系统，**短期见效，长期却总是输给能随算力与数据规模持续扩展的通用方法——搜索与学习**。以此衡量，Harness 里的约束、验证与纠正，有多少属于“人类先验”，注定会被模型内化？
- **本书的立场：方向认同，节奏务实。**
  - **方向上**：本书**不怀疑**模型会持续吃掉 Harness——工具调用、长程规划都曾靠外部编排，如今已是模型的原生能力；
  - **节奏上**：这个“吃”的过程**远比想象中慢**：训练以月计，模型也无法一次内化真实业务中所有的约束与偏好，**模型此刻的能力边界，就是 Harness 此刻的价值所在**。
  - 结论：**Harness 工程不是对苦涩的教训的抵抗，而是这一教训在工程时间尺度上的实践：模型还做不稳的，Harness 先补上；模型每内化一层，Harness 就卸下一层，转而兜底新的能力前沿。**

> 脚注 2（印刷 p.11）：Sutton, Rich. “The Bitter Lesson”, 2019. <http://www.incompleteideas.net/IncIdeas/BitterLesson.html>

#### 1.1.3.2 Agent 的学习机制：从上下文适应到持久更新

**原文要点**

- 前面讨论了模型可以通过强化学习把工具调用策略内化为原生能力；但 **Agent 的行为改变不只发生在训练阶段**。原文按**更新发生的位置和持续时间**，把它理解为**三条互补路径**（图 1-2）：
  1. **任务内的上下文适应（Context adaptation）**；
  2. **跨任务的外部产物（artifact）更新（External artifacts）**；
  3. **训练周期中的参数更新（Parameter update）**。
- 三条路径的具体内容（原文图 1-2 的结构）：

| 路径 | 主要载体 | 更新特性 | 补充说明 |
| --- | --- | --- | --- |
| 任务内适应（Context adaptation） | 当前上下文：示例 · 状态 · 检索结果 | 即时、低成本；任务结束后不自动保留 | 发生在当前任务中；示例、状态和检索结果进入上下文后，模型可以立即调整行为，却不会因此改变下一次会话的持久状态。优势是快速、低成本，局限是**受上下文窗口和信息组织方式约束**；第二章将详细讨论这种适应如何工作 |
| 外部制品更新（External artifacts） | 知识 · 指令 · 程序：文档 · Prompt/Skill · Harness | 跨任务持久、可审计；依赖检索或工具调用 | 把事实和经验整理为**知识文档**，把可语言化的策略写进 **Prompt 或 Skill**，把确定性流程与约束写成**程序和 Harness**。这些产物可审计、可修订，**执行时仍需通过上下文或工具接口被 Agent 使用**。第三至五章分别给出知识与程序基础，第九章讨论如何从已评价的运行轨迹中生成这些更新 |
| 模型参数更新（Parameter update） | 模型权重：SFT · 偏好训练 · RL | 高维能力、广泛泛化；训练与回归成本较高 | 当目标是**医疗影像理解、自然语言风格或隐式决策策略等高维能力**时，外部规则难以完整表达，就需要通过**后训练更新模型参数**。部署成本较高，却能形成**自然、广泛的泛化能力**；第八章将系统介绍其方法 |

> 图 1-2（原文插图）：图的标题是“Agent 能力更新的三个层次”，上方有一个总问题“Agent 的行为如何发生改变？”。图的主体是**三个并列的竖栏**，对应三条更新路径。**左栏**“任务内适应 / Context adaptation”，列出“主要载体：当前上下文（示例 · 状态 · 检索结果）”与“更新特性：即时、低成本 / 任务结束后不自动保留”。**中栏**“外部制品更新 / External artifacts”，列出“主要载体：知识 · 指令 · 程序（文档 · Prompt/Skill · Harness）”与“更新特性：跨任务持久、可审计 / 依赖检索或工具调用”。**右栏**“模型参数更新 / Parameter update”，列出“主要载体：模型权重（SFT · 偏好训练 · RL）”与“更新特性：高维能力、广泛泛化 / 训练与回归成本较高”。三栏下方有一条横向的汇总带，写着“**三者协同：临场适应 · 可控积累 · 能力内化**”——也就是说，这张图不是让你三选一，而是把三条路径按“更新的位置（上下文内 / 外部产物 / 模型权重）”和“持续的时间尺度（任务内 / 跨任务 / 训练周期）”排开，并指出它们合起来才构成完整的学习机制。

- **三条路径不是互斥分类，而是不同时间尺度上的协同机制**：**上下文负责临场适应，外部产物负责可控积累，参数负责内化难以显式表达的能力。**

**辅导讲解**

- **“内部思考”为什么被单列成一种独特能力？** 因为它把“想”和“做”分开了。传统 Agent（比如 Q-learning 的机器人）通常“想=做”：选一个动作就直接作用到环境上，试错只能靠真实交互。LLM Agent 可以在**不消耗环境代价**的前提下先推演一遍——原文说它“不改变外部环境，却能显著提升后续行动的质量”。工程上的直接收益是：**试错成本从“真实世界的一次操作”降低到“一次 token 生成”**。这也是 ReAct 里 `reasoning` 那一部分存在的理由（1.1.4 节的实验 1-1 会给它一个更精确的定位：它记录的是“为什么这么做”）。
- **“结构化知识体系上展开”这句话的分量**：原文用它来对比传统 RL Agent 的“盲目随机探索”。机制上，LLM 在推演时遵循的是**预训练语料里已经沉淀的逻辑规则**——数学定律、因果关系、问题分解策略。所以它不需要从零试错就能做“看起来合理”的规划。反过来说，**预训练语料里没有沉淀的规则，LLM 的推演也不可靠**——这解释了为什么私有业务规则、企业内部约束必须通过上下文（RAG、Prompt）或外部产物补进去（这正是 1.1.3.2 的中间那条路径）。
- **“模型即 Agent”最反直觉的地方**：字面上听起来像是“框架可以退休了”，但原文的结论恰恰相反——**模型越强，Harness 越关键**。理解这一点的关键是分清两件事：**“决策权”转移了，但“执行与治理”没有转移**。模型决定“调哪个工具、传什么参数”（决策），可工具的真实实现、代码沙盒、调用的发起与结果的回传，仍然在模型之外的基础设施里完成。原文在实验 1-2 里把这一点讲得极清楚：**编排循环并没有消失，只是决策权交给了模型**；至于循环本身跑在哪里，取决于接入方式。
- **马具这个类比的精确含义**：原文特意澄清“不是为了限制马的奔跑能力”。所以 Harness 的默认姿态不是“刹车”，而是**定向**。这解释了一个常见误解——很多人把 Harness 等同于“安全审查”，其实 Harness 还包括上下文管理和工具接口这两项**纯功能性**职责（1.2 节的公式：Harness = 上下文管理 + 工具接口 + 约束 + 验证 + 纠正）。前三项里有两项是“让它能做事”，后三项才是“别做错事”。
- **《苦涩的教训》该怎么读**：原文的用法是“以此衡量，Harness 里的约束、验证与纠正，有多少属于‘人类先验’？”——它把《苦涩的教训》当成一把**尺子**，用来判断哪部分 Harness 是临时脚手架、哪部分是长期价值。而本书给出的答案是前半句“方向认同”、后半句“节奏务实”。这个“节奏务实”有具体的支撑论据：**训练以月计**、**模型无法一次内化真实业务中所有的约束与偏好**。工程结论就是那句非常实用的话：**“模型还做不稳的，Harness 先补上；模型每内化一层，Harness 就卸下一层，转而兜底新的能力前沿。”** 如果你在做 Agent 产品，这句话可以直接当成技术路线图的原则：Harness 是**随能力前沿滚动**的，不是一次性建完的静态资产。
- **三条更新路径的效率—成本权衡**（笔记补充的对照，用来记忆）：上下文适应的延迟最低（下一次推理就生效）、成本最低，但**留不下**；外部产物的延迟中等（要写文档/改 Prompt/ 改代码）、成本中等，**能留下且可审计**，但要靠检索或工具调用才被用上；参数更新的延迟最高（要采集数据、训练、回归评测）、成本最高，但能拿到**高维、隐式、广泛泛化**的能力。所以选择顺序天然是“能靠上下文解决的就别改代码，能靠改文档/程序解决的就去改代码，只有规则说不清、写不出来的能力才去训模型”。原文在 1.3 节把这条顺序直接点破了：**“本章开头给出的三条更新路径（上下文内适应、外部产物更新、参数更新），也正是按可回滚程度从高到低排列的。”**
- **为什么“高维能力”必须走参数更新**：原文举了三个例子——**医疗影像理解、自然语言风格、隐式决策策略**。这三个的共同点是“**外部规则难以完整表达**”：你可以给模型写一条“写代码要符合 PEP8”，但你没法给模型写一条“用这种语气说话才像我们的品牌”或者“这张 CT 片上这个阴影意味着什么”。前者是可语言化的策略（→ Prompt/Skill），后者是隐式能力（→ 参数更新）。这就是三条路径的**分界线**：能不能用自然语言把这条规则完整写下来。
- **工程上的坑**：把本属于参数更新的问题硬塞进上下文——比如试图用一大段 Prompt 教会模型一种语言风格或一种影像判读能力。结果通常是长 Prompt 里规则打架、模型抓不住重点、成本和延迟还很高。反过来，把本属于上下文的临时事实硬塞进参数——为一个每周都在变的业务规则去微调模型，也会因为“训练与回归成本较高”而得不偿失。**判据就是“这条知识可语言化吗？它变的频率有多高？”**

> 🔎 检索确认：Rich Sutton 的《The Bitter Lesson》确实于 2019 年发表，原文链接 <http://www.incompleteideas.net/IncIdeas/BitterLesson.html> 有效，其核心论点正是“能随算力与数据规模扩展的通用方法（搜索与学习）长期胜过把人类先验编码进系统的方法”，与原文引用一致。（来源：[The Bitter Lesson](http://www.incompleteideas.net/IncIdeas/BitterLesson.html)）

**易混点**

- **“内部思考” vs “工具调用”**：都在模型的输出里，但内部思考（`reasoning`）**不改变外部环境**，工具调用（`tool_calls`）**会改变外部环境**。1.1.4 节会说，前者记录“为什么这么做”，后者（及其结果）记录“发生了什么”。
- **“模型即 Agent” vs “框架不重要了”**：前者不是后者的同义词。原文的立场是**决策权内化到模型，执行与治理仍在 Harness**。判断某产品是不是“模型即 Agent”式，看的不是“有没有框架”，而是“调不调工具、调哪个、传什么参数”这件事由谁决定。
- **三条更新路径的分界**：按“更新发生的位置”分（上下文内 / 外部产物 / 模型权重），不按“重要性”分。三者都重要，只是**时间尺度**和**可回滚程度**不同。
- **可语言化的策略 vs 隐式决策策略**：前者写成 Prompt/Skill（外部产物更新），后者必须走后训练（参数更新）。判据是“能不能用自然语言把这条规则完整写下来”。
- **《苦涩的教训》的两种误读**：一种读成“所有工程手段终将无用”（原文明确说“方向上认同，节奏上务实”，且“这个‘吃’的过程远比想象中慢”）；另一种读成“应该继续硬编码人类先验”（原文明确说“不怀疑模型会持续吃掉 Harness”）。原文的立场介于两者之间。

**一句话记住**

> LLM 是大脑：它在结构化的人类知识上做“理解-规划-执行”，并能“先想后做”；“模型即 Agent”意味着决策权内化进模型，但 Harness 不会消失——它随能力前沿滚动，模型还做不稳的就先补上。

### 1.1.4 上下文：Agent 的眼睛

**原文要点**

- **上下文是 Agent 在每个决策点能看到的全部信息。** 原文的类比是：就像一个人在做决策时需要看到桌上摊开的所有资料——**任务说明、参考手册、之前的沟通记录、最新的数据**——Agent 的**上下文窗口就是它的“视野”**。
- 从 **API 的视角**看（详见第二章），每次调用 LLM 时的上下文由**五个部分**构成：
  1. **系统提示词（System Prompt）**：与用户每次输入的提示词不同，**系统提示词由开发者编写，在整个对话过程中保持不变**，相当于 Agent 的“**岗位说明书**”——定义它的**身份、权限和行为准则**。通过**提示工程（Prompt Engineering）** 精心设计系统提示词，可以塑造 Agent 的工作方式。系统提示词中**还会包含跨会话保存的用户记忆**（用户偏好、历史行为、背景设定等个性化信息，详见第三章）和**动态注入的环境状态**。
  2. **工具定义（Tool Definitions）**：声明 Agent 可用工具的**名称、功能描述和参数格式**。**没有工具定义，Agent 就无法识别和调用任何工具，但它并不会因此停下来**——消融实验（实验 1-1）会说明这一点。工具定义与系统提示词一起构成对话中**保持不变的静态前缀**（原文注明：**这是基础模式**；2026 年以来，生产框架中**工具的完整 schema 也可以按需动态加载到上下文末尾而不破坏前缀**，详见第二章工具定义一节和第四章）。
  3. **用户消息（User Messages）**：来自用户的输入。用户消息中**还可能包含通过 RAG（检索增强生成，Retrieval-Augmented Generation，详见第三章）动态检索引入的外部知识**——覆盖**训练数据截止后的信息**或**私有领域知识**。
  4. **模型回复（Assistant Messages）**：模型之前生成的回复，**最多包含三个部分**——
     - **思考过程（reasoning）**：即内部思考链，用于保持思维的连贯性和决策的可解释性；
     - **文本内容（content）**：即对用户的回复；
     - **工具调用请求（tool_calls）**：即 Agent 采取行动的方式。
     - 原文强调：**在一次具体的回复中，三者不一定同时出现**。例如 **Agent 决定调用工具时通常只有 `reasoning + tool_calls`**，**给出最终回答时通常只有 `reasoning + content`**。
  5. **工具执行结果（Tool Results）**：Agent 框架执行工具后返回的结果。这些结果是**Agent 下一步思考的直接依据**，也让它能够**从执行结果中学习、避免重复犯错**。
- **静态前缀 vs 动态消息历史**：**前两项（系统提示词 + 工具定义）是静态前缀**，**后三项（用户消息 + 模型回复 + 工具执行结果）是随交互不断增长的动态消息历史**。这五个部分共同构成了 LLM 每次推理时的上下文。
- **验证方法：消融实验（Ablation Study）**。原文的类比是：就像医生诊断时逐一排除病因——先去掉 A 组件看系统是否还正常，再去掉 B 组件，以此类推，从而判断每个组件的贡献。**实验 1-1 正是按这个思路，对上述五个组件做了系统性测试。**

**实验 1-1 ★★：上下文的关键作用**（印刷 p.13–14）

- 实验方法：通过**系统性的消融实验（Ablation Study）**，探索不同上下文组件对 Agent 行为的影响。实验**从上述五个部分中选取了四个组件进行测试**——**系统提示词作为 Agent 的基本身份定义不参与消融**，因为**没有系统提示词，Agent 连基本的角色认知都没有，测试没有意义**。
- 实验设计：如图 1-3 所示，**五组对照实验**包括：**一组保留全部组件的完整基线**，再加上**四组各缺失一个组件的对照**，以此观察每个组件对 Agent 性能的影响。
- 实验设计表（表格按原文语义还原）：

| 组别 | 系统指令 | 工具定义 | 思考过程 | 历史记录 | 工具结果 | 结果 |
| --- | --- | --- | --- | --- | --- | --- |
| 完整基线 | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ 正常工作 |
| 无工具定义 | ✓ | ✗ | ✓ | ✓ | ✓ | ✗ 无法调用工具 |
| 无思考过程 | ✓ | ✓ | ✗ | ✓ | ✓ | △ 决策不连贯 |
| 无历史记录 | ✓ | ✓ | ✓ | ✗ | ✓ | △ 重复操作 |
| 无工具结果 | ✓ | ✓ | ✓ | ✓ | ✗ | ✗ 盲目循环 |

> 图 1-3（原文插图）：图题是“实验 1-1——上下文消融实验设计”。它是一张**实验设计矩阵**：第一行是列头，从左到右依次为“系统指令 / 工具定义 / 思考过程 / 历史记录 / 工具结果 / 结果”；从第二行起是五组对照，每组用一个符号标注该组件是否保留（✓ 表示保留、✗ 表示移除、△ 表示结果处于退化但未完全失效的状态）。第一组“完整基线”五个组件全部 ✓，结果为“✓ 正常工作”；后面四组依次把“工具定义”“思考过程”“历史记录”“工具结果”中的一个置为 ✗，而“系统指令”一列**五组全部为 ✓**（对应正文所说“系统提示词不参与消融”）。四组对照的结果分别是“✗ 无法调用工具”“△ 决策不连贯”“△ 重复操作”“✗ 盲目循环”——注意图中用 ✗ 和 △ 区分了**能力被彻底夺走**和**行为退化但还能跑**这两种不同程度的后果。

- **实验结果揭示的作用**（原文逐一说明）：
  - **工具定义（静态前缀的一部分）是 Agent 行动能力的基础**，没有它就无法调用任何工具；**但失去行动能力不等于沉默**——模型照样会给出一份**格式工整、语气笃定的答案**，**数据却来自参数记忆，与真正基于观测得出的答案排版一模一样**。它是**坦白拒绝还是就地编造，主要取决于模型自身的幻觉率与诚实度**；提示词里“不得自行估计”这类约束**只能降低编造的概率，并不能消除**。
  - **工具执行结果是闭环控制的关键**，缺失它会让 Agent **“盲目”执行，反复重试直到耗尽迭代预算**。
  - **思考过程（模型回复中的 reasoning 部分）记录的是“为什么这么做”，工具执行结果记录的是“发生了什么”；当前者可以从后者重建时，把它从历史中丢掉几乎没有代价。**
  - **历史消息（之前轮次的用户消息、模型回复和工具执行结果）则防止了冗余操作，避免重复犯同样的错误。**
- **实验的核心洞察**（原文原话）：
  1. **上下文决定了 Agent 能看到什么，而 Agent 只能基于它看到的信息做决策。**
  2. **但组件并不等价**，衡量的标准是**它承载的信息能否从别处重建**——“每个组件都不可或缺”这类论断**要靠实测**，而且**模型迭代很快，同一个消融换到新模型上完全可能得出不同的结论**。
  3. **对工程实践更重要的一点：“给出了回答”不等于“完成了任务”，上下文残缺时典型的失败不是报错退出，而是一个看上去毫无破绽的答案。**

**辅导讲解**

- **五个组件的划分是按“谁写的”和“变不变”来的**，这两条线一定要记住：
  - 按**谁写的**：系统提示词 = 开发者写；工具定义 = 开发者声明；用户消息 = 用户（或 RAG 检索）产生；模型回复 = 模型产生；工具结果 = 框架执行工具后产生。
  - 按**变不变**：系统提示词 + 工具定义 = **静态前缀**（对话中保持不变）；其余三项 = **动态消息历史**（随交互不断增长）。
  这个“2 + 3”的切分不是随意的，它是 1.1.5 节 `上下文 = 静态前缀 + 轨迹` 的直接来源，也是第二章 KV Cache 前缀稳定性的基础（改动越靠前，作废的缓存越多，见 1.3 节“只增不改”模式）。
- **`reasoning` / `content` / `tool_calls` 三者的组合规律很实用**：把“要行动”和“要回答”看成互斥的两个出口。**要行动 → `reasoning + tool_calls`（不含 content）；要回答 → `reasoning + content`（不含 tool_calls）**。所以你在轨迹里看到一条 `content` 非空、`tool_calls` 为空的 assistant 消息，基本可以判定这轮是“终点”——这也是 1.2.4.2 节“模型返回没有任何工具调用的响应”被列为退出条件之一的原因。
- **实验 1-1 最容易被忽略的一句话，其实是全节最有工程价值的一句**：**“上下文残缺时典型的失败不是报错退出，而是一个看上去毫无破绽的答案。”** 传统软件缺一个依赖会崩、会抛异常、会写日志；Agent 缺了工具定义不会崩，它会**照常输出一份排版漂亮的答案**，只是数据来自参数记忆。这意味着：
  - **不能用“有没有报错”来判断 Agent 是否健康**；
  - **必须引入独立的验证机制**（这正是 1.2 节 Harness 五要素里“验证 (Verify)”存在的根本原因）；
  - **不能把 Agent 的自信程度当成可靠性指标**——原文说得很直白：“与真正基于观测得出的答案排版一模一样”。
- **“✗”与“△”的区别说明后果的等级不同**：去掉工具定义 → ✗ 无法调用工具（**能力被夺走**）；去掉工具结果 → ✗ 盲目循环（**闭环断裂**）；去掉思考过程 → △ 决策不连贯（**质量下降**）；去掉历史记录 → △ 重复操作（**退化但可跑**）。而这四组的退化程度并非完全由“信息量”决定，而是由**“这条信息能不能从别处重建”**决定——这正是原文给出的衡量标准。
- **为什么“思考过程可以从工具结果重建时，丢掉它几乎没有代价”？** 因为 `reasoning` 是“为什么这么做”，`tool_calls` + `tool results` 是“发生了什么”。如果一条 assistant 消息是“我需要把 EUR 转成 USD，然后求和”，而下一段就是 `convert_currency(...)` 的调用和返回的汇率——那么“为什么”完全可以从“做了什么”推出来。反过来，如果模型的推理里包含**没有被工具结果体现的中间判断**（例如“我排除了 A 方案因为 X”），丢掉它就会让后续决策失去依据。这给了一个可操作的判断流程（笔记补充）：**逐条问“删掉这条 reasoning，后面的 tool_calls 和结果还能不能自解释？”能 → 可压缩；不能 → 必须留。**
- **消融实验的工程用法**：原文说“每个组件都不可或缺”这类论断**要靠实测**，而且**换模型结论可能变**。这句话的意思是：消融实验不是一次性结论，而是一种**必须随模型版本重跑的评估手段**。所以你在自己的 Agent 里想省上下文（省 token、省成本）时，正确做法不是照抄本实验的结论去删组件，而是**在自己的任务集上重跑一遍消融**。这与第七章的评估方法论、第九章的更新提案验证是同一套思路。
- **“基础模式”与“动态 schema”的区别值得留意**：原文说“工具定义与系统提示词一起构成对话中保持不变的静态前缀（**这是基础模式**）”，后面括号里补了一个例外——**2026 年以来，生产框架中工具的完整 schema 也可以按需动态加载到上下文末尾而不破坏前缀**。读者要理解这个补充的重要性：它说明“静态前缀”不是一个铁律，而是一个**性能优化下的默认约定**；只要能把新内容**追加到末尾**（而不是插回前缀），前缀的缓存依然有效。这正好是 1.3 节“只增不改”模式的一个实例。
- **RAG 在这里的角色**：用户消息里“可能包含通过 RAG 动态检索引入的外部知识”。注意它的两个用途原文点了名——**覆盖训练数据截止后的信息**（时效性）或**私有领域知识**（数据边界）。之所以放在“用户消息”里而不是“系统提示词”里，是因为它**每一轮都可能不同**，属于动态部分；这也解释了为什么第三章（用户记忆和知识库）要与第二章（上下文工程）分开讲。
- **工程上的坑**：
  - **系统提示词里塞太多东西**：原文说系统提示词里还会包含跨会话的用户记忆和动态注入的环境状态——这会让“静态”前缀事实上每轮都在变，直接击中缓存。取舍是第二章的主题。
  - **把 `reasoning` 当垃圾丢掉来省 token**：可能可行（如上），但推荐做法是**有条件压缩**而非一律丢弃。
  - **只靠提示词防幻觉**：原文明确说“提示词里‘不得自行估计’这类约束只能降低编造的概率，并不能消除”。

**易混点**

- **上下文 vs 上下文窗口**：上下文 = 内容（五个部分）；上下文窗口 = 容量（能装多少 token）。原文说“Agent 的上下文窗口就是它的‘视野’”，用的是比喻，别把两者当成同一个概念。
- **系统提示词 vs 用户提示词**：前者由开发者编写、整个对话保持不变，是“岗位说明书”；后者是用户每次的输入，属于动态消息历史。
- **`reasoning` vs `content` vs `tool_calls`**：同属一条 assistant 消息的三个可选部分。`reasoning` 不等于对用户说的话（`content` 才是）；`tool_calls` 不是文本回复，是行动请求。
- **工具定义 vs 工具执行结果**：都在“工具”名下，但一个是**静态前缀里的声明**（告诉你有什么能用），一个是**动态历史里的返回值**（告诉你刚刚发生了什么）。实验 1-1 里它们各自的缺失后果完全不同：前者 ✗ 无法调用工具，后者 ✗ 盲目循环。
- **消融实验（Ablation Study） vs 对照组实验**：消融实验是“完整系统去掉一个组件”，用退化程度反推该组件的贡献；它不是“加一个组件看有没有变好”。原文用“医生诊断时逐一排除病因”来类比，要点在“逐一排除”。

**一句话记住**

> 上下文 = 静态前缀（系统提示词 + 工具定义）+ 动态消息历史（用户消息 + 模型回复 + 工具结果）；消融实验说明组件并不等价——判据是“它承载的信息能否从别处重建”，而上下文残缺的典型症状是一个看起来毫无破绽的答案。

### 1.1.5 ReAct 循环

**原文要点**

- 了解了 Agent 的三大组件之后，自然的问题是：**它们如何协同工作？** 原文的回答是：**ReAct 循环就是将 LLM、上下文和工具串联起来的核心机制。**
- **Agent 执行任务的核心模式叫做 ReAct（Reasoning + Acting）。** 原文特别指出一个名实不符之处：**虽然名字只体现了思考（Reasoning）和行动（Acting）两个词，但实际循环包含三个环节**——模型先**思考**当前应该做什么，然后**调用工具行动**，再**观察**工具返回的结果并继续思考下一步。这个**“想→做→看→想→做→看”**的循环不断重复，直到任务完成。
- 原文用一个**多币种收入汇总**的具体例子来讲解 **轨迹（trajectory）**。轨迹的定义是：**Agent 在执行任务过程中不断积累的消息历史**——用户消息、模型回复（包括思考过程和工具调用）、工具执行结果。
- 每一次调用 LLM 时，它接收的完整上下文由两部分组成（图 1-4）：**静态前缀（系统提示词 + 工具定义）** 和 **轨迹（动态消息历史）**。原文由此给出一个关键事实：

$$\text{Agent 的上下文} = \text{静态前缀} + \text{轨迹}$$

  其中 **静态前缀对应前文五个组件中的前两项**（系统提示词 + 工具定义），**轨迹对应后三项**（用户消息 + 模型回复 + 工具执行结果，随交互不断增长）。基于这个完整上下文，**LLM 生成下一步的响应，然后这个响应又追加到轨迹中，供下一次调用使用**。

> 图 1-4（原文插图）：图题是“Agent 轨迹——多币种汇总任务的 ReAct 循环”。图的左侧是一条按轮次展开的**消息序列**，右侧标注“**轨迹 = LLM 每次调用时看到的完整输入**”，以及“关键特性：**上下文累积**（每轮都看到全部历史）、**结构化轨迹**（`user` / `assistant` / `tool`）”。序列内容按轮次如下：
> - **第 1 轮**：`user` 消息“计算年度总收入：Q1 \$2.5M, Q2 €2.1M, Q3 £1.8M”；然后是 `assistant.reasoning`“需要将 EUR 和 GBP 转换为 USD，再汇总计算”；接着是 `assistant.tool_calls`，一次发出两个调用：`convert_currency(2100000, "EUR", "USD")` 与 `convert_currency(1800000, "GBP", "USD")`；最后是 `tool`（结果）“EUR→USD: 2,282,608.70”和“GBP→USD: 2,278,481.01”。

> - **第 3 轮**：`assistant.content`（最终回答）“年度总收入 \$7,061,089.71，季度均值 \$2,353,696.57”。
>
> 这张图想说明的是：**轨迹就是一条不断向下追加的消息流水，而每一轮的 assistant 都只看得到它上方已经写下的全部内容**——第一轮模型只知道三种货币的金额，第二轮它多看到了两条汇率，第三轮它多看到了汇总结果。图里没有画出系统提示词和工具定义（对应正文那句“轨迹中没有显示系统提示词和工具定义”）。

- **最小运行骨架（Python 风格伪代码）**。原文说明：它说明的是**机制如何运行**——**Model 只负责决定下一步，Harness 负责组装上下文、校验并执行工具，Environment 负责产生真实状态变化和观察**。原文同时声明：**本书后续也沿用 Python 风格伪代码；伪代码不能直接运行，也不对应某个 SDK。具体的可执行代码在本书配套代码仓库中。**

```python
trajectory = [user_request]
repeat:
    context = stable_prefix + trajectory
    decision = Model(context)
    trajectory.append(decision)
    if decision has no tool call:
        return decision.answer
    for call in decision.tool_calls:
        # independent calls may run in parallel
        validated_call = Harness.validate(call)
        observation = Environment.execute(validated_call)
        trajectory.append(observation)
```

**实验 1-2 ★：Kimi K3 原生 Agent 能力**（印刷 p.16–17）

- 定位：这个实验展示了 **Kimi K3 的原生 Agent 能力**，体现了“**模型即 Agent**”的新范式。
- 模型规格（原文给的数字，逐条照录）：
  - **约 2.8 万亿参数的混合专家（MoE, Mixture of Experts）模型**。原文给了 MoE 的通俗解释：**可以把 MoE 想象成一个专家团队——面对不同类型的问题，系统会自动选择最合适的几位专家来作答，而不需要所有专家同时上阵，这样既保证了能力又提高了效率。**
  - **100 万 token 的上下文窗口**；
  - **原生的视觉理解能力**；
  - **始终开启的“思考模式”（thinking mode）**；
  - **通过强化学习训练，将工具调用的决策策略内化为原生能力**——何时调用工具、调用哪个、传什么参数都由模型自主决定，从而能够自主完成网络搜索等任务。
- **关键观察**：模型**自己决定何时搜索、搜索什么**，展现了**真正的自主性**；它能**根据搜索结果动态调整策略，自主判断信息是否充足**。
- **一个常见的误解需要厘清，关键在于分清两件事的归属**：
  - **强化学习写进参数的是决策**——何时该调用工具、调用哪个、传入什么参数、拿到结果后是否继续、如何把几十上百次调用串联成连贯的推理。
  - **工具本身及其执行则由 Agent 框架（或 API 内置工具）提供**——`web_search`、`code_runner` 的真实实现、代码沙盒环境、调用的发起与结果回传，**都在模型之外的基础设施里完成**（原文注明：**Kimi 通过名为 Formula 的服务端脚本引擎运行这些官方工具**）。
  - 因此，**编排循环并没有消失，只是决策权交给了模型**；至于**循环本身跑在哪里，取决于接入方式**：
    - 在**实验 1-3 的 Responses API 路径**中，搜索、代码执行和多轮编排**整体在服务端闭环完成**；
    - 而在**实验 1-2 的 Kimi 路径**中，**Formula 只负责在服务端执行搜索本身**，“调用模型 → 追加工具结果 → 再次调用”的 ReAct 循环**仍由客户端代码驱动**（原文指向 `chapter1/web-search-agent/agent.py` 中的 `while` 循环）。
- **Kimi K3 在 Agent 任务中的一个突出优势是长链工具调用的稳定性**——它能够**连续执行 200～300 次工具调用而保持思考的一致性**，**远超多数模型在数十次调用后就开始退化的表现**。
- **两个规格**：K3 面向**长周期编程与 Agent 工作负载**优化，发布时提供 **K3 Max**（面向对话与 Agent 任务）与 **K3 Swarm Max**（面向大规模并行处理）。
- 结论：作为**开源模型**，它在**软件工程和 Agent 基准测试**中展现了**可与顶尖闭源系统比肩的性能**，证明了**通过强化学习赋予模型原生 Agent 能力这条路线的有效性**。

**实验 1-3 ★：GPT-5.6 原生 Deep Research 能力**（印刷 p.17–18）

- 定位：使用 **OpenAI GPT-5.6**，展示先进模型如何借助 **API 内置工具**，在**服务端**形成 Deep Research 的 **“搜索—阅读—分析”编排闭环**。
- **自由格式工具调用（Freeform Tool Calling）**：
  - 传统方式中，模型调用工具时**必须把所有参数打包成严格的 JSON 格式**（原文括注：一种结构化的数据格式），**这就像填表格一样有很多格式限制**。
  - **自由格式工具调用（在 API 中通过 `type: "custom"` 的工具类型声明）允许模型直接向工具发送原始文本**（比如一段 Python 代码、一条 SQL 查询），**省去了 JSON 转义的麻烦**。
  - 原文特意澄清：**这是 API 参数格式的演进，而非模型架构的革新**——客户端的工具调用循环（**检测 `tool_calls` → 执行 → 回传结果**）逻辑保持不变，**改变的只是参数从 JSON 字符串变成了原始文本**。
- **与 Responses API 内置工具配合**：GPT-5.6 配合 Responses API 的**网络搜索**和**代码解释器**内置工具——**这正是 Deep Research 的核心**：模型能够**自主搜索网络获取实时信息**，并**编写代码进行深度分析**，实现 **“搜索 -> 阅读 -> 分析 -> 再搜索”** 的迭代研究过程。
- **两个具体任务示例**：
  - “**东盟 10 国首都之间，最近的一对首都距离多少**”：GPT-5.6 会自动搜索各国首都的**地理坐标**，然后**编写 Python 代码计算所有首都对之间的大圆距离**，最终找出最近的一对。
  - “**搜索最近一个月的比特币走势，做技术分析**”：它能从**多个金融数据源获取实时价格数据**，运用专业的技术分析库计算**移动平均线、RSI、MACD** 等技术指标，**生成可视化图表并给出交易建议**。
- **意图澄清过程（这是本节的重点判断）**：原文说，“更重要的是”，**GPT-5.6 将 OpenAI Deep Research 产品的设计理念内化到了模型层面，引入了意图澄清过程**。当用户提出研究需求后，GPT-5.6 **不会立即动手执行**，而是**首先通过一系列问题来澄清用户的真实意图**。以“搜索最近一个月的比特币走势，做技术分析”为例，它会先问：“**你偏好使用哪个数据源？需要分析哪些技术指标？**”通过这种交互式的意图澄清，GPT-5.6 能够生成**更精准、更符合用户需求**的研究报告。
- **原文的定位判断**：GPT-5.6 是“**模型即 Agent**”概念的一个**成熟实例**——网络搜索、代码解释器作为 Responses API 的**内置工具在服务端闭环执行**，**客户端不必再自行搭建“搜索—阅读—分析”的编排框架**。而**意图澄清的意义在于，它让“用户说了什么”和“用户真正想要什么”之间的差距，在任务执行之前就得到了弥合**。
- **可复现性说明**：这个实验**并不绑定某一家厂商**。没有 OpenAI 额度的读者完全可以用具备等价托管工具的提供商复现——例如**阿里云百炼 qwen3.7-plus 的 Responses API 同样内置 `web_search` 与 `code_interpreter`**；**Kimi K3 的 Formula 托管搜索与 `code_runner` 也属于同类能力**。

**辅导讲解**

- **ReAct 名字里为什么少了“观察”？** 这是本节标题下最容易被问到的点。原文明确说“名字只体现了思考（Reasoning）和行动（Acting）两个词，但实际循环包含三个环节”。原因在于 **Observing 不是一个“模型动作”，而是环境返回的结果**——它是工具执行完自动追加进轨迹的数据，不需要模型去“做”。所以 ReAct 这个词是从**模型视角**命名的：模型只做“想”和“做”两件事，“看”是被动的。理解这一点很关键，否则你会以为模型要主动发起一次“观察”。
- **走一遍数据流**（这是理解本节的唯一正确方式，笔记补充的逐步说明）：
  1. Harness 取 `stable_prefix + trajectory` 拼成 `context`（**前缀不动，轨迹变长**）；
  2. 调用 `Model(context)`，拿到 `decision`（可能含 `reasoning` / `content` / `tool_calls`）；
  3. **无条件**把 `decision` 追加进 `trajectory`——注意这一步在“判断有没有工具调用”**之前**，所以即使这轮就是最终回答，它也会留在轨迹里；
  4. 如果没有工具调用 → 直接 `return decision.answer`（**这就是循环的出口之一**）；
  5. 如果有工具调用 → 对**每一个** call 依次：`Harness.validate(call)` 校验，再 `Environment.execute(...)` 执行，把返回的 `observation` 追加进 `trajectory`；
  6. 回到第 1 步。
  伪代码里那句注释 **“# independent calls may run in parallel”** 讲的是：一轮里多个**互相不依赖**的调用可以并行执行——第 1 轮里两个 `convert_currency` 就是这种情况（第 2 轮的汇总必须等汇率回来，所以不能和第 1 轮并行）。
- **伪代码里最关键的一行是 `validated_call = Harness.validate(call)`**。它只有一行，但它是“模型想干什么”和“环境真的被改成什么样”之间的**唯一闸门**。这行代码就是 1.2 节 Harness 五要素里“约束 (Constrain)”和“验证 (Verify)”的最小形态。读者应该形成条件反射：**凡是 `Model(...)` 的输出要流向 `Environment` 的地方，都必须经过校验。**
- **验证一下原文给的数字**（笔记补充的计算，用来确认读懂了这张图）：
  - 图 1-4（三轮版本）：$2{,}500{,}000 + 2{,}282{,}608.70 + 2{,}278{,}481.01 = 7{,}061{,}089.71$，与图中“年度总收入 \$7,061,089.71”一致；季度均值 $7{,}061{,}089.71 \div 3 = 2{,}353{,}696.57$，与图中“季度均值 \$2{,}353{,}696.57”一致（**除以 3 是因为本例只有 Q1–Q3 三个季度**）。
  - 轨迹结构示例（四轮版本）：$2{,}500{,}000 + 2{,}282{,}608.7 + 2{,}278{,}481.01 + 2{,}541{,}806.02 = 9{,}602{,}895.73$，与“Total: \$9,602,895.73”一致；$9{,}602{,}895.73 \div 4 = 2{,}400{,}723.9325$，与“Average: \$2,400,723.93”一致（四舍五入到分）。
  - 两次示例的迭代次数与工具调用数要分开算。**图 1-4**（三轮版本）里出现的是 2 次 `convert_currency`（EUR、GBP）+ 1 次 `code_interpreter`，共 **3 次工具调用、3 轮迭代**。**轨迹结构示例**（四轮版本，多了一笔 Q4 380M 日元）里出现的是 3 次 `convert_currency`（EUR、GBP、JPY）+ 1 次 `code_interpreter`，共 **4 次工具调用、3 轮迭代**——这正是正文紧随其后那句“整个过程只用了 3 次迭代、4 次工具调用”所指的对象。注意“迭代次数”不是“工具调用次数”：**第 1 轮里并发发出的多个调用，只算一轮迭代。**
- **为什么“轨迹”这个概念值得单独命名？** 因为它把三件通常被混着说的事情分开了：
  - **轨迹**是**数据结构**（消息历史，`user`/`assistant`/`tool` 三种角色）；
  - **ReAct 循环**是**控制流**（谁在什么时候调用谁）；
  - **上下文**是**每次推理的输入**（= 静态前缀 + 轨迹）。
  三者关系是：循环每转一圈，就往轨迹尾部追加消息，下一圈重新拼出上下文。把这层分清以后，第二章讲上下文管理、第七章讲轨迹评估、第九章讲“从已评价的运行轨迹中生成更新”（原文 1.1.3.2 提到的），你都能定位它们在动哪一部分。
- **“分析大量轨迹”为什么有产品价值？** 原文列了三条：**发现 Agent 的行为模式、优化决策路径、改进工具设计**。这三条对应的其实是三种不同的问题：行为模式 → 评估与监控（第七章）；决策路径 → 提示/上下文优化（第二章）；工具设计 → 接口改进（第四章）。也就是说，**轨迹是 Agent 系统的“日志 + 数据资产”**。原文还说轨迹能“沉淀进知识库”或“用于强化学习训练更好的模型”——这正好对应 1.1.3.2 的三条更新路径里的后两条（外部产物、参数更新），闭环由此合上。
- **实验 1-2 真正的考点：分清“决策”与“执行”**。原文在这里花了一大段去“厘清一个常见的误解”，并把它做成了一条脚注（感谢读者 asdlem 通过 Issue #30 指出）。这条区分极其重要，值得背下来：
  - **RL 内化的**：何时调用、调用哪个、传什么参数、拿到结果后是否继续、**如何把几十上百次调用串联成连贯的推理**——这些都是**决策**，写进了参数；
  - **框架提供的**：`web_search` / `code_runner` 的**真实实现**、代码沙盒、**调用的发起与结果回传**——这些都是**执行**，留在模型之外。
  所以“模型即 Agent”**不等于“框架消失了”**。原文的措辞是“**编排循环并没有消失，只是决策权交给了模型**”。更进一步，**循环跑在哪里是接入方式的问题，不是范式的问题**：Responses API 路径整个循环在服务端闭环；Kimi 路径里 Formula 只做服务端搜索，“调用模型 → 追加工具结果 → 再次调用”仍由客户端 `while` 循环驱动。**两条路径的模型自主性一样，工程形态不一样。**
- **实验 1-3 真正的考点：意图澄清是“省钱”的机制，不只是“礼貌”**。做 Deep Research 最贵的失败不是“跑不动”，而是**跑完一趟才发现方向错了**——所有搜索、阅读、分析的算力全打水漂。意图澄清把这部分损失**提前**了：在任务执行之前就弥合“用户说了什么”与“用户真正想要什么”的差距（原文原话）。这也解释了为什么它被放在**模型层面**而不是产品层面：作为模型的原生行为，任何接了 Responses API 的调用者都自动获得这个能力，不用自己写一轮问答。这正好是“产品设计理念被内化进模型”的又一个实例，跟 1.2.4.1 节末尾“每一轮内化，消灭的都是‘翻译’和‘脚手架’”的判断是一条线。
- **自由格式工具调用到底改了什么、没改什么**：改了**参数的载体**（JSON 字符串 → 原始文本），没改**循环的形状**（检测 `tool_calls` → 执行 → 回传结果）。原文明确说“这是 API 参数格式的演进，而非模型架构的革新”，就是防止读者把它误读成一次模型能力的跃迁。它的实际收益很具体：写 Python 代码或 SQL 时不用再把整段代码做 JSON 转义——**摩擦小了，出错点也少了**。
- **工程上的坑**：
  - **退出条件必须显式设计**。伪代码里的 `return decision.answer` 只覆盖“模型不再调用工具”这一种情况。真实系统还要覆盖“达到最大轮次”“错误次数超限”等，否则一旦模型陷入“盲目循环”（实验 1-1 里“无工具结果”那组的症状）就会一直烧 token。完整清单见 1.2.4.2 与图 1-6。
  - **轨迹无限增长的代价**。原文说“上下文是不断追加的”，这在 3 轮的小任务里没问题，但长程 Agent 会撞上上下文窗口和成本上限。原文在图 1-4 里标出的“关键特性：上下文累积”既是优点也是约束——第二章的上下文压缩、多层压缩（Claude Code 的 Harness 里就有这一项）就是在处理它。
  - **并行调用的前提是“互相不依赖”**。并行发多个工具调用能省时间，但一旦其中有依赖（比如第二次调用需要第一次的返回值），就必须串行。判断依据是**参数里有没有引用其他调用的结果**。
- **不适用/例外**：只执行单步简单任务、或在 Computer Use 中仅需点击固定位置（见 1.2.3 节）时，不需要带思考的模型；同理，**一个不需要观察结果的任务也不需要完整的 ReAct 循环**，一次调用就够。原书在 1.2.4 节把这条上升为编排原则：“首先考虑单个 LLM 调用。”

**易混点**

- **ReAct 的“三环节” vs 名字的“两个词”**：名字里没有 Observing，但循环实际有“思考 → 行动 → 观察”。原因是观察是环境返回的、不是模型主动发起的动作。
- **轨迹（trajectory） vs 会话历史（conversation history）**：在本章语境里，轨迹就是不断累积的消息历史（含工具调用与工具结果），两者可以视为同义。关键是它**不含静态前缀**——前缀是每次调用时临时拼上去的。
- **`Tool Calling` vs `Function Calling`**：原文在 1.1.2 明确“本书后续统一使用‘工具调用’这一术语”。
- **模型决定调用 vs 框架执行调用**：前者是 RL 内化的**决策**，后者是模型之外的**基础设施**。实验 1-2 用整段篇幅澄清的就是这一对。
- **循环在服务端 vs 循环在客户端**：两条路径（Responses API / Kimi）的**模型自主性相同**，区别只在**ReAct 循环由谁驱动**。别把“循环在服务端”当成“模型更强”的标志。
- **自由格式工具调用 vs 结构化输出**：前者是把**参数**从 JSON 变成原始文本；后者通常是让模型**输出**符合 schema 的 JSON。方向不同，不要混。

**一句话记住**

> ReAct = 想 → 做 → 看，循环往复直到出口；每次调用的输入是 `静态前缀 + 轨迹`，而“模型即 Agent”改的是**决策权**（交给模型），不改**执行与循环的归属**（仍在 Harness 里）。

## 1.2 Harness 工程：模型之外的竞争力

**原文要点**

- **本节的问题意识**（原文开篇）：到这里你已经理解了 Agent 的核心工作原理——**LLM 通过 ReAct 循环，在上下文的辅助下使用工具完成任务**。前面的实验证明了这套基本机制是有效的，但同时也**暴露了明显的脆弱点**：
  - 模型可能**产生幻觉**（编造不存在的工具或参数）；
  - **选错工具**；
  - 或在遇到错误时**无法自我恢复**。
  - 原文的论断：**“一个能跑的 Demo 和一个可靠的产品之间还有巨大的鸿沟，而这些脆弱点正是 Harness 工程要解决的问题。”** 并且明确划分了本章的结构：**本章前半部分回答了 Agent 是什么，下半部分回答 Agent 如何在生产环境中可靠运行。**
- **从最小公式到生产公式**：前面几节建立了 `Agent = LLM + 上下文 + 工具` 的最小工程公式，并通过图 1-1 明确了 Agent 与 Environment 的边界。从 **Harness 工程的视角**看：
  - 可以把 LLM 抽象为核心组件 **Model**；
  - 把 **Agent 边界内**负责支撑模型运行及模型与环境交互的**代码、配置和服务**统称为 **Harness**。
  - 原文强调：**两个视角并非替代关系，而是不同抽象层次上对同一 Agent 实现的描述。**
- **Harness 的核心构成**：**Harness 的核心是原公式中的“上下文管理 + 工具接口”，再加上三层保障机制**：
  - **约束**：限定 Agent **能做什么、不能做什么**；
  - **验证**：检查 Agent **做得对不对**；
  - **纠正**：做错了**怎么补救**。
- **生产形态下的完整组成方程**（原文以独立公式形式给出）：

$$\text{Agent} = \text{Model} + \text{Harness}$$

$$\text{Harness} = \text{上下文管理} + \text{工具接口} + \text{约束} + \text{验证} + \text{纠正}$$

$$\text{Agent} \leftrightarrow \text{Environment}$$

  其中：$\text{Model}$ 是承担策略决策的模型本体（对应 LLM）；$\text{Harness}$ 是 Agent 边界内、模型之外的运行与治理层；$\text{Agent} \leftrightarrow \text{Environment}$ 的**双向箭头**表示二者是**闭环交互的两方**而非包含关系（沿用图 1-1 的边界）。第一式说明“生产形态的 Agent 就是 Model 加上外围那一层”；第二式把第一式里的 Harness **展开为五项职责**——前两项（上下文管理、工具接口）让它“能做事”，后三项（约束、验证、纠正）让它“不做错事”。把第二式代回第一式，就得到 `Agent = Model + 上下文管理 + 工具接口 + 约束 + 验证 + 纠正`，这正对应 1.1 节“LLM 对应 Model，‘上下文 + 工具’构成最小 Harness”的展开。

- **最小 Demo 与生产系统的差别**：**最小 Demo 只需 Model 和能构造上下文、暴露工具的 Harness；生产系统还要在同一边界内加入约束、验证和纠正。** 原文给了一个具体例子：**退款 Agent** 可以
  - 把**政策**放进**上下文**、
  - 用**权限和金额规则约束**调用、
  - 用**数据库状态验证**结果，
  - 并在**超时时重试或回退**。
- **Harness 工程的研究对象**：**“模型之外、Agent 边界之内”的运行与治理代码**。
- **边界的一次精确划清**（原文用“更精确地说”起头）：
  - **Harness 不是模型之外的一切，而是 Agent 边界内、模型之外的运行与治理层。** 它负责**协调 Model 与 Environment 的交互**，但**不包括与之交互的环境本身**。
  - **属于 Harness 的**：**工具定义、调用适配器、沙箱的权限与重置机制**。
  - **属于 Environment 的**：**沙箱内随行动变化的文件和进程、外部数据库、网页、用户及物理世界**。
  - **一条重要的判据**：**物理部署位置也不能决定概念归属——即使仿真环境与 Agent 运行在同一进程中，它仍然是 Environment。**
- **Harness 五要素总表**（表格按原文语义还原）：

| 功能 | 职责与核心原则 | 实际例子 | 详见 |
| --- | --- | --- | --- |
| Context（上下文） | 为模型提供感知信息；信息要充分，让 Agent 在每个决策点都基于足够的信息判断 | 系统提示词、知识库、Agent 状态栏、Sidecar 旁路查询 | 第二、三章 |
| Tools（工具接口） | 为模型提供观察与行动手段；接口要清晰，命名直观、参数有例子、边界有说明 | MCP 工具、代码解释器、搜索工具 | 第四章 |
| Constrain（约束） | 设定行为边界；采用故障安全默认值，所有能力默认关闭，必须显式开放（类似手机 App 权限管理） | Claude Code 中每个工具默认需要用户授权才能执行 | 第四章 |
| Verify（验证） | 自动判断操作结果的对错；安全检查只看结构化数据（如工具返回的 JSON 字段），而不看模型自由生成的文本，因为后者可能已被提示注入操纵 | Linter 检查、类型系统、工具调用结果校验 | 第五、六章 |
| Correct（纠正） | 发现问题时自动修正或回退；在确认无法恢复之前不暴露中间态，例如工具调用失败时先静默重试，不把半成品结果展示给用户 | 静默重试、接续生成、连续失败时回退到人工判断（熔断机制） | 第二、五章 |

- **模型控制循环的基本流程**（原文给出如下伪代码，并说明“这段骨架**刻意不展开具体实现**”）：

```python
observation = Environment.observe()
trajectory = [observation]
while true:
    actions = Model(Harness.build_context(trajectory))
    if len(actions) == 0:
        break
    allowed_actions = Harness.constrain(actions)
    observation = Environment.apply(allowed_actions)
    if not Harness.verify(Environment):
        observation = Harness.correct(Environment)
    trajectory.append(allowed_actions, observation)
```

- 原文注明：**完整的 API 消息循环将在第二章介绍，工具与自动验证则分别在第四、五章展开。**
- **五要素的相互关系**：**五个功能构成一个闭环**——
  - **上下文与工具让 Agent “能做事”**——理解任务并采取行动；
  - **约束预防错误，验证发现偏差，纠正使闭环得以形成，三者共同让 Agent “不做错事”**；
  - 原文强调：**它们不是独立于上下文和工具之外的东西，而是确保上下文和工具在生产环境中可靠运转的工程实践。缺少任何一个环节，系统都会出现可靠性缺口。**
- **两类功能的重要性是不对称的**（原文：“在 Agent 产品的成熟度曲线上，两类功能的重要性是不对称的”）：
  - **早期的 Agent 框架主要关注上下文与工具**：给模型工具、给模型上下文，让它“能做事”；
  - **而生产级 Agent 系统的重心已经转向约束、验证与纠正**：确保工具调用是**安全的**、上下文是**经过管理的**、错误是**可纠正的**。
- **以 Claude Code 为例的佐证**：**它的 Harness 中绝大部分代码都是约束、验证与纠正，而非上下文与工具**——工具本身（**文件读写、命令执行、搜索**）只是一小部分，而**围绕这些工具构建的保障机制才是真正的核心**。原文列举了这些机制：
  1. **流程状态管理**：追踪 Agent 当前执行到哪一步；
  2. **多层上下文压缩**：当信息太多时自动精简；
  3. **权限分类**：控制哪些操作需要用户确认；
  4. **熔断器（Circuit Breaker）**：当错误连续发生时**自动“断电”停止重试**——原文的类比是“就像家里电路短路时保险丝会自动跳闸，防止整个系统崩溃”；
  5. **错误恢复机制**：捕获异常、**回滚到上一稳定状态**、重试或**交还给人类**。
- **本节的结论**：**行业正在从“能做事”向“可靠地做事”转变，Harness 工程因此成为 Agent 系统的核心竞争力。**

**辅导讲解**

- **这一节是全章的分水岭**。1.1 讲的都是“Agent 能做什么”，1.2 开始讲“Agent 凭什么可信”。原文把这条线画得很清楚：“**本章前半部分回答了 Agent 是什么，下半部分回答 Agent 如何在生产环境中可靠运行。**” 读到这里你应该调整关注点：从“机制是什么”切到“失败在哪、怎么兜住”。
- **两个公式的正确关系，务必别记成两套骨架**。原文在 1.2.6 节会专门交代，这里先埋下伏笔：
  - `Agent = LLM + 上下文 + 工具` 是**全书唯一的结构骨架**；
  - `Agent = Model + Harness` 是**同一事物在生产形态下的展开**——它把“上下文”和“工具”两项**细分为五项职责**（上下文管理、工具接口、约束、验证、纠正）。
  所以正确的记法是：**一条骨架，两个抽象层次**。考试或面试里如果被问“哪个公式对”，答案是“都对，但层级不同”。
- **“Harness 不是模型之外的一切”这句话为什么要反复强调？** 因为一个常见的错误推论是：“凡是我写的、不是模型的代码，都是 Harness。” 正确判据有两条：
  1. **在不在 Agent 边界内？** 边界外的（外部数据库、网页、用户、物理世界）不是。
  2. **是“运行与治理”还是“被治理的对象”？** **沙箱的权限与重置机制**是 Harness，但**沙箱里跑起来的、随行动变化的文件和进程**是 Environment。前者是“规则”，后者是“被规则作用的状态”。
- **“物理部署位置不能决定概念归属”这条判据非常锋利**。它的意思是：概念归属看**角色**，不看**进程**。哪怕仿真环境和 Agent 跑在同一个进程里、共享同一块内存，只要它是“Agent 作用的对象 + 返回观察的来源”，它就是 Environment。这条判据在工程上极其实用：**当你决定“这段逻辑该写成工具、还是该留在环境里”时，问的是它的角色，不是它跑在哪台机器上。**
- **把伪代码逐行走一遍**（笔记补充，用来对照 1.1.5 的 ReAct 伪代码）：
  1. `observation = Environment.observe()`：循环**开始之前**先取一次观察（这是 1.1.5 里 `trajectory = [user_request]` 的对应物，只不过这里显式写成“从环境观察”）；
  2. `trajectory = [observation]`：轨迹初始化；
  3. `actions = Model(Harness.build_context(trajectory))`：注意这里是把“构造上下文”包在**取动作**这一步里的——`Harness.build_context` 就是 1.1.5 里的 `stable_prefix + trajectory`；
  4. `if len(actions) == 0: break`：**退出条件**——模型没有给出任何动作就结束；
  5. `allowed_actions = Harness.constrain(actions)`：**约束**落在“模型想做的”和“实际允许做的”之间；
  6. `observation = Environment.apply(allowed_actions)`：只有 `allowed_actions` 才被真正应用，**这是安全边界的物理位置**；
  7. `if not Harness.verify(Environment): observation = Harness.correct(Environment)`：**验证 + 纠正**——注意 `verify` 的参数是 `Environment`（**验证的是世界的状态，不是模型的文本**），这与表格里“安全检查只看结构化数据”的原则一致；
  8. `trajectory.append(allowed_actions, observation)`：把**实际执行的动作**（不是模型最初提议的动作）和观察一起追加。
  对比 1.1.5 的最小骨架，这里多了 `build_context`、`constrain`、`verify`、`correct` 四个 Harness 调用——**这就是“最小 Demo”和“生产系统”在代码层面的全部差别**。
- **“两类功能重要性不对称”该怎么落到工程决策上？** 早期框架的默认思路是“先把能力做出来”（加工具、加上下文），生产系统则必须把大部分工程量投在保障机制上。Claude Code 的例子是原文给的硬证据：**工具本身只是一小部分，保障机制才是核心**。这对做产品的人是一个明确的资源分配信号——**不要把“接了多少工具”当成竞争力指标**。
- **五个功能为什么构成“闭环”而不是“清单”？** 因为纠正的结果会**回流**：`Harness.correct(Environment)` 会产生一个新的 `observation`，它会和 `allowed_actions` 一起被追加进轨迹，下一轮模型看得到“刚才失败了、系统做了什么补救”。这样模型才有机会**换一个策略**而不是原地重试。原文对“纠正”这一项的说明也点了这层意思：“在确认无法恢复之前不暴露中间态，例如工具调用失败时先静默重试，不把半成品结果展示给用户。”
- **退款 Agent 那个例子的读法**：原文用一句话把五要素全串了一遍，值得当作模板背下来——**政策进上下文（Context）→ 权限和金额规则约束调用（Constrain）→ 数据库状态验证结果（Verify）→ 超时重试或回退（Correct）**。也就是说，任何一个“生产级 Agent 的某个业务场景”都能按这五格拆开看缺了什么。
- **“故障安全默认值（fail-safe default）”这条原则值得单独记住**：表格里对 Constrain 的要求是“所有能力**默认关闭**，必须显式开放（类似手机 App 权限管理）”。这与传统软件“默认允许”的思路相反，是对“模型会做出你没预料到的事”这一事实的工程回应。它的代价是配置变多、体验变钝，收益是**出错时的默认后果是“没做”而不是“做错了”**。注意 Claude Code 的例子正是这条原则的实例：“每个工具默认需要用户授权才能执行”。
- **“安全检查只看结构化数据”这条原则容易被忽略但极其重要**：表格里 Verify 一栏写的是“安全检查只看结构化数据（如工具返回的 JSON 字段），**而不看模型自由生成的文本，因为后者可能已被提示注入操纵**”。原因是：模型自由生成的文本**本身可能就是攻击载荷的一部分**（被注入后模型会照着攻击者的意思写），所以拿它当验证依据等于让攻击者自己给自己开证明。**验证依据必须来自模型无法直接改写的地方。**
- **工程上的坑**：
  - **只在最后加护栏**。原文说“安全问题从第一行代码就要考虑，而不是上线前打补丁”（见 1.4 本章小结）。把 constrain/verify/correct 当插件事后挂上去，往往要重构主循环。
  - **把验证写成“让模型自己检查”**。这与 Verify 的原则冲突（模型文本不可信）。原书在 1.3 节的“提议者—审核者”模式里给出正解：**评判方要看到产物本身（渲染结果、测试输出、结构化的调用参数），而不是产出方的推理过程**。
  - **熔断器与“重试”混为一谈**。重试是“再试一次”，熔断是“连续失败后停止重试”（连续失败时回退到人工判断）。二者是配套的两级机制，缺了熔断就会一直烧预算——这正好呼应实验 1-1 里“无工具结果 → 盲目循环 → 反复重试直到耗尽迭代预算”的症状。

**易混点**

- **Model vs LLM**：在 `Agent = LLM + 上下文 + 工具` 里叫 LLM，在 `Agent = Model + Harness` 里叫 Model，**指同一个东西**（策略决策的内核），只是抽象层次不同。
- **Harness vs “所有非模型代码”**：Harness 必须**在 Agent 边界内**且属于**运行与治理**范畴。外部数据库、网页、用户、物理世界不是 Harness；沙箱里变化的文件/进程也不是（那是 Environment），但**沙箱的权限与重置机制**是。
- **Constrain vs Verify**：约束是**事前**（在动作生效之前限制集合，`allowed_actions`）；验证是**事后**（对结果/状态做检查）。一个是“不许做”，一个是“做完检查对不对”。
- **Verify vs Correct**：验证是**判断**（`if not Harness.verify(...)`），纠正是**处置**（`Harness.correct(...)`）。原文的对应表述是“验证发现偏差，纠正使闭环得以形成”。
- **最小 Demo vs 生产系统**：差别不是“功能多少”，而是**有没有约束、验证、纠正这三层保障**。

**一句话记住**

> Harness = 模型之外、Agent 边界之内的运行与治理层 = 上下文管理 + 工具接口 + 约束 + 验证 + 纠正；前两项让它“能做事”，后三项让它“不做错事”，而生产系统的工程量主要花在后三项上。

### 1.2.1 从提示工程到Loop 工程：工程范式的演进

**原文要点**

- 原文说，回顾 AI 应用工程的发展，可以看到**一条清晰的演进弧线**：
  1. **提示工程（Prompt Engineering）是第一波创新**——通过**优化输入给模型的自然语言指令**来提升输出质量。
  2. **上下文工程（Context Engineering）是第二波**——人们认识到**单纯优化提示词还不够**，需要**系统性地管理模型能看到的所有信息**（**系统指令、工具定义、对话历史、外部知识**）。
  3. **Harness 工程是第三波**——它将视野从“模型能看到什么”进一步扩展到“**Agent 如何组织模型运行并与环境交互**”，涵盖**上下文与工具接口、约束机制、验证手段、反馈循环和错误恢复**等 **Agent 边界内、模型之外的运行与治理机制**。
  4. **Loop 工程（Loop Engineering）** 随后出现，**又把视野从单次运行扩展到跨轮次的持续自主运转**：**谁来发现下一件该做的事、何时验证、何时才算真正完成**（第十章将结合多 Agent 协作系统展开）。
  5. **Graph 工程（Graph Engineering）**：**2026 年 7 月**，业界又开始用这个词描述一种**更高层的编排视角**——把 **Agent 循环、确定性程序和人工审批组织成显式的执行图**，其中**节点承担具体能力，边规定路由与依赖，结构化状态沿边传递并在关键边界处持久化**。
- **五个阶段不是替代关系，而是层层包含的**：
  - **提示工程是上下文工程的子集，上下文工程是 Harness 工程的子集，Harness 工程是 Loop 工程的子集，Loop 工程又是 Graph 工程的子集**——**单个 Agent 循环正是执行图中的一个节点**。
  - **每一层都在前一层的基础上扩展了工程师的关注范围和影响力。**
- **核心判断**：**当各家模型的能力越来越接近、不再是决定性的差异因素时，竞争优势就转移到了模型之外的工程实践。**
- **一个有力的实证**：**LangChain 在 Terminal Bench 2.0**（原文括注：**一个评估 Agent 在终端环境中完成复杂任务能力的基准测试**）上的实践提供了一个有力例证——**得分从 52.8% 提升到 66.5%（从排行榜 30 名开外跃升至前 5）**，**改变的不是模型，而是 Harness**，具体包括：
  - 让 Agent **自动检查自己的执行结果**；
  - **检测是否陷入重复循环**；
  - **优化思考策略**等工程手段。

> 脚注 3（印刷 p.20）：Josh C. Simmons 在 2026 年 7 月 4 日的文章 *We Are Entering the Graph Engineering Phase* 中较早明确使用这一名称，并将其概括为**节点、类型化边和可检查点状态**；7 月 18 日，Peter Steinberger 关于“是否已从 loops 转向 graphs”的讨论进一步推动了该名称传播。需要注意的是，**相关实践早于这个名称**：LangGraph、Microsoft Agent Framework 和 Google ADK 的官方文档分别称其为图编排或 graph-based workflow。参见 <https://www.drjoshcsimmons.com/writing/we-are-entering-the-graph-engineering-phase>、<https://x.com/steipete/status/2078277297791189132>、<https://docs.langchain.com/oss/python/langgraph/overview>、<https://learn.microsoft.com/en-us/agent-framework/workflows/>、<https://adk.dev/workflows/>。

**辅导讲解**

- **“每一层扩展了什么”是这张演进图的关键**。把五个阶段排成一列，每一层的视野扩大一倍：
  - 提示工程 → 关注**指令文本**；
  - 上下文工程 → 关注**模型能看到的所有信息**（从“一句话”扩到“整个上下文”）；
  - Harness 工程 → 关注**模型怎么跑、怎么和环境交互**（从“输入”扩到“运行与治理”）；
  - Loop 工程 → 关注**跨轮次的持续运转**（从“单次运行”扩到“长期的自主循环”）；
  - Graph 工程 → 关注**多个循环 + 确定性程序 + 人工审批的组织形态**（从“一个循环”扩到“一张执行图”）。
  理解这个链条的最快方式是问：“**这一层在追问什么问题？**”——提示工程问“话怎么说”，上下文工程问“给它看什么”，Harness 工程问“它怎么跑才可靠”，Loop 工程问“它怎么一直跑下去、何时算完”，Graph 工程问“多个循环和人在图上怎么摆”。
- **“子集”这个词是原文的精确用词，值得推敲**。提示工程 ⊂ 上下文工程，因为系统指令本来就是上下文的一部分；上下文工程 ⊂ Harness 工程，因为上下文管理是 Harness 五要素之首；Harness 工程 ⊂ Loop 工程，因为一次运行是跨轮次运转的一个片段；Loop 工程 ⊂ Graph 工程，因为**单个 Agent 循环正是执行图中的一个节点**（原文原话）。**这就意味着后面这些范式出现时，前面那些并没有作废**——你在做 Graph 工程时仍然要写提示词、管上下文、搭 Harness。
- **“竞争优势转移到模型之外”这个判断怎么落地？** 原文给的落点是那句“当各家模型的能力越来越接近、不再是决定性的差异因素时”。也就是说，这个判断**有前提条件**：模型能力趋同。如果模型能力差距巨大（比如某家领先一代），那模型仍是决定性因素。工程含义是：**在模型同质化的赛道上，投 Harness 的边际收益高于投模型选型。**
- **LangChain 那组数字为什么是全章最有说服力的证据？** 因为它是一个**控制变量实验**：模型没换，只改了 Harness，指标从 52.8% 到 66.5%（**+13.7 个百分点**），排名从“30 名开外”到“前 5”。而且它改的三件事正好是 Harness 的职责范围：
  - “**自动检查自己的执行结果**”→ 对应 **Verify**（验证）；
  - “**检测是否陷入重复循环**”→ 对应 **Correct**（纠正/熔断），也正好治的是实验 1-1 里“无工具结果 → 盲目循环”那个症状；
  - “**优化思考策略**”→ 对应 **Context**（上下文管理，即 thinking 的组织方式）。
  这三点几乎把 Harness 五要素的后三项各覆盖了一项。**读者应该记住这个案例的读法：不是“某框架成绩好”，而是“同一模型下，Harness 决定了 13.7 个百分点的差距”。**
- **Graph 工程的“名称早于实践”这个脚注说明什么？** 原文脚注明确说“**相关实践早于这个名称**”——LangGraph、Microsoft Agent Framework、Google ADK 早就把它叫“图编排”或 “graph-based workflow”。所以当你在 2026 年看到“Graph 工程”这个新词时，应该理解它是**给已有实践起了个统一的名字**，而不是一种全新技术的诞生。附注里还给了这个名称的三个要素概括：**节点、类型化边、可检查点状态**。
- **工程上的用法**：这条演进弧线可以直接当**技术选型的自检表**。做一个 Agent 项目时按顺序问：提示词调过了吗？上下文组织过了吗？Harness（约束/验证/纠正）有吗？需要跨轮次持续运转吗？需要多个循环 + 人工审批编成图吗？**顺序不能跳**——原文的“层层包含”意味着跳到后面反而会返工。
- **不适用/注意**：原文说的是“演进弧线”和“层层包含”，**不意味着每个项目都要走到最右边**。1.2.4 节马上就会说“保持简单”“从简单到复杂”。**Graph 工程解决的是“多个 Agent/循环 + 确定性程序 + 人工审批”的组织问题；如果你的任务一个循环就搞定，引入显式执行图只会增加抽象层。**

> 🔎 检索确认：这条结论的算术依据来自原书正文本身给出的两个数——$66.5\% - 52.8\% = 13.7$ 个百分点（同一案例、模型不变、只改 Harness）；公开讨论中也以“13.7pt、同一模型、52 → 66”概括 LangChain 这次改进，与本笔记的复算方向一致。可追溯的官方出处是 LangChain 的 *Improving Deep Agents with harness engineering*（来源：[LangChain 官方博客](https://www.langchain.com/blog/improving-deep-agents-with-harness-engineering)）。另有第三方博客以该数字为题讨论，本笔记未能独立核实其数据来源，故不列为依据。

**易混点**

- **提示工程 vs 上下文工程**：前者只动“指令文本”；后者动“模型能看到的所有信息”（系统指令、工具定义、对话历史、外部知识）。提示工程是后者的**子集**。
- **上下文工程 vs Harness 工程**：前者管“模型能看到什么”；后者还管“Agent 如何组织模型运行并与环境交互”（约束、验证、反馈循环、错误恢复）。上下文工程是后者的**子集**。
- **Harness 工程 vs Loop 工程**：前者针对**单次运行**；后者针对**跨轮次的持续自主运转**（谁发现下一件事、何时验证、何时算完成）。前者是后者的**子集**。
- **Loop 工程 vs Graph 工程**：前者是“一个循环怎么持续转”；后者是“把 Agent 循环、确定性程序和人工审批组织成显式执行图”——**单个 Agent 循环只是图中的一个节点**。
- **“五波”不是“五代”**：不是替代关系。说“第五波”不意味着前四波过时，而是**层层包含**。

**一句话记住**

> 提示 ⊂ 上下文 ⊂ Harness ⊂ Loop ⊂ Graph——每一层扩展的是工程师的关注范围；当模型能力趋同，胜负就转移到模型之外的工程实践上（LangChain 只改 Harness 就从 52.8% 提到 66.5%）。

### 1.2.2 构建有效Agent 的核心原则

**原文要点**

- 原文明确来源：**根据 Anthropic 的经验，成功的 Agent 系统遵循三个核心原则**（脚注 4：Anthropic. “Building effective agents”, 2024 年 12 月. <https://www.anthropic.com/engineering/building-effective-agents>）。
- **原则一：保持简单。** 从**最简单的方案开始**，**只在确实必要时才增加复杂度**。原文给的两条判据是：
  - **直接的 API 调用优于复杂的框架**；
  - **清晰的代码优于聪明的抽象**。
  - 理由：**因为每多一层抽象都会成为以后调试时新的盲区。**
- **原则二：保持透明。** **明确显示 Agent 的规划步骤、执行日志和决策轨迹**——原文强调：**这不只是为了调试方便，也是让用户建立信任的前提**。理由：**因为黑箱里的错误一旦发生，外部观察者既无法定位也无法纠正。**
- **原则三：设计好工具接口（ACI，Agent-Computer Interface）。** 原文对 ACI 的定义是：
  - **ACI 强调的是从 Agent 视角设计接口（让 Agent 容易理解和使用），而非传统 API 从程序员视角设计接口**；
  - **工具的命名和参数要直观**；
  - **容易误用的地方要从设计上让错误无法发生**。
  - 原文给的两个具体类比：
    - **SIM 卡的缺角**让卡片**只能从一个方向插进卡槽**，避免了用户插反的错误；
    - **微波炉门没关好就绝不加热**，避免了用户开门加热的危险行为。
  - 原文指出这种“**用设计消除错误**”的思路在制造业里有一个专门的术语：**防呆（Poka-yoke），源自丰田生产体系**。
  - 理由：**设计不好的工具会让再强的模型也频繁出错——因为模型与工具之间唯一的沟通通道就是接口本身，模糊的接口会被模型放大成系统性的错误。**
- **本节收尾交代了后续三节的关系**：**以下三节展开 Harness 工程中三个独立但重要的主题：模型选型、编排模式、护栏与安全性。它们都不属于 Harness 五要素本身，但都是工程实践中绕不开的决策。**

**辅导讲解**

- **“保持简单”这句话为什么排在第一位？** 因为它对抗的是一个非常具体的失败模式：**过度抽象**。原文给的理由是“每多一层抽象都会成为以后调试时新的盲区”——注意它的落点是**调试**（可观测性），不是“性能”或“代码量”。这跟后面第三条“保持透明”是一对：抽象层让你看不见，看不见就没法定位错误。原文的措辞“直接的 API 调用优于复杂的框架”相当激进，但方向明确：**框架的价值必须大于它带来的盲区。**
- **“保持透明”不只是对外，也是对内**。原文说“明确显示 Agent 的规划步骤、执行日志和决策轨迹”，这三样正是 1.1.5 节里 ReAct 循环天然产出的东西——**轨迹的结构化（`user`/`assistant`/`tool` 彼此分明）本身就是透明性**。所以透明不是额外做一个 UI 面板，而是**别把已经有的信息藏起来**。原文说“这不只是为了调试方便，也是让用户建立信任的前提”，把透明抬到了产品层面。
- **ACI 与 API 的区别是本节最该记住的一条**：
  - **API 的读者是程序员**：程序员会读文档、会看类型定义、会容忍一些不直观的命名，因为他能查。
  - **ACI 的读者是模型**：模型只能看到工具的名称、描述和参数 schema，**它没有“我觉得这个名字有点怪，去查下文档”这种能力**。原文的措辞是“模型与工具之间**唯一的沟通通道就是接口本身**”。
  - 所以 ACI 的设计目标不是“功能完备”，而是“**不容易被误解**”。这就是为什么原文强调“命名和参数要直观”。
- **“让错误无法发生”和“让错误被检测到”是两种不同的设计哲学**，本节讲的是前者。对比一下：
  - **防呆（Poka-yoke）**：SIM 卡缺角、微波炉门锁——**错误在物理上不可能发生**，不需要检测、不需要报错、不需要用户理解。
  - **验证（Verify）**：工具调用结果校验、Linter——**错误可能发生**，但会被检测到并被处理。
  两者的关系是：**能用设计消除的错误，就不要留给验证去处理。** 因为设计消除的成本是一次性的，验证的成本是每次运行都要付（还可能有漏检）。这也解释了为什么“设计不好的工具会让再强的模型也频繁出错”——你把它留给模型去“小心一点”，而模型没有这种可靠性。
- **落到工程上，设计 ACI 时可以直接检查这几件事**（笔记补充的具体做法）：
  - **能不能让参数只能取合法值？**（枚举、格式约束、必填/选填明确）——对应 SIM 卡缺角。
  - **能不能让危险操作默认不发生？**（默认只读、删除需二次确认、预览而非直接执行）——对应微波炉门锁。
  - **名字能不能自解释？**（`delete_file` 优于 `df`，`search_web` 优于 `query`）
  - **描述里有没有给出“什么时候用/什么时候不用”？**（表格里 Tools 一栏写的“命名直观、参数有例子、边界有说明”正是这三点）
  - **出错时返回的是不是结构化信息？**（因为 1.2 节的 Verify 原则要求“只看结构化数据”，工具返回结构化字段就是在给验证留接口）
- **“每多一层抽象都会成为以后调试时新的盲区”与“保持透明”其实是一枚硬币的两面**：抽象层数 ↑ → 需要透传的信息 ↓ → 定位错误的难度 ↑。所以三原则可以合成一句话：**能用最简单的结构把话说清楚，就别把它藏进框架里。**
- **这三条原则与 Harness 五要素的关系**（笔记补充的映射，用来串联）：
  - “保持简单”→ 影响你**怎么实现** Harness（不要为了五要素齐全而造框架）；
  - “保持透明”→ 直接对应 **Context**（把规划步骤、执行日志、决策轨迹放进可观测的地方）；
  - “设计好 ACI”→ 直接对应 **Tools**（工具接口的质量标准）。
  原文在本节末尾说得很清楚：接下来的三节（模型选型、编排模式、护栏与安全性）“都不属于 Harness 五要素本身，但都是工程实践中绕不开的决策”——所以 1.2.2 是**原则**，1.2.3–1.2.5 是**决策**，1.2.6 再回到五要素的框架。

**易混点**

- **API vs ACI**：API 从**程序员视角**设计（读者会查文档）；ACI 从 **Agent 视角**设计（读者只有接口本身）。判据：**模型能不能只凭名称、描述、参数 schema 就正确使用它？**
- **防呆（Poka-yoke） vs 验证（Verify）**：前者让错误**不可能发生**（设计层面）；后者让错误**被发现并处理**（运行层面）。优先用前者。
- **“保持简单” vs “Harness 五要素都要有”**：不矛盾。五要素是**职责清单**（该考虑的方面），不是**实现清单**（都要写成框架模块）。简单实现同样可以覆盖五项职责。
- **“保持透明” vs “少暴露内部推理”**：原文要求暴露的是**规划步骤、执行日志和决策轨迹**（可审计的行为），这与 1.3 节“提议者—审核者”里“评判方看产物而非推理过程”并不冲突——**前者是给人看，后者是给验证机制用**。

**一句话记住**

> 三条原则：保持简单（别加没必要的抽象）、保持透明（把规划/日志/轨迹亮出来）、设计好 ACI（从模型视角设计接口，用防呆让错误无法发生）——因为模型和工具之间唯一的沟通通道就是接口本身。

### 1.2.3 如何选择模型

**原文要点**

- 本节回答一个实操问题：**在讨论编排模式之前，应该选什么样的模型来驱动 Agent？** 原文的定位声明：**模型是 Agent 的智能基座，选对模型往往比优化提示词更有效**；但**由于模型迭代极快，本节不推荐具体的模型版本，而是提供一些选型思路**。
- **要点一：闭源模型。** **目前 Agent 开发中最常用的两大闭源模型厂商是 OpenAI（GPT/o 系列）和 Anthropic（Claude 系列）**。闭源模型**通常在能力上领先**，但**成本较高且受限于厂商的 API 策略**。原文的操作建议：**选模型时不要只看排行榜，要在你自己的任务上做评估（见第七章）。**
- **要点二：开源模型。**
  - **在本书编写时，开源模型与闭源模型之间的差距在 6 个月以内，但成本显著低于闭源模型。**
  - **如果你的业务场景对模型能力没有很高要求，开源模型是务实的选择。**
  - 开源模型的优势：**成本低、可私有化部署、支持微调定制**，**适合对成本敏感或有数据合规要求的场景**。
  - **DeepSeek、Kimi、GLM 是国内 Agent 能力较强的模型。**
  - 原文的警告：**需要注意的是，不同模型在工具调用方面的能力差异很大，选型前务必在具体场景中测试。**
- **要点三：能力之外，还要考虑模型的策略边界。**
  - **模型在基准测试中具备某种能力，并不意味着承载它的产品一定允许用户调用这种能力。**
  - **不同厂商会对网络安全、模型蒸馏、模型提取、隐私数据和高风险操作设置不同的策略边界**；
  - **同一个任务在聊天产品、Coding Agent 和 API 中也可能得到不同结果。**
  - 因此，**模型选型不能只比较准确率、价格和速度**，还要在**自己的真实任务上测试**三件事：
    1. **模型是否愿意执行**；
    2. **接口是否暴露所需能力**；
    3. **服务条款是否允许这种使用方式**。
  - 补充要求：**对于业务关键任务，还应提前准备人工接管或其他合规模型作为替代路径。**
- **要点四：是否需要“思考（Reasoning）”。**
  - **绝大多数 Agent 需要支持思考（Reasoning）的模型。** 理由是：**Agent 需要进行多步思考、工具选择等复杂决策，不带思考能力的模型在这些任务上表现往往很差。**
  - **只有极少数场景例外**，原文举了两类：**只执行单步简单任务**；或**在 Computer Use 中仅需点击固定位置的简单 GUI 操作**——此时**不带思考的模型也能胜任**。
  - 结论：**但只要涉及多步思考或动态决策，就一定要选择支持思考的模型。**
- **要点五：关注输出速度和多模态能力**。原文说“除了成本，还有两个容易被忽视的维度”：
  1. **输出 token 的速度**：**Agent 往往需要多轮推理，每轮都要等待模型输出完成才能执行下一步，所以输出速度直接决定了端到端的响应延迟**——原文的算例是：**如果一个 Agent 任务需要 20 轮推理，每轮慢 2 秒就意味着总共多等 40 秒。**
  2. **多模态支持**：**如果你的 Agent 需要理解图片、音频或视频，多模态能力就是硬性要求，不同模型在这方面的差异很大。**

**辅导讲解**

- **这一节的“选型思路”其实是一张五问清单**，可以按顺序过（这是笔记对原文五点的重新组织，内容不出原文）：
  1. **闭源还是开源？**（能力 vs 成本/合规）
  2. **能不能用？**（策略边界：愿不愿意执行、接口暴不暴露、条款允不允许）
  3. **要不要思考？**（绝大多数要，极少数不要）
  4. **快不快？**（输出 token 速度 → 端到端延迟）
  5. **看得见什么模态？**（图片/音频/视频是硬性要求时）
  原文只列了“思路”而不推荐具体版本，原因写在开头：**模型迭代极快**。所以这份清单的价值恰恰在于它**不依赖具体型号**。
- **“不要只看排行榜”背后的机制**：排行榜（和各家的基准测试）测的是**通用任务上的平均能力**；而你的 Agent 会撞上的是**你的任务上的具体短板**——工具调用格式对不对、长链调用会不会退化（实验 1-2 提到 K3 能连续 200～300 次调用，而“多数模型在数十次调用后就开始退化”）、你的领域术语它认不认识。所以原文的措辞是“要在**你自己的任务上**做评估”。这与第七章的评估方法论是配套的。
- **“策略边界”这一条是纯工程老兵才会写的经验，值得展开理解**：它说的是**模型能力 ≠ 产品可用性**。三个层次都可能卡住你：
  - **厂商政策层**：对网络安全、模型蒸馏、模型提取、隐私数据、高风险操作，不同厂商设了不同的红线；
  - **产品形态层**：聊天产品、Coding Agent、API 三者的行为可能不同（原文原话）；
  - **合同层**：服务条款是否允许你这样用。
  这三层任何一层卡住，你选的“最强的模型”就用不了。原文给的对策很务实：**提前准备人工接管或其他合规模型作为替代路径**。这其实是 1.2.5 节“人工干预”和“护栏”在选型阶段的预演。
- **“20 轮 × 2 秒 = 40 秒”这个算例为什么值得记住？** 因为它把“输出速度”从一个模糊的体感指标变成了**可直接估算的延迟公式**：**端到端延迟 ≈ 轮数 × 每轮输出时间 + 工具执行时间**。据此可以推出几个反直觉的结论（笔记补充的推论）：
  - **长程 Agent 对输出速度的敏感度是线性放大的**——单轮快 1 秒，20 轮就省 20 秒；
  - **相比之下，工具执行时间在很多场景里反而是小头**（一次搜索几秒、一次代码执行几百毫秒），所以“选一个输出快但稍弱的模型”在长程任务上未必是坏选择；
  - **减少轮数（更好的规划、更少的返工）往往比提高单轮速度收益更大**——这正好是 1.2.4 节“编排模式”要优化的东西。
- **“思考模式”的取舍边界**：原文给的两个例外很具体——**单步简单任务**和 **Computer Use 中仅需点击固定位置的简单 GUI 操作**。它们的共同点是**没有动态决策的成分**（动作序列可以事先确定）。反过来说：**只要“下一步做什么”依赖上一步的观察结果，就需要思考模型。** 这跟 ReAct 循环的必要性是同一件事。
- **开源 vs 闭源的取舍不是“能力差距”而是“差距换成本”**：原文给的时间量度是“**差距在 6 个月以内**”，给的成本判断是“**显著低于**”。工程决策就是：你的任务能不能容忍落后 6 个月的能力？能，就换成本、私有化部署和微调自由度；不能，就付闭源的钱并接受 API 策略约束。原文还提了一个附加条件：**对成本敏感或有数据合规要求的场景**——后一条往往是硬约束（数据不能出境/不能上第三方），此时开源就是唯一选项，与能力无关。
- **工程上的坑**：
  - **只测“能不能答对”，不测“愿不愿意做、接口暴不暴露”**。这三件事（原文列的测试项）必须分开测。
  - **拿聊天产品的表现推断 API 表现**。原文明确说“同一个任务在聊天产品、Coding Agent 和 API 中也可能得到不同结果”。
  - **用“工具调用能力”当成模型的通用能力**。原文单独点了一句“**不同模型在工具调用方面的能力差异很大**”——一个在对话上很强的模型，工具调用可能很糟。所以选型测试必须是**带工具的**测试。

**易混点**

- **模型能力 vs 产品可用性**：能力是“基准测试上会不会”；可用性是“这个厂商的产品/接口/条款允不允许你这么做”。原文的判据是“模型是否愿意执行、接口是否暴露所需能力、服务条款是否允许”。
- **开源模型 vs 开放权重模型**：原文本节统一用“开源模型”这个说法，并强调它的三个实际好处：成本低、可私有化部署、支持微调定制。笔记按原文用词。
- **“支持思考” vs “始终开启思考”**：本节说的是“选**支持**思考的模型”；实验 1-2 里 Kimi K3 的规格是“**始终开启**的思考模式”——前者是能力选项，后者是该模型的具体形态。
- **输出速度 vs 首 token 延迟**：原文讨论的是“**输出 token 的速度**”（因为“每轮都要等待模型输出完成才能执行下一步”）。对多轮 Agent 来说，决定端到端延迟的是**整轮输出耗时**，而不只是第一个 token 多快。

**一句话记住**

> 选模型五问：闭源还是开源、策略边界允不允许、要不要思考、输出够不够快、模态够不够用——而这一切都不能只看排行榜，必须在自己的任务上、带工具地测。

### 1.2.4 编排模式：工作流与自主

**原文要点**

- **编排模式的定位**：原文说，**编排模式是 Harness 中“上下文与工具”层面的组织方式**——它决定了
  - **上下文如何在 LLM 调用之间流动**；
  - **工具如何被调度**；
  - **Agent 的执行路径是预先设定还是动态生成**。
- **演进前提**：**Agent 系统的编排方式经历了从简单到复杂的演进过程，每种模式都有其适用场景和相应的取舍。** 原文引用的经验来源（脚注 5）：**根据 Anthropic 与数十个团队合作构建 LLM Agent 的经验，最成功的实现往往不是使用复杂的框架，而是采用简单、可组合的模式。**
- **总原则：从简单到复杂**。原文给出的决策顺序是：
  1. **首先考虑单个 LLM 调用。如果通过优化提示词和上下文示例就能解决问题，就不要引入 Agent 系统。**
  2. **当需要多步骤处理时，对于可以清晰分解为固定子任务的场景，考虑使用工作流。**
  3. **只有当需要动态决策和灵活的执行路径时，才使用自主 Agent。**
  - 原文的提醒：**需要记住的是：Agent 系统通常会用延迟和成本换取更好的任务性能，应该谨慎权衡这种交换是否值得。**
- **一个常见的反面例子**：**一开始就构建一个非常复杂的工作流或多 Agent 系统**。原文举的具体案例是“**从百万条聊天记录中提炼个人记忆**”：
  - 一些 AI 模型很容易迅速画出一条“看似严谨”的流水线：**先切分对话片段，再依次安排提取、证据核验、身份解析、记忆整理和合并复核 Agent，最后建立事实图、覆盖账本和不可变版本**。
  - 原文的评价：**每个部件单看都有道理，组合起来却是非常低效、不可靠的**。
  - 原因分析：**因为复杂工作流的执行拓扑是固定的，遇到新的例外，系统很容易继续增加节点，架构越来越复杂，通用性却越来越差。模型原本可以根据上下文处理的语义判断，反而被工作流写死了。**
- **因此的结论**：**Harness 很重要，不等于 Harness 越复杂越好。**
  - 原文引用 **Manus 官网用“Less structure, more intelligence.”概括这种取舍**（脚注 6：Manus, “Less structure, more intelligence.” <https://manus.im/>）：**先给一个能力足够的 Agent 清晰的目标、必要的上下文和可组合的工具，用自然语言告诉它如何像人一样查证、比较、处理冲突；程序只固化权限、不得覆盖原始材料、原子发布等必须始终成立的边界。**
  - **只有业务约束本身要求，或评估反复暴露出某类稳定失败时，才把对应步骤升级为专门的验证器、独立 Agent 或确定性流程。**
  - 原文本节的点睛句：**好的结构不是替 Agent 预演全部思考，而是守住边界，并把边界内的决策空间还给模型。**

#### 1.2.4.1 工作流模式：确定性的编排

**原文要点**

- **定义**：**工作流（Workflow）是通过预定义的代码路径来编排 LLM 和工具的系统。它的执行路径是确定性的，由开发者预先设计好**——**每一步做什么、下一步去哪里，都是代码写死的，LLM 只在每个节点内部负责理解和生成。**
- **订机票 Agent 的例子**：工作流可以设计为**四个固定节点**：
  1. **核实用户身份**——调用身份验证 API，确认用户是谁；
  2. **搜索可用航班**——根据用户需求查询航班数据库；
  3. **完成付款**——调用支付接口扣款；
  4. **确认预订**——调用预订 API 锁定座位，向用户发送确认信息。
  - 原文说明：**每个节点内部可以使用 LLM**（例如用自然语言理解用户的出行需求），**但节点之间的流转顺序是代码固定的**——**系统不会在付款完成之前去预订座位，也不会在身份核实之前开始搜索航班**。
- **工作流模式的两个核心优势**：
  1. **严格的流程控制**：开发者可以确保**关键步骤不被跳过或乱序执行**，例如“**付款前不能预订**”这类业务规则**通过代码强制执行，不依赖 LLM 的判断**。
  2. **安全性**：**由于执行路径是确定的，提示注入或模型犯错最多只能影响当前节点内部的处理，无法让 Agent 跳到不该执行的分支——攻击面被限制在单个节点内。**
- **工作流的主要局限是缺乏变通性**：**当出现预设流程未覆盖的情况时**（原文举例：**用户在付款环节临时想改签、或航班突然取消需要推荐替代方案**），**固定的节点路径无法灵活应对，只能走预设的异常处理分支或将控制权交还给人类。**
- **最简单的工作流例子：文生图。**
  - 问题：**用户的需求往往就是一句大白话**（例如“帮我画一个 AGI 实现以后程序员的工作场景”）；**可 Stable Diffusion 这类文生图模型只接受特定风格的提示词**——**逗号分隔的英文标签、质量词、负面提示词**。
  - 所以工作流要在用户和生图模型之间安排**两个固定节点**：
    1. **提示词改写**——用 LLM 把用户的自然语言需求改写成文生图模型习惯的提示词格式。对于上面的例子，“AGI 实现以后程序员的工作场景”是个**很宽泛的需求**，因此 **LLM 还需要认真思考**（原文举例：“AGI 实现之后程序员不需要写代码了，因此应该画一个程序员在海边晒太阳，通过脑机接口指挥 AI 员工”），然后给出**具体的场景描述**。
    2. **图片生成**——用改写后的提示词调用文生图模型，得到图片。
  - 原文的三条判断：
    - **执行路径是代码写死的。**
    - **这个工作流里的 LLM 节点做的是翻译，即把人话转成工具听得懂的输入格式，它存在的原因是文生图模型“听不懂人话”。**
    - **这种专门给工具（或模型）的能力短板打补丁的 Harness 代码，不妨称为适配层。**
  - **“但如果”**：如果把生图工具换成**具备原生图像生成能力的多模态模型**，比如 **Nano Banana 2、GPT-Image 2**，**就不再需要提示词改写了**——**不管用户怎么措辞，模型自己就能听懂、直接出图。**

**实验 1-4 ★：文生图工作流与原生图像生成的对照**（印刷 p.23）

- **实验做法**：让**同一句大白话需求走两条路线**。
  - **工作流路线**：LLM 先把需求**改写成 Stable Diffusion 风格的提示词**，再调文生图模型出图；
  - **原生路线**：把这句话**原样**发给支持原生图像生成的多模态模型（如 **GPT-Image 2**），**一次调用直接出图**。
- **对照方式**：**看提示词改写节点把原始需求改成了什么样子，以及两条路线出的图谁更贴近原始需求。**
- **值得分两类需求对照**：一类是**描述具体的**（比如指定了海报文案）；另一类是**宽泛的**（比如上面的 AGI 工作场景），**这类需求下工作流路线仍可能有自己的优势**。
- **实验结论**：**Harness 里那些给模型能力短板打补丁的部分，会随着模型变强被模型自己内化。** 原文随即盘点了“**仅仅在本书第一章中，这样的事就已经发生了好几轮**”：
  1. **few-shot 示例、“让我们一步一步思考”之类的提示词技巧**，被**指令微调**和**推理模型**内化了；
  2. **输出格式修复、JSON 解析容错**，被**结构化输出和原生工具调用**内化了；
  3. **文生图的提示词改写**，被**模型的原生多模态理解与生成能力**吃掉了。
- 原文的总结句：**每一轮内化，消灭的都是“翻译”和“脚手架”这类适配层代码。**

**辅导讲解**

- **编排模式的三个要素是判断一个系统的钥匙**：**上下文怎么流动、工具怎么调度、路径是预设还是动态生成**。前两条决定“系统长什么样”，第三条决定“它属于工作流还是自主 Agent”。**工作流与自主 Agent 的唯一本质区别就是第三条**——这一点在 1.2.4.2 节被原文明确写出。
- **“从简单到复杂”的三级阶梯**（原文原话逐级）：
  1. 单个 LLM 调用（能靠提示词和上下文示例解决就别上系统）；
  2. 工作流（能清晰分解为固定子任务）；
  3. 自主 Agent（需要动态决策和灵活执行路径）。
  把这条阶梯记成**成本阶梯**更好理解：每上一级，**延迟 ↑、成本 ↑、可预测性 ↓、任务性能上限 ↑**。原文那句“Agent 系统通常会用延迟和成本换取更好的任务性能，应该谨慎权衡这种交换是否值得”就是这条阶梯的注解。**换句话说，“上自主 Agent”是一次交易，不是一次升级。**
- **那个反面例子（从百万条聊天记录中提炼个人记忆）是本节最有价值的反例**，因为它演示了复杂工作流**为什么会自己长大**：拓扑固定 → 遇到新例外 → 加节点 → 拓扑更复杂 → 更不适应新例外 → 再加节点。原文的措辞是“**架构越来越复杂，通用性却越来越差**”。这个“通用性变差”的机制值得想清楚：**你每加一个节点，就是在为某个已知例外写一条确定性规则；而规则越多，模型原本可以用语义判断灵活处理的空间就越小**。原文的结论句是“**模型原本可以根据上下文处理的语义判断，反而被工作流写死了**”。
- **Manus 那句 “Less structure, more intelligence.” 的正确读法**：它**不是“不要结构”**，而是“**结构放在边界上，不放决策路径上**”。原文紧接着的展开说得很精确：
  - **程序要固化的**：**权限、不得覆盖原始材料、原子发布**——这些是“**必须始终成立的边界**”；
  - **交给 Agent 的**：**清晰的目标、必要的上下文、可组合的工具**，加上**用自然语言告诉它如何像人一样查证、比较、处理冲突**。
  所以正确的分工是：**确定性的部分（约束）用代码写死，语义判断的部分（决策）交给模型**。这也是 1.2 节 Harness 五要素的另一种表述——约束归 Harness，决策归 Model。
- **“升级为验证器/独立 Agent/确定性流程”的触发条件**原文给了两个，都很关键：
  1. **业务约束本身要求**；
  2. **评估反复暴露出某类稳定失败**。
  注意第二条里的“**反复**”和“**稳定**”——不是出一次错就加节点，而是**评估**显示这是一个**可复现的模式**。这就把“何时变复杂”从一个主观判断变成了**由评估数据驱动**的决策。这与第七章、第九章是连着的。
- **工作流的两个优势其实指向同一件事：攻击面**。“严格的流程控制”是从**正确性**角度说的（关键步骤不被跳过/乱序）；“安全性”是从**安全**角度说的（攻击面被限制在单个节点内）。**它们都来自“执行路径确定性”这一个事实。** 理解这一点很重要：工作流的安全性不是一个附加属性，而是确定性拓扑的直接推论——因为模型**没有能力改变路径**，所以它**没有能力跳到不该去的地方**。
- **文生图这个例子与“适配层”这个概念**值得单独记住：
  - **适配层（adaptation layer）的定义**（原书用语）：**专门给工具（或模型）的能力短板打补丁的 Harness 代码**。
  - 判断一个 Harness 组件是不是适配层，只要问一句：**“如果模型/工具本身具备这个能力，这段代码还需要吗？”** 需要 → 不是适配层（是真职责）；不需要 → 是适配层。
  - 按这个判据，“提示词改写”是适配层（因为多模态模型自己能听懂）；而“权限控制”不是适配层（再强的模型也不该自己决定能不能删库）。
  - 这也解释了为什么**适配层会不断被模型吃掉**——因为它的存在理由就是模型/工具的能力短板，而短板会被补上。
- **实验 1-4 的对照设计有一处很细的地方**：原文说要**分两类需求**对照——**描述具体的**（如指定海报文案）和**宽泛的**（如 AGI 工作场景），并指出**宽泛需求下工作流路线仍可能有自己的优势**。这个补充很重要，它防止读者把这个实验读成“原生路线全面胜出”。可能的机制（笔记补充的解释）是：宽泛需求下，**改写节点相当于一次“创意扩写 + 结构化”**，它把模糊需求落成具体画面，这是“翻译”之外还附带的增益；而原生路线虽然能直接听懂，但生成的具体性可能没那么高。原文用“**仍可能有**”这种谨慎措辞，说明这是一个值得读者自己动手验证的开放结论。
- **三条“被内化”的清单是本章最实用的历史规律**：

  | 曾经的 Harness 适配层 | 被什么内化 |
  | --- | --- |
  | few-shot 示例、“让我们一步一步思考”类提示词技巧 | 指令微调、推理模型 |
  | 输出格式修复、JSON 解析容错 | 结构化输出、原生工具调用 |
  | 文生图提示词改写 | 原生多模态理解与生成能力 |

  读这张表的方法：**每一条都是“当年必须写在外部、后来写进了模型”**。原文的总结是“每一轮内化，消灭的都是‘翻译’和‘脚手架’这类适配层代码”。**给你的工程启示是：不要把适配层当资产去投资——它可以用来解决当下问题，但不是护城河。**
- **工程上的坑**：
  - **用工作流去处理会不断出现例外的问题**。症状就是原文描述的那个反面例子：节点越加越多、通用性越来越差。
  - **该用工作流的地方用了自主 Agent**。涉及付款、退款、生产部署这类强业务规则的场景，自主 Agent 的灵活性反而变成风险来源（“付款前不能预订”这种规则不应该依赖 LLM 的判断）。
  - **把“翻译节点”当成永久架构**。今天需要改写提示词的场景，明天可能就被多模态模型吃掉了——**适配层要设计成可摘除的**。

**易混点**

- **工作流 vs 自主 Agent**：唯一本质区别是**执行路径是预先设定还是动态生成**。工作流里 LLM 只在**节点内部**工作；自主 Agent 里 LLM 还决定**节点怎么走**。
- **“确定性” vs “没有 LLM”**：工作流**可以**包含 LLM 节点（订机票例子里每个节点内部都能用 LLM）。确定性指的是**节点之间的流转顺序**由代码固定，不是指节点内部不用模型。
- **适配层 vs Harness 保障机制**：适配层是“给能力短板打补丁”，会随模型变强被内化；保障机制（约束/验证/纠正）不是补丁，短期不会被内化（详见 1.1.3.1 的《苦涩的教训》讨论）。
- **提示词改写节点 vs 提示工程**：前者是一个**架构位置**（用户和生图模型之间的固定节点），后者是一种**实践**（优化提示词）。原文说这个节点“做的是翻译”——它的职责是格式转换，不只是措辞优化。

**一句话记住**

> 编排模式看三件事：上下文怎么流动、工具怎么调度、路径是写死的还是现定的；先试单次调用，再试工作流，最后才上自主 Agent——而“给模型短板打补丁”的适配层，会随模型变强被一层层吃掉。

#### 1.2.4.2 自主Agent：动态自主决策

**原文要点**

- **定义与核心区别**：**当工作流的固定路径无法满足需求时，我们就需要自主 Agent（Autonomous Agent）。自主 Agent 与工作流的核心区别在于：执行路径不是预先定义的，而是 Agent 根据环境反馈实时决定的。**
- **订机票的对照例**：**自主 Agent 不需要预定义四个固定节点。** 用户说“**帮我订下周三去上海的机票**”，Agent 会自行决定：**先搜索航班 → 发现需要登录，于是先核实身份 → 再回来搜索 → 发现最便宜的航班需要转机 → 主动询问用户是否接受 → 用户说不要转机 → Agent 调整搜索条件……**
- **对能力的要求**：这意味着自主 Agent **需要具备自主规划的能力**——**自主决定执行步骤**；**还需要能识别失败、调整策略，而不只是在出错时停下来**。
- **但自主性不等于无限制**：**必须设计明确的停止条件**（原文列了三类：**任务完成、达到最大迭代次数或遭遇不可恢复的错误**），**否则 Agent 容易陷入死循环或过度执行**。
- **从实现角度看**：**自主 Agent 本质上就是在一个循环中使用工具的 LLM，通过持续获取环境反馈来推进任务——这正是前面介绍的 ReAct 循环。**
- **常见的退出条件**（文字版，原文列了三项）：**调用最终输出工具、模型返回没有任何工具调用的响应，或者遇到错误、达到最大轮数。**
- **图 1-6 给出的退出条件**（图形版，原文列了五项，以“任一满足”为准）：① **任务完成**；② **调用 `final_answer`**；③ **无工具调用返回**；④ **错误次数超限**；⑤ **达到最大轮次**。

> 图 1-6（原文插图）：图题是“**自主 Agent 的执行循环**”。图的主干是一个**三环节的环**：① **思考（Reasoning）**，旁边标着示例文本“还需更多信息”；② **行动（Acting）**，示例是 `web_search(...)`；③ **观察（Observing）**，示例是 `tool_result: "..."`。三个环节首尾相连形成循环。从这个环引出一条“**判断依据**”的箭头，进入一个判断框“**满足退出条件？**”：**否** → “**继续下一轮循环**”（回到 ① 思考）；**是** → “**输出最终结果**”。图的一侧单列了“**退出条件（任一满足）**”，共五条：① 任务完成、② 调用 `final_answer`、③ 无工具调用返回、④ 错误次数超限、⑤ 达到最大轮次。这张图的读法要点是：**三环节是循环体，五条退出条件是唯一的出口**——而且五条里既有“正常完成”（① ② ③），也有“异常兜底”（④ ⑤），说明退出条件的设计本身就是安全机制的一部分。

- **适用场景**：**自主 Agent 特别适用于开放式的问题——这类问题难以预测所需的步骤数量。** 原文给出的典型应用场景：
  - **Coding Agent 解决 SWE-bench（Software Engineering Benchmark，一个评估 Agent 自动修复真实 GitHub Issue 能力的基准测试）任务**；
  - **“计算机使用”（Computer Use）Agent 像人类一样操作计算机界面**；
  - **需要迭代搜索和分析的研究任务**。
- **代价与部署要求**：**自主性也带来了更高的成本和潜在的复合错误风险**。因此在部署自主 Agent 时，原文给了三条要求：
  1. **必须在沙盒环境中进行充分的测试**；
  2. **设置适当的护栏和监控机制**；
  3. **在关键决策点考虑加入人机协作的检查点**。

**辅导讲解**

- **两个订机票例子的对照是本节最好的教具**：同一个任务（订机票），工作流是“**四个固定节点按序执行**”，自主 Agent 是“**搜索 → 需要登录 → 核实身份 → 回来搜索 → 发现要转机 → 问用户 → 调整条件 → …**”。差别不在**节点本身**（两者都要搜索、核实、付款），而在**谁决定下一步走哪**：工作流由代码决定，自主 Agent 由模型根据环境反馈决定。**记住这个对照，就记住了两个模式的分界线。**
- **“识别失败、调整策略，而不只是在出错时停下来”**——这半句是自主 Agent 的能力门槛。一个只会“遇到错误就终止”的系统不是自主 Agent，只是一个会调工具的单次调用。原文在实验 1-2 里给了一个可量化的对照指标：**长链工具调用的稳定性**——Kimi K3“能连续执行 200～300 次工具调用而保持思考的一致性，远超多数模型在数十次调用后就开始退化的表现”。所以**“能跑多长的链”是自主 Agent 的一个实际硬指标**。
- **“停止条件必须显式设计”这条为什么是本节最该记住的工程要点？** 因为循环的默认行为是“一直转下去”。图 1-6 列的五条退出条件里，只有 ① ② ③ 是“正常完成”路径，④ ⑤ 是**兜底**：
  - ④ **错误次数超限**：防的是“反复重试直到耗尽迭代预算”（实验 1-1 里“无工具结果”那组的症状）；
  - ⑤ **达到最大轮次**：防的是“模型一直在做微小调整但永远不收敛”。
  没有 ④ 和 ⑤，一个卡住的 Agent 会**一直烧钱**。这就是为什么原文把“必须设计明确的停止条件”写成了一句独立的判断，并警告“否则 Agent 容易陷入死循环或过度执行”。
- **文字版三项 vs 图形版五项的关系**：文字版是“**常见的退出条件包括**”（列举），图形版是“**退出条件（任一满足）**”（完整清单）。二者不冲突，图形版是超集：文字版里的“调用最终输出工具”对应图里的“② 调用 `final_answer`”，“模型返回没有任何工具调用的响应”对应“③ 无工具调用返回”，“遇到错误、达到最大轮数”对应“④ 错误次数超限、⑤ 达到最大轮次”，图里多出的是“① 任务完成”。注意“① 任务完成”和“② 调用 final_answer”在实践里往往是同一件事的两种判定方式——**前者靠外部判断（任务目标达成了），后者靠模型显式声明**。
- **“复合错误风险”这个概念值得展开**：自主 Agent 的每一轮输出都建立在前面所有轮的结果之上。**单轮错误率 p，走 N 轮不出错的概率大约是 $(1-p)^N$**——轮数越多，整体成功率衰减得越快（这个式子是笔记补充的粗略模型，不是原文公式）。所以自主 Agent 的可靠性问题**不是线性的，是累积的**。这也解释了为什么原文要求“在沙盒环境中充分测试”“设置护栏和监控”“在关键决策点加入人机协作检查点”——**这三条都是用来截断误差传播链的**：沙盒限制出错后果、护栏/监控及早发现、人在回路在关键节点强制纠偏。
- **SWE-bench 为什么是自主 Agent 的典型场景？** 原文给的理由是“开放式的问题——这类问题难以预测所需的步骤数量”。修一个真实的 GitHub Issue，可能是改一行、也可能是改五个文件加跑测试，
  **没法事先写好固定节点**。同理，Computer Use（界面状态千变万化）和迭代研究（搜到什么决定下一步搜什么）也都是“步骤数不可预测”的。反过来看：**如果一个任务的步骤数可以事先写清，那它就是工作流的活。**
- **工程上的坑**：
  - **只设“任务完成”一个退出条件**。一旦模型判断不了“完成”，循环就永远不结束。必须同时配 ④ ⑤ 两条兜底。
  - **把最大轮次设得过大以“保险”**。轮次上限是**成本熔断器**，设得太大等于没有。合理的上限应该由“这个任务的合理步数量级”推出来（可参照 Agent 产品表里各产品策略一栏描述的步数粒度，多数是四五步的量级）。
  - **不给自主 Agent 配沙盒**。原文把“必须在沙盒环境中进行充分的测试”写成了部署前置条件，不是建议。

**易混点**

- **“自主规划” vs “工作流里的 LLM 节点”**：前者是**决定执行哪些步骤、按什么顺序**；后者是**在被指定的那一步里完成理解和生成**。订机票例子里，自主 Agent 会“调整搜索条件”，工作流不会。
- **“最大迭代次数” vs “最大轮次”**：同一件事的两种说法（原文在不同位置分别用了“最大迭代次数”和“最大轮数/最大轮次”）。
- **退出条件 vs 终止条件**：图 1-6 用“退出条件（任一满足）”——**任一**满足就退出，不是全部满足。这与 1.3 节“边界集 + 保留集”那种“两个都要过”的验证逻辑正好相反，别记混。
- **自主性 vs 无限制**：原文明确写“但自主性不等于无限制”。自主性指的是**路径由模型决定**，不是“没有边界”；边界由停止条件、护栏、沙盒共同提供。

**一句话记住**

> 自主 Agent = 用工具的 LLM 跑在 ReAct 循环里，路径由环境反馈实时决定；它适合“步骤数无法预测”的开放问题，但**必须显式设计退出条件**（正常完成 3 条 + 异常兜底 2 条），否则会烧钱到死。

#### 1.2.4.3 两种模式的选择与混合

**原文要点**

- **基本判断**：**实践中，工作流和自主 Agent 并非非此即彼**——**很多系统会混合使用两种模式**：**关键的、有严格合规要求的流程用工作流来确保可靠性，需要灵活决策的部分切换到自主模式。**
- **混合方式一：同一系统内并存。** 原文的例子是 **n8n**——**一个成熟的工作流自动化开源框架**，**开发者通过可视化界面拖拽功能组件来构建 Agent**，**可以在同一个系统中同时使用工作流节点和自主 Agent 节点**。
- **混合方式二：先自主生成工作流，再按工作流执行。** 原文的说法是：**还有一种混合方式是先由自主 Agent 把工作流写出来，再由工作流去执行。**
  - 机制：**Agent 读完任务后自行决定拓扑并生成一段编排代码；代码一旦生成，执行阶段就退回工作流的确定性。**
  - 收益：**这样既保留了自主 Agent 面对未知任务的灵活性，又不必让模型在每一次调度上都参与决策。**
  - 原文注明：**第十章会详细讨论这种形态。**

> 图 1-7（原文插图）：原文只保留了图注“**图 1-7 n8n 工作流编辑器界面**”。由于纯文本提取后图本身没有保留，笔记只能说明：这是一张 n8n 工作流编辑器的界面截图，用来给上面“通过可视化界面拖拽功能组件来构建 Agent”这句话配一个直观印象。**界面的具体布局、画布上画了哪些节点、节点之间的连线形态，原文的纯文本中没有保留，笔记不做推测。**

**辅导讲解**

- **“并非非此即彼”这句话的分量在哪？** 因为它把 1.2.4.1 和 1.2.4.2 从“二选一”变成了“**按流程分段选**”。真实的业务系统通常是**混合体**：一整条链路里，合规相关的那几段用固定节点（付款前不能预订、大额操作要人工确认），开放判断的那几段用自主循环（怎么找航班、怎么找到最优方案）。**所以正确的问法不是“我该用哪种模式”，而是“这条链路的哪几段该固定、哪几段该放开”。**
- **混合方式一（n8n 式）的本质是“节点类型可以混”**：工作流引擎里既可以放**确定性节点**，也可以放**一个自主 Agent 节点**（在这个节点内部跑完整的 ReAct 循环）。这样做的好处是**边界清晰**：自主性被关在一个节点里，节点的输入输出是确定的，外层的合规流程依然由代码保证。这与 1.2.4.1 说的“工作流把攻击面限制在单个节点内”是同一个安全论点的反向应用——**你可以在需要灵活性的地方开一个自主的口子，而这个口子的边界是明确的。**
- **混合方式二（Agent 写工作流）是一个很值得琢磨的设计**，它同时取了两种模式的**长处**，代价是引入了**两个阶段**：
  - **规划阶段**：自主 Agent 面对未知任务，自行决定拓扑、生成编排代码——**灵活**；
  - **执行阶段**：代码已经写定，按工作流的确定性执行——**不必让模型在每一次调度上都参与决策**（省 token、省延迟、可复现、可审计）。
  你可以这样理解（笔记补充的类比）：**这相当于“编译”——把一次昂贵的动态决策编译成一段低成本的确定性执行**。它的风险也很清楚：**一旦编译错了，执行阶段会忠实地把错误执行到底**，而且不像运行时那样有机会中途纠正。所以这种形态对“规划阶段的质量”要求更高，通常需要配合验证机制（1.2.5 的护栏、第七章的评估）。原文注明第十章会详细讨论，读者在此记住这个模式的名字和取舍即可。
- **工程上的用法**：可以按一条简单的规则做切分——**把“必须始终成立的边界”（权限、金额上限、不可逆操作、合规顺序）交给工作流，把“取决于上下文内容的判断”（找什么、怎么比较、要不要追问）交给自主 Agent**。这正是 1.2.4 节开头 Manus 那句话的工程化表述：“程序只固化……必须始终成立的边界。”
- **不适用/注意**：混合不是免费的。它引入了**两套心智模型**（确定性流程 + 自主循环），调试时要在两种执行语义之间切换；n8n 这类工具的“低代码”优势在复杂逻辑下也会变成表达力的限制。原文对这个取舍没有下结论，只提供了两种形态，读者应按自己的合规要求和团队构成来选。

**易混点**

- **“混合使用两种模式” vs “两种模式选一个”**：原文明确说“并非非此即彼”。很多系统**同时**包含两者。
- **混合方式一 vs 混合方式二**：前者是**空间上的混合**（同一系统里并存工作流节点和自主节点，同时运行）；后者是**时间上的混合**（先自主规划生成代码，再确定性执行，分两个阶段）。
- **“Agent 生成编排代码” vs “Coding Agent”**：前者生成的是**自己下一步的执行计划**（编排拓扑）；后者生成的是**给用户/项目的代码产物**。两者都用代码生成能力，但目标不同。

**一句话记住**

> 两种模式可以混合：要么同一张流程图上既有工作流节点也有自主节点（n8n 式），要么先让自主 Agent 把工作流“编译”出来、再按确定性执行——切分依据是“哪些是必须始终成立的边界，哪些是取决于上下文的判断”。

### 1.2.5 护栏与安全性

**原文要点**

- **定义与作用**：**护栏（Guardrails）构成了保障 Agent 行为安全可控的分层防线**，可用于管理
  - **数据隐私风险**（例如**防止系统提示泄露**）；
  - **声誉风险**（例如**确保模型行为与品牌形象一致**）。
- **建设方式**：**实践中可以先针对已识别的风险设置护栏，再在发现新漏洞时逐步添加。**
- **本节的范围声明**：**本节只做高层次的概览，确立全书统一的分层骨架**；具体的实现细节将在
  - **第二章**（上下文层：**提示注入防护**）、
  - **第四章**（执行层：**工具权限控制**）、
  - **第五章**（执行层与数据层：**代码执行安全、信任边界下移**）
  分别展开，**初次阅读无需深究**。
- **组合使用**：**单个护栏不太可能提供足够的保护，多个专门的护栏组合使用，才能构建出更有韧性的 Agent 系统。**
- **另一类失败：误拒绝。** 为了降低危险请求被放行的概率，**模型可能同时拒绝一部分合法但形式敏感的任务**，例如**经过授权的安全测试、模型蒸馏研究**。因此，**护栏评估不能只测试“应当拒绝的请求是否被拦截”，还要测试“明确允许的请求是否能够正常完成”。**

#### 1.2.5.1 护栏类型

**原文要点**

- **三层的划分依据**：按防护位置可以分为三层：**上下文层、执行层、数据层**。原文特别强调一个容易误解的点：**这三层不是按请求处理的先后顺序排的，而是按被绕过的难度排的——越靠下的层越不依赖模型自己的判断，因此越难被一次成功的攻击穿透。** 原文的定位声明：**本书后面所有的安全讨论都挂在这棵树上。**
- **上下文层护栏：管的是模型能看到什么，在内容进入上下文之前拦截**，通常包含**四种机制**：
  1. **相关性分类器**：**标记偏离主题的查询**，比如编程助手收到“**帝国大厦有多高？**”这类无关问题。
  2. **安全分类器**：**检测越狱（Jailbreak，即诱导模型绕过安全限制）和提示注入（Prompt Injection，即在输入中嵌入恶意指令）**，**两者的关键区别在于：越狱是用户自己试图绕过模型的安全限制，提示注入则是攻击者通过外部数据（如网页内容、文档）间接操纵模型行为。**
  3. **内容审核**：**标记有害或不当的输入**，如**暴力、歧视性内容**。
  4. **基于规则的保护**：**采用确定性措施**，包括**黑名单、输入长度限制、正则表达式过滤器**，用以**防范 SQL 注入等已知威胁**。
  - 原文补充：**来源标注与“指令/数据”分离也属于这一层，第二章会展开。**
- **上下文层的代表性工业实践：Anthropic 的 Constitutional Classifiers。** 原文说其核心机制有**三点**：
  1. **规则驱动**——**用自然语言写成的规则（明确规定哪些内容允许、哪些禁止）生成合成训练数据，训练输入输出分类器**；
  2. **上下文联合判断**——**新一代系统把用户提问和模型回答放在一起检查**，因为**有些回答单独看毫无问题（如“如何使用食品调味料”），只有对照提问才能发现“食品调味料”其实是化学试剂的暗语**；
  3. **两级筛查**——**先用一个极轻量的探针（直接读取模型内部激活，几乎零成本）检查所有对话，发现可疑之处再交给更强的分类器复审，而不是直接拒绝**。这样一来，**第一级即使误报较多也不影响用户体验，成本也大大降低**。
- **上下文层的结构性上限**（原文的关键判断）：**处在同一个上下文里的 Agent，很难判断自己是否已经被注入。所以上下文层只能降低攻击成功率，给不出保证——这正是必须有下面两层的原因。**
- **执行层护栏：管的是模型能做什么，在动作真正生效之前验证。**
  - **其核心是工具风险评级**：**根据操作是否可逆、权限等级、财务影响，为每个工具标注风险等级（低/中/高），高风险操作需额外审查或人工确认。**
  - **关键在于这类复核必须由上下文之外的机制完成**——**独立的审查进程、最小权限凭证、沙盒隔离、人在回路**——**否则它会和被注入的 Agent 一起沦陷。**
  - **输出检查也属于这一层**：因为**返回给用户的回复本身也是一次动作**（第四章把它归为**用户沟通工具**），所以
    - **PII 过滤器**审查输出中的个人身份信息（如**身份证号、手机号**），**防止不必要暴露**；
    - **输出验证**则通过内容检查**确保回复与品牌价值一致**。
- **数据层护栏：管的是世界最终能被改成什么样。**
  - 它把“**谁能对哪条数据做什么**”交给**一层稳定的、经过人类审查的机制**强制执行，具体包括：
    - **数据库的行级安全策略**；
    - **约束与校验器**；
    - **受控视图与存储过程**；
    - 以及**由受信任运行时绑定、无法被伪造的访问上下文**。
  - 这一层的价值：**它不依赖上面两层是否正确**——**即使提示注入得手、生成的代码完全漏写了权限判断，越权操作仍会在数据层被拒绝。**
  - 原文注明：**第五章会以动态生成软件为例展开这一层。**

> 脚注 8（印刷 p.26）：Anthropic. “Next-generation Constitutional Classifiers: More efficient protection against universal jailbreaks”, 2026. <https://www.anthropic.com/research/next-generation-constitutional-classifiers>；论文：Cunningham et al., “Constitutional Classifiers++: Efficient Production-Grade Defenses against Universal Jailbreaks”, arXiv:2601.04603

#### 1.2.5.2 人工干预

**原文要点**

- **定义与价值**：**人工干预（Human in the loop，又称人在回路）是一个关键的保护措施，它让 Agent 能够在不损害用户体验的情况下提升实际性能。** 原文特别指出时机：**这在部署早期尤为重要，有助于识别失败模式、发现边缘情况并建立健壮的评估周期。**
- **机制作用**：**实施人工干预机制，可以让 Agent 在无法完成任务时平稳地移交控制权。** 原文举了两个具体含义：
  - 在**客户服务**中，这意味着**将问题升级到人工客服**；
  - 对于 **Coding Agent**，这意味着**将控制权交还给开发者**。
- **通常有两种主要情况会触发人工干预**：
  1. **超过失败阈值**：**为 Agent 的重试次数或操作次数设置上限。如果 Agent 超过了这些限制，就应该升级到人工干预。**
  2. **高风险操作**：**涉及敏感、不可逆或高风险的操作时，应触发人工监督，至少在团队对 Agent 可靠性建立起足够信心之前是如此。** 原文的典型例子是**授权大额退款或付款等**。
- 原文随后收尾：**回到 Harness 五要素的主线——下面看看它和本书的结构是什么关系。**

**辅导讲解**

- **三层护栏的排序逻辑是本节最重要的一句话，也是最容易记错的一处**：**不是按处理先后，而是按被绕过的难度**。为什么？因为“请求处理的先后”是时间维度，“被绕过的难度”是**依赖维度**——原文的解释是“**越靠下的层越不依赖模型自己的判断，因此越难被一次成功的攻击穿透**”。把这条说清楚：
  - **上下文层**依赖模型的**判断力**（分类器、审核、规则都在模型/上下文这一侧）；
  - **执行层**依赖**上下文之外的机制**（独立审查进程、最小权限凭证、沙盒、人在回路）；
  - **数据层**依赖**数据库自身的策略**（行级安全、约束、受控视图、受信任运行时）。
  依赖越少、越“笨”、越确定，就越难被“聪明”的攻击一次穿透。**这就是为什么数据层是最后一道、也是最可靠的一道。**
- **“处在同一个上下文里的 Agent，很难判断自己是否已经被注入”——这句是上下文层的根本瓶颈**，也是 1.3 节“提议者—审核者”模式存在的理由。机制上：如果攻击者把恶意指令写进了网页内容，而这个网页内容被检索进了上下文，那么模型看到的“指令”和“数据”在**同一个上下文里**、以**同样的形式**呈现——它没有外部参照系去区分“这是用户让我做的”还是“这是那篇网页让我做的”。所以原文的结论很克制也很准确：**上下文层只能降低攻击成功率，给不出保证。**
- **Constitutional Classifiers 的三点机制，每一点都值得单独理解**：
  1. **规则驱动**：**用自然语言写规则 → 生成合成训练数据 → 训练分类器**。这条的巧妙之处是**把“安全策略”和“分类器实现”解耦**：改策略只需要改自然语言规则，不用重新标注数据。这也是 1.1.3.2 节“外部产物更新”的一个实例——**可语言化的策略写进外部产物**。
  2. **上下文联合判断**：这个例子的机制很清楚——“**如何使用食品调味料**”单独看完全正常，只有**对照用户提问**才能发现“食品调味料”是**化学试剂的暗语**。所以判定的输入不能只有回答，必须“**提问 + 回答**”成对。**这条对工程实现的直接含义是：分类器接口要设计成接收问答对，不能只接收单条文本。**
  3. **两级筛查**：**极轻量探针（直接读取模型内部激活，几乎零成本）先过一遍所有对话 → 可疑的再交给更强的分类器复审**。这里最有价值的设计思想是“**不是直接拒绝**”：第一级只做**筛选**（可能是高误报的粗筛），第二级才做**裁决**。收益原文说得很清楚：“**第一级即使误报较多也不影响用户体验，成本也大大降低**”。这其实是一种**用分层来买成本**的架构——和 1.2.5 开头“多个专门的护栏组合使用，才能构建出更有韧性的 Agent 系统”是同一个思路。
- **“误拒绝”为什么被单独列出来讲？** 因为护栏的评估指标天然是不对称的：大家本能地只盯“危险请求有没有被放行”（漏杀），而“**明确允许的请求是否能够正常完成**”（误杀）往往没人测。原文给的两个例子很典型——**经过授权的安全测试、模型蒸馏研究**：这两类任务在网上看起来就是“在攻击模型”，但它们是**合法的**。原文因此给出了一条**双向的评估要求**：
  - 测“应当拒绝的请求是否被拦截”；
  - 测“明确允许的请求是否能够正常完成”。
  这与 1.3 节“边界集 + 保留集”完全同构——**任何一次修改都要同时在“它应当改变的那批样本”和“它不应当影响的那批样本”上验证**。护栏本质上就是一种修改，所以它要过这两组集合。
- **执行层的“复核必须在上下文之外”为什么是硬要求？** 原文的理由很直白：“**否则它会和被注入的 Agent 一起沦陷**”。想象一下：Agent 被网页注入后，去调用一个“审批工具”来批准自己的高风险操作——如果这个“审批”也是同一个上下文里的模型调用，那它看到的上下文同样是被污染的，它会批准。所以执行层的四个手段（**独立审查进程、最小权限凭证、沙盒隔离、人在回路**）的共同特征是：**它们的判定输入不来自被保护的那个上下文。**
- **“返回给用户的回复本身也是一次动作”这个洞察值得单独记住**：很多人的直觉是“回复只是输出，不是行动”。原文纠正了这一点——它按第四章的工具分类把回复归为**用户沟通工具**，所以回复**也是一次对外动作**，也需要护栏。这直接推出两项检查：**PII 过滤器**（防不必要暴露身份证号、手机号）和**输出验证**（确保回复与品牌价值一致）。这也解释了 1.2.5 开头为什么把“数据隐私风险（防止系统提示泄露）”和“声誉风险（模型行为与品牌形象一致）”列为护栏的两个目标。
- **数据层“不依赖上面两层是否正确”——这是它最大的价值主张**，也是最值得在架构设计时利用的一点。原文给的场景非常具体：**“即使提示注入得手、生成的代码完全漏写了权限判断，越权操作仍会在数据层被拒绝。”** 注意这里点出的是一个**真实的工程组合**：Agent 动态生成代码而代码里忘了做权限检查。前两层（上下文层判断、执行层评级）都可能因为各种原因放行，但**数据库的行级安全策略是独立的、由人类审查过的、无法被 Agent 改写的**。这就是原文 1.2.5.1 开头说的“越难被一次成功的攻击穿透”。
- **人工干预的两个触发条件与图 1-6 是同一套逻辑**：**超过失败阈值**（对应图 1-6 的“④ 错误次数超限”）、**高风险操作**（对应执行层的“高风险操作需额外审查或人工确认”）。所以人工干预不是外挂，它是**执行层护栏的一个手段**被打通到了组织流程层。原文还点出了它的两个价值：一是**平稳移交控制权**（对应 1.2 节 Correct 里的“连续失败时回退到人工判断（熔断机制）”），二是**在部署早期建立评估周期**——也就是说，**人在回路不只是安全措施，还是数据采集手段**（人在处理边缘情况时，你顺便知道了边缘情况长什么样）。
- **工程上的坑**：
  - **只做上下文层**。因为上下文层最容易做（加个分类器调用），但原文明确说它“给不出保证”。**只做这一层等于没有防线纵深。**
  - **把“人工确认”放在同一个上下文里**（例如让模型自己弹一个“我确定要删除吗？”）。这正是原文警告的“和被注入的 Agent 一起沦陷”。
  - **护栏只测漏杀不测误杀**。上线后会出现一批“用户明明提了合法需求却被拒”的工单。
  - **忽略“回复也是一次动作”**。没有输出侧的 PII 过滤，敏感信息可能通过回复泄露出去。
- **不适用/注意**：原文说“实践中可以先针对已识别的风险设置护栏，再在发现新漏洞时逐步添加”——**不要求一次做全三层**。但“分层骨架”要一开始就有，否则后面加层会处处返工。

**易混点**

- **越狱（Jailbreak） vs 提示注入（Prompt Injection）**：原文的关键区别是**攻击来源**——**越狱是用户自己试图绕过模型的安全限制**；**提示注入是攻击者通过外部数据（如网页内容、文档）间接操纵模型行为**。一句话记：**越狱是“我直接让你破防”，注入是“借别人的手让你破防”。**
- **上下文层 vs 执行层 vs 数据层**：按**防护位置**分（模型能看到什么 / 模型能做什么 / 世界最终能被改成什么样），并且**按被绕过的难度从低到高排**，不是按处理先后排。
- **约束（Constrain） vs 执行层护栏**：五要素里的“约束”是**动作生效前限制集合**（`Harness.constrain`）；执行层护栏是**在动作真正生效之前验证 + 工具风险评级 + 输出检查**，范围更宽，且强调“复核必须在上下文之外”。
- **人工干预（Human in the loop） vs 审批回调**：前者是**机制与触发条件**（失败阈值 / 高风险操作）；后者是**框架提供的接口形态**（例如 Codex Harness 的 `app-server` 通过 JSON-RPC 提供“审批回调”，见 1.2.4.4）。
- **误拒绝 vs 过度拒绝**：原文用的是“误拒绝”，指的是**合法但形式敏感的请求被拒**。它与“漏杀”是一对相反的错误，护栏评估要同时测两端。

**一句话记住**

> 护栏按**被绕过的难度**分三层——上下文层（管能看到什么，只能降低成功率、给不出保证）、执行层（管能做什么，复核必须在上下文之外）、数据层（管世界最终能被改成什么，不依赖上面两层是否正确）；再加人工干预兜底，而评估必须同时测漏杀和误杀。

### 1.2.6 Harness 五要素与「构建」部分的对应

**原文要点**

- **本节的首要任务是澄清两个公式的关系，以免读者记住两套骨架**（原文原话）：
  - **全书的结构骨架只有一个，就是引言和后记反复使用的 `Agent = LLM + 上下文 + 工具`**：**第二至六章讨论构建，第七至九章讨论评估与进化，第十章讨论协作。**
  - **`Agent = Model + Harness` 不是与它并列的另一套划分，而是同一事物在生产形态下的展开**——**它把“上下文”和“工具”两项细分为上下文管理、工具接口、约束、验证、纠正五项职责**。
  - 因此，**它是构建部分内部的一个观察视角，而不是覆盖全书十章的目录。**
- **Harness 五要素与第二至五章的对应关系**（表格按原文语义还原）：

| Harness 要素 | 对应章节 | 核心内容 | 安全关注点 |
| --- | --- | --- | --- |
| 上下文管理 | 第二章（上下文工程） | 提示工程、Agent 状态栏、上下文压缩、Agent Skills | 提示注入、上下文污染 |
| 上下文管理（跨会话） | 第三章（用户记忆和知识库） | 用户记忆、RAG、结构化索引、智能体化 RAG | 敏感信息暴露、隐私保护 |
| 工具接口与约束 | 第四章（工具） | 工具分类、权限控制、MCP 标准、主动工具发现 | 误操作、未授权访问、不可逆操作 |
| 验证与纠正 | 第五章（Coding Agent 与通用 Agent） | Coding Agent 的 Harness、测试驱动、代码化规则 | 身份冒用、责任归属 |

- **哪些章“不进格子”以及为什么**（原文明确说明）：
  - **第六章（交互）不属于五要素中的任何一项**——**它扩展的是观察与动作空间本身的模态与时机**；
  - **第七至九章讨论的是怎么知道 Harness 建对了、以及怎么让它持续变好**；
  - **第十章则把单个 Agent 的 Harness 换成多个 Agent 的协作结构**；
  - 原文的判据：**“把这些章也塞进五要素的格子里，只会让格子失去区分力。”**
- **安全为什么不按章划分**：**它是贯穿全书的横切关注点（Cross-cutting Concern，即一个影响系统多个部分的问题），按前一节的三层护栏组织——上下文层、执行层、数据层。** 上表的“安全关注点”一列，**给的是每一章在这三层里最主要的落点**。
- **一个实例：Anthropic 构建长时运行 Agent 的实践**（原文用它展示“Harness 设计如何解决模型本身无法解决的问题”）：
  - 他们把复杂任务分解为**“初始化 Agent”**（**设置环境、分解任务列表**）和**“执行 Agent”**（**在每个会话中增量推进并留下清晰的交接产物**）；
  - 通过**结构化的 Harness** 解决了 Agent 在长任务中的两个问题：**“上下文耗尽”** 和 **“过早声明完成”**。
- **后续章节的安排**：**后续章节将逐一深入 Harness 的各个组件——第二章从最核心的上下文工程开始，第五章将专门展开 Harness 工程在 Coding Agent 中的完整实践。**

**辅导讲解**

- **这一节表面上只是“对表格”，实际上是在给全书的读书方法定调**。它回答的是“我该记几套骨架”这个非常实际的问题：**一套**。`Agent = LLM + 上下文 + 工具` 是骨架；`Agent = Model + Harness` 是**在“构建”这一部分内部，把骨架里的两项拆成五项**的放大镜。记住这个层级关系，后面看到任何一个章节标题，你都能立刻定位它在骨架上对应哪一块。
- **“细分”这个词是理解本节的关键**：`上下文 + 工具` → `上下文管理 + 工具接口 + 约束 + 验证 + 纠正`。注意后三项**不是凭空多出来的**——它们是从“上下文 + 工具”里**分出来**的职责：
  - **约束**是从“工具接口”里分出来的（工具的风险等级、权限）；
  - **验证**横跨“上下文”（上下文是否被污染）和“工具”（调用结果对不对）；
  - **纠正**作用于整个运行过程（重试、回退、熔断）。
  所以五项职责**不是新增的五个模块**，而是同一个 Harness 的五个**关注点**。这个理解能防止你把架构画成五个孤立组件。
- **表格里“上下文管理”出现两次（第二、三章）说明什么？** 说明五要素不是与章节一一对应的。**上下文管理**这一个要素横跨了两章（第二章管单次会话内的上下文；第三章管跨会话的用户记忆和知识库）。这是原书自己的安排，读者不该期待一个完美的“要素—章节”双射。原文的说法是“在这个范围内，Harness 五要素与第二至五章有**清晰的对应**”——清晰，但不严格一一对应。
- **“第六章不进格子”这个说明其实很重要**，因为它划出了五要素的适用边界：**五要素讲的是“运行与治理”，而第六章（交互）扩展的是“观察与动作空间本身的模态与时机”**。也就是说，把语音、图像、异步通知这些新模态接进来，不是“把某项职责做得更好”，而是**把空间本身变大**——这是 1.1.1 节那条“扩展观察空间与动作空间”的杠杆在交互层面的体现。所以它天然不属于“治理层”的五要素。
- **“塞进去会让格子失去区分力”这句是方法论层面的忠告**：分类的价值在于**区分**，如果一个格子能装下几乎所有东西，它就失去了信息量。这个原则在做任何体系设计时都适用。
- **“安全是横切关注点”这个安排很聪明**：如果安全按章写（比如“第五章讲安全”），那第二、三、四章的安全问题就没地方放；而按 1.2.5 的三层护栏组织（上下文层/执行层/数据层），**每一层都能挂到多个章节上**。表格里的“安全关注点”一列正是这个映射的具体产物：
  - 第二章 → **提示注入、上下文污染**（上下文层）；
  - 第三章 → **敏感信息暴露、隐私保护**（数据层为主）；
  - 第四章 → **误操作、未授权访问、不可逆操作**（执行层为主）；
  - 第五章 → **身份冒用、责任归属**（跨层，尤其涉及“谁做的、谁负责”）。
  把这四行和三层的定义对起来看，你会发现**章节顺序（二→五）与护栏层级顺序（上下文层→执行层→数据层）大体同向**，这与 1.2.5.1 说的“越靠下的层越难被绕过”是呼应的。
- **Anthropic 长时运行 Agent 的实践，是“Harness 解决模型本身无法解决的问题”的范例**。原文点出的两个问题都很精准：
  - **上下文耗尽**：长任务的信息量必然超过窗口，**换更强的模型解决不了**（窗口是有限的），只能靠 Harness 的结构（分解任务、交接产物）；
  - **过早声明完成**：这是可靠性问题而非能力问题——模型“觉得”做完了，但实际没做完。**这也换更强的模型解决不了**，要靠显式的任务列表和验证。
  这两个问题之所以被选作例子，正是因为它们**不是能力短板，而是结构短板**——而这恰恰是 Harness 能补的。这与 1.1.3.1 节“模型此刻的能力边界，就是 Harness 此刻的价值所在”是同一层意思，只不过这里给了一个具体案例。
- **读法建议**：这一节可以当**全书的目录解释器**用。以后读第二章时，先问“这一章在补五要素的哪几项、挡三层护栏的哪一层”；读第六章时，记得它“不在五要素里”；读第七至九章时，记得它们回答“怎么知道建对了、怎么持续变好”；读第十章时，记得它把“单个 Harness”换成“多个 Agent 的协作结构”。

**易混点**

- **`Agent = LLM + 上下文 + 工具` vs `Agent = Model + Harness`**：**只有一套骨架**（前者）；后者是**同一事物在生产形态下的展开**，是“构建部分内部的一个观察视角”，**不是覆盖全书十章的目录**。
- **五要素 vs 五章**：不是一一对应。上下文管理横跨第二、三章；工具接口与约束对应第四章；验证与纠正对应第五章；第六章**不在**五要素之内。
- **横切关注点 vs 章节主题**：安全是横切关注点（影响多个部分），按三层护栏组织，不按章划分。
- **“初始化 Agent” vs “执行 Agent”**：Anthropic 长时运行实践里的两个角色。前者**设置环境、分解任务列表**（一次性）；后者**在每个会话中增量推进并留下清晰的交接产物**（可重复多次）。

**一句话记住**

> 全书只有一套骨架 `Agent = LLM + 上下文 + 工具`；`Agent = Model + Harness` 只是把“上下文 + 工具”细分成五项职责的放大镜——它管“构建”，不管全书；而安全是横切关注点，挂在三层护栏上。

## 1.3 贯穿全书的设计模式

**原文要点**

原文的开场说明：**后面章节会反复用到同一批设计模式，因此在这里一次性命名并给出规范定义。** 共五个：

- **（一）提议者—审核者（Proposer-Reviewer）**
  - **定义**：**产出与评判由两个不共享上下文的角色分别承担，评判方看到的是产物本身——渲染结果、测试输出、结构化的调用参数——而不是产出方的推理过程。**
  - **成立前提**：**自审不可靠**——**同一个上下文中的模型难以发现自己的认知盲区，也很难判断自己是否已被注入。**
  - **全书用例**：**第三章用它更新知识；第四章用它做工具调用的事前审批与事后验证（Sidecar 是它的一个只读变体）；第五章的 PPT、视频与日志三个实验都以它为骨架；第七章用它评估 UI；第九章用它审核更新提案；第十章讨论了它在对等协作中的形态，以及为什么不能让同一个 Agent 自审。**
- **（二）渐进式披露（Progressive Disclosure）**
  - **定义**：**不把全部信息一次性放进上下文，而是先给一份可检索的目录，再按需加载细节。**
  - **收益**：**它同时优化两件事——上下文预算与选择精度。**
  - **全书用例**：**第二章的 Agent Skills 是最典型的形态（元数据常驻、正文按需加载）；第三章的分层检索、第四章的主动工具发现与分页截断、第十章的 Agent 发现都是它的变体。**
- **（三）只增不改（Append-only）**
  - **定义**：**状态以追加的方式演进，已经写下的内容不再回头修改。**
  - **收益**：**换来的是可缓存、可重放、可审计。**
  - **全书用例**：**第二章的 KV Cache 前缀稳定性是它的性能形态——改动越靠前，作废的缓存越多；第三章的事件式记忆、第四章把新工具的 schema 追加到轨迹末尾而不是插回前缀，都是同一条纪律。**
- **（四）边界集 + 保留集（Boundary Set + Retention Set）**
  - **定义**：**任何一次修改都要同时在“它应当改变的那批样本”和“它不应当影响的那批样本”上验证。**
  - **反例警示**：**只测前者会把过拟合当成进步，只测后者会把无效修改当成安全。**
  - **全书用例**：**第七章的回归任务、第八章的训练与评估隔离、第九章的更新提案验证都建立在这对集合上。**
- **（五）最小 diff + 可回滚**
  - **定义**：**每次修改尽量小、带来源、可单独回滚，而不是整体重写。**
  - **收益**：**它让归因成为可能——出了问题能定位到具体哪一次改动。**
  - **全书用例**：**第三章的知识更新、第五章的代码补丁、第九章的 Prompt 与程序更新都遵循这条。**
  - **与本章的呼应（原文原话）**：**本章开头给出的三条更新路径（上下文内适应、外部产物更新、参数更新），也正是按可回滚程度从高到低排列的。**

**辅导讲解**

- **这五个模式是本章最“可迁移”的部分**。1.1 讲的是 Agent 是什么（概念），1.2 讲的是怎么可靠地跑（工程），1.3 给的是**五个可以直接套用到任何 Agent 系统上的设计套路**。它们的共同特征是：**不依赖具体模型、不依赖具体框架**——这正好回应了本章思考题第 10 题那种“设计原则应穿越模型迭代周期”的关切。
- **“提议者—审核者”为什么排在第一位？** 因为它是本节唯一一个**直接对应安全与可靠性根因**的模式。它的成立前提写得很硬：“自审不可靠”——理由有两条：**同一个上下文中的模型难以发现自己的认知盲区**，以及**很难判断自己是否已被注入**。第二条正好是 1.2.5.1 里“处在同一个上下文里的 Agent，很难判断自己是否已经被注入”的同一句话。所以这个模式不是“多一道保险”，而是**唯一能绕开这个结构性瓶颈的办法**：**换一个上下文**。
  - **关键细节：评判方看什么？** 原文说得很细——**“产物本身——渲染结果、测试输出、结构化的调用参数——而不是产出方的推理过程”**。这与 1.2 节 Verify 的原则（“安全检查只看结构化数据，而不看模型自由生成的文本，因为后者可能已被提示注入操纵”）是同一个道理：**产物是最难被话术污染的证据，推理过程是最容易被污染的部分。**
  - **Sidecar** 被点名为它的“只读变体”——即旁路查询：让一个独立角色只读地去看主流程在干什么，不做修改。这个名字在 1.2 节的五要素表里也出现过（Context 的“实际例子”一列里有“Sidecar 旁路查询”）。
- **“渐进式披露”的类比**：可以想成**查字典**——你不会把整本字典背下来（放不进上下文），而是先看目录/索引（可检索的目录），需要某个词的时候才翻到那一页（按需加载细节）。原文说它同时优化两件事，这两件事要分开理解：
  - **上下文预算**：不加载就没占用 token；
  - **选择精度**：目录本身是压缩过的，模型在目录上做选择比在全文里找更准（干扰信息少）。
  **第二章的 Agent Skills（元数据常驻、正文按需加载）是最典型的形态**——这个名字本身就说明了形态：**元数据小、常驻；正文大、按需**。
- **“只增不改”为什么能换来“可缓存、可重放、可审计”？** 三个收益的机制各不同：
  - **可缓存**：前缀不变 → KV Cache 命中（改动越靠前，作废的缓存越多，这就是它的“性能形态”）；
  - **可重放**：历史是一条只能追加的日志，按同样的顺序回放就能复现同样的输入；
  - **可审计**：已经写下什么就是什么，不会被事后改写。
  注意原文举的两个例子都很有说服力：**第三章的事件式记忆**（记忆是“发生过什么”的事件流，不改历史）、**第四章把新工具的 schema 追加到轨迹末尾而不是插回前缀**——后者正是 1.1.4 节里那句“2026 年以来，生产框架中工具的完整 schema 也可以按需动态加载到上下文末尾而不破坏前缀”的纪律来源。
- **“边界集 + 保留集”是本节最容易被忽略、但工程价值最高的一条**。它把“改得对不对”变成一个**必须双向验证**的问题：
  - **边界集（Boundary Set）**：这次修改**应当改变**的那批样本——用来证明改动**有效**；
  - **保留集（Retention Set）**：这次修改**不应当影响**的那批样本——用来证明改动**没有副作用**。
  原文给的两个反例警示极其精炼：**只测前者会把过拟合当成进步，只测后者会把无效修改当成安全。** 这两句话值得背下来——它们是所有“我改了 Prompt，感觉变好了”这类判断的解毒剂。
- **“最小 diff + 可回滚”的价值在“归因”这个词上**。原文说“它让归因成为可能——出了问题能定位到具体哪一次改动”。也就是说，**这不是为了代码整洁，而是为了可诊断性**。反过来说，一次大重写把十处改动混在一起，出问题时就无法判断是哪一个导致的，只能整体回退——**回退粒度等于调试粒度**。
- **本节末尾那句呼应非常关键，它把 1.1.3.2 的“三条更新路径”接了进来**：**上下文内适应 → 外部产物更新 → 参数更新，按可回滚程度从高到低排列**。具体对比一下：
  - **上下文内适应**：下一轮就不存在了，**回滚 = 不放进上下文**（可回滚度最高）；
  - **外部产物更新**：写进文档/Prompt/程序，**回滚 = 撤销那次 diff**（最小 diff + 可回滚模式正好服务于此）；
  - **参数更新**：改了权重，**回滚 = 重新训练或回滚模型版本**（可回滚度最低）。
  所以“优先用可回滚度高的手段”这条工程直觉，在本章里有了理论支撑。
- **工程上的用法**：这五个模式可以直接当**设计自检清单**：
  - 有没有让同一个 Agent 自己审自己？（该用提议者—审核者）
  - 上下文里是不是一股脑塞了全部资料？（该用渐进式披露）
  - 有没有改写历史导致缓存全失效、日志不可重放？（该用只增不改）
  - 改完之后有没有同时测“该变的”和“不该变的”？（该用边界集 + 保留集）
  - 改动是不是一大坨、出问题只能整体回退？（该用最小 diff + 可回滚）
- **不适用/注意**：原文说的是这五个模式**会被后续章节反复用到**，因为它们是**跨章的公共词汇**。所以本节的正确读法是“先建立索引”，不是“现在就掌握细节”——每个模式的具体形态都要等对应章节展开。原文每一处都点明了“哪个章节用它做什么”，这就是留给你的索引。

**易混点**

- **提议者—审核者 vs 自己检查自己**：区别在**上下文是否共享**。同一上下文的模型“自审不可靠”（发现不了自己的盲区、判断不了自己是否被注入）。
- **提议者—审核者 vs 人在回路**：前者是**两个角色**（可以是两个 Agent 实例）；后者是**人**在流程里。人在回路是执行层护栏的一个手段，提议者—审核者是一种通用的产出-评判结构。
- **渐进式披露 vs 上下文压缩**：披露是**先不加载**（按需取）；压缩是**已经加载了再精简**。前者省的是“从来没进来过”的 token，后者省的是“进来了但可以缩短”的 token。
- **只增不改 vs 不可修改**：只增不改说的是**状态轨迹**以追加方式演进（不改写历史），不是“永远不能改配置/代码”。改 Prompt、改程序代码属于另外的更新路径（外部产物更新），它们遵循的是“最小 diff + 可回滚”。
- **边界集 vs 保留集**：边界集 = **应当改变**的样本（测有效性）；保留集 = **不应当影响**的样本（测副作用）。名字容易记反，记法是“边界集画的是改动的**边界**（改动要覆盖到的范围）”。

**一句话记住**

> 五个模式：**提议者—审核者**（评判方不共享上下文、只看产物）、**渐进式披露**（先给目录、按需加载）、**只增不改**（可缓存/可重放/可审计）、**边界集 + 保留集**（既测该变的也测不该变的）、**最小 diff + 可回滚**（让归因成为可能）。

## 1.4 本章小结

**原文要点**

- **总起**：**本章从实践出发，建立了理解和构建 AI Agent 的基础框架。**
- **一、Agent = 大脑 + 眼睛 + 手脚**：**LLM 是大脑（决策核心），上下文是眼睛（决定它能看到什么），工具是手脚（决定它能做什么）。三者缺一不可。**
- **二、扩展眼睛和手脚是最主要的能力杠杆**：**在模型固定时，重新定义或扩展观察空间与动作空间——也就是扩展上下文和工具——往往能直接把原本不可解的任务变为可解。** **Manus 和 OpenClaw 的演进都说明，通用性很大程度上来自接口边界的扩大；这种扩大必须按需进行，并配合权限控制和验证。**
- **三、眼睛（上下文）是决定性的因素**：**上下文由静态前缀（系统提示词 + 工具定义）和动态轨迹（消息历史）构成。** **消融实验表明，各组件并不等价：去掉工具定义或工具执行结果会直接夺走行动与闭环能力，去掉另外两者的代价则取决于信息能否从当前观测重建。** **ReAct 循环的本质是通过不断追加轨迹来让模型持续推进任务。**
- **四、Harness 是竞争力所在**：**模型能力正在商品化，真正的差异在于 Harness——围绕上下文和工具构建的约束、验证与纠正机制，确保 Agent “可靠地做事”。** **在生产级的 Agent 系统中，Harness 的绝大部分代码都在实现这些保障机制，而不仅仅是上下文和工具本身。**
- **五、从工作流到自主 Agent**：**先优化提示词，再考虑工作流，最后才引入自主 Agent——这是降低意外风险最实用的顺序。每种编排模式都有其适用场景，不存在通用最优解。**
- **六、五个设计模式贯穿全书**：**提议者—审核者、渐进式披露、只增不改、边界集 + 保留集、最小 diff + 可回滚。**
- **七、安全是架构问题**：**安全问题从第一行代码就要考虑，而不是上线前打补丁。护栏按被绕过的难度分为上下文层、执行层与数据层三层，后续各章的安全讨论都挂在这个骨架上。**
- **过渡**：**下一章将深入探讨 Harness 中最核心的组件——上下文工程。关于 Agent 概念在强化学习中的学术渊源，以及传统 RL 与现代 LLM Agent 的深入对比，我们将在第八章系统展开。**
- 原文随后交代思考题的定位：**以下思考题旨在引导读者深入思考本章的核心概念，不设标准答案。**

**辅导讲解**

- **小结的七条正好对应本章的两大部分**：前三条（一、二、三）收 1.1，后四条（四、五、六、七）收 1.2 与 1.3。读小结时可以拿它当**检索表**：哪条想不起来，就回到对应小节。
- **“模型能力正在商品化”这个判断值得单独理解**。它和小结第五条的“不存在通用最优解”、以及 1.2.1 的“当各家模型的能力越来越接近……竞争优势就转移到了模型之外的工程实践”是同一个判断的三种表述。**“商品化”的含义是：模型会变成像云主机、数据库一样的东西——能买到、能替换、差距可被价格差弥补。** 一旦如此，产品之间的差距就只能来自你在这层商品之上搭的东西，也就是 Harness。
- **“这种扩大必须按需进行，并配合权限控制和验证”这句限定很重要**，它是 1.1.1 节“扩空间是主要杠杆”的**必要补丁**。没有这个补丁，读者可能得出“接口越宽越好”的错误结论。原文在本章小结里专门补回来，说明作者认为这个限定和大结论同等重要。
- **第三条里“眼睛（上下文）是决定性的因素”这个措辞值得留意**：原书小结的原文就是如此（不是笔记改写）。它的意思是：**在三大组件中，上下文对最终行为的影响最直接**——因为“Agent 只能基于它看到的信息做决策”（1.1.4 的核心洞察）。而消融实验给出的是更精细的结论：**不是“信息越多越好”，而是“信息的可重建性决定代价”**。
- **第四条的“绝大部分代码”是一个可检验的说法**：1.2 节用了 Claude Code 的例子佐证——“工具本身（文件读写、命令执行、搜索）只是一小部分，而围绕这些工具构建的保障机制才是真正的核心”。所以在自己的项目里，也可以粗算一下“保障机制代码 / 总代码”这个比例，作为成熟度的粗略参考。
- **第七条“安全是架构问题”是本章唯一一条以“何时做”为核心的结论**：**“从第一行代码就要考虑，而不是上线前打补丁。”** 这解释了为什么 1.2.5 的护栏要给出一个**三层骨架**（而不是一串零散的措施）——骨架是为了**在架构设计阶段就预留位置**。

**易混点**

- **“扩展上下文和工具” vs “扩展上下文窗口”**：前者是**把新数据和操作接进来**（接口层面的扩展）；后者是**加大模型的容量上限**（模型层面的参数）。小结第二条说的是前者。
- **“关注范围” vs “工作量分配”**：小结第四条说 Harness 是竞争力所在、工程量主要在保障机制上——这是**投入方向的判断**，不是“上下文和工具不重要”。原文明确说它们“缺一不可”。

**一句话记住**

> 三条讲“是什么”（脑眼手、扩空间是杠杆、上下文是决定因素），四条讲“怎么可靠”（Harness 是竞争力、先提示词后工作流再自主、五个模式、安全是架构问题）。

## 思考题

**原文要点**

原文说明：**以下思考题旨在引导读者深入思考本章的核心概念，不设标准答案。**（原文在页面上方另有一个“深度思考”的栏目标题。）共 10 题，题号前的 ★ 号为原文所标的难度：

> 1. ★★ 如果你只能给一个 Agent 系统增加一项能力——更强的模型、更丰富的上下文还是更多的工具——你会选哪个？在什么条件下你的选择会改变？
> 2. ★★★ ReAct 循环中，累计缓存读取量随轮数近似二次方增长。如何降低这种增长？
> 3. ★★ “模型即 Agent”范式意味着模型在工具调用决策上越来越自主。但本章论证了 Harness 工程的重要性反而在增加。这两个趋势如何共存？Agent 框架未来的核心价值体现在哪些方面？
> 4. ★★ 消融实验中“工具结果反馈”的缺失会让 Agent 反复重试直到耗尽迭代预算。在生产环境中，除了工具结果缺失，还有哪些情况可能让 Agent 陷入这种循环？你会设计怎样的检测和终止机制？
> 5. ★ 本章用感知、行动、策略三个维度分析了五个 Agent 产品。请选择一个你日常使用的 AI 产品，用这三个维度进行分析，并思考它的架构设计是否合理。如果由你来设计这个 AI 产品，有哪些改进空间？
> 6. ★★ 如果你要设计一个专门处理航班订票的客服系统，你会选择工作流模式还是自主 Agent 模式？有没有可能在同一个系统中混合使用两种模式？
> 7. ★★★ 护栏部分提到了工具风险评级。如果一个工具在大多数情况下是低风险的，但在特定参数组合下变为高风险（如 `delete_file` 删除普通文件 vs 删除系统文件），你会如何设计动态风险评估？
> 8. ★★ 本章的 Agent 产品表格中，所有 Agent 的动作空间都是“开放式”的。一个受限的动作空间（比如只能从预定义选项中选择）在什么场景下反而优于开放式？
> 9. ★★ 人工干预机制要求 Agent 能“优雅地移交控制”。但在实践中，用户可能不在线、响应很慢、或者给出模糊的指令。此时 Agent 应该怎么办？
> 10. ★★★ 引言指出“好的设计原则应该穿越模型的迭代周期”，但实现这些原则的具体工程手段可能会随模型能力进步而过时。试举一个这样的 Agent 工程手段，并说明理由。

**思路提示（笔记补充，非原文，不构成标准答案）**

1. **思路**：先分清“瓶颈归因”。可以套用 1.1.1 的判据——问“把数据/操作给到这个模型，它做得对吗？”若答案是“对”，缺的就是接口（上下文或工具）；若“不对”，才轮到模型。再想“条件变化”：如果任务本身是开放的探索型（步骤数不可预测），工具的边际收益通常最大；如果任务的知识需求随时间/私有化变化，上下文的边际收益最大；如果任务需要高维隐性能力（风格、影像判读），那模型才是瓶颈。另外别忘了 1.2.3 的提醒：换模型还受策略边界与服务条款约束。
2. **思路**：先想清楚“为什么是二次方”——提示可以说：每一轮都要把此前全部轨迹作为输入重新读一遍，第 $t$ 轮读的是前 $t$ 轮累积的内容，于是 $1+2+\dots+N \approx N^2/2$（这是笔记给的粗略模型，供你推理用，不是原文公式）。降低办法可以往“只增不改但别重复读”的方向想：前缀缓存能不能复用？轨迹能不能压成摘要或结构化状态？旧轮次能不能折叠成“已确认的结论”？哪些信息其实可以从当前观测重建（1.1.4 的判据）？
3. **思路**：把两件事拆到不同层看——**决策权**在往模型里走（RL 内化的是决策策略），**执行、治理、编排**仍在模型之外（实验 1-2 的区分）。再想“框架的价值会往哪挪”：当“怎么调工具”不再是问题时，价值可能转向上下文与记忆的组织、约束与验证、多 Agent 协作结构、可观测性与评估。也可以从 1.2.6 的五要素里挑你觉得最难被内化的那几项。
4. **思路**：先列出“循环不退出的其他成因”，例如：工具返回成功但结果不含所需信息（模型反复换 query）；工具一直报错但错误信息不可读；模型判断不了“信息是否充足”；任务本身无解但模型不肯放弃；多个工具互相矛盾导致来回切换。再设计机制时，可以参考图 1-6 的五条退出条件——特别是“错误次数超限”和“达到最大轮次”这两条兜底，加上“重复检测”（LangChain 那组 Harness 改进里就有“检测是否陷入重复循环”）。
5. **思路**：先确定“感知/行动/策略”三栏各自填什么。注意本章给这三维度配的学术概念是“观察与历史 / 观察-行动接口 / 策略”。分析时重点看“眼睛”那一栏——不同产品的差异主要在这里。改进空间可以从 1.1.1 的两个问句切入：有什么该看到的信息没进上下文？有什么该做的操作没被封成工具？别忘了权限与验证（1.4 小结第二条的限定）。
6. **思路**：把订票流程按 1.2.4.3 的思路切段。合规敏感、顺序刚性、不可逆的环节（身份核实、付款、锁定座位）倾向工作流；依赖上下文判断的环节（怎么找航班、要不要推荐替代方案、用户临时改签）倾向自主。混合的两条路都可以考虑：n8n 式（同一图里放两类节点）或“Agent 写工作流再执行”式。回答时最好说清“哪些边界必须写死”。
7. **思路**：核心是把风险评级从“按工具名”改成“按（工具，参数）”。想一想：能不能从参数里提取可判定的信号（路径是否落在受保护目录、金额是否超阈值、目标是否是系统关键资源）？能不能做分级（低风险直接放行、中风险二次校验、高风险人工确认）？能不能把判定放在**上下文之外**（1.2.5.1 强调的）？可以用“故障安全默认值”这条原则当收尾：判不出来时默认拒绝或转人工。
8. **思路**：从“开放式动作空间的代价”反推——开放式带来出错面、攻击面、不可预测性和评测困难。于是“受限更优”的场景通常是：高风险且可穷举（只能选“批准/拒绝/转人工”）、需要严格可审计（合规场景要求每一步都能列出来）、需要确定性保证（付款金额只能从预设档位选）、以及接口易用性（选项比自由文本更不容易被误解，对应 1.2.2 的 ACI 原则）。
9. **思路**：先分清“移交失败”的几种情形（不在线、慢、指令模糊）。可以想的方向：设定等待超时与默认动作（超时后走保守分支——只做可逆操作、或保持现状）；把模糊指令转成一个**有限选项**的问题（这正好呼应第 8 题受限动作空间的优势）；把未决状态**持久化**，等用户回来再续（对应 1.1.2 的“受控虚拟工作目录”与 1.3 的“只增不改”）；以及在关键路径上**提前**取得授权而不是事后移交。
10. **思路**：在 1.2.4.1 里找“适配层”清单最直接——few-shot 示例、“让我们一步一步思考”类提示词技巧、输出格式修复与 JSON 解析容错、文生图提示词改写，都是原文明确说“被内化了”的手段。选一个说清“它当初解决什么短板、后来被什么能力吃掉”。也可以反过来想哪些手段**不会**过时（提示注入防护的三个护栏层、权限与审计这类与“信任边界”有关的机制）。

**易混点**

- **思考题与练习题的区别**：本章只有思考题（10 题），**没有练习**。思考题原文明确“不设标准答案”，上面给的“思路提示”是笔记补充的，**不是答案**。
- **★ 号的含义**：原文只标了 ★、★★、★★★，**未在正文中解释星级的具体口径**。从分布看（第 5 题 ★，第 2、7、10 题 ★★★），大致对应论证复杂度，但笔记不做推断性定义。

## 原文本章小结

以下为原书“1.4 本章小结”的内容，按原文忠实整理（不加笔记评述）：

本章从实践出发，建立了理解和构建 AI Agent 的基础框架。

- **Agent = 大脑 + 眼睛 + 手脚**：LLM 是大脑（决策核心），上下文是眼睛（决定它能看到什么），工具是手脚（决定它能做什么）。三者缺一不可。
- **扩展眼睛和手脚是最主要的能力杠杆**：在模型固定时，重新定义或扩展观察空间与动作空间——也就是扩展上下文和工具——往往能直接把原本不可解的任务变为可解。Manus 和 OpenClaw 的演进都说明，通用性很大程度上来自接口边界的扩大；这种扩大必须按需进行，并配合权限控制和验证。
- **眼睛（上下文）是决定性的因素**：上下文由静态前缀（系统提示词 + 工具定义）和动态轨迹（消息历史）构成。消融实验表明，各组件并不等价：去掉工具定义或工具执行结果会直接夺走行动与闭环能力，去掉另外两者的代价则取决于信息能否从当前观测重建。ReAct 循环的本质是通过不断追加轨迹来让模型持续推进任务。
- **Harness 是竞争力所在**：模型能力正在商品化，真正的差异在于 Harness——围绕上下文和工具构建的约束、验证与纠正机制，确保 Agent“可靠地做事”。在生产级的 Agent 系统中，Harness 的绝大部分代码都在实现这些保障机制，而不仅仅是上下文和工具本身。
- **从工作流到自主 Agent**：先优化提示词，再考虑工作流，最后才引入自主 Agent——这是降低意外风险最实用的顺序。每种编排模式都有其适用场景，不存在通用最优解。
- **五个设计模式贯穿全书**：提议者—审核者、渐进式披露、只增不改、边界集 + 保留集、最小 diff + 可回滚。
- **安全是架构问题**：安全问题从第一行代码就要考虑，而不是上线前打补丁。护栏按被绕过的难度分为上下文层、执行层与数据层三层，后续各章的安全讨论都挂在这个骨架上。

下一章将深入探讨 Harness 中最核心的组件——上下文工程。关于 Agent 概念在强化学习中的学术渊源，以及传统 RL 与现代 LLM Agent 的深入对比，我们将在第八章系统展开。
