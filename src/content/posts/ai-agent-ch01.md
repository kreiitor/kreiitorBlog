# 第1章 AI Agent 入门

> 本笔记对应原书《深入理解AI Agent：设计原理与工程实践》第1章 AI Agent 入门，原书印刷页码 7–29 页（PDF 第 15–37 页）。
> 全章先给一张本章地图，再逐节精读，末尾是自测题与原书练习题的索引。

## 本章地图

这一章要回答两个问题。一个是 Agent 到底是什么，作者用一个能落地的最小工程公式把它拆开：`Agent = LLM + 上下文 + 工具`，同时划清 Agent 与 Environment（环境）的边界；另一个是 Agent 怎么在生产环境里可靠运行，由此引出 Harness 工程，并说明为什么模型之外的约束、验证和纠正才是产品化的胜负手。作者给这一章的定位是全书的概念地图，会快速引入 Agent 的核心公式、运行循环、工程框架和设计模式，为后面各章提供统一的术语和参照坐标；也正因为是地图，初读不必逐一记住所有概念，先建立整体印象就够，后续每一章都会把这里提到的某个方面展开讲。它在全书里排在第一章，没有上一章，向后提供的是统一的术语和坐标：第二至六章讨论构建（对应 Harness 五要素），第七至九章讨论评估与进化，第十章讨论多 Agent 协作；Agent 概念在强化学习里的学术渊源、以及传统 RL 与现代 LLM Agent 的深入对比，放在第八章系统展开，紧接的下一章则深挖 Harness 里最核心的那块，也就是上下文工程。作者还专门交代了本章与 1.2.6 节的关系：全书的结构骨架只有一个，就是引言和后记反复使用的 `Agent = LLM + 上下文 + 工具`，`Agent = Model + Harness` 是同一事物在生产形态下的展开。往下看的分法是这样：1.1 回答「Agent 是什么」，顺序先具体后抽象，先讲工具这双手脚，再深入大脑（LLM）和眼睛（上下文），再用 ReAct 循环把三者串起来，其中 1.1.1 先给出观察空间／动作空间这个接口层视角；1.2 回答「怎么可靠地跑」，先给 `Agent = Model + Harness` 与 Harness 五要素（上下文管理、工具接口、约束、验证、纠正），再展开三个不属于五要素却绕不开的决策主题，即模型选型、编排模式、护栏与安全性，1.2.6 再把五要素对回全书章节；1.3 一次性命名并定义贯穿全书的五个设计模式，1.4 收束全章。读完这一章，应该能用自己的话解释那个公式为什么不含 Environment、加号为什么表示工程组件的组合，能画出 Agent 与 Environment 的闭环交互以及 Agent 内部的 Model–Harness 结构，能说清观察空间与动作空间为什么是底层模型固定时最主要的系统工程杠杆，能完整复述 ReAct 循环并写出 `上下文 = 静态前缀 + 轨迹` 这个分解，能讲出 Harness 五要素各自的分工与它们落在第二至六章的哪一章，还能判断一个场景该用工作流还是自主 Agent、两类护栏（三层防线加人工干预）分别挡什么。章末的思考题一共 10 道，标了 ★/★★/★★★ 三档难度，原书明确声明不设标准答案。

## 1.1 现代Agent = LLM + 上下文+ 工具

现代 Agent 的最小工程实现可以浓缩成一个很短的公式：`Agent = LLM（大语言模型，Large Language Model）+ 上下文 + 工具`。原文给这个加号加了两条限定。一条是加号在这里只表示工程组件的组合，别把它读成强化学习里的形式化定义；另一条是这个公式只描述 Agent 边界之内的实现，其中不含 Agent 要与之交互的 Environment（环境）。公式里每个词都得做「广义但边界清楚」的理解，这一点是后面许多讨论的前提。

说到 LLM，它是 Agent 的大脑，指的是一整套决策内核：理解意图、思考规划、做出判断，模型参数只是它的载体之一。人的大脑不光是神经元的集合，还包括被经验塑造出来的思维方式，LLM 的能力同样来自两处，一是预训练积累的世界知识与语言能力，二是后训练固化下来的决策策略，监督微调与强化学习这些后训练技术放到第八章展开。上下文是 Agent 的眼睛，它涵盖 Agent 在每个决策点收到并保留的信息表示，包括来自环境的观察、用户记忆、领域知识、自身状态和任务进展，喂给模型的那段文本只是其中一部分。工具是 Agent 的手脚，指 Agent 用来感知或改变外部世界的接口，涵盖工具定义、调用协议和适配器，形态上从预定义的工具调用一直到动态生成代码，从委托子 Agent 协作到主动跟用户沟通。换个更直观的说法，`Agent = 大脑 + 眼睛 + 手脚`：大脑负责思考和决策，眼睛接收环境提供的观察，手脚把决策转化为作用于环境的行动。

在经典的强化学习和控制论视角下，Agent 与 Environment 是闭环交互的两方，两者谁也不属于谁。环境不断向 Agent 返回当前观察，Agent 根据已有上下文选择下一步行动；行动改变环境状态，新的状态再产生下一次观察，循环由此继续。原文称这是「理解所有 Agent 交互的最小结构」。

图 1-1 把两个抽象层次画在了同一幅图里：外层是 Agent 与 Environment 的交互关系，内层是 Agent 内部的 Model–Harness 结构。

> 图 1-1（原文插图）：外层是一个闭环。左侧是标记为「Agent（智能体）」的大框，右侧是标记为「Environment（环境）」的框；环境框里列出了它包含的东西，包括「状态与转移规律」「当前状态」「执行行动后产生新状态」，以及具体的载体「文件系统 · 数据库 / 网页 · API · 应用程序 / 用户 · 其他 Agent / 仿真或物理世界」。Agent 框与 Environment 框之间有两条方向相反的箭头：Environment 指向 Agent 的那条标注为「观察」，Agent 指向 Environment 的那条标注为「行动」，构成「观察 → 决策 → 行动 → 新状态 → 新观察」的循环。内层是 Agent 框内部的三段结构：上方是「Harness（模型运行与交互层）」，框内注明其职责为「循环 · 状态管理 · 权限 · 验证 · 纠正」；中部是「上下文」，括注「观察 · 历史 · 记忆 · 任务状态」；下部是「Model」，括注「理解 · 推理 · 选择下一步行动」；最下面是「工具与动作接口」。也就是说，Environment 只通过观察和行动两条边跟 Agent 打交道，Agent 内部再分成 Model（做决策）与 Harness（构造上下文、暴露工具、跑循环、做治理）两半。图中 Harness 画在 Agent 边界之内、Environment 画在边界之外，这正是原书反复强调的那条边界。

据此，本节开头的工程公式还可以重新展开：LLM 对应 Model，「上下文 + 工具」构成最小 Harness；生产系统还会在 Harness 里加入约束、验证和纠正。原文强调过一句，「后文所有架构都遵循这条边界。」这三个工程组件可以映射到 RL（强化学习，详见第八章）的策略与交互接口上，但谈不上严格的一一等同：上下文是具体观察和历史在 Agent 内部的表示，并不等于整个观察空间；工具定义的是 Agent 可使用的观察与行动接口，工具背后的对象仍然属于环境。

原书用一张表给出「直觉理解—实现组件—学术概念」的三列对应，这里按原文语义还原，并把各列含义一并列出：

| 直觉理解 | 实现组件 | 学术概念 | 含义 |
| --- | --- | --- | --- |
| 大脑 | LLM | 策略（Policy） | Agent 决定「下一步做什么」的决策逻辑——面对当前看到的信息，从所有可选行动中挑出最合适的一个 |
| 眼睛 | 上下文构造 | 观察与历史 | 将环境返回的观察与已有历史组织成当前决策所需的信息 |
| 手脚 | 工具与适配器 | 观察/行动接口 | 规定 Agent 可以读取哪些观察、发出哪些行动，以及接口采用什么格式 |

公式里为什么没有 Environment，这是初学者最容易忽略、也最容易被面试抓住的一点。如果写成 `Agent = LLM + 上下文 + 工具 + 环境`，这句话就成了同义反复，因为环境根本不归 Agent 所有，Agent 既不能构造它也不能修改它，只能观察它、对它施加行动。原书的说法是二者构成「闭环交互的两方」。可以这样理解：Agent 是你写的程序，Environment 是程序外面的世界，文件系统、数据库、网页、用户、传感器都在里面。程序里能定义「我怎么看世界」（观察通道）和「我怎么动手」（动作接口），却没法在代码里定义世界本身。所以公式只列 Agent 边界之内的三样东西。

加号的意思也值得澄清一句。原文特意说明它表示工程组件的组合，怕的是读者把它当成一个数学定义去推导，因为 RL 里的 Agent 是个被精确定义过的概念，一个策略函数加一套交互协议，而 `LLM + 上下文 + 工具` 只是工程上把三块拼起来。读懂这条限定，后面看到 `Agent = Model + Harness` 时就不会困惑「怎么又来一个公式」，它同样是工程视角的展开，谈不上另一套理论。

从三大组件走到 Model–Harness 两分，中间只有一步：先有 `Agent = LLM + 上下文 + 工具`，图 1-1 再指出「上下文 + 工具」总在同一侧，都在 Agent 边界内、都围绕模型服务，于是把它们打包成 Harness，得到 LLM → Model、上下文 + 工具 → 最小 Harness。这么打包的收益很实在，「围绕模型的那层工程外壳」从此有了名字，可以被单独讨论、单独优化。第 1.2 节整节就在讲它，第 1.2.6 节再把它拆细，跟后续章节一一对上。

脑／眼／手这个类比好用，但别推过头。眼睛并没有相机那么全，上下文并不等于整个观察空间；手脚也不是末端执行器，按原书的说法，工具定义的是观察与行动接口，工具背后的东西（那个真实的数据库、那个真人用户）仍然属于环境。准确的说法是，上下文和工具处在接口层，被接口连接的对象另有归属。这一点到 1.1.1 节会变成一条核心论点。

落到工程实践上，这三个组件正好对应三条可独立优化的杠杆：换更强的模型、把信息更好地组织进上下文、给模型更多更好的工具。1.1.1 节把这层意思说得很直接，底层模型固定时，最有效的系统工程手段往往就是后两条。这给排优先级提供了依据：预算只够动一项时，先动最有瓶颈的那一项，别本能地去换模型。

有两组概念容易混。上下文是 Agent 在每个决策点能看到的全部信息，是一个信息集合；上下文窗口则是模型／API 层面能容纳这段信息的容量上限，原书在实验 1-2 里提到 Kimi K3 拥有 100 万 token 的上下文窗口，前者讲内容，后者讲容量。工具和工具背后的对象也要分开：工具是接口，包括名称、描述、参数格式、调用协议、适配器；被工具操作的东西，数据库也好、网页也好、用户也好，都归 Environment。原文那句「工具背后的对象仍属于环境」把这条线划得很干净。

再看两个公式的关系。`Agent = LLM + 上下文 + 工具` 与 `Agent = Model + Harness` 算不上两套并列的划分：前者是全书从头到尾的结构骨架，后者是同一事物在生产形态下的展开，「上下文 + 工具」被细分成上下文管理、工具接口、约束、验证、纠正五项职责。骨架只有一个，Model + Harness 只是它在「构建」这部分内部的一个观察视角。RL 的 Agent 与本书的 Agent 之间可以映射，大脑对策略、眼睛对观察与历史、手脚对观察／行动接口，但原书反对把二者画等号。

回过头看那个公式：Agent 边界之内只有三样东西，大脑（LLM）、眼睛（上下文）、手脚（工具）；环境在边界之外，只通过「观察」和「行动」两条边进出。

### 1.1.1 观察空间与动作空间：模型与世界的接口

观察通道与动作接口一起，构成了 Agent 与外部环境之间的边界。Harness 在这里做两次转换：先把环境返回的观察转换成模型能够处理的上下文，再把模型选择的行动转换成对环境的工具调用。

原文给了两条「不存在」的判据。没有通过观察通道进入上下文的信息，对模型来说就像不存在；没有被动作接口允许的操作，模型即使知道该怎么做，也只能停留在文字建议上。由此推出本节的核心论断：在底层模型固定时，提升 Agent 任务表现最主要的系统工程手段，往往就是重新定义或扩展观察空间与动作空间。用本书的术语说，就是扩展上下文和工具。原文进一步说：「许多看似需要『更聪明模型』的问题，其实只是接口问题：把任务所需的数据纳入上下文，或把完成任务所需的操作封装成工具，原本不可解的任务就可能变得可解。」

Manus 是一个把原本分离的空间合并起来的例子。在 Manus 出现之前，生产级 Agent 大多沿着三条相对独立的路线发展：Deep Research（深度调研）、Coding（代码生成）、Computer Use（电脑操控）。Manus 的突破在于率先把三者放进同一个有广泛影响力的生产级 Agent 里：虚拟浏览器扩大了它的观察空间，文件系统、代码执行与命令行执行扩大了它的动作空间。原文的判断是，它的通用性来自取三类 Agent 观察空间与动作空间的并集，单靠替换一个更强的模型做不到这一点，而正是这个并集让同一个 Agent 能跨越原有产品边界完成任务。

OpenClaw 走的是另一条路，它把这两个空间向外又推进了一层。一边是通过用户已经在使用的 WhatsApp、Telegram、Slack、Discord、iMessage 等消息渠道接收任务和返回结果，让 Agent 可以随时随地被人触达；另一边是采用本地 Gateway，连接 Google Drive、Notion 等云应用以及本地文件系统。结果是分散在不同账号与设备中的数字文件，都可以在用户明确授权后进入同一个 Agent 的观察空间，并被它的工具处理。原文在这里做了一个对比：早期 Manus 以隔离云端沙盒为中心，往往需要上传文件或另行配置连接器，本地优先的 OpenClaw 跨越了更大的数据边界。原文还补了一句点睛的话，Manus 后来也加入了 Google Drive 连接器和桌面端本地访问，这恰好再次说明，产品能力的演进往往就是观察空间和动作空间的演进。

介绍顺序也在这里交代清楚了：理解工具、LLM、上下文这三者的作用及其相互关系，是构建有效 Agent 系统的基础，所以先从最具体的手脚（工具）讲起，再逐步深入到大脑（LLM）和眼睛（上下文）。原书随后给出一张五个真实 Agent 产品在「眼睛／手脚／策略」三个维度上的对照表：

| Agent 产品 | 眼睛（感知） | 手脚（行动） | 策略 |
| --- | --- | --- | --- |
| Cursor 等 Coding Agent | 需求、读取到的代码片段、目录列表、终端输出 | 开放式（代码搜索、文件读写、执行命令等） | 增量开发：理解需求→搜索相关代码→编辑代码→测试验证→调试修复 |
| Deep Research 等搜索 Agent | 搜索结果、网页内容、论文摘要与引用 | 开放式（搜索查询、网页读取、生成报告等） | 迭代深化：根据已有信息调整搜索方向，逐步综合出完整报告 |
| Browser Use 等电脑操控 Agent | 屏幕截图、DOM 或无障碍树、操作结果 | 开放式（点击、输入、滚动、截图、执行代码等） | 视觉感知+操作：观察屏幕→识别目标元素→执行操作→验证结果 |
| 豆包等手机助手 Agent | 手机截图、App 界面状态、系统反馈 | 开放式（点击、滑动、输入、打开 App 等） | 意图理解+App 操控：理解用户需求→定位目标 App→执行操作→确认完成 |
| Pine AI 等个人办事 Agent | 经授权读取的账户记录、账单结果、服务商资料 | 开放式（打电话、发邮件、填表单、与用户确认） | 多步骤任务执行：收集信息→制定协商策略→联系服务商→谈判→汇报结果 |

原书从表里总结出这些系统的共同特征：它们都使用开放式的动作空间，都能在采取行动前先思考和规划，也都能根据环境反馈不断调整策略。原文的结论是，这些能力来自大脑、眼睛和手脚，也就是 LLM、上下文和工具的协同作用。

「像不存在」这三个字是整个 1.1.1 节的题眼。模型的决策完全基于它当次调用看到的上下文，你没把某个数据放进去，它就只能靠参数里的记忆去猜。它不会知道自己看不到这个数据，反而很可能给出一个语气笃定的答案，这一点在 1.1.4 节的实验 1-1 里被明确验证。动作接口那边同理，模型知道该删文件，但你没给它 `delete_file` 工具，它就只能写一句「你可以这样删除……」。接口设计这件事，本质上是在决定模型的能力上限。

「很多问题只是接口问题」这句话，可以拿一个笔记自己举的例子（非原文）来体会。一个 Agent 要算「这批订单里有多少是重复下单」。如果它的上下文里只有订单号的文本列表、动作空间里只有「生成一段自然语言」，它会写出一段看着很有道理的估算。把订单表通过一个查询工具接进来（观察空间 +），再给一个代码解释器（动作空间 +），同一个模型就能精确算出来。模型一点没变，任务从不可解变成了可解，这正是原书那句话的字面意思。

观察空间和上下文、动作空间和工具之间存在换算关系：观察空间对应上下文（进入边界的信息），动作空间对应工具（能发出的操作）。两者并不完全等同。原书在 1.1 里就说过，上下文并不等于整个观察空间，上下文是观察在 Agent 内部被组织后的表示；同理，工具定义的是接口，工具背后的对象仍在环境里。

Manus 这个案例要读成「并集」，跟「更强的模型」是两回事。如果把 Manus 的成功归因于模型更强，就会得出错误的产品结论，跑去卷模型选型。原文特意强调它没有仅靠替换一个更强的模型，因为它取的是三类 Agent 空间的并集。并集带来的效果是跨越原有产品边界：Deep Research 的 Agent 走到写代码那一步就停下，Coding Agent 走到要上网查资料那一步就停下，而并集 Agent 可以一路走到底。原书后面反复说的「通用性很大程度上来自接口边界的扩大」（见 1.4 本章小结），讲的就是这件事。

OpenClaw 要把两件独立的事分开看。一件是触达渠道，WhatsApp、Telegram、Slack、Discord、iMessage 解决的是「用户在哪里找到 Agent」，属于交互时机（第六章）；另一件是数据接入，本地 Gateway 连 Google Drive、Notion 和本地文件系统，解决的是「Agent 能看到哪些数据」，属于观察空间的扩大。原文把「本地优先」当成关键对比点：云端沙盒意味着数据得先上传才能被看见，本地优先则意味着数据不动、Agent 动。

那个「Manus 后来也加了连接器」的细节之所以值得写进书里，因为它是可观察的行业证据。假如「产品能力等于观察空间加动作空间」这个判断成立，那么一个最初以云沙盒为中心的产品，就应该会逐步把边界往用户数据所在地推。原文的措辞是「这恰好再次说明」，也就是说它把该案例当论据用，谈不上趣味轶事。看一个 Agent 产品的路线图，可以看它在扩哪一侧的空间。

那张 Agent 产品表别只当清单看，要横向比「眼睛」那一列。五个产品的手脚一栏全都写着「开放式」，差异几乎全在眼睛和策略上：Coding Agent 看代码与终端输出，Browser Use 看截图与 DOM 或无障碍树，豆包看手机截图与 App 界面状态，Pine AI 看的是经授权读取的账户记录、账单结果、服务商资料。这些产品的差异主要是观察空间和策略的差异，而「策略」一栏恰恰是眼睛、手脚和模型三者协同出来的行为模式（原文用的词就是「策略」）。另外注意 Pine AI 那一行里的「经授权」三个字，原书在这里就埋下了权限与授权是观察空间前提的伏笔，后面 1.2.5 的「故障安全默认值」与此呼应。

「开放式动作空间」的开放落在哪里，原文的定义很精确：模型能生成任意自然语言和代码，可选范围不再限于有限的几个按钮。这解释了为什么 LLM Agent 与传统 GUI 自动化脚本有本质区别。脚本的动作集合是有限的，无非点击坐标和按键；LLM Agent 的动作集合是生成式的，理论上它可以写出一段谁也没预先写过的代码。好处是通用，代价是出错和攻击面也随之扩大，1.1.2 节马上会讲这个话题。

扩大观察空间不是免费的。把更多数据放进上下文会挤占上下文窗口、拉高成本，还会引入上下文污染和提示注入的风险面；扩大动作空间则放大了误操作、越权与不可逆操作的风险。所以原文在本章小结里补了一句关键限定：「这种扩大必须按需进行，并配合权限控制和验证。」接口确实是能力杠杆，但接口越宽并不因此越好。

瓶颈确实落在模型的推理或泛化能力上时，比如需要高维语义判断、需要多步严密逻辑，再怎么扩接口也补不上，这时只能等模型变强或者做后训练。原文的说法是「在底层模型固定时」这个手段才叫「最主要」；反过来说，模型本身是短板时，接口不是主要矛盾。

> 🔎 检索确认：Manus 在 2026 年发布的 My Computer / 桌面端确实把「重要工作位于本地而非云端」作为云沙盒的局限来陈述，与原文脚注 1 的描述方向一致。（来源：[Manus 官方博客](https://manus.im/blog/manus-my-computer-desktop)）

几组容易混的说法收在这里。观察空间是「环境能提供给 Agent 的全部观察」，上下文是「某一次决策时，Agent 内部实际组织好的那部分信息表示」，上下文是观察空间的一个子集，还可能掺入记忆、领域知识等非观察来源。动作空间是「允许发出的操作集合」，工具则是「这些操作的接口封装（定义、协议、适配器）」，工具是动作空间的实现形态。判断一个失败属于接口问题还是模型问题，可以问一句「把数据／操作给到这个模型，它做得对吗」：答案是「对」，原来的失败就是接口问题；答案还是「不对」，才是模型问题，这个问法是笔记补充的，也是本节论断最实用的操作化形式。至于 Manus 的「合并」与 OpenClaw 的「延伸」，前者是在云端把三条产品线的空间取并集，横向合流，后者是把接口推到用户已有的渠道和本地数据上，纵向外扩，共同点是都靠扩空间，谁也没靠换模型。

模型固定时，Agent 的能力上限由「它能看到什么」和「它能做什么」决定。扩观察空间（上下文）与动作空间（工具），常常比换一个更聪明的模型更管用。

### 1.1.2 工具：Agent 的手脚

模型再能推理，也只能吐出文字。想让它真的读到一个文件、真的发一封邮件，就得给它工具。原书把这个位置说得很直白：没有工具，Agent 只能纸上谈兵。工具也是「手脚」这个比喻的落点：感知类工具把外面的信息带进来，执行类工具把 Agent 的决策送出去。

原书按互动的方向把工具分成五类。五个名字不难背，难的是分清楚边界，所以记两个问题就够了：信息往哪边走，谁发起。

| 类别 | 信息方向 | 谁发起 | 例子 |
| --- | --- | --- | --- |
| 感知工具 | 环境 → Agent | Agent 主动去取 | 搜索引擎、读本地文档、查数据库、对接外部服务与企业核心数据的 API |
| 执行工具 | Agent → 环境 | Agent 主动去做 | 跑代码、写文件、执行系统命令、调外部 API |
| 协作工具 | Agent ↔ 别的 Agent 或人 | Agent 主动发起 | 委托子 Agent、请人确认、多 Agent 协调 |
| 事件触发工具 | 环境 → Agent | 外部事件推过来 | 新邮件、到点、别人发来的 Webhook |
| 用户沟通工具 | Agent → 用户 | Agent 主动发起 | 发消息、打电话、发邮件 |

看第一行和第四行：方向一样，发起方不同。这就是五类里唯一一个容易被归错的地方。前三类是 Agent 调用工具，事件触发工具反过来，是外部世界在调用 Agent。它把 Agent 从「我什么时候去查」变成「有事发生就叫醒我」。原书的措辞是「在调用方式上有本质的区别」；也正是因为它其实是环境向 Agent 提供观察的另一条通道，才被算进广义的工具里。

用户沟通工具也容易划错。它和执行工具一样由 Agent 主动发起，但不改变外部世界的状态：发一条「任务完成了」不会让数据库多一行记录。它的作用是让人知道发生了什么，原书在这里用了「主动关怀」这个说法。单独列出来的好处很实际，这类工具的风险天然很低，可以和扣款、删数据那种操作分开管。

工具调用（Tool Calling，也叫 Function Calling）是现在 LLM Agent 的一项核心能力，让模型用结构化的方式调外部工具。原书说它「将 LLM 从一个纯粹的文本生成器转变为能够执行实际操作的智能系统」。本书后面统一叫「工具调用」，见到 Function Calling 就当同一个词。流程分四步，用查天气走一遍：

```text
# 第一步：声明工具（开发者写）
tools: [{ name: "get_weather", parameters: { city: "string" } }]

# 第二步：模型决定调用（模型产出）
assistant: { tool_calls: [{ function: "get_weather", arguments: {city: "北京"} }] }

# 第三步：结果追加到上下文（框架执行后回填）
tool: { tool_call_id: "call_1", content: '{"temp":28,"sky":"晴"}' }

# 第四步：模型基于结果回复
assistant: { content: "北京今天28°C，晴。" }
```

四步里最值得记住的是那条分工线。第一步的 `tools` 数组是开发者写给模型的能力清单；第二步的 `tool_calls` 是模型自己产出的请求，要不要调、调哪个、参数填什么，全由模型决定。第三步是框架把执行结果用 `tool_call_id` 配对后塞回上下文，第四步模型看到结果再说话。开发者的活只有两件：定义工具、执行工具。

这四步其实就是一轮 ReAct：第二步是行动，第三步是观察，一头一尾分别是「有哪些工具可用」和「看着结果再想」。原书提醒这里的 API 是简化表示，真实字段层级更细，第二章展开。另外，这条分工线也正好把自主 Agent 和工作流分开：工作流连下一步走哪个节点都写死在代码里，工具调用把这一步交给了模型，所谓「自主」，说的就是这里。

设计工具的原则，原书的建议是从最窄的能力起步，随任务变复杂再扩。只做四则运算，一个参数清楚的计算器就够；任务变成「读表、补缺失值、算统计量、画图」，受限的 Python 代码解释器就比堆一堆专用工具好用，一次调用加一段模型自己写的代码，四件事全办了。不过通用是拿风险换来的：解释器是开放的，模型能写任意代码。所以原书给这些工具列了一串硬边界，用的词是「必须」和「默认」，不是可选，代码在隔离沙盒里跑，默认不联网，不读授权工作目录外的文件，执行时间、CPU、内存、输出大小都要设上限。

长程任务还有个专门设计，叫受控虚拟工作目录。单个日志工具记一段执行过程够用；但要跑几小时甚至几天的任务，麻烦不在某一步做错，而在上一次的结果带不到下一次。给它一个受控的虚拟工作目录，计划、中间结果、运行日志、最终产物都落在里面，「接着干」就变成了「读回自己写的文件」。这跟 1.1.3.2 讲的外部产物更新是一件事的两面。这个目录同样要限定可读写路径、容量和文件类型，防路径越界，而不是把宿主文件系统敞开。

反过来说，通用并不总是更好。支付、删数据、发邮件、生产部署这些操作，该封成参数明确、权限受限、全程可审计的专用工具，必要时加预览和人工确认。到了动钱、删数据、对外通信、改生产环境这几件事上，模型的判断不能依赖。原书把这条上升成原则：通用基础能力用于组合与探索，专用工具用于约束高风险和强业务规则的操作。

这里有两组词值得先分清。工具是被定义出来的能力，名称、用途、参数、执行实现加在一起才叫一个工具；工具调用是模型在某一轮做出的结构化动作，也就是 `tool_calls`。四步流程里第一步是「声明工具」，第二步才是「工具调用」，两个词别当同义词用。沙盒和虚拟工作目录也不是一回事：沙盒是隔离与限制的边界，不联网、越权即拒；虚拟工作目录是持久化与接续的介质，存计划、中间结果、日志和产物。两者常一起用，要解决的问题不同。

还有两件事值得记住。一是工具设计的质量直接决定 Agent 能走多远，原书点了三个失败模式：接口定义不清，模型就乱用工具；错误处理不到位，一次调用失败就可能死锁；权限放得太宽，出错之后难以挽回。二是 MCP（Model Context Protocol，模型上下文协议）标准的推广正在让工具接入变容易，它解决的是接入和互操作，把「给 Agent 加个工具」从各框架各做一遍变成统一协议，也就是把 1.1.1 说的「扩空间」这件事的成本压下来。五类工具的完整分类和设计原则在第四章，工具调用的真实 API 结构在第二章。

### 1.1.3 LLM：Agent 的大脑

大语言模型（Large Language Model, LLM）是 Agent 的决策核心。收到用户的请求后，它要完成三类工作。先解析真实意图，原文在这里特意加了一个括号说明，「用户说的往往不是他真正想要的」；再把模糊或复杂的任务拆解成可执行的步骤；执行过程中还要持续做出判断，下一步该做什么、要不要调用工具、调哪个工具、传什么参数。原文把上面这套能力称为「理解-规划-执行」，它来自预训练所积累的知识，也是工作流和自主 Agent 都依赖的基础。这里的范围值得留意：自主 Agent 固然依赖它，工作流里每个节点内部的「理解和生成」（见 1.2.4.1）同样依赖它。

LLM Agent 的一个独特能力是内部思考，也就是在采取实际行动之前先做规划与推演。这个过程不改变外部环境，却能显著提升后续行动的质量。它之所以能进行有效的内部推演，得益于预训练（Pre-training，即在海量互联网文本上进行初始训练，让模型学会语言规律和世界知识）阶段习得的能力：模型推演时遵循的是人类知识中已经沉淀下来的逻辑规则，包括数学定律、因果关系、问题分解策略等等。由此可以对比传统 RL Agent：今天基于 LLM 的 Agent 有一套结构化的知识体系可以依托，不必像传统强化学习 Agent 那样靠盲目的随机探索。

内部思考为什么被单列成一种独特能力？因为它把「想」和「做」分开了。传统 Agent（比如 Q-learning 的机器人）通常「想=做」：选一个动作就直接作用到环境上，试错只能靠真实交互。LLM Agent 可以在不消耗环境代价的前提下先推演一遍，原文说它「不改变外部环境，却能显著提升后续行动的质量」。工程上的直接收益是试错成本从「真实世界的一次操作」降到了「一次 token 生成」。这也是 ReAct 里 `reasoning` 那一部分存在的理由，1.1.4 节的实验 1-1 会给它一个更精确的定位：它记录的是「为什么这么做」。

「在结构化知识体系上展开」这句话是有分量的，原文用它来对比传统 RL Agent 的盲目随机探索。机制上，LLM 在推演时遵循的是预训练语料里已经沉淀的逻辑规则，也就是数学定律、因果关系、问题分解策略。所以它不需要从零试错就能做出看起来合理的规划。反过来也成立：预训练语料里没有沉淀的规则，LLM 的推演就不可靠。这解释了为什么私有业务规则、企业内部约束必须通过上下文（RAG、Prompt）或者外部产物补进去，也就是 1.1.3.2 里的中间那条路径。

#### 1.1.3.1 模型即Agent：当模型本身成为产品

「模型即 Agent」（Model as Agent）这个新范式代表了 AI Agent 发展的最新方向。先进模型通过后训练（特别是强化学习）把工具调用能力内化为原生能力：何时调用工具、调哪个、传什么参数，都由模型自己决定，无需人工编排。

不过这不意味着框架层变得不重要了。原文的措辞更重，恰恰相反，模型越强大，围绕模型构建的 Harness 就越关键。Harness 这个词原本指马具，也就是套在马身上的缰绳与挽具，它的用处在于把马的力量引导到正确的方向上，并不打算限制马的奔跑能力。换到 Agent 语境里，模型是那匹强大但不可预测的马，Harness 是把它的能力引导成可靠任务执行的工程外壳。在 Agent 中，Harness 包括上下文管理、工具接口、安全约束、验证与纠正等基础设施（详见本章末节 1.2.6）。模型自主决策的空间越大，出错时的影响面也越大，因此需要更精细的约束、验证和纠正机制来确保可靠性。原文对模型厂商的判断是：它们的真正优势在于能对模型与外围 Harness 做协同优化并持续迭代，把框架做薄算不上优势。

《苦涩的教训》之问值得单独说。Rich Sutton 在《苦涩的教训》（The Bitter Lesson）中回顾了 AI 研究七十年间反复上演的一幕：研究者一次次把自己对领域的理解编码进系统，短期见效，长期却总是输给能随算力与数据规模持续扩展的通用方法，也就是搜索与学习。以此衡量，Harness 里的约束、验证与纠正，有多少属于「人类先验」，注定会被模型内化？

本书的立场分两句：方向认同，节奏务实。方向上，本书不怀疑模型会持续吃掉 Harness，工具调用、长程规划都曾靠外部编排，如今已是模型的原生能力；节奏上，这个「吃」的过程远比想象中慢，训练以月计，模型也无法一次内化真实业务中所有的约束与偏好，模型此刻的能力边界，就是 Harness 此刻的价值所在。由此得到的结论是：Harness 工程并没有在抵抗《苦涩的教训》，它做的是把这一教训放到工程的时间尺度上实践，模型还做不稳的，Harness 先补上；模型每内化一层，Harness 就卸下一层，转而兜底新的能力前沿。

> 脚注 2（印刷 p.11）：Sutton, Rich. "The Bitter Lesson", 2019. <http://www.incompleteideas.net/IncIdeas/BitterLesson.html>

「模型即 Agent」最反直觉的地方在于，字面上它听起来像是「框架可以退休了」，原文的结论却恰恰相反：模型越强，Harness 越关键。理解这一点要分清两件事：决策权转移了，执行与治理没有转移。模型决定调哪个工具、传什么参数，这是决策；工具的真实实现、代码沙盒、调用的发起与结果的回传，仍然在模型之外的基础设施里完成。原文在实验 1-2 里把这一点讲得极清楚：编排循环并没有消失，只是决策权交给了模型；至于循环本身跑在哪里，取决于接入方式。

马具这个类比还有一层精确含义。原文特意澄清它不是为了限制马的奔跑能力，所以 Harness 的默认姿态是定向，谈不上刹车。这能纠正一个常见误解：很多人把 Harness 等同于「安全审查」，其实 Harness 还包括上下文管理和工具接口这两项纯功能性职责（1.2 节的公式：Harness = 上下文管理 + 工具接口 + 约束 + 验证 + 纠正）。前三项里有两项是「让它能做事」，后三项才是「别做错事」。

《苦涩的教训》的读法也要说一下。原文的用法是「以此衡量，Harness 里的约束、验证与纠正，有多少属于『人类先验』？」，也就是把它当成一把尺子，用来判断哪部分 Harness 是临时脚手架、哪部分是长期价值。本书给出的答案是前半句「方向认同」、后半句「节奏务实」。「节奏务实」有具体的支撑论据：训练以月计，模型无法一次内化真实业务中所有的约束与偏好。工程结论就是那句很实用的话，Harness 是随能力前沿滚动的，模型每内化一层它就卸下一层，因此它更像需要持续维护的活资产，一次性建完就搁置的静态资产在这里不成立。

接下来还有一段对比要交代：内部思考（`reasoning`）和工具调用（`tool_calls`）都出现在模型的输出里，但前者不改变外部环境，后者会改变外部环境。1.1.4 节会说，前者记录「为什么这么做」，后者及其结果记录「发生了什么」。「模型即 Agent」也不等于「框架不重要了」，原文的立场是决策权内化到模型、执行与治理仍在 Harness；判断某个产品算不算「模型即 Agent」式，关键落在「调不调工具、调哪个、传什么参数」这件事由谁决定，有没有框架说明不了什么。

#### 1.1.3.2 Agent 的学习机制：从上下文适应到持久更新

前面讨论了模型可以通过强化学习把工具调用策略内化为原生能力，但 Agent 的行为改变不只发生在训练阶段。原文按更新发生的位置和持续时间，把它理解为三条互补路径（图 1-2）：任务内的上下文适应（Context adaptation）、跨任务的外部产物（artifact）更新（External artifacts）、训练周期中的参数更新（Parameter update）。

| 路径 | 主要载体 | 更新特性 | 补充说明 |
| --- | --- | --- | --- |
| 任务内适应（Context adaptation） | 当前上下文：示例 · 状态 · 检索结果 | 即时、低成本；任务结束后不自动保留 | 发生在当前任务中；示例、状态和检索结果进入上下文后，模型可以立即调整行为，却不会因此改变下一次会话的持久状态。优势是快速、低成本，局限是受上下文窗口和信息组织方式约束；第二章将详细讨论这种适应如何工作 |
| 外部制品更新（External artifacts） | 知识 · 指令 · 程序：文档 · Prompt/Skill · Harness | 跨任务持久、可审计；依赖检索或工具调用 | 把事实和经验整理为知识文档，把可语言化的策略写进 Prompt 或 Skill，把确定性流程与约束写成程序和 Harness。这些产物可审计、可修订，执行时仍需通过上下文或工具接口被 Agent 使用。第三至五章分别给出知识与程序基础，第九章讨论如何从已评价的运行轨迹中生成这些更新 |
| 模型参数更新（Parameter update） | 模型权重：SFT · 偏好训练 · RL | 高维能力、广泛泛化；训练与回归成本较高 | 当目标是医疗影像理解、自然语言风格或隐式决策策略等高维能力时，外部规则难以完整表达，就需要通过后训练更新模型参数。部署成本较高，却能形成自然、广泛的泛化能力；第八章将系统介绍其方法 |

> 图 1-2（原文插图）：图的标题是「Agent 能力更新的三个层次」，上方有一个总问题「Agent 的行为如何发生改变？」。图的主体是三个并列的竖栏，对应三条更新路径。左栏「任务内适应 / Context adaptation」，列出「主要载体：当前上下文（示例 · 状态 · 检索结果）」与「更新特性：即时、低成本 / 任务结束后不自动保留」。中栏「外部制品更新 / External artifacts」，列出「主要载体：知识 · 指令 · 程序（文档 · Prompt/Skill · Harness）」与「更新特性：跨任务持久、可审计 / 依赖检索或工具调用」。右栏「模型参数更新 / Parameter update」，列出「主要载体：模型权重（SFT · 偏好训练 · RL）」与「更新特性：高维能力、广泛泛化 / 训练与回归成本较高」。三栏下方有一条横向的汇总带，写着「三者协同：临场适应 · 可控积累 · 能力内化」。这张图的用意不在于三选一，它把三条路径按更新的位置（上下文内／外部产物／模型权重）和持续的时间尺度（任务内／跨任务／训练周期）排开，并指出它们合起来才构成完整的学习机制。

三条路径并不互斥，它们是不同时间尺度上的协同机制：上下文负责临场适应，外部产物负责可控积累，参数负责内化难以显式表达的能力。

三条路径的效率与成本也可以对照着记（这一组是笔记补充的）：上下文适应的延迟最低，下一次推理就生效，成本也最低，但留不下东西；外部产物的延迟中等，要写文档、改 Prompt、改代码，能留下且可审计，不过得靠检索或工具调用才被用上；参数更新的延迟最高，要采集数据、训练、回归评测，成本最高，换来的是高维、隐式、广泛泛化的能力。选择顺序因此很自然：能靠上下文解决的就别改代码，能靠改文档或程序解决的就去改代码，只有规则说不清、写不出来的能力才去训模型。原文在 1.3 节把这条顺序直接点破了，「本章开头给出的三条更新路径（上下文内适应、外部产物更新、参数更新），也正是按可回滚程度从高到低排列的。」

为什么高维能力必须走参数更新？原文举了三个例子：医疗影像理解、自然语言风格、隐式决策策略。它们的共同点是外部规则难以完整表达。你可以给模型写一条「写代码要符合 PEP8」，却没法给它写一条「用这种语气说话才像我们的品牌」，或者「这张 CT 片上这个阴影意味着什么」。前者是可语言化的策略，交给 Prompt 或 Skill；后者是隐式能力，只能走后训练。这就是三条路径的分界线，判据是能不能用自然语言把这条规则完整写下来。

工程上最容易踩的两个坑正好在这条线的两侧。一边是把本属于参数更新的问题硬塞进上下文，比如试图用一大段 Prompt 教会模型一种语言风格或者一种影像判读能力，结果通常是长 Prompt 里规则打架、模型抓不住重点，成本和延迟还很高。另一边是把本属于上下文的临时事实硬塞进参数，为一个每周都在变的业务规则去微调模型，也会因为训练与回归成本较高而得不偿失。判据就是两问：这条知识可语言化吗，它变的频率有多高？

> 🔎 检索确认：Rich Sutton 的《The Bitter Lesson》确实于 2019 年发表，原文链接 <http://www.incompleteideas.net/IncIdeas/BitterLesson.html> 有效，其核心论点正是「能随算力与数据规模扩展的通用方法（搜索与学习）长期胜过把人类先验编码进系统的方法」，与原文引用一致。（来源：[The Bitter Lesson](http://www.incompleteideas.net/IncIdeas/BitterLesson.html)）

剩下几点也归到 1.1.3 一并说清。三条更新路径的分界按更新发生的位置来划，也就是上下文内、外部产物、模型权重，跟重要性无关，三者都重要，区别在时间尺度与可回滚程度。可语言化的策略写成 Prompt 或 Skill，走外部产物更新；隐式决策策略必须走后训练，走参数更新，分界还是那句「能不能用自然语言把这条规则完整写下来」。《苦涩的教训》有两种常见误读：一种读成「所有工程手段终将无用」，原文的回应是方向上认同、节奏上务实，而且这个「吃」的过程远比想象中慢；另一种读成「应该继续硬编码人类先验」，原文同样说得明确，它不怀疑模型会持续吃掉 Harness。本书的立场落在两者之间。

1.1.3 的落点可以这么说：LLM 是大脑，在结构化的人类知识上做「理解-规划-执行」，还能「先想后做」；「模型即 Agent」意味着决策权内化进模型，Harness 不会消失，它随能力前沿滚动，模型还做不稳的部分先由它补上。

### 1.1.4 上下文：Agent 的眼睛

上下文是 Agent 在每个决策点能看到的全部信息。原文的类比是，就像一个人做决策时需要看到桌上摊开的所有资料，任务说明、参考手册、之前的沟通记录、最新的数据都在手边，Agent 的上下文窗口就是它的「视野」。

从 API 的视角看（详见第二章），每次调用 LLM 时的上下文由五个部分构成。系统提示词（System Prompt）与用户每次输入的提示词不同，它由开发者编写，在整个对话过程中保持不变，相当于 Agent 的「岗位说明书」，定义它的身份、权限和行为准则；通过提示工程（Prompt Engineering）精心设计系统提示词，可以塑造 Agent 的工作方式。系统提示词里还会包含跨会话保存的用户记忆（用户偏好、历史行为、背景设定等个性化信息，详见第三章）和动态注入的环境状态。工具定义（Tool Definitions）声明 Agent 可用工具的名称、功能描述和参数格式；没有工具定义，Agent 就无法识别和调用任何工具，但它并不会因此停下来，消融实验（实验 1-1）会说明这一点。工具定义与系统提示词一起构成对话中保持不变的静态前缀，原文注明这是基础模式；2026 年以来，生产框架中工具的完整 schema 也可以按需动态加载到上下文末尾而不破坏前缀，详见第二章工具定义一节和第四章。用户消息（User Messages）是来自用户的输入，其中还可能包含通过 RAG（检索增强生成，Retrieval-Augmented Generation，详见第三章）动态检索引入的外部知识，覆盖训练数据截止后的信息或者私有领域知识。

模型回复（Assistant Messages）是模型之前生成的回复，最多包含三个部分：思考过程（reasoning），也就是内部思考链，用于保持思维的连贯性和决策的可解释性；文本内容（content），也就是对用户的回复；工具调用请求（tool_calls），也就是 Agent 采取行动的方式。原文强调，在一次具体的回复中三者不一定同时出现，比如 Agent 决定调用工具时通常只有 `reasoning + tool_calls`，给出最终回答时通常只有 `reasoning + content`。第五部分是工具执行结果（Tool Results），即 Agent 框架执行工具后返回的结果，它们是 Agent 下一步思考的直接依据，也让 Agent 能够从执行结果中学习、避免重复犯错。

这五个部分还可以按静态与动态再切一刀：前两项（系统提示词 + 工具定义）是静态前缀，后三项（用户消息 + 模型回复 + 工具执行结果）是随交互不断增长的动态消息历史。它们共同构成了 LLM 每次推理时的上下文。

要验证每个组件到底有多少贡献，原文给的验证方法是消融实验（Ablation Study），类比医生诊断时逐一排除病因：先去掉 A 组件看系统是否还正常，再去掉 B 组件，以此类推。实验 1-1 正是按这个思路，对上述五个组件做了系统性测试。

**实验 1-1 ★★：上下文的关键作用**（印刷 p.13–14）

实验方法是系统性的消融实验，探索不同上下文组件对 Agent 行为的影响。实验从上述五个部分中选取了四个组件进行测试，系统提示词作为 Agent 的基本身份定义不参与消融，因为没有系统提示词，Agent 连基本的角色认知都没有，测试没有意义。实验设计如图 1-3 所示，五组对照实验包括一组保留全部组件的完整基线，再加上四组各缺失一个组件的对照，以此观察每个组件对 Agent 性能的影响：

| 组别 | 系统指令 | 工具定义 | 思考过程 | 历史记录 | 工具结果 | 结果 |
| --- | --- | --- | --- | --- | --- | --- |
| 完整基线 | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ 正常工作 |
| 无工具定义 | ✓ | ✗ | ✓ | ✓ | ✓ | ✗ 无法调用工具 |
| 无思考过程 | ✓ | ✓ | ✗ | ✓ | ✓ | △ 决策不连贯 |
| 无历史记录 | ✓ | ✓ | ✓ | ✗ | ✓ | △ 重复操作 |
| 无工具结果 | ✓ | ✓ | ✓ | ✓ | ✗ | ✗ 盲目循环 |

> 图 1-3（原文插图）：图题是「实验 1-1——上下文消融实验设计」。它是一张实验设计矩阵：第一行是列头，从左到右依次为「系统指令 / 工具定义 / 思考过程 / 历史记录 / 工具结果 / 结果」；从第二行起是五组对照，每组用一个符号标注该组件是否保留（✓ 表示保留、✗ 表示移除、△ 表示结果处于退化但未完全失效的状态）。第一组「完整基线」五个组件全部 ✓，结果为「✓ 正常工作」；后面四组依次把「工具定义」「思考过程」「历史记录」「工具结果」中的一个置为 ✗，而「系统指令」一列五组全部为 ✓（对应正文所说「系统提示词不参与消融」）。四组对照的结果分别是「✗ 无法调用工具」「△ 决策不连贯」「△ 重复操作」「✗ 盲目循环」，图中用 ✗ 和 △ 区分了能力被彻底夺走和行为退化但还能跑这两种不同程度的后果。

实验结果逐一说明了各组件的作用。工具定义（静态前缀的一部分）是 Agent 行动能力的基础，没有它就无法调用任何工具；但失去行动能力不等于沉默，模型照样会给出一份格式工整、语气笃定的答案，数据却来自参数记忆，与真正基于观测得出的答案排版一模一样。它是坦白拒绝还是就地编造，主要取决于模型自身的幻觉率与诚实度，提示词里「不得自行估计」这类约束只能降低编造的概率，并不能消除。工具执行结果是闭环控制的关键，缺失它会让 Agent「盲目」执行，反复重试直到耗尽迭代预算。思考过程（模型回复中的 reasoning 部分）记录的是「为什么这么做」，工具执行结果记录的是「发生了什么」；当前者可以从后者重建时，把它从历史中丢掉几乎没有代价。历史消息（之前轮次的用户消息、模型回复和工具执行结果）则防止了冗余操作，避免重复犯同样的错误。

实验的核心洞察有三条。上下文决定了 Agent 能看到什么，而 Agent 只能基于它看到的信息做决策。但组件并不等价，衡量的标准是它承载的信息能否从别处重建，「每个组件都不可或缺」这类论断要靠实测，而且模型迭代很快，同一个消融换到新模型上完全可能得出不同的结论。对工程实践更重要的是第三条：「给出了回答」不等于「完成了任务」，上下文残缺时典型的失败是一个看上去毫无破绽的答案，它通常不会报错退出。

五个组件的划分按「谁写的」和「变不变」两条线来记就很清楚。按谁写的：系统提示词是开发者写的，工具定义是开发者声明的，用户消息由用户或 RAG 检索产生，模型回复由模型产生，工具结果由框架执行工具后产生。按变不变：系统提示词加工具定义是静态前缀，对话中保持不变；其余三项是动态消息历史，随交互不断增长。这个「2 + 3」的切分有来处，它是 1.1.5 节 `上下文 = 静态前缀 + 轨迹` 的直接来源，也是第二章 KV Cache 前缀稳定性的基础，改动越靠前，作废的缓存越多，见 1.3 节的「只增不改」模式。

`reasoning`／`content`／`tool_calls` 三者的组合规律很实用，把「要行动」和「要回答」看成互斥的两个出口就够了：要行动就是 `reasoning + tool_calls`，不含 content；要回答就是 `reasoning + content`，不含 tool_calls。所以你在轨迹里看到一条 `content` 非空、`tool_calls` 为空的 assistant 消息，基本可以判定这轮是终点，这也是 1.2.4.2 节把「模型返回没有任何工具调用的响应」列为退出条件之一的原因。

实验 1-1 里最容易被忽略、却最有工程价值的是一句话：上下文残缺时典型的失败是一个看上去毫无破绽的答案。传统软件缺一个依赖会崩、会抛异常、会写日志；Agent 缺了工具定义不会崩，它会照常输出一份排版漂亮的答案，只是数据来自参数记忆。这带来三条推论：不能用「有没有报错」来判断 Agent 是否健康；必须引入独立的验证机制，这正是 1.2 节 Harness 五要素里「验证（Verify）」存在的根本原因；也不能把 Agent 的自信程度当成可靠性指标，原文说得很直白，「与真正基于观测得出的答案排版一模一样」。

表中 ✗ 与 △ 的区别说明后果的等级不同。去掉工具定义是 ✗ 无法调用工具，能力被夺走；去掉工具结果是 ✗ 盲目循环，闭环断裂；去掉思考过程是 △ 决策不连贯，质量下降；去掉历史记录是 △ 重复操作，退化但还能跑。这四组的退化程度由「这条信息能不能从别处重建」决定，信息量本身说明不了全部问题，这正是原文给出的衡量标准。

「思考过程可以从工具结果重建时，丢掉它几乎没有代价」，这句话的道理在于 `reasoning` 是「为什么这么做」，`tool_calls` 加上工具结果是「发生了什么」。如果一条 assistant 消息是「我需要把 EUR 转成 USD，然后求和」，而下一段就是 `convert_currency(...)` 的调用和返回的汇率，那么「为什么」完全可以从「做了什么」推出来。反过来，如果模型的推理里包含没有被工具结果体现的中间判断，比如「我排除了 A 方案因为 X」，丢掉它就会让后续决策失去依据。这给了一个可操作的判断流程（笔记补充）：逐条问「删掉这条 reasoning，后面的 tool_calls 和结果还能不能自解释？」能就压缩，不能就必须留。

消融实验的工程用法也需要说清。原文说「每个组件都不可或缺」这类论断要靠实测，而且换模型结论可能变，意思是消融实验算不上一次性结论，它属于必须随模型版本重跑的评估手段。所以在自己的 Agent 里想省上下文、省 token、省成本时，正确做法是在自己的任务集上重跑一遍消融，照抄本实验的结论去删组件并不稳妥。这与第七章的评估方法论、第九章的更新提案验证是同一套思路。

「基础模式」与「动态 schema」的区别也值得留意。原文说工具定义与系统提示词一起构成对话中保持不变的静态前缀，这是基础模式，后面括号里补了一个例外：2026 年以来，生产框架中工具的完整 schema 也可以按需动态加载到上下文末尾而不破坏前缀。这个补充说明静态前缀算不上铁律，它是性能优化下的默认约定；只要能把新内容追加到末尾，而不是插回前缀，前缀的缓存依然有效。这正好是 1.3 节「只增不改」模式的一个实例。

RAG 在这里的角色同样要定位准。用户消息里「可能包含通过 RAG 动态检索引入的外部知识」，原文点了它的两个用途，覆盖训练数据截止后的信息（时效性）或者私有领域知识（数据边界）。它放在用户消息里而不是系统提示词里，因为它每一轮都可能不同，属于动态部分；这也解释了为什么第三章（用户记忆和知识库）要与第二章（上下文工程）分开讲。

工程上的坑集中在三处。系统提示词里塞太多东西，原文说它还会包含跨会话的用户记忆和动态注入的环境状态，这会让「静态」前缀事实上每轮都在变，直接击中缓存，取舍是第二章的主题。把 `reasoning` 当垃圾丢掉来省 token，有时候可行，但推荐的做法是有条件压缩，别一律丢弃。只靠提示词防幻觉也不行，原文明确说「提示词里『不得自行估计』这类约束只能降低编造的概率，并不能消除」。

余下是几组容易混的词。上下文是内容，也就是那五个部分；上下文窗口是容量，也就是能装多少 token，原文说「Agent 的上下文窗口就是它的『视野』」用的是比喻，别把两者当成同一个概念。系统提示词与用户提示词也不同，前者由开发者编写、整个对话保持不变，是岗位说明书；后者是用户每次的输入，属于动态消息历史。`reasoning`、`content`、`tool_calls` 同属一条 assistant 消息的三个可选部分，`reasoning` 不等于对用户说的话，`content` 才是，`tool_calls` 也不是文本回复，它是行动请求。工具定义与工具执行结果都在「工具」名下，一个是静态前缀里的声明，告诉你有什么能用，一个是动态历史里的返回值，告诉你刚刚发生了什么，实验 1-1 里它们各自的缺失后果完全不同，前者 ✗ 无法调用工具，后者 ✗ 盲目循环。消融实验与对照组实验的方向相反，消融实验是完整系统去掉一个组件，用退化程度反推该组件的贡献，要点在原文那个「逐一排除」的类比，跟加一个组件看有没有变好是两回事。

1.1.4 的落点可以这么记：上下文 = 静态前缀（系统提示词 + 工具定义）+ 动态消息历史（用户消息 + 模型回复 + 工具结果）；消融实验说明组件并不等价，判据是它承载的信息能否从别处重建，而上下文残缺的典型症状是一个看起来毫无破绽的答案。

### 1.1.5 ReAct 循环

了解了 Agent 的三大组件之后，自然的问题是它们如何协同工作。原文的回答是：ReAct 循环就是将 LLM、上下文和工具串联起来的核心机制。

Agent 执行任务的核心模式叫做 ReAct（Reasoning + Acting）。原文特别指出一个名实不符之处：虽然名字只体现了思考（Reasoning）和行动（Acting）两个词，实际循环却包含三个环节，模型先思考当前应该做什么，然后调用工具行动，再观察工具返回的结果并继续思考下一步。这个「想→做→看→想→做→看」的循环不断重复，直到任务完成。

原文用一个多币种收入汇总的具体例子来讲轨迹（trajectory）。轨迹的定义是 Agent 在执行任务过程中不断积累的消息历史，包括用户消息、模型回复（含思考过程和工具调用）以及工具执行结果。每一次调用 LLM 时，它接收的完整上下文由两部分组成（图 1-4）：静态前缀（系统提示词 + 工具定义）和轨迹（动态消息历史）。原文由此给出一个关键事实：

$$\text{Agent 的上下文} = \text{静态前缀} + \text{轨迹}$$

其中静态前缀对应前文五个组件中的前两项，轨迹对应后三项，随交互不断增长。基于这个完整上下文，LLM 生成下一步的响应，然后这个响应又追加到轨迹中，供下一次调用使用。

> 图 1-4（原文插图）：图题是「Agent 轨迹——多币种汇总任务的 ReAct 循环」。图的左侧是一条按轮次展开的消息序列，右侧标注「轨迹 = LLM 每次调用时看到的完整输入」，以及「关键特性：上下文累积（每轮都看到全部历史）、结构化轨迹（`user` / `assistant` / `tool`）」。序列内容按轮次如下：
> - 第 1 轮：`user` 消息「计算年度总收入：Q1 \$2.5M, Q2 €2.1M, Q3 £1.8M」；然后是 `assistant.reasoning`「需要将 EUR 和 GBP 转换为 USD，再汇总计算」；接着是 `assistant.tool_calls`，一次发出两个调用：`convert_currency(2100000, "EUR", "USD")` 与 `convert_currency(1800000, "GBP", "USD")`；末尾是 `tool`（结果）「EUR→USD: 2,282,608.70」和「GBP→USD: 2,278,481.01」。
> - 第 2 轮：`assistant.reasoning`「已获得汇率，调用代码解释器汇总」；`assistant.tool_calls` 为 `code_interpreter("total = 2.5M + 2.28M + 2.28M")`。
> - 第 3 轮：`assistant.content`（最终回答）「年度总收入 \$7,061,089.71，季度均值 \$2,353,696.57」。
>
> 这张图想说明的是：轨迹是一条不断向下追加的消息流水，而每一轮的 assistant 都只看得到它上方已经写下的全部内容。第一轮模型只知道三种货币的金额，第二轮它多看到了两条汇率，第三轮它多看到了汇总结果。图里没有画出系统提示词和工具定义，对应正文那句「轨迹中没有显示系统提示词和工具定义」。

ReAct 循环的最小运行骨架是一段 Python 风格伪代码。原文说明它讲的是机制如何运行：Model 只负责决定下一步，Harness 负责组装上下文、校验并执行工具，Environment 负责产生真实状态变化和观察。原文同时声明，本书后续沿用 Python 风格伪代码，伪代码不能直接运行，也不对应某个 SDK，具体的可执行代码在本书配套代码仓库中。

```python
trajectory = [user_request]
repeat:
    context = stable_prefix + trajectory
    decision = Model(context)
    trajectory.append(decision)
    if decision has no tool call:
        return decision.answer
    for call in decision.tool_calls:
        # independent calls may run in parallel
        validated_call = Harness.validate(call)
        observation = Environment.execute(validated_call)
        trajectory.append(observation)
```

再运行一次之后，轨迹里保存下来的内容长这样。原文强调这是消息数据的结构示意，不是 Agent 循环的实现代码：

```text
轨迹 = [
  {role: "user", content: "根据公司季度收入：Q1 2.5M 美元，Q2 2.1M 欧元，Q3 1.8M 英镑，Q4 380M 日元，计算公司年度总收入和季度平均收入"},

  # 第一次迭代 - LLM 看到上述轨迹，生成响应
  {role: "assistant",
   reasoning: "需要将所有货币转换为USD...",
   content: "",                      # 没有直接回复用户
   tool_calls: [
     {name: "convert_currency", args: {amount: 2100000,   from: "EUR", to: "USD"}},
     {name: "convert_currency", args: {amount: 1800000,   from: "GBP", to: "USD"}},
     {name: "convert_currency", args: {amount: 380000000, from: "JPY", to: "USD"}}
   ]},

  # Agent 框架执行工具，添加结果到轨迹
  {role: "tool", content: "EUR->USD: 2282608.7"},
  {role: "tool", content: "GBP->USD: 2278481.01"},
  {role: "tool", content: "JPY->USD: 2541806.02"},

  # 第二次迭代 - LLM 看到完整轨迹，包括工具结果
  {role: "assistant",
   reasoning: "已获得转换结果，现在需要汇总计算...",
   content: "",
   tool_calls: [
     {name: "code_interpreter", args: {code: "total = 2500000 + 2282608.7 + ..."}}
   ]},
  {role: "tool", content: "Total: $9,602,895.73, Average: $2,400,723.93..."},

  # 第三次迭代 - LLM 看到完整轨迹，生成最终答案
  {role: "assistant",
   reasoning: "所有计算完成，总结结果...",
   content: "FINAL ANSWER: 总收入$9,602,895.73..."}
]
```

原文随后有三条说明。轨迹中没有显示系统提示词和工具定义，它们作为静态前缀，在每次 LLM 调用时都会被自动拼接在轨迹前面。整个过程只用了 3 次迭代、4 次工具调用。在这种最基本的设计中，上下文是不断追加的，每次调用 LLM 都能看到完整的轨迹，因而它清楚任务进行到了哪一步、此前尝试过什么、得到了什么结果。

这种设计带来四条好处。轨迹的结构化让系统易于解释和调试，用户消息、模型回复（思考过程 + 工具调用）和工具执行结果彼此分明。更进一步，分析大量轨迹可以发现 Agent 的行为模式、优化决策路径、改进工具设计。轨迹还可以沉淀进知识库，或者用于强化学习训练更好的模型，形成从经验中学习的闭环。原文说，理解运行循环之后，要用两个实验来感受不同模型如何驱动这个循环。

**实验 1-2 ★：Kimi K3 原生 Agent 能力**（印刷 p.16–17）

这个实验展示了 Kimi K3 的原生 Agent 能力，体现的是「模型即 Agent」的新范式。原文给的模型规格逐条照录如下：约 2.8 万亿参数的混合专家（MoE, Mixture of Experts）模型，原文还给了 MoE 的通俗解释，可以把 MoE 想象成一个专家团队，面对不同类型的问题，系统会自动选择最合适的几位专家来作答，不需要所有专家同时上阵，这样既保证了能力又提高了效率；100 万 token 的上下文窗口；原生的视觉理解能力；始终开启的「思考模式」（thinking mode）；通过强化学习训练，将工具调用的决策策略内化为原生能力，何时调用工具、调用哪个、传什么参数都由模型自主决定，从而能够自主完成网络搜索等任务。

关键观察是模型自己决定何时搜索、搜索什么，这展现了真正的自主性；它能根据搜索结果动态调整策略，自主判断信息是否充足。

这里有一个常见误解需要厘清，关键在于分清两件事的归属。强化学习写进参数的是决策，包括何时该调用工具、调用哪个、传入什么参数、拿到结果后是否继续、如何把几十上百次调用串联成连贯的推理。工具本身及其执行则由 Agent 框架（或 API 内置工具）提供，`web_search`、`code_runner` 的真实实现、代码沙盒环境、调用的发起与结果回传，都在模型之外的基础设施里完成；原文注明 Kimi 通过名为 Formula 的服务端脚本引擎运行这些官方工具。因此，编排循环并没有消失，只是决策权交给了模型；至于循环本身跑在哪里，取决于接入方式。在实验 1-3 的 Responses API 路径中，搜索、代码执行和多轮编排整体在服务端闭环完成；而在实验 1-2 的 Kimi 路径中，Formula 只负责在服务端执行搜索本身，「调用模型 → 追加工具结果 → 再次调用」的 ReAct 循环仍由客户端代码驱动，原文指向 `chapter1/web-search-agent/agent.py` 中的 `while` 循环。

Kimi K3 在 Agent 任务中的一个突出优势是长链工具调用的稳定性，它能够连续执行 200～300 次工具调用而保持思考的一致性，远超多数模型在数十次调用后就开始退化的表现。K3 面向长周期编程与 Agent 工作负载优化，发布时提供两个规格：K3 Max 面向对话与 Agent 任务，K3 Swarm Max 面向大规模并行处理。作为开源模型，它在软件工程和 Agent 基准测试中展现了可与顶尖闭源系统比肩的性能，证明了通过强化学习赋予模型原生 Agent 能力这条路线的有效性。

**实验 1-3 ★：GPT-5.6 原生 Deep Research 能力**（印刷 p.17–18）

这个实验使用 OpenAI GPT-5.6，展示先进模型如何借助 API 内置工具，在服务端形成 Deep Research 的「搜索—阅读—分析」编排闭环。

自由格式工具调用（Freeform Tool Calling）是其中的关键变化。传统方式中，模型调用工具时必须把所有参数打包成严格的 JSON 格式（原文括注，一种结构化的数据格式），这就像填表格一样有很多格式限制。自由格式工具调用在 API 中通过 `type: "custom"` 的工具类型声明，允许模型直接向工具发送原始文本，比如一段 Python 代码、一条 SQL 查询，省去了 JSON 转义的麻烦。原文特意澄清，变的只是 API 参数格式，谈不上模型架构的革新：客户端的工具调用循环（检测 `tool_calls` → 执行 → 回传结果）逻辑保持不变，改变的只是参数从 JSON 字符串变成了原始文本。

GPT-5.6 配合 Responses API 的网络搜索和代码解释器内置工具，这正是 Deep Research 的核心：模型能够自主搜索网络获取实时信息，并编写代码进行深度分析，实现「搜索 -> 阅读 -> 分析 -> 再搜索」的迭代研究过程。原文给了两个具体任务示例。「东盟 10 国首都之间，最近的一对首都距离多少」：GPT-5.6 会自动搜索各国首都的地理坐标，然后编写 Python 代码计算所有首都对之间的大圆距离，最终找出最近的一对。「搜索最近一个月的比特币走势，做技术分析」：它能从多个金融数据源获取实时价格数据，运用专业的技术分析库计算移动平均线、RSI、MACD 等技术指标，生成可视化图表并给出交易建议。

意图澄清过程是这一节的重点判断。原文说，「更重要的是」，GPT-5.6 将 OpenAI Deep Research 产品的设计理念内化到了模型层面，引入了意图澄清过程。当用户提出研究需求后，GPT-5.6 不会立即动手执行，它会先问一系列问题把用户的真实意图澄清清楚。以「搜索最近一个月的比特币走势，做技术分析」为例，它会先问：「你偏好使用哪个数据源？需要分析哪些技术指标？」通过这种交互式的意图澄清，GPT-5.6 能够生成更精准、更符合用户需求的研究报告。

原文的定位判断是：GPT-5.6 属于「模型即 Agent」概念的一个成熟实例。网络搜索、代码解释器作为 Responses API 的内置工具在服务端闭环执行，客户端不必再自行搭建「搜索—阅读—分析」的编排框架。意图澄清的意义在于，它让「用户说了什么」和「用户真正想要什么」之间的差距，在任务执行之前就得到了弥合。可复现性方面，这个实验并不绑定某一家厂商，没有 OpenAI 额度的读者完全可以用具备等价托管工具的提供商复现，例如阿里云百炼 qwen3.7-plus 的 Responses API 同样内置 `web_search` 与 `code_interpreter`，Kimi K3 的 Formula 托管搜索与 `code_runner` 也属于同类能力。

图 1-5 展示了「模型即 Agent」范式下原生工具调用的完整架构，以及 Kimi K3 / GPT-5.6 在实际任务中的 ReAct 执行过程。原文特别提醒，图中「客户端无需手写 ReAct 循环」只对 Responses API 路径成立，两条路径都由模型决定何时调用哪个工具、工具都在服务端执行，区别在于 Kimi 路径的循环仍由客户端驱动。

ReAct 名字里为什么少了「观察」，这是本节最容易被问到的点。原文明确说名字只体现了思考（Reasoning）和行动（Acting）两个词，实际循环包含三个环节。原因在于 Observing 由环境返回，算不上一个「模型动作」，它是工具执行完自动追加进轨迹的数据，不需要模型去「做」。所以 ReAct 这个词是从模型视角命名的：模型只做「想」和「做」两件事，「看」是被动的。理解这一点很关键，否则容易以为模型要主动发起一次「观察」。

走一遍数据流是理解本节的唯一正确方式，这里按笔记补充的逐步说明来走。Harness 取 `stable_prefix + trajectory` 拼成 `context`，前缀不动，轨迹变长；调用 `Model(context)`，拿到 `decision`，其中可能含 `reasoning`、`content`、`tool_calls`；无条件把 `decision` 追加进 `trajectory`，注意这一步在「判断有没有工具调用」之前，所以即使这轮就是最终回答，它也会留在轨迹里；如果没有工具调用，直接 `return decision.answer`，这就是循环的出口之一；如果有工具调用，对每一个 call 依次执行 `Harness.validate(call)` 校验，再由 `Environment.execute(...)` 执行，把返回的 `observation` 追加进 `trajectory`；然后回到第一步。伪代码里那句注释 `# independent calls may run in parallel` 讲的是一轮里多个互相不依赖的调用可以并行执行，第 1 轮里两个 `convert_currency` 就是这种情况，而第 2 轮的汇总必须等汇率回来，不能和第 1 轮并行。

伪代码里最关键的一行是 `validated_call = Harness.validate(call)`。它只有一行，但它是「模型想干什么」和「环境真的被改成什么样」之间的唯一闸门。这行代码就是 1.2 节 Harness 五要素里「约束（Constrain）」和「验证（Verify）」的最小形态。读到这里应该形成条件反射：凡是 `Model(...)` 的输出要流向 `Environment` 的地方，都必须经过校验。

原文给的数字也值得动手验一遍，这里补上笔记自己算的核对过程。图 1-4 的三轮版本里，$2{,}500{,}000 + 2{,}282{,}608.70 + 2{,}278{,}481.01 = 7{,}061{,}089.71$，与图中「年度总收入 \$7,061,089.71」一致；季度均值 $7{,}061{,}089.71 \div 3 = 2{,}353{,}696.57$，与图中「季度均值 \$2{,}353{,}696.57」一致，除以 3 是因为本例只有 Q1–Q3 三个季度。轨迹结构示例的四轮版本里，$2{,}500{,}000 + 2{,}282{,}608.7 + 2{,}278{,}481.01 + 2{,}541{,}806.02 = 9{,}602{,}895.73$，与「Total: \$9,602,895.73」一致；$9{,}602{,}895.73 \div 4 = 2{,}400{,}723.9325$，与「Average: \$2,400,723.93」一致（四舍五入到分）。两次示例的迭代次数与工具调用数要分开算。图 1-4 的三轮版本里出现的是 2 次 `convert_currency`（EUR、GBP）加 1 次 `code_interpreter`，共 3 次工具调用、3 轮迭代。轨迹结构示例的四轮版本多了一笔 Q4 380M 日元，里面出现的是 3 次 `convert_currency`（EUR、GBP、JPY）加 1 次 `code_interpreter`，共 4 次工具调用、3 轮迭代，这正是正文紧随其后那句「整个过程只用了 3 次迭代、4 次工具调用」所指的对象。注意「迭代次数」不是「工具调用次数」：第 1 轮里并发发出的多个调用只算一轮迭代。

「轨迹」这个概念值得单独命名，因为它把三件通常被混着说的事情分开了。轨迹是数据结构，也就是消息历史，含 `user`／`assistant`／`tool` 三种角色；ReAct 循环是控制流，管谁在什么时候调用谁；上下文是每次推理的输入，等于静态前缀加轨迹。三者的关系是：循环每转一圈，就往轨迹尾部追加消息，下一圈重新拼出上下文。把这层分清以后，第二章讲上下文管理、第七章讲轨迹评估、第九章讲「从已评价的运行轨迹中生成更新」（原文 1.1.3.2 提到的），都能定位它们在动哪一部分。

「分析大量轨迹」的产品价值也落在具体位置上。原文列了三条，发现 Agent 的行为模式、优化决策路径、改进工具设计，它们对应三种不同的问题：行为模式通向评估与监控（第七章），决策路径通向提示与上下文优化（第二章），工具设计通向接口改进（第四章）。也就是说，轨迹是 Agent 系统的「日志 + 数据资产」。原文还说轨迹能「沉淀进知识库」或者「用于强化学习训练更好的模型」，这正好对应 1.1.3.2 三条更新路径里的后两条，也就是外部产物与参数更新，闭环由此合上。

实验 1-2 真正的考点是分清「决策」与「执行」，原文在这里花了一大段去厘清那个误解，还把它做成了一条脚注（感谢读者 asdlem 通过 Issue #30 指出），值得背下来。RL 内化的是何时调用、调用哪个、传什么参数、拿到结果后是否继续、如何把几十上百次调用串联成连贯的推理，这些都是决策，写进了参数。框架提供的是 `web_search`、`code_runner` 的真实实现、代码沙盒、调用的发起与结果回传，这些是执行，留在模型之外。所以「模型即 Agent」不等于「框架消失了」，原文的措辞是「编排循环并没有消失，只是决策权交给了模型」。更进一步，循环跑在哪里是接入方式的问题，谈不上范式的问题：Responses API 路径整个循环在服务端闭环，Kimi 路径里 Formula 只做服务端搜索，「调用模型 → 追加工具结果 → 再次调用」仍由客户端 `while` 循环驱动。两条路径的模型自主性一样，工程形态不一样。

实验 1-3 真正的考点是意图澄清属于省钱的机制，它带来的不只是礼貌。做 Deep Research 最贵的失败是跑完一趟才发现方向错了，所有搜索、阅读、分析的算力全打水漂。意图澄清把这部分损失提前了，在任务执行之前就弥合「用户说了什么」与「用户真正想要什么」的差距（原文原话）。这也解释了它为什么放在模型层面而不是产品层面：作为模型的原生行为，任何接了 Responses API 的调用者都自动获得这个能力，不用自己写一轮问答。这正好是产品设计理念被内化进模型的又一个实例，跟 1.2.4.1 节末尾「每一轮内化，消灭的都是『翻译』和『脚手架』」的判断是一条线。

自由格式工具调用到底改了什么、没改什么，也要说准。改的是参数的载体，从 JSON 字符串变成原始文本；没改的是循环的形状，依然是检测 `tool_calls`、执行、回传结果。原文明确说这是 API 参数格式的演进，谈不上模型架构的革新，就是防止读者把它误读成一次模型能力的跃迁。它的实际收益很具体：写 Python 代码或 SQL 时不用再把整段代码做 JSON 转义，摩擦小了，出错点也少了。

工程上的坑有三个。退出条件必须显式设计，伪代码里的 `return decision.answer` 只覆盖「模型不再调用工具」这一种情况，真实系统还要覆盖「达到最大轮次」「错误次数超限」等，否则一旦模型陷入盲目循环（实验 1-1 里「无工具结果」那组的症状）就会一直烧 token，完整清单见 1.2.4.2 与图 1-6。轨迹无限增长也有代价，原文说「上下文是不断追加的」，这在 3 轮的小任务里没问题，但长程 Agent 会撞上上下文窗口和成本上限；原文在图 1-4 里标出的「关键特性：上下文累积」既是优点也是约束，第二章的上下文压缩、多层压缩（Claude Code 的 Harness 里就有这一项）就是在处理它。并行调用的前提是互相不依赖，并行发多个工具调用能省时间，一旦其中有依赖，比如第二次调用需要第一次的返回值，就必须串行，判断依据是参数里有没有引用其他调用的结果。

也有用不上的场合。只执行单步简单任务、或者在 Computer Use 中仅需点击固定位置（见 1.2.3 节）时，不需要带思考的模型；同理，一个不需要观察结果的任务也不需要完整的 ReAct 循环，一次调用就够。原书在 1.2.4 节把这条上升为编排原则，先从单个 LLM 调用考虑起。

末尾几组容易混的说法收在一起。ReAct 的「三环节」与名字的「两个词」之间的差别，是因为名字里没有 Observing，而循环实际有「思考 → 行动 → 观察」，观察由环境返回，谈不上模型主动发起的动作。轨迹（trajectory）与会话历史（conversation history）在本章语境里可以视为同义，都是不断累积的消息历史，含工具调用与工具结果；关键是它不含静态前缀，前缀是每次调用时临时拼上去的。`Tool Calling` 与 `Function Calling` 也是同一个词，原文在 1.1.2 就明确本书后续统一使用「工具调用」。模型决定调用与框架执行调用要分清，前者是 RL 内化的决策，后者是模型之外的基础设施，实验 1-2 用整段篇幅澄清的就是这一对。循环在服务端还是客户端，两条路径（Responses API 与 Kimi）的模型自主性相同，区别只在 ReAct 循环由谁驱动，别把「循环在服务端」当成「模型更强」的标志。自由格式工具调用与结构化输出方向不同，前者是把参数从 JSON 变成原始文本，后者通常是让模型输出符合 schema 的 JSON。

1.1.5 的落点也一样：ReAct 就是「想 → 做 → 看」，循环往复直到出口；每次调用的输入是 `静态前缀 + 轨迹`，而「模型即 Agent」改的是决策权，把它交给模型，不改执行与循环的归属，它们仍在 Harness 里。

# 1.2 Harness 工程：模型之外的竞争力

到这里，Agent 的核心工作原理已经讲完：LLM 通过 ReAct 循环，在上下文的辅助下使用工具完成任务。前面那些实验既证明了这套机制有效，也把它的脆弱点摆到了台面上。模型可能产生幻觉，编造出不存在的工具或参数；可能选错工具；遇到错误时还不一定能自我恢复。原文在这里的判断是，一个能跑的 Demo 和一个可靠的产品之间还有巨大的鸿沟，而这些脆弱点正是 Harness 工程要解决的问题。本章的结构也因此一分为二：前半部分回答 Agent 是什么，下半部分回答 Agent 如何在生产环境中可靠运行。

换个视角看前面建立的 `Agent = LLM + 上下文 + 工具`。从 Harness 工程的角度，LLM 可以被抽象成核心组件 Model，而 Agent 边界内那些负责支撑模型运行、负责模型与环境交互的代码、配置和服务，统称 Harness。两个视角并不互相取代，它们是不同抽象层次上对同一份 Agent 实现的描述。

生产形态下的完整组成，原文用三个独立公式给出：

$$\text{Agent} = \text{Model} + \text{Harness}$$

$$\text{Harness} = \text{上下文管理} + \text{工具接口} + \text{约束} + \text{验证} + \text{纠正}$$

$$\text{Agent} \leftrightarrow \text{Environment}$$

$\text{Model}$ 是承担策略决策的模型本体，对应 LLM；$\text{Harness}$ 是 Agent 边界内、模型之外的运行与治理层；$\text{Agent} \leftrightarrow \text{Environment}$ 用双向箭头表示二者是闭环交互的两方，而不是包含关系，边界沿用图 1-1。第一式说的是生产形态的 Agent 就是 Model 加上外围那一层。第二式把 Harness 展开为五项职责，前两项让它「能做事」，后三项让它「不做错事」。把第二式代回第一式，得到

$$\text{Agent} = \text{Model} + \text{上下文管理} + \text{工具接口} + \text{约束} + \text{验证} + \text{纠正}$$

这正好是 1.1 节「LLM 对应 Model，'上下文 + 工具'构成最小 Harness」的展开。所以考试里被问「哪套公式对」，答案是都对，差别只在校验的抽象层次：`Agent = LLM + 上下文 + 工具` 是全书唯一的结构骨架，`Agent = Model + Harness` 是同一事物在生产形态下的展开，一条骨架、两个层次。

最小 Demo 和生产系统的差别也落在第二式里。Demo 只需要 Model 和能构造上下文、暴露工具的 Harness；生产系统还要在同一边界内加入约束、验证和纠正。原文举的退款 Agent 一句话把五项串完：把政策放进上下文，用权限和金额规则约束调用，用数据库状态验证结果，超时则重试或回退。任何一个业务场景都能按这五格拆开，看它缺了哪一格。

Harness 工程的研究对象，就是模型之外、Agent 边界之内的运行与治理代码。原文用「更精确地说」划清过一次边界：Harness 不是模型之外的一切，它负责协调 Model 与 Environment 的交互，但不包括与之交互的环境本身。工具定义、调用适配器、沙箱的权限与重置机制属于 Harness；沙箱内随行动变化的文件和进程、外部数据库、网页、用户及物理世界属于 Environment。还有一条判据值得单独拎出来：物理部署位置不能决定概念归属，即使仿真环境与 Agent 运行在同一进程中，它仍然是 Environment。这条判据看的是角色，不是进程。

| Context（上下文） | 为模型提供感知信息；信息要充分，让 Agent 在每个决策点都基于足够的信息判断 | 系统提示词、知识库、Agent 状态栏、Sidecar 旁路查询 | 第二、三章 |
| Tools（工具接口） | 为模型提供观察与行动手段；接口要清晰，命名直观、参数有例子、边界有说明 | MCP 工具、代码解释器、搜索工具 | 第四章 |
| Constrain（约束） | 设定行为边界；采用故障安全默认值，所有能力默认关闭，必须显式开放（类似手机 App 权限管理） | Claude Code 中每个工具默认需要用户授权才能执行 | 第四章 |
| Verify（验证） | 自动判断操作结果的对错；安全检查只看结构化数据（如工具返回的 JSON 字段），而不看模型自由生成的文本，因为后者可能已被提示注入操纵 | Linter 检查、类型系统、工具调用结果校验 | 第五、六章 |
| Correct（纠正） | 发现问题时自动修正或回退；在确认无法恢复之前不暴露中间态，例如工具调用失败时先静默重试，不把半成品结果展示给用户 | 静默重试、接续生成、连续失败时回退到人工判断（熔断机制） | 第二、五章 |

模型控制循环的基本流程，原文给了一段刻意不展开具体实现的伪代码：

```python
observation = Environment.observe()
trajectory = [observation]
while true:
    actions = Model(Harness.build_context(trajectory))
    if len(actions) == 0:
        break
    allowed_actions = Harness.constrain(actions)
    observation = Environment.apply(allowed_actions)
    if not Harness.verify(Environment):
        observation = Harness.correct(Environment)
    trajectory.append(allowed_actions, observation)
```

完整的 API 消息循环放在第二章，工具与自动验证分别在第四、五章展开。就这段骨架本身，值得逐行走一遍，对照 1.1.5 的 ReAct 伪代码看：循环开始之前先取一次观察，`trajectory = [observation]` 完成轨迹初始化；`actions = Model(Harness.build_context(trajectory))` 把「构造上下文」包进了取动作这一步，这个 `build_context` 就是 1.1.5 里的 `stable_prefix + trajectory`；`if len(actions) == 0: break` 是退出条件，模型没给出任何动作就结束；`Harness.constrain(actions)` 落在「模型想做的」和「实际允许做的」之间；`Environment.apply(allowed_actions)` 说明只有被允许的动作才真正生效，这是安全边界的物理位置；`if not Harness.verify(Environment)` 里 `verify` 的参数是 `Environment`，验证的是世界的状态，不是模型的文本，和表格里「安全检查只看结构化数据」是同一条原则；最后一步追加的是实际执行的动作，不是模型最初提议的动作。相比 1.1.5 的最小骨架，这里多出 `build_context`、`constrain`、`verify`、`correct` 四个 Harness 调用。最小 Demo 和生产系统在代码层面的全部差别，就在这四个调用上。

五个功能构成的是闭环，不是清单。上下文与工具让 Agent 能理解任务并采取行动，约束预防错误，验证发现偏差，纠正使闭环得以形成，三者共同让它不做错事。它们就长在上下文和工具旁边，是确保这两项在生产环境中可靠运转的工程实践；缺任何一个环节，系统都会出现可靠性缺口。

闭环这个说法有实指。`Harness.correct(Environment)` 会产生一个新的 `observation`，它和 `allowed_actions` 一起被追加进轨迹，下一轮模型看得到「刚才失败了、系统做了什么补救」，这才有机会换一个策略，而不是原地重试。原文对纠正那一项的说明也点了这层：「在确认无法恢复之前不暴露中间态，例如工具调用失败时先静默重试，不把半成品结果展示给用户。」

两类功能的重要性是不对称的。原文的说法是，在 Agent 产品的成熟度曲线上，两类功能的重要性不对称。早期的 Agent 框架主要关注上下文与工具，给模型工具、给模型上下文，让它「能做事」；生产级 Agent 系统的重心已经转向约束、验证与纠正，确保工具调用是安全的、上下文是经过管理的、错误是可纠正的。这对做产品的人是一个明确的资源分配信号：不要把「接了多少工具」当成竞争力指标。

Claude Code 是原文给的硬证据。它的 Harness 中绝大部分代码都是约束、验证与纠正，工具本身（文件读写、命令执行、搜索）只占一小部分，围绕这些工具构建的保障机制才是真正的核心。原文列举的机制包括流程状态管理，用来追踪 Agent 当前执行到哪一步；多层上下文压缩，信息太多时自动精简；权限分类，控制哪些操作需要用户确认；熔断器（Circuit Breaker），错误连续发生时自动断电停止重试，原文的类比是家里电路短路时保险丝跳闸，防止整个系统崩溃；还有错误恢复机制，捕获异常、回滚到上一稳定状态、重试或交还给人类。这一节的结论也就顺下来了：行业正在从「能做事」向「可靠地做事」转变，Harness 工程因此成为 Agent 系统的核心竞争力。

有三处边界最容易记岔。Model 和 LLM 在公式里换了名字，指的是同一个东西，即策略决策的内核，只是抽象层次不同。Harness 也不等于「所有非模型代码」，它有两条判据：在不在 Agent 边界内，是「运行与治理」还是「被治理的对象」。沙箱的权限与重置机制是 Harness，沙箱里跑起来的、随行动变化的文件和进程是 Environment，前者是规则，后者是被规则作用的状态。物理部署位置同样不能决定概念归属，仿真环境哪怕和 Agent 同进程、共享内存，只要它是「Agent 作用的对象加返回观察的来源」，它就是 Environment。等你决定「这段逻辑该写成工具还是该留在环境里」时，问的是它的角色，不是它跑在哪台机器上。

另外几对也顺手分清。Constrain 是事前，在动作生效之前限制集合，也就是 `allowed_actions`；Verify 是事后，对结果和状态做检查。Verify 是判断，`if not Harness.verify(...)`；Correct 是处置，`Harness.correct(...)`，原文的对应表述是「验证发现偏差，纠正使闭环得以形成」。最小 Demo 与生产系统的差别不在功能多少，而在有没有约束、验证、纠正这三层保障。

## 1.2.1 从提示工程到Loop 工程：工程范式的演进

原文回顾 AI 应用工程的发展，画出了一条清晰的演进弧线。第一波是提示工程（Prompt Engineering），通过优化输入给模型的自然语言指令来提升输出质量。第二波是上下文工程（Context Engineering），人们发现单纯优化提示词还不够，需要系统性地管理模型能看到的所有信息：系统指令、工具定义、对话历史、外部知识。第三波是 Harness 工程，视野从「模型能看到什么」扩展到「Agent 如何组织模型运行并与环境交互」，涵盖上下文与工具接口、约束机制、验证手段、反馈循环和错误恢复这些 Agent 边界内、模型之外的运行与治理机制。随后出现的是 Loop 工程（Loop Engineering），再度把视野从单次运行扩展到跨轮次的持续自主运转：谁来发现下一件该做的事、何时验证、何时才算真正完成，这一层会在第十章结合多 Agent 协作系统展开。第五个名称是 Graph 工程（Graph Engineering），2026 年 7 月业界开始用它描述一种更高层的编排视角，把 Agent 循环、确定性程序和人工审批组织成显式的执行图，其中节点承担具体能力，边规定路由与依赖，结构化状态沿边传递并在关键边界处持久化。

这五个阶段层层包含，后一个把前一个收进自己的范围，彼此之间谈不上替代。提示工程是上下文工程的子集，上下文工程是 Harness 工程的子集，Harness 工程是 Loop 工程的子集，Loop 工程又是 Graph 工程的子集，单个 Agent 循环正是执行图中的一个节点。每一层都在前一层的基础上扩展了工程师的关注范围和影响力。原文的核心判断是：当各家模型的能力越来越接近、不再是决定性的差异因素时，竞争优势就转移到了模型之外的工程实践。

一个有力的实证来自 LangChain 在 Terminal Bench 2.0 上的实践，原文括注这个基准评估的是 Agent 在终端环境中完成复杂任务的能力。它的得分从 52.8% 提升到 66.5%，排行榜名次从 30 名开外跃升至前 5，而改变的不是模型，是 Harness。具体动作包括让 Agent 自动检查自己的执行结果、检测是否陷入重复循环、优化思考策略这类工程手段。

> 脚注 3（印刷 p.20）：Josh C. Simmons 在 2026 年 7 月 4 日的文章 *We Are Entering the Graph Engineering Phase* 中较早明确使用这一名称，并将其概括为**节点、类型化边和可检查点状态**；7 月 18 日，Peter Steinberger 关于「是否已从 loops 转向 graphs」的讨论进一步推动了该名称传播。需要注意的是，**相关实践早于这个名称**：LangGraph、Microsoft Agent Framework 和 Google ADK 的官方文档分别称其为图编排或 graph-based workflow。参见 <https://www.drjoshcsimmons.com/writing/we-are-entering-the-graph-engineering-phase>、<https://x.com/steipete/status/2078277297791189132>、<https://docs.langchain.com/oss/python/langgraph/overview>、<https://learn.microsoft.com/en-us/agent-framework/workflows/>、<https://adk.dev/workflows/>。

这条链最好理解为「每一层把视野扩大了一圈」。提示工程问「话怎么说」，上下文工程问「给它看什么」，Harness 工程问「它怎么跑才可靠」，Loop 工程问「它怎么一直跑下去、何时算完」，Graph 工程问「多个循环和人在图上怎么摆」。落到具体对象上：提示工程盯的是指令文本；上下文工程扩到模型能看到的所有信息；Harness 工程扩到模型怎么跑、怎么和环境交互；Loop 工程扩到跨轮次的持续运转；Graph 工程扩到多个循环加确定性程序加人工审批的组织形态。

「子集」是原文的精确用词，值得多停一步。系统指令本来就是上下文的一部分，所以提示工程 ⊂ 上下文工程；上下文管理是 Harness 五要素之首，所以上下文工程 ⊂ Harness 工程；一次运行是跨轮次运转里的一个片段，所以 Harness 工程 ⊂ Loop 工程；单个 Agent 循环只是执行图中的一个节点，所以 Loop 工程 ⊂ Graph 工程。这意味着后面这些范式出现时，前面的并没有作废。你在做 Graph 工程时，照样要写提示词、管上下文、搭 Harness。

「竞争优势转移到模型之外」这个判断有前提。原文的落点是「当各家模型的能力越来越接近」，也就是说模型能力趋同才成立；如果某家模型领先一代，模型仍然可以是决定性因素。工程含义是：在模型同质化的赛道上，投 Harness 的边际收益高于投模型选型。

LangChain 那组数字之所以有说服力，在于它接近一次控制变量实验。模型没换，只改了 Harness，指标从 52.8% 到 66.5%，也就是 +13.7 个百分点，排名从 30 名开外到前 5。它改的三件事正好各落在一个 Harness 职责上：「自动检查自己的执行结果」对应 Verify；「检测是否陷入重复循环」对应 Correct 的熔断，治的正是实验 1-1 里「无工具结果导致盲目循环」那个症状；「优化思考策略」对应 Context，也就是 thinking 的组织方式。这个案例的读法是：同一模型下，Harness 决定了 13.7 个百分点的差距。

> 🔎 检索确认：这条结论的算术依据来自原书正文本身给出的两个数——$66.5\% - 52.8\% = 13.7$ 个百分点（同一案例、模型不变、只改 Harness）；公开讨论中也以「13.7pt、同一模型、52 → 66」概括 LangChain 这次改进，与本笔记的复算方向一致。可追溯的官方出处是 LangChain 的 *Improving Deep Agents with harness engineering*（来源：[LangChain 官方博客](https://www.langchain.com/blog/improving-deep-agents-with-harness-engineering)）。另有第三方博客以该数字为题讨论，本笔记未能独立核实其数据来源，故不列为依据。

「名称早于实践」这层意思，脚注说得很直白：LangGraph、Microsoft Agent Framework、Google ADK 早就把它叫「图编排」或 graph-based workflow。所以 2026 年看到「Graph 工程」这个新词，可以理解成给已有实践起了个统一的名字，而不是一种全新技术的诞生。脚注里还给了这个名称的三要素概括：节点、类型化边、可检查点状态。

这条演进弧线可以直接当技术选型的自检表用。做一个 Agent 项目时按顺序问：提示词调过了吗？上下文组织过了吗？约束、验证、纠正这三样有吗？需要跨轮次持续运转吗？需要把多个循环和人工审批编成图吗？顺序不能跳，层层包含的关系意味着跳到后面反而会返工。反过来也要注意，原文说的是演进弧线和层层包含，并不要求每个项目都走到最右边。1.2.4 节马上会讲「保持简单」「从简单到复杂」。Graph 工程解决的是多个 Agent、循环、确定性程序加人工审批的组织问题；任务一个循环就搞定的时候，引入显式执行图只会多一层抽象。

链的前后关系容易串错的地方在这里收一下。提示工程只动指令文本，上下文工程动模型能看到的所有信息，前者是后者的子集。上下文工程管「模型能看到什么」，Harness 工程还管「Agent 如何组织模型运行并与环境交互」，也就是约束、验证、反馈循环和错误恢复，前者又是后者的子集。Harness 工程针对单次运行，Loop 工程针对跨轮次的持续自主运转，问的是谁发现下一件事、何时验证、何时算完成。Loop 与 Graph 的差别，在于后者把 Agent 循环、确定性程序和人工审批组织成显式执行图，单个 Agent 循环只是图中的一个节点。至于「五波」这个说法，它不是「五代」，说第五波不意味着前四波过时，层层包含才是要点。

### 1.2.2 构建有效Agent 的核心原则

这一节的来源是 Anthropic 的经验（脚注 4：Anthropic. “Building effective agents”, 2024 年 12 月. <https://www.anthropic.com/engineering/building-effective-agents>），原文说成功的 Agent 系统遵循三个核心原则。

原则一，保持简单。从最简单的方案开始，只在确实必要时才增加复杂度。原文给的两条判据很直接：直接的 API 调用优于复杂的框架，清晰的代码优于聪明的抽象。理由在于，每多一层抽象都会成为以后调试时新的盲区。

这条原则对抗的是一个很具体的失败模式，过度抽象。原文的落点在调试，也就是可观测性，跟性能、代码量都无关。它和第三条「保持透明」是一对：抽象层让你看不见，看不见就没法定位错误。「直接的 API 调用优于复杂的框架」这个说法相当激进，方向却很明确，框架的价值必须大于它带来的盲区。

原则二，保持透明。明确显示 Agent 的规划步骤、执行日志和决策轨迹。原文强调这不只是为了调试方便，也是让用户建立信任的前提，因为黑箱里的错误一旦发生，外部观察者既无法定位也无法纠正。这三样正是 1.1.5 节里 ReAct 循环天然产出的东西，轨迹的结构化（`user`/`assistant`/`tool` 彼此分明）本身就构成透明性。所以透明并不要求额外做一个 UI 面板，要做的只是别把已经有的信息藏起来。

原则三，设计好工具接口（ACI，Agent-Computer Interface）。原文的定义是，ACI 强调从 Agent 视角设计接口，让 Agent 容易理解和使用，传统 API 则是从程序员视角设计。工具的命名和参数要直观，容易误用的地方要从设计上让错误无法发生。原文给的两个类比很传神：SIM 卡的缺角让卡片只能从一个方向插进卡槽，避免了插反；微波炉门没关好就绝不加热，避免了开门加热的危险行为。这种用设计消除错误的思路在制造业里有专门的术语，叫防呆（Poka-yoke），源自丰田生产体系。理由也很硬：设计不好的工具会让再强的模型也频繁出错，因为模型与工具之间唯一的沟通通道就是接口本身，模糊的接口会被模型放大成系统性的错误。

ACI 与 API 的差别在这里要单独说一句。API 的读者是程序员，程序员会读文档、会看类型定义，也能容忍不直观的命名，因为他能查。ACI 的读者是模型，模型只看到工具的名称、描述和参数 schema，它没有「我觉得这个名字有点怪，去查下文档」这种能力。所以 ACI 的设计目标落在「不容易被误解」上，功能完备并不是它的追求。

「让错误无法发生」和「让错误被检测到」是两种设计哲学，本节讲的是前者。防呆让错误在物理上不可能发生，不需要检测、不需要报错、也不需要用户理解；验证（Verify）承认错误可能发生，但会被检测到并被处理。两者的关系可以记成一句：能用设计消除的错误，就不要留给验证去处理。设计消除的成本是一次性的，验证的成本每次运行都要付，还可能漏检。这也解释了前面那句「设计不好的工具会让再强的模型也频繁出错」，把可靠性寄托在模型「小心一点」上是不成立的，模型没有这种可靠性。

落到工程上，设计 ACI 时可以直接检查这几件事（这几条是我按原文的两个类比和 Tools 一栏的标准补出来的具体做法）：能不能让参数只能取合法值，用枚举、格式约束、明确必填与选填，对应 SIM 卡缺角那个思路；能不能让危险操作默认不发生，默认只读、删除需二次确认、先预览不直接执行，对应微波炉门锁；名字能不能自解释，`delete_file` 优于 `df`，`search_web` 优于 `query`；描述里有没有给出「什么时候用、什么时候不用」，表格里 Tools 一栏写的「命名直观、参数有例子、边界有说明」正是这三点；出错时返回的是不是结构化信息，因为 1.2 节的 Verify 原则要求安全检查只看结构化数据，工具返回结构化字段就是在给验证留接口。

这里能看出「每多一层抽象都会成为以后调试时新的盲区」和「保持透明」讲的是同一件事：抽象层数越多，需要透传的信息越少，定位错误的难度越高。三条原则合起来就是，能用最简单的结构把话说清楚，就别把它藏进框架里。

三条原则和 Harness 五要素也能对上（这个映射是我补的，用来把前后两节串起来）：保持简单影响的是你「怎么实现」Harness，别为了五要素齐全去造框架；保持透明对应的就是 Context，把规划步骤、执行日志、决策轨迹放进可观测的地方；设计好 ACI 对应的就是 Tools，那是工具接口的质量标准。原文在本节末尾交代了后续三节的关系：模型选型、编排模式、护栏与安全性这三个主题都不属于 Harness 五要素本身，却都是工程实践中绕不开的决策。所以 1.2.2 讲的是原则，1.2.3 到 1.2.5 讲的是决策，1.2.6 再回到五要素的框架。

有几对容易混。API 与 ACI 的判据是，模型能不能只凭名称、描述、参数 schema 就正确使用它。防呆与验证的差别在设计层面和运行层面，优先用前者。保持简单与「五要素都要有」并不矛盾，五要素是职责清单，也就是该考虑哪些方面，它不是实现清单，简单实现同样可以覆盖五项职责。还有一处看着冲突其实不冲突：本节要求暴露规划步骤、执行日志和决策轨迹这些可审计的行为，1.3 节「提议者—审核者」里又要求评判方只认产物、不认推理过程，前者是给人看，后者是给验证机制用。

### 1.2.3 如何选择模型

这一节回答一个实操问题：在讨论编排模式之前，应该选什么样的模型来驱动 Agent。原文的定位声明是，模型是 Agent 的智能基座，选对模型往往比优化提示词更有效；但模型迭代极快，所以本节不推荐具体版本，只给选型思路。

目前 Agent 开发中最常用的两大闭源模型厂商是 OpenAI（GPT/o 系列）和 Anthropic（Claude 系列）。闭源模型通常在能力上领先，代价是成本较高，并且受限于厂商的 API 策略。原文的一条操作建议是，选模型时不要只看排行榜，要在你自己的任务上做评估，评估方法在第七章。

开源模型的处境是另一个样子。原书编写时，开源模型与闭源模型之间的差距在 6 个月以内，成本却显著低于闭源模型。如果业务场景对模型能力没有很高要求，开源模型是务实的选择。它的优势集中在三处：成本低、可私有化部署、支持微调定制，适合对成本敏感或有数据合规要求的场景。国内 Agent 能力较强的模型，原文点了 DeepSeek、Kimi、GLM。这里有一句警告要带上：不同模型在工具调用方面的能力差异很大，选型前务必在具体场景中测试。

能力之外还有一层，模型的策略边界。模型在基准测试中具备某种能力，并不意味着承载它的产品一定允许用户调用这种能力。不同厂商会对网络安全、模型蒸馏、模型提取、隐私数据和高风险操作设置不同的策略边界，同一个任务在聊天产品、Coding Agent 和 API 中也可能得到不同结果。所以选型不能只比较准确率、价格和速度，还要在自己的真实任务上测三件事：模型是否愿意执行，接口是否暴露所需能力，服务条款是否允许这种使用方式。业务关键任务还应提前准备人工接管或其他合规模型作为替代路径。

是否需要「思考（Reasoning）」这一项，绝大多数 Agent 的答案是要。Agent 需要进行多步思考、工具选择这类复杂决策，不带思考能力的模型在这些任务上表现往往很差。只有极少数场景例外，原文举了两类：只执行单步简单任务，或者在 Computer Use 中仅需点击固定位置的简单 GUI 操作。一旦涉及多步思考或动态决策，就必须选择支持思考的模型。

除了成本，还有两个容易被忽视的维度。一是输出 token 的速度。Agent 往往需要多轮推理，每轮都要等模型输出完成才能执行下一步，所以输出速度直接决定端到端响应延迟。原文的算例是，如果一个 Agent 任务需要 20 轮推理，每轮慢 2 秒，总共就多等 40 秒。二是多模态支持。如果 Agent 需要理解图片、音频或视频，多模态能力就是硬性要求，而不同模型在这方面的差异很大。

这一节的五点可以整理成一张五问清单（这个组织方式是我对原文五点的重新排列，内容没有出原文）。闭源还是开源，先在能力与成本、合规之间做取舍；能不能用，指的是策略边界，愿不愿意执行、接口暴不暴露、条款允不允许；要不要思考，绝大多数要，极少数不要；快不快，看输出 token 速度怎么折算成端到端延迟；看得见什么模态，图片、音频、视频属于硬性要求时就只剩少数选项。原文只列思路而不推荐版本，原因写在开头那句「模型迭代极快」上，也正因为如此，这份清单不依赖具体型号，过一两年还能用。

「不要只看排行榜」背后有具体机制。排行榜和各家的基准测试测的是通用任务上的平均能力，而你的 Agent 会撞上的是你的任务上的具体短板：工具调用格式对不对，长链调用会不会退化（实验 1-2 提到 K3 能连续 200 到 300 次调用，而多数模型在数十次调用后就开始退化），你的领域术语它认不认识。原文因此把话说成「要在你自己的任务上做评估」，这与第七章的评估方法论是配套的。

策略边界这一条是典型的工程经验，值得展开。它说的是模型能力不等于产品可用性，卡住你的地方有三个层次。厂商政策层对网络安全、模型蒸馏、模型提取、隐私数据、高风险操作设了不同的红线；产品形态层上，聊天产品、Coding Agent、API 三者的行为可能不同；合同层看服务条款是否允许你这样用。任何一层卡住，你选的「最强的模型」就用不了。原文给的对策很务实，提前准备人工接管或其他合规模型作为替代路径，这其实是 1.2.5 节「人工干预」和「护栏」在选型阶段的预演。

「20 轮 × 2 秒 = 40 秒」这个算例值得记住，因为它把输出速度从模糊的体感指标变成了可估算的公式：端到端延迟 ≈ 轮数 × 每轮输出时间 + 工具执行时间。顺着这个式子能推出几个反直觉的结论（这几条推论是我按这个式子加的）。长程 Agent 对输出速度的敏感度是线性放大的，单轮快 1 秒，20 轮就省 20 秒。相比之下，工具执行时间在很多场景里反而是小头，一次搜索几秒、一次代码执行几百毫秒，所以「选一个输出快但稍弱的模型」在长程任务上未必是坏选择。更划算的做法通常落在减少轮数上，靠更好的规划和更少的返工，这正是 1.2.4 节编排模式要优化的东西。

思考模式的取舍边界，原文给的两个例外很具体：单步简单任务，以及 Computer Use 中仅需点击固定位置的操作。它们的共同点是没有动态决策的成分，动作序列可以事先确定。反过来，只要「下一步做什么」依赖上一步的观察结果，就需要思考模型。这跟 ReAct 循环的必要性是同一件事。

开源与闭源的取舍，本质是拿能力差距换成本。原文给的时间量度是差距在 6 个月以内，成本判断是显著低于。工程决策就变成：你的任务能不能容忍落后 6 个月的能力。能，就换回成本、私有化部署和微调自由度；不能，就付闭源的钱，同时接受 API 策略的约束。原文还提了附加条件，对成本敏感或有数据合规要求的场景，后一条往往是硬约束，数据不能出境、不能上第三方，此时开源就是唯一选项，跟能力无关。

选型的坑集中在三处。只测「能不能答对」，不测「愿不愿意做、接口暴不暴露」，而原文列的这三件事必须分开测。拿聊天产品的表现推断 API 表现，原文明确说同一个任务在聊天产品、Coding Agent 和 API 中也可能得到不同结果。还有一种，把工具调用能力当成模型的通用能力，原文单独点过「不同模型在工具调用方面的能力差异很大」，一个在对话上很强的模型，工具调用可能很糟，所以选型测试必须是带工具的测试。

容易混的几对也说清楚。模型能力问的是基准测试上会不会，产品可用性问的是这个厂商的产品、接口、条款允不允许你这么做，判据就是原文那三问。「开源模型」这个词原文本节统一这么用，并强调成本低、可私有化部署、支持微调定制三个实际好处，笔记按原文用词，不改写成「开放权重模型」。还有「支持思考」与「始终开启思考」，本节说的是选支持思考的模型，实验 1-2 里 Kimi K3 的规格是始终开启的思考模式，前者是能力选项，后者是该模型的具体形态。输出速度与首 token 延迟也要分开，原文讨论的是输出 token 的速度，因为每轮都要等模型输出完成才能执行下一步，对多轮 Agent 来说，决定端到端延迟的是整轮输出耗时，第一个 token 多快只是其中一部分。

### 1.2.4 编排模式：工作流与自主

编排模式是 Harness 中「上下文与工具」层面的组织方式，它决定三件事：上下文如何在 LLM 调用之间流动，工具如何被调度，以及 Agent 的执行路径是预先设定还是动态生成。Agent 系统的编排方式经历过从简单到复杂的演进，每种模式都有自己的适用场景和相应取舍。原文引用的经验来源（脚注 5）是 Anthropic 与数十个团队合作构建 LLM Agent 的经历，其中最成功的实现往往没有使用复杂框架，用的都是简单、可组合的模式。

总原则是从简单到复杂，决策顺序分三级。先考虑单个 LLM 调用，如果通过优化提示词和上下文示例就能解决问题，就不要引入 Agent 系统。当需要多步骤处理、而且任务可以清晰分解为固定子任务时，考虑工作流。只有需要动态决策和灵活执行路径时，才使用自主 Agent。原文在这里加了一句提醒：Agent 系统通常会用延迟和成本换取更好的任务性能，应该谨慎权衡这种交换是否值得。

一个常见的反面例子是一开始就构建非常复杂的工作流或多 Agent 系统。原文举的案例是「从百万条聊天记录中提炼个人记忆」，一些 AI 模型很容易迅速画出一条看似严谨的流水线：先切分对话片段，再依次安排提取、证据核验、身份解析、记忆整理和合并复核 Agent，最后建立事实图、覆盖账本和不可变版本。原文的评价是，每个部件单看都有道理，组合起来却非常低效、不可靠。原因在于复杂工作流的执行拓扑是固定的，遇到新的例外，系统很容易继续增加节点，架构越来越复杂，通用性却越来越差；模型原本可以根据上下文处理的语义判断，反而被工作流写死了。

由此得到的结论是，Harness 很重要，不等于 Harness 越复杂越好。原文引用 Manus 官网的概括「Less structure, more intelligence.」（脚注 6：Manus, “Less structure, more intelligence.” <https://manus.im/>），做法是先给一个能力足够的 Agent 清晰的目标、必要的上下文和可组合的工具，用自然语言告诉它如何像人一样查证、比较、处理冲突；程序只固化权限、不得覆盖原始材料、原子发布这些必须始终成立的边界。只有业务约束本身要求，或者评估反复暴露出某类稳定失败时，才把对应步骤升级为专门的验证器、独立 Agent 或确定性流程。这一节的点睛句是：好的结构只守住边界，把边界内的决策空间还给模型，替 Agent 预演全部思考不在其中。

判断一个系统属于哪一类，钥匙是那三个要素。上下文怎么流动、工具怎么调度，决定的是系统长什么样；路径是预设还是动态生成，决定它属于工作流还是自主 Agent，而这也是两者的唯一本质区别，原文在 1.2.4.2 节明确写出了这一点。

「从简单到复杂」这条三级阶梯最好记成成本阶梯。单个 LLM 调用、工作流、自主 Agent，每上一级，延迟上升、成本上升、可预测性下降、任务性能上限上升。原文那句「Agent 系统通常会用延迟和成本换取更好的任务性能」就是这条阶梯的注解。上自主 Agent 是一次交易，不是一次升级。

那个反面例子值得多想一层，它演示了复杂工作流为什么会自己长大：拓扑固定，遇到新例外，加节点，拓扑更复杂，更不适应新例外，再加节点。原文的措辞是「架构越来越复杂，通用性却越来越差」。通用性变差的机制也清楚，每加一个节点，就是为某个已知例外写一条确定性规则，规则越多，模型原本可以用语义判断灵活处理的空间就越小。

Manus 那句话的正确读法是结构放在边界上，不放在决策路径上。程序要固化的是权限、不得覆盖原始材料、原子发布这类必须始终成立的边界；交给 Agent 的是清晰的目标、必要的上下文、可组合的工具，再加上用自然语言告诉它如何像人一样查证、比较、处理冲突。确定性部分（约束）用代码写死，语义判断部分（决策）交给模型，这其实是 1.2 节 Harness 五要素的另一种表述：约束归 Harness，决策归 Model。

升级为验证器、独立 Agent 或确定性流程的触发条件有两个，业务约束本身要求，以及评估反复暴露出某类稳定失败。第二个条件里的「反复」和「稳定」是关键，出一次错不加节点，评估显示这是可复现的模式才加。这就把「何时变复杂」从主观判断变成了由评估数据驱动的决策，与第七章、第九章是连着的。

工作流的两个优势其实指向同一件事，攻击面。「严格的流程控制」从正确性角度说，关键步骤不被跳过或乱序；「安全性」从安全角度说，攻击面被限制在单个节点内。两者都来自执行路径确定性这一个事实。工作流的安全性因此是确定性拓扑的直接推论，模型没有能力改变路径，也就没有能力跳到不该去的地方。

#### 1.2.4.1 工作流模式：确定性的编排

工作流（Workflow）是通过预定义的代码路径来编排 LLM 和工具的系统。它的执行路径是确定性的，由开发者预先设计好，每一步做什么、下一步去哪里都是代码写死的，LLM 只在每个节点内部负责理解和生成。

订机票 Agent 可以设计成四个固定节点。核实用户身份，调用身份验证 API 确认用户是谁；搜索可用航班，根据用户需求查询航班数据库；完成付款，调用支付接口扣款；确认预订，调用预订 API 锁定座位并向用户发送确认信息。每个节点内部都可以使用 LLM，比如用自然语言理解用户的出行需求，但节点之间的流转顺序由代码固定，系统不会在付款完成之前去预订座位，也不会在身份核实之前开始搜索航班。

这样编排换来两个核心优势。严格流程控制让开发者能确保关键步骤不被跳过或乱序执行，「付款前不能预订」这类业务规则通过代码强制执行，不依赖 LLM 的判断。安全性则来自执行路径确定这一点：提示注入或模型犯错最多只能影响当前节点内部的处理，无法让 Agent 跳到不该执行的分支，攻击面被限制在单个节点内。

工作流的主要局限是缺乏变通性。当出现预设流程未覆盖的情况，比如用户在付款环节临时想改签，或者航班突然取消需要推荐替代方案，固定的节点路径无法灵活应对，只能走预设的异常处理分支，或者把控制权交还给人类。

最简单的例子是文生图。用户的需求往往就是一句大白话，例如「帮我画一个 AGI 实现以后程序员的工作场景」，而 Stable Diffusion 这类文生图模型只接受特定风格的提示词：逗号分隔的英文标签、质量词、负面提示词。所以工作流要在用户和生图模型之间安排两个固定节点。第一个是提示词改写，用 LLM 把用户的自然语言需求改写成文生图模型习惯的提示词格式。上面那个需求很宽泛，LLM 因此还需要认真思考，原文举的例子是「AGI 实现之后程序员不需要写代码了，因此应该画一个程序员在海边晒太阳，通过脑机接口指挥 AI 员工」，然后给出具体的场景描述。第二个是图片生成，用改写后的提示词调用文生图模型，得到图片。

原文对这个例子给了三条判断。执行路径是代码写死的。工作流里的 LLM 节点做的是翻译，把人话转成工具听得懂的输入格式，它存在的原因是文生图模型「听不懂人话」。这种专门给工具或模型的能力短板打补丁的 Harness 代码，不妨称为适配层。接着是「但如果」：如果把生图工具换成具备原生图像生成能力的多模态模型，比如 Nano Banana 2、GPT-Image 2，就不再需要提示词改写了，不管用户怎么措辞，模型自己就能听懂、直接出图。

**实验 1-4 ★：文生图工作流与原生图像生成的对照**（印刷 p.23）

做法是让同一句大白话需求走两条路线。工作流路线由 LLM 先把需求改写成 Stable Diffusion 风格的提示词，再调文生图模型出图；原生路线把这句话原样发给支持原生图像生成的多模态模型（如 GPT-Image 2），一次调用直接出图。对照方式是看提示词改写节点把原始需求改成了什么样子，以及两条路线出的图谁更贴近原始需求。这里值得分两类需求来对照：一类是描述具体的，比如指定了海报文案；另一类是宽泛的，比如上面那个 AGI 工作场景，这类需求下工作流路线仍可能有自己的优势。

实验结论是，Harness 里那些给模型能力短板打补丁的部分，会随着模型变强被模型自己内化。原文随即盘点了「仅仅在本书第一章中，这样的事就已经发生了好几轮」：few-shot 示例、「让我们一步一步思考」之类的提示词技巧，被指令微调和推理模型内化了；输出格式修复、JSON 解析容错，被结构化输出和原生工具调用内化了；文生图的提示词改写，被模型的原生多模态理解与生成能力吃掉了。总结句是：每一轮内化，消灭的都是「翻译」和「脚手架」这类适配层代码。

| 曾经的 Harness 适配层 | 被什么内化 |
| --- | --- |
| few-shot 示例、「让我们一步一步思考」类提示词技巧 | 指令微调、推理模型 |
| 输出格式修复、JSON 解析容错 | 结构化输出、原生工具调用 |
| 文生图提示词改写 | 原生多模态理解与生成能力 |

适配层这个概念值得单独记住，它的定义是专门给工具或模型的能力短板打补丁的 Harness 代码。判断一个 Harness 组件是不是适配层，问一句就够：如果模型或工具本身具备这个能力，这段代码还需要吗？需要，它就是真职责；不需要，它就是适配层。按这个判据，提示词改写是适配层，因为多模态模型自己能听懂；权限控制则不是，再强的模型也不该自己决定能不能删库。适配层之所以会不断被模型吃掉，原因也在这里，它的存在理由就是模型或工具的能力短板，而短板会被补上。

实验 1-4 的对照设计里有一处很细的地方。原文要求分描述具体和需求宽泛两类来对照，并指出宽泛需求下工作流路线仍可能有自己的优势。这个补充能防止读者把实验读成「原生路线全面胜出」。可能的机制是这样（这一条是我补的解释）：宽泛需求下，改写节点相当于一次「创意扩写 + 结构化」，把模糊需求落成具体画面，这是「翻译」之外附带的增益；原生路线虽然能直接听懂，但生成的具体性可能没那么高。原文用的是「仍可能有」这种谨慎措辞，说明这是一个值得自己动手验证的开放结论。

读这张内化清单的方法，是看每一条都曾经必须写在外部，后来写进了模型。原文的总结是「每一轮内化，消灭的都是'翻译'和'脚手架'这类适配层代码」。由此得到一条工程启示：不要把适配层当资产去投资，它可以用来解决当下的问题，但不是护城河。

这一节的坑有三个。用工作流去处理会不断出现例外的问题，症状就是那个反面例子，节点越加越多、通用性越来越差。该用工作流的地方用了自主 Agent，涉及付款、退款、生产部署这类强业务规则的场景，自主 Agent 的灵活性反而变成风险来源，「付款前不能预订」这种规则不应该依赖 LLM 的判断。还有一种是把「翻译节点」当成永久架构，今天需要改写提示词的场景明天可能就被多模态模型吃掉，所以适配层要设计成可摘除的。

几对词需要分清。工作流与自主 Agent 的唯一本质区别是执行路径预先设定还是动态生成，工作流里的 LLM 只在节点内部工作，自主 Agent 里的 LLM 还决定节点怎么走。「确定性」也不等于「没有 LLM」，工作流完全可以包含 LLM 节点，订机票例子里每个节点内部都能用 LLM，确定性指的是节点之间的流转顺序由代码固定。适配层与 Harness 保障机制是两回事，适配层给能力短板打补丁，会随模型变强被内化；约束、验证、纠正这些保障机制不是补丁，短期不会被内化（详见 1.1.3.1 关于《苦涩的教训》的讨论）。还有提示词改写节点与提示工程，前者是一个架构位置，即用户和生图模型之间的固定节点，后者是一种实践，即优化提示词；原文说这个节点做的是翻译，它的职责是格式转换，不只是措辞优化。

#### 1.2.4.2 自主Agent：动态自主决策

当工作流的固定路径无法满足需求时，就需要自主 Agent（Autonomous Agent）。它与工作流的核心区别在于：工作流的路径事先写死，自主 Agent 的执行路径由它根据环境反馈实时决定。

订机票这个任务换成自主 Agent，就不再需要预定义四个固定节点。用户说「帮我订下周三去上海的机票」，Agent 会自行决定：先搜索航班，发现需要登录，于是先核实身份，再回来搜索，发现最便宜的航班需要转机，主动询问用户是否接受，用户说不要转机，Agent 再调整搜索条件。这要求自主 Agent 具备自主规划的能力，能自主决定执行步骤；也要求它能识别失败、调整策略，而不只是在出错时停下来。但自主性不等于无限制，必须设计明确的停止条件，原文列了三类：任务完成、达到最大迭代次数、遭遇不可恢复的错误。否则 Agent 容易陷入死循环或过度执行。

从实现角度看，自主 Agent 本质上就是在一个循环中使用工具的 LLM，通过持续获取环境反馈来推进任务，这正是前面介绍的 ReAct 循环。常见的退出条件有三项，调用最终输出工具、模型返回没有任何工具调用的响应，或者遇到错误、达到最大轮数。图 1-6 给出的版本更完整。

> 图 1-6（原文插图）：图题是「自主 Agent 的执行循环」。图的主干是一个三环节的环：① 思考（Reasoning），旁边标着示例文本「还需更多信息」；② 行动（Acting），示例是 `web_search(...)`；③ 观察（Observing），示例是 `tool_result: "..."`。三个环节首尾相连形成循环。从这个环引出一条「判断依据」的箭头，进入一个判断框「满足退出条件？」：否，则「继续下一轮循环」（回到 ① 思考）；是，则「输出最终结果」。图的一侧单列了「退出条件（任一满足）」，共五条：① 任务完成、② 调用 `final_answer`、③ 无工具调用返回、④ 错误次数超限、⑤ 达到最大轮次。这张图的读法要点是：三环节是循环体，五条退出条件是唯一的出口；而且五条里既有正常完成（① ② ③），也有异常兜底（④ ⑤），说明退出条件的设计本身就是安全机制的一部分。

适用场景上，自主 Agent 特别适合开放式的问题，这类问题难以预测所需的步骤数量。原文给的典型应用有三个：Coding Agent 解决 SWE-bench（Software Engineering Benchmark，一个评估 Agent 自动修复真实 GitHub Issue 能力的基准测试）任务；「计算机使用」（Computer Use）Agent 像人类一样操作计算机界面；需要迭代搜索和分析的研究任务。代价是更高的成本和潜在的复合错误风险，所以部署自主 Agent 时原文给了三条要求：必须在沙盒环境中进行充分的测试；设置适当的护栏和监控机制；在关键决策点考虑加入人机协作的检查点。

两个订机票例子放在一起是最好的教具。同一个任务，工作流是四个固定节点按序执行，自主 Agent 是搜索、需要登录、核实身份、回来搜索、发现要转机、问用户、调整条件。差别不在节点本身，两者都要搜索、核实、付款，差别在谁决定下一步走哪：工作流由代码决定，自主 Agent 由模型根据环境反馈决定。记住这个对照，就记住了两个模式的分界线。

「识别失败、调整策略，而不只是在出错时停下来」这半句是自主 Agent 的能力门槛。一个只会遇到错误就终止的系统算不上自主 Agent，它只是一个会调工具的单次调用。原文在实验 1-2 里给了一个可量化的对照指标，也就是长链工具调用的稳定性：Kimi K3 能连续执行 200 到 300 次工具调用而保持思考的一致性，远超多数模型在数十次调用后就开始退化的表现。能跑多长的链，是自主 Agent 的一个实际硬指标。

停止条件必须显式设计，这一条是本节最该记住的工程要点，因为循环的默认行为是一直转下去。图 1-6 那五条里，只有 ① ② ③ 属于正常完成路径，④ ⑤ 是兜底：错误次数超限防的是「反复重试直到耗尽迭代预算」，也就是实验 1-1 里「无工具结果」那组的症状；达到最大轮次防的是模型一直在做微小调整但永远不收敛。少了这两条，一个卡住的 Agent 会一直烧钱。原文因此把「必须设计明确的停止条件」写成一句独立的判断，并警告否则 Agent 容易陷入死循环或过度执行。

文字版三项与图形版五项并不冲突，前者说的是「常见的退出条件包括」，属于列举；后者标的是「退出条件（任一满足）」，属于完整清单。图形版是超集：文字版里的「调用最终输出工具」对应图里的「② 调用 `final_answer`」，「模型返回没有任何工具调用的响应」对应「③ 无工具调用返回」，「遇到错误、达到最大轮数」对应「④ 错误次数超限、⑤ 达到最大轮次」，图里多出来的是「① 任务完成」。① 和 ② 在实践里往往是同一件事的两种判定方式，前者靠外部判断，也就是任务目标达成了；后者靠模型显式声明。

复合错误风险这个概念值得展开。自主 Agent 的每一轮输出都建立在前面所有轮的结果之上。设单轮错误率为 $p$，走 N 轮不出错的概率大约是 $(1-p)^N$，轮数越多，整体成功率衰减得越快（这个式子是笔记补充的粗略模型，原书没有给这个公式）。所以自主 Agent 的可靠性衰减是累积的，跟线性外推差得远。这也解释了原文那三条部署要求为什么都要有，它们都是用来截断误差传播链的：沙盒限制出错的后果，护栏和监控负责及早发现，人在回路在关键节点强制纠偏。

SWE-bench 之所以是自主 Agent 的典型场景，原文给的理由是它属于开放式问题，难以预测所需的步骤数量。修一个真实的 GitHub Issue，可能是改一行，也可能要改五个文件加跑测试，没法事先写好固定节点。Computer Use 的界面状态千变万化，迭代研究里搜到什么决定下一步搜什么，同样属于步骤数不可预测的任务。反过来看，如果一个任务的步骤数可以事先写清，那它就是工作流的活。

这一节的坑集中在三处。只设「任务完成」一个退出条件，一旦模型判断不了「完成」，循环就永远不结束，必须同时配 ④ ⑤ 两条兜底。把最大轮次设得过大以求保险，轮次上限是成本熔断器，设得太大等于没有，合理的上限应该由这个任务的合理步数量级推出来，也可以参照 Agent 产品表里各产品策略一栏描述的步数粒度，多数是四五步的量级。还有一个是不给自主 Agent 配沙盒，原文把「必须在沙盒环境中进行充分的测试」写成了部署前置条件，不是建议。

容易混的几处也说清楚。「自主规划」与「工作流里的 LLM 节点」差别在于，前者决定执行哪些步骤、按什么顺序，后者在被指定的那一步里完成理解和生成；订机票例子里自主 Agent 会调整搜索条件，工作流不会。「最大迭代次数」与「最大轮次」是同一件事的两种说法，原文在不同位置分别用了这两个词。「退出条件」与「终止条件」的读法在图 1-6 里写得很明确，任一满足就退出，五个条件不必全部满足；这与 1.3 节「边界集 + 保留集」那种两个都要过的验证逻辑正好相反，别记混。自主性也不等于无限制，自主性指的是路径由模型决定，边界由停止条件、护栏、沙盒共同提供。

# 1.2.4.3 两种模式的选择与混合

前面两节把工作流和自主 Agent 各自的适用面讲清楚了，最容易读出来的结论是二选一。原文在这里踩了一脚刹车：实践中两者并非非此即彼，很多系统会混合使用两种模式。关键的、有严格合规要求的流程交给工作流来保证可靠性，需要灵活决策的部分切到自主模式。

这句话把 1.2.4.1 和 1.2.4.2 从「二选一」改成了「按流程分段选」。真实的业务系统通常是混合体：一整条链路里，合规相关的那几段用固定节点（付款前不能预订、大额操作要人工确认），开放判断的那几段跑自主循环（怎么找航班、怎么找到最优方案）。所以真正要回答的问题是：这条链路的哪几段该固定、哪几段该放开。

原文给了两种混合方式。

一种是同一系统内并存，例子是 n8n，一个成熟的工作流自动化开源框架。开发者通过可视化界面拖拽功能组件来构建 Agent，可以在同一个系统里同时使用工作流节点和自主 Agent 节点。这种做法的本质是「节点类型可以混」：工作流引擎里既可以放确定性节点，也可以放一个自主 Agent 节点，ReAct 循环就在这个节点内部跑完。好处是边界清晰，自主性被关在一个节点里，节点的输入输出是确定的，外层的合规流程依然由代码保证。这和 1.2.4.1 说的「工作流把攻击面限制在单个节点内」是同一个安全论点的反向应用，你在需要灵活性的地方开一个自主的口子，而这个口子的边界是明确的。

> 图 1-7（原文插图）：原文只保留了图注「图 1-7 n8n 工作流编辑器界面」。由于纯文本提取后图本身没有保留，笔记只能说明：这是一张 n8n 工作流编辑器的界面截图，用来给上面「通过可视化界面拖拽功能组件来构建 Agent」这句话配一个直观印象。界面的具体布局、画布上画了哪些节点、节点之间的连线形态，原文的纯文本中没有保留，笔记不做推测。

另一种是先由自主 Agent 把工作流写出来，再由工作流去执行。Agent 读完任务后自行决定拓扑并生成一段编排代码；代码一旦生成，执行阶段就退回工作流的确定性。收益是既保留了自主 Agent 面对未知任务的灵活性，又不必让模型在每一次调度上都参与决策。原文注明第十章会详细讨论这种形态。

这个设计很值得琢磨，因为它同时取了两种模式的长处，代价是引入了两个阶段。规划阶段由自主 Agent 面对未知任务，自行决定拓扑、生成编排代码，这里要的是灵活；执行阶段代码已经写定，按工作流的确定性跑，省 token、省延迟，还可复现可审计。笔记在这里补一个类比：这相当于「编译」，把一次昂贵的动态决策编译成一段低成本的确定性执行。风险也在这里，一旦编译错了，执行阶段会忠实地把错误执行到底，不像运行时那样有机会中途纠正。所以这种形态对规划阶段的质量要求更高，通常要配合验证机制（1.2.5 的护栏、第七章的评估）。名字和取舍记住就够了，细节留给第十章。

工程上可以按一条简单的规则做切分：把必须始终成立的边界（权限、金额上限、不可逆操作、合规顺序）交给工作流，把取决于上下文内容的判断（找什么、怎么比较、要不要追问）交给自主 Agent。这正是 1.2.4 节开头 Manus 那句话的工程化表述：「程序只固化……必须始终成立的边界。」

混合不是免费的。它引入了两套心智模型，确定性流程加自主循环，调试时要在两种执行语义之间切换；n8n 这类工具的低代码优势在复杂逻辑下也会变成表达力的限制。原文对这个取舍没有下结论，只提供了两种形态，选哪种得看自己的合规要求和团队构成。

这里有三处容易看混。原文明确说「并非非此即彼」，指的是很多系统同时包含两者，而不是从中挑一个。两种混合方式本身也有区别：同一系统内并存是空间上的混合，工作流节点和自主节点同时在跑；先规划后执行是时间上的混合，分两个阶段。还有一处是「Agent 生成编排代码」和 Coding Agent 的差别，前者生成的是自己下一步的执行计划，也就是编排拓扑，后者生成的是给用户或项目的代码产物，两者都用代码生成能力，目标不一样。

表里最该留意的是它挑的四个对比维度：核心定位、编排模式、开发方式、适用场景。这四个维度恰好回答选型时的四个问题，它是干什么的、路径是固定的还是动态的、我怎么用它、我的场景对不对得上。四个维度比九个名字耐放，原文自己也说了，在你阅读本书时很可能有些框架已经过时，又有新的框架流行起来。

编排模式这一列的读法需要一点背景。它的取值有六种写法：标「自主」的是 Codex Harness、Claude Agent SDK、Pi；标「工作流 + 自主」的是 LangChain/LangGraph、n8n；Dify 标「工作流 + 对话式」，CrewAI 标「Multi-Agent 协作」，OpenClaw 标「自主 + 事件驱动」，DeepSeek Harness 标「一切皆插件」。把它和 1.2.4.1、1.2.4.2 对起来就好理解了，标「工作流 + 自主」的框架同时支持两种模式，正对应 1.2.4.3 讲的混合方式一；标「自主」的以 ReAct 循环为核心；只有 CrewAI 标了 Multi-Agent 协作，那是第十章的主题。DeepSeek Harness 那一格写的「一切皆插件」其实是架构理念，不是编排模式，笔记照录原文表格的写法。

开发方式这一列是团队构成的镜像。代码优先是给工程师用的；低代码（可视化拖拽）是给业务和非技术团队用的，n8n 的适用场景里明确写了「业务自动化、非技术团队」；Dify 是低代码（可视化 + API），兼顾两者；OpenClaw 是配置 + 代码，自托管。选型时这一列往往比能力更决定性，团队里没人写代码，代码优先的框架再强也用不起来。

表中前两行原文单独做了澄清。Codex 是 OpenAI 的 Coding Agent 产品，有 App、CLI、IDE 扩展几种形态，Codex Harness 就是驱动这几种形态的那一层运行时。它提供三条集成路径：

1. `codex exec`：适合脚本与 CI 里的一次性任务；
2. Codex SDK：适合第三方应用代码启动、恢复和流式处理任务；
3. `app-server`：通过 JSON-RPC 协议提供持久会话、事件流与审批回调，适合把 Agent 直接做进产品。

这三条路径是按任务生命周期长度排的。`codex exec` 跑完就结束，所以用在脚本和 CI；Codex SDK 可以由第三方应用启动、恢复、流式处理，能恢复说明背后有会话状态；`app-server` 最重，持久会话、事件流、审批回调一起给，适合把 Agent 做进产品。`app-server` 里的审批回调尤其值得注意，它正是 1.2.5 节人工干预和 Harness 五要素里「约束」的接口形态，框架需要把「要不要批准这个操作」交回给宿主产品。选框架时可以据此看一眼它有没有这类回调接口，没有审批回调的框架很难做生产级的高风险操作。

Claude Agent SDK 与 Claude Code 也是类似的关系，区别在于 Claude 侧对外开放的是 SDK 接口，Harness 实现本身并不开源。这个对比说明「开放」可以发生在不同层次：Codex 把 Harness 开源了，可以拿运行时来嵌；Claude 开放的是调用接口，能用但看不到实现。对选型的影响是，需要深度定制或审计运行时行为时，开源那一侧更合适；只需要在应用里用起来，SDK 就够。

> 脚注 7（印刷 p.25）：OpenAI. “Codex as a platform: build on the open agent harness”, 2026 年 8 月。（原文照录：脚注给出的是文章标题与时间，未附 URL。）

还有两处概念要分清。表格「核心定位」一列里同时出现了框架、运行时、平台三种词，Codex Harness 被定位为运行时（驱动 App/CLI/IDE 扩展的那一层），Claude Agent SDK 是开发框架，Dify 是开发平台，它们不在同一层，别混着比。LangChain 和 LangGraph 在原文里被合并成一格写作「LangChain / LangGraph」，定位为通用 LLM 应用框架，编排模式是工作流 + 自主，正文没有区分二者（脚注 3 提到 LangGraph 官方文档把自己的实践称为「图编排」或 `graph-based workflow`）。CrewAI 的「Multi-Agent 协作」是多 Agent 之间的分工协作结构，和单个 Agent 的执行路径形态是两回事。

原文的选型标准值得逐字记住：「选择框架时，关键考量不在于框架本身的复杂度，而在于它能否用尽可能少的抽象层让你专注于业务逻辑。」这句话和 1.2.2 的「保持简单」是同一个论点在两个层面上的表述，1.2.2 讲你写代码时别加抽象，这里讲你选框架时别选抽象多的。所以这份表更适合当选型起点的索引用，更稳的做法是先把 Harness 五要素想清楚（要什么上下文、什么工具、什么约束/验证/纠正），再看哪个框架能最少摩擦地实现这五件事。框架是手段，五要素是需求。

本节收尾时原文把话头转向了护栏：编排模式解决的是上下文与工具的组织问题，但光能做事还不够，还要确保做得对、做得安全，为此需要设置护栏，将约束、验证与纠正落实到实践中。

### 1.2.5 护栏与安全性

编排模式解决的是上下文与工具怎么组织。护栏（Guardrails）要解决另一头的问题，让 Agent 的行为安全可控。原文把它定义成一层层的防线，覆盖的风险至少有数据隐私风险（比如防止系统提示泄露）和声誉风险（确保模型行为与品牌形象一致）。

怎么建呢。原文给的路子很务实：先针对已经识别出来的风险设置护栏，等发现新漏洞再逐步添加。单个护栏不太可能提供足够的保护，多个专门的护栏组合使用，才能构建出更有韧性的 Agent 系统。这一节只做高层次概览，把全书统一的分层骨架立起来，实现细节散在后面几章：第二章讲上下文层的提示注入防护，第四章讲执行层的工具权限控制，第五章讲执行层与数据层的代码执行安全、信任边界下移。初次阅读不用深究。

有一类失败容易被忽略，原文专门提了出来：误拒绝。为了降低危险请求被放行的概率，模型可能连一部分合法但形式敏感的任务一起拒掉，比如经过授权的安全测试、模型蒸馏研究。这两类任务放在网上看就像在攻击模型，可它们是合法的。所以护栏评估不能只测「应当拒绝的请求是否被拦截」，还要测「明确允许的请求是否能够正常完成」。这一对测试和 1.3 节的「边界集 + 保留集」完全同构：任何一次修改都要同时在它应当改变的那批样本和它不应当影响的那批样本上验证。护栏本质上就是一种修改，所以它得同时过这两组集合。

#### 1.2.5.1 护栏类型

三层按防护位置划分：上下文层、执行层、数据层。这里的排序依据最容易记错，原文特意强调，三层排的是被绕过的难度，跟请求处理的先后顺序没有关系：越靠下的层越不依赖模型自己的判断，因此越难被一次成功的攻击穿透。本书后面所有的安全讨论都挂在这棵树上。

为什么这么排？请求处理的先后是时间维度，被绕过的难度是依赖维度。上下文层的分类器、审核、规则，靠的都是模型的判断力；执行层靠的是上下文之外的机制；数据层靠的是数据库自身的策略。依赖得越少、越笨、越确定，就越难被聪明的攻击一次穿透。数据层排在最后，也是最可靠的一道。

**上下文层**管的是模型能看到什么，在内容进入上下文之前就拦下来。它通常有四种机制。相关性分类器标记偏离主题的查询，比如编程助手收到「帝国大厦有多高？」这类无关问题。安全分类器检测越狱（Jailbreak，即诱导模型绕过安全限制）和提示注入（Prompt Injection，即在输入中嵌入恶意指令），两者的关键区别在攻击来源，越狱是用户自己试图绕过模型的安全限制，提示注入是攻击者通过外部数据（如网页内容、文档）间接操纵模型行为。记住这个差别就够了，越狱是自己上手让你破防，注入是借别人的手让你破防。第三种是内容审核，标记有害或不当的输入，比如暴力、歧视性内容。第四种是基于规则的保护，采用确定性措施，包括黑名单、输入长度限制、正则表达式过滤器，用以防范 SQL 注入等已知威胁。原文补充说，来源标注与「指令/数据」分离也属于这一层，第二章会展开。

上下文层有一套代表性的工业实践，Anthropic 的 Constitutional Classifiers。原文说它的核心机制有三点。规则驱动指的是用自然语言写成的规则（明确规定哪些内容允许、哪些禁止）生成合成训练数据，再拿这些数据训练输入输出分类器。这手法的巧妙处在于把安全策略和分类器实现解耦了，改策略只需要改自然语言规则，不用重新标注数据，用 1.1.3.2 的话说就是把可语言化的策略写进外部产物。上下文联合判断指的是新一代系统把用户提问和模型回答放在一起检查，因为有些回答单独看毫无问题（如「如何使用食品调味料」），只有对照提问才能发现「食品调味料」其实是化学试剂的暗语。这对工程实现的直接含义是，分类器接口要设计成接收问答对，不能只接收单条文本。两级筛查则先用一个极轻量的探针（直接读取模型内部激活，几乎零成本）检查所有对话，发现可疑之处再交给更强的分类器复审，而不直接拒绝。第一级只做筛选，允许它误报偏高，第二级才做裁决，原文说这样一来「第一级即使误报较多也不影响用户体验，成本也大大降低」。这是用分层来买成本的架构，和本节开头「多个专门的护栏组合使用，才能构建出更有韧性的 Agent 系统」是同一个思路。

上下文层有一个结构性上限，原文的关键判断在这里：处在同一个上下文里的 Agent，很难判断自己是否已经被注入。机制上讲得通，攻击者把恶意指令写进网页内容，这段内容被检索进上下文之后，模型看到的「指令」和「数据」在同一个上下文里、以同样的形式呈现，它没有外部参照系去区分「这是用户让我做的」还是「这是那篇网页让我做的」。所以上下文层只能降低攻击成功率，给不出保证。这也正是 1.3 节「提议者—审核者」模式存在的理由，也是必须有下面两层的原因。

> 脚注 8（印刷 p.26）：Anthropic. “Next-generation Constitutional Classifiers: More efficient protection against universal jailbreaks”, 2026. <https://www.anthropic.com/research/next-generation-constitutional-classifiers>；论文：Cunningham et al., “Constitutional Classifiers++: Efficient Production-Grade Defenses against Universal Jailbreaks”, arXiv:2601.04603

**执行层**管的是模型能做什么，在动作真正生效之前验证。它的核心是工具风险评级：根据操作是否可逆、权限等级、财务影响，为每个工具标注风险等级（低/中/高），高风险操作需额外审查或人工确认。关键在于这类复核必须由上下文之外的机制完成，原文列的手段有独立的审查进程、最小权限凭证、沙盒隔离、人在回路，理由说得很直白，「否则它会和被注入的 Agent 一起沦陷」。想象一下，Agent 被网页注入之后去调用一个审批工具，想批准自己的高风险操作，如果这个审批也是同一个上下文里的模型调用，它看到的上下文同样被污染，它当然会批准。所以这四个手段的共同特征是，判定输入不来自被保护的那个上下文。

输出检查也属于执行层。很多人凭直觉觉得回复只是输出、不算行动，原文纠正了这一点，它按第四章的工具分类把回复归为**用户沟通工具**，所以回复也是一次对外动作，同样需要护栏。这直接推出两项检查：PII 过滤器审查输出中的个人身份信息（如身份证号、手机号），防止不必要暴露；输出验证则通过内容检查确保回复与品牌价值一致。这也解释了本节开头为什么把防止系统提示泄露和模型行为与品牌形象一致列为护栏的两个目标。

**数据层**管的是世界最终能被改成什么样。它把「谁能对哪条数据做什么」交给一层稳定的、经过人类审查的机制强制执行，具体包括数据库的行级安全策略、约束与校验器、受控视图与存储过程，以及由受信任运行时绑定、无法被伪造的访问上下文。这一层的价值在于它不依赖上面两层是否正确。原文给的场景很具体：「即使提示注入得手、生成的代码完全漏写了权限判断，越权操作仍会在数据层被拒绝。」这里点出的是一个真实的工程组合，Agent 动态生成代码，而代码里忘了做权限检查，前两层都可能因为各种原因放行，数据库的行级安全策略却是独立的、由人类审查过的、无法被 Agent 改写的。原文注明第五章会以动态生成软件为例展开这一层。

#### 1.2.5.2 人工干预

人工干预（Human in the loop，又称人在回路）是一个关键的保护措施，它让 Agent 能够在不损害用户体验的情况下提升实际性能。原文特别点了时机：这在部署早期尤为重要，有助于识别失败模式、发现边缘情况并建立健壮的评估周期。实施这套机制，可以让 Agent 在无法完成任务时平稳地移交控制权。原文举了两个具体含义：在客户服务中，这意味着将问题升级到人工客服；对于 Coding Agent，这意味着将控制权交还给开发者。

通常有两种主要情况会触发人工干预。一是超过失败阈值，也就是为 Agent 的重试次数或操作次数设置上限，超过这些限制就升级到人工干预。二是高风险操作，涉及敏感、不可逆或高风险的操作时，应触发人工监督，至少在团队对 Agent 可靠性建立起足够信心之前是如此，原文的典型例子是授权大额退款或付款。

这两个触发条件和图 1-6 是同一套逻辑：失败阈值对应图里的「④ 错误次数超限」，高风险操作对应执行层的「高风险操作需额外审查或人工确认」。所以人工干预不是外挂在流程外面的一层，它是执行层护栏的一个手段被打通到了组织流程层。原文还点出了它的两个价值，一是平稳移交控制权，对应 1.2 节 Correct 里的「连续失败时回退到人工判断（熔断机制）」；二是在部署早期建立评估周期。也就是说，人在回路不只是安全措施，还是数据采集手段，人在处理边缘情况的同时，你顺便知道了边缘情况长什么样。

还有几个概念容易混。五要素里的「约束」（Constrain）指的是动作生效前限制集合，也就是 `Harness.constrain`；执行层护栏的范围更宽，动作生效之前验证、工具风险评级、输出检查都在里面，并且强调复核必须在上下文之外。人工干预和审批回调也不是一回事，前者是机制与触发条件（失败阈值、高风险操作），后者是框架提供的接口形态，比如 Codex Harness 的 `app-server` 通过 JSON-RPC 提供审批回调（见 1.2.4.4）。至于误拒绝，原文用的这个词指的是合法但形式敏感的请求被拒，它和漏杀是一对相反的错误，过度拒绝只是它的另一种说法，评估时两端都要测。

工程上常踩的坑有这么几个。只做上下文层是最常见的，因为加个分类器调用最容易，但原文明确说它给不出保证，只做这一层等于没有防线纵深。把人工确认放在同一个上下文里也很常见，比如让模型自己弹一个「我确定要删除吗？」，这正好撞在原文的警告上。第三个是护栏只测漏杀不测误杀，上线之后会出现一批用户明明提了合法需求却被拒的工单。第四个是忽略回复也是一次动作，没有输出侧的 PII 过滤，敏感信息可能顺着回复泄露出去。原文对做全三层的节奏没有硬要求，实践中可以先针对已识别的风险设置护栏，再在发现新漏洞时逐步添加，但分层的骨架要一开始就有，否则后面加层会处处返工。

原文随后把话收回主线：下面看看 Harness 五要素和本书的结构是什么关系。

### 1.2.6 Harness 五要素与「构建」部分的对应

这一节的首要任务是澄清两个公式的关系，免得读者记住两套骨架。

原文的原话是，全书的结构骨架只有一个，就是引言和后记反复使用的 `Agent = LLM + 上下文 + 工具`：第二至六章讨论构建，第七至九章讨论评估与进化，第十章讨论协作。而 `Agent = Model + Harness` 不是与它并列的另一套划分，它是同一事物在生产形态下的展开，把「上下文」和「工具」两项细分为上下文管理、工具接口、约束、验证、纠正五项职责。所以它是构建部分内部的一个观察视角，并不覆盖全书十章。

说到这里就能看出「细分」这个词的分量了：`上下文 + 工具` 变成 `上下文管理 + 工具接口 + 约束 + 验证 + 纠正`。后三项不是凭空多出来的模块，它们是从前两项里分出来的职责。约束从工具接口里分出来，管的是工具的风险等级和权限；验证横跨上下文和工具两头，既要看上下文有没有被污染，也要看调用结果对不对；纠正作用于整个运行过程，重试、回退、熔断都在这里。所以五项职责是同一个 Harness 的五个关注点，别把架构画成五个孤立组件。

Harness 五要素与第二至五章的对应关系如下（表格按原文语义还原）：

| Harness 要素 | 对应章节 | 核心内容 | 安全关注点 |
| --- | --- | --- | --- |
| 上下文管理 | 第二章（上下文工程） | 提示工程、Agent 状态栏、上下文压缩、Agent Skills | 提示注入、上下文污染 |
| 上下文管理（跨会话） | 第三章（用户记忆和知识库） | 用户记忆、RAG、结构化索引、智能体化 RAG | 敏感信息暴露、隐私保护 |
| 工具接口与约束 | 第四章（工具） | 工具分类、权限控制、MCP 标准、主动工具发现 | 误操作、未授权访问、不可逆操作 |
| 验证与纠正 | 第五章（Coding Agent 与通用 Agent） | Coding Agent 的 Harness、测试驱动、代码化规则 | 身份冒用、责任归属 |

表里「上下文管理」出现两次（第二、三章），说明五要素和章节并非一一对应。上下文管理这一个要素横跨两章，第二章管单次会话内的上下文，第三章管跨会话的用户记忆和知识库。这是原书自己的安排，不必期待一个完美的「要素—章节」双射。原文的措辞是，在这个范围内，Harness 五要素与第二至五章有清晰的对应。清晰，但不严格一一对应。

哪些章不进格子，原文也说明了。第六章（交互）不属于五要素中的任何一项，它扩展的是观察与动作空间本身的模态与时机；第七至九章讨论的是怎么知道 Harness 建对了、以及怎么让它持续变好；第十章则把单个 Agent 的 Harness 换成多个 Agent 的协作结构。原文的判据是：「把这些章也塞进五要素的格子里，只会让格子失去区分力。」这句话其实是个方法论层面的忠告，分类的价值在于区分，一个格子能装下几乎所有东西，它就失去了信息量。

第六章这个例外值得多说一句，因为它划出了五要素的适用边界。五要素讲的是运行与治理，而交互扩展的是空间本身。把语音、图像、异步通知这些新模态接进来，做的是把观察与动作空间变大，跟把某项职责做得更好是两码事，这是 1.1.1 节那条「扩展观察空间与动作空间」的杠杆在交互层面的体现，所以它天然不属于治理层的五要素。

安全为什么不按章划分？原文的回答是，它是贯穿全书的横切关注点（Cross-cutting Concern，即一个影响系统多个部分的问题），按前一节的三层护栏组织，也就是上下文层、执行层、数据层。上表的安全关注点一列，给的是每一章在这三层里最主要的落点。这个安排很实际：如果安全按章写，比如「第五章讲安全」，那第二、三、四章的安全问题就没地方放；按三层护栏组织，每一层都能挂到多个章节上。具体映射是，第二章对提示注入、上下文污染（上下文层），第三章对敏感信息暴露、隐私保护（数据层为主），第四章对误操作、未授权访问、不可逆操作（执行层为主），第五章对身份冒用、责任归属（跨层，尤其涉及谁做的、谁负责）。把这四行和三层的定义对起来看，章节顺序（二到五）与护栏层级顺序（上下文层、执行层、数据层）大体同向，这和 1.2.5.1 说的越靠下的层越难被绕过是呼应的。

原文还用了一个实例来展示 Harness 设计如何解决模型本身无法解决的问题，那是 Anthropic 构建长时运行 Agent 的实践。他们把复杂任务分解为「初始化 Agent」和「执行 Agent」两个角色，前者设置环境、分解任务列表，后者在每个会话中增量推进并留下清晰的交接产物。靠这种结构化的 Harness，他们解决了 Agent 在长任务中的两个问题：上下文耗尽，以及过早声明完成。

这两个问题选得很准，因为它们都出在结构上，跟模型能力够不够无关。长任务的信息量必然超过窗口，换更强的模型解决不了，窗口是有限的，只能靠 Harness 的结构去分解任务、留下交接产物。过早声明完成也一样，模型「觉得」做完了，实际没做完，这是可靠性问题而非能力问题，也换更强的模型解决不了，要靠显式的任务列表和验证。Harness 能补的正是这一类窟窿。这和 1.1.3.1 节「模型此刻的能力边界，就是 Harness 此刻的价值所在」是同一层意思，只是这里给了一个具体案例。

把这一节当作全书的目录解释器用，读起来会省力很多。以后读第二章时先问一句，这一章在补五要素的哪几项、挡三层护栏的哪一层；读第六章时记得它不在五要素里；读第七至九章时记得它们回答的是怎么知道建对了、怎么持续变好；读第十章时记得它把单个 Harness 换成了多个 Agent 的协作结构。

几个对照关系最后归拢一下。`Agent = LLM + 上下文 + 工具` 和 `Agent = Model + Harness` 只有前者是骨架，后者是同一事物在生产形态下的展开，是构建部分内部的一个观察视角，不是覆盖全书十章的目录。五要素和五章不一一对应，上下文管理横跨第二、三章，工具接口与约束对应第四章，验证与纠正对应第五章，第六章不在五要素之内。横切关注点和章节主题也不是一回事，安全影响多个部分，所以按三层护栏组织，不按章划分。至于 Anthropic 实践里的两个角色，「初始化 Agent」做的是设置环境和分解任务列表，属于一次性动作；「执行 Agent」在每个会话中增量推进并留下清晰的交接产物，可以重复多次。

后续章节将逐一深入 Harness 的各个组件，第二章从最核心的上下文工程开始，第五章专门展开 Harness 工程在 Coding Agent 中的完整实践。

# 1.3 贯穿全书的设计模式

这一节是原书特意埋的索引。后面几章会反复动用同一批设计模式，所以作者在这里一次性命名并给出规范定义，每个模式都点明「哪个章节用它做什么」。现在读它，为的是建立查找入口，细节要等对应章节展开。

| 模式 | 定义 | 前提或收益 |
| --- | --- | --- |
| **提议者—审核者**（Proposer-Reviewer） | 产出与评判由两个不共享上下文的角色分别承担，评判方看到的是产物本身 | 自审不可靠 |
| **渐进式披露**（Progressive Disclosure） | 先给一份可检索的目录，再按需加载细节 | 同时优化上下文预算与选择精度 |
| **只增不改**（Append-only） | 状态以追加的方式演进，已经写下的内容不再回头修改 | 可缓存、可重放、可审计 |
| **边界集 + 保留集**（Boundary Set + Retention Set） | 每一次修改都同时在「应当改变的那批样本」和「不应当影响的那批样本」上验证 | 只测前者会把过拟合当成进步，只测后者会把无效修改当成安全 |
| **最小 diff + 可回滚** | 每次修改尽量小、带来源、可单独回滚 | 让归因成为可能 |

五个模式里，提议者—审核者排在第一位，因为它直接对着安全与可靠性的根因。原书给的前提只有四个字：自审不可靠。理由有两条，同一个上下文中的模型难以发现自己的认知盲区，也很难判断自己是否已被注入，后一条和 1.2.5.1 说的是一件事。于是这个模式的落点就在「换一个上下文」上，它是绕开这个结构性瓶颈的办法。评判方看到的是产物本身，渲染结果、测试输出、结构化的调用参数都算，产出方的推理过程不在其中。这和 1.2 节 Verify 的原则同源：安全检查只看结构化数据，不看模型自由生成的文本，后者可能已被提示注入操纵。产物是最难被话术污染的那部分证据。Sidecar 被点名为它的只读变体，让一个独立角色只读地看主流程在干什么、不做修改，这个名字在 1.2 节的五要素表里也出现过，Context 的「实际例子」一栏写的就是 Sidecar 旁路查询。全书用它做的事不少：第三章更新知识，第四章做工具调用的事前审批与事后验证，第五章的 PPT、视频与日志三个实验都以它为骨架，第七章评估 UI，第九章审核更新提案，第十章讨论它在对等协作中的形态，以及为什么不能让同一个 Agent 自审。

渐进式披露的类比是查字典，没人把整本字典背下来，先看目录或索引，需要某个词的时候再翻到那一页。原书说它同时优化上下文预算与选择精度，这两件事的机制要分开看。不加载就没占用 token，省的是预算；目录本身是压缩过的，干扰信息少，模型在目录上做选择比在全文里找更准，省的是精度。第二章的 Agent Skills 是最典型的形态，元数据小、常驻，正文大、按需加载，名字本身就说明了形态。第三章的分层检索、第四章的主动工具发现与分页截断、第十章的 Agent 发现都是它的变体。

只增不改说的是状态以追加方式演进，换来的三个收益机制各不相同。可缓存，是因为前缀不变，KV Cache 能命中，改动越靠前作废的缓存越多，第二章的前缀稳定性讲的就是它的性能形态。可重放，是因为历史成了一条只能追加的日志，按同样的顺序回放就能复现同样的输入。可审计，是因为已经写下什么就是什么，不会被事后改写。原文举的两个例子都很能说明问题：第三章的事件式记忆是「发生过什么」的事件流，不改历史；第四章把新工具的 schema 追加到轨迹末尾，插回前缀就会破坏缓存。后者正是 1.1.4 节那句「2026 年以来，生产框架中工具的完整 schema 也可以按需动态加载到上下文末尾而不破坏前缀」的纪律来源。

边界集加保留集这一条最容易被略过，工程价值却最高，因为它把「改得对不对」变成了必须双向验证的问题。边界集是这次修改应当改变的那批样本，用来证明改动有效；保留集是这次修改不应当影响的那批样本，用来证明改动没有副作用。原书给的两个反例警示很精炼：只测前者会把过拟合当成进步，只测后者会把无效修改当成安全。这两句话值得背下来，它们是「我改了 Prompt，感觉变好了」这类判断的解毒剂。名字容易记反，记法是边界集画的是改动的边界，也就是改动要覆盖到的范围。第七章的回归任务、第八章的训练与评估隔离、第九章的更新提案验证都建立在这对集合上。

最小 diff 加可回滚的价值全在「归因」这个词上。每次修改尽量小、带来源、可单独回滚，出了问题能定位到具体哪一次改动，它服务的是可诊断性。反过来看，一次大重写把十处改动混在一起，出问题时就判断不出是哪一个导致的，只能整体回退，回退粒度等于调试粒度。第三章的知识更新、第五章的代码补丁、第九章的 Prompt 与程序更新都遵循这条。

本节末尾那句呼应把 1.1.3.2 的「三条更新路径」接了进来，它们正是按可回滚程度从高到低排列的。上下文内适应下一轮就不存在了，回滚等于不把它放进上下文，可回滚度最高；外部产物更新写进文档、Prompt 或程序，回滚等于撤销那次 diff，最小 diff 加可回滚这个模式正好服务于此；参数更新改的是权重，回滚要重新训练或者回滚模型版本，可回滚度最低。而「优先用可回滚度高的手段」这条工程直觉，在本章里算是有了理论支撑。

工程上最实用的用法是拿它当设计自检清单。同一个 Agent 在审自己？该上提议者—审核者。上下文里一股脑塞了全部资料？该上渐进式披露。改写历史导致缓存全失效、日志不可重放？该上只增不改。改完只测了该变的样本？该补上保留集。改动一大坨、出问题只能整体回退？那就该拆成最小 diff。

这五个模式是本章最可迁移的部分。1.1 讲的是 Agent 是什么，1.2 讲的是怎么可靠地跑，1.3 给的是能直接套用到任何 Agent 系统上的设计套路，它们不依赖具体模型，也不依赖具体框架，这正好回应了本章思考题第 10 题那种「设计原则应穿越模型迭代周期」的关切。原文把它们说成会被后续章节反复用到的跨章公共词汇，所以这一节的正确读法是先建立索引，不必现在就掌握细节，每一处点明的「哪个章节用它做什么」就是留给你的入口。

## 1.4 本章小结

小结的七条正好对应本章的两部分，前三条收 1.1，后四条收 1.2 和 1.3。读的时候可以拿它当检索表，哪条想不起来，就回对应小节。

第一条把 Agent 说成大脑加眼睛加手脚：LLM 是决策核心，上下文决定它能看到什么，工具决定它能做什么，三者缺一不可。

第二条说扩展眼睛和手脚是最主要的能力杠杆。模型固定时，重新定义或扩展观察空间与动作空间，往往能直接把原本不可解的任务变为可解。Manus 把 Deep Research、Coding、Computer Use 三类 Agent 的观察空间与动作空间取并集，虚拟浏览器扩的是眼睛，文件系统、代码执行与命令行扩的是手脚；OpenClaw 走 WhatsApp、Telegram、Slack、Discord、iMessage 这类消息渠道收发任务，用本地 Gateway 连 Google Drive、Notion 和本地文件系统。两者的演进都说明，通用性很大程度上来自接口边界的扩大。这里有个限定必须一起读：这种扩大要按需进行，并配合权限控制和验证。原书在小结里专门把它补回来，说明作者认为这个限定和大结论同等重要，否则很容易读出「接口越宽越好」的结论。还有一对词要分开：扩展上下文和工具是把新数据和操作接进来，属于接口层面的扩展；扩展上下文窗口是加大模型的容量上限，属于模型层面的事。小结第二条说的是前者。

第三条说眼睛是决定性的因素，这个措辞是原书小结的原文。上下文由静态前缀（系统提示词加工具定义）和动态轨迹（消息历史）构成，它对最终行为的影响最直接，因为 Agent 只能基于它看到的信息做决策。消融实验给出的是更精细的结论：各组件并不等价，去掉工具定义或工具执行结果会直接夺走行动与闭环能力，去掉另外两者的代价则取决于信息能否从当前观测重建。真正决定代价的是信息的可重建性，跟信息条数关系不大。ReAct 循环的本质，也就是通过不断追加轨迹来让模型持续推进任务。

第四条说 Harness 是竞争力所在。模型能力正在商品化，含义是模型会变成像云主机、数据库一样的东西，能买到、能替换、差距可以被价格差补上；开源与闭源的差距在本书编写时被估计在 6 个月以内，成本还显著更低，DeepSeek、Kimi、GLM 属于国内 Agent 能力较强的模型。替代成本一旦下来，产品之间的差距就只能来自你在这层商品之上搭的东西。原书用一句话点出投入方向：在生产级 Agent 系统中，Harness 的绝大部分代码都在实现这些保障机制，而不仅仅是上下文和工具本身。这个说法可以检验，1.2 节拿 Claude Code 举过例，文件读写、命令执行、搜索这些工具本身只是一小部分，围绕它们构建的保障机制才是核心；LangChain 那组数字也在这一条上，模型不动、只改 Harness，Terminal Bench 2.0 的得分从 52.8% 升到 66.5%，排名从 30 名开外进到前 5。从提示工程到上下文工程、Harness 工程、Loop 工程、Graph 工程这五波范式层层包含，单个 Agent 循环只是执行图里的一个节点。在自己的项目里，也可以粗算一下「保障机制代码 / 总代码」这个比例，作为成熟度的粗略参考。这条讲的是投入方向，跟「上下文和工具缺一不可」并不冲突，原文明确说过它们缺一不可。

第五条是从工作流到自主 Agent 的顺序：先把提示词优化到位，再考虑工作流，真到了需要动态决策的时候才引入自主 Agent，这是降低意外风险最实用的顺序。每种编排模式都有其适用场景，不存在通用最优解。

第六条列了贯穿全书的五个模式：提议者—审核者、渐进式披露、只增不改、边界集加保留集、最小 diff 加可回滚。

第七条说安全是架构问题。安全问题从第一行代码就要考虑，而不是上线前打补丁。七条里它是唯一一条以「何时做」为核心的结论，这正好解释了 1.2.5 的护栏为什么要给出一个三层骨架，而不是一串零散的措施：骨架是为了在架构设计阶段就预留位置。护栏按被绕过的难度分成上下文层、执行层与数据层，后续各章的安全讨论都挂在这个骨架上。

过渡部分交代了去向：下一章深入 Harness 中最核心的组件，也就是上下文工程；Agent 概念在强化学习中的学术渊源，以及传统 RL 与现代 LLM Agent 的深入对比，留到第八章系统展开。最后一句给思考题定了位，这些题目用来引导读者深入思考本章的核心概念，不设标准答案。

## 思考题

这一节先把口径交代清楚。原书说，以下思考题旨在引导读者深入思考本章的核心概念，不设标准答案，页面上方另有一个「深度思考」的栏目标题。一共 10 题，题号前的 ★ 号是原文标的难度。本章只有思考题，没有练习题，下面附的思路提示是笔记补充的，不是答案。★ 号的具体口径原文正文里没有解释（原文只标了 ★、★★、★★★），从分布看（第 5 题是 ★，第 2、7、10 题是 ★★★）大致对应论证复杂度，笔记不做推断性定义。

> 1. ★★ 如果你只能给一个 Agent 系统增加一项能力——更强的模型、更丰富的上下文还是更多的工具——你会选哪个？在什么条件下你的选择会改变？
> 2. ★★★ ReAct 循环中，累计缓存读取量随轮数近似二次方增长。如何降低这种增长？
> 3. ★★ 「模型即 Agent」范式意味着模型在工具调用决策上越来越自主。但本章论证了 Harness 工程的重要性反而在增加。这两个趋势如何共存？Agent 框架未来的核心价值体现在哪些方面？
> 4. ★★ 消融实验中「工具结果反馈」的缺失会让 Agent 反复重试直到耗尽迭代预算。在生产环境中，除了工具结果缺失，还有哪些情况可能让 Agent 陷入这种循环？你会设计怎样的检测和终止机制？
> 5. ★ 本章用感知、行动、策略三个维度分析了五个 Agent 产品。请选择一个你日常使用的 AI 产品，用这三个维度进行分析，并思考它的架构设计是否合理。如果由你来设计这个 AI 产品，有哪些改进空间？
> 6. ★★ 如果你要设计一个专门处理航班订票的客服系统，你会选择工作流模式还是自主 Agent 模式？有没有可能在同一个系统中混合使用两种模式？
> 7. ★★★ 护栏部分提到了工具风险评级。如果一个工具在大多数情况下是低风险的，但在特定参数组合下变为高风险（如 `delete_file` 删除普通文件 vs 删除系统文件），你会如何设计动态风险评估？
> 8. ★★ 本章的 Agent 产品表格中，所有 Agent 的动作空间都是「开放式」的。一个受限的动作空间（比如只能从预定义选项中选择）在什么场景下反而优于开放式？
> 9. ★★ 人工干预机制要求 Agent 能「优雅地移交控制」。但在实践中，用户可能不在线、响应很慢、或者给出模糊的指令。此时 Agent 应该怎么办？
> 10. ★★★ 引言指出「好的设计原则应该穿越模型的迭代周期」，但实现这些原则的具体工程手段可能会随模型能力进步而过时。试举一个这样的 Agent 工程手段，并说明理由。

**思路提示（笔记补充，非原文，不构成标准答案）**

1. 先分清瓶颈归因，可以套用 1.1.1 的判据问一句：把数据或操作给到这个模型，它做得对吗？答「对」，缺的就是接口，该补上下文或工具；答「不对」，才轮到模型。再想条件变化。任务开放、步骤数不可预测时，工具的边际收益通常最大；知识需求随时间或私有化变化时，上下文的边际收益最大；任务需要高维隐性能力（风格、影像判读）时，模型才是瓶颈。另外别忘了 1.2.3 的提醒，换模型还受策略边界与服务条款约束。
2. 先想清楚为什么是二次方。每一轮都要把此前全部轨迹作为输入重新读一遍，第 $t$ 轮读的是前 $t$ 轮累积的内容，于是 $1+2+\dots+N \approx N^2/2$（这是笔记给的粗略模型，供推理用，不是原文公式）。降低办法往「只增不改但别重复读」的方向想：前缀缓存能不能复用？轨迹能不能压成摘要或结构化状态？旧轮次能不能折叠成「已确认的结论」？哪些信息其实可以从当前观测重建，这是 1.1.4 的判据。
3. 把两件事拆到不同层看。决策权在往模型里走，RL 内化的是决策策略；执行、治理、编排仍在模型之外，这就是实验 1-2 的区分。实验 1-2 里的 Kimi K3 可以当样本：约 2.8 万亿参数的 MoE、100 万 token 的上下文窗口、原生视觉理解、始终开启的思考模式，能连续执行 200～300 次工具调用而保持思考一致性。再想框架的价值会往哪挪：怎么调工具不再是问题之后，价值可能转向上下文与记忆的组织、约束与验证、多 Agent 协作结构、可观测性与评估。也可以从 1.2.6 的五要素里挑你觉得最难被内化的那几项。
4. 先列出循环不退出的其他成因：工具返回成功但结果不含所需信息，模型反复换 query；工具一直报错但错误信息不可读；模型判断不了信息是否充足；任务本身无解但模型不肯放弃；多个工具互相矛盾导致来回切换。设计机制时可以参考图 1-6 的五条退出条件，特别是「错误次数超限」和「达到最大轮次」这两条兜底，再加上重复检测，LangChain 那组 Harness 改进里就有「检测是否陷入重复循环」这一项。
5. 先确定感知、行动、策略三栏各自填什么。本章给这三维度配的学术概念是观察与历史、观察-行动接口、策略。分析时重点看「眼睛」那一栏，不同产品的差异主要在这里。改进空间可以从 1.1.1 的两个问句切入：有什么该看到的信息没进上下文？有什么该做的操作没被封成工具？别忘了权限与验证，也就是 1.4 小结第二条的限定。
6. 把订票流程按 1.2.4.3 的思路切段。合规敏感、顺序刚性、不可逆的环节（身份核实、付款、锁定座位）倾向工作流；依赖上下文判断的环节（怎么找航班、要不要推荐替代方案、用户临时改签）倾向自主。混合的两条路都可以考虑，n8n 式在同一个图里放两类节点，或者让 Agent 写工作流再执行。回答时最好说清哪些边界必须写死。
7. 核心是把风险评级从「按工具名」改成「按（工具，参数）」。可以从参数里找可判定的信号：路径是否落在受保护目录、金额是否超阈值、目标是否是系统关键资源。也可以分级，低风险直接放行、中风险二次校验、高风险人工确认，并把判定放在上下文之外，这是 1.2.5.1 强调的。收尾可以用「故障安全默认值」这条原则：判不出来时默认拒绝或转人工。
8. 从开放式动作空间的代价反推。开放式带来出错面、攻击面、不可预测性和评测困难，于是受限更优的场景通常是：高风险且可穷举（只能选批准、拒绝、转人工）；需要严格可审计，合规场景要求每一步都能列出来；需要确定性保证，付款金额只能从预设档位选；以及接口易用性，选项比自由文本更不容易被误解，对应 1.2.2 的 ACI 原则。
9. 先分清移交失败的几种情形：用户不在线、响应很慢、指令模糊。可以想的方向：设定等待超时与默认动作，超时后走保守分支，只做可逆操作或者保持现状；把模糊指令转成一个有限选项的问题，这正好呼应第 8 题受限动作空间的优势；把未决状态持久化，等用户回来再续，对应 1.1.2 的受控虚拟工作目录和 1.3 的只增不改；在关键路径上提前取得授权，别等事后再移交。
10. 在 1.2.4.1 里找适配层清单最直接：few-shot 示例、「Let's think step by step」这类一步一步思考的提示词技巧、输出格式修复与 JSON 解析容错、文生图提示词改写，都是原文明确说被内化了的手段。选一个说清它当初解决什么短板、后来被什么能力吃掉。也可以反过来想哪些手段不会过时，比如提示注入防护的三个护栏层、权限与审计这类跟信任边界有关的机制。
