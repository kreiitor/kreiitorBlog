## 先建立直觉：视图不是容器

很多初学者看到 `string_view`、`span`、`views::filter(...)` 时，容易把它们都当成“某种新容器”。

这其实是最容易产生误解的地方。

### 容器 vs 视图

你可以先这样理解：

| 对象 | 更像什么 |
| --- | --- |
| 容器 | 真正拥有数据的“仓库” |
| 视图 | 站在仓库门口往里看的“窗口” |

也就是说：

- 容器通常负责分配、持有、释放内存；
- 视图通常不拥有数据；
- 视图只是对已有数据的一种轻量访问方式。

本章反复强调的是：

> 视图的优势来自“轻量”和“少拷贝”，但它的风险也来自“不拥有数据”。

这句话你后面会反复看到。

---

## 10.1 视图概述

先总体上介绍“视图”这个概念。

视图的共同特点可以概括为：

1. **不拥有底层数据**
2. **创建成本低**
3. **适合作为接口层的参数或中间结果**
4. **前提是底层数据仍然存活**

### 为什么视图很重要

因为现实代码里有很多场景都只是“借用”数据：

- 我只想读一个字符串，不想复制一份；
- 我只想把一个数组的一部分传给函数；
- 我只想按条件看一批元素，不想先创建新容器；
- 我只想把“处理流程”拼起来，而不是在每一步都落地成新对象。

这正是现代 C++ 不断强化 view 思想的原因。

## 10.2 `string_view`

`std::string_view` 是本章最基础、也最常用的视图类型。

你可以先把它理解成：

> 一个“只读的字符串视图”，很像“字符指针 + 长度”。

它不拥有字符内存，只是指向某一段现有字符序列。

### 为什么它常用

因为很多函数根本不需要“拥有”字符串，它只需要：

- 看字符串内容；
- 读一小段子串；
- 做查找、比较、切片；
- 然后结束。

这时用 `string_view` 往往比用 `const std::string&` 还更灵活。

---

### 10.2.1 基本用法

#### 创建 `string_view`

```cpp
std::string s = "hello world";
std::string_view sv = s;
```

这里不会复制底层字符。

你也可以从字符串字面量创建：

```cpp
std::string_view sv = "hello";
```

或者只看其中一段：

```cpp
std::string_view sv = "abcdef";
auto sub = sv.substr(1, 3); // "bcd"
```

### 为什么说它很轻量

因为这些操作通常只是调整：

- 起始地址；
- 长度。

而不是重新分配一块新字符串。

### 常见成员函数

常见能力包括：

- `size()` / `length()`
- `empty()`
- `data()`
- `substr()`
- `remove_prefix()`
- `remove_suffix()`

例如：

```cpp
std::string_view sv = "abcdef";
sv.remove_prefix(2); // 现在看到的是 "cdef"
sv.remove_suffix(1); // 现在看到的是 "cde"
```

### 这一节最该建立的直觉

`string_view` 像一张“只读标签”：

- 标签上写着从哪里开始；
- 一共看多少个字符；
- 但它自己不拥有字符内容。

---

### 10.2.2 视图的生存期问题

这是 `string_view` 最关键的一节。

反复强调：

> `string_view` 不管理内存，所以一旦底层字符串没了，视图就悬空了。

#### 安全示例

```cpp
std::string s = "hello";
std::string_view sv = s;
```

只要 `s` 还活着，`sv` 就有效。

#### 危险示例

```cpp
std::string_view bad() {
    std::string s = "hello";
    return s;
}
```

这段代码的问题是：

- `s` 是局部变量；
- 函数返回时 `s` 被销毁；
- 返回出去的 `string_view` 仍然指向那块已经失效的内存。

也就是典型的**悬空视图**。

### 小白一定要背住的原则

> `string_view` 可以“借看”，但不能假装自己“接管了”底层字符串。

### 一个非常实用的经验

如果你不确定底层字符串能不能活得够久，那就不要返回 `string_view`。

特别是：

- 从局部 `string` 构造出来再返回；
- 从临时字符串对象里切出一段再返回；
- 把复杂表达式结果直接绑定到 `string_view` 上长期保存。

这些都要非常小心。

---

### 10.2.3 `string_view` 和 `string`

这一节很强调“接口设计”的视角。

#### 参数为什么常适合 `string_view`

如果函数只是读字符串，可以这样写：

```cpp
void print(std::string_view sv);
```

这有几个好处：

- 可以接 `std::string`；
- 可以接字符串字面量；
- 可以接字符数组；
- 也可以接另一个 `string_view`；
- 通常不需要额外分配和复制。

这比只写成：

```cpp
void print(const std::string& s);
```

更通用。

#### 返回值为什么要谨慎

参数常适合 `string_view`，但返回值不一定。

因为一旦返回 `string_view`，你就得保证：

- 它指向的底层字符在函数返回后仍然存在；
- 而且后续使用期间也不会失效。

如果这个保证做不到，宁可返回 `std::string`。

### 一句非常实用的结论

> **只读参数常优先考虑 `string_view`；返回值则要先想清楚生命周期。**

---

### 10.2.4 `string_view` 的哈希

顺带提到：标准库为 `string_view` 提供了哈希支持。

这意味着你可以把它用在：

- `std::unordered_set`
- `std::unordered_map`

这样的哈希容器里。

### 这一点说明了什么

说明 `string_view` 不只是一个“临时看字符串”的小工具，它已经被标准库认真纳入生态中。

但还是那句老话：

> 能放进哈希容器，不等于生命周期问题自动消失。

如果底层字符串失效，拿着这个键继续用仍然危险。

## 10.3 `span`

如果说 `string_view` 是“字符串的只读视图”，那么 `span` 可以理解成：

> 一段连续内存的视图。

它的覆盖范围更广，因为它不只面向字符串，还面向任意连续元素序列。

比如：

- 原生数组；
- `std::array`；
- `std::vector`；
- 某些连续存储的数据块。

### 为什么它很重要

很多函数其实只需要：

- 一段 `int`；
- 一段 `double`；
- 一段字节序列；

它根本不关心这段数据来自数组还是 `vector`。

这时候 `span` 就能把接口统一起来。

---

### 10.3.1 基本用法

#### 统一参数接口

```cpp
void printAll(std::span<const int> sp) {
    for (int x : sp) {
        std::cout << x << ' ';
    }
}
```

这个函数可以同时接：

```cpp
int a[] = {1, 2, 3};
std::vector<int> v = {4, 5, 6};

printAll(a);
printAll(v);
```

### 为什么这很有价值

因为以前你可能要写：

- 一个接数组的版本；
- 一个接 `vector` 的版本；
- 或者干脆写模板。

现在很多时候一个 `span` 参数就够了。

#### `span` 也可以修改底层数据

如果你写的是：

```cpp
void addOne(std::span<int> sp) {
    for (int& x : sp) {
        ++x;
    }
}
```

那么它改到的其实就是原始数据本身。

这再次说明：

> `span` 只是“看这段数据”的窗口，不是副本。

---

### 10.3.2 一些技术细节

这里会讲到 `span` 的几个关键细节。

#### 常见接口

`span` 支持很多像容器一样的操作：

- `begin()`
- `end()`
- `front()`
- `back()`
- `size()`
- `empty()`
- `data()`
- `operator[]`

所以用起来会很自然。

#### 动态长度 vs 固定长度

`span` 有两种典型形态：

```cpp
std::span<int> a;        // 动态长度
std::span<int, 5> b;     // 编译期固定长度
```

你可以先这样理解：

- 动态长度：运行时才知道长度；
- 固定长度：长度是类型的一部分。

#### 切片能力

 `span` 可以轻松取得子视图：

- `first(n)`
- `last(n)`
- `subspan(pos, count)`

例如：

```cpp
auto head = sp.first(3);
auto tail = sp.last(2);
auto mid = sp.subspan(1, 4);
```

这些操作通常仍然只是重新描述“看哪一段”，而不是复制内容。

### 这一节小白最该懂的事

`span` 和容器接口长得像，但它不是容器。

它没有“自己存数据”的责任，它只是：

- 指向一段连续区间；
- 记录这段区间多长；
- 让你安全、统一地访问它。

---

### 10.3.3 `gsl::span` 的性能问题

补充一点历史背景。

在标准库 `std::span` 出现前，很多项目会用 GSL 提供的 `gsl::span`。

但要注意：某些实现或某些历史环境下，`gsl::span` 可能会妨碍编译器做出最理想的优化。

### 对初学者该怎么理解

这一节你不必深挖编译器优化细节，只要记住：

- 现代标准里已经有 `std::span`；
- 如果环境支持，优先用标准库版本；
- 它和生态、工具链的配合通常更稳妥。

## 10.4 C++20 里的视图

这一节是本章最“现代 C++”的一部分。

前面的 `string_view` 和 `span` 主要是“对已有连续或字符串数据的轻量观察”。

而 C++20 的 `views` 更进一步：

> 它们把“数据处理过程本身”也变成了一种可组合、常常惰性求值的视图。

### 什么叫惰性求值

可以先这样理解：

- 它不会在你写下表达式时立刻把所有结果算完；
- 它更像是搭好了一个“处理管道”；
- 实际遍历时，元素才一个个经过这条管道。

这会让代码更优雅，也可能带来新的理解门槛。

---

### 10.4.1 映射

映射视图通常写成：

```cpp
auto v2 = v | std::views::transform([](int x) {
    return x * 2;
});
```

它并不一定立刻生成一个新的容器。

你可以把它理解成：

> 以后谁来遍历 `v2`，就会看到“把原始元素乘以 2 之后”的结果。

### 和第 9 章 `transform` 的关系

- 第 9 章 `std::transform`：通常是“把结果写到某个输出区间”；
- 这里的 `views::transform`：更像是“构造一个映射后的观察方式”。

两者目标相近，但风格不同。

---

### 10.4.2 过滤

```cpp
auto even = v | std::views::filter([](int x) {
    return x % 2 == 0;
});
```

这表示：

- 原始数据还是 `v`；
- 但通过 `even` 去看时，只会看到偶数元素。

### 这节的重点

它不会先新建一个“只装偶数的新数组”，而是：

> 当你遍历这个视图时，它会跳过不满足条件的元素。

这就是“惰性过滤”。

---

### 10.4.3 反转

```cpp
auto rev = v | std::views::reverse;
```

这表示“倒序观察”原数据。

重点是：

- 不一定复制数据；
- 不一定重新存储；
- 只是改变遍历视角。

这和“把整个容器复制一份再倒过来”完全不是一个成本级别。

---

### 10.4.4 键子元素

这里讨论的是关联容器上的视图操作，比如只看键、只看值。

你可以把它理解成：

```cpp
for (auto k : mp | std::views::keys) {
    ...
}

for (auto v : mp | std::views::values) {
    ...
}
```

这类写法的好处是：

- 你表达得更明确；
- 不必每次手写 `.first` / `.second`；
- 也更容易继续接后续管道。

---

### 10.4.5 管道和潜在的性能

这是非常重要的一节。

管道写法看起来很美：

```cpp
auto result = v
    | std::views::filter(pred)
    | std::views::transform(f)
    | std::views::reverse;
```

它把数据处理步骤写成了一条很清楚的流水线。

### 但重点是

惰性求值不等于永远更快。

因为它可能带来这些问题：

1. **重复遍历时重复计算**
   - 如果某个视图里的转换逻辑很贵；
   - 你又遍历它很多次；
   - 那每次遍历都可能重新做一遍。

2. **带副作用的变换会更难理解**
   - 如果 `transform` 里的 lambda 会打印、修改外部状态；
   - 那“什么时候执行”就变得没那么直观。

3. **调试体验可能更绕**
   - 因为中间结果不一定落地成容器。

### 小白最实用的建议

- 如果你只是做一次遍历，view 管道通常很优雅；
- 如果你要反复使用中间结果，有时把结果真正收集到容器里更合适；
- 不要在 `views::transform` 里塞很重的副作用逻辑。

---

### 10.4.6 其他视图

还有一些常见视图，用来帮助你建立“工具箱”的感觉。

例如：

- `iota`：生成一个数值序列视图；
- `take(n)`：只看前 n 个；
- `drop(n)`：跳过前 n 个；
- `take_while(pred)`：只看前面连续满足条件的部分；
- `join`：把嵌套范围拼接看成一个连续范围；
- `split`：按分隔符拆分视图。

### 你现在不必全背

学习阶段只要知道：

> C++20 的 view 生态是在帮你“按需观察、按需变换、按需组合数据”。

以后写得多了，自然会对哪些视图常用有感觉。

---

## 10.5 小结

本章的主线可以浓缩成四句话：

1. **视图通常不拥有数据**
   - 所以它们轻量、高效。

2. **不拥有数据也意味着要对生命周期负责**
   - 这是 `string_view` 最核心的风险。

3. **`span` 统一了连续内存区间接口**
   - 它让很多函数参数设计更简洁。

4. **C++20 views 把“数据处理过程”也做成了可组合的视图**
   - 但惰性求值既是优点，也可能带来理解和性能上的新问题。

如果只记一句话，那就是：

> 视图最大的价值是“借用而不是复制”，最大的风险是“借用对象必须还活着”。

## 关键术语表

| 术语 | 解释 |
| --- | --- |
| 视图 | 对已有数据的一层轻量观察或访问方式，通常不拥有数据。 |
| 非拥有 | 不负责管理底层对象的生存期和内存。 |
| 底层数据 | 视图真正引用的原始数据。 |
| 生存期 | 一个对象从创建到销毁的有效存在时间。 |
| 悬空视图 | 视图仍指向一块已经失效的数据区域。 |
| `string_view` | 只读字符串视图，常用于字符串参数和轻量切片。 |
| `substr()` | 取得子视图或子串的一种常见操作。 |
| `remove_prefix()` | 从前面缩短视图，不复制字符。 |
| `remove_suffix()` | 从后面缩短视图，不复制字符。 |
| `span` | 一段连续内存的视图。 |
| 连续内存 | 元素在内存里挨着存放。 |
| 固定长度 `span` | 长度是类型一部分的 `span`。 |
| 动态长度 `span` | 长度在运行期确定的 `span`。 |
| `subspan()` | 从原 `span` 中取出一段子视图。 |
| 惰性求值 | 实际遍历或使用时才计算，不立刻算完。 |
| 管道 | 用 `|` 串联多个视图适配器的写法。 |
| `views::filter` | 构造过滤视图，只暴露满足条件的元素。 |
| `views::transform` | 构造映射视图，按需变换元素。 |
