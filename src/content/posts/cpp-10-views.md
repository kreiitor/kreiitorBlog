## 视图不是容器

很多初学者看到 `string_view`、`span`、`views::filter(...)` 时，容易把它们当成「某种新容器」。容器拥有数据，视图只提供访问。

### 容器 vs 视图

| 对象 | 更像什么 |
| --- | --- |
| 容器 | 真正拥有数据的「仓库」 |
| 视图 | 站在仓库门口往里看的「窗口」 |

- 容器负责分配、持有和释放内存；
- 视图不拥有数据，只是对已有数据的一种轻量访问方式。

> 视图的优势来自「轻量」和「少拷贝」，风险也来自「不拥有数据」。

---

## 10.1 视图概述

视图有几个共同特点：

1. **不拥有底层数据**
2. **创建成本低**
3. **适合作为接口层的参数或中间结果**
4. **前提是底层数据仍然存活**

### 视图适用的场景

现实代码里有很多场景只是借用数据：

- 我只想读一个字符串，不想复制一份；
- 我只想把一个数组的一部分传给函数；
- 我只想按条件看一批元素，不想先创建新容器；
- 我只想把「处理流程」拼起来，而不是在每一步都落地成新对象。

现代 C++ 一直在强化这种 view 思路。

## 10.2 `string_view`

`std::string_view` 是最基础、也最常用的视图类型。它很像「字符指针 + 长度」的只读字符串视图。它不拥有字符内存，只指向某一段现有字符序列。

### 用途

很多函数不需要拥有字符串，只需要：

- 读取内容；
- 取一小段子串做查找、比较或切片。

这时用 `string_view` 往往比用 `const std::string&` 还更灵活。

---

### 10.2.1 基本用法

#### 创建 `string_view`

```cpp
std::string s = "hello world";
std::string_view sv = s;
```

这里不会复制底层字符。

你也可以从字符串字面量创建：

```cpp
std::string_view sv = "hello";
```

或者只看其中一段：

```cpp
std::string_view sv = "abcdef";
auto sub = sv.substr(1, 3); // "bcd"
```

### 轻在哪里

这些操作通常只调整起始地址和长度，不重新分配字符串。

### 常见成员函数

常用成员包括：

- `size()` / `length()`
- `empty()`
- `data()`
- `substr()`
- `remove_prefix()`
- `remove_suffix()`

例如：

```cpp
std::string_view sv = "abcdef";
sv.remove_prefix(2); // 现在看到的是 "cdef"
sv.remove_suffix(1); // 现在看到的是 "cde"
```

### 一张只读标签

`string_view` 像一张「只读标签」：标签上写着从哪里开始、一共看多少个字符，但它不拥有字符内容。

---

### 10.2.2 视图的生存期问题

> `string_view` 不管理内存，所以一旦底层字符串没了，视图就悬空了。

#### 安全示例

```cpp
std::string s = "hello";
std::string_view sv = s;
```

只要 `s` 还活着，`sv` 就有效。

#### 危险示例

```cpp
std::string_view bad() {
    std::string s = "hello";
    return s;
}
```

这段代码的问题是：

- `s` 是局部变量；
- 函数返回时 `s` 被销毁；
- 返回出去的 `string_view` 仍然指向那块已经失效的内存。

这是典型的**悬空视图**。

### 借看，不接管

> `string_view` 可以「借看」，但不能假装自己「接管了」底层字符串。

### 不确定时的选择

如果你不确定底层字符串能不能活得够久，那就不要返回 `string_view`。例如：

- 从局部 `string` 构造 `string_view` 再返回，或从临时字符串对象里切一段再返回；
- 把复杂表达式结果直接绑定到 `string_view` 上长期保存。

---

### 10.2.3 `string_view` 和 `string`

#### 参数用 `string_view`

如果函数只是读字符串，可以这样写：

```cpp
void print(std::string_view sv);
```

这有几个好处：

- 可以接 `std::string`；
- 可以接字符串字面量；
- 可以接字符数组；
- 也可以接另一个 `string_view`；
- 通常不需要额外分配和复制。

比只写：

```cpp
void print(const std::string& s);
```

更通用。

#### 返回值要谨慎

参数常适合 `string_view`，但返回值不一定。一旦返回 `string_view`，你就得保证：

- 它指向的底层字符在函数返回后仍然存在；
- 而且后续使用期间也不会失效。

如果这个保证做不到，宁可返回 `std::string`。

### 参数与返回值的分工

> **只读参数常优先考虑 `string_view`；返回值则要先想清楚生命周期。**

---

### 10.2.4 `string_view` 的哈希

标准库为 `string_view` 提供了哈希支持，可以把它用在：

- `std::unordered_set`
- `std::unordered_map`

### 哈希支持的含义

`string_view` 不只是临时查看字符串的小工具，标准库已经把它纳入生态。

> 能放进哈希容器，不等于生命周期问题自动消失。

如果底层字符串失效，拿着这个键继续用仍然危险。

## 10.3 `span`

`string_view` 是字符串的只读视图，`span` 则更进一步：

> 一段连续内存的视图。

它不只面向字符串，还面向任意连续元素序列。比如：

- 原生数组；
- `std::array`；
- `std::vector`；
- 某些连续存储的数据块。

### 统一接口的价值

很多函数只需要一段 `int`、`double` 或字节序列，并不关心数据来自数组还是 `vector`。这时候 `span` 就能把接口统一起来。

---

### 10.3.1 基本用法

#### 统一参数接口

```cpp
void printAll(std::span<const int> sp) {
    for (int x : sp) {
        std::cout << x << ' ';
    }
}
```

这个函数可以同时接：

```cpp
int a[] = {1, 2, 3};
std::vector<int> v = {4, 5, 6};

printAll(a);
printAll(v);
```

### 少写重载

以前要么为数组和 `vector` 各写一个版本，要么干脆写模板。现在很多时候一个 `span` 参数就够了。

#### `span` 也可以修改底层数据

如果写的是：

```cpp
void addOne(std::span<int> sp) {
    for (int& x : sp) {
        ++x;
    }
}
```

那么它改到的就是原始数据本身。

> `span` 只是「看这段数据」的窗口，不是副本。

---

### 10.3.2 一些技术细节

#### 常见接口

`span` 支持很多像容器一样的操作：

- `begin()`
- `end()`
- `front()`
- `back()`
- `size()`
- `empty()`
- `data()`
- `operator[]`

#### 动态长度 vs 固定长度

`span` 有两种典型形态：

```cpp
std::span<int> a;        // 动态长度
std::span<int, 5> b;     // 编译期固定长度
```

区别在长度何时确定：

- 动态长度：运行时才知道长度；
- 固定长度：长度是类型的一部分。

#### 切片能力

`span` 可以轻松取得子视图：

- `first(n)`
- `last(n)`
- `subspan(pos, count)`

例如：

```cpp
auto head = sp.first(3);
auto tail = sp.last(2);
auto mid = sp.subspan(1, 4);
```

这些操作通常仍然只是重新描述「看哪一段」，而不是复制内容。

### 像容器，但不是容器

`span` 和容器接口长得像，但它不是容器。它没有自己存数据的责任，只指向一段连续区间、记录长度，让你安全、统一地访问。

---

### 10.3.3 `gsl::span` 的性能问题

在标准库 `std::span` 出现前，很多项目会用 GSL 提供的 `gsl::span`。某些实现或历史环境下，它可能妨碍编译器做出最理想的优化。

### 优先标准库版本

现代标准已经有 `std::span`；环境支持时优先用标准库版本，它和生态、工具链的配合通常更稳妥。

## 10.4 C++20 里的视图

`string_view` 和 `span` 主要是对已有字符串或连续数据的轻量观察。C++20 的 `views` 更进一步：

> 它们把「数据处理过程本身」也变成了一种可组合、常常惰性求值的视图。

### 惰性求值

写表达式时不会立刻算完所有结果，而是先搭好一条「处理管道」，遍历时元素才一个个经过。代码会更简洁，理解门槛也可能更高。

---

### 10.4.1 映射

映射视图通常写成：

```cpp
auto v2 = v | std::views::transform([](int x) {
    return x * 2;
});
```

它并不一定立刻生成一个新的容器。遍历 `v2` 时，才会看到「把原始元素乘以 2 之后」的结果。

### 和第 9 章 `transform` 的关系

- 第 9 章 `std::transform`：通常是把结果写到某个输出区间；
- 这里的 `views::transform`：更像是构造一个映射后的观察方式。

两者目标相近，但风格不同。

---

### 10.4.2 过滤

```cpp
auto even = v | std::views::filter([](int x) {
    return x % 2 == 0;
});
```

这表示原始数据还是 `v`，但通过 `even` 去看时，只会看到偶数元素。

### 惰性过滤

它不会先建一个只装偶数的新数组：遍历视图时，才跳过不满足条件的元素。这种模式叫「惰性过滤」。

---

### 10.4.3 反转

```cpp
auto rev = v | std::views::reverse;
```

这表示「倒序观察」原数据。它只是改变遍历视角，不一定复制或重新存储数据。这和「把整个容器复制一份再倒过来」完全不是一个成本级别。

---

### 10.4.4 键子元素

关联容器可以只看键或只看值。写法：

```cpp
for (auto k : mp | std::views::keys) {
    ...
}

for (auto v : mp | std::views::values) {
    ...
}
```

这类写法的好处是：表达更明确，不必每次手写 `.first` / `.second`；后续管道也更容易接。

---

### 10.4.5 管道和潜在的性能

管道写法很直观：

```cpp
auto result = v
    | std::views::filter(pred)
    | std::views::transform(f)
    | std::views::reverse;
```

它把数据处理步骤写成了一条很清楚的流水线。

### 惰性不等于更快

惰性求值并不保证更快。它可能带来这些问题：

1. **重复遍历时重复计算**
   - 如果转换逻辑很贵，又遍历很多次，每次遍历都可能重做一遍。

2. **带副作用的变换会更难理解**
   - 如果 `transform` 里的 lambda 会打印或修改外部状态，「什么时候执行」就变得没那么直观。

3. **调试体验可能更绕**
   - 因为中间结果不一定落地成容器。

### 管道的取舍

- 只做一次遍历时，view 管道通常够用；要反复使用中间结果，把结果收集到容器里有时更合适。
- 不要在 `views::transform` 里塞很重的副作用逻辑。

---

### 10.4.6 其他视图

还有一些常见视图：

- `iota`：生成一个数值序列视图；
- `take(n)`：只看前 n 个；
- `drop(n)`：跳过前 n 个；
- `take_while(pred)`：只看前面连续满足条件的部分；
- `join`：把嵌套范围拼接看成一个连续范围；
- `split`：按分隔符拆分视图。

### 学到什么程度

学习阶段只要知道：

> C++20 的 view 生态解决的是按需观察、变换和组合数据的问题。

用得多了，自然会知道哪些视图常用。

---

## 10.5 小结

四条主线：

1. **视图通常不拥有数据**
   - 所以它们轻量、高效。

2. **不拥有数据也意味着要对生命周期负责**
   - 这是 `string_view` 最核心的风险。

3. **`span` 统一了连续内存区间接口**
   - 它让很多函数参数设计更简洁。

4. **C++20 的 views 把「数据处理过程」也做成了可组合的视图**
   - 但惰性求值既是优点，也可能带来理解和性能上的新问题。

> 视图最大的价值是「借用而不是复制」，最大的风险是「借用对象必须还活着」。

## 关键术语表

| 术语 | 解释 |
| --- | --- |
| 视图 | 对已有数据的一层轻量观察或访问方式，通常不拥有数据。 |
| 非拥有 | 不负责管理底层对象的生存期和内存。 |
| 底层数据 | 视图真正引用的原始数据。 |
| 生存期 | 一个对象从创建到销毁的有效存在时间。 |
| 悬空视图 | 视图仍指向一块已经失效的数据区域。 |
| `string_view` | 只读字符串视图，常用于字符串参数和轻量切片。 |
| `substr()` | 取得子视图或子串的一种常见操作。 |
| `remove_prefix()` | 从前面缩短视图，不复制字符。 |
| `remove_suffix()` | 从后面缩短视图，不复制字符。 |
| `span` | 一段连续内存的视图。 |
| 连续内存 | 元素在内存里挨着存放。 |
| 固定长度 `span` | 长度是类型一部分的 `span`。 |
| 动态长度 `span` | 长度在运行期确定的 `span`。 |
| `subspan()` | 从原 `span` 中取出一段子视图。 |
| 惰性求值 | 实际遍历或使用时才计算，不立刻算完。 |
| 管道 | 用 `|` 串联多个视图适配器的写法。 |
| `views::filter` | 构造过滤视图，只暴露满足条件的元素。 |
| `views::transform` | 构造映射视图，按需变换元素。 |
