前五章里，Agent 与世界的交互一直是"轮流"的：用户说完一句，Agent 想一段、调用几个工具，再回一句，在它思考的这段时间里世界被默认为静止。第一章提过一个论断，在底层模型固定时，提升 Agent 任务表现最主要的系统工程手段，往往是重新定义或扩展观察空间与动作空间。这一章要挑战的正是"世界在 Agent 思考时静止"这个前提，把两个空间沿另外两个方向扩展：**模态**与**触发时机**。第二至五章扩展的是这两个空间的内容，本章扩展的是模态（语音、屏幕、物理传感器；说话、点击、关节运动）与时机（世界主动推送、连续流；跨回合、可打断、可抢占）。四档时间尺度把这两根轴串成一条线，秒到天对应异步与事件驱动，10 毫秒到 1 秒对应语音，亚秒到秒对应 Computer Use，毫秒对应机器人；6.2 沿时机轴走到最长的一端，6.3 转到毫秒级的语音交互，6.4 把同一个闭环搬到二维屏幕，6.5 推到物理世界的机器人操作，6.6 收束出四节共享的一条控制骨架和一组原语。本章也是"构建 Agent"这一部分的最后一块，接下来第七章回答如何判断系统构建得对不对，第八章讨论如何通过后训练更新模型参数，第九章把运行轨迹、评估与多种更新载体组织成持续进化闭环，第十章转向多 Agent 协作。

## 6.1 模态与触发时机的扩展

把观察空间和动作空间摊开，会发现它们各有两个可以扩展的方向。**模态**决定观察和动作的形式：Agent 是只读文本，还是也能听见声音、看见屏幕、感知力矩；是只能输出 token，还是也能发声、点击、驱动关节。**触发时机**决定观察和动作的节奏：观察是 Agent 主动去取，还是世界主动推来；动作是必须在一个回合内做完，还是可以跨越回合、中途被打断、被更紧急的事抢占。

前五章解决的是这两个空间的内容，这一章动的是它们的模态和时机：

| | 观察空间的扩展 | 动作空间的扩展 |
| --- | --- | --- |
| 内容（第二至五章） | 上下文工程、记忆与知识库 | 工具、代码生成 |
| 模态（本章） | 语音、屏幕、物理传感器 | 说话、点击、关节运动 |
| 时机（本章） | 世界主动推送、连续流 | 跨回合、可打断、可抢占 |

回合制只是模型与接口之间的一种交互约定，环境本身并没有这种性质。早期工具调用接口通常按同步轮次组织消息：提问后面跟着回答，工具调用之后先补齐结果，再继续推理。真实环境不会这样配合：邮件在模型思考时到达，用户在它说到一半时插话，页面在两次截图之间已经变了样，杯子在机械臂伸手的途中被碰倒。

这个约定也正在改变。截至 2026 年 9 月，GPT-6 Astra 已经提供原生异步工具调用和回合中途追加用户指令的能力，所以本章同时讨论原生支持与兼容既有同步接口的两条路线。四档时间尺度上，观察侧与动作侧各自的变化如下：

| 尺度 | 场景 | 观察侧的变化 | 动作侧的变化 |
| --- | --- | --- | --- |
| 秒—天 | 异步与事件驱动 | 会被外部事件主动唤醒的 Agent | 动作跨回合：先发起，后续靠事件收尾 |
| 10 毫秒—1 秒 | 语音 | 边说边听，不等一句说完 | 边想边说，可被打断 |
| 亚秒—秒 | Computer Use | 屏幕在两帧之间持续变化 | 动作后必须重新确认现实是否仍符合计划 |
| 毫秒 | 机器人 | 传感器连续回流 | 动作分块：一次规划一小段，可被抢占 |

补充：① OpenAI, "Async tool calling"; "Using GPT-6 Astra"，核对日期：2026-09-05。② OpenAI, "Mid-turn steering"，核对日期：2026-09-05。

第一章的两根轴（观察空间、动作空间）各自是三维的，三个维度分别是内容、模态、时机。前五章解决内容，本章解决模态加时机。这也解释了本章四个场景看起来跨了好几个领域，却能被塞进同一章的原因：它们是同一件事在不同时间尺度上的投影。

"回合制是交互约定"这句话值得多停一会。它是早期 API 为了工程上简单而做的妥协，一问一答、工具调用必须配对。妥协本身没错，但它悄悄把"世界静止"当成了前提。一旦把模型放进真实世界，有别人发来的邮件、有正在变的页面、有会倒的杯子，这个前提就崩了。

第二张表里还藏着一个规律：时间尺度越短，环境变化给 Agent 的压力越大。秒到天级别，环境是事件式变化的，Agent 只要不错过事件就行；10 毫秒级，话还没说完就得决定要不要接话；亚秒级，屏幕在你点完之后可能已经不一样了；毫秒级，机械臂的动作必须切成小块，因为没法在单次推理里等完一整套动作。6.2 到 6.5 四节就是逐级下压时间尺度来展开的，读的时候心里揣着这根刻度尺会顺很多。

至于走兼容同步接口还是原生异步，取决于你手上模型与协议的能力边界，谈不上学理上的优劣。模型或 API 不支持工具挂起，你只能在自己这一层（事件队列、任务句柄、占位符）把异步语义翻译成同步格式；模型原生支持了，事件来源、工具生命周期与结果归属仍然要自己管。这一点 6.2.7 与 6.2.8 会反复展开。

模态扩展与时机扩展容易混。语音表面上像模态，多了声音这个通道，但 6.3 反复强调的其实是时机：边说边听、边想边说、可被打断。判断方法是问一句，变的是用什么通道，还是什么时候发生。另一处容易含糊的是"回合制"到底属于模型还是接口，这里明确说它是模型与接口的一种交互约定，所以同一个模型用不同协议包起来，交互节奏可以完全不同。

本章把观察与动作空间沿"模态（用什么通道）"和"时机（什么时候发生）"两根轴扩展，其中时机轴从秒—天一路压到毫秒；"世界在 Agent 思考时静止"只是一个接口约定，不是现实。

## 6.2 异步与事件驱动：当世界主动找上门

第四章讨论的感知、执行、协作三类工具都由 Agent 主动调用，那么 Agent 怎么响应随时可能到达的外部事件？这需要**事件驱动的异步架构**来支撑。第一章五类工具里剩下的两类，事件触发工具与用户沟通工具，正是依托这一架构发挥作用的，所以放在本节一并讨论。这一节模态没有变化，仍然是文本，变的只有时机，它是从前五章的回合制世界迈出的第一步。

这一节在全章里充当长时段那一端：秒到天。异步排在最前面，是因为它的变化最便宜，不需要新模态、不需要新硬件，只改交互节奏；但它对架构的冲击最大，回合制的假设一旦松掉，队列、优先级、取消、恢复全都要设计。这里的工具分类脉络也值得留意：第一章把工具分成五类，第四章只讲了感知、执行、协作三类（都是 Agent 主动调的），本章补上事件触发工具与用户沟通工具这两类。先讲主动调用、再讲被动触发这个顺序是有意的，不理解主动工具，就看不出被动工具多了什么。

本节结构上先讲为什么需要异步（6.2.1），再以 OpenClaw 为样本看事件驱动机制的实现（6.2.2），然后依次介绍事件触发工具（6.2.3）、用户沟通工具（6.2.4）、虚拟身份与隔离执行环境（6.2.5），最后讨论事件处理机制（6.2.6）、不支持原生异步时的兼容方案（6.2.7）与模型原生异步（6.2.8），并收在"从能接收异步消息到可靠处理异步任务"（6.2.9）。

6.2 不动模态、只动时机：把"Agent 主动去取"换成"世界主动推来"，为此需要一类全新的架构，也就是事件驱动。

### 6.2.1 为什么需要异步

先用一个比喻说明为什么需要异步。同步（Synchronous）意味着"做完一件事才能做下一件"，异步（Asynchronous）意味着"多件事可以同时进行"。传统的同步 Agent 架构像一个只会排队的柜台，每次只能处理一个顾客，处理完才能叫下一个号；真正智能的助手更像一个灵活的秘书，桌上摆着多个待处理的事项（邮件、电话、来访者），秘书根据紧急程度决定先处理哪个，处理到一半如果有更紧急的事情也可以暂停切换。

在同步模式下，Agent 要么等后台任务完成才能与用户对话，要么等对话结束才能处理新到达的事件，没法应对真实助理场景所需的几项核心能力：异步执行是常态，许多任务需要长时间运行，不应阻塞用户交互；事件优先级要动态判断，不是所有事件都同等重要，Agent 需要智能地选择处理策略，取消当前操作（紧急）、加入队列（常规）还是并行处理（独立的轻量级查询）；中断和恢复要流畅，被打断的对话或任务应该能够自然恢复。

把异步范式用到 LLM 上时，需要先检查模型和 API 是否支持这种消息时序。有些接口要求先补齐工具结果才能继续；有些已经允许工具挂起、模型继续工作，并在生成过程中接受用户更新。前者需要事件队列、任务句柄和兼容层，后者可以直接使用原生异步协议。两者都仍需要应用管理事件来源、工具生命周期与结果归属，不能仅凭代码用了 asyncio，就认定模型也具备原生异步能力。

柜台模型的隐含成本很少体现在"慢"上，真正的问题是它把等待变成了唯一选项：顾客必须等后台任务结束，或者后台任务必须等对话结束。秘书模型的关键也不在于更快，而在于有了一个可排序的待办池。有了池子，才谈得上优先级、抢占、恢复。

这里列举的三项能力其实是异步架构的三张验收单：长任务不阻塞交互，靠的是任务与对话解耦；动态优先级，靠的是事件建模加路由器；中断后可恢复，靠的是轨迹与状态可续接。6.2.6 讲的三种处理策略正好对应第二项，6.2.7 的五条规则对应第一项和第三项。

这里有一个很容易踩的坑，这里专门点了名：用了 asyncio 不等于模型支持原生异步。asyncio 只是你程序内部的并发工具；如果模型 API 要求工具调用必须配对结果才能继续，那么你在自己程序里再并发，模型看到的序列仍然是同步的，中间还得靠占位符圆场。判断标准要看协议与模型的组合，跟你代码里有没有 `async` 无关。

为此需要事件驱动的异步 Agent 架构。技术上，这意味着系统不再主动地反复检查"有没有新消息"，那叫**轮询**，效率低；而是在新消息到达时自动触发处理逻辑。所有的输入、输出、思考过程和外部交互都被统一建模为**事件流**，也就是一条时间线上依次排列的事件记录。图 6-1 给出了事件驱动异步 Agent 的整体架构，展示事件源、事件队列与 Agent 处理流程之间的关系。

"事件流"这个词的定义要记准：所有输入、输出、思考过程和外部交互都被统一建模为一条时间线上依次排列的事件记录。这句话是后面所有设计（事件队列、结构化事件、轨迹追加）的前提，只有进了这条线，才谈得上排序与消费。

同步与异步说的是时序语义，串行与并行说的是执行体是否真的同时在跑，属于实现方式。所以"兼容同步接口"的运行时完全可以并行执行多个工具，实验 6-2 就是，只是送给模型的轨迹看起来仍是同步配对的样子。轮询与事件驱动的区别则在谁先动：轮询是系统主动反复去问"有没有新消息"，事件驱动是新消息到达时自动触发处理逻辑，这里对轮询的评价是效率低，这也是 6.2.2 批评 Heartbeat 只能定时检查的原因。

一句话收在这里：同步是"做完一件才能做下一件"，异步是"多件事同时进行"；要做到后者，必须把一切输入输出统一建模为事件流，并让新消息到达时自动触发处理，而不是靠轮询。

### 6.2.2 OpenClaw 的事件驱动机制实现

开源框架 OpenClaw 通过 Gateway 控制平面接收多渠道消息并路由到 Agent 运行时，它提供了三种内置的事件驱动机制。Hooks（事件钩子）响应 Agent 生命周期中的事件，如会话创建、重置等，类似 GitHub Actions 中的事件触发器。Cron（定时调度器）按 cron 表达式（Unix 系统广泛使用的定时任务语法，如 `0 9 * * 5` 代表每周五上午 9 点）执行周期性任务。Heartbeat（心跳守护进程）每隔 N 分钟唤醒一次 Agent，检查是否有需要关注的事项。

这三种机制赋予了 OpenClaw Agent"自主"的外观，即使用户不在线，Agent 也能定时生成报告、检查系统状态、处理例行事务。但 Gateway 对内置渠道（如 IM、Web 界面）的消息本身就是推送式的，消息一到就路由给 Agent；三种自动化机制里，真正让 Agent 在没有用户消息时"自己动起来"的只有 **Cron 和 Heartbeat**，而它们都是时间驱动的。Heartbeat 每隔固定间隔检查一次，Cron 按预设时间触发，Hooks 的事件来源是 OpenClaw 框架内部，不在外部世界。

短板落在第三方事件源上：一封新邮件到达、一个外部 API 回调推送、一个紧急通知需要立即处理，OpenClaw 缺乏即时接入的通道，Agent 无法在事件发生后立即做出响应，只能等到下一个 Cron/Heartbeat 周期才可能察觉。这种延迟在许多场景下不可接受。

以 PineClaw（Pine AI 的 OpenClaw 插件）为例。Pine AI 是一款代替用户拨打真实电话的 AI 助手，典型场景包括协商账单、取消订阅和处理保险理赔。用户通过 OpenClaw Agent 发起一个 Pine 电话任务后，Pine 的语音 AI 会代表用户拨打电话，但通话过程中可能随时需要用户介入：客服要求验证账户持有人身份时，Pine 需要用户立即提供安全码或 OTP（一次性密码）；客服要求与账户持有人直接对话时，Pine 需要用户在几秒内接听电话；协商到关键节点（如对方提出降价方案）时，Pine 需要用户确认是否接受。如果依靠 Heartbeat 的定时轮询，用户可能在客服等待验证码时迟迟收不到通知，导致客服挂断、通话失败。

PineClaw 的解决方案是引入 **Channel 机制**，在 OpenClaw 的 Gateway 和 Pine API 之间建立实时的事件通道。电话接通、需要用户输入、通话结束等关键事件发生时，消息被即时推送到 OpenClaw Agent，Agent 立即处理并通知用户。

这个案例揭示了事件驱动架构对 Agent 框架的核心价值：真正的"主动服务"不仅需要 Agent 能定时检查事件，更需要事件能主动通知 Agent。将所有输入（用户消息、工具返回、外部回调、定时触发）统一建模为事件流，通过事件循环驱动 Agent 的思考和行动，是实现这一目标的架构基础。在这一架构之下，下面先介绍两类与事件直接相关的工具（事件触发工具、用户沟通工具），以及支撑 Agent 独立行动的虚拟身份与隔离执行环境，再讨论事件处理机制的具体设计。

这一小节的论证结构很值得学：先肯定能力，再指出能力的天花板。OpenClaw 三种机制让 Agent 看起来"自主"，这里随即把"自主"拆成两类，时间驱动（Cron、Heartbeat）与事件驱动（Channel）。前者是"我定期去看有没有事"，后者是"有事的时候有人来叫我"。区别落在延迟的分布上：定时轮询的延迟是"最多等一个周期"，事件推送的延迟是"几乎立即"。PineClaw 的例子就是在说明，在"客服在等验证码"这种场景下，"最多等一个周期"等于失败。

三者的分工可以这样记：Hooks 管框架内部生命周期（会话创建、重置），Cron 管按日历触发，Heartbeat 管固定间隔巡查。它们的共同点是事件来源都不在外部世界，Hooks 来自框架内部，另两个来自时间。缺的那一块正好是"外部世界主动敲门"，也就是 Channel 补上的位置。

工程上的启示：如果你的 Agent 框架只有 Cron/Heartbeat，它对"第三方的、突发性的、需要秒级响应的"事件天生不敏感。补救办法应是给事件源接一条推送通道；把 Heartbeat 的间隔调到 1 秒既浪费算力，延迟也还在。

顺带留意 cron 表达式的读法。给出的 `0 9 * * 5` 是"分 时 日 月 星期"五段，分钟=0、小时=9、星期=5（周五），即每周五上午 9 点。读 cron 时最容易出错的就是"星期"字段的取值起点，不同实现有 0 或 1 起算的差异，实战中要对着具体实现确认，这一点这里未展开。

时间驱动与事件驱动的判断方法很简单，问一句："如果事件发生了但没有到下一个周期，Agent 多久能知道？"Heartbeat/Cron 是到点去看，Channel/PineClaw 是有事被叫。另一处别读错的是内置渠道的推送：Gateway 对 IM、Web 这些渠道本来就是推送式的，这一块不是短板，短板在内置渠道之外的第三方事件源，不能把"消息一到就路由给 Agent"当成"OpenClaw 已经全事件驱动"。

OpenClaw 的 Hooks/Cron/Heartbeat 都只能让 Agent"定时去看"，只有 Channel 这类机制才能让外部世界"主动来叫"。主动服务既要 Agent 能定时检查，也要事件能主动通知 Agent。

### 6.2.3 事件触发工具

事件触发工具是外部事件驱动 Agent 行动的入口。没有它们，Agent 只能连续循环思考、调用工具，最后输出一个结果，然后等待用户的下一步输入。要让世界的变化转化为 Agent 可以处理的事件，常见的事件触发工具有三类。

**定时器（`set_timer`）**处理依赖物理时间的事件。发送了一封邮件但对方没有回复，那么过一段时间应该再发一封邮件询问进展；打了一个电话但对方不在工作时间内，那么需要到下一个工作时间再尝试拨打。OpenClaw、Claude Code 等工具都支持定时器工具，在指定的物理时间唤醒自己。一次性定时器用于有明确时间点的任务：用户要求"给银行房贷部门打电话问办理进展"，当前是周六，Agent 就设置"下周一上午 10:00 致电银行"，定时器触发后自动拨打。循环定时器用于周期性的任务，比如每小时检查一次服务器健康状况；此外，一些外部服务不支持主动推送进展，只能主动查询进展，此时就需要用循环定时器定时反复查询。上一节 OpenClaw 的 Heartbeat 正是这种机制的系统化实现，也是 OpenClaw 具备"主动服务"能力的根源。

**后台任务监控（`monitor_shell`）**处理来自异步执行的工具或命令行任务的事件。一些命令行任务需要长时间在后台执行，Agent 需要监控执行进展。让 Agent 不断"盯着命令行看"、不断调用工具查询当前进展，会浪费太多的 token；等命令行任务完全执行结束后再让 Agent 开始思考和行动，Agent 又无法及时发现执行过程中的严重问题，甚至在命令行卡死的情况下无法介入，导致整个任务停滞。Claude Code 解决这个问题的方法是引入 monitor（监控）工具，允许 Agent 监控命令行的新增输出，或者包含特定关键词的输出。

**外部事件通道（`connect_channel`）**把新邮件到达、API 回调、IM 消息等外部事件实时推送给 Agent，上一节 PineClaw 的 Channel 机制就是典型实现。

设计层面，事件触发工具应定义清晰的触发条件和过滤规则，避免无关事件唤醒 Agent 浪费算力；事件载荷（payload）应包含足够的上下文信息，减少 Agent 被唤醒后还需要额外查询的次数。

三类工具对应三种"世界变化"的来源，一句话就能分开：`set_timer` 对应时间本身的变化（到点了），`monitor_shell` 对应 Agent 自己发起的任务的进展（我让你跑的东西有动静了），`connect_channel` 对应纯外部世界的变化（别人或别的系统找上门）。它们必须同时存在的原因也在这里：只用定时器，Agent 对突发外部事件失明；只用外部通道，Agent 无法安排"过两天再问一次"。

`monitor_shell` 的设计动机是一道双向的成本题：频繁轮询浪费 token，完全不看则错过问题和卡死。监控工具给出的折中是只在有新增输出、或输出里出现指定关键词时才唤醒 Agent，这其实就是把轮询换成过滤后的推送。这个思路在工程上非常常用：把判断放在被监控端做，那里廉价；让昂贵的模型每次都去看，代价立刻上去。

设计层面的两条要求（触发条件与过滤规则、载荷带足上下文）看起来平淡，却是事件驱动系统最容易翻车的地方。事件粒度过粗，Agent 被无意义地反复唤醒，成本炸掉；载荷太薄，Agent 每次醒来都要额外查一圈，等于把服务端该做的事推给了模型。可以把它类比成告警系统设计，告警规则要准，告警内容要自带现场信息。

一次性定时器和循环定时器的分工要分清：前者针对有明确时间点的任务（下周一 10:00 致电），后者针对周期性的、或只能主动查询的任务（每小时查服务器健康、反复查询不推送进展的外部服务）。这里那句"一些外部服务不支持主动推送进展，只能主动查询进展"意味着这类场景只能用循环定时器兜住。`monitor_shell` 与轮询的区别也在这里：两者都能拿到命令行进展，但前者由新增输出或关键词触发，后者由 Agent 的固定节奏触发。

事件触发工具把世界的变化变成 Agent 能处理的事件：定时器管"到点了"，后台监控管"我派出去的任务有动静了"，外部事件通道管"别人找上门了"。

### 6.2.4 用户沟通工具

用户沟通工具是为了适应 Agent 与用户之间日益多元的沟通渠道而产生的。

许多 Agent（如 Claude Code、Manus）采用原生 ReAct 循环，Agent"说"的所有话（即 assistant 消息）都直接发送给用户，用户必须在应用中打开指定的会话才能与 Agent 对话。用户在会话中往往可以看到 Agent 调用工具的过程。

OpenClaw 打破了这一人机沟通范式。用户无需感知会话的存在，也无需关心 Agent 调用工具的细节；用户和 Agent 都可以随时给对方发送消息，不再是一问一答的严格轮次。因此很多人评价 OpenClaw 具备"活人感"，就像一个秘书一样通过文本消息与用户异步沟通。OpenClaw 并不直接把模型输出的 assistant 消息呈现给用户，而是使用专门的工具发送消息，这些消息还可以附带图片和文件，并可根据紧急程度附加推送提醒。

除了文本方式，越来越多的 Agent 具备多模态沟通能力，例如发送结构化卡片消息、发送提醒邮件。一些 Agent 已经开始尝试生成式 UI（Generative UI），即使用 HTML 等方式生成交互式界面，以更友好的方式向用户展示信息。

设计层面，用户沟通工具应支持异步消息模式（用户不一定在线），提供已读/未读状态追踪，并在多渠道场景下保持消息的一致性。

多渠道的用户沟通与召回。Agent 的响应不应局限于单一渠道，通知机制同时也是用户召回机制。消息发送扩展到即时通讯、短信、邮件、电话、推送等多种渠道，Agent 根据紧急程度、用户状态、内容性质、用户偏好综合决定渠道的选择，既保证不错过重要的消息，又避免重复打扰。对于长时间运行的任务，Agent 需要在完成时主动通知用户，召回用户的注意力；对于定期性的任务（如每日总结、周报），通知可以帮助用户建立固定的交互习惯。

用户沟通工具解决了"如何触达用户"。Agent 以什么身份出现在这些渠道上、在什么环境中代表用户执行操作，还需要一层身份与环境的基础设施，这就是下一节的主题。

这一节的核心变化是消息不再等于模型输出。在原生 ReAct 循环里，Agent 说的每句话本身就是 assistant 消息，等于把模型的生成过程直接暴露给用户；OpenClaw 用专门的工具去发消息，意味着"对用户说话"变成了一个被 Agent 主动选择的动作。什么时候说、说什么、附带什么附件、要不要加推送提醒，全都变成可控决策，不再只是生成过程的副产品。

"活人感"这个评价之所以成立，是因为异步双向沟通更接近人类用 IM 的方式：双方各自有空就发，不必卡在一问一答的轮次里。这也意味着 Agent 有了主动开口的能力，任务完成了主动汇报、例行事务主动汇报，不必永远等用户来问。这里把这一点点名为用户召回机制：通知不只是告知，它还在把用户的注意力拉回来。

渠道选择是个多目标优化，既要不错过重要消息（召回率），又要避免重复打扰（精确率与打扰成本）。这里给出的四个判断维度，紧急程度、用户状态、内容性质、用户偏好，可以理解成选渠道的四个输入特征。落到自己的 Agent 上，可以写成一条简单规则：越紧急、用户越可能不在电脑前，越要选强打扰渠道（电话、推送）；越不紧急、内容越长，越适合弱打扰渠道（邮件）。这条规则是工程直觉，这里只给了判断维度。

设计层面的三条要求也值得记：异步消息模式，用户不一定在线，所以消息必须能落库、能补送；已读/未读追踪，Agent 知道用户是否已经看到，才能决定要不要换渠道再通知一次；多渠道消息一致性，同一条消息在多个渠道之间的状态要统一，否则会出现"在邮件里回了、Agent 又在 IM 里问一遍"。

assistant 消息与工具发送的消息要分开看：前者是模型输出的直接呈现，也是原生 ReAct 循环的做法；后者是 Agent 调用沟通工具的显式动作，是 OpenClaw 的做法。区别在于后者可以选择渠道、附件、提醒级别，并且不需要用户打开某个会话。触达用户与用户召回也不是一回事，这里说"通知机制同时也是用户召回机制"，触达强调消息送到，召回强调把用户的注意力拉回到任务上，后者解释了为什么长时间运行的任务完成时要主动通知。

用户沟通工具把"对用户说话"从模型输出的副产物变成 Agent 的一个显式动作：可以选渠道、带附件、加提醒，既能异步触达，也承担把用户注意力召回来的职责。

### 6.2.5 虚拟身份与隔离执行环境

第四章开头以《Her》中的 Samantha 为例，说明 Agent 如何借助工具与真实数字世界交互。要实现这样的通用助理，会先撞上一个关键的架构选择：Agent 应该直接管理用户的个人账号，还是拥有自己的虚拟身份？直接管理看似便捷，但一旦 Agent 出现错误或被攻破，用户的全部数字身份将会暴露。更稳妥的方案是赋予 Agent 一套**独立的虚拟身份**，如同秘书拥有自己的办公电话和邮箱。这套虚拟身份包括专属的通讯账号、存储空间、计算环境，使 Agent 能以透明的身份代表用户工作。身份的明确性不仅没有削弱信任，反而增强了沟通的真实性。

虚拟身份需要部署在**隔离的执行环境**中。虚拟电脑（VM/容器）和虚拟手机（Android 模拟器）为 Agent 提供操作系统级的隔离和完整的桌面/移动操作能力，理由有三条。虚拟电脑可以全天候运行，不受用户设备联网状态的影响，也不影响用户正在操作的应用；即使 Agent 执行了错误操作，最多也只会导致虚拟环境崩溃，不会影响用户的真实设备；隔离环境还可以防止 Agent 随意访问用户的本地文件，提高安全性。

独立身份也带来两个现实挑战。**反机器人机制**：许多网站用 CAPTCHA 和 IP 信誉检测拦截自动化访问，使用数据中心 IP 的虚拟环境很容易被识别，实践中往往需要配置住宅代理网络（使用真实家庭 IP）才能正常访问。访问用户真实账号的场景：当任务必须以用户本人的身份登录时，应采用 Human-in-the-Loop 认证，通过 VNC/RDP 远程桌面让用户在可视化环境中亲自完成登录。用户能看到 Agent 正在操作的完整界面，理解为什么需要认证；认证后的会话令牌可以在有效期内复用，避免频繁打断用户，在自主性与安全性之间取得平衡。

Agent 与虚拟环境之间的数据交换通过共享文件系统完成：以卷挂载的方式（如 `/workspace/shared`）连接 Agent、虚拟电脑和虚拟手机，数据以文件路径引用的方式传递，内容本身不拷进对话，避免占用上下文窗口。以一个数据分析任务为例，用户上传 CSV 文件到共享目录，虚拟电脑中的 Agent 读取文件、执行分析、生成图表并保存回共享目录，Agent 只需将图表的文件路径返回给用户，各方之间传递的始终只是轻量级的路径字符串。

事件触发工具让世界能够唤醒 Agent，用户沟通工具让 Agent 能够触达用户，虚拟身份与隔离执行环境让 Agent 能以独立、可审计的身份行动。剩下的问题是：当多个事件同时涌向同一个 Agent 实例时，应该如何处理？

身份这件事常被当成合规问题，但这里把它放进了架构讨论，理由是它决定了信任边界与爆炸半径。用秘书类比很好懂：一个称职的秘书有自己的分机号和邮箱，客户知道"这是某某的秘书"，出错了也只影响秘书的账号，不会把老板的身份证、银行卡一起交出去。"身份的明确性不仅没有削弱信任，反而增强了沟通的真实性"是这里的判断，值得原样记住。

隔离环境的三条好处可以记成可用性、安全性、可控性：全天候运行，不受用户设备与联网状态影响；错误不外溢，最坏只崩虚拟环境；访问受限，不能随便碰本地文件。这三条合起来解释了为什么 Computer Use（6.4）几乎总是跑在容器或虚拟机里。

两个现实挑战其实是两类完全不同的敌人。反机器人机制是技术对抗，CAPTCHA 加 IP 信誉，所以要住宅代理；用户真实账号登录是信任问题，所以要 Human-in-the-Loop，让用户自己在 VNC/RDP 里点登录。后者的设计细节值得注意：用户"能看到 Agent 正在操作的完整界面，理解为什么需要认证"，这既是安全措施也是可解释性措施；而"认证后的会话令牌可以在有效期内复用"是在自主性与打扰频率之间取平衡。

共享文件系统那一段是本章最实用的工程技巧之一：数据用路径引用传递，不要把内容塞进上下文。可以把它类比成同事之间发共享盘链接，没人会把整份文件粘贴进聊天框。它的直接收益是省上下文窗口，一个几 MB 的 CSV 如果被读进上下文，代价极高；传一个字符串路径几乎免费。这里还藏着一个推论：Agent 的记忆或上下文里应该装的是指针（路径、ID），真正的数据放在外部存储。这与第二至五章的上下文工程、记忆是呼应的。

用用户身份操作与用虚拟身份操作各有利弊。前者上下文完整、权限更大，但一旦出错或被攻破，用户全部数字身份暴露；后者隔离性好、可审计，但会遇到第三方不信任（反机器人机制），并且在必须本人登录的任务上需要 Human-in-the-Loop 介入。这里的态度是"更稳妥的方案是赋予 Agent 一套独立的虚拟身份"，不过它并没有说后者万能。VM/容器 与 Android 模拟器也常被合并记忆，前者是虚拟电脑，后者是虚拟手机，二者都提供操作系统级隔离，这里把它们并列，用于覆盖桌面与移动两类操作能力。

让 Agent 拥有自己的虚拟身份（专属通讯账号、存储空间、计算环境）并跑在隔离环境里，再配合共享文件系统以路径引用交换数据，才能既自主又安全。

### 6.2.6 事件处理机制

一个 Agent 实例可能同时面对多个事件：用户的新消息、工具返回的结果、定时器到期、另一个 Agent 的协作请求。怎么高效而正确地处理这些事件，直接影响性能和用户体验。

这套机制的骨架是并发编程里的**事件循环（event loop）**。可以把异步 Agent 看作一个长期运行的循环：每一轮从输入队列取出若干事件，追加到轨迹，调用一次 LLM，执行它决定的工具，再回到循环开头等待下一批事件。这与 Go 的 goroutine 从 channel 读取消息、在 `for { select { ... } }` 中逐轮处理是同一个结构。

在传统的同步接口实现中，事件在每轮循环的边界被消费。当 LLM 正在推理、工具正在执行时，新事件先在队列中等待，待本轮到达一个**安全点**（一段推理结束、一次工具返回）再处理。原生异步则允许在模型仍在思考或输出时接收新要求，由系统选择合适的时机继续处理。两者都有边界，只是边界由不同层管理。工具取消仍需执行器响应取消信号，类似 Go 中对 `ctx.Done` 的检查；接收一条"停止"消息本身不会撤销已经发生的动作。

理解了这一点，下面先以兼容同步接口的事件循环说明三种处理策略：让事件等到下一个自然出现的安全点，还是主动提前制造一个安全点，又或者另起一个循环、不必等待主循环的安全点。原生 steering 的接续方式将在后文展开。

事件的结构化建模是处理的前提。通用 Agent 面对的输入不只来自用户一个人，第三方发来的消息不是用户发给 Agent 的，但 Agent 需要理解它、评估其重要性、决定如何介入。这要求将每个输入都建模为包含丰富语义的结构化事件：

- 来源（谁）：用户本人、联系人、陌生人、系统通知。
- 渠道（方式）：电话语音、短信、即时消息、邮件、社交媒体、定时器触发、异步工具调用结果、命令行监控状态更新。
- 内容（什么）：消息文本、情感色彩、紧急程度、是否需要回复。
- 上下文（背景）：是对之前某个对话的回复还是新发起的沟通，与当前任务的关联。

以一封客户退款请求邮件为例，结构化事件的具体形式如下：

```json
{
  "source": {"type": "email", "sender": "client@example.com"},
  "channel": "gmail_webhook",
  "content": {"subject": " 退款请求", "body": " 订单#12345 希望退款..."},
  "context": {"priority": "high", "customer_tier": "vip", "related_orders": ["#12345"]}
}
```

只有当这些维度被清晰地建模为结构化事件，Agent 才能在多方通信中保持清晰的认知，避免将用户输入误当成工具结果，或者把藏有指令的工具结果误认为用户指令而导致**提示注入**。多线程上下文管理的复杂性还要求 Agent 理解多个对话线程之间的关联：来自第三方的消息如何影响用户的情绪，用户在不同对话中扮演什么角色，何时需要将不同线程的信息综合起来提供建议。

从 n8n 等工作流平台的触发器生态可以看到，Webhook、定时器、邮件、数据库变更、文件监听，每一种触发器都是 Agent 感知世界的一个"感官"。这些异构的事件被统一建模为结构化格式之后，Agent 就能以一致的方式处理来自不同来源的刺激，下文的紧急度判定和处理策略也都建立在这一统一建模之上。

基于紧急度的动态处理策略。人类在处理多个任务时，会根据紧急程度采取不同的策略。面对突发的紧急情况，会立即停下手头的工作；面对常规的待办事项，则加入任务列表稍后处理。Agent 的事件处理也应体现这种智能性。

**取消式处理（Cancellation-Based）**用于紧急事件，其本质是为紧急事件提前制造一个安全点：主动中断当前步骤，把这一刻变成可以消费新事件的边界。当紧急事件到达时（如用户点击"停止"或监督系统发来高优先级指令）：

1. 停止当前操作——如果 LLM 正在推理，立即取消流式响应；如果有同步工具在执行，发送取消信号；
2. 清空待处理队列，将所有事件取出；
3. 将队列中的事件和紧急事件一起追加到轨迹末尾；
4. 立即重新调用 LLM，以更新后的完整轨迹为输入来评估局势。

例如，用户在 Agent 执行可能错误的操作时输入"停！我说错了"，Agent 会立即看到这条新输入，重新理解真实意图，从而避免执行错误的操作。

**队列式处理（Queued）**用于常规事件。当非紧急事件到达时（如异步工具返回结果或用户发来补充信息）：

1. 将事件放入队列末尾，不打断当前操作；
2. 等待当前操作完成，让 LLM 完成推理，让同步工具执行完毕；
3. 当任何工具调用完成并返回 `tool.result` 时，检查队列，如果队列非空则将所有事件一次性追加到轨迹；
4. LLM 综合处理更新后的轨迹。

这实现了批量处理，提高了效率。例如 Agent 调用搜索工具后，在等待期间用户补充了"只看最近一个月的结果"，这条补充信息进入队列，搜索结果返回时两个事件一起呈现给 LLM，避免了不必要的往返。

**并行处理（Parallel）**用于独立的轻量级查询。比如 Agent 正在分析大量数据时，用户突然问"今天天气怎么样？"此类查询具有三个特征：与主任务无关、需要快速响应、执行成本低。既不应该用取消式处理（会打断重要的主任务），也不应该用队列式处理（让用户等太久）。系统先判断查询的独立性和复杂度，然后在一个并行的推理会话中独立执行，调用必要的工具生成响应后立即返回。查询和响应会追加到主任务的轨迹中，并明确标记为"与主任务并行执行"，以避免 LLM 混淆。

紧急度的判定大体分两档。紧急事件包括用户中断（`user.interrupt`）、监督指令（`supervisor.instruction`）、Agent 间中断（`agent.interrupt`）、标记为紧急的外部触发器（如系统告警、支付失败）。非紧急事件包括常规用户输入（`user.input`）、Agent 输入（`agent.input`）、工具结果（`tool.result`）、定时器触发（`timer.trigger`）、常规外部触发器。

硬编码的规则有其局限性，事件的语义决定了处理方式："马上停下来"用取消式、"今天天气怎么样"用并行式、"报告需要用中文发给我"用队列式。建议使用轻量级的分类 LLM 作为**事件路由器**，在事件到达时快速判断应该采用哪种策略。

还有一条硬要求：取消点必须是工具或推理能够安全收尾的位置；未完成的工具结果用显式占位符表示，不能伪造成功。

安全点这个概念值得先钉牢，它是轨迹的一个合法边界。在同步接口下，边界是"一轮推理结束"或"一次工具返回"，因为只有在这两个时刻，assistant 消息与 tool result 才配得上对。取消式的精髓不在"打断"这个动作上，而在于主动提前造出这样一个边界，把当前步骤停掉，好让新事件合法地插进来。这里说"接收一条'停止'消息本身不会撤销已经发生的动作"，原因就在这里：停止只是让你能在下一个安全点作出反应，世界已经发生的变化不会回滚。

三种策略可以用"谁来等谁"区分。取消式是世界不等模型，紧急事件一来，模型让位，立即重新推理，代价是丢弃当前推理、浪费已算的算力。队列式是事件等模型，攒着，到安全点批量喂进去，代价是延迟，收益是省往返、省 token。并行式是谁都不等，另起一条轻量循环，代价是多一份推理，还需要标记以免污染主任务。

结构化事件的动机也值得强调：通用 Agent 的输入里混着用户的话、别人的话、工具的输出。不区分来源与渠道，就会出现这里点名的两类事故，把用户输入误当工具结果，或者把工具结果里夹带的指令当成用户指令，也就是提示注入。结构化建模因此不只是"整理数据"，它是权限与信任的边界。可以把它类比成邮件系统里必须分清"正文"和"附件里的宏"。

四个维度可以记成"谁、从哪来、说了什么、在什么背景下说"。JSON 示例就是这四维的落地：`source.type/sender` 是来源，`channel` 是渠道，`content.subject/body` 是内容，`context.priority/customer_tier/related_orders` 是上下文。

n8n 触发器生态的类比很形象，每一种触发器都是 Agent 的一个感官。这句话解释了统一的必要性：如果有 5 种感官，每种都用不同格式汇报，Agent 每接一条就要重新学一遍怎么理解；统一建模之后，下游的紧急度判定、路由、轨迹追加都能写成同一套逻辑。

至于谁来判紧急度，这里指出硬编码规则有局限，语义决定处理方式，建议用轻量级分类 LLM 当事件路由器。这里的工程直觉是，不要用昂贵的主模型做分类，也不要用僵硬的正则硬扛语义。这正好也是本章思考题第 1 题的争议点，规则引擎与另一个 LLM 调用各有各的代价。

最后两条注意事项极其实用。取消点必须在能安全收尾的位置，否则轨迹会处于半截状态、格式不合法；未完成的工具结果用显式占位符表示，不能伪造成功，伪造成功会让模型基于假数据继续决策。这两条是 6.2.7 五条规则的伏笔。

取消式与队列式都由事件驱动，但取消式打断并丢弃当前步骤，把这一刻变成安全点；队列式不打断，等下一个自然安全点批量追加，判断依据是事件紧急度与语义。并行式与队列式的区别在于，并行式另起一条推理会话，主循环不受影响；队列式仍在主循环内串行处理，只是延后，触发条件是与主任务无关、需快速响应、成本低这三条同时成立。结构化事件里"上下文（背景）"与内容里的"紧急程度"也容易混：这里把紧急程度放在内容维度，把与当前任务的关联放在上下文维度。前者是消息自身属性，后者是它和当前任务的相对关系，这也解释了为什么同一句话在不同任务下处理策略可能不同。

事件处理的骨架是"取事件 → 追加轨迹 → 调 LLM → 执行工具"的长期循环；紧急事件用取消式提前造安全点，常规事件用队列式批量追加，独立轻查询用并行式另起循环，判断依据来自结构化事件与语义，硬编码规则扛不住。

本实验构建一个最简单的事件驱动 Agent：自动邮件处理助手。Agent 监听邮件收件箱，每当收到新邮件时自动触发处理流程，做分类、摘要、起草回复，必要时通知用户。这是事件驱动 Agent 最直观的入门场景：一个外部事件（新邮件到达）触发一次完整的 Agent 思考循环。

实验目标是理解事件驱动的核心概念：Agent 不再只是被动地等待用户输入，而是可以响应外部事件来主动行动。通过这个实验，读者将掌握**事件源注册、事件队列**，以及"事件到达→Agent 处理→结果输出"的基本闭环。

事件源与事件队列。系统支持多种事件源的统一接入：

- 邮件事件（`on_email_received`）：通过定期检查收件箱或接收推送通知，在新邮件到达时触发；
- IM/短信消息（`on_im_message`、`on_sms_message`）：即时通讯消息触发；
- GitHub 事件（`on_github_pr_update`、`on_github_issue_update`）：PR review 意见、状态变化；
- 定时器触发（`on_timer_expire`）：定时任务（如每日摘要、周报生成）；
- Webhook（`on_webhook_received`）：通用的外部系统回调；
- 系统事件（`on_user_inactive`、`on_process_timeout`、`on_resource_alert`）：内部状态变化。

所有事件进入一个统一的事件队列，按到达顺序依次处理。每个事件触发一次独立的 Agent 思考循环：Agent 读取事件内容，调用相关的工具（如查询知识库、读取附件、搜索相关的邮件历史），生成处理结果（分类标签、摘要、草稿回复），最后通过通知工具告知用户或直接执行操作。

验证场景：配置 Agent 监听测试邮箱。模拟接收三封邮件，一封会议邀请、一封客户投诉、一封营销广告。Agent 依次处理：为会议邀请自动检查日历冲突并起草接受/拒绝回复；为客户投诉提取关键信息并标记为高优先级，通知用户处理；将营销广告自动归档。整个过程无需用户介入。

实验 6-1 展示了最简单的事件驱动模式，事件进入队列，Agent 依次处理。但当 Agent 需要在长时间运行的工具执行过程中响应打断，或同时管理多个并发任务时，简单的事件队列就不够用了。接下来讨论更深层的工程挑战。

这个实验的价值在于把 6.2.6 前面的抽象概念落成最小可运行系统：事件源注册（谁把事件送进来）、事件队列（先来先处理）、Agent 循环（每个事件跑一次完整思考）。可以把它看成前面"事件流"概念的最小实现。这里说它是"最简单"的，队列里只有"依次处理"，还没有紧急度路由和三种策略。

三封邮件的验证场景设计得很巧，用同一套流程覆盖了三种截然不同的处置方式：需要动作加需要回复（会议邀请，查日历冲突、起草接受或拒绝）、需要判定优先级并转人（客户投诉，提取关键信息、标记高优先级、通知用户）、无需动作、归档即可（营销广告）。这三类正好对应 Agent 在自动化程度上的三种档位，做真实系统时也可以拿它当自检清单：你的 Agent 是只会归档，还是会动手？

从图 6-3 还能读出一个工程要点：工具分成感知、执行、协作、通知四组，并且单独有一个持久层（对话历史、事件日志、定时任务、工具状态、审计追踪）。持久层的存在说明事件驱动 Agent 必须"记得住"：事件日志支撑去重与追溯，工具状态支撑任务恢复，审计追踪支撑可解释与合规。这正好呼应 6.2.5 里"独立、可审计的身份"。

### 6.2.7 不支持原生异步时的兼容方案

实验 6-1 只处理串行事件，事件依次进入队列，Agent 一个接一个处理完毕。如果选用的模型或接口不支持原生异步，当工具尚未返回时用户突然打断，就需要在同步格式中表达异步语义。下面给出一条兼容路线；后文再介绍 GPT-6 Astra 的原生接口。

假设 Agent 正在帮用户起草一封邮件（工具调用：搜索联系人信息），搜索还没返回结果时，用户突然说"等一下，先帮我查一下明天的天气"。如果接口要求未完成的工具调用先获得对应结果，Agent 就无法直接带着**悬空调用**处理这条新消息。这里的限制来自所选协议与模型组合，并非所有 LLM 都必须遵循的规律。

兼容同步格式的异步实现，核心思想是：在没有打断发生的常态下，让 LLM 看到标准的同步轨迹，只在打断时才插入占位符来修复格式。以下是五条关键规则：

- **规则 1**：及时记录 API 已完成的 assistant 消息和工具调用项；对服务端管理的 reasoning 状态，按提供商的续接协议保留，不自行拼接不可见的思考文本。
- **规则 2**：工具调用完成时才记录 tool result。执行中轨迹处于"部分完成"状态。
- **规则 3**：工具执行中的打断需要占位符。为未完成的工具生成占位符响应（如"工具正在后台执行，请优先处理新事件"），追加打断事件，重新调用 LLM。从 LLM 的视角看，assistant message 仍然有配对的 tool result。
- **规则 4**：在没有原生 steering 或受支持的中途续接接口时，取消未完成的生成，保留已经确认完成的消息和工具状态，将新事件追加后重新请求。不能假定半截输出或隐藏推理可以作为合法前缀任意回灌。
- **规则 5**：非打断事件进入队列等待批处理。当前周期完成后才一次性追加。

以 Agent 正在起草邮件时用户打断询问天气为例，这五条规则的运作过程如下：

1. Agent 调用 `search_contacts` 搜索联系人信息，assistant message 立即写入轨迹（规则 1）。
2. 搜索工具尚未返回结果时，用户发来"先帮我查一下明天的天气"。由于这是用户打断，系统为未完成的 `search_contacts` 生成占位符 tool result（"工具正在后台执行，请优先处理新事件"，规则 3），然后将用户的天气查询追加到轨迹，重新调用 LLM。此刻 LLM 看到的轨迹格式完全合法，assistant message 与 tool result 配对完好。
3. 天气查询完成并回复用户后，原先的 `search_contacts` 结果到达，作为新事件追加到轨迹（规则 2），Agent 读取联系人信息后继续起草邮件。

这套方案的作用是维持同步接口要求的工具配对关系。只有需要打断时才引入明确表示"未完成"的占位符；后台真实结果到达后，再通过有来源和任务 ID 的事件送入轨迹。对于已经支持原生异步的模型，系统可以保留任务的未完成状态，等真实结果到达后再交给模型处理。

占位符也带来语义上的风险：模型可能把"任务已启动"误当成"任务已完成"，在真实结果返回前作出依赖该结果的判断。应通过明确的任务状态和结果校验防止这种混淆，并在评估中检查是否编造了未到达的数据。不能仅凭一次失败，就把原因归结为某个未公开的训练过程。

通过任务句柄表达异步语义。无论是否使用原生异步协议，都可以从工具接口的设计层面明确异步语义。对同步接口尤其有用的方法，是让"启动任务"成为一次有真实返回值的完整调用。

传统的工具设计隐含了"调用即完成"的语义。例如 `phone_call` 这个名字暗示"调用将拨打电话并等待通话结束，返回通话记录"。在异步范式下应该将"启动"和"完成"解耦：

- `initiate_phone_call`：启动电话呼叫，立即返回任务标识符和初始状态（如"呼叫已发起，正在拨号"）；
- 通话进展通过事件通知（`phone_call_connected`、`phone_call_ended`）。

关键在于工具的名称和描述本身就要传达异步的语义。当模型看到 `initiate_phone_call` 时，它会自然推断这是"发起"而非"完成"。工具描述应进一步强化这一点："此工具将启动由子 Agent 处理的电话任务。任务成功发起后立即返回任务 ID，你可以继续处理其他事项。通话结束后会收到单独的通知事件。"

队列式处理中的注意力分散问题。在批量事件处理时，模型可能只回应最后一个事件而遗漏前面的要求。原生异步解决了消息能否在运行中到达的问题，仍需检查模型是否综合使用了所有更新。可以从两个层面进行干预：

- 提示词层面：告知模型"当收到多个连续事件时，请确保全面考虑所有信息"。
- Agent 状态栏标记：在每个事件前添加显式标记：

```text
[未处理事件1/4] Tool result from database_query：...
[未处理事件2/4] User 补充说明：只看北京地区的数据
[未处理事件3/4] 系统提醒：报告截止时间还有30 分钟
[未处理事件4/4] User 询问：进度如何？
```

在末尾添加汇总："上面有 4 个未处理事件，包括 1 个工具结果、2 条用户消息、1 个系统提醒。请确保回应涵盖所有信息。"

#### 实验 6-2 ★★★：带并行执行和打断能力的异步 Agent

在实验 6-1 的简单事件队列基础上，本实验通过兼容同步接口的运行时实现并行工具执行、执行取消和状态管理。Agent 不再只是逐个处理事件，而是需要同时管理多个并发任务，处理打断和恢复，并根据实时状态做出动态决策。原生 Astra 接口的对照见实验 6-3。

1. **异步工具执行**：支持耗时工具的异步执行（至少 3–5 秒），启动后立即返回占位符。验证场景：Agent 执行一个长时间的终端命令，期间用户问"现在几点了？"，Agent 立即回应，等分析结果返回后再呈现。
2. **事件队列与批量处理**：累积非紧急事件，批量追加到轨迹。验证场景：Agent 执行长任务，用户连续发送"记得用日语回复"和"整理成网页"，任务完成时一次性处理所有事件，生成日语网页。
3. **打断机制**：用户的"停止"立即终止执行流并取消异步工具。验证场景：Agent 执行长任务，用户发送"取消"，Agent 立即停止，轨迹记录打断事件和取消操作。
4. **并行工具的取消与状态查询**：异步工具完成后通过新事件将真实结果注入对话，支持通过任务 ID 取消或查询进度。验证场景：用户请求"帮我同时运行这三个脚本，哪个先完成了，就看看剩下的脚本进度怎么样，如果还没超过 50%，就取消"。三个脚本模拟分析进程，运行时不断输出进度，速度分别为每秒 3%、2%、1%。Agent 同时启动三个异步终端命令，当每秒 3% 的脚本在约 33 秒后完成时，Agent 查询剩下两个终端的状态，发现一个执行到约 66%、另一个约 33%，于是取消不超过 50% 的那个。两个终端都完成后整合结果生成完整报告。

这一小节回答的是一个很实际的问题：手上的模型不支持原生异步，是不是就做不了异步 Agent？这里的答案是可以，但要自己造一层翻译。核心思想一句话：常态下装作什么都没发生，走标准同步轨迹；只在打断时用一个占位符把格式补圆。五条规则其实就是在维护一个不变量，每一条 assistant 的工具调用都必有配对的 tool result。

把五条规则按"什么时候执行"排一下就清楚了。常态下，assistant 消息与工具调用项立即记录（规则 1），tool result 完成时才记（规则 2），非打断事件攒着（规则 5）。打断时，先给未完成的工具补一个占位符 result（规则 3），再把新事件追加、重新请求；如果协议不支持中途续接，就取消未完成的生成，只保留已确认完成的部分（规则 4）。

规则 1 里那句"不自行拼接不可见的思考文本"和规则 4 里那句"不能假定半截输出或隐藏推理可以作为合法前缀任意回灌"，说的是同一件事：服务端管理的 reasoning 状态是黑盒。你不能把看不见的思考文本当成可拼接的字符串，也不能把半截输出塞回去当合法开头。这是兼容层最容易想当然、也最容易踩的坑。

占位符的语义风险值得单独记：占位符说"工具正在后台执行"，但模型很可能读成"工具已完成，结果是'正在后台执行'"。于是它可能在真实结果到达前就基于"已启动"作出依赖结果的判断，甚至编造未到达的数据。给出的应对是明确的任务状态加结果校验，并在评估中专门检查"是否编造了未到达的数据"。最后那句"不能仅凭一次失败，就把原因归结为某个未公开的训练过程"是方法论提醒：失败的归因要落在可观测的系统环节上。

任务句柄这一节的思路非常值得迁移到自己的工具设计里，名字就是提示词。`phone_call` 暗示"调用即完成，等通话记录"；`initiate_phone_call` 暗示"只是发起，稍后有事通知你"。配合工具描述里的那句"任务成功发起后立即返回任务 ID，你可以继续处理其他事项"，模型就能自然地把"发起"和"完成"分开。这个技巧的普适性很强，凡是耗时超过一次推理的工具，都应该考虑改名叫 initiate/start/submit，并明确返回任务 ID。

注意力分散这一段是异步系统里最隐蔽的 bug：消息都到了，模型却只回应最后一条。这里给了两个层面的干预，提示词层面和状态栏标记层面。状态栏标记的设计要点有三个：编号（`1/4`）让模型知道总数与进度；每条标注来源（Tool result / User / 系统提醒）；末尾再做一次汇总统计（"包括 1 个工具结果、2 条用户消息、1 个系统提醒"）。这个末位汇总很有效，因为它把"不能遗漏"变成了一个可以对照的清单。

实验 6-2 的四项练习正好把上面的机制逐个测了一遍：异步工具执行（对应规则 1/2/3 与占位符）、事件队列与批量处理（对应规则 5）、打断机制（对应规则 3/4 与取消）、并行工具的取消与状态查询（对应 `cancel_tool(task_id)` 与异步完成事件）。第 4 项的数值场景值得自己算一下：三个脚本速度分别是每秒 3%、2%、1%，3% 的那个在 100/3 ≈ 33.3 秒完成；同一时刻 2% 的走到约 66.7%（与这里"约 66%"一致），1% 的走到约 33.3%（与这里"约 33%"一致）。所以"取消不超过 50% 的那个"正好落在那条每秒 1% 的脚本上。上面这段换算是算术，这里只给了"约 33 秒""约 66%""约 33%"这些结果。

兼容方案与原生异步的分工值得分清：兼容方案由运行时安排事件的接入顺序，模型仍按同步方式接收信息；原生异步由模型理解等待与中途变化。前者需要事件队列、任务句柄与兼容层，后者可以直接使用原生协议，但两者都需要应用管理事件来源、工具生命周期与结果归属。取消生成与撤销动作也不是一回事，取消未完成的生成只是不再等这段输出，已经发生的动作（比如已经拨出去的电话、已经点击的按钮）不会因此回滚，这里在 6.2.6 就强调过"接收一条'停止'消息本身不会撤销已经发生的动作"。非打断事件与打断事件的处理方式同样不同，前者进队列等批处理（规则 5），后者需要占位符修复格式（规则 3），判断标准是事件语义：用户中途补充一句"只看最近一个月"算打断还是补充，取决于它是否要求立刻改变当前动作。

同步接口上做异步，靠的是常态走标准同步轨迹、打断时补占位符以维持工具配对，再加上把"启动"与"完成"解耦的任务句柄设计，以及在批量追加时用编号与汇总防止模型只看最后一条。

### 6.2.8 模型原生异步：GPT-6 Astra

前面的兼容方案由运行时安排事件的接入顺序，让使用同步接口的模型参与异步任务。另一条路线是让模型原生理解这种交互节奏：工具还在运行时，自己可以继续做别的事；用户中途补充要求时，也可以据此调整后续工作。

**GPT-6 Astra** 已支持**异步工具调用（Async tool calling）**与**回合中途引导（Mid-turn steering）**，体现了这一变化（图 6-5）。补充：③ OpenAI, "Async tool calling"; "Using GPT-6 Astra"，核对日期：2026-09-05。④ OpenAI, "Mid-turn steering"，核对日期：2026-09-05。

异步工具调用将"发起行动"和"获得结果"分开。Agent 发起耗时查询后，可以继续推理、调用其他工具，或处理不依赖查询结果的部分。例如，查询会议场地时，可以先整理议程和准备清单；等场地信息返回，再比较方案。关键是分清工作的依赖关系：能独立推进的工作继续做，必须依据结果的决策留到结果到达之后。

回合中途引导让用户可以在任务进行中修正方向。当 Agent 还在思考或组织回答时，用户就可以追加"预算减少了""参会人数变了"等要求。系统保留已完成的工作，把新的约束带入后续处理，使 Agent 能够在同一次任务中调整计划。接收到更新与作出调整之间仍可能有延迟，但用户不必等一整轮回答结束才表达变化。

这两种能力扩展的是交互的时机：工具结果与用户要求都可以在任务推进过程中到达。系统仍要分清它们的来源，记住哪些工作已经完成、哪些还在等待。修改计划也不等于停止正在运行的工具，更不会自动撤销已经发生的动作；实际执行、取消和状态管理仍由运行时负责。

并非所有模型都具备原生异步能力。构建 Agent 时，应根据模型的支持范围选择原生交互或兼容方案，再检查整个系统能否正确应对延迟返回、中途修改与任务恢复。异步训练可以继续改善这些能力，但开发者已经可以利用现有模型构建这样的交互方式。

这一节的关键区分是谁理解异步。兼容方案里，理解异步的责任在运行时，它把事件排队、决定打断或并行，再翻译成同步格式；原生异步里，模型自己知道"这个工具还在跑""用户刚改了约束"。责任在哪一层，决定了你的工程复杂度落在哪一层。

图 6-5 的右栏给出了一个好用的依赖关系划分法：拿到一个任务，先把步骤分成两类，不依赖外部结果的（整理议程、准备清单）和必须依据结果的（比较场地、下结论）。前者立刻做，后者等结果。这既是异步工具调用的使用方式，也是一个通用的计划编排原则。

回合中途引导的收益在"用户不必整轮说完"上。传统轮次交互里，用户要等 Agent 说完整套回答，才能补充"预算减少了"；中途引导让这条约束在生成过程中就进入后续处理，同时系统保留已经做完的工作，不必从头再来。

但这里立刻补了两句"刹车"，很值得原样记住：修改计划不等于停止正在运行的工具，更不会自动撤销已经发生的动作。模型侧理解变化只是一半，真正的执行、取消与状态管理仍然在运行时手里。所以即使模型原生支持异步，你依然需要任务状态、事件来源与执行反馈这些系统能力，这也是 6.2.9 要检查的三件事。

最后一句"开发者已经可以利用现有模型构建这样的交互方式"，是对兼容方案的收尾肯定，不必等原生模型才能做异步 Agent。

异步工具调用与回合中途引导作用的位置不同：前者管工具结果的时序（发起与获得结果分开），后者管用户输入的时序（在生成过程中追加要求）。两者扩展的都是时机，但一个在动作的结果侧，一个在观察的输入侧。模型侧"理解变化"与运行时"按变化执行"也常被混为一谈，这里在图 6-5 底部明确分工，把这两者看成同一件事，就会出现"模型说改好了，但工具其实还在按旧计划跑"的事故。

原生异步把"理解等待与中途变化"交给模型、把"工具执行与任务状态"留给运行时；能独立推进的工作继续做，必须依据结果的决策留到结果到达之后。

### 6.2.9 从"能接收异步消息"到"可靠处理异步任务"

原生异步解决了消息能否在运行中到达的问题，复杂任务中的可靠性还取决于模型如何使用这些消息。至少要检查三件事：

1. **结果归属与未完成状态**：能否把延迟到达的结果归入正确任务，在结果缺席时避免编造数据？
2. **任务恢复与动作控制**：能否在处理新要求后继续原任务，并区分修改计划与停止执行？
3. **多条更新的综合使用**：能否同时遵守预算与人数等约束，不会只记住最后一条消息？

针对这些问题，可以通过异步环境中的训练改进模型，也可以通过清晰的任务状态、事件来源和执行反馈改进系统。评估需要覆盖两层：模型是否理解了变化，系统是否按变化正确执行。

#### 实验 6-3 ★★★：模型原生异步与回合中途引导

为一次会议选择场地：Agent 发起耗时查询后，先完成不依赖查询结果的准备工作；期间用户补充预算与人数要求。等查询完成，再根据全部约束选择场地。调用 GPT-6 Astra API，对比同步工具、原生异步工具和回合中途引导三种交互方式，观察等待是否阻塞其他工作、新要求是否进入后续计划，以及结果到达后能否继续原任务。再选择一个不支持原生能力的模型作为对照，理解模型能力与运行时编排各自解决什么问题。

异步与事件驱动让世界能够在任务进行中唤醒 Agent，原生引导又让用户不必等完整回答结束才能提交更新。接下来三节进一步压缩时间尺度：当环境变化的速度达到甚至超过模型的生成速度时，能接收更新还不够，系统还必须及时作出反应。

这三条检查项可以看成异步 Agent 的可靠性验收单，而且它们分别对应前面几节留下的坑：第 1 条对应占位符的语义风险，别把"已启动"当"已完成"、别编造未到达的数据；第 2 条对应"修改计划不等于停止工具"，别把新约束当成中止信号；第 3 条对应批量事件里的注意力分散，别只回应最后一条。

这里给出的改进路径也是两条腿走路：模型侧的异步环境训练，以及系统侧的任务状态、事件来源、执行反馈。这背后是一个实用的工程态度，不要把问题都押在模型能力上。清晰的任务状态和事件来源是运行时就能做好的事，而且做好的当天就能生效。

评估要覆盖两层，模型是否理解变化、系统是否按变化正确执行，这一点很关键：一个失败案例可能出在模型没理解，也可能出在系统没执行，不分层就没法定位。这与 6.2.7 那句"不能仅凭一次失败就把原因归结为某个未公开的训练过程"是同一个方法论。

实验 6-3 的设计值得抄：它用一个任务（选会议场地）串起三种交互方式（同步工具、原生异步工具、回合中途引导），并额外加一个"不支持原生能力的模型"作对照。这样对照得到的是两类能力各自解决的问题，模型能力管什么，运行时编排管什么，这正是本小节要的答案。

"能接收异步消息"与"能可靠处理异步任务"要分开看：前者是通道能力，消息能在运行中到达；后者是使用能力，正确归属、正确恢复、正确综合，这里标题的这组对比就是本小节的全部要点。修改计划与停止执行也属于两种不同意图：同样是"用户中途说了句新的要求"，"预算减少"要求修改计划，继续跑、带上新约束；"取消"要求停止执行，撤销或取消工具。系统必须能区分这两种意图。

异步的可靠性要查三件事，结果归属与未完成状态、任务恢复与动作控制、多条更新的综合使用；改进要同时从模型训练和任务状态、事件来源、执行反馈两方面下手，评估也要分"模型是否理解"与"系统是否执行"两层。

## 6.3 语音：最自然的人机接口

语音的价值不只是把文字换成声音。正常说话的速度约为打字的四倍，而且不占用双手与视线，这让它天然适合把 Agent 放进持续工作、随时可能被打断的输入输出回路。语音输入法把口述转成文字，语音 Agent 则让用户直接与 Agent 协作，两者都能支持引言里提到的 whisper coding。

6.3 要处理的方向有两个：用户对 Agent 说话，以及 Agent 代替用户对外部世界说话。前者关注听与答（6.3.1–6.3.5），后者关注「代替用户打电话」的效果与自然度，也就是 6.3.4 的实时翻译和 6.3.6 的拟人化合成，同时也呼应 6.2.2 里 Pine AI 那种代打电话的场景。

这里最需要先摆正的一点关系是：语音模型本身决定「能回答什么」，交互架构决定「能否听清、及时回应、自然换手，并在通话中完成确认和工具调用」。能力上限归模型，体验瓶颈归架构。所以 6.3 的绝大部分篇幅都在讲时序，而不是讲语音识别率。「说话速度约为打字四倍」是本节唯一给出的量化依据，它解释了为什么语音特别适合「持续工作、随时被打断」的回路：输入带宽更高，双手和视线空出来，人可以一边做别的事一边与 Agent 交互。

## 6.3.1 交互时序：从级联到全双工

OpenAI 在 GPT-Live 的介绍里用「级联、轮次式、全双工」概括了语音系统的三种交互范式。这三个词容易被读成一条新旧替代的路线，实际是不同延迟、成本和可观测性约束下的取舍。

| 范式 | 核心结构 | 主要优势 | 主要限制 |
| --- | --- | --- | --- |
| 级联 | VAD → ASR → LLM → TTS | 模块清晰、易替换、易调试 | 延迟累积，副语言信息在接口处丢失 |
| 端到端 Omni | 原生音频输入输出，按轮次交互 | 延迟较低，能保留语气、情绪和环境声 | 仍依赖轮次，训练和调试成本较高 |
| 全双工 | 原生音频输入输出，持续听、说和决策 | 支持重叠说话、自然打断和连续流 | 模型训练、控制和评估都更复杂 |

贯穿三种范式的主线是：如何摆脱「轮流说话」和 VAD 对发言权的猜测。级联和 Omni 仍要划分轮次，只有全双工把「该谁说话」变成模型的持续决策。

补充：⑤ OpenAI. *Introducing GPT-Live*. 2026-07-08。本节「级联/轮次式/全双工」三分法即出自该文对 ChatGPT 语音三代演进的总结；文中「端到端全模态（Omni）」对应其「turn-based voice models」一类。

按「发言权由谁决定」来排队，这三种范式的位置就清楚了。级联由 VAD 这个独立的声学模块决定谁说完了，听、想、说分成四个模型串起来。Omni 由模型处理音频输入输出，但节奏仍按轮次，通常还需要 VAD 划分发言权。全双工是模型持续决策，继续听、停顿、打断、说话，都是它在每个时刻的选择。

表格里的「主要限制」其实是一组成本项：级联的代价是延迟与副语言信息丢失，Omni 的代价是轮次依赖加上训练调试贵，全双工的代价是训练、控制和评估都更复杂。强调这不是简单的新旧替代，如果你的场景里可观测性与可调试性优先，比如要逐模块定位问题，级联反而更合适。

「副语言信息在接口处丢失」说人话就是：语气、情绪、犹豫、笑声、叹气这些信息在「音频→文字」这一步被扔掉了。级联的每一级接口都是离散的，文本或音频，而且是有损转换，所以信息越传越少。这也解释了 Omni 与全双工为什么反复强调「原生音频输入输出」。

轮次式与全双工的区别值得单独记一下：前者把对话切成「用户说」和「模型说」两个时段，即使输入输出都是音频的原生模型也如此；后者不预设轮次，两者可以重叠。补充：特意点明，「端到端全模态（Omni）」对应 GPT-Live 一文里的「turn-based voice models」一类，也就是说 Omni 是「音频端到端」，但仍是轮次式。另外，延迟低不等于交互好。全双工的优势不止于延迟，还包括重叠说话、自然打断与连续流；Omni 的优势是延迟较低且保留副语言信息，但打断判断仍然原始。

实验 6-4 ★：构建传统语音 Agent。本实验用 WebSocket 串起麦克风、Silero VAD、本地 Whisper、流式 LLM 和 Fish S1 TTS，建立后续方案的级联基线（baseline）。

图 6-6 最有价值的一笔是那条「用户说话 2–3 秒 → VAD 等待 → ASR 等待 → LLM 空闲」的时间线。它点出了级联范式的真正浪费：问题不在某一级太慢，而在用户说话的那 2–3 秒里，后面三级完全空转。6.3.2.1 的流式感知（LLM 推测执行）正是冲着这段空转去的。

图 6-7 的算术值得自己验一遍（是计算）。最优情形取每段下限：500+50+100+100+200 = 950ms；最差情形取每段上限：800+200+500+300+500 = 2300ms。给出的「最优 950ms ≈ 0.9s / 最差 2300ms ≈ 2.3s」与之一致。图 6-7 把 LLM 拆成了两段，TTFT（首 token 时间）100–500ms 与生成 100–300ms，这个拆分很关键：首 token 延迟才是用户感知到的等待起点，而开启 reasoning 会让这一段明显变长（见表格里 LLM 的典型瓶颈）。这里也强调「真实数值取决于输入长度、模型、硬件、网络和负载」。

图 6-8 的排队模型给出一个反直觉但重要的结论：即使空载延迟只有 1 秒，在生产环境的典型利用率下实际延迟也会变成 2–5 秒。公式是

$$
T_{\text{总}} = \frac{S}{1-\rho}
$$

其中 $S$ 是空载延迟（图例中取 $S=1\text{s}$），$\rho$ 是系统利用率（0 到 1，表示服务能力被占用的比例），$T_{\text{总}}$ 是含排队的实际总延迟，单位秒。分母 $1-\rho$ 是「系统还剩多少空闲余量」，利用率越高余量越小，等待就越长；当 $\rho \to 1$ 时余量为 0，延迟趋于无穷。代入数值看：$\rho=0.5$ 时 $T=1/0.5=2\text{s}$，正好触到这里标注的「用户忍受上限」；$\rho=0.8$ 时 $T=1/0.2=5\text{s}$，属于「不可接受」。这两个数字就是这里「生产环境 ρ 通常 0.5–0.8 → 实际延迟 2–5× 空载延迟」的来历（直接给出了 2s、5s 的读数）。

工程上由此得出一条：语音 Agent 的延迟预算不能按「空载理想值」来定。如果你的设计目标是从用户说完到 Agent 开口不超过 1 秒，那么空载延迟可能要压到 200–500ms 才有余量。反过来，如果算力吃紧、利用率会冲到 0.8 以上，再多的模型优化也救不回体验，这时候要考虑的是扩容或降级策略（说这属于服务容量规划，本章不展开）。

实验 6-4 的定位是基线：它故意用最原始的串行流水线，好让后面的流式感知（实验 6-5）、端到端（实验 6-6）、控制标记 TTS（实验 6-7）都有一个可比的起点。这种先搭基线再优化的实验设计思路，本身也值得学。

VAD 有两种错法。静音阈值定得长，就「等待」，用户说完还要多等一段；定得短，就「误切分」，话没说完就被当成说完了。这里把这一条列为 VAD 的典型瓶颈，这也是级联范式很难真正做到自然打断的原因。另外，首 token 延迟（TTFT）与总生成时间要分开看：用户感知的等待主要由 TTFT 决定，但图 6-7 里两段都要算进总响应时间，开启 reasoning 主要拉长的是前一段。

级联流水线是 VAD→ASR→LLM→TTS 的串行链，模块清晰易调试，但四段延迟串行相加（空载最优 950ms、最差 2300ms），再加上排队公式 $T=S/(1-\rho)$ 的放大，生产环境实际延迟往往是空载的 2–5 倍。

#### 6.3.2.1 从串行到流式感知

图 6-7 描述的是 VAD+ASR+LLM+TTS 的完全串行情形，这种串行感知方案有三个问题。延迟上必须等待一段静音才能确认说完；信息上有声/无声的二值信号无法表达犹豫、情绪、附和和环境声；上下文上邮箱、人名和专有名词可能被分片识别而出错。

在保留模块化分工的前提下，一种优化方案是流式感知，让各阶段尽早产出增量结果：

- ASR 边听边转：VAD 检测到用户开始说话时，就按照一定的时间间隔调用 ASR 模型，流式生成临时转录内容；VAD 检测到用户说话结束后，再确认最终文本。
- LLM 推测执行：临时转录内容生成后，就送给 LLM；如果最终文本与临时转录内容相同就不再调用 LLM，否则取消前序推测执行的思考，重新调用 LLM。
- LLM 分段输出：第一段适合播报的文本生成后立即交给 TTS，不等完整回复。
- TTS 增量合成：持续返回音频块，让后续生成、合成和播放重叠进行。

真正的流式 ASR 需要模型支持。Whisper 的解码虽然是自回归的，但编码器需要完整音频段，因此不能直接等同于流式模型。基于 LLM 的流式听觉模型可以从连续音频中输出文本和语义事件，把「识别」和部分「理解」放进同一个模型。它保留从对话开始到当前时刻的上下文，也可以利用世界知识处理品牌、人名和专有名词。

如果只想解决「用户是否说完」，也可以把轮次判断直接做进流式识别器：模型综合语义和静音判断一句话是否表达完整。端点判断的训练标签必须只使用决策时刻可见的信息，否则会因「上帝视角」产生线上无法复现的判断。

模型输出的不仅是文字，还可以包含声学事件标记：

- `speak_start/end`、`interrupt`：说话起止与打断意图；
- `emotion`：情感、犹豫等状态；
- `laugh`、`sigh`、`noise`：副语言和环境声。

这些标记和文字 token 形成统一事件流，Agent 可以据此识别犹豫、打断和环境变化，而不必把所有声音压成纯文本。

实验 6-5 ★：使用 Qwen2-Audio 模拟流式语音感知。Qwen2-Audio 本身不是流式模型。本实验用递增音频前缀模拟连续感知，并与 600ms VAD + Whisper 对照。

流式感知的四个动作其实是在给流水线「错峰」：ASR 不等用户说完就开始转，省掉 VAD 之后的等待；LLM 不等 ASR 最终结果就开始想，用推测执行填掉自己的空闲；TTS 不等 LLM 说完就开始合成，让合成与生成重叠。把它理解成工厂流水线上把「整批生产」改成「单件流」，大致就是这个意思。

「推测执行」这个名字容易让人以为是硬件里的分支预测，机制其实很像：拿临时转录先算，如果最终文本一致就复用，不一致就丢弃重算。收益因此取决于临时转录有多准。转得准，就白赚一段推理时间；转得不准，就白烧一次推理。这也是这里强调比较最终文本与临时转录、而不是无条件复用的原因。

关于 Whisper 的那句判断很关键，值得原样记住：自回归解码不等于流式模型。Whisper 的编码器要吃完整音频段，所以它天然需要「等一段」。这也是实验 6-4 用本地 Whisper、实验 6-5 用 Qwen2-Audio（且明确说「本身不是流式模型」，要靠递增音频前缀模拟）的原因。这里在此基础上又指出真正该走的方向，基于 LLM 的流式听觉模型：把识别与部分理解放进同一个模型，并保留从对话开始到当前的上下文。

端点判断（「用户说完了吗」）有一个非常专业的要求：训练标签只能使用决策时刻可见的信息。否则模型在训练时「偷看」了未来（后面其实还有话），学到的是一个线上无法复现的判断，一上线就会误切分。这里把它称为「上帝视角」，这个说法很精准。

声学事件标记这一块是把副语言信息显式化：与其让模型从波形里自己悟，不如把 `interrupt`、`emotion`、`laugh`、`sigh`、`noise` 当作与文字 token 并列的事件输出。好处是它们能和文字一起进统一事件流，Agent 因此能区分「嗯（附和）」和「嗯？（疑问/打断）」。这也正是图 6-9 里批评「打断判断原始：『嗯』『对』是附和不是打断」那条局限的解药。

几个容易混的说法在这里理一下。临时转录是流式 ASR 的中间产物，用于提前触发 LLM；最终文本是 VAD 判定说完后确认的结果，只有两者相同，前序推测执行的思考才能复用。流式 ASR 与传统 ASR 的判据不在「输出是不是逐字的」，而在「能不能在音频还没结束时给出可用的中间结果」，Whisper 就是典型的「自回归但非流式」。声学事件标记则是副语言/环境信息（情感、打断、笑声、噪声），与作为内容的转写文字不是一回事，这里的态度是不要「把所有声音压成纯文本」。

### 6.3.3 范式二 · 端到端全模态模型（Omni）

级联即使采用流式感知，听、想、说仍通过离散接口交接；情绪、语调和环境声等信息可能在转成纯文本时丢失。Omni 方案用同一个模型直接听音频、生成回复并输出语音，因而有机会保留这些信息，但训练的成本更高（图 6-9）。相比范式一的级联方案，Omni 的优势主要体现在延迟和非文字信息的理解和生成上。

在理解方面，Omni 模型可以理解声音中的停顿和。

在生成方面，Omni 模型可以传递更丰富的副语言信息，例如唱歌、用特殊的语调讲一句话。

Omni 模型仍然假设轮流说话，通常要靠 VAD 划分发言权。因此，用户报数字时的中途停顿仍可能被误判为说完。

实验 6-6 ★★：本地运行 MiniCPM-o 4.5，对比端到端与自级联。本实验使用本地 MiniCPM-o 4.5，关闭 thinking mode，比较直接从音频作答与同模型自级联先转录再作答。它测的是音频信息是否被保留，不是后文的「边想边说」。

Omni 的动机可以概括成一句话：别让信息在接口上被压成文本。级联即使流式化，听、想、说之间仍然是离散接口（音频→文本→音频），语气、情绪、环境声在「→文本」这一步就没了。Omni 把这三段合并进一个模型，因此有机会保留副语言信息。

但 Omni 并没有解决发言权问题。这里的判断很明确：「仍然假设轮流说话，通常要靠 VAD 划分发言权」，而且给出了一个非常具体的失败例子，用户报数字时的中途停顿仍可能被误判为说完（报手机号、报卡号时习惯性停顿）。这说明 Omni 是模态上的端到端，不是时序上的端到端。这个概念区分在 6.3.5.4 会再次出现。

图 6-9 底部的「共同局限」两段，实际上是对整个「轮次检测」路线的批评：VAD 基于声学信号，无法捕捉语义层面信息。所以「用户停顿 ≠ 说完」「『嗯』『对』是附和不是打断」「背景噪音误判为发言」这三类错误，根子不在模型不够大，而在判断依据错了（只看声学、不看语义）。这也解释了 6.3.2.1 为什么要提出「基于 LLM 的流式听觉模型」和把轮次判断做进流式识别器。

图 6-9 里几个可核查的数字值得记住：Qwen3-Omni 首包延迟 234ms、32/36 达开源 SOTA；Step-Audio 2 副语言理解 83.09%，并标注「超越 Qwen2.5-Omni (44.18%)」。

> 来源确认：Moshi（Kyutai，2024）确为真实工作，论文为 *Moshi: a speech-text foundation model for real-time dialogue*（arXiv:2410.00037），其「并行双音频流 + 内心独白文本流、无需 VAD / 轮次检测」的表述与图 6-9 一致。（来源：[Moshi: a speech-text foundation model for real-time dialogue](https://ar5iv.labs.arxiv.org/html/2410.00037v2)）

实验 6-6 的设计要点在于控制变量：同一个模型，一次直接听音频作答，一次先转录再作答（「自级联」），比较两种路径的表现。它测的是音频信息是否被保留，而不是「边想边说」。做了这个限定，避免读者把 Omni 与 6.3.5 的认知时序混淆。

「端到端」这个词在本节有两个含义，得分开。6.3.3 的 Omni 指语音通路上的端到端，即模型直接接收音频、生成音频。6.3.5.4 会澄清另一个含义，实时交互与深度思考是否在同一模型内共享状态。两者彼此独立。另一个容易混的是 Omni 与全双工：Omni 仍是轮次式（要靠 VAD 划分发言权），全双工则不再预设轮次。图 6-9 把它们放在同一张图里对比，正因为二者容易混。

### 6.3.4 范式三 · 全双工交互模型

Omni 仍然把对话分成「用户说」和「模型说」两个时段，但同声传译等任务要求两者重叠进行。全双工模型因此不再预设轮次，它持续听、持续说，并不断决定继续、停顿、打断或调用工具。

研究上的先声是 Kyutai 的 Moshi（2024）。它并行建模用户和模型的音频流，因此重叠说话和打断可以成为模型的自然行为。

Thinking Machines Lab 将这类路线称为交互模型（Interaction Model）：交互性不再依靠 VAD 等外部 harness 拼装实现，而是内建在模型中。其微轮次机制以短音频块持续推进，让静音、重叠和打断都作为连续上下文保留。交互模型还可以把完整对话委派给后台推理模型，自己继续维持话头；后台结果返回后，前台再在合适时机接入。

OpenAI 的 GPT-Live 则把全双工路线带到生产规模：模型持续处理输入并生成输出，能等待用户、附和、被打断，也能处理实时翻译。它与交互模型一样，把复杂任务委派给后台模型，前台继续维持对话。

补充：⑥ Thinking Machines Lab, "Interaction Models: A Scalable Approach to Human-AI Collaboration," 2026-05。

全双工的核心变化是把「该谁说话」从外挂模块搬进模型内部。级联和 Omni 都有一个外部的「发言权判定者」（VAD）；全双工模型没有，它每一小段时间都要自己决定继续听、停顿、打断还是开口。这里对此的表述是「交互性不再依靠 VAD 等外部 harness 拼装实现，而是内建在模型中」。

「微轮次（micro-turn）」这个概念值得体会：既然不能靠 VAD 划出「大轮次」，那就用短音频块不断推进，把静音、重叠、打断都当作连续上下文保留下来。好处是模型不再需要做「非此即彼」的发言权判断，用户说话时的一点背景音、一声「嗯」，都只是上下文的一部分，不必被硬切成一个事件。

全双工与前台/后台分工天然契合：前台模型负责维持话头（等待、附和、被打断），复杂任务被委派给后台推理模型，结果回来时前台再在合适时机接入。注意「后台结果返回后，前台再在合适时机接入」，这个「合适时机」正是前台模型要持续决策的事，不能在人说到一半时硬插结果。这条线索直接引向 6.3.5 的认知时序。

时间线上可以这样排：Moshi（2024，研究先声，验证并行双音频流可行）→ 交互模型（把交互性内建，微轮次 + 委派后台）→ GPT-Live（把全双工带到生产规模，能等、能附和、能被插话、能实时翻译）。

Moshi 与交互模型要分开看。这里说 Moshi 是「研究上的先声」，Thinking Machines Lab 把「这类路线」称为交互模型（Interaction Model）。Moshi 的关键是并行建模两条音频流；交互模型强调的是微轮次、把交互性内建、委派后台。全双工的「打断」与轮次式的「打断」也不是一回事：轮次式的打断通常是「检测到用户开始说话 → 停止当前生成」（图 6-9 里 OpenAI Realtime 就是这样）；全双工的打断是模型在持续决策中自然产生的行为，不需要被外挂检测器触发。

全双工不再预设轮次，它持续听、持续说并不断决定继续/停顿/打断/调用工具：Moshi 用并行双音频流开了先声，交互模型用微轮次把交互性内建进模型并可委派后台，GPT-Live 把它带到了生产规模。

### 6.3.5 认知时序：实时交互与深度思考

「交互表现」和「智能上限」是两个维度：前台模型要在用户仍然在线时回应，后台模型则可以花更多时间思考。

下面三种方案是设计取舍，不是线性迭代；前两种可以套在级联或 Omni 上，第三种则把深度思考与实时表达统一在同一模型内部。

#### 6.3.5.1 方案一：快思考回应，慢思考回答

快思考可以在几百毫秒内先给出即时回应，慢思考则在后台完成更深的推导。它的问题是简单问题会被重复处理，复杂问题又可能出现前后不一致：快模型先建议购买，慢模型随后发现套餐缺少关键功能，用户在几秒内便听到相互冲突的答案。根本原因是两个实例各自完成了一次独立思考。

#### 6.3.5.2 方案二：快思考交互，慢思考提醒

方案二让后台模型通过状态栏或专门接口向前台模型提供建议，前台继续维持话头并决定如何表达。它比方案一稳定，但通信仍然间接：前台可能误解建议，也看不到后台的中间思考；在后台完成前，用户追问时前台仍只能依靠自己的能力应答。它可以自然地「等结果」，但不能真正做到边想边说。

#### 6.3.5.3 方案三：端到端思考与表达统一

方案三把思考能力直接内化到端到端音频模型中。Step-Audio R1 用两个互补机制解决两个问题：模态锚定思考蒸馏（MGRD）让模型基于声学特征思考，MPS 双脑架构让构思与表达并行。前者保证「想得对」，后者解决「说得及时」。

理想情况下，模型应该从音高、节奏和语调判断情绪，而不是只看转录文本。MGRD 筛选真正引用声学特征的思考过程，再用这些数据训练模型，并通过强化学习防止模型跳过思考直接猜答案。MPS 让构思脑持续产出思考片段，表达脑收到片段后结合已有回复立即生成语音。两者以流水线方式并行，因此不必等完整思考结束才让用户听到第一句话。

#### 6.3.5.4 快慢思考分离与端到端思考的取舍

统一模型最紧密地实现了「边想边说」，代价是思考和实时表达需要一起重新训练；解耦路线更容易替换后台大脑。两者是取舍，不是简单的替代关系。

在前沿思考模型快速演进的当下，快慢分离有一个重要的工程优势：它能直接承接慢模型的迭代红利。前台快模型只负责低延迟地倾听、应答和维持对话，后台慢模型负责推理、规划和工具调用；更强的思考模型发布后，只需替换后台模型，不必重新训练整套实时语音系统。统一路线则把推理与交互绑定在同一个训练周期中，每次升级都要重新兼顾智能水平、响应延迟和表达自然度。因此，快慢分离并不只是对延迟的妥协，也是一种让交互能力与智能上限分别演进的模块化选择。

这种分离也不必然牺牲任务效果。截至 2026 年 8 月，采用快慢思考分离架构的 Pine AI 语音 Agent 在 τ³-Voice Leaderboard 上取得第一名，超过 Grok Voice、GPT-Realtime-2 等实时语音系统。这个结果至少说明，在同时考察深度推理与实时对话的任务上，解耦架构并不天然落后于端到端模型。补充：⑦ Pine AI. "The Most Natural Human-Computer Interface Is Your Voice." 2026-06-23（2026-08-06 更新）。

这里需要澄清「端到端模型」常被赋予的两个含义。第一是语音通路的端到端：模型直接接收音频、生成音频，不再由多个模型通过离散文本串接。Omni 和交互模型都属于这个意义上的端到端模型，但 Omni 模型通常仍按轮次推进，交互模型则可以边听边说，二者在架构上差别很大。第二是认知架构的端到端：实时交互与深度思考是在同一模型内部共享状态、共同训练，还是拆成前台快模型与后台慢模型。两条轴彼此独立，一个系统完全可以在语音通路上端到端，同时在认知架构上保持快慢分离；Thinking Machines Lab 把复杂任务委派给后台推理模型就是这种组合。

这三种方案的排序依据是「思考与表达离得多近」：方案一是两个独立实例并行跑（最容易实现，也最容易自相矛盾）；方案二是后台给前台递建议（前台仍是表达者，但看得到的东西有限）；方案三是构思脑与表达脑在同一模型内流水线并行（最紧密，也最难训练）。强调这不是「线性迭代」，因为方案一、二可以套在级联或 Omni 上，方案三则要求重新训练一个统一模型，它们处在不同的架构层级上。

图 6-10 的失败例子值得记牢：500ms 说「建议购买」，8s 说「缺少国际漫游，不太适合」。用户听到的并非一个「更全面的答案」，自相矛盾才是实际结果。根本原因这里点得很清楚，两个实例各自完成了一次独立思考，各自的假设集不同。工程上的教训是：并行的两个思考者必须共享状态或至少共享结论，否则快的那句会先污染用户的判断。

方案一的「改进版」（慢思考当军师、通过状态栏指导快思考）为什么还是不够？因为它把理解责任推给了前台：慢思考写下一句「确认价格」，前台可能理解成「向用户确认」而不是「重新计算」。这个例子的价值在于说明间接通信是有损的，这也是方案二即便「比方案一稳定」仍然做不到边想边说的原因。

MGRD 与 MPS 这两个机制的分工可以这样记：MGRD 管「想得对」（筛选真正引用声学特征的思考过程作为训练数据，并用强化学习防止模型跳过思考直接猜答案），MPS 管「说得及时」（构思脑持续产出思考片段，表达脑收到片段就立刻生成语音，形成流水线）。MGRD 想解决的正是本节的中心问题之一：模型应该从音高、节奏和语调判断情绪，而不是只看转录文本。如果只看转录，就等于退回了级联范式的信息损失。

6.3.5.4 关于「端到端」两个含义的澄清，是本节最容易被忽略但最重要的一段。把它做成一个 2×2 表就很清楚：语音通路（级联 ↔ 端到端）乘上认知架构（快慢分离 ↔ 统一）。四个格子都成立，而「Thinking Machines Lab 把复杂任务委派给后台推理模型」正是语音通路端到端加认知架构分离的组合。

关于 τ³-Voice 的排名，这里的用法很克制，「至少说明在同时考察深度推理与实时对话的任务上，解耦架构并不天然落后于端到端模型」。需要留意的是，这里该处的依据来自厂商官方博客（补充：⑦），属于厂商自述性质的来源。

方案一（快答 + 慢答）与方案二（快答 + 慢提醒）的区别在于：方案一是两个答案各自说给用户听，会出现前后矛盾；方案二是慢思考只给前台建议，用户只听到一个声音，但前台可能误解建议、也看不到后台的中间思考。「端到端」的两个含义同样要分清，语音通路的端到端是音频进、音频出，认知架构的端到端是交互与思考在同一模型内共享状态，同一个系统可以一半端到端、一半分离。至于快慢分离是妥协还是设计，这里的结论是后者，「不只是对延迟的妥协，也是一种让交互能力与智能上限分别演进的模块化选择」。

快慢思考有三种摆法：两个实例各说各话（会自相矛盾）、慢思考幕后提醒（沟通间接）、思考与表达在同一模型内并行（最紧密但要一起重训）；而「端到端」要分语音通路与认知架构两条轴来看，快慢分离的价值是让交互能力与智能上限各自演进。

### 6.3.6 更像人的语音合成

传统 TTS 过于流畅、零停顿，反而容易暴露机器身份。停顿、填充词和偶尔的重复，是人类表达不确定性和思考状态的信号。

可以让主 LLM 在文本之外输出控制标记，例如 `THINKING`、`EMO:happy` 和 `SPEED:0.8x`，由 TTS 将它们映射为停顿、韵律、语速或笑声、叹气等非语言音频。实现上可以自研支持控制标记的 TTS，也可以用语音克隆准备不同情绪和风格的参考音频。

实验 6-7 ★★：基于 Fish Audio 的控制标记驱动 TTS。使用 Fish Audio S1 构建多参考语音库，比较无控制标记、单一参考音和多参考音三种配置。执行层根据标记选择匹配的情绪、语速和风格。

这一节把「拟人」从玄学变成了一个接口设计问题：让主 LLM 在生成文本的同时，额外产出结构化的控制标记（`THINKING`、`EMO:happy`、`SPEED:0.8x`），由 TTS 把这些标记翻译成停顿、韵律、语速、笑声、叹气。「像不像人」被拆成了两层，LLM 决定「该有什么样的表达状态」，TTS 负责「把状态变成声音」。

为什么「过于流畅、零停顿」反而暴露机器身份？因为人类的停顿和填充词（「嗯……」「这个……」）携带的是认知状态信号：我在想、我不太确定、我准备换话题了。把这些全部抹平，听感上就少了「在思考」的痕迹。这个观察其实与 6.3.2.1 的「信息丢失」是同一条主线：不要把所有信息都压成平滑的文本。

这里给了两条实现路径，可以按成本选：自研支持控制标记的 TTS（控制粒度最细，但要训），或者用语音克隆准备不同情绪和风格的参考音频（改造成本低，靠「换参考音频」切换风格）。实验 6-7 的三种配置（无标记 / 单一参考音 / 多参考音）正好构成了一个从「完全不管」到「标记 + 多参考音」的阶梯，可以直接看出各因素各贡献多少。

控制标记与参考音频的关系是配合：前者是主 LLM 输出的符号（表达状态），后者是 TTS 的音色/风格素材，执行层根据标记去选择合适的参考音频。另外，停顿和填充词与卡顿、故障要分开，前者是主动设计的「思考痕迹」，后者是系统性能问题。

拟人化的关键是让主 LLM 在文本之外输出控制标记（THINKING、EMO:happy、SPEED:0.8x），再由 TTS 映射成停顿、韵律、语速、笑声与叹气，因为停顿和填充词正是人类表达「我在想、我不确定」的信号。

## 6.4 Computer Use：GUI 自动化 Agent

语音把时机轴推到了毫秒级，但它的观察仍是一维的声音流。Computer Use 把同一个问题搬上二维的屏幕：观察变成持续变化的像素，动作变成坐标上的点击与输入。语音场景强调「何时开口」，Computer Use 则强调「下一步点哪里」，以及一个语音交互中不存在的问题，动作执行之后，现实是否还与计划一致。

Computer Use（也称 GUI 自动化 Agent）让 AI 像人类一样通过观察屏幕、操作鼠标键盘来使用软件，比如打开浏览器搜索信息、在表格软件中填写数据或在系统设置中调整配置。其核心是一个感知-思考-行动的循环（图 6-11）：

1. Agent 截取当前屏幕画面；
2. 多模态模型接收截图和任务指令，输出一段思考和一个具体动作；
3. 执行层在真实环境中执行该动作（移动鼠标、点击、输入文字等）；
4. 等待界面响应后再次截图，进入下一轮循环。

这里要区分「看懂界面」和「完成任务」。前者更接近多模态理解能力，可以用一次截图问答来测量；后者则要求模型把理解和生成动作放进闭环，处理页面加载、状态变化、误操作和不可逆后果。Computer Use 的难点因此不只是让模型在截图上答对，还要让它在每一步之后重新确认现实是否仍符合计划。

这个循环中有三个关键设计维度：动作空间（Agent 能执行哪些操作）、视觉定位（如何在截图中找到目标元素）、以及模型架构（如何从截图生成正确动作）。

这一节的「问题转移」很漂亮：语音关心「何时开口」，Computer Use 关心「下一步点哪里」，再往后 6.5 的机器人关心「动作之后世界变成什么样」。所以要抓住 Computer Use 独有的那个新问题，动作执行之后，现实是否还与计划一致。这就是为什么整个循环里必须有第 4 步「等待界面响应后再次截图」。

「看懂界面 vs 完成任务」这个区分值得反复咀嚼：截图问答是一次性的理解测试，而闭环任务要处理页面加载（还没出来）、状态变化（自己动过）、误操作（点错了）、不可逆后果（删掉了）。这四件事都不是「理解能力」能解决的，它们需要的是重新观察、校验、恢复。

图 6-11 给出的坐标示例（`click(512, 250)`）和「10–20 轮循环」的典型规模，暗示了一个重要的工程事实：Computer Use 的成本主要来自轮数。一次多步表单要 10–20 次「截图 + 推理 + 执行」，每次都要送一张截图、都要等一轮推理。这直接解释了 6.4.3 为什么要做「只在有意义的变化时截图」，以及 6.4.4 为什么要用世界模型做「推测执行」。

三个设计维度可以当成一条 Checklist：动作空间决定能不能做，视觉定位决定点得准不准，模型架构决定从截图能不能生成正确动作。6.4.1、6.4.2 分别讲前两个，第三个只在 6.4.1 的实验里以「Anthropic 参考路径 / 开放模型路径」的方式出现。

再说两个容易混的地方。看懂界面是静态理解，可用一次截图问答测量；完成任务是闭环执行，必须放进「截图—思考—动作—再截图」的循环里衡量。Computer Use 与 6.5 的机器人也都是「感知—思考—行动」闭环，但 Computer Use 的观察是屏幕像素（离散、可回滚、可截图重放），机器人的观察是连续传感器流（物理、不可逆）。这个差别决定了后面动作分块、安全停等设计的分量。

Computer Use 把闭环搬到二维屏幕上，难点在于动作之后重新确认现实是否仍符合计划，典型多步表单要 10–20 轮「截图—推理—点击」。

### 6.4.1 动作空间设计

Anthropic 的参考实现把完整交互能力分成三类工具（图 6-12）。这是一个清晰的动作空间设计，但不是模型供应商必须遵守的私有协议：只要 Harness 能把同样的截图、动作约束和执行结果转换成目标模型支持的消息与结构化输出，Claude、开放权重视觉模型和自托管端点都可以驱动同一个感知-思考-行动循环。

GUI 操作工具（computer tool）覆盖鼠标、滚动、键盘和感知动作。鼠标操作包括移动（`mouse_move`）、左/右/中键点击、双击/三击、拖拽（`left_click_drag`），以及更精细的按下/松开（`left_mouse_down/up`）。滚动（`scroll`）支持四个方向并可配合修饰键。键盘操作包括逐字输入（`type`，每个字符间隔 12ms 模拟真实打字）、组合键（`key`，如 Ctrl+C）、长按（`hold_key`）。感知动作则是截图（`screenshot`）、获取光标位置（`cursor_position`）、等待（`wait`）。

命令执行工具（bash tool）提供持久的 bash 终端会话，120 秒超时，通过哨兵字符串检测命令是否执行完毕，多次调用之间保持环境状态（比如 `cd` 到某个目录后下次调用还在那个目录）。

文件编辑工具（`str_replace_editor`）通过字符串匹配实现安全编辑，支持查看、创建、替换、插入和撤销操作，比直接覆盖整个文件更精确，不容易误改其他内容。

实验 6-8 ★：运行 Computer Use（Anthropic 参考路径或开放模型路径）。路径 A 使用 Anthropic Computer Use Demo：容器打包完整的 Ubuntu 桌面环境（含浏览器、终端等常用工具），前端接收任务，后端把指令与截图发送给 Claude，再执行模型返回的鼠标、键盘、终端或编辑动作。路径 B 使用这里的 `chapter6/computer-use-open-model` 示例代码：默认以开放权重的 Qwen3-VL 32B Instruct 驱动 browser-use，可通过 OpenRouter 托管 API，也可连接自托管的 vLLM/SGLang 等服务。

三类工具的划分逻辑值得学：操作界面（computer）、操作命令（bash）、操作文件（str_replace_editor）。它们覆盖了「用人方式使用电脑」的三条主要路径，而且在能力粒度上是递进的。鼠标键盘最通用但最脆弱（依赖坐标与像素），终端最强力但要求 Agent 会写命令，文件编辑最精确但要先知道要改哪一段。设计自己的动作空间时，这种分层比「给一堆零散工具」更好用：模型可以按「有没有更稳的路径」来选择。

「不是私有协议」这一句很重要：动作空间是 Harness 的接口约定。只要你能把截图、动作约束、执行结果翻译成目标模型支持的消息格式，同一个循环就可以换模型驱动。这也是路径 B 能成立的原因，用开放权重的 Qwen3-VL 32B 驱动 browser-use，接托管 API 或自托管推理都可以。

那些看似琐碎的参数其实都在解决真实问题。`type` 的 12ms 字符间隔是为了模拟真实打字，很多前端会检测输入速度、或对超快输入做防抖/风控处理；bash 的 120 秒超时加哨兵字符串是为了知道「命令到底跑完了没有」，否则只能靠猜或固定睡眠；持久会话是为了保留 `cd`、环境变量这类跨调用状态；`str_replace_editor` 的字符串匹配编辑是为了不整文件覆盖（6.4 后面也强调不可逆后果）。这些细节是「能用」和「好用」的分界线。

图 6-12 底部的「每个动作间隔 2–5s，人类速度的 1/3 到 1/5」是一个很值得记住的效率基准：Computer Use 目前的动作速度是人类的三分之一到五分之一。这个数字在后面 6.4.4 讨论 OSWorld-Human 的效率研究时会再次成为焦点，准确率达标不等于实用，因为太慢。

实验 6-8 的两条路径实际上对应两种工程立场。路径 A 把环境也打包好了（容器 + Ubuntu 桌面 + 前端 + 后端，直接能跑，但绑定 Claude）；路径 B 把模型换成开放权重（默认 Qwen3-VL 32B Instruct + browser-use，可托管可自托管，灵活但要自己搭环境）。选哪条取决于你要的是「先跑通」还是「可替换」。

动作空间与视觉定位要分开：前者是把能力列成清单（鼠标、键盘、滚动、等待、终端、文件编辑），后者是在截图中找到目标元素并确定坐标，这里把它们并列为三个设计维度中的前两个。`screenshot` 是感知动作，不是纯 GUI 操作，三类工具里 `screenshot`/`cursor_position`/`wait` 与鼠标键盘同属 computer tool，但它们的性质是「读」而不是「写」，把它们摆在同一工具集里，是为了让「观察」也成为循环中一个显式动作。`type` 与 `key` 也别混：前者是逐字符输入文本（12ms 间隔），后者是组合键（如 Ctrl+C），还有 `hold_key` 负责长按。

Anthropic 参考实现把动作空间分成三类工具，computer（鼠标/键盘/滚动 + 截图/光标/等待）、bash（持久会话、120s 超时、哨兵字符串）、str_replace_editor（字符串匹配的查看/创建/替换/插入/撤销）；它只是 Harness 的接口约定，把截图与执行结果翻译好，就能用别的模型驱动同一个循环。

### 6.4.2 视觉定位（Grounding）

在循环的每一轮中，模型需要在截图中准确定位目标元素，「搜索框在哪里？」「提交按钮的坐标是什么？」这就是视觉定位（Grounding）问题。当前主要有两大思路：一是把定位变成选择题，先把界面元素标注好编号，模型只需从中选一个；二是纯坐标预测，让模型像人一样直接「看」着截图报出坐标。

其中选择题思路又有两种实现方式：纯视觉标注（原始的 Set-of-Mark，用分割模型在像素上切出候选区域）和结构化元素索引（DOM/Accessibility Tree，直接读取界面自带的结构）。

选择题思路的共同优势，是把开放式的「在截图中找到按钮并预测坐标」转化为封闭式的「从已标注好的元素中选一个」。就像考试中选择题比填空题更容易答对一样，模型只需说「点击 [123]」而不是「点击屏幕 (350, 464) 处的按钮」。输出坐标对模型来说挑战尤其大，需要大量训练才能做准确，而且在不同屏幕分辨率下很容易出错。

Set-of-Mark 是视觉标注法。原始的 Set-of-Mark（SoM）由微软研究院于 2023 年提出，最初是为了释放 GPT-4V 的视觉定位能力。它是一个纯视觉方法：用图像分割模型（SAM、SEEM 等）在截图上自动切出候选区域，为每个区域叠加编号标记，模型看到的是一张带编号的图，只需报出编号，由系统换算成对应区域的中心坐标。整个过程不需要 DOM，也不需要任何界面内部结构，因此原生桌面软件、游戏界面同样适用，只要分割模型能把候选区域切出来。

结构化元素索引是 SoM 思想在 Web 上的结构化实现。当界面本身能提供结构化信息时，标注可以做得更精确。现代网页在渲染之前就已经定义了完整的元素结构（DOM 树）和语义角色（哪个是按钮、哪个是输入框），无障碍接口（Accessibility Tree）为许多桌面应用提供了类似的信息。以 browser-use 项目为代表的 Web Agent 方案正是这样做的：从 DOM 中枚举可交互元素并编号，可以看作 SoM 思想在 Web 上的结构化实现（图 6-13）。流程分四步：通过浏览器调试接口（CDP，Chrome DevTools Protocol）获取网页的结构化表示（DOM 树）和无障碍信息；自动检测哪些元素可以交互（按钮、输入框、链接等）；为每个可交互元素标注唯一 ID 并在截图上绘制边界框；同时生成文本列表描述每个 ID 对应的元素。

这里给出的示例：

```text
Screenshot: [图片中关键元素标注了[1]、[2]、[3]、[4] 等ID]
Elements:
[1] <input type="text" placeholder="Search" aria-label="Search" />
[2] <button id="submit-btn" aria-label="Submit form" />
[3] <input type="text" placeholder="Enter your name" value="" />
[4] <a href="/docs" aria-label="Documentation" />
```

模型只需要输出一个 ID，系统就会自动用该元素的中心坐标执行点击。这类方案不省 token（因为要把所有标注信息都发给模型），但定位准确稳定，还免去了分割模型可能引入的漏检和误检。

纯坐标预测是第三条路线，不做任何标注，直接让模型输出坐标。以 SeeClick 和 Claude 的 computer use 为代表：在海量 GUI 截图和元素位置的配对数据上训练视觉模型，让它学会将自然语言描述（如「点击提交按钮」）直接映射到截图中的精确坐标，就像人类用户一样，纯粹靠「看」来找到要点击的位置。

在坐标预测方案中，模型对坐标的理解高度依赖训练时使用的分辨率（图 6-14）。Claude 训练使用 XGA（1024×768）、WXGA（1280×800）、FWXGA（1366×768），如果输入的截图分辨率不匹配，模型预测的坐标就会系统性地偏移，就像在小地图上量距离然后直接用到大地图上一样。因此，需要在工具层实现双向坐标缩放机制，而且要按宽高比选目标分辨率，避免非等比拉伸把画面压变形、连带把坐标判断也带偏。例如，真实屏幕分辨率为 2560×1440（16:9），就该在 Claude 支持的三档里挑一个宽高比同样接近 16:9 的目标，FWXGA（1366×768）最匹配。截图时把屏幕等比缩放到 1366×768 送入模型；模型输出点击坐标 (683, 384) 后，反向映射为真实坐标

$$
\left(683\times\frac{2560}{1366},\ 384\times\frac{1440}{768}\right) \approx (1280,\ 720)
$$

反过来，若硬把 16:9 拉伸进 4:3 的 1024×768，画面会被横向压扁，模型预测的坐标就会系统性偏移。

三条路线的选择逻辑可以概括为：结构化信息可得时，优先用 DOM/Accessibility Tree 索引，定位最精确稳定；不可得时（原生桌面软件如 Photoshop、Canvas/WebGL 渲染的界面、游戏），既可以用视觉标注（原始 SoM 路线），也可以用坐标预测。视觉标注把定位变成选择题，对未经专门训练的通用模型更友好；坐标预测省去标注步骤，对做过 GUI 定位训练的模型更直接。两者在小元素和密集界面上的精度都仍有差距。

实验 6-9 ★：使用 browser-use 实现自动浏览器操作。基于 Playwright 浏览器自动化框架（一个用代码控制浏览器的工具库），结合多模态大模型实现自然语言驱动的浏览器操作。启用 SoM 可视化模式，每次决策前保存带标注框的截图。测试任务「打开 Google 查询旧金山天气」：系统启动后截图显示 Google 搜索页面，交互元素被编号，模型选择搜索框、输入 "San Francisco weather today"、提交搜索，再从结果页提取温度和天气状况。

三条路线可以用「定位的答案空间」来统一理解：坐标预测的答案空间是连续的像素平面（无限多可能答案）；视觉标注的答案空间是分割模型切出的若干候选区域；结构化索引的答案空间是 DOM/A11y 里可交互元素的 ID 集合（通常几十个）。答案空间越小、越规范，模型越容易答对，这正是这里「选择题比填空题容易」的类比。

Set-of-Mark 的聪明之处在于把难题分包：找候选区域交给分割模型（SAM/SEEM 这类在像素上很强的模型），选哪个交给大模型（语义理解强）。代价是分割模型会漏检和误检，而且不省 token（图里画了框、还要把图送进去）。

结构化元素索引为什么「更精确稳定」？因为 DOM 和 Accessibility Tree 直接告诉你哪个是按钮、哪个是输入框，不需要猜。代价也很明显：只有提供了结构化信息的界面才行。Canvas/WebGL 渲染的界面、游戏、以及很多跨平台自绘控件（这一点在思考题第 9 题里会再次出现）拿不到这种信息，必须回退到视觉路线。

坐标缩放这一段是本节唯一给出了完整数值演算的地方，值得自己动手过一遍（下面的数值均为这里给出，是校验过程）。真实屏幕 2560×1440，宽高比 16:9；Claude 训练的三档里，XGA 1024×768 是 4:3，WXGA 1280×800 是 1.6:1，FWXGA 1366×768 ≈ 1.779:1，最接近 16:9 = 1.778:1，所以选 FWXGA。缩放系数：横向 1366/2560 ≈ 0.5336（标 ×0.53），纵向 768/1440 ≈ 0.5333，两者几乎相同，说明这是等比缩放。模型在小图上输出 (683, 384)，反算回真实坐标就是 $683\times\frac{2560}{1366}\approx 1280$、$384\times\frac{1440}{768}=720$，即 (1280, 720)，恰好是屏幕正中心。放大系数约为 1.874（标 ×1.87）。这个例子同时也验证了「等比缩放不会扭曲画面」这一点：横向与纵向缩放系数一致，所以在小图上测出来的比例可以直接用回大图。

换个角度理解「非等比拉伸为什么会带偏坐标」：如果你把 16:9 硬塞进 4:3 的 1024×768，横向被压缩得比纵向更多，模型在小图上看到的「圆」其实是压扁的椭圆，它基于这个畸变画面学到的相对位置规律，映射回真实屏幕时就整体偏了。这里那个「在小地图上量距离然后直接用到大地图上」的比喻说的正是这种比例错配。

「不省 token」这一点在小结里也值得记住：结构化索引的精度不是免费的，它把整页元素的描述塞进了上下文。所以在长任务（10–20 轮循环）里，这会是一笔持续开销，这也是 6.4.3 提出「用文字描述画面、把截图压缩成一句话」的动机之一。

视觉标注（SoM）与结构化元素索引都属于「选择题」，区别在候选区域从哪来：前者靠分割模型在像素上切（不需要 DOM，通用但可能漏检/误检），后者靠读界面自带的结构（精确稳定，但只适用于有 DOM/A11y 的界面）。坐标预测不做标注、直接输出坐标，省一步但要求模型经过专门的 GUI 定位训练；选择题对通用模型更友好，但需要先检测并标注元素。XGA / WXGA / FWXGA 是 Claude 训练时使用的三档分辨率（1024×768、1280×800、1366×768），不是屏幕规格标准，选哪一档看宽高比是否匹配，不是看分辨率大小。

视觉定位有两条大思路：把定位变成选择题（纯视觉的 Set-of-Mark 标注，或读 DOM/Accessibility Tree 的结构化索引）与直接输出坐标；结构化信息可得时优先用索引，不可得时用标注或坐标预测，而坐标预测必须在工具层做按宽高比匹配的双向坐标缩放。

### 6.4.3 能看动画、能听声音的 Computer Use Agent

到目前为止，Computer Use 的感知都建立在一个隐含假设上：屏幕是静止的。截一张图、想一步、点一下，再截下一张图。可现实里的屏幕会放视频、会弹出转瞬即逝的通知、会播放会议里的人声。一个每 3–5 秒才睁一次眼、而且完全没有耳朵的 Agent，对这些「两帧之间发生的事」既看不见也听不到。

这里真正该被重新设计的，不是「动作接口」，而是「观察接口」。核心思想是构建 Agent–电脑观察接口（AOI），把连续的环境观察转换成模型便于处理的离散事件。其中包括几项关键技术：屏幕关键帧截图，用一个小模型判断屏幕是否发生了有意义的变化，只在显著变化时截图，变化频繁时每秒截图 1 次就能有不错的效果；音量门控的语音转写，有声音时调用语音识别，把识别出的文字放入上下文，让 Agent 能够听到声音；用文字描述画面，让模型把捕获到的屏幕截图描述成一句话，这样即使原图之后被清理出上下文，这句文字仍留在上下文里，实现了多模态交互历史压缩的效果。

补充：⑧ 论文见 Li, Bojie and Noah Shi. *Agent-Computer Observation Interfaces Enable Dynamic Computer Use.* arXiv:2606.29472, 2026.

这一节的价值在于把「感知频率」当成一等设计变量。前面几节默认「需要时就截一张图」，但真实屏幕上的变化是连续的：视频在放、通知一闪而过、会议里有人在说话。如果 Agent 每 3–5 秒才看一眼，两帧之间发生的一切都被抹掉了。

三项技术的分工很清晰，可以分别对应「看到变化、听到声音、记住历史」。关键帧截图解决「什么时候看」：用一个小模型判断屏幕是否发生了有意义的变化。注意这里的设计取舍在于变化驱动，按固定频率硬截是要被放弃的方案；「变化频繁时每秒截图 1 次就能有不错的效果」，给出了一个可用的经验频率。音量门控的语音转写解决「听」：有声音时才调语音识别，把文字放进上下文，这是典型的门控（gating）设计，用廉价的信号（音量）决定是否启动昂贵的处理（ASR）。用文字描述画面解决「上下文太长」：把截图压缩成一句话。收益是即使原图被清理出上下文，这句话还在，这就是「多模态交互历史压缩」。对 10–20 轮的长任务来说，这条极其重要，否则上下文会被历史截图撑爆。

本节的核心判断是观察接口而非动作接口，这也呼应了第一章的论断：扩展观察空间往往比扩展动作空间更有效。你可能会本能地想去加更多点击/拖拽动作，但这里真正的瓶颈是「Agent 看不到两帧之间发生的事」。

固定频率截图与关键帧截图的区别在于：前者按时间间隔截（简单但浪费，画面没变也截），后者用一个小模型判断「是否有意义的变化」再截（省算力与上下文，但需要一个判断模型）。截图与画面文字描述也要分开看：截图信息全但占上下文且可能被清理；文字描述有损但持久。这里的用法是两者配合，原图可能被清出上下文，文字留下作为长期记忆。

屏幕不是静止的，所以该重新设计的是观察接口（AOI）：用小模型做关键帧截图（变化频繁时每秒 1 次即可）、用音量门控的语音转写让 Agent 听到声音、用一句话描述画面来实现多模态交互历史的压缩。

### 6.4.4 Computer Use 的世界模型

上一节的观察接口解决的是「屏幕中间发生了什么」：通过关键帧、语音转写和持久文字，让 Agent 不再只看到两张相隔很久的截图。但观察接口并不会消除规划延迟，Agent 仍然是串行的「截图—思考—点击」循环，每执行一个动作都重新观察、思考下一步。OSWorld-Human 的效率研究显示，即使任务最终成功，Agent 的操作步骤仍明显多于人类，等待时间也更长；准确率达到人类水平，并不等于已经足够实用。

人类操作电脑时不会点击之后才开始想下一步，他会先对动作后果作出预测：如果实际变化与预期一致，就沿着原定计划继续执行；只有发现页面状态偏离预期，才停下来重新观察和规划。世界模型让 Agent 能够在行动前预测桌面接下来可能变成什么，从而实现这种类似于人类的「推测执行」机制，大大提高效率。

桌面状态不只是一张像素图，还包括窗口、焦点、滚动位置、输入框内容、加载状态、权限和网络返回；动作则包括点击、键盘输入、滚动、拖拽和等待。一个可用于 Computer Use 的世界模型至少要能编码当前状态、预测候选动作造成的状态变化，并把预测交给规划器决定下一步：

```text
桌面状态 + click/type/scroll/wait ──> 下一状态的表示
```

这样，Agent 就能在真正点击之前比较候选动作的后果，在页面加载期间准备下一步，并在弹窗一闪而过时根据状态差异恢复。例如任务是「在 VS Code 新建 Python 文件并写入 hello world」，模型可以先预测文件树和编辑器在成功后的关键状态，再选择点击、输入和保存动作；如果任务是删除文件，则可以先在隔离的虚拟桌面中预测是否会出现不可逆确认框，必要时请求用户确认。这里的重点不是让模型生成一张逼真的未来截图，而是预测完成任务所需的、可检查的状态差异。

2026 年 7 月，Induction Labs 公布的 Photon-1 展示了这条路线的一种实现，仅用 3 万小时的 H200 GPU 时间就完成了 computer use 世界模型的预训练。它把每帧压缩为离散的潜在 token，自回归预测动作之后的下一状态表示，而不是在预训练阶段逐像素生成截图；另外接入的图像生成器只用于把潜在表示可视化，并非推理必需组件。给定一张种子截图和后续动作，模型可以连续「想象」桌面状态，再通过虚拟机上的在线训练学会输出 computer-use 动作。

补充：⑨ David Li and Jonathan Li, Induction Labs, "Scaling Video Pretraining with Imagination Models," 2026-07-23。文中 Photon-1 的参数、数据规模、内部 benchmark 和成本比较均为公司披露的结果。

本节与 6.4.3 的关系值得先说清：6.4.3 解决的是「看不见两帧之间的事」，6.4.4 解决的是「每走一步都要重新想」。前者是观察密度问题，后者是规划延迟问题。这里明确说「观察接口并不会消除规划延迟」，所以这两节管的是两个不同的瓶颈，彼此不能替代。

世界模型在这里的定位非常具体：它是一个「动作结果预测器」，输入「桌面状态 + 候选动作」，输出「下一状态的表示」。它的三个直接用途这里都给了：点击前比较后果（选风险小的）、加载期间准备下一步（把等待时间利用起来）、弹窗一闪而过时根据状态差异恢复（没截到也能推出来）。

特别要记住那句「重点不是让模型生成一张逼真的未来截图，而是预测完成任务所需的、可检查的状态差异」。这句话把 Computer Use 的世界模型与「视频生成模型」明确区分开了：前者要的是可用于决策的状态差（文件树变了没、确认框出现了没），后者要的是视觉真实性。追求逼真截图既昂贵又无必要。

「删除文件先预测不可逆确认框」这个例子很好地展示了世界模型与安全的结合：别等确认框弹出来再手忙脚乱，先在隔离虚拟桌面里推演，如果预判会触及不可逆操作就请求用户确认。这与 6.4 引言里「区分看懂界面与完成任务」中提到的「不可逆后果」是同一条安全线索。

Photon-1 的细节里有两个工程点很值得注意。它预测的是「下一状态表示」而不是像素（每帧压成离散潜在 token，自回归预测），所以那个图像生成器只是可视化工具、不是推理必需组件；另外是 3 万小时 H200 GPU 时间这个量级（这些参数与成本比较均为公司披露的结果）。它提到「通过虚拟机上的在线训练学会输出 computer-use 动作」，说明这套预训练表示最终还是要接到动作学习上才能用。

OSWorld-Human 的结论是本节的问题陈述：成功不等于实用。这里的措辞是「即使任务最终成功，Agent 的操作步骤仍明显多于人类，等待时间也更长」。这句话把 Computer Use 的评价标准从「成功率」扩展到了「步骤数 / 等待时间」，也预告了机器人那一节会出现的效率类指标（完成步数、路径长度）。

观察接口（6.4.3）与世界模型（6.4.4）是互补的：前者提高观察密度（关键帧、声音、文字描述），后者降低规划延迟（提前预测后果、推测执行），都不能替代对方。世界模型预测的「下一状态表示」也不是「下一帧截图」，这里明确不要后者，前者是可检查的状态差异（窗口、焦点、输入框内容、加载状态等），后者是像素。成功率与实用性同样不等价，OSWorld-Human 的结论就是任务成功但步骤多、等待长，仍然算不上实用。

观察接口解决「两帧之间发生了什么」，世界模型解决「每走一步都要重新想」：它预测的是完成任务的、可检查的状态差异（不是逼真截图），用来在点击前比较后果、在加载时准备下一步、在弹窗闪过时恢复。

### 6.4.5 移动端：生态壁垒比技术更难

Computer Use 也在向移动端扩展。移动端与桌面在技术上确有差异。动作空间通常不再是「鼠标坐标 + 键盘」，而变成接入系统的无障碍服务 API（如 Android 的 AccessibilityService）来读取界面元素、下发点击与文本输入；交互方式也从鼠标指针变成触摸手势，坐标的语义随之改变，同一个 (x, y) 到底是手指的单击、长按，还是滑动手势的起点，需要额外的手势类型来界定。第七章介绍的 AndroidWorld 等移动端基准，正是在这样的动作空间上评测 Agent 完成真实应用内任务的能力。

但真正卡住移动端的往往另有其物，是生态壁垒。曾有手机厂商尝试在消费级手机中集成 AI 助手，让它自动操作微信、淘宝、支付宝等日常应用，但很快遭遇平台限制。

这揭示了 Computer Use 面临的一个独特挑战：生态壁垒。封杀背后的根本原因是商业模式冲突。传统互联网应用的核心变现逻辑是流量与注意力：用户刷信息流时看到广告，搜索商品时跟随推荐算法的引导，浏览页面时产生冲动消费。而当 Agent 代替用户操作时，这条变现链路被彻底绕过：AI 不会关注广告，也不会冲动消费，直奔目标完成任务就走。对于靠广告和流量变现的平台来说，Agent 的每一次操作都在侵蚀其商业模式的根基。

这意味着 Computer Use 面对的不仅是 CAPTCHA（验证码）等技术层面的对抗，更是一个结构性的利益冲突。这一矛盾在短期内难以调和，也让 Computer Use 在消费级场景中的落地面临比纯技术问题更棘手的挑战。

技术差异那一小段可以拆成两点：读界面的方式变了（不再靠截图 + DOM，改成接系统无障碍服务 API），动作的语义变了（不再是一个坐标一个点击，改成坐标 + 手势类型）。第二点容易被低估：在桌面上 (x, y) 基本等价于「点这里」，而在手机上同一个坐标可能是点、长按、滑动的起点或终点，必须多带一个手势类型参数，动作空间因此变复杂了。

生态壁垒这一段是本章很特别的一节，它讲的是非技术瓶颈。这里的论证链条很干净：平台靠流量与注意力变现（广告、推荐、冲动消费）→ Agent 代操作绕过了这条链路（不看广告、不冲动消费、办完就走）→ 封杀的根子是商业模式冲突而不是技术缺陷 → 所以矛盾是结构性的，短期难以调和。

这条分析对做产品的人有直接含义：即使你的 Computer Use 技术在移动端做得很好，也可能因为平台不允许而无法落地。这里把它与 CAPTCHA 并列，技术对抗（CAPTCHA、IP 信誉）是可以想办法绕的（住宅代理、更拟人的操作节奏），但利益冲突不能靠技术绕。这也呼应 6.2.5 里的反机器人机制：那里讲的是「怎么绕过检测」，这里讲的是「就算绕过了，也没人愿意让你过」。

移动端的技术挑战与生态挑战要分开：前者（无障碍 API、手势类型）是工程问题，有明确解法；后者（平台封杀）是商业问题，技术上无解。这里的判断是后者才是真正卡住移动端的。另外，AccessibilityService 与桌面的 DOM/Accessibility Tree 名字相近，作用也相近（都是读取界面元素结构 + 下发操作），但一个是移动端系统级服务，一个是桌面/Web 的界面结构接口。

移动端 Computer Use 的技术差异（接 AccessibilityService、动作要带手势类型）都好解决，真正卡住它的是生态壁垒：Agent 绕过广告与推荐这条变现链路，平台因此封杀，这是结构性的商业冲突，不是技术对抗。

## 6.5 机器人操作：以 XLeRobot 整理桌面为例

本节从头到尾只用一个任务：把红色杯子放进托盘，把黄色废纸放进垃圾盒，最后重新观察并确认桌面状态。它在五个实验里反复出现，真机和模拟跑的是同一套题目。这里的阅读提示先交代了实验分工：实验 6-10 和 6-12 是 XLeRobot 真机实验，需要机械臂、标定、急停装置和现场观察员；实验 6-11、6-13 和 6-14 是对应的本地 GPU 实验。真机与模拟的结果会明确分开报告，任务目标、动作语义和成功条件则保持一致，这是横向比较的前提。

机器人操作比“看图回答问题”难得多。模型不但要看懂画面，还得在真实世界里连续做出动作，而每个动作都会改变下一刻的情况。XLeRobot 把这种区别摆得很具体：同一台机械臂既可以由人通过键盘、手柄或 VR 设备遥操作，也可以把摄像头观察和一组受约束的动作工具交给 Agent 自主调用。硬件和任务都不变，改变的只是操这里。前者由人持续观察和纠错，后者必须由模型与控制系统完成同样的工作。

五个实验排成一条线。先让人遥操作真实 XLeRobot，量出真机在足够强的操这里手里能做到什么；再在模拟器里建立同一任务的理想控制上限。接着让 Agent 自主控制真实 XLeRobot，看感知、规划和失败恢复如何影响结果；然后把相同的工具契约放进模拟器，批量比较开环、逐步检查和世界模型三种策略。最后改背景、物体外观、光照和视觉噪声，检查模拟里学到的视觉策略能不能适应新环境。

这里的瓶颈很少落在再给模型加一个静态问答基准上。真正的难点是让它在有限的感知和控制带宽下持续完成闭环。一个能用的机器人系统至少要回答四个问题：人想完成什么任务，接下来先做哪个子任务，当前技能具体输出哪些动作，动作执行后现实是否仍符合原来的计划。本节把这四个问题放进 XLeRobot 的同一个控制闭环里，分别说明四种技术各自负责什么。长程规划安排先处理杯子还是废纸，VLA 或动作原语完成抓取和放置，世界模型估计动作后果，从仿真环境迁移到现实环境则处理训练画面和真实摄像头、执行器之间的差异。即使高层模型已经具备足够的知识和规划能力，只要缺少其中任何一个反馈环节，系统仍可能无法把任务做完。

这一节的实验设计骨架值得先看懂，后面七个小节都是它的展开：两条参考线加三次对照，其中最后一次是跨环境测试。两条参考线是实验 6-10（真机上人类闭环，代表任务上限）和实验 6-11（模拟中理想闭环，代表理想控制上限）。三次对照分别是实验 6-12（Agent 自主控制真机，与 6-10 比“人类闭环与模型闭环差什么”）、实验 6-13（同一契约放进模拟器，比较开环、逐步检查与世界模型）和实验 6-14（换背景、外观、光照、噪声，测视觉策略的泛化）。所有实验共用同一个任务和同一套成功条件，这里的阅读提示特意强调了这一点。

那四个问题其实是把具身任务拆成了四层：任务是什么（目标）、先做哪一步（规划）、这一步怎么动（技能与动作）、做完对不对（校验）。读 6.5.2 那张分层表时可以对照着看，那张表的五行正好是这四个问题加上底层的稳定执行。

硬件方面，XLeRobot 在这里被描述为“成本只有几百美元”的机械臂。

> 来源确认：XLeRobot 是真实存在的开源项目，其 GitHub 仓库副标题为 “XLeRobot: Practical Dual-Arm Mobile Home Robot for \$660”，与这里“成本只有几百美元”的描述一致。（来源：[Vector-Wangel/XLeRobot](https://github.com/vector-wangel/xlerobot)）

“反复观察与纠错”是人类操这里的核心能力，也是本节全部实验的对照基准。人能减速、能修正抓取点、能发现没夹住并重试；Agent 必须把这些做成显式的检查与重试逻辑，也就是 6.5.3 里的 `verify_state` 和实验 6-13 的三种闭环策略。

还有一处容易被归错：实验 6-10、6-12 是真机，需要硬件、标定、急停、观察员；6-11、6-13、6-14 是本地 GPU 模拟。这里强调两者的任务目标、动作语义、成功条件一致，但结果不能互相直接代入。同样叫“上限”，含义也不同。人类闭环（6-10）代表真实硬件上能达到的上限，含操这里的技能与耐心；理想控制器（6-11）代表感知与决策都正确时的上限，不含感知误差。

## 6.5.1 硬件与算法的分工

XLeRobot 最适合回答的第一个问题是：自主整理桌面失败时，究竟是机械臂本身做不到，还是算法没有把它用好？

这里有一个不容忽视的事实。像 XLeRobot 这样成本只有几百美元的机械臂，通过遥操作已经能够完成本节这种连续的多步桌面任务：人看着摄像头画面，抓起红色杯子放进托盘，再把黄色废纸放进垃圾盒，最后重新确认状态。这个结果不只是说明硬件勉强具备可行性，它本身就是一条明确的诊断证据。对这个任务来说，硬件本体不是瓶颈，算法才是瓶颈。

诊断方法很直接：保持摄像头、机械臂、夹爪、桌面布置和成功条件不变，先让人接管闭环。人类会持续修正物体定位、动作选择和时机控制，并处理抓取失败。自主系统与人的差距，正体现在这些闭环能力上。这个判断仅限于本节的桌面任务：它说明硬件已经跨过了完成该任务所需的负载、精度和工作空间门槛，并不意味着几百美元的机械臂能胜任所有开放环境或更高难度的操作。做实验结论时，把适用范围说清楚和结论本身同样重要。

XLeRobot 支持的遥操作入口有键盘、Xbox 手柄、Switch Joy-Con 和 VR 设备。人类操这里会自然地做很多算法必须显式实现的事：夹爪靠近杯子时减速，杯子滑动时修正抓取点，第一次没夹住纸张时重新观察，物体放入目标区域后检查结果。这四件事可以直接当作做机器人 Agent 时的检查清单，后两条（重新观察、检查结果）在软件 Agent 里常常被偷懒省掉。遥操作因此不只是收集演示数据，它本身就是一种“固定硬件、替换操这里”的诊断实验。很多人把遥操作只当成数据采集工具，为模仿学习准备演示，这里指出它还能充当基准测试：固定硬件、替换操这里，看差距落在哪。

补充：⑩ XLeRobot, “Teleop 文档”.

**实验 6-10 ★：真机遥操作 XLeRobot 整理桌面。** 在真实 XLeRobot 工作区内放置红色杯子、托盘、黄色废纸和垃圾盒，操这里通过一种校准完成的遥操作方式执行固定任务：“把红色杯子放进托盘，把黄色废纸放进垃圾盒，最后重新观察并确认桌面状态。”实验至少重复多轮，记录摄像头画面、操这里输入、机械臂状态、动作时间、抓取失败、重试次数和最终状态。验收不能只看“最后桌面似乎收拾好了”：红色杯子必须位于托盘内，黄色废纸必须位于垃圾盒内，机械臂回到安全姿态，而且全程没有碰撞、越界或未经确认的人工代做。

那四条硬条件值得单独学。它是可检查的验收条件和“看起来成功了”之间的区别，后者在机器人场景里几乎一定会骗人：东西可能被撞到托盘边沿，也可能有人偷偷帮了一把。

**实验 6-11 ★：在模拟器中测量同任务的理想控制上限。** 在二维桌面模拟器中随机摆放红色杯子、黄色废纸及其目标区域，由理想控制器依次接近物体、抓取并移动到正确位置。它不需要识别图像，也不会选错动作，因此代表“感知和决策都正确时，这个任务至少可以做到什么”。实验关注任务成功率、完成步数和路径长度，并改变物体初始位置与任务规模，观察理想上限是否稳定。它和实验 6-10 使用相同的成功条件，但测量的是理想化模拟结果，不代表 XLeRobot 真机已经运行。

真机遥操作得到的是最有说服力的任务上限，可它不适合批量改变物体数量和位置。为了得到可重复、可统计的对照，下一步把同一个“物体归位”问题搬进二维桌面模拟器，用理想控制器代表一个不会感知错误、不会选错动作的强操这里。两条参考线到这里就齐了：实验 6-10 是真实硬件上的人类闭环，实验 6-11 是模拟环境中的理想闭环。

理想控制器是个很聪明的对照设计。它不看图，也不会选错动作，所以它测的是任务本身的难度下界，以及理想策略的效率，也就是成功率、完成步数和路径长度。把它和 6-10 并置，一边是真实硬件上的人能做到什么，另一边是理想情况下物理任务要求多少步。

### 6.5.2 机器人控制的基本结构

机器人系统通常会把不同时间尺度的工作分开：

| 层级 | 核心问题 | 输出 | 典型时间尺度 |
| --- | --- | --- | --- |
| 任务目标 | 人想完成什么 | “把杯子和废纸归位” | 分钟级 |
| 长程规划 | 先做什么、后做什么 | 先处理杯子，再处理废纸，最后检查 | 秒到分钟 |
| 基本技能 | 当前要完成哪个状态变化 | `pick(red_cup)`、`place(red_cup, tray)` | 约 1—3 秒 |
| VLA / 技能策略 | 这个技能具体怎么动 | XLeRobot 夹爪的一小段动作或连续轨迹 | 约 1—10 Hz 推理 |
| 底层控制与安全层 | 如何稳定、及时地执行 | 关节或末端控制量、限速与急停 | 约 50—1000 Hz |

这张表的核心是**时间尺度**的分离，从分钟级一路排到 50–1000 Hz，跨度超过三个数量级。之所以要分层，是因为不同频率的需求互相冲突：高层规划可以想上几秒钟，底层控制必须每毫秒都稳。把它们塞进同一个模型，要么高层被高频细节淹没，每次关节微调都要过一遍大模型；要么底层被推理延迟拖垮，等大模型想完，杯子已经掉了。表格的后三列正好回答了每层各自负责什么：核心问题（thinking）、输出形式（representation）、时间尺度（rate）。记住这个结构，再看 6.5.3 的长程规划、6.5.4 的 VLA 和 6.5.6 的世界模型，就能各归其位。

这里补了一句限定：这是一种常见的工程分工，不是唯一的模型架构。VLA 可以承担一部分高层判断，规划器也可以是规则程序、VLM 或优化器。所以这张表要理解成职责分离的原则，别当成必须照抄的组件清单。

模型不应直接输出任意关节角，这是本节最重要的一条工程约束。任意关节角意味着无限大的动作空间，模型很难学，也很难保证安全；而 `pick`、`place`、`verify_state`、`stop` 是**有边界的技能**，离散、语义明确、可校验。中间再加一层经过标定、限速并带超时的执行器，就把模型的不确定性挡在了硬件之外。这个思路和 6.4.1 里 Computer Use 用结构化动作空间而不用裸坐标是一致的。

基本技能和 VLA/技能策略也要分清。基本技能定义的是要完成哪个状态变化，离散、语义级；VLA 定义的是这个技能具体怎么动，是连续轨迹。6.5.4 会把这一点讲透。频率上同样别混：高层推理约 1—10 Hz，底层控制约 50—1000 Hz，差了一两个数量级，这正是“动作分块”存在的原因。

### 6.5.3 长程规划与任务分解

用户说“把桌面整理干净”时，系统不能把这句话直接交给动作模型。规划器要先列出场景中的物体和目标，再决定先后顺序，并为每一步写清楚开始条件、完成条件和风险限制。例如：

```text
处理红色杯子 → 清理黄色纸张 → 检查桌面
```

“处理红色杯子”还要继续拆成两个动作和一次检查：

```text
pick(red_cup) → place(red_cup, tray) → verify_state
```

每完成一个技能，就得到一个可以检查的节点。抓取失败，只重试当前这一步；物体被人挪动，或者用户改了目标，只需要重新规划受影响的后续步骤，不必把旧计划全部重做。给智能体的工具也应该足够简单：一次调用只做一件事，动作范围固定，有超时限制，执行后立即重新观察。

这几条放在一起，本质上是在限制错误传播。开环计划最怕的就是一次局部失败被一路带到任务末尾，这里在实验 6-13 里正是这么描述的。把计划切成可检查的节点，相当于在每个节点上设了一道闸门：不通过就不往下走。另外两件事也顺带清楚了：抓取失败属于执行层面，重试当前这一步就够；物体被挪动或目标改了属于计划层面，要重规划受影响的后续步骤。而 `verify_state` 换来的是新的观察，模型自己说过的话不算数。

**实验 6-12 ★★：使用 Gemini Robotics-ER 1.5 驱动 XLeRobot 自主整理桌面。** 保持实验 6-10 的真实 XLeRobot、桌面布置、任务指令和成功条件不变，把人类操这里替换为 Agent。可以用 Gemini Robotics-ER 1.5 这类具身推理模型负责观察和规划，通过 RoboCrew 风格的智能体循环只开放五个工具：`observe_scene`、`pick`、`place`、`verify_state` 和 `stop`。

模型先观察桌面，决定处理顺序，再调用经过标定的 XLeRobot 抓取和放置动作。每完成一个技能都必须重新观察并检查后置条件；抓取失败时只能重试当前技能；用户喊停、物体离开工作区或状态无法确认时，必须调用 `stop`。模型不能直接输出任意关节角，也不能仅凭自己先前说过“已经完成”就跳过真实检查。验收标准与实验 6-10 完全相同：杯子位于托盘内、废纸位于垃圾盒内、机械臂回到安全姿态且没有碰撞或越界。

区别在于，自主实验的任务语义必须来自模型观察，真实动作必须来自工具调用，最终状态必须由新观察确认。人只能负责启动、急停和安全监护，不能在中途代替 Agent 完成动作。做到这些，实验 6-10 与 6-12 才能直接比较：同一硬件、同一任务，人类闭环与模型闭环之间还差什么。

补充：a：Google DeepMind, “Gemini Robotics-ER 1.5”；XLeRobot, “LLM Agent 控制”。XLeRobot 上游示例展示模型与工具调用的编排方式；本节保持同一编排原则，但把动作工具限定为经过标定的桌面抓取、放置、检查和停止原语。

这个设计里有几处细节特别值得学。只开放五个工具，动作空间被限定得极小，每个工具都对应一个语义明确的技能；“每完成一个技能都必须重新观察并检查后置条件”把校验写成了强制流程，不依赖模型自觉；“不能仅凭自己先前说过'已经完成'就跳过真实检查”则直指一类失败模式，模型在轨迹里说过“已完成”，后续就默认真的完成了，这跟人“号称做完了”的风险是同一类；人的角色被严格限定为启动、急停、安全监护，否则实验 6-10 与 6-12 就无法比较，这也正是实验 6-10 验收条件里“未经确认的人工代做”要排除的东西。

真机实验能暴露标定误差、相机遮挡和夹爪失败，却很难安全、可控地重复大量故障。后面的模拟实验会保留这五个工具和完全相同的任务状态，只把真实执行器换成可注入失败的桌面环境，用来拆解开环执行、逐步检查和动作预测各自贡献了什么。真机负责真实性与暴露真实故障，模拟负责可控重复与策略对照，二者的分工就在这里。

### 6.5.4 VLA 控制

VLA 是 Vision-Language-Action 的缩写，中文可以理解成“视觉—语言—动作模型”。它接收当前画面和一条技能指令，然后输出机器人接下来要执行的动作：

```text
当前观察 + 技能指令 → 动作
```

在 XLeRobot 的例子里，高层规划器只提交 `pick(red_cup)`，VLA 或技能策略还要根据当前画面决定从哪个方向接近杯子、夹爪何时闭合、手臂以什么轨迹抬起。执行层完成这一小段运动后，系统会重新拍摄桌面；只有确认杯子确实被夹住，规划器才允许提交 `place(red_cup, tray)`。这里把 VLA 和技能策略并列着写（“VLA 或技能策略”），两者都负责这个技能具体怎么动；VLA 是学习方法的一种实现，技能策略也可以是别的形式。这两层的分工可以说得很干脆：工具调用定义的是期望的状态变化，VLA 定义的是如何通过连续动作实现这个状态变化。

用一句话说清就是，`pick(red_cup)` 讲的是目标状态，杯子要被拿起来；VLA 讲的是运动过程，从哪个方向接近、什么时候闭合、怎么抬起来。前者离散、可检查，后者连续、难检查。而“只有确认杯子确实被夹住才允许提交下一步”把校验的位置点得很明白：校验放在技能边界上做，不放连续动作内部做。连续动作中间的状态很难用语言判定对不对，技能完成后（比如 `verify_state` 观察一次）却是明确的。

路线选择上，RT-2 和 OpenVLA 把连续动作切成离散的 token，再像生成文字一样逐个输出；π₀ 代表另一条路线，直接生成连续、平滑的动作轨迹。两种方法没有简单的高下之分：离散 token 更容易和语言模型结合，连续轨迹通常更适合表达平滑运动。可以把它们想成“把动作当外语单词”还是“把动作当曲线”。前者把连续动作离散成 token，于是能直接复用语料训练出来的语言模型架构，代价是离散化损失了平滑性；后者直接回归连续轨迹，平滑自然，与语言模型的结合则没那么顺。这里的评价是“没有简单的高下之分”，这里不必预设结论。

补充：⑪ Moo Jin Kim et al. *OpenVLA: An Open-Source Vision-Language-Action Model.* arXiv:2406.09246, 2024.

大模型每秒通常只能推理 1—10 次，而传统控制器每秒可能要更新几十到上千次。工程上常用**动作分块**来弥合这个差距：模型一次生成一小段未来动作，控制线程按较高频率执行这一小段，模型则在后台准备下一段。这样就能把一部分推理等待藏在动作执行时间里。数据流走一遍是这样：大模型看着当前画面加技能指令，一次生成未来若干步的动作；控制线程按几十到上千 Hz 回放这一小段；与此同时模型在后台准备下一段。模型的 1—10 Hz 推理频率因此不必等于控制的 50—1000 Hz 频率。

代价这里也讲得很清楚。动作段越长，运动越平滑，模型在这段时间里看到的新画面却越少。如果 XLeRobot 伸手抓杯子时杯子被碰动，它可能仍在执行根据旧画面生成的动作。所以动作分块是在平滑性和反应速度之间做取舍，谈不上没有代价的加速，它把反应延迟换成了动作平滑。6.5.5 紧接着要讲的 VLA 局限里，“观察可能过时”就是动作分块的直接副作用。

### 6.5.5 VLA 的局限

“长程规划 + VLA”是一个实用的基本方案，但仍有几个容易被忽略的问题，按数据、目标、平台、时序四层来看比较清楚。

训练数据有限。机器人演示远少于互联网文本和图像数据，这是规模上的鸿沟。模型见过“杯子”这个词，不代表它见过各种材质和摩擦条件下的杯子，词汇层面的知识和物理层面的经验不是一回事。

只学会模仿，不一定懂后果。**行为克隆**主要学习示范者下一步怎么做，它的目标函数里并没有明确要求模型回答“这个动作会造成什么结果”。所以模型可以模仿得很像，却不知道这个动作会带来什么。这正好和 6.5.6 世界模型的动机互补。

机器人各不相同。不同机器人有不同的自由度、坐标系、夹爪和执行器延迟，同一个动作不一定能直接搬到另一台机器人上，这也是 6.5.2 强调执行层要“经过标定”的原因。

观察可能过时。动作块开始执行后，物体可能被移动、遮挡或碰倒，但模型仍在依据上一帧画面做决定。这跟 6.4.3 里 Computer Use 的“屏幕在两帧之间变化”是同一类问题在不同模态上的表现：那边是屏幕变了没看到，这边是物体被挪动、碰倒而仍按旧画面执行。它也呼应了 6.1 表格里机器人那一行的“传感器连续回流”。

所以，语言模型知道“杯子”是什么，并不代表它知道摩擦、接触、液体晃动和电源线会怎样改变未来状态。这一句区分了语义理解和物理预测。紧接着是分工：VLA 主要回答“现在应该做什么”，还需要另一类模型帮它判断“做了之后可能发生什么”。模仿和后果预测可以互补，不能互相替代，这就是 6.5.6 的引子。

### 6.5.6 世界模型

可以把世界模型理解成一个“动作结果预测器”。它学习的是：在当前状态下采取某个动作，下一刻的状态可能怎样变化。

```text
当前状态 + 候选动作 → 预测下一状态或未来片段 → 比较候选结果 → 选择动作、重新规划或安全停止
```

一个能用于机器人的世界模型，至少要能看懂当前状态，能预测不同动作可能带来的结果，还要能把这些预测交给规划器或控制器，帮它们做选择。这三点其实是接口要求：如果你的预测没法交给规划器做选择，那它就不是可用的世界模型，只是一段预测。

只会描述视频的 VLM，或者只会生成画面的模型，并不会自动变成可靠的机器人世界模型。它还必须知道动作是什么，并且能预测动作对物体和环境的影响。差别就在输入里有没有“动作”这个变量：一个只会描述或生成画面的模型学不到动作对物体和环境的影响。V-JEPA 2 代表在内部状态中预测未来的一条路线，World-Action Model 则明确学习“动作—未来观察”的关系。这些模型可以和 VLA 配合使用，不需要取代 VLA。

补充：⑫ Meta AI, “Introducing the V-JEPA 2 world model and new benchmarks for physical reasoning,” 2025-06-11；V-JEPA 2 技术报告：arXiv:2506.09985.

在实际系统中，世界模型通常有三种用法。动手前，比较抓取、推动、等待等候选动作，优先选风险更小的方案；执行时，把真实观察和预测结果对照，发现偏差就缩短动作、停止或重新规划；训练时，利用视频、仿真数据和失败轨迹学习状态变化，减少真机上的试错次数。这三条按时间排成一条线，其中“执行时”那条把世界模型和执行监控连了起来，它也正是动作分块那个“观察过时”问题的缓解手段：预测与观察不符，就立刻缩短当前动作段。

回到 XLeRobot 的桌面任务。如果黄色废纸被红色杯子部分遮住，系统可以比较“先抓纸”“先移动杯子”和“换一个抓取方向”几个候选技能。世界模型不需要生成一段逼真的机器人视频，只要能预测哪些候选动作更可能让纸张变得可抓取、哪些动作可能碰倒杯子，就已经能帮规划器排序了。动作执行后，真实摄像头观察仍然是最终事实；预测只能帮助选择，不能代替验收。

世界模型给出的是“如果这样做，可能会发生什么”的可比较预测，拿不到确定答案。边界这里划得很清楚：它能给排序依据，不能给验收；预测得越远，误差通常越大；一段看起来逼真的未来画面，也可能不符合真实的接触和摩擦规律。所以实际系统仍然需要短期预测、实时观察、对不确定性的估计，以及独立的硬件安全控制器。生成式世界模型可以拿来做交互式仿真或可视化，但不能把“会生成视频”和“能指导机器人动作”混为一谈，更不能让它兼任安全控制器。

补充：⑬ Jack Parker-Holder and Shlomi Fruchter, Google DeepMind, “Genie 3: A new frontier for world models,” 2025-08-05；Zachary Lin et al. *Cosmos World Foundation Model Platform for Physical AI.* arXiv:2501.03575, 2025.

**实验 6-13 ★★：在模拟器中比较三种自主整理桌面的闭环。** 把实验 6-12 的任务、对象状态、成功条件和五个工具原样放进桌面模拟器，只把真实 XLeRobot 执行器换成可控的模拟执行器，并让抓取偶尔出现可恢复的瞬时失败。这样可以在不改变问题的前提下比较三种策略：

- **开环执行**：一次生成完整动作序列，中途不重新观察；
- **逐步检查**：在每个 `pick` 和 `place` 之后重新读取状态，失败时只重试当前技能；
- **预测式执行**：再增加一个短期世界模型，先比较候选技能的预期结果，再选择下一步。

实验比较任务成功率、工具调用开销和失败恢复能力，并检查最终成功是否都由 `verify_state` 的新观察确认。这个实验的目标并不大，它要验证的是一个更基础的关系：开环计划会把一次局部失败带到任务末尾，逐步检查能够恢复，动作预测则可以进一步帮规划器为候选技能排序。最终是否真的完成，仍然必须由环境反馈决定。

> 来源确认：V-JEPA 2 确为 Meta 于 2025-06-11 发布的真实世界模型（补充：日期与之一致）；Meta 官方与技术报告均以“world model + 物理推理基准”定位该工作。（来源：[Meta 推出世界模型 V-JEPA 2](https://www.stcn.com/article/detail/1968677.html)）

### 6.5.7 从仿真环境到真实机器人

实验 6-13 即使在模拟器里表现稳定，也不能直接推出实验 6-12 的 XLeRobot 真机会同样成功。从仿真环境走到真实机器人，要处理的是两个环境之间的差异，换一种控制器解决不了这个问题。

训练时可以使用遥操作数据、视频数据或仿真交互数据；真正部署时，同一个红色杯子、黄色废纸、托盘和垃圾盒会出现在不同的背景、光照、相机位置和遮挡关系中，机械臂还会遇到不同的摩擦、传感器噪声和执行器延迟。只要这些差异足够大，模拟中学会的动作就可能在现实中失效。

差异清单可以按“看着不同”和“动着不同”分两类。视觉侧有背景、光照、相机位置、遮挡关系，加上实验 6-14 里单列的物体外观和视觉噪声；物理侧有摩擦、传感器噪声和执行器延迟。前者影响看到什么，后者影响动了之后会怎样，这正好对应 6.5.6 里世界模型要处理的两件事。

**实验 6-14 ★★★：同一桌面任务的 RGB 跨环境测试。** 在模拟环境中继续使用“把物体移动到对应目标”的基本问题，把每个样本理解成整理桌面中的一个局部决策：根据 RGB 画面判断应该向哪个方向接近物体，或者是否已经可以抓取。训练四种结构相同的视觉策略：

1. 一组只看固定画面；
2. 一组改变背景；
3. 一组改变物体外观；
4. 最后一组同时改变背景、外观、光照和噪声。

所有策略都在原始环境和变化后的新环境中测试，比较视觉条件变化前后的动作判断准确率。这个实验要回答的问题更窄：训练时主动扩大画面变化范围，是否有助于同一个杯子—托盘、废纸—垃圾盒任务适应新的摄像头画面。它不打算回答“模拟器是否已经等于 XLeRobot 真机”。即使结果改善，真机部署仍然需要真实相机标定、执行器测试和完整的安全闭环。

补充：a：LeRobot, “Sim2Real 教程”.

这个消融实验的设计很标准：固定画面、只变背景、只变外观、全变（背景 + 外观 + 光照 + 噪声）。四种策略结构相同，只有训练数据的视觉多样性不同，这样才能把差异归因到“训练时见过的变化范围”。测试时原始环境与新环境都要测，从而看出泛化增益与原环境性能是否下降之间的取舍。

把任务简化成局部决策也是有意为之。完整的整理桌面任务链条太长，很难只归因到视觉；拆成一个个“接近/可抓取”的判断，就能单独测量视觉策略的泛化能力。最后那句免责声明属于工程纪律：模拟里的成功从来不能直接换成真机上的成功。

## 6.6 本章小结

顺着模态和执行时机两根轴看，四节的推进很清楚。异步与事件驱动把观察从“Agent 主动去取”扩展为“世界主动推来”，把动作从“回合内做完”扩展为“先发起、后续靠事件收尾”，模态没变，变的只有时机。语音把尺度压到毫秒，级联、端到端 Omni 与全双工三种范式的演进主线，就是从“轮流说话”逐步走向持续听说，并在前台实时交互与后台深度思考之间做出分工。Computer Use 把同一个闭环搬到屏幕上，瓶颈已从“能否完成任务”扩展到操作效率、连续视觉理解和动作后的状态确认。机器人则把它推到物理世界，动作分块在平滑性与反应速度之间取舍，而最终是否完成，仍必须由新的观察来判定。

四节共享同一条控制骨架：

```text
持续感知 → 判断当前状态与时机 → 选择回复或动作 → 让输出进入环境
→ 观察反馈 → 继续、修正、重试、停止或重新规划
```

也共享同一组原语：唤醒、安全点、取消、抢占、快慢分离。

本章完成了“构建 Agent”这一部分的最后一块：观察与动作空间在内容、模态和时机三个方向上都已经展开。接下来第七章先回答如何判断系统构建得对不对；第八章讨论如何通过后训练更新模型参数；第九章再把运行轨迹、评估与多种更新载体组织成持续进化闭环；第十章则在这个完整的单 Agent 基础上转向多 Agent 协作。

那张控制骨架值得当成全章的路线图来用。把它和 6.2 到 6.5 对照，会发现四节都只是这条骨架在不同时间尺度、不同模态上的实例。异步事件驱动里，感知来自事件流，判断是紧急度路由，反馈是事件到达；语音里，感知是持续音频流，判断是“该谁说话”，反馈是用户的插话与副语言信号；Computer Use 里，感知是屏幕，判断是“下一步点哪里”，反馈是“界面是否仍与计划一致”；机器人里，感知是传感器，判断是“先做哪个子任务、这一步怎么动”，反馈是“新观察是否确认完成”。

那五个原语（唤醒、安全点、取消、抢占、快慢分离）是本章最抽象的收获。它们能跨四个场景复用，是因为回答的都是同一个问题：当感知与行动的节奏和世界变化的节奏不匹配时，系统靠什么机制协调。这一点本章思考题第 12 题会直接考。

小结对四节各自“瓶颈的迁移”概括得很准，值得单列记忆。异步的瓶颈是可靠性，也就是综合使用所有更新；语音的瓶颈是时机与思考的平衡，前台实时、后台深思；Computer Use 的瓶颈是效率与状态确认，步骤太多、动作后要重新确认；机器人的瓶颈是平滑性与反应速度的取舍（动作分块），以及验收必须靠新观察。共同的落点是一句话：最终是否完成，必须由新的观察来判定。

这里有两处容易混。骨架（持续感知→判断→选择→输出→观察反馈→继续/修正/重试/停止/重新规划）是通用的，抢占、动作分块、VAD、坐标缩放这些是各场景特有的实现，别把实现当成原则。本章在整体里的位置也别忘了：它是“构建 Agent”部分的最后一块，内容、模态、时机三个方向都展开了，而评估与训练是第七、八章的事。

## 思考题

**1.** ★★ 在异步 Agent 架构中，事件队列的优先级策略需要在设计时确定。但如果优先级判断本身需要语义理解（比如判断一条新消息是否比当前任务更紧急），这个判断应该由谁来做——规则引擎还是另一个 LLM 调用？各有什么代价？

> 思路提示：把两条路线的代价分别列成“延迟、成本、可预测性、可调试性”四个维度来比较。可以想：规则引擎在什么情况下必然失效（6.2.6 里“马上停下来 / 今天天气怎么样 / 报告用中文发给我”这三种语义）；轻量 LLM 分类器的误判又如何兜底（比如把“取消”误判成常规事件）。另外可以讨论混合方案：规则先筛高频明显事件，LLM 只处理灰色地带。

**2.** ★★ 在队列式事件处理中，模型倾向于只关注最后一个事件，本章通过 Agent 状态栏标记和汇总来缓解。但如果队列中积压了 20 个事件（10 个工具结果 + 5 条用户消息 + 5 个系统提醒），你会如何组织这些事件的呈现顺序和格式，使模型不遗漏关键信息？

> 思路提示：可以参考 6.2.7 的两个层面（提示词 + 状态栏标记），但要解决“20 条”带来的新问题：是否分组、是否按来源分层、是否给出摘要与索引、是否标注依赖关系（某条工具结果属于哪个任务）。别忘了“总量小”和“总量大”可能需要不同策略（比如超过某个条数就先做一轮摘要）。

**3.** ★★★ Agent 代表用户与外部世界交互时，本质上面临一个身份选择：是用独立的虚拟身份（专属邮箱和电话号码）以第三方身份行动，还是直接以用户本人的身份操作其个人账号？前者可以在后台自主操作，但第三方可能不信任一个非真人的身份；后者拥有更完整的上下文和权限，但引入了信任授权和安全边界的问题。你认为在什么场景下应该选择哪种模式？

> 思路提示：从 6.2.5 的两条线索切入——爆炸半径（出错/被攻破时暴露什么）与第三方信任（反机器人机制、身份核验）。可以按“任务是否需要以本人身份才能完成”与“任务失败/被攻破的后果有多严重”两个轴来分类，并考虑 Human-in-the-Loop 认证作为过渡方案（何时该用会话令牌、令牌有效期怎么定）。

**4.** ★★ 语音 Agent 的端到端模型将 ASR-LLM-TTS 合并为单一模型，降低了延迟却失去了模块化。如果端到端模型在某个环节（如语音识别）出错，调试和修复比串行管道困难得多。你会如何设计端到端语音 Agent 的可观测性（observability）系统？

> 思路提示：级联范式的优势正是“模块清晰、易替换、易调试”（6.3.1 表格），那么端到端要补的就是把中间状态显式化。可以考虑的方向：让模型输出中间产物（转录、控制标记、声学事件标记，见 6.3.2.1）、全链路留痕与回放、把“错误”归因到可观测的代理指标（如误切分、误打断）、以及用人工抽查与在线抽样评估兜底。

**5.** ★ Step-Audio R1 通过 MPS 双脑架构实现“边想边说”。但人类在“边想边说”时经常会说出未经深思熟虑的话、自我纠正或使用填充词。Agent 的“边想边说”应该模仿人类的这些特征吗？

> 思路提示：可以分成两个问题：表达层（填充词、停顿是否提升自然度与可信度，参见 6.3.6 的控制标记）与内容层（未经深思熟虑的话会不会造成实际损害）。再考虑场景差异：闲聊、客服、医疗/金融建议对“说错话”的容忍度完全不同。

**6.** ★★ SoM（Set-of-Mark）及其结构化变体（DOM 元素索引）将 Computer Use 的视觉定位从开放坐标预测转为封闭 ID 选择，但都需要先检测和标注界面元素——无论靠分割模型还是靠 DOM。如果界面包含非标准控件或动态变化的元素，标注就可能不完整或不准确。这种情况下应该回退到坐标预测吗？

> 思路提示：先区分两种“标注不完整”的情况：读不到结构（Canvas/WebGL、游戏，见 6.4.2 的适用边界）与能读到但会变（动态元素、非标准控件）。前者更适合回退，后者可能适合“标注 + 坐标”的混合，或改善标注时机（等界面稳定、关键帧触发，见 6.4.3）。还要衡量回退的代价：坐标预测需要专门训练的模型，且在密集小元素上精度仍不足。

**7.** ★★ XLeRobot 等几百美元级机器人平台让遥操作数据收集变得廉价。但遥操作数据的质量高度依赖操这里的技能。一个不熟练的操这里提供的数据会如何影响 VLA 模型的训练？如何在数据收集阶段自动筛选低质量数据？

> 思路提示：先想“不熟练”具体表现成什么可观测的信号（反复重试、路径冗长、抖动、未完成、误碰），这些正好是实验 6-10 里记录的字段（动作时间、抓取失败、重试次数、最终状态）。然后考虑筛选手段：自动指标（成功率/步数/路径长度）、状态校验（是否真的放入目标区域）、以及“人 vs 理想控制器”的对照（实验 6-11 的思路）能否用作质量基线。

**8.** ★★★ 本章覆盖了语音、Computer Use 和机器人三种交互形态。交互架构可以通过端到端统一、模块化级联或前台交互与后台推理解耦来改进，而不必与智能上限同步提升。未来五年的 Agent 应该优先追求更强的统一模型，还是保留可替换的快慢分工？请结合延迟、可观测性、模型迭代速度和任务风险讨论。

> 思路提示：6.3.5.4 已经给了四条线索：延迟（快慢分离天然满足前台低延迟）、可观测性（级联/分离更易定位）、模型迭代速度（分离路线只需换后台模型）、任务风险（越不可逆的任务越需要可校验的环节）。可以构造一个判断框架，而不是给单一结论。

**9.** ★★ DOM/Accessibility Tree 元素索引在标准 Web 应用上效果显著，但越来越多的软件界面（Canvas/WebGL 渲染、跨平台自绘控件）不提供可访问的结构化信息，只能依靠视觉标注或坐标预测。你认为 Computer Use 应该押注纯视觉路线，还是同时维护结构化和视觉两条路径？维护两条路径的成本和收益分别是什么？

> 思路提示：收益侧看覆盖面（结构化只覆盖一部分界面）与精度（6.4.2 的“优先用 DOM/A11y”结论）；成本侧看两套标注管线、两套训练数据、两套评测，以及路由问题——系统怎么知道当前界面该走哪条路。别忘了“两条路都要维护”本身就是长期的工程负担。

**10.** ★★ VLA 模型采用动作分块（action chunking）——如正文所述，模型一次生成一小段未来动作，由控制线程以更高频率回放——将推理延迟隐藏在执行时间里。但如果执行过程中环境突变（如物体被移走），预生成的动作序列就会失效。如何在动作分块的效率优势和环境变化的响应速度之间取得平衡？

> 思路提示：可从三个层面想：段长自适应（按场景风险/物体是否易动调整）、中途打断（把“取消/抢占”原语用上，见 6.6 小结的原语清单）、预测校验（用世界模型或高频视觉监测发现偏差就缩短动作，见 6.5.6 的“执行时”用法）。

**11.** ★★★ 本章的三个场景（语音、Computer Use、机器人）都面临“感知-思考-行动”循环的延迟问题，都需要在智能上限和交互时效之间做分工。在语音场景中，这表现为“说错了再纠正”；在 Computer Use 场景中，这表现为“先点再看”；在机器人场景中，这表现为“走一步看一步”。如何通过动作分级、可逆操作、状态确认、权限控制和安全停止，保证快速交互不会导致无法挽回的后果？

> 思路提示：把这五个手段各对应到本章的实例：动作分级（有边界的技能 vs 任意关节角，6.5.2）、可逆操作（删除文件先在隔离虚拟桌面预测确认框，6.4.4）、状态确认（`verify_state` 必须由新观察确认，6.5.3）、权限控制（虚拟身份/Human-in-the-Loop，6.2.5）、安全停止（`stop` 工具与独立硬件安全控制器，6.5.6）。再想一个总的判据：什么条件下可以快，什么条件下必须先确认。

**12.** ★★★ 本章反复出现同一组原语（唤醒、安全点、取消、抢占、快慢分离）在不同时间尺度上的实现。请任选其中一个，说明它在事件驱动（秒—天）与机器人动作分块（毫秒）两处的实现差异；这种差异主要由什么决定——环境变化的速度、动作的可逆性，还是观察的获取成本？

> 思路提示：以“抢占”为例，事件驱动侧是“紧急事件到达 → 造安全点 → 清空队列 → 重新推理”（6.2.6）；机器人侧是“动作段被执行到一半时被新观察打断 → 缩短或丢弃剩余动作段”（6.5.4）。再比较代价：一边是浪费一段推理，另一边可能是机械臂停在半空甚至碰倒物体。最后回到题干那三个候选因素，判断哪个是主导，并说明理由。
