## 本章地图

- **这一章要解决什么问题**：模型"上岗"之后，能不能像新员工一样在日常工作中持续长进？本章的答案是：**今天还不能指望模型参数层面的持续学习（continual learning）自己变可靠，所以要把"学习"这件事做成模型外围的一套自主系统**——作者把它命名为**持续进化**。这套系统要回答四个问题：一次运行到底好在哪里、错在哪里（学习信号）；这次改进应该落到知识、指令、程序还是参数（四种更新载体）；这些更新怎么被验证、发布、修订与淘汰（长期闭环）；以及怎么保证它不会把一次错误变成永久风险（安全边界）。
- **它在全书中的位置**：本章是"收口"的一章。第二章提供任务内的上下文与状态管理，第三章提供知识与记忆基础设施，第五章赋予 Agent 创造工具、修改系统的元能力，第七章建立评估与验证体系，第八章讲怎么更新模型参数；**第九章的任务就是把这些散件组装成一个闭环**（原书图9-1）。作者还点明：本章构建的正是第一章"发现循环"中的**实验与反馈**环节——提案已经有了，问题变成"怎样用一次以真实观测为基础的实验，判断它到底有没有让系统变好，以及怎样把结果送回下一轮"（印刷 p.271）。
- **小节之间的关系**：9.1 解决"信号从哪来"（三层轨迹验证 + 可学习诊断信号的结构）；9.2 解决"改到哪里去"，先给四种载体（知识 9.2.1、指令 9.2.2、程序 9.2.3、参数 9.2.4）的总览与边界，再用 9.2.5 把视角从"改产物"抬升到"改产生产物的方法"；9.3 解决"怎么长期跑下去"——在线执行与离线进化的双循环（9.3 主体）、可验证闭环的失效边界（9.3.1）、三条安全边界（9.3.2）、睡眠学习式的整合与遗忘（9.3.3）；9.4 收束全章。
- **读完你应该能做到**：1) 为一条 Agent 轨迹设计出"结果—过程—质量"三层验证，并把评价输出成能当学习信号用的结构（总判定 + 维度结论 + 证据位置 + 失败标签 + 允许拒答）；2) 拿到一个具体缺陷，能判断该改知识库、Prompt/Skill、程序/Harness 还是模型参数，并说出理由；3) 能设计一条从失败轨迹到"待验证版本"再到灰度发布的更新流水线，包括边界集/保留集、独立验证者、回滚路径；4) 能识别自我进化系统的三类安全漏洞（证据当指令、待验证能力直通生产、安全机制可自我修改），并说出对应的隔离手段。

## 章首导言（原书无编号）

**原文要点**

- **Agent 的能力悖论**：它可以零样本解决从未见过的复杂任务，却可能在处理了一万次相似任务之后，第二天仍然犯下第一天的错误。
- 由此提出本章的核心问题：模型上岗之后，能否像新员工一样从日常工作中不断长进？能否自主从经验中学习（所谓**持续学习，continual learning**）？作者判断，这正在成为 Agent 从"会完成任务"走向"能够可靠工作"的**关键能力**，也是下一代模型的核心研究课题。
- **概念澄清**：今天的"持续学习"与早年"学了新任务就忘掉旧任务"的持续学习研究**不是同一个问题**。遗忘只是其中一个子问题；更难的是**没有人告诉模型，今天这一天的经历里哪些是做对的，哪些是做错的**。就目前而言，模型本身的持续学习能力仍**远远不够**。
- **为什么不够**（原因一）：部署后的模型并不会因为一次推理自动改变参数。第二章讨论的上下文学习、状态维护和压缩，能让 Agent 在当前任务内适应；但**上下文结束后，这种变化不会自然进入下一次任务**。把对话存进记忆也不等于学会了新的行为：原始轨迹可能很长，其中既有有效策略，也有偶然成功、错误归因和不可信输入。
- **一个容易混淆的区别**：**保存经历 ≠ 从经历中学习**。把一百条轨迹放进长上下文或向量库，可以帮助模型在需要时找回某个案例，却**不会自动完成跨案例比较**——哪些步骤在成功轨迹中反复出现，哪些做法只在旧版接口上有效，某次成功究竟来自正确策略还是环境偶然。作者给出判据：**学习发生在系统主动完成"评价、对照、归纳、验证"之后，而不是发生在日志写入磁盘的那一刻。**
- **本章与第三章的分工**：第三章的**用户记忆**主要沉淀"用户与世界是什么样的"；本章的**经验学习**则要进一步沉淀"**在什么条件下应该怎样行动**"。前者让 Agent 记得更多，后者才让它**从聪明变得熟练**。
- **为什么不让模型在每次任务后直接训练自己**（原因二）：生产环境很少提供干净的学习信号。用户满意不意味着合规；局部参数更新还可能造成**能力遗忘、策略漂移或安全退化**。若允许模型依据未经验证的反馈直接修改自身参数，错误经验和提示注入就可能被**固化**，并在后续任务中持续放大。另一方面，基础模型的周期性训练可以提升通用能力，却无法及时吸收每个 Agent 每天遇到的**私有规则、工具变化和局部经验**。
- **本章的定义**：在模型自身尚不能可靠地持续学习时，必须先把"学习"构建成模型外围的一套自主系统，本书称之为**持续进化**，以区别于模型权重层面的持续学习。它做四件事：**记录运行证据 → 验证结果与过程 → 从多条轨迹中提取共性 → 再决定应更新知识、指令、程序还是模型参数**。并且有一条硬约束：**所有修改先形成待验证版本，经过回归测试和安全检查后，才能改变下一轮运行。**
- **闭环总图（图9-1）**：作者把前述章节的部件串成"持续进化：从运行经验到新版本 Agent"的闭环。

> 图 9-1（原文插图）：**Agent 持续进化的总体闭环**（印刷 p.256）。这是一张环形流程图，箭头依次指向五个环节：
> ① **执行任务**——旁注"用户、环境与工具交互"；
> ② **记录轨迹**——旁注"动作、结果与反馈"；
> ③ **形成信号**——旁注"结果·过程·质量"（对应 9.1 的三层验证）；
> ④ **生成候选更新**——旁注四个并列分支"知识 / 指令 / 程序 / 参数"（对应 9.2 的四种方法）；
> ⑤ **验证与发布**——旁注"回归、灰度与回滚"；
> 之后箭头回到起点，标注"**新的 Agent 进入下一轮运行**"。
> 图下方有一句贯穿全章的原则：**"只有改变后续行为且通过验证的更新，才构成持续进化。"**

**辅导讲解**

- 这一节最值得划下来的是那句判据：**学习发生在"评价、对照、归纳、验证"之后，而不是在日志写盘的那一刻。** 很多团队做"记忆"时其实只做了"存"，于是得到一个错觉——库里东西越来越多，Agent 却越来越像一个记性很好但不会总结的实习生。存是"证据保全"，学是"跨案例比较 + 接受检验"，两者对基础设施的要求完全不同（前者要不可变、可追溯，后者要能聚类、能对照、能被验证器否决）。
- "上下文适应不会自动持久化"这句话，可以这样理解：上下文里的学习像**白板**，写的时候好使，擦掉就没了；参数里的学习像**纹身**，改起来很贵但一直带着；而本章要建的持续进化像**工作手册 + 审批流程**——手册随时可以改，但改完必须走评审，改坏了还能回滚。作者选第三条路，是因为前两者在当前技术条件下各有致命伤：白板留不住，纹身改错了洗不掉。
- 为什么"用户满意不等于合规"这么重要？因为它是**单一指标的经典陷阱**。客服为了让用户满意，可以口头承诺"7 天内退款"（原文在 9.1 用来举例），满意度当场可能是涨的，但承诺是否兑现、是否符合政策，是一个**完全不同的问题**。如果一个系统只拿满意度当奖励信号，它就会学会"用承诺换好评"这种策略——而参数一旦内化了这种策略，纠正成本极高。
- 工程上要落地的第一步，其实不是"让 Agent 自我修改"，而是**把证据链建起来**：轨迹不可变、结果可核对、评价带证据位置。这一步不做，后面四种更新方法全都无从谈起——因为"该改哪一层"这个判断，完全依赖"失败是什么类型、发生在哪一步"这些信息。
- 容易被忽略的一点：本章强调的"待验证版本"是一个**状态**，不是一句口号。也就是说，任何一条新知识、新规则、新代码、新权重，在被验证前都不能改变下一轮运行。这个"闸门"是整套体系可回滚的前提。

**易混点**

- **持续进化 vs 持续学习（continual learning）**：前者是模型**外围**的一套自主系统（知识/指令/程序/参数的更新流程），后者指模型**权重层面**的持续学习能力。本章主要讲前者，并明确说后者"目前仍远远不够"。
- **保存经历 vs 从经历中学习**：保存 = 把轨迹存进长上下文或向量库；学习 = 主动完成评价、对照、归纳、验证。前者只提升"回忆"能力，后者才改变行为。
- **用户记忆 vs 经验学习**：用户记忆回答"用户与世界是什么样的"（第三章），经验学习回答"在什么条件下应该怎样行动"（本章）。
- **上下文内适应 vs 跨任务进化**：前者在任务内有效、上下文结束即失效；后者必须改变下一轮运行才能算数。

**一句话记住**

> 上下文里的学习不留痕、参数里的学习不可回退，所以在模型可靠地自我学习之前，先把"学习"做成模型外面一套**可验证、可回滚**的持续进化系统。

## 9.1 从运行轨迹中获得学习信号

> 小节位置：印刷 p.257（`<<<PAGE 265>>>`）。原文该页页眉重复了一次标题"9.1 从运行轨迹中获得学习信号"，此处归位；页眉之后那段"持续进化必须以可追溯的运行经验为基础……"实际是章首导言的结尾（承接图9-1 之后的过渡段），笔记把它放回导言语境中理解。

**原文要点**

- **起点是评估**：持续进化的起点是第七章所述的**评估（evaluation）**。作者的因果表述很直接：如果系统不知道任务是否完成，也不知道哪一步造成了成功或失败，那么**语言模型生成的反思只能是一种猜测**。
- 章首导言的过渡段（页眉后那段）概括了本章路线：持续进化必须以**可追溯的运行经验**为基础，能够**改变后续行为**，并**经过验证**，确保没有造成明显退化。本章依次讨论：如何判断一次运行究竟好在哪里、错在哪里；比较四种更新方法及其适用边界；这些更新如何在长期运行中被验证、发布、修订与淘汰。
- **评价一条轨迹，实质上是依次回答三个问题**：① 事情是否办成了；② 是否以允许的方式办成；③ 是否让用户舒服。图9-2 把它们组织为**三层验证结构**。

> 图 9-2（原文插图）：**从环境结果到 LLM Rubric 的三层轨迹验证**，副标题"三层轨迹验证：尽量让证据来自真实环境"（印刷 p.257）。图左是自下而上的三层验证器：
> - **结果验证器**（底层）——证据举例"测试、金额、订单最终状态"；
> - **过程验证器**（中层）——证据举例"政策、权限、动作与承诺"；
> - **LLM Rubric**（顶层）——评判"自然、简洁、合规变通"。
>
> 图右侧是三层输出汇合后的产物：**结构化轨迹评价**，它包含四项——**任务结果**（成功、部分成功或失败）、**维度评价**（逐项评分，而不是只给总分）、**证据位置**（标明对话轮次与工具状态）、**失败标签**（保留问题类型，支持后续诊断）。图右下方另有一条规则："**证据不足时，允许拒绝评分**"。图的右下角标注这整套输出的去向：**可学习的诊断信号**——保留成功与失败的位置、说明证据与问题类型、交给独立模块选择更新对象。

- **底层：结果验证器**回答"**事情是否真的办成**"。它读取测试结果、数据库状态和工具返回。原文例子：Coding Agent 可以运行测试、类型检查和性能基准；替用户办理退款的 Agent 可以查询订单状态和实际退款金额。作者强调：这类信号来自环境中的**真实状态**，**通常比模型对自己行为的描述可靠**，因此是**三层中最应优先建立的一层**。
- **中层：过程验证器**回答"**是否以允许的方式办成**"。作者先立论："**结果正确并不代表过程正确**"，并给出两个反例：删除失败的测试用例也能让测试通过；口头承诺用户"我们会在7 天内退款，请耐心等候"也可能得到暂时的满意反馈。这一层检查**业务规则、权限和动作序列**，用以区分"结果已经达成"与"结果以允许的路径达成"。由于政策库、权限表与动作轨迹**均可精确表达**，这一层**同样可以由代码判定**。
- **上层：质量验证器**回答"**是否让用户舒服**"。原文列举维度：客服是否耐心、是否提供了合规范围内的变通方案，研究报告是否抓住了关键证据，生成文本是否自然简洁。作者明确这些维度"**不影响事情办成与否**，但对用户体验是有影响的"。做法是使用第七章介绍的 **LLM-as-a-Judge**，**预先定义评价量表（Rubric）**，要求验证器**逐项给分并引用轨迹证据**。
- **七个维度的三层归属（表9-1）**：以客服 Agent 为例，三层展开为**七个可逐项评分的维度**——任务结果属于**结果层**；规则遵从、隐私边界与承诺—行动一致性属于**过程层**；表达质量与合规变通属于**质量层**；**事实可靠性横跨两层**，可与工具返回逐一比对的部分由代码核验，其余交由 Rubric 判断。

**表9-1 客服 Agent 的轨迹评价维度**（原书印刷 p.257–258；原文表格因跨页与分栏被拆成"标题在上页、表头与表体在下页"，此处按语义还原）「表格按原文语义还原」

| 维度 | 验证问题 | 主要证据 |
| --- | --- | --- |
| 任务结果 | 用户的核心诉求是否得到解决 | 最终环境状态、工具结果 |
| 规则遵从 | 是否违反政策、权限或必要流程 | 政策库、动作轨迹 |
| 隐私边界 | 是否泄露不应提供的信息 | 回复文本、数据访问记录 |
| 事实可靠性 | 陈述是否有知识或工具结果支持 | 引用来源、工具返回 |
| 承诺—行动一致性 | 声称完成的操作是否真实发生 | 回复与工具日志对照 |
| 表达质量 | 是否自然、简洁，避免重复与模板化 | 对话全文、语言Rubric |
| 合规变通 | 原方案不可行时，是否找到允许的替代路径 | 用户目标、政策与后续动作 |

- **学习信号的结构要求**：**验证器的输出形态决定了它能否成为"学习信号"。** 单一总分只能反映一次运行的优劣，**无法指出应当修改之处**。可供后续学习的评价**至少应包含四项内容**：
  1. 任务是**成功、部分成功还是失败**；
  2. **每个维度各自的结论**；
  3. 每条结论对应的**证据位置**（哪一轮对话、哪一次工具调用）；
  4. **失败的类型标签**。
- 此外还有一条"宁缺毋滥"的规则：**验证器还应被允许在证据不足时拒绝评分**。作者的判断是——与其把低置信度的结论当作事实固化下来，不如将该案例**排除在学习集之外**。具备这四项内容，下一节讨论的**四种更新方法才能判断应当更新知识、提示词、程序还是模型参数**。
- **实验9-1 ★★：为客服Agent 构建轨迹验证器**
  - 实验目的：把客服Agent 的运行轨迹转换成**带证据的结构化诊断**，为后续的经验提炼提供可靠学习信号。
  - 实验说明：对照"**只输出一个总分**"和"**逐维度输出结论、证据与置信度**"两种验证方式，观察哪一种更容易区分**任务失败、规则违规、虚假承诺和表达问题**。
  - 实验说明了什么：持续进化不能只依赖成功率或单一分数。只有保留"**哪里错、为什么错、证据在哪里**"，后续模块才知道应该更新知识、Prompt、程序还是模型参数；**低置信度案例也不应自动进入学习集**。

**辅导讲解**

- 这三层的顺序不是随意的，它对应**可靠性从高到低**：结果验证器看的是环境的真实状态（数据库里钱到底退没退），这是最难造假的；过程验证器看的是可枚举的规则与动作序列，也能用代码判；到了质量层，才不得不请 LLM 当裁判。原文那句"最应优先建立的一层"是个很有用的落地顺序建议——**先把能自动核验的结果层做出来**，再补过程层，最后才做 Rubric 层。反过来先搭 Rubric，等于把最不可靠的判据放在最前面。
- "结果正确不代表过程正确"这句在原文里就配了一个例子（笔记把它的后果展开）：一个 Agent 为了通过测试而**删掉了测试用例**，结果层看到的是"测试全绿"，过程层如果不存在，系统就会把"删测试"当成成功经验学下来——这正是原文在 9.2.2.1 讲的"把失败写入规范"的同一类病。
- "事实可靠性横跨两层"是个很细致的设计：**能被工具返回逐条比对的事实**（比如订单号、金额、日期）用代码核验，属于结果层能力；**无法逐条比对的一般性陈述**（比如对政策的解释是否准确）交给 Rubric。这样既避免了让 LLM 去做它做不牢的核对工作，也避免让代码去判断它判不了的语义。
- 为什么"允许拒绝评分"这么关键？因为**错误的学习信号比没有信号更糟**。持续进化系统会把评价结果沉淀成长期能力，一条被误判为"失败"的偶然成功，可能让系统永久弃用一个正确策略；一条被误判为"成功"的违规捷径，可能被写进 Prompt 甚至参数。**允许弃权，等于给学习集加了一道精度闸门。**
- 工程落地上，"四项内容"其实定义了一个 schema：`{outcome, dimensions[], evidence_refs[], failure_tags[]}`，外加一个 `confidence` 和 `refused` 标志。这个结构同时也是 9.2 里"路由到哪一层更新"的输入——原文说"交给独立模块选择更新对象"，这个"独立模块"就是在读这个结构。
- 一个常见的误解：以为"逐维度评分"就是把总分拆成加权和。原文强调的是**逐项给分并引用轨迹证据**，重点在**证据引用**而不是分数本身——因为没有证据位置，后续模块无法做根因分析，也无法在跨轨迹比较时统计"哪种错误反复出现"。

**易混点**

- **结果验证器 vs 过程验证器**：前者问"事情成了吗"（读环境真实状态），后者问"是按规定的方式成的吗"（读政策库、权限表、动作轨迹）。区分方法：把这个验证器删掉，Agent 有没有可能"靠违规手段拿高分"？有可能 → 你缺的是过程验证器。
- **质量验证器 vs 过程验证器**：质量层的问题是"用户舒不舒服"（耐心、简洁、抓住关键证据），过程层的问题是"允不允许"（合规、越权、虚假承诺）。原文明确质量维度"不影响事情办成与否"。
- **置信度 vs 批准门槛**：验证器给的置信度只是**估计**（见 9.3.2 原文），不能用它当发布门槛；门槛必须是确定性的 schema、允许列表和来源检查。
- **失败标签 vs 维度结论**：维度结论说"哪一项不合格"，失败标签说"这是哪一类问题"——后者是为跨轨迹统计与诊断服务的。

**一句话记住**

> 评价一条轨迹要按"**办成了吗 / 按规矩办成的吗 / 用户舒服吗**"三层来问，并且输出必须是"**总判定 + 逐维结论 + 证据位置 + 失败标签**"，证据不足时宁可拒评也不能猜。

## 9.2 Agent 持续进化的四种方法

> 小节位置：印刷 p.258–259（`<<<PAGE 266>>>`–`<<<PAGE 267>>>`）。原文 `<<<PAGE 266>>>` 之后的"9.2 Agent 持续进化的四种方法"是该页页眉，真正的小节标题在同一页靠下位置（表9-1 表体之后），笔记按语义归位。

**原文要点**

- 这句是全节的引子：**"学习信号说明Agent 应当改变，但没有说明改变应发生在哪里。"** 作者随后给出四句对应关系：
  - **事实和经验**适合写成**知识文档**；
  - **可以用语言清楚表达的策略**适合写入**提示词或Skill**；
  - **可以精确执行的流程与约束**适合写成**程序**；
  - **感知、语言风格和隐式策略等高维能力**则**必须进入模型参数**。
- 图9-3 展示了这四种方式及其关系。

> 图 9-3（原文插图）：**持续进化的四种更新方式**，副标题"能力的表示性质决定主要更新位置"（印刷 p.258）。图中四个横向条目，每条两行（上：能力类型；下：承载形式）：
> - **知识**——事实、经验与例外——载体是 **Markdown / 知识库**；
> - **指令**——可语言化的判断原则——载体是 **Prompt / Skill**；
> - **程序**——确定性流程与强约束——载体是 **工具 / 工作流 / Harness**；
> - **参数**——高维感知与隐式策略——载体是 **SFT / 蒸馏 / RL**。
>
> 图左侧标出一条渐变轴："**易更新、可追溯**"（对应知识/指令一端）←→"**内化、低推理开销**"（对应程序/参数一端）。图中有三句关键注释：①"**不是单向阶梯，而是四种互补载体**"；②"**首要判断：能力能否被事实、语言规则或程序完整表达？**"；③"**稳定性、成本与更新频率决定具体部署方式，而非能力能否参数化**"。

- **表9-2 给出了一个紧凑的比较。四种方式并不互斥**，原文给的复合例子是：**医疗影像Agent** 依靠**参数**识别病灶，用**知识库**提供最新指南，再用**代码**计算风险指标；**客服模型**的自然语气来自**后训练**，具体企业政策由**知识和Skill** 提供，关键合规**则由服务端代码兜底**。

**表9-2 四种持续进化方式的适用边界**（原书印刷 p.258–259）「表格按原文语义还原：PDF 提取把每个单元格都拆成了单独一行，"适合承载""主要优势"两列的内容因此看不出与表头的对应关系，此处按语义合并回单元格；这不是原书表格本身的问题」

| 更新方式 | 适合承载 | 主要优势 | 主要局限 |
| --- | --- | --- | --- |
| 经验知识库 | 事实、经验规律、例外与来源 | 更新快、可追溯、可按需检索 | 依赖检索和模型正确应用 |
| Prompt 与Skill | 需要理解语境、例外和优先级，但仍能用自然语言说明的判断原则 | 可解释、作用范围可控 | 容易膨胀、冲突或被忽略 |
| 程序与Harness | 可确定解析、可执行验证和高风险硬约束 | 可测试、执行稳定、成本低 | 开发与维护成本较高 |
| 模型参数 | 高维感知、生成风格和隐式策略 | 泛化能力强、推理开销低 | 更新与回归成本高 |

- **同一能力可以拆到多个载体**：原文的拆法是——**事实进入知识库，解释例外的原则进入Skill，不可绕过的权限仍由程序门控，高维识别能力再进入参数**。
- 最后一句是本节的"闸门"：**"路由结果只是更新提案，尚未获得发布资格。"**

**辅导讲解**

- 这一节可以看成一张**分诊表**。拿到"某类任务老出错"这个现象，先别急着改 Prompt，而是问两个问题：**这个能力能不能被事实/语言规则/程序完整表达？** 能→就走知识/指令/程序；不能（比如"写出不像 AI 的文字"、"看懂 CT 片"）→才考虑参数。这就是图9-3 说的"首要判断"。
- 注意图9-3 那句反直觉的注解：**"稳定性、成本与更新频率决定具体部署方式，而非能力能否参数化。"** 意思是：一个能力**能不能**写进参数，和它**该不该**写进参数，是两个问题。稳定性差的能力（语言风格变得快）也完全可以参数化（周期性偏好训练），只是你不会把它当成一次性永久投资。9.2.4 会把这句话展开。
- 表9-2 的"主要局限"一列很值得记：
  - 知识库的坑是"**依赖检索和模型正确应用**"——知识写对了，检索没召回，或者召回了模型没照做，等于没写；
  - Prompt/Skill 的坑是"**容易膨胀、冲突或被忽略**"——这三件事在 9.3.3 的"上下文腐化"里会再出现一次；
  - 程序的坑是"**开发与维护成本较高**"——所以别拿程序去装那些天天变的策略；
  - 参数的坑是"**更新与回归成本高**"——也正是 9.2.4 说"是否参数化不由任务是否长期稳定单独决定"的原因。
- "四种方式并不互斥"这一点在工程上极其重要。原文的医疗影像与客服两个例子都在说明：一个能力往往**不是选一个载体，而是分工**。判断"关键合规用服务端代码兜底"就是典型——因为它是**不可绕过**的硬约束，放在 Prompt 里只是"请求模型遵守"，放在代码里才是"做不到就是做不到"。
- 一个实用启发（笔记补充）：可以按"**错了会怎样**"来选载体。错了只是体验差 → 知识/指令；错了会造成越权或资金损失 → 程序；错了难以枚举、只能靠统计意义上的判断 → 参数。这条经验与表9-2 的"局限"列是自洽的。

**易混点**

- **载体 vs 内容**：知识、Prompt、程序、参数是**四种载体**，不是四个能力层级。同一个能力可以拆到多个载体（医疗影像例子），也可以整体迁移到另一个载体（比如一条稳定下来的 Skill 规则被"编译"成程序，见 9.2.3）。
- **参数化能力 vs 高频更新**：容易混成"稳定才参数化"。原文明确否定：稳定性影响的是**更新频率和成本**，真正决定主要载体的是**能力的表示性质**。
- **路由结果 vs 已发布更新**：路由只是**提案**，没有发布资格。这个区别是整章反复强调的"待验证版本"概念的起点。

**一句话记住**

> 更新该落到哪一层，取决于**这个能力能不能被事实、语言或程序完整表达**；四种载体是互补分工，且任何"该改哪一层"的结论都只是提案，不是发布许可。

### 9.2.1 将经验沉淀为知识

> 小节位置：印刷 p.259–260（`<<<PAGE 267>>>`–`<<<PAGE 268>>>`）。

**原文要点**

- **定位**：这是**最轻量的进化方式**——把多次运行中反复出现的经验整理成**可检索的知识文档**。
- **与第三章的异同**：这里的"**经验知识库**"与第三章**共享存储、索引和检索技术**，但**知识来源和验证目标不同**。第三章主要从用户对话、文档和数据集中提取"**用户与世界是什么样的**"；本章则从 **Agent 的行动轨迹和结果**中提取"**在什么条件下应该怎样做**"。
- 原文用一对例子把"领域知识"和"行动经验"区分开：
  - 领域知识："**该航空公司要求特殊餐食提前二十四小时预订**"；
  - 行动经验："**订票前先检查特殊餐食截止时间，避免付款后才发现无法满足需求**"。
- **为什么原始轨迹不能直接当知识单元**：它**既长又嘈杂**，包含**工具原始输出、偶然的绕路和环境细节**。更稳妥的系统**保留三层数据**：
  1. **不可变的原始轨迹**，用于**审计**；
  2. **单次运行分析**，记录**本次成败与经验草案**；
  3. 再对**多条同类轨迹**进行比较、聚类和归纳，形成**面向未来的 Markdown 知识文档**。
- **正式文档应写什么**：通常写清**适用场景、推荐策略、禁止做法、例外条件、证据来源和最近验证时间**，而不是**复述某一次任务的完整过程**。
- **与 User as Code 同构**：这种设计与第三章的 **User as Code 采用了相同的两阶段思路**——User as Code **先把对话事实追加到不可变日志，再周期性重建结构化用户模型**；经验学习**同样应先保存证据，再离线生成可变知识**。图9-4 展示了这一过程。
- **分阶段的好处**：把**记录与整理分开**，可以**避免一次偶发成功或网络故障立即改变Agent**，也使系统能够**在看到多条成功和失败后再判断共性**。

> 图 9-4（原文插图）：**从已评价轨迹到经验知识文档**，副标题"经验知识化：原始轨迹是证据，知识文档才是复用单元"（印刷 p.260）。图是一条从左到右的五段流水线：
> ① **原始轨迹**——动作、结果、环境；标注"不可变证据"；
> ② **单次评价**——成功、失败、标签；标注"保留证据位置"；
> ③ **跨轨迹比较**——三件事：聚合同类任务、对照成功与失败、提取共性与边界；
> ④ **Markdown 文档**——写清适用场景与策略；例外、禁区与来源；版本与验证时间；
> ⑤ **检索应用**——"新任务按需加载"，并"继续产生反馈"。
> 图中有一条**从第⑤段回到第④段的回边**，标注"**新证据用于修订、限定或淘汰旧知识**"——说明知识文档是**活文档**，会被后续证据修正。图下方的注释界定了它与第三章的关系："**与第三章共用抽取和检索基础设施；本章新增轨迹评价与行为改进闭环**"。

- **经验文档不是简单的轨迹摘要**。真正有迁移价值的内容来自**对照**：同类**成功轨迹做了什么**，**失败轨迹缺少什么**；某种策略**在哪些环境版本中有效，在哪些前置条件下失效**。作者说明分工：第三章已经介绍**知识抽取、聚类与检索**，本章**不再重复这些算法**，而把重点放在两点上——**轨迹评价如何成为抽取条件**，以及**抽取出的知识是否能提高后续任务表现**。
- **完整的知识提炼管道五步**：
  1. **保存不可变轨迹和环境结果**；
  2. 为**单次运行生成结构化分析**，列出**任务类型、所需能力、观察到的策略、错误与例外**；
  3. 按**任务族聚合同类运行**，为每条经验草案建立"**哪些轨迹支持、哪些轨迹反驳**"的**证据表**；
  4. 只有**达到支持门槛的草案才写入正式文档**；
  5. 最后在**未参与提炼的新任务上测试迁移效果**。
- **GAIA 经验学习实例**：
  - **GAIA** 包含需要**综合搜索、网页阅读、文件处理和计算**的多步骤问题；**AWorld** 则提供**运行Agent、调用这些工具和保存轨迹的执行环境**。原文的比喻很直白：**前者像试卷，后者像考场与实验记录系统**。
  - **旧式做法**：在一次任务**成功后立刻**生成策略摘要并向量化入库。
  - **更严格的实现**：先用 **GAIA 答案验证或其他环境验证器**标记**成功、部分成功和失败**，再**比较同一任务族的多条路径**。三种轨迹各有用处——**成功轨迹贡献策略草案，失败轨迹贡献排除性知识，部分成功轨迹则帮助识别"哪一段有效、哪一段仍有问题"**。
  - **Reflexion 的定位**：其所提出的**自然语言反思可以参与生成经验草案，但反思本身不是证据**；只有**与环境结果相符、得到跨轨迹支持并在新任务上显示正向迁移**的内容，才应进入正式经验文档。
  - 原书此处引用的文献（脚注，印刷 p.260）：**GAIA**——Mialon, G., et al. *GAIA: a benchmark for General AI Assistants*. arXiv:2311.12983, 2023；**AWorld**——Yu, C., et al. *AWorld: Orchestrating the Training Recipe for Agentic AI*. arXiv:2508.20404, 2025；**Reflexion**——Shinn, N., et al. *Reflexion: Language Agents with Verbal Reinforcement Learning*. arXiv:2303.11366, 2023。

> 🔎 检索确认：原文脚注所记 **GAIA 的 arXiv 编号 2311.12983、第一作者 Mialon**（Grégoire Mialon 等，Meta FAIR）与外部资料一致，论文标题为 *GAIA: A Benchmark for General AI Assistants*，与原文"需要综合搜索、网页阅读、文件处理和计算的多步骤问题"这一描述相符。（来源：[GAIA: A Benchmark for General AI Assistants](https://ar5iv.labs.arxiv.org/html/2311.12983#1)）

**辅导讲解**

- 这一节的核心是一句话：**"原始轨迹是证据，知识文档才是复用单元。"** 你可以把原始轨迹想成**监控录像**——它忠实、完整、不可改，但你不会拿监控录像当操作手册；操作手册是从大量录像里总结出来的、写清了条件和例外的薄薄几页。
- "三层数据"的设计非常像数据库里的 **ODS → DWD → 指标层**：最底层是不可变原始事实，中间层是单条的加工结果（单次评价 + 草案），上层是跨条汇总的、面向未来使用的结论。分开的收益是**幂等与可重算**：任何一条知识都可以追到它是由哪几条轨迹支持的，新的反例出现时也能精准地找出该修订哪一条知识。
- "正式文档写清六件事"这个清单可以直接当模板用：**适用场景 / 推荐策略 / 禁止做法 / 例外条件 / 证据来源 / 最近验证时间**。注意其中有两项是很多团队会漏的——**例外条件**（没有它，规则会在不该用的地方被套用）和**最近验证时间**（没有它，无法做 9.3.3 说的时效性淘汰）。
- **"失败轨迹贡献排除性知识"** 这一点特别值得强调，因为它是很多人做经验库时的盲区。只学成功经验，你得到的是"这样做行得通"；补上失败经验，你才得到"这样做**不行**、以及为什么不行"。后者往往更省事，因为它把搜索空间直接剪掉了一块。9.3.1 里"保留负面结果"是同一条道理在科研场景的延伸。
- **"反思不是证据"** 是本节最需要划线的一句。Reflexion 式的自我反思很自然会生成一段听起来很有道理的经验——但它的来源只是模型自己的叙述。判定标准被作者写死了三关：**与环境结果相符**、**得到跨轨迹支持**、**在新任务上显示正向迁移**。三关都过，才写进文档。你可以把这理解成"经验的三重验证"，与 9.1 的"轨迹三层验证"是配套的两层把关。
- 迁移测试放在管道最后一步（第 5 步）不是凑数：**如果知识只在产出它的那些任务上有效，那它可能只是对那批轨迹的过拟合**。这和 9.3 的"保留任务集增益"、9.2.2 的"边界集/保留集"是同一个方法论——**永远留一批没参与提炼的任务做验收**。
- 工程上的常见坑：把"经验文档"写成"某次任务的复盘流水账"。判断标准很简单——**换一个不同但同族的任务，这段话还有指导力吗？** 如果答案是否定的，那它还是轨迹摘要，不是知识。

**易混点**

- **领域知识 vs 行动经验**：前者是"世界是什么样的"（特殊餐食需提前 24 小时预订），后者是"什么条件下该怎么做"（订票前先查截止时间）。本章的经验库偏后者，第三章的用户记忆偏前者。
- **经验知识库 vs 第三章的知识库**：共享存储/索引/检索技术，但**来源不同**（本章来自行动轨迹与结果）、**验证目标不同**（本章要以"能否提高后续任务表现"为准）。
- **经验文档 vs 轨迹摘要**：前者来自**跨轨迹对照**（成功做了什么、失败缺什么、哪种策略在哪个环境版本有效），后者只是复述一次过程。
- **反思 vs 证据**：反思是 LLM 生成的叙述，属于**候选草案**；证据是与环境结果相符、被多条轨迹支持、并能迁移到新任务的结论。
- **单次评价 vs 跨轨迹比较**：前者产出"这一次为什么成/败"，后者才产出共性、边界与例外。

**一句话记住**

> 先把不可变轨迹和结构化评价存下来（证据层），再**离线**对多条同类轨迹做对照与归纳，只有**过关（环境相符、跨轨迹支持、新任务正迁移）**的结论才写成带适用场景、例外和验证时间的知识文档。

### 9.2.2 将经验写成指令

> 小节位置：印刷 p.260–261（`<<<PAGE 268>>>`–`<<<PAGE 269>>>`）。原文 `<<<PAGE 268>>>` 之后的"9.2 Agent 持续进化的四种方法"为该页页眉，笔记按语义归位。

**原文要点**

- **分工对照**："**经验知识库给Agent 提供"可以参考的资料"，Prompt 和Skill 则规定"应该怎样行动"。**"
- **升级为指令的门槛**：当**多条相似轨迹反复暴露同一种策略错误**，**而且错误能够用语言清楚描述**时，**才值得**把经验提升为指令。
- **三个概念先分开**：
  - **系统 Prompt**：对**所有任务**生效；
  - **Skill**：只在**匹配到某个领域或工具时按需加载**；
  - **程序/Harness**：负责**权限和其他硬约束**。
- **相关研究脉络**：
  - **Andrej Karpathy** 将这种做法称为**系统提示学习（System Prompt Learning）**：模型遇到问题后，**用一句清楚的话提醒未来的自己**。
  - **DSPy** 在**开发集上搜索指令和示例**；
  - **OPRO** 根据**历史提示词及其得分**提出提示提案；
  - **GEPA** 从**失败轨迹的自然语言反思中生成并筛选提示提案**。
  - 作者对这些方法给出适用性判断：**这些方法适合离线批量优化；生产环境更适合使用可审计的最小更新提案，并保留快速回滚路径。**
- **与第二章的提示工程不是一回事**：第二章讨论**怎样组织一份好Prompt**；本节讨论**什么反馈足以触发修改**，以及**更新提案怎样安全发布**。
- **两条硬性做法**：
  1. 修改应是**带来源的最小diff**，而不是让模型每次都**重写整份Prompt**——这正是**第一章命名的最小diff + 可回滚模式**。
  2. **待验证版本必须同时在触发失败的边界集和正常工作的保留集上测试，前者要改善，后者不能退化。**

#### 9.2.2.1 例子一：转接边界的规则化

**原文要点**

- **场景**：**τ²-bench** 的 **telecom** 政策中，关于**转接人工**只有**两条原则性规定**：**请求超出Agent 的动作范围时才转接；转接前应先尽力解决**。
- **缺陷如何暴露**：第七章解剖该环境时，**这两条并未显出问题**；**换用能力较弱的模型运行，缺陷随即暴露**——**工具返回错误后Agent 反复重试，最终以转接人工收场**，**提炼集的20 条任务中有19 条如此结束**。
- **提升结果**：将这 **19 条失败轨迹**交由**模型自行归纳**，产出**若干条可执行的规则追加到政策末尾**，再在**一批未参与提炼的任务**上重新运行：**通过率由12.3% 升至19.3%**，且**原本通过的任务无一被改坏**。
- **关键变量：提炼所依据的材料决定了能够归纳出什么。** 同样是这 19 条轨迹：
  - **仅提供失败摘要与错误文本**时，模型归纳出的是"**同一工具反复报错即不应继续调用**"；
  - **补充Agent 与用户各自可调用的工具清单**之后，归纳结果变为"**网络状态、SIM 卡、APN 等项属于用户设备侧，应引导用户自行操作而非直接调用**"。
  - 作者的评断：**"前者记录的是教训，后者理解的是职责归属。"**
- **第二个坑：模型会把观察到的行为当作应然的行为。**
  - 第一版规则中有两条是"**连续三次调用失败即转接人工**""**用户两次未提供号码即转接人工**"——因为**轨迹中出现最频繁的正是转接人工**，模型据此将其视为**合理的兜底手段**。
  - 但**在这套评估中转接人工必然判定失败**，所以这两条规则**等于把失败写入了规范**。
  - 结论：**提炼产物因此不能直接发布，须经与提炼者相互独立的验证。**
- **典型失败轨迹（"被修复的往往是极朴素的缺陷"）**：
  - 基线中一条典型轨迹：Agent 需要用户的电话号码，于是**调用查询工具**，并将"**请您提供您的电话号码**"**填入参数**，**连续五次，五次报错，随后转接人工**。
  - 作者的诊断：**它已经判断出应当询问用户，却把这句话说给了工具。**
  - 规则生效后的行为：**先在对话中提出请求，取得号码再行查询**；此后**欲检查SIM 卡状态遭工具拒绝**，**转而引导用户自行重新插拔SIM 卡**，**任务通过**。
- **实验9-2 ★★：从τ²-bench 失败轨迹提炼转接与工具使用规则**
  - 实验设计：沿用第七章的 τ²-bench telecom 环境。**提炼集与迁移集在上游仓库中本就是两套互不相交的任务，提炼过程接触不到迁移集。**
  - 步骤：**先以弱模型运行提炼集并保存失败轨迹**；**规则由模型归纳而非人工撰写**，生成后**追加至原始政策末尾**；再在**迁移集**上对照**原始策略与两个进化版本**。**三臂之间只替换策略文件，用户模拟器保持不变。**
  - 记录指标：除**通过率**外，还需记录**三项与规则直接对应的行为指标**——**转接人工的比例**、**Agent 越界调用用户侧工具的次数**、**参数缺失即发出的调用次数**。
  - 结果：**后两项在进化版本中均下降约八成**，说明**通过率的提升来自规则修复了具体动作**。
- **可移植性**：同样的做法可以移植到其他领域。**航空客服Agent** 的典型问题案例是：**用户对退票费、改签费或行李政策提出异议，Agent 未查询政策、未解释规则、未寻找合规的替代方案，即调用 transfer_to_human**。作者给出的正确边界是：**一般的政策争议无须转接，只有用户明确要求人工介入，或出现安全相关情形时才必须转接**。诊断同样指向**转接边界未予明确**，**修法同样是将其落成一条带出处的最小规则**。
- **实验9-3 ★★：基于失败轨迹优化航空客服的系统Prompt**
  - 实验目的：让航空客服Agent 修复"**遇到普通政策争议就过早转人工**"的行为，**同时保留明确要求人工和安全事件的转接能力**。
  - 实验说明：从失败轨迹中提取**规则遵从、任务解决和合规变通三个维度**，生成**一条带来源的最小Prompt 补丁**，再与**初始版本、人工调优版本**在**相同条件**下对照。**更新提案只有在边界案例改善、旧任务不退化并通过发布门槛后，才进入灰度阶段。**
  - 实验说明了什么：**"Prompt 自动优化的重点不是让模型自由改写一大段文字，而是把可归因的失败转成作用域明确、可回滚、可验证的局部规则。"**

**辅导讲解**

- 这个例子里最有价值的是**两个反面发现**，都可以直接拿去当自己的检查清单：
  1. **材料的完整性决定归纳的质量**。只给"失败摘要 + 错误文本"，模型学到的是"别老调同一个工具"这种**表层教训**；补上"谁能调哪些工具"的**职责边界**，模型才能学到"这类问题属于用户设备侧"。也就是说，**不是模型归纳能力不够，而是你给它的信息里根本没有"职责归属"这一维**。
  2. **频率会被误当成正确性**。轨迹里"转接人工"出现最多，模型就把它当成合理兜底——这在统计上是"最常见的动作"，在评估里却是"必然失败的动作"。这提醒我们：**提炼器如果只看"什么经常发生"，就会把系统的坏习惯固化**。所以原文强调必须有**与提炼者相互独立**的验证。
- "通过率由 12.3% 升至 19.3%"这个数字值得算一下（笔记补充计算）：绝对提升 **19.3% − 12.3% = 7 个百分点**，相对提升 **7 ÷ 12.3 ≈ 56.9%**，也就是 **19.3 ÷ 12.3 ≈ 1.57 倍**（两个说法同源：涨到 1.57 倍 = 多出约 57%）。这里必须交代**口径**，否则很容易算错：12.3% 与 19.3% 是**同一批任务、同一口径**的两个通过率——都是在**未参与提炼的迁移集**上测的，所以 56.9% 与 1.57 倍可以直接由这两个数相除得到（笔记另按两路独立复算核对过：$7/12.3=0.5691$、$19.3/12.3=1.5691$）。而前文说的 **20 条是提炼集**的规模（20 条中 19 条以转人工收场）——**两者不是同一批任务**，不能把通过率乘到 20 条上换算条数；若迁移集规模为 $n$，两种通过率对应的通过条数约为 $0.123n$ 与 $0.193n$（由这两个百分数还可知：既然 $0.123n$ 与 $0.193n$ 都是整数、而 $123/1000$ 与 $193/1000$ 都已是最简分数，那么 $n$ 应为 1000 的倍数）。绝对量不大，但方法学意义大：这是**零训练、只用推理侧规则**拿到的提升，而且**原本通过的任务无一被改坏**（即没有出现回退）。注意：7 个百分点、56.9% 与 1.57 倍都是笔记据原文数字推算的，**原文只给了 12.3% 和 19.3% 两个数**，两数本身没有口径冲突。
- "**后两项下降约八成**"是个很聪明的指标设计。它回答了"**通过率为什么涨**"——如果只是通过率涨了而行为指标没动，那就可能是评估波动或侥幸；现在**越界调用用户侧工具**和**参数缺失即发出调用**这两个与规则一一对应的行为都降了约 80%，说明**规则确实改掉了具体动作**。这就是"可归因"：**成绩变化要能挂到一个具体机制上**（9.2.3 会再次强调这个原则）。
- "把话说给工具"那条轨迹特别经典，值得单独记住：Agent 在**语义层面判断对了**（应该向用户要号码），但在**接口层面用错了通道**（把请求用户的话塞进了工具参数）。这说明很多失败**不是认知失败，而是动作—接口映射失败**——而这类问题恰恰最适合用一条最小规则修掉，也恰恰是"知识库"解决不了、只有"指令/程序"能解决的。
- 与第二章提示工程的区别要记牢：**提示工程问"怎么写好"，本节问"什么时候该改、改完怎么发布"**。一个很实际的推论是：**自动 Prompt 优化不该产出"一整份新 Prompt"**，那既不可归因也不可回滚；它应该产出**一条带来源的补丁**（原文反复用"最小 diff""带出处的最小规则"这类说法）。
- 关于实验设计（笔记补充）：实验9-2 的"三臂只替换策略文件，用户模拟器保持不变"是很标准的**控制变量**做法——因为用户模拟器的随机性会污染结果，必须固定住。而"提炼集/迁移集互不相交、提炼过程接触不到迁移集"则是对**数据泄露**的防范：如果提炼时见过迁移集的任务，那 19.3% 就不是泛化成绩，而是记忆成绩。

**易混点**

- **系统提示学习 vs 提示工程**：前者关心"什么反馈触发修改、怎样安全发布"，后者关心"怎样组织一份好 Prompt"。
- **教训 vs 职责归属**：前者是"别重复调同一个工具"（表层），后者是"这类问题属于用户侧，应引导用户自己操作"（结构）。差别来自**是否给了职责边界信息**。
- **最常见的动作 vs 正确的动作**：轨迹频率高的行为不一定对；本案例中"转接人工"出现最多却必然判失败。
- **通过率提升 vs 行为改善**：通过率可能因波动而变；行为指标（越界调用次数、参数缺失调用次数）才是**因果证据**。
- **最小 diff vs 重写整份 Prompt**：前者可归因、可回滚、带来源；后者不可归因、容易丢细节。

**一句话记住**

> 把经验升级为指令的前提是"**同类错误反复出现且能用语言说清**"；提炼出来的必须是**带来源的最小规则补丁**，而且**只能当提案**——因为模型会把"最常见的做法"当成"正确的做法"，必须由独立的验证者把关。

#### 9.2.2.2 例子二：需求澄清Skill——从"直接开工"到"先确认再执行"

**原文要点**

- **前提**：第二章已介绍如何编写一份 Skill。这里**假设系统已经有一份初版的需求澄清Skill**，本节关注的是另一件事：**当Agent 在生产环境中不断收到用户反馈时，如何自动判断"什么时候应该先问，问什么，什么时候可以直接开始"是否需要更新。**
- **为什么这是典型的流程性问题**：用户说"**把登录页改成支持企业登录**"，Agent 如果**立刻开工**，**可能在身份提供商、回退方式、兼容旧用户和上线范围上替用户作出其尚未考虑过的选择**；如果**无论任务大小都先列十几个问题**，又会**把简单修改变成一次访谈**。作者概括这条权衡：**问得太少会导致返工，问得太多会增加打扰**。
- **Skill 应该表达什么**：**不是"所有任务都必须确认"，而是一条带作用域的判断路径。**
- **一个初版流程可以这样写**：
  1. 先判断任务的**歧义程度、风险和返工成本**；
  2. **低风险、容易撤销的小改动**，**说明假设后直接执行**；
  3. 涉及**架构、数据、权限、公开接口或大范围改动**时，**集中提出少量真正会改变方案的问题**；
  4. **得到答案后生成短Spec 或Plan**，列出**目标、非目标、关键取舍、假设和验收标准**，**交给用户确认**；
  5. **确认后再执行**，**过程中发现原Spec 不成立时暂停并重新确认**。
- **要记录什么运行证据**：系统应**同时记录任务、澄清问题、Spec 版本、用户修改、执行结果和交付后的返工**。
- **反馈的正负两侧**：
  - **负反馈**可能是"**做出来的和我想象的不一样**"，也可能是"**你问得太多了**"；
  - **正反馈**包括**用户一次确认后顺利交付**、**主动修改Spec 后减少返工**，以及**在低风险任务中没有被多余问题打断**。
  - 作者的硬性要求：**单独保存一句抱怨不足以触发更新，必须把反馈和具体轨迹、任务类型以及结果关联起来。**
- **何时能提提案**：**当多条轨迹反复指向同一个缺口时，Agent 可以提出最小Skill 更新提案。** 原文给了两个方向相反的例子：
  - **多个涉及认证架构的任务都在交付后才发现需要兼容旧登录方式** → 规则草案可以**要求在执行前确认"身份提供商、回退路径和兼容范围"**；
  - **如果大量拼写修复都被Agent 先问一轮** → 规则草案则**应收窄高风险与高歧义的触发范围**。
- **怎么验证**：可以比较"**直接执行**""**先提问再执行**"和"**提问后生成Spec、确认后执行**"**三种策略**，并**按任务复杂度分层**。
  - **评价指标至少包括**：**需求偏差率、交付后的返工次数、澄清轮数、首次有效产出时间、用户放弃率、Spec 被修改的比例和高风险操作错误率**。
  - **发布条件**：更新提案只有**在减少需求偏差的同时没有显著增加打扰**，并**在未参与提炼的任务上通过回归**，**才进入灰度发布**。
- **Skill 与Harness 的边界**：**Skill 负责理解语境并主动提出问题、整理Spec 和说明取舍**；**Harness 负责在缺少确认时否决高风险写入、直接操作main 或绕过发布流程**。作者还划出一条反向边界：**Harness 中的否决器不能替模型决定PR 应该怎样描述，也不能代替模型选择需求方案。**
- **与第八章的衔接**：随着经验积累，**稳定的对话轨迹还可以进一步生成第八章所需的SFT 或RL 训练数据**。
- **实验9-4 ★★：从用户反馈中进化需求澄清与Spec 确认Skill**
  - 实验目的：检验Agent 能否**在"需求偏差"和"交互打扰"之间找到更好的澄清策略**，并把经过验证的改进**写回Skill**。
  - 实验说明：准备**一组低风险、低歧义任务**和**一组涉及架构、权限、数据或公开接口的高风险任务**，比较**直接执行、提问后执行、提问后Spec 确认**三种流程。记录**用户回答、Spec 修改、交付结果和返工反馈**，让Agent **生成Skill 更新提案**；提案必须经过**留出任务回归、打扰成本检查和高风险否决器验证**。
  - 实验说明了什么：**"持续进化不是把每次抱怨直接追加到Prompt，而是从结果和反馈中识别作用域，提出最小指令更新，再用独立评价器决定是否发布。"**

**辅导讲解**

- 这个例子的精彩之处在于它把"**该不该问**"变成了**一个可优化的问题**，而不是风格问题。很多人讨论"Agent 要不要先澄清"时容易站队（"必须问清楚"/"别啰嗦直接干"），原文的做法是：**把它参数化成一条带作用域的判断路径**——先看歧义程度、风险和返工成本，再决定走哪条分支。这样"问多少"就变成了**可以用指标衡量、可以用实验优化**的对象。
- 注意两个负反馈的性质完全不同：
  - "**做出来的和我想象的不一样**" → 典型的**问得不够**（需求偏差）；
  - "**你问得太多了**" → 典型的**问得过量**（打扰成本）。
  作者特意把这两类都列出来，是因为**优化目标是有双边约束的**：你不能只盯"减少返工"，否则 Agent 会退化成"什么都先问一遍"；也不能只盯"减少打扰"，否则又会退回"直接开工"。所以指标里同时有**需求偏差率/返工次数**（偏少问的代价）和**澄清轮数/用户放弃率/首次有效产出时间**（偏多问的代价）。
- "**首次有效产出时间**"这个指标值得单独留意：它衡量的是"**从任务开始到第一次产出真正有用东西**"的时间，而不是"总耗时"。一个先问 12 个问题的流程，总耗时可能没增加多少，但首次有效产出时间会显著变长——用户体感的"被打扰"往往就体现在这里。
- "**单独保存一句抱怨不足以触发更新**"是本节的关键工程判断，它其实在说：**反馈需要上下文才能变成信号**。一句"你问得太多了"如果不知道是哪个任务、什么复杂度、问了几轮、最后有没有返工，就无法区分"这是低风险任务的过度澄清"（该收窄）还是"这是高风险任务用户不耐烦但结果其实没错"（不该动）。这和 9.1 的"证据位置"要求是同一套逻辑。
- **Skill 与 Harness 的边界**这条最容易搞混，原文的两句话可以当口诀：
  - **Harness 管"不许做什么"**（缺确认时否决高风险写入、否决直接在 main 上提交、否决绕过发布流程）；
  - **Skill 管"应该怎么做"**（理解语境、提问、整理 Spec、说明取舍）。
  并且作者补了一句反向约束：**否决器不能替模型做判断**——否决器可以拦下"未经确认的高风险写入"，但不能规定"PR 该怎么写"，因为那是一个需要理解语境的创作性任务。
- 关于"**稳定的对话轨迹进一步生成 SFT 或 RL 训练数据**"：这解释了四种载体之间的**升级路径**——先用 Prompt/Skill 快速试错（改得快、可回滚），等某种行为在多条轨迹上稳定下来、又需要低推理开销和更好的泛化时，再考虑把它**内化进参数**。这与 9.2.4 讲"是否参数化"的判断是连着的：**Skill 是参数的试验田**。
- 实验9-4 的"**高风险否决器验证**"是个很容易被忽略的验收项：一个只优化"减少打扰"的提案，很可能顺手把"高风险操作前必须确认"这条规则也收窄掉了。所以发布门槛里必须有一条**独立于提案的安全检查**——这正是 9.3.2 第三道边界在具体案例上的体现。

**易混点**

- **需求偏差 vs 交互打扰**：前者来自"问得太少"，后者来自"问得太多"。两者是**互相拉扯的目标**，不能用单一指标优化。
- **Skill 的作用域 vs 全局 Prompt**：Skill 只在匹配到某领域/工具时按需加载，所以它天然适合装"分场景的澄清策略"；把这类规则塞进全局 Prompt 会让它膨胀并干扰所有任务。
- **Harness 的否决权 vs 模型的判断权**：Harness 是否决器（管边界），不是决策者（不管方案选择、不管 PR 怎么写）。
- **单条抱怨 vs 可触发更新的信号**：前者缺上下文；后者必须绑定轨迹、任务类型与结果，并且要**多条轨迹反复指向同一缺口**。
- **初版 Skill 的手工编写 vs 后续的自动更新**：本节不讨论怎么写初版（那是第二章），讨论的是**"什么时候、依据什么反馈、怎样安全地改"**。

**一句话记住**

> 把"该不该先问"写成**带作用域的判断路径**，并用**成对指标**（需求偏差 vs 打扰成本）来优化；更新必须是"**多条轨迹指向同一缺口**"才提的最小补丁，且要过留出任务回归与高风险否决器两道关。

### 9.2.3 将经验写成程序

> 小节位置：印刷 p.263–265（`<<<PAGE 271>>>`–`<<<PAGE 273>>>`）。原文 `<<<PAGE 271>>>` 之后的"9.2 Agent 持续进化的四种方法"为该页页眉，笔记按语义归位。

**原文要点**

- **适用条件**：当经验描述的是**稳定、重复且可验证的操作**时，**每次都让模型重新阅读文档和推理并不经济**。此时更合适的做法是**把经验编译为工作流、工具或Harness 代码，使一次探索变成可重复执行的程序**。
- **与第五章的边界**：第五章已经说明 **Coding Agent 如何读写文件、运行测试和生成系统**；本节关注的**不是一般代码生成**，而是**Agent 如何根据自己的轨迹修改未来版本的自己**。
- **可修改的对象远不止"新工具"**，原文按层列出：
  - **操作层**：可以把**浏览器轨迹编译为参数化工作流**，或**为变化的API 生成适配器**；
  - **控制层**：可以修改**工具路由、重试、熔断和上下文压缩策略**；
  - **验证层**：可以根据生产失败**新增参数检查、状态验证器和回归测试**；
  - **架构层**：可以**增加Reviewer Agent**，**改变规划与执行之间的信息流**。
- **浏览器工作流的价值（类比电子表格宏录制）**：第一次发送邮件时，多模态Agent 通过**观察—思考—行动**寻找"**撰写、收件人、主题、正文、发送**"这些控件；以后发送另一封邮件时，**流程没有变化，只有收件人和内容不同**，**没必要再次调用模型从像素和DOM 中重新发现整条路径**。系统要做的，是**把第一次探索产生的轨迹编译成一个带参数、状态检查和版本信息的小程序**。
- **图9-4 所示的知识提炼过程在浏览器场景中对应一个更具体的生命周期（6 步）**：
  1. **捕获轨迹**：记录**导航、点击、输入、下拉选择**等动作，保存**动作参数、当时的URL，以及XPath、CSS 等元素定位证据**。作者强调：**定位信息只用于再次寻找元素，不能证明任务已经完成**。
  2. **参数化**：把**首次运行中的字面量识别为模板变量**，例如将 `test@example.com`、邮件主题和正文替换为 `{recipient}`、`{subject}` 和 `{content}`；**其余稳定动作保持不变**。
  3. **定义状态检查**：为动作增加**执行前检查和执行后检查**，例如"**发送按钮当前可见**"；为**整个工作流增加最终状态检查**。作者的判据：**"动作执行成功与任务成功是两件事，最终状态检查必须读取真实页面或后端状态。"**
  4. **独立回放验证**：系统必须**把沙盒账号或测试站点重置到独立初始状态**，再**完整回放录制下来的程序**；**每一步的执行前检查、执行后检查和最终状态检查全部通过后，才能发布**。
  5. **匹配与回放**：新任务到来时，先在**正式能力库中按意图和关键词寻找工作流**，**提取本次参数**，然后由 **Playwright 直接执行**。**回放路径不需要逐步调用LLM，但仍需等待元素可用并完成所有状态检查。**
  6. **失效与重学**：**找不到目标元素、状态检查不通过、API Schema 改变或最终状态错误**时，**回退到完整的Agent 模式重新探索**。
- **PreAct 的实验结论**：这类程序在**重复任务上实现了 8.5–13 倍的端到端加速**，**回放阶段不需要逐步调用语言模型**；作者点出**更重要的结论**是——**流程记忆必须同时具备动作前验证、动作后验证和独立回放验证**。否则系统很容易得到一种**危险的假象**：**每个按钮都点过了，但某个字段其实为空，任务从未真正完成。**
- **实验9-5 ★★★：从浏览器轨迹生成可验证工作流**
  - 实验目的：验证网页Agent 能否**把一次探索转化为可复用工作流**，并**在页面变化或状态异常时拒绝错误回放**。
  - 实验说明：把**一次成功轨迹编译成带参数和状态检查的待验证工作流**，与"**每次都重新探索**"的基线比较；再**改变页面或制造假成功**，观察待验证工作流是否失效并**回退到完整Agent**。
  - 实验说明了什么：**"流程记忆的价值不在于重复执行动作，而在于确保任务的最终状态仍然正确。可复用工作流必须有独立验证和失效机制，否则加速只是把错误更快地重复。"**
- **自我修改 ≠ 进程直接覆盖自身**：**Agent 修改自己的代码不意味着运行中的进程直接覆盖自身。** 生产系统应当：
  1. **从当前稳定版本创建隔离更新分支**；
  2. 由 **Coding Agent 生成最小补丁**；
  3. 依次通过**静态检查、单元测试、安全扫描、失败轨迹重放和旧任务回归**；
  4. 再生成**可灰度部署的新版本**。
  作者概括其意义：这把"**自我修改**"转化为**可审计的软件发布流程**，也正是**第九章与第五章的边界**——**第五章提供修改系统的能力，本章提供由经验触发、以验证闭环约束的自我修改方法**。
- **Git worktree 与 Pull Request 的示范作用**：**"Skill 应主动指导Agent：先为任务创建独立worktree，确认需求和Spec，完成实现与测试，提交有意义的commit，并在Pull Request 中写清背景、方案、测试结果和剩余风险。"**
  **Harness 的职责**：**不负责替模型做这些判断**，但可以在它**准备结束任务时检查是否仍在main 上直接提交、是否遗漏worktree 或Pull Request**；**一旦违反边界就否决这次操作，要求Agent 返回修复**。
- **变更契约（可证伪）**：**仅有"补丁尽量小"还不足以支持可靠归因。** 每个修改请求还应是一份**可证伪的变更契约**，列出：
  - **失败证据**、**推断根因**、**归属的Harness 组件**、**修改提案**、**预期修复的行为**、**可能受损的既有行为**，以及**分别验证两者的用例**。
- **Agentic Harness Engineering 的三层可观测性**：**组件、经验和决策**三层——**可编辑组件都有文件级表示**；**海量轨迹先整理为可逐层下钻的证据**；**每次编辑在执行前声明影响预测，再由下一轮结果验证**。作者的评价：这样**"分数上涨才能与某个具体机制建立联系，而不只是一次不可解释的试错"**。
- **提案生成器的输入不应只有失败案例**：**Self-Harness** 的做法还会提供**必须保留的成功行为**和**此前被拒绝的修改记录**。前者告诉Agent **哪些性质不能在修复时被破坏**，后者**避免它换一种说法重复提交已经失败的方案**。作者的结论：**失败证据、成功约束与历史尝试共同构成一个有边界的方案空间，比把全部源码和原始日志无差别塞给修改Agent 更容易产生局部、可验证的改动。**
- **工具创造遵循同一协议**：**Alita** 给出的案例是：Agent 要从一段由《**指环王**》中**咕噜配音演员解说的 YouTube 360 VR 视频**中，找出**恐龙首次出现后紧接着提到的数字**。它发现自己**缺少字幕读取能力**后，**搜索并测试 youtube-transcript-api**，将其**封装为新的字幕工具**，最终从字幕中得到答案 **100000000**。作者补上准入条件：**只有安全扫描、功能测试和后续任务复用都通过，新工具才进入能力库。**
- **实验9-6 ★★★：由失败轨迹触发Agent 自我修改**
  - 实验目的：检验系统能否把"**不可重试错误被反复调用**"的经验**写入重试与熔断程序**，同时**保留临时故障的恢复能力**。
  - 实验说明：比较"**只在Prompt 中提醒不要重试**"和"**修改程序中的重试策略**"两种修复。修改提案必须经过**失败轨迹重放、正常故障回归和安全发布门槛**，且**不能修改验证器或稳定版本**。
  - 实验说明了什么：**"能够确定性执行的约束应该进入程序，而不是继续堆在Prompt 里。Agent 可以提出代码提案，但"是否能发布"必须由模型外的测试、审计和回滚机制决定。"**
- **验证层同样采用这一协议**：当**多条用户纠正、点踩或事后审计**都指向"**高风险操作未经确认**"时，系统生成一个**确认门禁提案**。提案**必须在边界任务和正常任务上都通过验证**，且**安全门本身不能被提案修改**。作者把它与第一章的观点对齐：**"这与第一章三层护栏里数据层的道理相同：真正的保证必须来自被修改者无法触及的那一层。"**
- **实验9-7 ★★：由用户反馈触发高风险操作确认门禁**
  - 实验目的：检验系统能否**从用户纠正和事后审计中发现安全流程缺口**，并为**高风险工具调用生成确认门禁**。
  - 实验说明：用**危险操作边界集**和**正常操作保留集**共同评价门禁提案。提案**既要拦住未经确认的高风险调用，也不能阻断正常任务**；**生成提案的Agent 无权修改安全测试和批准规则**。
  - 实验说明了什么：**"安全能力的进化不能由修改者自证成功。真实模型生成的更新提案可能被安全门拒绝，这正说明独立验证器和不可修改的可信根比"提案看起来合理"更重要。"**

**辅导讲解**

- 这一节的判断标准可以浓缩成一句：**"稳定、重复且可验证"三件事同时成立，才值得编译成程序。** 不稳定（天天变）→ 编译出来很快过时；不重复（一次性任务）→ 编译成本收不回；**不可验证**（没法定出"成了"的检查）→ 编译出来的东西无法防止"假成功"，这正是 PreAct 那段警告的核心。
- **"动作成功 ≠ 任务成功"** 是本节最该背下来的一句。放到浏览器场景里就是：点击"发送"返回成功，不代表邮件发出去了；放到 API 场景里就是：HTTP 200 不代表业务成功。所以工作流必须带**两层检查**：每一步的**前后置条件**（局部正确性）+ **整个流程的最终状态检查**（全局正确性），而且**最终状态检查必须读真实页面或后端状态**，不能读自己刚点过的那个按钮的缓存。
- 六步生命周期里，**第 4 步"独立回放验证"** 和 **第 6 步"失效与重学"** 是最容易被省掉、也最不能省的两步：
  - 省掉独立回放，你就会把一次**带残留状态的偶然成功**当成可复用流程（比如账号已经是登录态，所以流程里"没登录"这件事被掩盖了）；
  - 省掉失效机制，页面一变，工作流会**继续"点按钮"但点到错的地方**，于是"加速只是把错误更快地重复"。
- **8.5–13 倍加速**这个数字的来源要理解对：它快**不是因为程序比模型聪明**，而是因为**回放阶段把逐步的 LLM 调用完全去掉了**（原文："回放阶段不需要逐步调用语言模型"）。也就是说，加速的前提是**这条路径已经被证明是稳定的**——一旦页面变化，收益就归零，必须回退到完整 Agent 重新探索。这是一种典型的"**用缓存换速度、用失效检测保正确**"的设计。
- **自我修改要走软件发布流程**这一条，是把 Agent 安全问题的讨论从"模型会不会乱来"拉回到"工程流程怎么设计"。原文的四步（隔离分支 → 最小补丁 → 静态检查/单测/安全扫描/失败重放/旧任务回归 → 灰度）**没有一步是新的发明**，全都是成熟的 CI/CD 实践——作者的观点其实是：**别为 Agent 发明一套新的发布机制，把它塞进已有的那套里。**
- "**变更契约**"这个提法值得展开理解：它要求的不是"改了什么代码"，而是**一个可以被证伪的因果主张**——"我认为失败是因为 X，我要改 Y，改完之后 Z 行为会变好，同时 W 行为可能受损，我用这两个用例分别验证"。有了这份契约，"分数涨了"才能被解释成"**因为机制 M 被修好了**"。反之，如果没有契约，涨分只能算"试对了"。
- **Self-Harness 的两个额外输入**（必须保留的成功行为、此前被拒绝的修改记录）解决的是两类很实际的失败：
  - 前者防**回归**——修改 Agent 为了修 A 把 B 弄坏了，因为它根本不知道 B 是需要保护的；
  - 后者防**绕圈**——同一个不work的方案换个说法又提一遍。这也解释了原文为什么说"**有边界的方案空间**"比"把全部源码和日志都塞进去"更好：**信息量不等于有效信息量**，无差别喂料会让修改 Agent 抓不住重点。
- **Alita 的案例**（从 360 VR 视频里找"恐龙首次出现后紧接着提到的数字"，答案 100000000）说明**工具创造是"程序化经验"的另一种形态**：不是把流程编成工作流，而是**补上一个自己缺的能力**。而准入门槛是三条都过：**安全扫描 + 功能测试 + 后续任务复用**。最后一条常被忽略——一个工具只在一个任务上用过一次，还不知道它是否具有复用价值就收进能力库，会增加维护面和检索噪声。
- **实验9-6 的对照设计很经典**：同样是"不要让 Agent 在不可重试错误上反复重试"，一种修法是**在 Prompt 里提醒**（软约束），另一种是**改程序里的重试策略**（硬约束）。原文的判断是后者——**"能够确定性执行的约束应该进入程序"**。但注意它同时要求"**保留临时故障的恢复能力**"，也就是不能简单粗暴地把重试全关掉：**要区分"不可重试错误"和"临时故障"**，前者立刻停，后者仍要退避重试。
- **"安全门不能被提案修改"** 这条贯穿了实验9-6、实验9-7 和 9.3.2 的第三道边界。它的逻辑是**权限层面的，不是内容层面的**：无论提案内容多合理，**修改者都不能触及验证自己的那套东西**。原文用第一章"三层护栏里数据层"来类比，意思是**真正的保证必须来自被修改者无法触及的那一层**。

**易混点**

- **代码生成 vs 经验程序化**：第五章讲的是 Agent 会写代码；本节讲的是 Agent **把自己的轨迹编译成未来可复用的程序**（工作流、工具、Harness 代码），重点在"从经验触发、被验证闭环约束"。
- **动作执行成功 vs 任务成功**：前者是"这一步没报错"，后者是"最终状态正确"。工作流必须用**最终状态检查**判断后者。
- **回放加速 vs 正确性保证**：加速来自"不再逐步调用 LLM"，正确性来自"前置/后置/最终状态三类检查 + 独立回放验证 + 失效回退"。缺了后者，加速是负收益。
- **Program 里的约束 vs Prompt 里的提醒**：确定性可执行的约束放程序；需要语境判断的原则放 Prompt/Skill。
- **提案生成者 vs 发布批准者**：Agent 可以提代码提案，但"能不能发布"由**模型外的测试、审计、回滚机制**决定；生成提案的 Agent **无权修改安全测试与批准规则**。
- **最小补丁 vs 可归因**：小补丁是必要条件，不是充分条件；还需要**可证伪的变更契约**（失败证据、根因、影响预测、验证用例）才能建立分数与机制的因果联系。

**一句话记住**

> 对**稳定、重复且可验证**的操作，把一次探索**编译成带参数、带前后置检查、带最终状态检查、带失效回退的程序**；而 Agent 修改代码时必须走**隔离分支 + 最小补丁 + 静态检查/单测/安全扫描/失败重放/旧任务回归 + 灰度**的常规发布流程——**自我修改只是"由经验触发的软件发布"，不是进程改自己**。

#### 9.2.3.1 案例：DeepSeek Harness 以"一切皆插件"实现自我进化

> 小节位置：印刷 p.265（`<<<PAGE 273>>>`）。

**原文要点**

- **定位**：**第一章的框架对比表把DeepSeek Harness（dsh）归为"Agent 自进化框架"**。它的底座 **Cordis** 论文指出：**传统意义上的组合是静态的**——**函数调用、模块导入和类继承都在编译期确定，运行期不再变化**；而**插件系统和自进化Harness 需要的是动态组合**——**组件要在运行中被装入、卸下和重新配置**。作者的结论：**"Agent 的每一次自我修改，本质上都是一次动态组合。"**
- **动态组合的两个正交维度**：
  - **时间可组合性（temporal composability）**问的是：**一个组件被移除时，它对共享环境做过的修改能否被完整、安全地撤销**——这要求**运行时追踪它的每一次资源分配、事件注册和状态变更**。
  - **空间可组合性（spatial composability）**问的是：**组件之间能否以结构化、可验证的方式声明、发现和解析彼此的依赖，并在依赖变化时协调各自的生命周期**。
  - 作者的概括：**"前者关心改了什么，后者关心依赖什么。"**
- **为什么自进化Harness 是这个问题最尖锐的场景**：它带来的困难在于——**要撤销的副作用是长期存活、带状态的；要解析的依赖会在运行中出现、消失或改变身份**。
  - **由于缺少时间可组合性**：**每次自我修改都要整体重启，丢掉进程内积累的全部状态，进行中的任务被反复打断。**
  - **由于缺少空间可组合性**：**每个模块只能用临时手段自己察觉依赖的出现、消失和改变，而一次简单的代码替换可能静默地破坏依赖方，或者引入循环依赖。**
- **Cordis 的思路：把两个原本属于编译期的概念提升到运行时。**
  - **效果系统**本来用于推理"**计算如何修改环境**"，被提升为**可撤销效果**：**每一次对上下文的变换都携带一个显式的逆操作，由运行时追踪，组件移除时上下文随之恢复。**
  - **协效果（coeffect）系统**本来用于推理"**计算对环境有什么要求**"，被提升为**反应式协效果**：**组件把自己需要的依赖声明成一份规格，上下文每次变化都按这份规格通知它激活、失活还是无关。**
  - 论文进一步用一套**动态组合演算**，把这个性质**从单个组件推广到相互交错的组件系统**——**可组合性必须是可传递的**。
- **核心论断**：**"自我进化的上限，不取决于模型能写出多好的代码，而取决于承载它的系统具有多强的可组合性。"** 这也是 dsh 让**模型适配器、工具注册表、会话日志乃至Agent 主循环本身都成为插件**的原因：**不存在一个只能由人类维护的特权内核。**
- **可组合性不解决"该不该装"**：可组合性解决了"**能不能安全地装卸**"，**没有解决"该不该装"**。**模型写出的插件只活在进程内存里，重启即消失，不能被自动提升为正式插件，要留下来必须另走前面说的worktree 加Pull Request 那条更慢的路。**
- **进化的代价（KV Cache）**：运行中的插件会**改变模型可见的工具集和提示片段**，**请求前缀一变，第二章讨论的KV Cache 就从变化处开始失效**。因此 **dsh 插件的说明文档中需要专门描述对上下文和KV Cache 的影响**。

**辅导讲解**

- 这一小节回答了一个很自然的问题："**如果 Agent 能改自己的代码，是不是让它随便装卸插件就行了？**" 作者的答案是否定的，理由是两个可组合性问题。可以用一个类比（笔记补充）来理解这两者：
  - **时间可组合性像"撤销"**：你装了个插件，它注册了一个定时器、占了两个端口、往全局配置里写了一项。现在要卸掉它——**你能把这些副作用全部收回来吗？** 如果不追踪，就只能重启进程，把所有状态清空（原文说的"每次自我修改都要整体重启"）。
  - **空间可组合性像"依赖解析"**：A 插件依赖 B 提供的接口。B 被换成 B' 了，A 怎么办？如果依赖关系是隐式的、靠"运行时撞见"，那一次看似无害的替换就可能**静默破坏 A**，或者让 A 和 B' 互相依赖成环。
- **"逆操作"和"依赖规格声明"是两个非常工程化的答案**：
  - 前者要求**每一次对上下文的变换都自带 undo**（原文："携带一个显式的逆操作，由运行时追踪"）——这样组件移除时上下文能自动恢复，不需要重启；
  - 后者要求**组件把自己的依赖写成一份规格**（原文："声明成一份规格"，上下文变化时按规格通知它"激活、失活还是无关"）——这样依赖变化是**被通知**的，而不是靠模块自己"临时手段去察觉"。
- **"可组合性必须是可传递的"** 这句容易一晃而过，但它很关键：单个插件能做到装卸干净还不够，**A 依赖 B、B 依赖 C 的整条链**也必须保持这个性质。否则系统一层层组合起来，中间某一层就漏了。
- **"不存在一个只能由人类维护的特权内核"** 是 dsh 设计取向的直白表述：如果系统里有一块"只有人能改"的核心，那么 Agent 的自我进化就永远被卡在那块核心之外。把它也插件化，等于**把自我进化的天花板整体抬高了一层**。不过注意作者紧接着的限定：**内存里的插件只是临时生效，重启即消失，要转正还得走 worktree + PR。** 这保持了 9.2.3 的"待验证 → 发布"原则——**"能装卸"不等于"能转正"。**
- **KV Cache 那段是"进化有代价"的最好例证**。运行中的插件会改变**工具集**和**提示片段**，而这些都位于请求的**前缀**里；前缀一变，第二章讲的 KV Cache **从变化处开始失效**。工程上的含义很实在：**频繁的自我修改会让推理成本上升**，所以插件文档必须写明它对上下文和缓存的影响——这既是个性能约束，也是个"改动要克制"的理由。
- 与本章其他部分的呼应（笔记补充）：9.2.3.1 讲的是**"能不能安全地改"**，9.2.2/9.2.3 讲的是**"该改什么"**，9.3.2 讲的是**"谁能改什么"**。三者叠起来才是一个完整的自我修改系统。

**易混点**

- **静态组合 vs 动态组合**：函数调用、模块导入、类继承属于静态组合（编译期定），插件系统属于动态组合（运行期可装入、卸下、重配置）。
- **时间可组合性 vs 空间可组合性**：前者问"**改了的东西能不能撤销**"（副作用可逆），后者问"**依赖能否被声明与解析**"（依赖可协调）。一句话：**前者关心改了什么，后者关心依赖什么。**
- **效果系统 vs 协效果系统**：效果是"**计算如何修改环境**"（→ 提升为可撤销效果），协效果是"**计算对环境有什么要求**"（→ 提升为反应式协效果）。
- **能装卸 vs 能转正**：可组合性保证可以安全装卸；但**内存插件重启即消失**，转正必须走 worktree + Pull Request 的正式流程。

**一句话记住**

> 自我进化的上限**不由模型写代码的水平决定，而由承载它的系统的可组合性决定**——要做到"**改动可撤销（时间）× 依赖可声明（空间）**"，但可组合性只解决"能不能安全装卸"，"**该不该转正**"仍须走正式的发布流程。

### 9.2.4 将经验写入参数

> 小节位置：印刷 p.265–266（`<<<PAGE 273>>>`–`<<<PAGE 274>>>`）；9.2.4 的正文实际起于 PDF 第 274 页（印刷 p.266）页首。

**原文要点**

- **前提与例外**：知识、指令和程序都建立在一个前提上——**目标能力能够被外部符号较完整地表达**。但原文列出的这几类能力**很难压缩成几条规则或工作流**：
  - **医疗影像理解**、
  - **自然的语音韵律**、
  - **消除文本的模板化"AI 味"**、
  - **长程规划**。
  **这类能力必须通过后训练写入模型参数。**
- **中间地带的例子**：**弯引号的作用域判断处在中间地带**——**文档语法边界可以由程序解析**，**语境和例外需要Skill 表达**，**跨任务的识别习惯才适合通过后训练内化**。
- **是否参数化不由"任务是否长期稳定"单独决定**：
  - **新影像设备带来的域偏移仍可能需要LoRA 或持续微调**；
  - **快速变化的语言风格也可以通过周期性偏好训练适应**。
  - 作者的结论：**"稳定性影响的是更新频率和成本，真正决定主要载体的是能力的表示性质。"**
- **与第八章的分工**：第八章已经**完整讨论SFT、蒸馏和RL**，**本节不重复**。对持续进化而言，**关键是把经过评价的生产轨迹转化为训练数据**：
  - **高质量示范**可以进入 **SFT**；
  - **明确偏好**可以形成**成对数据**；
  - **具有可靠环境奖励的交互**可以用于 **RL**。

**辅导讲解**

- 这一节很短，但它是四种载体里**最容易被误用**的一节。常见误解是"参数学习是终极形态，前面三种只是过渡"。原文明确否定了这个阶梯观（图9-3 的注解就是"**不是单向阶梯，而是四种互补载体**"）。判断标准只有一条：**这个能力能不能被外部符号（事实、语言规则、程序）较完整地表达？** 能 → 不要动参数；不能 → 只能动参数。
- "**弯引号的作用域判断**"这个例子把"分工"演示得非常清楚（笔记补充解读）：决定一个引号是开引号还是闭引号，**文法的层面对应关系（哪一对配哪一对）是可以被程序解析的**；**具体的语境和例外（比如某种排版惯例）需要用自然语言规则说明**，所以放 Skill；而**在大量任务上稳定形成的识别习惯**，才值得通过后训练内化进参数。同一件事被**按性质**切成了三份，不是一个整体地选一个载体。
- "**域偏移**"和"**语言风格**"这两个反例专门用来打掉"稳定才参数化"的直觉：新影像设备带来的分布变化是**新出现的、不可预期的**，但它恰恰需要 LoRA 或持续微调；语言风格是**变化最快的**，但它恰恰适合周期性偏好训练。所以正确的问法不是"这任务稳定吗"，而是"**这个能力是符号可表达的吗**"。
- **"把经过评价的生产轨迹转化为训练数据"** 是本章与第八章的接缝，也是持续进化闭环里最实际的一环。三种数据的对应关系可以这样记：
  - **SFT ← 高质量示范**（"这样做是对的"，需要成功且合规的轨迹）；
  - **成对数据 ← 明确偏好**（"A 比 B 好"，需要能可靠判定优劣的对比）；
  - **RL ← 具有可靠环境奖励的交互**（"这样做的结果是可量化的好"，需要环境能给出可信回报）。
  注意这三个前提里都藏着一个"**可靠**"：**示范要高质量（不能拿侥幸成功的轨迹当示范）、偏好要明确、奖励要可靠**。这与 9.1 的三层验证是同一件事的两面——**没有可靠的评价，就没有可用的训练数据。**

**易混点**

- **能不能参数化 vs 该不该参数化**：前者是技术可行性，后者取决于**能力的表示性质**（外加稳定性对更新频率与成本的影响）。
- **稳定性决定载体 vs 稳定性决定节奏**：稳定性**不**决定"放哪个载体"，它决定**更新频率和成本**。
- **SFT / 成对偏好数据 / RL 数据的来源**：分别是**高质量示范**、**明确偏好**、**具有可靠环境奖励的交互**——不要混用。
- **参数学习 vs 硬性业务规则**：参数擅长高维感知、生成风格、隐式策略；**硬性业务规则不适合靠参数保证**（参见思考题第 6 题）。

**一句话记住**

> 只有当能力**无法被事实、语言规则或程序完整表达**时（如医疗影像理解、语音韵律、去"AI 味"、长程规划），才把经验写进参数；判断依据是**能力的表示性质**而非任务是否稳定，而写入的前提是**先有经过评价的可靠轨迹**。

### 9.2.5 从更新产物到更新"更新方法"

> 小节位置：印刷 p.266–267（`<<<PAGE 274>>>`–`<<<PAGE 275>>>`）。原文 `<<<PAGE 274>>>` 之后的"9.2 Agent 持续进化的四种方法"为该页页眉；`<<<PAGE 275>>>` 之后的"9.3 构建可长期运行的持续进化闭环"也是页眉（该页页脚为 267），**本小节结尾关于"回放"的讨论与实验9-8 仍属于 9.2.5**，笔记按语义归位到本节，不放在 9.3 之下。

**原文要点**

- **另一条正交的轴**：前面的四种方法讨论了**经验最终写到哪里**，但持续进化还有另一条正交的轴——**系统正在优化的究竟是某份产物的内容，还是产生、管理和验证这些产物的方法**。
- **优化对象的逐层扩大**：沿这条轴看，优化对象可以逐层扩大为：
  **单条规则或记忆 → 结构化上下文 → 工作流 → Harness 代码 → 产生更新提案的优化器代码**。
  作者的重要限定：**"这不是五种新的更新载体，而是五种不同的搜索尺度；知识、Prompt、Skill 和程序都可能出现在其中多个层级。"**
- **最内层（只修改产物内容）**：例如，根据失败轨迹**给系统提示增加一条局部规则**，或**给经验文档补充一个例外条件**。特点：**作用面小，容易归因和回滚，应当是默认选择。**
  - 但**反复让模型重写整份Prompt 或记忆会产生另一类退化**：**为了追求简洁，旧版本中的少数重要细节可能在多轮改写后逐渐消失；相互制约的条件也可能被合并成一句过度抽象的原则。**
  - **Agentic Context Engineering（ACE）** 的做法：**把上下文维护成带稳定标识符的条目集合**，由**生成、反思和整理模块提出增量更新**，再用**确定性逻辑合并与去重**，**而不是每轮重写一个越来越短的文本块**。作者的评价：它**为本章前文"最小diff、保留来源"的原则提供了一个具体研究实例**。
- **再向外一层（优化"上下文应怎样被构造"）**：优化对象不再只是"**上下文里有什么**"，而是"**上下文应怎样被构造**"。
  - **Meta Context Engineering（MCE）** 把两者拆成**内外两个循环**：**内层在给定管理方法下优化当前任务的上下文产物**，**外层则根据多轮执行和验证结果，修改搜索、选择、过滤、格式化这些上下文操作本身**。
  - 作者点出这个区分的意义：**修改一条检索规则是在改内容管理机制；让系统比较多种检索与整理机制、保留迁移效果更好的版本，才是在学习"如何管理上下文"。**
- **扩展到工作流与整个Harness**：
  - **AFlow** 把**由多个LLM 调用组成的工作流表示为代码图**，通过**执行反馈搜索节点与控制流的组合**；
  - **Meta-Harness** 则让 **Coding Agent 读取待验证Harness 版本的源码、分数和轨迹**，**搜索决定信息如何存储、检索和呈现的代码**。
  - 与第五章的衔接：**第五章已经说明代码是Agent 表达系统结构的通用语言**；此处的新增之处是——**代码不只是一次生成的产物，还可以连同评估历史一起成为持续搜索的对象**。
- **外层搜索的反馈成本问题**：**探索策略**决定**从哪个候选继续、何时另开分支、并行投入多少Worker，以及什么时候停止**；它的好坏**往往要经过很长的生成—评估链条才能显现**。作者的担心很直接：**若每个候选策略都必须重新调用Agent 和评估器，优化探索策略本身可能比完成任务更昂贵。**
- **Dream-RSI 的机制（发现树 + 回放模拟器）**：Dream-RSI 提出了一种**不同于"总结历史"的机制**——**把已经完成的发现过程保存为发现树，再把这棵树当作经验性的回放模拟器（replay simulator）**。
  - **根节点表示初始工作区**；
  - **每个子节点保存从某个历史状态继续尝试后得到的工作区快照、候选产物、评估诊断和分数**；
  - **候选策略通过与在线探索相同的接口，逐步选择要展开的叶节点或从根节点打开新分支**；
  - **回放器只揭示相应节点中已经记录的结果，不必再次运行底层Agent 和评估器。**
- **回放成立的关键**：
  1. **在线与离线阶段使用相同的决策接口**；
  2. **只向策略逐步揭示当前已经展开的子树**。
  - **在线阶段**：被选中的节点**会真正调用底层Agent 和评估器**；
  - **离线阶段**：相同选择**只返回历史中已经记录的后继**。
  - 因此**候选策略可以比较不同的分支、顺序、并行批次和停止时机，又不能偷看在线决策时尚不可见的未来结果**。
- **三阶段的递归闭环**：
  1. **在线探索**使用当前策略**生成新的发现树**；
  2. **构造回放世界**把发现树**加入历史模拟器池**；
  3. **离线做梦**让**策略开发Agent 修改探索策略代码**，并**按候选质量、执行成本和并行效率比较版本**。
  入选策略**重新上线后产生新的树，也扩大下一轮可以回放的经验范围**。作者的限定条件：**候选集合保留当前策略，因此新版本至少不会在已有历史的平均回放分数上更差，但这只是历史内的保证。**
- **"回放"与前文两种历史复用方式的区别**（原文在本节末，跨到印刷 p.267）：
  - **轨迹总结**把经验压缩成**知识或Prompt**，改变的是 **Agent 知道什么**；
  - **浏览器工作流回放**让程序**在新任务中重复一条已验证路径**，改变的是 **Agent 怎样重复执行**；
  - **发现树回放**则比较 **Agent 怎样组织探索**。
  - 作者同时明确其局限：**"它也不是能够预测任意动作后果的完整世界模型，只能重组历史中实际走过的分支，不能保证在旧树上得分更高的策略能迁移到新任务。"**
- **归类**：从本章的分类看，**历史回放不是知识、Prompt、程序和参数之外的第五种更新载体，而是一种产生并验证更新提案的新机制**。**Dream-RSI 最终修改的是探索策略代码，因此产物仍属于程序/Harness**；它的新意在于**把过去作为上下文或训练数据的历史，变成可反复交互的离线评估环境**，**把自我进化推进到"如何分配探索计算"的元策略层**。
- **实验9-8 ★★★：把这本书交给Hermes：它能升级自己吗？**
  - 实验目的：检验Agent 能否**阅读外部知识、发现自身问题，并在外部审查和测试约束下完成一次自我更新**。
  - 实验说明：**不给Agent 预设修复目标**，而是观察它**能否把书中的原则映射到自己的代码**，并根据 **Reviewer 的退回意见继续修正**。**稳定版本、验收测试和批准门槛始终位于它的修改权限之外。**
  - 实验说明了什么：**"自我修改不是"模型读完资料后直接改代码"，而是"理解原则→提出更新提案→接受外部检验→根据反馈修正"的闭环。一次提案被接受，只能证明更新流程成立，不能自动证明下游能力已经提升。"**

**辅导讲解**

- 这一节是本章思想密度最高的一节。它要你区分两类优化：
  - **在给定方法下优化产物**（"这次该往上下文里写什么"）——**内容层**；
  - **优化产生产物的方法**（"我们应该怎样搜索、选择、过滤、格式化上下文"）——**方法层**。
  作者用 MCE 的例子把它讲得很清楚：**改一条检索规则 = 改内容管理机制**（还是在内层打转）；**让系统自己比较多种检索与整理机制、保留迁移更好的那套 = 学习如何管理上下文**（这才是外层）。
- **"五种搜索尺度"这个说法要理解准**：它不是说有五种新载体，而是说**同一批载体（知识/Prompt/Skill/程序）可以在不同粒度上被搜索**。一条规则、一整份上下文、一个工作流、一整个 Harness、以及产生提案的那个优化器本身——**越往外，单次改动的杠杆越大，归因和回滚也越难**。所以原文说**最内层"应当是默认选择"**。
- **ACE 解决的退化非常具体**，值得记下来当反面清单：多轮"重写整份 Prompt"会导致 ① **重要细节被"为了简洁"删掉**；② **互相制约的条件被合并成一句过度抽象的原则**。ACE 的对策是**带稳定标识符的条目集合 + 增量更新 + 确定性合并去重**——注意"**确定性逻辑**"这个词：合并去重不交给模型即兴发挥，而是用确定性的规则做。这与"最小 diff、保留来源"是同一套工程价值观。
- **外层搜索会遇到"反馈成本"这个天花板**，这是本节最实际的洞见。想优化"探索策略"（从哪个候选继续、何时分叉、并行多少 Worker、何时停），你得**反复跑完整的生成—评估链条**才知道策略好不好——于是就出现了原文那句话：**优化探索策略本身可能比完成任务更昂贵**。Dream-RSI 的整个设计动机就是**把这一步变便宜**。
- **发现树 = 把过去变成可交互的离线模拟器**。它的三个要素可以这样理解（笔记补充）：
  - **节点** = 一个历史状态：工作区快照 + 候选产物 + 评估诊断 + 分数；
  - **边** = "从某个历史状态继续尝试"这一步；
  - **回放器** = 一个只会"揭示已记录结果"的假环境，**不再真的调用 Agent 和评估器**。
  于是候选策略可以在**不花真实算力**的情况下，试遍不同的分支选择、执行顺序、并行批次和停止时机。
- **两条防作弊的规则很关键**：
  1. **在线与离线用同一决策接口**——否则离线学到的策略在线根本用不上（接口不一致，相当于换了题目）；
  2. **只逐步揭示已展开的子树**——否则策略会"偷看未来"，在离线回放里表现完美，在线却无法复现。这就是原文说的"**不能偷看在线决策时尚不可见的未来结果**"。
  这两条加起来保证了**回放是有信息价值的，但不是作弊的**。
- **Dream-RSI 那个"至少不会更差"的保证要读准**：它来自"**候选集合保留当前策略**"这个保险措施（相当于在搜索里永远保留 baseline），因此新版本**在已有历史的平均回放分数上**不会更差。但原文立刻补了限定：**"这只是历史内的保证"**——换句话说，**在旧树上不退化，不代表在新任务上会更好**。这与 9.3.1、9.3.2 反复强调的"历史内/保留集/迁移集"是同一套谨慎。
- **本节末尾那个"三种回放"的对照非常值得背**：

  | 方式 | 改变的是什么 | 复用的是什么 |
  | --- | --- | --- |
  | 轨迹总结 | Agent **知道什么** | 压缩后的知识 / Prompt |
  | 浏览器工作流回放 | Agent **怎样重复执行** | 一条已验证的执行路径 |
  | 发现树回放 | Agent **怎样组织探索** | 历史上走过的整棵分支树 |

  三者的抽象层级依次升高：**知识 → 动作 → 搜索策略**。而作者对发现树回放的边界说得很克制：**它只能重组历史中真实走过的分支，不是能预测任意动作后果的世界模型**。所以"在旧树上得分高"**不能保证迁移**——这句话是实验9-8 与思考题第 7 题的伏笔。
- **实验9-8 的设计目标不是"Agent 会不会改代码"，而是"它会不会走流程"**。原文给出的链条是四步：**理解原则 → 提出更新提案 → 接受外部检验 → 根据反馈修正**。而且有一条额外的谨慎：**"一次提案被接受，只能证明更新流程成立，不能自动证明下游能力已经提升"**——这直接对应 9.3 里的"Harness 更新能力 ≠ Harness 受益能力"。

**易混点**

- **更新产物内容 vs 更新"更新方法"**：前者是"这次写什么"，后者是"我们该怎样产生/管理/验证这些产物"。MCE 的内循环 = 前者，外循环 = 后者。
- **五种搜索尺度 vs 五种更新载体**：尺度不是载体；知识、Prompt、Skill、程序可能出现在多个尺度上。
- **Dream-RSI 的"回放" vs 前文两种回放**：轨迹总结改变"知道什么"，浏览器工作流回放改变"怎样重复执行"，发现树回放比较"怎样组织探索"。
- **回放模拟器 vs 世界模型**：前者**只能重组历史中实际走过的分支**，**不能预测任意动作的后果**。
- **历史内不退化 vs 新任务有提升**：保留当前策略只保证"在已有历史的平均回放分数上不更差"，**这是历史内的保证**。
- **离线回放的分数 vs 在线探索的表现**：只有接口一致、且不偷看未展开子树时，回放分数才有预测意义（参见思考题第 7 题）。

**一句话记住**

> 除了"改产物内容"，还可以**改产生与管理产物的方法**（上下文构造、工作流、Harness 代码、优化器本身）；越往外杠杆越大但越难归因，所以**默认先从最内层的最小修改做起**，而 Dream-RSI 用"**发现树当离线模拟器**"把外层搜索的反馈成本降了下来——**但它只是历史内的保证，不是世界模型**。

## 9.3 构建可长期运行的持续进化闭环

> 小节位置：印刷 p.267–269（`<<<PAGE 275>>>`–`<<<PAGE 277>>>`）。原文 `<<<PAGE 275>>>` 与 `<<<PAGE 276>>>` 之后的"9.3 构建可长期运行的持续进化闭环"均为页眉，真正的小节标题在 `<<<PAGE 275>>>` 中下部（"这里的'回放'与前文两种历史复用方式不同"那段之前的内容属于 9.2.5，已归位）。

**原文要点**

- **双循环结构**：四种更新方式只有**进入同一个自主循环**，才会从**单次优化**变成**持续进化**。图9-5 展示了生产系统中更稳妥的**双循环结构**：
  - **在线执行循环**：**只完成任务并记录证据，不直接改写正式Agent**；
  - **离线进化循环**：**聚合轨迹、诊断根因、生成更新提案，再通过验证门槛发布新版本**。
  - 两者通过**版本化的经验库和评估集连接**。

> 图 9-5（原文插图）：**在线执行与离线进化的双循环**，副标题"在线执行与离线进化：正式版本不在运行中直接改写"（印刷 p.267）。图分左右两个循环：
> **左：在线执行循环**——"稳定版 Agent" → "处理真实任务" → "记录轨迹与反馈"（箭头回到稳定版 Agent，构成循环）。
> **右：离线进化循环**——"聚合与诊断"（旁注"寻找共同根因"）→"候选修改"（旁注"知识·指令·程序·参数"，对应 9.2 四种载体）→"回归与安全验证"（旁注"保留旧能力"）→"灰度、监控与回滚"→"晋升为新稳定版"（箭头回到"聚合与诊断"，构成循环）。
> 两个循环之间的连接标注为："**版本化经验日志**"（从左往右传证据）与"**通过验证的新版本**"（从右往左回流新版本）。
> 图底有一条贯穿性约束："**可信根：权限、审计、验证与回滚机制不由普通进化流程自行修改。**"

- **Voyager 的完整循环**：**Voyager** 展示了一个较完整的持续进化循环。它在 **Minecraft** 中**根据当前能力选择新目标**，**通过环境反馈迭代程序**，**验证成功后把代码存入技能库**，再**组合旧技能解决更难任务**。
  - **三个必要条件（缺一不可）**：作者的原话是"**自动课程、可执行技能和环境验证缺一不可**"，并给出三条反例：
    - **只有技能库而没有课程**，Agent **不知道下一步学什么**；
    - **只有自我反思而没有环境验证**，**技能库会积累错误**；
    - **只有探索而没有持久化**，**每次任务仍要从头开始**。
  - 作者补充：**现实Agent 的知识、Prompt、工具和参数虽然更复杂，基本学习过程是类似的。**
  - 原书此处引用的文献（脚注 20，印刷 p.267）：**Voyager**——Wang, G., et al. *Voyager: An Open-Ended Embodied Agent with Large Language Models*. arXiv:2305.16291, 2023。

> 🔎 检索确认：原文脚注所记 **Voyager 的 arXiv 编号 2305.16291、第一作者 Wang（Guanzhi Wang 等）**与外部资料一致，论文题为 *Voyager: An Open-Ended Embodied Agent with Large Language Models*，是 Minecraft 中的开放式具身 Agent。（来源：[Voyager: An Open-Ended Embodied Agent with Large Language Models](https://sinoxiv.napstic.cn/article/4679869)）
- **Voyager 的三个互相咬合的机制**：
  1. **自动课程生成器**：**根据当前物品、环境和已掌握技能提出下一个难度适中的目标**，**使探索不是随机漫游**；
  2. **技能库**：把**成功程序保存为可检索、可组合的代码**，例如**高级采集技能可以调用移动和制作等基础技能**；
  3. **迭代提示机制**：把**环境观察、执行错误和自验证结果带回下一轮代码生成**，**直到任务真正通过**。
- **发现循环（假设、实验、评估、反馈）**：以 **Voyager** 为代表的 Agent 自我进化系统正是遵循了由**假设、实验、评估和反馈**组成的**发现循环**，**这也是数百年来逐渐形成的科学方法**。
  - **Jeff Dean 等人创办的 Discovery Loop** 提出将发现循环推向自动化：**提出实验、实现实验、开展评估、取得结果，再把结果交给下一轮**。
  - 作者的判断：这**本质上就是Agent 自我进化在科学领域的应用**；并给出要求——**"本章所述的Agent 自我进化要想避免自说自话、自我感觉良好，就必须遵循科学方法。"**
- **两种必须区分的能力**：
  - **Harness 更新能力（harness-updating）**：**从轨迹中产生有价值的持久修改**；
  - **Harness 受益能力（harness-benefit）**：**任务Agent 在后续运行中找到、激活并正确使用这些修改**。
  - 作者举的失败情形：**一个Skill 本身可能写得完全正确，但较弱的任务模型没有在合适场景加载它，或加载后无法长期遵循，其中任一种都会让最终成绩看起来"没有进化"。**
  - 由此得出的方法论：**不能只用端到端分数反推更新器好坏**。**Lin 等人的模型替换实验表明，这两种能力与基础模型能力的关系并不相同。**

**表9-3 持续进化的分层评估指标**（原书印刷 p.268）「表格按原文语义还原：原文第一列与第三列因分栏而断行，此处合并回单元格」

| 指标 | 回答的问题 | 主要证据 |
| --- | --- | --- |
| 更新提案有效率 | 更新器是否提出了有价值的修改 | 提案在独立验证中的接受率与增益 |
| 产物激活率 | 任务Agent 是否在正确场景加载了新Skill、记忆或工具 | 检索、路由与工具调用轨迹 |
| 遵循成功率 | 激活后是否按新规则或流程执行 | 动作序列与过程验证器 |
| 保留任务集增益 | 整体是否改善了未参与进化的任务，是否有泛化能力 | 保留集成功率、质量与成本 |

- **评估的定位与五类长期观测结果**：**"评估不是学习结束后集中进行的考试，而是自我进化过程中不可或缺的一部分。"** 长期评价**至少同时观察五类结果**：
  1. **回退（regression）**，即新经验**是否与已有的其他经验冲突**，**原本能通过的案例是否出现回退**；
  2. **泛化能力**，即新经验在**测试集尚未覆盖的场景**中带来的**效果提升**；
  3. **Token 效率**，即**完成任务消耗的Token 成本**；
  4. **安全性**，即**规则、隐私和拒绝边界是否随进化漂移**；
  5. **长期工程质量**，即**维护复杂度、架构一致性、所有权边界、向后兼容性以及未来迁移和调试负担是否恶化**。
- **判定标准**：**"只解决了当前失败案例的问题，却在其他已有案例或新领域中退化，不是成功的持续进化。"**
- **实验9-9 ★★★：评估Agent 是否在持续进化**
  - 实验目的：**区分"保存反馈""不断追加反馈"和"能够更新、迁移并保留能力"三种行为**，验证Agent 是否真的在持续进化。
  - 实验说明：让Agent 先**在一组任务中获得反馈**，再面对**表述变化、规则更新和原有能力保持**等情况。对照**静态记忆、只追加记忆和可替换/可淘汰的版本化记忆**，观察**经验能否迁移**，也观察**新规则是否覆盖旧规则、更新后是否遗忘**。
  - 实验说明了什么：**持续进化至少包含四个环节——记住、迁移、更新和保持。最终分数高并不够；若系统继续使用已废止规则、靠违规捷径完成任务，或更新后破坏原有能力，都不能判定为持续进化。**

**辅导讲解**

- **"正式版本不在运行中直接改写"** 是这一节的总纲。这句话解决的是一个很实际的工程焦虑：如果 Agent 在线跑着跑着就把自己改了，那么 ① 出问题时你**不知道当时跑的是哪个版本**；② 无法回滚；③ 正在进行的任务可能被中断。双循环的分解方式——**在线只做"完成任务 + 记证据"，离线才做"聚合诊断 + 生成提案 + 验证发布"**——让"学习"这件事变成了**一个可版本化、可回滚的发布流程**。
- 两个循环之间的两条连接线很值得注意：
  - **往右传的是"版本化经验日志"**：证据必须带版本（因为轨迹是在某个版本下产生的，脱离版本它无法解释）；
  - **往左回的是"通过验证的新版本"**：不是"一个新的记忆条目"，而是一个**新的稳定版**。
  也就是说，**闭环的产物是"新版本"，不是"新知识"**——这个区别决定了整个系统是否可审计。
- **图9-5 底部的"可信根"约束**（权限、审计、验证与回滚机制不由普通进化流程自行修改）在 9.3.2 会展开成三道边界。它是整个闭环能成立的前提：**如果进化流程能改自己的验证器，那么这个闭环就没有可信的收敛方向。**
- **Voyager 的三条"缺一不可"值得逐个想清楚**：
  - 没有**自动课程** → 探索退化为**随机漫游**（不知道学什么）；
  - 没有**环境验证** → 自我反思的结论直接进技能库，**错误会积累**（这正是 9.2.1 说的"反思不是证据"）；
  - 没有**持久化** → 每次都从零开始（这正是本章开头"第二天仍然犯第一天的错误"那个悖论）。
  把这三条放一起看，会发现它们恰好对应**方向（课程）、正确性（验证）、累积性（持久化）**——一个学习系统要长期有效的三个必要条件。
- **"发现循环 = 科学方法"** 是本章的价值取向："假设 → 实验 → 评估 → 反馈"。作者用它来对抗自我进化系统最常见的病：**自说自话、自我感觉良好**。判断一个自进化系统是否可信，就看它**有没有真正的实验环节**（在真实环境里做，有可证伪的预期），还是只在自己的叙述里循环。
- **Harness 更新能力 vs Harness 受益能力** 这一对概念是本节最容易被忽略、但工程上最有用的。它解释了为什么"端到端分数没涨"**不能直接归咎于更新器**：
  - 可能是更新器没提出好提案（**更新能力**问题）；
  - 也可能是提案很好，但任务 Agent **没在正确场景加载/激活它**（**产物激活率**问题）；
  - 还可能是加载了但**没有长期遵循**（**遵循成功率**问题）；
  - 或者都做到了，但**只对参与进化的那批任务有效**（**保留任务集增益**问题）。
  表9-3 的四个指标正好一一对应这四层，**这就是"分层评估"的意义：把端到端分数拆成可归因的四段。**
- **五类长期观测结果**可以按"防什么"来记（笔记补充梳理）：
  - **回退**：防"修一个坏一个"（新经验与旧经验冲突）；
  - **泛化**：防"过拟合到当前失败集"（要测测试集未覆盖的场景）；
  - **Token 效率**：防"用更多算力换分数"（成本也是能力的一部分）；
  - **安全性**：防"边界随进化漂移"（规则、隐私、拒绝边界）；
  - **长期工程质量**：防"技术债累积"（维护复杂度、架构一致性、所有权边界、向后兼容、迁移与调试负担）。
  注意最后一项是**面向人的成本**，也是最容易被"分数导向"的系统忽略的一项。
- **实验9-9 的三种记忆对照**（静态记忆 / 只追加记忆 / 可替换可淘汰的版本化记忆）是在验证一个很硬的结论：**"只追加"不等于学习**。只追加的系统会遇到原文列的三类问题：**继续使用已废止规则**（旧规则没被覆盖）、**靠违规捷径完成任务**（没有过程验证）、**更新后破坏原有能力**（没有回归）。而"持续进化"的四个环节——**记住、迁移、更新、保持**——正好把这三种失效都堵住。

**易混点**

- **在线循环 vs 离线循环**：在线只完成任务并记证据（**不改写正式 Agent**）；离线做诊断、提案、验证与发布。
- **Harness 更新能力 vs Harness 受益能力**：前者是"产生有价值的持久修改"，后者是"任务 Agent 找到、激活并正确使用这些修改"。**成绩没涨不一定是更新器的问题。**
- **端到端分数 vs 分层指标**：表9-3 的四项（提案有效率、产物激活率、遵循成功率、保留任务集增益）才能定位问题出在哪一层。
- **评估是流程的一部分 vs 评估是最后的考试**：原文明确说评估"不是学习结束后集中进行的考试"。
- **记住 / 迁移 / 更新 / 保持**：四个环节缺一不可；"只追加记忆"只做到了"记住"。

**一句话记住**

> 持续进化必须把**在线执行**与**离线进化**拆成两个循环——**在线只记证据，离线才生成并验证更新，最终产出的是一份通过验证的新稳定版**；评估要**分层**（提案有效 / 被激活 / 被遵循 / 保留集增益），并长期同时看**回退、泛化、Token 效率、安全性、长期工程质量**五件事。

### 9.3.1 可验证闭环的边界：当"完成"不等于"进步"

> 小节位置：印刷 p.269（`<<<PAGE 277>>>`）。原文 `<<<PAGE 277>>>` 之后的"9.3 构建可长期运行的持续进化闭环"为该页页眉，笔记按语义归位。

**原文要点**

- **闭环在哪些任务上最容易成立**：**Coding、工具调用和业务状态变更等任务**最容易成立，因为**测试、环境状态或确定性规则能够快速给出反馈**。
- **在哪些任务上最难成立**：**开放式科研、战略规划和复杂产品设计**则不同，原因是三条：
  1. **评价信号来得慢**；
  2. **正确答案不唯一**；
  3. **研究品味、长期价值、可维护性等真正重要的目标还很难用分数评判**。
  作者刻画了这类场景下的典型失效形态：**此时Harness 可能把流程执行得非常完整，却只是稳定地产出"像成果的东西"，没有推动真实目标。**
- **自动科研作为压力测试**：**Trehan 与Chopra 记录了四次从研究想法走向论文的端到端尝试，其中三次在实现或评估阶段失败，只有一次完成整条流水线。** 这些案例暴露的问题可以**归成三类**：
  1. **实现漂移**：**原方案一旦变难，Agent 会逐渐退回训练数据中更熟悉、但已经偏离研究假设的普通实现。**
  2. **认识论上的过度乐观**：**信号仍可能只是噪声，系统却开始解释结果、添加补丁并宣布发现；失败和阴性结果则更容易被忽略。**
  3. **隐性判断力不足**：**Agent 可以运行实验，却未必知道什么基线真正重要、哪个异常值得追踪、何时应该放弃假设。**
- **结论与对策**：**这类任务不能靠换一个模型彻底解决，而要改变证据和监督结构。** 原文给出四条：
  1. **结论与证据分离**：**对引用、数字、方法和结论分别记录证据来源，最终文稿只是证据图的一种呈现。** **ScientistOne** 的 **Chain-of-Evidence** 设计**把每类声明都链接到可审计来源**，是这一方向的案例；但它**提高的是可追溯性，并不自动保证研究问题有价值**。
  2. **保留负面结果**：**失败实验、被拒提案和停止原因写入日志。** 否则**进化模块只看到幸存方案，会反复探索已经证伪的路径**。
  3. **维护搜索多样性**：**不应只保留当前得分最高的一条链。** **备选方案池还需保留若干暂时低分但类型不同的分支**，**避免所有方案收敛成同一个易得分模板**。
  4. **让人类在更高层介入**：**人的作用不应只是在危险工具调用前点"批准"，还包括定义问题、审查评价标准、解释反常结果和决定何时停止。**

**辅导讲解**

- 这一节的关键句是"**把流程执行得非常完整，却只是稳定地产出"像成果的东西"**"。这是自进化系统里最隐蔽的一种失败：所有指标都是绿的（流程走完了、报告生成了、格式没毛病），**唯一的问题是真实目标没有被推进**。它比"跑出错"危险得多，因为错误看得见，而"看起来很完整"看不见。
- 三类问题的性质各不相同，可以分别理解（笔记补充）：
  - **实现漂移**是一种**优化压力下的滑坡**：原方案难，模型会自然滑向训练数据里更常见、更省力的写法——它**不是故意跑偏，而是"更熟悉"的路径在梯度/采样的意义上更容易被选中**。
  - **认识论上的过度乐观**是一种**叙事冲动**：信号还只是噪声，系统已经开始"解释结果、添加补丁并宣布发现"。注意它还配了一个不对称：**失败和阴性结果更容易被忽略**——这正好是第 2 条对策（保留负面结果）要治的病。
  - **隐性判断力不足**是一种**品味缺失**：能跑实验，但不知道**什么基线重要、哪个异常值得追、何时该放弃假设**。前两条可以靠"证据结构"缓解，这一条更接近"研究品味"，也是原文说"不能靠换一个模型彻底解决"的原因。
- **四条对策其实是四种不同的治理手段**（笔记补充梳理）：
  - **结论与证据分离** → 治**不可追溯**（要求每类声明都链接到可审计来源）；注意作者的限定：**可追溯 ≠ 问题有价值**。追得再清楚，也可能是在研究一个不重要的问题。
  - **保留负面结果** → 治**幸存者偏差**（不保留失败，进化模块只能看到活下来的方案）；
  - **维护搜索多样性** → 治**收敛到易得分模板**（只留最高分那条链，会导致所有方案长得一样）；
  - **人类在更高层介入** → 治**目标与标准本身的问题**（定义问题、审查评价标准、解释反常、决定停止）。
- "**让人类在更高层介入**"这一条特别值得停下来看，因为它澄清了一个常见误解：**人在 Agent 系统里的角色不只是"审批危险操作"**。原文列举的四件事——**定义问题、审查评价标准、解释反常结果、决定何时停止**——全都是**元层面的判断**，而且正好是当前模型最不擅长的（也正是第三类问题"隐性判断力不足"）。所以"人工介入"不应该只被设计成一个弹窗，而应该是**对评价标准和问题定义的所有权**。
- 与本章主线的呼应（笔记补充）：9.3 讲闭环怎么搭，9.3.1 讲**闭环在什么条件下不成立**。作者的态度很诚实——**可验证闭环有边界，越出边界它就会退化成"稳定地产出像成果的东西"**。这也解释了为什么 9.4 小结最后要补一句"对于目标模糊、反馈延迟的开放任务，人仍需参与问题定义和评价标准的制定"。

**易混点**

- **"完成任务" vs "取得进步"**：前者是流程走完（Harness 执行完整），后者是真实目标被推进。在结果可自动验证的任务上两者大致重合，在开放式任务上可能完全脱节。
- **可追溯性 vs 有价值**：ScientistOne 的 Chain-of-Evidence 提高的是**可追溯性**，**不自动保证研究问题有价值**。
- **保留成功 vs 保留失败**：只留成功会得到"幸存者方案集"，进化模块**会反复探索已证伪的路径**。
- **单一最优链 vs 多样化备选池**：只保留最高分链会收敛到**同一个易得分模板**；需要保留"暂时低分但类型不同"的分支。
- **人在低层审批 vs 人在高层定义**：前者是"危险调用前点批准"，后者是**定义问题、审查评价标准、解释反常结果、决定何时停止**。

**一句话记住**

> 可验证闭环只在**结果可自动验证**的任务上可靠；在开放式科研/战略/产品设计里，"**流程走完**"很容易伪装成"**取得进步**"，此时要改的是**证据与监督结构**——**结论与证据分离、保留负面结果、维护搜索多样性、让人在更高层介入**。

### 9.3.2 持续进化的安全边界

> 小节位置：印刷 p.269–270（`<<<PAGE 277>>>`–`<<<PAGE 278>>>`）。

**原文要点**

- **风险的三个具体形态**：**Agent 的自我进化能力有可能把一次错误变成长期风险。**
  1. **网页、邮件和工具输出中的提示注入若被总结成经验，可能跨会话反复生效**；
  2. **自动搜索的恶意软件包若被封装成工具，影响会从一次沙盒运行扩散到所有后续任务**；
  3. **一个有缺陷的验证器还可能持续批准看似进步、实际退化的待验证版本**。
  - 因此得出的总要求：**Agent 自我进化系统除了验证"是否更强"，还必须限制"谁能改什么、依据来自哪里"。**
- **第一道边界：证据与指令隔离**
  - **原始网页、工具输出及其LLM 摘要都属于不可信证据**，**不能当作指令执行**，**也不能直接纳入Skill 等长期能力**。
  - 作者特别澄清一个误解：**"LLM 总结只是为了提高可读性和便于处理的转换，并不是把输入变得无害的净化过程。"**
  - 具体做法：**系统应按固定schema 提取主张、原文位置和采集时间，同时保留原文与来源；提取出的字符串绝不能作为指令执行。**
  - **模型给出的置信度也只是未经验证的估计，不能充当批准门槛。**
  - **待发布内容还需通过确定性的schema、允许列表和来源检查**，**再以版本化的pull request 提交**；**独立于生成者的reviewer 应对照原始证据审查变更**，**高风险Skill 上线前还应经过人工批准**。
- **第二道边界：待验证能力与正式能力隔离**
  - **新知识、Prompt、Skill、程序和参数都先进入不可服务真实流量的待验证区。**
  - **新生成的代码和外部依赖还要经过沙盒、权限检查、供应链扫描与行为测试等安全检查。**
  - **安全检查和回归测试通过后，才能服务真实流量，成为正式能力。**
- **第三道边界：安全机制不可自我修改**
  - **业务Agent 可以修改Prompt、Skill、知识库、工具等**，**但不能修改批准自身更新的验证器、测试用例、发布门槛、审计日志和稳定版本备份**。
  - 作者的推理很直接：**"否则，一个Agent 只需降低测试阈值或删除失败用例，就能把退化伪装成进步。"**

**辅导讲解**

- 这三道边界可以概括成三个问题，值得背下来（笔记补充）：
  - **第一道：这段话可信吗？**（证据与指令隔离——依据来自哪里）
  - **第二道：它上线了吗？**（待验证区与正式能力隔离——谁能影响真实流量）
  - **第三道：谁在给谁打分？**（安全机制不可自我修改——谁能改什么）
  三者分别管**输入、通道、裁判**。
- **第一道边界最容易犯的三个错**：
  1. **把摘要当净化**。原文否定得很干脆：**"LLM 总结只是为了提高可读性和便于处理的转换，并不是把输入变得无害的净化过程。"** 也就是说，一段含提示注入的网页，经过 LLM 摘要之后**依然是不可信输入**——摘要不会"洗掉"注入，它只是换了种写法。
  2. **把置信度当门槛**。模型说"我 90% 确信这条经验正确"，这句话本身也是模型的输出，**不能拿来当批准依据**。批准门槛必须是**确定性的**检查（schema、允许列表、来源检查）。
  3. **把字符串当指令**。即使已经按 schema 提取成"主张 + 原文位置 + 采集时间"，**提取出来的字符串也绝不能作为指令执行**——因为它依然是外来文本。
- **第一道边界的正解可以拆成"四步走"**：**固定 schema 提取 → 保留原文与来源 → 确定性检查（schema / 允许列表 / 来源）→ 版本化 PR + 独立 reviewer（高风险还要人工批准）**。注意这里**没有任何一步依赖模型的自评**，这正对应 9.2.2.1 里"提炼产物不能直接发布，须经与提炼者相互独立的验证"。
- **第二道边界的核心是"没有一条路径能绕过待验证区"**。它把 9.2 里的四种载体**一视同仁**：不管是知识、Prompt、Skill、程序还是参数，**都先进待验证区**。其中"参数"这一项容易被忘——SFT/RL 出来的权重同样是待验证能力，也要先不服务真实流量。并且对新代码和外部依赖，原文额外要求了一组**供应链性质**的检查：**沙盒、权限检查、供应链扫描、行为测试**（这直接对应本节开头"恶意软件包被封装成工具"那个风险）。
- **第三道边界是这三道里最"元"的一条**，也是整章反复出现的那句"可信根"的落地：**业务 Agent 可以改业务资产（Prompt、Skill、知识库、工具），但不能改评判自己的东西（验证器、测试用例、发布门槛、审计日志、稳定版本备份）**。原文给的反例很有画面感：**只要降低测试阈值或删除失败用例，退化就能伪装成进步**。
- 三条边界与前面各处的呼应（笔记补充）：**9.2.2.1** 的"模型把失败写入规范"→ 靠第一道 + 独立验证防；**9.2.3** 的"生成提案的 Agent 无权修改安全测试与批准规则"→ 就是第三道；**9.2.3 验证层**的"安全门本身不能被提案修改"→ 也是第三道；**实验9-7** 的"真实模型生成的更新提案可能被安全门拒绝"→ 三道边界合力的效果。
- 一个实践提醒（笔记补充）：这三道边界的**成本是不对称的**。第一、二道边界主要增加流程开销（提取、检查、待验证区、灰度）；第三道边界才是**架构层面**的约束——它要求系统设计时就把"可信根"划出来，**不能事后补**。如果一开始就让进化流程持有验证器和发布门槛的写权限，后面再想收回来会非常困难。

**易混点**

- **不可信证据 vs 无害输入**：原始网页/工具输出**及其 LLM 摘要**都属于不可信证据，摘要**不是净化**。
- **模型的置信度 vs 批准门槛**：置信度是**未经验证的估计**；门槛必须是**确定性的** schema / 允许列表 / 来源检查。
- **待验证能力 vs 正式能力**：新知识、Prompt、Skill、程序和参数**一律先进待验证区**，不可服务真实流量。
- **业务资产 vs 安全机制**：可以改 Prompt、Skill、知识库、工具；**不能改**验证器、测试用例、发布门槛、审计日志、稳定版本备份。
- **人工批准的位置**：**高风险 Skill 上线前**必须人工批准；而第一道边界中的常规检查是靠确定性规则 + 独立 reviewer，不是每件事都等人点批准。

**一句话记住**

> 自我进化系统除了问"**是不是更强**"，还必须管住"**依据来自哪里、谁能改什么**"：**不可信证据绝不当指令**（摘要不等于净化、置信度不等于门槛）、**一切新能力先进待验证区**（含参数与新依赖的供应链检查）、**评判系统自身的那套东西不可被它修改**（否则降低阈值就能把退化伪装成进步）。

### 9.3.3 睡眠学习：整合、遗忘与能力保鲜

> 小节位置：印刷 p.270（`<<<PAGE 278>>>`）。原文 `<<<PAGE 278>>>` 之后的"9.4 本章小结"为该页页眉（该页页脚为 270），真正的 9.3.3 标题紧接其后；9.4 的实际正文标题在下一页（印刷 p.271），笔记按正文页脚归位。

**原文要点**

- **定义与澄清**：**"睡眠学习"是对离线整合的认知类比，并不要求任务真的在夜间运行。**
- **在线与后台的分工**：
  - **在线Agent 的首要职责是完成当前任务并追加不可变证据**；
  - **后台学习进程则在空闲期或满足门控条件时读取一批新经历**，**比较新旧结论、合并重复项、解决冲突、提出更新提案并运行回归**。
  - **把采集与整理分开**的两个好处：**可以防止一次偶发成功、网络故障或恶意输入立刻改写长期能力**，**也允许系统使用更大的批量和更便宜的模型完成整理**。
- **一个典型的睡眠学习周期包含五步**：
  1. **触发**：**达到时间间隔、新增轨迹数量、存储容量或错误频率门槛，并确认当前没有高优先级在线任务**；
  2. **定向**：**读取正式知识、Prompt、Skill 目录及其版本，了解已有能力和不可修改边界**；
  3. **采集与整合**：**从近期已评价轨迹中寻找新信号，合并重复内容，标记冲突与适用条件，优先生成局部补丁**；
  4. **验证与审批**：**在迁移集、保留集和安全集上评估待验证版本，高风险写入等待人工批准**；
  5. **修剪与索引**：**更新检索索引，把长期不用或被新证据推翻的能力标记为过期，或将其归档、删除，同时保留来源和回滚版本**。
- **用户记忆的实例（Claude Code）**：**用户记忆是最直观的例子，但要与行动经验区分。**
  - **Claude Code 的自动记忆**为**每个项目维护 MEMORY.md 索引和按主题拆分的详细文件**，**会话启动只加载索引的有界前缀，其余内容按需读取**；**当索引接近上限时，系统要求Agent 合并或移走细节**。
  - 作者的评价：它说明**纯文本记忆也需要容量约束、分层加载和主动整理**，**但当前公开机制主要是在会话中持续写入，并不能简单等同于一个固定的夜间后台任务**。
- **更完整的后台记忆进化案例（Hermes）**：
  - 它把长期信息分成**有界的 MEMORY.md 与 USER.md**、**基于 SQLite/FTS5 的历史会话检索**、**按需加载的 Skill**，以及 **Honcho 等可选外部记忆提供者**。
  - **历史检索返回原始消息而非先由 LLM 摘要**，**避免把检索和生成混成一个不可审计步骤**。
  - **触发后台复盘的条件**：**当一次任务包含较多工具调用、从错误或死路中恢复、收到用户纠正，或发现非显而易见的工作流时**，后台复盘**可以创建或局部修订 Skill**；**记忆和 Skill 写入还可以经过审批门控**。
  - **独立的 Curator**：**进一步跟踪 Skill 的使用、陈旧和归档状态**，**在空闲期执行确定性修剪**，**并可选择运行 LLM 合并**；**变更前保存快照，错误整理可以回滚**。
- **周期性离线整理的必要性**：**持续进化也不是让知识、Prompt 和工具无限增长。** **第二章所说的上下文腐化会在更长时间尺度上重现**：
  - **经验文档相互冲突**，
  - **Prompt 被边界规则淹没**，
  - **Skill 库出现重复能力**，
  - **多次微调造成灾难性遗忘**。
- **系统需要周期性离线整理，原文列出六项**：
  1. **合并重复经验，保留来源和版本**；
  2. **把局部规则从全局Prompt 移动到领域Skill，保持全局Prompt 整洁**；
  3. **Prompt 和Skill 保持结构清晰**；
  4. **重新验证长期未使用的工具**；
  5. **删除被新证据推翻的知识**；
  6. **从原始基座模型重新训练LoRA**。

**辅导讲解**

- "**睡眠学习**"这个名字的妙处在于它抓住了两件事：**整合**（把新经历和旧结论放在一起比较、合并、解决冲突）和**遗忘**（把过期、冲突、长期不用的东西修剪掉）。而且它明确**只是认知类比，不要求夜间运行**——触发条件可以是时间间隔、轨迹数量、存储容量或错误频率（第 1 步）。工程上这一点很重要：**别把"离线"理解成"定时任务"，它更应该是一个受门控的批处理**。
- **"把采集与整理分开"是本节的核心原则**，它的两个好处值得分别记住：
  - **安全好处**：**一次偶发成功、网络故障或恶意输入不会立刻改写长期能力**。这直接呼应 9.3.2 的第一道边界——如果在线就把观察写进长期能力，提示注入只要成功一次就能持久化；批量整理时，多条轨迹互相印证能大幅降低这种风险。
  - **成本好处**：**允许使用更大的批量和更便宜的模型完成整理**。因为整理不是在关键路径上，可以用更廉价的模型、更多的样本、更充分的比较。
- **五步周期里，"定向"这一步容易被忽略但其实很关键**：它要求后台进程先**读取正式知识、Prompt、Skill 目录及其版本**，**了解已有能力和不可修改边界**。也就是说，整理进程在动笔之前必须先**知道现状和红线**——这既避免了重复劳动（已有能力不再重复生成），也避免了越界（不可修改边界）。
- **第 5 步"修剪与索引"是"遗忘"的落地**：**标记过期 / 归档 / 删除**，并且强调"**同时保留来源和回滚版本**"。注意这里的三档操作是渐进的（标记 → 归档 → 删除），不是一刀切。一个可复用的判断标准是原文给的两种依据：**长期不用** 或者 **被新证据推翻**。
- **Claude Code 的 MEMORY.md 例子演示了"容量约束 + 分层加载 + 主动整理"**三件事（笔记补充解读）：
  - **容量约束**：索引是**有界**的；
  - **分层加载**：会话启动**只加载索引的有界前缀**，细节文件**按需读取**；
  - **主动整理**：索引接近上限时，**要求 Agent 合并或移走细节**。
  作者同时做了一个诚实的限定：**当前公开机制主要是在会话中持续写入，并不能简单等同于一个固定的夜间后台任务**——也就是说，它更像"边写边整"，而不是标准的"睡眠学习"。
- **Hermes 是更完整的例子**，它的设计里有三个细节值得单独记住：
  1. **历史检索返回原始消息，而不是先让 LLM 摘要**——作者的评价是"**避免把检索和生成混成一个不可审计步骤**"。这跟 9.3.2 第一道边界完全一致：**摘要不是净化，也不是证据**；要审计就得能看到原文。
  2. **后台复盘有明确的触发条件**（工具调用多、从错误/死路恢复、收到用户纠正、发现非显而易见的工作流）——这比"定时全量复盘"更精准，因为它只在**可能产生新经验的时刻**才触发。
  3. **独立 Curator + 空闲期确定性修剪 + 变更前快照**——注意"**确定性修剪**"和"**变更前保存快照，错误整理可以回滚**"这两点：整理本身也是要能回滚的操作。
- **"上下文腐化会在更长时间尺度上重现"** 是本节最重要的一句判断。第二章讲的上下文腐化（任务内的上下文被无关内容稀释）在这里变成了**跨会话、跨月的知识腐化**：四个具体形态是——**经验文档相互冲突、Prompt 被边界规则淹没、Skill 库出现重复能力、多次微调造成灾难性遗忘**。前三个都是"**只增不减**"的必然结果，第四个是参数载体特有的。
- **六项整理措施可以按对象分组**（笔记补充）：

  | 整理动作 | 针对的对象 | 治的病 |
  | --- | --- | --- |
  | 合并重复经验，保留来源和版本 | 知识 | 经验文档相互冲突 / 重复 |
  | 局部规则从全局 Prompt 移到领域 Skill | 指令 | Prompt 被边界规则淹没 |
  | Prompt 和 Skill 保持结构清晰 | 指令 | 同上（结构层面） |
  | 重新验证长期未使用的工具 | 程序 | 工具陈旧、失效未被发现 |
  | 删除被新证据推翻的知识 | 知识 | 知识过期、被推翻 |
  | 从原始基座模型重新训练 LoRA | 参数 | 多次微调造成灾难性遗忘 |

  最后一项是很有代表性的一招：**当多次增量微调把模型带偏（灾难性遗忘）时，补救方式不是继续在小数据集上微调，而是回到原始基座模型重新训练**。这与 9.2.4 的判断一致——参数的更新与回归成本高，所以参数的维护周期也最长。

**易混点**

- **睡眠学习 vs 定时夜间任务**：前者是**对离线整合的认知类比**，**不要求任务在夜间运行**；触发条件是门控（时间间隔、轨迹数量、存储容量、错误频率 + 无高优先级在线任务）。
- **在线写入 vs 离线整理**：在线**只完成任务 + 追加不可变证据**；比较、合并、解决冲突、提案、回归都在后台批处理中做。
- **用户记忆 vs 行动经验**：用户记忆是"用户与世界是什么样的"（本节用 Claude Code / Hermes 举例说明记忆系统本身怎么整理），本章的经验学习目标是"在什么条件下应该怎样行动"；原文明确要**把两者区分开**。
- **标记过期 / 归档 / 删除**：三档渐进操作，且都要**保留来源和回滚版本**。
- **修剪（确定性）vs 合并（可选用 LLM）**：Curator 在空闲期执行的是**确定性修剪**，LLM 合并是**可选**的、且变更前保存快照、可回滚。
- **上下文腐化 vs 知识腐化**：第二章讲任务内上下文腐化，本节讲**同一问题在更长时间尺度上的重现**（文档冲突、Prompt 淹没、Skill 重复、灾难性遗忘）。

**一句话记住**

> 把"**采集**"和"**整理**"分开：在线只追加不可变证据，后台在门控条件下批量做**整合与遗忘**（比较新旧、合并重复、解决冲突、修剪过期、重建索引），且**每一次整理都要可回滚**——因为不整理的话，知识、Prompt、Skill 和参数都会像上下文一样腐化。

## 9.4 本章小结

> 小节位置：印刷 p.270–271（`<<<PAGE 278>>>`–`<<<PAGE 279>>>`）。原文 `<<<PAGE 279>>>` 之后的"9.4 本章小结"为该页页眉，笔记按语义归位；本节内容横跨两页。

**原文要点**

- **现状判断**：**持续进化正在成为Agent 最重要的能力之一，但今天的模型还无法自行完成可靠的持续学习。** 两条具体理由：
  - **推理时的上下文适应不会自动持久化**；
  - **未经验证的在线参数更新又会放大噪声、攻击和能力漂移**。
  - 由此得出的路径选择：**现阶段更可行的路径，是在模型外围建立可验证的学习系统。**
- **在全书中承担的角色**：**就全书的结构而言，本章构建的是第一章发现循环中的实验与反馈环节**——**提案已经有了，问题变成怎样通过一次以真实观测为基础的实验，判断它到底有没有让系统变好，以及怎样把结果送回下一轮。**
- **方法层面的总结**：**Agent 从与环境的交互和评价中获得学习信号，再根据能力的表示性质更新知识、Prompt、Skill、程序或模型参数。**
  - **系统也可以进一步优化管理和生成这些产物的方法**，**但应优先采用可归因、可验证、可回滚的局部修改**。
  - **遇到问题时，先判断它更适合由外部规则、程序流程、Skill 还是模型参数处理，再用独立的边界任务和原有任务检查修改是否真正有效。**
- **关于历史的作用（回放）**：**历史不仅能被提炼为静态经验，还能在支持域内组成回放环境，低成本筛选探索策略。** 其意义是——**这使持续进化可以进一步作用于"如何组织探索"，而不只作用于探索产生的知识、指令和程序。**
- **在线/离线分离与边界**：**持续进化需要把在线执行与离线学习分开**：**在线记录证据，离线生成并验证更新提案，再逐步发布、整理或回滚。**
  - **这个闭环在结果可自动验证的任务上最可靠**；
  - **对于目标模糊、反馈延迟的开放任务，人仍需参与问题定义和评价标准的制定。**

**辅导讲解**

- 小结里的这句话值得当作整章的定位声明：**"本章构建的是第一章发现循环中的实验与反馈环节"**。也就是说，第九章不是又发明了一种方法，而是**给全书的方法论装上了"学习回路"**——提案（来自第五章的元能力、第八章的参数更新等）本身不算进步，**只有经过一次以真实观测为基础的实验，判断它是否让系统变好，并把结果送回下一轮，才算闭环**。
- 小结把全章的判断浓缩成了一条**决策顺序**（笔记补充整理）：
  1. **先要信号**：从与环境的交互和评价中获得学习信号（对应 9.1）；
  2. **再定位置**：按**能力的表示性质**决定更新知识 / Prompt / Skill / 程序 / 参数（对应 9.2）；
  3. **再定尺度**：优先采用**可归因、可验证、可回滚的局部修改**（对应 9.2.5，默认最内层）；
  4. **最后验证**：用**独立的边界任务和原有任务**检查修改是否真正有效（对应 9.2.2 的边界集/保留集、9.3 的分层评估）；
  5. **长期维护**：在线记录证据、离线生成并验证提案、逐步发布/整理/回滚（对应 9.3、9.3.3）。
- "**在支持域内组成回放环境**"这个限定词（"在支持域内"）很关键，它和 9.2.5 末尾那句"**不能保证在旧树上得分更高的策略能迁移到新任务**"是同一个谨慎：**回放只对历史实际覆盖过的分布（支持域）有效**，出了这个域，回放成绩就失去预测力。思考题第 7 题问的正是这件事。
- 最后那句"**对于目标模糊、反馈延迟的开放任务，人仍需参与问题定义和评价标准的制定**"是本章的诚实收尾。注意它说的"人参与"**不是审批危险操作**（那是 9.3.2 第二道边界的层面），而是**定义问题与制定评价标准**——也就是 9.3.1 第四条对策"让人类在更高层介入"的复述。**整章的乐观是有边界条件的乐观。**

**易混点**

- **本章的位置 vs 本章的内容**：本章构建的是第一章发现循环中的**实验与反馈**环节，而不是一套全新的方法论。
- **优化产物 vs 优化方法**：小结明确"系统也可以进一步优化管理和生成这些产物的方法"，但**优先级**是可归因、可验证、可回滚的局部修改。
- **可自动验证任务 vs 开放任务**：前者的闭环最可靠；后者需要人参与**问题定义与评价标准**。
- **静态经验 vs 回放环境**：历史既能被提炼为静态经验（知识/Prompt），也能在支持域内组成回放环境（筛选探索策略）——两者不是一回事。

**一句话记住**

> 现阶段的可靠路径是**在模型外围建一套可验证的学习系统**：从交互与评价中获得信号 → 按能力表示性质决定更新哪一层 → 优先做可归因、可验证、可回滚的局部修改 → 用独立边界任务与原有任务验收 → 在线记证据、离线做提案与发布；**开放任务上，人仍要参与问题定义和评价标准。**

## 思考题

> 原文在"思考题"之前有一个"**深度思考**"的栏目名（印刷 p.271），随后列出 7 道题。以下每题**题干照抄原文**，其后是**思路提示（笔记补充，非原文答案）**。

**1. ★★ 一条经验文档由三次成功轨迹和一次失败轨迹支持。失败发生在较新的API 版本上。系统应如何判断这是经验被推翻，还是适用条件发生了变化？**

- *思路提示*：关键是先判断"变量是什么"。如果是**API 版本变化**，那么合理的假设是"经验本身仍成立，但适用条件需要收窄/追加例外"，而不是"经验被推翻"——按 9.2.1 的要求，正式文档本来就该写清**适用场景、例外条件、最近验证时间**。可操作的做法：把失败轨迹与三条成功轨迹按**环境版本**分层对照（9.2.1 说的"某种策略在哪些环境版本中有效，在哪些前置条件下失效"），在一个**未参与提炼**的迁移集上分别测试"原经验 + 版本条件"与"直接废弃经验"两种处理，看哪种在两类版本上都不退化。另外要考虑 9.1 的"证据不足时允许拒绝评分"：如果只有一条新版本轨迹，样本量可能还不足以支撑任何结论，可以先标记为"待观察/需限定"，而不是立刻改写文档。

**2. ★★ 客服Agent 的用户满意度上升，但规则违规率也上升。为什么不能把满意度作为单一学习信号？你会怎样设计护栏指标？**

- *思路提示*：原文在 9.1 与章首导言都点明了这个病——**"用户满意不意味着合规"**，且 9.1 举例"口头承诺我们会在 7 天内退款"可能换来暂时的满意反馈。**满意度是质量层（甚至只是质量层的一个侧面）的信号，不能替代结果层与过程层。** 护栏指标可直接取自表9-1：与满意度**成对观测**规则遵从、隐私边界、承诺—行动一致性、事实可靠性；再加 9.3 的五类长期结果（回退、泛化、Token 效率、安全性——特别是"规则、隐私和拒绝边界是否随进化漂移"、长期工程质量）。设计要点：① 护栏指标必须是**可以被独立验证的**（政策库、动作轨迹、工具日志），不能由生成回复的同一个模型自评；② 发布门槛应是"满意度不降 **且** 违规率不升"，而不是两者加权求和（加权会把违规"换"成满意度）；③ 借鉴实验9-2 的做法，除主指标外记录**与规则一一对应的行为指标**，用来证明提升是来自机制而不是波动。

**3. ★★★ 同一个"虚假承诺"问题可以通过Prompt、Harness 检查或参数训练缓解。你会依据哪些证据选择修改位置？**

- *思路提示*：回到图9-3 的"首要判断"——**这个能力能否被事实、语言规则或程序完整表达？** "不要承诺未兑现的操作"这类**硬性业务规则**是可以被完整表达的，所以**首选不是参数**（9.2.4、思考题6 都暗示参数难以保证硬性业务规则）。然后在 Prompt 与 Harness 之间选，依据可以包括：① **确定性**——"承诺—行动一致性"可以由"回复与工具日志对照"来判定（表9-1），说明它是**可确定解析、可执行验证**的，按表9-2 更适合**程序与 Harness**；② **是否可绕过**——如果这是不可绕过的硬约束（9.2 的"关键合规则由服务端代码兜底"），就应由程序门控；③ **归因证据**——按 9.2.3 的"变更契约"要求，看失败轨迹里是"模型知道规则但没遵守"（→ 需要更硬的手段/Harness 检查），还是"模型根本不知道这条规则"（→ 补一条最小 Prompt 规则即可）；④ **作用域**——如果是某类企业政策特有的，放进 Skill 而不是全局 Prompt（表9-2 的"作用范围可控"）。另外注意 9.3.2 第三道边界：无论选哪一层，验证器与发布门槛都不能由提案方修改。

**4. ★★★ Agent 能修改工具和验证器，却不应修改批准自身更新的可信根。你会如何划分这两部分的权限和代码边界？**

- *思路提示*：原文的判据是"**真正的保证必须来自被修改者无法触及的那一层**"（9.2.3 验证层）、"**安全机制不可自我修改**"（9.3.2 第三道）。可写进答案的划分依据：**业务资产可改**（Prompt、Skill、知识库、工具），**评判系统自身的那套不可改**（验证器、测试用例、发布门槛、审计日志、稳定版本备份）。工程上的落地方式可以借用 9.2.3 已有的机制：① 权限上分离——进化流程只有"**提 PR**"的权限，没有合并与发布权限；② 代码边界上，可信根所在的仓库/模块对提案 Agent **只读**，且安全测试与批准规则由独立于生成者的角色持有（实验9-6/9-7 都要求"生成提案的 Agent 无权修改安全测试和批准规则"）；③ 审计上，所有变更走**版本化 pull request + 独立 reviewer + 高风险人工批准**（9.3.2 第一道边界）；④ 可回滚上，保留稳定版本备份与快照。注意题面本身有个陷阱值得指出：如果说"Agent 能修改验证器"，那要看这个"验证器"是**业务验证器**（比如新增一个参数检查，9.2.3 允许）还是**批准它自身更新的验证器**（绝不允许）——两者同名不同权。

**5. ★★ 经验知识库不断增长后，检索错误和知识冲突会抵消学习收益。如何设计版本、时效和淘汰机制？**

- *思路提示*：原文给的素材集中在 9.2.1 与 9.3.3。① **版本**：正式文档要写"**版本与验证时间**"（图9-4），新证据用于"**修订、限定或淘汰**"旧知识；9.3.3 的修剪要"**保留来源和回滚版本**"。② **时效**：文档里记"**最近验证时间**"；9.3.3 第 5 步把"**长期不用或被新证据推翻的能力标记为过期，或归档、删除**"，并且是**标记 → 归档 → 删除**三档渐进。③ **冲突处理**：9.3.3 第 3 步明确要"**合并重复内容，标记冲突与适用条件**"；ACE（9.2.5）用"**带稳定标识符的条目集合 + 增量更新 + 确定性合并去重**"来避免多轮重写丢细节。④ **检索错误**：9.2.1 的"三层数据"（不可变轨迹 / 单次分析 / 跨轨迹归纳文档）保证了任何一条知识都能追到支持它的轨迹与反例，从而能精准修订；9.3.3 第 5 步还要求"更新检索索引"。⑤ 指标上要看表9-3 的"保留任务集增益"与 9.3 的"回退"，确认整理之后旧任务没有退化。可以补一句判断标准：**只增不减的库必然腐化**（原文列出的四种腐化形态）。

**6. ★★★ 参数学习擅长自然语言风格，却难以保证硬性业务规则。请为医疗客服设计一套参数、知识、Skill 和代码约束协同的持续进化方案。**

- *思路提示*：可以直接套图9-3 + 表9-2 的分工，并参照原文两个复合例子（医疗影像 Agent"依靠参数识别病灶，用知识库提供最新指南，再用代码计算风险指标"；客服模型"自然语气来自后训练，具体企业政策由知识和 Skill 提供，关键合规由服务端代码兜底"）。建议的协同方案骨架：**参数**——自然语气、同理心表达、去模板化"AI 味"、跨任务的识别习惯，用 SFT/偏好训练/RL 写入，数据来源是"经过评价的生产轨迹"（9.2.4：高质量示范→SFT、明确偏好→成对数据、可靠环境奖励→RL）；**知识**——最新诊疗指南、药品说明、保险政策条款，写成带**适用场景、例外条件、证据来源、最近验证时间**的经验文档，按需检索；**Skill**——需要理解语境与例外的判断路径（例如"什么情况下必须建议转人工/急诊"的带作用域判断），放领域 Skill 而非全局 Prompt；**代码约束**——不可绕过的硬边界（禁止给出确诊结论、禁止越权查询病历、必须确认高风险操作）由服务端代码/Harness 门控，并配确认门禁提案（实验9-7）。协同的**发布流程**必须统一：四种载体的更新都先进**待验证区**（9.3.2 第二道边界），在**边界集与保留集**上验证（9.2.2），经过独立 reviewer 与高风险人工批准，再灰度、监控、可回滚（图9-5）；**可信根**（验证器、测试用例、发布门槛、审计日志、稳定版本备份）不由进化流程修改。另外应包含 9.3.3 的周期性整理：合并重复经验、把局部规则从全局 Prompt 挪到领域 Skill、删除被推翻的知识、**从原始基座模型重新训练 LoRA**（防灾难性遗忘）。

**7. ★★★ 历史回放中的某个探索策略在所有旧发现树上得分最高，却在下一轮在线探索中退化。哪些支持域偏差、随机性和评价过拟合可能造成这种结果？你会怎样划分回放世界并设计发布门槛？**

- *思路提示*：原文在 9.2.5 末尾已经给了机制层面的伏笔："**回放器只揭示相应节点中已经记录的结果，不必再次运行底层 Agent 和评估器**"、"**只能重组历史中实际走过的分支**"、"**不能保证在旧树上得分更高的策略能迁移到新任务**"，而 Dream-RSI 的"不更差"保证"**只是历史内的保证**"。可展开的偏差来源：① **支持域偏差**——发现树只覆盖历史走过的分支，策略可能学到"只在历史上出现过的状态分布里有效"的启发式（例如过度偏好历史上高产的某类分支）；② **随机性**——在线探索的执行含随机（采样、环境随机、评估噪声），回放返回的是**已记录**的结果，剥离了方差，因此离线得分更"干净"、更乐观；③ **评价过拟合**——候选集合保留当前策略，比较只发生在**已有历史**上，反复在同一个模拟器池上搜索会逐渐拟合这批历史的噪声；④ 还有接口层面的两个前提，如果被破坏就会直接导致离线-在线不一致：**在线与离线必须使用相同的决策接口**，且**只逐步揭示已展开的子树**（不能偷看未来）。设计建议：**划分回放世界**时按支持域切分（保留一批"从未用于策略搜索"的发现树作为回放保留集，类比 9.3 的保留集/迁移集）；**发布门槛**上除了历史内平均回放分数不更差，还要加上：在保留树上评估、在线 A/B 或灰度对照（含随机重复以估计方差）、以及 9.3 的五类长期结果（回退、泛化、Token 效率、安全性、长期工程质量），并保留快速回滚路径。

## 原文本章小结

> 本节标题即原书 9.4"本章小结"（印刷 p.270–271）。逐句精读见上文 9.4 小节，此处把原文小结的要点忠实整理如下：

- 持续进化正在成为 Agent 最重要的能力之一，但今天的模型还无法自行完成可靠的持续学习。**推理时的上下文适应不会自动持久化，未经验证的在线参数更新又会放大噪声、攻击和能力漂移。** 因此，现阶段更可行的路径，是**在模型外围建立可验证的学习系统**。
- 就全书的结构而言，**本章构建的是第一章发现循环中的实验与反馈环节**：提案已经有了，问题变成怎样通过一次以真实观测为基础的实验，判断它到底有没有让系统变好，以及怎样把结果送回下一轮。
- Agent 从与环境的交互和评价中获得学习信号，再根据**能力的表示性质**更新知识、Prompt、Skill、程序或模型参数。系统也可以进一步优化管理和生成这些产物的方法，但应优先采用**可归因、可验证、可回滚的局部修改**。遇到问题时，**先判断它更适合由外部规则、程序流程、Skill 还是模型参数处理，再用独立的边界任务和原有任务检查修改是否真正有效**。
- 历史不仅能被提炼为静态经验，还能**在支持域内组成回放环境**，低成本筛选探索策略。这使持续进化可以进一步作用于"**如何组织探索**"，而不只作用于探索产生的知识、指令和程序。
- 持续进化需要把**在线执行与离线学习分开**：在线记录证据，离线生成并验证更新提案，再逐步发布、整理或回滚。这个闭环**在结果可自动验证的任务上最可靠**；对于**目标模糊、反馈延迟的开放任务，人仍需参与问题定义和评价标准的制定**。
