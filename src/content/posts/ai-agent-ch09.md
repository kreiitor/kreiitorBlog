## 本章地图

本章依次讨论：9.1 从运行轨迹中获得学习信号；9.2 Agent 持续进化的四种方法；9.3 构建可长期运行的持续进化闭环。

模型上岗之后，能不能像新员工那样在日常工作里持续长进？本章要回答的就是这个问题。这里的判断是，今天还不能指望模型在参数层面自己可靠地持续学习（continual learning），所以要把「学习」这件事做成模型外围的一套自主系统，命名为**持续进化**。这套系统得回答四件事：一次运行到底好在哪里、错在哪里；这次改进应该落到知识、指令、程序还是参数；这些更新怎么被验证、发布、修订与淘汰；以及怎么保证它不会把一次错误变成永久风险。放到全书看，本章是收口的一章，第二章提供任务内的上下文与状态管理，第三章提供知识与记忆基础设施，第五章赋予 Agent 创造工具、修改系统的元能力，第七章建立评估与验证体系，第八章讲怎么更新模型参数，第九章把这些散件组装成一个闭环（图9-1），而它构建的正是第一章「发现循环」里的实验与反馈环节：提案已经有了，问题变成怎样用一次以真实观测为基础的实验，判断它到底有没有让系统变好，以及怎样把结果送回下一轮。

小节分工是这样的：9.1 解决信号从哪来，也就是三层轨迹验证加上可学习诊断信号的结构；9.2 解决改到哪里去，先给知识（9.2.1）、指令（9.2.2）、程序（9.2.3）、参数（9.2.4）四种载体的总览与边界，再用 9.2.5 把视角从「改产物」抬到「改产生产物的方法」；9.3 解决怎么长期跑下去，包括在线执行与离线进化的双循环、可验证闭环的失效边界（9.3.1）、三条安全边界（9.3.2）和睡眠学习式的整合与遗忘（9.3.3）；9.4 收束全章。读完这一章，你应该能为一条轨迹设计出「结果—过程—质量」三层验证，并把评价输出成能当学习信号用的结构（总判定加维度结论、证据位置、失败标签、允许拒答）；拿到一个具体缺陷时，能判断该改知识库、Prompt/Skill、程序/Harness 还是模型参数，并说出理由；能设计一条从失败轨迹到待验证版本再到灰度发布的更新流水线，包括边界集/保留集、独立验证者和回滚路径；

也能识别自我进化系统的三类安全漏洞（证据当指令、待验证能力直通生产、安全机制可自我修改）并说出对应的隔离手段。

## 章首导言（无编号）

Agent 的能力悖论摆在这儿：它可以零样本解决从未见过的复杂任务，却可能在处理了一万次相似任务之后，第二天仍然犯下第一天的错误。由此提出本章的核心问题，模型上岗之后能否像新员工一样从日常工作中不断长进，能否自主从经验中学习，也就是所谓的**持续学习（continual learning）**。这里的判断是，这正在成为 Agent 从「会完成任务」走向「能够可靠工作」的关键能力，也是下一代模型的核心研究课题。

这里要澄清一个概念。今天的「持续学习」与早年那种「学了新任务就忘掉旧任务」的持续学习研究处理的并不是同一个问题，遗忘只是其中一个子问题；更难的地方在于，没有人告诉模型，今天这一天的经历里哪些是做对的、哪些是做错的。就目前而言，模型本身的持续学习能力仍远远不够。

不够的原因有两方面。部署后的模型不会因为一次推理就自动改变参数，第二章讨论的上下文学习、状态维护和压缩能让 Agent 在当前任务内适应，但上下文结束后这种变化不会自然进入下一次任务。把对话存进记忆也不等于学会了新的行为：原始轨迹可能很长，里面既有有效策略，也有偶然成功、错误归因和不可信输入。

保存经历和从经历中学习是两件事，这个区别很容易混。把一百条轨迹放进长上下文或向量库，可以帮助模型在需要时找回某个案例，却不会自动完成跨案例比较：哪些步骤在成功轨迹中反复出现，哪些做法只在旧版接口上有效，某次成功究竟来自正确策略还是环境偶然。给的判据很硬，只有当系统主动完成「评价、对照、归纳、验证」之后，才算发生了学习，日志写入磁盘的那一刻不算。

本章与第三章的分工在这里：第三章的**用户记忆主要沉淀「用户与世界是什么样的」，本章的经验学习**要进一步沉淀「在什么条件下应该怎样行动」。前者让 Agent 记得更多，后者才让它从聪明变得熟练。

还有一个原因让模型不能每次任务后直接训练自己：生产环境很少提供干净的学习信号。用户满意并不意味着合规，局部参数更新还可能造成能力遗忘、策略漂移或安全退化。要是允许模型依据未经验证的反馈直接修改自身参数，错误经验和提示注入就可能被固化，并在后续任务中持续放大。反过来，基础模型的周期性训练可以提升通用能力，却无法及时吸收每个 Agent 每天遇到的私有规则、工具变化和局部经验。

于是就有了本章的定义：在模型自身尚不能可靠地持续学习时，必须先把「学习」构建成模型外围的一套自主系统，这里称之为持续进化，以区别于模型权重层面的持续学习。它做四件事：记录运行证据，验证结果与过程，从多条轨迹中提取共性，再决定应更新知识、指令、程序还是模型参数。另有一条硬约束：所有修改先形成待验证版本，经过回归测试和安全检查后，才能改变下一轮运行。

> ① 执行任务，旁注「用户、环境与工具交互」；
> ② 记录轨迹，旁注「动作、结果与反馈」；
> ③ 形成信号，旁注「结果·过程·质量」，对应 9.1 的三层验证；
> ④ 生成候选更新，旁注四个并列分支「知识 / 指令 / 程序 / 参数」，对应 9.2 的四种方法；
> ⑤ 验证与发布，旁注「回归、灰度与回滚」。
> 之后箭头回到起点，标注「新的 Agent 进入下一轮运行」。图下方有一句贯穿全章的原则：「只有改变后续行为且通过验证的更新，才构成持续进化。」

这一节最值得划下来的是那句判据：学习发生在「评价、对照、归纳、验证」之后。很多团队做「记忆」时其实只做了「存」，于是得到一个错觉，库里东西越来越多，Agent 却越来越像一个记性很好但不会总结的实习生。存是证据保全，学是跨案例比较加上接受检验，两者对基础设施的要求完全不同：前者要不可变、可追溯，后者要能聚类、能对照、能被验证器否决。

「上下文适应不会自动持久化」这句话可以这样理解：上下文里的学习像白板，写的时候好使，擦掉就没了；参数里的学习像纹身，改起来很贵但一直带着；本章要建的持续进化像工作手册加审批流程，手册随时可以改，改完必须走评审，改坏了还能回滚。第三条路更合适，是因为前两者在当前技术条件下各有致命伤：白板留不住，纹身改错了洗不掉。

用户满意不等于合规这件事为什么重要？因为它是单一指标的经典陷阱。客服为了让用户满意，可以口头承诺「7 天内退款」（9.1 用来举例），满意度当场可能是涨的，但承诺是否兑现、是否符合政策，是完全不同的问题。如果一个系统只拿满意度当奖励信号，它就会学会「用承诺换好评」这种策略，而参数一旦内化了这种策略，纠正成本极高。

工程上要落地的第一步，其实还轮不到让 Agent 自我修改，得先把证据链建起来：轨迹不可变、结果可核对、评价带证据位置。这一步不做，后面四种更新方法全都无从谈起，因为「该改哪一层」这个判断完全依赖「失败是什么类型、发生在哪一步」这些信息。

容易被忽略的一点是，本章强调的「待验证版本」是一个状态，不是一句口号。任何一条新知识、新规则、新代码、新权重，在被验证前都不能改变下一轮运行。这个闸门是整套体系可回滚的前提。

有四组东西容易混。持续进化指模型外围的一套自主系统，也就是知识、指令、程序、参数的更新流程；持续学习（continual learning）指模型权重层面的持续学习能力，本章主要讲前者，并明确说后者目前仍远远不够。保存经历是把轨迹存进长上下文或向量库，从经历中学习则是主动完成评价、对照、归纳、验证，前者只提升回忆能力，后者才改变行为。用户记忆回答「用户与世界是什么样的」，属于第三章；经验学习回答「在什么条件下应该怎样行动」，属于本章。上下文内适应在任务内有效、上下文结束即失效；跨任务进化必须改变下一轮运行才算数。

所以顺序是清楚的：上下文里的学习不留痕，参数里的学习不可回退，在模型可靠地自我学习之前，先把「学习」做成模型外面一套可验证、可回滚的持续进化系统。

## 9.1 从运行轨迹中获得学习信号

持续进化的起点是第七章所述的**评估（evaluation）**。这里的因果表述很直接：如果系统不知道任务是否完成，也不知道哪一步造成了成功或失败，那么语言模型生成的反思只能是一种猜测。

章首导言那段过渡概括了本章路线：持续进化必须以可追溯的运行经验为基础，能够改变后续行为，并经过验证，确保没有造成明显退化。本章依次讨论三件事，如何判断一次运行究竟好在哪里、错在哪里；比较四种更新方法及其适用边界；这些更新如何在长期运行中被验证、发布、修订与淘汰。

评价一条轨迹，实质上是依次回答三个问题：事情是否办成了；是否以允许的方式办成；是否让用户舒服。图9-2 把它们组织为三层验证结构。

> - 结果验证器（底层）：证据举例「测试、金额、订单最终状态」；
> - 过程验证器（中层）：证据举例「政策、权限、动作与承诺」；
> - LLM Rubric（顶层）：评判「自然、简洁、合规变通」。
>
> 图右侧是三层输出汇合后的产物，也就是**结构化轨迹评价**，它包含四项：任务结果（成功、部分成功或失败）、维度评价（逐项评分，不止给一个总分）、证据位置（标明对话轮次与工具状态）、失败标签（保留问题类型，支持后续诊断）。图右下方另有一条规则：「证据不足时，允许拒绝评分」。图的右下角标注这整套输出的去向：可学习的诊断信号，也就是保留成功与失败的位置、说明证据与问题类型、交给独立模块选择更新对象。

底层的结果验证器回答「事情是否真的办成」。它读取测试结果、数据库状态和工具返回。这里的例子是：Coding Agent 可以运行测试、类型检查和性能基准；替用户办理退款的 Agent 可以查询订单状态和实际退款金额。这类信号来自环境中的真实状态，通常比模型对自己行为的描述可靠，因此是三层中最应优先建立的一层。

中层的过程验证器回答「是否以允许的方式办成」。先立论：「结果正确并不代表过程正确」，并给出两个反例：删除失败的测试用例也能让测试通过；口头承诺用户「我们会在 7 天内退款，请耐心等候」也可能得到暂时的满意反馈。这一层检查业务规则、权限和动作序列，用来区分「结果已经达成」与「结果以允许的路径达成」。由于政策库、权限表与动作轨迹都可以精确表达，这一层同样可以由代码判定。

上层的质量验证器回答「是否让用户舒服」。这里列举的维度包括客服是否耐心、是否提供了合规范围内的变通方案，研究报告是否抓住了关键证据，生成文本是否自然简洁。这些维度「不影响事情办成与否，但对用户体验是有影响的」。做法是使用第七章介绍的 LLM-as-a-Judge，预先定义评价量表（Rubric），要求验证器逐项给分并引用轨迹证据。

以客服 Agent 为例，三层可以展开成七个可逐项评分的维度：任务结果属于结果层；规则遵从、隐私边界与承诺—行动一致性属于过程层；表达质量与合规变通属于质量层；事实可靠性横跨两层，能与工具返回逐一比对的部分由代码核验，其余交给 Rubric 判断。

**表9-1 客服 Agent 的轨迹评价维度**「表格按语义整理：这张表格因跨页与分栏被拆成「标题在上页、表头与表体在下页」，此处按语义还原，不是这张表格本身的问题」

| 维度 | 验证问题 | 主要证据 |
| --- | --- | --- |
| 任务结果 | 用户的核心诉求是否得到解决 | 最终环境状态、工具结果 |
| 规则遵从 | 是否违反政策、权限或必要流程 | 政策库、动作轨迹 |
| 隐私边界 | 是否泄露不应提供的信息 | 回复文本、数据访问记录 |
| 事实可靠性 | 陈述是否有知识或工具结果支持 | 引用来源、工具返回 |
| 承诺—行动一致性 | 声称完成的操作是否真实发生 | 回复与工具日志对照 |
| 表达质量 | 是否自然、简洁，避免重复与模板化 | 对话全文、语言Rubric |
| 合规变通 | 原方案不可行时，是否找到允许的替代路径 | 用户目标、政策与后续动作 |

验证器的输出形态决定了它能否成为学习信号。单一总分只能反映一次运行的优劣，无法指出应当修改之处。可供后续学习的评价至少应包含四项内容：任务是成功、部分成功还是失败；每个维度各自的结论；每条结论对应的证据位置，也就是哪一轮对话、哪一次工具调用；失败的类型标签。

此外还有一条宁缺毋滥的规则：验证器还应被允许在证据不足时拒绝评分。这里的判断是，与其把低置信度的结论当作事实固化下来，不如将该案例排除在学习集之外。具备这四项内容，下一节讨论的四种更新方法才能判断应当更新知识、提示词、程序还是模型参数。

**实验9-1 ★★：为客服Agent 构建轨迹验证器**

- 实验目的：把客服Agent 的运行轨迹转换成带证据的结构化诊断，为后续的经验提炼提供可靠学习信号。
- 实验说明：对照「只输出一个总分」和「逐维度输出结论、证据与置信度」两种验证方式，观察哪一种更容易区分任务失败、规则违规、虚假承诺和表达问题。
- 实验说明了什么：持续进化不能只依赖成功率或单一分数。只有保留「哪里错、为什么错、证据在哪里」，后续模块才知道应该更新知识、Prompt、程序还是模型参数；低置信度案例也不应自动进入学习集。

这三层的顺序对应可靠性从高到低。结果验证器看的是环境的真实状态，数据库里钱到底退没退，这是最难造假的；过程验证器看的是可枚举的规则与动作序列，也能用代码判；到了质量层，才不得不请 LLM 当裁判。那句「最应优先建立的一层」是个很有用的落地顺序建议：先把能自动核验的结果层做出来，再补过程层，Rubric 层放最后。反过来先搭 Rubric，等于把最不可靠的判据放在最前面。

「结果正确不代表过程正确」这句在这里配了一个例子，笔记把它的后果展开：一个 Agent 为了通过测试而删掉了测试用例，结果层看到的是「测试全绿」，过程层如果不存在，系统就会把「删测试」当成成功经验学下来。这正是9.2.2.1 讲的「把失败写入规范」的同一类病。

「事实可靠性横跨两层」是个很细致的设计。能被工具返回逐条比对的事实，比如订单号、金额、日期，用代码核验，属于结果层能力；无法逐条比对的一般性陈述，比如对政策的解释是否准确，交给 Rubric。这样既避免了让 LLM 去做它做不牢的核对工作，也避免让代码去判断它判不了的语义。

「允许拒绝评分」为什么关键？因为错误的学习信号比没有信号更糟。持续进化系统会把评价结果沉淀成长期能力，一条被误判为「失败」的偶然成功，可能让系统永久弃用一个正确策略；一条被误判为「成功」的违规捷径，可能被写进 Prompt 甚至参数。允许弃权，等于给学习集加了一道精度闸门。

工程落地上，「四项内容」其实定义了一个 schema：`{outcome, dimensions[], evidence_refs[], failure_tags[]}`，外加一个 `confidence` 和 `refused` 标志。这个结构同时也是 9.2 里「路由到哪一层更新」的输入，「交给独立模块选择更新对象」，那个独立模块读的就是这个结构。

还有一个常见的误解，以为「逐维度评分」就是把总分拆成加权和。这里强调的重点在证据引用，逐项给分只是形式：没有证据位置，后续模块无法做根因分析，也没法在跨轨迹比较时统计「哪种错误反复出现」。

区分结果验证器和过程验证器有个简单办法：前者问「事情成了吗」，读环境真实状态；后者问「是按规定的方式成的吗」，读政策库、权限表、动作轨迹。把这个验证器删掉，Agent 有没有可能靠违规手段拿高分？有可能，那你缺的就是过程验证器。质量层问的是「用户舒不舒服」，耐心、简洁、抓住关键证据都算；过程层问的是「允不允许」，合规、越权、虚假承诺都归它。说质量维度不影响事情办成与否。

另外两组也要分清。验证器给的置信度只是估计（见 9.3.2 这里），不能拿它当发布门槛，门槛必须是确定性的 schema、允许列表和来源检查。维度结论说的是「哪一项不合格」，失败标签说的是「这是哪一类问题」，后者是为跨轨迹统计与诊断服务的。

评价一条轨迹就按「办成了吗 / 按规矩办成的吗 / 用户舒服吗」三层来问，输出必须是「总判定 + 逐维结论 + 证据位置 + 失败标签」，证据不足时宁可拒评也不能猜。

## 9.2 Agent 持续进化的四种方法

这一节从一句引子开始：「学习信号说明 Agent 应当改变，但没有说明改变应发生在哪里。」随后给出四句对应关系：事实和经验适合写成知识文档；可以用语言清楚表达的策略适合写入提示词或 Skill；可以精确执行的流程与约束适合写成程序；感知、语言风格和隐式策略等高维能力则必须进入模型参数。

> - 知识：事实、经验与例外，载体是 Markdown / 知识库；
> - 指令：可语言化的判断原则，载体是 Prompt / Skill；
> - 程序：确定性流程与强约束，载体是工具 / 工作流 / Harness；
> - 参数：高维感知与隐式策略，载体是 SFT / 蒸馏 / RL。
>
> 图左侧标出一条渐变轴：「易更新、可追溯」对应知识/指令一端，「内化、低推理开销」对应程序/参数一端。图中有三句关键注释：①「是四种互补载体」，不是单向阶梯；②「首要判断：能力能否被事实、语言规则或程序完整表达？」；③「稳定性、成本与更新频率决定具体部署方式，而非能力能否参数化」。

表9-2 给了一个紧凑的比较，四种方式并不互斥。这里给的复合例子是：医疗影像 Agent 依靠参数识别病灶，用知识库提供最新指南，再用代码计算风险指标；客服模型的自然语气来自后训练，具体企业政策由知识和 Skill 提供，关键合规则由服务端代码兜底。

**表9-2 四种持续进化方式的适用边界**（表格按语义整理：原表逐单元格拆行，此处按语义合并回单元格）

| 更新方式 | 适合承载 | 主要优势 | 主要局限 |
| --- | --- | --- | --- |
| 经验知识库 | 事实、经验规律、例外与来源 | 更新快、可追溯、可按需检索 | 依赖检索和模型正确应用 |
| Prompt 与Skill | 需要理解语境、例外和优先级，但仍能用自然语言说明的判断原则 | 可解释、作用范围可控 | 容易膨胀、冲突或被忽略 |
| 程序与Harness | 可确定解析、可执行验证和高风险硬约束 | 可测试、执行稳定、成本低 | 开发与维护成本较高 |
| 模型参数 | 高维感知、生成风格和隐式策略 | 泛化能力强、推理开销低 | 更新与回归成本高 |

同一能力也可以拆到多个载体上，这里的拆法是：事实进入知识库，解释例外的原则进入 Skill，不可绕过的权限仍由程序门控，高维识别能力再进入参数。这一节收尾那句是个闸门：「路由结果只是更新提案，尚未获得发布资格。」

这一节可以当成一张分诊表来用。拿到「某类任务老出错」这个现象，先别急着改 Prompt，而是问两个问题：这个能力能不能被事实、语言规则或程序完整表达？能，就走知识、指令或程序；不能，比如「写出不像 AI 的文字」「看懂 CT 片」，才考虑参数。这就是图9-3 说的首要判断。

图9-3 里那句注解有点反直觉：「稳定性、成本与更新频率决定具体部署方式，而非能力能否参数化。」一个能力能不能写进参数，和它该不该写进参数，是两个问题。稳定性差的能力（语言风格变得快）也完全可以参数化，比如周期性偏好训练，只是你不会把它当成一次性永久投资。9.2.4 会把这句话展开。

表9-2 的「主要局限」一列值得逐个记。知识库的坑是依赖检索和模型正确应用，知识写对了，检索没召回，或者召回了模型没照做，等于没写。Prompt 和 Skill 的坑是容易膨胀、冲突或被忽略，这三件事在 9.3.3 的「上下文腐化」里会再出现一次。程序的坑是开发与维护成本较高，所以别拿程序去装那些天天变的策略。参数的坑是更新与回归成本高，也正是 9.2.4 说「是否参数化不由任务是否长期稳定单独决定」的原因。

四种方式并不互斥，这一点在工程上极其重要。这里的医疗影像与客服两个例子都在说明，一个能力往往需要在多个载体之间分工，很少是挑一个就完事。判断「关键合规用服务端代码兜底」就是典型，因为它是不可绕过的硬约束，放在 Prompt 里只是请求模型遵守，放在代码里才是做不到就是做不到。

笔记在这里补一条实用启发：可以按「错了会怎样」来选载体。错了只是体验差，就放知识或指令；错了会造成越权或资金损失，就放程序；错了难以枚举、只能靠统计意义上的判断，就归参数。这条经验与表9-2 的「局限」列是自洽的。

容易混的地方有三组。知识、Prompt、程序、参数是四种载体，谈不上四个能力层级，同一个能力可以拆到多个载体（医疗影像那个例子），也可以整体迁移到另一个载体，比如一条稳定下来的 Skill 规则被「编译」成程序（见 9.2.3）。参数化能力与高频更新也不是一回事，容易混成「稳定才参数化」，否定：稳定性影响的是更新频率和成本，真正决定主要载体的是能力的表示性质。路由结果与已发布更新的区别同样要守住，路由只是提案，没有发布资格，这个区别是整章反复强调的「待验证版本」概念的起点。

更新该落到哪一层，取决于这个能力能不能被事实、语言或程序完整表达；四种载体是互补分工，而任何「该改哪一层」的结论都还只是提案，离发布许可还有距离。

### 9.2.1 将经验沉淀为知识

这是最轻量的进化方式，把多次运行中反复出现的经验整理成可检索的知识文档。这里的经验知识库与第三章共享存储、索引和检索技术，知识来源和验证目标却不同：第三章主要从用户对话、文档和数据集中提取「用户与世界是什么样的」，本章从 Agent 的行动轨迹和结果中提取「在什么条件下应该怎样做」。

用一对例子把领域知识和行动经验区分开。领域知识是「该航空公司要求特殊餐食提前二十四小时预订」；行动经验是「订票前先检查特殊餐食截止时间，避免付款后才发现无法满足需求」。

原始轨迹不能直接当知识单元，因为它既长又嘈杂，里面混着工具原始输出、偶然的绕路和环境细节。更稳妥的系统会保留三层数据：不可变的原始轨迹，用于审计；单次运行分析，记录本次成败与经验草案；再对多条同类轨迹进行比较、聚类和归纳，形成面向未来的 Markdown 知识文档。正式文档通常写清适用场景、推荐策略、禁止做法、例外条件、证据来源和最近验证时间，而不去复述某一次任务的完整过程。

这种设计与第三章的 User as Code 采用了相同的两阶段思路：User as Code 先把对话事实追加到不可变日志，再周期性重建结构化用户模型；经验学习同样先保存证据，再离线生成可变知识。图9-4 展示了这一过程。把记录与整理分开的好处很实际，可以避免一次偶发成功或网络故障立即改变 Agent，也使系统能在看到多条成功和失败之后再判断共性。

> ① 原始轨迹：动作、结果、环境，标注「不可变证据」；
> ② 单次评价：成功、失败、标签，标注「保留证据位置」；
> ③ 跨轨迹比较，做三件事：聚合同类任务、对照成功与失败、提取共性与边界；
> ④ Markdown 文档：写清适用场景与策略、例外与禁区、来源、版本与验证时间；
> ⑤ 检索应用：「新任务按需加载」，并「继续产生反馈」。
>
> 图中有一条从第⑤段回到第④段的回边，标注「新证据用于修订、限定或淘汰旧知识」，说明知识文档是活文档，会被后续证据修正。图下方的注释界定了它与第三章的关系：「与第三章共用抽取和检索基础设施；本章新增轨迹评价与行为改进闭环」。

经验文档不是简单的轨迹摘要。真正有迁移价值的内容来自对照：同类成功轨迹做了什么，失败轨迹缺少什么；某种策略在哪些环境版本中有效，在哪些前置条件下失效。明了分工，第三章已经介绍过知识抽取、聚类与检索，本章不再重复这些算法，重点放在两点上：轨迹评价如何成为抽取条件，以及抽取出的知识是否能提高后续任务表现。

完整的知识提炼管道有五步。保存不可变轨迹和环境结果；为单次运行生成结构化分析，列出任务类型、所需能力、观察到的策略、错误与例外；按任务族聚合同类运行，为每条经验草案建立「哪些轨迹支持、哪些轨迹反驳」的证据表；只有达到支持门槛的草案才写入正式文档；第 5 步是在未参与提炼的新任务上测试迁移效果。

GAIA 经验学习实例把这些步骤落到了具体环境上。GAIA 包含需要综合搜索、网页阅读、文件处理和计算的多步骤问题，AWorld 则提供运行 Agent、调用这些工具和保存轨迹的执行环境。这里的比喻很直白：前者像试卷，后者像考场与实验记录系统。旧式做法是在一次任务成功后立刻生成策略摘要并向量化入库。更严格的实现先用 GAIA 答案验证或其他环境验证器标记成功、部分成功和失败，再比较同一任务族的多条路径。三种轨迹各有用处：成功轨迹贡献策略草案，失败轨迹贡献排除性知识，部分成功轨迹帮助识别「哪一段有效、哪一段仍有问题」。

Reflexion 的位置也要摆正。它提出的自然语言反思可以参与生成经验草案，但反思本身不是证据；只有与环境结果相符、得到跨轨迹支持并在新任务上显示正向迁移的内容，才应进入正式经验文档。

此处引用的文献：GAIA，Mialon, G., et al. *GAIA: a benchmark for General AI Assistants*. arXiv:2311.12983, 2023；AWorld，Yu, C., et al. *AWorld: Orchestrating the Training Recipe for Agentic AI*. arXiv:2508.20404, 2025；Reflexion，Shinn, N., et al. *Reflexion: Language Agents with Verbal Reinforcement Learning*. arXiv:2303.11366, 2023。

> 检索确认：脚注所记 **GAIA 的 arXiv 编号 2311.12983、第一作者 Mialon**（Grégoire Mialon 等，Meta FAIR）与外部资料一致，论文标题为 *GAIA: A Benchmark for General AI Assistants*，与「需要综合搜索、网页阅读、文件处理和计算的多步骤问题」这一描述相符。（来源：[GAIA: A Benchmark for General AI Assistants](https://ar5iv.labs.arxiv.org/html/2311.12983#1)）

这一节的核心是一句话：原始轨迹是证据，知识文档才是复用单元。可以把原始轨迹想成监控录像，它忠实、完整、不可改，但你不会拿监控录像当操作手册；操作手册是从大量录像里总结出来的、写清了条件和例外的薄薄几页。

三层数据的设计很像数据库里的 ODS → DWD → 指标层：最底层是不可变原始事实，中间层是单条的加工结果（单次评价加草案），上层是跨条汇总、面向未来使用的结论。分开的收益是幂等与可重算，任何一条知识都可以追到它是由哪几条轨迹支持的，新的反例出现时也能精准地找出该修订哪一条知识。

正式文档要写清的那六项可以直接当模板用：适用场景、推荐策略、禁止做法、例外条件、证据来源、最近验证时间。其中有两项是很多团队会漏的，例外条件（没有它，规则会在不该用的地方被套用）和最近验证时间（没有它，无法做 9.3.3 说的时效性淘汰）。

失败轨迹贡献排除性知识这一点特别值得强调，因为它是很多人做经验库时的盲区。只学成功经验，你得到的是「这样做行得通」；补上失败经验，你才得到「这样做不行、以及为什么不行」。后者往往更省事，因为它把搜索空间直接剪掉了一块。9.3.1 里「保留负面结果」是同一条道理在科研场景的延伸。

「反思不是证据」是这一节最需要划线的一句。Reflexion 式的自我反思很自然会生成一段听起来很有道理的经验，它的来源却只是模型自己的叙述。判定标准可以固定为三关：与环境结果相符、得到跨轨迹支持、在新任务上显示正向迁移。三关都过，才写进文档。你可以把这理解成经验的三重验证，与 9.1 的轨迹三层验证是配套的两层把关。

迁移测试放在管道第 5 步，这个位置不是凑数：如果知识只在产出它的那些任务上有效，那它可能只是对那批轨迹的过拟合。这和 9.3 的「保留任务集增益」、9.2.2 的「边界集/保留集」是同一个方法论，永远留一批没参与提炼的任务做验收。

工程上的常见坑是把经验文档写成某次任务的复盘流水账。判断标准很简单：换一个不同但同族的任务，这段话还有指导力吗？答案是否定的，那它还是轨迹摘要。

几组区分值得过一遍。领域知识说的是世界是什么样的（特殊餐食需提前 24 小时预订），行动经验说的是什么条件下该怎么做（订票前先查截止时间）；本章的经验库偏后者，第三章的用户记忆偏前者。经验知识库与第三章的知识库共享存储、索引、检索技术，来源不同，本章来自行动轨迹与结果；验证目标也不同，本章要以能否提高后续任务表现为准。经验文档与轨迹摘要的分界在于有没有跨轨迹对照，成功做了什么、失败缺什么、哪种策略在哪个环境版本有效，这才是经验文档的内容。反思是 LLM 生成的叙述，属于候选草案；证据是与环境结果相符、被多条轨迹支持、并能迁移到新任务的结论。单次评价产出「这一次为什么成或败」，跨轨迹比较才产出共性、边界与例外。

所以顺序是：先把不可变轨迹和结构化评价存下来（证据层），再离线对多条同类轨迹做对照与归纳，只有过了环境相符、跨轨迹支持、新任务正迁移这三关的结论，才写成带适用场景、例外和验证时间的知识文档。

### 9.2.2 将经验写成指令

分工对照很清楚：经验知识库给 Agent 提供「可以参考的资料」，Prompt 和 Skill 则规定「应该怎样行动」。

升级为指令有门槛：当多条相似轨迹反复暴露同一种策略错误，而且错误能够用语言清楚描述时，才值得把经验提升为指令。在此之前，三个概念要先分开。系统 Prompt 对所有任务生效；Skill 只在匹配到某个领域或工具时按需加载；程序与 Harness 负责权限和其他硬约束。

研究脉络上，Andrej Karpathy 把这种做法称为系统提示学习（System Prompt Learning），模型遇到问题后用一句清楚的话提醒未来的自己。DSPy 在开发集上搜索指令和示例；OPRO 根据历史提示词及其得分提出提示提案；GEPA 从失败轨迹的自然语言反思中生成并筛选提示提案。对这些方法的适用性判断是：它们适合离线批量优化，生产环境更适合使用可审计的最小更新提案，并保留快速回滚路径。

这一节与第二章的提示工程不是一回事。第二章讨论怎样组织一份好 Prompt；本节讨论什么反馈足以触发修改，以及更新提案怎样安全发布。

有两条硬性做法。修改应该落成带来源的最小 diff，让模型每次都重写整份 Prompt 是反例，这正是第一章命名的「最小 diff + 可回滚」模式。待验证版本必须同时在触发失败的边界集和正常工作的保留集上测试，前者要改善，后者不能退化。

#### 9.2.2.1 例子一：转接边界的规则化

场景来自 τ²-bench 的 telecom 政策。关于转接人工，政策里只有两条原则性规定：请求超出 Agent 的动作范围时才转接；转接前应先尽力解决。

缺陷怎么暴露出来的？第七章解剖该环境时，这两条并未显出问题；换用能力较弱的模型运行，缺陷随即暴露：工具返回错误后 Agent 反复重试，最终以转接人工收场，提炼集的 20 条任务中有 19 条如此结束。

提升结果是这样拿到的：把这 19 条失败轨迹交给模型自行归纳，产出若干条可执行的规则追加到政策末尾，再在一批未参与提炼的任务上重新运行，通过率由 12.3% 升至 19.3%，且原本通过的任务无一被改坏。

这里的关键变量是提炼所依据的材料决定了能够归纳出什么。同样是这 19 条轨迹，仅提供失败摘要与错误文本时，模型归纳出的是「同一工具反复报错即不应继续调用」；补充 Agent 与用户各自可调用的工具清单之后，归纳结果变为「网络状态、SIM 卡、APN 等项属于用户设备侧，应引导用户自行操作而非直接调用」。这里的评断是：「前者记录的是教训，后者理解的是职责归属。」

第二个坑更隐蔽，模型会把观察到的行为当作应然的行为。第一版规则里有两条是「连续三次调用失败即转接人工」「用户两次未提供号码即转接人工」，因为轨迹中出现最频繁的正是转接人工，模型据此把它视为合理的兜底手段。但在这套评估中转接人工必然判定失败，所以这两条规则等于把失败写入了规范。结论是提炼产物不能直接发布，须经与提炼者相互独立的验证。

典型失败轨迹有一个很朴素的样子。基线中一条轨迹里，Agent 需要用户的电话号码，于是调用查询工具，并把「请您提供您的电话号码」填入参数，连续五次，五次报错，随后转接人工。这里的诊断是：它已经判断出应当询问用户，却把这句话说给了工具。规则生效后的行为变成：先在对话中提出请求，取得号码再行查询；此后欲检查 SIM 卡状态遭工具拒绝，转而引导用户自行重新插拔 SIM 卡，任务通过。

**实验9-2 ★★：从τ²-bench 失败轨迹提炼转接与工具使用规则**

- 实验设计：沿用第七章的 τ²-bench telecom 环境。提炼集与迁移集在上游仓库中本就是两套互不相交的任务，提炼过程接触不到迁移集。
- 步骤：先以弱模型运行提炼集并保存失败轨迹；规则由模型归纳而非人工撰写，生成后追加至原始政策末尾；再在迁移集上对照原始策略与两个进化版本。三臂之间只替换策略文件，用户模拟器保持不变。
- 记录指标：除通过率外，还需记录三项与规则直接对应的行为指标，转接人工的比例、Agent 越界调用用户侧工具的次数、参数缺失即发出的调用次数。
- 结果：后两项在进化版本中均下降约八成，说明通过率的提升来自规则修复了具体动作。

可移植性方面，同样的做法可以搬到其他领域。航空客服 Agent 的典型问题案例是：用户对退票费、改签费或行李政策提出异议，Agent 未查询政策、未解释规则、未寻找合规的替代方案，即调用 transfer_to_human。给出的正确边界是：一般的政策争议无须转接，只有用户明确要求人工介入，或出现安全相关情形时才必须转接。诊断同样指向转接边界未予明确，修法同样是把边界落成一条带出处的最小规则。

**实验9-3 ★★：基于失败轨迹优化航空客服的系统Prompt**

- 实验目的：让航空客服 Agent 修复「遇到普通政策争议就过早转人工」的行为，同时保留明确要求人工和安全事件的转接能力。
- 实验说明：从失败轨迹中提取规则遵从、任务解决和合规变通三个维度，生成一条带来源的最小 Prompt 补丁，再与初始版本、人工调优版本在相同条件下对照。更新提案只有在边界案例改善、旧任务不退化并通过发布门槛后，才进入灰度阶段。
- 实验说明了什么：「Prompt 自动优化的重点是把可归因的失败转成作用域明确、可回滚、可验证的局部规则，不是让模型自由改写一大段文字。」

这个例子里最有价值的是两个反面发现，都可以直接当检查清单用。

材料的完整性决定归纳的质量。只给「失败摘要 + 错误文本」，模型学到的是「别老调同一个工具」这种表层教训；补上「谁能调哪些工具」的职责边界，模型才能学到「这类问题属于用户设备侧」。也就是说，问题不出在模型的归纳能力上，而出在你给它的信息里根本没有「职责归属」这一维。

频率会被误当成正确性。轨迹里「转接人工」出现最多，模型就把它当成合理兜底，这在统计上是最常见的动作，在评估里却是必然失败的动作。提炼器如果只看什么经常发生，就会把系统的坏习惯固化下来，所以这里强调必须有与提炼者相互独立的验证。

12.3% 到 19.3% 这个数字值得算一下（补充计算）：绝对提升 19.3% − 12.3% = 7 个百分点，相对提升 7 ÷ 12.3 ≈ 56.9%，也就是 19.3 ÷ 12.3 ≈ 1.57 倍（两个说法同源，涨到 1.57 倍等于多出约 57%）。这里必须交代口径，否则很容易算错：12.3% 与 19.3% 是同一批任务、同一口径的两个通过率，都是在未参与提炼的迁移集上测的，所以 56.9% 与 1.57 倍可以直接由这两个数相除得到（笔记另按两路独立复算核对过：$7/12.3=0.5691$、$19.3/12.3=1.5691$）。前文说的 20 条是提炼集的规模（20 条中 19 条以转人工收场），两者不是同一批任务，不能把通过率乘到 20 条上换算条数；若迁移集规模为 $n$，两种通过率对应的通过条数约为 $0.123n$ 与 $0.193n$（由这两个百分数还可知：既然 $0.123n$ 与 $0.193n$ 都是整数、而 $123/1000$ 与 $193/1000$ 都已是最简分数，那么 $n$ 应为 1000 的倍数）。绝对量不大，方法学意义大：这是零训练、只用推理侧规则拿到的提升，而且原本通过的任务无一被改坏，也就是说没有出现回退。7 个百分点、56.9% 与 1.57 倍都是笔记据这里数字推算的，本节只给了 12.3% 和 19.3% 两个数，两数本身没有口径冲突。

「后两项下降约八成」是个很聪明的指标设计，它回答了通过率为什么涨。如果只是通过率涨了而行为指标没动，那就可能是评估波动或侥幸；现在越界调用用户侧工具和参数缺失即发出调用这两个与规则一一对应的行为都降了约 80%，说明规则确实改掉了具体动作。这就是可归因：成绩变化要能挂到一个具体机制上，9.2.3 会再次强调这个原则。

「把话说给工具」那条轨迹特别经典，值得单独记住：Agent 在语义层面判断对了（应该向用户要号码），在接口层面用错了通道（把请求用户的话塞进了工具参数）。这说明有一类失败的根源落在动作与接口的映射上，跟认知判断无关，而这类问题恰恰最适合用一条最小规则修掉，也恰恰是知识库解决不了、只有指令和程序能解决的。

与第二章提示工程的区别要记牢：提示工程问怎么写好，本节问什么时候该改、改完怎么发布。一个很实际的推论是，自动 Prompt 优化不该产出一整份新 Prompt，那既不可归因也不可回滚；它应该产出一条带来源的补丁，这里反复用「最小 diff」「带出处的最小规则」这类说法。

关于实验设计再补一点：实验9-2 的「三臂只替换策略文件，用户模拟器保持不变」是很标准的控制变量做法，因为用户模拟器的随机性会污染结果，必须固定住。而「提炼集/迁移集互不相交、提炼过程接触不到迁移集」则是对数据泄露的防范：如果提炼时见过迁移集的任务，那 19.3% 反映的就是记忆成绩，泛化的成分很少。

几个区分值得单独列一下。系统提示学习关心什么反馈触发修改、怎样安全发布，提示工程关心怎样组织一份好 Prompt。教训是「别重复调同一个工具」这种表层结论，职责归属是「这类问题属于用户侧，应引导用户自己操作」这种结构性理解，差别来自有没有给职责边界信息。最常见的动作与正确的动作也不是一回事，轨迹频率高的行为不一定对，本案例里转接人工出现最多却必然判失败。通过率提升与行为改善要分开看，通过率可能因波动而变，行为指标（越界调用次数、参数缺失调用次数）才是因果证据。最小 diff 与重写整份 Prompt 的区别在于能否归因、能否回滚、有没有来源。

把经验升级为指令的前提是同类错误反复出现且能用语言说清；提炼出来的必须是带来源的最小规则补丁，而且只能当提案，因为模型会把最常见的做法当成正确的做法，这中间必须由独立的验证者把关。

#### 9.2.2.2 例子二：需求澄清Skill——从「直接开工」到「先确认再执行」

第二章已经介绍过如何编写一份 Skill。这里假设系统已经有一份初版的需求澄清 Skill，本节关注的是另一件事：当 Agent 在生产环境中不断收到用户反馈时，如何自动判断「什么时候应该先问，问什么，什么时候可以直接开始」是否需要更新。

为什么这是典型的流程性问题？用户说「把登录页改成支持企业登录」，Agent 如果立刻开工，可能在身份提供商、回退方式、兼容旧用户和上线范围上替用户作出其尚未考虑过的选择；如果无论任务大小都先列十几个问题，又会把简单修改变成一次访谈。这条权衡可以概括为：问得太少会导致返工，问得太多会增加打扰。

Skill 该表达的是带作用域的判断路径，一刀切的「所有任务都必须确认」并不在其中。一个初版流程可以这样写：

1. 先判断任务的歧义程度、风险和返工成本；

澄清策略往下还有几档，越往后越重。低风险、容易撤销的小改动，说明自己的假设之后直接执行；一旦碰到架构、数据、权限、公开接口或者大范围改动，就只把少量真正会改变方案的问题集中提出来，别拿边角问题凑数。拿到答案以后生成一份短 Spec 或 Plan，把目标、非目标、关键取舍、假设和验收标准列清楚，交给用户确认；确认了再动手，执行过程中发现原来的 Spec 站不住，就停下来重新确认。

证据要一起留。系统得同时记录任务、澄清问题、Spec 版本、用户修改、执行结果和交付后的返工，少哪一项，后面的归因都会缺角。

反馈分正负两侧看。负反馈一种长成「做出来的和我想象的不一样」，另一种长成「你问得太多了」，这两句话背后的问题正好相反。正反馈包括用户一次确认后就顺利交付、用户主动改 Spec 之后返工减少，以及在低风险任务里没有被多余的问题打断。在这里下了一条硬要求：**单独保存一句抱怨不足以触发更新**，反馈必须和具体轨迹、任务类型以及结果关联起来。

提提案也有门槛。当多条轨迹反复指向同一个缺口时，Agent 才可以拿出一个最小的 Skill 更新提案。这里给了两个方向相反的例子：多个涉及认证架构的任务都在交付后才发现需要兼容旧登录方式，规则草案就该要求在执行前确认「身份提供商、回退路径和兼容范围」；反过来的情形是大量拼写修复都被 Agent 先问一轮，那规则草案要做的是收窄高风险与高歧义的触发范围。

怎么验证这件事，这里给的是把「直接执行」「先提问再执行」「提问后生成 Spec、确认后执行」三条策略放在一起比，并且按任务复杂度分层看结果。指标至少要覆盖需求偏差率、交付后的返工次数、澄清轮数、**首次有效产出时间**、用户放弃率、Spec 被修改的比例和高风险操作错误率。发布条件是两条一起满足：减少需求偏差的同时没有显著增加打扰，并且在没参与提炼的任务上通过回归，之后才进灰度。

Skill 与 Harness 的分工在这一节划得很清楚。Skill 管理解语境，负责主动提问、整理 Spec、说明取舍；Harness 管边界，在缺少确认时否决高风险写入，也否决直接在 main 上操作或绕过发布流程。还补了一条反向边界：Harness 里的否决器不能替模型决定 PR 应该怎样描述，也不能替模型选需求方案。

经验攒到一定程度，稳定的对话轨迹还能继续长成第八章需要的 SFT 或 RL 训练数据，这条线把两种载体接上了。

**实验9-4 ★★：从用户反馈中进化需求澄清与Spec 确认Skill**

这条实验要看的是 Agent 能不能在「需求偏差」和「交互打扰」之间找到更好的澄清策略，并把验证过的改进写回 Skill。做法是准备一组低风险、低歧义任务和一组涉及架构、权限、数据或公开接口的高风险任务，比较直接执行、提问后执行、提问后 Spec 确认三种流程；记录用户回答、Spec 修改、交付结果和返工反馈，让 Agent 生成 Skill 更新提案，提案要过留出任务回归、打扰成本检查和高风险否决器验证三关。这里的总结是：持续进化的做法是从结果和反馈里识别作用域，提出最小指令更新，再由独立评价器决定是否发布，把每次抱怨直接追加进 Prompt 算不上进化。

这个例子的价值在于它把「该不该问」从一个风格问题变成了一个可优化的问题。很多人聊「Agent 要不要先澄清」的时候容易站队，一边说必须问清楚，一边说别啰嗦直接干；这里的做法是把它参数化成一条带作用域的判断路径：先看歧义程度、风险和返工成本，再决定走哪条分支。这么一转，「问多少」就变成能用指标衡量、能用实验优化的对象。

两个负反馈的性质也得分开看。「做出来的和我想象的不一样」是问得不够，属于需求偏差；「你问得太多了」是问得过量，属于打扰成本。把两类都摆出来，是因为优化目标天然带双边约束：只盯减少返工，Agent 会退化成什么都先问一遍；只盯减少打扰，又会退回直接开工。所以指标里既要放需求偏差率和返工次数这类偏少问的代价，也要放澄清轮数、用户放弃率和首次有效产出时间这类偏多问的代价。首次有效产出时间这条值得单独留意，它量的是从任务开始到第一次产出真正有用的东西，跟总耗时是两回事。一个先问十二个问题的流程，总耗时可能没多多少，首次有效产出时间却会明显拉长，用户体感里的「被打扰」往往就出在这里。

反馈需要上下文才能变成信号，这是本节的关键工程判断，也是「单独保存一句抱怨不足以触发更新」的落点。一句「你问得太多了」，如果不知道是哪个任务、什么复杂度、问了几轮、之后有没有返工，就没法区分这是低风险任务上的过度澄清（该收窄），还是高风险任务里用户不耐烦但结果其实没错（不该动）。这跟 9.1 讲的证据位置是同一套逻辑。

Skill 与 Harness 的那条边界最容易搞混，这里两句话可以直接当口诀用：Harness 管「不许做什么」，缺确认时否决高风险写入，否决直接在 main 上提交，否决绕过发布流程；Skill 管「应该怎么做」，理解语境、提问、整理 Spec、说明取舍。另一句反向约束同样重要，否决器可以拦下未经确认的高风险写入，但不能规定 PR 该怎么写，因为那是需要理解语境的创作性任务。

稳定的对话轨迹进一步生成 SFT 或 RL 数据这件事，串起了四种载体之间的升级路径：先用 Prompt 和 Skill 快速试错，改得快也能回滚；等某种行为在多条轨迹上稳定下来，又需要低推理开销和更好的泛化时，再考虑把它内化进参数。这跟 9.2.4 讲的「是否参数化」是连着的，Skill 相当于参数的试验田。

实验9-4 里「高风险否决器验证」是个很容易被忽略的验收项。一个只优化减少打扰的提案，很可能顺手把「高风险操作前必须确认」这条规则也一起收窄掉，所以发布门槛里必须有一条独立于提案的安全检查。这正是 9.3.2 第三道边界在这个具体案例上的样子。

还有几组概念别搞混。需求偏差和交互打扰，一个来自问得太少，一个来自问得太多，两者互相拉扯，不能用单一指标优化。Skill 的作用域和全局 Prompt 要分开看：Skill 只在匹配到某个领域或工具时按需加载，天然适合装分场景的澄清策略；把这类规则塞进全局 Prompt，会让它膨胀并干扰所有任务。Harness 手里是否决权，模型手里是判断权，前者管边界，不管方案选择，也不管 PR 怎么写。单条抱怨缺上下文，能触发更新的信号必须绑定轨迹、任务类型与结果，而且要多条轨迹反复指向同一个缺口。至于本节讨论的范围，是「什么时候、依据什么反馈、怎样安全地改」，初版 Skill 怎么写属于第二章的内容。

把「该不该先问」写成带作用域的判断路径，再用成对指标来优化，需求偏差对着打扰成本，一头松另一头就紧。更新本身要是多条轨迹指向同一缺口之后才提的最小补丁，而且得过了留出任务回归和高风险否决器这两道关。

## 9.2.3 将经验写成程序

这里处理的是一类特定的经验：它描述的是稳定、重复且可验证的操作。这样的操作每次都让模型重新阅读文档、重新推理，并不经济，更合适的做法是把经验编译成工作流、工具或者 Harness 代码，让一次探索变成可以重复执行的程序。这三个条件得同时成立才值得动手。不稳定，编译出来很快过时；不重复，编译成本收不回；不可验证，就没法防住 PreAct 后来警告的那种假成功。

跟第五章的边界要划清。第五章讲的是 Coding Agent 怎么读写文件、跑测试、生成系统；这里关心的是 Agent 怎么根据自己的轨迹修改未来版本的自己，一般意义上的代码生成不在讨论范围内。

可以修改的对象远不止一个新工具，下面按层列了四类。操作层可以把浏览器轨迹编译成参数化工作流，或者为变化的 API 生成适配器；控制层可以改工具路由、重试、熔断和上下文压缩策略；验证层可以根据生产失败新增参数检查、状态验证器和回归测试；架构层可以增加 Reviewer Agent，改变规划与执行之间的信息流。

浏览器工作流这件事，这里拿电子表格的宏录制来类比。第一次发邮件时，多模态 Agent 通过观察—思考—行动去找撰写、收件人、主题、这里、发送这些控件；下次再发一封邮件，流程没变，变的只有收件人和内容，没必要再让模型从像素和 DOM 里重新发现整条路径。系统该做的是把第一次探索留下的轨迹编译成一个带参数、带状态检查和版本信息的小程序。

图9-4 那张知识提炼的图，落到浏览器场景里就是一个六步的生命周期。第一步捕获轨迹，记下导航、点击、输入、下拉选择这些动作，保存动作参数、当时的 URL，以及 XPath、CSS 这类元素定位证据；定位信息只用来重新寻找元素，它不能证明任务已经完成。第二步参数化，把首次运行里的字面量识别成模板变量，`test@example.com`、邮件主题和这里就变成 `{recipient}`、`{subject}`、`{content}`，其余稳定动作保持不动。第三步定义状态检查，给每个动作加执行前检查和执行后检查，比如「发送按钮当前可见」，再给整个工作流加一个最终状态检查。这里的判据是：动作执行成功与任务成功是两件事，最终状态检查必须读取真实页面或后端状态。第四步独立回放验证，把沙盒账号或测试站点重置到独立的初始状态，完整回放录制下来的程序，每一步的前置检查、后置检查和最终状态检查全部通过才能发布。第五步匹配与回放，新任务进来先按意图和关键词在正式能力库里找工作流，提取本次参数，交给 Playwright 直接执行；这条回放路径不需要逐步调用 LLM，但仍然要等元素可用，要跑完所有状态检查。第六步失效与重学，找不到目标元素、状态检查不通过、API Schema 变了或者最终状态错误，都回退到完整的 Agent 模式重新探索。

六步里第 4 步和第 6 步最容易被省掉，也最不能省。省掉独立回放，你会把一次带残留状态的偶然成功当成可复用流程，比如账号本来就是登录态，于是流程里「没登录」这件事被掩盖了；省掉失效机制，页面一变，工作流会继续点按钮，但点到错的地方去。

PreAct 的实验结论很硬：这类程序在重复任务上拿到 8.5–13 倍的端到端加速，回放阶段不需要逐步调用语言模型。更重要的结论是流程记忆必须同时具备动作前验证、动作后验证和独立回放验证，否则很容易得到一种危险的假象：每个按钮都点过了，但某个字段其实是空的，任务从未真正完成。提速的来源也得理解对，它快是因为回放阶段把逐步的 LLM 调用整个去掉了，跟程序比模型聪明没关系。所以加速的前提是这条路径已经被证明稳定，一旦页面变化，收益归零，只能退回完整 Agent 重新探索。这是典型的用缓存换速度、用失效检测保正确。

**实验9-5 ★★★：从浏览器轨迹生成可验证工作流**

目的在检验网页 Agent 能不能把一次探索变成可复用工作流，并且在页面变化或状态异常时拒绝错误回放。做法是把一次成功轨迹编译成带参数和状态检查的待验证工作流，跟「每次都重新探索」的基线比；再改页面或者制造假成功，看这个工作流会不会失效并退回完整 Agent。这里的结论是，流程记忆的价值在于确保任务的最终状态仍然正确，可复用工作流必须有独立验证和失效机制，否则加速只是把错误更快地重复一遍。

自我修改不等于进程直接覆盖自身。Agent 改自己的代码，并不意味着运行中的进程要把自己覆盖掉，生产系统该走的是四步：从当前稳定版本拉一个隔离的更新分支；由 Coding Agent 生成最小补丁；依次通过静态检查、单元测试、安全扫描、失败轨迹重放和旧任务回归；再生成一个可以灰度部署的新版本。这么做的意义是把自我修改变成可审计的软件发布流程，这也是第九章和第五章的分界：第五章提供修改系统的能力，本章提供由经验触发、被验证闭环约束的自我修改方法。四步里没有一步是新发明，全是成熟的 CI/CD 实践，这里的意思是不必为 Agent 另造一套发布机制，塞进已有的那套就行。

Git worktree 和 Pull Request 在这里是示范。Skill 应主动指导 Agent 先为任务创建独立 worktree，确认需求和 Spec，完成实现与测试，提交有意义的 commit，并在 Pull Request 里写清背景、方案、测试结果和剩余风险。Harness 的职责不在这里替模型做判断，但可以在它准备收工时检查是否仍在 main 上直接提交、是否漏了 worktree 或 Pull Request，一旦违反边界就否决这次操作，要求 Agent 回去修。

变更契约这块值得展开。这里的起点是一句很务实的话：仅有「补丁尽量小」还不足以支持可靠归因。每个修改请求还得附带一份可证伪的**变更契约**，列出失败证据、推断根因、归属的 Harness 组件、修改提案、预期修复的行为、可能受损的既有行为，以及分别验证这两者的用例。它要提出的其实是一个可以被证伪的因果主张：我认为失败是因为 X，要改 Y，改完之后 Z 行为会变好，同时 W 行为可能受损，我用两个用例分别验证。有了这份契约，「分数涨了」才能解释成某个机制被修好了；没有它，涨分只能算试对了。

Agentic Harness Engineering 讲了三层可观测性：组件、经验和决策。可编辑组件都有文件级表示；海量轨迹先整理成可以逐层下钻的证据；每次编辑在执行前声明影响预测，由下一轮结果来验证。这里的评价是，这样「分数上涨才能与某个具体机制建立联系，而不只是一次不可解释的试错」。

提案生成器的输入也不该只有失败案例。Self-Harness 的做法会额外提供必须保留的成功行为，以及此前被拒绝的修改记录。前者告诉 Agent 哪些性质不能在修复时被破坏，后者避免它换个说法把已经失败的方案再提一遍。这里的结论是，失败证据、成功约束与历史尝试共同构成一个有边界的方案空间，比把全部源码和原始日志无差别塞给修改 Agent 更容易产生局部、可验证的改动。这两个额外输入解决的是很实际的失败：修改 Agent 为了修 A 把 B 弄坏了，因为它不知道 B 需要保护；同一个行不通的方案被换个说法又提一遍。信息量不等于有效信息量，无差别喂料会让它抓不住重点。

工具创造走的是同一套协议。Alita 的案例是这样的：Agent 要从一段由《指环王》里咕噜配音演员解说的 YouTube 360 VR 视频里，找出恐龙首次出现后紧接着提到的数字。它发现自己缺少字幕读取能力，于是搜索并测试 youtube-transcript-api，把它封装成新的字幕工具，最终从字幕里得到答案 100000000。准入条件是：安全扫描、功能测试和后续任务复用都通过，新工具才进入能力库。复用这一条常被忽略，一个工具只在一个任务上用过一次，还不知道有没有复用价值就收进能力库，只会增加维护面和检索噪声。这也说明工具创造是程序化经验的另一种形态：编工作流是把一条流程固化下来，工具创造则是给自己补上一个缺的能力。

**实验9-6 ★★★：由失败轨迹触发Agent 自我修改**

这条实验检验系统能不能把「不可重试错误被反复调用」这条经验写进重试与熔断程序，同时保留临时故障的恢复能力。做法是拿「只在 Prompt 里提醒不要重试」和「修改程序里的重试策略」两种修复做对照，修改提案要过失败轨迹重放、正常故障回归和安全发布门槛，并且不能修改验证器或稳定版本。这个对照设计很经典：同样是不要让 Agent 在不可重试错误上反复重试，一种修法是 Prompt 里的提醒，属于软约束；另一种是程序里的重试策略，属于硬约束。这里选后者，理由是能够确定性执行的约束应该进入程序。同时它要求保留临时故障的恢复能力，也就是不能粗暴地把重试全关掉，得区分不可重试错误和临时故障，前者立刻停，后者仍然退避重试。

验证层用的是同一套协议。当多条用户纠正、点踩或者事后审计都指向「高风险操作未经确认」，系统会生成一个确认门禁提案。提案必须在边界任务和正常任务上都通过验证，而且安全门自己不能被提案修改。把它跟第一章的观点对齐了：「这与第一章三层护栏里数据层的道理相同：真正的保证必须来自被修改者无法触及的那一层。」这条限制的逻辑在权限层面，跟提案内容多合理无关，修改者不能触及验证自己的那套东西。

**实验9-7 ★★：由用户反馈触发高风险操作确认门禁**

这条实验看系统能不能从用户纠正和事后审计里发现安全流程缺口，并为高风险工具调用生成确认门禁。评价用的是危险操作边界集和正常操作保留集，门禁既要拦住未经确认的高风险调用，也不能阻断正常任务；生成提案的 Agent 无权修改安全测试和批准规则。结论是安全能力的进化不能由修改者自证成功，真实模型生成的更新提案被安全门拒绝是正常现象，这恰好说明独立验证器和不可修改的可信根比「提案看起来合理」更重要。

几组概念在这里容易混。代码生成和经验程序化要分开：第五章讲 Agent 会写代码，本节讲的是 Agent 把自己的轨迹编译成未来可复用的程序，重点落在由经验触发、被验证闭环约束。动作执行成功和任务成功的区别是前者只说明这一步没报错，后者要求最终状态正确，判断后者只能靠最终状态检查。回放加速和正确性保证也别混，加速来自不再逐步调用 LLM，正确性来自前置、后置、最终状态三类检查加上独立回放验证和失效回退，缺了后面这些，加速就是负收益。确定性可执行的约束放程序，需要语境判断的原则放 Prompt 或 Skill。提案生成者和发布批准者是两个角色，Agent 可以提代码提案，能不能发布由模型外的测试、审计、回滚机制决定。最小补丁和可归因也不是同一件事，小补丁是必要条件；要建立分数与机制之间的因果联系，还得有可证伪的变更契约。

对稳定、重复且可验证的操作，把一次探索编译成带参数、带前后置检查、带最终状态检查、带失效回退的程序；Agent 改代码时要走一遍隔离分支、最小补丁、静态检查、单元测试、安全扫描、失败轨迹重放和旧任务回归，灰度发布排在末尾。自我修改说到底是一次由经验触发的软件发布，进程并不会去覆盖自己。

## 9.2.3.1 案例：DeepSeek Harness 以"一切皆插件"实现自我进化

第一章的框架对比表把 DeepSeek Harness（dsh）归为「Agent 自进化框架」。它的底座 Cordis 论文指出，传统意义上的组合是静态的：函数调用、模块导入和类继承都在编译期确定，运行期不再变化；而插件系统和自进化 Harness 需要的是动态组合，组件要在运行中被装入、卸下和重新配置。由此得到一句结论：Agent 的每一次自我修改，本质上都是一次动态组合。

动态组合有两个正交的维度。**时间可组合性（temporal composability）问的是一个组件被移除时，它对共享环境做过的修改能不能被完整、安全地撤销，这要求运行时追踪它的每一次资源分配、事件注册和状态变更。空间可组合性**（spatial composability）问的是组件之间能不能用结构化、可验证的方式声明、发现和解析彼此的依赖，并在依赖变化时协调各自的生命周期。这里的概括很省事：前者关心改了什么，后者关心依赖什么。

自进化 Harness 是这个问题上最尖锐的场景，因为它要撤销的副作用是长期存活、带状态的，要解析的依赖会在运行中出现、消失或者改变身份。少了时间可组合性，每次自我修改都要整体重启，进程内积累的状态全部丢掉，进行中的任务被反复打断。少了空间可组合性，每个模块只能用临时手段自己察觉依赖的出现、消失和改变，一次简单的代码替换就可能静默地破坏依赖方，或者引入循环依赖。

Cordis 的思路是把两个原本属于编译期的概念提升到运行时。效果系统本来用于推理「计算如何修改环境」，现在被提升成可撤销效果：每一次对上下文的变换都携带一个显式的逆操作，由运行时追踪，组件移除时上下文随之恢复。协效果（coeffect）系统本来用于推理「计算对环境有什么要求」，被提升成反应式协效果：组件把自己需要的依赖声明成一份规格，上下文每次变化都按这份规格通知它激活、失活还是无关。论文进一步用一套动态组合演算，把这个性质从单个组件推广到相互交错的组件系统，也就是说可组合性必须是可传递的。

核心论断是：「自我进化的上限，不取决于模型能写出多好的代码，而取决于承载它的系统具有多强的可组合性。」这也是 dsh 让模型适配器、工具注册表、会话日志乃至 Agent 主循环本身都成为插件的原因，用这里的话说，不存在一个只能由人类维护的特权内核。系统里如果留着一块只有人能改的核心，Agent 的自我进化就永远卡在那块核心之外；把它也插件化，等于把天花板整体抬高一层。

可组合性解决的是能不能安全地装卸，它没有回答该不该装。模型写出的插件只活在进程内存里，重启就消失，不能被自动提升为正式插件；要留下来，必须另走前面那条 worktree 加 Pull Request 的慢路。这里守着 9.2.3 的「待验证 → 发布」原则：能装卸和能转正是两件事。

进化的代价落在 **KV Cache** 上。运行中的插件会改变模型可见的工具集和提示片段，请求前缀一变，第二章讨论的 KV Cache 就从变化处开始失效。所以 dsh 插件的说明文档里需要专门描述它对上下文和 KV Cache 的影响。工程含义很实在：频繁的自我修改会让推理成本上升，把缓存影响写进插件文档，既是性能约束，也是改动要克制的理由。

两个可组合性问题各自有个顺手的类比。时间可组合性像撤销。装了个插件，它注册了一个定时器、占了两个端口、往全局配置里写了一项，要卸掉它的时候，这些副作用能不能全部收回来？不追踪就只能重启进程，把状态清空。空间可组合性像依赖解析：A 插件依赖 B 提供的接口，B 被换成 B' 之后 A 怎么办？依赖关系如果是隐式的、靠运行时撞见，一次看着无害的替换就可能静默破坏 A，或者让 A 和 B' 互相依赖成环。

「逆操作」和「依赖规格声明」是两个很工程化的答案。前者要求每一次对上下文的变换都自带 undo，组件移除时上下文自动恢复，不用重启；后者要求组件把自己的依赖写成一份规格，依赖变化是被通知的，不用靠模块自己临时察觉。「可组合性必须是可传递的」这句容易一晃而过，但很关键：单个插件装卸干净还不够，A 依赖 B、B 依赖 C 的整条链都得保持这个性质，否则系统一层层组合起来，中间某一层就漏了。

这一小节和本章别处是分工的：9.2.3.1 讲能不能安全地改，9.2.2 和 9.2.3 讲该改什么，9.3.2 讲谁能改什么，三者叠起来才算一个完整的自我修改系统。

概念上要分清几组。函数调用、模块导入、类继承属于静态组合，编译期就定了；插件系统属于动态组合，运行期可以装入、卸下、重配置。时间可组合性和空间可组合性的区别就一句话，前者关心改了什么，后者关心依赖什么。效果系统管「计算如何修改环境」，提升为可撤销效果；协效果系统管「计算对环境有什么要求」，提升为反应式协效果。能装卸和能转正也要分开，可组合性保证的是安全装卸，内存里的插件重启即消失，转正得走 worktree 加 Pull Request。

自我进化的上限由承载它的系统的可组合性决定，要做到改动可撤销、依赖可声明；但可组合性只管能不能安全装卸，该不该转正仍然要过正式的发布流程。

### 9.2.4 将经验写入参数

知识、指令和程序都建立在一个前提上：目标能力能够被外部符号比较完整地表达。有几类能力很难压缩成几条规则或者一个工作流，这里点名的有医疗影像理解、自然的语音韵律、消除文本的模板化「AI 味」，以及长程规划。这些能力必须通过后训练写进模型参数。

弯引号的作用域判断处在中间地带：文档的语法边界可以由程序解析，语境和例外需要用 Skill 表达，跨任务的识别习惯才适合通过后训练内化。拿一个引号是开引号还是闭引号来说，文法的层面对应关系（哪一对配哪一对）程序就能解析；具体的语境和例外，比如某种排版惯例，得用自然语言规则说明，所以放 Skill；只有在大量任务上稳定形成的识别习惯，才值得做后训练。同一件事被按性质切成了三份，没法整体只挑一个载体。

是否参数化，也不由任务是否长期稳定单独决定。新影像设备带来的域偏移仍然可能需要 LoRA 或持续微调；快速变化的语言风格也可以通过周期性偏好训练来适应。这里的结论是，稳定性影响的是更新频率和成本，真正决定主要载体的是能力的表示性质。这两个反例专门用来打掉「稳定才参数化」的直觉：新设备带来的分布变化是新出现的、不可预期的，它恰恰需要 LoRA 或持续微调；语言风格属于变化最快的一类，它恰恰适合周期性偏好训练。该问的是这个能力能不能用符号表达。

一种常见的误解是把参数学习当成终极形态，前面三种只是过渡。图9-3 的注解把这个阶梯观否掉了：四种载体是互补关系，谁都不在终点。所以判断标准只有一条，这个能力能不能被事实、语言规则或程序较完整地表达；能，就别动参数，不能，才动参数。

与第八章的分工很清楚。SFT、蒸馏和 RL 在第八章已经完整讨论过，本节不重复；对持续进化而言，关键的一步是把经过评价的生产轨迹转成训练数据。高质量示范可以进 SFT；明确偏好可以形成成对数据；具有可靠环境奖励的交互可以用于 RL。这三个对应关系背后都藏着一个「可靠」：示范要真的高质量，不能拿侥幸成功的轨迹当示范；偏好要明确；奖励要可靠。没有可靠的评价，就没有可用的训练数据，这跟 9.1 的三层验证是同一件事的两面。

几组概念要分开。能不能参数化是技术可行性，该不该参数化取决于能力的表示性质。稳定性管的是更新频率和成本，跟选哪个载体无关。三类训练数据的来源别混用，SFT 对应高质量示范，成对数据对应明确偏好，RL 对应具有可靠环境奖励的交互。参数擅长高维感知、生成风格和隐式策略，硬性业务规则不适合靠参数保证，这一点参见思考题第 6 题。

只有当能力无法被事实、语言规则或程序完整表达时，才把经验写进参数，比如医疗影像理解、语音韵律、去「AI 味」和长程规划；判断依据是能力的表示性质，跟任务稳不稳定没有直接关系，而写入的前提是先有经过评价的可靠轨迹。

### 9.2.5 从更新产物到更新"更新方法"

前面四种方法讨论的是经验最终写到哪里。持续进化还有一条正交的轴：系统正在优化的，究竟是某份产物的内容，还是产生、管理和验证这些产物的方法。沿这条轴看，优化对象可以逐层扩大：单条规则或记忆、结构化上下文、工作流、Harness 代码，一直到产生更新提案的优化器代码。限定了一句，这五种是五种不同的搜索尺度，算不上五种新的更新载体，知识、Prompt、Skill 和程序都可能出现在其中多个层级。

最内层只改产物内容，比如根据失败轨迹给系统提示加一条局部规则，或者给经验文档补一个例外条件。它的特点是作用面小、容易归因、容易回滚，应当是默认选择。但反复让模型重写整份 Prompt 或记忆会带来另一类退化：为了追求简洁，旧版本里少数重要细节会在多轮改写后逐渐消失，相互制约的条件也可能被合并成一句过度抽象的原则。Agentic Context Engineering（ACE）的对策是把上下文维护成带稳定标识符的条目集合，由生成、反思和整理模块提出增量更新，再用确定性逻辑合并与去重，不必每轮重写一个越来越短的文本块。它给「最小 diff、保留来源」提供了一个具体的研究实例。注意「确定性逻辑」这个词，合并去重不交给模型即兴发挥，而是用确定性规则做，这跟最小 diff、保留来源是同一套工程价值观。

再往外一层，优化对象从「上下文里有什么」变成「上下文应该怎样被构造」。Meta Context Engineering（MCE）把两者拆成内外两个循环：内层在给定管理方法下优化当前任务的上下文产物，外层根据多轮执行和验证结果，修改搜索、选择、过滤、格式化这些上下文操作本身。这个区分的意义在于：修改一条检索规则是在改内容管理机制，让系统比较多种检索与整理机制、保留迁移效果更好的那个版本，才是在学习如何管理上下文。

继续往外就到工作流和整个 Harness。AFlow 把由多个 LLM 调用组成的工作流表示成代码图，通过执行反馈搜索节点与控制流的组合；Meta-Harness 让 Coding Agent 读取待验证 Harness 版本的源码、分数和轨迹，去搜索决定信息如何存储、检索和呈现的代码。第五章说过代码是 Agent 表达系统结构的通用语言，这里新增的一点是：代码不再只是一次生成的产物，它还可以连同评估历史一起成为持续搜索的对象。

外层搜索有个反馈成本的天花板。探索策略决定从哪个候选继续、什么时候另开分支、并行投入多少 Worker、什么时候停，它的好坏往往要经过很长的生成—评估链条才看得出来。这里的担心很直接：如果每个候选策略都得重新调用 Agent 和评估器，优化探索策略本身可能比完成任务更昂贵。Dream-RSI 的整套设计动机就是把这一步变便宜。

Dream-RSI 提出了一个不同于「总结历史」的机制：把已经完成的发现过程保存为**发现树**，再把这棵树当成经验性的回放模拟器（replay simulator）。根节点表示初始工作区；每个子节点保存从某个历史状态继续尝试后得到的工作区快照、候选产物、评估诊断和分数；候选策略通过与在线探索相同的接口，逐步选择要展开的叶节点，或者从根节点打开新分支；回放器只揭示相应节点里已经记录的结果，不必重新运行底层 Agent 和评估器。

把发现树当成模拟器来读，三个要素很清楚。节点是一个历史状态，装着工作区快照、候选产物、评估诊断和分数；边代表「从某个历史状态继续尝试」这一步；回放器是个只会揭示已记录结果的假环境，不再真的调用 Agent 和评估器。候选策略于是可以在不花真实算力的情况下，试遍不同的分支选择、执行顺序、并行批次和停止时机。

回放要成立，有两条规则是硬的。在线和离线阶段必须用同一个决策接口，否则离线学到的策略在线根本用不上，相当于换了题目。只向策略逐步揭示当前已经展开的子树，否则它会偷看未来，在离线回放里表现完美，在线却复现不出来。在线阶段里被选中的节点会真正调用底层 Agent 和评估器，离线阶段同样的选择只返回历史里已经记录的后继。两条加起来，候选策略可以比较不同的分支、顺序、并行批次和停止时机，又不能偷看在线决策时尚不可见的未来结果，回放因此有信息价值，也不至于变成作弊。

整个闭环跑三个阶段。在线探索用当前策略生成新的发现树；构造回放世界，把发现树加进历史模拟器池；离线做梦，让策略开发 Agent 修改探索策略代码，并按候选质量、执行成本和并行效率比较版本。入选的策略重新上线后产生新的树，也扩大了下一轮可以回放的经验范围。在这里补了限定：候选集合里保留了当前策略，所以新版本至少不会在已有历史的平均回放分数上更差，但这只是历史内的保证。

三种历史复用方式放在一起看，区别就出来了：

| 方式 | 改变的是什么 | 复用的是什么 |
| --- | --- | --- |
| 轨迹总结 | Agent 知道什么 | 压缩后的知识 / Prompt |
| 浏览器工作流回放 | Agent 怎样重复执行 | 一条已验证的执行路径 |
| 发现树回放 | Agent 怎样组织探索 | 历史上走过的整棵分支树 |

轨迹总结把经验压缩成知识或 Prompt，改变的是 Agent 知道什么；浏览器工作流回放让程序在新任务里重复一条已验证路径，改变的是 Agent 怎样重复执行；发现树回放比较的是 Agent 怎样组织探索。三者的抽象层级依次升高，从知识到动作再到搜索策略。对发现树回放的边界说得很克制：它只能重组历史中实际走过的分支，不能保证在旧树上得分更高的策略迁移到新任务，也不是能够预测任意动作后果的完整世界模型。「在旧树上得分高不能保证迁移」这句话是实验9-8 和思考题第 7 题的伏笔。

从本章的分类看，历史回放算不上知识、Prompt、程序和参数之外的第五种更新载体，它是一种产生并验证更新提案的新机制。Dream-RSI 最终修改的是探索策略代码，产物仍然属于程序或 Harness；它的新意在于把过去作为上下文或训练数据的历史，变成可以反复交互的离线评估环境，把自我进化推进到「如何分配探索计算」的元策略层。

**实验9-8 ★★★：把这里交给Hermes：它能升级自己吗？**

这个实验真正想看的，是 Agent 会不会走流程，而不只是能不能改代码。做法是不给 Agent 预设修复目标，观察它能否把这里的原则映射到自己的代码，并根据 Reviewer 的退回意见继续修正；稳定版本、验收测试和批准门槛始终在它的修改权限之外。这里给的链条有四步：理解原则、提出更新提案、接受外部检验、根据反馈修正。还有一条额外的谨慎：一次提案被接受，只证明更新流程成立，不能自动证明下游能力已经提升，这直接对应 9.3 里「Harness 更新能力 ≠ Harness 受益能力」。

这一节的判断标准可以压缩成：越往外的改动杠杆越大，归因和回滚也越难，所以默认从最内层的最小修改做起；而外层搜索最大的敌人是反馈成本，Dream-RSI 用发现树把这一项压了下来。

概念上还要分清几组。更新产物内容和更新「更新方法」是两回事，前者是这次写什么，后者是我们该怎样产生、管理、验证这些产物；MCE 的内循环对应前者，外循环对应后者。五种搜索尺度跟五种更新载体也不是一回事，知识、Prompt、Skill、程序可能出现在多个尺度上。三种回放各管一件事：轨迹总结改变知道什么，浏览器工作流回放改变怎样重复执行，发现树回放比较怎样组织探索。回放模拟器和世界模型要分清，它只能重组历史中实际走过的分支。历史内不退化不等于新任务有提升，保留当前策略只保证在已有历史的平均回放分数上不更差。离线回放的分数只有在接口一致、且不偷看未展开子树的前提下才有预测意义，参见思考题第 7 题。

除了改产物内容，还可以改产生与管理产物的方法，从上下文构造到工作流、Harness 代码，再到优化器本身；越往外杠杆越大，归因和回滚也越难，所以默认先从最内层的最小修改做起。Dream-RSI 用发现树当离线模拟器，把外层搜索的反馈成本降了下来，但它给的只是历史内的保证，不是世界模型。

## 9.3 构建可长期运行的持续进化闭环

四种更新方式各自都能带来一次改进，但只有进入同一个自主循环，单次优化才会变成持续进化。图9-5 给的是生产系统里更稳妥的搭法：把在线执行和离线进化拆成两个循环。

左边这个循环只完成任务并记录证据，不直接改写正式 Agent；右边才做聚合轨迹、诊断根因、生成更新提案，再通过验证门槛发布新版本。两边靠版本化的经验库和评估集连起来。

"正式版本不在运行中直接改写"是这一节的总纲，它要解决的是一个很实际的工程焦虑。如果 Agent 在线跑着跑着就把自己改了，出问题时你不知道当时跑的是哪个版本，也没法回滚，正在进行的任务还可能被中断。把"完成任务并记证据"和"聚合诊断、生成提案、验证发布"拆到两个循环里，学习就变成了一条可版本化、可回滚的发布流程。

那两条连接线值得单独看一眼。向右传的证据必须带版本，因为轨迹是在某个版本下产生的，脱离版本它没法解释；向左回流的是一个新的稳定版。闭环的产物是一份可发布的版本，零散的新记忆条目给不了这种可审计性。

图9-5 底部那条"可信根"约束在 9.3.2 会展开成三道边界。它是整个闭环能成立的前提：如果进化流程能改自己的验证器，这个闭环就没有可信的收敛方向。

Voyager 展示的是一个更完整的循环。它在 Minecraft 里根据当前能力选择新目标，通过环境反馈迭代程序，验证成功之后把代码存进技能库，再组合旧技能去解决更难的任务。这里的表述是"自动课程、可执行技能和环境验证缺一不可"，并且给了三条反例：只有技能库而没有课程，Agent 不知道下一步学什么；只有自我反思而没有环境验证，技能库会积累错误；只有探索而没有持久化，每次任务仍要从头开始。现实里的 Agent 知识、Prompt、工具和参数都更复杂，基本的学习过程是类似的。

此处引用的文献是脚注 20：**Voyager**，Wang, G., et al. *Voyager: An Open-Ended Embodied Agent with Large Language Models*. arXiv:2305.16291, 2023。

> 检索确认：脚注所记 **Voyager 的 arXiv 编号 2305.16291、第一作者 Wang（Guanzhi Wang 等）**与外部资料一致，论文题为 *Voyager: An Open-Ended Embodied Agent with Large Language Models*，是 Minecraft 中的开放式具身 Agent。（来源：[Voyager: An Open-Ended Embodied Agent with Large Language Models](https://sinoxiv.napstic.cn/article/4679869)）

三个机制互相咬合。自动课程生成器根据当前物品、环境和已掌握技能提出下一个难度适中的目标，探索因此不会是随机漫游；技能库把成功的程序保存成可检索、可组合的代码，高级采集技能可以调用移动和制作这些基础技能；迭代提示机制把环境观察、执行错误和自验证结果带回下一轮代码生成，直到任务真正通过。

那三条缺一不可，逐个想清楚比背下来有用。没有自动课程，探索就退化成随机漫游。没有环境验证，自我反思的结论会直接进技能库，错误累积起来，这正是 9.2.1 说的"反思不是证据"。没有持久化，每次都从零开始，也就是本章开头那个"第二天仍然犯第一天的错误"的悖论。放在一起看，它们对应的其实是方向（课程）、正确性（验证）和累积性（持久化），这三件事一个学习系统要长期有效就得做到。

以 Voyager 为代表的自我进化系统遵循的是由假设、实验、评估和反馈组成的发现循环，也就是数百年来逐渐形成的科学方法。Jeff Dean 等人创办的 Discovery Loop 提出把这个循环推向自动化：提出实验、实现实验、开展评估、取得结果，再把结果交给下一轮。这里的判断是，这是 Agent 自我进化在科学领域的应用，并且给出了一条要求："本章所述的Agent 自我进化要想避免自说自话、自我感觉良好，就必须遵循科学方法。"要判断一个自进化系统可不可信，就看它有没有真正的实验环节，是在真实环境里做、有可证伪的预期，还是只在自己的叙述里循环。

然后是一对最容易被忽略、工程上却最好用的概念。Harness 更新能力（harness-updating）指的是从轨迹中产生有价值的持久修改；Harness 受益能力（harness-benefit）指的是任务 Agent 在后续运行中找到、激活并正确使用这些修改。一种失败情形是：一个 Skill 本身可能写得完全正确，但较弱的任务模型没有在合适的场景加载它，或者加载之后无法长期遵循，任一种都会让最终成绩看起来"没有进化"。结论是不能只用端到端分数反推更新器好坏。Lin 等人的模型替换实验表明，这两种能力和基础模型能力的关系并不相同。

表9-3 持续进化的分层评估指标。

| 指标 | 回答的问题 | 主要证据 |
| --- | --- | --- |
| 更新提案有效率 | 更新器是否提出了有价值的修改 | 提案在独立验证中的接受率与增益 |
| 产物激活率 | 任务Agent 是否在正确场景加载了新Skill、记忆或工具 | 检索、路由与工具调用轨迹 |
| 遵循成功率 | 激活后是否按新规则或流程执行 | 动作序列与过程验证器 |
| 保留任务集增益 | 整体是否改善了未参与进化的任务，是否有泛化能力 | 保留集成功率、质量与成本 |

这四个指标正好对应四层可能的失败。分数没涨，可能是更新器压根没提出好提案，也可能是提案很好但任务 Agent 没在正确场景加载它，还可能是加载了却没有长期遵循，再或者是前三步都做到了，但好处只落在参与进化的那批任务上。分层评估的意义就在这里：把端到端分数拆成可归因的四段。

评估的定位需要说清楚。"评估是自我进化过程中不可或缺的一部分，不是学习结束后集中进行的考试。"长期评价至少同时观察五类结果：回退（regression），即新经验是否与已有的其他经验冲突、原本能通过的案例是否出现回退；泛化能力，即新经验在测试集尚未覆盖的场景中带来的效果提升；Token 效率，即完成任务消耗的 Token 成本；安全性，即规则、隐私和拒绝边界是否随进化漂移；长期工程质量，即维护复杂度、架构一致性、所有权边界、向后兼容性以及未来迁移和调试负担是否恶化。判定标准给得很直接："只解决了当前失败案例的问题，却在其他已有案例或新领域中退化，不是成功的持续进化。"

这五类可以按"防什么"来记。回退防的是修一个坏一个；泛化防的是过拟合到当前失败集；Token 效率防的是用更多算力换分数，成本也是能力的一部分；安全性防的是边界随进化漂移；长期工程质量防的是技术债累积。排在末位的这一项面向的是人的成本，也最容易被分数导向的系统忽略。

**实验9-9 ★★★：评估Agent 是否在持续进化**

实验目的是区分"保存反馈""不断追加反馈"和"能够更新、迁移并保留能力"三种行为，验证 Agent 是不是真的在持续进化。做法是让 Agent 先在一组任务中获得反馈，再面对表述变化、规则更新和原有能力保持等情况，对照静态记忆、只追加记忆和可替换/可淘汰的版本化记忆，观察经验能否迁移，也观察新规则是否覆盖旧规则、更新后是否遗忘。它说明了什么：持续进化至少包含记住、迁移、更新和保持四个环节。最终分数高并不够，如果系统继续使用已废止规则、靠违规捷径完成任务，或者更新之后破坏原有能力，都不能判定为持续进化。

三种记忆的对照值得多停一会。只追加的记忆系统会遇到这里列的三类问题：旧规则没被覆盖，于是继续使用已废止规则；没有过程验证，于是靠违规捷径完成任务；没有回归，于是更新后破坏原有能力。而记住、迁移、更新、保持这四个环节，正好把这三种失效都堵住。说白了，只追加不等于学习。

9.3 全节的判据可以收在这么一段里：持续进化要把在线执行和离线进化拆成两个循环，在线只记证据，离线生成并验证更新，产出的是一份通过验证的新稳定版；评估要分层看提案是否有效、是否被激活、是否被遵循、是否在保留集上有增益，长期还要同时盯住回退、泛化、Token 效率、安全性和长期工程质量这五件事。

### 9.3.1 可验证闭环的边界：当"完成"不等于"进步"

这个闭环在哪些任务上最容易成立？Coding、工具调用和业务状态变更这一类，因为测试、环境状态或者确定性规则能够快速给出反馈。最难的是开放式科研、战略规划和复杂产品设计，原因有三条：评价信号来得慢；正确答案不唯一；研究品味、长期价值、可维护性这些真正重要的目标还很难用分数评判。对这种场景下的典型失效形态刻画得很准："此时Harness 可能把流程执行得非常完整，却只是稳定地产出'像成果的东西'，没有推动真实目标。"

这是自进化系统里最隐蔽的一种失败。所有指标都是绿的，流程走完了，报告生成了，格式没毛病，唯一的问题是真实目标没有被推进。它比跑出错危险得多，因为错误看得见，而"看起来很完整"看不见。

自动科研可以当成一次压力测试。Trehan 与 Chopra 记录了四次从研究想法走向论文的端到端尝试，其中三次在实现或评估阶段失败，只有一次完成整条流水线。这些案例暴露的问题可以归成三类。实现漂移，指原方案一旦变难，Agent 会逐渐退回训练数据中更熟悉、但已经偏离研究假设的普通实现。认识论上的过度乐观，指信号仍可能只是噪声，系统却开始解释结果、添加补丁并宣布发现，而且它还配了一个不对称：失败和阴性结果更容易被忽略。隐性判断力不足，指 Agent 可以运行实验，却未必知道什么基线真正重要、哪个异常值得追踪、何时应该放弃假设。

三者的性质各不相同。实现漂移是优化压力下的滑坡，原方案一难，模型就会自然滑向训练数据里更常见、更省力的写法；它谈不上故意跑偏，更熟悉的路径在采样意义上本来就更容易被选中。认识论上的过度乐观是一种叙事冲动，它对应的正是保留负面结果这条对策要治的病。隐性判断力不足更接近品味缺失，前两条还能靠证据结构缓解，这一条不行，这也是"不能靠换一个模型彻底解决"的原因。

这类任务要改变的是证据和监督结构，这里给了四条。结论与证据分离，即对引用、数字、方法和结论分别记录证据来源，最终文稿只是证据图的一种呈现；ScientistOne 的 Chain-of-Evidence 设计把每类声明都链接到可审计来源，是这一方向的案例，但它提高的是可追溯性，并不自动保证研究问题有价值。保留负面结果，即把失败实验、被拒提案和停止原因写进日志，否则进化模块只看到幸存方案，会反复探索已经证伪的路径。维护搜索多样性，即不应只保留当前得分最高的一条链，备选方案池还需保留若干暂时低分但类型不同的分支，避免所有方案收敛成同一个易得分模板。让人类在更高层介入，即人的作用不应只是在危险工具调用前点"批准"，还包括定义问题、审查评价标准、解释反常结果和决定何时停止。

这四条对策其实对应四种不同的治理手段。结论与证据分离治的是不可追溯，追得再清楚也可能是在研究一个不重要的问题。保留负面结果治的是幸存者偏差。维护搜索多样性治的是收敛到易得分模板。人类在更高层介入治的是目标与标准本身的问题。

让人类在更高层介入这一条特别值得停下来看，因为它澄清了一个常见误解：人在 Agent 系统里的角色不只是审批危险操作。这里列的四件事，定义问题、审查评价标准、解释反常结果、决定何时停止，全都是元层面的判断，也正好是当前模型最不擅长的部分。所以人工介入不该只被设计成一个弹窗，它更应该是评价标准和问题定义的所有权。

放到本章的结构里，9.3 讲闭环怎么搭，9.3.1 讲闭环在什么条件下不成立。这里的态度很诚实：可验证闭环有边界，越出边界它就会退化成稳定地产出像成果的东西。这也解释了 9.4 小结末尾为什么要补一句"对于目标模糊、反馈延迟的开放任务，人仍需参与问题定义和评价标准的制定"。

几组容易混的地方留在这里。"完成任务"是流程走完，"取得进步"是真实目标被推进，在结果可自动验证的任务上两者大致重合，在开放式任务上可能完全脱节。ScientistOne 的 Chain-of-Evidence 提高的是可追溯性，不自动保证研究问题有价值，可追溯和有价值是两件事。只留成功会得到幸存者方案集，进化模块会反复探索已证伪的路径。只保留最高分那条链会收敛到同一个易得分模板，所以需要留下暂时低分但类型不同的分支。至于人，低层审批是危险调用前点批准，高层定义是定义问题、审查评价标准、解释反常结果、决定何时停止，这两件事不该混为一谈。

### 9.3.2 持续进化的安全边界

Agent 的自我进化能力有可能把一次错误变成长期风险，这里给了三个具体形态。网页、邮件和工具输出中的提示注入如果被总结成经验，可能跨会话反复生效；自动搜索到的恶意软件包如果被封装成工具，影响会从一次沙盒运行扩散到所有后续任务；一个有缺陷的验证器还可能持续批准看似进步、实际退化的待验证版本。由此得出的总要求是，Agent 自我进化系统除了验证"是否更强"，还必须限制"谁能改什么、依据来自哪里"。

第一道边界是证据与指令隔离。原始网页、工具输出及其 LLM 摘要都属于不可信证据，不能当作指令执行，也不能直接纳入 Skill 等长期能力。这里要澄清一个误解："LLM 总结只是为了提高可读性和便于处理的转换，并不是把输入变得无害的净化过程。"具体做法是，系统按固定 schema 提取主张、来源位置和采集时间，同时保留出处与来源；提取出的字符串绝不能作为指令执行。模型给出的置信度也只是未经验证的估计，不能充当批准门槛。待发布的内容还要通过确定性的 schema、允许列表和来源检查，再以版本化的 pull request 提交；独立于生成者的 reviewer 应对照原始证据审查变更，高风险 Skill 上线前还应经过人工批准。

第二道边界是待验证能力与正式能力隔离。新知识、Prompt、Skill、程序和参数都先进入不可服务真实流量的待验证区。新生成的代码和外部依赖还要经过沙盒、权限检查、供应链扫描与行为测试等安全检查。这些检查与回归测试通过之后，才能服务真实流量，成为正式能力。

第三道边界是安全机制不可自我修改。业务 Agent 可以修改 Prompt、Skill、知识库、工具这些业务资产，但不能修改批准自身更新的验证器、测试用例、发布门槛、审计日志和稳定版本备份。这里的推理很直接："否则，一个Agent 只需降低测试阈值或删除失败用例，就能把退化伪装成进步。"

这三道边界可以概括成三个问题。这段话可信吗，问的是证据与指令隔离，依据来自哪里。它上线了吗，问的是待验证能力和正式能力的隔离，谁能影响真实流量。谁在给谁打分，问的是安全机制不可自我修改，谁能改什么。三者分别管输入、通道和裁判。

第一道边界上有三个最容易犯的错。把摘要当净化，这里否定得很干脆：一段含提示注入的网页，经过 LLM 摘要之后依然是不可信输入，摘要不会洗掉注入，它只是换了种写法。把置信度当门槛，模型说"我 90% 确信这条经验正确"，这句话本身也是模型的输出，不能拿来当批准依据，门槛必须是确定性的检查。把字符串当指令，即使已经按 schema 提取成"主张 + 来源位置 + 采集时间"，提取出来的字符串也绝不能作为指令执行，因为它依然是外来文本。

这一道的正解可以拆成四步走：固定 schema 提取，保留出处与来源，做确定性检查（schema、允许列表、来源），再走版本化 PR 加独立 reviewer，高风险还要人工批准。四步里没有任何一步依赖模型的自评，这正对应 9.2.2.1 里"提炼产物不能直接发布，须经与提炼者相互独立的验证"。

第二道边界的核心是没有一条路径能绕过待验证区，它把 9.2 里的几种载体一视同仁：知识、Prompt、Skill、程序、参数，都先进待验证区。其中"参数"这一项容易被忘，SFT/RL 出来的权重同样是待验证能力，也要先不服务真实流量。对新代码和外部依赖，这里额外要求了一组供应链性质的检查，沙盒、权限检查、供应链扫描、行为测试，这直接对应本节开头那个恶意软件包被封装成工具的风险。

第三道边界是三道里最"元"的一条，也是整章反复出现的那句"可信根"的落地：业务 Agent 能改业务资产（Prompt、Skill、知识库、工具），不能改评判自己的东西（验证器、测试用例、发布门槛、审计日志、稳定版本备份）。这里给的反例很有画面感，只要降低测试阈值或者删掉失败用例，退化就能伪装成进步。

三道边界和前面几处是呼应的。9.2.2.1 的"模型把失败写入规范"靠第一道加独立验证来防；9.2.3 的"生成提案的 Agent 无权修改安全测试与批准规则"就是第三道；9.2.3 验证层那句"安全门本身不能被提案修改"也是第三道；实验9-7 里真实模型生成的更新提案可能被安全门拒绝，那是三道边界合力的效果。

还有一点实践上的提醒：这三道边界的成本是不对称的。第一、二道主要增加流程开销，提取、检查、待验证区、灰度都要花时间；第三道是架构层面的约束，它要求系统设计时就把可信根划出来，不能事后补。如果一开始就让进化流程持有验证器和发布门槛的写权限，后面再想收回来会非常困难。

几组概念要分开。原始网页、工具输出及其 LLM 摘要都属于不可信证据，摘要不是净化。模型的置信度只是未经验证的估计，门槛必须是确定性的 schema、允许列表和来源检查。待验证能力和正式能力之间隔着流量这道关，新知识、Prompt、Skill、程序、参数一律先进待验证区。业务资产可以改，安全机制不能改。人工批准的位置也要放准：高风险 Skill 上线前必须人工批准，而第一道边界里的常规检查靠确定性规则加独立 reviewer，不需要每件事都等人点批准。

### 9.3.3 睡眠学习：整合、遗忘与能力保鲜

"睡眠学习"是对离线整合的认知类比，并不要求任务真的在夜间运行。这个名字抓住了两件事。整合，把新经历和旧结论放在一起比较、合并、解决冲突。遗忘，把过期、冲突、长期不用的东西修剪掉。工程上这一点很重要，别把"离线"理解成"定时任务"，它更应该是一个受门控的批处理。

在线和后台的分工是这样的。在线 Agent 的首要职责是完成当前任务并追加不可变证据；后台学习进程在空闲期或满足门控条件时读取一批新经历，比较新旧结论、合并重复项、解决冲突、提出更新提案并运行回归。把采集与整理分开有两个好处。安全上的好处是一次偶发成功、网络故障或恶意输入不会立刻改写长期能力，这直接呼应 9.3.2 的第一道边界：如果在线就把观察写进长期能力，提示注入只要成功一次就能持久化；批量整理时多条轨迹互相印证，风险会低很多。成本上的好处是整理允许使用更大的批量和更便宜的模型，因为它不在关键路径上。

一个典型的睡眠学习周期包含五步。触发，达到时间间隔、新增轨迹数量、存储容量或错误频率门槛，并确认当前没有高优先级在线任务。定向，读取正式知识、Prompt、Skill 目录及其版本，了解已有能力和不可修改边界。采集与整合，从近期已评价轨迹中寻找新信号，合并重复内容，标记冲突与适用条件，优先生成局部补丁。验证与审批，在迁移集、保留集和安全集上评估待验证版本，高风险写入等待人工批准。修剪与索引，更新检索索引，把长期不用或被新证据推翻的能力标记为过期，或将其归档、删除，同时保留来源和回滚版本。

五步里"定向"容易被忽略，其实很关键。它要求后台进程先读取正式知识、Prompt、Skill 目录及其版本，了解已有能力和不可修改边界。整理进程动笔之前得先知道现状和红线，这既避免重复劳动，已有能力不再重复生成，也避免越界。

第五步是"遗忘"的落地。标记过期、归档、删除是三档渐进的操作，不是一刀切，而且都要保留来源和回滚版本。判断依据这里给了两种：长期不用，或者被新证据推翻。

用户记忆是最直观的例子，但要和行动经验区分开。Claude Code 的自动记忆为每个项目维护 MEMORY.md 索引和按主题拆分的详细文件，会话启动只加载索引的有界前缀，其余内容按需读取；索引接近上限时，系统要求 Agent 合并或移走细节。这个例子演示了容量约束、分层加载和主动整理三件事。同时做了一个诚实的限定：当前公开机制主要是在会话中持续写入，并不能简单等同于一个固定的夜间后台任务，它更像边写边整。

Hermes 是更完整的后台记忆进化案例。它把长期信息分成有界的 MEMORY.md 与 USER.md、基于 SQLite/FTS5 的历史会话检索、按需加载的 Skill，以及 Honcho 等可选外部记忆提供者。设计里有三个细节值得单独记住。历史检索返回原始消息，不先由 LLM 摘要，这里的评价是"避免把检索和生成混成一个不可审计步骤"，这跟 9.3.2 第一道边界一致，要审计就得能看到这里。后台复盘有明确的触发条件：一次任务包含较多工具调用、从错误或死路中恢复、收到用户纠正，或发现非显而易见的工作流。这比定时全量复盘更精准，因为它只在可能产生新经验的时刻才触发。此外还有一个独立的 Curator，进一步跟踪 Skill 的使用、陈旧和归档状态，在空闲期执行确定性修剪，并可选择运行 LLM 合并，变更前保存快照，错误整理可以回滚。

周期性离线整理的必要性来自一个判断：持续进化也不是让知识、Prompt 和工具无限增长。第二章所说的上下文腐化会在更长时间尺度上重现，四个具体形态是经验文档相互冲突、Prompt 被边界规则淹没、Skill 库出现重复能力、多次微调造成灾难性遗忘。前三个都是只增不减的必然结果，第四个是参数载体特有的。

系统因此需要周期性离线整理，这里列出六项。

| 整理动作 | 针对的对象 | 治的病 |
| --- | --- | --- |
| 合并重复经验，保留来源和版本 | 知识 | 经验文档相互冲突 / 重复 |
| 局部规则从全局 Prompt 移到领域 Skill | 指令 | Prompt 被边界规则淹没 |
| Prompt 和 Skill 保持结构清晰 | 指令 | 同上（结构层面） |
| 重新验证长期未使用的工具 | 程序 | 工具陈旧、失效未被发现 |
| 删除被新证据推翻的知识 | 知识 | 知识过期、被推翻 |
| 从原始基座模型重新训练 LoRA | 参数 | 多次微调造成灾难性遗忘 |

末项很有代表性：多次增量微调把模型带偏、出现灾难性遗忘时，补救办法是回到原始基座模型重新训练 LoRA，在小数据集上继续微调解决不了这个问题。这与 9.2.4 的判断一致，参数更新与回归的成本高，维护周期也最长。

几组概念留在这里对齐。睡眠学习是对离线整合的认知类比，不要求夜间运行，触发条件是门控：时间间隔、轨迹数量、存储容量、错误频率，再加上"当前没有高优先级在线任务"。在线只完成任务并追加不可变证据，比较、合并、解决冲突、提案、回归都在后台批处理里做。用户记忆回答的是"用户与世界是什么样的"，行动经验回答的是"在什么条件下应该怎样行动"，要把两者区分开。修剪、合并这些操作本身也要能回滚：Curator 在空闲期执行的是确定性修剪，LLM 合并是可选的，而且变更前保存快照。上下文腐化和本节讲的其实是同一个问题在不同时间尺度上的重现，前者在任务内，后者跨会话、跨月。

## 9.4 本章小结

先看现状判断。持续进化正在成为 Agent 最重要的能力之一，但今天的模型还无法自行完成可靠的持续学习，理由有两条：推理时的上下文适应不会自动持久化；未经验证的在线参数更新又会放大噪声、攻击和能力漂移。现阶段更可行的路径，是在模型外围建立一套可验证的学习系统。

就全书的结构而言，本章构建的是第一章发现循环中的实验与反馈环节。提案已经有了，问题变成怎样通过一次以真实观测为基础的实验，判断它到底有没有让系统变好，以及怎样把结果送回下一轮。第九章并没有再发明一种方法，它给全书的方法论装上的是那段学习回路。放到数字上看更清楚：τ²-bench telecom 那批失败轨迹把通过率从 12.3% 抬到 19.3%，这个结论之所以算数，是因为它在一批未参与提炼的任务上量过；PreAct 在重复任务上拿到 8.5–13 倍加速，也是因为已验证的路径被固化成了程序。提案本身不构成进步，经过实验判断、并把结果送回下一轮才算闭环。

把全章的判断压成一条决策顺序，大致是五步。从与环境的交互和评价中获得学习信号，对应 9.1。按能力的表示性质决定更新知识、Prompt、Skill、程序还是参数，对应 9.2。优先采用可归因、可验证、可回滚的局部修改，默认从最内层做起，对应 9.2.5。用独立的边界任务和原有任务检查修改是否真正有效，对应 9.2.2 的边界集与保留集、9.3 的分层评估。再往后是长期维护，在线记录证据、离线生成并验证提案、逐步发布、整理或回滚，对应 9.3 与 9.3.3。

方法层面的总结是：Agent 从与环境的交互和评价中获得学习信号，再根据能力的表示性质更新知识、Prompt、Skill、程序或模型参数。系统也可以进一步优化管理和生成这些产物的方法，但应优先采用可归因、可验证、可回滚的局部修改。遇到问题时，先判断它更适合由外部规则、程序流程、Skill 还是模型参数处理，再用独立的边界任务和原有任务检查修改是否真正有效。

历史的作用也在这里收了尾。历史不仅能被提炼为静态经验，还能在支持域内组成回放环境，低成本筛选探索策略。这使持续进化可以进一步作用于"如何组织探索"，而不只作用于探索产生的知识、指令和程序。"在支持域内"这个限定词很关键，它和 9.2.5 末尾那句"不能保证在旧树上得分更高的策略能迁移到新任务"是同一种谨慎：回放只对历史实际覆盖过的分布有效，出了这个域，回放成绩就失去预测力。思考题第 7 题问的正是这件事。

在线与离线的分离还有一句要交代清楚：在线记录证据，离线生成并验证更新提案，再逐步发布、整理或回滚。这个闭环在结果可自动验证的任务上最可靠；对于目标模糊、反馈延迟的开放任务，人仍需参与问题定义和评价标准的制定。这里的「人参与」指的是定义问题与制定评价标准，跟 9.3.2 第二道边界讲的审批危险操作不在一个层面，它是 9.3.1 第四条对策的复述。整章的乐观，是有边界条件的乐观。

几组容易混的收在这里。本章在全书的位置是第一章发现循环中的实验与反馈环节，它同时又确实提出了一整套工程做法，这两件事并不矛盾，只是别把"位置"和"内容"混成一件事。小结明确说系统也可以进一步优化管理和生成产物的方法，但优先级在可归因、可验证、可回滚的局部修改这一边。可自动验证的任务上闭环最可靠，开放任务需要人参与问题定义与评价标准。历史既能被提炼为静态经验，也能在支持域内组成回放环境，这是两种不同的用途。

## 思考题

1. ★★ 一条经验文档由三次成功轨迹和一次失败轨迹支持。失败发生在较新的API 版本上。系统应如何判断这是经验被推翻，还是适用条件发生了变化？

思路提示：关键是先判断变量是什么。如果是 API 版本变化，合理的假设是"经验本身仍成立，但适用条件需要收窄或追加例外"，按 9.2.1 的要求，正式文档本来就该写清适用场景、例外条件、最近验证时间。可操作的做法是把失败轨迹与三条成功轨迹按环境版本分层对照，也就是 9.2.1 说的"某种策略在哪些环境版本中有效，在哪些前置条件下失效"，再在一个未参与提炼的迁移集上分别测试"原经验 + 版本条件"与"直接废弃经验"两种处理，看哪种在两类版本上都不退化。另外要考虑 9.1 的"证据不足时允许拒绝评分"：如果只有一条新版本轨迹，样本量可能还不足以支撑任何结论，可以先标记为待观察或需限定，不必立刻改写文档。

2. ★★ 客服Agent 的用户满意度上升，但规则违规率也上升。为什么不能把满意度作为单一学习信号？你会怎样设计护栏指标？

思路提示：这个病9.1 与章首导言都点明了，"用户满意不意味着合规"，9.1 还举例"口头承诺我们会在 7 天内退款"可能换来暂时的满意反馈。满意度是质量层的信号，甚至只是质量层的一个侧面，替代不了结果层与过程层。护栏指标可以直接取自表9-1，与满意度成对观测规则遵从、隐私边界、承诺—行动一致性、事实可靠性；再加 9.3 的五类长期结果，其中安全性那一项问的正是"规则、隐私和拒绝边界是否随进化漂移"，另外还有回退、泛化、Token 效率和长期工程质量。设计上有三个要点。

- 护栏指标必须可以被独立验证（政策库、动作轨迹、工具日志），不能由生成回复的同一个模型自评；
- 发布门槛应是"满意度不降且违规率不升"，两项分别设卡，加权求和会把违规换成满意度；
- 借鉴实验9-2 的做法，除主指标外记录与规则一一对应的行为指标，用来区分真实的机制改进和随机波动。

3. ★★★ 同一个"虚假承诺"问题可以通过Prompt、Harness 检查或参数训练缓解。你会依据哪些证据选择修改位置？

思路提示：回到图9-3 的首要判断，这个能力能否被事实、语言规则或程序完整表达。"不要承诺未兑现的操作"这类硬性业务规则是可以被完整表达的，所以首选不是参数（9.2.4 与思考题第 6 题都暗示参数难以保证硬性业务规则）。接下来在 Prompt 与 Harness 之间选，依据有四条。

- 确定性："承诺—行动一致性"可以由"回复与工具日志对照"来判定（表9-1），说明它可以确定解析、可以执行验证，按表9-2 更适合程序与 Harness；
- 是否可绕过：如果这是不可绕过的硬约束（9.2 的"关键合规则由服务端代码兜底"），就应由程序门控；
- 归因证据：按 9.2.3 的"变更契约"要求，看失败轨迹里是"模型知道规则但没遵守"（需要更硬的手段，比如 Harness 检查），还是"模型根本不知道这条规则"（补一条最小 Prompt 规则就够了）；
- 作用域：如果是某类企业政策特有的，就该放进 Skill，别塞进全局 Prompt（表9-2 的"作用范围可控"）。

另外注意 9.3.2 第三道边界：无论选哪一层，验证器与发布门槛都不能由提案方修改。

4. ★★★ Agent 能修改工具和验证器，却不应修改批准自身更新的可信根。你会如何划分这两部分的权限和代码边界？

思路提示：这里的判据是"真正的保证必须来自被修改者无法触及的那一层"（9.2.3 验证层）和"安全机制不可自我修改"（9.3.2 第三道）。可写进答案的划分依据是：业务资产可改（Prompt、Skill、知识库、工具），评判系统自身的那套不可改（验证器、测试用例、发布门槛、审计日志、稳定版本备份）。工程上可以借用 9.2.3 已有的机制。

- 权限上分离，进化流程只有"提 PR"的权限，没有合并与发布权限；
- 代码边界上，可信根所在的仓库或模块对提案 Agent 只读，安全测试与批准规则由独立于生成者的角色持有（实验9-6 与实验9-7 都要求"生成提案的 Agent 无权修改安全测试和批准规则"）；
- 审计上，所有变更走版本化 pull request 加独立 reviewer，高风险还要人工批准（9.3.2 第一道边界）；
- 可回滚上，保留稳定版本备份与快照。

题面本身还有个陷阱值得指出：如果说"Agent 能修改验证器"，得先看这个验证器是业务验证器（比如新增一个参数检查，9.2.3 允许）还是批准它自身更新的验证器（绝不允许），两者同名不同权。

5. ★★ 经验知识库不断增长后，检索错误和知识冲突会抵消学习收益。如何设计版本、时效和淘汰机制？

思路提示：可用的素材集中在 9.2.1 与 9.3.3。

- 版本：正式文档要写"版本与验证时间"（图9-4），新证据用于"修订、限定或淘汰"旧知识；9.3.3 的修剪要"保留来源和回滚版本"。
- 时效：文档里记"最近验证时间"；9.3.3 第 5 步把长期不用或被新证据推翻的能力标记为过期，或归档、删除，并且是标记、归档、删除三档渐进。
- 冲突处理：9.3.3 第 3 步明确要"合并重复内容，标记冲突与适用条件"；ACE（9.2.5）用"带稳定标识符的条目集合 + 增量更新 + 确定性合并去重"来避免多轮重写丢细节。
- 检索错误：9.2.1 的"三层数据"（不可变轨迹、单次分析、跨轨迹归纳文档）保证任何一条知识都能追到支持它的轨迹与反例，从而能精准修订；9.3.3 第 5 步还要求更新检索索引。
- 指标上要看表9-3 的"保留任务集增益"与 9.3 的"回退"，确认整理之后旧任务没有退化。

还可以补一句判断标准：只增不减的库必然腐化，这里列出的四种腐化形态就是它的四个出口。

6. ★★★ 参数学习擅长自然语言风格，却难以保证硬性业务规则。请为医疗客服设计一套参数、知识、Skill 和代码约束协同的持续进化方案。

思路提示：可以直接套图9-3 加表9-2 的分工，并参照这里两个复合例子（医疗影像 Agent"依靠参数识别病灶，用知识库提供最新指南，再用代码计算风险指标"；客服模型"自然语气来自后训练，具体企业政策由知识和 Skill 提供，关键合规由服务端代码兜底"）。协同方案的骨架大致如下。

- 参数：自然语气、同理心表达、去模板化的"AI 味"、跨任务的识别习惯，用 SFT、偏好训练或 RL 写入，数据来源是经过评价的生产轨迹（9.2.4：高质量示范走 SFT，明确偏好做成对数据，可靠环境奖励走 RL）。
- 知识：最新诊疗指南、药品说明、保险政策条款，写成带适用场景、例外条件、证据来源、最近验证时间的经验文档，按需检索。
- Skill：需要理解语境与例外的判断路径，例如"什么情况下必须建议转人工或急诊"这种带作用域的判断，放领域 Skill。
- 代码约束：不可绕过的硬边界，禁止给出确诊结论、禁止越权查询病历、必须确认高风险操作，由服务端代码或 Harness 门控，并配确认门禁提案（实验9-7）。

发布流程必须统一：四种载体的更新都先进待验证区（9.3.2 第二道边界），在边界集与保留集上验证（9.2.2），经过独立 reviewer 与高风险人工批准，再灰度、监控、可回滚（图9-5）；可信根（验证器、测试用例、发布门槛、审计日志、稳定版本备份）不由进化流程修改。方案里还应包含 9.3.3 的周期性整理：合并重复经验、把局部规则从全局 Prompt 挪到领域 Skill、删除被推翻的知识，以及从原始基座模型重新训练 LoRA 以防灾难性遗忘。

7. ★★★ 历史回放中的某个探索策略在所有旧发现树上得分最高，却在下一轮在线探索中退化。哪些支持域偏差、随机性和评价过拟合可能造成这种结果？你会怎样划分回放世界并设计发布门槛？

思路提示：机制层面的伏笔在 9.2.5 末尾已经给了，"回放器只揭示相应节点中已经记录的结果，不必再次运行底层 Agent 和评估器""只能重组历史中实际走过的分支""不能保证在旧树上得分更高的策略能迁移到新任务"，而 Dream-RSI 的"不更差"保证只是历史内的保证。可展开的偏差来源有四类。

- 支持域偏差：发现树只覆盖历史走过的分支，策略可能学到只在历史上出现过的状态分布里有效的启发式，比如过度偏好历史上高产的某类分支。
- 随机性：在线探索的执行含随机（采样、环境随机、评估噪声），回放返回的是已记录的结果，方差被剥离，因此离线得分更干净、更乐观。
- 评价过拟合：候选集合保留当前策略，比较只发生在已有历史上，反复在同一个模拟器池上搜索会逐渐拟合这批历史的噪声。
- 接口前提被破坏：在线与离线必须使用相同的决策接口，而且只逐步揭示已展开的子树，不能偷看未来；这两条任一条破了，都会直接导致离线与在线不一致。

设计建议上，划分回放世界时按支持域切分，保留一批从未用于策略搜索的发现树作为回放保留集，类比 9.3 的保留集与迁移集；发布门槛除了"历史内平均回放分数不更差"，还要加上在保留树上评估、在线 A/B 或灰度对照（含随机重复以估计方差），以及 9.3 的五类长期结果（回退、泛化、Token 效率、安全性、长期工程质量），并保留快速回滚路径。
