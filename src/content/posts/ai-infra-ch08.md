# 第 8 章 推理优化

> 本笔记对应原书《深入理解AI Infra：量化分析与系统设计》第 8 章 推理优化，原书印刷页码 317–353 页（PDF 第 327–363 页）。

## 本章地图

这一章要回答的问题是：同一个模型跑在同一张加速器上，单个用户每秒可能只收到几十个 token，所有用户合计每秒却能收到上千个 token，这中间的差额从哪来，又该怎么把它攥住。原因落在 decode 上，每读一遍权重只做很少的计算，速度受限于显存带宽，够不到峰值算力允许的水平，所以把多个请求合并计算、共用一次读取的权重，总吞吐就能成倍提高。而每条请求的上下文长度、排队时间和执行顺序，又决定了用户究竟何时能收到答案。本章讨论的就是如何组织这些请求，在给定时间内返回更多正确答案。

放进全书的位置看，第 6、7 章已经说明模型计算如何切分、加速器如何通信；本章以给定的加速器组合为基础，研究批处理、请求调度、内存管理、压缩、卸载和推测解码，比较不同运行配置的执行效率。第 9 章再往前一步，讨论计算和状态应该分布在哪里，如何组织完整副本、阶段服务池和算子分工，并据此确定服务规模。

小节之间的分工是这样铺开的。8.1 建立「请求生命周期 + 资源需求 + 服务指标」三件套，也就是 TTFT、ITL、总耗时、batch、吞吐这几个量；8.2 讲批处理与调度，包括权重复用、连续批处理、分块 prefill 和 token 预算；8.3 讲 KV 缓存的分配、复用与释放，涉及分页、前缀共享、引用计数、写时复制、缓存准入与淘汰；8.4 讲压缩与卸载，覆盖权重量化、KV 量化、权重卸载与预取；8.5 讲推测解码，草稿、验证、回退、接受率与草稿长度都在那里；8.6 把这些拼回服务现场，讨论到达率与排队、质量与 SLO 约束下的有效吞吐，并给一个配置选择的完整算例。

原书给的分析路线也顺着这条线走：先算实例能同时保存多少条请求的 KV 缓存，再算增大 batch 能为每个输出 token 减少多少权重读取，随后逐个引入分页、前缀共享、压缩、卸载和推测解码，看每一项省了什么、又添了什么，章末把这些分析收拢到同一个问题上，也就是 16 条长请求同时到达时该选哪种配置。

**章首先给出的算例条件（贯穿全章，原书印刷 p.317）**

- 硬件：示例中的 Qwen3-8B 实例运行在一张 **RTX PRO 6000 Blackwell 工作站版**显卡上，显存 96 GB，带宽 1792 GB/s，BF16 输入、FP32 累加的稠密峰值为 503.8 TFLOP/s，功耗上限 600 W。（原书脚注 1 注明规格出自附录 A 表 4，整理在硬件参数表的 `rtx-pro6000-blackwell-ws` 一行。）
- 例外：除在 Apple M2 Max 上运行的实验 8-7 外，本章实验都在这张卡上完成。
- 权重：每元素 2 字节的 BF16 浮点格式，约占 15.3 GiB。
- 显存划分：本实例分到 32 GiB 显存，为 KV 缓存及辅助缓冲区预留 12 GiB，其余约 4.7 GiB 用于激活、计算图重放（第 5.5 节）的固定缓冲以及其他执行工作区。
- 请求类型：短对话输入 2048 个 token，长上下文请求输入 8192 个 token，二者都输出 256 个 token；**长请求的前 6144 个 token 是相同的系统提示和工具定义**。
- 时限：每条请求从到达到返回完整正确答案，耗时不超过 7 秒。一条短请求在这张卡上单独运行约需 6.95 秒（见 8.1.1 节），该时限只留出约 **0.05 秒**的余量。

| 设计条件 | 短对话 | 长上下文 |
| --- | --- | --- |
| 输入长度 | 2048 token | 8192 token |
| 输出长度 | 256 token | 256 token |
| 公共前缀长度 | 0 | 6144 token |
| 完成时限 | 7 s | 7 s |

这几行数字可以自己验算一遍：`32 − 15.3 − 12 = 4.7`（GiB）。也就是说，这张卡在这个实例里的预算表是死的，权重 15.3 GiB、KV 12 GiB、激活与工作区 4.7 GiB，后面每一个方案（共享、压缩、卸载、推测）本质上都是在动这三格里的某一格。

整章最反直觉的一句话请先记住：推理的瓶颈常常不是算力，而是内存带宽。decode 阶段每生成 1 个 token，都要把（几乎）整份权重从显存里读一遍，但每条权重元素只参与极少的乘加。于是决定速度的是「读多少字节」，跟「能算多快」关系不大。这也解释了为什么后面所有优化都围着「减少每 token 的读取字节数」和「让一次读取服务更多行」打转。

读完这一章，你应该能做到七件事：说清一条请求从到达到结束的完整生命周期，并写出 TTFT、ITL、总耗时三者的关系；独立算出 Qwen3-8B 每个 token 的 KV 容量，以及给定内存下能装多少条请求；用「权重读取摊薄 + 本请求 KV 读取」两项解释批处理的收益与极限；说清分页、前缀共享、写时复制、引用计数各自解决什么问题；用 $V_h$ 公式判断一份前缀值不值得留在缓存里；用 $\Delta T/\Delta N < T/N$ 判断草稿该加长还是缩短；面对一批请求时，按「内存够不够、能不能按期、每个合格结果花多少 GPU 秒」三步选配置。

## 8.1 推理请求的执行过程与资源需求

本节先把三件基础事情讲清楚：一条请求是怎么被执行完的（8.1.1），执行它需要占多少内存（8.1.2），以及这些过程如何折算成可以设定时限的服务指标（8.1.3）。

### 8.1.1 执行资源与请求生命周期

先把两个词钉死。请求是一条有独立输入、输出和结束条件的推理工作；本章所说的 batch，指在同一次加速器执行中一起计算的一组输入 token；调度迭代则是调度器选择本轮工作、提交执行并处理结果的一个周期。请求可以跨越许多迭代，每一轮与它合批的其他请求可能并不相同。

生命周期的前半段是这样走的。请求到达后先进入等待队列，调度器把请求加入 batch、分配 KV 空间之后，模型才开始处理输入，也就是 prefill 阶段。由于输入 token 已经全部给定，模型可以同时计算多个 token，并保存各层的键和值。提示的最后一个 token 计算完成，模型就生成第一个输出 token。随后进入 decode 阶段：模型把刚生成的 token 当作下一次前向计算的输入，读取上下文 KV，再生成下一个 token。同一条请求必须依次完成这些步骤，不同请求的当前步骤则可以一起计算。单条请求只能逐个生成 token，实例仍然能靠合批把总吞吐提上去，道理就在这里。

把 batch 的定义读三遍都不算多。别把它读成「一批请求」，它的定义就是「一次加速器执行里一起算的一组 token」。这是理解连续批处理（8.2.2）的关键：一个请求在 prefill 阶段可能只占这一组 token 的一小部分，到 decode 阶段才占一个 token，因此「这一轮 batch 里有谁」每一轮都在变。调度迭代和 batch 属于两个层次，调度迭代是时间上的一格（选活、提交、收结果），batch 是这一格里塞进去的 token 集合。8.2.4 里的 token 预算约束的正是「一格里最多塞多少 token」。

prefill 能并行、decode 必须串行，原因在依赖关系上。prefill 的输入是已经给定的一整段提示，这些 token 之间没有数据依赖（它们只依赖前面的 token，而前面也已经在手里），所以能一次算完；decode 的下一个 token 依赖刚生成的这个 token，只能一步步来。这个区别决定了后面分块 prefill（8.2.3）的整个动机。

实验 8-1 给出了这条时间线的实测数字。在这张卡上单独运行一条 2K 输入的短请求，prefill 并返回首个 token 用时约 **0.096 秒**，此后平均每隔 26.5 ms 返回一个 token。假设这条请求先排队 0.1 秒，用户便在到达后的第 0.196 秒收到第一个 token。总共输出 256 个 token，需要经历 **255 个输出间隔**，因此请求总耗时为

$$T_{\text{request}} = 0.1 + 0.096 + 255 \times 0.0265 = 6.95\ \text{s}$$

这条请求能在 7 秒内完成。如果生成期间插入另一条短请求的 prefill，某个输出间隔就要多等约 0.096 秒，从 26.5 ms 延长到约 **123 ms**，总耗时增加到 **7.05 秒**。每个 token 的计算内容没有改变，仅仅调整执行顺序，就可能使请求超时。

这里藏着一个很容易滑过去的细节：255 而不是 256。prefill 结束时已经免费得到第一个输出 token 了，后续只需要再做 255 次「读一遍权重、再吐一个 token」的动作。8.2.1 里 KV 容量用 2048 + 255 = 2303 个 token 计算，也是同一个道理。本章凡是这种 ±1 的地方都算得很细，读的时候值得留意。

那 0.05 秒的余量意味着什么？意味着这张卡上「短请求」这条线本来就贴着时限跑。任何一次插入，别人的 prefill、更大的 batch、一次格式转换，都可能把它推过 7 秒。这就是为什么 8.6.1 的准入控制要先检查可用 KV 空间和距离截止时间还剩多久。

7.05 秒这个数字值得自己复算一遍（这一步是笔记补的复算，原书只给了结论）：

$$0.1 + 0.096 + 254 \times 0.0265 + 0.123 = 0.196 + 6.731 + 0.123 = 7.05\ \text{s}$$

注意这里被拉长的只有一个间隔，第 255 个间隔仍然正常，所以是 254 个 26.5 ms 加 1 个 123 ms。原文只说「某个输出间隔多等约 0.096 秒」，复算结果 26.5 + 96.5 ≈ 123 ms，与原文一致。

图 8-2 把这 6.95 秒画成一条时间线。首个 token 的返回时刻将时间线分成两段：此前的排队和输入处理决定用户何时看到响应，此后的 255 个间隔决定用户何时收到完整答案。后续所有调度优化，都可以理解为改变这条时间线上某一段的长度。

工程上的第一个坑就出在这里：调度要处理的不只是「把 GPU 塞满」，还要在「总吞吐」和「单条请求的时序」之间做取舍，后面 8.2.3 的分块 prefill、8.2.4 的 token 预算，都是在调这个取舍的旋钮。

请求完成之后，调度器不再为它安排计算，状态管理器则决定如何处理留下的 KV。该请求独有的 KV 随请求结束而释放，公共前缀的 KV 可以保留下来供后续请求复用，由缓存策略继续管理。8.3 节会进一步说明这些缓存何时共享、何时释放。

> 图 8-1（原文插图）：展示"请求保持身份，batch 每轮重新组成"。图中有两个迭代：迭代 0 里请求 A 与请求 B 各占一行执行位置；迭代 1 里请求 A 仍在，但 B 的位置被请求 C 接替。图注说明：A 跨越两个迭代继续执行，B 在第一轮结束，下一轮由 C 接替其执行位置（**每轮为一条活跃请求预留的一行计算**）；请求状态仍按各自身份保存。

> 图 8-2（原文插图）：一条输出 256 个 token 的请求的时间线。横轴是"从到达起计时（s）"，刻度 0 到 7；条形按实际时间比例绘制，依次是**排队**（0.1 s）、**prefill**（0.096 s）和 **decode**（后续 255 个输出间隔各 26.5 ms）。点标出首、末 token；7 秒处的虚线是完成时限。图注注明数据来自实验 8-1 的 batch 1 实测。

三组容易混的东西收个尾。prefill 处理「用户给的输入」，可以并行、算力受限；decode 生成「模型的输出」，必须串行、带宽受限，二者的耗时模型完全不同（8.6.3 会用 $r_P$ 与 $r_D$ 分别表示）。batch 与请求也不能画等号，一条请求在 prefill 阶段可以贡献几千个 token，在 decode 阶段只贡献 1 个，所以「batch size = 16」通常说的是「这一轮有 16 条请求在 decode」，而不是「这一轮只有 16 个 token」。排队时间与执行时间同样要分清，原文那 0.1 秒排队属于等待、不属于计算，但用户的 TTFT 里它照样算数，8.1.3 会把它形式化。

一条请求的一生是「排队 → prefill → 255 次 decode」，而所有调度优化都只是在改变这条时间线上某一段的长度：改的是顺序，不变的是每个 token 的计算内容。

### 8.1.2 权重、KV 与运行时缓冲的存储容量需求

要让多条请求沿各自的时间线向前执行，实例必须同时保存权重、请求状态和计算中间结果。本节的算例只用一张卡，所以只列出这张卡上的内存占用。多卡实例要按各卡保存的权重分片、KV 和缓冲区分别列式，某张卡上的空闲内存只有改变数据放置才能用于另一张卡的计算。

先把符号定下来：

| 符号 | 含义 |
| --- | --- |
| $M_w$ | 常驻权重的容量 |
| $M_{\mathrm{KV}}$ | 去除重复引用后的**物理** KV 块总容量（KV 按固定大小的块分配，多条请求共用的块只计一次） |
| $M_a$ | 激活与普通工作区的容量 |
| $M_u$ | 计算图重放等其他缓冲区的容量 |
| $C$ | 加速器可用容量 |

这些内存占用之和必须小于或等于加速器可用容量：

$$M_w + M_{\mathrm{KV}} + M_a + M_u \le C$$

这是一条容量约束式，它只回答「装得下」，不回答「跑得快」。装不下会发生什么？8.3.2 会给出两种后果：抢占（暂停一条请求、释放它的 KV、以后重算），或者干脆拒绝（准入控制，8.6.1）。

在这几项里，权重在请求到达前就已加载，KV 则随请求到达和生成不断增长。要算出实例能同时处理多少请求，先求每个 token 要保存多少 KV。Qwen3-8B 有 **36 层**，每层有 **8 个 KV 头**，每个头的维度为 **128**。每个 token 在每层都需要保存 K 和 V，BF16 每个元素占 2 bytes，因此每个 token 所需的 KV 容量为

$$k = 2 \times 36 \times 8 \times 128 \times 2 = 147\,456\ \text{bytes} = 144\ \text{KiB}$$

这个连乘的每一项都有来历（下面几步是笔记补的复算）：开头的 2 代表每个 token 每层要存两份东西，键 K 和值 V；36 是 Qwen3-8B 的层数，也就是 transformer block 数；8 是每层的 KV 头数，注意这里数的是 KV 头，跟注意力头总数是两回事，这是 GQA（分组查询注意力）的结果，多个查询头共享一组 K/V；128 是每个头的维度；最后的 2 bytes 是 BF16 每个元素的宽度。连乘得到 147,456 bytes，除以 1024 得 147,456 / 1024 = 144 KiB，与原文一致。

输入 2048 个 token 后，KV 占 288 MiB；输入 8192 个 token 后，KV 占 1152 MiB。把 $k$ 用在上下文长度上就能核对：$2048 \times 144\ \text{KiB} = 294\,912\ \text{KiB} = 288\ \text{MiB}$（$288 \times 1024 = 294\,912$），$8192 \times 144\ \text{KiB} = 1\,179\,648\ \text{KiB} = 1152\ \text{MiB}$。8192 是 2048 的 4 倍，KV 也就正好是 4 倍，这就是后面反复出现的「上下文翻四倍，KV 翻四倍」。

所有请求共用约 15.3 GiB 权重，但每增加一条上下文独立的长请求，就要增加 1.125 GiB KV（因为 $1152\ \text{MiB} = 1.125\ \text{GiB}$，即 $1152/1024$）。16 条长请求仅保存输入的 KV 就需要 **18 GiB**（$16 \times 1.125 = 18$），超过预留的 12 GiB。这是本章第一个「装不下」的结论，章末综合算例（8.6.3）的方案 A 正是死在这条上。

生成输出时 KV 还会继续增长：prefill 产生第一个输出 token，此后将前 255 个输出 token 依次送回模型，生成剩余的 255 个 token。短请求共计算 2048 + 255 = 2303 个 token，长请求共计算 8192 + 255 = 8447 个 token。若每块容纳 16 个 token，分别需要分配能容纳 **2304** 和 **8448** 个 token 的空间。这两个数是这样来的：请求实际需要保存 2048 + 255 = 2303 个 token 的 KV，之所以是 2303 而不是别的数，是因为最后一个输出 token 生成后请求就结束了，它本身不需要再进 KV，原文脚注 8 也强调「最后一个输出 token 在请求结束时尚未写入 KV」。但块是固定 16 个 token 一块，$\lceil 2303/16 \rceil = 144$ 块，$144 \times 16 = 2304$ 个 token 的容量。长请求同理，$8192 + 255 = 8447$，$\lceil 8447/16 \rceil = 528$ 块，$528 \times 16 = 8448$。

原文紧接着给出下面这张表，把两类请求的 KV 占用与 12 GiB 能容纳的请求数并列：

| 独立请求 | prefill 后 KV | 输出 256 个 token 后的 KV（分配量） | 12 GiB 可同时容纳的请求数 |
| --- | --- | --- | --- |
| 短对话 | 288 MiB | 324 MiB | 37 |
| 长上下文 | 1152 MiB | 1188 MiB | 10 |

（表格按原文语义还原：原文表头把「分配量」与「输出 256 个 token 后的 KV」分列排印，提取后串成一行，语义上「分配量」指的就是按最大输出长度预留的那一列。）

这张表要横着读：「prefill 后」是刚进场时的样子，「输出 256 个 token 后」才是真正要预留的样子。短请求从 288 MiB 涨到 324 MiB，多出来的部分是 255 个 token 的 KV，$255 \times 144\ \text{KiB} = 36\,720\ \text{KiB} = 35.86\ \text{MiB}$，再加上按 16 个 token 一块向上取整的边角，就是 324 MiB；长请求从 1152 MiB 涨到 1188 MiB。最后一列分别由 $\lfloor 12288/324 \rfloor$ 和 $\lfloor 12288/1188 \rfloor$ 得到，具体算下来 $12288 / 324 = 37.93$，向下取整 **37**；$12288 / 1188 = 10.34$，向下取整 **10**。

如果只按 prefill 结束时的 KV 大小计算，12 GiB 能容纳 42 条短请求（$12288 / 288 = 42.67$，向下取整 42）；但这些请求都生成 256 个输出 token 后，所需空间会增加到 13,608 MiB（$42 \times 324 = 13\,608$）。这就是「按 prefill 后大小算」与「按生成结束大小算」的差额。接收请求时就预留生成阶段所需的空间，可以避免执行到一半才发现内存不足。这条工程原则说白了就是：准入时按最坏情况（生成完毕）预留，不能按当前时刻的占用预留。否则会出现「接进来了但跑不完」的情况，那比直接拒绝更糟。

共享公共前缀可以进一步节省内存。长请求的前 6144 个 token 占 **864 MiB** KV（$6144 \times 144\ \text{KiB} = 864\ \text{MiB}$），其余输入占 288 MiB。如果 16 条请求各自保存前缀，就会保存 16 份相同的 KV；如果引用同一份 KV，节省的空间便可用于各自的后缀。一份前缀加 16 份后缀，和 16 份前缀加 16 份后缀的差别，就是这一节和 8.3.2 全部内容的经济学基础。第 8.3 节将说明具体的块映射方式，并计算生成结束时的总容量。

原文脚注 2（印刷 p.319）另外给出了一组字节数：固定模型在 RTX PRO 6000 上的批处理计算及 8K 对照。完整 BF16 权重为 **16,381,470,720 bytes**（约 15.26 GiB，即正文说的「约 15.3 GiB」），一步理想共享矩阵权重读取为 **15,136,811,008 bytes**（约 14.10 GiB）；embedding 按请求查行，内存中仍需保存完整的 embedding 矩阵。读取表先用精确字节计算，再舍入各项。两个字节数的差值就来自 embedding 矩阵：它按请求查行，一步里并不会把所有行都读一遍，但它必须一直在内存里。这个区别在后面所有「读取量」的计算里都会用到，算容量用大的那个，算读取用小的那个。

这一节的三个易混点摊开说。$M_{\mathrm{KV}}$ 算的是「物理」容量，跟「逻辑」容量是两回事，原文特意加了一句「去除重复引用后的物理 KV 块总容量……多条请求共用的块只计一次」，这就是 8.3 前缀共享的立足点：块表里可以有 416 条引用（8.3.2 的四分支例子），物理块却只有 131 个。「计算了多少 token」与「保存了多少 token 的 KV」也不是一回事，短请求计算 2303 个 token，按块分配却要预留 2304 个 token 的容量。容量不足属于「还没跑就注定」的问题，与运行时快慢无关，8.6.3 的综合算例第一步就是查这个不等式，方案 A 直接被排除。

每个 token 的 KV 是 144 KiB，长请求（8K 输入）一人就要 1.125 GiB 起。容量是本章第一个、也是最硬的约束。

### 8.1.3 从单请求时间到服务目标

接下来把 8.1.1 时间线的两段写成可以设定时限的指标。设请求到达时刻为 $t_a$，共输出 $G$ 个 token，第一个与最后一个 token 返回给用户的时刻分别为 $t_1$、$t_G$。于是首 token 时间（TTFT）为

$$\mathrm{TTFT} = t_1 - t_a$$

第 $j$ 个输出间隔为 $\mathrm{ITL}_j = t_{j+1} - t_j$。将首输出之前与之后的时间相加，完整请求时间为

$$T_{\text{request}} = \mathrm{TTFT} + \sum_{j=1}^{G-1} \mathrm{ITL}_j$$

三个指标的物理含义可以直接对应到图 8-2 的两段。TTFT 是「用户看到第一个字等了多久」，包含排队加 prefill，它对交互式体验最敏感。ITL（inter-token latency，输出间隔）是「吐字速度」，决定阅读是否流畅；原文提示调度算例还会比较最长输出间隔，因为一次卡顿比平均略慢更影响体验。$T_{\text{request}}$ 是「什么时候拿到完整答案」，直接对应 SLO 的 7 秒。

8.1.1 节的例子中，TTFT 为 0.196 秒，后续 255 个输出间隔合计 6.76 秒。较短的 TTFT 让用户尽早看到响应，均匀的输出间隔便于连续阅读，而总耗时决定完整答案何时可用。**SLO** 把这些要求量化为时限，章首算例要求总耗时不超过 7 秒，调度算例还会比较最长输出间隔。这些指标针对单条请求，实例整体的产出还取决于一次同时处理多少请求，即 batch size（下文简称 batch）。

吞吐表示单位时间内完成的工作量。实验 8-1 同时处理 16 条 2K 请求时，引擎每轮 decode 约 27.44 ms，每轮共输出 16 个 token，生成吞吐约为 $16 / 0.02744 \approx 583$ token/s；单条请求每 26.26 ms 输出一个 token 时，该值只有约 **38**。增加每轮输出数或缩短每轮时间，都能提高吞吐；用户实际等待多久，还取决于请求开始执行前的排队时间。

为什么吞吐要从「每轮」来算？因为一轮 decode 的所有请求共享同一次权重读取。16 条请求一轮 27.44 ms，就是 16 个 token 除以 27.44 ms，约 583 token/s；单条请求是 $1/0.02626 \approx 38$ token/s。差了约 **15 倍**，而这 15 倍几乎不要钱，这正是 8.2 节要展开的核心。另外注意「每轮输出 16 个 token」意味着 batch=16，而 27.44 ms 正好是 8.6.3 效率表里 batch 16 的实测一轮 decode 时间，数字是互相对得上的。读的时候可以把这些表格当成同一个实验的不同切面。

吞吐和延迟这两件事不要混。batch 从 1 增到 64，吞吐从约 37 涨到 1165 token/s（8.2.1 的 batch 扫描实验），但 TTFT 从约 96 ms 恶化到 3.29 秒。吞吐是服务方的产能，延迟是单个用户的体验，第 8.6.2 节的有效吞吐就是把两者（再加上正确性）合起来的结果。

衡量服务效果还要检查答案是否正确。固定输出长度，便于在相同工作量下比较执行时间；让模型自然停止，则可以观察答案正确率、回答长度和重试次数。第 8.6 节将计算单位时间内正确且按期完成的请求数，同时评价速度与质量。原文特意提了这两种口径的差别：前者是为了可比的执行时间测量（每条请求工作量相同），后者才能观察真实的质量（正确率、回答长度、重试次数），8.4.4 的质量实验就是按后者做的。这是很典型的 benchmark 设计取舍，值得记下来。

三个容易混的对照收个尾。TTFT 与 prefill 时间不同，TTFT = 排队 + prefill，prefill 只是其中一段，8.6.1 强调排队时间必须计入 TTFT。ITL 与一轮 decode 时间也不同，单请求时二者接近但不等（客户端看到的间隔还要加交付时间，见 8.6.3），多请求时一轮 decode 会同时产出多个 token，不能把一个 ITL 直接当成一轮的耗时。吞吐（token/s）与有效吞吐（req/s）更是两码事，前者是 token 计数，后者是正确且按期完成的请求数，8.6.2 会说明二者的差距正是「花在错误或迟到答案上的处理能力」。

TTFT 管「看见」，ITL 管「读得顺」，总耗时管「交卷」；而吞吐衡量的是「一轮里一共有多少个 token 分享了同一次权重读取」。

## 8.2 批处理与请求调度

本节回答「为什么合批能提速、能提多少、极限在哪」（8.2.1），接着讲固定 batch 与连续批处理的区别（8.2.2）、长输入为什么要分块（8.2.3），以及每轮能塞多少 token 如何决定执行时间（8.2.4）。

### 8.2.1 权重复用如何提高批处理效率

考虑矩阵乘法 $Y = XW$，输入矩阵 $X$ 有 $b$ 行。同一个权重元素参与所有行的计算，因此将多行一起处理，可以在读取一次权重后完成更多乘加。假设每个权重元素在批内只读取一次，每次乘加计为两次运算，权重元素占 $s_w$ bytes，只计权重读取时，算术强度为

$$I_{\text{weight}} \approx \frac{2b}{s_w}$$

这个推导很直白：读一次权重元素（$s_w$ 字节），它在 $b$ 行上各参与一次乘加，每次乘加记 2 FLOPs，于是得到 $2b$ FLOPs / $s_w$ bytes。BF16 的 $s_w = 2$，所以 $I_{\text{weight}} \approx b$，batch 就是算术强度。batch 16 意味着每读 1 字节能换来 16 次浮点运算，这远低于典型加速器的算力/带宽比（本卡 503.8 TFLOP/s ÷ 1792 GB/s ≈ 281 FLOP/byte），所以 decode 必然带宽受限。（这一比值是笔记补算的。）

把同时执行一步 decode 的请求数从 1 增至 16，每条请求都提供一个新 token，各 token 的特征向量分别占输入矩阵的一行；矩阵便从一行增至 16 行，同样一次权重读取对应的运算量增至原来的 16 倍。不同请求共用权重矩阵，但注意力计算仍要分别读取各自的上下文 KV。

LoRA 放宽了「共用同一份权重」这个前提。低秩适配（LoRA）用两个小矩阵的乘积表示权重的调整量，基础权重原样保留，于是不同任务可以共用一个基础模型，各自只附加一份小的 **adapter**（适配器，即附加在基础模型上的可训练参数模块）。对 Qwen3-8B 的 Q、V 投影取低秩维度 16、BF16，一套 adapter 占 **14.6 MiB**，100 套合计 **1.43 GiB**，远小于 **14.1 GiB** 的矩阵权重。

一批请求若来自不同 adapter，共用的就只剩基础权重这一部分。低秩计算要按 adapter 分组，每组的行数是本批中属于该 adapter 的请求数；adapter 分得越散，每组行数越少，这部分的权重复用就越差。因此，「一批里放几种 adapter」和「放多少条请求」是两个要分开决定的量。合批的前提是「同一份权重」，多 adapter 服务里基础权重可以共享，但每个 adapter 的低秩计算要按组做，组的行数等于本批中该 adapter 的请求数。所以放 8 种 adapter、每种 1 条，和放 1 种 adapter、8 条，代价完全不同。

容量上同样要分开算。100 套 adapter 占 1.43 GiB，而 100 条互不共享的 8K 上下文，KV 合计 **112.5 GiB**（$100 \times 1152\ \text{MiB} = 115\,200\ \text{MiB} = 112.5\ \text{GiB}$，这一步是笔记补算的）。能容纳多少套 adapter 由小矩阵决定，能同时服务多少条请求仍由 KV 决定；前者宽裕，不等于后者也宽裕。100 套 adapter 看起来随便放，但 100 条 8K 上下文根本放不下，参数够小并不等于服务能扩，KV 才是并发数的天花板。

设每轮只需读取一次的矩阵权重大小为 $D_w$，每条请求有 $L$ 个上下文 token，彼此不共享 KV，每个 token 的 KV 容量为 $k$。一轮的读取总量、以及平均每个输出 token 分摊的读取量分别为

$$D(b, L) = D_w + bLk, \qquad d(b, L) = \frac{D_w}{b} + Lk$$

在每个输出 token 的读取量中，第一项是分摊后的权重读取，第二项是本请求的上下文 KV 读取。Qwen3-8B 的 $D_w$ 约为 14.1 GiB，2K 上下文的 KV 为 0.28125 GiB。当 batch 从 1 增加到 16 时，每个输出 token 分摊的权重读取降至约 **0.88 GiB**；batch 增至 64 时，再降至约 0.22 GiB。此时，每个输出 token 读取的 KV 已经比权重更多。

$d(b,L) = D_w/b + Lk$ 是这一节的核心式子，可以把它当成「每个输出 token 要付的内存过路费」：第一项是摊到自己头上的权重读取，第二项是自己的 KV 读取。合批之所以有用，是因为第一项被 $b$ 除了；合批之所以有极限，是因为第二项不随 $b$ 变。逐符号看：$b$ 是本轮一起执行 decode 的请求数，也就是矩阵的行数；$D_w$ 是每轮只需读取一次的矩阵权重大小，这里用 14.1 GiB（即脚注里的 15,136,811,008 bytes），不含 embedding 那部分；$L$ 是每条请求的上下文 token 数；$k$ 是每个 token 的 KV 容量，等于 144 KiB 也就是 147,456 bytes；$Lk$ 是单条请求本步要读的 KV 字节数，注意它不带 $b$，因为有 $b$ 条请求就要读 $b$ 份各自的 KV，平摊到 $b$ 个输出 token 上正好是一份；$D_w/b$ 是分摊后的权重读取，单位都是字节每输出 token，除以带宽 $\beta$（GB/s）就变成秒。

图 8-3 展示了这一变化。横轴上相邻的刻度表示 batch 加倍，因此权重项每次减半；KV 项保持不变，两项之和逐渐接近 KV 对应的水平线。上下文为 2K 时，batch 从 1 增至 64，每个输出 token 的读取量从约 **14.38 GiB** 降至 **0.50 GiB**，约为原来的 **1/29**。上下文长度增至 8K 后，KV 容量变为原来的四倍，合批后的每个输出 token 仍需读取更多数据。

随着 batch 增加，分摊权重带来的节省逐渐减少。可以用权重读取量与 KV 读取量相等时的 batch 描述这一变化，使整批 KV 读取量达到或超过共享权重读取量的最小 batch 为

$$b_{\mathrm{KV}} = \left\lceil \frac{D_w}{Lk} \right\rceil$$

用未经四舍五入的权重字节数计算，2K 上下文的结果为 **51**，8K 上下文为 13。复算一遍：$15\,136\,811\,008 / 301\,989\,888 = 50.12 \to 51$；$15\,136\,811\,008 / 1\,207\,959\,552 = 12.53 \to 13$。上下文长度增至四倍后，KV 读取在小得多的 batch 下就超过了权重读取，交点 batch 几乎变成原来的四分之一（$51/4 ≈ 12.75 ≈ 13$），这正说明「KV 项线性增长、权重项被 $b$ 摊薄」的结构。

与此同时，更大的 batch 也需要更多内存：64 条 2K 请求的权重和一步 decode 后的 KV 合计约占 **35.7 GB**。这个数也能自己复算（笔记补算）：若用完整 BF16 权重字节数 $16\,381\,470\,720$ bytes = 16.38 GB，加上一步 decode 后 64 条请求的 KV，$64 \times 2049 \times 147\,456 = 19\,336\,790\,016$ bytes = 19.34 GB，合计 **35.72 GB**，与原文的 35.7 GB 一致。若只算每轮读取的理想共享权重 15.14 GB，则得到 34.47 GB，这正是 8.6.3 效率表里 batch 64 的「每轮读取的权重与 KV = 34.46 GB」。两个数字的差别，就是「内存里必须占着的 embedding」与「这一步实际读的权重」。合批减少了每个输出 token 的读取量，却增加了同时驻留的数据量。

再估算这些读取所需的时间。设每条请求的运算量为 $F$，加速器每秒完成 $P$ 次运算，内存带宽为 $\beta$。分别计算运算与读取所需的时间，再取较大者估计一轮执行时间：

$$T_{\text{step}} \approx \max\left( \frac{bF}{P},\ \frac{D_w + bLk}{\beta} \right)$$

令两项相等并整理，得到 $b(F/P - Lk/\beta) = D_w/\beta$。每增加一条请求，计算时间增加 $F/P$，KV 读取时间增加 $Lk/\beta$。前者更大时，计算时间会随着 batch 增长而追上读取时间；否则读取始终耗时更长。上面那个 51 和 13 比较的是两类数据的读取量，这个方程比较的是计算与内存带宽对执行时间的限制，两者不是一回事。若 $F/P > Lk/\beta$，那么随着 $b$ 增大，计算项会先追上并超过读取项，$T_{\text{step}}$ 就从带宽受限切换成算力受限。8.6.3 会说明这张卡在 2K、batch 1–64 的范围内始终是带宽受限（带宽效率 33%–65%）。

两项分别按峰值算力和峰值带宽计算，得到的是这张卡在这组条件下的物理下界。下界与实测一轮时间之比，就是第 1.2.2 节定义的 **MFU 和 MBU**；第 8.6.3 节将用逐轮记录校准这两个比值，再用于本章其余算例。

落实到请求时间上，还要看更大的 batch 是否延迟了首个 token，以及相邻输出之间是否等得更久。batch 扫描实验同时记录了这两项变化：Qwen3-8B 输入 2K、输出 256 个 token 时，batch 从 1 增至 64，总吞吐从约 37 增至 1165 token/s；但首个 token 的返回时间从约 96 ms 延后到 3.29 秒，平均输出间隔从约 27 增至 40 ms。每轮输出虽然更多，但处理更多输入、运行更大的 batch 也花了更多时间。该实验中每批请求同时提交，在线服务若额外等待 batch 集满，这段时间还要计入首 token 延迟。三组数的方向并不一致：吞吐 37 → 1165 token/s 是好事，TTFT 96 ms → 3.29 s 坏了 34 倍，输出间隔 27 → 40 ms 坏了 1.5 倍。而且这还是每批请求同时提交的理想情况，真实在线服务如果为了凑 batch 而等待，等待时间还要再加到 TTFT 上。所以最优 batch 取决于你的 SLO 容忍哪一个指标变差。

**练习 8-1 ・计算：batch 增大时的读取量变化**（印刷 p.322）

- **题干（照抄原文）**：取 $D_w = 15{,}136{,}811{,}008$ bytes、$k = 144$ KiB，计算 2K 与 8K 上下文在 batch 为 1、4、16、64 时每个输出 token 的读取量，并分别求两种上下文长度下，KV 读取量首次达到或超过分摊权重读取量的最小整数 batch。再用 12 GiB KV 可用内存、每块 16 个 token 和 256 输出，分别求两种上下文长度下最多可以接纳多少条独立请求。比较可容纳请求数的上限与两类读取量相等时的 batch，判断容量限制是否会先阻止 batch 继续增大。
- **参考解答（笔记补充，非原文）**：代入 $d(b,L) = D_w/b + Lk$。2K 时 $Lk = 2048 \times 147\,456 = 301\,989\,888$ bytes = 0.28125 GiB；8K 时 $Lk = 8192 \times 147\,456 = 1\,207\,959\,552$ bytes = 1.125 GiB。

| batch $b$ | 2K：$D_w/b$ | 2K：$d$（GiB） | 8K：$D_w/b$ | 8K：$d$（GiB） |
| --- | --- | --- | --- | --- |
| 1 | 14.098 GiB | 14.38 | 14.098 GiB | 15.22 |
| 4 | 3.525 GiB | 3.81 | 3.525 GiB | 4.65 |
| 16 | 0.881 GiB | 1.16 | 0.881 GiB | 2.01 |
| 64 | 0.220 GiB | 0.50 | 0.220 GiB | 1.35 |

  最小整数 batch：2K 为 $\lceil 15\,136\,811\,008 / 301\,989\,888 \rceil = \lceil 50.12 \rceil = 51$；8K 为 $\lceil 15\,136\,811\,008 / 1\,207\,959\,552 \rceil = \lceil 12.53 \rceil = 13$。
  容量上限：12 GiB = 12288 MiB。2K 请求按生成结束需 324 MiB 计，$\lfloor 12288/324 \rfloor = 37$ 条；8K 请求按 1188 MiB 计，$\lfloor 12288/1188 \rfloor = 10$ 条。
  **结论：两种上下文长度下都是容量先撞墙**。2K 最多 37 条 < 51，8K 最多 10 条 < 13，所以在到达 $b_{\mathrm{KV}}$ 之前 KV 空间就已经用尽，batch 无法继续增大。也就是说，「权重复用什么时候失效」这个理论交点，在这张卡的这个配置下根本达不到；真正决定并发数的是 KV 容量。
- **补充说明（笔记补充）**：练习要求的是「每条请求的读取量」，即 $d$；图 8-3 纵轴画的是「整批读取字节数除以本轮输出 token 数」，也就是同一个 $d$，因为一轮输出 $b$ 个 token，整批读取 $D_w + bLk$，相除即 $D_w/b + Lk$。

- 如果权重改由足够快的独立存储提供，读取耗时减少，批处理的收益就需要重新计算。沿用第 4 章的 8K 示例，设 $W$ 为整批读取的权重字节数，$B$ 为批内请求数，$K$ 为单请求本步读取的 KV 字节数。传统方案中，每个输出 token 分摊的 HBM 读取量为 $W/B + K$；权重由足够快的独立 ROM 提供时，HBM 每输出一个 token 仍需读取 $K$。图 8-4 中两条曲线的距离随 batch 增大而缩小，说明原先依靠 batch 摊薄权重读取的收益正在消失。这其实是个思想实验：如果权重不进 HBM（比如放在足够快的片上 ROM 或专用存储里），那么 $W/B$ 这项就消失了，HBM 每 token 只需读 $K$，此时合批对 HBM 带宽的意义就只剩「合并 KV 读取」，原来那套「batch 越大越省」的逻辑失效。

- 不过，batch 仍会影响矩阵计算对计算单元的利用率，以及 batch 内的 KV 读取量。将新的读取量代入上述时间模型，就能求出计算与 KV 读取的交点，再按首 token 延迟和输出间隔选择 batch。（原书脚注 6：本章条件比较的逐项复算与计算程序。）

> 图 8-4（原文插图）：每输出 token 分摊的 HBM 读取量。**固定 8K 上下文**，横轴为 batch size $B$（1 到 32），纵轴为每输出 token 的 HBM 读取（GB，0 到 20）。两条曲线：**传统 HBM 路径为 $W/B + K$**，随 $B$ 增大而下降，图中标出 $B=1$ 处约 **16.34 GB**、$B=16$ 处约 **2.15 GB**；**独立快速 ROM 路径为 $K$**，是一条不随 batch 变化的水平线。图注强调 $W$ 是整批读取的权重字节数、$B$ 是批内请求数、$K$ 是单请求本步读取的 KV 字节数。

这一节的易混点集中在四组对照上。$D_w$（14.1 GiB）与完整权重（15.3 GiB）不同，前者是一轮里真正要读的矩阵权重，后者是内存里必须常驻的全部权重（含 embedding 矩阵），算读取量用前者，算内存占用用后者。算术强度 $I_{\text{weight}}$ 与每输出 token 的读取量 $d$ 方向相反、用途也不同，前者是 FLOP/byte（越大越偏算力受限），后者是 bytes/token（越小越快）。$b$（batch，请求数）与 token 数在 decode 阶段一轮里数字相同（每条请求 1 个新 token），在 prefill 阶段则完全不同。至于「权重读取量相等」与「读取时间相等」，前者看字节，后者还要除以各自的有效带宽；$\beta$ 是同一个，所以本节这两个判据恰好一致，但概念上要分清。

合批的本质是「一次权重读取服务更多行」，收益按 $1/b$ 衰减、在 $b \approx D_w/(Lk)$ 处失效，而在这张卡上，KV 容量总比这个交点先到。

### 8.2.2 从固定 batch 到连续批处理

设想两条请求同时开始生成，一条需要八个 token，另一条只需要两个。短请求结束以后，长请求还要继续六步。如果一定要等这两条请求都结束才接下一组，短请求空出的执行位置就会一直闲置。固定批处理按整组接收、整组结束；连续批处理则在迭代边界重新安排活跃请求，空出位置后即可接纳新请求。

8.2.1 节的 batch 分析假定一轮中有 $b$ 条请求参与计算，实际行数会随请求结束和新请求加入而变化。图 8-1 中的执行位置对应这里的一行计算，与第 7 章记录通信请求的槽位是不同的资源。能否及时补入新请求，决定了下一轮还能有多少行参与计算。

新请求更早进入，也意味着其输入计算更早占用加速器。若新请求带有较长的提示，prefill 就会延长已有请求两次 decode 之间的等待。调度器因此要在两件事之间分配加速器时间：处理新请求的输入，以及让已有请求继续生成。（原书脚注 7：Orca 原文与分块计算和版本说明。）

**算例：连续批处理为何缩短总时间，却延长输出间隔？**（原文例题，印刷 p.323）

- **题干（照抄原文）**：最多同时运行两条请求。r0、r1 在零时刻到达，各输入 2048 个 token，分别输出 8、2 个 token；r2 在 20 ms 到达，输入 8192 个 token、输出 2 个 token；r3 在 30 ms 到达，输入 2048 个 token、输出 4 个 token。每轮耗时由实验 8-1 的 batch 1 实测拟合：**固定 26.22 ms，每个新 token 加 30.4 μs，每对满足因果关系的查询与键加 3 ns**。这组参数复现了 2K 请求单独运行时一轮 decode 的 26.26 ms 和 prefill 的 94.8 ms。固定部分是一轮中与 token 数无关的时间，包括读取整份权重（按 1792 GB/s 的峰值带宽约需 8.4 ms）和逐个提交 kernel 等开销。
- **原文给出的结果**：固定 batch 让 r2、r3 等待 r0、r1 整组结束，**总时间约 870 ms**。连续批处理在 r1 结束后接纳 r2，**总时间降到约 766 ms**；但 r0 的下一次输出要等 r2 的 8K prefill，**最大输出间隔从约 26 ms 增至 376 ms**。总时间节省约 12%，一次输出停顿却增长到原来的 14 倍。
- 进一步把 r2 的 prefill 分成每块 2048 个 token，每轮最多处理 4096 个 token（与实验 8-1 的设置相同），每次先让已有请求继续 decode，再执行一段输入。最大输出间隔降到约 **133 ms**，所有请求的总完成时间约为 **844 ms**。分块后，调度器能更频繁地安排已有请求继续生成，使输出间隔更均匀。
- 原书脚注 8（印刷 p.323）：固定 batch、连续批处理、分块策略。每轮耗时参数由实验 8-1 的逐轮记录拟合：batch 1 的 2K decode 一轮 26.26 ms、prefill 94.8 ms；**最后一个输出 token 在请求结束时尚未写入 KV**。

这个时间模型值得自己复算一遍（笔记补算）。单条 2K 请求的 prefill：固定 26.22 ms 加 $2048 \times 30.4\ \mu s = 62.26$ ms，再加因果配对数 $2048 \times 2049 / 2 = 2\,098\,176$ 对 $\times 3\ \text{ns} = 6.29$ ms，合计 **94.77 ms**，与原文的 94.8 ms 一致。单条 2K 请求的一步 decode：26.22 ms 加 $1 \times 30.4\ \mu s = 0.0304$ ms，加 $2048 \times 3\ \text{ns} = 0.0061$ ms，合计 **26.26 ms**，与原文一致。而 r2 的 8K prefill 独占一轮时：26.22 加 $8192 \times 30.4\ \mu s = 249.04$，加 $8192 \times 8193/2 = 33\,558\,528$ 对 $\times 3\ \text{ns} = 100.68$，合计 **375.94 ms ≈ 376 ms**，这正是最大输出间隔 376 ms 的来源：r0 本来 26 ms 就该吐下一个 token，结果要等这一整轮 8K prefill。

所以这个算例的精髓在于：连续批处理优化的是座位利用率（吞吐与总时间），代价是新来的大活儿会插队到已有请求的输出之间，表现为延迟抖动。总时间省了 12%（$870 \to 766$，$(870-766)/870 = 11.95\%$），但最长间隔涨了 14 倍（$376/26 \approx 14.5$，原文说约 14 倍）。分块（chunked prefill）就是把那个 376 ms 的大活儿切碎，夹在 decode 之间做。原文的做法是每轮先让已有请求 decode，再执行一段 prefill，于是 r0 最多只需要等一块 prefill 的时间，最长间隔从 376 ms 降到 133 ms。代价是总时间从 766 ms 涨回 844 ms，因为轮数变多、每轮的固定开销 26.22 ms 被多付了几次。这是一个非常典型的「延迟换一点点吞吐」的取舍，而且换得划算：133 ms 的抖动可以接受，376 ms 的抖动不行。

原文脚注 8 那句「最后一个输出 token 在请求结束时尚未写入 KV」还要再提一次，它就是 8.1.2 里 2303 而不是 2304 的原因，也解释了为什么容量按 `⌈(L+G−1)/p⌉` 而不是按 `L+G` 算。

> 图 8-5（原文插图）：固定 batch 的执行时间线。横轴为时间（ms，0 到 900），纵轴为四条请求 r0、r1、r2、r3。**蓝色为 prefill，绿色为 decode，三角形为到达时刻**；各色带的宽度为该次调度迭代的耗时，时间按 RTX PRO 6000 上的实测拟合计算。读图要点：r0、r1 先跑完一整组，r2、r3 的色带都排在很靠后的位置，说明它们白等了。

「执行位置」这个词值得钉死：它是一行计算，也就是这一轮矩阵乘法里的一行。它是 GPU 上的一个座位，属于计算资源，第 7 章的「槽位」则是通信资源。固定 batch 的问题是座位空了也不让别人坐：r1 只输出 2 个 token，早早就走了，但它留下的座位要一直空到 r0 也结束。连续批处理（continuous batching）也叫迭代级调度（iteration-level scheduling），它放弃了「请求组」这个粒度，改在每一个调度迭代的边界上重新决定下一轮谁来算，原文那句「空出位置后即可接纳新请求」就是这个意思。

三组边界要划清。固定 batch（static batching）与连续批处理（continuous batching）的区别不在 batch size 的大小，而在重组的时机：前者以一组请求为调度单位，整组进整组出；后者以一次迭代为单位，随时可以换人。总完成时间与最长输出间隔这两个指标经常反向运动，连续批处理让前者变好、后者变坏，分块 prefill 把后者拉回来、前者略微变差，不能只看一个。「执行位置」与「通信槽位」也要分开，前者是计算行（GPU 上的矩阵行），后者是第 7 章讲的网络资源，原文特意提醒这是两种不同的资源。

连续批处理在每次迭代的边界上重新安排活跃请求，用别人的空位换吞吐；分块 prefill 再把大块输入切碎夹进 decode 之间，把换来的抖动压回去。

### 8.2.3 长 prefill 对生成的干扰与分块执行

一次处理的 prefill 块越大，新请求所需的输入处理轮数越少；块越小，已有请求就越早得到下一次执行机会。调度器通常先安排正在 decode 的请求，再用本轮 token 上限中剩下的部分处理 prefill，这样长输入就分散到多个输出间隔里计算。

块长相同，注意力的工作量仍会随着上下文增长。设本块包含 $c$ 个新 token，已有上下文长度为 $h$。第一个新 token 关注 $h+1$ 个 token，第二个关注 $h+2$ 个，最后一个关注 $h+c$ 个。把这些配对逐项相加：

$$N_{\text{pair}} = (h+1) + (h+2) + \cdots + (h+c) = ch + \frac{c(c+1)}{2}$$

$ch$ 来自新 token 对旧上下文的访问，三角形项来自块内的因果注意力。取 $c = 512$，首块的 131,328 个配对全部来自块内；8K 输入的末块已有 **7680** 个上下文 token，配对数增至 **4,063,488**，约为首块的 31 倍。

这个公式值得记牢，它是「为什么长上下文越跑越慢」的数学表达：

$$N_{\text{pair}} = \underbrace{ch}_{\text{矩形：新 token 看旧上下文}} + \underbrace{\frac{c(c+1)}{2}}_{\text{三角形：块内因果注意力}}$$

其中 $c$ 是本块新处理的 token 数（块长），$h$ 是处理这一块之前已有的上下文长度。第一项 $ch$ 与上下文长度成正比，上下文翻倍这一项就翻倍；第二项只与块长有关，块长固定时它是常数。所以「块长一样，为什么末块更慢」的答案就是矩形变宽了，三角形没变。复算原文的两个数：$c = 512$、$h = 0$ 时 $N_{\text{pair}} = 0 + 512 \times 513/2 = 131\,328$；$h = 7680$ 时 $N_{\text{pair}} = 512 \times 7680 + 131\,328 = 3\,932\,160 + 131\,328 = 4\,063\,488$；比值 $4\,063\,488 / 131\,328 = 30.94 \approx 31$ 倍。

图 8-8 将配对数画成面积：每个新 token 都要访问全部旧上下文，形成左侧矩形；块内只能关注当前 token 位置及其之前的位置，形成右侧三角形。块长固定时，右侧三角形不变，左侧矩形随上下文增长而变宽。这就是末块需要更多注意力计算的原因。

模型还要执行投影和 FFN，这些对各 token 分别做特征变换的计算每块都处理 512 个新 token，工作量基本相同。在已有逐块记录中，末块的模型主干矩阵运算量比首块多约 32%，执行时间中位数从约 **25.3 ms** 增至 **35.1 ms**，增加约 **39%**。整块执行时间因此由两部分共同决定：一部分主要随新增 token 数变化，另一部分还随已有上下文长度增长。

这里有个重要限定：注意力配对数涨了 31 倍，整块执行时间却只涨了约 39%（25.3 → 35.1 ms），矩阵运算量只多约 32%。这说明在 8K 上下文、512 token 块这个尺度上，注意力还不是主导项，投影和 FFN 才是。这也是为什么 8.6.3 的算例里一轮 decode 的时间几乎不随 batch 和上下文变化。如果上下文长到几万 token，$ch$ 项就会翻盘，这是后文 8.4.2（用 FP8 压缩 KV 换取更长上下文）的动机。

上下文增长解释了同样大小的块为何越来越慢，缩小块长则会带来另一种开销。把一个 256 个 token 的块拆成两个 128 个 token 的块，调度机会增加一次，矩阵行数减半，每个小块都要使用同一份权重。以一层 FFN 的 **288 MiB** 权重为例，设两次执行分别从显存读取它们，这部分读取就从 **288 增至 576 MiB**。只要执行一次，就要把权重从显存读一遍，在 batch=1、块长 256 时一次执行读 288 MiB，拆成两个 128 的块就要读两遍，合计 576 MiB。也就是说，块越小，每 token 分摊的权重读取越高，这和 8.2.1 里 batch 越小越亏是同一个道理，只不过这里的「行数」是块长。

所以块长的选择是一个双侧约束。块太大，已有请求的输出间隔被拉长（图 8-6 的 376 ms）；块太小，权重读取被重复付（288 → 576 MiB），加上每轮的固定开销 26.22 ms 被多付。正确做法就是原文那句「选择能满足输出间隔要求的较大块」：先满足延迟约束，再在这一约束下尽量放大块长。这也是「prefill 优先还是 decode 优先」的答案，先 decode、再 prefill。因为 decode 是已经承诺、正在途中的输出，让它等会直接伤害用户已感知的体验；而新请求的输入晚一点开始，只影响它自己的 TTFT。

> 图 8-8（原文插图）：首次处理 4 个 token 时，**没有旧上下文**，只有新 token 之间的因果注意力配对，形成 $1 + 2 + 3 + 4 = 10$ 个绿色格（一个下三角形状）。**白格表示未来 token，不参与当前查询。** 图中标注"旧上下文 0 token + 新输入 4 token，旧上下文配对 0 + 块内配对 10 = 10"。

> 图 8-9（原文插图）：已有 8 个 token 的上下文时，4 个新 token 与旧上下文形成 $4 \times 8 = 32$ 个蓝色格（左侧矩形），块内仍为 10 个绿色格（右侧三角形）。**块长相同，总配对从 10 增至 42。** 图中标注"旧上下文 8 token + 新输入 4 token，旧上下文配对 32 + 块内配对 10 = 42"。

原文脚注 9、10、11（印刷 p.326）附了出处与测量条件：脚注 9 是逐块计算和封存测量，11 次请求、每次 16 块，首末块时间中位数 25.30、35.07 ms，CUDA event 区间包括完整模型路径和可能的主机间隙，不含外部 logits／采样，各块按原始顺序执行，输入 token 与内容逐块变化；脚注 10 是 OSDI 2025 调研、NanoFlow 正式稿与资源共享算例；脚注 11 是六请求实测及图执行取舍，实验在共享 GPU 上按固定顺序执行六条合成文本请求。

三个容易混的点。块长 $c$ 与上下文长度 $h$ 是两回事，前者是你这一轮新加进去多少，后者是之前积累了多少，$N_{\text{pair}}$ 的矩形项是二者的乘积，三角形项只跟 $c$ 有关。注意力配对数的增长与整块时间的增长也不能互相推断，前者可以涨 31 倍，后者只涨 39%，不要用一个算子的增长去推断整个模型的增长。分块 prefill 与连续批处理解决的也不是同一个问题，连续批处理处理的是座位空了没人坐，分块 prefill 处理的是新活儿太大、一次占太久，两者常一起用。

长 prefill 会卡住已有请求的输出，所以要分块；但块不能太小，因为每一块都要重新读一遍权重。块长的选择由「输出间隔」这个上限来定。

### 8.2.4 Token 预算、动态形状与执行时间

调度器通常设置每轮处理的 token 数量上限，称为 **token 预算**；8.2.2 节分块算例中每轮最多处理的 **4096 个 token** 就是一例。实际执行则要把这些 token 的特征向量组成矩阵，并选用 kernel 或预先捕获的 **CUDA Graph**（第 5.5.2 节）。实际执行的矩阵可能比本轮需要的更大，因此少处理一个 token，并不一定能少做一份计算。

例如，预先捕获 16 行和 32 行两种计算图，将 17 到 32 行的输入都填充到 32 行。把工作从 18 行减为 17 行，仍执行 32 行图；再从 17 行减为 16 行，才能使用较小的图。若为 17 行另捕获一个图，就省去 15 行填充，但捕获该图需要准备时间，重放所用的缓冲区还要长期占用内存。因此，选择 CUDA Graph 的预设形状时，也要计入第 8.1 节的运行时内存开销。

这个填充（padding）效应是一个非直觉但很重要的工程细节。你以为是 batch 从 17 降到 16 省了一份计算，其实真正的分界线在预设形状的档位上：

| 实际行数 | 使用哪个图 | 实际执行行数 | 浪费的填充行 |
| --- | --- | --- | --- |
| 16 | 16 行图 | 16 | 0 |
| 17 | 32 行图 | 32 | 15 |
| 18 | 32 行图 | 32 | 14 |
| 32 | 32 行图 | 32 | 0 |

也就是说，在 17–32 这个区间里，你把工作量从 32 减到 17，一步计算都没少做，只有跨过 16 这个档位才真正省下来。这也解释了 8.2.1 里 batch 扫描实验为什么会出现「batch 从 1 到 64，一轮 decode 只从 26.26 ms 涨到 29.63 ms」，因为一轮的时间里有很大一块是固定开销。反过来，为每个行数都捕获一个图看起来很美，代价却是捕获要时间（图捕获本身是一次一次真实执行的记录过程），每个图的缓冲区还要长期占显存。而显存正是本章最紧的资源（12 GiB 要给 KV），所以原文说「选择 CUDA Graph 的预设形状时，也要计入第 8.1 节的运行时内存开销」，它属于 $M_u$ 那一项。

执行形状决定一轮的耗时，token 上限则决定这一轮分给新请求多少工作。增加上限能让长输入更早处理完，但已有请求要等这轮结束才能继续输出。在六条请求的回放记录中，请求每隔 80 ms 到达，每轮 token 上限从 512 增至 8192，后到请求在引擎中排队的时间从约 **149 ms** 降到不足 **0.1 ms**，最长输出间隔却从约 32 增至 183 ms。上限越高，一轮完成的输入越多，新请求越早离开队列，已有请求等待下一次输出的时间也越长。

因此，可以分两步确定每轮处理多少 token。先根据允许的输出间隔确定一轮最多执行多久，再结合上下文长度和预设执行形状，换算为可处理的新 token 数。这相当于一个反解过程：先定时间，希望最长输出间隔不超过 $T_{\max}$（例如 50 ms），那么一轮最多能跑多久也就定了；再定 token 数，用 8.2.3 的每轮耗时模型（固定开销 + 新 token 数 × 每 token 成本 + 因果配对数 × 每对成本）反算出这一轮能塞多少新 token；还要注意上下文长度的影响，同样的时间预算下，上下文越长，每 token 的因果配对成本越高，能塞的新 token 越少。在相同时间内，上下文较长的请求能处理的新 token 较少，上下文较短的请求则可以使用更大的块。

这与调度的实际实现是对应的。调度器一般会在每轮开始时遍历运行队列，先给所有正在 decode 的请求各分 1 个 token（这部分几乎不能省），剩余预算按优先级分给排队中的 prefill 请求，并把长 prefill 切成若干块。确定执行安排后，还要为这些请求分配 KV 空间；下一节将讨论如何分配和复用这部分内存。

原文脚注 11（印刷 p.326）：六请求实测及图执行取舍。实验在共享 GPU 上按固定顺序执行六条合成文本请求。

**练习 8-2 ・核心・分析：由输出间隔限制确定 prefill 分块大小**（印刷 p.327）

- **题干（照抄原文）**：采用 8.2.2 节的四条请求与执行时间模型，手算 r0、r1 的初次 prefill 和下一步 decode 各需多久，再计算连续批处理接纳 r2 时该轮的耗时。解释最长输出间隔的来源。固定新块长度 $c = 512$，分别计算已有上下文长度 $h = 0$ 与 $h = 7680$ 时的注意力配对数。最后分析配套的六条请求回放记录，在「最长间隔小于 50 ms」和「后到请求尽快接纳」两种目标下分别选择每轮 token 上限，并指出哪一项耗时决定了选择。
- **参考解答（笔记补充，非原文）**：
  - **r0、r1 的初次 prefill**（两条一起算，batch 2）：固定 26.22 ms + 新 token $2 \times 2048 \times 30.4\ \mu s = 124.52$ ms + 因果配对 $2 \times 2\,098\,176 \times 3\ \text{ns} = 12.59$ ms，合计约 **163.3 ms**。
  - **下一步 decode**（两条各出 1 个 token）：26.22 ms + $2 \times 30.4\ \mu s = 0.061$ ms + $2 \times 2048 \times 3\ \text{ns} = 0.012$ ms，合计约 **26.29 ms**。
  - **连续批处理接纳 r2 的那一轮**（r2 的 8192 token prefill 与 r0/r1 的 decode 同轮）：26.22 + $8192 \times 30.4\ \mu s = 249.04$ + $8192 \times 8193/2 \times 3\ \text{ns} = 100.68$ + 两条 decode 的约 0.07 ms，合计约 **376.0 ms**，与原文「约 376 ms」一致。
  - **最长输出间隔的来源**：r1 只输出 2 个 token，因此它一结束，连续批处理就把空出的执行位置交给了 r2；而 r2 的 8192 个输入 token 全部塞在这一轮里，整轮耗时 376 ms。r0 本来每隔约 26 ms 就能吐一个 token，这一轮却要等满 376 ms，于是它的相邻两次输出之间就出现了约 376 ms 的间隔。
  - **注意力配对数**：$c = 512$、$h = 0$ 时 $N_{\text{pair}} = 0 + 512 \times 513/2 = 131\,328$；$h = 7680$ 时 $N_{\text{pair}} = 512 \times 7680 + 131\,328 = 4\,063\,488$。
  - **token 上限的选择**：回放记录显示，上限从 512 增至 8192 时排队时间从约 149 ms 降到不足 0.1 ms，但最长输出间隔从约 32 ms 涨到 183 ms。因此，若目标是「最长间隔小于 50 ms」，应取较小的 token 上限（约 512 量级），因为决定它的是每轮 prefill 摊到的 token 数，也就是一轮被拉长的时长；若目标是「后到请求尽快接纳」，应取较大的 token 上限（约 8192），因为决定它的是一轮能消化多少输入 token。「决定了选择的耗时」是同一个量，也就是一轮的持续时间，它既是对已有请求输出间隔的伤害，也是新请求离开队列的速度。

token 预算是本章最实用的一个旋钮。它的作用相当于把 8.2.3 的块长从「单条请求的块」升级为「整轮所有工作的总量」，一轮里既有 decode 的 token，也有 prefill 的 token，两者共用这个预算。

还有两个坑要提。token 预算是软上限，不是硬保证，因为 CUDA Graph 会填充，实际执行的行数可能远高于预算里的 token 数，真正的耗时要用执行形状来估，不能拿 token 数来估。另外，预算限制的是本轮一共多少个 token（decode 的 1×b 加上 prefill 的若干），batch 只是其中 decode 那部分的请求数；块长是「一条请求一次 prefill 切多大」，token 上限是「一整轮所有工作加起来多大」，后者是前者的容器。执行形状与实际工作量的行数也可能差很多，因为填充，少处理一个 token 并不等于少做一份计算。

每轮的 token 预算先由「能容忍多长的输出间隔」反推出来，再按上下文长度换算成块长；而真正的耗时由 CUDA Graph 的执行形状决定，跟实际 token 数关系不大。

## 8.3 KV 缓存的分配、复用与释放

8.1.2 只算了「总共需要多少 KV」，本节讲「这些 KV 具体怎么放、怎么共享、什么时候能还回来」。四小节分别是：分页分配（8.3.1）、分支共享与释放（8.3.2）、跨请求的前缀复用（8.3.3）、缓存的准入与淘汰（8.3.4）。

### 8.3.1 预留、碎片与分页分配

本节对应印刷 p.327–328。（节级页码正文原缺，这里按章末速查表的「出处」列补上。）

8.1 节按最大输出长度为每条请求预留空间，这样它才能一直生成下去。麻烦出在请求往往提前结束，预留空间的尾部就再也没人用过。另一种做法是随生成过程逐步扩展内存，可一旦要求空间必须连续，邻接区域被其他请求占着时就只剩两条路：搬移数据，或者等。

分页分配借的是活页册的思路。活页册的阅读顺序由页码决定，各页不必放在相邻位置，只要记得每一页在哪里；序列增长时，在任意空位放入新页并记录其位置，就不必为了连续排列而搬动整册内容。落到实现上，序列被切成固定大小的块。逻辑块按序列中的 token 位置编号，相当于页码；物理块是实际保存 KV 的内存区域；每条请求维护一张块表，记录逻辑块对应哪个物理块。序列长到需要新块时，引擎从空闲池分配一个物理块，并在块表里增加映射。注意力计算根据块表找到所需位置的 KV，所以物理块可以分散存放。这里讨论的范围是 KV 在内存中的分块寻址，多级存储之间的换入换出留到 8.3.4 节和 8.4.3 节。

设每块可保存 $p$ 个 token 的 KV，当前长度为 $L$，则需要 $\lceil L/p \rceil$ 个块。只有最后一块存在尾部未使用的 KV 槽位，浪费为

$$p\left\lceil \frac{L}{p} \right\rceil - L$$

最多浪费 $p-1$ 个 token 的 KV 空间。块越小，这一上限越低，块表项和分配次数也越多。

2023 年，伯克利等机构的研究者在 vLLM 中提出 PagedAttention，将操作系统分页管理的思路用于 KV 缓存，减少预留空间与内存碎片对服务并发的限制。PagedAttention 将这种映射带入注意力执行；FlashAttention 则在算子内部组织分块计算与中间结果，两者分别作用于状态分配和计算访存。

**算例：KV 分页分配能减少多少预留空间？**（原文例题，印刷 p.328）

题干照抄原文：设 A、B、C、D 当前长度分别为 9、13、5、15，每条最大允许 16 个 token。整段预留时，四条请求共预留可保存 64 个 token 的 KV 空间；取 $p = 4$，分页分别分配 12、16、8、16，共可保存 52 个 token 的 KV 空间。其中实际保存的 KV 仍对应 42 个 token，未用容量从 22 个 token 减到 10 个 token。

若 A、B 的前八个 token 相同，还可以让它们共用两个完整块，使总分配量进一步降至 44 个 token。分页减少了尚未使用的预留空间，共享消除了重复保存的上下文，两者节省的是不同部分的内存。

> 图 8-10（原文插图）：逻辑块按序排列、物理块分散存放。逻辑块 0、1、2 按顺序组成序列，块表分别是 $0 \to 2$、$1 \to 0$、$2 \to 3$。**四个物理块中，物理块 1 是空闲的**；注意力按块表恢复逻辑顺序。读图要点：物理块的编号顺序与逻辑顺序完全无关，这正是分页的自由度来源。

> 图 8-11（原文插图）：四条请求分别含 9、13、5、15 个 token，**每条预留可保存 16 个 token 的 KV 空间，共分配可保存 64 个 token 的 KV 空间**。图中蓝色为已用、灰色为预留未用——灰块连成很大一片，说明整段预留的浪费很严重。

> 图 8-12（原文插图）：按**每块保存 4 个 token**的 KV 分配空间，四条请求分别获得 12、16、8、16 个 token 的容量，**合计 52 个**。灰色（块尾未用容量）**由 22 个 token 减到 10 个 token**。注意现在灰色只剩每条第 5、9、13… 位置处的零碎块尾。

> 图 8-13（原文插图）：A、B 的**两个共同前缀块只保存一次**，各自的块表都指向它们；A、B 保留各自的私有尾块。四条请求实际分配的 KV 容量进一步降至 **44 个 token**。

整段预留浪费属于外部浪费：每个请求按最大输出预留一大段，请求提前结束后尾部就空着，而图 8-11 里那些灰色块永远也借不出去，因为它们已经被划给某条请求了。分页把浪费从「最多一整段」压到「每块最多 $p-1$ 个 token」。按公式验算一遍（这个数是我按 $\lceil L/p \rceil$ 自己算的，原书只给了结论）：A 长度 9、$p = 4$，$\lceil 9/4 \rceil = 3$ 块 = 12 个 token 的容量，浪费 3 个；B 长度 13，$\lceil 13/4 \rceil = 4$ 块 = 16，浪费 3 个；C 长度 5，$\lceil 5/4 \rceil = 2$ 块 = 8，浪费 3 个；D 长度 15，$\lceil 15/4 \rceil = 4$ 块 = 16，浪费 1 个。合计容量 $12+16+8+16 = 52$，浪费 $3+3+3+1 = 10$，与原文一致；整段预留则是 $4 \times 16 = 64$，浪费 $64 - 42 = 22$。这就是「从 22 减到 10」的来历。

前缀共享是另一种节省，别和分页混为一谈：分页省的是没被用上的预留，共享省的是被重复保存的内容。A、B 的前 8 个 token 相同，等价于 2 个完整块（$8/4 = 2$）。按物理块计，A 的 3 块中有 2 块与 B 共享，B 的 4 块中也有 2 块与 A 共享，所以物理块总数 $= 3 + 4 - 2 + 2(\text{C}) + 4(\text{D}) = 11$ 块 = 44 个 token，比 52 少 8 个 token，正好是两个共享块省下的量。（这笔复算是笔记补的。）

块大小 $p$ 的取舍很直白。$p$ 小，尾部浪费上限 $p-1$ 就小，但块表项多、分配和回收的次数也多；$p$ 大，浪费上限大，管理开销小。本章的算例几乎都取 $p = 16$，比如 8.1.2 里「每块容纳 16 个 token」、8.3.2 里「按每块 16 个 token 分配」，只有这个算例为了看清位数取了 $p = 4$。真实系统的块大小通常就是 16 或 32 个 token。

PagedAttention 与 FlashAttention 的分工，原文有一句话值得抄下来：「两者分别作用于状态分配和计算访存」。PagedAttention 管的是 KV 放在哪，把 KV 切成块、用块表间接寻址，让逻辑连续、物理离散，属于内存管理层的创新。FlashAttention 管的是注意力怎么算，在算子内部把 Q/K/V 分块、分块做 softmax 与累加，避免把整个注意力矩阵落到显存，属于计算访存层的创新。两者可以叠加：分页的 KV 块本来就只有 16 个 token，注意力算子按块去取即可，不需要物理连续。

还有一个容易被忽视的细节：「逐步扩展内存」这条路本身没错，错的是「必须连续」这个附加条件。内存必须连续时，扩展要么搬家（代价是拷贝，而且必须等加速器不再访问旧位置），要么等（代价是排队）。分页恰好把这个条件去掉了，于是浪费和扩展困难两个问题一起解决。

几个容易归错的概念放在一起看。逻辑块是「序列里第几个 token 段」，物理块是「显存里第几号块」，块表就是二者的映射表。分页消除的是外部碎片（大块空地无法利用），代价是引入内部碎片（每块尾部最多浪费 $p-1$ 个 token 的槽位）；在 LLM 场景里，后者远小于前者。分页分配与前缀共享的关系也没那么对称：分页是地址映射，共享是多张块表指向同一个物理块，没有分页就没有共享的物理基础，因为连续的段没法只共享一半。

> 🔎 检索确认：原文说"2023 年，伯克利等机构的研究者在 vLLM 中提出 PagedAttention"。外部资料显示，该工作即 *Efficient Memory Management for Large Language Model Serving with PagedAttention*（Woosuk Kwon 等，UC Berkeley），发表于 2023 年 SOSP，正是 vLLM 系统的论文。（来源：[Efficient Memory Management for Large Language Model Serving with PagedAttention | Proceedings of the 29th Symposium on Operating Systems Principles](https://dl.acm.org/doi/abs/10.1145/3600006.3613165)）

分页把 KV 从「一整段连续预留」改造成「按块寻址」，尾部浪费就从最多一整段降到每块最多 $p-1$ 个 token，前缀共享也顺带成了可能。

### 8.3.2 分支共享、写时复制与内存释放

本节对应印刷 p.328–331。（节级页码正文原缺，按章末速查表的「出处」列补上。）

前缀共享图里，B 与 A 引用相同的两个物理块。如果 A 先结束，这两个块仍要留给 B；如果 B 要修改其中的内容，又不能影响 A。要实现共享，就得先回答两件事：什么时候释放共享块，以及怎么避免不同请求互相覆盖数据。

每张块表中指向某个物理块的记录称为一个引用，共享块由多个块表引用，引用计数记录还有多少使用者需要它。每当一条请求获得引用，引用数加一；请求结束时释放引用。最后一个引用释放后，该块才能回到空闲池，此时还要确认加速器操作不再访问它。这样，同一份共同上下文既能服务多个分支，也能在其中一条分支结束后继续服务其余分支。

写入共享尾块需要取得独立副本。举个例子，可存 4 个 token 的块中已经写入三个共同 token 的 KV，两个分支接下来分别写入不同 token。写到原块的话，两条分支会争用块中的第四个 token。写时复制就是在修改共享内容之前取得私有副本的机制：先把这三个 token 复制一份，两条分支分别追加，此前已填满的只读块继续共享。随着分支增长，公共前缀保持一份，各分支分别保存自己新增的后缀。

在已有的四分支实验中，公共前缀占 95 块，每条分支另有 9 个私有块。四张块表共有 $4(95 + 9) = 416$ 次引用，实际物理块数却只有

$$95 + 4 \times 9 = 131$$

独立保存需要 416 块，共享后减少约 69%。这项节省来自对公共前缀的去重，36 个私有尾块仍随分支数增长。

原书脚注 12（印刷 p.329）记的是分页、取消与抢占、四分支共享、冷分支对照：共享分支的输出相同；冷、热分支具有相同的块峰值，但 prefill 量不同。

> 图 8-14（原文插图）：引用计数的生命周期。**A、B 使用共同块时引用为 2；A 结束、B 继续使用时引用降到 1；B 结束且加速器已不再访问时引用为 0**，块才能回到空闲池。

> 图 8-15（原文插图）：写时复制。**共享尾块是 [a, b, c, 空]**（可存 4 个 token）；分支 A 想追加 x 得到 [a, b, c, x]，分支 B 想追加 y 得到 [a, b, c, y]。**写入分歧前，各自取得尾块副本**；此前已填满的块继续共享。

数据流走一遍，这是本节最要紧的机制。先建分支：B 复用 A 的前缀时，B 的块表里指向 A 已有的那两个物理块，于是这两个块的引用计数从 1 变 2。共享期间它们是只读的，A、B 各自 decode 时都会读公共前缀块，但不会写，因为这些 token 的 KV 早就算好了，不会再变。等到追加阶段，A、B 开始生成不同的 token，各自需要往当前尾块写；如果尾块还有空位且被共享，就必须先复制一份（写时复制，Copy-on-Write），A 拿到一份私有副本写 x，B 拿到另一份写 y，而已经写满的块（那三个 token 所在的块）保持只读、继续共享。等到结束：A 结束，释放它持有的所有引用，公共块引用数 2→1 不回收，A 的私有块引用数 1→0 回收，B 继续；B 结束时公共块引用数 1→0，回收。

引用为 0 还不够，原文强调还要确认「加速器操作不再访问它」。因为调度是异步的：主机端已经把这一轮 kernel 提交给 GPU，而 GPU 可能还在读这块显存。这时立刻把块分给别人，新请求写入的数据就会覆盖旧请求正在读的数据，结果是「答案错得莫名其妙」。后面取消实验里那 1.6 ms 与 31 ms 的差别，就是这件事的实测证据。

四分支那笔账再复算一次（笔记补充计算）：$4 \times (95+9) = 416$ 条引用；物理块 $95 + 4 \times 9 = 95 + 36 = 131$ 个；省下 $416 - 131 = 285$ 块，比例 $285/416 = 68.5\% \approx 69\%$。36 个私有尾块仍随分支数增长这件事要留意，共享只能去掉公共部分，每个分支自己的后缀省不掉。这与 8.3.1 算例里「分页省预留、共享省重复」是同一个道理。

把这段机制和 8.1.2 的容量公式接起来就通了：$M_{\mathrm{KV}}$ 之所以定义成「去除重复引用后的物理 KV 块总容量」，正是因为物理块数和引用条数可以差好几倍。做容量规划时必须按 131 算，不能按 416 算。

写时复制的粒度是块，不是 token。只要块里有一个 token 要分叉，整个块就要复制，所以 $p$ 越大，写时复制的代价越大（要复制 $p$ 个 token 的 KV）；$p$ 越小，复制越便宜但块表管理越繁琐。这又是一次块大小的权衡。

服务系统知道哪些 token 属于共同前缀、哪些 token 会在分支后独立写入，因此可以把模型的复用关系落实为物理块共享。块表负责地址映射，前缀关系决定共享范围，分支写入时才创建私有副本。原来按整条请求独立预留的空间，由此改为按实际产生与复用的状态分配。

公共前缀共享后的整批 KV 容量可以算得很细。16 条长请求共享前 6144 个输入 token，其 KV 共占 864 MiB。每条请求的私有部分包含 $8192 - 6144 + 255 = 2303$ 个 token，按每块 16 个 token 分配，需要容纳 2304 个 token，即 324 MiB。于是整组请求生成完毕时所需的 KV 空间为

$$M_{\mathrm{KV}} = 864 + 16 \times 324 = 6048\ \text{MiB}$$

这组请求原来需要 $16 \times 1188 = 19008$ MiB，共享后约为 5.91 GiB，可以放入预留的 12 GiB 内存。一般地，$b$ 条同类长请求占 $864 + 324b$ MiB，容量上限因此从 10 条独立请求增加到 35 条共享请求。

复算这串数字（笔记补充计算）：前缀 $6144 \times 144\ \text{KiB} = 864\ \text{MiB}$；每条私有部分 $8192 - 6144 + 255 = 2303$ 个 token，向上取整到 16 的倍数 = 2304，容量 $2304 \times 144\ \text{KiB} = 324\ \text{MiB}$；合计 $864 + 16 \times 324 = 864 + 5184 = 6048$ MiB $= 5.90625$ GiB ≈ 5.91 GiB。对照不共享的 19,008 MiB ≈ 18.56 GiB，共享后只剩 5.91 GiB，省了约 68%。容量上限也一样：$864 + 324b \le 12288 \Rightarrow b \le (12288-864)/324 = 11424/324 = 35.26 \Rightarrow b_{\max} = 35$，同样的 12 GiB，共享前缀后能容纳的请求数变成 3.5 倍。

释放内存需要同时满足两个条件：没有使用者继续持有引用，已提交的加速器操作也不再访问该块。用户取消请求后，调度器停止安排新计算，等待已提交的操作完成，随后释放私有块。一次观察中，取消调用约 1.6 ms 就返回了，而对应的 104 个块直到约 31 ms 才释放。后续请求在释放之后使用这些块，便不会覆盖旧请求仍在读取的数据。

除了请求结束或取消后的正常释放，内存不足时，引擎还可以抢占一条请求：暂停该请求并释放其 KV，之后再根据已保存的输入和输出重新计算状态。同一组实验使用 1 GiB KV 池时发生了一次抢占，比正常执行多调度 1805 个 token；使用 2 GiB 池时则没有这次重算。抢占暂时把内存让给其他请求，代价是恢复执行时需要重复计算。

原书脚注 13（印刷 p.331）注明取消观察来自状态实验，记录值约 1.55 ms 与 31.41 ms，计时包含观察器开销；脚注 14 与脚注 12 是同一组对照。

> 图 8-16（原文插图）：取消请求的执行流程。方框依次是：**收到取消 → 停止后续迭代 → 等待已提交加速器操作完成 → 释放私有块 → 更新共享引用**。图注强调：**取消接口返回只表示已接收取消请求**；已提交的加速器操作完成后，再释放私有块和相关引用；观测中的 **1.6 ms 与 31 ms 对应不同事件**（前者是接口返回，后者是块真正释放）。

取消那两个时间一定要分清。1.6 ms 是接口返回，意思是「我知道你要取消了，不再给它排新活儿」；31 ms 是块真正回到空闲池，因为已经提交给 GPU 的 kernel 还在跑，必须等它读完。这跟实现得快慢无关，是正确性上的硬要求。工程上这意味着取消并不释放空间，只是停止消耗，空间要过一会才回来，所以准入控制（8.6.1）不能把「已取消」当成「已释放」。

抢占是最后手段，机制其实很优雅：请求的输入和已生成的输出 token 都在手里，只要把它们重新喂进去就能恢复状态。抢占不需要保存额外数据，代价纯粹是重算，那个「多调度 1805 个 token」就是重算的代价。这也解释了为什么池子越小抢占越多，1 GiB 触发、2 GiB 不触发。

几个容易混的点。引用计数与占用标记不是一回事：占用标记只能回答「这块有没有人用」，引用计数才能回答「还有几个人要用」；共享场景下必须有引用计数，否则 A 一结束就把公共块回收，B 就崩了。写时复制也容易被理解成「复制整个前缀」，其实它只在真正要写的时候复制要写的那一块，后者则会在建分支时就复制全部前缀；对多分支共享长前缀的场景，前者省几个数量级的拷贝。释放引用与回收物理块同样要分开：前者是逻辑动作（块表摘掉这一项），后者是物理动作（块回到空闲池），中间还夹着一个「加速器不再访问」的确认。

共享块的正确性靠两个机制撑着：引用计数决定什么时候能回收，写时复制决定谁写谁先拷一份，而回收还必须等到加速器真正读完。

**练习 8-3 ・计算：KV 块大小与前缀共享如何影响容量**（印刷 p.331）

题干照抄原文：将四条长度 9、13、5、15 的序列分别按 2、4、8 个 token 分页，计算四条序列各自尾块中未使用的 KV 槽位数，并分别求出未使用 KV 槽位和块表项的总数。再按章首算例计算 8、16、32 条长请求在独立与共享状态下的完整容量。保持每条请求的总长度不变，将一个原本私有的完整块改为公共前缀的一部分，求 $b$ 条请求合计可以少分配多少物理块。

下面是笔记补的解答，不是原文。长度为 $L$、块大小为 $p$ 时，尾块未用槽位为 $p\lceil L/p \rceil - L$。

| $p$ | A(9) | B(13) | C(5) | D(15) | 未用槽位合计 | 块表项合计 |
| --- | --- | --- | --- | --- | --- | --- |
| 2 | 1 | 1 | 1 | 1 | 4 | $\lceil 9/2 \rceil + \lceil 13/2 \rceil + \lceil 5/2 \rceil + \lceil 15/2 \rceil = 5+7+3+8 = 23$ |
| 4 | 3 | 3 | 3 | 1 | 10 | $3+4+2+4 = 13$ |
| 8 | 7 | 3 | 3 | 1 | 14 | $2+2+1+2 = 7$ |

8、16、32 条长请求的容量：每条长请求生成完毕需 1188 MiB（按 $p = 16$ 向上取整到 8448 个 token）。独立状态下为 $8 \times 1188 = 9504$ MiB、$16 \times 1188 = 19008$ MiB、$32 \times 1188 = 38016$ MiB；共享状态下为 $864 + 324b$ MiB，即 $864+2592 = 3456$ MiB、$864+5184 = 6048$ MiB、$864+10368 = 11232$ MiB。最后一个问题：若把一条请求的某个私有完整块改成公共前缀的一部分（该块被 $b$ 条请求共享），则这 $b$ 条请求合计少分配 $b - 1$ 个物理块，原来要 $b$ 份副本，现在只留 1 份。（这步推导是笔记补的。）

### 8.3.3 对话与智能体的前缀复用

本节对应印刷 p.332–334。（节级页码正文原缺，按章末速查表的「出处」列补上。）

8.3.2 节算的是同时运行的请求如何共用物理块。这种共享还能跨越请求的结束时刻：旧请求留下的前缀 KV，可以让后来的请求免去同一段输入的计算。如果后续请求的前缀完全相同，并使用相同的模型、位置编码规则、adapter 和状态格式，就能直接使用缓存中的 KV，从前缀末端继续 prefill。章首算例的公共前缀有 6144 个 token，命中缓存后，每条长请求只需处理剩余 2048 个输入 token，再开始生成。

这种复用沿前缀连续发生。假设两条提示前 100 个 token 相同，第 101 个不同，那么即使后面的文本又相同，它们从第 101 个 token 起所依赖的上下文已经不同。把动态时间戳放在提示最前面，会使后面较长的共同工具定义失去复用机会；把稳定的系统提示与工具定义放在前面，再追加本轮变化，就能保留较长的公共前缀。（原书脚注 15 注明这是上下文工程案例。）

前缀树把这种结构直接表达出来：从根到分叉点是共同上下文，从分叉点到叶子是私有后缀。图 8-17 里前四轮输入一上来就共享 206 个 token，后三轮又沿同一条路径延伸。树上的边按新增 token 数标记，叶子给出完整输入长度。图 8-18 描述的则是每轮输入与上一轮的逐 token 重合程度：每轮在末尾追加内容，可以保留已有的公共前缀，但上下文越长，KV 占用和后续读取量也越大。

混合注意力模型还有一个额外问题，就是如何确定可恢复的前缀位置。全注意力保留逐 token KV，递推模型通常只保留当前状态。设文本匹配到第 10,752 个 token，递推快照分别保存在第 4096 和第 8192 个 token，系统从 8192 恢复，再计算到 10,752，重算 2560 个 token。增加快照可以减少重算的 token 数，但要保存更多状态。以第 2 章的 KDA 为例，一种实现将层内张量分到八张卡（TP=8），此时每卡每份快照约 53.6 MiB，保存 2 份约 107 MiB，保存 32 份约 1714 MiB。快照保存得越密，恢复时需要重算的 token 就越少，保留的状态也越多。

上下文编排还可以主动改变复用机会。假设已有 8K token 的上下文，下一轮追加 1K 工具结果，最多可复用原来的 8K 前缀，只需处理新增部分；如果改写最前面的指令，后面的内容即使文字相同也不能继续复用。另一种方案是把历史总结为 2K，再追加 1K。摘要替换原始历史后，后续计算使用更短的上下文，但多出一次总结与重新处理的开销。所以组织上下文时，内存占用、重算时间和后续读取量要一起看。

模型侧的前缀复用还涉及更细的状态区分。DeepSeek V4.1 在复用前缀时，对两类局部状态分别处理。第 2 章介绍的 CED 结构包含因果编码器和解码器，两者各有 SWA 的局部状态：编码器 SWA 可以在主机 DRAM 池中短期保留，供下一轮沿已有前缀继续处理新输入；解码器 SWA 只为本轮后续生成使用，论文中的部署不把它作为前缀缓存保存。全局 KV 则进入可较长期复用的缓存。因此，生成期间驻留的 40 层 SWA 与跨轮次保留的前缀缓存，需要分别计算容量。

这两类状态是否命中，决定了下一轮续算时编码器要恢复多少前缀。假设工具返回后，恢复所需的 token 或输入表示仍可取得，模型版本、token 位置索引与输入保持一致，那么有三种情形。全局 KV 和编码器 SWA 都命中时，编码器直接处理追加输入。仅全局 KV 命中时，编码器重放已缓存前缀的最近最多 128 个 token，并与未缓存后缀一起执行，重放段重建编码器 SWA，继续使用既有全局 KV，新增后缀产生新的全局 KV 和 SWA。全局 KV 也未命中时，则重算缺失前缀。

随后，每次 prefill 都有共同的一步：取完整提示末尾最多 128 个 token 的编码器输出，经过 20 层解码器，近似构建解码器 SWA，为第一步 decode 准备局部状态。因此，编码器缓存全部命中时，可以省去编码器的前缀恢复，但解码器仍需执行窗口重放。

短窗口重放得到的是近似恢复的状态，误差来自更早的局部依赖被截断。每层虽然只访问最近 128 个 token，多层叠加后，局部状态仍可通过前一层间接依赖更早的输入，从窗口边界重新执行，就会改变这部分历史信息。技术报告第 3.2.2 节因此将编码器重建的状态定义为近似状态；这一状态又参与后续计算，使新增后缀的全局 KV 和 SWA 随恢复起点变化。

两类状态的区分最终体现在缓存容量上：在 DeepSeek V4 技术报告采用的工作负载与缓存策略下，SWA 约占长期缓存的一半。V4.1 将这部分移出持久化缓存，再将全局 KV 压到约四分之一，长期存储量因此约为原来的

$$\frac{1}{2} \times \frac{1}{4} = \frac{1}{8}$$

短期保留的编码器 SWA 放在 DRAM 中，解码器 SWA 则在本轮生成时驻留加速器。缓存按使用时段分层保存，进一步降低了长期容量需求。

前缀复用是跨请求的缓存，和 8.3.2 的同批次内共享不是一回事：前者共享的是旧请求留下的、以后可能有用的 KV，属于时间维度的复用；后者共享的是此刻多条请求共同的 KV，属于空间维度的复用。两者都基于同一套分页、块表与引用计数机制。

复用的四个前提值得背下来：前缀完全相同、相同模型、相同位置编码规则、相同 adapter 和状态格式。位置编码为什么也要相同？因为 KV 是在该位置上算出来的，位置不同，同样的 token 也会得到不同的 K/V。这也解释了为什么把动态时间戳放在最前面是灾难：它让后面所有 token 的位置都发生偏移，公共部分从第 1 个 token 就分叉了。

前缀的连续性是最实用的一条结论：复用只能沿着从头开始一模一样的部分延伸，一旦分叉，后面即使文本相同也不能复用。所以上下文工程的第一原则是把稳定内容放前面、把变化内容放后面。这是第 2 章的内容，本章给出的是它在缓存层面的收益。

快照那笔账复算一遍（笔记补充计算）：匹配到 10,752、最近快照在 8,192，则 $10752 - 8192 = 2560$ 个 token 需要重算 ✓。快照容量 $2 \times 53.6 = 107.2 \approx 107$ MiB ✓；$32 \times 53.6 = 1715.2 \approx 1714$ MiB ✓（原文按未舍入的精确值算）。这就是快照密度的取舍曲线：密度翻倍，重算量减半，状态存储也按比例增长。

DeepSeek V4.1 那一段的工程含义是状态要分层管理。编码器 SWA 短期、放 DRAM，便宜但慢，可以复用；解码器 SWA 只服务本轮生成、驻留加速器，快但贵，不持久化；全局 KV 长期，进持久化缓存。这样分层的直接效果就是最后那个 $\frac{1}{2} \times \frac{1}{4} = \frac{1}{8}$，长期缓存容量降到原来的八分之一。原文的说法是「缓存按使用时段分层保存，进一步降低了长期容量需求」。

近似状态这个概念值得单独拎出来说。从窗口边界重放只覆盖最近 128 个 token，而多层叠加后，局部状态其实会间接依赖更早的输入，所以重放恢复出来的状态和原始状态并不完全相等，这个差异还会传播到后面生成的 KV 上。原文用「使新增后缀的全局 KV 和 SWA 随恢复起点变化」来描述这个传播。工程含义是：缓存命中换来的速度里可能含有一点数值差异，这也与 8.4.4 节的质量实验呼应，不同的数值处理会改变答对的题目。

几个对照关系收在这里。前缀共享（同批次）与前缀缓存（跨请求），一个是同时活着的人共用，一个是前人留给后人的，机制相同，触发时机不同。判断能否复用，光看字符串相等不够，要求从第 0 个 token 起逐 token 相同，再加上模型、位置编码、adapter、状态格式一致。编码器 SWA 与解码器 SWA 名字相同，生命周期却完全不同，前者可跨轮保留在 DRAM，后者只在本轮用、驻留加速器。完整状态与近似状态的差别在于，全注意力逐 token 保存 KV 可以精确恢复，递推或局部窗口模型只能从快照重放，得到的是近似状态。

前缀复用只能从头顺着来：稳定内容放前面、变化内容追加在后面，就能一直复用；一旦在开头改动，后面全废。而混合注意力模型还要额外决定从哪个快照恢复、愿意重算多少 token。

### 8.3.4 缓存准入、淘汰、换出与重计算

本节对应印刷 p.335。（节级页码正文原缺，按章末速查表的「出处」列补上。）

请求结束后保留前缀，是为了将来再次使用时省去重算。设前缀再次用到的概率为 $p_h$，重算时间为 $T_r$，从缓存取回并准备好状态的时间为 $T_f$，维护缓存所需时间为 $T_m$。每次命中能节省 $T_r - T_f$；乘以命中概率，再减去维护时间，就得到期望净节省：

$$V_h = p_h (T_r - T_f) - T_m$$

以章首长请求的 6144 个 token 公共前缀为例，它的 KV 占 864 MiB（0.906 GB）。在 RTX PRO 6000 上重算这段前缀要做 96.5 TFLOP 的矩阵运算，按实验 8-1 中 batch 1 prefill 达到的 BF16 峰值的 62%（第 8.6.3 节）计，约需 307.9 ms。把这段前缀换出到主机内存后，经这张卡的 PCIe Gen5 x16 链路（每方向 64 GB/s）取回约需 14.2 ms；维护开销取换出时写回主机的一次传输，也是 14.2 ms。命中概率为 50% 时平均节省 132.7 ms。要让保留前缀节省时间，需满足

$$p_h > \frac{T_m}{T_r - T_f} = \frac{14.2}{293.7} = 4.8\%$$

若主机链路换成 PCIe Gen4 x16（每方向 32 GB/s），取回和换出各增至 28.3 ms，每次命中只省 279.6 ms，所需的最低命中概率升至 10.1%。换出释放了加速器空间，但只有前缀足够常用，才能抵消取回和维护所需的时间。

前缀值得保留，并不意味着应该优先保留。空间紧张时，大前缀会占用原本能保存多个小前缀的空间。设 A 为上述 6144 个 token 前缀；每个 B 类前缀含 2048 个 token，占 288 MiB，同样按 PCIe Gen5 取回与换出，重算 94.7 ms、取回和维护各 4.7 ms，命中概率同为 50%，期望节省 40.3 ms。图 8-22 将两者放进同样大小的缓存：保存一个 A 能节省 132.7 ms，保存三个 B 合计节省 120.9 ms。重算时间随前缀长度超线性增长，6144 个 token 的 prefill 是 2048 个 token 的 3.25 倍，因此同一块内存用于保存长前缀的收益更高。

这种比较也可以换算成单位容量的收益：A 每 MiB 约节省 0.154 ms，B 约 0.140 ms。按该数值排序，就可以比较大小不同的前缀。

上述选择有一个前提：前缀必须保留到下一次使用时。缓存容量不足时，即使下一轮输入保留了相同前缀，也可能因为状态已经淘汰而要重新计算。一次 12 轮 Agent 输入回放包含 19,556 个输入 token。在相同干扰请求下，6 GiB 缓存池命中 16,304 个 token，只需重新处理 3252 个；1 GiB 池则没有命中，需要重新处理全部输入。将相邻两轮之间的等待时间增加 0.2 秒后，命中数量没有改变。这组对照中，增加容量保留了可复用的前缀，单纯延后下一轮请求没有产生同样的效果。

缓存准入决定请求结束后是否保留其前缀；淘汰策略决定空间不足时先删除哪个前缀；换出策略决定将状态移到哪一级存储；重计算策略决定重新执行多少输入 token。对于章首的 16 条长请求，保留一份公共前缀只需 864 MiB，却能同时节省重复存储和后续请求的 prefill 计算。

原书脚注 18（印刷 p.335）给出链路规格：RTX PRO 6000 Blackwell 工作站版的系统接口为 PCIe 5.0 x16，带宽为 PCIe Gen4 的两倍；A100 80GB 的 PCIe 4.0 为 64 GB/s（收发合计），即 x16 每方向 32 GB/s，由此 PCIe Gen5 x16 每方向 64 GB/s。正文按标称值计算，得到的是传输时间的下界，前缀的重算时间按实验 8-1 的效率表计算。脚注 19 是 12 轮实际输入的缓存回放，回放采用原任务的输入序列，串行执行请求，每轮生成一个 token。

> 图 8-22（原文插图）：**两种方案的缓存容量都是 864 MiB**。左：**A 占 864 MiB，期望净节省 132.7 ms**；右：**三个 B 类前缀各占 288 MiB、各节省 40.3 ms，合计 120.9 ms**。图中**宽度表示容量**；时间按 RTX PRO 6000 上的重算时间和 PCIe Gen5 取回时间计算，命中概率均为 50%。

**练习 8-4 ・核心・分析：有限缓存应保留哪些前缀，才能节省最多时间？**（印刷 p.335）

题干照抄原文：缓存可用空间为 864 MiB。前缀 A 含 6144 个 token、占 864 MiB；三个相互独立的 B 类前缀各含 2048 个 token、占 288 MiB。在 RTX PRO 6000 上，按 BF16 峰值 503.8 TFLOP/s 的 62% 由矩阵运算量求重算时间，按 PCIe Gen5 x16 每方向 64 GB/s 求取回时间，维护时间取一次换出，与取回相同；命中概率均为 50%。比较保留一个 A 前缀与保留三个 B 类前缀的期望净节省时间。保持 B 类前缀的命中概率不变，求 A 的命中概率低于多少时，应改为保留三个 B。再把链路换成 PCIe Gen4 x16（每方向 32 GB/s），重新比较。数据分析部分读取配套 12 轮输入与缓存回放，分别计算共同前缀比例和实际命中比例，解释其他请求占用缓存空间为何会影响实际命中比例。

下面是笔记补的解答，不是原文。在 Gen5 x16（64 GB/s）下，A 的取回和维护各为 $0.906\ \text{GB} / 64\ \text{GB/s} = 14.2$ ms，重算 307.9 ms，故 $V_A = 0.5 \times (307.9 - 14.2) - 14.2 = 146.85 - 14.2 = 132.65 \approx \mathbf{132.7}$ ms。B 的取回和维护各 $0.302\ \text{GB}/64 = 4.7$ ms，重算 94.7 ms，故 $V_B = 0.5 \times (94.7-4.7) - 4.7 = 45 - 4.7 = \mathbf{40.3}$ ms；三个 B 合计 120.9 ms < 132.7 ms，所以保留 A 更优。A 的命中概率阈值这样求：要使 $p_h \times 293.7 - 14.2 < 120.9$，得 $p_h < 135.1/293.7 = 46.0\%$，即当 A 的命中概率低于约 46% 时，应改为保留三个 B。

换成 PCIe Gen4 x16（32 GB/s）后，A 的取回和维护各 $0.906/32 = 28.3$ ms，$V_A = 0.5 \times (307.9-28.3) - 28.3 = 139.8 - 28.3 = 111.5$ ms；B 的取回和维护各 $0.302/32 = 9.4$ ms，$V_B = 0.5 \times (94.7-9.4) - 9.4 = 42.65 - 9.4 = 33.25$ ms，三个 B 合计 99.8 ms。A 仍然更优（111.5 > 99.8），而且两者的绝对差距几乎不变，Gen5 时 132.7 − 120.9 = 11.8 ms，Gen4 时 111.5 − 99.8 = 11.7 ms。差距主要来自重算时间（307.9 ms 对 3 × 94.7 = 284.1 ms），与链路带宽关系不大；阈值变为 $p_h < (99.8+28.3)/279.6 = 45.8\%$。

数据分析部分：共同前缀比例 = 相邻两轮逐 token 相同的长度 ÷ 上一轮长度（图 8-18 的蓝色部分比例）；实际命中比例 = 实际命中（未重算）的 token 数 ÷ 输入 token 总数。其他请求占用缓存空间会挤压可用的物理块，使本该保留的前缀被淘汰，于是同样的输入、同样的等待时间，实际命中比例会低于共同前缀比例。

$V_h$ 这个公式值得当成缓存决策的一般原则记住：

$$V_h = \underbrace{p_h(T_r - T_f)}_{\text{命中时省下的时间} \times \text{命中概率}} - \underbrace{T_m}_{\text{维护成本}}$$

$T_r$（重算时间）是收益的来源，能省的只有本来要重新算的那一遍。$T_f$（取回时间）是命中的代价，从主机内存搬回显存要花时间，所以命中净省 $T_r - T_f$，而不是 $T_r$。$T_m$（维护时间）是不管命不命中都要付的：把状态写出去、管理它、占着显存。所以值不值得留的判据就是 $p_h > T_m/(T_r - T_f)$，说白了就是命中率必须高到能把维护成本赚回来。

A 的那串数字再复算一遍（笔记补充计算）：重算 $96.5\ \text{TFLOP} \div (503.8 \times 0.62)\ \text{TFLOP/s} = 96.5/312.36 = 0.309$ s $= 309$ ms，原文给的是 307.9 ms，与这里的粗算差约 1 ms，属四舍五入与效率取值差异，笔记按原文记录；取回 $864\ \text{MiB} = 905.97\ \text{MB} = 0.906$ GB，$0.906/64 = 0.01416$ s $= 14.2$ ms ✓；净节省（$p_h = 50\%$）$0.5 \times (307.9 - 14.2) - 14.2 = 132.7$ ms ✓；阈值 $14.2 / 293.7 = 4.835\% \approx 4.8\%$ ✓。

重算时间超线性增长是本节的第二个关键点：6144 个 token 的 prefill 是 2048 个的 3.25 倍，而不是 3 倍。超线性的来源是注意力部分那个 $\frac{c(c+1)}{2}$ 三角形项（8.2.3），token 数翻倍时这部分翻四倍。所以大前缀的单位容量收益更高，A 每 MiB 0.154 ms，B 每 MiB 0.140 ms。长前缀更划算这个结论有个前提：重算，而不是读 KV，占主导。

值得保留和应该优先保留是两件事。A 的单位收益更高，所以在容量受限、必须二选一时先保 A。但如果 A 的命中概率低，比如它是个很少重复的独特请求，而三个 B 都是高频重复的，那就要按 $p_h$ 加权后再比。这就是练习 8-4 里那个 46% 阈值的含义。

延后 0.2 秒没有改变命中数量这组对照很关键，它排除了一个常见的错误直觉：请求间隔太短、状态还没用完就被淘汰了。实验结果指向容量：可复用的前缀是被空间挤掉的，跟等待时间无关。6 GiB 池能命中 16,304 个 token（19,556 个里只重算 3252 个），1 GiB 池一个都命中不了。换成 Gen4 链路会让阈值从 4.8% 升到 10.1%，因为取回变慢了，命中一次的净收益从 293.7 ms 降到 279.6 ms，而维护成本从 14.2 涨到 28.3 ms。慢链路让缓存这件事整体变得不那么划算。

四个策略名词正好对应缓存系统的四个决策点。准入（admission）管新来的前缀要不要留下，判据是 $V_h > 0$ 吗。淘汰（eviction）管空间不够时删谁，按单位容量收益乘以命中概率排序，删最低的。换出（offload）管放哪一级存储，DRAM、SSD、远端都可以，链路带宽决定 $T_f$。重计算（recomputation）管重放多少 token，也就是 8.3.3 里的快照密度问题。

几个容易混的点收在这里。$T_r$（重算）与 $T_f$（取回），前者是用算力重新造出来，后者是用带宽搬回来；重算时间和前缀长度的关系是超线性的（含注意力三角形项），取回时间是线性的。命中概率 $p_h$ 与共同前缀比例也不是一回事，前者是实际缓存命中的概率，后者只是内容上可复用的比例，图 8-18 明确提醒「实际缓存命中还取决于状态是否保留」。淘汰（eviction）与换出（offload）的区别在于前者是丢掉，数据没了、以后要重算，后者是挪到别处，数据还在、以后搬回来。还有一点，换出释放的是加速器空间，不是总成本，取回要花 PCIe 时间，所以换出等于用未来的传输换现在的容量。

一份前缀值不值得留，用 $V_h = p_h(T_r - T_f) - T_m$ 算；多个前缀争容量时，按单位容量收益乘以命中概率排序。重算对长前缀是超线性的，所以长前缀通常更值得留。

## 8.4 压缩与卸载

8.3 节靠「共享」把重复的 KV 去掉了。本节换一条路：把每个数值本身变小，这是量化，8.4.1 和 8.4.2 讲它；或者把数据轮流搬进加速器，这是卸载与预取，8.4.3 讲它。走完这两条路，还剩一个绕不开的问题，改了数值格式，答案还对吗，这是 8.4.4。三节合起来回答同一件事：显存不够的时候，你还能怎么办。

### 8.4.1 权重量化后的内存占用

前缀共享靠去除重复的 KV 省空间。可即使请求之间没有相同前缀，也还有别的办法：用量化把权重和 KV 的存储量降下来。量化的做法通常是把数值分组编码，每组保存较低位宽的编码值，再附带一份 scale 之类的元数据，计算时按这些信息把近似值恢复出来。

Q2_K 是张量计算库 GGML 系列里的一种分组量化格式，主编码用 2 bit，另外为组内的 scale 保存额外信息。就以它为例：每组 256 个值，2-bit 编码占 $256 \times 2 / 8 = 64$ bytes，scale 和最小值这类元数据另占 20 bytes。一组下来共需 84 bytes，平均每值 $84 \times 8 / 256 = 2.625$ bit。位宽降低之后，元数据在总容量里的比重就上来了，在这个格式里约占 24%。

原书脚注 20（印刷 p.336）给出了 Q2_K 的逐张量布局，以及 8K 文件容量与 32K 对照。文件总量 85,691,002,112 bytes，其中码值与浮点载荷 69,178,275,840 bytes，量化元数据 16,506,720,256 bytes，文件头与填充 6,006,016 bytes。这几个文件大小是按已归档文件头与发布元数据算出来的。

#### 扩展算例：量化权重加载到内存后，还能容纳多长的上下文？（原文例题，印刷 p.336）

题干照抄原文。Qwen3-235B-A22B 的一个 Q2_K 文件变体采用以 2 比特为主的分组量化，混合使用多个位宽，量化编码与未量化的浮点数据约 64.43 GiB，量化元数据约 15.37 GiB，加上文件头与填充共约 79.81 GiB。另一个 UD-Q2_K_XL 变体约 81.97 GiB。以实验 8-7 所用的 Apple M2 Max 为例，它的统一内存标称 96 GB（十进制），给系统与工作区预留 8 GiB，剩余约 81.41 GiB。把前一个文件加载到内存后，还剩 1.60 GiB；后一个文件已经超出可用空间约 0.56 GiB。该模型一条 8K 上下文的 BF16 KV 约占 1.47 GiB，所以前一种方案还能处理一条请求，并剩余约 0.13 GiB。若上下文长度增至 32K，KV 就需要约 5.88 GiB，必须增加内存或改变权重的存放方式。两个文件的大小只相差 2.16 GiB，已经足以决定能否容纳请求。

原书脚注 21 交代了固定模型文件、业务预算与 235B 分片元数据的口径，精确字节、GB 与 GiB 都分别报告。

这两笔账连着看，量化的账本其实好算，值得亲手算一遍（以下为笔记补充计算）：

- 主编码：$256 \text{ 个值} \times 2\ \text{bit} \div 8 = 64$ bytes；
- 元数据：20 bytes，装 scale、最小值之类；
- 合计：84 bytes 覆盖 256 个值，等于 0.328 bytes/值，也就是 2.625 bit/值；
- 元数据占比：$20/84 = 23.8\% \approx 24\%$。

位宽越低，元数据占比越高，这是条结构性规律。2 bit 的编码已经快缩到极限了，但每组 20 bytes 的元数据是固定的，于是它成了大头。顺着这个思路往下推：如果换成 8 bit，一组 256 个值是 $256 \times 8/8 = 256$ bytes 编码再加 20 bytes 元数据，共 276 bytes，平均 8.625 bit/值，元数据只占 7.2%。所以 2 bit 量化并不能真的把权重压到 1/8。本格式相对 BF16 的实际压缩比是 $16/2.625 = 6.10$ 倍。这个 6.10 倍是笔记自己算的，原书只给了 2.625 bit 和 24% 这两个数。

扩展算例里每个数字都能对上（笔记补充复算）：

- 文件总量 $69\,178\,275\,840 + 16\,506\,720\,256 + 6\,006\,016 = 85\,691\,002\,112$ bytes，与脚注一致；
- $85\,691\,002\,112 / 1024^3 = 79.80$ GiB，取两位就是 79.81 GiB；
- 可用内存要先换算：96 GB（十进制）$= 96 \times 10^9 / 1024^3 = 89.41$ GiB，减去预留的 8 GiB 得 81.41 GiB。这就是「标称 96 GB 内存实际只有 89.41 GiB」那个经典换算陷阱；
- 79.81 GiB 加载后剩 $81.41 - 79.81 = 1.60$ GiB；81.97 GiB 则超出 $81.97 - 81.41 = 0.56$ GiB；
- 8K BF16 KV 按原文给的 1.47 GiB 代入，$1.60 - 1.47 = 0.13$ GiB；32K 则是 $1.47 \times 4 = 5.88$ GiB。

到这里能看出这一节真正想说的道理，决定权落在小数位上。两个文件相差 2.16 GiB，约 2.6%，却决定了能不能跑。在本地推理这种内存刚好够的场景里，带几位小数的那点差距比模型能力的差距更早决定结果。

统一内存（unified memory）那一段是另一课，而且很重要：文件能装下和模型能跑是两件事。在统一内存系统里 CPU 与 GPU 共用物理内存，权重文件映射到地址空间后，访问到相应数据时文件页面才需要驻留物理内存。但如果执行时要访问的数据总量超过内存容量，页面就会不断换入换出，也就是 thrashing，速度直接崩。对策有两条：减少数据本身的字节数，或者只保留当前需要的数据、其余在使用前搬入。作者把「压缩」和「卸载」放进同一节，原因就在这里。下面先算 KV 压缩的收益，再分析权重搬入需要多少时间。

三处容易混的地方值得先点出来。量化位宽不等于存储位宽，编码是 2 bit，实际摊到每个值是 2.625 bit，因为每组还要摊一份元数据。十进制 GB 与 GiB 也要看清，$96\ \text{GB} = 89.41\ \text{GiB}$，原文在这个算例里两种单位都出现过。还有装得下文件与跑得动模型，前者只看文件大小，后者还要留出 KV 和运行时缓冲。

> 量化省的是每个数值占多少字节，而分组元数据是省不掉的固定开销。位宽越低，元数据占比越高，2 bit 量化的实际压缩比远达不到 8 倍。

### 8.4.2 KV 压缩与读取成本

把同样的分组方法用到 KV 上，就能算出省下来的空间能多容纳多少请求。权重由许多请求共享，KV 却持续随输入与输出增长。对本章这个模型，一条 8K 上下文的 BF16 KV 是 1152 MiB。量化改的是每个值的位宽，而上下文表示改的是每个 token 要保存多少个值：第 9.2.2 节把同一 8K 上下文的 GQA 与紧凑 MLA 状态并列，后者只有 549 MiB。每 32 个 BF16 值占 64 bytes。

q8_0 是每 32 个值共用一个 scale 的 8 bit 量化格式。改成 q8_0 时保存 32 bytes 码值和 2 bytes scale，变为原来的 34/64；q4_0 采用同样的分组方式，只把码值降到 4 bit，保存 16 bytes 码值和 2 bytes scale，变为 18/64。于是同一条上下文所需容量为

$$M_{q8} = 1152 \times \frac{34}{64} = 612\ \text{MiB}, \qquad M_{q4} = 1152 \times \frac{18}{64} = 324\ \text{MiB}$$

与 BF16 相比，q8_0 节省 540 MiB，q4_0 节省 828 MiB。把 scale 计进去，两种格式平均每值分别占 8.5 bit 和 4.5 bit。由于每组都要保存 scale，元数据也会随 KV 长度一起增长。

图 8-23 把这一步还原成字节布局。每行都保存相同的 32 个值：编码部分缩短了，scale 仍要留下。所以 q8_0 和 q4_0 的总长度分别是 34 和 18 bytes，而不是只看编码位宽得到的 32 和 16 bytes。

> 图 8-23（原文插图）：横条按字节数成比例绘制，横轴为「保存同一组 32 个值（bytes）」，刻度 0 到 60。三行分别是 **BF16（64 bytes）、q8_0（34 bytes）、q4_0（18 bytes）**；**橙色为每组 2 bytes 的 scale**。图注说明：**把每组总长度乘以组数，就得到整条上下文的 KV 容量。**

章首算例里那条长请求生成完毕后，BF16 KV 按块分配共占 1188 MiB。改用同一布局的 q8_0 后需要 $1188 \times 34/64 = 631.125$ MiB，16 条独立长请求合计约 9.86 GiB，可以放进预留的 12 GiB。可见共享和压缩节省空间的方式不同：共享去除重复前缀，压缩减少每个数值所占的字节。

用压缩 KV 做注意力计算时，读取量少了，但格式转换本身要花时间。设一次计算少读 $\Delta D$ bytes，有效带宽为 $\beta$，转换增加的串行执行时间为 $T_c$，净节省时间是

$$\Delta T = \frac{\Delta D}{\beta} - T_c$$

举个例子。在 RTX PRO 6000 上把一条 8K 上下文从 BF16 改成 q8_0，少读 540 MiB。按读取受限时的有效带宽约 1.16 TB/s 计（来自第 8.6.3 节，是峰值 1792 GB/s 的 65%），约节省 0.487 ms。若转换增加 0.2 ms，最终节省约 0.287 ms；若转换增加 0.8 ms，反而增加约 0.313 ms。同一种压缩格式能不能加快执行，取决于转换时间是否少于节省下来的读取时间。

上下文越长，减少读取所省下的时间越多。一项早期评估在 H100 上运行 Llama-3.1-8B，用 $6.44 + 4.37 \times 10^{-5} L$ 和 $6.58 + 2.37 \times 10^{-5} L$（ms）分别拟合 BF16 与 FP8 的输出间隔。FP8 的固定项多 0.14 ms，每个上下文 token 的增长项少 $2 \times 10^{-5}$ ms。用固定开销之差除以每增加一个上下文 token 的耗时之差，得到交点约为 7000 个 token。在 2K 时 BF16 约 6.53 ms、FP8 约 6.63 ms，到 16K 则分别约 7.16 和 6.97 ms。上下文较长时，读取省下的时间超过了新增的固定开销。

原书脚注 22 与 23（印刷 p.337–338）对应 KV 格式和执行成本，资料包含 GGML 分组格式、FP8 scale 粒度以及 H100 上的拟合结果。

本节开头说过，上下文表示决定每个 token 要保存多少个值。混合注意力模型里局部与全局两类状态同样可以这样比容量：在 8K 上下文基线下，把全局历史与有效 SWA 的容量相加，DeepSeek V4.1 的两项分别为 6.953 MiB 与 2.578 MiB，共 9.531 MiB；V4 的对应两项合计为 30.521 MiB，约为 V4.1 的 3.20 倍。局部窗口占的是固定空间，所以短上下文下的合计容量差距小于全局历史那 3.95 倍。

q8_0 与 q4_0 的账可以列成一张表（笔记补充计算）：

| 格式 | 每 32 个值的码值字节 | scale 字节 | 合计字节 | 平均位/值 | 相对 BF16 的比例 |
| --- | --- | --- | --- | --- | --- |
| BF16 | 64 | 0 | 64 | 16 | 1 |
| q8_0 | 32（8 bit × 32） | 2 | 34 | $34 \times 8/32 = 8.5$ | $34/64$ |
| q4_0 | 16（4 bit × 32） | 2 | 18 | $18 \times 8/32 = 4.5$ | $18/64$ |

由表可以复算：

- $M_{q8} = 1152 \times 34/64 = \mathbf{612}$ MiB，节省 $1152 - 612 = \mathbf{540}$ MiB；
- $M_{q4} = 1152 \times 18/64 = \mathbf{324}$ MiB，节省 $1152 - 324 = \mathbf{828}$ MiB；
- 长请求那条 1188 MiB：$1188 \times 34/64 = \mathbf{631.125}$ MiB；$16 \times 631.125 = 10\,098$ MiB $= 9.861$ GiB，约 9.86 GiB，能塞进 12 GiB。

$\Delta T = \Delta D / \beta - T_c$ 是本节的核心判据，而且是通用判据：省下来的读取时间必须大于多花出去的转换时间。复算一遍（笔记补充计算）：

- $\Delta D = 540\ \text{MiB} = 566.23\ \text{MB} = 0.566$ GB；$\beta = 1.16\ \text{TB/s}$，即 1160 GB/s；$0.566/1160 = 0.488$ ms，约 0.487 ms；
- $T_c = 0.2$ ms 时净省 $0.487 - 0.2 = \mathbf{0.287}$ ms；
- $T_c = 0.8$ ms 时净亏 $0.487 - 0.8 = \mathbf{-0.313}$ ms，原文的说法是「反而增加约 0.313 ms」。

有效带宽为什么取 1.16 TB/s，原文说它是峰值 1792 GB/s 的 65%，也就是 8.6.3 节效率表里 batch 64 的 decode 带宽效率。$1792 \times 0.65 = 1164.8$ GB/s，四舍五入就是约 1.16 TB/s（笔记补充核对）。

上下文越长压缩越划算，这件事用那两条线性拟合式能说得很干净。BF16 是 $6.44 + 4.37 \times 10^{-5} L$，FP8 是 $6.58 + 2.37 \times 10^{-5} L$。两条直线，FP8 起点高 0.14 ms，斜率小 $2 \times 10^{-5}$ ms/token，交点就在 $0.14 / (2 \times 10^{-5}) = 7000$ 个 token。两端各复算一次（笔记补充计算）：

- $L = 2048$：BF16 $= 6.44 + 0.0895 = 6.53$ ms，FP8 $= 6.58 + 0.0485 = 6.63$ ms，此时 BF16 更快；
- $L = 16384$：BF16 $= 6.44 + 0.716 = 7.16$ ms，FP8 $= 6.58 + 0.388 = 6.97$ ms，此时换成 FP8 更快。

这两个式子还顺手给出一个很好用的估算结论：FP8 大约有 0.14 ms 的固定转换开销，但每处理一个上下文 token 少花 0.02 ms。所以短上下文，比如 7K 以下，别上压缩；长上下文一定要上。

压缩与共享的区别原文点得很清楚：共享是去重，同一份数据只存一次；压缩是瘦身，每个数值用更少的比特。两者能叠加，先共享前缀再对剩下的 KV 做量化。但共享之后前缀只剩一份，压缩它省下的绝对量也跟着变小，所以这两种优化会互相削弱对方的收益。

DeepSeek V4.1 与 V4 那组容量对比，优化发生在「上下文表示」这一层，跟精度无关：$6.953 + 2.578 = 9.531$ MiB，$30.521 / 9.531 = 3.202$，约 3.20 倍。原文还提到短上下文下的合计容量差距小于全局历史的 3.95 倍，原因是局部窗口（SWA）占的是固定空间，不随上下文增长，上下文越短，固定部分占比越大，差距就越小。

几处易混的地方。权重压缩和 KV 压缩的价值不一样：权重是共享的，省一次就全省；KV 每个请求独有且持续增长，省的是每个请求、每个 token，所以 KV 量化的收益会随并发数和上下文长度一起放大。压缩比和平均位/值也不同，q4_0 的码值只有 4 bit，加上 scale 是 4.5 bit/值，对外报「4 bit 量化」时通常把这 0.5 bit 略掉了。$T_c$ 与解压也不在同一处：KV 量化的转换通常发生在读入之后、算注意力之前，是反量化，串行叠加在一轮里；8.4.3 里权重卸载的解压是另一回事。还有一条最容易踩：减少读取量不等于减少总时间，必须减去转换开销，看 $\Delta T$ 的符号。

> KV 量化是用少读换多算：$\Delta T = \Delta D/\beta - T_c$ 决定它到底赚不赚。上下文越长越赚，短上下文反而亏在那笔固定的转换开销上。

### 8.4.3 权重卸载、预取与每步搬移

压缩减少的是数据本身的大小。另一种扩展容量的方法是让数据轮流驻留在 GPU 上，只在计算需要时搬入，用完把这块空间复用掉。权重卸载就是把部分原本常驻 GPU 的权重移到主存，在计算到相应层之前再搬回 GPU。省下来的加速器内存可以给 KV 用，代价是每次前向计算都要重新搬入这些权重；请求逐步生成输出时，这个搬移还会随每轮 decode 重复一遍。

拿 Qwen3-8B 算一笔。一层 FFN 的三个 BF16 矩阵共占 288 MiB，36 层里每四层卸载一层，共卸九份 FFN 权重，释放 2592 MiB。GPU 上还得为预取留缓冲区，预取的意思是计算某层之前提前把它的权重复制到 GPU：一组缓冲占 288 MiB，净省 2304 MiB；两组占 576 MiB，净省 2016 MiB。以一条 8K 输入的 1152 MiB KV 为单位，前者能多容纳两条，后者只能多容纳一条。若按生成完毕时所需的 1188 MiB 预留空间，两种方案都只能增加一条完整请求。

预取有两个先后关系必须遵守：权重复制完成后计算才能读取；计算不再使用这组权重后，缓冲区才能写入下一组。只用一组缓冲时，同一块缓冲区依次承担复制、计算和下一次复制；用两组缓冲时，可以一边计算当前层，一边把后续层的权重复制到另一组缓冲区。这样就能把复制与计算重叠起来，代价是缓冲区本身占掉更多内存。

接下来算搬移的链路成本。这张卡经 PCIe Gen5 x16 连接主机，每方向标称 64 GB/s。每轮要搬入 2592 MiB，即 2.72 GB，于是需要

$$T_{\text{copy}} \ge \frac{2.72\ \text{GB}}{64\ \text{GB/s}} \approx 42.5\ \text{ms}$$

这已经超过 batch 1 一轮 decode 的 26.26 ms。即使其余计算都能与复制同时完成，每轮仍至少需要约 42.5 ms。若每轮为四条请求各生成一个 token，总输出吞吐最多约为 $4/0.0425 \approx 94$ token/s，每条请求的输出间隔也至少约为 42.5 ms。生成 256 个输出 token 需要 255 次后续前向计算，仅权重搬移就要约 10.8 秒，所以经 PCIe 卸载这部分权重，无法满足 7 秒的完成时限。

CPU 与 GPU 之间还有快得多的链路。GH200 用 NVLink-C2C 连接 Grace CPU 与 Hopper GPU，每方向 450 GB/s。同样的 2.72 GB 每轮至少约需 6.0 ms，255 轮合计约 1.54 秒。每轮复制短于一轮 decode 的计算，预取就能用计算把复制盖住。

若先压缩权重再搬移，还要把解压时间加进来。设原始数据为 $S$ bytes，压缩后为 $rS$ bytes，链路带宽为 $B_{\text{link}}$，解压吞吐为 $R_{\text{dec}}$（按输出的原始字节计）。先传完再解压需要 $rS/B_{\text{link}} + S/R_{\text{dec}}$，直接传输需要 $S/B_{\text{link}}$，所以只有当

$$R_{\text{dec}} > \frac{B_{\text{link}}}{1 - r}$$

时，压缩后搬移才更快。把 96 MiB 权重压缩到四分之一，经 PCIe Gen5 x16 直接传输约需 1.57 ms，传输压缩数据只需 0.39 ms；要保住这 1.18 ms 的节省，解压器每秒必须输出超过 85.3 GB 的原始数据。链路越快，对解压吞吐的要求就越高。

这一节的卸载里，模型计算始终由 GPU 执行，主存只负责保存暂不使用的权重。第 9.3 节会进一步改变计算位置：专家权重已经在主存时，可以由 CPU 直接计算，只向 GPU 传回较小的激活，那时就要比较每个专家的输入行数、CPU 计算时间与权重传输时间。

原书脚注 24（印刷 p.338）对应权重卸载与预取计算，PCIe Gen5 与 NVLink-C2C 两档链路的复制与预取调度都在里面，每层计算时间取 batch 1 一轮 decode 的 26.26 ms 除以 36 层；GH200 架构说明写的是 NVLink-C2C 合计 900 GB/s，每方向 450 GB/s。脚注 25 对应张量压缩与传输，资料包含 LLM.265 的视频引擎实现、专用硬件设计与性能估计。

#### 练习 8-5 ・计算：权重卸载节省的容量与增加的搬移（印刷 p.340）

题干照抄原文。设卸载九份 FFN 权重，每份占 288 MiB。设每组预取缓冲可以容纳一份 FFN 权重，分别计算使用一组和两组缓冲时净节省的加速器内存，并求这些空间能多容纳多少份 1152 MiB 的输入状态，或多少份 1188 MiB 的完整请求状态。再分别取 PCIe Gen5 x16 的每方向 64 GB/s 与 GH200 NVLink-C2C 的每方向 450 GB/s，求每步复制以及累计 255 步复制的时间下界。若留给所有复制的总时间为 1 秒，求所需的最低单向带宽。

参考解答（笔记补充，非原文）：

- 净节省：卸载 $9 \times 288 = 2592$ MiB；一组缓冲占 288 MiB，净省 2304 MiB；两组缓冲占 576 MiB，净省 2016 MiB。
- 能多容纳的输入状态（1152 MiB）：$\lfloor 2304/1152 \rfloor = 2$ 份；$\lfloor 2016/1152 \rfloor = 1$ 份。
- 能多容纳的完整请求状态（1188 MiB）：$\lfloor 2304/1188 \rfloor = 1$ 份；$\lfloor 2016/1188 \rfloor = 1$ 份。
- 每步复制下界：$2592\ \text{MiB} = 2.718\ \text{GB} \approx 2.72$ GB。PCIe Gen5 x16 是 $2.72/64 = \mathbf{42.5}$ ms；NVLink-C2C 是 $2.72/450 = \mathbf{6.0}$ ms。
- 累计 255 步：$42.5 \times 255 = 10\,838$ ms，约 10.8 s；$6.04 \times 255 = 1541$ ms，约 1.54 s。
- 总时间限定 1 秒时的最低单向带宽：$2.72\ \text{GB} / (1\ \text{s}/255) = 2.72 \times 255 = \mathbf{693.6}$ GB/s。255 步共 1 秒，每步只有 $1/255$ 秒，每步要传 2.72 GB。

卸载那三笔账可以这样理顺：腾出多少，$9 \times 288 = 2592$ MiB，每四层卸一层，36 层正好 9 份；要还回去多少，预取缓冲必须留在 GPU 上，一组 288 MiB、两组 576 MiB；净赚多少，一组是 $2592 - 288 = 2304$ MiB，两组是 $2592 - 576 = 2016$ MiB。

「净省 2304 MiB 能多装两条 8K 请求」这笔账要和前面的容量口径对齐：$2304/1152 = 2$，按 prefill 刚结束的 KV 算；$2304/1188 = 1.94$，取整得 1，按生成完毕预留算。同一块空间，按不同口径能容纳的请求数不同，这正是 8.1.2 里「接收请求时就预留生成阶段所需的空间」那句话的代价，预留得越保守，能容纳的并发就越少。

一组缓冲与两组缓冲值得单独讨论，因为它体现了预取流水线的本质。一组缓冲时流程是复制、计算、复制、计算，严格串行，搬移时间完全暴露在外。两组缓冲也就是 double buffering，计算第 $i$ 层的同时把第 $i+1$ 层复制到另一组缓冲，复制被计算掩盖，前提是复制时间不超过该层的计算时间。代价就是那 288 MiB 的额外显存，净收益从 2304 掉到 2016 MiB。

复制到底能不能被掩盖，完全取决于链路带宽，这正是图 8-25 要说明的。PCIe Gen5 x16 的 42.5 ms 大于一轮 decode 的 26.26 ms，掩盖不了，每轮必然被拖到至少 42.5 ms。NVLink-C2C 的 6.0 ms 小于 26.26 ms，能掩盖，总时间回到 1.54 s。原文那句「每轮复制短于一轮 decode 的计算，预取就能用计算掩盖复制」就是判据。

「每层计算时间」的口径也要注意。脚注 24 说每层计算时间取 batch 1 一轮 decode 的 26.26 ms 除以 36 层，得 0.729 ms/层。把 PCIe 的 42.5 ms 摊到 9 个被卸载的层上是 4.72 ms/层，远大于 0.729 ms/层，所以 PCIe 这条路根本盖不住（笔记补充计算）。

先压缩再传输的那个判据 $R_{\text{dec}} > B_{\text{link}}/(1-r)$ 也值得掰开看：压缩传输省下的时间必须大于解压多花的时间。复算（笔记补充计算）：

- $S = 96$ MiB $= 100.66$ MB；直接传是 $100.66/64 \times 10^{-3} = 1.573$ ms，约 1.57 ms；
- 压缩到 $r = 1/4$：$100.66 \times 0.25 / 64 = 0.393$ ms，约 0.39 ms；
- 省下 $1.573 - 0.393 = 1.18$ ms，但解压必须满足 $S/R_{\text{dec}} < 1.18$ ms，即 $R_{\text{dec}} > 100.66\ \text{MB} / 1.18\ \text{ms} = 85.3$ GB/s，与公式 $64/(1-0.25) = 85.33$ GB/s 一致。

结论有点反直觉：链路越快，压缩传输省下的越少，对解压吞吐的要求反而越高，因为节省量正比于 $1/B_{\text{link}}$，而解压时间是固定的。所以在极快的链路上，压缩后再传往往得不偿失。

工程上还有几个坑。卸载的本质是用带宽换容量，决定卸载之前先问三个问题：我缺的是容量还是带宽，缺容量才卸载；每轮搬移量除以链路带宽是多少，它会不会超过一轮计算的时间；能不能用两组缓冲把搬移藏到计算后面。三问里任何一个答案不利，卸载就不划算。原文那个 PCIe 例子就是第一、二问都通过、第三问失败的典型。

这里还有两处名字相近的东西要分清。8.3.4 换出的是每个请求的状态，也就是 KV，一次性写出去、需要时再取回；本节卸载的是共享的权重，每一轮都要重新搬入。后者频率高得多，对带宽的要求也高得多。一组缓冲与两组缓冲的区别则在执行顺序，前者顺序执行，不支持重叠，后者是 double buffering，支持重叠但多占一份缓冲。报数字时别把「净省」和「腾出」混了，净省等于腾出减去缓冲区，2592 不是可用空间。压缩传输与 KV 压缩也不一样，前者为了省传输时间，后者为了省显存和读取量，两者判据形式相似，都是省的要大于花的，但对象不同。

> 卸载是用带宽换容量。能不能成，只看每轮搬移量除以链路带宽是否小于一轮计算的时间。PCIe 上 42.5 ms 不行，NVLink-C2C 上 6.0 ms 可以。
### 8.4.4 质量约束下的容量与速度选择

8.4.2 节算出了压缩节省的空间和增加的转换时间，但漏了一个问题：改了数值格式之后，答案还一样吗。这里的执行后端指真正完成注意力计算的那个 kernel 实现。压缩 KV 改变的是保存的数值，而换执行后端还可能同时改变 Q 的计算格式、转换过程和归约运算的数值精度。想找出输出差异的来源，办法是逐项比较张量的存储格式与计算精度。

这套比较用八道固定任务来做，三幅图按相同顺序排列这些任务。八道任务来自两种长度的文档，每份文档含 128 或 512 条六位数字记录，两种长度各有四份独立文档，实验记录里分别标为 n128-r0 至 n128-r3 和 n512-r0 至 n512-r3，图中依次记为任务 1 至 8。每道任务在两种并发数下各运行两次，这样就能用同一道任务逐一比较不同数值格式的影响。

一组 Qwen3-8B 实验保持 BF16 权重不变，比较了三种注意力计算方式。32 次自然生成里，用 BF16 KV 答对 28 次；改用原 FP8 实现后答对 26 次；保留 FP8 KV、把 Q 恢复成 BF16 之后，又答对 28 次。后一种配置只改了 Q 的精度，结果就变了，所以 KV 的存储格式和 Q 的计算精度必须分开考察。

图 8-28 做的正是这件事，只恢复查询 Q 的 BF16 精度，KV 仍保持 FP8。按同一列去比三幅图，能看出改变的是哪些题目的结果，而不只是总正确数。

图中任务 5，也就是实验记录里的 n512-r0、含 512 条记录的第一份长文档，在 BF16 KV 下四次均错，在「FP8 KV 加 BF16 Q」下四次均对；任务 6（n512-r1）恰好相反。两种配置都答对 28 次，但答错的任务不同。把同一道任务的结果排在一起，就能看出差异发生在哪里，以及重复运行时是否一直如此。

错误还会拖长完成任务的时间。第一次回答失败后再试一遍，得到正确答案的总时间应当包括首次生成、检查答案和再次生成。已有实验里两次重试修正了错误，但额外增加了约 2.0 秒生成时间和 92 个 token。如果第一次回答虽然更快、却更容易出错，把整个任务做完反而可能更慢。

前面那两种 KV 容量方案也可以放在一起比：16 条独立长请求采用 q8_0 后约占 9.86 GiB，共享 BF16 前缀后约占 5.91 GiB。要判断哪种更合适，还得把转换、生成和重试的时间一起算进请求的总耗时，这一步留给第 8.6 节的综合例题。

#### 练习 8-6 ・数据分析：KV 压缩如何影响容量、答案正确性与重试成本（印刷 p.341）

题干照抄原文。设每组包含 32 个值，另用 2 字节保存 scale，复算 8K 输入和完整长请求在 q8_0、q4_0 格式下的 KV 容量。再读取配套三种 KV／Q 精度配置的逐题结果，列出 BF16 KV 与「FP8 KV 加 BF16 Q」中正确性改变的题目。最后读取重试记录，对每个成功任务合计首答与重试时间，并与只计入最后一次成功生成时间的结果比较。

参考解答（笔记补充，非原文）：

- 8K 输入的 KV，BF16 为 1152 MiB：q8_0 $= 1152 \times 34/64 = \mathbf{612}$ MiB；q4_0 $= 1152 \times 18/64 = \mathbf{324}$ MiB。
- 完整长请求，生成 256 个 token、按块分配，BF16 为 1188 MiB：q8_0 $= 1188 \times 34/64 = \mathbf{631.125}$ MiB；q4_0 $= 1188 \times 18/64 = \mathbf{334.125}$ MiB。
- 正确性改变的题目集中在任务 5（n512-r0）与任务 6（n512-r1）：任务 5 从 BF16 KV 下四次均错，变为「FP8 KV 加 BF16 Q」下四次均对，任务 6 恰好相反。两边总正确数都是 28/32。
- 重试成本方面，只计最后一次成功生成会漏掉首次生成、检查答案、再次生成的全部开销。实验中被两次重试修正的错误额外增加了约 2.0 秒生成时间和 92 个 token，所以合计首答与重试时间的结果比只看成功那次高出这 2.0 秒和 92 个 token。

这一节的方法论比结论更重要：总正确数相同不等于答对的题相同。图 8-26 与图 8-28 都是 28/32，但错的是不同的题，任务 5 与任务 6 正好对调。只看总数，会得出「两种格式质量一样」的错误结论。

为什么非要比较三幅图而不是两幅，因为原 FP8 实现同时改了两件事，KV 的存储格式从 BF16 变成 FP8，Q 的计算精度也跟着变了。所以要拆开：

- 图 8-26：KV 为 BF16，基线，28/32；
- 图 8-27：KV 为 FP8 且 Q 走原 FP8 实现，26/32；
- 图 8-28：KV 为 FP8 且 Q 为 BF16，28/32。

从 26 恢复到 28 只靠把 Q 恢复成 BF16，说明掉的那 2 分主要出在 Q 的计算精度上，KV 的存储格式这一项基本没有责任。（这是笔记的补充解读，原文只说最后一种配置只改变 Q 的精度、结果就发生了变化，说明需要分别考察 KV 的存储格式和 Q 的计算精度。）脚注 26 还给了另一组：固定 FP8 权重时，BF16 Q 与默认路径分别为 32/32 和 28/32，同一个现象又出现了一次，把 Q 换成 BF16 就能拿回几分。

重试成本必须计入，这是本节最实用的一条工程结论。一个更快但更容易错的配置，在端到端任务里可能更慢，因为重试要重跑一遍生成，还有检查答案的开销。原文给的数字是约 2.0 秒加 92 个 token。把这笔账和 8.1 的 7 秒时限放在一起看，一次重试就可能把一条本来及格的请求推到超时。

8.4.4 在全章里承担的是「质量约束」这一半。前面所有关于容量和速度的优化，归根结底都要回答同一个问题：这样改数值，答案还对不对。8.6.2 的有效吞吐会把这件事形式化，分子只计「正确且按期完成」的请求，所以错的和迟到的同样都是浪费。

那八道任务也值得看一眼。每份文档含 128 或 512 条六位数字记录，两种长度各四份文档，合起来 8 道。这是一类长上下文检索与归纳的任务，需要从长文档里找出并处理数字记录。任务越长（n512），数值精度的影响越明显，图里出现差异的正好是任务 5 和 6，两道都是 n512。

几处容易含混的地方。KV 的存储精度决定读出来的数有多准，Q 的计算精度决定算出来的数有多准，图 8-27 到 8-28 的对比说明后者可能更关键。总正确数与逐题结果是两回事，总数相同不代表逐题相同，评估数值格式的影响必须逐题比对。生成更快和任务更快完成也不是一回事，前者只看一次生成，后者要算上重试，错误本身是有时间成本的。

> 换了数值格式，要同时看三件事：容量省了多少，速度上 $\Delta T$ 是正是负，质量上逐题比对再加重试成本。只看总正确数，会漏掉「错的是不同的题」。

## 8.5 推测解码

前面几节改变的是数据的存放和读取方式，每条请求仍然要逐轮生成。本节换一条完全不同的路，让一次目标模型计算确定多个输出：先由一个便宜的草稿猜出几个 token，再让目标模型一次验完。

### 8.5.1 草稿、验证、回退与正确性

前两节主要改变数据的存放和读取方式，每条请求仍要逐轮生成。假如能让一次目标模型计算确定多个输出，生成 256 个 token 就不必再执行同样多的轮次。普通 decode 里目标模型每次前向计算只生成一个 token；8.2 节的办法是把不同请求合并计算，让一次权重读取服务更多行。推测解码走的是另一条路：先为同一请求生成一段草稿序列，再由目标模型同时验证其中的多个 token。只要目标模型接受了多个草稿 token，一次计算就能确定多个输出。

先看最简单的贪心生成，每一步都选目标模型给出的概率最高的 token。假设草稿序列包含四个 token，目标模型分别计算各个 token 位置应当输出什么。前两个与草稿相同，第三个不同，那么最终保留前两个草稿 token，并在第三处输出目标模型选出的 token。第四个草稿 token 是在错误的第三个 token 之后生成的，也随之一并丢弃。下一轮从修正后的序列继续生成。如果四个草稿 token 全部匹配，目标模型通常还能在它们之后再生成一个 token。

图 8-29 展示的就是第三个 token 发生分歧时的处理顺序。目标模型虽然已经算出了后续 token 的验证结果，但第四个 token 依赖错误的第三个草稿 token，不能继续采用。一次验证最终留下两个匹配的草稿 token 和一个修正 token，共三个输出。

> 图 8-29（原文插图）：贪心验证的过程。**草稿序列是 a、b、c、d**（a、b、c、d、x 表示 token）；**验证结果是 a、b、x**——目标模型在第三个 token 位置选出 x，与草稿 c 不同。**第四个 token 及其后的验证结果作废**，下一轮从 a、b、x 继续生成。**「丢弃」标在 c、d 上，「保留」标在 a、b、x 上。方框表示序列中的 token 位置，不表示执行耗时。**

换成随机采样，就得让最终输出仍然服从目标模型的概率分布。设目标分布为 $p(x)$，草稿分布为 $q(x)$。先从 $q$ 中采样得到草稿 token $x$，再以如下概率接受它：

$$\alpha(x) = \min\left(1, \frac{p(x)}{q(x)}\right)$$

采样到 $x$ 并直接接受它的概率为 $q(x)\alpha(x) = \min(p(x), q(x))$。要达到目标概率 $p(x)$，还差 $[p(x) - q(x)]^{+}$。这里 $[z]^{+} = \max(z, 0)$，表示只保留正的差额。所以拒绝草稿 token 之后，把这个正差额归一化，再从得到的分布中重新采样。直接接受和拒绝后重新采样两种情况合起来，最终输出 $x$ 的概率就是 $p(x)$。

用一个只有 A、B 两个符号的例子走一遍。目标分布为 $p(A) = 1/4$、$p(B) = 3/4$。若草稿总是生成 A，就以 1/4 的概率接受 A，其余 3/4 的情况拒绝 A、改为输出 B。若草稿总是生成 B，则以 3/4 的概率接受 B，其余情况改为输出 A。两种方法最终都得到目标分布，但草稿的接受概率不同，执行效率也不同。

验证之后，KV 的有效长度要调整到已经确定的输出位置，丢弃的草稿 token 对应的 KV 不再参与后续计算。分页器按已经确定的输出长度更新块引用，采样器和语法检查器（按指定输出格式限制可选 token 的组件）也恢复到对应的状态。下一轮便从修正后的序列继续计算。

原书脚注 28（印刷 p.343）对应推测采样原文、推测解码原文、框架计数与预算笔记以及调研中的框架覆盖，基础概率算法、草稿路线和具体实现分别引用。

> 图 8-30（原文插图）：草稿恒为 A 时的两条路径。**接受 A 的概率 0.25；拒绝 A、输出 B 的概率 0.75。** 最终：$P(A) = 1/4$、$P(B) = 3/4$。

> 图 8-31（原文插图）：草稿恒为 B 时的两条路径。**接受 B 的概率 0.75；拒绝 B、输出 A 的概率 0.25。** 最终：$P(A) = 1/4$、$P(B) = 3/4$——**目标分布相同，但草稿的接受概率更高**（所以这种草稿更高效）。

先回答「为什么可能省时间」这个问题。验证多个位置的成本，几乎等于生成一个位置的成本。一轮 decode 的时间主要花在读一遍权重上，读完之后多算几行、也就是多个候选位置的额外算力开销很小。8.5.2 会给出实测数字：多 4 行矩阵运算约 65 GFLOP，只要约 0.2 ms。所以「一次读权重验证 5 个位置」和「一次读权重生成 1 个 token」大致等价，这是整个推测解码的经济学基础。

贪心验证的规则最简单：草稿 $c_1, c_2, \ldots, c_m$ 与目标模型的输出逐位置比对，一旦第 $k$ 位不同，就保留前 $k-1$ 个草稿 token，第 $k$ 位用目标模型的结果，后面全部丢弃。图 8-29 就是 $c_3 \ne x$ 的情形，留下 a、b，第 3 位改成 x，d 作废，一次验证得 3 个输出。

还有一种情况是全对还能多送一个。如果所有草稿都被接受，目标模型在第 $m+1$ 个位置上算出来的 token 也是免费的，因为那一行本来就算过了，于是还能多拿一个。这就是 8.5.2 里 $\mathbb{E}[N] = 1 + a + a^2 + \cdots + a^m$ 开头那个 1 的来历，也是公式里 $j$ 从 1 加到 $m$ 的含义。

随机采样不能照搬贪心那套，因为贪心的目标是挑最高概率的 token，而采样的目标是让输出的分布与目标模型一致。直接接受草稿的采样结果，最终分布会偏向草稿分布 $q$。修正分三步：先从 $q$ 采样得到 $x$；再以 $\min(1, p(x)/q(x))$ 的概率接受，草稿比目标更想要这个 token 时（也就是 $q > p$），用这个比例把它的超额概率压掉；若被拒绝，就从差额分布 $[p(x) - q(x)]^{+}$ 归一化后的分布中重新采样。把两条路径加起来，$q(x)\alpha(x) + (1-\sum_z q(z)\alpha(z)) \cdot \frac{[p(x)-q(x)]^+}{\sum_z [p(z)-q(z)]^+}$，结果正好是 $p(x)$。原文的结论是「直接接受和拒绝后重新采样两种情况合起来，最终输出 $x$ 的概率就是 $p(x)$」，不接受这个结论也没关系，但要知道它是被严格保证的。

两符号的例子可以复算一遍（笔记补充计算）：

- $p(A) = 1/4$、$q(A) = 1$（草稿恒为 A）：$\alpha(A) = \min(1, \frac{1/4}{1}) = 1/4$。以 1/4 概率输出 A，其余 3/4 拒绝后按差额分布重新采样，$[p-q]^+$ 只有 B 有正差额（$3/4 - 0 = 3/4$），归一化后就是确定地输出 B。最终 $P(A) = 1/4$、$P(B) = 3/4$。
- $q(B) = 1$（草稿恒为 B）：$\alpha(B) = \min(1, \frac{3/4}{1}) = 3/4$，其余 1/4 拒绝后差额只有 A（$1/4$），确定输出 A。最终分布相同。
- 两种草稿的期望接受率分别是 1/4 和 3/4，这就是 8.5.2 里 $a = 0.25$ 与 $a = 0.75$ 的来源。

验证后的状态回滚很重要，也很容易被忽略。草稿 token 已经写进了 KV，否则没法验证后面的位置，一旦被拒绝，必须把 KV 的有效长度截断到确认输出的位置，还要把分页器的块引用、采样器状态、语法检查器状态都恢复回去。换句话说，推测解码不是免费加速，它需要一套能做回滚的状态管理，这正好接上 8.3 的分页与引用计数机制。

这里有三处容易混。贪心验证与随机采样验证的差别在于，前者只需比对 argmax 是否一致，后者要按 $\min(1, p/q)$ 做接受—拒绝采样，才能保持目标分布。草稿接受概率 $a$ 与草稿质量也不完全是一回事，$a$ 高说明草稿分布接近目标分布，但即使 $a$ 很低，比如 1/4，推测解码也不会比普通 decode 慢，因为每轮至少还能拿到 1 个 token，这是 8.5.2 会强调的一点。还有草稿序列与最终输出序列，草稿是猜测，最终输出是被验过的，图 8-29 里 a、b、x 才是输出，c、d 从来不是。

> 推测解码是便宜的猜加一次验多个。贪心时逐位比对、一旦分歧就截断到分歧点；随机采样时必须用 $\min(1,p/q)$ 加差额重采，才能保证最终分布仍是目标分布。

### 8.5.2 每轮耗时与输出数量

推测解码既改变每轮耗时，也改变每轮最终输出的 token 数。设第 $r$ 轮耗时为 $T_r$，输出 $N_r$ 个 token，那么连续执行多轮之后，平均每个输出 token 的耗时为

$$\bar{t}_{\text{spec}} = \frac{\sum_r T_r}{\sum_r N_r}$$

举个反例就明白为什么要这么算。两轮各耗时 1.5 ms，分别输出 1 个和 5 个 token，总计 3 ms、6 个 token，平均每个 token 耗时 0.5 ms。如果先算每轮的平均值，再把 1.5 和 0.3 ms/token 等权平均，会得到 0.9 ms。这相当于让只输出一个 token 的轮次与输出五个 token 的轮次占相同权重。直接用总时间除以总 token 数，才能得到每个 token 的平均耗时。

#### 算例：草稿接受率如何决定每轮的平均输出数？（原文例题，印刷 p.344）

题干照抄原文。沿用两符号目标分布，并假设各 token 位置独立。每轮草稿生成四个相同符号，最终输出还包括拒绝时的修正 token，或全部接受后的额外 token。设前面的草稿 token 都已接受时，当前位置的接受概率为 $a$。每轮至少输出一个 token；要输出第二个，需接受第一个草稿 token，概率为 $a$；要输出第三个，需接受前两个，概率为 $a^2$。依次相加，平均每轮输出数为

$$\mathbb{E}[N] = 1 + a + a^2 + a^3 + a^4$$

上式每一项都表示「最终至少输出这么多个 token」的概率。草稿为 AAAA 时 $a = 1/4$，平均每轮输出约 1.33 个 token；为 BBBB 时 $a = 3/4$，平均输出约 3.05 个。

在 RTX PRO 6000 上，batch 1、2K 上下文的普通 decode 一轮 26.26 ms（实验 8-1）。验证 5 个位置时，读取的权重和 KV 与普通 decode 相同，多出的 4 行矩阵运算约 65 GFLOP，按 BF16 峰值的 62% 计只需约 0.2 ms，所以一轮验证仍按 26.26 ms 计。

实验 8-5 也观察到同样的现象：DFlash（一种前向一次就并行生成整段草稿的草稿网络）每轮生成 7 个草稿 token 并验证 8 个位置，中位耗时 15.2 ms，与同一配置下普通 decode 一步的 16.9 ms 相当。再加上查询草稿的 0.1 ms，一轮共 26.36 ms，两种草稿对应的平均每 token 耗时分别约为 19.8 和 8.64 ms，都快于 26.26 ms/token 的普通 decode。

验证几乎不增加一轮的时间，即使草稿大多被拒绝，每轮也至少得到一个 token，所以接受率低的 AAAA 同样能加速。

接受更多草稿 token 所节省的时间，也可能被查询开销抵消。要优于普通 decode，一轮总耗时须小于平均输出数乘以 26.26 ms。扣掉验证所需的 26.26 ms，AAAA 留给草稿查询的时间约为 8.7 ms，BBBB 约为 53.9 ms。图 8-32 把这两个交点画在查询成本轴上。

使用草稿之前的准备工作也要计入总时间。若建立上下文索引需要 2 秒，而 BBBB 草稿每个输出 token 能节省约 $26.26 - 8.64 \approx 17.6$ ms，那么生成约 114 个 token 就能抵消这 2 秒开销。输出 256 个 token 的请求用普通 decode 约需 6.72 秒；先用 2 秒建立索引再用 BBBB 草稿，期望约 4.22 秒完成。如果索引可以提前建立并由多个请求共用，这项开销还能由更多输出分摊。

原书脚注 29（印刷 p.345）对应上下文草稿的分布与成本计算及有理数穷举结果。算例采用二符号目标分布；RTX PRO 6000 上的每轮时间见 AAAA、BBBB 与含 2 秒索引的 256 token 请求；普通 decode 一轮 26.26 ms 取自实验 8-1 的逐轮记录，DFlash 的每轮耗时取自实验 8-5 的逐步记录。脚注 30 对应推测采样原文、推测解码原文、框架计数与预算笔记以及调研中的框架覆盖。

> 图 8-32（原文插图）：两符号目标分布、每轮生成四个草稿 token 的情形。**横轴为每轮草稿查询时间（ms，0 到 60），纵轴为每输出 token 耗时（ms，0 到 70）**。三条曲线：**AAAA、BBBB 以及「普通 decode」（水平直线 26.26 ms/token）**。每轮验证固定 26.26 ms，每个输出 token 的耗时 = 一轮耗时 ÷ 平均输出数；**没有提前停止，额外 token 计入输出数**。**图中的点标出查询耗时为 0.1 ms 的算例；AAAA、BBBB 分别在查询约 8.7、53.9 ms 处与普通执行相交**——也就是说，只要草稿查询的开销低于这个值，推测解码就比普通 decode 快。

$\bar t_{\text{spec}} = \sum T_r / \sum N_r$ 这种先加总再相除的算法是本节第一个坑。原文那个反例很有说服力，两轮各 1.5 ms，分别输出 1 个和 5 个 token：

- 正确算法：$(1.5 + 1.5) / (1 + 5) = 3/6 = \mathbf{0.5}$ ms/token；
- 错误算法，先算每轮平均再平均：$(1.5/1 + 1.5/5)/2 = (1.5 + 0.3)/2 = \mathbf{0.9}$ ms/token。

错在它给了「只输出 1 个 token 的轮」和「输出 5 个 token 的轮」相同的权重，而按 token 数加权的正确做法自然让产出多的轮占更大权重。这是调和平均与算术平均的经典陷阱。凡是「单位成本」类的指标，ms/token、token/s、J/request 都一样，都要用总量相除，不能对比率做算术平均。

$\mathbb{E}[N]$ 也可以复算（笔记补充计算）：

- AAAA（$a = 1/4$）：$1 + 0.25 + 0.0625 + 0.015625 + 0.00390625 = \mathbf{1.3320}$，约 1.33；
- BBBB（$a = 3/4$）：$1 + 0.75 + 0.5625 + 0.421875 + 0.31640625 = \mathbf{3.0508}$，约 3.05。

这个式子的概率解释要理解：$\mathbb{E}[N] = \sum_{k=0}^{m} P(N \ge k+1)$。每一项 $a^k$ 都是「至少输出 $k+1$ 个 token」的概率，也就是前 $k$ 个草稿全部被接受的概率。这也解释了「每轮至少输出 1 个 token」那一项常数 1 的来源：$P(N \ge 1) = 1$，永远成立。

接着算平均每 token 耗时（笔记补充计算）：

- AAAA：一轮是 26.26（验证）加 0.1（查询）等于 26.36 ms，除以 1.3320 得 19.79，约 19.8 ms/token；
- BBBB：26.36 / 3.0508 = 8.64 ms/token。

两者都小于 26.26 ms/token，所以即使草稿很差，AAAA 只有 25% 的接受率，也仍然加速。

那为什么验证 5 个位置几乎不增加时间，原文的账是这样的：多出的 4 行矩阵运算约 65 GFLOP，按 $503.8 \times 0.62 = 312.36$ TFLOP/s 计，$65 \times 10^9 / (312.36 \times 10^{12}) = 0.208$ ms，约 0.2 ms（笔记补充复算）。相对 26.26 ms 的固定成本来说可以忽略，而那笔固定成本主要是读权重。这就是「decode 是带宽受限」这个判断的直接应用：既然一轮的时间由读多少字节决定，多算几行就几乎免费。

查询交点是这样来的：要优于普通 decode，需 $\frac{26.26 + T_q}{\mathbb{E}[N]} < 26.26$，也就是 $T_q < 26.26 \times (\mathbb{E}[N] - 1)$。

- AAAA：$26.26 \times 0.3320 = \mathbf{8.72 \approx 8.7}$ ms；
- BBBB：$26.26 \times 2.0508 = \mathbf{53.85 \approx 53.9}$ ms。

这意味着草稿查询（建立索引、跑草稿网络、查表）的开销预算差别很大。草稿质量高的时候，你花得起 53.9 ms 去找草稿；草稿质量低的时候，查询必须快过 8.7 ms，否则不如老老实实 decode。

准备成本那 2 秒建索引的摊销也复算一遍：BBBB 每 token 省 $26.26 - 8.64 = 17.62$，约 17.6 ms，$2000/17.62 = 113.5$，约 114 个 token 回本。256 个 token 的请求，普通 decode 是 $256 \times 26.26 = 6723$ ms，即 6.72 s；用 BBBB 是 $2000 + 256 \times 8.64 = 2000 + 2212 = 4212$ ms，即 4.21 s，原文写作约 4.22 s。

工程结论是准备成本要能被多个请求或更多输出摊薄。如果每条请求都要重新建 2 秒的索引，而它只输出 20 个 token、省 0.35 秒，那就亏了。这也解释了为什么「上下文查找草稿」特别适合 Agent 场景，索引建立在系统提示和工具定义上，可以被大量请求共用。

三处易混。每轮耗时 $T_r$ 与每 token 耗时不是一回事，前者是这一轮花了多久，后者还要除以这一轮输出几个；轮数变少但每轮变贵，只有每 token 耗时才知道到底赚还是亏。接受率 $a$ 与平均输出数 $\mathbb{E}[N]$ 之间，$\mathbb{E}[N] \approx 1/(1-a)$ 只在草稿很长时才近似成立，草稿长度 $m$ 有限时是 $1 + a + \cdots + a^m$，会被 $m+1$ 封顶。验证开销与查询开销也要分开算，前者是目标模型跑一遍，约 26.26 ms，与普通 decode 相同，后者是草稿本身的开销 $T_q$。

> 推测解码的收益公式是用 $26.26 + T_q$ 的时间换 $\mathbb{E}[N]$ 个 token。只要 $T_q < 26.26(\mathbb{E}[N]-1)$ 就比普通 decode 快，而且必须用总时间除以总 token 数来算每 token 耗时。
### 8.5.3 草稿来源与串行、并行生成方式

四个草稿 token 能省下多少时间，既取决于其中有多少通过了验证，也取决于生成这段草稿要花多久。实际系统可以从上下文中查找草稿，也可以调用额外的网络来生成草稿，两种选择带来的准备时间和内存占用完全不同。

上下文查找的做法是从输入或已有回答里找出重复片段，主要开销在匹配和建立索引上。独立小模型逐步生成草稿，代价是需要额外保存自己的权重和 KV。EAGLE 类方法把目标模型的中间表示送进一个较小的预测网络；DFlash 类方法并行生成多个草稿 token。模型自带的 MTP 头则利用联合训练得到的预测能力来生成草稿。

把每轮拆成生成草稿、准备验证、目标验证和确定输出这四个阶段，就能逐项比较这些方法。以实验 8-5 的 DFlash 草稿网络为例，它的权重约 1.95 GiB（2.10 GB）。按 batch 1 的有效带宽计，也就是 26.26 ms 读取 15.44 GB、约 588 GB/s，这个网络前向一次约需 3.57 ms。若用它逐个生成四个草稿 token，要前向四次，共 14.28 ms；像 DFlash 那样并行生成整段草稿，只需前向一次，约 3.57 ms。目标验证都需要 26.26 ms。如果最终每轮平均输出 3 个 token，串行方式每个 token 约需 $(14.28 + 26.26)/3 \approx 13.5$ ms，并行方式约需 $(3.57 + 26.26)/3 \approx 9.9$ ms。这时候的加速来自草稿生成时间的缩短。

再设并行生成的草稿接受率较低，平均输出数降到 2 个，平均每个输出 token 的耗时就升到 $(3.57 + 26.26)/2 \approx 14.9$ ms，反而慢于串行方式。更快的草稿生成节省了 10.7 ms，但每轮输出变少，每个输出 token 分摊的时间随之增加，整个请求因而变慢。

原书脚注 30 与 8.5.1 的脚注相同，对应推测采样原文、推测解码原文、框架计数与预算笔记以及调研中的框架覆盖，基础概率算法、草稿路线和具体实现分别引用。

四条草稿路线可以列成一张对比表：

| 路线 | 草稿从哪来 | 主要开销 | 需要额外内存吗 |
| --- | --- | --- | --- |
| 上下文查找 | 输入或已有回答里的重复片段 | 匹配 + 建立索引 | 索引（可放主机内存） |
| 独立小模型 | 另一个（更小的）模型逐步生成 | 前向 + 自己的 KV | 草稿模型权重 + 它的 KV |
| EAGLE 类 | 目标模型的**中间表示**喂给小的预测网络 | 预测网络前向 | 预测网络权重 |
| DFlash 类 | 并行生成多个草稿 token | 一次前向出整段草稿 | 草稿网络权重 |
| 模型自带 MTP 头 | 联合训练得到的预测头 | 头的前向 | MTP 头参数（较小） |

四阶段那套分解是一种很好用的算账框架，每个方法其实只是在改变这四个阶段里某一个的耗时。上下文查找把「生成草稿」换成「查表」；DFlash 把「生成草稿」从 $m$ 次前向压成 1 次；EAGLE 用中间表示让预测网络更准，从而提高接受率。

DFlash 那串数字复算一遍（笔记补充计算）：

- 有效带宽：$15.44\ \text{GB} / 0.02626\ \text{s} = 588.0$ GB/s，与原文的约 588 GB/s 一致；
- 草稿网络一次前向：$2.10\ \text{GB} / 588\ \text{GB/s} = 3.57$ ms。这里用的是「权重 2.10 GB 除以有效带宽」，也就是假设一次前向只读一遍权重；
- 串行四次：$4 \times 3.57 = 14.28$ ms；
- 串行每 token：$(14.28 + 26.26)/3 = 40.54/3 = \mathbf{13.51 \approx 13.5}$ ms；
- 并行每 token：$(3.57 + 26.26)/3 = 29.83/3 = \mathbf{9.94 \approx 9.9}$ ms；
- 并行省下的就是草稿生成时间：$14.28 - 3.57 = 10.71 \approx 10.7$ ms。

并行更快并不是无条件成立的。如果并行草稿的接受率更低，平均输出从 3 降到 2，并行就变成 $(3.57+26.26)/2 = \mathbf{14.92 \approx 14.9}$ ms，反而慢于串行的 13.5 ms。更快的草稿生成被更低的接受率吃掉了，这个反例很干净。

把这件事形式化一下（笔记补充）：串行方案每 token 成本是 $\frac{T_q^{(\text{ser})} + T_v}{N^{(\text{ser})}}$，并行方案是 $\frac{T_q^{(\text{par})} + T_v}{N^{(\text{par})}}$。因为 $T_v = 26.26$ ms 是两边共同的大头，胜负就由省下的草稿时间与少产出的 token 数共同决定。记 $\Delta T_q = T_q^{(\text{ser})} - T_q^{(\text{par})}$ 为省下的草稿时间，$\Delta N = N^{(\text{ser})} - N^{(\text{par})}$ 为少产出的 token 数，则只有当 $\frac{\Delta T_q}{\Delta N} > \frac{T_q^{(\text{ser})} + T_v}{N^{(\text{ser})}}$ 时并行才划算。代入本例：$\Delta T_q = 14.28 - 3.57 = 10.71$ ms，$\Delta N = 3 - 2 = 1$，串行每 token 耗时是 $(14.28+26.26)/3 \approx 13.5$ ms，$10.71 < 13.5$ 不满足，所以并行反而更慢。省下的草稿时间必须大于接受率下降造成的损失。

工程上的判断顺序应该是先把接受率做上去，再优化草稿生成速度。接受率不行，再快的草稿也是白跑，这从 8.5.2 的 $\mathbb{E}[N]$ 公式也能看出来，$a$ 是唯一决定每轮输出数的量。

三处易混。草稿生成时间与草稿查询时间，8.5.2 里的 $T_q$ 是「查询草稿」的总开销，这里把 $T_q$ 具体化为草稿网络一次前向，$m$ 次或者 1 次。EAGLE 与 DFlash 的分工也不同，EAGLE 用中间表示喂小预测网络来提高准确性，DFlash 一次前向出整段草稿来缩短延迟，一个改质量，一个改速度。草稿模型与 MTP 头则在于，前者是独立网络，要存权重和 KV，后者是模型自带、联合训练出来的预测头，参数小，但要求训练时就带上。

> 草稿的来源决定了 $T_q$、内存、接受率三者的组合。并行生成能省下 10.7 ms 的草稿时间，但如果接受率从 3 降到 2，这点便宜立刻被吃掉。

### 8.5.4 草稿长度的动态选择与并发竞争

确定了草稿来源，还得决定每轮生成多长。草稿越长，一轮能够输出的 token 上限越高，但只有前面的 token 全部接受，后面的才有机会进入最终输出。设前面的草稿 token 都已接受时，第 $j$ 个 token 的条件接受概率为 $a_j$，则长度为 $m$ 的草稿对应的平均输出数为

$$\mathbb{E}[N_m] = 1 + \sum_{j=1}^{m} \prod_{i=1}^{j} a_i$$

草稿长度从 $m-1$ 增至 $m$ 时，平均多输出 $\Delta N = \prod_{i=1}^{m} a_i$ 个 token。设为此增加 $\Delta T$ 的时间，原先一轮耗时为 $T$、平均输出 $N$ 个 token，平均每个输出 token 的耗时就是 $T/N$。要使增加草稿长度后平均每个输出 token 的耗时更短，需要满足 $(T + \Delta T)/(N + \Delta N) < T/N$，整理得

$$\frac{\Delta T}{\Delta N} < \frac{T}{N}$$

也就是说，为新增输出付出的平均时间必须低于原来的平均每 token 耗时。接受概率需要逐项相乘，越靠后的草稿 token 保留下来的概率越低，增加它们就越难获得足够的时间收益。

预设执行形状也会影响新增时间 $\Delta T$。如果本次验证四个或五个 token，都把各 token 的特征向量补齐为八行矩阵、使用预先准备的八行计算图，增加一个 token 所需的额外计算较少；若待验证的 token 从八个增至九个，就要补齐为十六行矩阵并改用相应计算图，计算量会突然增加。

并发请求数同样影响推测解码的收益。低负载时，多行验证可以利用闲置算力；高负载时，普通批处理已经充分共享了权重，草稿生成和验证还要与其他请求争用加速器和内存。

一组实测比较了不同草稿长度。K7 和 K15 分别表示每轮生成 7 个和 15 个草稿 token 的配置。Qwen3-8B／DFlash 的短提取任务在并发 1 时，普通 decode、K7、K15 的完整耗时中位数约 90.0、30.6、29.4 ms。普通执行改为 K7 节省约 59 ms，从 K7 改为 K15 只再节省约 1.2 ms。逐轮记录里还出现两种块长都只接受一个草稿 token 的轮次：K7 丢弃六个草稿 token，K15 丢弃十四个，最终输出长度相同。更大的验证块增加了计算量，却没有在这一轮带来更多输出。

所以动态调整草稿长度时可以用上面的判断条件：对接受概率高、增加验证位置所需时间短的请求，生成更长的草稿；对草稿前几个位置就经常通不过验证，或需要改用更大执行形状的请求，缩短块长。确定草稿长度时还要给目标模型和草稿模型的 KV 留出空间，再按第 8.3 节的方法决定接收多少请求。

原书脚注 31（印刷 p.346）对应 DFlash 同执行器对照及逐请求阶段观测。实验在低并发下按固定顺序执行给定短题集，并发 1 通过短题的普通、K7、K15 时间中位数分别为 90.02、30.58、29.43 ms，配对输出共 32 对。

#### 练习 8-7 ・推导：多长的草稿能使平均每个输出 token 的耗时最短？（印刷 p.346）

题干照抄原文。固定草稿接受概率 $a = 3/4$，计算草稿块长为 1、2、4、8 时每轮平均输出的 token 数。沿用 8.5.3 节 RTX PRO 6000 上的数据并保留一位小数：一轮验证 26.3 ms，草稿网络逐个生成、每个草稿 token 3.6 ms，即 $T_m = 26.3 + 3.6m$ ms，求每种块长的平均每个输出 token 的耗时。再设草稿按每组 4 个位置执行，不足一组也按整组计时，即 $T_m = 26.3 + 3.6 \times 4\lceil m/4 \rceil$ ms，比较块长 4 与 5，并用边际条件解释选择。

参考解答（笔记补充，非原文）：

- $\mathbb{E}[N_m] = 1 + \sum_{j=1}^{m} a^j$：$m=1$ 得 1.75；$m=2$ 得 2.3125；$m=4$ 得 3.0508；$m=8$ 得 3.6997。
- 逐个生成，$T_m = 26.3 + 3.6m$：$m=1$ 是 $29.9/1.75 = \mathbf{17.1}$ ms；$m=2$ 是 $33.5/2.3125 = \mathbf{14.5}$ ms；$m=4$ 是 $40.7/3.0508 = \mathbf{13.3}$ ms；$m=8$ 是 $55.1/3.6997 = \mathbf{14.9}$ ms。最短落在 $m = 4$，约 13.3 ms/token。
- 按每组 4 个位置执行：$m=4$ 时 $T_4 = 26.3 + 3.6 \times 4 = 40.7$ ms，仍是 $40.7/3.0508 = \mathbf{13.3}$ ms；$m=5$ 时因 $\lceil 5/4 \rceil = 2$，$T_5 = 26.3 + 3.6 \times 8 = 55.1$ ms，$\mathbb{E}[N_5] = 3.2881$，得 $55.1/3.2881 = \mathbf{16.8}$ ms，比 $m=4$ 更差。
- 边际条件：$\Delta T/\Delta N = (55.1 - 40.7)/(3.2881 - 3.0508) = 14.4/0.2373 = \mathbf{60.7}$ ms，而原来的平均每 token 耗时 $T/N = 40.7/3.0508 = \mathbf{13.3}$ ms。$60.7 \gg 13.3$，不满足 $\Delta T/\Delta N < T/N$，所以应该选 $m = 4$。

$\mathbb{E}[N_m] = 1 + \sum_{j=1}^{m} \prod_{i=1}^{j} a_i$ 是 8.5.2 那个公式的一般化版本，每个位置有自己的条件接受概率。当所有 $a_i$ 都等于 $a$ 时，它就退化成 $1 + a + a^2 + \cdots + a^m$。

越往后越难赚，数学根源在 $\Delta N = \prod_{i=1}^{m} a_i$。如果有 4 个位置、$a = 3/4$，那么加第 1 个位置的边际产出是 $a = 0.75$，第 2 个是 $a^2 = 0.5625$，第 3 个是 $a^3 = 0.4219$，第 4 个是 $a^4 = 0.3164$，到第 8 个只剩 $a^8 = 0.1001$。而每加一个位置的成本 $\Delta T$ 基本恒定，3.6 ms，或者按整组算是 14.4 ms。收益指数衰减、成本线性增长，交点必然落在某个有限的 $m$ 上，这就是 8.5.4 的核心直觉。

执行形状会让 $\Delta T$ 突变，这和 8.2.4 的 CUDA Graph 是同一件事。验证 4 个或 5 个位置都补齐到 8 行矩阵，成本几乎一样，而验证 9 个位置就要跳到 16 行矩阵，成本跳一级。所以 $\Delta T$ 随 $m$ 的变化是阶梯状的，谈不上连续，最优 $m$ 总是落在阶梯的某个台阶边缘上，本例里正好是 4，也就是一组 4 个位置。

练习里的关键数复算一遍（笔记补充计算）：

- $m=8$ 的 $\mathbb{E}[N_8] = 1 + 0.75 + 0.5625 + 0.421875 + 0.316406 + 0.237305 + 0.177979 + 0.133484 + 0.100113 = 3.6997$；
- $m=8$ 的每 token 耗时 14.9 ms 反而比 $m=4$ 的 13.3 ms 差，这是收益衰减的直接体现：多花 14.4 ms 只多换来 0.649 个 token，也就是 $3.6997 - 3.0508$，边际成本 $14.4/0.649 = 22.2$ ms，大于 13.3 ms。

并发的影响要单独记一句：推测解码吃的是闲置算力。

- 低负载时，batch 里空闲的执行位置多，多行验证几乎不增加时间，收益接近理论上限。
- 高负载时，普通批处理已经把权重复用到了极致，也就是 8.2.1 的 $b_{\text{KV}}$，此时草稿网络的前向要和目标模型争带宽与算力，草稿还要额外占显存存 KV，所以收益会明显缩水。
- 这也解释了 8.6.3 综合算例里方案 D 为什么在 16 条请求并发的场景仍然有效：方案 D 用的是共享前缀加推测，而且这张卡的一轮 decode 时间几乎不随 batch 和上下文变化，还有余量承担验证的额外行数。

K7 与 K15 的实测差距只有 1.2 ms（30.6 变到 29.4），却把验证块从 7 增到 15，多验证 8 个位置，收益几乎为零。原因就是逐轮记录里那两种块长都只接受一个草稿 token 的轮次，K7 丢弃六个，K15 丢弃十四个，最终输出长度相同。这是「该停就停」的实证。动态草稿长度的判据因此是两句话：接受概率高、$\Delta T$ 便宜，就加长；前几个位置就常挂、要跨执行形状，就缩短。

三处易混。$\mathbb{E}[N_m]$ 与 $\Delta N$ 不是一回事，前者是总平均输出数，后者是再长一位能多换多少，决策看的是后者这个边际量而不是前者这个总量。草稿长度上限 $m$ 与「至少输出数 1」也不冲突，即使所有草稿都被拒绝，每轮仍输出 1 个，来自验证的第一行，所以 $m$ 增加不会让每轮输出变成 0。还有 $\Delta T$ 的连续性，它被执行形状（8 行或者 16 行）切成阶梯，谈不上平滑，做最优 $m$ 的选择时要用阶梯函数，不能用线性函数。

> 草稿该多长，看边际：$\Delta T/\Delta N < T/N$ 才值得加长。接受概率是逐项相乘的，越靠后的草稿 token 越难赚回它多花的时间，而执行形状还会让成本跳台阶。

### 8.6.1 到达率、排队、准入与取消

8.2 到 8.5 节讨论的都是怎么改变一个实例的内存占用和执行方式：批怎么组、KV 怎么放、数值怎么压、草稿怎么投机。在线服务还要多回答一层问题，请求是不断到达的。一条请求还没做完，下一条已经进了队列；一条请求在等工具返回的时候，模型的计算暂停了，它占着的 KV 却一行都不能少。调度器因此要同时管两件事，既安排此刻要算的批次，也为那些正在生成或等着继续执行的请求保留状态。

这些没做完的请求要占多少空间，取决于系统里平均有多少条请求。稳定服务中这个平均值由 Little 定律给出：

$$\bar{n} = \lambda \bar{T}$$

$\lambda$ 是平均到达率，$\bar{T}$ 是请求在系统里的平均停留时间。把观察期间每条请求的停留时间相加，再除以观察时长，得到的就是系统内的平均请求数。原书举了两个数：每秒到达 4 条、每条平均停留 0.5 秒，系统里平均有 2 条；平均停留时间涨到 2 秒，就变成 8 条。

这个式子的三个量单位是配的：$\lambda$（请求/秒）乘 $\bar{T}$（秒）得到 $\bar{n}$（条，无量纲）。复算原文那两个例子，$4 \times 0.5 = 2$、$4 \times 2 = 8$，都对得上。它更好用的地方在反推：12 GiB 的预留空间除以每条长请求 1188 MiB，能同时容纳 10 条请求的状态，而每条请求要跑 7 秒，可持续的到达率上限约为 $10/7 \approx 1.43$ 请求/秒。这个数是我按前面的容量结论算的，原书只给了公式和那两个例子。

系统里的请求状态并不一样：有的在排队，有的正在计算，还有的只是把状态留着。增大 batch 能提高输出吞吐，但 KV 读取、计算和其他开销会逐渐吃掉这种增长。处理速度跟不上到达率的时候，新请求就在队列里越堆越多，等待时间跟着变长。

8.2.1 已经说明，batch 增到一定程度后"每个输出 token 的读取量"不再明显下降，KV 项开始主导，吞吐也就不再随 batch 线性上涨。上面那句"处理速度无法继续随到达率提高"讲的正是这个饱和点。到达率一旦越过饱和吞吐，队列必然累积，8.6.2 里"16/s 反而更差"的机理就在这里。

"等待中的请求"贵在哪儿？它已经开始了，所以不算排队；它在等人，所以也不在计算；但它的状态必须留着，一旦释放，工具返回后一切重来。这就是"仅保留状态"那一类请求的成本。8.3.3 里 DeepSeek V4.1 把编码器 SWA 放到主机 DRAM 短期保留，压的就是这类成本。

准入控制决定要不要开始处理一条新请求，接之前先看两件事。一个是空间：$M_w + M_{\mathrm{KV}} + M_a + M_u \le C$ 这个 8.1.2 的容量约束式还成立吗。另一个是时间：现在接进来，它能在截止时间前跑完吗，最坏情况下 TTFT 还要加上排队时间。

原书那条短请求就是时间线的极端情形。0.196 秒首输出加 6.76 秒生成，已经用掉 6.95 秒，余量只剩 0.05 秒，再多排 0.1 秒就会超时。对这种请求，"接收"本身就是一个需要算的决策。提前识别出来，可以拒绝、转交其他实例，或者换更快的执行配置。

取消是反方向的动作。请求失去使用价值时，停止给它安排后续迭代，等已经提交的加速器操作做完，再释放空间。8.3.2 讲过机制，这里讲的是策略，顺序不能颠倒，因为已提交的 kernel 还在读显存。取消在服务层面还多一层含义，也就是判断"失去使用价值"：客户端断连算，已经超时也算。已经超时的请求继续跑只会白白消耗算力和能耗，8.6.3 会把这笔能耗算进成本。

本节最后一句原话是"这些优化会相互影响"，它其实是全章的收束。KV 压缩让实例能同时接收更多请求，较大的 batch 又让普通 decode 更有效地共享权重，两件事一叠加，闲置算力变少，推测解码的相对收益也就跟着下降。所以任何一个优化都不能孤立地评价，必须在同一组条件、同一套指标下比较。接下来的 8.6.3 就把这些变化放到同一组请求上，算一算组合之后的执行时间和内存占用。

三处容易混的地方。到达率 $\lambda$ 和吞吐方向相反：前者是"来得多快"，由用户决定；后者是"跑得多快"，由系统决定；$\lambda$ 超过吞吐，队列就开始累积。停留时间 $\bar{T}$ 也不等于执行时间，它还包含排队和等待工具的时间，是在系统里的全部时间。至于"等待中的请求"和"排队的请求"，前者可能已经分配过 KV 了，后者还没进引擎，二者对内存和调度的影响不同。

原书这一节在印刷 p.347（节级页次取自章末速查表的"出处"列）。

把这两条线放在一起看：请求在系统里待多久乘上来得多快，就是系统里同时有多少条，这个数决定了要为状态留多少内存；准入控制要守的则是内存够不够和来不来得及两条线，缺一条都会让服务在过载时失控。

### 8.6.2 质量与 SLO 约束下的有效吞吐

只看队列长度和完成速度，回答不了一个问题：用户拿到的答案是不是能用。8.4.4 的质量实验里出现过错误答案，排队则会制造"正确但迟到"的回答。两种损失一起计入，才能评价服务效果。

设观察窗口长为 $T_{\text{obs}}$，第 $i$ 条请求正确时 $Q_i = 1$，按期完成时 $D_i = 1$。按完成的请求数计量，有效吞吐为

$$R_{\text{good}} = \frac{\sum_i Q_i D_i}{T_{\text{obs}}}$$

分子只数正确且按期完成的请求。把分子换成全部完成的请求数，得到的就是完成吞吐。两个数的差距说明有多少处理能力花在了错误或迟到的答案上。

这个差距有多大，有一组实测。Qwen3-8B 检索实验用相同的八道题，要求请求在到达后 3 秒内正确完成，比较逐个接收请求、连续批处理、一次提交全部请求三种方式。每次实验提交 16 条请求，全部实验共生成 336 次回答，其中 294 次正确，只有 155 次同时满足时限，剩下 139 次正确回答因为返回太晚，仍然不满足服务要求。

到达率 1/s 时，两种在线策略的有效吞吐都约为 0.90 req/s，每批工作少，逐个接纳也能及时处理大部分正确请求。到达率升到 4/s，逐个接纳的完成吞吐约 1.22 req/s，有效吞吐却掉到 0.31 req/s，队列变长，不少正确输出越过了期限；连续批处理把完成吞吐提到约 2.33 req/s，有效吞吐约 1.02 req/s，更多请求在期限内完成。把连续模式的到达率再推到 16/s，完成吞吐只涨到约 2.38 req/s，有效吞吐反而降到约 0.60 req/s，减少约 41%。完成吞吐基本不再增长，多来的请求主要变成了排队时间。就这组窗口而言，4/s 比 16/s 按时返回了更多正确答案。选服务配置时，先找出有效吞吐开始下降的那个到达率，再限制新接收的请求数，别让排队时间无限拉长。

计时口径这里有一句话很关键：逐个接收请求时，其他请求虽然没进引擎，却仍在应用队列里等着。计时应该从请求原定的到达时刻开始，把引擎外的等待也算进去。把本节的几组测量放在一起看，加速器每秒输出多少 token、单条请求要等多久、每秒有多少请求正确且按期完成，这几件事得分开算，互相代替不了。

原书脚注 32（印刷 p.347–348）交代了这组数据的来路：服务与能量原始记录，同一设备、八道题、七条件各三个 16 请求窗口；同题跨条件输出一致，42 个错误来自同一道题。吞吐表取各窗口指标的中位数。每个窗口包含 16 条请求，p95 按排序后向上取整的位置计算，得到的就是最大值。NVML 与 RAPL 组件计数窗口略宽于请求窗口，其他服务仍在运行。

> 图 8-33（原文插图）：横轴为"接纳策略；下行为到达率（req/s）"，七组条件依次是**逐个 1、逐个 4、逐个 16、连续 1、连续 4、连续 16、突发一次到达**；纵轴为**完成吞吐（req/s）**，0.0 到 3.0。**柱为全部完成请求的吞吐中位数，圆点为各窗口结果**（每种条件使用三个 16 请求窗口）。**时间从计划到达起计算。**

> 图 8-34（原文插图）：横轴顺序与纵轴范围与图 8-33 完全相同，纵轴改为**"正确且按期完成（req/s）"**。图注说明：**分子仅计正确且在 3 秒内完成的请求；两图的差额来自错误或迟到的回答。** 对照读法：逐个 4 的柱子明显比连续 4 矮，说明在相同到达率下，接纳策略决定了"及格率"。

$R_{\text{good}}$ 把"快"和"对"压进一个数，这是本章所有分析的落点。$Q_i$ 管对不对，来自 8.4.4 的质量实验；$D_i$ 管来不来得及，来自 SLO 和完成时限；分母 $T_{\text{obs}}$ 是观察窗口。两者相乘意味着错了或晚了都记 0，这比完成吞吐严格得多，也更接近用户的真实感受。

复算一遍刚才那组数：336 次回答中 294 次正确、155 次按时，正确率是 $294/336 = 87.5\%$，加上时限只剩 $155/336 = 46.1\%$。因为"太晚"而丢掉的是 $294 - 155 = 139$ 次，占正确回答的 $139/294 = 47.3\%$。也就是说，迟到造成的损失和错误造成的损失几乎一样大（139 对 42）。而脚注 32 说 42 个错误全部来自同一道题，错误是集中在一个任务上的系统性失败，迟到却是普遍性的。这个对比很说明问题：在服务系统里，排队造成的损失往往比模型能力造成的损失更大，也更分散。

三个到达率下逐个与连续的对比可以排成一张表（比值为笔记补充计算；1/s 条件下原文只给了有效吞吐约 0.90 req/s）：

| 到达率 | 策略 | 完成吞吐（req/s） | 有效吞吐（req/s） | 有效/完成 |
| --- | --- | --- | --- | --- |
| 1/s | 逐个 | （原文未给） | 约 0.90 | — |
| 1/s | 连续 | （原文未给） | 约 0.90 | — |
| 4/s | 逐个 | 约 1.22 | 约 0.31 | 25.4% |
| 4/s | 连续 | 约 2.33 | 约 1.02 | 43.8% |
| 16/s | 连续 | 约 2.38 | 约 0.60 | 25.2% |

"16/s 反而比 4/s 差"是这一节点睛的地方。完成吞吐从 2.33 只涨到 2.38，几乎不动，有效吞吐却从 1.02 掉到 0.60，跌掉 41%（$1.02 - 0.60 = 0.42$，$0.42/1.02 = 41.2\%$ ✓）。多来的请求没有变成更多产出，只变成了更长的队列。这就是过载：系统的产能已经饱和，再多的输入只增加等待，而等待会把本来能及格的答案拖成不及格。

工程上的结论可以直接拿来用。先做扫描，找出有效吞吐开始下降的到达率，然后在那里设置限流（rate limit）。这比把 GPU 塞满更划算，因为超载不增产，反而减产。

最后回到计时口径。如果测试脚本把请求攒在自己手里，只在提交时才"开始计时"，就会系统性地低估延迟，测出来的有效吞吐虚高。这是做服务 benchmark 最容易犯的错误之一。

三处易混。完成吞吐和有效吞吐，前者数跑完了多少，后者数跑对且按时了多少，两者的差就是浪费掉的处理能力。错误和迟到是两种不同的质量损失，错误来自数值格式和实现（8.4.4），迟到来自排队（8.6.1），$R_{\text{good}}$ 把它们合并成一个指标，但排查原因时要分开看。到达率和并发数也不是同一个量，前者是每秒来几条，后者是同时在系统里有几条，二者由 Little 定律联系。

原书这一节在印刷 p.347–348（节级页次取自章末速查表的"出处"列）。

有效吞吐只数正确且按期完成的请求；实践上要先扫出有效吞吐开始下降的到达率，然后主动限流，因为过载不增产，反而减产。

### 8.6.3 配置、加速器与完整任务成本

比较配置之前，得先把实测换算成处理速度。批处理、精度和缓存设置定下来之后，用完成的工作量除以占用加速器的时间，就得到各阶段的实际处理速度：prefill 速度 $r_P$ 按每秒处理的新输入 token 计，decode 速度 $r_D$ 按每秒完成的 decode 调用计。批内多条请求共享一次执行时，每条请求都算完成了一次调用，占用时间只计一次。

一条请求有 $L$ 个新输入 token、输出 $G$ 个 token，它占用加速器的时间（以 GPU 秒计）为

$$t_{\text{GPU}} = \frac{L}{r_P} + \frac{G-1}{r_D}$$

手头没有同条件的测量时，可以用规格乘以效率来估算：prefill 时间取矩阵运算量除以峰值算力与算力效率之积，decode 一轮的时间取读取的权重与 KV 字节数除以峰值带宽与带宽效率之积。下面这张表是实验 8-1 在 RTX PRO 6000 上测得的效率。一轮 decode 取引擎逐轮记录中不含 prefill 的轮次；客户端看到的输出间隔还包括交付时间，会略长一些，例如 8.1.1 节的 26.5 ms。

| 2K 上下文、无共享前缀 | batch 1 | batch 4 | batch 16 | batch 64 |
| --- | --- | --- | --- | --- |
| 每轮读取的权重与 KV | 15.44 GB | 16.34 GB | 19.97 GB | 34.46 GB |
| 按 1792 GB/s 读取所需时间 | 8.62 ms | 9.12 ms | 11.14 ms | 19.23 ms |
| 实测一轮 decode | 26.26 ms | 26.62 ms | 27.44 ms | 29.63 ms |
| decode 带宽效率 | 33% | 34% | 41% | 65% |
| prefill 算力效率 | 62% | 61% | 61% | 58% |

> 「表格按原文语义还原」（原文表头为两行，第一行为"2K 上下文、无共享前缀"，第二行为四个 batch 档位。）

decode 效率随 batch 上升，原因不在读取变快。这组实验关闭了 CUDA Graph，每轮都要逐个提交 kernel：读取量从 15.44 GB 涨到 34.46 GB，一轮的时间却只从 26.26 ms 走到 29.63 ms，batch 越大，这段几乎固定的时间摊到的字节就越多。prefill 效率则稳定在 BF16 峰值的 58%–62%，8K 输入、前 6K 已缓存时为 52%–58%。

表中的带宽效率就是第 1.2.2 节的 MBU，算力效率就是 MFU。batch 为 1 时，一轮 decode 比 8.62 ms 的读取下界多出约 17.6 ms，而且这段时间基本不随读取量变化。按第 1.3.4 节的判据，这段多出来的时间来自逐个提交 kernel、主机侧调度与同步，模型本身没有漏项，用 CUDA Graph 和更好的调度可以去掉；第 5.5.1 节的 vLLM v0.6.0 案例说明主机侧开销能压到什么程度。

**综合算例：在内存与时限约束下选择前缀共享、压缩和推测配置**（原文例题，印刷 p.349–350）

题干照抄原文：有效吞吐给出了服务的评价标准，容量和时间分析则能在运行之前排除不合适的配置。采用章首给定的推理实例：RTX PRO 6000 分给本实例 32 GiB，扣除权重和基本工作区后，留给 KV 及辅助缓冲区的空间为 12 GiB。16 条长请求同时到达，每条输入 8192 个 token、输出 256 个 token，前 6144 个输入 token 相同，完成时限为 7 秒。下面比较四种方案，并假设四种方案都能给出正确答案。共享方案在请求到达前已经缓存了公共前缀。推测方案使用实验 8-5 的 DFlash 草稿模型：启用后进程显存峰值增加约 3.1 GiB（从 17,706 MiB 增至 20,894 MiB），其中草稿模型权重约 1.95 GiB；草稿模型还要处理输入，实验 8-5 中输入约 2300 个 token 时，首 token 时间从 129.4 ms 增至 141.6 ms，多出 9.4%。设这组请求平均每轮输出 3 个 token。

A、C 不共享前缀，每条请求都要完整处理 8192 个 token，整批矩阵运算量为 2137.5 TFLOP，按同一条件 58% 的算力效率计，约需 7.34 s。A 每轮读取 34.46 GB，与 64 条 2K 请求相同，取表中的 29.63 ms；C 的 KV 按 34/64 压缩，每轮读取 25.40 GB，在表中 19.97 GB 与 34.46 GB 两列之间按读取量插值，约 28.26 ms，这里还没有计入格式转换的时间。D 的 prefill 比 B 多 9.4%，约 2.23 s。D 每轮让 16 条请求各验证 8 个位置，矩阵运算约 2.56 TFLOP，按 58% 的效率约需 8.8 ms，短于 B 一轮的 27.35 ms；按 8.2.1 节取两者中的较大值，每轮仍为 27.35 ms。草稿网络的前向也在同一轮内完成，实验 8-5 中 DFlash 一轮的中位耗时并不长于普通 decode 一步（8.5.2 节），因此这里不另加时间。

接下来先检查内存是否足够。A 需 $16 \times 1188 = 19008$ MiB，超出 12 GiB，无法同时接纳这组请求。B 只需一份前缀加 16 份私有状态，共 6048 MiB，约 5.91 GiB。C 的状态按 34/64 压缩，共约 9.86 GiB。D 在 B 的基础上增加 3188 MiB，共 9236 MiB，约 9.02 GiB。B、C、D 都能放入内存，剩下的就是比完成请求所需的时间。

B 的总耗时为 $2.04 + 255 \times 0.02735 = 9.01$ 秒，与实验 8-1 实测的请求耗时中位数 9.02 秒一致，但超过了 7 秒的时限。在这张卡上，仅 255 轮 decode 就要 6.97 秒，16 条请求一起逐 token 生成 256 个输出，无法按期完成。C 失去了前缀复用，prefill 从 2.04 s 增至 7.34 s，总耗时达到 $7.34 + 255 \times 0.02826 = 14.55$ 秒。D 每轮输出 3 个 token，用 85 轮生成剩余的 $85 \times 3 = 255$ 个 token，总耗时为

$$T_D = 2.23 + 85 \times 0.02735 = 4.56\ \text{s}$$

内存不足的 A 和超时的 B、C 都已排除，只有 D 能按时返回 16 个正确答案。这一比较用到了四样东西：前缀共享后的容量、压缩格式的大小、每轮耗时、每轮输出数量。在这张卡上，一轮 decode 的时间几乎不随 batch 和上下文变化，只有减少轮数，才能明显缩短生成阶段。

图 8-35 把这两项检查画在同一张平面图上。横向越过虚线，表示 KV 和辅助缓冲区超过 12 GiB；纵向越过虚线，表示完成时间超过 7 秒。只有 D 同时落在两个限制以内。

> 图 8-35（原文插图）：16 条长请求在 RTX PRO 6000 上的配置比较。**横轴为 KV 与辅助缓冲（GiB，0 到 20），纵轴为整组完成时间（s，0 到 16）**；已扣除共同的权重与基本工作区。四个点：**A、B、C、D**。**A 内存不足，不能在本实例上执行，图中画的是它所需的时间。** **阴影区域同时满足 12 GiB 和 7 秒限制——只有 D 落在里面。** 图注给出方案定义：A 为 BF16 独立上下文，B 为 BF16 共享前缀，C 为 q8_0 独立上下文，D 为 BF16 共享前缀加推测解码。数据由实验 8-1、8-5 的实测推出。

再看成本。每个合格结果占用这张卡的时间，等于整批从到达到全部完成的时间除以合格结果数。D 为 $4.56/16 \approx 0.285$ GPU 秒；按 600 W 的功耗上限计，每个合格结果的能耗不超过约 171 J。B 占用这张卡 9.01 秒，在 7 秒时限下却没有一个合格结果，这些时间和能量全部浪费。

容量和输出长度一变，选择也会变。可用内存从 12 GiB 减到 6 GiB，D 所需的约 9.02 GiB 装不下；B 所需的约 5.91 GiB 虽能容纳，却会超时。这组请求没有可行方案，只能放宽时限、缩短输出，或者改用不占显存的草稿来源（见练习 8-9）。内存不变，只把输出缩短到 16 个 token，B 需要 $2.04 + 15 \times 0.02735 = 2.45$ 秒，D 需要 $2.23 + 5 \times 0.02735 = 2.37$ 秒。两者都能按期完成，D 只快 0.08 秒：草稿模型多做的 0.19 秒 prefill，几乎抵消了少执行 10 轮 decode 节省的时间。

上面算的都是实例内的执行时间。计算完整 Agent 任务的耗时，还要加上工具执行和外部等待。假设一次任务耗时 100 秒，其中 decode 占 50 秒，把 decode 加速四倍，总耗时变成 $50 + 50/4 = 62.5$ 秒，整体加速 1.6 倍；如果 decode 原本只占 20 秒，总耗时则变成 $80 + 20/4 = 85$ 秒，整体只加速约 1.18 倍。一般地，设 decode 占原总时间的比例为 $f$，该阶段加速 $s$ 倍，其他阶段耗时不变，由 Amdahl 定律得到

$$S_{\text{task}} = \frac{1}{(1-f) + f/s}$$

图 8-36 里，decode 占比越低，曲线越早变平：即使生成阶段继续加速，工具调用和其他等待仍占着原来的时间。比较加速器占用和能耗时也要覆盖这些阶段，并按最终得到的合格请求数计算。设观察期间占用加速器的总时间为 $T_{\text{GPU}}$，总能耗为 $E_{\text{obs}}$，合格结果数为 $N_g$，则每个合格结果平均占用 $T_{\text{GPU}}/N_g$ 的 GPU 时间，消耗 $E_{\text{obs}}/N_g$ 的能量。

> 图 8-36（原文插图）：横轴为 **decode 加速比（1 到 8）**，纵轴为**完整任务加速比（1.0 到 3.0）**。三条 Amdahl 曲线分别取 **decode 占基线时间 20%、50%、80%**，都是"其他阶段时间固定、没有新增准备工作"的理想曲线。**该阶段原有的耗时占比越高，局部加速带来的收益就越大**；decode 占比越低，曲线越早变平。

实验 8-9 在同一张卡上读取了 GPU 与 CPU package（整个处理器封装）的能量计数：连续批处理在到达率 1、4、16 req/s 下，每个合格结果分别消耗 615.0、652.0、1083.7 J；逐个接纳在 4 req/s 下为 1982.3 J。16/s 时连续批处理的完成吞吐与 4/s 相近，迟到的回答却更多，每个合格结果的能耗高出约 66%。即使答案错误或返回太晚，已经消耗的能量也必须计入总成本。

原书脚注 33（印刷 p.350）：实验 8-1 的效率表由计算脚本从 batch 扫描的逐轮记录导出，峰值取硬件表中 RTX PRO 6000 的 1792 GB/s 与 503.8 TFLOP/s；DFlash 的显存峰值、首 token 时间与每轮耗时取自实验 8-5。各方案的内存与时间由算例检查复算。脚注 34：服务与能量原始记录（同脚注 32）。

**练习 8-8 ・计算：阶段加速与草稿准备如何改变任务总时间**（印刷 p.352）

题干照抄原文：一个 100 秒任务由 prefill 20 秒、decode 50 秒、工具及等待 30 秒组成。分别将三个部分的耗时单独减半，求每种情况下的任务总耗时。另从原始任务出发，将 decode 耗时降为原来的四分之一，并增加 8 秒草稿准备时间，求净加速比，并计算准备时间达到多少时这项改动不再节省时间。

解法是笔记补的，原书只给题面：

- prefill 减半（20 → 10 s）：$10 + 50 + 30 = 90$ s，加速 1.11 倍。
- decode 减半（50 → 25 s）：$20 + 25 + 30 = 75$ s，加速 1.33 倍。
- 工具及等待减半（30 → 15 s）：$20 + 50 + 15 = 85$ s，加速 1.18 倍。
- decode 降为 1/4 再加 8 秒准备：$20 + 50/4 + 30 + 8 = 20 + 12.5 + 30 + 8 = 70.5$ s，净加速比 $100/70.5 = 1.42$ 倍。
- 准备时间的临界值：不加准备时是 $20 + 12.5 + 30 = 62.5$ s，即省下 $100 - 62.5 = 37.5$ s。准备时间达到 37.5 秒时，这项改动不再节省时间。

**练习 8-9 ・核心・综合设计：在容量与时限内减少每个合格结果占用的 GPU 时间**（印刷 p.352）

题干照抄原文：沿用综合算例在 RTX PRO 6000 上的容量与时间，以 B 为基础构造方案 E：共享 BF16 前缀，草稿改为从上下文中查找（8.5.2 节），索引放在主机内存，不占显存，也不增加 prefill；每条请求平均每轮输出 2 个 token，后续执行 128 轮，整批每轮 27.35 ms 加 0.1 ms 查询。计算 E 的显存占用、总耗时和每个合格结果占用的 GPU 秒，与 B、D 比较；再分别把 KV 和辅助缓冲区的可用内存改为 6 GiB、把输出长度改为 16 个 token，重新选择。开放实验部分使用相同题集和到达轨迹运行两种配置，记录全部请求的到达、首输出、结束、正确性与状态峰值，按本节公式计算有效吞吐。

解法同样是笔记补充：

- E 的显存占用与 B 相同，即一份前缀加 16 份私有状态，共 6048 MiB ≈ 5.91 GiB（索引在主机内存，不计入显存）。
- E 的总耗时：prefill 与 B 相同为 2.04 s；后续 128 轮，每轮 $27.35 + 0.1 = 27.45$ ms，故 $T_E = 2.04 + 128 \times 0.02745 = 2.04 + 3.51 = 5.55$ s。
- 每个合格结果占用 $5.55/16 = 0.347$ GPU 秒，按 600 W 计约 208 J。
- 与 B、D 比较：B 为 9.01 s 但超时，没有合格结果，分母为 0，全部浪费；D 为 4.56 s、0.285 GPU 秒。在 12 GiB / 7 秒这组条件下，D 仍然最优，E 次之（0.347 > 0.285）。
- 内存改为 6 GiB：E 需 5.91 GiB，能装下（B 也能，但 B 会超时）；此时 E 是唯一可行方案，因为它总耗时 5.55 s < 7 s，而 D 需要 9.02 GiB 装不下。
- 输出改为 16 个 token：E 需 $2.04 + 8 \times 0.02745 = 2.26$ s（$16/2 = 8$ 轮）；B 需 2.45 s，D 需 2.37 s。三者都能按期完成，E 最快（2.26 < 2.37 < 2.45），因为 E 没有草稿网络额外承担的那 0.19 s prefill。
- 开放实验：按"到达时刻、首输出时刻、结束时刻、正确性、状态峰值"逐请求记录，再套 $R_{\text{good}} = \sum_i Q_i D_i / T_{\text{obs}}$ 计算有效吞吐（把引擎外的等待也计入，见 8.6.2）。

效率表怎么读、怎么用，是理解这一节的关键，它是全章从实测走向估算的那座桥。

"每轮读取的权重与 KV"一行的四个数（15.44 / 16.34 / 19.97 / 34.46 GB）与 8.2.1 的公式完全对应：$D_w + bLk$，其中 $D_w = 15.137$ GB、$Lk = 0.302$ GB（2K 上下文）。复算：$b=1$ 时 $15.14 + 0.30 = 15.44$ ✓；$b=4$ 时 $15.137 + 1.208 = 16.345 \approx 16.34$ ✓；$b=16$ 时 $15.14 + 4.83 = 19.97$ ✓；$b=64$ 时 $15.137 + 19.327 = 34.464 \approx 34.46$ ✓。这里 $D_w$ 用的是 15.14 GB 而不是 14.1 GiB，二者是同一个 15,136,811,008 bytes 的不同单位写法。（以上复算是笔记补充的。）

"按 1792 GB/s 读取所需时间"一行同样能对上：$15.44/1.792 = 8.62$ ms ✓；$16.34/1.792 = 9.12$ ✓；$19.97/1.792 = 11.14$ ✓；$34.46/1.792 = 19.23$ ✓。decode 带宽效率则是读取下界除以实测：$8.62/26.26 = 32.8\% \approx 33\%$ ✓；$9.12/26.62 = 34.3\% \approx 34\%$ ✓；$11.14/27.44 = 40.6\% \approx 41\%$ ✓；$19.23/29.63 = 64.9\% \approx 65\%$ ✓。（这两组也是笔记补充复算。）

效率随 batch 上升，靠的是固定开销被摊薄，跟读取变快没关系。batch 1 时一轮 26.26 ms 里有 $26.26 - 8.62 = 17.64$ ms 与读取量无关（原文写"约 17.6 ms"）；到了 batch 64，读取下界涨到 19.23 ms，固定开销还是那约 17.6 ms，于是实测 29.63 ms 里的"有效带宽"显得很高，占 65%。MBU 这个指标本身会随 batch 变化，拿它当硬件质量的度量并不合适。原文点出这段开销来自逐个提交 kernel、主机侧调度与同步，并说用 CUDA Graph 和更好的调度可以去掉。

综合算例的走法可以整理成四步，值得直接记住。第一步算容量：$M_{\mathrm{KV}}$ 是否 $\le$ 12 GiB，A 因为 19008 MiB 出局。第二步算时间：$T = T_{\text{prefill}} + \text{轮数} \times \text{每轮耗时}$ 是否 $\le$ 7 s，B、C 出局。第三步算成本：$T_{\text{GPU}}/N_g$ 与 $E_{\text{obs}}/N_g$。第四步做敏感性分析，内存减半、输出缩短，看选择会不会翻转。

综合算例的关键数字复算一遍（笔记补充计算）：B 的 $r_P = 32768\ \text{new tokens} / 2.04\ \text{s} = 16{,}062.7$ token/s，原文写 16,059，差异来自 2.04 s 的舍入；B 的 $r_D = 16 / 0.02735 = 585.0$ 调用/s ✓；B 的 $t_{\text{GPU}} = 2048/16059 + 255/585 = 0.12753 + 0.43590 = 0.5634$，约 0.563 秒 ✓，乘 16 得 9.01 ✓；B 的总时间 $2.04 + 255 \times 0.02735 = 9.014$，约 9.01 s ✓；C 的 $7.34 + 255 \times 0.02826 = 14.55$ ✓；D 的 $2.23 + 85 \times 0.02735 = 4.555$，约 4.56 s ✓，能耗上限 $0.285 \times 600 = 171$ J ✓。换成 6 GiB 内存，D 的 9.02 GiB 装不下，B 的 5.91 GiB 能装但 9.01 s 超时，这组请求在 6 GiB / 7 s 下无解。输出缩到 16 个 token 时，B 是 $2.04 + 15 \times 0.02735 = 2.450$，约 2.45 s ✓；D 是 $2.23 + 5 \times 0.02735 = 2.367$，约 2.37 s ✓，差值 0.08 s ✓；而 D 的 prefill 多花 $2.23 - 2.04 = 0.19$ s ✓，少执行 $15 - 5 = 10$ 轮 decode ✓。

"输出缩短后推测解码优势消失"这条结论分量很重。推测解码省下来的是轮数，而轮数只在输出很长时才成为大头。输出只有 16 个 token 时，prefill 那 0.19 秒额外开销几乎就是全部差距了。这与 8.5.2 里"建索引 2 秒需要 114 个 token 才能回本"是同一个逻辑。

Amdahl 定律在服务语境下的含义，就是 $S_{\text{task}} = 1/((1-f) + f/s)$ 这个式子。复算原文两个例子：$f = 0.5$、$s = 4$ 时 $1/(0.5 + 0.125) = 1.6$ ✓；$f = 0.2$、$s = 4$ 时 $1/(0.8 + 0.05) = 1.176 \approx 1.18$ ✓。它对服务优化的意义在于，如果 decode 只占整个 Agent 任务的 20%，把 decode 加速到无穷倍，整体也只能加速 1.25 倍（$1/0.8$）。优化的上限由非 decode 部分决定，工具调用和外部等待才是真正的天花板，练习 8-8 就是这个道理的算术版。

能耗指标 $E_{\text{obs}}/N_g$ 是最诚实的成本指标。分母 $N_g$ 只数合格结果，错误和迟到都算浪费；分子 $E_{\text{obs}}$ 统计的是整个观察窗口的能量，GPU 加 CPU package，包括那些没用的工作。复算那组数：连续批处理从 4 req/s 走到 16 req/s，每合格结果能耗从 652.0 涨到 1083.7 J，$1083.7/652.0 = 1.662$，高出约 66% ✓。逐个接纳在 4 req/s 下是 1982.3 J，是连续批处理的 3 倍（$1982.3/652.0 = 3.04$）。

四处容易混的地方。MFU 量的是算力用得多满，MBU 量的是带宽用得多满；decode 看 MBU，prefill 看 MFU，这张表里 decode 带宽效率只有 33%–65%，prefill 算力效率有 58%–62%，正好反映两个阶段的不同瓶颈。$r_P$ 与"prefill 吞吐"的口径也不同，$r_P$ 只数新输入 token，前缀命中缓存的那部分不计入工作量，这就是 B 的 prefill 只用 2.04 s 的原因：它处理的是 32768 个新 token，而不是 $16 \times 8192 = 131072$ 个。实例内时间与完整任务时间差着工具和外部等待（Amdahl）。至于"每轮耗时"与"每轮读取时间"，前者是实测，8.6.3 表中 batch 16 一行是 27.44 ms；后者是同一行的读取下界 11.14 ms；两者相差约 16.3 ms，就是主机侧开销。

原书这一节在印刷 p.349–352（节级页次取自章末速查表的"出处"列；综合算例、图 8-35、图 8-36、实验 8-9 与两道练习的页次已在上文各处标注）。

选配置就四步：先查内存，再看时限，然后比每个合格结果的 GPU 秒与焦耳，剩下一步是敏感性分析。而在这张卡上，一轮 decode 的时间几乎不随 batch 和上下文变化，所以只有减少轮数，也就是靠推测解码，才能真正压缩生成阶段。

## 历史与延伸阅读

本节对应印刷 p.352，原书在这一节按主题给出了脚注 35–42 的文献线索，笔记再补一层读法。

第 8 章讲的三件事各有出处。每轮迭代接纳新请求来自 Orca 的迭代级调度，分页注意力来自 PagedAttention，前缀树缓存来自 SGLang。原书用一句话把它们的贡献分开命名：请求调度、状态分配、计算复用。这三条正好是整章的三条主线，值得单独抄在笔记上。再往后，Sarathi-Serve 和 NanoFlow 把关注点换到重叠上，研究分块、流水以及不同资源之间怎么叠起来用，也就是 8.2.3 和 8.4.3 里「用计算掩盖复制」那一类思路。

8.2.1 的多 adapter 服务可以顺着 Punica 与 S-LoRA 读下去。这两项工作分工不同，一个管 adapter，一个管请求状态，共同点是在共用基础模型的同时，各自执行自己那份 adapter 的低秩计算。

混合注意力与递推模型把缓存索引扩展成了状态恢复问题。索引要回答的已经不只是「这块 KV 放在哪儿」，还包括状态丢了以后怎么找回来。Marconi 这类工作讨论的是恢复机会和缓存价值，和 8.3.4 的准入取舍是同一个问题的延伸。权重卸载、张量编码和统一内存执行把加速器容量与链路成本挂在一起，配套的 M2 Max 记录给的是小模型上真实的 KV 分配与输入处理数据，8.4.1 里那两个量化变体的 79.81 GiB 与 81.97 GiB 就是这么量出来的。

推测解码这一路，接受与修正规则是保持目标分布的基础，8.5.1 的 $\alpha(x) = \min(1, p(x)/q(x))$ 加上差额重采样就是它。后续工作分成三路：从上下文里查草稿、按中间特征预测草稿、并行生成草稿。它们改的都是每轮开销和能接受的草稿长度这两个量，8.5.3 与 8.5.4 的取舍落在这里。完整 Agent 任务还包含工具和外部阶段，公开的速度与任务记录可以对着 8.6 节的阶段分解看。

这些文献散在四个方向上，压回第 8 章的度量框架来看，它们动的是同三个量。内存占用（$M_{\mathrm{KV}}$ 与 $M_w$）决定一个实例能同时接多少条请求；每轮耗时（$T_{\text{step}}$）决定每条请求多久收到答案；每轮输出数（$N$，推测解码带来的）决定要跑多少轮。原书小结里那句「这些变化都可以通过内存占用、每轮耗时和每轮输出数来比较」，说的就是这件事。任何一项优化都能用这三个量的变化来描述，任何两个方案也都能用这三个量来比。这套框架比任何单个结论都耐用。

三个量算完，要落成三类可记录的结果：给定加速器、精度和请求长度下能同时保存多少条请求的状态；prefill 与 decode 分别以多快的速度处理工作，也就是 $r_P$ 与 $r_D$；请求延迟怎么随 batch 和到达率变化。第 9 章的部署规划直接吃这三样。第 8 章算的是一个实例能干什么，第 9 章算的是要多少个实例、怎么分工。多个加速器可以共同执行一个实例，也可以组成多个完整副本或分别调度的阶段服务池；批处理决定已有资源怎么处理请求，部署方式决定这些资源怎么分工，两件事一起决定完整服务的性能。

章末那组 16 条长请求的算例值得再回看一遍。前缀共享把原先装不下的请求塞进了显存，但逐 token 生成 256 个输出在 RTX PRO 6000 上仍然超时，靠推测解码把 decode 轮数压下来才按期完成。四个方案的内存分别是 19008 / 6048 / 约 10100 / 9236 MiB，方案 D 每个合格结果占 0.285 GPU 秒，按 600 W 折算能耗上限 171 J。可用内存掉到 6 GiB，这组请求就找不到可行方案；输出缩到 16 个 token，推测解码的优势也几乎消失。选择为什么会变，答案都能在本章推导出的数据量、执行时间和输出数量里找到，具体算法在 8.6.3。本章正文的页码跨度是印刷 p.317–352（这个跨度是我按原章末速查表的「出处」列整理的）。
