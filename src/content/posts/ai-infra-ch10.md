一个模型能在单张加速卡上生成文本，并不等于它也能在那张卡上训练完。这一章拿一项具体任务把训练系统拆开来算：用 Qwen3-8B 处理 100B token 做特定领域的继续训练，期限 30 天。要回答的问题有三个，而且必须连起来看：哪些张量和缓冲区需要同时占用显存，哪些操作决定训练步何时结束，故障之后能够恢复到哪一步。

第 6 章按样本、特征、序列、层和专家介绍了六种并行方式，第 7 章讨论并行系统的组织方式，本章把这些方法放进训练这个真实场景，先做容量与时间的量化估算，再谈状态分片、重计算、卸载，以及流水调度与通信重叠。10.1 给定任务并算出两个硬约束，显存容量与每步约 67.9 s 的时间预算，同时给出 32 卡与 48 卡两套候选方案；10.2 从容量一侧出发，讲 ZeRO／FSDP 状态分片、激活的选择性重计算和 CPU／GPU 卸载，再把它们组合成完整的并行方案；10.3 从时间一侧出发，先讲一次迭代的目标函数与 micro-batch 梯度累积，再分析流水线的气泡与激活生命周期、反向依赖与梯度分桶带来的通信重叠，以及 MoE 与长上下文给调度带来的变化。10.4 节及之后处理 checkpoint、故障恢复、掉队者这些长周期训练问题。读完这一章，你应该能按模型规模、token 量和期限估出常驻训练状态容量、每步时间预算和所需卡数下界，能说清 ZeRO 三个阶段各自分片了什么、每卡容量怎么算，也能分清填满排空、1F1B、交错式 1F1B、零气泡、DualPipe 五种流水调度在时间轴和显存轴上的取舍并用气泡公式估算，还能判断一段通信能否被计算覆盖、算出无法隐藏的通信等待。

这里开篇先给出一笔总账。全参数训练会更新模型的全部可训练权重，Qwen3-8B 的 BF16 权重约 16.4 GB，而用混合精度 Adam 做全参数训练时，系统除权重外还要保存梯度、FP32 主权重，以及优化器跨步保留的梯度历史，合计约 131 GB，约为 BF16 权重的八倍。反向传播求导要读取前向阶段保留的激活，执行期间还需要参数收集和格式转换用的缓冲区。设计训练系统，先要确定这些张量和缓冲区放在哪里、需要保留多久。

把训练状态分到更多卡上能减轻单卡显存压力，代价是计算要等其他卡传来的数据；把状态移到主机内存能腾出显存，代价是主机与 GPU 之间的传输变多。训练持续数周时，等待输入、保存 checkpoint 和故障后的重复计算都会计入完成时间。卡数上千以后，故障不再是偶发事件：按每卡约 337 天故障一次计，1024 卡的作业平均约 7.9 小时中断一次，第 10.4.4 节会展开。

这些设计都有依据，依据是训练计算图。前向产生的激活在反向时使用，梯度在参数更新前汇集，优化器状态跨步保留。运行时利用这些已知关系，可以提前取回即将使用的参数、重算开销较小的激活，并让已就绪梯度的通信与后续反向计算重叠。本章任务：用 Qwen3-8B 处理 100B token 完成特定领域的继续训练，期限 30 天，先估算至少需要多少资源，再比较由 32 张和 48 张 RTX 4090 组成的两套方案，比较从显存需求开始，逐步加入计算、通信、数据准备和故障恢复的耗时，据此确定哪套方案能按期完成。为了讲清各项机制，文中穿插了较小的张量和流水线算例；RL 部分另外分析生成、验证和学习如何组成反馈循环。单位约定上，本章容量数字用两套单位：GB、TB 表示十进制容量，GiB、MiB 表示二进制容量。

## 10.1 根据训练任务估算容量与时间需求

### 10.1.1 训练任务、可训练参数与完成目标

系统设计从要完成的工作开始。本章任务采用全参数训练、混合精度 Adam，序列长度固定 8,192 个 token，总共处理 100B 有效 token；每次训练迭代吃掉 384 条完整长度的序列，也就是 3,145,728 个有效 token。最后一次迭代只处理剩余数据，时间预算仍按完整一步安排。比较两套系统方案时，训练数据、目标函数和评估要求都一样。

**有效 token** 指任务里实际需要处理的 token，不含为对齐长度而补入的填充 token。填充让张量形状更规整，可它照样占用计算和存储资源，统计任务完成量时只累计有效 token。与全参数训练相对的是 LoRA：它在原权重旁增加较小的可训练矩阵，用两者乘积表示权重调整量，基础权重仍参与前向计算，梯度和优化器状态的大小主要取决于适配器参数量，需要训练的参数因此少得多。这里只作对比，本章任务仍走全参数训练。

一次训练迭代包括前向传播、反向传播、梯度归约和参数更新四段；持续训练由很多次迭代组成，中间还要准备输入数据、保存 checkpoint，启动、准备资源和维护同样要计入从开始到结束的总时间。30 天里有 5 天预留给启动、评估和计划性停顿，剩下 25 天用于训练、checkpoint 与故障恢复，平均有效吞吐的要求因此从约 38,600 token/s 提高到约 46,300 token/s。

完成整个任务需要

$$
\lceil 10^{11}/3\,145\,728 \rceil = 31\,790
$$

次训练迭代。25 天分摊到每次迭代，只有约 67.9 s。这个时间预算贯穿全章：每步计算、通信等待、输入等待，以及分摊到这一步的 checkpoint 保存与故障恢复时间，都要算在这 67.9 s 之内。

每步的 batch size 同样需要确定。全局 batch 取 384 条序列后不再继续放大，原因在梯度的信噪比。batch size $B$ 增大时梯度估计的噪声随之下降；$B$ 足够大以后，再增加样本只能略微减少达到同一损失所需的步数，每步的计算量却成比例增加。发生这一转折的 batch size 称为**临界 batch size（critical batch size）**，它可以用梯度噪声尺度（gradient noise scale）来估计。设损失对参数的 Hessian（二阶导数矩阵）为 $H$、单样本梯度的协方差为 $\Sigma$、真实梯度为 $G$，梯度噪声尺度定义为

$$
B_{\text{noise}} = \frac{\operatorname{tr}(H\Sigma)}{G^{\mathsf T} H G}
$$

达到给定损失所需的步数 $S$ 与处理样本数 $E$ 满足经验关系

$$
\left(\frac{S}{S_{\min}} - 1\right)\left(\frac{E}{E_{\min}} - 1\right) = 1, \qquad B_{\text{crit}} = \frac{E_{\min}}{S_{\min}}
$$

其中 $S_{\min}$ 为达到该损失的最少步数，$E_{\min}$ 为所需的最少样本数。临界 batch size 约等于梯度噪声尺度；按临界 batch size 训练时，步数和样本数都是各自最小值的两倍。

$B_{\text{noise}}$ 随模型与训练阶段变化。本例取二百万个 token，依据是文献在已训练的最大模型上测得的收敛时约一到二百万 token 这一区间。把本章的参考运行（48 卡、每步 $384 \times 8192$ 个 token、31,790 步完成 100B token）视为恰好达到目标，由关系式反推得到 $S_{\min} \approx 19\,434$ 步、$E_{\min} \approx 38.9\text{B}$ token。当前每步 batch size 约为 $B_{\text{noise}}$ 的 1.57 倍，已经越过 batch size 翻倍、步数近似减半的区间；batch size 再放大，步数最多也只能从 31,790 降到 19,434。

下表比较卡数增加时弱扩展与强扩展两种方式的完成时间。

| 卡数 | 弱扩展：每步 token 数 | 弱扩展完成时间/天 | 强扩展完成时间/天 |
| --- | --- | --- | --- |
| 48（参考） | 3,145,728 | 19.4 | 19.4 |
| 96 | 6,291,456 | 15.7 | 9.8 |
| 192 | 12,582,912 | 13.8 | 5.0 |
| 384 | 25,165,824 | 12.8 | 2.6 |
| 1536 | 100,663,296 | 12.1 | 0.8 |

表中的**弱扩展**让每卡固定累积 8 个 micro-batch，每步仍为 52.8 s，全局 batch 随卡数放大；**强扩展**固定全局 batch，单卡计算量与卡数成反比，每步 0.58 s 的通信与输入等待不变。两者都不计并行效率的变化。弱扩展的加速上限为 $31\,790/19\,434 \approx 1.64$ 倍：1536 卡把每步 batch size 放大到参考值的 32 倍，完成时间只从 19.4 天降到 12.1 天。强扩展不受 $B_{\text{noise}}$ 限制，但固定等待在每步中的占比随卡数上升，0.8 天里通信与输入等待已经占到约四分之一。

弱扩展的收益何时翻转，取决于 $B_{\text{noise}}$ 的取值。若噪声尺度是两千万个 token，弱扩展上限升至约 7.36 倍，batch size 随卡数放大才有明显收益。所以扩卡之后 batch size 能否随之放大，先要估计 $B_{\text{noise}}$：当前 batch size 远小于它就可以跟着放大，远大于它就只能在每步时间里省。384 条序列正是这样选出来的，它在 48 卡的显存与每步预算之内，又略高于噪声尺度，再放大 batch size 的收益已经开始递减。

> 补充：1：临界 batch size 复算与噪声尺度两千万 token 的对照。梯度噪声尺度的定义见大 batch 训练经验模型式(2.8)；步数—样本关系式(5.1)、临界 batch size 定义式(5.2) 与收敛时约一到二百万 token 的区间见缩放定律论文。$B_{\text{noise}}$ 为本例取值，未对本章模型实测；弱扩展与强扩展都不含并行效率变化。

这一节有三笔账，后面全章都在用它们。

先说总工作量。100B 有效 token 是任务的分子，3,145,728 是每一步的分子，两者相除并向上取整得到 31,790 步。这里强调最后一次迭代只处理剩余数据、时间预算仍按完整一步安排，工程上算工期就该按整数步算，不会因为最后一步只用到 3% 的数据就把它记成 0.03 步。

时间预算这一笔，这里做过复算：$25 \times 86400 = 2{,}160{,}000$ s，除以 31,790 得 67.94 s，与这里的 67.9 s 一致。30 天全用上是 $30 \times 86400 = 2{,}592{,}000$ s，对应吞吐 $100\text{e}9/2{,}592{,}000 \approx 38{,}580$ token/s，这里写「约 38,600」；按 25 天算则是 $100\text{e}9/2{,}160{,}000 \approx 46{,}296$ token/s，这里写「约 46,300」。这两个数字就是 10.1.3 里「至少六张 H100」与「31 张 RTX 4090」两处结论的判据来源。

第三笔账是为什么要谈信噪比。卡多就 batch 大、batch 大就快，这个直觉只对一半。梯度是带噪估计，batch 小时噪声大，增大 batch 确实能改进梯度方向；当 batch 越过临界值以后，方向已经足够准，再多采样只是把同一条路走得更稳，收敛所需的样本数却继续线性增长，于是墙钟时间不再下降。这里的形式化就是那条经验关系式 $(S/S_{\min}-1)(E/E_{\min}-1)=1$，把它展开后两端的含义就清楚了：若 $S = S_{\min}$，等式左边第二项必须无穷大（$E \to \infty$，只能靠堆样本、不减少步数）；若 $S = 2S_{\min}$，则 $E = 2E_{\min}$，这正是「按临界 batch size 训练时步数与样本数都是最小值两倍」这句话的来历。

代入这里数字再做一遍复算。本步 batch 是 $384 \times 8192 = 3{,}145{,}728$ token，除以 $B_{\text{noise}} = 2\times10^{6}$ 得 1.5729，即这里说的约 1.57 倍。再验证 $S_{\min}$ 与 $E_{\min}$：$B_{\text{crit}} = E_{\min}/S_{\min} = 38.9\times10^{9}/19\,434 \approx 2.00\times10^{6}$，正好等于所取的 $B_{\text{noise}}$，说明 19,434 与 38.9B 这组数是由 $B_{\text{noise}} = 2\times10^{6}$ 反推出来的。用 $S = 31\,790$、$E = 100\times10^{9}$ 检验关系式，$(31\,790/19\,434-1)(100/38.9-1) = 0.6358 \times 1.5707 = 0.999 \approx 1$，等式成立。所谓弱扩展上限 1.64 倍，就是 $31\,790/19\,434 = 1.6358$，也就是步数最多只能降到 19,434 的直接结果。

弱扩展与强扩展的区别可以一句话分清：弱扩展是卡多了、每卡干的事不变、全局 batch 变大；强扩展是卡多了、总量不变、每卡分到的活变少。所以弱扩展的天花板由 $B_{\text{noise}}$ 决定，强扩展的天花板由那部分无法随卡数摊薄的固定等待决定，也就是每步 0.58 s 的通信与输入等待。

强扩展那一列也自洽。取参考侧每步纯计算时间 52.2 s（10.1.3 推出的 48 卡数字），31,790 步是 1,659,438 s ≈ 19.21 天；固定等待 $0.58 \times 31{,}790 = 18{,}438$ s ≈ 0.213 天。于是 96 卡 ≈ 19.21/2 + 0.21 = 9.81 天、192 卡 ≈ 4.80 + 0.21 = 5.01 天、384 卡 ≈ 2.40 + 0.21 = 2.61 天、1536 卡 ≈ 0.60 + 0.21 = 0.81 天，与这里表中的 9.8／5.0／2.6／0.8 天逐项吻合，48 卡那一行取 19.4 天。强扩展一列等于纯计算按卡数反比加固定等待不变，这条规律是自洽的。

弱扩展一列同样自洽：$S_{\min} = 19\,434$ 步 × 52.8 s = 1,026,115 s ≈ 11.88 天，加上少量其他开销就是这里 1536 卡的 12.1 天；48 卡的 19.4 天除以 12.1 天约 1.60，与 1.64 倍的上限口径一致，上限是纯计算比值，实测还包含等待。

工程上的用法很直接。这里那句「扩卡后 batch size 能否随之放大，要先估计 $B_{\text{noise}}$」就是扩容决策的检查表：先估噪声尺度，再定是加卡加 batch 还是加卡缩每步。噪声尺度若是两千万 token 而不是两百万，弱扩展上限升到约 7.36 倍，加卡放大 batch 才划算。同一个集群，两种噪声尺度给出完全不同的扩容策略。

还有一个口径差别，它不属于这里错误。本节描述弱扩展算例时写「每步仍为 52.8 s」，而 10.1.3 用 40% 效率推出 48 卡每卡矩阵计算约 52.2 s，再加约 0.08 s 的通信等待约 52.3 s。两处相差约 0.5 s：52.8 s 是整步耗时，已含通信等待与其余每步开销；52.2 s 是单纯的矩阵计算时间。

> 说明：10.1.1 的弱扩展算例取每步 52.8 s（整步耗时，已含约 0.08 s 通信等待及其余每步开销），10.1.3 推出的 52.2 s 是 48 卡每卡的矩阵计算时间，加上通信等待约 52.3 s。两者相差约 0.5 s，来自**整步耗时与纯计算时间两种口径**以及取整，**这不是这里的错误**，这里按分别保留。

还有几处容易混的地方。有效 token 与填充 token 的分工是：只有有效 token 计入任务完成量，填充 token 只影响张量形状，照样吃算力和带宽，但不计入分母，所以「处理了 100B token」与「跑了 100B token 的算力」是两件事。临界 batch size 与梯度噪声尺度的量纲都是样本数（此处按 token 计），含义却不同：一个是再增大 batch 收益开始递减的拐点，一个是梯度中噪声与信号之比的度量，前者由后者估计出来。弱扩展保持每卡工作量、放大全局 batch，受 $B_{\text{noise}}$ 限制；强扩展保持全局 batch、缩小每卡工作量，受固定等待占比限制。步数减少和时间缩短也要分开看，batch 放大最多把步数从 31,790 降到 19,434（约 −39%），但每步计算量成比例增加，弱扩展的墙钟收益上限只有约 1.64 倍。

把任务先算成「31,790 步 × 67.9 s」的时间预算，再用 $B_{\text{noise}}$ 判断加卡时能不能放大 batch；batch 已经越过噪声尺度，就只能在每步时间里省。

### 10.1.2 参数、梯度、优化器与激活

67.9 s 给出了每步允许花费的时间，但计算开始前还要满足显存要求。设参数数量为 $N$。一次迭代中，前向由输入算出预测和损失，反向沿计算依赖求出损失对各个中间值和参数的梯度，并读取前向留下的激活，优化器再用参数梯度计算下一步权重。

  <figcaption><strong>一次训练步的状态与数据流。</strong> 前向保留激活供反向使用，Adam 更新读取 FP32 主权重与两份矩状态；每参数常驻训练状态约 16 字节。</figcaption>
</figure>

具体到本章任务，混合精度 Adam 用 BF16 权重执行矩阵运算，用 FP32 主权重保存优化器计算后的参数值，并保存两份 FP32 矩状态。一阶矩和二阶矩跨迭代保留，分别记录梯度方向和大小的历史；主权重更新后再转换为 BF16 供矩阵运算使用。梯度以 BF16 累积，逐项相加得到每参数 16 bytes。

| 状态 | 每个参数所占字节数 | Qwen3-8B 容量/GB | 使用时机 |
| --- | --- | --- | --- |
| BF16 模型权重 | 2 | 16.4 | 前向与反向矩阵运算 |
| BF16 梯度 | 2 | 16.4 | 反向传播时产生，计算新参数时使用 |
| FP32 主权重 | 4 | 32.8 | 保存新参数，随后生成 BF16 副本 |
| Adam 一阶矩 | 4 | 32.8 | 在训练迭代之间保留梯度历史 |
| Adam 二阶矩 | 4 | 32.8 | 在训练迭代之间保留梯度平方历史 |
| 合计 | 16 | 131.1 | 常驻训练状态 |

Qwen3-8B 有 $N = 8\,190\,735\,360$ 个参数，因此

$$
M_{\text{persistent}} = 16N \approx 131.1\ \text{GB} \approx 122.1\ \text{GiB}
$$

梯度格式是另一项选择。把梯度改为 FP32，每参数增加 2 bytes，总量变为 18 bytes。这一变化来自梯度的数据格式，「混合精度」这个词本身并不规定梯度格式。

MoE 每次由路由器选择部分专家子网络执行；各专家同样拥有待更新参数和优化器历史，所以状态容量由全部可训练参数决定。

除了各类数据占多大空间，还要区分各自需要保留多久。前向产生的激活要等到相应的反向计算结束后才能释放，而参数收集缓冲区可能只在某个模块执行期间使用。第 $i$ 张卡的显存峰值取决于同一时刻驻留的训练状态、激活和临时缓冲区：

$$
M_{\text{peak},i} = \max_t\left[M_{\text{persistent},i}(t) + M_{\text{activation},i}(t) + M_{\text{temporary},i}(t)\right]
$$

拿 8 GiB 激活与 4 GiB 收集缓冲来说，若两者同时出现，就要共同占用 12 GiB；若先释放激活再收集参数，同一片空间可以复用。容量优化由此有**两个方向**：减少张量和缓冲区的大小，或减少需要同时保留的数据。下一节的分片、重计算与卸载分别从这两个方向改变峰值。

上面这套容量是按 BF16 执行矩阵运算算的。换一种浮点格式，状态占用的字节数和数值风险会同时改变。先看 FP16。第 4.6.1 节已经比较过 FP16 与 BF16 的指数与尾数：FP16 的五位指数把最小正规数定在 $2^{-14} \approx 6.1\times10^{-5}$，小于它的值只能用次正规数表示，有效位随数值减小而逐位丢失；小于 $2^{-24} \approx 6\times10^{-8}$ 的值则直接变为零。混合精度训练论文给出两组统计：普通话语音识别模型的权重梯度中，约 5% 的值指数小于 $-24$，在 FP16 中会变为零，该文以此说明需要 FP32 主权重；Multibox SSD 检测网络的激活梯度中，大量数值低于 FP16 的可表示范围而变为零，其中落在 $[2^{-27}, 2^{-24})$ 的值对训练仍然重要。

**损失缩放（loss scaling）** 解决这一问题：在反向传播前把损失乘以因子 $S$，梯度随之放大 $S$ 倍，进入 FP16 可表示的范围，参数更新前再除以 $S$。该文训练多种网络时使用的缩放因子在 8 到 32K 之间。因子过小，小梯度仍然下溢；过大，大梯度溢出为无穷大，必须跳过这次更新并调小因子。

BF16 的八位指数与 FP32 相同，两者的表示范围一致，梯度不需要缩放，这是状态表采用 BF16 的原因之一。代价是尾数只有七位：矩阵运算输入的舍入误差大于 FP16，长内积的精度要靠 FP32 累加器保证。

继续压低位宽，就要把单一的全局缩放因子细化成**分块缩放**。FP8 的 E4M3 编码只有四位指数、三位尾数，最大正规数为 448，单一全局因子无法让各层激活同时落入如此窄的范围。DeepSeek-V3 的 FP8 训练按块管理缩放：激活按 $1\times128$ 小块（每个 token、每 128 个通道）求 scale，权重按 $128\times128$ 块求 scale，矩阵单元每累加 128 个元素就把部分和转为 FP32 继续累加。与 BF16 的对照训练相比，相对损失误差低于 0.25%。

FP8 也改变容量账，改的只是送入矩阵单元的那份权重副本：DeepSeek-V3 的 FP8 训练把矩阵运算的操作数转成 FP8，主权重、梯度与优化器状态仍以更高精度保存。这份操作数副本每参数 1 byte，每 $128\times128$ 块附加一个 FP32 scale，合计每参数约 $1 + 4/16384 \approx 1.0002$ bytes；对 Qwen3-8B，矩阵运算读取的权重从 BF16 的 16.4 GB 降为约 8.2 GB，而状态表中每参数 16 bytes 的常驻训练状态并不因此降到 1 byte。

| 矩阵运算的权重格式 | 每参数字节（含 scale） | Qwen3-8B 矩阵运算读取的权重 | 缩放管理 | 主要数值风险 |
| --- | --- | --- | --- | --- |
| FP16 | 2 | 16.4 GB | 全局损失缩放 | 梯度下溢、缩放溢出 |
| BF16 | 2 | 16.4 GB | 无需 | 尾数较短，由 FP32 累加补偿 |
| FP8（E4M3）操作数副本 | 约 1.0002 | 约 8.2 GB（主权重与优化器状态另存） | 分块缩放与定期高精度累加 | 块内舍入、scale 过期 |

精度越低、缩放粒度越粗，节省的容量越多，数值偏离高精度参考的风险也越大。无论起因是缩放失效、数据异常还是硬件错误，训练偏离都表现为损失曲线上的尖峰（**loss spike**），常见的处理是回滚到上一份 checkpoint 重新训练。回滚损失多少进度由第 10.4 节的保存周期模型决定，第 10.4.5 节再把回滚的发生率计入该模型。

16 bytes 是怎么凑出来的，把表里的数字换成「每个参数要存几份」就一目了然：BF16 权重 2 B、BF16 梯度 2 B、FP32 主权重 4 B、一阶矩 4 B、二阶矩 4 B，加起来 16 B。权重和梯度各占一份 BF16，主权重与两份矩状态各占一份 FP32。这里的「约为 BF16 权重的八倍」也是这么来的：$16 \div 2 = 8$。

代入这里数字再复算一遍：$16N = 16 \times 8\,190\,735\,360 = 131{,}051{,}765{,}760$ B ≈ 131.05 GB（十进制），与这里 131.1 GB 一致；换成二进制 $131{,}051{,}765{,}760 / 1024^3 = 122.06$ GiB，与这里 122.1 GiB 一致。单看 BF16 权重是 $2N = 16.38$ GB ≈ 16.4 GB；每一项 FP32 状态是 $4N = 32.76$ GB ≈ 32.8 GB。把梯度换成 FP32 就是 $16 + 2 = 18$ bytes/参数，总量 $18N = 147.4$ GB。

训练比推理贵这么多，原因在于推理只需要一份 BF16 权重 16.4 GB，训练却要同时握住当前权重、权重梯度、高精度主权重和两份矩状态。这是优化器算法的内在需求：Adam 需要一阶矩和二阶矩来平滑梯度方向和尺度，这两个统计量必须跨迭代保留，就得一直躺在显存或主机内存里。这里强调「主权重更新后再转换为 BF16 供矩阵运算使用」，说明 BF16 权重其实是主权重的一个派生副本，存在的唯一理由是矩阵单元跑得快。

$M_{\text{peak},i}$ 这条公式要读懂它的「取最大值」：它是按时间取上确界，不能把三类简单相加后固定下来。理解它最好的办法就是这里那个 8 GiB 加 4 GiB 的例子，两者的生命周期重叠时峰值多 12 GiB，先释放激活、腾出空间再收集参数则几乎不额外增加。显存不够的时候，多半是同一时刻撞了车，总量其实还够。这直接导出后续两种优化手段：分片把同一份数据切小，减小 $M_{\text{persistent}}$；重计算和卸载改变生命周期，减小同时驻留量。

FP16 为什么必须配损失缩放、BF16 不用，差别在指数位。FP16 只有 5 位指数，范围约为 $[6.1\times10^{-5}, 65504]$；BF16 有 8 位指数，与 FP32 同范围（约 $[1.2\times10^{-38}, 3.4\times10^{38}]$）。梯度里大量数值非常小，这里引用的统计是约 5% 的值指数小于 −24，也就是小于 $6\times10^{-8}$，FP16 直接把它们变成 0，学习信号就丢了。把损失乘一个因子 $S$ 相当于把整个梯度谱整体上移，落回 FP16 能表示的范围，更新前再除回去。BF16 的指数位够宽，小梯度不会下溢，所以不用缩放，这也是状态表选 BF16 的原因之一。

FP8 的容量账要看清它改的是哪一份：改的只有矩阵运算的操作数副本，16.4 GB 变 8.2 GB，其余四类状态仍是 16 bytes 里的对应项。用这里的数字复算，$N \times 1.0002 \approx 8.19\times10^9 \times 1.0002 \approx 8.19$ GB，与约 8.2 GB 一致；其中 scale 的开销是每 $128\times128 = 16{,}384$ 个参数多 4 bytes，即 $4/16384 \approx 0.000244$ bytes/参数，所以系数是 1.0002 而不是 1.0000。低精度省下的是带宽和那一份副本，优化器状态一点没省。

分块缩放为什么必要：E4M3 只有 4 位指数、3 位尾数，最大正规数 448，动态范围极窄。用单一全局因子时，只要某一层的激活幅度比其他层大几个数量级，整层就会被截断或归零。按每个 token 每 128 通道、或 $128\times128$ 权重块各自求 scale，等于给每个小块单独找一个合适的基准点；代价是 scale 本身要存、要维护，而且 scale 过期（数据分布漂移）就会引入误差。

loss spike 与 checkpoint 的关系也在这里埋下：数值偏离最终表现为损失曲线的尖峰，工程上的标准动作是回滚到上一份 checkpoint 重训，回滚会白白烧掉一段训练时间。checkpoint 保存周期因此不只影响存储开销，也影响可用训练时间，第 10.4 节展开。

还有几个词容易被混用。「混合精度」只规定矩阵运算是低精度（BF16）、优化器状态是高精度（FP32），并不规定梯度用什么格式。这里专门点出「这一变化来自梯度的数据格式，『混合精度』一词本身并不规定梯度格式」，就是为了避免把 16 bytes 当成永远不变的常数，改成 FP32 梯度就是 18 bytes。

常驻状态与执行峰值要分开看：$M_{\text{persistent}}$ 是长期躺在卡上的量，$M_{\text{peak},i}$ 是瞬时上确界，后者还要加上激活和临时缓冲区。10.2 里会出现「常驻减半、峰值只降 23%」的现象，根子就在这两个量的区别。

FP16 与 BF16 的差别是：指数位 5 对 8（范围窄对宽），尾数位 10 对 7（精度高对低）。一个要防下溢，所以需要损失缩放；另一个不用缩放，但要靠 FP32 累加器补精度。

FP8 节省与优化器状态是两回事。把矩阵权重换成 FP8，不等于把训练状态换成 FP8，主权重、梯度、两份矩状态该多大还多大。

MoE 的容量与稠密模型是否相同，也要小心：状态容量由全部可训练参数决定。MoE 每次只激活部分专家，可每个专家都有自己的参数和优化器历史，都要保存，激活得少并不等于存得少。

训练状态就是权重 2B、梯度 2B、主权重 4B、两份矩 4B + 4B，合计 16 B/参数，Qwen3-8B 是 131.1 GB（122.1 GiB），只有分片、重计算和卸载能改变峰值。

### 10.1.3 计算需求、MFU 与资源下界

显存决定模型能否开始训练，计算速度决定能否按期完成。同一个模型的状态可以分到多张卡上，但究竟需要多少张卡，还要根据总计算量和期限判断。

一条 8,192 个 token 的序列在前向和反向传播中的矩阵计算量约为 $4.31\times10^{14}$ FLOPs，平均每 token 约 52.7 GFLOPs。处理 100B token 共需约 $5.27\times10^{21}$ FLOPs。这里的工作量由模型矩阵形状和前后向运算累计得到。

先假设这 30 天全部用于训练计算。H100 SXM 的稠密 BF16 矩阵运算峰值为 989 TFLOP/s，达到峰值的 40% 时，一张卡约能处理 7,500 token/s。五张卡合计约 37,600 token/s，低于 30 天所需的约 38,600 token/s，所以至少需要六张卡才能满足计算需求。相比之下，两张 80 GB 卡已能容纳理想均分的 131.1 GB 常驻训练状态，却需约 77 天完成计算。

设算法所需的总计算量为 $F$，卡数为 $p$，单卡峰值为 $P$，统计时段内的平均计算效率为 $\eta$，则

$$
T = \frac{F}{pP\eta}, \qquad p_{\text{compute}} = \left\lceil \frac{F}{P\eta T_{\text{available}}} \right\rceil
$$

本章按第 1.2.2 节的定义计算 MFU，分母取全部卡的峰值算力。若实际耗时取完整的训练迭代时间，通信等待已经计入其中；若只统计加速器执行计算的时间，得到的就是单卡计算效率。本章的设计案例采用后一种分解：单卡计算效率取 40%，随后把无法与卡内计算重叠的通信时间，以及等待输入数据的时间逐项加上，这样可以直接观察每项系统设计对完成时间的影响。

40% 来自 Llama 3 的公开记录：405B 模型在 8,192 至 16,384 张 H100 上预训练，BF16 MFU 为 38%—43%。这组数按整步耗时统计，本身已包含通信等待，本章再单独加上通信，算出的完成时间因此偏长。RTX 4090 没有 NVLink，卡间数据都要经过 PCIe，这部分代价在第 10.3.3 节按实际链路单独计算。图 10-3 至图 10-5 保留 30% 与 50% 两档，用来观察效率偏离时卡数如何变化。

另外六成峰值算力去了哪里，本章各节分别作答：无法与计算重叠的通信（第 10.3.3 节）、流水线气泡（第 10.3.2 节）、受内存带宽限制的参数更新与状态转换（第 10.2.3 节）、重计算（第 10.2.2 节）、掉队者（第 10.4.5 节）和 checkpoint 保存（第 10.4.3 节）。按第 1.3.4 节的判据，前四项是模型必须计入的工作，漏掉任何一项，估出的完成时间都会偏短；后两项和通信中没有重叠的部分则含有可以减少的开销，那才是系统设计的优化空间。

52.7 GFLOPs/token 是本节所有计算的基准。这里说它「由模型矩阵形状和前后向运算累计得到」，也就是把每一层矩阵乘的乘加次数加总（一次乘加记 2 FLOPs）。作为量级检查，稠密 Transformer 训练常见的粗略口径是每 token 约 $6N$ FLOPs（前向 $2N$ 加反向 $4N$）：$6 \times 8.19\times10^9 = 4.91\times10^{10} = 49.1$ GFLOPs，与这里的 52.7 GFLOPs 同一量级，多出来的部分来自注意力、归一化和词表投影等非「参数乘输入」的运算。这里提醒一句：$6N$ 只是量级对照，给出的是逐矩阵累计的确切值，复算一律以 52.7 GFLOPs 为准。

代入这里数字复算：

- 一条 8,192 token 序列：$8192 \times 52.7\times10^9 = 4.317\times10^{14}$ FLOPs，与这里 $4.31\times10^{14}$ 一致。
- 100B token：$100\times10^9 \times 52.7\times10^9 = 5.27\times10^{21}$ FLOPs，与这里一致。
- H100 一张卡 40% 效率下的吞吐：$989\times10^{12} \times 0.4 = 3.956\times10^{14}$ FLOP/s，除以每 token 的 52.7 GFLOPs 得 7,508 token/s，与这里「约 7,500 token/s」一致。
- 五张卡：$7{,}508 \times 5 = 37{,}540$ token/s ≈ 37,600，确实低于 30 天所需的 38,600；六张卡是 45,048 token/s，超过需求，所以是「至少六张」。
- 两张 80 GB 卡：单卡 7,508 token/s，跑完 100B token 需 $10^{11}/7{,}508 = 1.332\times10^{7}$ s ≈ 154.2 天，两张卡并行约 77.1 天，与这里「约 77 天」一致。
- 用 $p_{\text{compute}}$ 公式检验 4090 方案：$F = 1.66\times10^{17}$（每步）、$P = 165.2\times10^{12}$、$\eta = 0.4$、$T_{\text{available}} = 30 \times 86400 = 2{,}592{,}000$ s，则 $P\eta T = 165.2\times10^{12} \times 0.4 \times 2.592\times10^6 = 1.7128\times10^{20}$，$1.66\times10^{17}/(1.7128\times10^{20}) = 9.69\times10^{-4}$。这个式子算的是「一步的计算量在 30 天里占多少张卡」，要用整章的总量 $F_{\text{total}} = 5.27\times10^{21}$ 才对：$5.27\times10^{21}/(1.7128\times10^{20}) = 30.77$，向上取整 31 张，与这里「至少 31 张卡」完全一致。
- 每步在 32 卡上的耗时：$1.66\times10^{17} / (32 \times 165.2\times10^{12} \times 0.4) = 1.66\times10^{17}/(2.1146\times10^{15}) = 78.5$ s，与这里 78.3 s 一致（差异来自取整：改用 $4.31\times10^{14}\times384 = 1.655\times10^{17}$ FLOPs 复算即 78.3 s）。48 卡：$1.66\times10^{17}/(3.1718\times10^{15}) = 52.3$ s，与这里 52.2 s 一致（同一口径下为 52.2 s）。32 卡 78.3 s 大于 67.9 s，所以「加入通信前已经超时」；48 卡 $67.9 - 52.2 = 15.7$ s 余量，与这里一致。

图 10-3 至图 10-5 三个数字组可以自己验算。以 RTX 4090（峰值 165.2 TFLOP/s）为例：跑完 100B token 需要的卡·天数为 $5.27\times10^{21} / (86400 \times 165.2\times10^{12} \times \eta)$。$\eta = 0.4$ 时得到 923 卡·天，除以 30 天是 30.8，向上取整 31，与图 10-4 一致；$\eta = 0.3$ 时 1,231 卡·天 / 30 = 41.0，得 41，与图 10-3 一致；$\eta = 0.5$ 时 738 卡·天 / 30 = 24.6，得 25，与图 10-5 一致。用 H100 SXM 的 989 TFLOP/s 验算：$\eta = 0.3$ 得 205.6 卡·天/30 = 6.85，取 7（图 10-3）；$\eta = 0.4$ 得 154.2/30 = 5.14，取 6（图 10-4）；$\eta = 0.5$ 得 123.3/30 = 4.11，取 5（图 10-5）。三图数字全部自洽。A100 与 B200 的峰值这里未给出，故不作复算。

容量下限为什么在每张图里都远低于计算下限：131.1 GB 的常驻状态理想均分到 N 张卡就是 131.1/N GB（十进制），即使按每卡 80 GB 计，两张卡就够了，而计算需求动辄几十张卡。本章任务的结论很干脆，瓶颈在计算，不在容量。这也解释了后文为什么还要专门讲分片、重计算和卸载：它们的价值不在让这套方案能跑起来（32/48 卡方案本来就装得下），而在于减少通信与重算之外的额外显存压力，并为更大的 micro-batch 或更长序列留出余量。

MFU 口径的坑是本章时间账里最容易被误算的一处。MFU 的分母是全部卡的峰值算力，可代入公式的实际耗时有两种口径：用整步耗时做分母时，通信等待被算进「实际用掉的时间」，MFU 天然偏低；只用加速器执行计算的时间时，得到的是单卡计算效率。这里采用后一种口径，取 40%，然后把通信和输入等待一项一项加回来。这里还专门提示，Llama 3 的 38%—43% 是按整步统计的，本身含通信等待；本章在 40% 之外再加通信，算出的完成时间因此偏保守、偏长。理解这一点，就不会误以为 40% 加通信是双重扣减而算错了，这是这里有意选择的一种可分解口径，好处是每项系统设计对完成时间的影响可以直接看见。

另外六成算力去哪了，那份清单同时是本章的问题清单：无法重叠的通信、流水线气泡、受内存带宽限制的参数更新与状态转换、重计算属于必须计入的工作，漏了就低估工期；掉队者、checkpoint 保存以及通信中可重叠的部分属于可以削减的开销，那才是设计的优化空间。这条「必须计入」与「可以优化」的分界线，后面 10.2、10.3 会反复用到。

MFU 与单卡计算效率的分母相同（都是峰值），差别在统计时间是否包含非计算时间。本章的 40% 是后者，用于分解式估算；引用 Llama 3 的 38%—43% 时要注意那是前者。

「至少 31 张卡」与「至少 6 张 H100」都是计算下限，前提相同（30 天全部用于计算、40% 效率），差别只在硬件峰值：RTX 4090 为 165.2 TFLOP/s，H100 SXM 为 989 TFLOP/s。两者都按 5.27e21 FLOPs 总量算出；而 67.9 s/步 的预算对应的是 25 天，要求更高。

计算下限与容量下限也要分清：图里橙色菱形是「显存约束卡数下限」，蓝柱是「计算需求」。本章任务下蓝柱总是更高，所以两套候选方案（32、48 卡）是按计算需求与「每台八卡」的硬件粒度选出来的，并没有被显存逼着走。

每步 1.66e17 FLOPs 与总量 5.27e21 FLOPs 同样要分开：前者是全局 batch（384 条序列）一次迭代的量，后者是整个任务 100B token 的量。$1.66\times10^{17} \times 31{,}790 \approx 5.28\times10^{21}$，两者吻合。

计算需求 5.27e21 FLOPs 除以「卡数 × 峰值 × 效率 × 可用时间」就得到卡数下界：30 天全用是 31 张 4090，而 67.9 s/步 的预算只留给 48 卡约 15.7 s。

## 10.2 训练状态的分片、重计算与卸载

### 10.2.1 数据并行与 ZeRO／FSDP 状态分片

第 6 章按样本、特征、序列、层和专家介绍了六种并行方式。本节进入训练场景，进一步讨论数据并行副本内部的状态分片。

**FSDP（Fully Sharded Data Parallel，全分片数据并行）** 切分参数、梯度和优化器状态：这些状态分散到各个 rank，需要计算某一层时临时收集参数，反向完成后分散梯度。它主要解决训练状态的显存占用与副本冗余，通常与 DP、TP、PP 组合使用。

**SP（Sequence Parallel，序列并行）** 切分的是同一批输入的序列位置，主要作用于 TP 组中的 LayerNorm、Dropout 等逐 token 算子。进入需要完整 token 行的矩阵乘时，各卡收集输入，计算完成后再按位置分片。FSDP 管理模型状态的所有权，SP 管理中间激活的工作位置，两者的切分对象、通信时机和适用阶段各有侧重。论文图 1 将 FSDP 列为独立层级，正好说明训练状态分片与执行激活分片属于两条不同的并行轴。

状态如何分配到多张卡上，由并行方式决定。同步数据并行让各卡处理不同样本，再用归约后的梯度更新各自的参数。各卡得到的新参数相同，因此每张卡通常都保存一份相同的权重与优化器状态；卡越多，复制的状态越多。

**ZeRO** 由微软研究者在 2019 年提出、2020 年发表，用跨卡分片来减少大模型训练中重复保存的状态副本。ZeRO 分阶段划分这些状态的归属：每张卡只负责一部分参数的更新，其他卡通过通信取得执行所需的数据。

完全分片数据并行（FSDP）按同样的分片思路组织执行，参数、梯度与优化器状态都分片保存。下面用四张卡逐步改变状态的归属，再分析相应的执行方式。图中每列始终对应同一张卡；「完整」表示该卡保存整份状态，「片」表示只保存该卡负责的四分之一。

分片顺序按“占空间最大、与参数更新耦合最松”来排：先动优化器状态，再动梯度，最后才动每层前向都要用的权重。d=8 时，每卡常驻状态从 122.1 GiB 压到 15.3 GiB，但执行峰值压不动每个模块本来就要有的缓冲区。

前两个阶段仍为每张卡保留完整模型权重。图 10-9 再划分权重的归属，长期驻留的空间进一步下降，代价是执行每个模块前要通过通信取得所需的权重。

设数据并行组中有 $d$ 张卡。先计算常驻训练状态，普通数据并行和 ZeRO 三个阶段的每卡容量分别为

$$
M_0 = 16N, \qquad M_1 = 4N + \frac{12N}{d}, \qquad M_2 = 2N + \frac{14N}{d}, \qquad M_3 = \frac{16N}{d}
$$

第一阶段分片 FP32 主权重和两份 Adam 状态，共 12 bytes/参数，权重与梯度仍各保留一份。第二阶段再把梯度分片，完整复制只剩 BF16 权重。第三阶段连权重也分片。把 $d = 8$ 代进去，就得到下面的容量变化。

| 配置 | 每卡常驻训练状态/GiB | 完整复制的训练状态 |
| --- | --- | --- |
| 普通 DP | 122.1 | 权重、梯度与优化器状态 |
| ZeRO-1 | 42.0 | 权重与梯度 |
| ZeRO-2 | 28.6 | 权重 |
| ZeRO-3 | 15.3 | 常驻训练状态均已分片 |

分片的先后顺序是有讲究的，按占空间从大到小、按与参数更新的耦合从紧到松。第一阶段动的是最大头，主权重加两份矩状态合计 12 B/参数，它只在参数更新时用到，最容易异地保存；第二阶段分梯度，再多分出 2 B/参数的份额；第三阶段才碰权重，那最后 2 B 每层前向都要用，分片之后必须靠通信临时取回。

四个公式拆开看更清楚（这几句是我按公式逐项写的，这里只给了总式）。$M_0 = 16N$ 就是 10.1.2 的 16 B/参数什么都不分。$M_1 = 4N + 12N/d$ 里，权重 2 B 加梯度 2 B 仍然完整，合起来 $4N$，主权重与两份矩合计 12 B/参数由 $d$ 张卡均分。$M_2 = 2N + 14N/d$ 只剩 BF16 权重的 $2N$ 完整，其余 14 B/参数（梯度 2、主权重 4、两矩 8）都被切开。$M_3 = 16N/d$ 是 16 B/参数全分片，每卡只留 $1/d$。

代入这里数字复算一遍能确认表没写错（这几个数是这里按公式算的，这里只给了结论）。取 $N = 8.1907\times10^9$、$d = 8$，并注意 1 GiB = $1024^3$ B：$M_0 = 16N = 131.05\times10^9$ B $= 122.06$ GiB ≈ 122.1；$M_1 = (4 + 12/8)N = 5.5N = 45.05\times10^9$ B $= 41.95$ GiB ≈ 42.0；$M_2 = (2 + 14/8)N = 3.75N = 30.72\times10^9$ B $= 28.61$ GiB ≈ 28.6；$M_3 = 16N/8 = 2N = 16.38\times10^9$ B $= 15.26$ GiB ≈ 15.3。四项与表中数字逐项吻合。

规律也随之浮出来：每卡容量 ≈（完整复制的那部分）＋（分片的那部分除以 $d$）。$d$ 越大，后一项越趋近 0，前一项却永远消不掉。这正是 ZeRO-1/2 的瓶颈，也是必须走到 ZeRO-3 的原因。

分片以后，每个模块按这样的顺序执行：先通过 **AllGather** 取得所需参数，执行前向或反向，再通过 **ReduceScatter** 汇总梯度并分配梯度分片，让负责该分片的卡得到全部梯度贡献，最后各自更新所负责的参数。FSDP 的全分片执行也围绕这条路径组织。前向算完就释放完整参数，反向前就得再收集一次；保留完整参数，反向可以直接用，代价是这份完整权重会和后续激活同时占用显存。

这组状态差异在小实验里能直接观察到。一组用 PyTorch 第二代 FSDP 实现（**FSDP2**）做的 CPU 小模型实验，把参与的进程从两个增加到四个：参数更新后保留的状态从约 18 MiB 减到 9 MiB，执行峰值却只从约 39 MiB 减到 30 MiB。长期保存的部分减半，峰值只减少约 23%，因为执行中仍需约 21 MiB 的其他张量和缓冲区。分析分片后的容量需求，还要考察模块执行时参数与激活各需保存多久。

那个 23% 值得自己算一遍：$(39.16 - 30.14)/39.16 = 23.0\%$，剩下那份不随卡数缩小的量是 $30.14 - 9 = 21.14$ MiB，跟这里说的"约 21 MiB 的其他张量和缓冲区"对得上（这个差是我从这里两个数相减得到的）。$M_{\text{peak}}$ 的含义也就清楚了：分片只能压缩可均分的那部分，压不动每个模块执行时本来就要存在的那部分。

再回头看两条容易被混在一起的并行轴。一条切训练状态，管的是谁拥有哪份参数、梯度、优化器状态；另一条切执行激活，管的是某个中间张量此刻由谁负责算、放在哪张卡上。FSDP 属于前者，SP 属于后者。这里引用论文图 1，把 FSDP 列为与 DP、PP、EP、CP、TP 并列的独立层级，说的就是状态分片有自己的一条轴，同一条轴也可以被 TP／PP 的组合复用。

数据并行是每卡处理不同样本，分片是同一份状态由多卡分别保存一部分，FSDP 相当于数据并行加状态分片，这两件事要分开看。常驻容量随 $1/d$ 收缩，执行峰值还要叠加执行时必然存在的完整参数缓冲区、激活和临时空间，所以下降幅度小得多。AllGather 是每卡出一份、人人得全份，用来取回参数；ReduceScatter 是人人都出全份、每人得一份归约结果，用来把梯度求和后切开。

ZeRO 与 FSDP 的关系也顺带清楚了。这里说 FSDP 按同样的分片思路组织执行，并把参数、梯度、优化器状态都分片，可以理解为 ZeRO-3 思想的工程实现。两者的差别主要在实现层面：ZeRO 常作为优化器或通信库的分片策略，FSDP 由框架在执行图中按模块组织收集与释放，这里此处未展开这一区别。至于 SP 与 TP，SP 切的是序列位置，作用于逐 token 算子，通常复用 TP 组；TP 切的是层内矩阵。这里说 SP 管理中间激活的工作位置，强调的是给激活换个摆放方式，它并不减少参数。

通信发生在取参数和散梯度这两处，而这两处恰好都可以尝试与计算重叠，10.3.3 会用这一点算通信等待。工程上先上哪个阶段也有现成答案：ZeRO-1 通信最少，只多了一次参数更新相关的通信，通常作为先省显存又不改执行路径的第一选择；ZeRO-2 增加梯度 ReduceScatter 带来的粒度变化；ZeRO-3 通信最重，却能把常驻状态压到最低。本章的 32/48 卡方案最终选了全组 ZeRO-3（见 10.2.4），原因是 4090 只有 22 GiB 可用显存，需要把常驻状态压到 3.8／2.5 GiB，才留得出给激活与缓冲区的 10 GiB 余量。

ZeRO 的分片顺序就是优化器状态、梯度、权重，每卡容量等于仍完整复制的那部分加上其余部分除以 $d$：$d=8$ 时把 122.1 GiB 压到 15.3 GiB，但执行峰值压不动那些每个模块本来就要有的缓冲区。

### 10.2.2 激活的保留与选择性重计算

前向计算留下的激活，像草稿纸上记的中间步骤：反向回到这一层时，还要用到其中一些值。草稿全部保留，取用方便，却占空间；只保留部分步骤，缺失的值就要在使用前重新算出。参数分片已经减少了权重和优化器状态的复制，**激活重计算**走的是另一条路，用额外的计算换取保存这些中间值所需的空间。

拿矩阵运算 $Y = XW$ 说最清楚，$X$ 为输入、$W$ 为权重、$Y$ 为输出。前向计算结束后，$X$ 还要等到求权重梯度时使用。记损失为 $\mathcal{L}$，$dY = \partial\mathcal{L}/\partial Y$ 是后续计算传来的梯度，$dX$ 和 $dW$ 分别是损失对输入与权重的梯度，上标 $\mathsf{T}$ 表示矩阵转置，反向要计算

$$
dX = dY\,W^{\mathsf T}, \qquad dW = X^{\mathsf T} dY
$$

两路计算都要读上游梯度 $dY$，其中 $dW = X^{\mathsf T} dY$ 还要读前向输入 $X$；$dX = dY\,W^{\mathsf T}$ 读的是 $W$，而参数一直都在。反向的显存压力主要就来自前向输入和中间结果。若保留 $X$，就要让它从前向计算时一直驻留到反向计算用完为止；释放 $X$，则要在反向使用前从已保留的输入或中间结果出发，重新执行相应的前向计算。选择哪些值保留、哪些值重算，要看节省多少空间，以及重新计算需要多少工作。

一个具体算例能把这笔账算实。Qwen3-8B 的多层感知机（MLP，即本例的前馈子网络）先得到门控结果 $a$ 和上投影结果 $u$，再形成 $h = a \odot u$，最后计算 $Y = hW_{\text{down}}$。下投影的参数梯度 $dW_{\text{down}} = h^{\mathsf T} dY$ 需要 $h$，可 $h$ 只是 $a$、$u$ 逐元素相乘的结果，而 $a$、$u$ 在非线性算子的反向里本来就要用到。已为非线性算子的反向保留了 $a, u$，就可以在下投影反向前重新相乘，不必一直保留 $h$。

重建后只需在下投影反向即将开始时生成 $h$，并保留到这一步计算结束。这块缓冲区的大小如下：取 128 个 token 的 micro-batch 和 FP32 激活，$h$ 的形状为 $[128, 12288]$，占 $128 \times 12288 \times 4 = 6$ MiB；重建需要约 157 万次乘法。同一层的两个归一化加权输出形状均为 $[128, 4096]$，每个占 2 MiB，也可由已保存的归一化结果和权重重建。于是每层省去 $6 + 2 + 2 = 10$ MiB，每个 micro-batch 在九层组成的流水阶段中可省去 90 MiB，约 94 MB。

原方案为这些 GEMM 保存的输入每层共占 15 MiB，其中上述三个乘积占 10 MiB，其余 Q、K、V 和注意力输出占 5 MiB。九层阶段因此从 135 MiB 降到 45 MiB，即从约 142 MB 降到 47 MB。重建按层依次发生，最大的乘积工作区为 6 MiB；上一层用完后，下一层复用这块空间。

若有四个 micro-batch 同时等待反向计算，需要长期保存的数据就能减少 $4 \times 90 = 360$ MiB，约 377 MB，反向时则逐个 micro-batch 执行重建计算。这里的收益来自数据生命周期的差别：等待反向计算的 micro-batch 越多，需要长期保存的数据越多；逐层重建时，却只需反复使用同一块工作区。流水调度若让反向更早开始，等待反向计算的 micro-batch 数量又会下降。重计算与流水调度共同决定需要保存多少数据；新增的计算是否延长每步训练时间，则取决于它在时间线上的位置。

> 补充：10：填满排空事件模型、1F1B 事件模型、GEMM 输入张量的保留关系、选择性重计算。GEMM 输入采用 FP32 参考表示，九层的可重建乘积为 90 MiB，最大逐层重建工作区 6 MiB。流水图采用 save_nonlinear 策略保存的中间结果及其收发缓冲。

把这里数字复算一遍可以确认这串结论（下面的数是我按给出的形状和精度算的）。$h$ 的大小 $128 \times 12288 \times 4$ B $= 6{,}291{,}456$ B $= 6$ MiB（$6 \times 1024^2$）；重建乘法次数 $128 \times 12288 = 1{,}572{,}864 \approx 157$ 万；归一化加权输出 $128 \times 4096 \times 4 = 2{,}097{,}152$ B $= 2$ MiB；每层 $6 + 2 + 2 = 10$ MiB，九层 $10 \times 9 = 90$ MiB $= 94.37$ MB（$90 \times 1.048576$）；原方案九层 $135$ MiB $= 141.6$ MB ≈ 142 MB，重建后只剩那 5 MiB，九层 $45$ MiB $= 47.2$ MB ≈ 47 MB；四个 micro-batch 同时在等反向是 $4 \times 90 = 360$ MiB $= 377.5$ MB。全部与这里吻合。

157 万次乘法这个量级小得值得单独说一句。相对每一层数十 GFLOPs 的矩阵运算，它几乎可以忽略，重计算划算的原因就在这里。被重建的只是逐元素乘或小规模逐 token 运算，换成整个注意力块或大矩阵乘，这笔账立刻反过来；给出的判据始终是节省多少空间与重新计算需要多少工作两相比较。

"最大工作区只要 6 MiB"同样关键。如果九个层各自需要一块 6 MiB 的工作区同时存在，那就又变成 54 MiB 了。重建按层依次发生，上一层用完后下一层复用这块空间，这就是**工作区复用**：算力上把重建摊到时间维度，显存上只留一块。

还有一句把 10.2.2 和 10.3.2 连起来的话：等待反向的 micro-batch 份数 $k$ 直接乘在节省量上，$k \times 90$ MiB，而 $k$ 由流水调度决定。填满排空要求所有 $m$ 个 micro-batch 都做完前向才开始反向，$k = m$；1F1B 让较早的 micro-batch 尽快反向，$k$ 就小了。换一种调度，同一份重计算策略能省下的量随之变化。新增的计算会不会拖慢每步，看它在时间线上的位置：重建正好落在某个必须等待的间隙里（等上游梯度、等通信），相当于白捡；挤在关键路径上就会延长每步。这与 10.3.3 分析通信重叠的逻辑一致，同样是多做了一点事，落在关键路径内还是外，结论完全相反。

重计算（recomputation / activation checkpointing）与重跑（rollback）都叫"重算"，层级却完全不同。前者是同一层内部丢掉中间值、需要时现算，代价是几百次到几百万次额外运算；后者是 loss spike 之后回到旧 checkpoint 重训，代价是几分钟到几十分钟的训练进度。

保留 $h$ 与保留 $a$、$u$ 的账也不一样。保留 $h$ 要 6 MiB，且存活时间长，从前向一直撑到下投影反向；保留 $a$、$u$ 本来就是必须的，额外收益是把 $h$ 的 6 MiB 从长期驻留变成短期工作区。

省空间有两个方向，这一节讲的是减少需要同时保留的数据，靠生命周期差与工作区复用；10.2.1 的分片讲的是减少每一份的大小。两者常常一起用，机制不同。单位也要留心，这里同时给出两个口径（90 MiB ≈ 94 MB、135 MiB ≈ 142 MB、45 MiB ≈ 47 MB），换算系数是 $1$ MiB $= 1.048576$ MB，读表时不要混用。

门控乘积 $h$ 不必一直留着：$a$、$u$ 本来就要为反向保留，反向到该层时现乘一次只要 157 万次乘法，就能让每层少留 10 MiB、九层阶段少留 90 MiB。

### 10.2.3 CPU／GPU 卸载与缓冲区的使用时间

用已保存的结果重建数据的开销较小时，适合重计算。另一种办法是保留数据本身，把它移到容量更大的主机内存，使用前再传回 GPU，这就是**卸载（offload）**。选择卸载以后，原先的显存问题就变成了传输能否及时完成的问题。

假设一份状态大小为 $V$，链路有效带宽为 $B$，从可以开始传输到算子需要这些数据之间有 $W$ 秒，则超出这段时间的传输耗时为

$$
T_{\text{wait}} = \max\left(0,\ \frac{V}{B} - W\right)
$$

相应算子需要等待这段时间。$V/B$ 是传完这份数据要多久，$W$ 是从能开始传、到算子真正需要它之间的时间窗。窗口够长，$W \ge V/B$，传输完全被掩盖，等待为 0；窗口不够，差额 $V/B - W$ 就是算子必须干等的时间。$\max(0,\cdot)$ 这一项值得留意：所有提前预取的优化，本质都是在增大 $W$。传输和计算能重叠多少，取决于数据何时可发、链路何时空闲、相应算子何时需要这些数据。

**DMA** 由设备发起数据搬移，传输期间源数据必须保留。源缓冲在 DMA 结束前保持有效，目标缓冲从开始接收时就占用内存；卸载同时改变两端缓冲区的使用时间。工程上如果源和目标都在同一块显存里，就要预留两份；如果把源留在主机内存、目标直接写到显存，两端各有各的占用时间。这与 10.2.2 里工作区复用的思路一脉相承。

接着看一个卸载里的具体选择：在 CPU 还是 GPU 上转换梯度，哪个更快？门控投影的梯度形状为 $[12288, 4096]$，BF16 大小 $G = 96$ MiB，FP32 为 192 MiB。**CPUAdam** 是在 CPU 上执行 Adam 更新的实现，它使用 FP32 梯度，可以先传 BF16 再在 CPU 转换，也可以先在 GPU 转换再传 FP32。转换都要读 $G$、写 $2G$，共访问 $3G$ bytes。转换受内存带宽限制，读入 $G$（BF16）写出 $2G$（FP32），合计 $3G$ bytes，所以分母取带宽：GPU 取 RTX 4090 的 1008 GB/s 显存带宽，CPU 取第四代至强单路八通道 DDR5-4800 的 307.2 GB/s。记 CPU、GPU 转换吞吐为 $C_c, C_g$，链路有效带宽为 $B$，串行路径时间为

$$
T_c = \frac{G}{B} + \frac{3G}{C_c}, \qquad T_g = \frac{3G}{C_g} + \frac{2G}{B}
$$

两个式子的成本结构是这样的（这一条是我按公式对照这里写的）：CPU 转换路径 $T_c$ 跨链路传 $G$（96 MiB，因为传的是 BF16），再在 CPU 上做 $3G$ 的转换；GPU 转换路径 $T_g$ 先在 GPU 上做 $3G$ 的转换，再跨链路传 $2G$。两个式子里的 $G/B$ 与 $2G/B$ 都是跨链路传的字节数除以带宽，CPU 路径传 $G$，GPU 路径传的是 FP32 的 $2G$，GPU 路径原来那份 BF16 输入本来就在 GPU 上，不需要传。两者相减时，$2G/B$ 与 $G/B$ 的差正是多传的 96 MiB。

图 10-14 与图 10-15 的差别集中在跨越链路的箭头上：GPU 虽然转换更快，却要多传 96 MiB。链路越慢，这部分额外传输越容易抵消转换收益。

RTX 4090 经 PCIe 4.0 x16 连接主机，每方向 32 GB/s。在这条链路上，CPU 路径约为 $3.15 + 0.98 = 4.13$ ms，GPU 路径约为 $0.30 + 6.29 = 6.59$ ms。GPU 路径的转换少约 0.68 ms，传输却多约 3.15 ms，所以更慢。把数代进去复核（$G = 96$ MiB $= 96 \times 1024^2 = 100{,}663{,}296$ B $= 0.10066$ GB）：CPU 路径 $G/B = 0.10066/32 = 3.146$ ms，$3G/C_c = 3 \times 0.10066/307.2 = 0.983$ ms，合计 $4.129$ ms；GPU 路径 $3G/C_g = 0.30199/1008 = 0.2996$ ms，$2G/B = 0.20133/32 = 6.292$ ms，合计 $6.592$ ms。差额也对得上，转换上 GPU 省 $0.983 - 0.300 = 0.683$ ms，传输上多 $6.292 - 3.146 = 3.146$ ms，净差约 2.46 ms。

链路换成 GH200 中 CPU 与 GPU 之间的 NVLink-C2C，每方向 450 GB/s，多传 96 MiB 只增加约 0.22 ms，两条路径变为约 1.21 ms 和 0.75 ms，GPU 转换获得明显收益。复算过来：$T_c = 0.10066/450 + 0.983 = 1.207$ ms，$T_g = 0.2996 + 0.20133/450 = 0.747$ ms，多传 96 MiB 的代价从 3.146 ms 降到 0.2237 ms。

令两条路径耗时相等，可以求出两种方式快慢互换的带宽分界点

$$
B^* = \frac{1}{3\left(1/C_c - 1/C_g\right)} \approx 147\ \text{GB/s}
$$

这个式子的来历可以推一遍：令 $T_c = T_g$，得 $G/B + 3G/C_c = 3G/C_g + 2G/B$，两边消去 $G$ 再移项，$3(1/C_c - 1/C_g) = 1/B$，$B^*$ 就是这个式子的倒数。代入数字，$1/\left[3(1/307.2 - 1/1008)\right] = 1/(3 \times 0.0022631) = 1/0.0067894 = 147.3$ GB/s。物理含义很直白：链路越快，多传 96 MiB 的惩罚越小，而 GPU 转换更快的收益不变，所以高速链路偏向 GPU 转换、低速链路偏向 CPU 转换。该阈值把两种相反作用放在同一尺度上，147 GB/s 高于 PCIe 5.0 x16 的每方向 64 GB/s，所以经 PCIe 连接的卡在本算例中都应先传 BF16、在 CPU 上转换。

显存容量还带来另一项限制。GPU 转换期间原始 96 MiB 与输出 192 MiB 共存，峰值为 288 MiB（$96 + 192$）；先传 BF16 的路径则只需在 GPU 上保留参与这次转换的 96 MiB 梯度。选择 GPU 转换需要额外 192 MiB 缓冲区。卸载本来是来省显存的，选错转换位置反而多占显存，所以卸载的收益要同时看时间与容量两本账。

**SuperOffload** 是面向 GH200 这类 CPU 与 GPU 紧耦合芯片的训练卸载系统，它把转换位置和主机上的优化器执行一起安排，利用的正是转换速度、传输数据量和缓冲区使用时间之间的取舍。整步收益则由最后一桶梯度、CPU 上的参数更新和权重回传何时完成决定，卸载在这里属于系统工程：梯度下传、主机更新、权重回传这条链的尾部没对齐，前面省下的时间就会被尾部等待吃掉。

> 补充：11：梯度转换复算、快链路变体、SuperOffload 阅读与转换案例、CPUAdam 卸载记录。转换路径从 GPU 梯度就绪开始，到 CPU 可读取 FP32 梯度结束；两条路径均使用页锁定主机内存作为缓冲区。GPU 转换吞吐取 RTX 4090 的 1008 GB/s 显存带宽（calculations/configs/hardware.json）；CPU 转换吞吐取至强 Platinum 8480+ 规格的八通道 DDR5-4800，$8 \times 4800$ MT/s $\times 8$ B = 307.2 GB/s；两者都是按内存带宽计的上限。NVLink-C2C 每方向 450 GB/s 见 GH200 架构说明。

卸载与重计算都用来降低显存峰值，换的东西不一样。重计算丢掉数据、用到时重算，换的是算力；卸载把数据搬到主机内存、用到时传回，换的是传输。选择依据也简单：重算便宜就重算，传输窗口够长且链路快就卸载。转换位置与传输量的取舍同样是一组对立项，CPU 转换传 BF16（少传）但转换慢，GPU 转换快但要多传一份 FP32，分界点 $B^*$ 就是在比较这两者。

脚注提到两条路径都用页锁定主机内存作缓冲区，这是为了让 DMA 能直接搬，避免分页换出，否则实际带宽会远低于标称值；这里只在脚注提及，未展开。另外要区分有效带宽与标称带宽：$B$ 是链路有效带宽（PCIe 4.0 x16 每方向 32 GB/s、NVLink-C2C 每方向 450 GB/s），$C_c$、$C_g$ 是按内存带宽计的上限，实际值通常低于这些上限，这里也说明了这一点。

卸载把容量问题换成传得够不够快：$T_{\text{wait}} = \max(0, V/B - W)$；在本算例的 PCIe 4.0 上先传 BF16 再在 CPU 转换更快（4.13 ms 对 6.59 ms），只有链路超过约 147 GB/s 才轮到 GPU 转换。

### 10.2.4 组合并行方案中的每卡状态分配与互联拓扑

分片、重计算和卸载分别改变存储量、计算量和传输量。把这些办法组合成完整系统时，还要确定它们作用于哪些卡和通信组。第 6、7 章的并行方法在训练中划分不同的数据和计算：TP 切分层内矩阵，PP 划分层，DP 划分样本，EP 划分专家。

第 6.1.4 节的一览表还包括 SP 与 CP：前者让逐 token 算子的激活沿序列分片，通常复用张量并行组；后者把同一条长序列的注意力上下文分到多张卡，保留跨位置的依赖。这些并行方法延续第 5 章"分块—安排输入—汇合结果"的方法，训练再沿相同计算图逆向传播梯度。先确定每份参数由谁更新，再沿前向和反向的依赖关系安排收集、交换与归约，就能同时得到每卡容量和各接口流量。

三种容量优化可以用同一组问题比较。

| 方法 | 减少的显存占用 | 增加的工作 | 决定收益的时间关系 |
| --- | --- | --- | --- |
| 状态分片 | 重复保存的权重、梯度或优化器状态 | 参数收集、梯度归约并分片 | 收集能否赶在模块执行前完成 |
| 激活重计算 | 前向到反向之间保存的中间值 | 重建前向值 | 重建是否延迟关键路径上的反向计算 |
| 状态卸载 | 加速器上暂时不用的状态 | 主机与加速器间传输 | 数据能否在使用前传回 |

表格里最关键的是最后一列。三种手段其实是在三个不同的资源账户之间做兑换：分片把显存换成通信（收集参数、归约梯度），重计算把显存换成算力（重建前向值），卸载把显存换成传输（主机与加速器之间）。少占的显存如果不能换来时间收益，通信没藏在计算里、重建落在关键路径上、数据没在使用前传回，那这个手段只解决能不能跑，不解决跑得快不快。

"先确定每份参数由谁更新，再安排收集、交换、归约"这句话是组合并行的方法论。TP、PP、DP、EP 各自规定了不同的切分维度，叠起来以后，每张卡上存哪些参数分片、每个通信组里谁跟谁通信，需要沿计算图重新推一遍。这里说这样能同时得到每卡容量和各接口流量，容量分析和通信量分析因此是同一个依赖图的两种读法。

六个缩写一句话分工：TP 切层内矩阵（同一层内拆列或行），PP 切层（不同卡负责不同层），DP 切样本（每卡一批不同数据），EP 切专家（MoE 的专家分布到不同卡），SP 切序列位置（逐 token 算子的激活沿序列分片），CP 切上下文（同一条长序列的注意力上下文分到多卡，保留跨位置依赖）。前四个在本节直接用到，SP／CP 这里只作定位，细节在第 6 章。

接着是一个显存不足时该怎么选的例子：增加分片的卡数，还是重计算激活？RTX 4090 标称 24 GB，约合 22.35 GiB；扣除运行时占用，每卡按 22 GiB 可用显存计。Qwen3-8B ZeRO-3 在八卡上每卡保存约 15.3 GiB，留给其他张量和缓冲区约 6.7 GiB。如果激活与临时缓冲区同时需要 10 GiB，总量约 25.3 GiB，超出约 3.3 GiB。此时可以用重计算节省这 3.3 GiB，也可以增至十六卡，将常驻训练状态降到约 7.6 GiB，总量降至约 17.6 GiB。

这个例子的算术很干净，复算一遍（下面的数是我按 $M_3 = 16N/d$ 算的）：$d = 8$ 时 $16 \times 8.1907\times10^9/8 = 16.38\times10^9$ B $= 15.26$ GiB ≈ 15.3；$d = 16$ 时 $8.19\times10^9$ B $= 7.63$ GiB ≈ 7.6。$15.3 + 10 = 25.3$，$25.3 - 22 = 3.3$；$7.6 + 10 = 17.6$。3.3 GiB 这个量级和 10.2.2 里每层省 10 MiB、九层省 90 MiB 不在一个层级上，走重计算这条路要动的是更多层的中间结果。

## 10.3 训练步的流水调度与通信重叠

容量分析回答了显存能不能装下所需数据，时间分析回答了数据能不能及时送到。到了这一节，要先把一次训练迭代究竟在优化什么写清楚，再把前向、反向与通信摆到同一条时间轴上看。本章的设计案例走的是数据并行这条路；四阶段流水另外当一个算例，用来说明调度同时改变了关键路径和激活的生命周期这两件事。

### 10.3.1 micro-batch、梯度累积与参数更新

全局 batch 指的是一次参数更新用到的全部样本。它不一定要塞进一次前向反向里，可以切成若干个 micro-batch 依次跑反向，把梯度累积起来，最后统一更新参数一次。设 micro-batch $k$ 中有效 token 的索引集合为 $S_k$，有效 token 总数为 $L = \sum_k |S_k|$，token 平均损失写成

$$
\mathcal{L} = \frac{1}{L}\sum_k \sum_{j \in S_k} \ell_j
$$

这一节的技术核心就是这个共同分母 $L$。梯度的加法可以交换顺序，所以「把全局 batch 拆成 micro-batch 分别反传、再把梯度加起来」和「对全局 batch 一次反传」在数学上等价，但等价有个前提：每个 micro-batch 的损失都除以全局的 $L$，不能改成各自的 token 数。这里把这句话写得很直白，计算每个 micro-batch 的损失时「都用其损失总和除以同一个 $L$」。全部 micro-batch 的梯度累积完毕，才执行一次梯度裁剪和一次参数更新。这样切分只改执行顺序，不改变各个 token 在损失函数里的权重。

分母为什么这么要命，这里用一个八条回答的例子来说明。八条回答里四条各含两个有效 token，四条各含三个，合计 20 个；短回答每 token 的损失记为 $\theta/5$，长回答记为 $2\theta/5$。按 token 平均时

$$
\mathcal{L} = \frac{8\theta/5 + 12(2\theta/5)}{20} = \frac{8\theta}{25}, \qquad \frac{d\mathcal{L}}{d\theta} = 0.32
$$

这个结果可以手工核一遍：四条短回答各 2 个 token 共 8 个，四组长回答各 3 个共 12 个，$L = 20$ 对得上；短回答每 token 贡献 $\theta/5$，8 个合计 $8\theta/5$，长回答每 token $2\theta/5$，12 个合计 $24\theta/5$，总损失 $(8\theta/5 + 24\theta/5)/20 = 8\theta/25 = 0.32\theta$，导数 0.32。（的代入复算是这里补的）

换成别的分母，梯度就变了。若先求每条回答的平均损失，再对八条回答取平均，短回答与长回答各占一半权重，梯度成为 $(0.2+0.4)/2 = 0.30$。按 token 平均时长回答占 $12/20 = 60\%$，所以结果更靠近 0.4；一旦改成按回答平均，长回答那三个 token 就被压成与短回答的两个 token 等权，样本单位从 token 悄悄换成了回答。还有一种叠错的方式：已经用 20 做共同分母，累积之后又除以八，梯度变成 **0.04**，相当于把梯度再缩小到 $1/8$。三处分母摆在一起，结论只有一句，分母决定每个 token 对参数梯度的贡献。

回到设计案例。第 10.1.3 节那 384 条完整长度的序列，在 32 卡上每卡累积 12 个 micro-batch，48 卡上每卡累积 8 个。384 条序列都是等长的 8,192 token，每卡一次只处理一条，也就是 micro-batch 等于一条序列，所以每张卡执行的矩阵形状完全相同，全局有效 token 数和目标函数也相同。两套方案的差别只是每步循环 12 次还是 8 次，这给后面把通信按 micro-batch 逐层排进时间轴留了方便。参数收集和梯度通信则随执行路径另行排入时间轴，不属于目标函数。

工程上还有一点不能含糊：如果按 micro-batch 各自平均再累加，每个 micro-batch 里长回答占比不同，就会给出不同的加权，梯度方向随切分方式漂移，等于隐式换掉了损失函数。累加得到的已经是对全 batch 的平均梯度，不必再除 micro-batch 个数，再除一次就是上面那个 0.04。裁剪也必须作用在完整梯度上，因为裁剪看的是梯度范数；每个 micro-batch 各自裁剪，范数就被切碎了。补充：13记的实验口径是把 verl 小模型的真实闭环、loss 与更新都对着源码核过：固定 Qwen2.5-0.5B-Instruct、单卡 NO_SHARD、`no_sync=False`，用真实长度结构去核对，验证教学用的标量推导与真实框架实现是否一致。

> 补充：13：固定 verl 小模型真实闭环、loss 与更新的源码核对。固定 Qwen2.5-0.5B-Instruct 训练配置采用单卡 NO_SHARD、no_sync=False；源码和版本锁定见链接中的记录。0.32／0.30／0.04 使用真实长度结构与教学标量损失推导。

### 10.3.2 流水线调度、气泡与激活的生命周期

micro-batch 的划分保住了训练目标，却改掉了计算的先后顺序。在流水线并行里，顺序还决定每个阶段何时能开始计算，以及有多少份激活正在等反向。流水线并行把模型切成多个阶段，每个 micro-batch 依次前向，再沿反方向把梯度传回去。

最朴素的排法是填满排空（fill–drain）：先让所有 micro-batch 走完前向，再集中做反向。1F1B（one forward, one backward）改了这件事，流水线预热之后交替执行一次前向和一次反向，较早的 micro-batch 因此更快释放激活。反向需要前向保存的激活，所以每个 micro-batch 的激活从它的前向完成起就得留在显存里，一直等到对应的反向到达；同一时刻有几个 micro-batch 在等反向，显存里就有几份激活。填满排空要等全部 $m$ 个 micro-batch 的前向都做完才开始第一个反向，峰值随 $m$ 线性增长，一旦超出显存容量，这一训练步根本执行不了，只能减少同时在流水线中的 micro-batch、缩短序列，或者改用代价更高的重计算来换可行性。

提前反向就是提前结束激活的等待。峰值降下来，训练步才装得下；释放出的余量也可以让给更大的 micro-batch 和更长的序列。显存驻留在这类系统里常常已经跨过了快慢的层面，直接决定这一步能不能跑起来。比较任意两种调度，都得同时看两根轴：完成时间取决于流水线里空闲等待（气泡）的大小，显存驻留取决于每份激活要保存多久才等到自己的反向。

先看时间这根轴。设 $p$ 个阶段完全平衡，每阶段前向耗时 $t_f$、反向耗时 $t_b$，传输和参数更新暂取零，$m$ 个 micro-batch 填满排空需要

$$
T = (m + p - 1)(t_f + t_b), \qquad u = \frac{m}{m + p - 1}
$$

式里的 $m$ 项对应 micro-batch 的实际计算工作，$p - 1$ 项来自填充和排空。卡的时间利用率 $u$ 因而随 micro-batch 数量增加而提高。取 $p = 4$、$m = 8$，得到 $u = 8/11 \approx 72.7\%$。若保持全局 batch size 不变，增加 micro-batch 数量意味着缩小每个 micro-batch，由此省下的流水线空闲时间，得与更小矩阵的执行时间一起比较。

气泡是这么来的：阶段 0 做完第一个 micro-batch 的前向，阶段 1 才能开始；阶段 3 要等前三个阶段都填上。填充和排空期间总有些阶段闲着，这段空闲就是气泡。把这里数字代进去核一遍：$p = 4$、$m = 8$ 时 $u = 8/(8+3) = 8/11 = 0.7273$，与 72.7% 一致；无传输的填满排空 $(8+4-1)\times(10+20) = 11 \times 30 = 330$ ms，加上前向填充跨三条边界的 $3 \times 1 = 3$ ms、反向排空再 3 ms、参数更新 1 ms，共 $330+3+3+1 = 337$ ms。（这两处复算是这里补的。）

换个角度看气泡的规模。$p = 4$ 时气泡永远至少占 $3/(m+3)$：$m = 8$ 是 27.3%，$m = 16$ 降到 $3/19 = 15.8\%$。这里后面还有一组数字说「16 个 micro-batch 时 1F1B 的气泡占比从 37.5% 降到 18.8%」，那一处换了口径，分母取 $m$，量的是气泡相对实际计算工作量的比例，$3/8 = 37.5\%$、$3/16 = 18.75\%$。读这两个百分比时得留意分母不同，前者是 $m+p-1$，后者是 $m$。

现在把 1F1B 放进同一个算例。将 Qwen3-8B 的 36 层分为四个九层阶段，八个 micro-batch 各含一条 128 个 token 的序列；每阶段前向 10 ms、反向 20 ms，边界传输每次 1 ms，正反方向链路独立，参数更新耗时 1 ms。填满排空调度无传输时为 $(8 + 4 - 1) \times 30 = 330$ ms，前向填充经过三条边界增加 3 ms，反向排空再增加 3 ms，参数更新增加 1 ms，总计 337 ms。

1F1B 更早开始反向，后续的前向也就得等反向释放计算资源。在阶段 0，前四个 micro-batch 于 40 ms 完成前向，第一份传回的梯度于 106 ms 到达，随后反向执行到 126 ms，第五个 micro-batch 才开始前向。这种交错逐级影响下游的到达时间。阶段 3 在 93 ms 完成第二个 micro-batch 的反向，但第三个前向输入到 95 ms 才到，于是空出 2 ms；后续相似的等待继续延长关键路径。按这些依赖关系排定执行顺序后，所有梯度在 346 ms 时计算完毕，加上参数更新共为 347 ms。

两图对比能看出最关键的一句话：两种调度做相同的前后向工作，气泡时间同为 $(p-1)(t_f + t_b)$，都是 $3 \times 30 = 90$ ms。1F1B 反而因交错引入的依赖等待（图 10-19）多用约 3% 的时间，收益体现在图 10-20 上，中间结果与缓冲区的最大显存占用从约 2.57 GB 降到 0.97 GB，减少约 62%。差别在于气泡的分布：1F1B 把气泡打散成许多小空隙，比如图 10-19 那个 2 ms 的等输入空隙，空隙是因为反向占用了计算资源、前向要等；填满排空则把气泡集中成一整段填充和一整段排空。气泡一样大，分布不同，激活驻留时间就不同，这就是两根轴的由来：时间轴打平，显存轴分出胜负。所以「1F1B 优于填满排空」只在显存这根轴上成立，在时间轴上反而略慢。若只给这些中间结果和缓冲区留 1 GB，只有提前反向的调度能执行这一训练步；容量充裕时，337 ms 的填满排空完成得更早。选择哪种调度，由「何时释放张量」和「何时得到下一份输入」共同决定。

显存收益和激活释放这两件事都可以再核一遍：$(2.57 - 0.97)/2.57 = 62.3\%$，时间代价 $(347-337)/337 = 2.97\%$，与这里的约 62% 和约 3% 都对得上。2.57 GB 与 0.97 GB 也不是另算的，它们正是后文中两种调度的最高单阶段峰值：填满排空的 2,448 MiB $= 2.567$ GB，1F1B 的 921 MiB $= 0.966$ GB（$1$ MiB $= 1.048576$ MB），两处口径自洽。（这些换算是这里补的。）

「只留 1 GB 时只有 1F1B 能跑」把容量是可行性问题这句话落到了具体数字上：1F1B 的峰值 0.97 GB 小于 1 GB，填满排空的 2.57 GB 大于 1 GB。资源刚好卡在两者之间时，慢的那个方案连被比较的资格都没有。这里在 10.3.2 末尾和 10.2.4 的例子里都出现过同一条准则：先按容量排除不可行方案，再比完成时间。

要缩短完成时间，就得压缩气泡本身：反向拆得更细、同时流动的 micro-batch 更多，空隙就能填得更满。下面三类调度都建立在上面那套依赖分析之上，各自用通信次数、激活峰值和参数量去换更小的气泡。三者沿用同一算例（四个阶段、前向 10 ms、反向 20 ms、边界传输 1 ms、参数更新 1 ms），各 micro-batch 在每个阶段上的槽位顺序由事件模型排定，气泡公式与反向拆分的思路来自已发表的论文。

交错式 1F1B（interleaved 1F1B，又称虚拟流水线）把 36 层切成八个块，轮流分给四张卡，每卡拿到 $v = 2$ 个不连续的块，合计仍是九层：前四块各五层、后四块各四层，卡 0 执行第 0—4 层与第 20—23 层，其余各卡依次类推。每个 micro-batch 的前向因此要跨越边界 $2p - 1 = 7$ 次，填满排空原本只需 3 次，气泡比例从 $(p-1)/m$ 缩小为

$$
\frac{1}{v}\cdot\frac{p-1}{m}
$$

八个 micro-batch 时完成时间从 347 ms 降到 298 ms，每卡空闲从约 106 ms 降到约 57 ms。代价有两项：传输次数增加一倍以上，全步前向消息从 24 次增到 56 次；较早阶段的激活要等待更多块完成前向，阶段 0 的激活与收发缓冲峰值从 921 MiB 升到约 1,329 MiB。边界数 $2p-1 = 7$、前向消息 $8 \times 7 = 56$ 次（原为 $8 \times 3 = 24$ 次）、层块分配 $4$ 块 $\times 5$ 层 $+ 4$ 块 $\times 4$ 层 $= 36$ 层，都能对上。（这三项是。）

零气泡（zero-bubble）调度把反向拆成两段。输入梯度 $dX$（论文记作 B）要传给上一阶段，上一阶段在等它，所以它待在关键路径上，应该尽早执行；权重梯度 $dW$（论文记作 W）只交给本层的梯度累积，可以放在本阶段对应 $dX$ 之后的任意时刻，于是被推迟到空隙里执行。设每阶段前向、$dX$、$dW$ 的耗时分别为 $T_F$、$T_B$、$T_W$，则 1F1B 的气泡为 $(p-1)(T_F+T_B+T_W)$；ZB-H1 把 $dW$ 填进空隙，气泡降为 $(p-1)(T_F+T_B-T_W)$；ZB-H2 再把更多前向提前，气泡降为 $(p-1)(T_F+T_B-2T_W)$。零气泡论文的两种手工调度按 $T_F = T_B = T_W$ 构造，论文表 2 给出上述一般形式。

零气泡的核心在于反向里两路梯度的重要性不一样。$dX$ 要给上一阶段，上游在等它；$dW$ 只进本层的梯度累积桶，没有任何下游在等它，所以它可以挪到反正闲着的时间片里。这里那句「$dW$ 位于本层，可以放在本阶段对应 $dX$ 之后的任意时刻」就是全部依据。本例把 20 ms 的反向对半拆成 $T_B = T_W = 10$ ms：1F1B 的气泡为 $3 \times 30 = 90$ ms，ZB-H1 的下界为 $3 \times (10 + 10 - 10) = 30$ ms，ZB-H2 的下界为 0。按论文图 3 的 ZB-H1 槽位顺序排定事件模型后，八个 micro-batch 的完成时间为 283 ms，每卡空闲 42 ms；把边界传输取零，空闲恰好是 30 ms 的下界，多出的 12 ms 来自传输。阶段 0 的激活与收发缓冲峰值与 1F1B 相同，都是 921 MiB。代价落在靠后的阶段：阶段 3 的 $dW$ 比 $dX$ 晚三个 micro-batch 执行，事件模型把这段时间里的激活按完整一份保留，阶段 3 的峰值从 1F1B 的 308 MiB 升到约 1,226 MiB。论文按 $dW$ 实际所需的较小激活量计算，其表 2 中 ZB-H1 的峰值与 1F1B 同为 $pM_B$（$M_B$ 为一个 micro-batch 的激活量）。

推迟 $dW$ 等于让激活多活三个 micro-batch 的时间，这也解释了为什么 ZB-H1 的完成时间能降到 283 ms、阶段 3 的激活峰值却涨到 1,226 MiB。把数字再核一遍：1F1B 气泡 $(p-1)(T_F+T_B+T_W) = 3 \times (10+10+10) = 90$ ms，ZB-H1 下界 $3\times(10+10-10) = 30$ ms，ZB-H2 下界 $3\times(10+10-20) = 0$；ZB-H1 实测空闲 42 ms 与下界 30 ms 的差 12 ms 来自边界传输，每个 micro-batch 都要过边界，$8 \times 1$ ms 量级的两端合计约 12 ms，这里只说多出的 12 ms 来自传输。（这些代入是这里补的。）

DualPipe 把 micro-batch 分成两半，从流水线两端相向注入，每个阶段同时承载两个方向的块。沿用 DeepSeek-V3 的记号，它的气泡为

$$
\left(\frac{PP}{2} - 1\right)\left(F\&B + B - 3W\right)
$$

其中 $PP$ 为流水线阶段数，$F\&B$ 为前向与反向重叠执行的时段，$B$ 指完整反向 20 ms，$W$ 指其中的 $dW$ 10 ms。本例不模拟前向与反向的计算重叠，取 $F\&B = F + B = 30$ ms，气泡为 $(2-1)\times(30+20-30) = 20$ ms，完成时间为 306 ms。代价同样直接：每卡要保存两个方向的参数副本，参数量翻倍，激活保留 $PP+1$ 份；本例各阶段峰值约为 1,228—1,612 MiB。这一处也核得上：$(PP/2 - 1) = 2-1 = 1$，$F\&B + B - 3W = 30+20-30 = 20$ ms，完成时间 306 ms 比 1F1B 的 347 ms 少 41 ms、比零气泡的 283 ms 多 23 ms。

### 10.3.3 反向依赖、梯度分桶与通信重叠

上一节那个 2 ms 空隙来自输入尚未到达。梯度通信受同一条规律支配：发送之前要等数据产生，发送时又要等链路空闲。反向传播逐层产生梯度，实现中通常把多个梯度张量合并成一个通信桶（bucket），等桶内所有梯度都算完再发送。桶越大，越可能被最后生成的那个梯度拖住；桶越小，需要启动通信的次数就越多。调度要在这两者之间找平衡。

设想归约需要 3 ms，梯度就绪之后还有 5 ms 与它无关的计算，归约本来可以和这段计算同时进行。但链路此前已经安排了 4 ms 的专家交换，归约只能利用剩下的 1 ms，另有 2 ms 延伸到计算之后。这 2 ms 无法与计算重叠、会延长训练步，称为通信等待时间。这里的依赖关系有三层：数据依赖给出最早开始时刻，资源争用把它往后推，后续算子的依赖关系决定这段等待是否延长整个训练步。图 10-26 那 2 ms 之所以真的延长了训练步，是因为那段归约处在关键路径上；如果它在路径之外，2 ms 只是填掉了一个本来就要等的空隙。

图 10-25 和图 10-26 暂时把梯度产生的时刻固定住了。实际训练还可以改变计算顺序，让某些梯度更早产生，把归约在时间轴上提前。矩阵反向里，输入梯度 $dX$ 交给前一层继续反向，参数梯度 $dW$ 交给本层的归约。先算 $dX$ 可以让前一层更早开始反向传播，先算 $dW$ 则可以更早启动本层的梯度通信。两者争用同一份计算资源，改变顺序等于重新分配通信窗口，这也是训练调度必须同时看前后向依赖的原因。

现在用这条规律算设计案例的通信等待。两套方案都采用全组 ZeRO-3，每个 micro-batch 要做三次集合通信：前向之前用 AllGather 收集一遍 BF16 权重，反向之前再收集一遍，反向之后对 BF16 梯度做一次 ReduceScatter。每次集合通信中，每张卡收发的字节为 $(d-1)/d \times 2N$，48 卡时约 16.0 GB。每卡累积 $m$ 个 micro-batch，一步的通信量为

$$
V = 3m \cdot \frac{d-1}{d} \cdot 2N
$$

48 卡时 $m = 8$，$V \approx 385$ GB；32 卡时 $m = 12$，$V \approx 571$ GB。

这些字节走哪条路，由硬件定。RTX 4090 没有 NVLink，也不支持卡间 P2P（一张卡经 PCIe 直接读写另一张卡的显存），同一台主机里的两张卡交换数据也要经过主机内存，所以每张卡的全部收发都得穿过各自的 PCIe 4.0 x16，每方向 32 GB/s。按公开的 4090 集群配置分析，每台八卡主机配八张 200 Gbit/s 网卡，每张 25 GB/s；环形集合通信把跨主机的流量分到八张网卡上，网卡不是瓶颈。于是 48 卡每步的链路时间约为 $385/32 \approx 12.0$ s，32 卡约为 17.9 s。

链路时间并不等于通信等待，这是本小节最容易算错的地方。链路时间是这些字节走完链路需要多久，12.0 s 或者 17.9 s；通信等待是其中没能被计算掩盖、真正拖长关键路径的那部分。把 17.9 s 直接加进每步耗时，会得出 32 卡每步 96 s 这种完全错误的结论。ZeRO-3 的做法是在执行某一层之前预取它的参数，一层反向结束后立即归约它的梯度。48 卡每个 micro-batch 的链路时间约 1.50 s，而这个 micro-batch 的计算约 6.53 s；逐层看，收集一层约 0.39 GB 的参数只需约 12 ms，也远短于这一层的计算。通信与计算之比约 23%，大部分通信都能落在计算之内。MegaScale 在数据并行里采用同样的做法，并指出无法隐藏的只剩一步中第一次 AllGather 和最后一次 ReduceScatter。对 Qwen3-8B，这两次通信都作用于约 1.24 GB 的词嵌入：词嵌入是前向的第一层，也是反向最后求出梯度的一层。两次合计约 0.08 s，这就是每步的通信等待。参数更新和卡内的非矩阵运算已包含在单卡计算效率里，两套方案在输入就绪时的每步耗时分别约为 78.4 s 和 52.3 s。

为什么偏偏是这两次藏不住，看 ZeRO-3 的执行顺序就明白了。它的顺序是某层参数先收集、再算、再散梯度。对第一层来说，在它开始计算之前没有别的前向计算可以拿来掩盖收集它的通信，所以第一次 AllGather 必然露在外面；对最后一层来说，在它的梯度归约完成之前反向就结束了，没有后续计算可以掩盖。两处的字节数都等于词嵌入的大小 1.24 GB，合起来 0.08 s。

把这一节的数字核一遍。$N = 8.1907\times10^9$，$2N = 16.38$ GB。每次集合通信每卡收发 $\frac{d-1}{d}\times 2N$，$d = 48$ 时 $\frac{47}{48}\times 16.38 = 16.04$ GB，与约 16.0 GB 一致。$V = 3m\cdot\frac{d-1}{d}\cdot 2N$：48 卡（$m = 8$）$3\times8\times16.04 = 384.9$ GB ≈ 385 GB；32 卡（$m = 12$）$\frac{31}{32}\times16.38 = 15.87$ GB，$\times 36 = 571.3$ GB ≈ 571 GB。链路时间 $385/32 = 12.03$ s ≈ 12.0 s，$571/32 = 17.84$ s ≈ 17.9 s。48 卡每个 micro-batch 三次集合通信共 $3 \times 16.04 = 48.1$ GB，除以 32 GB/s 得 1.504 s ≈ 1.50 s，该 micro-batch 的计算 $52.3/8 = 6.54$ s ≈ 6.53 s。每层参数收集 $0.39/32 = 12.2$ ms ≈ 12 ms，这一项直接引用设计案例逐层参数表算出的 0.39 GB。词嵌入按 Qwen3-8B 的词表 151,936 与隐藏维 4096 算，BF16 下 $151{,}936\times4096\times2 = 1.2447\times10^9$ B ≈ 1.24 GB，两次通信共约 2.48 GB，除以 32 GB/s 得 0.0776 s ≈ 0.08 s。输入就绪时的每步耗时 $52.2 + 0.08 = 52.28$ s ≈ 52.3 s，$78.3 + 0.08 = 78.38$ s ≈ 78.4 s。（以上代入复算是这里补的。）这里还有个容易忽略的后果：这两个数仍然大于 67.9 s 预算中 32 卡那一档，所以 32 卡方案即便通信只等 0.08 s 也无法按期，48 卡则留下 $67.9 - 52.3 = 15.6$ s 给输入等待、checkpoint 分摊与故障恢复。

> 补充：17：本章设计案例的输入、推导与复算。32／48 卡的容量预留、输入等待和计划停顿为给定输入；单卡计算效率取 Llama 3 的 MFU；模型矩阵工作来自既有 training-deadline 计算，ZeRO-3 通信量由同一份参数表推出。RTX 4090 的 PCIe 4.0、无 NVLink 见 RTX 4090 规格页，卡间不支持 P2P、八卡主机配八张 200 Gbit/s 网卡见 4090 集群配置分析；一步中只有第一次 AllGather 与最后一次 ReduceScatter 无法隐藏见 MegaScale §3.2。逐项数值与独立复算保存在 design-case.json。

通信大多被计算覆盖，这件事也给优化设定了收益上限。若一段 1.3 s 的归约中只有 0.2 s 延续到反向计算结束之后，在其余时间轴不变时，哪怕把这段通信等待彻底消除，整步至多缩短 0.2 s。计算覆盖通信做得越好，通信优化的收益天花板就越低；此时若还差 0.5 s 才能满足目标，就得同时缩短其他关键路径工作，比如落在关键路径上的那部分重计算、输入等待、掉队者。

**案例：全局 batch 不变时，卡数增至四倍能加速多少？** 大规模分布式训练系统 MegaScale 在 175B 模型上保持全局 batch size 为 6144，把卡数从 3072 增至 12288。原每步耗时约 23.7 s，若卡数增至四倍就能带来四倍加速，每步应缩短至约 5.9 s，实际约 6.3 s。总加速约 3.7 倍，对应约 93% 的扩展效率。卡数增加后每卡的工作减少，跨组同步和负载不均衡造成的等待在每步耗时中所占的比例随之上升；实际每步比理想值多约 0.4 s，这就是扩展后需要进一步分析的额外耗时。按第 1.3.4 节的顺序，先把跨组同步和负载不均补进模型：卡数越多，每步等待最慢一组的时间占整步的比例越大，这是扩展本身带来的工作；补齐之后仍然解释不了的差额，才归于实现开销。差额那 0.4 s 并不是实现太差，它主要来自跨组同步与负载不均，和 10.1.3 里「哪些是必须计入的工作、哪些是可优化开销」的判据是同一条。

数字核验：$23.66/4 = 5.915$ s ≈ 5.9 s；实际 6.34 s ≈ 6.3；加速比 $23.66/6.34 = 3.73$ ≈ 3.7 倍；扩展效率 $3.73/4 = 93.3\%$ ≈ 93%；差额 $6.34 - 5.915 = 0.425$ s ≈ 0.4 s。这里的约 93% 是相对理想强扩展（卡数 ×4、时间 ÷4）而言，不是相对峰值算力的 MFU。

> 补充：a：论文报告的每步耗时为 23.66／6.34 s，扩展效率约 93.3%；对应固定全局 batch 的整套系统扩展实验。MegaScale 正式论文及固定任务、历史配置与计量这里。

关于通信桶的大小，还有一个折中的判断：桶越大越可能被最后生成的梯度拖住，启动就晚；桶越小则启动次数多，启动开销高。这不属于单向最优的问题，只能调。至于先算 $dX$ 还是先算 $dW$，两条路都有人走，先 $dX$ 让上游更早开始（压缩流水线气泡的方向），先 $dW$ 让自己这层的梯度更早进入通信，两者争用同一份算力，本质上是调度问题。

### 10.3.4 MoE 与长上下文的调度变化

稠密模型的每次前向都使用各层全部前馈权重，数据并行时工作划分相当规则。MoE 的路由会让各卡收到数量不同的 token，序列长短不一也会让相同的 token 数对应不同的计算量。分析每步耗时时，要看工作如何分到各张卡上，以及哪张卡最后完成。

先看专家 dispatch 不均如何延长最忙那张卡的计算时间。设两张卡上的专家分别接到 96、32 次 token dispatch，每次 dispatch 把一个 token 的特征向量送给一个专家，在该专家输入矩阵中占一行，假定每次 dispatch 的计算时间近似相同。总计 128 次 dispatch，对应 128 个有效行，平均每卡 64 行，但完成时间由 96 行的那一侧决定。把分配调成 64、64 行，专家计算时间就从处理 96 行所需的时间降到处理 64 行所需的时间，缩短三分之一。这里的缩短三分之一就是 $(96-64)/96 = 33.3\%$ 的含义。这里的 64 行只是平均值的意义，只要一侧是 96 行，整步就要等 96 行那一侧干完，另一半算力白白闲着。训练中的路由均衡机制决定样本如何选择专家，专家副本和拓扑映射则决定这些选择在哪里执行。

上面这个调整假定 token 可以在专家之间随意搬移。实际的 dispatch 由路由器打分决定，均衡机制只能影响 dispatch 的分布，执行时还需要一条处理不均的明确规则。容量因子（capacity factor）$c$ 给出这条规则：每个专家的输入矩阵最多为

$$
\text{每专家容量} = \left\lfloor c \times \frac{\text{token 数} \times k}{E} \right\rfloor
$$

行，也就是平均 dispatch 量的 $c$ 倍，其中 $k$ 为每个 token 选择的专家数，$E$ 为专家数。超出容量的 dispatch 被丢弃，该层不处理这些 token，它们的表示经残差连接直接传给下一层；容量未用满的槽位补零，这些行仍占用计算与通信。

代入前例：128 次 dispatch、$E = 2$、$k = 1$，平均每专家 64 行。$c$ 取 1.0、1.25、1.5、2.0 时，每专家容量为 64、80、96、128 行，收到 96 次 dispatch 的专家分别丢弃 32、16、0、0 个 token，两个专家合计补零 32、48、64、128 行。$c = 1.0$ 时总执行量恰好等于 128 次有效 dispatch，却丢弃了其中四分之一；$c = 1.5$ 起不再丢弃，代价是执行行中有三分之一为补零。

自己核一遍这个前例：容量 $= \lfloor c \times 128 \times 1/2 \rfloor = 64c$，$c = 1.25 \to 80$、$c = 1.5 \to 96$、$c = 2.0 \to 128$。热专家有 96 次，$c = 1.0$ 时丢 $96-64 = 32$，$c = 1.25$ 时丢 $96-80 = 16$，$c \ge 1.5$ 时丢 0。补零来自两头：冷专家 32 次，容量 64／80／96／128，补零 $64-32 = 32$、$80-32 = 48$、$96-32 = 64$、$128-32 = 96$，再加上热专家侧的补零（$c = 2.0$ 时 $128-96 = 32$），两侧合计 32、48、64、128。执行总行数为 128、160、192、256，$c = 1.5$ 时补零占比 $64/192 = 33.3\%$。

再看真实模型的路由规模。Qwen3-235B-A22B 有 $E = 128$ 个专家，每个 token 选择 $k = 8$ 个；8,192 个 token 共 65,536 次 dispatch，平均每专家 512 行。设一半专家收到 1.5 倍于均值的 dispatch，与前例 96/32 同为 3:1 的不均衡，热专家各 768 行、冷专家各 256 行。$c$ 取 1.0、1.25、1.5、2.0 时，每专家容量为 512、640、768、1,024 行，热专家分别丢弃 256、128、0、0 次 dispatch，合计占总 dispatch 的 25%、12.5%、0、0；补零行占全部执行行的 25%、30%、33%、50%。

这一组也能逐步核出来。$8192 \times 8 = 65{,}536$ 次 dispatch，除以 $E = 128$ 得均值 512 行。一半即 64 个专家热，1.5 倍均值是 768 行，另一半 256 行，校验总量 $64\times768 + 64\times256 = 49{,}152 + 16{,}384 = 65{,}536$，正好等于总 dispatch。$c = 1.0$ 时容量 512，热专家丢 $768-512 = 256$，64 个热专家共丢 16,384，即总 dispatch 的 25%；执行 $128\times512 = 65{,}536$ 行，冷专家补零 $512-256 = 256$，共 16,384，占执行行数的 25%。$c = 1.25$ 时容量 640，热专家丢 128，共 8,192，占 12.5%；执行 $128\times640 = 81{,}920$，冷专家补零 384，共 24,576，占 30%。$c = 1.5$ 时容量 768，热专家丢 0；执行 $128\times768 = 98{,}304$，冷专家补零 512，共 32,768，占 33.3%。$c = 2.0$ 时容量 1,024，热专家补零 $1024-768 = 256$，冷专家补零 $1024-256 = 768$，合计 65,536；执行 $128\times1024 = 131{,}072$，占 50%。五项数字与这里完全一致。

> 补充：18：容量因子与丢弃复算。容量规则见 Switch Transformer 式(3)（每专家容量 = 每批 token 数／专家数 × 容量因子）与 GShard（容量取 $O(N/E)$，溢出 token 的表示经残差连接传给下一层）；无辅助损失的偏置均衡见 DeepSeek-V3 技术报告。一半专家 1.5 倍热的分布为本例取值，与正文的 96/32 例子同为 3:1。

容量因子为什么算调度问题而不是纯算法问题，看它管住了什么就清楚了。$c$ 是一个静态上界，要对所有专家、所有 batch 都成立，所以只能按「平均 dispatch 量 × $c$」来定。$c$ 太小（比如 1.0），容量刚好等于平均值，任何高于平均的专家都会丢 token，丢掉的 token 不走这一层，靠残差直通，但执行的行数最少，没有补零；$c$ 太大（比如 2.0），几乎不丢 token，代价是大量行在补零，补零的行照样进矩阵乘、照样占带宽，等于花钱算零。容量决定了每个专家矩阵的形状，形状又决定每张卡的算力负载与通信量。给得太小，丢弃的 token 让模型质量下降，这些 token 在这一层等于没被处理；给得太大，整步时间被补零拉长。$c$ 因此成了训练质量与系统效率之间的旋钮，它既能影响收敛，也能影响每步耗时，这里把它放在「调度变化」一节里讲，正是这个意思。

专家副本与拓扑映射决定不均匀最终落在谁头上。即使 dispatch 分布不变，把哪些专家放在同一张卡上、是否为热专家准备副本，会直接改变最忙那张卡的工作量。这里那句「训练中的路由均衡机制决定样本如何选择专家；专家副本和拓扑映射则决定这些选择在哪里执行」，区分的是影响分布（均衡／偏置）与影响落点（副本／拓扑）两类手段。负载均衡机制试图让 dispatch 分布更均匀，有的实现用辅助损失，有的用偏置项；容量因子只是在分布已经确定之后，给出每个专家最多接多少行的执行规则，两者互补，不能互相替代。

顺带把几个量纲理一下。丢弃与补零是两件事：丢弃是 token 不走这一层、表示经残差连接直通下一层，省了计算但损失了这一层的建模能力；补零是槽位空着也要算，行照占计算与通信。容量公式里的 $k$ 容易漏，总 dispatch 数是「token 数 × $k$」，不是 token 数；$c$ 是相对平均 dispatch 量的倍数，$E$ 决定平均量本身。一次 dispatch 在专家输入矩阵里占一行，所以 128 次 dispatch 与 128 个有效行是同一个量纲，但执行时因为补零，执行行数往往大于有效行数。

MoE 与本章其他部分的接口也值得点一句。路由不均衡会同时改变两件事：每步耗时（最忙卡决定完成时间，属于 10.3 的时间轴）与每卡状态容量（10.1.2 已指出各专家同样拥有待更新参数和优化器历史，所以状态容量由全部可训练参数决定，属于 10.2 的容量轴）。MoE 因此成了本章两条主线交汇的一个例子。

这张表讲的其实是一次两害相权。$c$ 太小，超容量的 dispatch 被直接丢弃，这些 token 在这一层等于没被处理，丢的是真实工作；$c$ 太大，每张卡上的专家都按容量补零凑满，补出来的行是白算的，丢的是算力。读的时候要留意两个百分比的口径并不一样：25% 是丢掉的 dispatch 占总 dispatch 的比例，另一个 25% 是补零行占本层执行量的比例，$c=1.0$ 时两者数值相同，含义却不同，当成同一件事就会读错。

把数字自己算一遍更踏实。8192 个 token 乘 $k=8$，共 65,536 次 dispatch；分给 128 个专家，平均每专家 $65536/128 = 512$ 行，正是表中 $c=1.0$ 的容量。$c=1.5$ 对应 $512\times1.5 = 768$ 行，$c=2.0$ 对应 1,024 行，与表一致。容量因子的实质就是「专家容量取平均负载的多少倍」。

翻转条件为什么落在 1.5？因为例子里的路由是一半专家 1.5 倍热，最热的那个专家正好接到平均负载的 1.5 倍，容量开到同一倍数就不再溢出。这里那句「翻转条件由路由分布决定」说的正是这件事：需要的 $c$ 不是一个常数，而等于最热专家的负载倍数。路由越均衡，所需 $c$ 越接近 1，补零浪费越少。辅助损失（在训练目标里额外加进去的负载均衡项）直接惩罚 dispatch 不均；DeepSeek-V3 的无辅助损失方案按专家负载动态调整路由偏置。两条路都把分布推向均衡，让容量因子可以取更小的值。第 2.4 节的专家容量公式假设路由过程中不丢弃任何 token dispatch（$\sum_e t_e = m k_{\text{top}}$），对应的就是容量因子足够大、丢弃率为零的情形。

均衡了专家的计算量，数据传输仍可能让卡等着。MoE 的前向 token 交换、反向输入梯度传输和参数梯度归约会争用同一条链路，所以还要用上一节的通信时间轴来分析。给出的算例是这样：取 72 MiB 的 FP32 专家梯度，由持有该专家的四个数据并行成员做环形 AllReduce，每张卡发送 $2\times\frac{3}{4}\times 72 = 108$ MiB。每卡配一张 200 Gbit/s 网卡，每方向 25 GB/s，每次集合调用启动约 0.02 ms。整桶耗时约 4.55 ms，塞不进一个 2 ms 的空闲时段。把梯度切成三个 24 MiB 子桶，每桶发送 36 MiB，约 1.53 ms，就可以分别落在三个这样的空闲时段里；总通信处理时间却涨到约 4.59 ms。

这里的方法论比数字本身重要。整桶 4.55 ms 是把 108 MiB 一次发完的时间；切桶后总时间 4.59 ms，多出来的是两次 0.02 ms 启动开销，单看总量反而变差。但每一桶都能塞进 2 ms 的空隙，于是不落在关键路径上。真正决定训练步耗时的是**通信结束时刻相对于计算结束时刻的位置**，通信处理时间本身说明不了什么。这条判断在后面的常见误区里还会再出现一次。复算过程：108 MiB = 113.25 MB，除以 25 GB/s 得 4.53 ms，加 0.02 ms 启动即 4.55 ms；切成三桶后每桶 36 MiB = 37.75 MB，除以 25 GB/s 得 1.51 ms，加启动 1.53 ms，三桶合计 4.59 ms。换成 400 Gbit/s 网卡，每方向 50 GB/s，113.25/50 = 2.27 ms，加启动为 2.28 ms，仍然大于 2 ms，切桶依然必要。

专家负载取决于每张卡上的专家接到了多少次 token dispatch。长上下文还多一层差别：即使 token 总数相同，需要计算的注意力配对数也可能不同。对长度 $s$ 的因果序列，第一个 token 查看一个 token，第二个查看两个，依次相加得到 $s(s+1)/2$ 个有效注意力配对。两条长度 4096、4096 的序列合计约 1680 万对；改成 7168、1024，总 token 数仍是 8192，配对数却增至约 2620 万，增加约 56%。注意力配对数随序列长度近似按平方增长，所以较长的序列抬高了总计算量。

这里的配对数复算：$4096\times4097 = 16,781,312$，两段合计乘以 2 再除以 2 仍是这个数；$7168\times7169/2 = 25,693,696$，$1024\times1025/2 = 524,800$，相加得 26,218,496，相对 16,781,312 增加 56.2%。有两点结论要分开：$s(s+1)/2$ 是因果注意力必须算的 query-key 对数量，它是计算量的下界，不能靠删 padding 省掉；而在总 token 数固定时，长度越不均衡，总配对数越大，这是凸性使然。图 10-29 里长三角形多出来的那部分面积来自真实的注意力关系，靠删除填充 token 是消不掉的。

对策有三条，各自作用在不同环节。打包把多条较短的序列首尾拼接成一条目标长度的序列，减少填充 token，改的是无效工作量；按长度分组让各卡承担的三角形面积更接近，改的是工作分配，也就是谁是掉队者；上下文并行进一步把长序列的计算分到多张卡，并通过交换 K、V 取得其他卡保存的数据，改的是数据到达路径。用相同总 token 数比较方案时，保持长度分布、可见性掩码（mask，规定各 token 位置能读取哪些上下文 token）和损失权重不变，才能把调度收益与任务本身的变化分开。

## 10.4 数据输入、checkpoint 与故障恢复

第 10.3 节的每步耗时分析假定输入数据已经准备好，训练也没有因故障中断。持续跑起来以后，数据读取和预处理要跟得上计算速度，还要有 checkpoint 保存可恢复的训练状态。本节把这两件事加进章首的完成时间：输入决定卡能不能持续工作，恢复决定已经做过的工作有多少需要重做。

这一节的性质和前几节不同。前面算的是「一步要多久」，这里算的是「长期跑下去，有多少时间没花在有用的训练上」。这里用两个词概括：输入（input）决定 GPU 会不会饿着，恢复（recovery）决定白干多少。两项都不改变单步的算法，却直接决定总完成时间。读的时候建议把两个问题挂在心里：这件事有没有出现在每步的关键路径上；它是一次性的还是随时间累积的。10.4.1 属于速率匹配问题，10.4.2 到 10.4.4 属于周期性成本问题，10.4.5 则是每步都被拉长几个百分点的问题。

### 10.4.1 数据读取、打包与预取

数据通路是这样的：原始数据经过读取、解码或分词、筛选，再按目标长度拼接成训练序列，放入主机内存缓冲区，最后传到 GPU。主机缓冲区通常用**锁页内存**（pinned memory），使数据在异步传输期间保持在物理内存中。各环节的持续处理速度决定输入速度，队列用来缓冲短时间内的速度波动。

GPU 最终收到的数据量小，不意味着此前的准备过程同样快。25 天预算要求约 46,300 token/s，即每秒约 5.7 条 8,192 个 token 的序列。若以每个编号占 8 字节的 int64 格式传输 token ID，数据率只有约 0.37 MB/s。设每个 CPU 数据准备进程每秒准备两条序列，两个进程只有四条/s，低于需求；三个进程达到六条/s。传输的数据量虽少，CPU 上的准备过程仍可能拖慢整个集群。

复算一下这几个数：25 天 = $25\times86400 = 2{,}160{,}000$ s；$100\times10^9 / 2{,}160{,}000 \approx 46{,}296$ token/s，约 46,300；除以 8,192 得 5.65 条/s，约 5.7 条/s。数据率 $46{,}300\times8 = 370{,}400$ B/s $\approx 0.37$ MB/s。

本章的设计案例为输入安排四个这样的数据准备进程，合计八条/s。48 卡输入就绪时每步约 52.3 s，每步处理 384 条，需求约为 7.3 条/s，低于八条/s；也就是 $384/52.3 \approx 7.34$ 条/s，数据准备略有富余，短暂变慢之后可以重新补满预取队列。设计案例再给每步 0.5 s 的平均输入等待时间，表示预取没能消除的等待，32 卡和 48 卡的每步训练时间由此变为约 78.9 s 和 52.8 s。

数据量小为什么不等价于准备快？因为 GPU 收到的只是 token ID 这种极小的整数流，0.37 MB/s 比一张图片还小，而 CPU 侧要做的是解码、分词、筛选、拼接到目标长度，属于字符串与规则处理，代价与字节数不成比例。网络和 PCIe 带宽一点都不紧张，紧张的是 CPU 的算力。所以文本任务上加带宽没用，该加的是数据准备进程或更快的分词实现。

预取队列让数据准备与 GPU 计算以不同进度运行。正常训练时，提前准备的数据可以缓解输入速度波动造成的等待；保存 checkpoint 时，则必须分清哪些数据已经用于训练。这里举的错位例子是：数据加载器已经为前 108 个 batch 分配了准备任务，而训练只完成第 100 个，第 101—108 个仍在处理或排队。恢复时若直接从第 109 个 batch 开始，就会跳过八个 batch。已分配给数据准备进程的位置反映预取进度，已用于训练的位置反映训练进度，两者之间的缓冲保存了尚未训练的数据。

预取队列本质是一个生产者–消费者缓冲，生产者是 CPU 数据进程，消费者是 GPU 训练步。只要消费速率超过生产速率，本例是 7.3 对 8，队列就能在波动后补满；一旦反过来，队列单调下降，终会取空，GPU 开始等数据。它是用内存换时间的缓冲，不是产能。那个 100 与 108 的例子说明 checkpoint 要记两个位置：训练进度和预取进度，只记一个不够。恢复时只用前者，101–108 这八个 batch 就白扔了；粗暴地用后者，又会漏掉这八个里没练过的部分。正确做法是记住已训练到的位置，并保留或重新准备中间那段数据。第 10.4.2 节会接着说，连打包器手里剩下的半个序列也要一起存。

图 10-30 的队列只能暂时填补准备速度的下降。数据长期准备得更慢，队列终将取空。checkpoint 写入受同样的约束：保存产生数据的平均速率一旦超过存储能持续接收的速率，待写的快照就会越积越多，有限的暂存缓冲终将被占满，第 10.4.3 节按具体写入速率计算这种积压。对本章的文本任务，输入端字节量很小，瓶颈在 CPU 上的数据准备；checkpoint 的平均写流量也不大，设计案例采用 1800 s 保存间隔，约 115 GB 的 checkpoint 平均只有约 64 MB/s。保存时的停顿在第 10.4.4 节单独计入。

工程上有几个容易踩的坑。预取队列太浅，抖一下就饿；太深，故障恢复时要保留或重做的数据变多，而且数据在内存里会过期，它与当前采样进度、随机状态相关。锁页内存能加速 H2D 拷贝，但它不可换出，过度使用会挤占主机内存，而打包和 checkpoint 缓冲都要吃主机内存。数据准备进程数与训练卡数的比例要按「每步消耗条数／每步耗时」算，别凭感觉配。

### 10.4.2 可恢复状态与布局变换

设训练刚完成一次参数更新，此时停机。恢复后要接着训练，需要知道当时的权重、下一批该读哪些数据，以及优化器已经累积了哪些历史。仅有权重，可以执行前向推理，却不足以确定训练的下一次更新。所以训练 checkpoint 要保存与同一训练进度对应的全部必要状态，恢复后才能接着训练。

本章采用 Adam 的训练需要保存：权重、一阶矩与二阶矩、步数、学习率状态、随机状态和下一批数据的组成。学习率控制更新步长，随机状态决定后续随机采样的序列。权重相同而优化器的矩状态不同，下一次参数更新便可能不同；数据读取位置相同而打包时剩余的 token 不同，下一条训练序列也会变。第 10.2.2 节的激活重计算解决的是一次前向、反向之内哪些中间值可以重建；checkpoint 要解决的是中断之后整个训练过程如何继续。

训练在这里是一台带内部状态的状态机，光看 $W \to W'$ 这个函数不足以描述它。Adam 的一阶/二阶矩是梯度历史的指数滑动平均，它决定同一个梯度下一步会把权重推多远；学习率调度器决定当前步长；随机状态决定下一个 batch 怎么采样、数据怎么 shuffle、dropout 或数据增强怎么做；数据加载位置决定下一条序列由哪些 token 组成。少任何一项，恢复后的轨迹都会偏离原来的轨迹。后果是这次训练变成了另一个实验，此前的训练进度不能算数。

一次训练迭代结束后，下一批梯度由反向重新产生。此时保存权重 2 bytes、主权重 4 bytes 和两份 Adam 状态 8 bytes，每参数合计 14 bytes。Qwen3-8B 的这部分 checkpoint 约为 115 GB（补充：给出精确值 114,670,295,040 bytes）。这里的口径是「参数 × 每参数字节数」，不含激活，也不含 KV。复算：14 = 2（BF16 权重）+ 4（FP32 主权重）+ 8（两份 Adam 状态，各 4 bytes）；$8\times10^9\times14 = 112$ GB，与这里的约 115 GB 同量级；补充：的精确值对应约 8.19e9 个参数，说明 Qwen3-8B 的实际参数量略大于 8e9。

恢复时还可能需要改变并行布局，同一份状态要重新分片。这里的例子是 checkpoint 如何从四路张量并行重分片为八路。门控投影的权重形状为 $[12288, 4096]$，BF16 大小 96 MiB。沿输出维四分，每片 3072 行、24 MiB；八分后，每片 1536 行、12 MiB。rank 为 $r$ 的目标卡读取旧分片 $\lfloor r/2 \rfloor$，偶数 rank 取前半，奇数 rank 取后半。全局行坐标把旧布局和新布局联系起来。

这段算术值得自己走一遍：$12288\times4096\times2$ bytes $= 100{,}663{,}296$ bytes $= 96$ MiB；四分后 $12288/4 = 3072$ 行、24 MiB；八分后 1536 行、12 MiB。$\lfloor r/2 \rfloor$ 这个映射说明两个新分片拼回一个旧分片：$r=0,1$ 都读旧分片 0，$r$ 为偶数取前半（行 0–1535），奇数取后半（行 1536–3071），这就是图 10-31 里「旧 0 一分为二」的含义。

沿图 10-31 的箭头，恢复程序可以找到每个新分片对应的原始行范围。FP32 主权重与 Adam 两项状态也按相同的行范围拆分，每项为 BF16 权重的两倍。该矩阵在 checkpoint 中的全部状态因此为 $96\times(1+2+2+2) = 672$ MiB。这个乘法的意思是：BF16 权重 1 份、FP32 主权重是 BF16 的 2 倍字节、两份 Adam 状态各 2 倍字节，共 7 份 96 MiB。只要状态都落在同一矩阵的行范围内，布局变换就只是按行号重新切，不需要理解每个张量的语义。ByteCheckpoint 一类系统用全局形状、偏移和片段长度描述这些张量，使恢复程序按目标布局读取需要的范围，原因就在这里：恢复程序只处理坐标，不处理语义。

文件分片是存储安排，全局坐标标明每个分片属于哪个张量、位于哪些行列。存储上想怎么切都行，按卡、按层、按张量都可以，但每个片段必须能回答「我是哪个张量的哪几行」，否则换并行度时无法重新组合。工程上这对应 checkpoint 元数据（metadata）的设计：数据文件之外必须有描述完整快照的元数据，第 10.4.3 节还会从「提交」的角度再讲一次。

权重可以凭原矩阵的行号重新拼接，训练序列也需要保留足够的信息，才能重新组成同样的输入。图 10-30 中已经准备好但尚未用于训练的数据，同样需要在恢复时重新定位。除了 batch 位置，还要保留数据预处理的中间结果。

打包器若保留 2,000 个 token，下一份数据提供 6,192 个，两者组成下一条 8,192 个 token 的序列。丢失这 2,000 个 token，就只能从后续数据中取出额外的 token 来补齐下一条序列，从而改变它的前缀、注意力关系和标签。$2000 + 6192 = 8192$，前缀一变，同样的标签对应的注意力关系也变了，这条样本就不是原来那条样本了。所以要把已用于训练的数据位置、尚未组成完整序列的 token 与参数更新结果一起保存，恢复后才能继续构造同一批数据。第 10.4.1 节里「预取进度 vs 训练进度」的区分，到这里升级成「把半个序列也存下来」。

> 补充：checkpoint 布局、ByteCheckpoint 与后台保存阅读、逻辑重分片计算、112 GB 时间线；DCP 恢复记录、真实文本管线恢复；2,000＋6,192 是说明打包时剩余 token 的教学例；DCP 小模型将两份行分片恢复为三份列分片，且参数、Adam、随机状态和下一次参数更新结果与不中断训练一致。

### 10.4.3 同步、异步保存与带宽竞争

这一节讨论保存过程如何与训练同时进行，以及一份快照何时才真正可用。

同步保存先生成内容固定的快照，写入完成后继续训练。异步保存把快照复制到独立的内存缓冲区，再由后台写入，让训练较早恢复执行。训练恢复执行时，快照可能还没写完；只有写入并提交完成后，这份快照才能用于故障恢复。

  <figcaption><strong>保存与训练解耦。</strong> 捕获和复制是前台停顿，写入在后台进行；提交是快照可用的最后一步。</figcaption>

同步与异步的差别不在快慢，而在谁在等。同步保存时训练等 I/O，前台停顿等于整个写入时间，本例是 16 s 或 5.6 s；异步保存把「复制到独立缓冲」做成瞬间的一致快照，训练立刻回来，漫长的那段写入挪到后台。代价是内存里多一份快照（补充：提到共享存储与缓冲的竞争），以及「快照已生成但未提交」这个中间状态必须被故障恢复逻辑正确理解。

「提交（commit）」是这一节的核心概念，可以类比数据库事务。数据文件全写完了并不算数，只有元数据提交成功，恢复程序才会认为这份 checkpoint 有效。这里的 CPU 实验是 API 调用约 7 ms 返回、恢复元数据约 48 ms 才提交，说明调用返回得太早是危险的：如果此时进程被杀，恢复程序只能退回上一份完整快照。

例：checkpoint 上传速度如何决定故障后的重做量？取每份 112 GB 的快照。DGX SuperPOD 参考架构按工作负载给出存储性能档次，NLP 训练对应 Good 档，一个 SU（32 台 DGX 组成的扩展单元）的存储合计写入为 7 GB/s；按此速率，一份快照要写 16 s。每 10 s 产生一份时，待写入数据的产生速率为 11.2 GB/s，队列持续增长。改为每 20 s 一份，平均需求降到 5.6 GB/s，存储能在下一份到达前写完上一份。

在第 20、40 s 捕获两份快照，各花 0.5 s 复制到缓冲区后上传，完成时刻为 36.5、56.5 s。若第 50 s 故障，第二份仍在上传，只能恢复到第 20 s，重做 30 s。换用 Better 档的 20 GB/s 合计写入，每份只需 5.6 s，两份分别在 26.1、46.1 s 完成；同一故障可恢复到第 40 s，只重做 10 s。

这一段的复算：$112/7 = 16$ s；$112/10 = 11.2$ GB/s，超过 7 GB/s，队列必然增长；$112/20 = 5.6$ GB/s，低于 7 GB/s，能写完。7 GB/s 档：$20+0.5+16 = 36.5$ s，$40+0.5+16 = 56.5$ s；50 s 故障时第二份尚未提交，最后可用提交点是 36.5 s 那份，对应 20 s 时刻的训练状态，重做 $50-20 = 30$ s。20 GB/s 档：$112/20 = 5.6$ s，$20+0.5+5.6 = 26.1$ s，$40+0.5+5.6 = 46.1$ s；50 s 故障时第二份已提交，重做 $50-40 = 10$ s。两档差 20 s 重做。

「重做 30 s」的口径要注意：它是从上次可用快照对应的训练状态到故障时刻的时间，而不是从快照捕获时刻算起，虽然两者在这里都是 20 s。这一点在 10.4.4 节的一阶模型里被抽象成「故障落在两次保存之间平均丢半个间隔」。

两种方案的前台暂停都是两次 0.5 s，合计 1 s，差别全在后台完成时刻。写入更快，故障后就能恢复到更近的训练进度，少重做 20 s。异步保存的完成点因而直接影响长期进展。这里有两个结论要记住：存储持续写带宽与快照产生速率必须匹配，产生 11.2 GB/s 而接收只有 7 GB/s 就是积压，待写数据会像 10.4.1 节的预取队列一样越积越多；前台停顿来自捕获与复制，后台时间来自写入与提交，优化这两段的手段不同，前者要缩短一致状态的抓取（如增量或写时复制），后者要提带宽或用更近的提交粒度。

写入数据文件之外，实际系统还要提交描述完整快照的元数据。一组 CPU 实验中，保存接口（API）的调用约 7 ms 就返回，恢复元数据约 48 ms 才提交；提交前终止进程，恢复程序选择上一份完整的 checkpoint。数据文件与提交记录共同构成可用快照，恢复程序据此判断哪一份 checkpoint 已经完整保存。

工程上还有一点：后台写入会与训练本身争夺同一套存储和网络（要求「独立的内存缓冲区」和足够带宽）。如果训练的数据读取与 checkpoint 写入来自同一存储，10.4.1 节说的「输入队列被取空」就会真的发生。

> 补充：异步保存与提交前故障实验及无保存／同步／异步对照；原正常路径 API 为约 7.25 ms、元数据提交约 48.30 ms；故障实验在提交前设置屏障并终止进程。

### 10.4.4 故障规模、保存周期与有效训练进度

图 10-33 固定了两次保存的时刻，比较的是写入速度的影响。还可以改变保存间隔：间隔短，故障时离上一份快照更近；间隔长，正常训练时需要暂停保存的次数更少。这两项代价方向相反，因此存在一个折中点。

设每次同步保存耗时 $c$，保存之间完成 $\tau$ 秒有用训练，作业故障率为 $\lambda$，恢复耗时为 $r$。假设故障发生频率较低且彼此独立，在一阶模型下，单位有用训练时间的附加成本为

$$
L(\tau) = \frac{c}{\tau} + \frac{\lambda\tau}{2} + \lambda r
$$

三项各有来历。第一项来自每隔 $\tau$ 保存一次：每 $\tau$ 秒有用训练就要停 $c$ 秒去保存，开销按 $1/\tau$ 摊，间隔越长越省。故障落在两次保存之间的任意位置，平均丢失半个间隔，得到第二项 $\lambda\tau/2$，间隔越长越亏。第三项是单位有用训练时间内的预期恢复次数乘以每次恢复时间；在故障彼此独立、频率低的假设下，恢复时间与 $\tau$ 无关，所以它只抬高基线，不改变最优点的位置。前两项一减一增，最优点满足

$$
-\frac{c}{\tau^2} + \frac{\lambda}{2} = 0,\qquad \tau^{*} = \sqrt{\frac{2c}{\lambda}}
$$

对 $\tau$ 求导令零就得到这个式子，它衡量的是每单位有用训练时间要多付多少，跟绝对总时间无关。有个挺好用的直觉：最优间隔是「保存成本」与「故障频率」的几何平均量。$c$ 越大（checkpoint 越大、写得越慢）就该少存；$\lambda$ 越大（卡越多、故障越频繁）就该多存。

例：卡数与故障率如何决定 checkpoint 保存间隔？Meta 统计了研究集群上的训练作业：1024 卡作业平均 7.9 小时中断一次，而且中断率与卡数成正比，相当于每卡平均约 337 天出一次故障。任一卡故障均中断作业。约 115 GB 的 checkpoint 以 7 GB/s 保存，$c\approx16.4$ s。设恢复需 120 s，代入得到最优间隔约 965 s，即约 16 分钟。

复算这几个数：1024 卡平均 7.9 h 中断一次，$\lambda = 1/(7.9\times3600) = 3.52\times10^{-5}\ \text{s}^{-1}$；$c = 16.381$ s；$\tau^{*} = \sqrt{2\times16.381/(3.52\times10^{-5})} = \sqrt{9.31\times10^{5}} \approx 965$ s $\approx$ 16.1 分钟，与这里一致。每卡 MTBF：$1024\times7.9\ \text{h} = 8089.6\ \text{h} \approx 337$ 天，也与这里一致。

| 有用训练间隔 | 保存成本 | 重做成本 | 恢复成本 | 合计 |
| --- | --- | --- | --- | --- |
| 300 s | 5.5% | 0.5% | 0.4% | 6.4% |
| 900 s | 1.8% | 1.6% | 0.4% | 3.8% |

表里三行自己算一遍：$\tau=300$ s 时保存项 $16.381/300 = 5.46\%$、重做项 $3.52\times10^{-5}\times150 = 0.53\%$、恢复项 $3.52\times10^{-5}\times120 = 0.42\%$，合计 6.41%，与表中 6.4% 相符；$\tau=900$ s 得 1.82% + 1.58% + 0.42% = 3.82%（表中 3.8%）；$\tau=1800$ s 得 0.91% + 3.16% + 0.42% = 4.49%（表中 4.5%）。表中合计由未经四舍五入的数值计算，所以三项相加可能与合计有小差，这是这里说明过的。

将保存间隔从五分钟延长到十五分钟，节省的保存时间多于新增的重做时间；继续延长到三十分钟，新增的重做时间就超过了节省的保存时间。卡数翻倍会使故障率翻倍，最优间隔缩短为原来的 $1/\sqrt{2}$；保存速度翻倍也使最优间隔按同样比例缩短，因为每次保存耗时更短。$\tau^{*}\propto 1/\sqrt{\lambda}$，卡数翻倍则 $\lambda$ 翻倍，最优间隔变成 $1/\sqrt{2}\approx0.707$ 倍；$\tau^{*}\propto\sqrt{c}$，而 $c$ 与 checkpoint 大小成正比、与保存带宽成反比，保存速度快一倍则 $c$ 减半，最优间隔同样缩到 $1/\sqrt2$。这里把这两条并列，是因为它们对公式的作用方式相同，工程含义却不同：前者是卡多了就存勤点，后者是存得快了也可以存勤点。

本章设计案例使用的卡数较少，沿用每卡平均约 337 天故障一次（单卡平均故障间隔，MTBF）、恢复耗时 120 s 和保存耗时约 16.4 s 的条件，取有用训练间隔 1800 s。32 卡的保存、重做与恢复合计约增加 1.02% 时间，48 卡约增加 1.08%。这两个数是这样算出来的：32 卡时 $\lambda = 32/(337\times86400) = 1.10\times10^{-6}$，$0.91\% + 1.10\times10^{-6}\times900 + 1.10\times10^{-6}\times120 = 0.91\% + 0.099\% + 0.013\% \approx 1.02\%$；48 卡时 $\lambda = 48/(337\times86400) = 1.65\times10^{-6}$，$0.91\% + 0.148\% + 0.020\% \approx 1.08\%$。48 卡方案被卡故障中断的概率更高，但附加比例只多约 0.06 个百分点，远小于缩短单卡计算时间带来的收益。

大规模训练中，即使一次中断只耽误两三个小时，整组资源的费用也可能达到数万美元。保存周期决定一次故障需要重做多少工作，系统的可靠性则决定这样的损失会发生多少次。

例：一次训练中断会浪费多少钱？小米的 MiMo-V2.6 是前沿实验室中首次直播 RL 过程的。公开运行看板显示，Pro 与 Flash 两种尺寸的模型 RL 后训练分别花费约 260 万和 90 万美元，即每小时约 2.06 万和 1.03 万美元。

MiMo 这个例子把重做时间换算成了钱。这里的口径要看清楚：金额是「日志事件区间 × 看板固定费率」的估算，不是报告里单列的故障账单。区间内的重做、检测和等待没有单独拆分，也没有扣除可能复用的采样结果。所以这些数字适合看量级和比例（23.6%、16.5%），不宜当成精确的会计数据。

若能将 Pro 的中断总耗时减少一半，同样的训练工作就能少用约 15 h，按上述费率节省约 31 万美元。这可以来自两方面：排除反复触发的故障，例如 MiMo 团队曾调整训练并行方式、降低激活显存，以容纳专家负载峰值；以及更早发现故障、更快恢复，用较近的 checkpoint 减少重做，缩短恢复时间 $r$ 或丢失的训练间隔。

三类故障来源对系统设计有不同含义。硬件故障（显存双比特错误）要靠 ECC、巡检和换卡；服务故障（容器崩溃、评分服务网络不通）要靠编排、重试和健康检查；内存不足（KV 缓存耗尽、专家负载不均导致显存溢出、打包时主机内存不足）要靠容量预留与负载均衡。最后一类其实可以靠设计避免，MiMo 团队调整训练并行方式、降低激活显存以容纳专家负载峰值就属于这一类。

「一次 infra 错误没有及时被检出，直到完成第 17 步后才从第 15 步重新训练」这个细节很值钱：故障检测延迟本身会放大重做量。系统若能在第 15 步就发现异常，只需要回滚到第 15 步；晚了以后，第 16、17 步的 4 小时全部作废。

### 10.4.5 掉队者与慢节点

上一节的模型把故障当作中断作业的事件。还有一类更频繁的退化不会中断作业：某张卡在某一步算得慢。同步数据并行的每一步要等最慢的那张卡算完，这张拖慢整步的卡称为**掉队者（straggler）**，步时间因此由各卡的最大值而不是均值决定。

设各卡计算时间独立同分布，均值为 $\mu$、标准差为 $\sigma$，$N$ 张卡时步时间的计算部分是 $N$ 个样本的最大值。取 $\mu = 52.2$ s（48 卡方案的单卡计算时间）与每步 0.58 s 的通信与输入等待，$\sigma$ 分别取均值的 2%（1.04 s）与 5%（2.61 s）。

$N$ 个独立正态样本最大值的期望为 $\mu$ 加上若干倍 $\sigma$：$N=8,48,1024$ 时分别约为 1.42、2.23、3.25 倍。代入即得每步的期望耗时：

| 卡数 | $E[\max]-\mu$（倍 $\sigma$） | 每步，$\sigma=2\%$ / s | 每步，$\sigma=5\%$ / s |
| --- | --- | --- | --- |
| 8 | 1.42 | 54.3 | 56.5 |
| 48 | 2.23 | 55.1 | 58.6 |
| 1024 | 3.25 | 56.2 | 61.3 |

表里的数可以验算：$\sigma = 2\%$ 时 $\sigma = 0.02\times52.2 = 1.044$ s，$\sigma = 5\%$ 时为 2.61 s。8 卡、$\sigma=2\%$：$52.2 + 1.42\times1.044 + 0.58 = 54.26 \approx 54.3$ s；48 卡：$52.2 + 2.23\times1.044 + 0.58 = 55.11 \approx 55.1$ s；1024 卡：$52.2 + 3.25\times1.044 + 0.58 = 56.17 \approx 56.2$ s。$\sigma=5\%$ 时同理得 56.49、58.60、61.26，与表中 56.5、58.6、61.3 一致。这也印证了那张表的读法：「每步」列已经把 0.58 s 的通信与输入等待算进去了。

无波动时每步约为 $52.2 + 0.58 \approx 52.8$ s。卡数越多，最大值的期望越大：48 卡、$\sigma=5\%$ 时每步多约 5.8 s，占去第 10.6 节约 14.4 s 余量的四成；1024 卡时多约 8.5 s。

为什么「由最大值决定」这件事在分布式训练里这么要命？因为同步数据并行有全局屏障，梯度 AllReduce 就是一次全组等待，一步的耗时是 $\max_i t_i$。极值统计的规律是样本越多、最大值离均值越远，而且这个偏离按 $\sqrt{2\ln N}$ 量级缓慢增长。卡数从 8 涨到 1024，差 128 倍，$E[\max]-\mu$ 从 $1.42\sigma$ 涨到 $3.25\sigma$，本质是同一份随机波动被抽到极端的机会变多了，而不是机器变坏了。

慢卡可以从通信等待中检测出来：每张卡在梯度桶 AllReduce 上的等待，等于步结束时刻减去自己的计算结束时刻；对计算耗时恰为均值的卡，这段等待的期望正是 $E[\max]-\mu$。这个原理挺漂亮：如果所有卡同时结束计算，AllReduce 的等待对谁都一样；实际上早算完的卡会一直等在集合通信里。所以不需要额外的监控探针，梯度同步本身就是一个天然的测量工具，只要统计每张卡在桶 AllReduce 上的停留时间。

发现慢卡以后有三种响应：等待、重分配和驱逐。

等待是本步按慢卡时间结束。一张慢到 $\mu+3\sigma$ 的卡让其余各卡多等的时间，取决于其余 $N-1$ 张卡的最大值本来有多大：$\sigma=2\%$ 时，8 卡多等约 $1.65\sigma$（1.72 s），48 卡多等约 $0.78\sigma$（0.81 s），1024 卡时其余卡的最大值本身已超过 $\mu+3\sigma$，多等的时间为零。重分配把慢卡的工作均匀摊给其余 $N-1$ 张卡，均值变为 $\mu N/(N-1)$。仍取 $\sigma=2\%$、不计迁移成本，48 卡每步约 56.2 s，8 卡升到约 61.6 s，都高于同一 $\sigma$ 下等待的期望步时间 55.1 s 与 54.3 s。摊派让每张卡多做 $1/(N-1)$ 的工作，这份增量超过了一张慢卡带来的等待，卡越少差距越大；48 卡时 $\mu N/(N-1)$ 是 53.31 s，比 52.2 s 多 1.11 s，而等待一张慢卡的平均代价比这更小。驱逐是把慢卡移出作业，从上一个 checkpoint 重启，代价为期望丢失工作 $\tau/2$ 加恢复时间 $r$。这里取比设计案例的 1800 s 更短的保存间隔 $\tau=600$ s，$r=120$ s，代价为 420 s，按 48 卡方案每步 52.8 s 计约为八步。一次 $\mu+3\sigma$ 的抖动只损失几秒，只有慢卡持续多步时驱逐才值得。

三种响应其实对应三种判断：抖动是偶发还是持续；迁移成本是否小于收益；回滚成本是否小于继续忍。等待的成本是 $(E[\max_{N-1}] - 3\sigma)^{+}$ 这种量级，卡多时其余卡的最大值本来就大，多等一张 $\mu+3\sigma$ 的卡几乎不额外增加等待。

实际集群中确实存在慢卡：MegaScale 报告约 0.5% 的机器明显变慢；第 10.4.4 节的 Meta 集群统计则给出作业规模与中断的关系，1024 卡作业的平均无故障时间为 7.9 小时；按每卡约 337 天、故障率与卡数成正比折算，8 卡作业约为 42.1 天。

除硬件故障外，还有一种事件需要回滚 checkpoint：第 10.1.2 节的损失尖峰。损失尖峰不损坏硬件，处理方式却相同，都是丢弃当前参数、回到上一份快照，对保存周期的影响也与硬件故障相同。把损失尖峰导致的回滚看作整个作业同时受到的冲击，平均每隔 $1/\lambda_{\text{spike}}$ 发生一次，上一节的一阶模型修正为

$$
L(\tau) = \frac{c}{\tau} + (\lambda_{\text{hw}} + \lambda_{\text{spike}})\left(\frac{\tau}{2} + r\right),\qquad \tau^{*} = \sqrt{\frac{2c}{\lambda_{\text{hw}} + \lambda_{\text{spike}}}}
$$

把两个发生率直接相加，理由很直白：两者对保存周期的影响方式相同，都是回到上一份快照、白干一段，所以在同一阶模型里可以合并成同一个 $\lambda$。但它们的物理来源完全不同：$\lambda_{\text{hw}}$ 与卡数成正比，卡越多越容易坏；$\lambda_{\text{spike}}$ 是整个作业同时受到的冲击，不是某张卡的问题，所以不能按卡数缩放。

沿用 48 卡的硬件故障率（每卡 MTBF 约 337 天），设损失尖峰平均七天导致一次回滚：同样取 $\tau=600$ s 时，附加比例从 2.80% 升到 2.87%，最优保存周期从约 4,458 s 缩到约 3,150 s。本章设计案例的 1800 s 间隔处，附加比例从 1.08% 变为约 1.25%，完成时间增加约 0.03 天，不改变第 10.6 节的方案选择。翻转条件由两个发生率的相对大小给出：尖峰越频繁，最优周期越短，$\lambda_{\text{spike}}\gg\lambda_{\text{hw}}$ 时保存周期几乎只由数值稳定性决定；回滚间隔以月计时，对 1.08% 的附加比例几乎没有影响。

这几个数的复算：48 卡 $\lambda_{\text{hw}} = 48/(337\times86400) = 1.65\times10^{-6}\ \text{s}^{-1}$。$\tau=600$ s、仅硬件时 $16.381/600 + 1.65\times10^{-6}\times(300+120) = 2.73\% + 0.069\% = 2.80\%$；加入尖峰 $\lambda_{\text{spike}} = 1/(7\times86400) = 1.65\times10^{-6}$ 后合计 $\lambda = 3.30\times10^{-6}$，$2.73\% + 3.30\times10^{-6}\times420 = 2.73\% + 0.139\% = 2.87\%$。最优周期：$\sqrt{2\times16.381/(1.65\times10^{-6})} = \sqrt{1.99\times10^{7}} \approx 4{,}458$ s，加入尖峰后 $\sqrt{2\times16.381/(3.30\times10^{-6})} \approx 3{,}150$ s。1800 s 处则是 $0.91\% + 3.30\times10^{-6}\times(900+120) = 0.91\% + 0.337\% = 1.25\%$。

「翻转条件」在第二次出现，第一次是容量因子，含义一致：两个方向的力量交叉时，最优解会跳变。这里的两股力量是尖峰回滚频率和保存成本；当尖峰频繁到 $\lambda_{\text{spike}}\gg\lambda_{\text{hw}}$，最优周期就由数据与数值稳定性主导，硬件故障率反而无所谓了。

工程上的实用结论：如果你在长跑一个训练任务，看到损失尖峰导致的回滚比硬件故障还频繁，那么调 checkpoint 周期已经没用了，收益有限，应该去查数值稳定性（学习率、精度、梯度裁剪、数据质量）；反过来若尖峰稀少，硬件故障才是决定保存周期的那一项。

> 补充：掉队者最大值模型（$\sigma$ 为均值的 2%）与（$\sigma$ 为均值的 5%）；约 0.5% 的机器明显变慢见 MegaScale；1024 卡作业平均无故障 7.9 小时、8 卡作业 47.7 天见 Meta 集群可靠性论文，保存周期部分的每卡故障率即由 1024 卡的 7.9 小时折算；每卡计算时间的标准差与损失尖峰回滚间隔为本例取值；最大值期望按阶次统计的数值积分求得，未模拟相关性、周期性抖动或持续性慢卡。

## 10.5 强化学习训练

前四节假定训练数据已经给定。RL 让模型参与产生下一批数据：模型生成轨迹，系统计算奖励或验证结果，再将轨迹用于训练，更新后的权重又改变下一轮生成。系统由处理固定数据的训练流水变成反馈循环，新的问题集中在各阶段的处理速度、切换时的状态重叠，以及样本究竟由哪一版策略产生。

生成轨迹的推理端与计算损失的训练端还必须对同一条轨迹给出可对齐的概率，这就是本节的训推一致性（training-inference consistency）。它直接影响参数更新是否遵循算法预期，也约束阶段加速与异步执行的收益。

把 SFT 和 RL 放在一起看，区别不在损失函数，而在数据是从哪来的。SFT 的数据是一个预先固定的数据集，训练是把这份数据的分布学进去；RL 的数据由当前策略与环境交互产生，训练会改变下一批数据的分布。这就把训练系统从一条单向流水线变成了一个闭环，闭环里每一段的速度、每一段的延迟，以及各段看到的策略版本，都成了设计变量。

「训推一致性」这个词容易被读得太轻。它的意思是：同一条轨迹、同一个前缀、同一个 token，生成端（推理引擎）和训练端（训练引擎）算出的概率要能对齐。难在两端用的注意力实现、归约次序、并行度、批形状、数值精度都不一样，采样时还经过温度、top-k、top-p 变换。一旦对不上，训练端以为自己在优化策略 π，实际优化的是带系统误差的 π，这正是 10.5.3 与 10.5.4 要量化的东西。

### 10.5.1 一轮回答生成、验证与参数更新

一轮反馈循环是这样走完的：从四条提示词（prompt）出发，每题生成两条回答，得到八条轨迹。奖励描述这些回答的结果，优势值（advantage）衡量回答比所选基准好多少，用来确定调整回答概率的方向和幅度。训练端按有效 token 构造损失并完成一次参数更新。新权重交给生成端后，下一轮样本来自更新后的策略。生成、奖励与学习分别使用不同形式的数据，样本标识将三者连接起来。

一轮循环的数据流可以画成这样（是这里按元素画的示意）：

```
四条 prompt ──► 生成端（每题两条回答）──► 八条轨迹
                                          │
                                          ├─► 奖励/验证（打分）
                                          │
                                          └─► 训练端：按有效 token 构造损失 → 反向 → 参数更新
                                                                       │
                            新权重发布回生成端 ◄───────────────────────────┘
```

关键在于每一步都有元数据：样本标识。奖励是对哪条轨迹给的、损失是对哪些 token 算的、更新后的权重该发给谁，都靠标识对齐。

这里的数据来源与通常采用固定数据集的 SFT 不同。SFT 在给定答案的真实前缀上预测下一个 token，即教师强制（teacher forcing）；部署时模型则根据自己生成的前缀继续回答。一旦前面生成错误，后续就可能进入训练数据较少覆盖的上下文，误差随生成累积。这种训练与使用时的前缀分布偏移，是固定数据 SFT 的局限之一。梯度仍可以正确对应当前损失，但训练覆盖的情境与模型实际遇到的情境不同。

针对这种前缀分布偏移，OPD 让当前学生模型自己生成轨迹，再由教师针对学生实际生成的前缀提供监督，例如下一 token 的概率分布。学生因而能在自己容易出错的位置学习，减少前缀分布偏移；教师的逐 token 反馈也提供了比单个终局奖励更细的学习信号。DeepSeek V4 用多教师 OPD 将领域专家的能力合入统一模型，第 3 章已把教师前向列为一项独立的计算工作。

与固定数据的 SFT 相比，OPD 的潜在优势在于达到目标能力所需的学习样本或更新次数可能减少。它同时增加学生在线生成、教师前向与权重同步的成本，是否减少总 GPU 小时或完成时间仍要实测。OPD 的定位要说准：它是专门对付前缀分布偏移的一种监督方式，让学生在自己生成的前缀上接受教师的逐 token 监督，跟 RL 算法不是一回事。它与 RL 的奖励信号可以叠加，代价是多了一个教师前向的开销。

几个容易混的概念要分开。SFT 描述的是监督目标，离线（offline）描述的是数据是否预先固定；也可以在线收集数据后使用监督损失。在线（online）表示数据随训练过程持续产生，on-policy 则进一步要求采样分布与所优化的策略一致。两对概念是正交的：离线与在线说的是数据是否预先固定，on-policy 说的是采样分布是否等于当前被优化的策略。异步的在线 RL 可能使用滞后的策略，OPD 也会遇到生成引擎与训练引擎的计算差异。在线采样用于缓解数据分布偏移，而训推一致性还需要对齐生成与训练两端的计算过程。

回到本节开头那一轮的八条轨迹，看训练端如何按有效 token 构造损失。第 10.3.1 节的八条回答例子来自一次小模型实验的回答长度：回答中的有效 token 共 20 个，包含表示序列结束的 EOS token；输入计算的有效 token 共 366。提示词和回答都参与前向计算，损失则按选中的回答 token 归一化。所以生成长度影响计算成本，损失掩码（mask）标明每个 token 是否计入损失、决定哪些 token 参与梯度计算，两者作用不同。前向成本由输入长度（prompt 加回答）决定，梯度成本由被选中的回答 token 决定；只提升生成吞吐量并不会等比提升训练速度。反之，如果回答很长而 prompt 很短，损失占前向的比例也会不同。这里的 20 与 366 来自第 10.3.1 节的小模型实验，属于给定数字。

损失之外，同一提示词下的相对奖励还决定优势。两条回答奖励均为 1，减去组内均值后都为零；奖励变为 1、0，中心化后为 0.5、−0.5，策略才获得区分两条回答的方向。策略梯度是按优势加权、朝提高该回答概率的方向走，同一 prompt 下两条回答奖励相同的时候，不管系统把前向、反向、优化器都跑完，梯度依然是零，只可能剩权重衰减，这一批样本对学习毫无贡献。系统即使完成了前向、反向和优化器调用，也可能遇到第一种优势全为零的 batch。统计训练吞吐量时，应计算每秒实际用于训练的轨迹或 token 数；模型能力是否提高，则用固定的评估任务检验。

案例：参数发生变化，模型能力为何没有提高？一次固定的小模型实验用强化学习训练框架 verl 和推理引擎 vLLM 协作运行：算术题的精确匹配奖励让同组回答得到相同的奖励，优势和策略梯度都为零，参数变化只来自 AdamW 的权重衰减。AdamW 在 Adam 的梯度更新之外，单独按比例缩小权重；即使当前策略梯度为零，这一步也能改变参数。改用固定符号奖励后，两步训练都出现了非零梯度与权重更新，但算术验证只有 2/4 正确。

这个案例是本章最实用的一个警示：不要用参数是否变化判断训练是否有效。AdamW 即使梯度为零也会按比例缩小权重，参数一定在动，要看的是固定评估任务上的表现。它也给出了诊断顺序：先看优势是否全零，这是奖励构造问题；再看梯度是否非零，这是系统执行问题。改为固定符号奖励后梯度出现了，但算术验证只有 2/4 正确，说明有梯度也不等于学到了正确的东西，奖励设计本身仍然是决定性的。奖励构造决定学习方向，系统执行负责把这一方向一致地应用到参数。

### 10.5.2 各阶段的资源分配与权重同步

明确了样本如何形成梯度以后，才能讨论每秒能训练多少样本。RL 的反馈阶段可能执行规则验证或奖励模型（为回答打分的模型），OPD 则需要教师给出监督；两者都应按实际反馈工作的处理能力分配资源。生成、验证和学习像前后相接的三道工序，前一道做得更快，只有后一道能够消化，才会增加最终产出。

先把三者的处理能力换算成同一种工作单位。设三者分别为 $r_g, r_v, r_l$，验证后符合策略版本要求的比例为 $q$，在独立资源上稳定流水执行时，每秒可用于训练的样本数上限为

$$
r_{\text{effective}} = \min\left(r_l,\; q\min(r_g, r_v)\right)
$$

这个式子的读法：先取生成与验证中较慢的那个 $\min(r_g,r_v)$，因为两者是串行工序；再乘上「过了验证还能用」的比例 $q$，得到真正能送到训练端的样本率；最后与训练端自己的处理能力 $r_l$ 取小。任何一段变快，只有当下游能消化时才有效。

例：RL 生成、验证与学习三个阶段中，应优先扩容哪一个？生成每秒提供 12 条等长轨迹，验证处理六条，学习阶段处理八条；验证后四分之一因版本过旧被丢弃。每秒进入学习的只有 $6 \times 0.75 = 4.5$ 条。生成翻倍到 24 条/s，验证瓶颈仍将进入学习的样本限制在 4.5 条/s；验证翻倍到 12 条/s，每秒可送往训练端的轨迹达到九条，此时训练端每秒只能处理八条，成为整个流水线的瓶颈。所以应把新增资源分配给当前最慢的阶段，该阶段加速后，再判断瓶颈转移到了哪里。

复算一遍：$q = 1-0.25 = 0.75$。原状态 $\min(12, 6) = 6$，$6\times0.75 = 4.5$，与 $r_l = 8$ 取小得 $r_{\text{effective}} = 4.5$ 条/s，瓶颈是验证；生成翻倍到 24 时 $\min(24,6)$ 仍是 6，仍 4.5 条/s，等于白加资源；验证翻倍到 12 时 $\min(12,12) = 12$，$12\times0.75 = 9$，与 $r_l=8$ 取小得 8 条/s，瓶颈转移到学习端。

「保留 75%」为什么会出现？异步或滞后执行时，一部分样本是用过旧策略生成的，按策略版本筛选后被丢弃；$q$ 就是 10.5.3 节里那个保留比例在资源分配公式里的位置。它在两处出现，含义一致：有效产出的瓶颈既可能是速度，也可能是版本合格率。

图 10-37 先把三道工序画在各自独立的资源上。若改用同一组卡轮流执行，就能减少所需的卡数，但生成和学习之间要切换整套显存里的数据。

共享加速器让同一组卡轮流训练和生成，节省重复资源；独立部署让两侧独立执行，获得重叠机会，但要在两组卡之间发送权重。共享加速器的关键成本发生在切换：旧状态尚未释放，新状态已经开始加载，两个阶段各自运行时显存都足够，切换时却可能因两套数据同时占用显存而超出容量。

设共享的卡为 H100 SXM，标称 80 GB，约合 74.5 GiB。训练状态占用显存 40 GiB，生成需要约 15.3 GiB BF16 权重与 24 GiB KV 缓存池，另有两阶段共用开销 4 GiB。训练独占时 44 GiB，生成独占时约 43.3 GiB，都低于 74.5 GiB。先恢复生成权重和 KV，再释放训练状态，峰值为 $40 + 15.3 + 24 + 4 \approx 83.3$ GiB，超出一张 H100 的容量。

改变次序就没事了。先加载生成所需的权重，暂不分配 KV，峰值为 $40 + 15.3 + 4 \approx 59.3$ GiB。随后释放 40 GiB 训练状态，显存占用降为约 19.3 GiB，再分配 KV，进入约 43.3 GiB 的生成状态。两条路径最终状态相同，峰值差 24 GiB，恰好是一份 KV 池。

这段显存分析是「张量生命周期」方法的教科书例子，关键不在总量，而在峰值出现在哪个瞬间。路径 A 是先 KV 后释放，$40 + 15.3 + 24 + 4 = 83.3$ GiB 大于 74.5 GiB，爆；路径 B 是先权重、后释放、最后 KV，先 $40 + 15.3 + 4 = 59.3$ GiB，安全，释放训练状态后降到 19.3 GiB，再上 KV 变 43.3 GiB。两条路径的终态完全相同，都是 43.3 GiB 的生成状态，差别只在中间某一刻两套数据是否重叠。切换期的容量不由稳态决定，而由操作顺序决定，只要把分配 KV 推到释放训练状态之后，就省下一整份 KV。

独立部署的代价则由权重发送范围决定。Qwen3-235B-A22B 的 BF16 专家权重为 423 GiB，采用 16 路专家并行（EP16）时，每个接收方只需要约 26.4 GiB。逐一向 16 个接收方发送完整专家集合，共发送 $16\times423 = 6768$ GiB；按各自的分片发送，合计为 423 GiB。先确定每个接收方需要的参数分片，再组织分发，可以同时减少接收缓冲和发送方的发送量。这条和 10.4.2 节的全局坐标是同一个思想：先确定接收方需要哪个分片，再组织传输。

这里再次用到了本章的两种分析方法：共享加速器时要分析张量的生命周期，独立部署时要分析数据传输和各阶段的处理时间。把两条路线对照起来，成本结构完全不同：

| 维度 | 共享加速器 | 独立部署 |
| --- | --- | --- |
| 资源 | 一组卡兼顾两阶段，卡数少 | 两组卡，资源多 |
| 主要成本 | 切换时的显存峰值（操作顺序敏感） | 权重发送范围（分片粒度敏感） |
| 分析方法 | 张量生命周期 | 数据传输 + 各阶段处理时间 |
| 收益 | 省重复资源 | 生成与学习可重叠 |

阶段独立以后，还会产生策略版本差异，下一小节将分析这种版本差异如何影响可用于训练的样本数量。

权重同步中还有一类生命周期不同的权重：第 4.7.3 节的固定权重加速器可以运行 RL 流程中权重长期不变的模型。算法采用固定参考模型时，其权重能够留在专用存储中反复读取；持续更新的策略模型则使用可写权重存储，并将新版本发布给生成端。图 10-40 按这两种生命周期画出权重路径。

### 10.5.3 异步训练、策略版本与长轨迹恢复

第 10.5.2 节的独立部署进一步允许不同 batch 交错进行：学习端处理上一批样本时，生成端已经开始生成下一批。同步循环则等待学习和权重同步完成，再产生下一批样本。异步循环让生成与学习重叠，生成端可能仍在使用旧权重。为计算样本对当前参数更新的贡献，需要保留实际采样策略的概率。

权重更新后，模型给出的策略随之变化。下面沿样本流转顺序区分三个策略版本。令实际行为分布为 $\mu$，本轮优化的起点策略为 $\pi_{\text{old}}$，当前优化策略为 $\pi_\theta$。起点策略随优化轮次更新，用 KL 散度做正则时所用的参考模型则保持固定。对同一 token 和前缀，在三个概率有定义且分母非零的位置，概率比满足

$$
\frac{\pi_\theta}{\mu} = \frac{\pi_\theta}{\pi_{\text{old}}} \cdot \frac{\pi_{\text{old}}}{\mu}
$$

三个版本的关系可以用一句话说清：$\mu$ 是谁生的样本，$\pi_{\text{old}}$ 是本轮优化的起点，$\pi_\theta$ 是当前正在优化的策略。理想情况下（同步、同引擎、无采样变换）三者相同，概率比为 1；一旦异步执行，$\mu$ 就滞后于 $\pi_{\text{old}}$ 与 $\pi_\theta$。参考模型与 $\pi_{\text{old}}$ 要分开：参考模型在整个训练中固定，$\pi_{\text{old}}$ 每轮更新。

概率比分解式的作用是把「本轮学习率带来的变化」和「采样与起点的历史差异」分成两个因子，分别处理：前者是 PPO 裁剪要管的，不能一步走太远；后者是过期样本造成的重要性权重偏差。右边第一项描述本轮参数优化带来的概率变化，第二项描述实际采样分布与本轮起点策略之间的差异，其中既可能有策略版本滞后，也可能有采样配置或跨引擎计算差异。

数值不一致的代价可以算得很直观。若行为策略和当前策略对该 token 给出的对数概率（logprob）都为 −3，总比值为 1；若误用重新计算得到的对数概率代替行为策略原先记录的值，将它写成 −3.25，比值就变为 $\exp(0.25)\approx 1.28$。参数没有变化，样本权重却增加了约 28%。在 PPO 里这可能导致两个后果：贡献被错误放大或压低，或者因为超过裁剪范围而被错误裁掉。所以生成端必须保存当时实际用的 logprob，而不是事后让训练端重算一个「更准」的值。保留行为概率，训练端才能区分策略变化与计算差异。

即使每轮都先同步权重，第二项也未必等于 1。生成端通常逐 token decode 并读取 KV 缓存，训练端则把整段轨迹并行输入，重算各 token 位置的概率后再反向传播。生成端是每步一个 token、带 KV 缓存、batch 形状随请求变化；训练端是一次算完整条轨迹。同一个数学式子，在不同 kernel、不同归约次序、不同并行度下结果位不同。第 5.2.4 节已经测量过其中一项：同一行输入按不同段数做归约，平方和相差 166 个 ULP，而切成几段又取决于当时的 batch 大小，批形状一变，数值结果就变。两端最先出现差异的是前向计算；反向会把训练前向构造出的损失差异传入梯度。MoE 的离散路由还会放大这种差异。

第二项中还有一部分来自采样配置：行为概率按实际采样规则计算。温度缩放、top-k 或 top-p 截断会改变模型原始 Softmax 分布，因此应保存变换后的概率及采样配置。训练端用对应的分词、对话模板、位置编号、注意力掩码和 EOS／截断位置重建输入，才能对同一事件计算概率比。

在近端策略优化（PPO）一类更新中，概率比决定优势对梯度的权重，也参与裁剪判断：概率比偏离 1 超过设定范围时，裁剪截断它对梯度的贡献。若把实现差异误认为参数更新，样本的贡献就可能被错误地放大或压低，也可能错误地触发裁剪；若使用序列概率比，各 token 位置的 logprob 之差还会相加。因此较长轨迹会积累更多概率偏差，使更新更容易波动。

重要性加权用概率比调整已采样事件的贡献，因此采样分布必须覆盖目标事件。截断采样排除的 token 无法通过已有样本的概率比补回；分布差异过大时，权重方差也会增大。裁剪可以限制极端权重，但会引入偏差，而且分别裁剪两个因子与裁剪总比值会产生不同的损失，所以工程实现里的裁剪口径必须与算法设计一致。异步执行会增加策略版本的时间差，下面将可用样本比例与执行周期一起计入收益。

例：异步流水能承受多高的过期样本丢弃率？每批生成 40 s、学习 16 s、阻塞两侧的权重同步 4 s，同步周期为 60 s。设生成和学习使用独立资源，权重同步仍独占 4 s，则异步稳态周期为 $\max(40,16) + 4 = 44$ s。

从图 10-42 的同步执行改为图 10-43 的异步执行后，减少的是学习端与生成端轮流等待的时间。但生成得更早也意味着样本可能使用较旧的权重，因此还要扣除被丢弃的样本。

若每批原有 $B$ 条等效轨迹，异步执行后，其中比例为 $q$ 的轨迹保留下来用于训练，则同步和异步执行的有效样本吞吐量分别为 $B/60$、$qB/44$。异步更快要求

$$
q > \frac{44}{60} = \frac{11}{15} \approx 73.3\%
$$

这个门槛可以这样理解：同步周期 60 s 出一批，异步周期 44 s 出一批，异步的吞吐倍率是 $60/44 \approx 1.364$；但要扣掉 $1-q$ 的样本，只有当 $q\times1.364 > 1$ 时才真的更快，即 $q > 44/60$，边界 73.3% 就是这个交叉点。

当 $q=0.8$ 时，有效样本吞吐量提高约 9%；当 $q=0.7$ 时，虽然每批更早结束，有效样本吞吐量反而减少约 5%。复算：$q=0.8$ 时 $qB/44 = 0.8B/44 = 0.01818B$，同步 $B/60 = 0.01667B$，比值 1.0909，即提高约 9%；$q=0.7$ 时 $0.7/44 = 0.01591$，比值 $0.9545$，即减少约 4.5%，这里说约 5%。所以异步更快不是无条件的，它是在拿样本新鲜度换周期长度。计算异步执行的收益时，还要减去因策略版本过旧而被丢弃的样本。

图中的生成阶段画成了一段连续的工作。轨迹越长，这一段越容易跨过参数更新或遇到中断，于是除了筛选完成的样本，还要考虑尚未完成的轨迹如何继续。长轨迹也会延长生成样本与使用样本训练之间的时间差。KV 是给定权重对前缀执行的结果：使用相同权重恢复时，可继续使用已保存的 KV，换权重后则需重新执行前缀来生成对应 KV。Qwen3-8B 的 8K BF16 KV 占 1.125 GiB，保存和取回 KV 缓存需要存储空间与传输时间，重建 KV 缓存则需要重新执行 prefill 计算。恢复方案据此比较取回时间与重建时间。

这条因果链要抓牢：若一律丢弃重采，长样本会因为更容易撞上中断而被系统性淘汰，学习数据随之出现长度偏移。

若总是丢弃中断轨迹并重新采样，长轨迹因执行时间更长而更容易被丢弃。设生成期间的中断率为 $\lambda$，持续 $t$ 的轨迹能不受中断、完整生成的概率为 $e^{-\lambda t}$；随着 $t$ 增长，进入学习的数据比例下降。逐 token 记录生成进度和策略版本，可以在恢复后继续生成同一条轨迹，减少这种由系统中断引入的长度偏移。轨迹在模型与环境两侧的状态如何跨过中断保留下来，见第 11.3.3 节。

让训练与部署使用同一条路径的做法，在实际模型中已经出现。DeepSeek V4.1 把部署时的稀疏访问与恢复方式纳入训练。稀疏注意力从训练之初就使用 64K 序列，后训练加入层级候选限制，使训练和推理使用相同搜索域；量化感知训练（训练时模拟低精度量化的误差）让模型适应 FP4 的主 KV；只重放有限长度的输入来重建解码器 SWA 状态，这一过程也在后训练中模拟。模型由此学习使用部署路径实际提供的表示与局部状态。这是训推一致思路的延伸：与其事后对齐，不如训练时就模拟部署路径。

### 10.5.4 专家路由重放与训推一致性

MoE 把 10.5.3 的数值差异变成了更硬的问题：即使权重完全相同，生成端与训练端的数值计算差异也可能改变专家的选择。专家选择本身是离散的，分数上一点抖动就足以让某个 token 换一条计算路径。给出的例子取选择分数最高的两个专家（top-2），前三个专家的分数是 0.500、0.301、0.300，此时选专家 1 和 2；第三个分数因为计算次序变成 0.302，选择就改成专家 1 和 3。0.301 与 0.302 之间隔着一道悬崖，跨过去之后这个 token 乘的就是另一个专家的权重矩阵，而且影响会沿后续层继续传播：第 3 层选错专家，产生的表示就变了，第 4 层的路由分数也跟着变，误差被逐层放大。

路由重放（Routing Replay）的思路接近录制加回放。录下来的只是生成时选中的**逻辑专家 ID**，没有权重，也没有分数；训练时按这些 ID 去挑专家，而路由分数、专家输出和梯度仍旧用当前权重算。样本、token 位置和层号共同定位这一份记录，于是生成与训练经过相同的离散专家路径，数值计算又始终反映当前参数。这样保住了两件事：概率比建立在同一条路径上才有意义；训练用的还是当前参数的梯度，不至于退化成拿旧模型的输出来训练。ID 重放和输出重放要分清，前者只固定离散选择，后者等于直接搬用旧计算的结果，梯度会被破坏。

先算这份记录占多大空间。Qwen3-30B-A3B 的 48 层各记录分数最高的八个专家（top-8）的编号，对 8,192 个 token，以每个整数占 2 字节的无符号整数格式 uint16 保存每个专家 ID，大小为

$$
8192 \times 48 \times 8 \times 2 = 6\ \text{MiB}
$$

使用每个整数占 4 字节的 int32 格式则为 12 MiB。随手核一遍：$8192\times48\times8\times2 = 6{,}291{,}456$ 字节，正好 6 MiB（这一处复算是这里补的）。这个量级相对 checkpoint 的 115 GB 微不足道，真正的麻烦在于记录必须随 token 一起移动。序列打包改变 token 的位置，上下文切分把 token 换到别的卡上，重计算还会再读一次同一层的记录；只有让 ID 与 token 的原始位置绑定、一起经历这些变换，训练端才能找回原先那组专家。

案例这边，NVIDIA 公布的路由重放（R3，即 Rollout Routing Replay）验证报告有四组开关对照，各训练 100 步。开启重放之后，日志中记录的对数概率误差中位数都下降，每步总耗时中位数略长，训练奖励则没有一致提高。重放减少了路由差异，可保存记录和执行重放本身也要花时间。比较两种方案时，概率误差、训练时间和固定评估任务上的表现要分开看，前者是一致性指标，中间那个是成本指标，后者是能力指标；这一组对照里一致性一致改善、成本略有增加、能力却没有一起跟上。

> 补充：路由元数据预算、R3 这里公开的日志与分析；**四对设置共用 seed42**；reward 为训练 batch 指标，logprob 为 R3 这里的日志级统计。

同一份权重、同一批 token 下，生成端与训练端的 logprob 差异反映的是计算路径和采样定义的影响，MoE 的专家 ID 则标明离散路由是否一致。数值对不对得上、采样策略滞后当前策略多少、以及路由是否一致，这三件事共同决定有效训练样本数。训练端要用生成时记录的（行为）概率算比，重算出来的 logprob 只用于诊断差异。序列打包、上下文切分、重计算这三种变换都会改变 token 的物理位置，坐标对齐因此成了这份元数据的核心工程问题：ID 记的是「样本 A 的 token 17、第 3 层」，token 一旦被重排或被切到别的卡上，就只能靠原始位置把它找回来。

把视野拉开一点，RL 是把生成、环境验证和参数更新组织成一个完整的反馈过程。生成端提供采样概率与专家选择，训练端据此组织更新，资源调度再安排各阶段重叠；贯通这几路信息，就能同时优化数据交接、执行一致性与资源利用。本节前半段的异步周期与这里的路由重放，分别对应省下的等待和新增的记录成本，而整个反馈循环最终要用有效样本和训练进展来评价。评估一套 RL 训练系统时，光看吞吐（每秒多少条轨迹）是不够的，得看每秒有多少条真正可用、且与当前策略一致的轨迹。

MoE 的离散路由会把数值误差变成路径误差；路由重放只固定逻辑专家 ID，数值仍由当前权重算，代价是一份必须随 token 位置迁移的元数据。

## 10.6 从系统方案到完成期限与硬件选择

### 10.6.1 汇总容量、每步耗时、停顿与恢复

把前面各层的结论汇到一处，就能算章首那个训练任务的完成时间。两套方案都处理 100B token，每步 384 条 8,192 个 token 的序列，共 31,790 次训练迭代。设每步训练时间 $t_s$ 已经包含单卡计算、通信等待与输入等待，保存与恢复的附加时间比例为 $L$，计划性停顿为 $T_0$，本章的一阶完成时间模型写成

$$
T_{\text{finish}} = T_0 + \left\lceil \frac{D}{b} \right\rceil t_s (1 + L)
$$

式子里 $\lceil D/b\rceil$ 是迭代数，$t_s$ 每步都要付一次所以落在乘法里，$T_0$ 是一次性的加法常数，$L$ 则把保存、重做与恢复摊到每一步上。

式中每一项都来自本章不同层次的分析：分析张量的生命周期，可以确认显存是否足够；分析关键路径，可以求得 $t_s$；checkpoint 模型给出 $L$；计划性停顿取 $T_0 = 5$ 天。汇总起来就能比较两套方案的完成时间。

表格读起来按「容量、时间、汇总」三组最省事。容量组里每卡可用 22 GiB，预计占用 13.8 与 12.5 GiB，两套都过，这是先决条件，不构成取舍。时间组里单卡计算从 78.3 s 降到 52.2 s，ZeRO-3 链路时间从 17.9 s 降到 12.0 s（PCIe 4.0 x16），可两条方案的通信等待都只有 0.08 s，原因是大部分链路时间被计算盖住了，这正是 10.3.3 的重叠分析在起作用。汇总组把基础训练时间从 29.0 天压到 19.4 天，加上 5 天与附加比例后得到 34.3 与 24.6 天。

「每卡单序列累积次数 12 / 8」这一行容易被跳过去，它说的是梯度累积次数。卡少时每张卡要攒更多 micro-batch 才凑够全局 batch，单卡计算时间因此更长；48 卡把同样 384 条的全局 batch 摊到更多卡上，累积次数从 12 降到 8，单步时间从 78.3 s 降到 52.2 s。这就是这里那句「增加卡数的主要价值」落到实处的地方。

决策顺序很清楚：先把违反硬约束的方案排除掉，再在剩下的方案里比总成本。32 卡 34.3 天超过 30 天期限，出局；48 卡 24.6 天，还留 5.4 天余量。这里特别强调「额外故障成本只抵消很小一部分收益」，因为附加比例只有 1.08%，比 32 卡的 1.02% 高不了多少，而多买卡省下的单卡工作量要大得多。容量够的前提下，把每卡的工作量摊薄是划算的。

几个容易混的量摆在一起看：$t_s$ 里的通信等待是实际落在关键路径上的部分（0.08 s），链路时间是通信完全暴露时会花的时长（12.0 s），两者差两个数量级。从基础训练时间走到「加入保存恢复和 5 天预留」，中间要过 $\times(1+L)+T_0$ 这一道，直接相加会算少。计划性停顿 $T_0 = 5$ 天是主动预留，故障恢复时间 $r$ 已经计进 $L$，两笔不能重复算。容量满足与按期完成也是两回事：两套方案的显存都放得下（13.8 与 12.5 GiB 都小于 22 GiB），差别只在时间上。

完成时间 $= T_0 + \lceil D/b\rceil\, t_s(1+L)$：每步耗时来自容量与关键路径，$L$ 来自 checkpoint 模型，5 天是主动预留。本案例中 48 卡以 24.6 天胜过 32 卡的 34.3 天，代价只是 0.06 个百分点的故障附加成本。

### 10.6.2 4090 集群的可行范围

图 10-42 给出了约 5.4 天的剩余时间。把这部分余量分摊回每次迭代，就知道每步还允许增加多少等待，也就得到可用于实际调优的性能目标。48 卡的每步训练时间必须满足

$$
t_s \le \frac{25 \times 86400}{31{,}790 \times (1 + 0.0108)} \approx 67.2\ \text{s}
$$

本方案现在是约 52.8 s，余量约 14.4 s/步。固定单卡计算时间约 52.2 s、输入等待 0.5 s，那么总通信等待最多约 14.5 s；按第 10.3.3 节的重叠分析，当前只有约 0.08 s。即使预取完全失效、12.0 s 的链路时间全部暴露，每步约 64.8 s，仍在上限之内。

复算一遍（用这里数字）：$25\times86400 = 2{,}160{,}000$ s，$31{,}790\times1.0108 = 32{,}133.3$，相除得 67.22 s；余量 $67.2-52.8 = 14.4$ s。这里那句「固定单卡计算 52.2 s、输入等待 0.5 s，则总通信等待最多约 14.5 s」对应的是 $67.2-52.2-0.5 = 14.5$ s，比 14.4 s 略大一点，因为 52.8 s 里已经含了 0.08 s 的通信等待。

这个上限的来源要说清楚：30 天期限减去 5 天预留，剩下 25 天才是反推的基数。两个「12.0 s」的用法也得分开看，作为链路时间它相当于每步的 23%，作为暴露时间却只有 0.08 s。这里用两次不同的假设考验它：预取完全失效时链路时间整段暴露，每步 64.8 s，仍在 67.2 s 以内；每卡一张网卡时，最坏情况也不超预算。在这套设计里，通信还排不上风险点，真正的风险落在单卡计算效率上。

32 卡想挤进这个预算，就得提高单卡计算效率。扣除恢复、0.08 s 通信和 0.5 s 输入之后，可留给单卡计算的时间约 66.7 s，而 40% 效率下需要约 78.3 s。同样的工作量要求效率提高到约 $40\% \times 78.3/66.7 \approx \mathbf{47\%}$，**已高于 Llama 3 报告的最高 43%**。两条改进路线于是可以直接比较：增加两台主机，或者在原有的卡上把单卡计算效率从 40% 提到约 47%。47% 一旦超过 43%，靠工程优化去够它就相当难，本案例因此选了加卡。这条推理值得记住：当优化目标的可行性被打上问号时，比较的另一端（买资源）就自动胜出。

通信预算还要落到物理接口上。第 10.3.3 节的 12.0 s 链路时间以每卡一张 200 Gbit/s 网卡为前提。若一台主机的八张卡只共用一张 200 Gbit/s 网卡，环形集合通信进出这台主机的那条边就要承载每卡的全部收发量（第 7 章例题 7.1 的割集），按每卡每步约 385 GB 计，八卡共用一张 200 Gbit/s 网卡时，每台主机出口要承载约 8×385 GB，链路时间约 123 s，远超前文 14.5 s 的通信上限；即使按每个 micro-batch 分摊，链路时间也约 15.4 s，已接近或超过单 micro-batch 6.53 s 的计算时间，预取失效时会直接暴露。每卡配一张网卡时，12.0 s 即使全部暴露也在上限以内。两种配置的差别在于，共用网卡把按期完成押在重叠上，每卡一张网卡则不依赖重叠。

性能目标就这样对应到了具体的执行过程：每步最多允许 67.2 s，其中计算约需 52.2 s，其余时间留给通信和输入等待。调优时先去缩短超出预算的那段关键路径；如果显存已经足以保存所需张量，就不必再为节省显存而引入额外工作，那会反过来抬高每步时间。

把几个量再理一遍：通信链路时间 12.0 s 是总工作量，通信等待 0.08 s 是实际暴露的部分，通信预算 14.5 s 是允许的上限，三个数各管一件事。每卡一张网卡时链路 12.0 s、最坏也安全；八卡共用一张网卡时每步链路约 123 s，只有把绝大部分通信藏进计算才可能安全。67.2 s 的上限是从 25 天反推的，期限 30 天减去 5 天预留才是基数，不能拿 30 天直接推。micro-batch 的 6.53 s 与每步的 52.8 s 也不是一个量级：前者是单个 micro-batch 的计算时间，后者是整个训练步（含多个 micro-batch 与通信）。

从「还剩 5.4 天」反推出「每步最多 67.2 s」，就能看出本方案真正的风险在单卡计算效率（47% 已超过 Llama 3 的 43%），通信暂时不成问题；网卡共用则会把安全性押在重叠是否成立上。

### 10.6.3 替换硬件后的瓶颈与选择

更换加速器时，上一小节的预算还能接着用，判断计算变快会缩短哪一段、带宽变小又会延长哪一段。新的加速器会同时改变单卡计算、容量和互联，把原有每步耗时拆成计算、通信等待等部分，就能判断某项硬件变化到底值多少。设某资源占原每步耗时的比例为 $f$，处理能力变为原来的 $r$ 倍，其他执行和依赖保持不变，则

$$
\frac{T'}{T} = 1 - f + \frac{f}{r}
$$

这就是根据各项耗时的比例应用 Amdahl 定律。原来 100 ms 中只有 5 ms 通信等待，带宽减半后变为 $95 + 10 = 105$ ms；若原来通信占 50 ms，同样减半后是 $50 + 100 = 150$ ms。前一个任务耗时增加 5%，后一个增加 50%，差别来自等待该资源的原有时间占比相差十倍。

式子的读法是：把原耗时分成受影响的部分（占比 $f$）和不受影响的部分（占比 $1-f$），受影响的那部分按能力倍数 $r$ 缩放，不受影响的照旧。$r=0.5$（能力减半）时 $f/r = 2f$，受影响部分耗时翻倍。这是 Amdahl 定律的反向用法，平常拿它算加速上限，这里拿它算退化的代价。这里两个例子正好展示 $f$ 的杠杆效应：$f=0.05$、$r=0.5$ 时 $T'/T = 0.95+0.1 = 1.05$（+5%）；$f=0.5$、$r=0.5$ 时 $T'/T = 0.5+1.0 = 1.5$（+50%）。同样把带宽砍半，一个几乎无感，一个灾难性，区别只在原来有多少时间在等这件事。所以评估硬件升级或降级时，第一个该问的是「瓶颈环节在原耗时里占多少」，新卡快多少反而排在后面。

套到本章 48 卡方案上，这个式子给出的结论更有意思。暴露的通信只有约 0.08 s，约占每步的 **0.14%**。PCIe 带宽减半时，每个 micro-batch 的链路时间升到约 3.0 s，仍短于 6.53 s 的计算，暴露部分翻倍到约 0.15 s，每步从约 52.8 s 增到 52.9 s，几乎看不出来。反过来，单卡计算效率从 40% 降到 30%，单卡计算时间变为约 69.6 s，加上通信与输入约为 70.2 s，直接超过 67.2 s 的目标。对这套方案而言，决定能否按期完成的是单卡计算效率；带宽只有在预取失效、通信整段暴露时，才会成为式中比例 $f$ 较大的那一项。

这两处也核一遍（用这里数字）：$52.2\times40/30 = 69.6$ s，加通信 0.08 与输入 0.5 得 70.18 s，确实大于 67.2 s。带宽减半时，每个 micro-batch 的链路时间由 $12.0/8 = 1.5$ s 翻倍到约 3.0 s，与这里一致；这里用的是每卡一张 200 Gbit/s 网卡下的 12.0 s，而 15.4 s 属于「八卡共用一张网卡」那种配置，两种配置不能混着比。3.0 s 仍短于 6.53 s 的计算时间，所以暴露部分只是小幅翻倍，从 0.08 s 变成 0.15 s。

比较 A100、A800、H20 或其他加速器时，可以把它们的单卡计算时间、接口传输时间和容量代进同一套分析。先用「能否满足期限」做门槛筛选，再用加速器租用、能源和准备成本比性价比。这里的收尾句很有分量：「更强的单项指标是否值得购买，取决于它能减少多少完成时间或卡数。」这句话是对唯指标论的直接反驳。

几个概念别混：$f$ 是任务属性，说的是你的负载有多依赖它；$r$ 是硬件属性，说的是新设备快或慢多少。同一个式子里 $r>1$ 是加速、$r<1$ 是退化，退化时 $T'/T$ 可以大于 1。单卡计算时间是 $t_s$ 的主体（52.2 s），每步训练时间还要含通信等待与输入等待（52.8 s）。至于 A100、A800、H20 这类替代品，这里只说可以把它们的三项参数代入同样的分析，没有给出具体数值，这里也不替这里补数。

硬件更换的价值由「该项在原耗时中的占比 $f$」决定，$T'/T = 1-f+f/r$；本章 48 卡方案里起决定作用的是单卡计算效率，带宽要等到预取失效才排得上号。

### 10.6.4 模型规模、数据量与期限的敏感性

前几节保持模型不变，比较了卡数和加速器型号。这一节把同一套方法扩展到模型规模，看模型放大之后计算量怎么长。采用稠密模型的粗略计算量公式 $F = 6ND$，固定数据量 $D = 20\text{T}$ token、40% MFU 和可用于执行的期限 $T$，满足期限所需卡数为

$$
p \ge \left\lceil \frac{6ND}{P\eta T} \right\rceil
$$

$F = 6ND$ 的口诀是「每参数每 token 6 次浮点运算」：前向 2 次（一次乘加算 2 FLOPs）乘以参数量，再乘 token 数，反向约为前向的两倍，合计 $2+4=6$，所以训练总计算量对模型规模和数据量都是线性的。卡数公式里 $N$ 是参数量、$D$ 是 token 数、$P$ 是单卡峰值算力、$\eta$ 是 MFU（模型算力利用率）、$T$ 是可用执行时间。它回答的是「给定模型、数据、硬件、效率和期限，至少要多少卡」；$T$ 在分母上，期限越紧，卡就要越多。

图 10-44 把 90 天期限画成了卡数边界。选定某个模型规模之后，边界上方的计算资源能够在该效率下完成工作，边界下方则需要提高效率或者延长期限。

对 1T 参数，16,384 张 A100、H100、B200 在 40% MFU 下分别约需 679、214、94 天。90 天执行预算下，三者都落在计算边界下方，B200 也超出约 4 天，需增至约 17,147 张。只有 MFU 达到 50% 时，B200 才降到约 75 天，落进期限，余下约 15 天可以分配给计划停顿与恢复。**MFU 相差 10 个百分点，就决定了 16,384 张 B200 能否在 90 天内训练完 1T 模型。**

量级上感受一下（用这里数字）：1T 参数、20T token 时 $F = 6\times10^{12}\times20\times10^{12} = 1.2\times10^{26}$ FLOPs。给出的三个天数是 679／214／94，它们的比值大致反映三种卡 BF16 稠密峰值的比值。要让 1T 模型落进 90 天，B200 需从 16,384 张增到约 17,147 张，这是这里数值；这里按 $16{,}384\times94/90$ 估算得约 17,112 张，两者只差 0.2%，差异来自这里用的是未取整的 94.2 天。

「MFU 差 10 个百分点」这一段是全篇最有冲击力的敏感性结论：B200 在 40% MFU 下要 94 天，超期 4 天；在 50% 下只要 75 天，反而余出 15 天。用同样的卡、同样的模型，把效率从 40% 提到 50% 比多买 4% 的卡更管用，因为时间与 MFU 成反比（$94\times40/50 = 75.2$）。用「余下约 15 天可分配给计划停顿与恢复」把两件事连了起来：MFU 提高后的余量正好覆盖 10.6.1 节那 5 天预留与 1% 级附加成本。

固定数据量时，模型参数量增至五倍，计算量也增至五倍；若数据量同时取 $D = 20N$，则 $F = 6N\times20N = 120N^2$，参数量增至五倍，计算量就增至 25 倍。所以「模型大 5 倍，算力要多少」这个问题没有唯一答案，取决于你是否同比放大数据，规模问题的答案由模型和数据共同决定。MoE 的规模核算与稠密不同，这里一句话给出方法：全部可训练参数决定状态（显存、checkpoint），被激活路径决定执行工作（FLOPs），专家交换另外放进关键路径（通信）。这三者正好对应本章的三套分析工具，也解释了为什么 MoE 的「参数量」和「计算量」要分开算。

设计完成以后，还要检验长期执行是否达到预期。公开训练日志提供了长期的观察窗口。若从 checkpoint 继续训练，本次新增 token 等于结束累计值减去恢复起点累计值，再用新增工作除以本次时间，就得到对应的长期速率。这里要记得扣掉恢复起点之前的累计 token，否则会把之前的工作算进本次速率（脚注里 SmolLM3 的例子正说明记录里包含此前工作）。这个速率可以直接检验整套系统能否保持设计中的有效训练进度。

> 补充：Dense 规模与期限、数据量随参数增长的变体；16,384 张 H100、DP=128、8K 序列时 41% 的 BF16 MFU 见 Llama 3 报告表 4。脚注：SmolLM3 原始训练记录核验；SmolLM3 记录含 384、288、192 rank 阶段，最后一次恢复实际运行 14,000 步；终点累计 token 包含此前工作。

回看全章，图 10-10 至图 10-14 解释了数据如何占用显存和经过链路；图 10-17 至图 10-36 说明这些操作如何形成等待、又如何影响长期训练；图 10-42 则把各项耗时汇成了章首任务的完成时间。状态安排、执行顺序和恢复方式由此连成了同一个设计问题。RL 把工作来源改成反馈循环，仍然通过同一套方法比较资源和有效训练进度，下一章进一步讨论这些作业与阶段如何共享资源池。

几个成对的量分清：$N$（参数量）与 $D$（token 数）在 $F=6ND$ 里地位相同、都是线性，可一旦 $D=20N$，$F$ 对 $N$ 就变成平方。40% MFU 的 94 天与 50% MFU 的 75 天之间没有固定差值，两者与 $\eta$ 成反比。图 10-44 里，卡数在边界上方意味着能在剩余时间内完成，下方就要提高效率或者延长期限。MoE 的总参数量与激活参数量也不能混用，前者决定状态占用，后者决定执行工作。

训练算力 $F=6ND$ 对模型和数据都线性（数据随参数同步放大时变成平方），所需卡数 $p\ge\lceil 6ND/(P\eta T)\rceil$；MFU 从 40% 提到 50%，就能让 16,384 张 B200 把 1T 模型从 94 天压到 75 天。

## 常见误区

这里在章末收了一组「看着对、用起来错」的直觉，五条，对应。拿它当设计评审的检查清单很顺手：谁提「加卡就能把时间减半」「把通信再优化短一点」「保存调用返回了就能重启」，都能直接对到其中某一条。

第一条错在把分量当成总量。分片数翻倍，缩小的只是分给各卡的常驻训练状态，小模型例子里从 18 MiB 降到 9 MiB；同一时刻还要占着的其他张量和缓冲区仍有约 21 MiB，峰值于是从 39 MiB 只落到 30 MiB。判容量要看同一时刻所有占用之和，所以问题永远是「哪一刻最大」，逐项去看各自多大并不解决问题。

第二条错在把处理时间当成关键路径时间。72 MiB 的梯度切成三个 24 MiB 子桶，总处理时间约 4.59 ms，比整桶的 4.55 ms 还长，可这三笔传输能分别塞进三个计算空闲时段，每步耗时反而可能更短。真正加进训练步时间的是通信超出计算窗口的那一段。同一种错觉落到保存上就是第三条：50 s 的故障之后能恢复到哪一点，取决于哪份快照已经提交；同样的 1 s 前台暂停可以对应 30 s 重做，也可以只对应 10 s，差别来自后台写入的完成时刻（30 s 与 10 s 分别是 7 GB/s 与 20 GB/s 档位下的结果）。

第四条错在把局部瓶颈的解除当成整体加速。本章 RL 流水线里生成 12 条/s、验证 6 条/s、样本保留比例 75%，学习端每秒只能拿到 4.5 条轨迹，此时把生成资源翻倍毫无用处；只有验证这一步提上去才有效，而它一提上去，限制就转移到训练端。这条对应 $r_{\text{effective}}=\min(r_l,q\min(r_g,r_v))$：流水线的产出由最慢的一段决定。

第五条最容易被预算表掩盖。卡数翻倍、batch size 跟着翻倍，完成时间并不会减半，因为 batch size 超过**临界 batch size** 之后，达到同一损失所需的步数不再明显减少。机制出在梯度噪声上：SGD 的噪声随 batch 增大被平均掉，每步的进展不再随 batch 线性增长，「步数按比例减少」这个假设就失效了。本章给的数：梯度噪声尺度为 200 万个 token 时，每步 batch size 从 315 万放大到约 1 亿个 token（1536 卡），完成时间只从 19.4 天降到 12.1 天，加速上限 1.64 倍。

五条合起来是三样思维习惯：把分量当总量、把处理时间当关键路径时间、把局部瓶颈的解除当整体加速。后两样所依赖的洞察在本章出现过两次（10.3.3 与 10.4.3），是重复强调最多的一处。还有一个词要分清：**弱扩展**（weak scaling）让 batch size 随卡数一起放大，受临界 batch size 限制；**强扩展**（strong scaling）保持 batch size 不变、只增加卡数，用更多卡更快算完同一个 batch，每步的统计性质没变，所以不受梯度噪声尺度约束。

按主题收一句：容量看同一时刻的总占用，时间看关键路径上暴露的那一段，吞吐看最慢的那道工序；加卡和加 batch 的收益都被梯度噪声尺度封了顶，本章算出的上限是 1.64 倍。

## 习题与实验

十道题按基础计算、机制分析、综合设计三段递进，做题需要的条件全部在正文里；每题末尾还挂着「实验部分」，要求你用配套记录或自己测出来的数据完成。

**习题 10-1 ・基础：训练状态分片与每卡峰值内存**

题干把本章的梯度改成 FP32，要求先算 Qwen3-8B 的常驻训练状态，再求八卡 ZeRO-1、ZeRO-2、ZeRO-3 的每卡容量；执行期间另有 6 GiB 激活和两份各 3 GiB 的模块缓冲，分别算两份缓冲同时占用与顺序复用时的峰值。

参考解答：先把每参数的字节数按格式算清，BF16 权重 2 bytes、FP32 主权重 4 bytes、Adam 两份状态共 8 bytes，梯度跟权重同精度取 FP32 再加 4 bytes，于是每参数合计 $2+4+8+4=18$ bytes。以 $N\approx 8.19\times10^{9}$ 代入，常驻状态约 $18\times8.19\text{e}9\approx147$ GB（按 8e9 算则是 144 GB，具体位数以本章给定的 Qwen3-8B 参数与 checkpoint 口径为准）。八卡时：ZeRO-1 切优化器状态，每卡约 $2+4+(8+4)/8=7.5$ bytes/参数；ZeRO-2 再切梯度，约 $2+(4+8+4)/8=4.0$ bytes/参数；ZeRO-3 连参数一起切，约 $(2+4+8+4)/8=2.25$ bytes/参数。峰值的关键是把 6 GiB 激活和两份 3 GiB 缓冲叠在常驻状态上：同时占用是常驻 + 6 + 3 + 3，顺序复用是常驻 + 6 + 3，差别只在最大那份缓冲要不要同时驻留。这道题想让你亲手验证的结论只有一条，分片只压缩常驻状态，激活与缓冲一动不动。

思路提示：三个阶段的切分对象分别是优化器状态、梯度、参数，别记混。

**习题 10-2 ・基础：按期完成训练需要多高的单卡计算效率**

题干沿用本章的训练任务，全局 batch size 取 384 条序列，先算 30 天和 25 天对应的每步预算；给定 32 卡，按第 10.3.3 节求 ZeRO-3 每步的链路时间与暴露出来的通信等待，再加 0.5 s 输入等待，先忽略恢复求 25 天内完成所需的最低单卡计算效率，然后带上本章的恢复成本重算。接着把梯度噪声尺度取成 200 万个 token，按第 10.1.1 节的关系式求弱扩展的加速上限，算出 96 卡和 1536 卡在弱扩展与强扩展下的完成时间，并把噪声尺度换成 2000 万个 token 再走一遍。

参考解答：每步预算的算法与 10.6.2 节一样，$t_s \le \dfrac{T\,(\text{天})\times86400}{31{,}790\times(1+L)}$。忽略恢复即 $L=0$ 时，30 天对应 $2{,}592{,}000/31{,}790\approx81.5$ s，25 天对应 $2{,}160{,}000/31{,}790\approx68.0$ s；若计入本章 32 卡的恢复成本 $L=1.02\%$，25 天的预算收紧到约 67.3 s（10.6.2 节按 48 卡的 1.08% 得 67.2 s）。32 卡的单卡计算时间是 78.3 s，对应 40% 效率，要压进预算就得提效率：以 25 天、$L=0$ 为例，可用计算时间约 $68.0-17.9-0.5=49.6$ s（链路时间按 32 卡的 17.9 s 计），所需效率约 $40\%\times78.3/49.6\approx63\%$；换成「链路时间大部分被掩盖、只暴露 0.08 s」的口径，则约 $40\%\times78.3/(68.0-0.58)\approx47\%$。两种口径差的就是通信到底暴露了多少，答题时要把自己采用的那一种写明。弱扩展的上限按临界 batch size 与噪声尺度的关系求，本章给了「噪声尺度 200 万个 token」时 batch 放大 32 倍（315 万到约 1 亿）只换来 1.64 倍加速，据此求上限，再代入 96 卡与 1536 卡。

思路提示：先算每步允许的最长时间，减掉通信与输入，剩下的才是计算预算，再换算成 MFU。2000 万个 token 的噪声尺度更大，能撑起更大的 batch，上限也更高。

**习题 10-3 ・综合设计：在容量、期限与加速器成本之间选择训练方案**

题干要比较 32 卡与 48 卡的训练完成时间和累计 GPU·小时；把每步激活与临时缓冲的峰值需求从 10 GiB 提到 20 GiB，重新判断容量；把 BF16 权重副本换成第 10.1.2 节的 FP8 分块缩放格式，重算两套方案的每卡常驻状态与容量余量；若只能租四台八卡主机，分别算出任务量要减到多少、期限要延到多久、效率要提到多少才能完成训练。实验部分要求选一条路线实际测量，用测得的数值替换本章给定的参数。

参考解答：GPU·小时 = 卡数 × 完成时间 × 24，32 卡约 $32\times34.3\times24\approx26{,}342$ GPU·小时（约 2.63 万），48 卡约 $48\times24.6\times24\approx28{,}339$ GPU·小时（约 2.83 万）。48 卡是用更多 GPU·小时换更短的完成时间，这正是期限与成本之间的取舍。容量上本章每卡可用 22 GiB，预计占用 13.8 / 12.5 GiB；激活与临时缓冲从 10 GiB 提到 20 GiB 后，两套方案都可能超容量，需要按本章的状态口径重算。FP8 分块缩放把 BF16 权重副本从 2 bytes 降到 1 byte/参数，直接压低常驻状态。若手上只有 32 卡，三条路是等价的换算：把任务量减到原 32 卡方案能按期完成的规模，把期限从 30 天往后延（补上超出 34.3 天的那部分），或者把效率从 40% 提到约 47%。

思路提示：三条路都落在同一个 $T_{\text{finish}}$ 公式里，先把公式写出来再代入，比逐项试算快得多。

**习题 10-4 ・分析：micro-batch 数与激活重计算如何改变流水开销**

题干给四阶段、前向 10 ms、反向 20 ms 的模型，求 1、4、8、16 个 micro-batch 的理想利用率；沿图 10-19 解释 93—95 ms 的等待来自哪项依赖；对八个 micro-batch 比较交错式 1F1B（$v=2$）与零气泡调度 ZB-H1（$T_B = T_W$），用正文的气泡公式分别算气泡时间，对照事件模型给出的 298 ms 与 283 ms，并说明交错式为什么增加了跨界传输次数。再一个问题是激活重计算：设每层每个 micro-batch 的可重建乘积占 10 MiB，原方案里四个 micro-batch 还没做反向，每个都要保留九层的乘积；改成每次只重建一层中一个 micro-batch 所需的乘积、用完就释放，问新方案少保留多少数据、逐层串行重建需要多大工作区，以及两层同时反向时工作区怎么变。

参考解答：理想利用率按流水线气泡公式，$m$ 个 micro-batch、$p$ 个阶段时约为 $\dfrac{m}{m+p-1}$，因为流水线充满后每步完成一个 micro-batch。$p=4$ 代入：$m=1$ 为 $1/4=25\%$，$m=4$ 为 $4/7\approx57.1\%$，$m=8$ 为 $8/11\approx72.7\%$，$m=16$ 为 $16/19\approx84.2\%$。93—95 ms 那段等待对应图 10-19 里流水线的启动与排空，最早几段前向要等前一个阶段腾出位置，反向要等对应 micro-batch 的前向结果，空隙来自跨 micro-batch 的先后依赖。气泡时间按第 10.3 节的公式代入（1F1B 与 ZB-H1 各一套），交错式之所以增加跨界传输次数，是因为 $v=2$ 让每个阶段同时处理两个 micro-batch，阶段之间要传递更多次中间结果。激活占用这边：原方案保留 $4\ \text{micro-batch}\times9\ \text{层}\times10\ \text{MiB}=360$ MiB，改成逐层重建、用完即释后工作区只需 1 层 × 1 个 micro-batch，也就是 10 MiB，少保留约 350 MiB；两层同时做反向时工作区变成 $2\times10=20$ MiB。

思路提示：气泡公式的自变量只有 micro-batch 数和阶段数；重计算部分的自变量是同时保留的层数与 micro-batch 数之积。两者都是乘法结构，先把维度写清再代数。

**习题 10-5 ・分析：数据准备进程暂停时，需要预取多少序列**

场景是 48 卡每步处理 384 条序列、每步训练约 52.8 s，四个数据准备进程每个每秒准备两条序列。问一个进程暂停 60 s 时，按训练端的平均消耗速率算，至少预存多少条才能维持原来的训练速度；四个进程全部恢复后，要多久把预取队列补回暂停前的数量。再按第 10.4.3 节 7 GB/s 的合计写入，求约 115 GB 的 checkpoint 不产生写入积压的最短保存间隔。

参考解答：训练端消耗速率 $384/52.8\approx7.27$ 条/s，四个进程供应 8 条/s。一个进程暂停 60 s 后供应降到 $3\times2=6$ 条/s，缺口 $7.27-6=1.27$ 条/s，暂停期间累计约 $1.27\times60\approx76$ 条，这就是维持原速所需的最少预存。若按更保守的口径，暂停期间完全靠预存供应、不许训练降速，那要预存 $7.27\times60\approx436$ 条。恢复后供应回到 8 条/s，相对消耗富余 $8-7.27=0.73$ 条/s，补回 76 条约需 $76/0.73\approx104$ s。写入那边：产生速率不能超过 7 GB/s，所以最短间隔是 $115/7\approx16.4$ s。

思路提示：分清「净缺口」与「总消耗」两个口径；补队列的时间要用供应减消耗的富余去除以缺口。

**习题 10-6 ・分析：checkpoint 保存频率与故障重做成本**

题干要求按本章的一阶近似模型推导最优保存周期，计算 1024 卡作业在 300、900、1800 s 三档间隔下，保存 checkpoint 与故障重做各花掉多少时间；加入每天一次、同时影响全作业的共同中断后重新算故障率与最优周期；再把平均七天一次的损失尖峰回滚当成同类冲击加到 48 卡的模型上，重算最优周期与 600 s 处的附加时间比例。实验部分在提交前后分别注入故障，比较恢复位置与需要重做的工作。

参考解答：推导见 10.4.4 节，$L(\tau)=c/\tau+\lambda\tau/2+\lambda r$，$\tau^{*}=\sqrt{2c/\lambda}$。取 $c\approx16.4$ s、$r=120$ s、$\lambda=1/(7.9\times3600)=3.52\times10^{-5}\ \text{s}^{-1}$，三档的附加开销是 6.4%（300 s）、3.8%（900 s）、4.5%（1800 s），与正文表一致；同一组参数下 1024 卡作业的最优间隔落在 965 s 附近，约 16 分钟。式中的 7.9 小时是 Meta 集群统计的作业级 MTBF，折到单卡是 337 天。加上每天一次的共同中断，$\lambda_{\text{daily}}=1/86400=1.16\times10^{-5}$ 与 $\lambda$ 相加，$\tau^{*}$ 缩短到 $\sqrt{2\times16.4/(4.68\times10^{-5})}\approx837$ s。损失尖峰部分见 10.4.5 节的 48 卡算例：$\tau=600$ s 时附加比例从 2.80% 升到 2.87%，最优周期从 4,458 s 降到 3,150 s。保存调用自身也要占时间，CPU 实验里 API 返回约 7 ms、元数据提交约 48 ms，这一小段计入了 $c$。

思路提示：所有「同时影响全作业」的冲击都只是把 $\lambda$ 相加，它们在模型里与硬件故障等价。

**习题 10-7 ・综合设计：RL 各阶段配比与有效样本吞吐**

题干给生成、验证、学习三个阶段 12、6、8 条/s 的处理率和 75% 的样本保留比例，要求比较只把一个阶段能力翻倍的收益；另用生成 40 s、学习 16 s、权重同步 4 s 的周期模型，设每批生成的样本数为同一个常数，算异步执行下保留比例 80% 和 70% 时的有效样本吞吐率，与不丢弃样本的同步执行对比，结果可以表示成每秒处理的 batch 比例。实验部分要求追踪一批样本的标识、奖励、有效损失位置和接收方的权重。

参考解答：基线是 $r_{\text{effective}}=\min(8,\ 0.75\times\min(12,6))=\min(8,4.5)=4.5$。生成翻倍到 24，结果仍是 4.5，等于白加；验证翻倍到 12 得到 $\min(8,\ 0.75\times12)=\min(8,9)=8$，提升约 78%，瓶颈随之转到学习端；学习翻倍到 16，还是 4.5。所以只有翻倍当前瓶颈那一段才有效。异步吞吐以同步为 1：同步周期是 $40+16+4=60$ s，异步稳态是 $\max(40,16)+4=44$ s，于是同步是 $B/60$、异步是 $qB/44$；$q=0.8$ 时 $0.8\times60/44\approx1.091$（约 +9%），$q=0.7$ 时 $0.7\times60/44\approx0.955$（约 −5%）。换算成每秒处理的 batch 比例，同步是 $1/60$ 批/s，异步是 $q/44$ 批/s，异步要划算得跨过 $q>73.3\%$（也就是 11/15）这道门槛。

思路提示：三个阶段各自翻倍时，先判断它是不是 $\min$ 里被选中的那一项，再算。

**习题 10-8 ・分析：路由记录与样本对应关系**

题干设序列含 8K token、模型 48 层、每层为每个 token 选 8 个专家，要求分别算 uint16 和 int32 编码专家 ID 所需的记录容量；把两条序列打包后沿上下文切成四份，描述专家 ID 怎么随 token 重排；再构造一个 token 位置错位的例子，说明训练端会怎样用到错误专家，并设计一个能定位这一错误的检查。

参考解答：uint16 时需要 $8192\times48\times8\times2\ \text{bytes}=6$ MiB，换成 int32 翻倍到 12 MiB。打包把两条序列首尾相接，切分把 token 分到不同 rank，所以每条记录的定位键必须是「样本 + 原始 token 位置 + 层号」，并且跟着 token 一起迁移。位置错位可以照 10.5.4 节那个 0.301 与 0.302 的翻版来构造：第 3 层某个 token 的 ID 被贴到了另一个 token 上，训练端就会拿邻居 token 的专家去做前向，概率和梯度跟着一起错。检查手段是在重排前后对「样本 + 位置 + 层」做校验和比对，或者抽样重放少量 token，验证专家 ID 与分数的一致性。

思路提示：记录容量只跟 token 数、层数、top-k 和字节宽度有关，工程上的难点全在定位键。

**习题 10-9 ・分析：通信、计算效率与输入等待如何影响训练期限**

题干在 48 卡设计案例上做三组退化：PCIe 带宽减半（分预取有效与完全失效两种情况）、单卡计算效率降到 30%、输入等待增到 5 s，各自重算完成时间并判断能否满足期限；再给每卡计算时间加上 5% 标准差的独立波动，求每步的期望耗时并判断是否仍然满足期限；假设三项退化同时发生而额外资源只能把其中一项恢复到原值，比较分别恢复各项时能减少多少关键路径耗时。实验部分要求选一份硬件规格或执行记录，把本章的一个给定输入换成有来源的数值。

参考解答：PCIe 减半而预取有效时每步 52.9 s（10.6.3 节），仍然满足期限；预取完全失效时链路时间从 12.0 s 涨到约 24 s，每步约 $52.2+24+0.5\approx76.7$ s，超过 67.2 s。效率降到 30% 则单卡计算 69.6 s、每步约 70.2 s，同样超期。输入等待增到 5 s 时每步约 $52.2+0.08+5\approx57.3$ s，勉强满足，但 5 s 的余量已经吃掉一大块。$\sigma=5\%$ 的波动下 48 卡对应 58.6 s，小于 67.2 s，仍然满足；作为参照，$N=8/48/1024$ 时步时间超出均值的部分是 $E[\max]-\mu$ 的 1.42、2.23、3.25 倍标准差，$\sigma=2\%$ 时三档每步期望耗时是 54.3、55.1、56.2 s，MegaScale 报告的明显变慢机器约占 0.5%。三项同时退化、只能救一项的话，该救单卡计算效率：它占每步的绝对多数（$52.2/52.8$），恢复它能减掉最多的关键路径时间，这与 10.6.3 节关于 $f$ 的结论一致。

思路提示：判断是否满足期限的标准只有一个，每步有没有超过 67.2 s，或者等价地看完成时间有没有超出 25 天的基础预算。先算每步，再乘迭代数。

**习题 10-10 ・综合设计：满足训练期限需要多少加速器、付出多少成本**

题干对 1T、5T、10T 三个稠密模型用 $6ND$ 算两种数据规模下的训练运算量：一种把训练数据固定为 20T token，另一种让训练 token 数满足 $D=20N$；再按 40% 与 50% 两档 MFU，求各情形下在 90 天和 180 天内完成所需的最少 A100、H100、B200 卡数；用累计 GPU·小时比较两个满足期限的方案，并说明准备时间和恢复参数如何改变结论。实验部分要求选一份标明恢复起点的公开日志，扣除恢复时已经完成的 token 数，算出观察期间新增训练 token 的平均处理速率。

参考解答：$F=6ND$。固定 $D=20\text{T}$ 时，1T 是 $1.2\times10^{26}$ FLOPs，5T 是 $6\times10^{26}$，10T 是 $1.2\times10^{27}$；取 $D=20N$ 时公式变成 $F=120N^2$，1T 是 $1.2\times10^{26}$，5T 是 $3\times10^{27}$，10T 是 $1.2\times10^{28}$，参数涨 5 倍、计算量涨 25 倍。卡数用 $p \ge \lceil 6ND/(P\eta T)\rceil$，其中 $P$ 取各卡的 BF16 稠密峰值，$T$ 取 90 或 180 天，$\eta$ 取 40% 或 50%。这里对 1T 模型、20T token、16,384 张卡给出的天数是 A100 679 天、H100 214 天、B200 94 天（40% MFU），据此能反推出三张卡的 $P$ 再套用；同样是 B200，要在 90 天内训完 1T，40% MFU 下需要 17,147 张，MFU 提到 50% 后降到约 75 天。累计 GPU·小时是 $p$ 乘实际天数再乘 24，用它比较两个满足期限的方案。准备时间与恢复参数分别通过 $T_0$ 与 $L$ 进入公式，准备越久、恢复越频繁，可行域越窄。前面 10-10 的实验部分需要一个带恢复起点的日志样本，SmolLM3 的公开记录正合适：里面有 384、288、192 rank 三个阶段，最后一次恢复运行了 14,000 步，可以拿来算长期速率。

思路提示：先固定数据量口径（固定 20T 还是 $D=20N$），再套 $6ND$；卡数公式里唯一需要外部数据的是各卡的峰值算力 $P$。

**十道题怎么串起来**

十道题的分布是基础 2 题（10-1、10-2）、分析 5 题（10-4、10-5、10-6、10-8、10-9）、综合设计 3 题（10-3、10-7、10-10）。做题顺序建议按容量、时间、恢复、RL、规模走，它们对应的正是正文的五套工具：状态字节数、关键路径、checkpoint 模型、流水线瓶颈、$6ND$ 规模公式。

每题都挂了一句「实验部分」，这是本章的特色，练习不只要算，还要去测量并替换给定输入。10-5 要求用自己存储的实测值换掉 7 GB/s，10-9 要求拿一份硬件规格换掉本章给定值。这跟本章反复出现的那句「逐项数值与独立复算保存在 design-case.json」是同一件事：设计案例本来就按可复算组织，读者的任务是把其中每一项换成自己有出处的数据。

有三组概念容易混。题目里的 30 天、25 天预算，是从期限反推出来的每步上限；正文那个 67.2 s，是本章 48 卡在 25 天基础预算下的具体取值，一个是通式、一个是代入结果。弱扩展的加速上限和强扩展是两回事，只有后者不受梯度噪声尺度限制。GPU·小时和完成时间是两个口径，前者算成本（卡数 × 时间），后者算期限，48 卡通常时间更短而 GPU·小时更多。

十道题说到底只用五个公式：状态字节数、$T_{\text{finish}}$、$L(\tau)$ 与 $\tau^{*}$、$\min(r_l,\ q\min(r_g,r_v))$、$p\ge\lceil 6ND/(P\eta T)\rceil$，而且每题都要求你把给定的输入换成自己测出来的数。

本章的落点可以收成几句。训练内存容量由状态的存储格式、卡间分配方式和生命周期共同决定，ZeRO 减少状态复制、激活重计算减少前向到反向之间要保存的数据、卸载把暂时不用的状态挪到主机内存，三种手段都拿额外的计算或传输换显存空间；每步耗时由数据就绪、资源空闲与依赖链共同决定，估长期完成时间还要补上数据准备、checkpoint 保存与故障重做，而 batch size 能否随卡数放大由临界 batch size 决定、每步由最慢的那张卡决定、损失尖峰的回滚率与硬件故障率一起进保存周期模型，是同步训练绕不开的几件事。RL 在此之上还要跟踪样本标识、策略版本和行为概率，并对齐生成与训练的数值路径。设计案例的收尾是 32 卡 34.3 天、48 卡 24.6 天，以及 48 卡每步 67.2 s 的上限。这一段的出处是这里本章小结。
