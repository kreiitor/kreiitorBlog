可以把 Git 想成一套**给整个工程保存历史版本的系统**，有点像“文档的版本历史”，但它记录的是代码。为了把常见术语和补丁流程一次串清，下面以一道自动化代码修复评测任务为例：

> 一个记账 App 有 bug：点击 `+` 后金额没有增加。有人在平台上提了 **Issue #42**；开发者提交了 **MR !100**，修改代码并增加测试，最后把修改合入主线。

在这个评测任务中，评测脚本会把仓库恢复到提交 **A**，把 Issue 描述交给 Agent 让它自行修复，再用隐藏测试集验证结果。**M 是参考修复，不要求 Agent 写出与 M 完全相同的代码。**

## 核心术语对照

| 名词                      | 通俗解释                                 | 在例子中                          |
| ----------------------- | ------------------------------------ | ----------------------------- |
| **仓库（repository/repo）** | 工程文件加上它们的版本历史，相当于“项目文件夹 + 历史记录”。      | 记账 App 的整个工程。                 |
| **提交（commit）**          | 一次保存的版本快照。                           | A、B、C、M、H 都是提交。               |
| **SHA**                 | 每个提交的独特“长编号”，用来准确找到它；界面常只显示前几位。      | 即使两个提交都叫“修复按钮”，它们的完整 SHA 也不同。 |
| **分支（branch）**          | 从某个版本出发，另走一条修改路线。                    | B、C 是开发者在修复分支上的工作。            |
| **合并（merge）**           | 把分支上的修改接回主线。                         | M 是这次合并形成的提交。                 |
| **父提交（parent）**         | 某个提交直接接在哪个旧版本之后。合并提交通常有两个父提交。        | M 的第一父提交是主线的 A；另一边来自修复分支 C。   |
| **基线（base）**            | 出题时交给 Agent 的**修复前版本**。              | A。                            |
| **修复后版本（post）**         | 用作参考修复的版本。                           | M。                            |
| **固定提交（pin）**           | 给仓库历史划一条固定终点，以后主线又有新提交，也不悄悄改变本次扫描范围。 | 假设登记时固定在 H，就只看 H 及以前的历史。      |

**Issue** 和 **PR/MR** 容易混淆：Issue 是“提出了什么问题”，PR/MR（合并请求）是“有人建议怎样修改代码”。它们是代码托管平台上的记录，**不等于 Git 提交**。一个 Issue 可以涉及多个合并请求；请求编号 `!100` 也只在所属仓库和序号体系中有意义。因此在整理候选任务时，应当用“仓库身份 + 完整合并提交 SHA”作唯一标识，而不能只写裸 `!100`——就像不能只凭“学号 100”认定两所不同学校的学生是同一个人。

## “差异”和“补丁”是什么

**diff（差异）** 就是比较两个版本，列出“删了哪些行、加了哪些行”。例如 A 中是：

```text
amount = amount
```

M 中变为：

```text
amount = amount + 1
```

**patch（补丁）** 是把这种差异保存成一个可应用的文件。在自动化代码修复评测里，通常需要区分三份材料：

- **代码修复补丁（solution patch）**：`A → M` 中除测试之外的生产代码改动，是*参考答案*，不交给作答 Agent。
- **`tests.patch`**：给 A 和 M 都装上同一套判卷测试，是*隐藏考卷*，也不交给作答 Agent。
- **`problem.md`**：描述“点击 `+` 后金额应增加”等需求的*公开题面*。

“补丁能应用到 A”只说明“测试文件能顺利打上”，**不代表测试本身有效**。还必须实际运行验证：针对该 bug 的 **Fail-to-Pass（F2P）** 用例在 A 失败、在 M 通过；用于防止回归的 **Pass-to-Pass（P2P）** 用例在 A 和 M 都通过。

最后两个常见但容易漏扫描的合入方式：**squash merge** 是把分支上的多次提交压缩成一次提交再接入主线；**快进合并（fast-forward）** 则是直接把主线指针挪到分支末端。这两种方式都**不会产生有两个父提交的合并提交 M**，如果任务筛选脚本只扫描普通合并提交，就会漏掉它们；因此有必要保留“从已关闭 Issue 反向追踪关联提交”作为补充召回路径。
