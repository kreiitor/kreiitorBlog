可以把 Git 想成一套**给整个工程保存历史版本的系统**，有点像“文档的版本历史”，但它记录的是代码。先用一道虚构的题串起来看：

> 一个记账 App 有 bug：点“＋”后金额没有增加。有人在平台上提了 **Issue #42**；开发者提交了 **MR !100**，修改代码并增加测试，最后把修改合入主线。

```
主线：  A（有 bug）──────── M（合并修复）──── H（仓库后来的版本）
          \              /
修复分支：  B（改代码）─ C（加测试）
```

对这道评测题，我们希望把仓库恢复到 **A**，把 Issue 描述交给 Agent，让它自己修；然后用测试判断结果。**M 是参考修复，不要求 Agent 写出与 M 一模一样的代码。**

## 这些词各是什么意思

| 名词                      | 通俗解释                                 | 在例子中                          |
| ----------------------- | ------------------------------------ | ----------------------------- |
| **仓库（repository/repo）** | 工程文件加上它们的版本历史，相当于“项目文件夹＋历史记录”。       | 记账 App 的整个工程。                 |
| **提交（commit）**          | 一次保存的版本快照。                           | A、B、C、M、H 都是提交。               |
| **SHA**                 | 每个提交的独特“长编号”，用来准确找到它；界面常只显示前几位。      | 即使两个提交都叫“修复按钮”，它们的完整 SHA 也不同。 |
| **分支（branch）**          | 从某个版本出发，另走一条修改路线。                    | B、C 是开发者在修复分支上的工作。            |
| **合并（merge）**           | 把分支上的修改接回主线。                         | M 是这次合并形成的提交。                 |
| **父提交（parent）**         | 某个提交直接接在哪个旧版本之后。合并提交通常有两个父提交。        | M 的第一父提交是主线的 A；另一边来自修复分支 C。   |
| **基线（base）**            | 出题时交给 Agent 的**修复前版本**。              | A。                            |
| **修复后版本（post）**         | 用作参考修复的版本。                           | M。                            |
| **固定提交（pin）**           | 给仓库历史划一条固定终点，以后主线又有新提交，也不悄悄改变本次扫描范围。 | 假设登记时固定在 H，就只看 H 及以前的历史。      |

**Issue** 和 **PR/MR** 容易混淆：Issue 是“提出了什么问题”，PR/MR（合并请求）是“有人建议怎样修改代码”。它们是代码托管平台上的记录，**不等于 Git 提交**。一个 Issue 可以涉及多个请求；请求编号 `!100` 也只在其所属仓库和编号序列中才有意义。因此候选应当用“仓库身份＋完整合并提交 SHA”来标识，而不用裸 `!100`——就像不能只凭“学号 100”认定两个不同学校的学生是同一个人。

## “差异”和“补丁”是什么

**diff（差异）** 就是比较两个版本，列出“删了哪些行、加了哪些行”。例如 A 中是：

```
amount = amount
```

M 中变为：

```
amount = amount + 1
```

**patch（补丁）** 是把这种差异保存成一个可应用的文件。这类任务里要把它们分开：

- **产品补丁**：A→M 的修复代码，是*参考答案* ，不交给作答 Agent。
- **`tests.patch`**：给 A 和 M 都装上同一套判卷测试，是*私有考卷*，也不交给作答 Agent。
- **`problem.md`**：描述“点＋后金额应增加”等要求，是*公开题面*。

“补丁能应用到 A”只相当于“试卷能装进考场”，**不表示测试有效**。还得实际运行：针对 bug 的 **F2P** 用例在 A 失败、M 通过；防止破坏旧功能的 **P2P** 用例在 A 和 M 都通过。这些结果应当来自实际运行验证。

最后两个较少见的词：**squash** 是把分支上的多次提交压成一次再接入主线；**快进合并**是直接把主线指向分支末端。这两种方式可能**没有 M 这样的合并提交**，所以只扫描合并提交的发现脚本会漏掉它们。这也是“从 Issue 往回查修复”值得保留为补漏路线的原因。
