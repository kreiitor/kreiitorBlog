## 本章地图

这一部分回答的是"这份材料为什么存在、写给谁、怎么用"。这一部分的讨论范围围绕一个核心公式展开，后面十章都在这个框架里填入具体设计。真正要带走的东西只有一件，就是那个核心公式 Agent = LLM + 上下文 + 工具，后面十章都在往这个框架里填肉。除了公式，引言还给了一张十章的结构地图、三条按读者身份划分的阅读路径与实验使用说明、以及必需和推荐两档前置知识。它在全书的位置可以看成第 0 层，不教具体技术，只给统一的概念框架（LLM／上下文／工具，以及它们在强化学习里的对应物 Policy／Observation Space／Action Space）、一条判断标准（实践在前，命名在后），还有入门的门槛。

## 引言内容

2025 年 8 月到 10 月，在图灵《AI Agent 实战营》里讲了一系列课。课程追的问题是：怎么用可解释、可验证、可复用的工程原则去设计 AI Agent，不靠经验和直觉反复试错。所以课程不打算停在"能跑通一个演示系统"，还要往下问一句为什么这个架构是这样，以及每个设计决策换来了什么、又放弃了什么。换来什么、放弃什么，这是工程取舍；做到什么程度还行、什么条件下会失灵，这是能力边界。读后面每一章时都可以拿这两问自查，比如讲到上下文压缩，你该能说出压掉的是什么、换回来的是什么。这份材料就是在这批讲义和配套实验的基础上，重新整理、补充、拆解出来的。

顺便说一句，这份材料的写法本身也是一次人机协作实践。从最初的构思到定稿，主要用 **whisper coding**（口述式协作），跟 Pine 的语音 Agent 一起整理资料、迭代文本。备课时先口述提纲，让 Agent 去调研相关工作、形成草稿；课上完再结合学员反馈，把论证、案例和实验反复核查、修订。语音把"把想法变成文字"这件事的成本压了下来，"提问—检索—成稿—复核"这一圈也转得更快。所以这份材料不光在讲 Agent，还顺手记录了一种 Agent 深度参与的知识生产方式。

2025 年初 DeepSeek R1 发布之后，研究和产业的重心从基座模型能力往 Agent 的系统化落地上挪。模型侧出现的是**智能体强化学习**（Agentic Reinforcement Learning），它把工具调用和环境交互的能力内化进模型参数，于是模型在编程、数学推理、图形界面操作（computer use）这些地方显得更能通用了。产品侧则是 Manus、Claude Code、OpenClaw 这类通用 Agent 把人机交互的方式改了一遍，也让"代码生成 + 文件系统"成了一种重要的系统架构范式。

再回头看课程里总结的那些架构原则，模型和产品迭代得很快，这些原则的解释力却一直没掉。业界后来流行的 Skill、harness、loop engineering 这些词，对应的工程实践往往出现得更早。概念是对大量实践经验的归纳，它落在实践后面。说白了，实践在前，命名在后。

这批原则主要来自长流程、高风险的工程实践。Pine AI 团队把 Pine 做出来，让 Agent 能代表用户去跟真人打交道，处理账单协商、退款投诉、订阅取消这类牵扯真实经济利益的活。这类任务拖得久、来回好几轮，中间任何一步出错都可能造成实际损失；可靠性、安全性、可审计性上的要求一严，这套架构原则就被逼出来了。下面几个例子都出自这段实践。

在 Skill 这个概念流行之前，Pine 团队已经在用动态加载提示词的办法对付提示词无限膨胀，用命令行执行工具的办法对付工具列表无限膨胀，用系统状态栏的技术让 Agent 感知到执行环境和用户的时间、工作状态。在 harness 流行之前，他们已经在用类似 Claude Code 的做法处理模型工具调用不稳、产生幻觉、执行危险或越权操作、不遵循指令这些问题。在 loop engineering 流行之前，**提议者-审核者**（proposer-reviewer）这套方法已经在用了，专门对付模型过早认为任务完成。

这些方法并非 Pine 独有。很多模型和 Agent 团队在解决相似问题时都独立摸出了相近的工程方法，这种趋同恰恰说明它们反映的是 Agent 系统的共性约束。

2025 年，这门课在图灵开设《AI Agent 实战营》，2024 到 2026 年又持续在中国科学院大学讲授 AI Agent 实践课程。这里选择开源发布，也是希望这些可复用的知识和经验能给更多研究者和工程实践者用上。

对企业级 Agent 开发来说，"实践在前，命名在后"还有一层现实含义：实践不能一直落在概念普及的后面。等某个术语变成行业共识的时候，它对应的问题往往已经在领先系统里被摸索很久了。想更早识别并解决这些问题，要满足两个条件。

头一个条件是挑一个对 Agent 能力上限要求足够高的真实业务，并且持续拿真实反馈。拿 Pine 打比方，一项任务可能持续数小时乃至数周，中间要跟多个利益相关方反复沟通，长时间通话、复杂表单操作、多轮邮件往来都得做，同时还得保证关键数字准确、操作可控、始终维护用户利益。场景够复杂，模型能力和业务要求之间的差距才会不断暴露出来，团队也才会去做 harness，系统性地解决那些模型暂时做不了、业务又必须完成的事。反过来看，如果业务需求很容易被下一次模型升级覆盖掉，团队就很难沉淀出稳定的系统设计原则。

另一个条件是建立系统的评估（Evaluation）机制。没有评估，一次改动带来的提升到底来自设计本身还是随机波动，根本分不清。评估把 Agent 的迭代从经验判断变成可比较、可复现的工程过程，这是用科学方法做系统开发的基础，第七章专门讲这套方法。两个条件合起来其实就是一个能自我改进的闭环：有难度才有信息量，有评估才知道有没有变好。把评估放在第七章，图 0-1 里又单独标了一句"评估贯穿全局"，意思是评估不属于哪个模块，它是所有模块迭代的前提。

不管底层模型怎么升级、产品形态怎么翻新，几乎所有成功的 Agent 系统都遵循着相同的架构模式。这不太可能只是巧合。好的设计原则本来就该穿越模型的迭代周期，它们描述的是智能系统与世界交互的基本模式，跟某个具体模型的用法没多大关系。

图灵奖得主、强化学习之父 Richard Sutton 说过，宇宙演化走了四个阶段：从尘埃到恒星，从恒星到生命，从生命到智能体（用的是"设计实体"，designed entities）。生物进化是盲目的，随机变异、自然选择，大多数生物并不理解自己怎么运作，也没法自主设计和改造自己。Agent 是演化史上一个全新的存在，它能通过生成代码实现自举（bootstrap）和自我进化，像一个程序员写出另一个程序员，新的程序员接着再写下一个。也就是说，Agent 能理解自身的运作机制，能按目标造出全新的智能体，甚至改进自己。这份材料想帮读者掌握的，就是这种创造的原则。

这里要分清一件事。所谓"自我进化"，是转述 Sutton 观点之后对 Agent 性质的一个主张，不是这里要交付的某个具体功能。真正落到工程上的那条线是代码生成，它之所以重要，除了能写程序这一点，更在于系统由此获得了改造自己、造出新 Agent 的能力，这条线到第五章展开。

全书的核心公式只有一句话：

$$
\text{Agent} = \text{LLM} + \text{上下文} + \text{工具}
$$

三者缺一不可。LLM 是大语言模型，上下文是模型能感知到的全部信息，工具是 Agent 可调用的外部能力。这里写的是加号，所以这三样是并列相加的关系，缺任何一项都不构成完整的 Agent。

这个加号容易被误读成"能力相乘"，其实它描述的是组成关系。工程上更实用的用法是把它当排查清单：Agent 表现不好时，先分清是大脑不行（模型能力不够）、眼睛不行（上下文缺信息或者被噪声挤满），还是手脚不行（工具缺失或者描述不清），再决定改哪一层。这三层的改动成本差得很远，换模型最贵，改上下文最便宜也最见效，加工具则要一并考虑安全和维护成本。

换成更直观的说法，就是大脑 + 眼睛 + 手脚。大脑（LLM）负责思考和决策，眼睛（上下文）决定 Agent 能看到什么，手脚（工具）决定 Agent 能做什么。这里主动给类比打了个折扣：严格说，眼睛只是个粗略的说法。

之所以要打折，是因为类比很容易让人以为上下文就是"环境信息 + 对话历史"。还要补一句：工具定义也在上下文里。这一点在工程上很要紧：工具不是外挂，它的名字、描述、参数 schema 都要写进模型能看到的地方，于是"工具设计"和"上下文设计"是耦合的。工具描述写得好不好，直接决定模型会不会用、用对没有；工具一多，上下文又会被工具定义撑爆，也就是前面说的"工具列表无限膨胀"。图 0-1 把工具标成"手脚"，同时在上下文那一栏里列出"指令 · 记忆 · 知识 · 轨迹"，暗示的就是这个重叠关系。

对熟悉强化学习的读者，这三者还能映射到 RL 的形式化语言里。

$$
(\text{LLM},\ \text{上下文},\ \text{工具}) \;\longleftrightarrow\; (\text{Policy},\ \text{Observation Space},\ \text{Action Space})
$$

LLM 对应 Policy（策略），上下文对应 Observation Space（观察空间），工具对应 Action Space（动作空间）。这里的结论是三种说法对应同一个对象，只是表达层次不同：实现层说"LLM + 上下文 + 工具"，直觉层说"大脑 + 眼睛 + 手脚"，学术层说"策略 + 观察空间 + 动作空间"。

把这三层当成三种沟通场景的坐标，用起来就顺了。写代码、读源码时用实现层的说法，因为它对应具体的 API 消息和函数调用；向非技术同事解释时用直觉层的说法；读论文尤其是 RL 论文时用学术层的说法。混着用会出事，比如拿 RL 的"观察空间"去讨论 prompt 里该不该放工具定义，两边会各说各话。

"实践在前，命名在后"这句话容易读歪，它并不是说术语没用。它反对的是把术语当成实践的起点、为术语而术语；术语本身是对经验的归纳，对交流有帮助。真正的坑是只记住名字，说不出它挡的是哪个具体的坑。学的时候把问题当起点，看到一个新名词先问它解决什么、不解决会怎样，往往会发现它只是某个早就存在的工程需求的重新命名。

Pine 那几条对应关系也值得单独记一下顺序：动态加载提示词、命令行执行工具、系统状态栏对应后来的 Skill 类做法，类 Claude Code 的方法对应 harness，提议者-审核者对应 loop engineering。做法在先，名字在后。

逐章看下去，第一部分的顺序和核心公式的三件套基本对齐。第 1 章从多个真实的 Agent 产品出发建立直观理解，把核心公式从实现层讲到直觉层、学术层，再用实验剖析 **ReAct 循环**，也就是"思考→行动→观察"的迭代过程，并区分任务内的上下文适应、跨任务的外部产物（artifact）更新和训练周期中的参数更新，末尾讨论从工作流到自主 Agent 的编排设计模式。

第 2 章讲上下文工程，是明确说的全书最关键的一章。它先从 API 消息结构和 Agent 核心循环讲起，为"上下文就是消息列表"这个认识打底，再往 KV Cache（大模型推理过程中复用历史计算结果的机制）的底层原理走，然后依次展开提示工程（Prompt Engineering，含流程化设计、工具描述、业务规则细化）与提示注入（Prompt Injection）攻防、Agent Skills 的按需加载机制、Agent 状态栏技术，以及上下文压缩（Context Compression）策略。

没有把"最关键"展开成论证，不过线索是清楚的。上下文就是 Agent 的"眼睛"，眼睛决定模型能感知到什么，而感知不到的东西模型一定做不好；这一章又把"上下文就是消息列表"这个认识打底，后面的记忆、知识库、压缩、缓存优化全要站在它上面。KV Cache 那条常被忽略，弄懂之后你会明白上下文的写法（消息顺序、前缀稳定性）影响的是成本，不只是效果。

第 3 章把上下文管理延伸到跨会话的持久化知识体系，让 Agent 记住当前对话之余，还能在多次对话之间积累和调用知识。跟第 2 章的分工很干脆，一个管"这一轮"，一个管"很多轮"。章里排了三层递进的东西：用户记忆的四种渐进式策略管"记住你"，RAG（检索增强生成，先检索相关文档再让模型生成回答）的技术栈管"查资料"，**Agentic RAG** 则是让 Agent 自主决定何时检索、检索什么。

前两层是给定输入就执行的固定管线，Agentic RAG 把决定权交回模型手里。这一章还覆盖不同的文本搜索方法与搜索结果排序优化、更高级的知识组织方法，以及多模态记忆的前沿探索。

第 4 章讲 Agent 与外部世界交互的桥梁，也就是工具：MCP（Model Context Protocol）工具互操作标准、五类工具的设计原则（感知、执行、协作、事件触发、用户沟通）、多模态感知的三条技术路线（原生多模态处理、提取为文本、工具化多模态分析），以及执行工具的安全机制。这里有个分工要记清楚，事件触发、用户沟通与异步运行时放到第六章展开。

第 5 章换了个更高的视角，它要论证 Coding Agent 加文件系统是所有通用 Agent 最核心的技术基础。主线是 OpenClaw 架构，讲 Coding Agent 的工作流程和实现技巧，再展示代码生成在编程之外的价值，从辅助思考、构建知识库，到动态创造新工具和 Agent 自举。所以第 4 章讲工具怎么设计，第 5 章讲怎么用代码和文件系统把工具的边界打开。

（第 5 章的章名有两处写法：图 0-2 写"第 5 章　Coding Agent"，另一处写"第五章（Coding Agent 与通用 Agent）"，指同一章，笔记两处都按原样保留。）

第 6 章从模态与时序两个维度看 Agent 与环境的交互。模态这一维回答交换什么形态的信息，从文本到语音、到图形界面、再到物理动作；时序那一维回答什么时候交换，从同步的请求响应，到异步事件驱动，再到实时语音。异步与事件驱动让 Agent 能持续接收外部事件并及时响应，语音交互把感知、推理与生成推进到实时尺度，Computer Use 把动作空间扩展到图形界面，机器人操作再延伸到物理环境。四类场景其实就是这两维上的四个点，所以能共享同一批系统原语：唤醒、安全点、取消、抢占与快慢路径分离。先记一个直觉就够，只要 Agent 要跟物理时间打交道，就得能被打断、能被叫醒、能中途刹车。

第二部分四章各自对应一个能力扩张的层级，这是本节最值得背下来的结构信息。第 7 章评估是前提，它建立可度量的反馈，本身不提升能力，但没有它后面三章都无从判断。第 8 章后训练动的是模型参数，能力被内化进权重；第 9 章持续进化动的是单体系统，改的是 Prompt／Skills／Harness／知识文档这些参数之外的东西；第 10 章多 Agent 协作动的是群体系统。从内到外就是参数、单体系统、群体系统。第 7 章不归在这三个层次里，它是三层共同的前提。

这里容易搅混的是"第一部分／第二部分"和"三个层次"。两大部分是书的编排顺序，先构建、后提升；三个层次是第二部分内部的递进关系。另外"一至六章＝构建"也不意味着后半部分不需要构建，第 7 到第 10 章都是在已经搭好的系统上做提升，评估、后训练、持续进化、协作最终都要落到同一套架构上。

第 7 章讲评估方法论，覆盖评估环境（工具调用型和人机交互型两种核心范式，以及章末单独讨论的仿真环境）、数据集的设计原则、**LLM-as-a-Judge** 自动化评判方法、评估驱动的模型选型，以及把评估结果转化为系统改进的完整闭环。仿真环境被放到章末单独讨论，说明在这里的评估体系里它是补充手段，两种核心范式才是主干。

第 8 章讲 **SFT（监督微调，用标注数据教模型"照样学样"）与 RL**（强化学习，让模型通过试错和奖励反馈自主提升）。两个核心论点建议现在就背下来。一个是"SFT 记忆、RL 泛化"，SFT 让模型记住示范，RL 让模型学会泛化到没见过的情形；另一个是"数据与环境比算法更重要"，算法不再是瓶颈，数据和环境的质量才是。这一章还覆盖预训练／SFT／RL 三阶段全景、经典 RL 理论、奖励信号设计（从二元奖励到过程奖励，再到"奖励结果、约束过程"的验证路径惩罚）、单轮与多轮强化学习算法，以及样本效率优化。

第 9 章研究怎么把 Agent 的运行经验转成下一版本的能力。章里先建立由环境结果、过程规则和 LLM Rubric 组成的学习信号，再比较四种更新载体：知识文档、Prompt 与 Skills、程序与 Harness、模型参数。这四种载体可以按"改动成本从低到高、需要的数据量从少到多"排个序，能用文档解决的别改 Prompt，能用 Prompt 解决的别改代码，能用代码解决的别去动参数。后半段的验证、灰度发布、回滚与长期整理说的是进化本身要按发布流程来管，不能悄悄改了就上线。

第 10 章从单体能力扩到系统级协同，讲多个 Agent 怎么分工合作，给出多 Agent 协作的分类框架：上下文共享／独立 × 对等／管理者／去中心化。这是一张二维表，先问多个 Agent 看不看得到同一份上下文，再问它们之间的权力关系是平级、有老板，还是没人管。后面的翻译 Agent、电话与电脑协同 Agent 这些案例，都可以先放进这张表里定位。章里还讨论了 Agent 社会和 Agent 经济的方向。

这一节是全书唯一的"索引页"，读法应当是先记骨架、再当字典用。第一部分里，第 1 章给框架，第 2、3 章管"眼睛"（上下文、记忆与知识），第 4、5 章管"手脚"（工具、代码生成），第 6 章扩观察与动作空间。这个内外结构与核心公式的三件套正好对齐，也是图 0-1 把十章挂到三个部件上的原因。

引言给的是地图与公式，真正的展开从第一章开始。第一章"为后续章节建立统一的概念框架"，所以只读引言的话，请务必把"三层说法"和"三种更新（上下文适应／artifact 更新／参数更新）"这两组词带走，它们是后面很多章的公共语言。

## 如何阅读这份材料

各章节相对独立，你可以按自己的需求挑阅读路径走。按读者身份给了三条。

如果你是 Agent 开发者，建议按顺序读完全书：第一至六章建立完整的 Agent 构建方法，第七至十章从评估、模型后训练、持续进化和多 Agent 协作四个方向讨论能力提升。时间有限的话优先读第一章和第二章，第一章建立全局认知，第二章是标注的"全书最关键的一章"。第二章里 **KV Cache** 的底层原理偏技术化，初次阅读可以先跳过原理部分，只记住开头给出的三条核心结论，不影响后面理解。如果关注模型训练，可以直接看第八章，但评估方法（第七章）是训练的前提，建议一并读，另外先读第一、二章建立整体认知。

各章独立，是因为全书有一根共同的轴，就是引言那个公式 LLM／上下文／工具。第 2、3 章落在"上下文"上，第 4、5 章落在"工具"上，第 6 章扩展观察与动作空间，第 7 至 10 章在这套架构上做提升。跳读的代价只是失去章节之间的引用链，所以跳的时候至少把第一章读掉，它是唯一提供统一术语的地方，否则后面几章会冒出没定义的词。

"时间有限就先读第一、二章"这条路径值得多说两句。第二章讲的是怎么写好上下文，这恰好是投入产出比最高的一层：不动模型权重、不改系统架构，只改消息列表就能拿到明显提升。这两章合起来算是最小可用知识集。

至于 KV Cache 该跳还是该读，给的办法是初次阅读只看开头那三条核心结论。三条结论属于结论层的知识，先拿去用；底层原理是"为什么是这样"的推导，用来解释结论的边界。跳过原理不会让你用错，但当你的场景偏离了那三条结论的前提时，就得回来补原理。那三条具体是什么，引言没列，要到第二章这里找。

每章都有大量实验和思考题，编号格式是"**实验X-Y**"，X 是章节号，Y 是章节内的序号。标题里用 ★–★★★ 标难度：★ 是入门级，适合所有读者；★★ 是中等难度，需要一定的工程实践基础；★★★ 是进阶挑战，通常涉及开放性问题或复杂的系统设计。星级不光是难度提示，它是给人做时间预算用的。★ 的实验照着做就能跑通，用来建立手感；★★ 通常要自己配环境、调依赖；★★★ 大概率没有唯一正确答案。挑实验时按"我现在有多少时间 + 我想练什么"来选，别按顺序从头刷到尾。

大部分实验配有完整的可运行代码，放在配套的开源仓库里：

- 配套代码仓库：`https://github.com/bojieli/ai-agent-book`
- 用 Git 获取全部配套代码：

  ```bash
  git clone https://github.com/bojieli/ai-agent-book.git
  cd ai-agent-book
  ```

不熟悉 Git 的话，也可以在仓库页面点 Code → Download ZIP。两者有区别，ZIP 拿到的是某一时刻的快照，clone 可以用 Git 拉更新。

代码按章节组织在 `chapter1/` 到 `chapter10/` 里。找"实验X-Y"要先打开对应的 `chapterX/README.md`，按实验编号找到项目目录，再按项目自己的 README 装依赖、跑起来。这两级 README 的分工值得留意：章节 README 是索引，告诉你编号对应哪个目录；项目 README 是操作手册，写依赖、命令、参数。很多人卡住，问题就出在跳过了第二级 README 里的依赖安装步骤，实验本身其实不难。标为"复现指南"的实验依赖外部仓库，这类最花时间，建议提前确认外部仓库还在不在。

顺带说一句，"实验"和"思考题"共用同一套编号和星级，区别在实验是动手做的、多数有配套代码，思考题是开放性的，★★★ 尤其如此。另外"先读第一至二章"在两条路径里都出现，理由不一样：时间有限那条是因为这两章覆盖最小可用知识，关注训练那条是为了先建立整体认知再进第八章。

在结尾强烈建议动手跑一遍这些实验。AI Agent 是个实践性极强的领域，很多设计上的直觉要在动手调试的过程里才能真正建立起来。这里说的直觉，指的是你能预判某个设计改动大概会带来什么效果，这种预判只能从"我改过、我看到过结果"里长出来，读书读不出来。这这里的作用是降低你跑实验时的理解成本，它替代不了实验。

## 前置知识

这里面向有一定技术背景的读者，但不要求你是某个特定领域的专家。把前置知识分成必需和推荐两档，方便你评估自己的准备程度。必需项缺了会读不动或者跑不动实验，推荐项缺了只是在某些章读得吃力，两档的分界线就在这里。

必需的第一项是 Python 编程。这里几乎所有实验都基于 Python，你需要熟悉基本语法、常用数据结构、包管理（`pip`）这些概念。标准是能读懂和修改中等复杂度的 Python 代码，不要求精通。第二项是 LLM 的基本使用经验，用过 ChatGPT、Claude 或类似产品，理解"提示词（Prompt）→ 模型回复"这个基本交互模式就够了。

第三项是一款 AI 辅助编程工具，建议安装并熟悉至少一款，比如 Claude Code、Codex、Cursor、TRAE。这里给了两方面理由。一条是实用层面的，实验涉及大量代码编写和调试，这些工具能显著提高开发效率。另一条在认知层面：这些编程工具本身就是成熟的 Coding Agent，你在用的过程中会直观体验到 ReAct 循环、工具调用、上下文管理这些这里反复讨论的机制，这种第一手体验对理解 Agent 的设计原则极有价值。

一般技术书不会把"装某个工具"写成前置知识，这条要求确实特别。你用它的时候会亲身经历"它要不要调用工具、上下文满了会怎样、它为什么跳过了某条指令"，这些正是第二至六章要讲的东西。使用 Coding Agent 的经验，差不多就是这里最好的实验材料。

第四项是软件工程常识，命令行操作、Git 版本控制、JSON 数据格式、REST API 这些基本概念要熟，它们是运行实验和理解 Agent 工具调用机制的基础。把必需的四项摆在一起看，会发现它们对应 Agent 工程的四类日常动作：写代码（Python）、当用户（LLM 基本使用）、用工具（AI 辅助编程工具）、跑工程（命令行／Git／JSON／REST API）。其中跑工程那一项最容易被低估。Agent 的工具调用是调 API、拼 JSON、读命令行输出，你如果不熟这些格式，就很难判断模型生成的调用参数错在哪。

推荐的四项按章节对号入座。机器学习基础对应第八章，了解训练与推理、损失函数、梯度下降、过拟合这些概念，有助于理解模型后训练。基础数学对应第 2-3、8 章（这里写作"第 2-3、8 章"，指第 2 章、第 3 章和第 8 章），对线性代数有直观理解，比如知道向量可以表示方向和大小、矩阵可以做批量运算，有助于理解嵌入和注意力机制；基本的概率统计知识则有助于理解评估指标和强化学习里的期望奖励。这里的数学不涉及复杂推导，侧重直观解释。

Web 开发基础对应第 6 章，了解 HTTP、WebSocket、前后端分离架构，有助于理解事件驱动的异步 Agent 架构和语音 Agent 的实时通信实验。对 Transformer 架构的基本了解对应第 2、8 章。Transformer 是当前几乎所有大语言模型的底层架构，对于想系统补充大模型基础知识的读者，推荐《图解大模型》（图灵出版），那用直观的图解方式讲 Transformer 架构、预训练与微调等核心概念，跟这里的 Agent 工程视角形成互补。

这几组范围容易记混，拢一下：机器学习基础是第 8 章，基础数学是第 2-3、8 章，Transformer 是第 2、8 章，Web 是第 6 章。

Transformer 那条推荐其实是给零基础读者留的一条后路。这里先承认 Transformer 是当前几乎所有大语言模型的底层架构，再承认有人需要系统补充，于是推荐了《图解大模型》。这里假设你大概知道 Transformer 是什么，但不打算教你；如果连"注意力机制在算什么"都没概念，第 2 章（嵌入、注意力、KV Cache）和第 8 章（预训练／SFT／RL）会比较吃力。

> 检索确认：《图解大模型》确实存在，国内图书馆书目信息中其完整书名为《图解大模型：生成式AI原理与实战》。（来源：[中国人民大学图书馆书目检索](https://vstudy.ruc.edu.cn/mystudy/search/detail/m23c09666f4b1b005509c5f397b4c14ad)）

"除第八章后训练以外，全书对数学和机器学习的要求很低"这句话有信息量。它在告诉你，这把难度放在系统设计上，数学推导不是重点，第 8 章是唯一例外，因为它讲 SFT／RL。对应的读法是：第 2、3 章遇到向量、注意力这样的词，只需要"知道它在干什么"的直观理解就够了；如果你准备认真读第八章，再补损失函数、梯度下降、期望奖励这些基础。

在这里给了一句宽慰，前置知识有欠缺不必因此却步。这里的核心价值在架构设计原则和工程实践的方法论，不在某个具体的算法或技巧；除第八章后训练以外，全书对数学和机器学习的要求很低，完全可以作为起点。

结语那两句话可以当成全书的阅读心态设定。Agent 技术还在快速演进，但好的架构设计原则具有穿越时间的力量；掌握了"为什么要这样设计"，你就能在技术浪潮的变化中保持清醒的判断力。这跟引言这里的"实践在前，命名在后"说的是同一件事，要学的是"为什么这样设计"，至于当下哪个模型、哪个库怎么用，反倒次要。你遇到具体产品的参数、具体模型的版本号，可以放心把它们当例子看待，不必当知识点背。
