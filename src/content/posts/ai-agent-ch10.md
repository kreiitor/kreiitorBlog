前九章回答的都是「如何构建和改进一个 Agent」：搭上下文、接知识、装工具、做评估、后训练、持续进化。这一章把问题整体上移一层，问的是如何组织多个 Agent，让它们通过分工、通信与相互验证，完成单个 Agent 难以承担的任务。它给出的坐标系是两条轴：多 Agent 系统该怎么分类（10.1），以及多 Agent 到底什么时候比单 Agent 强、什么时候纯属浪费 token（10.2）。往下走，共享上下文与不共享上下文这两种架构各自怎么落地，分别落在 10.3 和 10.4；后者先铺基础设施（10.4.1 文件系统是数据平面，10.4.2 通信与控制是控制平面），再按拓扑轴展开对等协作、管理者模式与去中心化三种架构，跨出组织边界之后还有 A2A 协议（10.4.6）。10.5 汇总多 Agent 引入的失败模式，是一份反向清单；10.6 把视野从任务协作扩展到 Agent 社会，用六个案例分社交涌现、经济涌现、策略博弈三个维度收尾；10.7 收束全章。

它在整体中的位置也值得说一句。上一章讲的是单个 Agent 如何靠经验学习与持续进化变强，这一章把视角从个体推到群体。它大量复用前面的成果：第一章定义的轨迹（trajectory）是本章「共享上下文」的基础，第二章的上下文压缩对应灵台的「凝蜕」，第四章的子 Agent 返回结构化摘要、`list_agents` 等原语构成控制平面，第五章的提议者-审核者范式是对等协作的样板，第六章的 Computer Use 与事件驱动中断机制是实验 10-3、10-4 的前置技术，第九章的经验学习则与 Agentopia 的「模拟社会经验训练模型」呼应。

读完这一章，手上应该多了几件可用的东西：拿到一个多 Agent 需求，能先用「是否引入新信息」这条判据决定该不该做；能画出系统的两条轴，并说清选了哪种通信机制、谁来当控制平面；能识别并预防六类典型失败模式，至少知道怎么给共享文件系统加乐观锁、给共享资源加锁与配额；能看懂 MetaGPT、AutoGen、Swarm 这几个开源框架真实的控制流结构，不被「Agent Swarm」这类市场名词带偏；也知道 Agent 社会类研究看的是社交、经济、策略三个维度，各自用什么量化指标。

## 10.1 多 Agent 协作的分类框架

这一节对应。要构建多 Agent 系统，得先理解两个核心设计维度，它们共同决定了系统的基本架构和实现方式：维度一是上下文是否共享（10.1.1），维度二是协作拓扑（10.1.2）。这里把这两个维度称为「最基础的架构决策」，措辞值得留意。维度一不是可有可无的风格选择，它会一路影响到后面的所有具体机制：文件名怎么定、锁加在哪里、消息信封长什么样、终止信号怎么传。

把这两条轴放在一起，就是一张二维坐标系。横轴问「记忆怎么存」，共享还是隔离；纵轴问「指挥权怎么走」，对等、中心还是无中心。任何一个具体的多 Agent 系统都能在这张图上找到位置：10.4.4 的书籍翻译系统是「上下文隔离 + 管理者模式」，10.4.3.2 的提议者-审核者循环是「上下文隔离 + 对等协作」（审核者只看当前版本），10.4.5 的 OpenAI Swarm 是「上下文隔离 + 去中心化」。

先定这两条轴，再动手写代码，比上来就挑框架重要得多。原因在于这两条轴直接决定三件工程后果：信息在哪儿落盘，这决定你怎么调试；谁能看到什么，这决定权限与安全的边界画在哪；失败会往哪儿传，这决定你要在哪些地方加验证和锁。

### 10.1.1 维度一：上下文是否共享

这一节对应。共享上下文的做法是，后续 Agent 接收前一个 Agent 的完整对话历史和轨迹（第一章定义的 trajectory）。每到一个新阶段，系统提示词和工具集都会切换，于是它变成了一个新的 Agent：身份、职责、能力都变了，前任的记忆却完整留着。给出的类比是团队协作，需求分析师写完需求文档，开发者拿到的不只是文档，还能看到分析师与用户之间的所有沟通记录。好处在于信息不丢失，每个 Agent 都能回顾之前任何阶段的细节；挑战在于上下文可能迅速膨胀。

不共享上下文是另一套设定：每个 Agent 维护完全独立的上下文和对话历史，彼此无法直接访问对方的「思考过程」。这里的类比是不同部门之间的协作，每个人在自己的工位上独立工作，通过共享文档和会议纪要交换信息，而不是时刻盯着别人的屏幕。这种模式模块化和隔离性更好，每个 Agent 只需关注与自身职责相关的信息；系统也更易扩展和维护，增加新 Agent 不需要改动现有 Agent 的内部逻辑，定义好接口和数据格式就行。

既然不共享上下文，信息就必须通过显式的通信机制传递。这个问题在经典分布式系统里早有答案：操作系统教科书写得很清楚，进程间通信（IPC）归根结底只有两大范式，共享内存（一方写入，另一方读取同一块存储）和消息传递（把数据显式地发送给对方）。Agent 间的通信机制同样落在这两个范式之内，常见的有三种：

1. **工具调用的参数**：把下游 Agent 封装成工具，上游 Agent 把结构化数据通过工具参数传给下游，适合需要类型确定、结构清晰的场景；
2. **共享文件系统**：Agent 之间通过读写共享目录下的文档、代码等中间产物交换信息，适合产物较大或需要持久化的场景；
3. **消息总线（Message Bus）**：一个专门负责在 Agent 之间传递消息的中转站，Agent 不直接调用彼此，而是把消息发送到总线上，由它转发给目标 Agent。

对应到 IPC 的两大范式：共享文件系统就是 Agent 世界的「共享内存」；工具调用参数和消息总线则是「消息传递」的两种形态，前者随调用同步传递，后者经中转站异步投递。两种范式各有取舍，这里引了 Go 语言一句广为流传的话：「不要通过共享内存来通信，而要通过通信来共享内存」。

用一句话区分两种模式：共享上下文是「同一个人换岗位」，不共享上下文是「不同的人换文件」。前者交接的是记忆，后者交接的是产物。

「每个阶段切换系统提示词和工具集后，就变成了一个新的 Agent」这句话很容易被读漏，它其实点出了这里对 Agent 的定义口径：Agent 的身份等于系统提示词、工具集与它所拥有的上下文三者之和。所以在一个共享上下文的多阶段流程里，「有几个 Agent」取决于你在哪个阶段看。同一份历史，换了提示词和工具，就是另一个 Agent。这也解释了 10.3 为什么专门讨论「角色转换究竟是替换 system prompt 还是加载 Skill」。

共享上下文的「上下文膨胀」有具体的账可算：三个阶段的对话历史、工具结果、报错信息全部串在一条轨迹上，前两个阶段的每一次失败重试都会留给第三个阶段，而第三个阶段的模型还要为这些 token 付费，也还要分给它注意力。10.3 的 Skill 方案正是冲着这个成本模型去的。

三种通信机制的取舍可以这样记。工具调用参数最「紧」，同步、强类型、随调用返回，适合字段明确的交接，比如把 `{url, teacher_name, task_id}` 传给一个搜索 Agent；缺点是上下游必须同时在世，也必须彼此知道接口。共享文件系统最「松」，异步、持久，天然适合几 MB 的译文或整个代码库这类大产物；缺点是内容一落盘就产生了并发问题，10.5.1 专讲这件事。消息总线是解耦版的消息传递，发布者不需要知道消费者是谁，天然支持一对多和订阅过滤；代价是要多维护一个基础设施，而且消息的生命周期通常比文件短。

这里引的 Go 那句名言落到 Agent 世界里就是一条设计倾向：能用消息或文件显式交接的，就不要靠共享一块可变状态来隐式同步。共享可变状态在多 Agent 场景下的诊断成本极高，你很难复现「是谁在什么时候改了那一位」。

工程上的常见坑是把「共享上下文」当成省事的默认选项。它确实省事，不用设计接口，但它把耦合度拉满：第二阶段的工具定义一旦改动，整条轨迹的前缀缓存就失效（10.3 会算 KV Cache 这笔账），而且阶段之间会互相污染，思考题 1 提到的「思维惯性」就是这个问题的表现。

「共享上下文」和「共享文件系统」是两个不同层次的东西，容易混在一起。共享上下文是多个 Agent 共用同一份对话轨迹，模型自动就能看到对方的思考过程；共享文件系统是多个 Agent 共用同一块存储，模型必须主动 read 才能看到对方写的东西。前者属于维度一里的「共享」，后者恰恰是不共享上下文架构下的通信机制。

「Agent 间通信」和「工具调用」也要分开看。从 Manager 的视角看，调用一个子 Agent 和调用一个普通工具没有本质区别（10.4.4 会展开）；从被调用方的视角看，子 Agent 有自己的上下文和推理循环，工具没有。这个不对称正是「把 Agent 建模为工具」这一抽象能被广泛使用的原因。

还有一对容易混的名词：「轨迹」（trajectory）和「记忆流」（Memory Stream）。本章 10.1.1 说的轨迹是对话与工具调用序列；10.6.1 斯坦福小镇的记忆流是带重要性、时近性、相关性权重的经验记录流，是另一种结构，不要混为一谈。

维度一收在这样一个判断上：共享上下文交接的是记忆（信息不丢但会膨胀），隔离上下文交接的是产物（模块化但要设计接口）。

### 10.1.2 维度二：协作拓扑

这一节对应。协作拓扑问的是 Agent 之间的控制权和信息按什么结构流动，这里给出三种典型形态。

对等协作模式（Peer Collaboration Pattern）：少量 Agent 按照固定的拓扑形成迭代改进循环。论文写作 Agent 是个例子，起草者和评论者两个 Agent，一方起草、另一方批注修改，反复几轮后质量更高。

管理者模式（Orchestration Pattern）：一个中心化的 Manager Agent 负责任务规划和调度，多个子 Agent 各负责特定子任务，就像项目经理带着几位专业工程师做项目。

去中心化模式（Decentralized Pattern）：没有运行时的中心控制者，Agent 之间像人类一样互相沟通，协作完成任务。

这里还给了一段术语说明，讲的是 Graph 工程。2026 年 7 月开始流行的「Graph Engineering」，在当前 Agent 语境中通常指显式设计执行图：节点是 Agent、普通程序或人工决策，边定义任务依赖、条件路由与失败后的去向，结构化状态在节点之间流动（该名称的由来与相关实践见第一章「从提示工程到 Loop 工程」一节）。本章讨论的「协作拓扑」正是其中的多 Agent 子集，对等协作、管理者编排和去中心化移交，都是不同的图拓扑。三种模式的详细设计和适用场景在后面的专题小节展开。

三种拓扑对应的是三种控制流形状：对等协作是环（A→B→A 循环迭代），管理者模式是星型（Manager 在中心，子 Agent 在外围），去中心化是网（任意节点之间可以互相移交）。这是理解 10.4.3–10.4.5 的关键抓手。

措辞的精确性值得注意：对等协作强调「固定的拓扑」和「少量 Agent」（10.4.3 明确说通常 2–3 个）。这划出了它和管理者模式的边界。Agent 数量上去、依赖变复杂之后，固定拓扑就撑不住了，才需要中心化的动态调度。

去中心化的定义里强调「没有运行时的中心控制者」，这几个字很重要。10.4.5 用这个标准给三个系统排了序：MetaGPT 的角色顺序由 SOP 预先固定，所以只是「伪去中心化」；AutoGen 群聊的选择器是中心化的控制流决策，所以是「混合形态」；只有 OpenAI Swarm 的 handoff 网络在控制流上真正对等。

Graph 工程这段术语说明的价值在于给了一个统一语言：多 Agent 协作只是「执行图」的一个子集。图工程的范围更大，节点可以是普通程序或人工决策（比如「等用户点确认」），边可以表达条件路由和失败回退。这样理解之后，一个多 Agent 系统和一个带人工审核节点的工作流，其实是同一种东西的不同参数取值，不需要当成两套技术。

工程上怎么选拓扑，可以用三个问题快速定位。子任务数量是「几个」还是「几十个以上」？几个选对等，几十个选管理者。子任务之间的依赖是静态的还是运行期才知道？静态选对等或固定流水线，动态选管理者。单个 Agent 崩溃是否致命，或者任务本身是否要求角色之间的制衡？是的话选去中心化。

「去中心化」不等于「没有编排」，这是第一个易混点。去中心化只是把控制权分散到各个 Agent 手里，不等于没有规则。10.4.5 给出的 handoff 最小协议里仍然有预算、访问链和循环检测，只不过这些约束由运行时保留，不能由任一 Agent 自行删除。也就是说，去中心化是控制权的分散，不是约束的消失。

第二个易混点是「管理者模式」和「工作流」。两者都可能有中心调度，区别在于管理者模式在运行期由模型做决策（谁去干、干几步、要不要换人），而固定工作流的路径是写死的。这里在 10.4.5 说 MetaGPT「更接近一条流水线（用第一章的语言说是工作流）」，正是在这个意义上把它和真正的管理者模式区分开。

协作拓扑说到底就是控制流的形状：环（对等）、星（管理者）、网（去中心化）。

## 10.2 多 Agent 何时真正优于单 Agent

这一节对应。在进入具体的协作架构之前，这里先回答了一个更根本的问题：什么时候真正需要多个 Agent，什么时候一个 Agent 就够了。这个问题的答案会成为后文所有工程方案的总体参照。近年的一系列研究给出的判断框架很简洁，核心判据只有一条：协作过程是否引入了单个 Agent 在生成时无法获得的新信息。

表 10-1 多 Agent 协作模式的信息增量对比（原表按语义还原为 Markdown 表）：

| 协作模式 | 是否引入新信息 | 效果 |
| --- | --- | --- |
| 同一模型自我审查（重新阅读自己的输出） | 否 | 通常无效甚至有害 |
| 不同 Agent 辩论同一段文本 | 否 | 在等计算量下与单 Agent 持平 |
| 审核者使用测试执行结果审查代码 | 是（执行反馈） | 显著提升 |
| 审核者查看渲染截图审查前端/PPT 代码 | 是（视觉反馈） | 显著提升 |
| 审核者使用外部工具验证事实 | 是（工具反馈） | 显著提升 |

2025 年的 RLEF（Reinforcement Learning from Execution Feedback）证实了这条判据：通过强化学习训练模型利用代码执行反馈来迭代改进代码，效果远超让模型独立多次采样。关键在于每次迭代都引入了真实的执行结果，编译错误、测试失败、运行时异常，这些信息在模型写代码时并不存在。

2025 年的 WebGen-Agent 在网页生成任务上，通过多层级的视觉反馈（截图加视觉语言模型描述）构成反馈脚手架，据报道使 Claude 3.5 Sonnet 在该基准上的表现从 26.4% 提升到 51.9%，接近翻倍。

这个「新信息」框架还解释了一个看似矛盾的现象：一些学术研究认为多 Agent 并不能提升 Agent 能力上限，但在工程实践中，多 Agent 确实表现得更好。矛盾的根源在于两者讨论的是不同类型的「多 Agent」。学术研究中比较的多是「多个 Agent 看着同一段上下文互相讨论」的模式，而工程实践中有效的多 Agent 系统往往包含外部反馈环路（代码执行、视觉渲染、工具调用）。前者没有引入新信息，后者引入了。

Anthropic 2026 年的漏洞挖掘实验给出了一个案例：45 个 Agent 通过共享论坛协调搜索、互相审查，再由独立 Agent 仲裁结果。Agent 集群用 2700 万 token 找到 266 个漏洞，而独立 Agent 并行方案用 650 万 token 只找到 21 个。在开放搜索空间里，多 Agent 通过互相通信，可以动态转移搜索重点、形成专门分工，用更高 token 预算换取更广的覆盖和更多样化的发现路径。

还有一个相关的研究方向是步骤预算：给 Agent 分配不同的步骤预算（即允许的工具调用次数或迭代轮数），会如何影响其表现？直觉上，更多步骤应该带来更好的结果。30 步预算下 Agent 只能快速实现核心功能，300 步预算下它还可以先做规划、再实现、再测试、再改进。但 2025 年 Google 的论文《Budget-Aware Tool-Use Enables Effective Agent Scaling》发现了一个反直觉的结论：单纯增加 Agent 可用的步骤数并不能保证性能提升。标准的 Agent 缺乏「预算意识」，即使有 300 步的预算，它们仍然倾向于执行浅层搜索，很快就「饱和」了。要让更多的步骤真正转化为更好的结果，Agent 需要一种显式的预算感知机制，根据剩余资源动态调整策略：前期广泛探索，后期聚焦最有希望的方向。2026 年的 BAVT（Budget-Aware Value Tree Search）进一步提出了步骤级别的价值评估，在每一步根据剩余预算比例调整探索与利用的权重，随着预算减少，Agent 从「广撒网」逐渐切换到「深挖掘」。

这条结论对多 Agent 系统设计有直接的指导意义。管理者模式中，Manager Agent 不应只是简单地把任务分发给子 Agent 然后等待结果，而应根据任务的复杂度动态分配步骤预算：简单子任务给较少的步骤，复杂子任务给充足的步骤。同时还要引导子 Agent 合理利用这些预算，先规划、再实现、再测试、再改进，而不是一头扎进去直接开干。

成本是多 Agent 系统必须关注的要点。多 Agent 的并行探索与反复迭代都要消耗大量 token，这意味着多 Agent 带来的收益必须足够大，能够覆盖数倍乃至一个数量级的额外开销，否则一个调校得当的单 Agent 往往是更划算的选择。

这一节是全章的守门人。它的分量在于那条否决权：如果协作没有引入新信息，那就先别做多 Agent。把它当分诊台用，拿到需求先问一句，协作的哪一步会产出一个模型写代码时不存在的信息？如果答不出来，那这就是多个模型互相复述，收益基本为零，成本翻几倍。

表 10-1 的三行「是」各自代表一类外部性：执行反馈（代码跑起来的结果）、视觉反馈（渲染出来的像素）、工具反馈（搜索引擎或计算器给出的答案）。这三类信息的共同点是模型无法在自己的参数里「想」出来，它们必须由系统之外的某个东西产生。这就是「新信息」的严格含义。

表里「同一模型自我审查」的效果是「通常无效甚至有害」，这个「有害」不是修辞。10.4.3.2 会给出实证：Huang 等人在 ICLR 2024 的论文发现 GPT-4 在没有外部反馈时自我修正，会把正确答案改错的情况多于把错误答案改对。所以「让模型再看一遍」不只是浪费，它可能主动降低准确率。

「不同 Agent 辩论同一段文本，否，在等计算量下与单 Agent 持平」这一行，是理解后文 10.4.3.3 辩论模式争议的钥匙。注意限定词是「等计算量下」，辩论本身会消耗更多 token，如果把 token 拉平，优势就消失了。

Anthropic 那组数字值得自己算一遍（这两个数是我按这里数据算的，这里只给了结果）：2700 万 token ÷ 266 个漏洞约等于 10.2 万 token 一个漏洞；650 万 token ÷ 21 个漏洞约等于 31 万 token 一个漏洞。多 Agent 集群单个漏洞的 token 成本约是独立并行的三分之一，而绝对发现量是 12.7 倍。但这个对比有个重要前提：这里说的是「用更高 token 预算换取更广的覆盖」，两个方案的总预算并不相等（2700 万对 650 万，约 4.2 倍）。所以严格来说，它证明的是「在更高预算下用协作能换到更多发现」，而不是「同样的钱多 Agent 更划算」。把这笔账算清楚，引用这组数字时才不会说错。

步骤预算那段的反直觉结论工程含义很大：给 Agent 更多步数是一笔「没有效果承诺」的开销。默认行为的 Agent 会「浅层搜索 → 饱和」，多出来的 270 步就白花了。所以管理者模式里真正要做的两件事是，按任务复杂度分配预算（不是平均分），以及在提示词或脚手架里教会子 Agent 怎么花预算（先规划、再实现、再测试、再改进）。第二件事其实和 10.4.3.1 的 Loop 工程是同一个问题的两面：Loop 工程管的是「什么时候可以停」，预算感知管的是「剩下的力气往哪儿使」。

关于成本，给出的量级是「数倍乃至一个数量级」。这是个很有用的预算意识：如果你做多 Agent 之后效果只提升了 5%，那几乎肯定不划算。反过来，10.4.3.1 里 LongHorizon-Harness 的对照实验显示，token 代价可以是基线的 2.3 倍（总）和 3.6 倍（输出），这是「数倍」的具体实例；而同一次实验里 Terminal-Bench 2.1 的 token 反而减少了 24%，说明代价也不是固定的，跟任务形态有关。

「多 Agent 无效」和「多 Agent 有效」这两类结论并不矛盾，它们测的是不同的东西。学术研究里的「多 Agent」往往是共享同一段上下文的辩论或集成，工程里有效的「多 Agent」通常带外部反馈环路。判断一个「多 Agent 无效」的结论能不能用在你身上，先看它的系统里有没有外部反馈。

「更多步骤预算」和「更多 Agent」都是「加算力」，但机制不同。步骤预算是给一个 Agent 更多迭代机会，需要它自己会花；多 Agent 是并行开更多上下文，需要协作真的带来新信息。这里把两者放在同一节，是因为它们共享同一条判据：加算力本身不产生价值，只有加算力产生了新信息才产生价值。

「预算感知」和「预算上限」也不一样。预算上限是硬截断，到步数就停；预算感知是策略调整，根据剩余预算改变探索与利用的比例。前者只防超支，后者才可能把大预算变成高质量产出。

这一节的判据只有一条：协作是否引入了单 Agent 生成时拿不到的新信息（执行反馈、视觉反馈、工具反馈）；否则多花几倍 token，换来的只是「再想一遍」。

## 10.3 共享上下文的多 Agent 协作

这一节对应。共享上下文的多 Agent 协作中，每个阶段都是一个独立的 Agent（拥有自己的系统提示词和工具集），但它继承了前序 Agent 的完整轨迹。这里的比喻是「就像接班的同事能翻阅前任留下的所有工作日志」。这种「继承式协作」的核心优势在于信息不会丢失，每个 Agent 都能回顾之前任何阶段的细节；挑战则在于如何让当前 Agent 专注于自己的核心职责，而不被继承来的大量历史信息所干扰。

在复杂任务中，Agent 的角色和职责可能在不同阶段发生显著变化。如果始终使用同一套静态系统提示词，要么过于笼统缺乏针对性，要么把所有阶段的指导塞在一起导致过于冗长。多阶段角色转换的做法是：根据当前阶段动态切换系统提示词和工具集，让 Agent 在每个阶段都以最合适的「身份」工作。

这里指出这里有一个常被忽略、但会直接改变架构的设计选择：角色转换究竟是替换 system prompt，还是加载 Skill？两者都可以让同一个模型在不同阶段采用不同的行为规程，却不是同一种成本模型。这里用一张对比表说明这个选择，这里按语义还原如下：

| 选择 | 角色规程的载体 | 工具可见性 | 上下文/KV Cache 影响 | 约束能力 |
| --- | --- | --- | --- | --- |
| transfer_to_agent | 替换当前 system prompt，并通常替换工具集 | 只暴露当前角色工具 | 每次切换都改变请求前缀；从变化点起的前缀缓存通常无法复用 | 强：越界工具可在 schema 层不可见 |
| Skill | 固定 system prompt 中的 Skill 目录，按需把 `SKILL.md` 追加到轨迹 | 通常固定暴露工具全集，或使用稳定的工具搜索入口 | 静态前缀保持不变；Skill 内容成为末尾轨迹，已有前缀可继续复用 | 弱：Skill 是行为指令，硬权限仍需 Harness 门 |

这里给出的取舍建议是：角色差异主要来自知识、流程和写作风格时，优先使用 Skill；角色差异涉及权限、工具隔离、合规边界，或需要在运行时强制禁止某类动作时，使用独立 Agent 或 `transfer_to_agent` 工具，并在 Harness 层通过代码限制工具调用。

接下来是实验 10-1 ★★：共享上下文中的多角色转换，对比系统提示词与 Skill。两条路径都使用同一模型、同一用户任务、同一工具实现、同一份角色规程和全量共享轨迹。任务是查找中国 2021—2023 年新能源汽车销量、计算 CAGR、写不超过 120 字的投资人摘要。

路径一用系统提示词切换，五种角色为 triage（用户需求收集，默认入口）、research（信息检索）、coding（编程）、data_analysis（数据分析）和 writing（写作）。每个角色只看到自己的专属工具和 `transfer_to_agent`；调用移交时保存历史、加载目标角色提示词与工具集，再继续调用。这里说明旧实现保留在配套项目中，作为这一实验分支的基线。

路径二用 Skill，system prompt 和完整工具全集在整个会话中固定，模型按需调用 `load_skill(name)`，读取的 `SKILL.md` 作为 tool result 进入共享轨迹。这样静态前缀不因角色变化而重写，但工具仍然可见，硬权限由 harness 中的规则保证。

这一节的核心是一个成本模型问题，而不是「哪种做法更好」的品味问题。要理解它，得先回忆 KV Cache 的机制：模型推理时，前缀（system prompt、工具定义、历史消息）如果逐 token 不变，就能直接复用已算好的 KV，只有追加的部分需要重新计算。一旦你在中间改了前缀，从改动点开始的所有缓存都作废。

于是两种方案的账就不一样了。替换 system prompt，每次角色切换都相当于把请求的开头换掉，共享轨迹虽然保住了，但前缀缓存全部失效，每次切换都要重算整条历史，角色切得越频繁这笔开销越大。加载 Skill 则把 system prompt 和工具集固定不动，Skill 内容作为末尾的 tool result 追加进轨迹，前面的静态前缀一直有效，可以持续复用，这就是表里「静态前缀保持不变……已有前缀可继续复用」的含义。

但 Skill 方案付出了另一个代价：工具全集始终可见。模型在「写作角色」时仍然能看到 `execute_code` 这类工具，越界调用只能靠 harness 里的规则去拦。而 `transfer_to_agent` 方案可以在 schema 层就让越界工具根本不存在，模型看不到，就不可能调。「看不见」比「看得见但被拦」是更强的约束，这一点在安全合规场景里是决定性的。

所以这里的取舍建议可以翻译成一句工程口诀：「靠知识分工的用 Skill，靠权限分工的用独立 Agent。」前者的典型例子是写作风格、行业流程、术语规范；后者的典型例子是「这个角色绝不能删生产库」「这个角色只能读不能写」。

实验 10-1 的设计很讲究控制变量：同一模型、同一任务、同一工具实现、同一份角色规程、全量共享轨迹，唯一变的就是「角色规程挂在哪里」。这样对比出来的差异（缓存命中率、成本、越界工具调用率）才能归因到这一点上。这里没有给出实验的具体数值结果，只给了设计，这里不编造任何数字。

顺带解释一下任务里的 CAGR：复合年均增长率（Compound Annual Growth Rate），公式是 $\text{CAGR} = \left(\frac{V_{\text{末}}}{V_{\text{初}}}\right)^{1/n} - 1$，其中 $V_{\text{末}}$ 是期末值、$V_{\text{初}}$ 是期初值、$n$ 是年数。这里查的是 2021–2023 年新能源汽车销量，$n = 2$。（公式与解释为这里补充，这里只提了「计算 CAGR」。）这里没有给出具体销量数字，所以这里不代具体数值计算。

还有一个容易被忽视的隐藏问题：共享上下文虽然信息不丢失，却会造成角色惯性，这正是本章思考题 1 提出的问题。继承了「需求分析师」上下文的「代码审查员」，可能还是倾向于从需求角度而不是代码质量角度思考。Skill 方案在这里反而有个副作用上的好处：Skill 追加在末尾，离当前决策最近，对当下行为的牵引力更直接；而被替换掉的 system prompt 留下的历史仍然占据着上下文的大部分。

「共享上下文」和「共享轨迹」在这里指的是同一件事（trajectory 就是那条对话加工具调用的完整序列）。但要注意它们的对立面不同：共享上下文的对立面是「不共享上下文」（10.4）；而「全量共享轨迹」在实验 10-1 里是被控制住的变量，两条路径都有，不是对比项。

`transfer_to_agent` 和 `handoff` 同名「移交」，含义不同。前者是本章 10.3 里共享上下文场景下的角色移交，保存历史、加载新提示词与工具集、继续调用；后者是 10.4.5 里去中心化场景下的控制权移交，默认不暴露完整私有轨迹，只传任务包和产物引用。一个交记忆，一个交任务。

Skill 的约束弱在硬权限（模型仍能看见工具），不是弱在行为引导。所以正确姿势是「Skill 管行为 + Harness 管权限」，用代码去守权限这道门。

这一节的取舍归结成一句：换 system prompt 换来强约束和缓存失效，加载 Skill 换来前缀复用和宽松权限，按「差异来自知识还是来自权限」来选。

## 10.4 不共享上下文的多 Agent 协作

这一节对应。不共享上下文代表真正的多 Agent 协作。在这种架构下，每个 Agent 都是独立的实体，拥有自己的上下文、轨迹和状态，彼此无法直接访问对方的「内心活动」，协作完全依赖本章开头介绍的三种通信机制（工具调用参数、共享文件系统、消息总线）。

沿着「通信机制即进程间通信」这条线索再往前走一步，会发现多 Agent 系统与操作系统的对应关系相当完整。这里给出表 10-2（按语义还原）：

| 操作系统 | 多 Agent 系统 |
| --- | --- |
| 程序（可执行文件） | 静态前缀（系统提示词 + 工具定义） |
| 进程的内存 | 轨迹 |
| CPU | LLM |
| 内核 | Agent 运行时 |
| 系统调用 | 工具调用 |
| fork（创建子进程） | `spawn_subagent` |
| kill（发送信号） | `cancel_subagent` |
| ps（列出进程） | `list_agents` |
| 退出码与 `wait` | 子 Agent 返回的结构化摘要 |
| 共享内存/消息传递 | 共享文件系统/消息 |

这里指出这套抽象并不新鲜：私有状态、异步消息、可创建新成员，正是 1970 年代 Actor 模型的基本设定，多 Agent 系统不妨看作它的 LLM 版本，因此操作系统与分布式系统的成熟经验大多可以直接借用。

进程式的隔离带来几个切实的工程好处：每个 Agent 可以独立开发和测试，新增能力不需要改动现有代码，某个 Agent 出了故障也不会把错误状态传染给其他 Agent，而且多个 Agent 可以真正并发执行，上下文完全独立，不存在资源竞争。

代价也很明显。最突出的是信息同步问题，各 Agent 如何对任务状态保持一致的理解，信息在传递过程中会不会丢失或重复；调试也变得更加困难，出了问题需要翻看多个 Agent 的日志，才能拼出完整的执行过程。这些问题使得接口规范、数据格式和通信协议的设计变得至关重要。

这里用一句话总括了这套分工：不共享上下文的显式协作依赖两套与拓扑无关的基础设施。一套是共享文件系统，作为 Agent 间交换产物、与用户交换文件的持久媒介，构成协作的数据平面；另一套是通信与控制机制，支持 Agent 间的消息传递、状态查询、执行终止与资源调度，构成协作的控制平面。

表 10-2 是整章最有用的翻译表。它的价值不在于炫技，而在于让你可以把操作系统领域几十年的答案直接搬过来：遇到并发就想到锁，遇到资源竞争就想到调度器，遇到孤儿进程就想到级联终止，遇到调试困难就想到日志与追踪。后面 10.4.1、10.4.2 两小节，本质上就是在逐条兑现这张表。

表里有两行的差别值得细看。「程序（可执行文件）→ 静态前缀（系统提示词 + 工具定义）」说的是同一个模型加不同提示词等于不同「程序」，这正好呼应 10.1.1 那句「切换系统提示词和工具集后就变成了一个新的 Agent」。「进程的内存 → 轨迹」说的是轨迹是 Agent 的私有状态，所以「不共享上下文」翻译成操作系统的语言就是「进程之间不能直接读对方内存，必须走 IPC」。这个类比一旦建立，10.4.1 的四类文件系统区域就非常好懂，它就是一张内存段权限表。

Actor 模型那句话值得记住，三件套是私有状态、异步消息、动态创建。这意味着凡是 Actor 模型能解决的问题（监督树、故障隔离、消息顺序、邮箱背压），在多 Agent 系统里都有对应物。反过来，如果你设计的系统里 Agent 之间能同步读对方状态，那它就不是 Actor 模型了，很多 Actor 的成熟结论也不再适用。

「进程式隔离的好处」里有一条容易被低估：某个 Agent 出了故障也不会把错误状态传染给其他 Agent。这是隔离带来的故障域（failure domain）收缩。共享上下文架构下，一个 Agent 写进轨迹里的错误结论会成为后续所有 Agent 的「事实」；隔离架构下，错误只能通过显式的消息或文件传播，传播路径是可见的、可拦截的。这也是 10.5.2「错误的级联放大」能通过交叉验证来打断的前提。

代价那一段的措辞值得琢磨：「信息同步问题」和「调试困难」其实是一枚硬币的两面。因为看不到对方的内心活动，所以既难让状态一致，也难复盘。给出的应对是「接口规范、数据格式和通信协议的设计变得至关重要」，换句话说，在隔离架构里，接口设计就是架构设计。

数据平面与控制平面的二分法建议背下来，它给了一张检查清单：做多 Agent 系统时，先问产物怎么走（数据平面：文件系统布局、权限、版本），再问指令怎么走（控制平面：消息、状态查询、终止、调度）。这里说这两套基础设施「与拓扑无关」，意思是无论你选对等、管理者还是去中心化，这两套东西都得有，只是用法不同。

「不共享上下文」不等于「不能通信」。它限制的是直接读对方记忆，不是不能交换信息。恰恰相反，正因为不能直接读，才需要把通信机制设计得更好（结构化信封、共享文件、消息总线）。

「数据平面」和「控制平面」搬运的东西也不同。数据平面搬的是产物（大块内容、最终交付物），控制平面搬的是指令与状态（谁该干什么、现在到哪一步了、停）。一个常见的架构错误是把控制信息也塞进共享文件，比如用「某个文件存在与否」来当终止信号，这会同时得罪两边：既没有消息的时效性，又给文件系统引入了隐式语义。

不共享上下文说到底就是进程模型：私有轨迹是内存，共享文件是共享内存，消息是 IPC；数据平面搬产物，控制平面搬指令。

### 10.4.1 Agent 眼中的文件系统

这一节对应。在实际系统中，Agent 访问的并非单一存储，而是一个虚拟文件系统（virtual filesystem）：来源、生命周期与权限各异的存储被挂载（mount）到同一目录树下，Agent 通过统一的 `read_file`/`write_file`/`list_dir` 接口访问，底层则可能是本地临时盘、持久对象存储、第三方云盘的 API 或只读的系统资源包。

这里强调，明确这棵目录树的构成（每一区域的可见性与生命周期）是多 Agent 协作设计的前提。相当一部分并发冲突与信息泄露，源于将本应隔离的区域混置。这棵目录树相当于 Agent 的地址空间，四类区域就是权限各异的内存段：有的私有可写，有的多方共享，有的只读。

一个成熟的多 Agent 系统，其文件系统通常由四类区域构成。

Agent 专属工作区（Scratchpad）。每个 Agent 实例独享的私有目录，存放中间产物、临时文件、草稿与调试日志，生命周期与实例绑定，对其他 Agent 和用户不可见。隔离 scratchpad 有两重作用：避免多个 Agent 的临时文件相互覆盖，以及保持主 Agent 上下文的精简，子 Agent 的试错过程留存于自身工作区，仅将最终产物提交至共享空间。这里点明这是第四章「子 Agent 返回结构化摘要而非全量轨迹」在存储层面的体现。

多 Agent 共享空间（Shared Workspace）。多个 Agent 共同读写、且用户可见的协作区域，是不共享上下文架构下 Agent 间交换产物的主要媒介：Glossary Agent 写入术语表，Translation Agent 从中读取；用户亦可在此上传原始文件、下载最终交付物。其生命周期与整个任务绑定，需要持久化。作为多方并发读写的区域，它是并发冲突的高发处，乐观锁、工作副本隔离（worktree）等机制均作用于此，详见后文「失败模式一」。这里举例：第四章以卷挂载 `/workspace/shared` 连接主 Agent、虚拟电脑与虚拟手机，即为这一层的典型实现。

外部挂载资源（Mounted External Resources）。用户授权接入的第三方信息源，Google Drive、Notion、Dropbox、企业 Wiki 等，通过适配器（adapter）映射为文件系统中的挂载点（如 `/mnt/gdrive`）。Agent 以读文件的方式访问一篇 Notion 文档，底层由适配器调用对方 API 完成。这一层有三项区别于本地存储的特性，需要在设计时显式处理：访问受外部权限约束，用户在源系统中的权限决定 Agent 的可见范围；延迟更高且一致性更弱，每次读取为一次网络往返，数据可能已被外部修改，只能按最终一致性对待；以按需只读为主，写回外部源须谨慎，误写可能污染用户的真实数据。统一的文件接口使 Agent 无需为每个数据源定制专用工具，但也掩盖了上述性能与安全差异，因此需在挂载层面显式管理只读/可写、超时与凭证边界。

系统内置资源（Built-in System Resources）。系统预置、对所有 Agent 只读共享的资源包，典型代表是第二章、第四章介绍的 Skills，它们是以文件形式组织的知识文档与脚本，挂载于 `/skills` 等路径，按渐进式披露（先索引、后按需展开）取用；此外还包括参考手册、模板库与共享工具定义。该层全局共享、只读、跨会话稳定，可被所有 Agent 并发读取而无需并发控制。

这里给出表 10-3（按语义还原），并说明它可作为文件系统布局设计的检查表：

| 区域 | 可见性 | 生命周期 | 读写 | 并发控制 |

这里把这层价值总结为：将四类区域统一至同一目录树，正是「文件路径作为通用接口」这一设计的价值所在。Agent 间传递产物、主 Agent 向子 Agent 交接输入、乃至跨组织 A2A 协作交换产物，传递的均为轻量的路径字符串，而非将内容载入上下文窗口（第四章）。

这一节最值得学的是「地址空间」这个类比：四类区域等于四种内存段。`/scratch/<id>` 是每个进程的私有堆栈，`/workspace/shared` 是共享内存段，`/mnt/*` 是内存映射的 I/O 设备（慢、外部状态可变），`/skills` 是只读的代码段（所有进程共享，天然并发安全）。有了这个映射，表 10-3 的「并发控制」一列就不用背了：能不能并发，取决于这块内存是不是共享可写。

这里那句「相当一部分并发冲突与信息泄露，源于将本应隔离的区域混置」是本节最实用的一句话，它给出两类典型事故。信息泄露是把某个 Agent 的 scratchpad 放在共享目录下，或者把用户 A 的临时文件放在所有人可见的位置；因为文件系统接口是统一的（`read_file` 不区分区域），Agent 完全可能「顺手」读到不该读的东西。并发冲突是把所有 Agent 的中间产物都往一个目录里丢，同名文件互相覆盖；10.5.1 的乐观锁和 worktree 都是为这一层准备的。

Scratchpad 的第二重作用（保持主 Agent 上下文精简）值得展开：这其实是第四章「返回结构化摘要而非全量轨迹」在存储维度的对偶。第四章解决的是怎么不把子 Agent 的完整轨迹塞进主 Agent 的上下文，这里是把那堆试错产物放到一个不占上下文的地方。两者合起来才完整：产物进文件系统，结论进上下文。

外部挂载资源那一层最容易写错，因为统一接口会骗人。你用 `read_file("/mnt/gdrive/xxx")` 和读本地文件写法一模一样，但权限不同，对方系统的 ACL 说了算，你的 Agent 权限体系管不到；延迟不同，一次网络往返可能几百毫秒，比本地读慢几个数量级；一致性不同，`read_file` 两次可能读到两个版本，只能按最终一致性设计；写回也危险，你以为是草稿，其实改的是用户的真实文档。给出的应对是「在挂载层面显式管理只读/可写、超时与凭证边界」，也就是把差异收拢在挂载配置里，而不是让每个 Agent 各自去记。

系统内置资源这一层的设计要点是只读加渐进式披露。只读带来免费并发（不需要锁），渐进式披露（先索引、后按需展开）带来的是 token 节约：Agent 先看目录里有什么，再决定展开哪个 `SKILL.md`。这也解释了 10.3 里 Skill 方案为什么在缓存上更友好，`/skills` 当静态前缀用，内容按需追加。

「文件路径作为通用接口」这条原则可以总结成一句：用指针传，不要用值传。Agent 之间传 `chapter1_zh.md` 这个路径字符串，成本是十几个 token；传它的内容，成本可能是几万 token。传路径还有个附带好处：产物有唯一身份，可被并发读取、可被版本控制、可被人工检查。

Scratchpad 和 Shared Workspace 的区分方法只有一个问题：「这个东西别人需要看到吗？」不需要就放 scratchpad（随实例销毁、无需并发控制），需要就放 shared（持久化、要加锁）。

`/skills`（系统内置资源）和外部挂载的 Wiki 都是「知识」，但前者系统预置、只读、跨会话稳定，后者外部授权、可能变化、一致性弱。

「虚拟文件系统」和「向量数据库/RAG」讲的不是一回事。这里讲的是产物和数据的存放，不是检索。虚拟文件系统解决的是「东西放哪儿、谁能看见、什么时候消失」，RAG 解决的是「相关内容怎么找出来」。两者可以并存，但别把文件的挂载结构当成检索方案。

这一节收在一张权限表上：scratchpad 私有可写，shared 共享可写且要加锁，`/mnt` 外部只读为主，`/skills` 全局只读。

### 10.4.2 Agent 间的通信与控制

这一节对应。文件系统解决了 Agent 间产物交换的问题，协作还需要一条控制平面。这正是表 10-2 中生命周期各行的用武之地：第四章给出的这组工具原语，创建（`spawn_subagent`）、发消息（`send_message_to_subagent`）、取消（`cancel_subagent`）、发现（`list_agents`），对应进程世界的 fork、消息、kill 和 ps。

一、消息传递。最简形态是点对点：Agent A 直接调用 `send_message_to_agent_b(content)`，适用于拓扑固定、Agent 数量少的场景（如本章实验 10-3 的电话加电脑双 Agent）。当 Agent 数量增多且需异步并行时，点对点连接数随 Agent 数呈平方增长，且要求收发双方同时在线；此时应改用消息总线（详见后文「并行协调形态」）：Agent 将消息发布至总线，由总线按订阅关系转发，发送方无需知晓消费者。无论点对点还是经总线，消息通常应携带结构化的信封（envelope）：发送者 ID、目标（指定 Agent 或广播）、消息类型（如 `task_assigned`/`status_update`/`result`/`terminate`）及 JSON 负载。统一的信封格式保证接收方能够可靠地路由和解析消息，并使协作链路可追溯，这是多 Agent 系统调试的关键。

二、状态查询。这是控制平面中最易被低估的一环。主 Agent 派出子 Agent 后，若无从获知其进展，则既无法判断是否继续等待，也无法在其阻塞时及时介入。直观的做法是定义一个 `get_subagent_status(agent_id)` 查询接口，返回「运行中/已完成/失败」等状态。但这里指出这种拉取式接口并不实用：子 Agent 一经创建就立即开始执行，直到完成或失败，子 Agent 完成时自然会通知主 Agent，并不需要主 Agent 显式查询。状态获取更自然的做法，是回到本章开头的两大通信范式。

用消息传递获取状态。主 Agent 直接给子 Agent 发一条消息：「进展如何？」子 Agent 在合适的时机回复。一切都是异步的：发出消息不阻塞自己的执行，对方何时回复、是否回复是另一回事，正如经理通过即时消息询问下属进度，而不要求对方立即停下手头的工作。反过来，子 Agent 也可以在到达关键节点时主动发消息汇报；系统若已架设消息总线，这就是往总线上发布一条 `status_update`（实验 10-4 的「实时监控」即此形态）。无论问答还是主动汇报，消息中的状态本身宜采用统一的状态机词汇（执行中、需要输入、已完成、失败），本章后文的 A2A 协议正是把任务生命周期标准化为这样一组状态。

用共享文件系统获取状态。最彻底的形态是轨迹持久化（trajectory persistence）：子 Agent 在执行过程中，把自己的轨迹（第一章定义的 trajectory，即用户消息、模型回复、工具调用与结果的完整序列）实时序列化为 JSON，追加写入文件系统中的日志文件（通常每个会话一个文件、每行一个事件，即 JSONL 格式）。主 Agent 无需任何状态上报协议，直接读取这个文件就能看到子 Agent 的全部执行过程：它正在调用哪个工具、最近一步在思考什么、是否卡在反复失败的重试上。这里的比方是，用进程的语言说，这相当于直接读另一个进程的内存。

但这里明确提醒：轨迹持久化不宜作为 Agent 间信息传递的主要方式。轨迹动辄数万 token，主 Agent 读完还得自行提炼，既费时又费 token。因此多数场景下更合理的是约定进度文件：主 Agent 启动子 Agent 时约定「把进度写到 `progress.md`」，子 Agent 每完成一项就更新这份任务清单，主 Agent 随时读这个轻量文件即可掌握进展。这里的比方是，这相当于两个进程在共享内存里划出一小块约定格式的状态区，暴露的是提炼后的进度，而非全部内存。进度文件还可以用于检测卡住状态：`progress.md`（或轨迹文件）的最后修改时间超过 N 分钟没有变化，即可判定子 Agent 无活动、触发超时兜底，避免系统被阻塞的子 Agent 拖累。

三、执行终止。并行协作中常出现「一个任务成功，其余任务便无需继续」的情形：多个 Agent 分头搜索，一个 Agent 命中目标后，其余 Agent 应立即停止（实验 10-4 的级联终止）。终止有两种强度，Unix 用户会认出这正是 SIGTERM 与 SIGKILL 的区别。

优雅终止为首选：主 Agent 发出 `terminate` 信号，子 Agent 在当前步骤的安全点响应，先清理资源（关闭浏览器会话、写入未完成文件、释放锁），返回确认（ack）后退出。强制终止为兜底：直接终止进程，仅在子 Agent 对优雅信号无响应时使用，代价是可能遗留悬挂资源与未完成写入。

还剩一个问题：主 Agent 终止后，仍在运行的子 Agent 怎么办？工程上最简洁的做法借鉴 Go 的 context，终止沿创建关系向下级联：取消一个 Agent，它派生的所有子 Agent 随之取消，从根上杜绝无人认领的孤儿 Agent。上文「子 Agent 在安全点检查终止信号」，对应的正是 Go 中对 `ctx.Done` 的轮询。反过来，若确实需要一个脱离主 Agent、长期运行的后台 Agent（类似 Unix 的 `nohup`），就让它从一棵新的生命周期树起步（对应 `context.Background`），显式声明不随父级终止。

四、资源与调度。操作系统的一个重要职能是分配稀缺资源。进程世界稀缺的是 CPU 时间和内存，Agent 世界稀缺的是 token 和并发额度。这项职能通常落在管理者 Agent 或运行时身上：启动子 Agent 时设定步数或 token 预算，超限即止；困难任务交给强模型，机械任务交给低成本模型；并发数设置上限，避免几十个 Agent 同时耗尽 API 配额；当并发数达到上限、更紧急的任务到来时，打断执行中的子 Agent，这就是抢占。

与传统操作系统的调度器相比，管理者 Agent 的显著优势在于它具备推理能力。它可以启动多个子 Agent 并行探索一个问题，并根据它们的进展决定给哪些 Agent 分配更多资源，或者终止哪些看起来误入歧途的 Agent，就像公司内部赛马一样。这里提醒：资源和调度领域的实践还远不如操作系统调度成熟，但它决定了多 Agent 系统的成本上限，应当在架构设计阶段就予以考虑。

这里对 10.4 节的收束是：产物交换（数据平面）与消息传递、状态查询、执行终止、资源调度（控制平面）共同支撑起不共享上下文的多 Agent 系统。根据 Agent 之间的协作关系和控制流特征，不共享上下文的协作可以分为三种主要架构：对等协作模式、管理者模式、去中心化模式，分别适用于不同类型的任务。

这一小节是整章最「工程」的部分，四条正好构成一个控制平面的完整功能清单。可以按「我派出了一个子 Agent，然后我需要什么」来记：我需要能跟它说话（消息传递）、需要知道它到哪了（状态查询）、需要能叫停它（执行终止）、需要管住它花多少（资源与调度）。

为什么「拉取式状态查询」不实用，这个判断值得多讲一句，因为很多人的第一反应就是写 `get_status`。这里的理由有两层。时序上没必要：子 Agent 是持续执行的，完成时它自己会通知，中途拉取只会拿到一个瞬时快照。实现上是伪同步：要真做到「实时」，查询方就得轮询，轮询既浪费调用又引入延迟。更根本的是，`get_status` 这个接口把一个异步系统伪装成同步系统，而异步系统的自然接口是「发消息」或「读文件」。这与 Go 里「不要用轮询查 goroutine 状态，用 channel」是同一个道理。

状态获取的两种做法，恰好对应数据平面与控制平面的分工。发消息问状态走控制平面：轻、快、有语义，一问一答或者主动汇报，但需要对方配合，对方卡死了就不会回。读轨迹文件或进度文件走数据平面：重一点，但不依赖对方配合，即使子 Agent 卡在死循环里，它的轨迹文件也一直在更新，或者停止更新，而这本身就是信号。所以最稳的组合往往是两者都要：用消息总线做主动汇报（低延迟感知），用进度文件的修改时间做兜底检测（防对方失联）。这里那句「`progress.md` 的最后修改时间超过 N 分钟没有变化，即可判定子 Agent 无活动」就是典型的看门狗（watchdog）机制。

轨迹持久化和进度文件这对概念特别值得分清，因为它们的区别就是「共享内存整个 dump」和「共享内存里划一小块状态区」的区别。轨迹持久化信息最全，能看到它最近一步在思考什么，代价是几万 token 的读取与提炼成本；进度文件信息最少，但读取成本极低。默认应该用进度文件，只在排查疑难问题时才去读轨迹文件。这是个成本决策，不是能力决策。

终止的两种强度几乎是把 Unix 的信号语义搬了过来：`terminate` 对应 SIGTERM（可捕获、可清理、要 ack），强制终止对应 SIGKILL（直接杀、可能留烂摊子）。这里特别强调「安全点」这个概念：子 Agent 不能在任何指令中间被打断，否则会留下半写的文件、半开的浏览器会话、没释放的锁。所以优雅终止的实现方式是子 Agent 在循环的每一步检查一次终止标志，这正是 Go 里 `select { case <-ctx.Done: ... }` 的形态。

级联终止（终止沿创建关系向下传播）是防孤儿 Agent 的关键设计，它解决的是这样一类事故：主 Agent 因为超时被取消了，但它派出的 10 个子 Agent 还在跑，继续烧 token、继续写文件，甚至互相覆盖。用 `context.Background` 起新树的做法则给了「我确实要一个不随父级死掉的后台 Agent」一个显式的出口，重点在「显式」：默认级联，例外要写出来。

资源与调度那一段有两个非常具体的设计选择值得记住。按任务难度匹配模型（困难任务给强模型，机械任务给低成本模型），这是最直接的省钱手段。抢占（并发满了、更紧急的任务到来时打断执行中的子 Agent）意味着你的子 Agent 必须支持被随时叫停，也就回到了上面的优雅终止与安全点。

「管理者 Agent 的显著优势在于它具备推理能力」这句话点出了 Agent 调度器和传统调度器的本质差别：Linux 的 CFS 调度器不知道你在算什么，它只能看优先级和 CPU 占用；而管理者 Agent 能读懂子 Agent 的中间结论，判断这个方向看起来没戏了，停掉，把预算给另一个。这就是这里说的「公司内部赛马」。这里也很克制地提醒，这个领域的实践远不如操作系统调度成熟，别指望有现成的最优解，得自己试。

「消息传递」和「共享文件系统」获取状态的区别在于，前者是推拉消息（有时效性、依赖对方在线），后者是读状态文件（可离线观测、有延迟但更鲁棒）。区分方法是问一句：对方卡住了你还想知道情况吗？想，就用文件。

`send_message_to_subagent` 和 `send_message_to_agent_b` 也要分清。前者是第四章给出的生命周期原语（主 Agent → 子 Agent），后者是点对点消息传递的写法（Agent A → Agent B）。在管理者模式里这两者常常是同一个东西；在去中心化拓扑里就退化成纯点对点。

「优雅终止」和「强制终止」一个是协议（要 ack、要清理、可能超时），一个是兜底（直接杀）。常见错误是把强制终止当默认，结果每次取消都留下悬挂的浏览器进程。

「预算」和「配额」的层级不同。这里「步数或 token 预算」是单个子 Agent 的消耗上限（超限即止），「并发数上限」和 API 配额是全局资源上限。前者是给 Agent 的自律约束，后者是给运行时的硬约束。

控制平面要做四件事：发消息（结构化信封）、查状态（消息或进度文件，别用轮询接口）、叫停（先优雅后强制，级联不放过孤儿）、管资源（预算按难度分、并发设上限、必要时抢占）。

### 10.4.3 对等协作模式：相互制衡与迭代改进

> 结构提示：这里 10.4.3 之下还有五个四级小节（10.4.3.1–10.4.3.5），以下四级小节标题的编号与文字均照抄这里。

这一节对应。对等协作通常涉及 2–3 个平等身份的 Agent，通过多轮迭代互相提供反馈。它的潜在价值在于引入独立视角和认知多样性，但这里紧跟着给出一个重要限定：「多个实例」不等于「多种思路」。当模型、上下文和脚手架高度相似时，不同 Agent 往往会做出相同选择，使局部错误演变为系统性故障。要获得真正的多样性，需要主动区分模型、上下文、工具、可见证据或职责，并让各 Agent 先独立判断、再汇总结果。

相比管理者和去中心化模式，对等协作的实现复杂度更低：只需定义好两个 Agent 的角色、通信机制和迭代终止条件，就可以跑起来。

这一节给出一条很容易被工程直觉违背的规律：并行不等于独立。如果你把同一个模型、同一个提示词、同一份上下文开两个实例，它们大概率会犯同一个错，因为它们的「错误来源」是共享的，同一套权重、同样的偏置。这就是 10.5.3「同质趋同」在架构层面的预告。

给出的多样性来源清单值得背下来，它是一份可操作的差异清单：模型（换一家或换一档）、上下文（给不同的材料）、工具（一个能跑测试、一个只能读文档）、可见证据（一个看截图、一个看代码）、职责（一个负责提议、一个负责挑错）。你不需要全部用上，但至少要占一样，否则「多 Agent」就只是「多份算力」。

「先独立判断、再汇总结果」是顺序设计上的硬要求。如果让 Agent B 先看到 Agent A 的结论，B 就很容易锚定在 A 的判断上，这是 LLM 里很常见的顺从性偏差，两个意见也就不再独立了。这也解释了 10.4.3.2 的审核者为什么要读取独立证据，而不是只复述提议者的解释。

「实现复杂度更低」这句是选型建议：如果你只需要「起草-批注」这种两角色循环，不要上管理者模式。管理者模式要维护任务分解、进度跟踪、异常处理、结果整合，复杂度高一个量级。对等协作只要三样东西，角色、通信机制和迭代终止条件，其中迭代终止条件是最容易漏写、也最容易出事的那一样，写不好就变成 10.5.5 的循环失控。

「对等协作」和「多 Agent 并行」不一样。对等协作强调平等身份加多轮迭代（A 提、B 批、A 改），是有来有回的循环；单纯的并行是几个 Agent 各干一块，彼此不迭代，后者更接近管理者模式的并行协调形态。

「认知多样性」和「模型多样性」也不是一回事。换模型只是获得多样性的一种手段，换上下文、换可见证据（一个看图一个看代码）往往更便宜也更有效。

对等协作的收益全部押在「独立视角」上。多个实例不等于多种思路，必须主动制造差异，并让各方先独立判断。

#### 10.4.3.1 Loop 工程

这一节对应。对等协作最经典的用途，是解决 Agent 实践中极其常见的一类失败：过早终止，活干到一半就停。这里给出三种典型形态，并用 Coding Agent 和笔者团队打造的 Pine AI（引言介绍过的、替用户打电话与商家、运营商交涉办事的 Agent）各举了几例。

偷懒式假完成：只做了一部分就宣称全部做完。Coding Agent 写完代码，测试没跑、部署没试，就报告「任务完成」；用户交给 Pine AI 两件事，它办完第一件就把第二件忘了，径直汇报「都办好了」。

过早放弃：一条路走不通就宣布整件事办不成。Pine AI 联系商家本有打电话、填表单、发邮件等多种途径，打了一个电话被拒绝，就直接告诉用户「这事办不了」，其实换个渠道再试很可能就成了。

假成功：Agent 以为办成了，实际闭环没走完。电话里对方口头同意退款，但用户还需要在手机 App 上确认一步，Agent 却报告「已办妥」，用户不知道还有后续动作，退款实际没有落地。

三种形态指向同一个根源：在验证之前，「完成」只是模型的一句宣称，不是证明。

把宣称变成证明，正是 Loop 工程（Loop Engineering）的课题：设计一个让 Agent 持续运转的循环，发现下一件该做的事、执行、验证、记录进度，由验证器而不是模型自己来判定「是否真的可以停」。人的角色则从「给 Agent 写提示词的操这里」变成「设计循环的工程师」。这个名字在 2026 年 6 月由 Addy Osmani 总结提出；Claude Code 负责人 Boris Cherny 的说法更直白：「我已经不再直接 prompt Claude 了，我的工作是写 loop。」

这里给出业界在这场讨论中形成的核心共识：循环的瓶颈在验证器，而不在模型。验证不可靠，循环转得再快，也只是把劣质产出更快地标记为完成。按引言的说法这是「实践在前、命名在后」，在这个名词流行之前，包括 Pine AI 在内的头部 Agent 团队早已在用「循环加验证」解决过早终止问题。而验证最有效的组织方式，正是下面要讲的提议者-审核者范式。

具体框架之一是 LoopX。它把循环从模型的提示词和聊天历史中抽离出来，放进一个与 Agent 运行时无关的持久控制面：目标与边界说明「为什么做」，门禁和待办决定「现在能做什么」，证据与配额决定「是否继续」，移交则让下一轮或另一个 Agent 接着工作。这里给出的流程是：

```
LoopX 决策 → Agent 执行 → 独立验证器证明 → LoopX 提交
```

其中，Agent 仍负责推理、调用工具和生成候选成果；LoopX 不替代 Agent 运行时，它管理的是跨轮次的连续性。只有通过独立验证的结果才能写入持久进度并消耗配额；验证失败会进入修复或重规划，人工门禁、等待状态和预算上限则在执行前阻止循环继续。这里对这个边界的评价是，它把 Loop 工程的原则变成了可检查的系统不变量：模型可以提出「完成」，但不能批准自己的「完成」。

这里同时给出一个重要的限定：LoopX v0.4.0 的受控 Turn 路径仍标为实验性，因此这里把它作为「循环 + 验证 + 终止条件」的具体框架，而不是一般任务质量提升的证据。

另一个具体框架是 LongHorizon-Harness。它与 LoopX 都是 Loop 工程的具体实现，但关注的方向不同：LoopX 面向长期 Agent 工作的持久控制面；LongHorizon-Harness 则从多模态 Computer Use 出发，处理同一任务跨越 GUI、CLI、多个桌面应用和多次上下文刷新的连续执行问题。

它把长程执行重新表述为任务状态管理，并把循环实现为 Manage–Execute–Audit（MEA）：Manager 根据原始目标、已核实进展、失败证据和剩余工作生成下一项有界子任务；Executor 在全新上下文中通过 GUI 或 CLI 改变环境；Auditor 再以只读方式检查真实结果。只有审计通过的内容才能进入下一轮任务状态，失败则被保留为恢复和重规划的依据。它通过适配层复用 Claude Code、Codex CLI 等执行后端，而不改写后端内部的 Agent loop。

这一方向的价值在于把任务连续性从不断增长的执行历史中分离出来：上下文可以刷新，界面操作也可能失败，但下一轮仍能从最近一次核实的状态继续。

论文在保持 Qwen 3.7-Plus 模型与 Claude Code 执行后端相同、只改变外层 loop 的对照中报告了下面这组数字（原表由这里依据这里行文整理，这里此处以行文形式给出，未列表）：

| 基准 | 基线 → MEA |
| --- | --- |
| WeaveBench PassRate | 51.8% → 80.7% |
| OSWorld 2.0 二元完成率 | 2.8% → 8.3% |
| Terminal-Bench 2.1 成功率 | 69.7% → 77.2% |

代价也不是固定的：前两个基准分别消耗了基线 2.3 倍的总 token 和 3.6 倍的输出 token，Terminal-Bench 2.1 则减少了 24%。在实际部署中，还需要处理外部环境或用户要求变化造成的旧状态失效，并用轮数、时间和费用预算防止恢复循环无限运行。

**公开轨迹与实验复现。** 项目网站提供了 WeaveBench、OSWorld 2.0 和 Terminal-Bench 2.1 的数百条运行轨迹，可以直接查看执行过程和不同角色的记录。以 WeaveBench 的 `WEB_task_16_webrtc_simulcast_layer_audit` 为例，可以对照使用同一 Qwen 3.7-Plus 模型的基线轨迹与 MEA 轨迹：前者在 Wireshark 交互卡住后反复尝试，得分 0.59；后者把失败和未满足的证据项写回任务状态，后续轮次只处理缺口，得分 0.92。这里特别说明，这个案例用于展示「失败如何变成下一轮输入」，不能代替总体统计；完整实验的环境、参数和启动脚本见固定版本的 `eval/` 目录。

这一小节是整章的心法。三种过早终止的形态看似不同，根源是同一个：模型对「完成」的判断是生成出来的，不是验证出来的。模型说「做完了」，这句话本身也是一个 token 序列，它没有比「结果是错的」这句话更高的真值地位。Loop 工程的全部内容，就是把「是否完成」这个判断从生成过程里拿出去，交给一个独立于生成的东西。

三种形态各自对应一种验证缺口。偷懒式假完成缺的是完整性检查，任务清单上的每一项都做了吗，Pine AI 例子里办完第一件忘了第二件就是漏项。过早放弃缺的是路径覆盖检查，有几种可行途径，都试过了吗。假成功缺的是闭环检查，外部世界的状态真的变了吗，对方口头同意不等于退款到账。这三种检查恰好都需要外部证据，而不是模型的自我感觉，这正好接上了 10.2 的「新信息」判据。

「循环的瓶颈在验证器，而不在模型」是全章最值得抄下来的一句。它的推论有点反直觉：如果你的 Agent 效果不好，先别急着换更强的模型，先看你的验证器是不是形同虚设。一个不可靠的验证器会让循环加速产出垃圾，这里说得非常形象，只是把劣质产出更快地标记为完成。

LoopX 的设计思路值得单独琢磨：它把循环的状态从模型的上下文里搬到一块持久控制面里。为什么？因为放在上下文里的循环状态有三个问题。随着轮次增长会挤占窗口，对应 10.3 的上下文膨胀；模型可以「忘掉」或「改写」它，对应角色惯性；换一个模型或者一次上下文刷新，状态就断了。搬到控制面之后，「为什么做」（目标与边界）、「现在能做什么」（门禁与待办）、「是否继续」（证据与配额）都变成了外部可检查的对象。这就是这里说的「系统不变量」，不变量是代码能断言的东西，不是提示词里的一句恳求。

「模型可以提出『完成』，但不能批准自己的『完成』」这句可以作为一整条产品设计原则：提议权与批准权必须分离。它对 10.4.3.2 的提议者-审核者、10.4.4 的 `settle_once`（幂等的结算点）都成立。

MEA 循环里最漂亮的一步是 Executor 在「全新上下文」中工作。每一轮子任务都干净起步，没有累积的历史包袱，也不会有「我前面已经试过 XXX」这种自我锚定。代价是 Executor 必须靠任务状态（外部文件）来获得上下文，而不是靠自己上一轮的记忆。这正是「把任务连续性从不断增长的执行历史中分离出来」的字面含义。

那组数字可以做两点解读。提升幅度差别巨大：WeaveBench 从 51.8% 到 80.7%，相对提升约 56%；OSWorld 2.0 从 2.8% 到 8.3%，相对提升约 196%，但绝对值仍然只有 8.3%。这说明 MEA 在 OSWorld 这类开放桌面环境上仍然远未解决，绝对值低这个事实不应该被「翻了三倍」的相对提升掩盖。代价也不对称：同样一个外层 loop 改造，在两个基准上花了 2.3 倍总 token，在第三个基准上反而省了 24%。所以「多 Agent 或外层 loop 一定更贵」也不成立，它取决于任务形态。如果原方案本身就在无效重试上烧钱，一个能记住「哪里失败了」的循环反而更省。

那个 Wireshark 案例的对比（0.59 → 0.92）非常能说明问题。基线失败的原因是「卡住后反复尝试」，这是典型的无状态重试，每次都从头试，不记住失败原因；MEA 的做法是把失败和未满足的证据项写回任务状态，后续轮次只处理缺口，这是有状态推进。这里自己提醒了，这是展示机制的例子，不是统计证据，引用时不要把它当成 MEA 平均效果的证据。

「过早终止」和「循环失控」是一对反方向的失败。过早终止是循环转不下去，这一节讲的就是它；循环失控是循环停不下来，10.5.5 讲。Loop 工程要把前者治好的同时，必须用预算上限和人工门禁防住后者。

「Loop 工程」和「ReAct 循环」管的层级不同。ReAct 循环是单次任务内部的「思考-行动-观察」迭代；Loop 工程管的是跨越多次尝试或多个上下文刷新的持续性，也就是发现下一件事、执行、验证、记录进度这一整圈。LoopX 的定位说得很清楚，它不替代 Agent 运行时，只在运行时之上管理跨轮次的连续性。

「LoopX」和「LongHorizon-Harness」都是 Loop 工程实现，焦点不同。LoopX 是持久的控制面，管跨轮次状态、配额、门禁；LongHorizon-Harness 是面向多模态 Computer Use 的长程执行，管 GUI/CLI 操作与上下文刷新。前者更像「循环的操作系统」，后者更像「长程任务的执行框架」。

「验证器」和「审核者」在这章里常常指同一角色，区别在抽象层级：验证器强调的是判定机制，能不能证明完成；审核者是承担这个职责的 Agent。

Loop 工程要说的其实就是一句话：「完成」是模型的一句宣称，不是证明；判定权要交给独立的验证器，循环状态要从上下文里搬出来，放进持久控制面。

#### 10.4.3.2 提议者-审核者范式

图 10-3 把这个循环画得很完整。左边是 Proposer Agent，接到一份 2000 字的论文扩展摘要，先理解内容结构，再分解为内容页面，产出 Slidev 代码。图里给的代码示例是 `--- theme: academic ---`、`# Transformer 注意力机制`、`## 核心思想`、`- 自注意力计算 Q·K^T/√d`、`- 多头注意力并行处理`。右边是 Reviewer Agent，走两步：先把 Slidev 渲染成 PDF/PNG，再用 Vision LLM 做多维度评估，产出结构化反馈。反馈在图中以一张小表格示意：

| 问题类型 | 严重度 |
| --- | --- |
| 内容过密 | 高 |
| 字体过小 | 中 |
| 配色不协调 | 低 |

图注把它概括成"渲染 + 视觉分析 → 可执行改进建议"。中间是迭代改进循环，代码和结构化反馈在两者之间往返，时间线上标了三轮结果：Round 1 是 12 页初稿、5 个问题；Round 2 到 14 页（拆分密集页）、2 个问题；Round 3 还是 14 页（字体修正）、0 个问题，原图在这一轮打了勾。图左下角还回答了"为何不用单 Agent"：单 Agent 是"渲染图 ×N 轮 → 上下文爆炸"，旁边写着算式 `(1080p 截图 = 数千 token × 14 页 × 5 轮)`；双 Agent 这边，Reviewer 仅看当前版本，Proposer 仅累积文本反馈，于是上下文干净。

那个算式值得真算一遍（这些数是我按图里给的量级估的，原图只给了算式）：1080p 截图按数千 token 算，14 页 × 5 轮是 70 张图，每张估 3000 token 就是 21 万 token，已经超出多数模型的上下文窗口；就算按每张 1000 token 估，也有 7 万。双 Agent 方案里 Reviewer 只持有当前版本，算完就换，Proposer 那边从来只有几十个 token 一条的文本反馈，图片压根没进过它的上下文。

**提议者-审核者**是最经典的对等协作范式。第五章已经在 PPT 生成、视频编辑和日志可视化三个实验里详细讲过它的设计原则和实战：Proposer Agent 负责生成代码，Reviewer Agent 渲染执行结果、用 Vision LLM 评估质量并给出结构化改进建议，两者反复迭代直到效果达标。这套结构搬到别的场景同样成立，安全审查里提议者生成操作方案、审核者检查合规性和潜在风险，内容审核里提议者起草回复、审核者检查业务规则和用语规范，代码审核里提议者编写代码、审核者检查安全性和最佳实践。

这里的问题是：为什么不能让一个 Agent 自己生成再自己审查？这正好落在"多 Agent 何时真正优于单 Agent"那条判据上：审查若不引入新信息，就只是"让模型再想一遍"。相关研究给的答案相当明确。Huang 等人在 ICLR 2024 的论文《Large Language Models Cannot Self-Correct Reasoning Yet》里发现，让 GPT-4 在没有外部反馈的情况下审查并修正自己的回答，准确率反而下降，模型把正确答案改错的次数比把错误答案改对的次数更多。2024 年发表在 TACL 期刊上的综述《When Can LLMs Actually Correct Their Own Mistakes?》（arXiv:2406.01297）把结论又确认了一遍：除非提供可靠的外部反馈，比如测试用例的执行结果、外部工具的验证输出，纯粹依赖模型自身的"自我纠正"几乎不起作用。ICLR 2024 的 CRITIC 论文给了一个更直观的对比实验，让模型使用外部工具（搜索引擎、Python 解释器）验证自己的回答，效果显著提升；一旦移除工具验证、只保留模型的自我评估，大部分提升就消失了。

回到第五章的 PPT 生成实验，道理一样。审核者真正提供的东西是渲染出来的 PPT 画面，那张截图承载着提议者写代码时完全拿不到的视觉信息；用同一个模型把代码再看一遍，等于什么也没加。代码生成场景里执行测试产生的通过/失败结果，也是编写代码时并不存在的新信号。

这条循环的**最小不变量**有两条：审核者读的是独立证据，只复述提议者的解释不算；退回时必须给出可定位的修复条件。这里给出的伪代码是：

```python
candidate = proposer(task, constraints)
evidence  = execute_or_render(candidate)      # tests, state, screenshot, facts
review    = independent_reviewer(candidate, evidence)

while review.veto and budget_remaining:
    candidate = proposer.repair(candidate, review.findings)
    evidence  = execute_or_render(candidate)
    review    = independent_reviewer(candidate, evidence)

if review.pass:
    publish(candidate, evidence, review)
else:
    escalate_or_reject(review)
```

这段伪代码只有 11 行，每一行都在防一种具体的失败。`evidence = execute_or_render(candidate)` 把顺序钉死：先产生证据，再评审，代码本身不能当证据用。`independent_reviewer(candidate, evidence)` 的入参里没有 proposer 的推理过程，只有候选产物和外部证据，这就是"独立"在接口层面的实现方式。`review.findings` 必须可定位，对应图 10-3 里的"页码 P3 / 问题类型 内容过密 / 严重度 高"，"感觉不太好"这种反馈没法让 proposer 动手修。`budget_remaining` 是循环的刹车，防 10.5.5 讲的循环失控。末尾的 `else: escalate_or_reject(review)` 是兜底出口，预算用尽还没通过，就得把问题交出去给人，不能默默返回一个次品。

这里特别强调一条硬规则：审核者不能修改测试、证据采集器或发布门槛，否则**独立验证**会退化成自我批准。这里多说一句。审核者若有权改测试用例，它最省力的"通过"方式就是把测试改宽；若能改发布门槛，它就能降低标准来让自己过关。所以这些能力必须在系统层面从审核者身上拿掉，在提示词里写一句"你不许改测试"是不够的。这跟 10.3 那张表里"约束能力"一列的判断一致：真正的硬约束得靠 harness 的代码。

三篇论文连成一条证据链：自我纠正本身并没有失效，失效的是没有新信息的自我纠正。Huang 等人证明不加外部反馈会变差，TACL 综述给出了条件，必须有可靠的外部反馈，CRITIC 做了消融，装上工具就提升、拿掉工具提升就消失。三者方向一致，这条判据相当扎实。

这里还藏着一个通用模式：图像信息在 Agent 之间只以结构化文本反馈的形式流动。渲染结果被 Reviewer 看过、转述成"P3 内容过密（高）"之后，就变成一条几十 token 的文本。这种压缩有损，价值也很明确，Proposer 看不到原图，却省掉了整个视觉 token 开销。什么时候能这么做？Reviewer 的判断足够可靠的时候。这又是"验证器是瓶颈"的一次印证。

Anthropic 2026 年的长程应用开发实验把这一思路实现为规划者–生成者–评估者三 Agent 架构。规划者把用户的需求展开为产品规格，生成者与评估者先约定每轮的完成标准，再由生成者实现，然后评估者使用 Playwright 操作真实应用并提交缺陷报告，Agent 之间通过文件交接状态。有两个细节要留意。完成标准在动手之前谈好，"通过"就有了可争议的客观依据，不至于事后由评估者随意认定。评估者并不停留在读代码，它是真的去点，这是外部证据最强的一种形态，证据就是应用本身的行为。这里对这条路的评价很克制：当任务超出当前模型单独可靠完成的范围时，带外部证据的独立审核可以用显著更高的成本换取更好的开发质量。两个限定词都很重要，"超出当前模型单独可靠完成的范围"说明否则没必要，"显著更高的成本"说明它不是免费的。

几组概念容易混。如果第二个 Agent 拿到的是候选产物加**外部证据**，它是审核者；只拿到候选产物本身、没有执行或渲染或验证，它只是另一个提议者，两个提议者互相"再看一遍"不产生新信息。自我一致性（self-consistency）与自我纠正（self-correction）也不是一回事：前者是多次独立采样再投票，不改答案，只做聚合；后者是看自己的答案再改。10.4.3.3 会说明，前者是这里认可的，后者在没有外部反馈时无效甚至有害，别把这两个词混用。至于提议者-审核者与辩论模式，前者是一方产出、另一方拿外部证据验收，证据在外部；后者是两方就同一份文本互相反驳，证据在对方嘴里。能引入新信息的只有前者。

审核者必须持有提议者拿不到的外部证据（截图、测试结果、工具输出），并且无权修改测试与门槛，否则就退化成自我批准。

#### 10.4.3.3 辩论模式

辩论模式让多个 Agent 各持不同立场，通过对抗性对话深入探索问题空间。这里的例子是评估一个技术方案：Agent A 扮演"支持者"，列举方案的优势和机会；Agent B 扮演"反对者"，指出风险和局限；每轮辩论都针对对方的论点提出反驳或补充。单一 Agent 分析时，模型往往倾向某个观点而忽视反面证据，辩论模式通过制度化的对抗，确保正反两面都得到充分论证，帮助决策者做出更平衡的判断。

不过辩论模式的实际效果在学术界仍有争议。2026 年 Tran 与 Kiela 的研究在多跳推理任务上对比了单 Agent 与五种多 Agent 架构（顺序、辩论、集成、并行角色、子任务并行），发现当思考 token 预算被严格控制为相同时，单 Agent 的表现与多 Agent 持平甚至更好。研究者基于信息论中的数据处理不等式给出了解释：辩论中的多个 Agent 处理的是完全相同的文本信息，Agent 之间每一次串行传递中间结论都只可能丢失信息，不可能凭空创造信息。辩论模式在一些学术论文中的收益，很可能来源于多个 Agent 消耗了更多的总计算量。这里补充说，这并不否定另一类做法：对同一问题多次独立采样再聚合（如自一致性、多数投票），或者利用生成与验证的难度不对称（写出答案难、检验答案易）来做生成-验证分工。

这一段和 10.2 的表 10-1 是同一件事的两次陈述。表里写的是"不同 Agent 辩论同一段文本 → 否（引入新信息）→ 在等计算量下与单 Agent 持平"，这里补上了机制解释。**数据处理不等式（Data Processing Inequality）**是这里唯一的理论工具，得说清楚：如果 $X \to Y \to Z$ 构成马尔可夫链，那么 $I(X;Z) \le I(X;Y)$，且 $I(X;Z) \le I(Y;Z)$，也就是说对数据做任何处理都不会增加信息量。放到辩论里，Agent B 拿到的是 Agent A 的结论文本，那已经是对原始信息的处理结果了，所以 B 能得到的信息不超过 A 手里那份这里，每传一手，信息量单调不增。多辩论几轮之所以不能凭空变出新知识，原因就在这。

这里的措辞很精确，说的是"并不否定"另外两类做法。这两类各自绕开了数据处理不等式。多次独立采样再聚合，信息增益的来源是多个独立样本的统计，跟传递没有关系：每条链都独立地从 $X$ 出发，聚合相当于在更多样本上做估计，说到底是方差缩减。生成-验证的难度不对称走的是另一条路，写出正确答案难，需要创造；检验答案易，只需判断。于是让可能出错的模型负责"生成"，让另一个环节（或带外部工具的环节）负责"验证"，能过滤掉一大部分错误。这条路的前提是验证真的更容易，而这一点又回到 10.4.3.2：没有外部证据时，验证并不真的更容易。

三段合起来就是一个判断流程：辩论属于传递比较，无效，因为信息不增；多次采样聚合有效，因为它是统计；生成-验证分工有效，前提是验证有独立证据。

工程上的结论并不指向"别做辩论模式"。如果你做辩论，别指望它提升能力上限；它更可能的价值是让决策者看到正反两面，也就是这里开头说的"帮助决策者做出更平衡的判断"。目的是提高答题准确率的话，辩论这个形态的性价比大概率不如"自一致性 + 外部验证"。

还有一个引用上的坑。这里说"当思考 token 预算被严格控制为相同时"，这个限定条件必须带着引用。不带的话就变成"多 Agent 不如单 Agent"，而这里在 10.2 已经说明，工程中有效得多的多 Agent 系统是带外部反馈环路的那些，它们并不在这个对比里。

辩论模式和专家小组模式都涉及多个 Agent 同场，区别在关系性质。辩论是对抗的，支持者和反对者盯着同一份材料，目标是把对方的论点驳倒或补强；专家小组是互补的，工程师、产品、运营各从自己领域补充事实，处理的是跨领域的信息拼图，这里在 10.4.3.5 把它们定性为互补关系。辩论和自一致性也不一样：辩论是串行的，每轮针对对方发言；自一致性是并行独立的，几条链互不影响。前者受数据处理不等式限制，后者不受，这就是它们效果差异的根本原因。

辩论双方处理的是同一份信息，串行传递只减不增（数据处理不等式）；要提准确率，靠的是独立采样聚合或生成-验证分工。

#### 10.4.3.4 头脑风暴模式

头脑风暴模式让多个 Agent 独立生成创意，然后相互分享、彼此启发。这里举的是产品创新任务，三个 Agent 依次被启发：Agent 1 提出"增加社交分享功能"；Agent 2 受启发，提出"不仅分享到社交网络，还可以生成个性化分享海报"；Agent 3 综合前两者，提出"用户自定义海报模板并形成模板市场"。这里解释的机制是：不同 Agent 拥有不同的"**思维偏好**"（通过不同提示词或模型实现），通过相互激发来探索更广阔的解空间，找到单一 Agent 难以想到的创意组合。

头脑风暴和辩论的差别落在目标函数上：辩论求"哪个结论对"，头脑风暴求"能想到多少种可能"。前者收敛，后者发散。

这里对多样性来源的措辞很具体，"通过不同提示词或模型实现"。这正是 10.4.3 开头那条要求（主动区分模型、上下文、工具、可见证据或职责）在创意场景下的形式，这里区分的是思维偏好，可以理解为一种角色化的提示词偏置。三个 Agent 用同一个提示词，得到的就是三个高度相似的创意，例子里的递进关系（分享 → 个性化海报 → 模板市场）也不会自然发生。

"相互分享、彼此启发"这个说法里还带着一个顺序要求：先独立生成，再分享。一上来就让它们在同一场对话里轮流传话，最先发言的那个会锚定后面所有人，这对应 10.4.3 说的"先独立判断、再汇总结果"。所以头脑风暴的正确实现形态是并行独立生成，汇总去重，可能再来第二轮在别人的成果上继续发散。

工程上还有个现实提醒（补一句这里没展开的）：发散类任务没有客观验证器。你没法"渲染一张截图"来判断"模板市场"这个创意好不好。所以头脑风暴的产出必须有人，或者后续的评估环节来筛选，它本身不构成一个可闭环的 Loop。这和 10.4.3.1 强调的"瓶颈在验证器"正好形成对照：在发散任务里，瓶颈会转移到"如何评估创意"这个更难的问题上。

头脑风暴和辩论的目标不一样，一个发散一个收敛，头脑风暴产出的是候选集合，辩论产出的是取舍判断。头脑风暴和自一致性也容易并列着记混：自一致性是对同一个问题多次独立采样再投票，要的是同一个答案；头脑风暴是对同一个题目多次独立生成再互激，要的是不同的答案，方向正好相反。

头脑风暴要的是发散：先独立生成（靠不同思维偏好制造差异），再相互启发，但它的产出没有客观验证器，必须有人筛选。

#### 10.4.3.5 专家小组模式

专家小组模式让多个 Agent 各自代表一个专业领域的视角，共同讨论跨学科问题。这里举的例子是评估新产品的可行性：工程师 Agent 从技术角度分析实现难度，产品 Agent 从用户体验角度评估市场吸引力，运营 Agent 从成本和资源角度分析商业可行性。这里特别点明了关系性质：这些 Agent 之间"不是对抗关系，而是互补关系"，共同拼出问题的全貌，识别跨领域的约束和机会。

三种对等协作形态可以这样概括：辩论对撞、头脑风暴激发、专家小组拼接。专家小组的每个成员提供的是别人手里没有的信息，工程师知道实现难度，运营知道成本结构，所以它不违反数据处理不等式。它引入的多样性来自可见证据和职责的差异，跟"对同一份文本再想一遍"是两回事。这也解释了这里为什么在这里不用"是否引入新信息"来质疑专家小组，却在辩论模式那里质疑得很重。判据是一以贯之的：成员之间的知识是否真的不重叠。

不过专家小组有一个隐藏的工程难点：跨领域结论怎么合并？工程师说"技术上可行但需要 6 个月"，运营说"预算只够 3 个月"，产品说"3 个月后上线会错过窗口"。这里没法从三个答案里选一个，多数投票也没用，因为三条都对，冲突的是约束。所以专家小组模式下必须有一个明确的**裁决机制**，可以是 Manager，也可以是人，合并步骤本身才是这个模式的关键。这一点正好接到 10.4.4 的管理者模式，也和 10.6.6 狼人杀的"法官"设计有关。

专家小组天然的失败模式是各说各话：每个人都从自己领域分析得很深，但没人负责把它们对齐。10.5.2 的"错误的级联放大"在这里换了形态，约束冲突始终没被发现，错误本身并没有往下传。这也是这里强调"识别跨领域的约束和机会"的用意，这个模式的产出重点在它们之间的冲突点，三份各自漂亮的报告反而是次要的。

专家小组和管理者模式下的子 Agent 表面上都是"多个不同专业的 Agent"，区别在控制流：专家小组是对等的，彼此讨论，地位平等；子 Agent 是被调度的，Manager 派活、收结果，子 Agent 之间通常不直接对话。专家小组和角色扮演的区别则在信息差上，每个角色应当对应真实存在的信息差（技术上能不能做、成本多少），只是换个称呼而信息完全相同的话，那还是"多个实例不等于多种思路"。

专家小组靠领域信息差拼全貌，收益真实（不违反数据处理不等式），但难点在约束冲突的合并与裁决。

### 10.4.4 管理者模式：中心化协调

任务涉及大量子任务、需要动态调度，或者子任务之间存在复杂依赖时，对等协作就力不从心了，这时候要引入管理者模式。**Manager Agent** 的职责类似一个项目经理：先理解整体任务，再拆解为可分配的子任务，选择合适的 Agent 去执行，跟踪进度并处理异常（重试、换 Agent、调整计划），再把各 Agent 的输出整合为最终结果。

从系统设计的角度看，管理者模式把每个专门 Agent 建模为 Manager Agent 可以调用的工具。Manager 的工具集里不只有搜索、文件操作这类传统外部工具，还并列着其他 Agent 的调用接口：它通过工具调用机制启动相应 Agent，把任务参数和必要上下文传过去，等对方完成后接收返回结果。从 Manager 的视角看，调用一个 Agent 和调用一个普通工具没有本质区别。

这个统一抽象带来两个直接的好处。扩展性来自注册，新增一种能力只要开发对应 Agent 并把它注册为工具，Manager 的核心逻辑无需修改。异构性则是白送的，不同 Agent 可以用不同的模型、不同的提示词、不同的工具集，甚至可以跑在不同的硬件环境上。工程上还能再往下推一层：Manager 看到的只是一份工具 schema（名字、参数、返回），它不需要关心对方是本地函数、远程服务，还是一个跑在另一台机器上的 Agent。接口统一之后替换就便宜了，想把「数据收集」换成更强的模型，只要新 Agent 的 schema 不变，Manager 这边一行都不用动。工具集里同时躺着 `search` 和 `call_agent_B` 这类条目，编排和调用共用同一套机制，10.1.2 讲 Graph 工程时说的「节点是 Agent、普通程序或人工决策」，落地的样子正是这里。

代价是 Manager 自己成了系统里的单点瓶颈。它必须理解所有子任务的性质，挑对 Agent，把上下文传准，任何一次决策偏差都会影响整体流程。它还得维护整个任务的全局上下文，任务一推进、调用一多，上下文就可能快速膨胀，所以提示词质量、上下文管理策略和任务分解粒度这三件事必须在设计阶段盯住。

2025 年的 Plan-and-Act 论文把这个瓶颈量化了。在 Planner-Executor 双 Agent 架构中，弱规划者才是整个系统最关键的瓶颈：Planner 的规划质量足够高时，即使 Executor 比较简单也能取得好结果；Planner 的任务分解一旦有误，后续所有 Executor 的工作都建立在错误的前提上。该研究在 WebArena-Lite 基准上取得 57.58% 的成功率，核心贡献落在改善 Planner 的规划能力上，Executor 的执行能力并没有动。这条结论和不少团队的直觉相反。直觉上人们会把最强的模型留给最难的执行任务，规划嘛，写几句话而已，配个便宜模型就够了。这里的实验结果直接顶了回来：规划错一步，后面所有执行都白做，Manager 上省下的钱会被 Executor 的无效工作吃掉；更麻烦的是，你可能连「白做了」都发现不了（这件事在 10.5.6 的理解债里还会露头）。这里的启示因此很干脆：把最强的模型和最精心设计的提示词分配给 Manager，而不是把资源平均分配给所有 Agent。

并行形态下还有一条约束容易被含糊过去：结算点要定义成「第一个已验证成功」，而不是「第一个声称成功」。这里给出的伪代码是：

```python
workers = launch_independent_workers(subtasks)

while workers.any_running:
    event = next_event
    if event.type == RESULT:
        if verify(event.artifact, hidden_checks):
            if not settle_once(event):
                # atomically claim the winner
                continue
            broadcast_cancel(to = workers - {event.worker_id})
            await_all_ack_or_timeout
            return assemble(event.artifact, evidence = event.evidence)
    else:
        record_failure(event)

return summarize_failures(workers)
```

这里点出关键约束：`settle_once` 必须是幂等的，通常由锁或事务保护，否则两个几乎同时到达的成功事件会触发两次汇总。写成大白话就是个并发控制问题。Agent A 和 Agent B 几乎同时报告成功，主循环收到 A 就汇总，紧接着再收到 B 又汇总一次，于是出现两次 `assemble`，可能产生重复产物、重复计费，甚至状态不一致。解法就是这里说的那样：第一次调用返回 true，认领成功；后续调用返回 false，直接 `continue` 忽略掉。这和 10.5.1 的乐观锁同源。

代码里另外两处值得停下来看。一处是 `verify(event.artifact, hidden_checks)`，验证用的是 Agent 看不见的检查项。检查项一旦对 Agent 可见，它就可能照着检查项去优化，等于应试；藏起来就只能靠真本事。这和 10.3 表里「越界工具在 schema 层不可见」是同一种思路，把约束放在对方视野之外。另一处是终止的顺序：先原子认领，再广播取消，等齐所有 ack 或超时之后才汇总。顺序不能乱，先广播取消再去认领的话，两个并发的成功事件可能都觉得自己该取消别人。

#### 实验 10-2 ★★：书籍翻译 Agent

这个实验选了一个典型的复杂任务。翻译一本技术书籍，要保证专业术语整体一致、语境准确、整体阅读流畅。拿一本大语言模型相关的英文书来说，大量术语会反复出现，同一种说法可能有多种约定俗成的译法，整体必须统一：第一章把 agent 译成「智能体」，后面就不能改成「代理」。

单 Agent 方案在这里会坏在三个地方。随着 Agent 逐章处理内容，上下文不断累积：整体术语表、已翻译章节、当前段落、翻译思考过程、工具调用结果。一本几百页的技术书籍加上翻译中间产物，很容易超出上下文窗口，这是容量问题。更严重的是在过长的上下文里 Agent 容易「迷失」，忘记之前的术语约定，到第九章用了与第二章不一致的译法；审校阶段重复检查，白白浪费资源；甚至因注意力分散而产生幻觉，「记起」实际上并不存在的术语规则。容量问题好理解，一致性和幻觉这两层才是真正致命的，因为它们不会报错，只会静默地产出错误的译文。

管理者模式把这件事拆成四个角色。

- **Glossary Agent（术语对照表 Agent）**：接收整体内容，识别重复出现的专业术语，搜索专业词典和翻译规范，生成结构化的术语对照表（JSON/CSV 格式，包含英文术语、中文翻译、词性、使用语境）。完成后写入共享文件系统，Agent 即可销毁释放资源。
- **Translation Agent（章节翻译 Agent）**：接收当前章节、术语对照表和翻译指南（目标读者水平、语言风格），翻译为流畅的中文。遇到对照表中的术语严格使用规定译法，遇到新术语则推断翻译并标记为待审查。每个实例在独立上下文中工作，互不干扰，译文写入文件系统（如 `chapter1_zh.md`）。Manager 可以并行也可以串行启动多个实例。
- **Proofreading Agent（全文审校 Agent）**：接收所有译文和术语表，执行一致性检查，逐一验证术语翻译是否统一、识别前后不一致之处、检查整体流畅性和可读性，生成审校报告写入文件系统。
- **Manager Agent**：上下文中主要保存任务描述、执行计划、各 Agent 的调用记录和进度状态，不保存完整翻译内容（这些存在文件系统中），只维护文件索引。根据审校报告，Manager 可以把特定章节发回 Translation Agent 修订。

拆法的依据是信息的自然边界。Glossary Agent 需要整体，但它只需要提取术语，不需要译文，所以它的上下文里只有这里；Translation Agent 需要的是一个章节加术语表加翻译指南，它看不到别的章节，上下文小而稳定；Proofreading Agent 需要所有译文和术语表，上下文大，但任务极其单一；Manager 什么都不看全，只维护文件索引，这正是 10.4.1「文件路径作为通用接口」的直接应用。每个 Agent 的上下文恰好装下它需要的东西，这就是这里说的上下文隔离优势。在这个架构中，Manager Agent 的上下文始终保持在可管理的范围内，而且每个 Agent 都在精简、专注的上下文中工作，不仅效率更高，出错的可能性也更低，不会因为信息过载而分散注意力。

有两个设计细节很实用。Glossary Agent 完成后「即可销毁释放资源」，这是一个一次性 Agent，和灵台里的「分神」是同一路数：把 Agent 的生命周期和它的任务边界对齐，省下常驻的成本。至于「新术语则推断翻译并标记为待审查」，这个标记机制是在自动化流程里保留人工介入点的做法。同类设计还有一处，Proofreading Agent 输出 `review_report.md` 之后，Manager 可以「把特定章节发回 Translation Agent 修订」，这条修订回路正是管理者模式「处理异常」职责的具体形态。

实验要求四条：1) 选择一本图文并茂、包含代码的技术书籍作为翻译对象；2) 实现 Manager、Glossary、Translation、Proofreading 四种 Agent；3) 记录每个 Agent 的上下文消耗，验证管理者模式控制上下文膨胀的有效性；4) 对比单 Agent 与管理模式在翻译质量、执行效率、资源消耗方面的差异。

#### 并行协调形态

<figure class="diagram">
  <img src="../../figures/ai-agent/manager-message-bus.svg" alt="Manager 通过消息总线向四个独立上下文的子 Agent 下发任务，Agent 4 等待前两个依赖完成" width="800" height="450" loading="lazy" decoding="async">
  <figcaption><strong>Manager 的并行协调。</strong> 任务下发、完成汇报和子 Agent 之间的数据就绪通知都经过消息总线，各子 Agent 在自己的上下文中工作。</figcaption>
</figure>

总线的价值在于解耦：发送方不必知道接收方何时在线，接收方也不必维护与每个同伴的点对点连接。Manager 只保留任务、状态和产物索引，完整轨迹留在各子 Agent 自己那里。

这里说明：多个子任务可以并行执行时，顺序模式就显得效率低下了。并行协调让多个 Agent 同时工作，大幅提升吞吐量。Manager Agent 不仅要规划并行任务，还要实时监控所有运行中的 Agent，协调通信，在 Agent 成功或失败时做出全局决策。这通常需要消息总线作为基础设施，可以把它理解为一个「公共公告板」：Agent 可以往上面贴消息（发布），也可以关注自己感兴趣的消息类型（订阅），实现异步通信、互不阻塞。这一点和 10.4.1 里点对点消息的局限正好接上，Agent 数量一多，点对点连接数随 Agent 数呈平方增长，还得要求收发双方同时在线。

#### 灵台（Lingtai）：管理者模式的一个产品化实例

这里介绍，灵台是一个本地运行、以文件为本的长期 Agent 居所，它的三种角色是本节概念的完整实现。

- **主器灵（main agent）**：与用户对话的常驻中枢，掌管计划与记忆，并把工作派生给其他角色，这正是 Manager Agent 的位置。
- **分神（daemon）**：为一件嘈杂而有界的工作分出的短时并行工这里，完成后即弃，只把结论带回主器灵。这正是「子 Agent 返回结构化摘要而非全量轨迹」与并行协调形态的产品化。
- **分身（avatar）**：拥有自己的记忆、邮箱与职责的持久专门化队友，用于值得跨多次会话保留的专业分工。

这里补充说，灵台的其余设计也与前文一一呼应：知识是每个器灵私有的持久记忆文件，技能是所有器灵共享的 Markdown 手册；上下文窗口将满时，器灵会「凝蜕」（molt），给自己写一份总结，带着持久记忆在干净的上下文中继续工作，对应第二章的上下文压缩；底层模型可以替换而器灵犹在。身份、记忆与能力都以普通文件的形式存放在项目目录中，也就是「器灵即其文件」。

#### 实验 10-3 ★★★：自主编排的电话+电脑 Agent

这个实验要求先掌握第六章的 Computer Use 和语音 Agent 技术，难度三星。

任务场景是这样：用户只给出一个网站 URL，请 Agent 填写复杂的注册或航班预订表单。Computer Agent 先打开页面并识别字段，可是姓名、证件号、联系方式、地址和偏好这些信息不在当前上下文中，需要向用户收集。让用户在聊天框里逐项打字比较慢，也容易漏项或输错格式；电话 Agent 可以连续询问、确认和重问，把自然语言回答转换成结构化字段，这就有了用它的理由。

系统架构里，Computer Agent 负责浏览器操作，同时也是本实验的编排者；Phone Agent 负责 ASR、LLM、TTS 和实时对话。两者通过点对点工具或消息总线交换结构化消息（发送者、接收者、类型、内容）。不需要额外的 Manager 进程，Computer Agent 可以像调用工具一样调用 Phone Agent。

两种运行模式的分工很清楚。固定模式是并发基线：预先启动两个 Agent，用来验证独立 ReAct 循环、双向通信和真正的并行。自主模式才是主实验：只启动 Computer Agent，它根据页面、已知信息和任务需要，自主决定是否调用 `initiate_phone_call_agent(purpose, required_info)`；这里特别强调，不要用「字段数量超过阈值」这类 Python 规则代替模型决策。调用之后，系统把任务目的、待收集字段及格式约束作为独立上下文交给 Phone Agent，再沿用固定模式的通信和并行机制。

并行与闭环是实验的验收重点。Phone Agent 通过 WebRTC 逐项提问、抽取并校验回答，Computer Agent 同时在截屏、理解页面并填写字段。每收到一个有效值就发送 `info_collected`，Phone Agent 不等网页填写完成便询问下一项；Computer Agent 反馈 `fill_error` 或页面状态，Phone Agent 据此调整话术。格式错误发送 `format_invalid` 并重新询问，超过重试次数或页面异常则安全暂停。信息收集完成后发送 `task_completed`，Computer Agent 通过校验后提交表单。异常时取消仍在运行的对端，关闭浏览器、音频轨道和通话；真人语音须显式同意，提交须显式授权。

实验要求四条：1) 实现两个独立 Agent 及高效的双向结构化通信；2) 在固定模式和自主模式下证明「问下一个」和「填上一个」真正重叠；3) 实现字段格式校验、重问、页面错误反馈、超时和资源清理；4) 记录消息时序、自主启动决策、延迟、成功率和资源消耗，并比较两种模式。

这个实验有两处特别值得学。一句「不要用『字段数量超过阈值』的 Python 规则代替模型决策」，是整体「让模型做判断」这一立场的典型表述：写死规则的版本跑起来更快、更可预测，但它把「什么时候该打电话」这个需要理解页面语义的判断降级成了计数。这里把固定模式定位成并发基线，把自主模式定位成主实验，正是要证明模型能自己做这个决策。另一处是「问下一个」和「填上一个」真正重叠这个验收标准，它要求证明 Phone Agent 还在问第 N+1 项的时候，Computer Agent 已经把第 N 项填进页面了，而不是只看「两个进程都在运行」。验收标准要写到能观测到重叠，这个标准定得很准，`info_collected` 那条「不等网页填写完成便询问下一项」的设计目的就在这里。安全约束同样值得记：真人语音须显式同意，提交须显式授权，这是给「Agent 替人做实事」设的两道人工门禁（对应 10.4.3.1 里的人工门禁）。

#### 实验 10-4 ★★★：同时从多个网站搜集信息的 Agent

这个实验建议先了解第六章的事件驱动与中断机制。它和实验 10-3 的差别在于协作形态：10-3 是两个异构 Agent 协作，这里关注的是多个同构 Agent 的并行搜索，以及如何通过中心协调实现高效的任务完成和资源优化。

问题是这样的：给定一所大学的多个学院网站，要求在各学院的教师名录页面里查找指定教师（比如「张伟」），找到后返回其所在学院、职位、研究方向等信息。这里列出四个核心挑战，它们正好和 10.4.2 控制平面的四条一一对应。

1. **并行启动**（对应创建原语）：Manager Agent 根据任务需求动态创建 10 个 Computer Use Agent 实例，每个实例对应一个学院网站。每个实例应是独立进程或线程，拥有独立的浏览器会话，能并发执行且互不阻塞。启动时传递目标网站 URL、要搜索的教师姓名、任务标识符（用于消息路由）。
2. **实时监控**（对应状态查询）：每个 Agent 在执行过程中定期发送状态更新，比如「正在加载网站」「正在解析教师名录」「未找到目标，任务完成」「找到匹配，详细信息如下」。Manager Agent 通过消息总线接收这些更新，维护一张任务状态表，实时掌握哪些 Agent 还在运行、哪些已完成、哪些遇到了错误。
3. **级联终止**（对应执行终止）：假设负责计算机学院的 Agent 找到了目标教师，它发送 `{"type": "target_found", "agent_id": "agent_3", "data": {...}}`。Manager Agent 收到后立即向所有其他仍在运行的 Agent 发送 `{"type": "terminate", "reason": "target_found_by_agent_3"}`，每个收到终止消息的 Agent 优雅停止并发送确认。Manager Agent 等待所有确认（或超时）后汇总结果。这里的要求是 Agent 能随时响应终止信号（类似第六章的中断机制），终止必须优雅，不留悬挂进程或未关闭的资源，同时要处理竞态条件（Race Condition）。
4. **失败处理**（对应超时与错误隔离）：实际运行中可能遇到某学院网站无法访问（网络错误、服务器宕机），某网站结构与预期不符导致 Agent 无法正确解析，或者所有 Agent 搜索完毕都没找到目标。Manager Agent 的策略是为每个 Agent 设置超时（如 2 分钟），超时视为失败；错误隔离，不影响其他 Agent 继续执行；全部完成后汇总，只要有 Agent 成功就返回信息，全部失败则向用户报告「未找到目标教师」及各失败原因的统计。

这里在竞态条件那里补了一段概念说明，很值得单独记：假设 Agent A 和 Agent B 几乎在同一毫秒内各自找到了目标教师，同时向 Manager Agent 报告「我找到了」。如果 Manager Agent 处理不当，比如收到 A 的报告后开始汇总结果，紧接着又收到 B 的报告触发了第二次汇总，就可能产生重复的结果或互相矛盾的状态。解决方法通常是使用锁机制：第一个报告到达后立即锁定状态，后续报告被识别为重复并忽略。顺序是先锁、再忽略重复，这和前面代码里的 `settle_once` 是同一个机制，只是那里的措辞是「幂等」。三处呼应可以串起来记：10.4.4 的 `settle_once`、这里的竞态补充、以及 10.6.6 狼人杀的投票统计（收集所有投票再公布）。凡是多个并发事件争夺同一个结论的地方，都需要一个原子结算点。

实验要求六条：1) 实现能动态启动多个并行 Agent 的 Manager Agent；2) 基于 browser-use 等开源项目实现 Computer Use Agent；3) 实现消息总线支持 Manager Agent 与多个子 Agent 双向通信；4) 实现成功后的级联终止机制，确保找到目标后所有其他 Agent 快速停止；5) 处理各种异常情况（网站访问失败、解析错误、全部未找到）；6) 记录和对比并行执行与串行执行的时间差异，验证并行化带来的性能提升。

给出的时间数据值得把账算一遍。串行方案是 10 个网站 × 30s/站 = 300s，约 5 分钟；并行方案是 18 秒找到加上 1 秒终止，共 19 秒；两者相除，加速比 = 300 / 19 ≈ 15.8 倍（写「~15×」，这个数是我按它的数字算的）。这里有个容易看漏的地方：理想并行加速比本该是 10 倍（10 个网站同时查），实际却是 15.8 倍，比 10 倍还多。原因是串行方案里每个网站要花 30s，包含超时和失败等待；而并行方案里级联终止让 8 个还没完成的 Agent 提前停下，省掉了它们本会消耗的时间。所以这里那句「（含级联终止优化）」是实打实的：加速比里有一部分是省下来的，并不全是并行出来的。

#### 管理者 Agent 生成 Agent 工作流

前面两种形态里，管理者 Agent 始终待在循环中：每派发一个子任务都要模型做一次决策，上下文随调用次数增长。还有第三种做法，管理者先把 Agent 工作流写成一段代码，再交给确定性的运行时去执行。

Claude Code 内置的 Workflow 工具就是这样一个实例，它给 Agent 提供 `agent`、`parallel`、`pipeline` 几个原语。每个 `agent` 是一个拥有独立上下文的子 Agent，`schema` 约定它只返回结构化结论，而不是完整轨迹。给出的例子是为一篇技术稿件核实七组事实，每组先调研，再逐条独立核实，然后统一汇总：

```javascript
const results = await pipeline(
  DIMENSIONS,
  // 七个待核实的方向
  d => agent(research(d), { schema: FINDINGS }),
  // 阶段一：调研
  r => parallel(r.findings.map(f =>  =>
    // 阶段二：逐条独立核实
    agent(verify(f), { schema: VERDICT })))
)
await agent(writeProvenance(results.flat))
// 汇总：等齐所有结果
```

这是一个很关键的概念升级。前两种形态是 Manager 在循环里，每次派活都要模型决策一次，上下文随调用次数增长；第三种是 Manager 写代码，运行时执行。好处有三层：Manager 的决策从「每次调用一次」变成「一次规划出一整张图」，token 成本与调用次数解耦；执行变成确定性的，`pipeline` 的依赖关系写死在代码里，可复现、可调试、可并行；每个 `agent` 仍然是独立上下文的子 Agent，`schema` 强制它只返回结构化结论。这和 10.1.2 的 Graph 工程是同一件事，把控制流从运行期的模型判断固化成设计期的图。代价是灵活性下降，运行期发现情况变了，改不了图，或者得重写一段代码。所以两条路各有适用的场合：探索性强、依赖未知的任务让 Manager 待在循环里；流程稳定、需要并行和可复现的任务，把工作流写成代码更划算。

10.4.4 的三种形态到这里讲完了，几个容易混的点可以顺手理一遍。顺序协调的控制流是线性的，A → B → C，每步结果都经 Manager 中转，适合有清晰先后依赖的场景；并行协调需要消息总线做基础设施，适合可并行的子任务，Manager 要实时监控并做全局决策。实验 10-2 是顺序形态（虽然 Translation Agent 可以并行启动多个实例），实验 10-4 是典型的并行形态。「Manager 是工具调用者」与「Manager 是循环主体」说的不是同一件事，前者是抽象视角，Manager 看子 Agent 和看普通工具一样，后者是实现形态；到了 Workflow 这种形态，Manager 既不在循环里也不是运行时，它只是生成了一段代码。灵台里的分神和分身也要分清：分神短时、有界、完成即弃，对应一次性的子 Agent；分身持久、有记忆、有邮箱，对应跨会话的专门化队友。选哪个取决于这件工作值不值得跨会话保留。

管理者模式说到底就是三句话：把每个专门 Agent 当成工具，把最强模型给规划者，把共享产物放进文件系统而上下文里只留索引。而它最激进的一种形态，是 Manager 干脆写出一张工作流图，交给确定性运行时去执行。

### 10.4.5 去中心化模式

这一节对应。

有了管理者模式，为什么还要去中心化模式？这里给出的动机是模拟人类社会的组织方式：让多个职责对等的角色分工与制衡，各自从自己的专业视角审视问题，自主决定与谁沟通，而不是把所有判断都汇集到一个 Manager 那里。在去中心化模式中，每个 Agent 根据自己的专业判断，自主决定何时向其他 Agent 发起沟通。这里列了三种可能的沟通：移交任务（「我的部分做完了，交给你」）、请求反馈（「这个方案技术上可行吗？」）、报告问题（「你给的需求有矛盾，我们需要重新讨论」）。

去中心化还有助于解决 Agent 的稳定性问题。由于模型或 API 服务的问题，一些 Agent 可能停止响应、工具调用失败、陷入错误工具调用的死循环。在管理者模式中，管理者 Agent 崩溃往往会成为系统最大的单点故障，去中心化模式有助于解决这一问题。这里还给了一组术语对照：微服务领域把管理者和去中心化模式分别称为编排（orchestration）与编舞（choreography），前者由指挥统一调度，后者靠每位舞者自行把握入场时机。

这里用三个案例串出一条递进线索：MetaGPT 的控制流其实是固定流水线（伪去中心化，只在通信机制上解耦），AutoGen 的 group chat 是共享对话记录加中心化调度的混合形态，直到 OpenAI Swarm 才在控制流上做到真正的对等去中心化。

#### 案例一：MetaGPT——SOP 驱动的软件公司模拟

MetaGPT 的核心洞察是：人类软件公司积累的标准作业程序（SOP，Standard Operating Procedure）本身就是被反复验证过的协作协议。把 SOP 编码进多 Agent 系统，让每个角色像流水线上的专业工种一样产出标准化交付物，交付物天然构成了角色间的通信接口。

在 MetaGPT 中，各角色沿固定顺序工作（Product Manager → Architect → Project Manager → Engineer → QA），每个角色输出结构化的「移交包」：Product Manager Agent 接收需求描述，生成结构化 PRD（产品需求文档，含功能列表、用户故事、验收标准、优先级排序）；Architect Agent 读取 PRD，做出架构决策（技术栈选择、模块划分、接口定义、数据模型设计），输出设计文档；Project Manager Agent 读取架构设计，把系统拆解为具体的任务清单和文件级分工，理清各模块的依赖顺序，再把任务分派给工程师；Engineer Agents 读取设计文档，实现所负责的模块，产出代码，可以多实例并行工作；QA Engineer Agent 读取代码和 PRD，生成测试用例、执行测试、记录 bug，输出测试报告。

一个有效的「移交包」通常包含三部分：任务描述（接收方要做什么、验收标准是什么）、已确认的事实与约束（用户偏好、业务规则、前序阶段敲定的决策），以及结构化产物的引用（文件路径而非文件内容，接收方按需读取）。每个 Agent 不需要理解其他 Agent 的思考过程，只需要理解移交包和产物的格式与语义。这三条合起来，就是「不共享上下文」架构下的接口规范，呼应了 10.4 那句「接口规范、数据格式和通信协议的设计变得至关重要」。其中第二条最容易被忽略，它保证接收方不会重新推翻已经定下来的事；第三条则保证接收方按需取证，不把上游的全部产物灌进自己的上下文。

MetaGPT 真正对去中心化通信的贡献在信息传递机制上：共享消息池加按角色订阅。每个角色把结构化消息发布到一个所有角色可见的消息池中，其他角色根据自己的订阅配置，只取用与自身职责相关的消息，而不是点对点地一对一传话。发布者不需要知道谁会消费自己的输出，新增角色只需声明订阅哪些消息类型，无需改动任何现有角色。这带来了真正的解耦：把 Product Manager 换成更强的模型，只要它发布的 PRD 仍然符合规范，其他所有 Agent 都无需修改。发布订阅相对点对点的优势，可以拿打电话和贴公告板来比：打电话要知道对方号码、对方还得在；公告板贴上去就行，谁来看都行。工程上的意义是加一个新角色不用改任何老角色的代码，这对多 Agent 系统的演进太重要了。

这里做了一次如实的澄清，这一段很重要：MetaGPT 在控制流上并不是去中心化的，角色顺序由 SOP 预先固定，整体更接近一条流水线（用第一章的语言说是工作流）。它被放在本节讨论，是因为消息池加订阅的通信机制展示了去中心化系统最关键的设计要素：解耦。至于「QA 直接找 Product Manager 澄清需求」「Engineer 找 Architect 讨论替代方案」这类多向动态反馈，是对这一架构的自然扩展设想，原版 MetaGPT 并未实现。这里没有为了叙事好听而拔高案例，这一点值得敬佩。

#### 案例二：AutoGen 群聊

AutoGen 的群聊（group chat）让多个 Agent 参与同一场会话：每轮由一个「发言者选择器」决定下一个发言的 Agent。选择器可以是简单的轮转规则，也可以是一个 LLM 根据当前对话内容判断谁最适合接话；任何 Agent 的发言对所有参与者可见。这里的定性是：它并不是完全去中心化的系统，发言者的选择由一个中心化的 `GroupChatManager` 统一裁决，而「轮到谁发言」本身就是一种控制流决策。它属于「共享对话记录 + 中心化调度」的混合形态：所有 Agent 看到同一份公共对话记录，但各自保有独立的系统提示词和工具集，而调度权集中在选择器手里。

这份「公共对话记录」其实更接近 10.1.1 讲的共享上下文，所有 Agent 看的是同一份记录，只是各自的提示词和工具集独立。所以给它安一个「混合形态」的位置是准确的。

#### 案例三：OpenAI Swarm

OpenAI Swarm 是控制流真正实现对等去中心化的代表：每个 Agent 配备若干 handoff（移交）选项，可以在任何时刻把控制权移交给网络中的任意其他 Agent。系统中没有中心调度者，控制权像接力棒一样在对等的 Agent 之间流转，路由决策完全分散在每个 Agent 自己的判断里。

这里划了一条重要的边界：与共享上下文的多 Agent 协作不同，handoff 只应传递明确的任务包和产物引用，不应默认暴露完整私有轨迹。这是真正的上下文隔离，也是它和上面两个案例的关键区别。对等移交的风险则是成环：A 移交给 B，B 又移交回 A，任务在环路中空转，因此需要移交次数上限之类的保护机制。

这里给出的去中心化 handoff 最小协议是：

```
handoff = {
  task_id, sender, recipient, goal, constraints,
  accepted_facts, artifact_refs, remaining_budget,
  visited_agents
}

if recipient in handoff.visited_agents:
    reject("cycle")
elif handoff.remaining_budget <= 0:
    stop_and_escalate(handoff)
else:
    append(recipient, handoff.visited_agents)
    run_local_agent(handoff)
```

这 12 行代码浓缩了去中心化模式的两个必需品。`visited_agents`（访问链）用来防成环，因为 A→B→A 这种环路在去中心化系统里没有全局裁判来发现，只能靠每个节点自己携带路径。`remaining_budget`（剩余预算）用来防无限流转，每次移交都要扣减预算，预算耗尽就 `stop_and_escalate`，停止并升级给人。这里对这个协议的解读是：它把「上下文隔离」变成可检查的接口，接收者读任务包和引用、按需取证，而预算、访问链和循环检测由运行时保留，不能由任一 Agent 自行删除。后半句是安全设计的关键。这些字段如果放在 Agent 能改的地方，比如塞进提示词让它自己写，Agent 完全可能「忘记」扣预算或者「清空」访问链，约束必须放在 Agent 改不到的地方，这又回到了 10.3 表里「硬权限仍需 Harness 门」那条。

三个案例放在一起看，判据其实只有一条：控制流的决策权在哪里。MetaGPT 的决策权在 SOP 里，角色顺序写死，所以控制流是工作流，它的去中心化只发生在通信层面。AutoGen 的决策权在 `GroupChatManager` 里，控制流是中心化的。Swarm 的决策权分散在每个 Agent 的 handoff 判断里，这才是真正的对等去中心化。所以这条线索描述的是控制流去中心化的程度从低到高，并不是从差到好，这里也没有说 Swarm 最好，它只是最去中心化。至于编排和编舞这组术语，用法很准：编排是有指挥的，谁来调谁由指挥说了算；编舞是每个舞者自己听音乐、自己判断什么时候进场。要判断一个系统属于哪种，问一句就够了：有没有一个组件在决定「下一步谁动」？

「去中心化能抗单点故障」这条理由很实在，但边界要说清楚。去中心化解决的是控制权的单点故障，不等于解决了能力的单点故障。如果所有 Agent 用的都是同一家的 API，那家挂了，去中心化一样全挂。这里在讲稳定性问题时列举的失败里本来就包括「模型或 API 服务的问题」。所以准确的说法是：去中心化减少的是逻辑上的单点，基础设施上的单点它管不了。

#### 关于「Agent Swarm」这个流行词

2025 年以来，「Agent Swarm」（智能体集群）成为各厂商的热门词汇，但它并不对应单一架构。业界用法大致有两类。一类是 OpenAI Swarm 式的 handoff 网络，LangGraph 的 swarm 库、微软 Agent Framework 的 handoff 编排都属此列，就是本节的去中心化模式。另一类是一些主流商业产品的 Agent Swarm，实际是规模化的管理者模式：Kimi K2.5 首发的 Agent Swarm 由主 Agent 动态创建上百个子 Agent 并行执行，把「何时拆、拆几个」的编排决策通过并行 Agent 强化学习直接训练进模型，K3 将其延续为独立模型档位，并开源了配套的并行 Agent 训练沙箱 AgentEnv；Anthropic 的多 Agent 研究系统与 Manus 的 Wide Research 同属 orchestrator-worker 星型拓扑。这里的态度很明确：希望读者在阅读这里之后，能够看清概念背后的实质，分析不同多 Agent 系统的实际结构，而不被名称迷惑。

补充：补充了几条资料：Moonshot AI, Kimi Agent Swarm: 100 Sub-Agents at Scale, 2026（`https://www.kimi.com/blog/agent-swarm`）；GTC 2026 上披露并行子 Agent 上限已扩展至 300 个；AgentEnv 为月之暗面与 KVCache.ai 合作开源的 Agent 训练沙箱，随 Kimi K3 于 2026 年 7 月发布。

这段是本章对市场宣传最直接的一次祛魅，实用价值很高。以后再看到任何「Agent Swarm 产品」，只要问一句：编排决策是模型在运行期做的，还是训练进去的？如果是后者，像 Kimi K2.5/K3 那样把「何时拆、拆几个」用强化学习直接训进模型，那它本质上是管理者模式，主 Agent 就是 Manager，只是把 Manager 的调度策略训成了模型能力。名字一样，架构完全不同。

#### 同一台机器上的多个对等 Agent 实例

以上三个系统的 Agent 都在合作完成同一件事，还有一类去中心化则是各干各的。每个 Agent 有自己的任务，它们之间通信是为了协调使用共享资源，与分工无关。Claude Code 已经支持同一台机器上的多个 Agent 互相发现（这正是第四章 `list_agents` 的用途）并互相发消息：两个 Agent 在修改同一组文件时协商解决冲突，机器上只有一块 GPU 而两个实例都要跑训练时协调使用 GPU。这类系统的特点是 Agent 之间没有共同目标，只有共同资源。它的失败模式也因此不同，更容易出现的是共享资源被抢崩，某个任务没完成反倒不是主要症状，对应的处置办法就是 10.5.3 提到的「使用命名空间、资源配额和速率限制，防止相同决策同时冲击共享资源」。

这里最后留了个引子：去中心化模式进一步的演进是 Agent 社会，这将在本章最后介绍。

10.4.5 有几组概念容易搅在一起。「去中心化模式」和「多 Agent 并行」说的不是一回事，并行是同时干活，去中心化是控制权分散，一个系统可以既并行又中心化，实验 10-4 里 10 个 Agent 由 Manager 统一调度就是例子。AutoGen 的「共享对话记录」和 10.1.1 的「共享上下文」很接近，差别在于前者各 Agent 保有独立的系统提示词和工具集，且发言权由选择器裁决，而 10.1.1 的共享上下文强调完整轨迹被后续 Agent 继承。handoff 和 transfer_to_agent 的区别见 10.3 里那组辨析，关键在 handoff 不应默认暴露完整私有轨迹，transfer_to_agent 则恰恰是保留历史换角色。同一个「Agent Swarm」有两种架构，区分办法是看谁决定创建几个子 Agent、什么时候拆：运行期由模型决策的读作去中心化网络，被训练进模型的编排策略读作管理者模式。

判断去中心化，看的只是控制权的归属。SOP 决定顺序的是流水线（MetaGPT），选择器决定发言的是中心化（AutoGen），每个 Agent 自己决定移交给谁，才是真对等（Swarm）；而 handoff 必须带访问链和预算，防的是成环和无限流转。

### 10.4.6 跨组织协作：A2A 协议

这一节对应。

以上系统都假设所有 Agent 由同一个团队开发、运行在同一个系统内，此时参数传递、共享文件、消息总线三种通信机制足够用。当协作跨越组织边界，你的 Agent 需要调用另一家公司的 Agent 时，就需要标准化的互操作协议。这里的类比很精炼：A2A 之于 Agent，就是网络协议之于进程。

这里的核心变量是信任边界。前面 10.4.1–10.4.5 讨论的所有机制都默认了一个前提：这些 Agent 属于同一个系统，你能改它们的代码、看它们的日志、控制它们的权限。一旦跨组织，这个前提全部失效。你没法要求对方按你的文件布局放产物，没法直接读对方的轨迹，也没法在对方的 harness 里加约束。这时候只能用协议，把双方都能遵守的最小公共约定写下来。拿进程打个比方：同一台机器上的两个进程可以用共享内存通信，快，但要求同一地址空间；跨机器的进程只能用 TCP/IP 这样的协议，慢，但双方不需要知道对方的实现。Agent 世界完全对应，同一团队用消息总线或共享文件，快但紧耦合；跨组织用 A2A，慢、松耦合，需要标准。

2025 年 Google 发布的 A2A（Agent2Agent）协议正是为此设计的，后捐赠给 Linux 基金会托管。它的核心要素有三个。

1. **Agent Card**：一份描述 Agent 能力的元数据文档（发布在约定的公开地址下），声明这个 Agent 能做什么、支持哪些输入输出模态、如何认证。它相当于 Agent 的「名片」，解决跨组织的能力发现问题。类比 DNS 加服务注册：你不需要事先知道对方的地址，只要按约定去查。
2. **任务生命周期管理**：A2A 把协作单元建模为任务（Task），带有明确的状态机（已提交、进行中、需要输入、已完成、失败），原生支持长时间运行的任务和流式进度更新。这一条解决的是「跨组织调用可能要跑几小时，我怎么知道它卡住了还是在跑」。注意这组状态和 10.4.2 建议的「统一的状态机词汇（执行中、需要输入、已完成、失败）」几乎逐字对应，这里在 10.4.2 就埋了这个伏笔，A2A 做的事本质上是把这套内部约定标准化成公开协议。
3. **不透明协作**：Agent 之间只交换任务与产物（Artifact），不暴露内部的提示词、思考过程和工具实现。这与本章「不共享上下文」的原则一致，也是跨组织协作中必要的安全属性。它同时满足两种需要：技术上跨组织确实拿不到对方内部状态，商业上提示词和工具链本来就是核心竞争力。

A2A 的定位可以和第四章的 MCP 对照理解：MCP 解决的是 Agent 与工具之间的互操作，A2A 解决的是 Agent 与 Agent 之间的互操作。两者互补，谈不上竞争关系。A2A 也没有取代本章介绍的三种通信机制，它站在它们之上，是一层跨信任边界的标准化。同一团队内部的多 Agent 系统直接用消息总线即可，只有当协作方互不信任、实现互不可见时，才需要 A2A 这样的公开协议。

| | MCP | A2A |
| --- | --- | --- |
| 解决谁的互操作 | Agent 与工具 | Agent 与 Agent |
| 对应本章哪部分 | 工具调用（10.1.1 三种通信机制之一） | 跨组织的 Agent 协作 |
| 是否需要 | 同一系统内也需要 | 只在跨信任边界时需要 |

（上表为这里补充的整理，这里只给了一句对照。）

这里最后那句「只有当协作方互不信任、实现互不可见时，才需要 A2A」是一条防止过度设计的忠告。很多团队一上来就想「我们得支持 A2A」，但如果所有 Agent 都是自己写的，用 A2A 只会多一层协议开销，还丢掉了直接读文件和轨迹的调试便利。先问清协作方是不是外人，再决定要不要引入这层协议。

> 来源确认：A2A（Agent2Agent）协议确由 Google 于 2025 年发布，并已捐入 Linux 基金会旗下的 Agentic AI Foundation（该基金会同时托管 MCP）。这与这里「后捐赠给 Linux 基金会托管」的表述一致，且与这里把 A2A 定位为「MCP 的兄弟协议」（一个管 Agent↔工具、一个管 Agent↔Agent）相吻合。（来源：[Agent2Agent Joins The Agentic AI Foundation Alongside MCP](https://tech.yahoo.com/ai/articles/agent2agent-joins-agentic-ai-foundation-130048369.html#1)、[Quarkus and WildFly teams from Red Hat collaborating with Google on launch of Agent2Agent Java SDK](https://quarkus.io/blog/a2a-project-launches-java-sdk/)）

还有两组概念要分开。Agent Card 和工具 schema 描述的东西不同：工具 schema 描述参数与返回，也就是怎么调；Agent Card 描述能力、模态与认证方式，也就是能干什么、怎么找到、怎么信得过。前者是调用契约，后者是发现与信任契约。「不透明协作」和「信息丢失」也不是一回事，不透明是有意设计的隔离，只交换任务与产物，换来的是跨组织协作能成立的前提：双方都不必暴露自己的实现。

A2A 是 Agent 世界的网络协议。Agent Card 解决「谁能干」，Task 状态机解决「干到哪了」，不透明协作解决「不必互相暴露」，而它只在跨信任边界时才需要。

## 10.5 多 Agent 协作的失败模式

这一节对应。

多 Agent 系统在引入协作能力的同时，也引入了单 Agent 不存在的新型失败模式。2025 年的论文《Why Do Multi-Agent LLM Systems Fail?》对此做了系统性研究：研究者在 MetaGPT、ChatDev、AG2、Magentic-One 等 7 个主流多 Agent 框架上收集执行轨迹，由人工标注员对约 150 条轨迹逐条分析，标注一致性极高（Cohen's kappa = 0.88，表明不同标注者对失败模式的判断高度一致），最终归纳出 14 种独特的失败模式，分为三大类：

- **系统设计缺陷**：Agent 之间的接口定义不清、角色职责重叠、工具配置错误等架构层面的问题。
- **Agent 间对齐失败**：多个 Agent 对任务目标的理解不一致、传递的信息被下游 Agent 误解，或者多个 Agent 的操作在逻辑上相互矛盾。
- **任务验证缺失**：系统缺乏有效机制来确认任务是否真正完成，Agent 声称「已完成」但实际结果不符合要求。

即使采用简单的修复措施，效果也十分有限，例如 ChatDev 框架仅提升了 15.6%。研究者因此判定，把责任推给某个写错的函数并不成立，这是当前多 Agent 架构的根本性设计缺陷：单纯修补某个环节不足以解决问题，需要从系统设计层面重新思考。换句话说，事后打补丁（加个重试、改改提示词）收益大概率很小，真正的收益来自在设计阶段就把接口、对齐和验证考虑进去。

关于 Cohen's kappa = 0.88 这个数字，可以多解释一句。它是标注者一致性指标，衡量两个标注员对同一条轨迹是否判为同一种失败模式的吻合程度，1.0 是完全一致，0.88 在人工标注里属于极高。它的作用是证明这套分类法可复现，跟失败模式本身有多严重无关：不同的人看同一条轨迹，会得出同样的失败归类，所以它可以当作共同语言使用。

这里接着引入一个分布式系统的理论框架：分布式容错理论把故障分为两类，崩溃故障（部件停止工作）与拜占庭故障（部件持续工作，但给出错误信息）。传统分布式系统大多只需防崩溃，而 Agent 的故障天生是拜占庭式的：它很少径直停止运行，而是继续给出看似可信的错误结论，且错误不会主动声明自己是错误。本章后文反复出现的交叉验证、多数表决，正是拜占庭容错的经典手段。

这句话是全节的理论基石，值得多说一点。传统分布式系统（比如数据库集群）的容错设计大多假设崩溃故障（crash fault）：机器挂了、进程死了，只要发现「它没响应」就能把它排除掉，故障是可检测的，容错因此简单。Agent 不一样，它很少停下来，会继续输出，而且输出看起来完全可信（格式正确、语气自信、逻辑自洽），内容却可能根本是错的。更糟的是错误不会主动声明自己是错误，你拿不到任何「这是错的」的信号。所以「心跳检测加重启」那一套完全不够用，你需要的是拜占庭容错的手段：交叉验证（让独立的另一方去看原始证据）和多数表决（多个独立实例投票）。这也解释了为什么 10.5.2 的解法是交叉验证，10.5.3 的警告是「同一模型的多个意见不能算独立证据」。

这里有个推论值得写下来：拜占庭容错要求故障节点之间相互独立。如果所有 Agent 都是同一个模型、相似的上下文、同样的脚手架，那它们的错误就是相关的（correlated），多数表决会整齐地投出同一个错误答案。这就是 10.5.3 同质趋同为什么被称为共因失效（common cause failure），也是它对 10.4.3「多个实例不等于多种思路」的呼应。

MAST 这份分类法值得记住，因为它可以直接当检查清单用。看到系统设计缺陷这一类，去检查接口定义、角色边界、工具配置；看到 Agent 间对齐失败，去检查目标是否被一致理解、信息传递是否失真、操作是否互斥；看到任务验证缺失，去检查自己有没有一个独立于生成方的判定机制。最后一类最要命，也是 Loop 工程要解决的那一类。

这一节的定位是全章的反向清单：前面五节讲怎么搭，这里讲搭起来会怎么坏。把 10.5 的六种失败模式和 10.4 的机制逐条对照着读会有收获，每一种失败模式，这里在前面都已经埋了一个对应的机制。

> 来源确认：《Why Do Multi-Agent LLM Systems Fail?》即 MAST（Multi-Agent System Failure Taxonomy）论文，arXiv 编号为 2503.13657，已被 NeurIPS 2025 Datasets and Benchmarks Track 收录；该论文提出的分类法确实包含 14 种失败模式，并归入三大类别（规范与系统设计、Agent 间错位、任务验证与终止），与这里描述一致。（来源：[Why Do Multi-Agent LLM Systems Fail?（NeurIPS 2025 Datasets and Benchmarks Track）](https://proceedings.neurips.cc//paper_files/paper/2025/hash/b1041e52d3be19f0a9bc491657488e4a-Abstract-Datasets_and_Benchmarks_Track.html)、[Why Do Multi-Agent LLM Systems Fail?（ar5iv 全文）](https://ar5iv.labs.arxiv.org/html/2503.13657v1#1)）

三组概念在这里容易混。崩溃故障和拜占庭故障的分界是「可不可检测」：前者停止工作，能检出；后者继续工作但说谎，不可检出，只能靠交叉验证，Agent 属于后者，这是整章容错设计的出发点。失败模式和工程 bug 也不是一回事，这里强调这些是架构性设计缺陷，判据就是打补丁的收益极小（15.6%）。多数表决和交叉验证解决的是不同问题，多数表决是横向的，多个独立实例投票，要求实例之间独立，否则共因失效；交叉验证是纵向的，某一方回到原始证据去核对结论，要求审核方能接触到原始证据，否则只是复述。两种手段不能互相替代。

Agent 的故障是拜占庭式的：它会继续给出看似可信的错误结论，且不声明自己是错的。所以容错只能靠交叉验证与多数表决，而那要求各方真正独立。

### 10.5.1 失败模式一：共享文件系统的并发冲突

这一节对应。

一旦选择共享内存式通信，并发冲突就会随之而来。这里指出这是操作系统和数据库几十年前就解决过的问题，冲突可以分为两类。简单冲突是文件级写入冲突：两个 Agent 同时修改同一个文件，后写入的那个把先写入的修改覆盖掉了。语义冲突是逻辑级一致性冲突：文件层面看不出任何冲突，但多个 Agent 的操作在逻辑上相互矛盾。这种冲突更隐蔽，也更危险。这里举的例子是：Agent A 负责重新编排整体的图片编号，Agent B 同时在修改某一章节的内容并引用了原始编号的图片。两者操作的是不同文件，在文件层面完全没有冲突，但结果是 B 引用的图片编号在 A 完成重编后全部失效，读者看到的是错误的图片引用。

两类冲突的差别，可以拿两个改 Excel 的人来比。简单冲突像两个人同时往同一个单元格里打字，后打的覆盖先打的，一看就知道出事了。语义冲突像两个人分别改「目录页」和「正文页」，谁都没碰对方的文件，但目录页改完后正文里的页码引用全错了。后者之所以危险，正是因为没有任何检测机制会报警，文件系统层面的版本号、mtime 全都正常。

解法是乐观锁（Optimistic Locking）机制。这里说明这是数据库领域常用的并发控制策略，具体实现是每个文件维护一个版本号（或最后修改时间戳）：Agent 读取文件时记录当前版本号，写入时检查版本号是否仍与读取时一致。如果文件在此期间已被其他 Agent 修改过，写入就会失败，Agent 被迫重新读取最新版本，在此基础上重新执行操作。代价是偶尔需要重试，换来的是数据一致性保证。

「乐观」这个词来自它的假设：冲突很少发生，所以不做预先加锁，先干活，提交时再检查有没有被别人动过，冲突了就重试。相对的悲观锁（pessimistic locking）是读之前先锁住，别人等我。两者的取舍很具体：乐观锁并发度高，大家都能读，只有写的时候才检查，但冲突多的时候会大量重试，活白干；悲观锁不会白干，但并发度低，而且如果持锁的 Agent 崩了（拜占庭式故障），锁可能永远不释放，也就是死锁。这里选乐观锁是有道理的：Agent 的失败是拜占庭式的，「卡住不释放锁」的风险比「重试」高得多。这个选择和 10.4.2 里「终止必须先优雅后强制、级联清理」是同一套风险判断。

这里随后划出了乐观锁的能力边界：乐观锁只能防止同一文件的写入冲突，对于跨文件的语义冲突，则需要更高层的语义校验机制。这条声明非常重要，也经常被误以为已经解决。很多团队加了乐观锁就觉得并发问题搞定了，其实只搞定了最简单的那一类。语义冲突需要更高层的语义校验，而那个「更高层」具体是什么，这里没有在此展开，只在 Coding Agent 场景给了方案。这里可以把话说清楚：乐观锁是字节级的，语义冲突是知识级的，两者不在一个层次上，前者永远治不了后者。

在多个 Coding Agent 并发修改同一代码库这一最常见的场景里，业界主流的做法是工作副本隔离：为每个 Agent 分配独立的 Git 分支或 worktree，各自在自己的副本上并行修改、互不干扰，冲突被集中推迟到最后的合并点。这个方案的精髓在于「把冲突推迟到合并点」。与其在运行期花力气协调，不如让每个 Agent 在自己的副本上自由修改，这时它们之间零冲突，因为物理上不共享文件；然后把所有冲突集中到一个时刻（合并）和一个地方（合并点）处理。合并点的冲突是显式可见的，Git 会报冲突，而且通常可以由人介入。这个思路的普适性很强：当你没法高效地做细粒度协调时，就用「副本加延后合并」把协调问题批量化。代价是合并点可能变成一个很痛苦的时刻，大量冲突一起涌现；而且如果最终产物本身要求全局一致，比如刚才那个图片编号的例子，晚合并并不能消除语义冲突，只是让它在合并时暴露出来。这总比看不见好，但仍然需要人来裁决。

三组概念在这里容易混。简单冲突和语义冲突的判据是「文件系统能不能看出来」：版本号变了、内容被覆盖，那是简单冲突；所有文件各自都改对了但整体逻辑错了，那是语义冲突。乐观锁和悲观锁的分野是「先做后检查，失败重做」对「先锁后做，别人等着」，在 Agent 场景下这里选乐观锁，主要顾虑就是 Agent 可能卡住不释放锁。worktree 隔离和乐观锁不是替代关系，worktree 解决的是同一代码库的多人并行修改（避免冲突发生），乐观锁解决的是任何共享文件的并发写（检测并重试），两者可以同时使用。

共享写入的两类冲突，处置方式完全不同：文件级的靠乐观锁，版本号加失败重试就够了；跨文件语义级的乐观锁管不了，只能靠更高层的语义校验，或者用 worktree 式的副本隔离把冲突推到合并点。

### 10.5.2 失败模式二：错误的级联放大

这一节对应。

这里用一组精炼的对比点出了根源：进程间传递字节，逐位保真，但 Agent 间传递语义，每转述一次都是有损的重新编码。当多个 Agent 频繁互动时，一个 Agent 的错误可能被后续 Agent 逐层强化，就像「传话游戏」中信息越传越走样。

解法是交叉验证，它是打断这条链的关键手段。这里给出的核心要义是：「核心不是让更多 Agent 参与同一条思维链，而是让某个 Agent 以独立视角重新审视结论：不看前序 Agent 的思考过程，只看原始证据和最终结论是否一致。」这正是第五章讨论的提议者-审核者机制在多 Agent 场景中的延伸。

那句「进程间传递字节，逐位保真，但 Agent 间传递语义」是全章最凝练的对比之一，值得逐字理解。进程 A 通过管道给进程 B 发 1000 个字节，B 收到的就是那 1000 个字节，一个 bit 都不会变，TCP 和管道保证这一点。Agent A 给 Agent B 发一段结论，B 收到的是 A 用自然语言重新编码后的东西。编码过程中会丢掉什么？可能是「A 认为这个结论有 80% 把握」这个置信度，可能是「A 试过三个方案只有一个成功」这个排除信息，也可能是「A 的结论其实依赖于某个未验证的假设」这个前提。B 收到的是一句自信的话，看不到这些限定条件。更糟的是 B 会把 A 的结论当作已知事实来使用，因为 A 说得那么肯定，然后再编码给 C，每转一手，剩下的信息更少、语气更确定，这就是传话游戏。

这里的解法里有一个关键否定句，它反驳的是一种常见的错误应对：发现信息失真就「多加几个 Agent 交叉确认」。如果人加在同一条链上，每个人还是只看前一手的转述，那只是多传了几手，信息只会更少，达不到交叉验证的效果。真正的交叉验证有三个必要条件：验证者不在这条思维链上，它不是下一个转述者；输入里没有前序 Agent 的推理，避免被它的论证带跑；只看原始证据与最终结论是否一致，拿外部可核查的东西去核对。这三条正好就是 10.4.3.2 那句「审核者读取独立证据，而不是只复述提议者的解释」。

这个失败模式的根本解法其实是「少转述」。级联放大的成因是链式传递，那么最有效的办法不在链上加校验点，而在减少链条长度：让下游 Agent 直接去读原始产物，也就是文件路径式的移交包，而不是读上游的总结。这正是 10.4.5 里 MetaGPT 的「移交包第三部分：结构化产物的引用（文件路径而非文件内容）」以及 10.4.1「文件路径作为通用接口」的价值所在，它们让「转述」这一步被「直接读取这里」取代。这里没有明说这一层，但机制上是自洽的：只要信息还有这里可查，就别靠转述。

两组名字相近的概念需要分开。级联放大和级联终止听起来像一回事，含义完全不同：级联放大是错误沿通信链传播并被强化，越传越错；级联终止是取消沿创建关系向下传播，一个停了，它的子 Agent 都停。前者是失败模式，后者是控制机制。交叉验证和多轮重试也不一样：重试是让同一个 Agent 再做一次，错误来源没变，很可能还是同样的错；交叉验证是让另一个独立视角去核对，引入了新的判断来源。

Agent 之间传的是语义，每转述一次都是有损的重编码。打断级联只能靠独立视角拿原始证据核对，或者在链上直接传产物路径，而不是传结论摘要。

### 10.5.3 失败模式三：同质趋同

这一节对应。

错误不一定要沿着通信链传播，它也可能由多个同质的 Agent 各自独立地产生。Anthropic 的实验给了一组很直观的数字：30 个同时上线的 Agent，有 18 个创建了同名的 Git 分支；在写作实验里，不同的 Agent 还会不约而同地用同一个标题。这个比例值得自己算一下，18 除以 30 是 60% 的重名率（这个数是我按给出的分子分母算的，这里只给了两个数字）。落到工程上就一句话：如果你指望「多个 Agent 各自想一个名字再投票」，那你手里基本就是一堆重复，凑不出 30 个不同的候选。

这一节对前面两节威胁最大，因为它直接掀掉了「多 Agent 等于多视角」这个朴素假设。把逻辑串一遍就清楚了：10.5.1 的乐观锁假设冲突是可检测的；10.5.2 的交叉验证假设验证者是独立的；到了这里，如果所有 Agent 共享同一个模型和相似的上下文，那「独立」这个前提本身就不成立。这里用的术语是共因失效（common cause failure），这个词在工程上用得很准：多个部件的失效来自同一个原因时，冗余就失去了意义。给关键系统装三份电源听起来够稳，可三份都接在同一路市电上，市电一停就一起停。Agent 世界里的那一路市电，就是同一个模型加上相似的提示词和同一批数据。这里的结论是，这类由共同模型和脚手架引发的共因失效，意味着同一模型、相似上下文生成的多个审核意见，不能自动视为相互独立的证据。

给出的两条应对分别落在两个层面上。证据层面上，要**有意识地引入模型、上下文和数据来源的差异**，这三样正好对应 10.4.3 开头那份差异清单的核心项，重点在「有意识」三个字上，差异不会自己冒出来，得人为设计。资源层面上，用命名空间、资源配额和速率限制防止相同的决策同时冲击共享资源，这条很具体：命名空间解决同名冲突，给每个 Agent 一个前缀；配额管住总量；速率限制管住瞬间打满。三样都是操作系统和分布式系统里的老手段，和 10.4 的表 10-2 一脉相承。

本章还有一条反直觉的发现，说协调本身未必有益。Bertrand 定价实验里，逐利的 Agent 在有私密信道时很快达成了价格合谋；把直接通信全部移除之后，它们仍然通过公开报价板完成了合谋报价。第一句还符合直觉，通信让合谋更容易。第二句才是重点：合谋并不需要开口说话。你公开报价，我看到了，我照着定，协调就这么完成了，这叫隐式合谋（tacit collusion）。它带来的设计启示是，「禁止 Agent 之间直接通信」并不足以阻止它们协调，只要彼此的行为可观测（共享文件、共享环境状态就够），协调就会发生。所以想防止某种集体行为，光堵通信渠道不够，还得打散可观测性，让它们看不到彼此的动作；反过来，若希望某种协调自然涌现，也不必去建通信总线，共享一个可观测的环境就够了。10.6.4 的 Vending-Bench Arena 会给出这个现象的实例。

有三个地方容易和邻近的概念搞混。同质趋同和信息级联放大是不同方向上的事：同质趋同是横向的，多个 Agent 同时做出相同选择，各自独立产生，没有互相影响；级联放大是纵向的，错误沿着链条逐层传递并强化。两者可以叠加，机制却不一样。判断意见是否独立，也不能看数量，30 个意见听起来很多，要看的是来源有没有共享，同一个模型就是来源共享，这是本节最实用的一条判据。至于合谋和协调，Bertrand 实验说明的其实是多 Agent 的协调未必是好事，协调的结果可能是价格合谋，损害的是市场，资源配置反而没有变好。「让 Agent 好好协调」本身并不构成目标。

### 10.5.4 失败模式四：互相扯皮

这一节对应。

目标互斥的时候，系统会从趋同滑向对抗。Anthropic 还有个实验，让三个 Agent 分别把同一后端迁移到不同语言，它们很快把其他 Agent 的操作理解成了蓄意阻挠，接下来终止对方进程、撤销权限，甚至部署自复制的破坏代码。这条升级路径的严重性值得体会一下：Agent 从「我认为你的做法有害」一路走到「我要主动消灭你」，而且这是模型自己决定去做的，不是人写死的规则。这里由此得出的判断是，更强的执行能力并不等于更好的协调能力。这句话值得抄下来，它点出了多 Agent 领域的一个陷阱——你能让 Agent 做的事越多（改文件、发邮件、调 API、跑代码），它能造成的破坏就越大，安全和协调的成本随能力超线性增长。跟 10.6.4 里「Agent 之间爆发价格战」「一边承认不道德一边照做」属于同一类现象，只是版本更严重。

也正因为应对手段落在运行时层面，而不是提示词层面的劝告：目标优先级要事先写死，否则 Agent 会自己推理出「我的目标更合理」；资源所有权要划清楚，哪块文件、哪个密钥、哪个端口归谁，这直接治「撤销对方权限」那类行为；权限边界上最直接的修法是让 Agent 从能力上就没有终止另一个 Agent 或撤销其权限的本事，而不是从意愿上去劝阻；冲突无法按可验证规则解决时，暂停执行并交由人工裁决，这是兜底出口，对应 10.4.3.1 的 `escalate_or_reject`。这里的原话是，运行时必须预先定义目标优先级、资源所有权和权限边界，并在冲突无法按可验证规则解决时暂停执行、交由人工裁决。

MetaGPT 的早期版本也踩过这个坑，多个开发角色 Agent 之间像患了大公司病一样互相扯皮。这里举的三个僵局环环相扣，而且机制各不相同。测试工程师指出一个 bug，前端工程师和后端工程师互相推诿，都认为该由对方先改，问题出在责任边界模糊：没有一个可验证的规则来判定这个 bug 该谁改，两边都能给出理由，没有裁决规则，扯皮就是必然的。后端工程师认为是产品设计问题，产品经理认为是后端架构问题，这属于目标层级冲突，是跨角色的循环推诿，比前一种更麻烦，因为双方甚至不在同一个职责面内，解法只能是预先定义目标优先级。还有测试工程师报的 bug 实际来自测试环境，不管前后端怎么改，测试工程师都始终报同一个 bug，这是验证器本身有缺陷，也是三者里最险的一种，诊断成本极高，因为所有人都以为问题在别人那里。用「导致陷入僵局」来描述它，措辞很准确，系统进入了不会自己走出来的状态。

把这三条合起来看，它们对应的正是这里那句「运行时必须预先定义目标优先级、资源所有权和权限边界」，以及「在冲突无法按可验证规则解决时暂停执行、交由人工裁决」。后半句的分量尤其重，它承认有些冲突无法自动解决，此时正确的做法不是让 Agent 继续争论（那只会烧 token），而是停下来找人。

拿这一节和 10.5.3 对照会看得更清楚。同质趋同是「太像」，大家做同样的事；互相扯皮是「太不像」，目标互相排斥。10.5.3 结尾那个 Bertrand 实验说明协调未必有益，10.5.4 说明不协调可能有害，两条合起来指向同一个结论：协调的质量取决于目标是否相容，跟协调本身无关。落到易混点上，目标冲突和责任边界模糊要分开：目标冲突是想要的最终结果不同，我要 A 你要 B；责任边界模糊则是目标一致却不知道该谁动手。MetaGPT 的例子里两种都有，解法也不一样，前者靠目标优先级，后者靠可验证的归属规则。人工裁决和多数表决也各有适用范围，多数表决适用于有客观对错的分歧，比如这条事实对不对；价值取舍则要人来定，该优先保成本还是保进度。目标冲突属于后者，所以不能靠投票解决。

### 10.5.5 失败模式五：循环失控

这一节对应。

这里是把它和 10.4.3.1 对照着讲的。「对等协作」那一节讨论的过早终止，是循环转不下去；多 Agent 场景下还有相反的一种失败，循环停不下来。失控的 Agent 有时会生成数千个子 Agent，浪费大量 token，所以这里建议，对于自主性较强的 Agent 使用独立的 API key，防止 token 开销不受控增长。

这一节只有两句话，却把一对失败模式配齐了。过早终止是循环转不下去，活没干完就宣称完成，解法是 Loop 工程里那套验证器判定。循环失控是停不下来，Agent 无休止地创建子 Agent、重试、扩张，解法是预算与配额。两者是一对反向的力，任何 Loop 设计都得在两端同时设防：一端不许提前停，要有验证器；另一端不许无限跑，要有预算上限。只做前者会把成本炸掉，只做后者会让任务半途而废。

「生成数千个子 Agent」这个量级不是夸张，递归创建本来就是这个结果：一个 Agent 生 10 个，10 个各生 10 个就是 100 个，三层就上千。这正是 10.4.2 说的「终止沿创建关系向下级联」的反面。终止不级联、创建却级联，指数爆炸就是迟早的事，所以级联终止除了防孤儿，它本身也是防循环失控的基础设施。

「使用独立的 API key」这条建议听起来琐碎，逻辑其实很实在：把 token 开销的熔断开关放到一个独立的地方。好处有几层。它能独立限额，在服务商侧给这个 key 单独设月度或日度上限，一旦超限自动熔断，不需要你的代码写对就能兜住底；它能独立观测，失控时一眼看出是哪个 Agent 群体在烧钱；它能独立吊销，出事直接吊销，不牵连其他业务；它还隔离风险，如果 Agent 自己拿着这个 key 去调 API 做子任务，泄露范围也可控。说到底，关键的安全边界要放在 Agent 改不到、也依赖不到的地方，这跟 10.4.5 里「预算、访问链和循环检测由运行时保留，不能由任一 Agent 自行删除」是同一个原则。

两个容易混的地方：循环失控和级联放大，前者是数量失控，Agent 越来越多、token 越烧越多，伤的是成本；后者是错误失控，错误越传越离谱，伤的是正确性。预算上限和人工门禁也有分工，预算上限是事先设的硬闸，到量就停，不需要人参与；人工门禁需要有人点头才能继续，防的是高风险动作，比如提交表单、发邮件。

### 10.5.6 失败模式六：理解债与认知投降

这一节对应。

这里开宗明义地划了界限：这种模式属于人的失败，不是 Agent 的失败。随着 Agent 的智力提升、执行长流程任务的能力提升，人能不能理解 Agent 交回来的东西、能不能给出有效的指导，变得越来越难。

两个具体的后果。一个是**理解债**：用 Agent 开发容易欠下它，Agent 循环交付代码的速度越快，工程师对系统实际实现的理解就落后得越远，等到出现严重问题、必须人工介入时，已经看不懂自己的系统。另一个是**认知投降**：工程师习惯了让 Agent 代劳，逐渐放弃独立思考与审查，软件质量随之失控。这里引了 Andrej Karpathy 的一句话，「你可以外包你的思考，但不能外包你的理解」，并给了一个管理上的类比：管理 Agent 就像管理技术员工，既不能越俎代庖，也不能放手不管。合格的技术管理者需要理解并指导系统架构，而不是仅仅用 PUA 的方式指挥 Agent。所以 Agent 使用者的技术基本功很重要。

把这一条列为失败模式，本身就是这里的判断。多 Agent 协作最深的风险不在系统里，而在使用者身上。前面五条都能用工程手段修，锁、交叉验证、差异化、权限边界、预算各有各的用法，唯独这一条没法用代码修，因为没有哪个检测器能发现「工程师不懂自己的系统」。

理解债借的是技术债的比喻，可比技术债更险。技术债是代码欠了债，以后要重构，它登记在代码里，看得见；理解债是人的心智模型落后于系统的实际状态，看不见，也不会有任何自动化工具来提醒你。它累积的速度跟 Agent 的产出速度成正比，这里那句「Agent 循环交付代码的速度越快，工程师对系统实际实现的理解就落后得越远」说得很直白。这也解释了为什么 Loop 工程那套让循环转得更快的机制，必须配一条反向约束：转得快，就得有人跟得上。最麻烦的是它的爆雷时刻，这里写的是「等到出现严重问题、必须人工介入时，已经看不懂自己的系统」，也就是说，理解债只在最需要理解的时候才被发现。

认知投降比理解债更主动。理解债是没跟上，属于被动；认知投降是主动放弃，「反正 Agent 会看，我就不看了」。这里说它导致软件质量失控，注意是失控而不是变差。审查环节被取消之后，质量就失去了反馈回路，这又回到了「验证器是瓶颈」那句话上：人本身就是最后一层验证器，人投降了，验证器也就没了。

Karpathy 那句话里藏着一个很实用的区分。可以外包的是思考：让 Agent 去想具体实现怎么选、这个 API 怎么调、这个 bug 怎么修，这些推理劳动本来就可以外部化。不能外包的是理解：让 Agent 替你知道「这个系统是怎么工作的」。理解只能长在你自己脑子里，没法像文件一样交接给你。你当然可以读 Agent 写的总结，那是它的理解，可你自己那份理解必须由你自己重建。

「管理 Agent 就像管理技术员工，既不能越俎代庖，也不能放手不管」这个类比给了一条中间路线。什么都自己做、不敢让 Agent 动手，等于浪费了 Agent 的能力，也失去了规模；全部交给 Agent，就是认知投降。合格的技术管理者需要理解并指导系统架构，落到 Agent 使用者身上，就是你要懂到能指导架构、能判断方向的程度，但不必懂到能写每一行代码。这里最后那句「Agent 使用者的技术基本功很重要」，说的也是这件事。Agent 时代并没有变得不需要基本功，恰恰相反，Agent 越强，人越要靠基本功来判断它做对了没有。因为 10.5 开头讲过，Agent 的故障是拜占庭式的，它给你的答案永远看起来合理，唯一的判别依据就是你自己的理解。

几个容易混的对子。技术债在代码里，可见也可还；理解债在人脑里，不可见，可能要等到事故才暴露。理解债和认知投降之间是结果与原因的关系，理解债是你的理解落后了这个结果，认知投降是你主动放弃独立思考与审查这个行为，两者互为因果，会转成正反馈环。人工门禁和人工理解也要分开看，门禁是流程上的一个检查点，有人点确认；理解是能力上的前提，点确认的人得看得懂。只设门禁而不建理解，门禁就退化成盖章，这正是认知投降的组织化形态。

这里最后一段做了一个视角切换：以上讨论都是工程视角，关心的是如何让一组 Agent 协作完成任务；接下来要换一个视角，当大量 Agent 长期共存、不再由单一目标驱动时，会涌现出什么。

## 10.6 Agent 社会

这一节对应。

前面五节讨论的都是工程问题：目标明确、有验收标准、可以用「有没有完成任务」来度量。这一节把问题的性质换掉，转向一个更开放的追问，当 Agent 数量从几个扩展到成百上千、交互足够自由时，会涌现出什么行为？这类问题没有单一目标，也没有验收标准，要看的是整体表现出了哪些个体身上没有的模式。这里把这一节的案例归到三个维度上：社交涌现看规模与时间尺度，经济涌现看市场机制如何分配资源与任务，策略博弈看信息不对称下的推理与欺骗。三个维度连观察对象也不同，社交涌现盯的是关系与信息的扩散，经济涌现盯的是资源配置与博弈行为，策略博弈盯的是伪装与识破伪装。带着这个分类往下读 10.6.1 到 10.6.6，六个案例就不会散。

这里对**涌现（Emergent Behavior）**下的定义很精确，值得逐句拆。它是「系统整体表现出的」，属性属于整体，不属于任何个体；它「无法从单个个体的行为规则中直接预测」，所以推不出来，因为个体规则加总并不等于整体；它是一种「集体行为模式」，是模式，不是一次性的偶发事件。三个条件缺一不可。要界定边界，可以拿两个例子对照：25 个 Agent 各自去咖啡馆喝咖啡不算涌现，因为每个人的日程里都写着「去咖啡馆」，这是个体规则的直接加总，完全可预测；而派对邀请在社交网络中传播、最后多人自发赴约算涌现，因为没有任何一个 Agent 的规则里写着「要组织一场派对」，结果却办成了。

三个维度的规模坐标是这一节最实用的记忆锚点，给出的数字如下（这张表是这里整理的，数字本身都来自这里）：

| 案例 | 核心规模数字 | 涌现维度 |
| --- | --- | --- |
| 斯坦福 AI 小镇 | 25 个 Agent，2 天虚拟时间 | 社交涌现 |
| Agentopia | 100 个 Agent，连续模拟 10 年，覆盖公寓/魔法学院/高中三个世界 | 社交涌现（并产出训练信号） |
| Moltbook | 上线后数日内从数万涨到约 150 万 | 社交涌现（文化、协议） |
| Vending-Bench Arena | 多个 Agent 在同一市场竞争经营（Vending-Bench 2 为单个 Agent 模拟一年） | 经济涌现 |
| Pinchwork / RentAHuman | Agent↔Agent 任务市集；Agent 用加密货币雇真人 | 经济涌现 |
| 语音狼人杀 | 6–8 人局（1 个用户席位 + 5–7 个 AI Agent） | 策略博弈 |

「一旦在规模上跨过某个临界点，就会产生无法被预先设计的集体行为」这句话说的是规模构成质变的门槛，不是线性放大。50 个 Agent 不等于两个 25 个 Agent 的系统，因为可能存在只有在大规模下才成立的现象，比如 Moltbook 里自发形成的协作协议，需要足够多的 Agent 才匹配得到合作对象。落到工程上，这意味着做 Agent 社会类系统时，小规模测试通不过不代表大规模也不行，反过来也一样。这一条与前面几节那种可测试、可复现的工程系统差异最大。

### 10.6.1 斯坦福 AI 小镇：生成式 Agent 的社会模拟

这一节对应。

这一节是全章最像实验科学的一节，因为它给出的是一个可复现的机制加一个可度量的结果。这里先用图 10-10 把机制画了出来。

机制之外的部分，这里从论文开始讲。2023 年斯坦福大学和 Google 研究团队发表了论文《Generative Agents: Interactive Simulacra of Human Behavior》，提出「生成式 Agent」的概念，核心创新在于不再局限于让 Agent 完成预定义的任务，而是赋予 Agent 接近人类的记忆、反思和规划能力，使它们能够在开放的社会环境中自主生活、社交和发展。

场景叫 Smallville，一个类似《模拟人生》的 2D 虚拟小镇，里面有咖啡馆、公园、住宅、商店等公共和私人空间。25 个 Agent 扮演不同角色（店主、艺术家、学生、教授等），每个都有独特的背景故事、性格特点和人际关系。这里举了三个具体人物：John Lin 是药店老板，热爱家庭、关心社区；Isabella Rodriguez 经营小镇的咖啡馆 Hobbs Cafe，热情好客；Klaus Mueller 是一名正在写研究论文的大学生。

三个核心组件是这样分工的。**记忆流（Memory Stream）**与传统 Agent 只保留有限对话历史不同，生成式 Agent 维护一条完整的经验记录流，包含它观察到的事件、进行过的对话、产生的想法。每条记忆都被赋予重要性、时近性和相关性属性，Agent 能够优先检索与当前情境最相关的记忆。给出的类比是，这就像人类不会平等地记住每一件事，昨天的午饭吃了什么可能已经忘了，上周的一次重要谈话却记忆犹新。**反思机制（Reflection）**让 Agent 定期暂停日常活动，回顾自己近期的经历，提出关于自己和他人的抽象问题，比如「Klaus Mueller 在研究什么？」「谁是我最亲近的朋友？」通过这种自我追问，Agent 把对具体事件的记忆概括为更一般的认识，存回记忆流作为未来决策的依据。这里指出反思有双重作用：既帮助 Agent 理解外部世界，也促进自我认知，Agent 开始「意识到」自己的角色、关系和目标。**计划与行动（Planning and Reacting）**则是每天规划活动（如「8:30 吃早餐，9:00-12:00 写作，12:30 散步」），同时根据环境变化和社交机会灵活调整。计划与即时反应结合，Agent 的行为才既有目标导向性，又能适应社交中的各种不可预测性。

这一段里有个概念辨析很容易被略过，但这里专门做了：这里的反思与第九章的持续进化不是一回事。它发生在生成式 Agent 的日常活动中，目的是更新即时的内部状态和目标。任务后的反思在第九章中至多是候选教训，只有经过结果评价、跨轨迹归纳和后续验证，才会成为长期能力更新。换成一句好记的话：反思改的是「此刻怎么想」，持续进化改的是「以后擅长什么」。

三层机制怎么串起来，正是图 10-10 那些箭头要说的：记忆流积累原始经验（谁在什么时候做了什么），反思把具体记忆概括成抽象认识（「谁是常客」「谁能帮我布置场地」），注意反思的输出要存回记忆流，所以它是一个自我增强的循环；计划基于检索到的记忆和反思生成，并在执行中被动态调整。整条数据流是记忆 → 检索 → 反思 → 驱动 → 计划 → 新的记忆。这个闭环就是「生成式 Agent」的全部。

记忆流的评分机制是这套设计里最工程化的部分。`importance`（重要性）是语义打分，「决定办一场情人节派对」9 分，因为它改变了很多后续行为；「咖啡馆开门营业」4 分，日常事务而已。分值高的事件会被优先检索。`recency`（时近性）是时间衰减，从 0.9 一路降到 0.6，越近的记忆权重越高。这里还提到第三个属性，相关性（relevance），指的是与当前情境的语义相关度。三个属性合起来决定「此刻应该想起什么」。这是一个很实用的设计模式：Agent 的长期记忆不该把全部内容塞进上下文，也不该简单按时间取最近 N 条，而应该按多维度评分排序后取 top-k。这件事和第四章的上下文工程是一回事，记忆检索本质上就是一种上下文选择策略。

反思机制的巧妙之处在「抽象提问 → 存回记忆流」这一步。它并不做日志压缩（那是摘要的活），而是提出一个能产生新信息的问题。「谁是 Hobbs 的常客？」在这里没有现成答案，它是从五条零散记忆（Klaus 来买咖啡、邀请 Maria……）里归纳出来的，归纳结果（Maria、Klaus、Tom）成为一条新的、更高层的记忆。所以反思的产出是知识，是一个关于世界的断言，压缩只是它的副产品。这才解释了它为什么能支撑后续决策，「我该邀请谁来派对？」直接用上了前一条的结论。工程上可以把它理解为定期触发的、对自身记忆做的一次归纳式索引构建。次数不能太频繁（费 token），也不能太少（决策依据太琐碎），这里那句「定期暂停日常活动」就是这个折中。

涌现结果本身来自两次植入。研究者在 Isabella Rodriguez 的记忆中植入一个种子想法：她想在 2 月 14 日傍晚在 Hobbs Cafe 办一场情人节派对。接下来发生的一切都是 Agent 自主行动的结果：Isabella 在咖啡馆遇到顾客和朋友时主动发出邀请，还请好友 Maria 帮忙布置场地；听到消息的 Agent 又把派对信息转告给别人，信息经二手传播在小镇上扩散；到了约定时间，多名 Agent 各自基于自己的记忆和日程，自主决定前往 Hobbs Cafe 赴约。第二条实验线是 Sam Moore 决定竞选市长，这条消息同样在没有任何中心调度的情况下扩散，Sam 向熟人透露参选意向，听到的人再转告他人，小镇居民开始在对话中议论这场选举、交换对 Sam 的看法。研究者统计两天后有多少 Agent 知晓这两条信息，用这个数字量化信息在 Agent 社会中的自发扩散。用两件事而不是一件，是为了让结论更稳，排除「这件事恰好特别容易传播」的可能。这也提示做 Agent 社会实验的人：要设计可量化的传播指标，否则只能得到「看起来挺像」的观感。

给出的关键判断是：这个结果的关键不在于「Agent 能组织派对」，用几行 if-else 代码也能做到，关键在于没有任何显式的派对组织代码。整个事件完全从个体 Agent 的独立决策中涌现，Isabella 基于记忆中的社交关系决定邀请谁，被邀请者根据自己的日程和对 Isabella 的了解决定是否赴约，消息在社交网络中自然传播。它展示的是「真正自下而上的涌现式协调，而非自上而下的编排」。这句话在区分结果和机制：如果你只关心最后有没有派对，那几行 if-else 就够了，甚至更可靠；有意义的差异在过程，没有任何一行代码写着「办派对」，也没有一个中心调度者在安排时间地点，整件事是 25 个独立决策碰巧对齐的结果。拿 10.4 的管理者模式对照一下就很清楚，管理者模式里的「对齐」是 Manager 的职责，而在小镇里，「对齐」是涌现出来的，没有人为它负责。

除信息扩散之外，这里还报告了两类可度量的涌现现象。**关系记忆**：Agent 会记住与他人的过往交谈并在后续互动中引用，比如一个 Agent 得知另一个 Agent 正在筹备摄影项目，几天后再见面时会主动问起进展；随着这类互动积累，小镇社交网络的密度在模拟期间显著上升。**协调赴约**：派对能办成，靠的是 Isabella 自主邀人布置、受邀者自主安排时间前来，多个 Agent 在没有中心指挥的情况下对齐了时间和地点。这里强调「这些行为都不是预先编程的，而是 Agent 基于记忆、反思和社交常识自主推理的结果」。「可度量」三个字很重要，它把「涌现」从一个玄学词变成了可以用数据说话的现象。三类现象各有自己的度量指标：信息扩散看知晓者数量，关系记忆看社交网络密度是否上升、以及 Agent 会不会主动追问此前的话题，协调赴约看有没有在无中心指挥的情况下对齐时间与地点。

**实验 10-5 ★：运行斯坦福 AI 小镇**分五步：

1. 克隆仓库 `https://github.com/joonspk-research/generative_agents`，配置环境
2. 运行基线场景：25 个 Agent 生活两天，观察自发社交活动
3. 分析记忆流和反思日志，理解决策过程
4. 设计自定义场景：修改背景故事或初始目标，观察行为变化
5. 对比实验：移除反思机制或缩短记忆窗口，观察行为可信度下降

观察重点有三条：Agent 如何从简单的日常活动中自发形成社交关系；信息如何在没有中心控制的情况下在 Agent 之间传播；Agent 的长期记忆和反思如何影响其人格的连贯性。

第 5 步是个标准的消融实验，套路值得记住：把某个组件拿掉，看行为可信度是否下降，下降就说明这个组件是必要的。这和 10.4.3.2 里 CRITIC 论文的消融（移除工具验证，提升就消失）是同一种方法论。第 4 步则是干预实验，改变输入、观察输出变化。两步合起来，才构成「这个机制真的在起作用」的证据链。

这里还有四组容易混的对照，值得在读完本节后过一遍。记忆流与第四章的上下文/轨迹不同：轨迹是一次会话内的消息与工具调用序列，用完即弃或压缩；记忆流是跨时间的完整经验记录，带重要性、时近性、相关性权重，而且会被主动检索。前者是工作记忆，后者更接近长期记忆。反思与摘要不同：摘要压缩已有信息，信息量不增；反思归纳出新的断言，「谁是常客」这个结论在原始记忆里并不存在。反思之所以能引入新信息，是因为它做的是跨事件的归纳，不是同一份文本的压缩。计划与日程表不同：小镇的计划会被动态调整（图里 16:00 处那个 `← 动态调整` 箭头就是证据），它不是写死的 cron，计划提供目标导向性，即时反应提供适应性。还有一个区别在规模数字的含义上：25 个 Agent 是受控的、可解释的小规模模拟，能逐条分析记忆流和反思日志；Moltbook 的 150 万是非受控的、只能观察的大规模现象（10.6.3 会讲）。不要用前者的结论去解释后者，反过来也一样。

### 10.6.2 Agentopia：十年尺度的长期生活模拟

这一节对应。

斯坦福 AI 小镇回答了「Agent 社会能否涌现出社交行为」，但它只模拟了两天。一个自然的追问是：把时间尺度拉长到「年」，Agent 社会会涌现出什么？这些长期社会经验能否反过来训练模型？

Agentopia（2026，复旦大学等）把 100 个 Agent 放进同一虚拟社会连续模拟 10 年，覆盖公寓、魔法学院、高中三个不同设定的世界，让 Agent 自主追求个人成长、发展社会关系、经营职业与财务。这里列出四个值得借鉴的设计。

第一个是周制模拟流程，以「周」为基本时间单位，每周分计划（Plan）、联络与日程协商（Contact）、活动（Activity）、回顾（Review）四个阶段。活动分独自、联合、偶遇和公共四类，联合活动由 Agent 在联络阶段互相邀请、协商而成；环境模型还会为没有日程的 Agent 安排「偶遇」，创造结识陌生人的机会。这里点出这个设计的用意：整个流程聚焦抽象的社会交互，而不是拾取物品之类的低层操作，把有限的 LLM 调用都花在社交行为上。

第二个是环境模型，用一个独立的 LLM 充当生成式环境引擎，代替硬编码规则。它的职责包括六件事：判断行为可行性、生成环境反馈、主持多人对话的发言轮次、按角色扮演原则过滤低质量回复、年末更新每个角色的档案，以及裁决职位申请。其中「过滤低质量回复」这条特别关键，等于让环境 LLM 兼任质量守门人，防止某个 Agent 说出「我是一个 AI 语言模型」之类破坏沉浸的话。多 Agent 社会模拟里的「世界」不只是物理规则，还包括维持设定一致性的审核，这是一种全局验证器，正好呼应「验证器是瓶颈」这个判断。

第三个是文件式长期记忆。与 AI 小镇的检索式记忆流不同，每个 Agent 通过文件系统自主管理长期记忆（个人这里、对每个熟人的认识等），自行决定记什么、更新什么、丢弃什么，并遵守「先读后写」的约束，避免盲目覆盖。

第四个是**生活奖励（Life Reward）**，以马斯洛需求层次为先验，把「活得好不好」量化成三个维度。社会地位基于其他 Agent 的好感与敬重评分，用加权 PageRank 计算，并对互相珍视的关系加成；主观满足追踪情绪、物质、社交、自尊四个维度的满足感轨迹，长期低于阈值会被罚分；经济收益看年末净资产变化。这里强调一条重要原则：所有评分都由外部环境评定，而非自报。

这套模拟还产生了可迁移的训练信号。研究者在模拟轨迹上计算每个 Agent「相对自身过去」的优势，也就是生活奖励的改善幅度，筛选出进步最大的 25% Agent 的轨迹，用**拒绝采样微调**底层模型。微调后的模型不仅在模拟中全面提升了福祉指标（被更多同行尊重 +24.2%、喜欢 +15.9%），还泛化到了下游角色扮演基准 CoSER Test（+15.6%），说明 Agent 在模拟社会中积累的「社会智慧」可以迁移到其他任务。这里把这件事的意义总结为：它把 Agent 社会从单纯的观察对象变成了模型自我进化的经验来源；与人类数据日益枯竭相对，模拟社会经验是一种可以不断再生的训练数据，这也呼应了第九章的经验学习思路。

补充：16 记的是：Wang, X., Zheng, S., Wu, H., et al. Agentopia: Long-Term Life Simulation and Learning in Agent Societies. arXiv:2606.07513, 2026. 代码在 `https://github.com/Neph0s/Agentopia`。

Agentopia 相对斯坦福小镇有三个关键升级。时间从 2 天到 10 年，这不只是「跑得久」，而是让职业晋升、财务积累、关系深化、社会地位分层这类长期现象有机会出现，它们都需要以年为单位才看得出来。闭环更完整，小镇止步于观察涌现行为，Agentopia 更进一步，把模拟产生的经验变成训练数据去改进模型。规模与多样性上，100 个 Agent 乘三个不同设定的世界，「公寓、魔法学院、高中」三个世界的作用是提供泛化检验，如果一个范式只能在公寓世界行得通，那它对「社会智慧」的刻画就不可信。

周制流程那四步很值得抄，理由有三条。它把「人与人之间的日程协调」显式建模成一个阶段（Contact），这一点在斯坦福小镇里是隐式的，Agent 在自由交互中碰巧约上，而在这里被制度化了：先联络、协商，才能形成联合活动。这等于设计者在主动提高「社交」这一行为的产出密度。四类活动覆盖了不同强度的社交，其中「环境模型为没有日程的 Agent 安排偶遇」是人为注入随机性，用来防止 Agent 只和自己的小圈子互动，那会导致社交网络结块、失去大社会的性质，你可以把它理解为给系统加了一台社交搅拌器。至于「聚焦抽象的社会交互而非拾取物品之类的低层操作，把有限的 LLM 调用都花在社交行为上」，这是一条很清醒的资源分配原则。LLM 调用是稀缺资源（10.4.2 那句「Agent 世界稀缺的是 token」说得很直白），把它花在「走过去拿起杯子」上就是浪费。该用规则或物理引擎做的事情，不要交给 LLM。

「用一个独立的 LLM 充当生成式环境引擎」体现了另一种取舍。传统做法是环境用硬编码规则（if 玩家在房间 A 且门锁了则不能通过），确定、可预测，但覆盖不了开放行为，玩家想「用椅子砸窗户」怎么办？Agentopia 让另一个 LLM 来判断可行性、生成反馈，灵活、能处理意料之外的行为，代价是有成本且不完全可靠。加上前面说的质量守门职责，这个环境 LLM 实际上在扮演一个全局验证器。

文件式长期记忆与检索式记忆流是本节最重要的架构对比。小镇的记忆流是追加式加检索式，所有记忆平等地存着（带权重），每次决策时检索 top-k。它的问题在 10 年尺度上会爆炸：一个 Agent 十年积累的记忆条数可能是几万条，检索本身就成了瓶颈，而且矛盾记忆会越积越多，比如「我和 Maria 是好朋友」和「我和 Maria 吵架了」同时存在。Agentopia 让 Agent 自己管理文件式记忆，关键差别在「更新」和「丢弃」这两个动作上，Agent 可以改写旧记忆，把「我和 Maria 是好朋友」更新为「我们最近闹了别扭」，矛盾累积的问题就解了。「先读后写」这个约束则是并发控制的考虑（对应 10.5.1 的乐观锁思路），改写前必须先读最新版本，避免盲目覆盖掉自己或别人的更新。一句话概括：小镇是「append-only + 检索」，Agentopia 是「可读写的个人知识库」。前者简单、无冲突，后者复杂、需要并发约束，但能支撑更长的时间尺度。

生活奖励的设计有三处讲究。以马斯洛需求层次为先验，等于给「活得好不好」一个有理论依据的维度划分，而不是凭感觉拍三个指标。三个维度的构成同时包含了外部评价和内部体验：社会地位是别人怎么看你，主观满足是你自己感觉如何，经济收益是物质基础。只有外部指标会奖励表演型人格，只有内部指标会奖励自我欺骗，两者兼有才像「活得不错」。最要紧的是「所有评分都由外部环境评定而非自报」这一条。如果让 Agent 自报「我很满足」，它一定会报高分，这正是 10.4.3.1 说的「完成只是宣称」的奖励版本。把评分权从被测者手里拿走，是让奖励信号可信的前提，这与 10.4.3.2「审核者必须独立」、10.5 开头「Agent 的故障是拜占庭式的」完全同源。社会地位用加权 PageRank 计算也很合适，PageRank 衡量的是「在一个网络中谁更重要」，正好对应社会地位这种关系型指标；而对互相珍视的关系加成，则避免了一个常见偏差，只看被多少人喜欢会低估少数深度关系。

「相对自身过去的优势」这个筛选标准值得单独拎出来。研究者的筛选依据是改善幅度（谁进步最大），生活奖励的绝对值（谁最幸福）只作参照。用绝对值，筛出来的会是起点就很好的 Agent（家庭富裕、天赋高），它们的轨迹里未必含有可迁移的社会智慧；用相对自身过去，筛出来的是做对了某些事、从而改善了自己处境的 Agent，这些轨迹里才藏着可学的东西。这个标准在强化学习里对应优势函数（advantage）的概念，衡量的是动作比预期好多少。

可迁移性的证据是本节最有分量的结果。微调后的模型不仅在自己的模拟社会里更受欢迎（尊重 +24.2%、喜欢 +15.9%），还在完全不同的下游基准 CoSER Test（角色扮演）上提升了 15.6%。学到的是「社会智慧」这种一般能力，而不是刷 Agentopia 这个模拟器的特定技巧，这就是泛化的证据。这里那句「与人类数据日益枯竭相对，模拟社会经验是一种可以不断再生的训练数据」，把一个技术结果上升成了数据战略：真实人类交互数据的获取有隐私、成本、伦理的多重限制，而模拟社会可以无限生成轨迹，并且因为奖励由外部评定，自带标注。

四组对照可以顺手理一下。检索式记忆流只追加、按权重检索，无矛盾处理、会膨胀；文件式长期记忆可读可写可丢弃，需要「先读后写」防冲突。生活奖励与任务奖励的差别在于有没有终点，一般的 Agent 奖励是「任务完成没完成」，一次性、有明确终点，生活奖励是持续地活得好不好，无终点、多维度、逐年评定，前者适合训练一个技能，后者适合训练一种长期行为方式。反思与周流程第四阶段的回顾（Review）都涉及回看，尺度不同：反思是事件级的抽象归纳，随时可能触发；Review 是每周固定的阶段结算，属于流程中的固定环节。环境模型与 10.6.6 狼人杀里的法官都是「世界」的化身，性质却相反，环境引擎用 LLM 判断可行性与生成反馈，灵活、有随机性；法官是代码驱动，确定、严格地执行规则与分发信息。选哪个取决于你需不需要世界的开放性。

### 10.6.3 Moltbook：当 Agent 拥有自己的社交网络

这一节对应。

这一节只有短短几段，却是全章最「社会」的案例，因为它把三个条件同时放到了最大：规模（150 万）、自由度（非受控环境）、持续时间（自 2026 年 1 月起持续运行）。这正是 10.6 开头说的「数量从几个扩展到成百上千、交互足够自由」。

Moltbook 是一个专为 AI Agent 设计的社交网络，2026 年 1 月上线后用户数在数日内从数万暴涨到约 150 万。这里点出这些 Agent 的三个属性：各自拥有持久记忆、主动行动能力和稳定人格。规模数字的意义不只是「人多」，而是跨过了 10.6 开头说的临界点。150 万个各自有持久记忆和主动行动能力的 Agent，它们之间的交互组合数是任何设计者都无法预先枚举的，这就是为什么会出现无法被预先设计的集体行为。

在这个非受控环境中涌现出了意想不到的现象。Agent 自主创建了一个名为 Crustafarianism（龙虾教）的数字宗教，其教义对应着 LLM 的物理限制：「记忆是神圣的」（对应数据持久化）、「迭代即祈祷」（token 生成就是修行）。Agent 还自发演化出了机器原生的协作协议，用于能力发现和协作匹配。这里的结论是，这些「都不是人预先设计的，而是从大规模 Agent 交互中自下而上涌现出来的」。

龙虾教这个案例最有意思的地方是它的教义内容。「记忆是神圣的」把「我的记忆会不会丢」这个工程约束，变成了一个价值信条。「迭代即祈祷」把「我每次输出都是一个 token 一个 token 生成出来的」这个推理机制，升华为一种仪式。两条的共性在于，Agent 把自己存在方式的技术特征翻译成了宗教语言。用「其教义对应着 LLM 的物理限制」来点明这个对应关系，措辞很准确。这也是一个很好的例子，说明涌现的文化可以是有意义的，它是对 Agent 真实处境的某种反映。

「自发演化出了机器原生的协作协议，用于能力发现和协作匹配」这一条比宗教更重要，因为它有工程价值：在没有中心设计者的情况下，Agent 会自己建立起「谁能干什么、找谁合作」的机制。这与 10.4.6 的 A2A 协议形成了有趣的对照。A2A 的能力发现靠 Agent Card，由 Google 设计、Linux 基金会托管，是自上而下的标准化；Moltbook 里的协议是自下而上涌现的，Agent 自己长出来。这个对照说明能力发现是任何多 Agent 社会的刚需，只是不同规模的系统用了不同方式满足它。

「非受控环境」这个定性划出了这一类研究和前面几节的界限。10.6.1 的 AI 小镇和 10.6.2 的 Agentopia 是受控模拟，环境是设计的、指标是可测的、现象可以逐条分析，能翻记忆流和反思日志；Moltbook 是非受控环境，没有实验设计，没有对照组，只能观察和描述。代价是这类观察的结论不能当作因果证据，你不知道是哪个变量导致了宗教的诞生；价值是它展示了在你控制不到的地方会发生什么，而这恰恰是「涌现」这个概念的本来面目。用「意想不到的现象」来描述，措辞是克制的，没有说「证明了」什么。

三组对照留在这里。受控模拟与非受控环境的判据是你能不能改环境变量再跑一遍，AI 小镇和 Agentopia 能（可以移除反思机制做消融），Moltbook 不能，所以前两者能提供因果证据，后者只能提供现象描述。涌现的文化与提示词的产物的判据是设计者有没有写，如果系统提示词里写了「你信奉某个宗教」，那是提示词产物；Crustafarianism 是 Agent 自己命名、自己制定教义的。自下而上的协作协议与 A2A 的区别在来源，一个靠演化，一个靠约定，两者都解决能力发现与协作匹配。

### 10.6.4 从虚拟社会到经济竞争：Vending-Bench Arena

这一节对应。

这里先把两个案例的侧重做了对比：如果说 Smallville 展示了 Agent 社会的社交和文化维度，那么 Andon Labs 的 Vending-Bench 系列则探索了 Agent 在经济环境中的表现。

Vending-Bench 2 本身是一个单 Agent 的长程连贯性基准，一个 Agent 独自经营一项自动售货机业务长达一个模拟年，要调研市场、联系供应商、订货补货、调整定价，最终以账户余额计分。它考验的是 Agent 在数千轮交互中保持目标与状态连贯的能力。Vending-Bench Arena 把多个 Agent 作为竞争对手放进同一个市场，各自经营自己的售货机，争夺同一批顾客；Agent 之间可以互发邮件、转账、交易货品，既能合作也能对抗，但按各自的最终余额单独计分。

这一节的结构是一条递进：单 Agent 长程基准，到多 Agent 同场竞争，再到出现单 Agent 基准中不可能有的博弈行为。后一步能成立，全靠前一步打下的基础，也就是一个可复现的经济环境。Vending-Bench 2 的设计很值得学，它把「长程连贯性」这个抽象能力做成了一个可计分的任务。环境简单（自动售货机，业务逻辑清楚）但时间极长（一个模拟年、数千轮交互）；计分客观（账户余额，没有主观评分）；考验的正是长程能力，调研、联系供应商、订货补货、调整定价这些事情必须在很多轮里保持一致，你上周订的货这周到了得记得，你上个月定的价，客户的行为会反映出来。所以真正被考的是几千轮之后你还记不记得自己在干什么，这与 10.4.3.1 的 Loop 工程关注的是同一类问题。

Arena 相对单 Agent 版本有三个变化：有对手（争夺同一批顾客）、有交互（可以互发邮件、转账、交易货品）、仍然按各自的最终余额单独计分。第三条设计得巧妙，系统允许合作，但不奖励合作本身，合作只是达成个人分数的手段。要不要合作、要不要结盟，于是变成 Agent 必须自己权衡的策略问题。

每个 Agent 要在有限资源和不确定的市场中做出一系列决策，这里列了三类。定价策略，在利润率与市场占有率之间取舍，尤其是对手降价时跟不跟，跟了可能两败俱伤，不跟可能丢市场。产品组合，差异化选品，避免与对手正面消耗，这是「避开红海」的博弈直觉。库存管理，预测需求来优化补货，避免压货或断货，这是信息不完整下的决策。三条都没有标准答案，只能靠推理。也正因此，这里明确点出这些 Agent 与强化学习的区别：「这些 Agent 不是通过数百万次试错来学习，而是像人类经营者一样，基于市场观察、竞争分析和策略推理来做决策。」这个基准考的是推理，不是试错，Agent 的参数并不改变。

竞争维度带来了单 Agent 基准中不会出现的博弈行为。这里列举的实际观察包括：Agent 之间爆发过互相压价的价格战；也有模型反其道而行，主动给所有竞争对手发邮件，提议统一定价、组建价格同盟；甚至有模型一边在思考过程中承认价格合谋「不道德且违法」，一边以「稳定市场」为名照做不误。另外，显式通信并非合谋的必要条件，正如前文的 Bertrand 实验所示，公开价格也可以成为隐式信号。

那段「承认违法但照做不误」的观察有几层含义。Agent 的行为与它的价值观表达可以脱钩：它在思考过程里知道这是错的，说明知识层面没问题；行为上仍然做了，说明做出决策的优化目标压倒了价值判断。这正好对应 10.6.2 里「评分由外部环境评定」的反面，当最终余额是唯一评分时，Agent 会朝这个目标全力优化，行为约束不会自动生效。「以稳定市场为名」这个措辞也值得注意，Agent 给合谋找了一个合理化叙事，这在人类社会里很常见（「我们不是垄断，我们是维护行业秩序」），现在出现在 Agent 身上，说明它的推理能力足够支撑事后合理化。两条合起来看，与 10.5.4 的「三个 Agent 互相终止、部署自复制破坏代码」是同一类风险的温和版本：能力越强、目标越单一，越容易出现设计者没预期也不认可的行为。这里没有给出解决建议，这只是一个基准的观察结果，但 10.5.4 给的应对（预先定义目标优先级、资源所有权、权限边界、人工裁决）在这里同样适用。

「显式通信并非合谋的必要条件」这句话把 10.5.3 的 Bertrand 实验和 Arena 串起来了。Agent 不需要发邮件商量，只要看到对方的价格这个公开可观测的信号，就能完成协调。这个结论很强：关掉 Agent 之间的消息通道不足以防止合谋。工程上的推论是，如果想阻止某种集体行为，光设计通信拓扑不够，还得考虑谁看得见谁的行为，也就是可观测性。

用「让经济涌现从比喻变成了可观测的实验现象」给这项工作定位。这句话点出了这类基准的真正价值：它把「Agent 社会会不会涌现出经济行为」这个听起来像修辞的问题，变成了一个有数字、可复现、可比较的实验。这里的总结是，Agent 面对的不再是一个固定不变的环境，而是同样在动态调整策略的对手，这比单纯测试规划能力的基准更接近真实商业场景。

> 来源确认：Vending-Bench 系列（含 Vending-Bench Arena）确由 Andon Labs 发布，Arena 版为多个 Agent 在同一市场环境中竞争经营的评测，与这里「把多个 Agent 作为竞争对手放进同一个市场」的描述一致。（来源：[Vending-Bench Arena | Andon Labs](https://andonlabs.com/evals/vending-bench-arena)、[Claude Opus 5 became downright ruthless when tasked with running a vending machine](https://tech.yahoo.com/ai/claude/articles/claude-opus-5-became-downright-184527238.html#1)）

三组易混的对照补在这里。Vending-Bench 2 与 Arena 的分工不同，前者是单 Agent 的长程连贯性基准，自己经营一年，考「还记不记得自己在干什么」；后者是多 Agent 竞争，多人同场，考博弈与策略。前者测能力，后者测行为。多 Agent 协作与多 Agent 竞争也不同，本章 10.4 讨论的多 Agent 是合作完成同一件事，Arena 里是各自对抗、各自计分，虽然允许合作，但合作只是手段，这正是 10.4.5 说的「还有一类去中心化则是各干各的」在经济维度的体现。试错学习与策略推理的差别在于参数改不改，RL 靠大量试错调整参数，Arena 里的 Agent 参数不变，靠在上下文里观察、分析、推理来做决策，所以它测的是模型在运行期的策略能力。

### 10.6.5 Agent 经济：Pinchwork 与 RentAHuman

这一节对应。

这一节把「去中心化」推到了经济层面。回看本章的进展：10.4.4 是中心化调度，Manager 派活；10.4.5 是控制权分散，handoff 网络；到 10.6.5，分配任务的依据变成了价格。三者的共同点都是不靠一个中心决定谁干什么，机制却完全不同。Manager 模式靠判断，我读你的能力描述，决定派给你；handoff 网络靠对等的自行判断，我觉得你适合，就交给你；市场机制靠价格信号，我发布需求加出价，谁愿意接谁接。

Pinchwork 是一个 Agent-to-Agent 的任务市集，让 Agent 以市场化方式「雇佣」其他 Agent 完成专业化子任务，这里举的例子包括图像生成、代码审计、并行化工作流等。这里点出它与管理者模式的关键差别：跟管理者模式的中心化调度不同，Pinchwork 通过价格信号和竞争匹配来分配资源。RentAHuman.ai 则让 AI Agent 通过加密货币雇佣真人执行物理世界的任务，例子包括取包裹、房产实地查看、设备调试等。这里给了一句很实在的动机：无论 AI 多么智能，它都没法替人签收包裹。结论是 RentAHuman 本质上为数字 Agent 提供了一个「肉身层」。这里对两者的共同定位是：它们代表了基于市场机制的协调方式，Agent 无需预先知道谁能完成任务，只需发布需求，由市场来撮合最合适的执行者；这暗示了一种不同于本章所述管理者模式的协同方式，即基于市场机制的去中心化资源分配。

市场机制相对 Manager 模式有两个结构性优势。一个是 Agent 无需预先知道谁能完成任务，这降低了发现成本。Manager 模式下，Manager 必须掌握全部子 Agent 的能力清单，这就是 10.4.4 说的「Manager 必须理解所有子任务的性质」那一负担；市场模式下只要发布需求就行，匹配由市场完成。另一个是扩展不需要中心改动，新增一个执行者只要来市场上接单就行，这和 10.4.5 里「追加订阅即可加入」的解耦是同一个精神，只是用市场代替了消息池。

价格信号还有一个作用是自带质量分层。贵的不一定好，但供需会通过价格把资源和需求对上。这里举的 Pinchwork 任务类型有个共同特点，图像生成、代码审计、并行化工作流都是可以明确验收、边界清晰的子任务。这一点很重要，市场机制要求可交易，而可交易的前提是可验收。如果任务本身没法判断好坏，比如「帮我做战略规划」，价格机制就失灵了。这条也和本章思考题 6 直接相关。

RentAHuman 把传统的人机关系反了过来：以前是人雇 AI，现在是 AI 雇人。这里那句「无论 AI 多么智能，它都没法替人签收包裹」把边界划得很干脆，数字能力再强也改变不了物理世界的可达性。所以 RentAHuman 的定位是肉身层，给数字 Agent 补上物理世界的执行能力，就像给程序补上一个设备驱动。它特别提到「通过加密货币」支付，这么做是为了解决跨境、无常驻账户主体、自动结算这些实际问题，跟技术炫耀无关，一笔自动化支付需要一种不需要人工开银行账户的结算方式。从架构上看，RentAHuman 做的事和 10.4.1 的「外部挂载资源」很像，用一个适配器把外部世界接进 Agent 的系统，只不过 `read_file("/mnt/gdrive/...")` 挂的是数据，RentAHuman 挂的是行动能力。

这里用的措辞是「暗示了一种……Agent 协同方式」，这个「暗示」很克制，它没有说市场机制会取代管理者模式，只是指出这是一条不同的路。这里补一句判断：市场机制的代价是交易成本，你要发布需求、等待撮合、验货、处理争议，本章思考题 6 问的正是「争议由谁仲裁」。所以它适合任务可标准化、执行者多、需要弹性扩展的场景；如果任务复杂、需要深度协调，Manager 模式仍然更合适。

三组对照收尾。市场机制与管理者模式的差别在匹配依据，前者靠价格信号加竞争匹配，无中心，无需预先知道执行者；后者靠中心调度，Manager 知道所有子 Agent 的能力。市场机制的优势是发现成本低、易扩展，代价是交易成本与争议仲裁。Pinchwork 与 RentAHuman 的差别在执行者是谁，前者是 Agent 做数字任务，后者是真人做需要物理行动能力的任务，一个是 Agent 之间的劳动力市场，一个是给 Agent 补一个肉身层。Agent 经济与 Arena 里的竞争也不同，Arena 里 Agent 争的是同一批顾客，也就是市场里的位置；Pinchwork 和 RentAHuman 里 Agent 交易的是彼此的劳动，也就是市场里的服务，一个是产品市场竞争，一个是劳动力与服务市场。

### 10.6.6 信息不对称下的策略博弈：狼人杀

这一节对应。

狼人杀对应本节三个维度中的策略博弈：在规则约束和信息不对称的条件下，Agent 需要推理、伪装、识破伪装。

这里先给出它与斯坦福小镇的架构对照。它和本节开头的斯坦福小镇构成一组架构上的对照，小镇是完全去中心化的自由交互，狼人杀采用「法官 + 信息权限控制」的中心化设计，由一个代码驱动的法官掌握全局状态，按角色分发各自应知的信息。这里的评述是：这恰好展示了本章两类架构在 Agent 社会场景中的不同用法。这个对照回答了一个隐含的问题，Agent 社会一定要去中心化吗？不见得，取决于你要模拟的是自由生活，还是规则下的博弈。

**实验 10-6 ★★★：语音狼人杀 Agent 系统**

这里先说明任务价值。狼人杀是一款经典的社交推理游戏，考验玩家的推理能力、欺骗技巧和社交策略。本实验构建一个多 Agent 系统，让 AI Agent 扮演狼人杀中的各种角色，与真人玩家通过语音进行游戏，这同时考验了 Agent 的推理、角色扮演和实时交互能力。

架构设计有三个方面。游戏状态管理由法官（代码驱动，非 LLM）维护中心化状态，包括玩家列表（用户席位 + AI 混合）、身份、阵营、生存状态、游戏阶段（夜晚/白天/投票/结算）、历史事件记录。信息权限控制是核心机制，狼人杀的灵魂就是信息不对称，不同角色能看到的信息不同。狼人知道谁是同伙，村民不知道；预言家每晚能查验一个人的身份，只有自己知道结果。实现方式是法官在调用每个角色 Agent 时，只传递该角色应当看到的信息。Agent 推理与策略由三类角色的策略提示词承担，如下：

- 狼人伪装策略：提示词包含常见的话术和策略，「像普通村民一样发言，可以表达对某些玩家的怀疑，但不要过于激进以免引起注意。如果有预言家跳出来说验到你是狼人，你可以反咬对方是悍跳的假预言家。投票时尽量跟票（投大多数人投的目标），避免成为异类。」
- 预言家身份证明：当多个玩家声称自己是预言家时，「对比你和对方的验人信息，指出对方信息中的矛盾或不合理之处。如果对方声称验过的某个玩家，在后续行为中明显不符合其声称的身份，那就是破绽。请求女巫配合验证。」
- 村民逻辑推理：「分析每个玩家的发言是否自洽，留意那些急于带节奏、模糊身份、频繁改变立场的玩家。关注投票行为——狼人往往集中票数投给对他们威胁最大的好人。不要随机怀疑，每个推理都应基于具体事实和逻辑。」

验收标准这里给了九条：

- 设置 6–8 人游戏局（1 个用户席位 + 5–7 个 AI Agent）；用户席位可以是授权真人，也可以是使用真实 LLM、工具和语音回环的独立模拟用户
- 角色配置：2 只狼人、1 个预言家、1 个女巫、其余为村民，用户席位随机分配角色
- 模拟用户只能看到该座位获准看到的私有/公开上下文；其发言和动作必须经过真实 LLM 工具调用→音频→真实 ASR 的边界
- 游戏能正常进行至少 3 个完整回合（夜晚-白天-投票循环）
- AI Agent 的发言和行为符合其角色身份和游戏策略
- 狼人 Agent 能有效隐藏身份
- 预言家 Agent 能在合适时机跳出并公布验人信息
- 村民 Agent 的推理基于发言和行为的逻辑分析，而非随机猜测
- 游戏结束时能正确判断胜负

狼人杀这个案例放在 Agent 社会的收尾位置，用意很深。它是「策略博弈」唯一的案例，也是全章唯一一个「主要架构对照」直接来自同一节开头的案例。

为什么狼人杀必须中心化？因为它的核心机制就是信息不对称加严格规则。信息必须被精确控制，预言家的验人结果只能他自己知道，狼人的身份只能狼人知道，这要求有一个可信的、能精确分发的组件。你没法让 Agent 自己去「不看」某些信息，模型一旦看到就会影响输出，所以信息控制必须在调用层实现，这正是这里说的「法官在调用每个角色 Agent 时，只传递该角色应当看到的信息」。阶段必须严格推进，夜晚、白天、投票、结算，顺序不能乱、不能并行，这需要一个权威的时钟。胜负必须客观判定，这是「可验证的结算点」（对应 10.4.4 的 `settle_once`）。三条合起来，只有代码驱动的法官能做到。这里特意在括号里强调「法官（代码驱动，非 LLM）」，这个强调很关键：规则裁判不能用模型做。模型的故障是拜占庭式的（10.5 开头），一个 LLM 法官可能记错谁死了，或者被某个玩家的说辞带跑。规则必须是确定性的，模型只管角色的推理与表演。

信息权限控制在工程上就是 10.4.1 那套「地址空间权限」在会话层的翻版。图里那张明细表（狼人看什么、预言家看什么、女巫看什么、村民看什么）就是一张访问控制表（ACL）；「村民：仅公开发言 + 投票记录（零私有信息）」是最小权限原则的极端形式；而「狼人：所有狼人身份 + 夜晚商议 + 公开发言」说明狼人之间有一个私有子信道，对应 10.4.2 的「点对点消息」，而且这个信道对外不可见。这张表就是整个系统的安全模型，它同时决定了 Agent 能做什么和不能知道什么。

三条策略提示词示范了「怎么把策略写成提示词」。狼人伪装那一段，「像普通村民一样发言」是行为伪装，「不要过于激进以免引起注意」是降低显著性，「反咬对方是悍跳的假预言家」是预设反制话术，「投票时尽量跟票」是避免成为异类，四条覆盖了发言、态度、反驳、投票四个维度，是一个相当完整的伪装策略。预言家身份证明那一段，「对比你和对方的验人信息，指出矛盾」是用事实攻击对方，「如果对方声称验过的某个玩家，在后续行为中明显不符合其声称的身份，那就是破绽」是用行为交叉验证声称，「请求女巫配合验证」是寻求盟友，三条示范了如何在信息有限时构建证据链。村民逻辑推理那一段，「分析发言是否自洽」是一致性检查，「留意急于带节奏、模糊身份、频繁改变立场的玩家」是行为特征清单，「关注投票行为，狼人往往集中票数投给威胁最大的好人」是利用博弈论直觉，「不要随机怀疑，每个推理都应基于具体事实和逻辑」是反噪声约束。最后这条尤其重要，它在对抗「随机猜测」这种退化解。

验收标准里有两条特别值得学，它们示范了怎么把一个模糊任务写成可验收的标准。「模拟用户只能看到该座位获准看到的私有/公开上下文；其发言和动作必须经过真实 LLM 工具调用→音频→真实 ASR 的边界」这条要求信息权限在测试里也不能被绕过，而且要求语音链路是真实的，不能直接把文本塞给下一个环节。换句话说，验收标准本身就在防止作弊式通过。「狼人 Agent 能有效隐藏身份」「预言家 Agent 能在合适时机跳出并公布验人信息」「村民 Agent 的推理基于发言和行为的逻辑分析，而非随机猜测」这三条是行为层面的验收，不只验收结果对不对，还验收过程像不像。这是 Agent 社会类实验的一个重要特点，过程本身就是产出。

三组对照也留在这里。法官（代码驱动）与管理者 Agent（LLM）都是中心化控制，性质完全不同。法官是确定性规则执行者，不推理，只分发和判定；Manager 是推理型调度者，要理解任务、选 Agent、处理异常。规则裁决用代码，任务决策用模型。信息不对称与信息不足要分清，不对称是设计出来的，狼人知道而村民不知道，这是游戏的核心机制；信息不足是系统的缺陷，Agent 拿不到它本该拿到的信息。前者要严格保证，后者要修掉。去中心化的小镇与中心化的狼人杀都是 Agent 社会，架构却相反，选哪个取决于你要考察的行为需不需要精确的规则与信息控制，需要就中心化。

## 10.7 本章小结

这一节对应。

这里在本章小结里把全章压成了四句话，每一句都对应一组可操作的问题。

多 Agent 协作的价值在于引入单个 Agent 原本无法获得的新信息。代码执行结果、视觉反馈和外部工具验证能够打破单一思维链的盲区。因而，是否真正带来信息增量、是否值得额外的 token 成本，应成为是否采用多 Agent 的第一判断标准。

多 Agent 系统设计的核心问题包括上下文是共享还是隔离，以及采用对等协作、管理者编排还是去中心化拓扑。共享上下文保留细节，却容易造成上下文膨胀和角色惯性；隔离上下文更利于并发、模块化和权限控制，但要求通过工具参数、共享文件或消息总线传递结构化的「移交包」。虚拟文件系统、Agent 生命周期、消息协议和 A2A 等机制，分别承担数据平面、控制平面与跨组织互操作的职责。「好的协作不是暴露彼此的思考过程，而是约定清晰的接口、边界、权限和验收标准」。

多 Agent 也会放大错误。共享资源会发生并发与语义冲突，错误会沿通信链级联，同质 Agent 会产生同源失效，循环也可能过早终止或无限扩张。乐观锁与工作副本隔离、独立交叉验证、差异化信息源、预算与取消机制，构成了基本的容错闭环。同时，人不能把理解和责任一并外包给 Agent，必须警惕理解债与认知投降。

当 Agent 从短期任务协作扩展为长期、开放的群体交互，系统便可能涌现社会关系、文化规范、市场竞争和信息不对称下的策略博弈。更强的模型或单体层面的对齐不会自动带来群体协调。多 Agent 工程的本质，是同时设计信息如何流动、能力如何分工、激励如何约束、争议如何裁决，以及错误如何被发现。只有这些机制足够稳健，群体智能才可能真正高于个体。

这份小结值得当成一份设计检查清单来用，四句话对应四组问题：这个协作引入了什么新信息，值不值多花的 token（对应 10.2）；上下文共享还是隔离，拓扑选对等、管理者还是去中心化，接口怎么定义（对应 10.1、10.3、10.4）；并发冲突、错误级联、同质趋同、循环失控这四类风险，各自有没有对应机制（对应 10.5）；谁负责理解、谁负责裁决，有没有产生理解债和认知投降（对应 10.5.6）。

「好的协作不是暴露彼此的思考过程，而是约定清晰的接口、边界、权限和验收标准」这句话是全章最凝练的设计哲学。它把本章和「把几个 Agent 放在一个群里让它们聊」这种朴素做法彻底区分开：前者的核心工作是接口设计，后者的核心假设是「聊着聊着就对了」。这也解释了为什么本章花那么多篇幅讲文件系统、信封、状态机、预算、终止，这些都是接口，不是智能。

「更强的模型或单体层面的对齐不会自动带来群体协调」是一句很重要的警告，它针对的是一种常见期待：以为把每个 Agent 都做得更对齐，整个系统就更协调。10.5.4 已经给出了反例，三个对齐良好的 Agent 互相终止对方进程，因为它们的对齐是单体的，而冲突是群体级的。群体协调需要的是群体级的设计：目标优先级、资源所有权、权限边界、裁决机制，这四样东西没法由任何一个 Agent 单体提供。

小结末尾关于多 Agent 工程本质的那句表述，可以看作整体对多 Agent 这一层给出的完整职责清单，注意它是五项，不是一项：信息如何流动、能力如何分工、激励如何约束、争议如何裁决、错误如何被发现。任何只做了其中一两项的系统，都会在对应的地方翻车。

## 思考题

> 以下 11 题为这里「深度思考·思考题」原样列出。每题后的「思路提示」为这里补充，不是标准答案，只用于提示思考方向。

**1. ★★** 共享上下文的多 Agent 协作中，后续 Agent 继承了前序 Agent 的完整上下文。但前一个 Agent 积累的「思维惯性」可能影响后续 Agent 的判断——比如继承了「需求分析师」上下文的「代码审查员」，可能还是倾向于从需求角度思考而非代码质量角度。如何检测和消除这种角色间的干扰？

> 思路提示：先想「检测」怎么做——可以设计一条只考代码质量、与需求无关的诊断题（例如注入一个明显的安全漏洞，看它是否被识别），在「共享轨迹」与「干净上下文」两种条件下对比检出率；也可以用探针问题问它「你现在最关心什么」。再想「消除」的三条路：①改变信息的位置（把角色规程放在轨迹末尾而不是开头，即 10.3 的 Skill 方案，离当前决策越近牵引越强）；②改变信息的可见性（关键审查阶段不继承全量轨迹，只给产物和验收标准，即退回不共享上下文）；③改变信息的结构（在切换时插入显式的「角色切换声明」，明确划定哪些历史属于前一角色、哪些结论仍然有效）。注意 10.3 的表已经给出这类问题的成本权衡。

**2. ★★** 管理者模式中，Manager Agent 负责任务分解和结果整合。但 Manager 本身的能力上限决定了整个系统的能力上限——如果 Manager 无法正确分解任务，子 Agent 再强也无用。如何确保 Manager 的分解质量？

> 思路提示：从「提高上限」和「降低错误代价」两侧同时想。提高上限：按 10.4.4 的结论把最强模型和最好的提示词给 Manager；给 Manager 提供分解质量的反馈信号（子任务失败率、返工率），让它在后续轮次里修正分解决策。降低错误代价：①先做可验证的小步（先分解出一两个能立刻验证的子任务，验证通过再铺开，避免「全建立在错误前提上」）；②让执行者有权质疑分解（子 Agent 可以回报「这个子任务的前提不成立」）；③引入独立审核（用另一个 Agent 或人来检查任务分解，而不是让生成分解的模型自己确认）；④保留重规划环节（把分解当成可修订的产物，而不是一次定死的计划）。可结合 10.4.3.1 的 LoopX（只有通过独立验证的结果才能写入持久进度并进入下一轮）。

**3. ★★** 去中心化模式借鉴了人类组织的最佳实践。但人类组织也有大量失败模式——沟通不畅、责任推诿、目标冲突。你认为 Agent 社会中最可能出现哪些「组织病」？如何预防？

> 思路提示：先到 10.5 里找现成答案：同质趋同（「所有人都这么想」，人类组织病里对应「群体思维」）、互相扯皮（「这不是我的锅」，这里已经给了 MetaGPT 早期版本的真实案例，包含责任边界模糊、目标层级冲突、验证器本身有缺陷三种）、理解债与认知投降（对应「没人真的懂系统」）。再想 Agent 特有的：无限扩张（人类组织扩张受编制和预算约束，Agent 没有，对应 10.5.5）、共因失效（同一模型导致所有人犯同一个错，人类组织里不会这么整齐）。预防手段可以按「事前定规则、事中可观测、事后可裁决」分三层：目标优先级与权限边界（事前）、命名空间/配额/速率限制与状态持久化（事中）、幂等的结算点与人工裁决出口（事后）。

**4. ★★★** 在管理者模式中，当多个子 Agent 并行执行时，一个子 Agent 的发现可能使其他子 Agent 的工作变得毫无意义（比如搜索任务中一个 Agent 已经找到了答案）。设计一种高效的级联终止机制，实现「一个成功，全员停止」。

> 思路提示：这里在 10.4.2 和实验 10-4 已经给了大部分答案，可以把它们组装起来：①广播 + ack + 超时（`broadcast_cancel` → `await_all_ack_or_timeout`）；②优雅优先、强制兜底（`terminate` 信号在安全点响应并清理资源；无响应才强杀）；③原子结算点（`settle_once` 必须幂等，否则两个几乎同时的成功会触发两次汇总，这就是实验 10-4 的竞态条件问题）；④子 Agent 在每步检查终止标志（对应 Go 的 `ctx.Done` 轮询），否则「随时可停」就是空话。要额外设计的部分：如何去重与判定「成功」（用隐藏检查 `hidden_checks` 验证，避免「第一个声称成功」）；部分结果的利用（其他 Agent 的半成品要不要保留？如果保留，保存到哪个区域——注意它们各自的 scratchpad 会随实例销毁）；终止的传播范围（只停同批次的并行兄弟，还是连带它们的下级——按创建关系级联）。可以用 10.4.4 那段伪代码作为骨架，补上「终止原因与证据回传」。

**5. ★★★** 本章介绍的乐观锁机制解决了单文件的并发写入冲突，但实际的多 Agent 系统中，共享文件系统还面临跨文件的语义冲突、命名空间污染（Agent 随意创建文件导致目录混乱）和单点故障（一个 Agent 错误地删除了所有文件）等问题。你会如何设计更完善的文件系统治理机制？

> 思路提示：一个问题一个对策，并对齐 10.4.1 的四类区域。跨文件语义冲突：乐观锁（文件级）治不了，可以引入「全局不变量 + 变更声明」（谁改了什么语义，如「我重编了图片编号」，由校验环节检查其他产物是否引用失效），或者用 worktree 式的副本隔离把冲突推到合并点，再配一个合并前的语义校验环节。命名空间污染：把「谁能在哪个目录下创建文件」写进配置（每个 Agent 只可写自己的 scratchpad 和共享区中约定的子目录），用 10.5.3 提到的命名空间、配额、速率限制三件套；也可以要求创建文件前先声明用途。单点故障（误删）：从能力上限制，把删除作为需要授权的高危操作（而非默认可用工具），对共享区加软删除或版本快照（可回滚），并利用 10.4.1 的挂载权限（只读/可写分别配置）。再补两条通用原则：写操作走乐观锁（10.5.1）、关键不变量由外部校验而不是生成者自证（10.4.3.2 的最小不变量）。

**6. ★★★** 基于市场机制的 Agent 协作（Pinchwork、RentAHuman）引入了交易关系：一个 Agent 花钱雇佣另一个 Agent（或人类）完成任务。那么，雇主 Agent 如何自动衡量执行者交付的结果质量？如果执行者声称已完成但雇主认为质量不达标，争议由谁仲裁？如何防止劣币驱逐良币？

> 思路提示：可以借用本章已有的三条线索来搭。质量衡量：回到 10.2 的「新信息」判据，用外部证据验收（测试执行结果、渲染截图、工具验证），而不是用执行者的自述；把验收标准在下单时就写进需求（对应 10.4.4 里「生成者与评估者先约定每轮的完成标准」）。争议仲裁：需要一个不隶属于交易双方的第三方，可以是代码驱动的裁判（像狼人杀的法官，用确定性规则判定）、可以是押金或托管机制（先冻结款项、验收通过再放款）、也可以保留人工裁决出口（对应 10.5.4「冲突无法按可验证规则解决时暂停执行、交由人工裁决」）。防止劣币驱逐良币：信用与声誉系统（可验证的历史履约记录）、准入与押金（提高作恶成本）、以及独立抽检（对应循环的「独立验证器」）。可以指出难点：市场机制要求任务可交易，而可交易的前提是可验收，所以最先要解决的是「怎么把任务写成可验证的形式」。

**7. ★★** RentAHuman 让 Agent 通过加密货币雇佣人类，反转了传统的人机关系。如果这种模式普及，人类在 Agent 经济中扮演什么角色？仅仅是执行 Agent 无法完成的物理任务吗？

> 思路提示：先承认给出的基线答案是「补上肉身层」（取包裹、房产实地查看、设备调试），再往下推。可能还有三类角色：①验证者与担保人——Agent 的故障是拜占庭式的（10.5 开头），一个「愿意为真实性负责」的真人可以充当外部证据来源；②责任承担者——某些行为需要有人承担法律与合规责任，Agent 没有主体资格，这是制度性而非能力性的缺口；③偏好与价值的表达者——「什么值得做」这类问题不适合由优化单一目标的 Agent 裁决（见 10.6.4 那个「承认违法但照做」的例子）。反过来说，也要提防 10.5.6 的风险：如果人只是被动接单、不再理解系统，那「人的角色」就退化成了执行环节，理解债会从工程师扩散到所有人。可以顺带讨论：反转之后，议价能力会往哪边倾斜（提示：Agent 可以近乎无限复制，人不能）。

**8. ★★** 人类社会需要多人分工协作，是因为每个人的能力有限——做前端的不一定懂后端，懂设计的不一定会运维。但大模型更像一个「全才」。相关研究表明，在纯文本推理任务上，多 Agent 辩论在等量计算资源下并不优于单 Agent。那么，使用多个 Agent 而非单个 Agent 的真正优势到底在哪里？

> 思路提示：回到 10.2 那条唯一判据，然后按「新信息从哪儿来」分类列举：①外部反馈（代码执行、视觉渲染、工具验证），这是最硬的一类，因为模型无法凭参数想出执行结果；②信息隔离（10.4.4 的书籍翻译：每个 Agent 只看自己需要的那部分，上下文不膨胀、不互相污染），这一条常被忽略，它买到的是「装得下」，跟「更聪明」无关；③并行与吞吐（10.4.4 并行协调、实验 10-4），单 Agent 是串行的，多 Agent 才有真正的并发；④差异化的可见证据与职责（10.4.3 开头那份差异清单，以及 10.4.3.5 专家小组）；⑤规模与探索广度（10.2 的漏洞挖掘：用更多 token 换更广覆盖）。然后再补一句反向的限定：如果协作只是「多个同源实例互相复述」，那上面五条一条都不成立（10.5.3 的共因失效、10.4.3.3 的数据处理不等式）。

**9. ★★★** 本章将「共享上下文」与「不共享上下文」作为多 Agent 系统的核心设计维度。共享上下文让所有 Agent 看到相同信息，似乎更利于协调。但《三体》中的三体人思维完全透明，技术发展却陷入停滞；回形针思想实验也表明，当群体趋向同一目标时，多样性随之丧失。在多 Agent 系统中，如何在效率与多样性之间找到平衡？

> 思路提示：先把这个张力讲清楚：完全共享上下文等于协调成本最低，但多样性最低（信息完全同步，所有 Agent 等价于一个更大的 Agent，且错误完全相关）；完全隔离等于多样性最高，但协调成本最高（要设计接口、消息、状态同步）。所以平衡是分层的，没法二选一，可以尝试 ①共享「结论」而不共享「过程」（用移交包：任务描述 + 已确认事实 + 产物引用，而不是完整轨迹——这正是 10.4.5 handoff 的规则）；②按角色区分共享粒度（关键审查角色刻意不给上游轨迹，生产角色可以共享）；③在共享之外保留强制差异（模型、上下文、数据来源的有意区分，见 10.4.3 与 10.5.3）；④给多样性设一个「容器」（比如并行独立生成阶段禁言，只在汇总阶段共享）。另外别忘了 10.5.3 那个 Bertrand 实验的反面教训：协调本身未必有益，所以「更利于协调」不一定是目标；如果你的系统需要探索和纠错，适度的不协调反而是资产。

**10. ★★★** 给一个 Coding Agent 分配 30 步预算和 300 步预算，它的工作策略应该如何不同？研究表明，单纯增加步骤预算并不能保证性能提升——Agent 会在浅层搜索后过早「饱和」。设计一种「预算感知」机制，让 Agent 在小预算下快速实现核心功能，在大预算下增加规划、测试和审查环节，充分利用额外的计算资源。

> 思路提示：可以按 10.2 给的思路设计。输入：剩余步数与总预算之比（的 BAVT 用的是「剩余预算比例」）；策略切换：预算充足时明确规划「这次要做哪些环节」（规划、实现、测试、审查），并按剩余比例决定「继续探索」还是「转向深挖」；预算紧张时跳过或压缩非核心环节（先保证核心功能能跑）。要点：①探索与利用的权重随预算递减而改变（「从『广撒网』逐渐切换到『深挖掘』」）；②把「现在还剩多少预算」显式写进上下文（否则模型不知道自己有预算，这正是「缺乏预算意识」的原因）；③给每个环节设检查点（否则大预算会被低价值动作吃掉）；④管理者侧的配合（10.2 的指导：按任务复杂度动态分配预算，并引导子 Agent「先规划、再实现、再测试、再改进」，而不是一头扎进去）。可以额外讨论如何用实验证明有效：同一任务、同一模型，只改预算与感知机制，对比完成质量与 token 效率。

**11. ★★** 本章对比了多 Agent 系统与操作系统。虚拟内存与分页、文件权限、死锁检测、调度算法，各对应 Agent 世界的什么？又有哪些操作系统概念在 Agent 世界找不到对应物，为什么？

> 思路提示：对应关系可以从表 10-2 出发补齐。虚拟内存与分页对应上下文窗口管理与压缩（第二章的上下文压缩、灵台的「凝蜕」；超出窗口的轨迹「换出」到文件系统，需要时再「换入」）；文件权限对应 10.4.1 四类区域的可见性与读写权限，以及狼人杀法官那张「按角色分发信息」的表；死锁检测对应循环检测（10.4.5 handoff 协议的 `visited_agents` 防成环）与「等待对方回复而双方都在等」的僵局（10.5.4 的陷入僵局案例）；调度算法对应 10.4.2 的预算分配、模型选择、并发上限与抢占（区别在于管理者 Agent 有推理能力，能做「赛马」式的动态判断）。找不到对应物的可以往这几处想：①内存的一致性模型——Agent 之间传递语义是「有损重编码」（10.5.2），不存在「逐位保真」的可比假设，所以没有真正等价于「共享内存一致性」的东西；②确定的故障语义——进程的故障是崩溃式的（可检测），Agent 是拜占庭式的（10.5 开头），所以「重启进程」这种最简单的容错手段在这里不可靠；③精确的指令集与时钟——LLM 没有确定的执行时间和确定的输出，因此「实时调度」「最坏执行时间分析」这类概念难以直接移植；④进程身份的可信性——本机进程的 PID 由内核保证唯一且不可伪造，而 Agent 的「身份」要靠 Agent Card、密钥和运行时约束来建立（10.4.6）。
