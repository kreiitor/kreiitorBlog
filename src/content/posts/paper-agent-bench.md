三个基准都在回答同一个问题：怎么用真实仓库而不是孤立的函数，来衡量编程 Agent 的能力。差别在任务粒度、测试来源和上下文处理。

## R2E：仓库级编程 Agent 评测

发表于 2024 年，正处在聊天机器人向 Agent 过渡的阶段。

### 仓库与函数怎么选

仓库要求在大模型知识截止日期之后，避免模型靠记忆做题。函数按规则过滤，没有 docstring 的直接去掉，留下的 docstring 当作题面提示。函数的复杂度用调用关系来评判：被谁调用、又调用了谁。

### 测试怎么生成

论文认为，即使是 Python 仓库，也普遍缺少高质量的代码生成测试。一条测试由测试函数和测试输入组成，预期输出不预先写死，而是用原函数跑一遍得到。

测试有两个作用。一是检查生成的代码与原函数是否等价；二是编排，把测试结果回灌给 Agent 作为反馈。覆盖率用分支覆盖（branch coverage），不是行覆盖。

运行环境用 Docker 配置，测试夹具负责把函数跑起来所需的依赖备齐。测试质量直接决定基准质量，论文为此引用了两项研究，并强调等价性测试和覆盖率两项都要做。

### 指标与上下文

指标有两个：等价性，即生成函数与原函数的功能等价程度；质量，用分支覆盖率衡量，它同时反映测试能否判别等价性。

上下文有三种取法：不给、全量给、只给最小必需。消融结果显示，不给上下文时测试的有效性下降，但测试对函数的覆盖反而提升；全量上下文的结果相反；最小上下文是一个有效的折中。

最小上下文的做法是程序分析：先找出直接和间接调用的函数与全局变量，再逐层扩展。工具上，调用图用 pycg，最小上下文则靠调用图加字节码分析，递归进行——目标函数调用 f1，再对 f1 重复同一过程。

题面描述在函数筛选时刻意保留了带 docstring 的函数，但这些描述不一定符合代码补全的要求，所以再用模型生成或优化一版，上下文是测试夹具和测试的输入输出。

## DevEval：与真实仓库对齐的代码生成基准

发表于 2024 年。背景是当时的代码基准没有完整覆盖真实仓库的形态：孤立函数与多依赖函数并存、自然语言依赖与代码依赖都要标注、指标要基于执行结果。

任务形式是给定函数签名、依赖和完整仓库，让模型生成函数，落在仓库级依赖和函数粒度上。

指标两个：pass@k 衡量函数生成的正确性，recall@k 衡量模型对上下文的使用是否准确。

人工标注带来了两处差异。函数描述由人工撰写和优化，R2E 用的是 LLM 润色；调用路径由人工标注出唯一一条，R2E 用调用图和字节码分析。

仓库从 PyPI 前十个流行话题里各选最多 50 个，两个基准都排除了 fork。函数会排除简单函数，保留那些已有可执行测试、且测试满足 fail-to-pass 的函数；R2E 按复杂度筛，DevEval 则明确要求孤立函数和非孤立函数都要覆盖。

2024 年的模型上下文只有 128k，论文针对短上下文另提了解决办法。

## FeatureBench：复杂功能开发的 Agent 评测

投稿于 2026 年 ICLR。出发点是现有代码评测的覆盖面太窄：多数只考察单个 PR 的缺陷修复，评估方式不执行代码，自动化程度也不足以扩展。

论文主张做 feature 级别的 agentic coding 基准，并给出了 PR 级方法不够用的四条理由：

- feature 级别需要清晰的 spec；
- 一个功能常常分散在多次 PR 里；
- PR 本身缺少标签，难以判断哪些提交对某个功能有贡献；
- PR-driven 的方法被提交历史绑死，任务只能落在固定的历史组合上，不利于灵活构造和扩展。

测试沿用 fail-to-pass 与 pass-to-pass 的判定方式。
