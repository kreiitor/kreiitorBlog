## R2E：仓库级编程 Agent 评测

> **背景**：聊天机器人到 agent 的过渡期，此基准可以评测 agent。
>
> **时间**：2024

可借鉴:
1. 仓库的选择
	- 大模型知识截止日期之后的仓库
2. **函数的选择:**
	- 根据需要的过滤规则->例如没有docstring的去除(当做提示词)
	- 函数调用和被调用作为复杂度评判
3. **测试生成:** 即使是py工程仓库,论文也认为缺少高质量评估代码生成的测试
	- 测试函数: 测试用例和预期输出
	- 测试质量: line coverage vs. branch coverage 本论文是后者
	- 测试的两种作用:
		- 检查: 检查生成的代码是否和原代码"等价"
		- 编排: 根据生成代码的测试结果,可以给agent以反馈
	- 论文的关键设计:
		- 使用docker配置测试、函数的运行环境
		- 只关注测试函数和测试输入,测试输出不提前"预测",而是用原函数运行测试得到输出
		- 倾向测试动态运行函数:为测试配齐夹具(harness,运行函数和测试需要的配置等)
		- 最小化上下文:进行程序分析->调用的函数或者全局变量->间接和非间接
		- 测试质量影响基准质量(本论文引用两篇论文说明这个观点): 要进行等价性测试和测试覆盖率
4. 指标:
	- 等价性: 和原函数的功能等价程度
	- 质量: 使用分支覆盖率来衡量，也一定程度上反映测试对于等价性的判别能力
5. 上下文选择策略:
	- 不需要上下文，全部上下文，最小必须上下文
	- 论文进行了消融实验，预测输出差于原函数测试输出。

上下文策略，不给上下文测试有效性降低，但是测试对函数的覆盖率提升。全量上下文则相反，最小上下文也是有效的权衡。
6. 题面描述:
	- 在函数筛选时刻意留下了有文档字符串的函数
	- 但是这个描述不一定是符合代码补全要求的。所以需要用模型来进行生成或优化(用测试夹具和测试输入输出作为上下文)
7. 工具选型:
	- 调用图分析使用 pycg 工具
	- 最小上下文使用 f 调用的函数和全局变量，直接和间接的
	- 前者使用调用图，后者使用字节码分析。是一个不断迭代的过程，f 调用 f1，然后 f1 重复这个过程。

## DevEval: A Manually-Annotated Code Generation Benchmark Aligned with Real-World Code Repositories

> **背景**：现存的代码基准没有全面展现真实仓库、真实代码分布（孤立函数和多依赖函数）、完整的注解（自然语言的依赖、代码等）和鲁棒的指标（基于执行的指标、pass@k）。
>
> **时间**：2024

**成果**：给定函数签名、依赖和完整仓库，让模型生成函数，形成仓库级依赖、函数粒度任务。

1. 指标:
	- pass@k: 函数生成的正确性指标
	- recall@k: llm对上下文使用的准确性指标
2. 人工标注: 本论文使用了人工标注依赖
	- 函数描述: 人工撰写和优化,与之相比,上一篇论文是llm润色
	- 函数变量等调用: 人工标注唯一调用路径,与之相比,上一篇论文是调用图和字节码分析
3. 仓库选择:
	- pypi中按前十个流行话题各选择最多50个仓库(上一篇和这一篇都要求仓库没有fork)
4. 函数和测试选择和构建:
	- 函数排除简单函数
	- 涉及已有可执行测试的函数被保留,测试必须f2p
	- 上一篇会考虑函数复杂度,这一篇明确要求孤立函数和非孤立函数都要有
5. 模型短上下文问题及解决方法:
	- 因为24年上下文是128k,论文提出了解决方案

## FEATUREBENCH: BENCHMARKING AGENTIC CODING FOR COMPLEX FEATURE DEVELOPMENT

> **背景**：现有代码能力评测的范围限制明显，例如只覆盖单个 PR 的故障修复、采用非执行性评估、自动化程度不足难以扩展。
>
> **时间**：2026 ICLR

1. 论文技术转向:
	- 本论文认为需要feature-level的agentic coding基准，并且强调传统pr-based方法不足以做成
		- feature-level依赖清晰的spec
		- 一个功能可能分散在多次PR
		- PR缺少标签,难以辨认哪些PR对一个功能有了贡献
		- **PR-driven 方法受提交历史轨迹限制**:任务被绑定到固定历史开发组合，不利于灵活构造和扩展 benchmark。
2. 测试: 采用f2p,p2p式
