三个基准都在回答同一个问题：怎么用真实仓库而不是孤立的函数，来衡量编程 Agent 的能力。差别在任务粒度、测试来源和上下文处理。

## R2E：仓库级编程 Agent 评测

该基准发表于 ICML 2024（*R2E: Turning any Github Repository into a Programming Agent Environment*，项目主页 [r2e.dev](https://r2e.dev/)），正值代码模型从单轮对话补全向自主编程 Agent 过渡的阶段。

### 仓库与函数怎么选

仓库要求在大模型知识截止日期之后，避免模型靠记忆做题。函数按规则过滤，没有 docstring 的直接去掉，留下的 docstring 当作题面提示。函数的复杂度用调用关系来评判：被谁调用、又调用了谁。

### 测试怎么生成

R2E 论文指出，即使是主流 Python 仓库，也普遍缺少可直接用于代码生成评测的高质量测试。一条测试由测试函数和测试输入组成，预期输出不预先写死，而是用原函数跑一遍得到。

测试有两个作用：一是检查生成的代码与原函数是否等价；二是流程编排与反馈（orchestration），把测试结果回灌给 Agent 用于迭代修正。覆盖率用分支覆盖（branch coverage），不是行覆盖。

运行环境用 Docker 配置，测试夹具负责把函数跑起来所需的依赖备齐。测试质量直接决定基准的区分度，因此 R2E 同时要求等价性验证与分支覆盖率检查。

### 指标与上下文

指标分为两项：生成代码的功能等价性，以及测试自身的质量（用分支覆盖率衡量，用以判断测试能否真正区分错误实现）。

上下文有三种取法：不给、全量给、只给最小必需。消融结果显示，不给上下文时测试的有效性下降，但测试对函数的覆盖反而提升；全量上下文的结果相反；最小上下文是一个有效的折中。

最小上下文通过程序分析构造：利用 PyCG 生成调用图，再结合字节码分析，从目标函数出发递归收集直接与间接依赖的函数及全局变量。

虽然函数筛选阶段特意保留了带 docstring 的函数，但原有 docstring 未必适合直接作为代码补全题面，因此作者结合测试夹具与测试输入输出，用大模型重新生成或润色题面描述。

## DevEval：与真实仓库对齐的代码生成基准

发表于 Findings of ACL 2024（*DevEval: A Manually-Annotated Code Generation Benchmark Aligned with Real-World Code Repositories*）。针对当时基准未能反映真实仓库开发形态的问题，DevEval 提出三项要求：同时覆盖孤立函数与多依赖函数、标注自然语言依赖与代码依赖、采用基于执行的评测指标。

任务形式是给定函数签名、依赖和完整仓库，让模型聚焦于函数粒度的仓库级依赖补全。

指标两个：`pass@k` 衡量函数生成的正确性，`recall@k` 衡量模型对上下文的使用是否准确。

与 R2E 相比，DevEval 更多依赖人工标注，差异主要在两处：函数描述由人工撰写和优化（R2E 用 LLM 润色）；调用路径由人工标注（R2E 用调用图和字节码分析）。

仓库从 PyPI 热门分类的前 10 个主题中各选最多 50 个，且排除了 fork。函数会排除简单函数，保留已有可执行测试的函数，并明确要求孤立函数和非孤立函数都要覆盖。此外，针对当时主流模型约 128k 的上下文窗口限制，论文还对比了不同上下文截取与检索策略。

## FeatureBench：复杂功能开发的 Agent 评测

发表于 ICLR 2026。出发点是不少现有代码基准仅考察单个 PR 的缺陷修复，或停留在不执行代码的静态评估，且数据构造自动化程度有限。

论文主张做功能级（feature-level）的编程 Agent 基准，并给出了 PR 级方法不够用的四条理由：

- 功能级别需要清晰的规格说明（spec）；
- 一个功能常常分散在多次 PR 里；
- PR 本身缺少标签，难以判断哪些提交对某个功能有贡献；
- 基于 PR 历史的方法受限于既有提交拆分，任务只能落在固定的历史组合上，不利于灵活构造和扩展。

测试沿用 `fail-to-pass`（F2P）与 `pass-to-pass`（P2P）的判定方式：前者验证新功能测试通过，后者确保仓库原有回归测试不被破坏。
