# 第 3 章 推理与训练负载

> 本笔记对应原书《深入理解AI Infra：量化分析与系统设计》第 3 章 推理与训练负载，原书印刷页码 74–107 页（PDF 第 84–117 页）。
> 笔记结构：先给"本章地图"，再逐节精读，最后是术语速查、原文小结与自测题。

**章首引入**

原文用一个具体的算例开场：假设某服务平均每秒收到四个请求，每个请求输入 4,608 个 token、输出 1,152 个 token。第 2 章已经说明如何按输入和输出长度计算模型工作量，那么"把平均工作量乘以每秒请求数"是否就能确定需要多少资源？原文的回答是不能。它给了两组"平均请求率和平均输入、输出长度完全相同"的服务作对比：一种始终均匀接收请求，另一种前一分钟集中处理长文档、后一分钟集中生成长回答。前者的资源需求在各阶段较为稳定，后者则在不同时段分别需要更多输入处理能力或生成能力。

原文接着指出，**到达顺序之外，任务内部的往返与等待同样影响负载**：Agent 在模型与工具之间往返，等待工具结果时模型暂停生成，上下文状态却仍要保留，供后续调用使用。训练中的序列长度、有效标签（参与损失计算的 token）和更新次数，也会影响运算量和状态需要驻留的时间。

于是本章在第 2 章（单次调用的容量、运算量和读取量）之上再加入三个问题：**工作何时到达，哪些步骤必须等待，什么结果才算任务完成**。由此依次建立排队、状态驻留时间、关键路径和成功任务成本的模型，再综合计算训练和长期服务的成本。

## 本章地图

- **这一章要解决什么问题**：第 2 章算清了"单次调用"要花多少算力、多少存储、多少读取量；本章把静态的工作量接到时间轴上，回答"这份工作量在什么时间到达、要等多久、什么时候算真正完成、完成一个合格结果平均要付多少钱"。三个新增问题是：工作何时到达、哪些步骤必须等待、什么结果才算任务完成。
- **它在全书中的位置**：上一章（第 2 章）给出模型架构与单次请求的调用约定、KV 计数与运算量；本章把这些量组织成负载；下一章（第 4 章）结合芯片的算力、存储容量与带宽，分析这些负载如何在加速器上执行。本章算出的矩阵尺寸、状态大小和访问次数，将用于判断计算需要多久、数据能否容纳、读写能否及时完成；各阶段的依赖关系则决定哪些工作可以重叠、哪些必须等待。
- **小节之间的关系**：3.1 把"一次请求"推广成"持续到达的请求流"，给出排队模型与评价指标体系；3.2 把"一次调用"升级为多轮对话与 Agent 任务，引入前缀复用、成功任务成本、依赖图与关键路径、状态驻留；3.3 再加入多模态与实时约束（视觉编码、音频与图像生成的迭代、连续播放与打断）；3.4 转到训练侧，算前向、反向与参数更新的计算量和状态量；3.5 讲强化学习（RL）这一"生成—反馈—更新"闭环；3.6 把训练投入和长期服务摊到一张总账上（Scaling Law、公开训练记录、全生命周期成本）。最后是谬误与陷阱、代码任务轨迹与本章小结。
- **读完你应该能做到**：1) 给定到达速率、输入/输出长度和硬件带宽下界，判断系统会不会积压、积压多少、停止到达后多久排空；2) 会用 TTFT、完整请求时间、token 间隔、p95、状态占用积分（byte·s）和成功任务成本这几类指标描述负载，并知道每个指标只对哪一段耗时敏感；3) 会从线性层 $Y=XW$ 推导输入梯度与权重梯度，得出"训练矩阵运算量约为前向三倍"以及 $F_{\text{train}}\approx 6ND$，并把注意力、词表头、优化器状态逐项补成完整预算；4) 会用 Scaling Law 的分配指数和全生命周期成本公式，判断"该训多大、该服务多少次"。

## 3.1 从单次请求到持续到达的负载

### 3.1.1 Prefill 与 Decode

**原文要点**

- **负载的定义**：负载是**一定时间内到达系统、等待和执行的工作集合**。这一定义同时包含了"多少工作"和"什么时候到"两件事。
- **单个请求的调用链**：恢复 $S$ 个上下文 token（即已有前缀），处理 $P$ 个新输入，返回 $G$ 个 token。这样一个请求的调用链由**一次 prefill 和 $n_d = G-1$ 次 decode** 构成。也就是说，首个输出 token 由 prefill 阶段产生，之后每产生一个输出 token 需要一次 decode。
- **decode 的编号与上下文长度**：把后续 decode 从 $j=0$ 开始编号，第 $j$ 次 decode 开始时已有上下文为 $S+P+j$。因此每次调用的资源需求都可以用第 2 章的方法算出，调用之间的顺序则由生成依赖确定（第 $j+1$ 次 decode 必须等第 $j$ 次产出 token 后才能开始）。
- **图 3-1 的算例**：复用 6,144 个上下文 token，处理 2,048 个新 token，生成 4 个输出。列表形式是：prefill（KV 覆盖 8192 token，产生第 1 个输出）→ decode 1（KV 覆盖 8193，产生第 2 个输出）→ decode 2（KV 覆盖 8194，产生第 3 个输出）→ decode 3（KV 覆盖 8195，产生第 4 个输出）。

> 图 3-1（原文插图）：恢复 6144 个上下文 token，处理 2048 个新输入并生成 4 个输出。首输出来自 prefill，后续 3 次 decode 各追加一个 token；纵向表示调用次序，间距仅用于示意。图中可以看到每次调用后 KV 覆盖的 token 数依次从 8192 增长到 8195，正好对应"输入 6144+2048=8192，之后每次 decode 加 1"。

- **同一套权重、不同的资源画像**：以一组权重矩阵为例，prefill 的输入包含 $BP$ 行（$B$ 为批大小），单步 decode 只有 $B$ 行。输入 token 较多时，一次读入的权重可以参与更多乘加运算；低并发 decode 则可能只为少数几个 token 读取整组权重。**这就是"prefill 通常受算力限制、decode 通常受内存带宽限制"这种说法的由来。**
- **请求之间的复用机会**：多个 decode 同时执行时，共同使用权重，各自读取上下文；一条长输入到来时，prefill 可以同时处理较多已知 token，它们的特征向量组成行数更大的输入矩阵。
- **资源分配的含义**：服务系统需要在这些形状不同的工作之间分配时间。**仅把总 token 数相加，会丢失这些 token 分别属于哪个阶段、何时能够执行的信息。**

**辅导讲解**

- 为什么必须把 prefill 和 decode 分开算？因为两者的"瓶颈"不同。衡量一个算子吃算力还是吃带宽，可以看它的**算术强度**（arithmetic intensity，每读入 1 字节数据能做多少次浮点运算）。prefill 一次要吃进 $P$ 个 token 的行（$P$ 通常几百到几万），权重读一次就被重复利用了 $P$ 次，算术强度高，所以算力是瓶颈；decode 每步只增加 1 个 token，权重读一次只服务极少的行，算术强度低，所以显存带宽是瓶颈。这就是 3.1.1 那句结论的物理来源（此处算术强度的说法是笔记补充的表述，原文只给出"输入行数 $BP$ 对 $B$"这个解释）。
- 数据流走一遍：客户端发来 $S$ 个已缓存前缀 + $P$ 个新 token → 调度器把这条请求排进 prefill 批次 → prefill 一次性算出这 $S+P$ 个位置的 KV 并保留在 KV 池里，同时在最后一个位置采出第 1 个输出 token → 之后每来一次 decode，模型只用**新采出的那 1 个 token** 作输入，用已存的 KV 算注意力，再加 1 个 KV 进去，采出下一个 token。所以 decode 的时间由"读权重 + 读全部旧 KV"决定，而这两项都随并发数变化。
- 工程上的两个坑：一是**"总 token 数"是个会骗人的指标**。一条"输入 8192、输出 256"的请求和一条"输入 1024、输出 2048"的请求，总 token 都是 8448，但前者的成本几乎全压在 prefill（受算力限制）上，后者几乎全压在 decode（受带宽限制）上。把它们混在一起统计，你既不知道要补哪一类资源，也不知道延迟会烂在哪一段。二是**decode 的"步"要看清计数单位**：在批处理里，一次 decode 调用同时推进 $B$ 条序列各一个 token，通常被数成 $B$ 个 decode 步。这一点在 3.1.3 的带宽下界计算里非常关键（见下文对该算式的拆解）。
- 什么时候这种"两阶段"模型不够用：当系统启用了分块 prefill（chunked prefill，把一条长输入拆成几段插入 decode 批次）、或者 prefill 与 decode 在不同机器上分离部署（PD 分离）时，单个请求的"一次 prefill"就变成了多次调度，时间线要按调度器实际切分来重排。原文在此处只给基本约定，未展开这些部署形态。

**易混点**

- **$n_d = G-1$ 与 $G$**：第一个输出由 prefill 产出，所以后续 decode 次数是 $G-1$ 而不是 $G$。这个"减一"在后面的 4,604 步、552,480 步、1279 长度等处反复出现，是最容易算错的地方。
- **$S$ 与 $P$**：$S$ 是**已经存在、可复用**的上下文 token 数，$P$ 是**本次要重新计算**的新输入 token 数。两者的和 $S+P$ 才是 prefill 之后 KV 里的 token 总数。3.2.1 会把这个区分推广到多轮对话（$K_i$ 与 $P_i$）。

**一句话记住**

> 一条请求 = 一次 prefill（产首 token、吃算力）+ $G-1$ 次 decode（每次加 1 个 token、吃带宽）；$S+P+j$ 是第 $j$ 次 decode 开始时的上下文长度。

### 3.1.2 任务目标与评价指标

**原文要点**

- **请求与任务不是一一对应**：模型请求与用户任务通常不是一一对应的。回答问题可能只需一次生成，修复函数却可能需要读文件、改代码、运行测试、根据错误再修改。**评估系统时，先写出什么算完成，再决定统计什么。**
- **三个事件与三个时间指标**：在时间线上标出请求到达 $t_a$、首个 token 返回 $t_1$、最后一个 token 返回 $t_G$，由此得到

$$T_{\text{TTFT}} = t_1 - t_a,\qquad T_{\text{request}} = t_G - t_a,\qquad T_{\text{token}} = \frac{t_G - t_1}{G-1}\ (G>1)$$

  其中 $T_{\text{TTFT}}$ 缩写自 time to first token（首 token 时间），本书也称**首响应**；$T_{\text{request}}$ 为**完整请求延迟**，衡量多久生成完；$T_{\text{token}}$ 为**平均 token 间隔**，衡量输出节奏。三个量的单位都是秒（$T_{\text{token}}$ 是秒/token）。
- **指标的敏感范围**：把某一段时间缩短，只会直接改变包含这段时间的指标。例如，减少请求开始执行前的排队会改善 TTFT，却不会自动缩短已经开始生成后的 token 间隔。

> 图 3-2（原文插图）：请求到达、首输出与末输出决定三个计时区间。首响应（TTFT）从"请求到达"到"首个输出"；后续输出间隔是首个输出到最后一个输出之间被 $(G-1)$ 除；完整请求时间从到达累计到结束。图中把三个区间画在同一时间轴上，可以看出 TTFT 和完整请求时间共享"到达"这个起点，而 token 间隔只看生成过程本身。

- **TTFT 内部还有阶段**：首个 token 到达客户端之前，请求要依次经过排队、输入准备、加速器计算和结果返回等阶段。输入最初保存在主机还是加速器上，决定数据传输发生在哪里；计算完成后，结果还要经过主机处理和连接发送。记录同一请求在各阶段的开始和结束时间，就能看出 TTFT 主要消耗在哪些环节。第 5 章将展开加速器提交、传输与完成的具体时序。
- **流式输出的额外观察点**：客户端按块接收多个 token 时，可以直接记录每块的到达时间与 token 数，再统计输出节奏。reasoning 模型还会多出一个观察点：它在给出可见回答前先生成中间思考内容（称为**思考 token**），首个内部 token 出现时，用户未必已看到答案。因此，**内部生成、用户可见输出和任务完成分别对应不同的时间点**。语音的首次播放还要再经过解码与设备缓冲，3.3.3 节再讨论。
- **"要回答的问题 → 需要的指标"对照表**（表格按原文语义还原）：

| 要回答的问题 | 需要的指标或记录 |
| --- | --- |
| 多久开始回应？ | TTFT；reasoning 另记首个有用输出 |
| 输出是否连续？ | 逐 token／逐块间隔及其分布 |
| 多久把事情做完？ | 完整请求时间、完整任务时间 |
| 每秒完成多少合格任务？ | 在质量与时限要求下的有效吞吐 |
| 得到一个成功结果花多少？ | 全部尝试的模型、工具和环境成本／成功任务数 |
| 等待期间还占着什么？ | 状态所属的请求与模型版本、大小、存放位置和驻留时间 |

- **p95 与最近秩法**：只看平均值会掩盖较慢的一部分请求。p95 是第 95 百分位数，用来描述所选指标中较慢的一部分观测。本章采用**最近秩法**：把 $n$ 个观测从小到大排列，取第 $\lceil 0.95n \rceil$ 个。四条请求的 p95 是最大值（$\lceil 3.8 \rceil = 4$，即第 4 个）；480 条请求的 p95 是第 456 个（$0.95 \times 480 = 456$）。将请求完成、排队与首响应的耗时**分别排序**，就能看出长等待发生在哪一段；完整请求的 p95 则直接由各请求的全程耗时排序得到。
- **状态占用：面积积分**：除响应时间外，等待期间的状态占用也需要度量。状态驻留得越久，同样的容量能同时服务的任务就越少。令任务状态大小为 $M(t)$，则状态占用空间对时间的积分为

$$A_M = \int_{t_{\text{start}}}^{t_{\text{end}}} M(t)\,\mathrm{d}t$$

  也就是"把各时间段占用的空间乘以持续时间再相加"，得到占用空间随时间变化的**曲线下面积**，单位是 byte·s。例如 1 GiB 状态持续占用空间 10 秒，对应 $10\ \text{GiB}\cdot\text{s}$。状态没有变大，但这段时间里这块空间不能供其他请求使用。
- **稳定到达下的平均占用**：若任务以平均每秒 $\lambda$ 个的速度持续到达，每个任务都占用 $M_0$ 字节、平均等待 $\tau$ 秒，稳定情况下仅这些等待任务的平均占用就约为 $\lambda M_0 \tau$。原文由此得出结论：**工具等待也会成为容量问题。**（$\lambda$ 单位 1/s，$M_0$ 单位 byte，$\tau$ 单位 s，乘积单位 byte。）

> 图 3-3（原文插图）：1 GiB 状态持续占用空间 10 秒，对应面积为 10 GiB·s。横轴为状态驻留时间（0–12 s 量级），纵轴为占用空间（0–1.0 GiB 量级）；曲线是高度 1 GiB 的一条水平线，阴影矩形面积即 1 GiB × 10 s = 10 GiB·s，描述这段等待期间的累计存储占用。

- **成功任务成本**：时间与状态之外，还要核算完成任务的代价。**成功任务成本 = 把所有尝试的成本相加，再除以成功任务数**。这样，失败生成、工具测试和环境运行都进入分子，分母对应用户得到的合格结果。**batch 零成功时，记录其总消耗与失败原因；取得成功结果后，再用全部尝试的总成本除以成功任务数。**

**辅导讲解**

- 这一个小节其实是"**先定义完成，再定义指标**"的方法论。原文那句"评估系统时，先写出什么算完成，再决定统计什么"值得单独记下来：如果你没有先定义"合格任务"，那么"每秒完成多少任务"这个数字可以被任意解释——把没写完的回答算成完成，吞吐立刻翻倍。
- 三个时间指标的分工可以用一个比方理解：TTFT 是"餐厅多久把第一道菜端上来"，token 间隔是"上菜的节奏"，完整请求时间是"整顿饭吃完要多久"。**优化其中一段只会改善包含它的指标**：比如把排队时间砍掉一半，TTFT 立刻变好，但菜端上来之后的出菜速度一点没变——这就是原文"减少请求开始执行前的排队会改善 TTFT，却不会自动缩短 token 间隔"的意思。
- p95 为什么用最近秩法而不是插值？因为最近秩法**一定返回一个真实存在的观测值**，不需要假设分布形状。四条请求的 p95 是最大值，这在样本量小时很反直觉（"p95 竟然等于 max"），但正是最近秩法的定义使然；样本少时 p95 就退化成"最坏情况"，读论文时要留意观测条数。
- 状态占用的"面积"是个非常好用的思维工具。你可以把它理解成"**停车位·小时**"：一辆车停 10 小时占 1 个车位，和 10 辆车各停 1 小时，占用面积都是 10 车位·小时，但对"同一时刻能容纳多少车"的压力完全不同。原文的 $\lambda M_0 \tau$ 说的正是后者：如果每秒有 $\lambda$ 个任务在等工具、每个都占 $M_0$、平均等 $\tau$ 秒，那么稳态下"正在等的任务数"就是 $\lambda\tau$ 个（这是排队论里的 Little 定律：系统中的平均任务数 = 到达率 × 平均逗留时间，此处为笔记补充的术语），占用空间就是 $\lambda\tau M_0$。所以工具等待时间一长，KV 池会被"没在算的请求"占满——这正是 3.1.3 结尾那个"状态池填满后，即使部分计算单元空闲，新请求也要等待"的伏笔。
- 工程上怎么用：一个成熟的推理服务至少要同时打三类日志——(1) 时间戳（到达、排队开始/结束、首 token、末 token）；(2) 状态（每个请求占多少 KV、属于哪个模型版本、存在哪张卡上）；(3) 结果（这次尝试成不成功）。缺了第 (3) 类，"成功任务成本"根本算不出来；缺了第 (2) 类，你只会看到"吞吐上不去"，却不知道是被计算拖住还是被状态占满。
- 不适用的情况：p95 对**短时间突发**不敏感。如果某个 10 秒的窗口里所有请求都卡住，但整段时间的 p95 仍在可接受范围，你在报表上什么也看不到——这就是 3.1.3 要引入排队模型的理由。

**易混点**

- **首响应（TTFT）与完整请求时间**：前者只到**第一个** token，后者到**最后一个** token。一个请求可以 TTFT 很差（排队很久）但完整时间不算离谱（生成很快），也可以反过来（几乎立刻开始输出，但输出很长很久）。3.1.3 的实测里，两种负载的"完整请求 p95"几乎相同，而"TTFT p95"相差约 16 秒，正是这个区别的直接体现。
- **内部思考 token 与用户可见输出**：reasoning 模型的"首个 token"可能是一个用户看不见的思考 token。原文因此强调要额外记录"首个有用输出"。若不区分，你会把"模型已经开始算了"误报成"用户已经看到回应了"。
- **"平均占用"与"峰值占用"**：$\lambda M_0 \tau$ 是稳态的平均值（单位 byte），$A_M$ 是一段时间的累计量（单位 byte·s）。前者回答"平均同时占多少"，后者回答"总共占用了多少资源时长"。

**一句话记住**

> 先定义"什么算完成"，再选指标：TTFT 管"多久开始"、token 间隔管"输出节奏"、完整请求时间管"多久做完"、$A_M=\int M(t)\mathrm{d}t$ 管"等待期间占了多少容量"、成功任务成本 = 全部尝试成本 ÷ 成功任务数。

### 3.1.3 请求分布

**原文要点**

- **空闲时间不能存起来**：前一分钟加速器有空闲，后一分钟突然到达许多需要长时间生成的请求，后到的请求仍然要排队：**先前空闲的计算时间无法留到现在使用**。TTFT 和输出间隔描述单个请求的体验；多个请求陆续到达时，这些指标还取决于各请求是否争用同一时段的处理能力。
- **负载描述要保留联合分布**：负载描述应保留**到达时间、输入与输出长度的联合分布**。长请求既增加自身服务时间，也可能延长状态驻留；短请求提前完成，则可能让后续请求较早开始。因此，即使平均工作量相同，等待时间、完成时间和状态占用峰值也可能不同。
- **客户组成会变**：实际请求往往来自不同客户。某个客户主要提交长文档，另一个主要生成长回答；即使各自的请求形状稳定，各客户请求到达速率的变化也会改变整体负载。**ServeGen** 对生产服务的研究观察到了这种现象，并用客户组成与时间变化重建请求分布。
- **图 3-4 的三种时间窗**：保持章首两分钟负载的请求总量与平均长度不变，只改变到达顺序，观察积压怎么变。

> 图 3-4（原文插图）：两分钟总量相同的三个时间窗中的请求组成。长输入类为 8192 输入、256 输出，长输出类为 1024 输入、2048 输出；两类混合比例改变阶段需求。各类请求的输入、输出长度均以 token 为单位。图中"均匀混合"两根柱子各占 0.5；"变化前窗"长输入类约占 0.9、长输出类约 0.1；"变化后窗"正好倒过来（约 0.1 对 0.9），纵轴为请求比例。

**例题 3-1：平均处理能力足够，为什么仍会积压？**（decode 由两张 RTX PRO 6000 Blackwell Workstation Edition 承担，判断它们能否持续处理章首的负载。）

**解（原文给出）**：定义两类请求：**长输入类**输入 8192、输出 256 个 token；**长输出类**输入 1024、输出 2048 个 token。两分钟内各到达 240 条，合计平均每秒四条。一种负载中，两类请求始终各占一半；另一种前一分钟两类占比为 $9:1$，后一分钟为 $1:9$。每条请求的首输出由 prefill 产生，后续 decode 步数为输出数减一，于是有：

| 时间窗 | 新输入 token/s | 后续 decode 步/s |
| --- | --- | --- |
| 均匀混合 | 18,432 | 4,604 |
| 时段变化，前一分钟 | 29,900.8 | 1,736.8 |
| 时段变化，后一分钟 | 6,963.2 | 7,471.2 |

（表格按原文语义还原。）

> 图 3-5（原文插图）：三个时间窗中，请求组成对应的输入与后续生成需求。输入数按 token 计，后续生成按每请求的一次 decode 步计；每请求首输出已计入 prefill。输入项统计每秒新处理的输入 token；decode 项统计所有请求每秒需要执行的后续 decode 步，每步推进一个 token。图中"均匀混合"输入约 18,432、decode 约 4,604；"变化前窗"输入高（约 29,900）、decode 低（约 1,737）；"变化后窗"输入低（约 6,963）、decode 高（约 7,471）——两个时间窗分别在压不同的资源。

- **队列假设**：窗口内均匀到达、处理率固定。使用**流体队列模型**，把离散的生成工作近似为连续流量；每个窗口内均匀到达，处理率固定，初始队列为空。单位是一条请求的一次后续 decode 步，**prefill 能力单独核算**。以时间窗为步长，积压逐窗递推：

$$Q_{k+1} = \max\bigl(0,\ Q_k + A_k - \mu_k \Delta t\bigr)$$

  其中 $Q_k$ 是窗口开始时的待处理工作（单位：decode 步），$A_k$ 是窗口内新到达的工作（decode 步），$\mu_k \Delta t$ 是可完成量（$\mu_k$ 为处理率，单位步/秒；$\Delta t$ 为窗口长度，单位秒）。到达速度低于处理速度时，积压逐渐减少，直至队列排空；到达速度超过处理速度时，未完成的工作留到下一窗口。

> 图 3-6（原文插图）：工作先进入队列，再由处理资源完成。图中左侧是"新到工作"流入"待处理队列"，右侧是"完成工作"流出；标注说明"到来速度超过处理速度，队列就增长"、"处理快于到来时，资源逐步消化已有积压"。这是一张概念示意图，不含坐标轴。

- **处理率 $\mu_k$ 要从硬件参数求出**：每秒四个请求的首个输出由 prefill 产生，所以 4,608 个输出中有 4,604 步属于后续 decode（$4608 - 4 = 4604$，每条请求减去由 prefill 产出的首输出）。decode 的处理率由**显存带宽**决定。RTX PRO 6000 Blackwell Workstation Edition 有 **96 GB 显存、1792 GB/s 带宽**，每张卡各放一份完整的 Qwen3-8B BF16 权重，最多同时执行 **64 条序列**。每步 decode 至少要把 **15.14 GB 共享权重**读一遍，再读出每条序列的全部旧 KV，**每个上下文 token 占 144 KiB**。
- **平均上下文**：decode 期间，长输入类的平均上下文为 $8192 + 127 = 8319$ 个 token，长输出类为 $1024 + 1023 = 2047$ 个；均匀混合时按 decode 步加权，平均上下文为

$$\frac{255 \times 8319 + 2047 \times 2047}{2302} \approx 2742\ \text{个 token}$$

- **带宽下界**：64 条序列同时执行时，一步至少读写 41.02 GB，耗时 22.89 ms，所以一张卡每秒最多完成约 **2,795.66 步**，两张卡约 **5,591.33 步**。原文强调：**这一处理率是显存带宽允许的物理极限，实测只会更低**。三个时间窗都沿用这一处理率。

> 🔎 检索确认：NVIDIA RTX PRO 6000 Blackwell Workstation Edition 确有 96 GB GDDR7（ECC）显存的版本，与原文"96 GB 显存"一致。原文给出的 1792 GB/s 带宽未在本次检索中独立核实，笔记按原文保留。（来源：[PNY NVIDIA RTX PRO 6000 Blackwell 96GB GDDR7 ECC PCIe 5.0 x16](https://cipc.com/en/details/pny-nvidia-rtx-pro-6000-blackwell-96gb-gddr7-ecc-pcie-50-x16-4xdp-video-card-vcnrtxpro6000b-pb)）
- **积压与排空**：令 decode 队列初始为空，先把请求的生成工作均匀汇入各窗口。均匀混合和前一分钟的处理能力都足够；后一分钟每秒多到来 $7471.2 - 5591.33 \approx 1879.87$ 步，60 秒便留下约 **112,792 步**；停止到达后，按 $112792/5591.33$ 计算，还需约 **20.17 秒**才能排空。**前一分钟未使用的能力无法保存到后一分钟，这正是全局均值掩盖积压的原因。**

> 图 3-7（原文插图）：两张 RTX PRO 6000 每秒最多完成约 5,591 个 decode 步时的流体模型。横轴为从开始到达计时（0–140 s 量级），纵轴为待处理 decode 步（0–140,000 量级）。曲线在前 60 秒线性上升到约 112,792 步（图中标出"112,792 步"），第 120 秒停止到达，随后按处理率线性下降，再经过约 20.17 秒排空。

- **KV 容量限制如何影响排队与首响应**：在 Qwen3-8B／vLLM 0.23 上运行这两种到达序列，可以观察到上述差异如何影响用户等待。加速器为一张 96 GB 显存的 RTX PRO 6000 Blackwell Workstation Edition，**KV 池**是专门留给请求键值上下文的显存区域，本次容量为 **24 GiB**，同时最多执行 64 条序列；**前缀缓存**指跨请求复用相同开头的已有 KV，本次**关闭**这一功能，每条请求生成指定数量的 token。KV 空间不足时，调度器可以暂停某条已开始的请求、释放它占用的 KV 空间，之后再恢复或重算，这种行为称为**抢占**（preemption）。两组负载都在 120 秒内到达 480 条请求，全部完成后的结果如下（表格按原文语义还原）：

| 实际观察 | 均匀混合 | 前 9:1、后 1:9 |
| --- | --- | --- |
| 完整请求 p95 | 约 299.4 s | 约 299.4 s |
| TTFT p95 | 242.9 s | 258.9 s |
| 初次调度等待 p95 | 242.4 s | 258.4 s |
| 最后一条请求完成时距起点的时间 | 419.8 s | 418.7 s |
| 抢占事件 | 62 | 24 |

- **结果解读**：两次回放都出现了大量积压，这在例题 3-1 的带宽下界中已经可以预见：一张卡每秒最多完成约 2,796 个 decode 步，低于均匀混合时 4,604 步的平均需求，而且同一张卡还要执行 prefill。480 条请求共需 **552,480 个后续 decode 步**，单是这部分工作就至少需要 **197.6 秒**，而全部请求在 120 秒内就已到达。
- 两次回放的完整请求 p95 与最后完成时间接近，TTFT 和初次调度等待却**相差约 16 秒**。采样记录显示，两次实验的 KV 池占用都达到过 100%，请求在进入执行前经历了长时间等待。输入与输出的时段组合改变了何时释放状态、何时接纳新请求，所以即使整批请求的完成时间接近，用户开始收到响应的时间仍可不同。**KV 池填满时发生的抢占，还会改变请求的等待和后续执行次序。**

> 图 3-8（原文插图）：同一实际实例回放两种到达序列的结果。横轴为客户端时间（0–350 s 量级）。"均匀混合"与"时段变化"两组柱中，"完整请求 p95"两根几乎等高（约 299 s），而"首响应 p95"两根分别约 243 s 与 259 s，相差约 16 秒；模型、加速器、KV 池与并发上限均按正文实验条件固定。

- **结论式的一句话**：排队因此**既可能来自处理速度不足，也可能来自已有请求的状态尚未释放**：状态池填满后，即使部分计算单元空闲，新请求也要等待已有请求释放空间。
- **通用突发公式**：例题 3-1 中的积压递推式还能预测其他突发条件下的积压。若工作到达速率 $\lambda_w$ 连续 $\tau$ 秒高于处理率 $\mu$，初始队列为空，则积压为

$$Q = (\lambda_w - \mu)\tau,\qquad T_{\text{drain}} = \frac{(\lambda_w - \mu)\tau}{\mu}$$

  也就是说，**突发持续时间加倍，积压与排空时间都加倍**（因为分子里有个 $\tau$，而分母 $\mu$ 不变）。

**练习 3-2〔核心〕：突发请求与工具等待如何增加积压和状态占用**

**题干（原文）**：采用例题 3-1 中第二分钟的负载强度，即每秒新增 7,471.2 步 decode 工作。将这一突发负载的持续时间改为 30 秒，decode 资源分别取两张和三张 RTX PRO 6000 Blackwell Workstation Edition，每张卡的处理率沿用例题 3-1 求得的约 2,796 步/秒。初始队列为空，求这 30 秒内积压量随时间的变化，以及请求停止到达后清空积压所需的时间。随后考虑另一种负载：每秒有两个任务进入工具等待阶段，每个任务等待 10 秒，期间状态占用 1 GiB 空间。求稳定状态下的平均等待任务数与状态占用；将等待延长到 30 秒后重新计算。

**参考解答（笔记补充，非原文）**

1. 突发积压。到达率 $\lambda_w = 7471.2$ 步/s。
   - 两张卡：$\mu = 2 \times 2795.66 = 5591.33$ 步/s。净增长 $7471.2 - 5591.33 = 1879.87$ 步/s，则积压随时间线性增长 $Q(t) = 1879.87\,t$（$0 \le t \le 30$ s，初始队列为空），30 秒末 $Q(30) = 1879.87 \times 30 \approx 56{,}396.1$ 步。停止到达后按 $\mu$ 排空，$T_{\text{drain}} = 56396.1/5591.33 \approx 10.09$ s。
   - 三张卡：$\mu = 3 \times 2795.66 = 8386.99$ 步/s $> 7471.2$ 步/s，到达速度低于处理速度，队列始终为空，积压恒为 0，无需排空。
   - 与例题 3-1 对照：例题里突发持续 60 秒、资源两张卡，积压 112,792 步；这里突发只有 30 秒，积压正好减半（56,396 步），排空时间也从 20.17 s 减半到约 10.09 s——这正是"突发持续时间加倍，积压与排空时间都加倍"的直接体现。
2. 工具等待。到达率 $\lambda = 2$ 个/s，每个任务等待 $\tau$ 秒、占用 $M_0 = 1$ GiB。
   - $\tau = 10$ s：稳态平均等待任务数 $\approx \lambda\tau = 2 \times 10 = 20$ 个；平均状态占用 $\approx \lambda M_0 \tau = 2 \times 1 \times 10 = 20$ GiB（等价地说，占用面积的增长速率为 20 GiB·s 每秒）。
   - $\tau = 30$ s：任务数变为 $2 \times 30 = 60$ 个，平均占用变为 $2 \times 1 \times 30 = 60$ GiB。
   - 结论：**等待时间延长三倍，等待中的任务数和被占住的容量都延长三倍**，而这些任务在等待期间一次计算也没做。

**辅导讲解**

- 先看例题 3-1 的表是怎么算出来的，否则很容易以为作者随手给的数（以下均为笔记复算）：
  - 均匀混合：每秒 2 条长输入 + 2 条长输出。输入 token/s $= 2\times 8192 + 2\times 1024 = 18432$；decode 步/s $= 2\times(256-1) + 2\times(2048-1) = 510 + 4094 = 4604$。
  - 前一分钟 $9:1$：240 条里长输入 216 条、长输出 24 条，即每秒 3.6 条与 0.4 条。输入 token/s $= 3.6\times 8192 + 0.4\times 1024 = 29491.2 + 409.6 = 29900.8$；decode 步/s $= 3.6\times 255 + 0.4\times 2047 = 918 + 818.8 = 1736.8$。
  - 后一分钟 $1:9$：反过来，每秒 0.4 条长输入与 3.6 条长输出。输入 token/s $= 0.4\times 8192 + 3.6\times 1024 = 3276.8 + 3686.4 = 6963.2$；decode 步/s $= 0.4\times 255 + 3.6\times 2047 = 102 + 7369.2 = 7471.2$。
  - 三个窗口的两分钟总量完全相同（各 480 条请求、两类各 240 条），所以"平均值一样"，但阶段需求在"输入重"和"生成重"之间来回摆动。
- 再看那个 41.02 GB / 22.89 ms / 2795.66 步的算式，这里有一个**计数单位的坑**，原文写得很紧凑（以下为笔记拆解）：
  - 一步（一个 batch 迭代）要读：共享权重 15.14 GB + 64 条序列各自的旧 KV。KV 部分 $64 \times 2742 \times 144\ \text{KiB} = 175{,}488 \times 147{,}456$ bytes $\approx 25.88$ GB。合计 $15.14 + 25.88 \approx 41.02$ GB。
  - 用带宽折算：$41.02\ \text{GB} / 1792\ \text{GB/s} = 22.89$ ms。这是**一个 batch 迭代**的时间。
  - 一个 batch 迭代同时推进 64 条序列各一个 token，也就是完成了 **64 个 decode 步**。所以每秒的步数 $= 64 / 0.02289\ \text{s} \approx 2795.66$ 步/s。这解释了为什么"22.89 ms 一步"却能"每秒 2795 步"：原文说的"步"是**按序列计的 decode 步**，不是按 batch 迭代计的次数。读原文时如果不注意这一点，会觉得数字自相矛盾。
  - 两张卡翻倍到 5591.33 步/s。
- **为什么"处理能力足够"仍会积压**？因为"够"是**平均值**层面的够。均匀混合下平均需求 4604 步/s，确实低于两卡的 5591.33 步/s；但后一分钟的需求是 7471.2 步/s，超出 1879.87 步/s。计算能力**不像电池**，前一分钟空闲出来的算力不能存进"余量账户"里（原文的"先前空闲的计算时间无法留到现在使用"）。这就是排队系统与预算系统的本质区别：预算看总量，排队看逐时刻的差额。
- **两个不同的瓶颈**：例题 3-1 表里的积压来自**处理率不足**；实际回放里 TTFT p95 的差异（16 秒）却主要来自**状态池**——KV 池 24 GiB 被占满，新请求排队等空间，而不是等算力。注意实测里的一个反直觉现象：时段变化那组"抢占事件"只有 24 次，比均匀混合的 62 次还少。这并不矛盾：均匀混合下两类请求长期同时在场，KV 池更容易被"各占一半、互不释放"的组合填满；而时段变化下前段以长输入为主（输入算完就可以较早释放？并非如此——长输入生成的 KV 会一直留到请求结束），原文只给出了观测值和"抢占会改变等待与执行次序"的定性结论，未展开机制解释；上面这句只是笔记按请求在场情况作的一般性提示，不再作定量推断。
- **抢占（preemption）为什么必须存在**：KV 池是有限的。如果调度器宁可让新请求等也不肯打断老请求，那么一条超长请求就能把池子锁死很久，TTFT 会彻底失控。抢占的代价是"被抢占的请求要恢复或重算"——如果它必须从零重算 prefill，那省下的等待就变成了额外的计算。
- **工程上的三个动作**：
  1. 报指标要分工。想看"容量够不够"看吞吐与状态占用；想看"体验好不好"看 TTFT p95；想看"整件事多久做完"看完整请求 p95。三个都看，才能区分是算力瓶颈还是容量瓶颈（对照 3.1.3 实测：两个负载的完整请求 p95 相同、TTFT p95 差 16 秒）。
  2. 突发要按窗口算，不要按天算。用 $Q = (\lambda_w-\mu)\tau$ 先做一页纸的估算，就能在买卡之前知道"峰值时段会积压多少、峰值过后多久能消化掉"。
  3. 工具等待要按容量算。$\lambda M_0 \tau$ 告诉你，就算 GPU 全空闲，仅仅是"一堆请求在等工具回调"也能把 KV 池吃干净（第 8、9 章会讲换出与缓存策略）。
- **不适用的情况**：流体队列把离散工作近似成连续流量，适合"窗口内到达很多、单条工作相对小"的场景。如果窗口内只到达一两条超长请求（单条就上万步），连续近似会失真，此时应直接做逐请求的时间线推演。

**易混点**

- **处理率不足 vs 状态池不足**：两者都表现为"排队变长、TTFT 变差"，但根源不同。判别方法：如果算力（decode 步/s）低于到达需求，是前者；如果算力有富余而 KV 池占用长期接近 100%，是后者。原文 3.1.3 的实测里两者同时存在。
- **p95 的"完整请求"与"TTFT"**：同一个 KV 池填满，会让首响应变差，却未必改变完整请求时间——因为请求迟早都要做完，总工作量没变，只是"开始得晚、结束得也就晚一点或在同一时间结束"。原文给的数据正是：完整请求 p95 都是约 299.4 s，TTFT p95 却是 242.9 s 对 258.9 s。
- **$1:9$ 与 $9:1$ 的方向**：前一分钟 $9:1$ 指"长输入类 : 长输出类 = 9 : 1"（输入重），后一分钟 $1:9$ 指反过来（生成重）。搞反了会把两条曲线完全对调。

**一句话记住**

> 平均值够用不代表不积压：$Q_{k+1}=\max(0, Q_k + A_k - \mu_k\Delta t)$ 逐窗算账，$(\lambda_w-\mu)\tau$ 估突发积压，$\lambda M_0\tau$ 估工具等待占住的容量；容量瓶颈和带宽瓶颈都会让用户等，但修法完全不同。

## 3.2 多轮交互与 Agent 任务

### 3.2.1 多轮对话与前缀增长

**原文要点**

- **从独立请求到相连调用**：3.1 节把每个请求当作一次独立调用；在对话和 Agent 任务中，**同一任务的多次调用前后相连**。多轮对话的下一次请求通常带着上下文：第一轮输入系统提示和用户问题；第二轮除了新问题，还可能包含上一轮回答；之后每轮继续累积。**若只看用户新写了多少字，就会低估送入模型的输入长度。**
- **前缀复用的基本关系**：设第 $i$ 轮输入长度为 $I_i$，可复用的前缀长度为 $K_i$，则本轮需要重新处理的输入为

$$P_i = I_i - K_i,\qquad S_i = K_i$$

  将 $P_i$ 与 $S_i$ 代入第 2 章的公式：**投影和 FFN 只处理新增 token，注意力仍要让新查询访问完整前缀**。缓存复用因而**减少了重算，却没有把旧上下文从后续计算中删除**。
- **四轮代码修复任务的缓存收益**：四轮累计输入 5,297 个 token，其中命中 4,480 个，未命中 817 个。第二轮输入 1,443 个、命中 1,392 个，只需处理 51 个未缓存 token；**但后续 decode 仍然要访问其上下文状态**。如果每轮都重新计算全部输入，prefill 的矩阵运算共需 **76.196 TFLOPs**；复用已命中的前缀后，共需 **11.976 TFLOPs**。因此，**缓存命中既减少了旧输入的重算，也要求系统继续保留旧状态**。
- **修改上下文会改变可复用的前缀长度**：
  - **末尾追加**新内容时，原有前缀保持不变；
  - **摘要替换一段旧上下文**时，替换位置之后的表示要从新的前缀重新计算；
  - **工具定义或模板变化**则可能更早改变输入。
  这些操作决定下一轮有多少 token 命中、多少 token 重新进入 prefill。
- **上下文策略会改变未来负载**：把新内容持续追加在上下文末尾，有利于复用原有前缀，却会让陈旧内容继续占据上下文；替换前面的内容可以缩短上下文，但其后的缓存可能需要重建。**保留、淘汰和重算的代价取决于重建计算量、状态大小与复用间隔**（第 8 章）。
- **编辑位置决定收益（原文的量比较）**：在末尾追加 100 个 token，只增加 100 行新输入；若改动已有 2,000 个 token 中的第 501 个，其后的表示都会变化，最长可直接复用的前缀只剩 500 个 token。**缓存收益不仅取决于改了多少字，还取决于改动发生在哪里。**
- **两个视角**：从应用看，上下文是编排任务的接口；从系统看，上下文的组织方式决定了计算量和状态驻留时间。追加工具返回的内容、替换早期内容、生成多个候选分支，分别改变新增计算、可复用前缀和私有状态。
- **负载记录应增加字段**：应包含**稳定前缀、改写位置、分支依赖和复用间隔**。第 8 章将使用这些信息选择上下文与缓存策略，第 9 章再加入状态位置和传输时间。

**辅导讲解**

- 这一小节的价值在于把"上下文工程"翻译成系统语言。用户看到的是"我又追问了一句"，系统看到的是"输入长度从 $I$ 变成 $I+\Delta$，其中 $K$ 个 token 的 KV 可以直接拿现成的，$P$ 个要重算，而且这 $K+P$ 个 token 的 KV 在后续 decode 中还要被反复读"。**应用层的一个小动作，在系统层是一组明确的代价**。
- 把四轮任务的数据流走一遍（数据来自原文，说明为笔记整理）：
  - 累计输入 5,297 token，命中 4,480（命中率 $4480/5297 \approx 84.6\%$），未命中 817（约 $15.4\%$）。
  - 全量重算的 prefill 矩阵运算 76.196 TFLOPs，复用后 11.976 TFLOPs，比值约 $6.36$ 倍。
  - 注意这个比值远高于 $5297/817 \approx 6.48$ 的"token 比"——两者接近并不是巧合：prefill 的投影/FFN 部分确实与 token 数成正比。所以一个很好用的经验是：**prefill 的投影类运算量大致与"未命中的新 token 数"成正比**。但注意原文紧接着补了一句关键限定：**注意力部分仍要让新查询访问完整前缀**，所以不能把全部 prefill 成本都按未命中 token 数等比缩小。
- "命中"到底省了什么、没省什么，值得逐项列清（笔记整理，依据原文"投影和 FFN 只处理新增 token，注意力仍要让新查询访问完整前缀"）：
  - 省了：新 token 的 QKV 投影、FFN、以及旧 token 的投影与 FFN 重算。
  - 没省：新 token 的注意力要 attend 到全部 $S+P$ 个位置（$QK^{\mathsf T}$ 与 $AV$ 的查询数减少了，键数没减少）；后续 decode 每一步仍要读全部旧 KV。
  - 因此，"命中率高"擅长省算力（compute），但**不省状态（memory）**。这正是原文那句"缓存复用减少了重算，却没有把旧上下文从后续计算中删除"的完整含义。
- 编辑位置的算例可以这样理解：KV 是**从左到右**依赖的。改动第 501 个 token，第 501 个位置的注意力分布变了，它之后的每个位置都跟着变，所以能直接复用的最短公共前缀只有前 500 个 token。而改动越靠后，可复用前缀越长。工程上有个直接推论：**把易变的内容（工具返回、最新观测）放在末尾，把稳定内容（系统提示、工具定义、模板）放在开头**，能把缓存命中率拉到最高。反过来说，如果系统提示或工具定义频繁变动，整条上下文的缓存就废了。
- 一个容易忽略的坑：**"缩短上下文"未必省钱**。把一段旧内容替换成摘要确实让总长度变小，但替换点之后的 KV 全部作废，下一轮要重建。到底值不值，要比较"重建的计算量"和"后续每轮省下的读取量"，再乘上"这段内容还剩多少轮会被用到"（复用间隔）。原文把这个问题留给第 8 章，但判断框架在这里已经给出。
- 与 3.1.1 的联系：3.1.1 里的 $S$ 与 $P$，就是这里每轮的 $S_i$ 与 $P_i$。也就是说，3.1.1 假设的"恢复 $S$ 个上下文、处理 $P$ 个新输入"这个前置条件，在多轮场景里是**由上一轮的历史自然产生的**；"恢复"不是从磁盘读一份 KV 回来，而是"上一轮的 KV 还在显存里，这一轮直接接着用"。

**易混点**

- **命中（cache hit）≠ 不读**。命中省的是**算**，不是**读**：decode 时仍然要把命中的那些 token 的 KV 从显存里读出来参与注意力。把"命中率高"误当成"状态占用小"，是规划 KV 池容量时最常见的错误。
- **输入长度 $I_i$ 与新增输入 $P_i$**：用户新写的那句话只是 $P_i$ 的一部分（$P_i$ 还可能包含新的工具返回、新的检索结果）。原文的"若只看用户新写了多少字，就会低估送入模型的输入长度"正是指这一点。
- **"替换"与"追加"的缓存后果完全不同**：追加使前缀不变（缓存友好），替换使替换点之后的缓存全部失效（缓存不友好）。所以"同样改了 100 个 token，代价可能差几个数量级"。

**一句话记住**

> 多轮调用里 $P_i = I_i - K_i$、$S_i = K_i$：命中省的是重算、不省状态；而缓存收益取决于**改动发生在哪里**——末尾追加最便宜，越靠近开头越贵。

### 3.2.2 推理与验证：完成一个任务需要多少成本

**原文要点**

- **问题的转换**：前缀缓存减少的是已有输入的重复计算；**另一类方法则主动增加生成计算**，希望提高答案的正确率。
- **增加推理阶段计算量的三种方式**：
  1. **延长一条回答中的思考过程**（test-time compute 的一种形态）；
  2. **同时生成多份回答并从中选择**；
  3. **根据题目难度分配生成次数和长度**。
  原文指出各自的代价：延长思考会增加**串行生成时间与上下文状态**；生成多份回答会增加**计算和验证次数**；按难度分配则需要**决定每道题何时停止**。
- **成功任务成本公式**：是否值得增加生成计算，需要比较每个成功任务的成本。设每次尝试的平均成本为 $c$、成功率为 $p$，相同策略下重复尝试的期望次数为 $1/p$，则

$$C_{\text{success}} = \frac{c}{p}$$

- **决策准则**：新方法的成本和成功率分别为 $c_2, p_2$，旧方法为 $c_1, p_1$，**成本下降要求**

$$\frac{p_2}{p_1} > \frac{c_2}{c_1}$$

  也就是说，延长思考或增加采样的依据，是**正确率的相对提升能否超过成本的相对增长**。原文特别强调：**所有生成、验证和失败尝试的成本都计入 $c$。**
- **例子：延长生成仍未提高数学题解答成功率。** 生成速度只有与任务正确率一起考察，才能反映系统是否有用。一次数学题实验中，对四道题分别生成多份回答，将**输出上限从 1024 提高到 4096 个 token，两轮尝试仍未得到通过评分的最终答案**。生成已经消耗资源，任务却没有完成；**增加输出长度也没有自动带来有效解答**。
- **答案检查要分两类**：答案检查应区分**接口格式**和**内容正确性**。格式正确的回答可能算错，数值正确的回答也可能缺少任务要求的字段。**把两类错误分开，才能判断应调整生成方式、输出约束还是解题过程。**
- **价格变化下的成本核算**：核算成本时，还要考虑价格本身的变化。token 单价降低后，仍需计算完成任务的总成本。原文用简单假设说明：新系统 token 单价降到原来的 $1/10$，每任务用量却增加到 20 倍，成功率由 50% 提高到 80%。只计模型成本，并假定重复尝试的分布稳定，每个成功任务的成本比为

$$\frac{c_2}{c_1}\cdot\frac{p_1}{p_2} = \frac{2 \times 0.5}{0.8} = 1.25$$

  其中 $c_2/c_1 = (1/10)\times 20 = 2$。（原文写作 $2 \times 0.5 / 0.8 = 1.25$。）**价格下降、质量提高和成功任务成本上升可以同时发生。** 对带上下文的 Agent，可以沿实际轨迹累加各次尝试，再以通过检查的任务数作分母。

> 图 3-9（原文插图）：各尝试 100 次的教学比较。左侧"原策略"：100 成本 ÷ 50 次成功 = 2 成本／成功；右侧"新策略"：200 成本 ÷ 80 次成功 = 2.5 成本／成功。所有尝试的成本都进入分子，通过检查的成功任务数进入分母；两种策略的成功任务成本分别为 2 和 2.5 单位。图中标注"两种策略各尝试 100 次"。

**练习 3-3〔延伸〕：成功率提高能否抵消单次尝试成本的增加**

**题干（原文）**：旧方法每次尝试成本为 1 单位、成功率为 50%；新方法成本为 2 单位、成功率为 80%。计算平均每完成一个成功任务所需的成本，并判断新方法是否更省。若新方法成本降到 1.5 单位，成功率至少应达到多少，才能使每个成功任务的平均成本不高于旧方法？对需要多次采样的任务，说明生成、验证和失败尝试的开销应怎样计入总成本。

沿用第 3.2.4 节末的决策请求算例：决策模型处理一条请求花费 0.000081 美元，转交 LLM 每条花费 0.013880 美元。设转交前后的成功率分别为 $p_1, p_2$，求转交比例为 1% 和 5% 时每条请求的平均费用；$p_2/p_1$ 至少达到多少，转交才能降低每个成功任务的费用？

**参考解答（笔记补充，非原文）**

1. 单价比较。旧方法 $C_1 = 1/0.5 = 2$ 单位/成功；新方法 $C_2 = 2/0.8 = 2.5$ 单位/成功。$2.5 > 2$，**新方法不更省**：成功率从 50% 提到 80% 只提升了 1.6 倍，而单次成本涨了 2 倍，$p_2/p_1 = 1.6 < c_2/c_1 = 2$。
2. 成本降到 1.5 单位时，要求 $1.5/p_2 \le 2$，即 $p_2 \ge 0.75$，**成功率至少 75%**。
3. 多次采样的成本归集（依据原文"所有生成、验证和失败尝试的成本都计入 $c$"）：分子应包含每一次采样的生成成本、每一次验证／评分的成本（含另一个模型的前向、规则测试、沙箱运行时间）、被丢弃样本的成本，以及失败后重试的全部成本；分母只放**通过检查的成功任务数**。因此 $c$ 本身已经是"每次尝试的平均成本"，$p$ 是"单次尝试通过的概率"，$C_{\text{success}} = c/p$ 就是"含失败摊销的每成功任务成本"。
4. 转交算例。每条请求的平均费用为

$$c(e) = c_{\text{dec}} + e\,c_{\text{LLM}} = 0.000081 + e \times 0.013880$$

- $e = 1\%$：$c = 0.000081 + 0.0001388 = 0.0002198$ 美元/条。
- $e = 5\%$：$c = 0.000081 + 0.000694 = 0.000775$ 美元/条。

  要让转交降低每成功任务费用，需 $\dfrac{c_{\text{dec}} + e\,c_{\text{LLM}}}{p_2} < \dfrac{c_{\text{dec}}}{p_1}$，整理得

$$\frac{p_2}{p_1} > 1 + e\,\frac{c_{\text{LLM}}}{c_{\text{dec}}} = 1 + e \times 171.358$$

- $e = 1\%$：$p_2/p_1 > 1 + 0.01\times 171.358 \approx 2.71$（转交后的成功率要达到原来的约 2.71 倍以上才划算）。
- $e = 5\%$：$p_2/p_1 > 1 + 0.05\times 171.358 \approx 9.57$。

  这说明"**只把少量难例转交给贵模型**"是否划算，完全取决于那部分请求的成功率能提升多少——转交比例越高，门槛涨得越快。

**辅导讲解**

- $C_{\text{success}} = c/p$ 这个式子看起来简单，但它是本章最重要的"思维换挡"之一：**把"每次调用多少钱"换成"每个成功结果多少钱"**。用前面的停车场比方：单次尝试成本是"每次停车收费"，成功率是"停进去的概率"；如果一次停不进去还得再绕一圈，真正该算的是"停好一次平均花多少钱"。这也解释了为什么"token 降价"不等于"任务变便宜"——如果为了拿到同样的成功率需要多生成 20 倍的 token，单价降 10 倍正好被抵消掉（$c_2/c_1 = 2$）。
- 三种"增加推理计算"的方式，本质区别在于**代价落在哪个维度**（笔记整理）：
  - 延长思考：代价主要是**串行时间**（$G$ 变大 → decode 步数变多）和**上下文状态**（KV 变长）。它不增加并发的份数，但直接拉长关键路径。
  - 生成多份再选：代价主要是**并行计算量**（prefill 与 decode 都按份数放大）和**验证成本**（要么用规则/测试，要么再上一次模型）。它可以并行，因此可能只放大吞吐需求而不放大延迟。
  - 按难度分配：代价是**调度决策的复杂度**——难在"何时停"。停早了浪费已投入的算力，停晚了纯烧钱。
- 原文那个"延长到 4096 token 仍未通过评分"的例子值得反复看。它提醒我们一个反直觉的事实：**生成更长 ≠ 更可能答对**。模型可能在错误的方向上"想得更久"，把 4,096 个 token 全部用在复述和绕圈上。所以在做资源规划时，不能把"输出上限提高 4 倍"直接换算成"成功率提高"，必须实测。这也是原文那句"生成速度只有与任务正确率一起考察，才能反映系统是否有用"的分量所在。
- "接口格式 vs 内容正确性"这个区分，工程上对应两类完全不同的修法：格式错 → 改输出约束、改 schema、改解析（这是**工程问题**）；内容错 → 改提示、改检索、改模型或加采样（这是**能力问题**）。如果把两者混在一个"准确率"数字里，你会不知道该调哪一头。原文说要"把两类错误分开"，实际上也意味着日志里要有结构化的失败原因字段——这正好接回 3.1.2 里"batch 零成功时要记录失败原因"的要求。
- **不适用于**：$C_{\text{success}} = c/p$ 假设"重复尝试的分布稳定"（每次尝试独立同分布、$p$ 不随尝试次数漂移）。如果模型会记住上一次的错误（多轮自我修正），$p$ 会随尝试次数变化；如果系统会因反复失败而限流，$c$ 也会变化。原文明确写了"假定重复尝试的分布稳定"这一前提，用的时候别把它丢掉。

**易混点**

- **单次尝试成本 $c$ 与成功任务成本 $C_{\text{success}}$**：前者是"打一枪的成本"，后者是"打中一只兔子的成本"。报价单上通常只有前者，决策必须用后者。
- **$p_2 > p_1$ 与 $C_2 < C_1$**：成功率提高**不自动**意味着更省钱，必须看 $p_2/p_1$ 是否大于 $c_2/c_1$。练习 3-3 里的 50%→80%（×1.6）配 1→2 单位（×2）就是反例。
- **降价带来的"用量暴增"**：单价降 10 倍、用量涨 20 倍，实际单次成本反而变成 2 倍。这是"成本下降"叙事里最常被漏掉的一项。

**一句话记住**

> 一切都要折算成 $C_{\text{success}} = c/p$：分子含生成、验证与全部失败尝试，分母只数通过检查的成功任务；新方法划不划算看 $p_2/p_1$ 是否大于 $c_2/c_1$。

### 3.2.3 智能体工作负载

**原文要点**

- **反馈改变后续计算**：代码 Agent 先生成修改方案，工具写入代码并运行测试，模型再读取测试结果决定下一步。**每个循环既有模型计算，也有工具执行**；工具返回的日志又成为下一轮输入。因此：**减少无关日志能降低下一轮的 prefill 计算量和上下文状态占用，减少无效修改则能直接减少循环次数。**
- **本章的实测任务**：修复**区间合并函数**，检查**返回结果是否正确**、**输入是否保持不变**。模型负责决定修改并调用工具，工具负责写入文件和运行测试。
- **统计口径**：按四轮内成功完成原定检查的那条轨迹，**分开统计模型时间、工具时间和等待期间保存的状态**。工具调用明细见章末"代码任务轨迹"。
- **检索增强问答同构**：检索增强问答也包含类似的处理过程：检索器找到文档，再将文档交给语言模型生成答案。**回答质量相同时，检索内容越少，后续 prefill、KV 存储和上下文读取的开销就越小。** 因此，检索器返回的内容会直接影响模型负载。第 8 章将结合具体任务比较不同检索方案。

**辅导讲解**

- 这一小节短，但给的是一个**通用的 Agent 负载拆解方法**：把一个 Agent 任务拆成"模型段 / 工具段 / 等待段"三类时间，再把"等待段"里仍在占用的状态单独记一笔。原文明确要求"分开统计模型时间、工具时间和等待期间保存的状态"，因为这三者的优化手段完全不同：模型段靠更强的加速器或更小的模型，工具段靠并行和更快的环境，等待段靠换出/缓存/更短的依赖链。
- 为什么"减少无关日志"如此有效？回到 3.2.1 的公式：下一轮的输入 $I_{i+1}$ 里包含了工具返回的日志。日志是最典型的"**前缀不稳定 + 内容冗长**"的数据——它一变，从它开始往后的所有 KV 都作废（3.2.1 讲的"改写位置"）；它一长，prefill 的行数和 KV 池的占用都上去。所以"少给模型看无关日志"是**同时**降计算、降状态、提缓存命中率的三重收益。这是 Agent 系统里性价比最高的优化之一。
- 数据流走一遍（笔记整理）：模型决定改哪几行 → 控制器把补丁写进文件 → 运行固定测试 → 捕获 stdout/stderr → 把（可能被截断或摘要过的）测试输出拼到上下文末尾 → 进入下一轮。注意"拼到末尾"这个动作本身是**缓存友好**的（前缀不变），而"把日志摘要后替换掉上一轮日志"是**缓存不友好**的。工程上很多系统为了省 token 做了后者的替换，结果把缓存全打掉了——收益可能为负。
- 与 3.2.1 的呼应：这里的"每轮输入"就是 3.2.1 的 $I_i$，"命中"就是 $K_i$，"新处理"就是 $P_i$。原文在 3.2.4 会给出这个实测任务的完整数据（12 轮 vs 4 轮、765 vs 2,733 输出 token 等），到那里可以把这里的定性描述对上具体数字。
- **检索增强（RAG）同理**：检索器返回的文档就是"工具返回的内容"。检索得越多，看起来"证据更全"，但 prefill 行数、KV 占用、后续每步 decode 要读的旧 KV 都跟着涨。原文说"回答质量相同时，检索内容越少，开销越小"——注意前提是**质量相同**；如果减少检索会让质量掉下来，那么按 3.2.2 的成功任务成本公式，省下的计算未必能补偿成功率下降。
- **不适用的情况**：如果工具调用是"执行很久但不返回大量文本"的类型（例如编译 10 秒只回一行结果），那么"减少日志"几乎无用，瓶颈在**工具执行时间**和它带来的状态驻留（见 3.2.4）。判断该往哪优化，先看这类任务的实测时间构成。

**易混点**

- **"减少循环次数" 与 "减少每轮开销"**：前者靠提高单次修改的正确率（更好的模型/提示/验证），后者靠裁剪输入（少喂日志、少喂检索）。两者的收益结构不同：减少一次循环等于省下"一整轮模型时间 + 一整轮 KV"；减少每轮 token 只省一部分。
- **工具时间与工具等待状态**：工具只跑 0.078 秒，状态占用几乎可以忽略；工具跑 10 秒，同样的语句就变成 10 GiB·s 的占用（练习 3-4 就是算这个）。**时间短不代表这个维度不重要，关键看工具的绝对耗时。**

**一句话记住**

> Agent 负载 = 模型段 + 工具段 + 等待段；裁剪无关日志同时降低下一轮的 prefill、KV 与读取量，而减少无效修改直接减少循环次数——两者是不同层面的优化。

### 3.2.4 分支、工具等待与状态驻留

**原文要点**

- **依赖图与关键路径**：模型调用与工具执行之间的先后关系可以画成一张**依赖图**。沿一条串行路径，阶段时间相加；互不依赖的分支可以同时开始，汇合点等待较慢的分支。一张依赖图中，**从开始到结束累计耗时最长的路径称为关键路径，它决定任务最早何时能够完成。**

**例题 3-2：加速首轮模型计算能缩短多少代码任务时间？**（用第 1 章的 Amdahl 定律分析，假设后续行为与质量不变。）

**解（原文给出）**：以同一条执行轨迹为基准，将首轮耗时 36.375 秒的模型计算**缩短一半**，其余阶段、输出、工具行为和质量都不变，总时间便从 **76.510 秒降到 58.323 秒**。此时 $f = 36.375/76.510$，$s = 2$，总加速比约为 **1.31**。首轮占总时间约 **47.5%**，将这一段减半节省约 **23.8%** 的总时间；其余阶段仍合计耗时约 **40.1 秒**。**优化的收益取决于缩短的那一段原来占多大比例。**

- **工具之间的依赖关系也影响总时间**：设模型先计算 2 秒，随后调用两个工具，耗时分别为 6 秒和 10 秒，最后再计算 3 秒。
  - 若**第二个工具依赖第一个的结果**，总时间为 $2 + 6 + 10 + 3 = 21$ 秒；
  - 若**工具相互独立**，总时间为 $2 + \max(6, 10) + 3 = 15$ 秒。
  并行减少了 6 秒，但**两个工具的总执行工作仍为 16 秒**。

> 图 3-11（原文插图）：两个工具存在前后依赖时的任务时间线。横轴为任务时间（0–20 s 量级），色块自上而下为"模型 / 工具 A / 工具 B"。时间线是：模型 2 s → 工具 A 6 s → 工具 B 10 s → 模型 3 s，总计 21 秒。工具 A 与工具 B 的色块首尾相接，不重叠。

> 图 3-12（原文插图）：两个工具独立时可以同时开始，模型在较慢的工具 B 完成后继续，任务共 15 秒。与前图使用相同时间尺度（0–20 s 量级）；模型 2 s 后，工具 A（6 s）与工具 B（10 s）的色块上下并排、同时开始，模型等到第 10 秒（工具 B 结束）才继续跑最后的 3 s，总计 15 秒。工具工作总量仍为 16 秒。

- **并行改变的不只是时间，还有状态占用**：若分支还要分别生成文本，**公共前缀可以共享，分支尾部独立增长**。设共享前缀长 $H_0$，第 $i$ 个分支新增 $h_i$ 个 token，每 token 状态为 $c_{\text{KV}}$，则总状态为

$$C_{\text{KV}}^{\text{total}} = c_{\text{KV}}\Bigl(H_0 + \sum_i h_i\Bigr)$$

  **并行缩短了关键路径，也让更多分支的状态同时占用内存。**

> 图 3-13（原文插图）：两个生成分支指向同一份公共前缀，并各自保存新增尾部。图中左侧是"公共前缀"块，右侧是"分支 A 尾部"与"分支 B 尾部"两个块，箭头从两个分支尾部指回同一份公共前缀，表示引用关系；共享前缀只计一份容量。

- **状态驻留与工具耗时的关系**：3.2.3 节代码修复任务的实测记录中，工具调用耗时极短，大部分时间都消耗在模型计算上。若工具操作改为耗时 10 秒的编译，**模型暂停的同时，下一轮所需上下文仍占据容量**；若多个任务同时等待，驻留量按任务累加。**工具执行时间越长，状态保留得越久，系统能同时处理的请求数就越少。** 第 8、9 章将在这条时间线上安排缓存与交接。

**练习 3-4〔核心〕：工具并行与局部加速能节省多少任务时间**

**题干（原文）**：一次任务先由模型计算 2 秒，然后调用两个相互独立的工具，分别耗时 6 秒和 10 秒。两个工具都完成后，模型再计算 3 秒，任务结束。分别计算两个工具依次执行和同时执行时的任务总耗时。假设仅在等待工具返回期间状态占用 1 GiB 空间，求两种执行方式下状态占用量与占用时长的乘积，单位为 GiB·s。

本节的代码任务实测记录显示，任务总耗时为 76.510 秒，其中首轮模型计算耗时 36.375 秒，所有工具执行合计耗时 0.078 秒。保持其余阶段不变，分别计算两种优化能节省多少任务时间：将首轮模型计算速度提高到原来的四倍；将所有工具的执行速度提高到原来的两倍。根据计算结果，解释为什么局部加速倍数不能单独决定一项优化对完整任务的收益。

**参考解答（笔记补充，非原文）**

1. 两种执行方式的任务总耗时：
   - 依次执行：$2 + 6 + 10 + 3 = 21$ s。
   - 同时执行：$2 + \max(6,10) + 3 = 15$ s。
2. 状态占用乘积（只在等工具期间占用 1 GiB）：
   - 依次执行：等待工具的总时长为 $6 + 10 = 16$ s，占用 $1 \times 16 = 16$ GiB·s。
   - 同时执行：等待时长为 $\max(6,10) = 10$ s，占用 $1 \times 10 = 10$ GiB·s。
   - 并行把占用面积砍掉 6 GiB·s，正好对应它砍掉的那 6 秒等待。
3. 两种局部加速：
   - 首轮加速到四倍：$36.375/4 = 9.09375$ s，新总时间 $= 76.510 - 36.375 + 9.09375 \approx 49.229$ s，节省约 **27.28 s**，加速比 $76.510/49.229 \approx 1.554$。
   - 工具加速到两倍：$0.078/2 = 0.039$ s，新总时间 $= 76.510 - 0.078 + 0.039 = 76.471$ s，节省约 **0.039 s**，加速比约 **1.0005**。
4. 为什么"局部加速倍数"不能单独决定收益：Amdahl 定律里真正决定加速比的是**被加速部分原来占多大比例**（$f$）。首轮占 $36.375/76.510 \approx 47.5\%$，即使只加速 4 倍也能换来约 1.55 倍的整体加速；工具只占 $0.078/76.510 \approx 0.1\%$，即使加速到无穷倍，整体最多也只能加速约 $1/(1-0.001) \approx 1.001$ 倍。**倍数很大但占比很小的优化，收益上限就是那个占比。**

**负载需求反过来推动模型结构的变化：DeepSeek V4.1 Flash 与 CED**（原文要点）

- 把同一条会话换成 DeepSeek V4.1 Flash，可以看到具体例子。设 Agent 已有一段公共上下文，工具随后返回新材料；**如果前缀未命中，服务要重新处理较多输入，而本轮输出可能较短**。为这样的输入密集场景降低 prefill 成本，比只优化单步生成更有价值。
- V4.1 因而采用第 2 章介绍的 **CED 结构**，使用 **20 层因果编码器和 20 层解码器**：大部分输入只执行编码器主体，**解码器的全局 KV 从编码器末层表示投影得到**；为了构建解码器的 **SWA 状态**，把提示末尾最多 **128 个 token** 的编码器输出重新送入解码器，近似恢复这部分局部状态。**输出 token 继续经过全部 40 层。**
- **专家矩阵工作量的比较**：以各 token 经过的专家层数之和衡量工作量。设一次从空状态开始的输入为 $P$ 个 token，则

$$F_{\text{普通全层}} = 40P,\qquad F_{\text{CED}} = 20P + 20\min(P, 128)$$

  当 $P = 8192$ 时，两者分别为 **327,680** 与 **166,400**，后者约为前者的 **50.8%**；当 $P \le 128$ 时，该子项没有减少。
- **已有前缀时**：输入处理的工作量由**追加长度**与**恢复方式**共同决定。若编码器 SWA 命中缓存，编码器主体便可以继续处理追加的输入；编码器 SWA 缺失，则先重放前缀末尾窗口。两条路径随后都要构建本轮的解码器 SWA。第 8 章将用 8K 与 128K 上下文的教学算例，比较保存状态和重新执行的成本。

> 图 3-14（原文插图）：同一批 8K 输入中，各 token 经过的专家层数之和。普通全层路径为 8,192 token × 40 层；CED 路径为 8,192 token × 20 层编码器，另加 128 × 20 的局部重放，合计 327,680 → 166,400 token·层。图注说明：灰色说明项（全局 KV 投影、注意力及其他工作）仍需另外计算；生成阶段仍执行完整 40 层主干。

**算例：Jev 为什么一眨眼就给出答案**（原文要点）

- 2026 年 9 月，前 OpenAI 研究员 **Diogo Almeida** 创办的 **TypeSafe AI** 发布了 **Jev** 模型。按创始人在发布文章中的说法，他在 OpenAI 参与了让语言模型学会遵循指令、与人对话的方法，这些工作后来成了 ChatGPT 背后的研究。Jev 的官方演示相当吸睛：**同一条客服请求，GPT-5.6 Terra 用了 8.566 秒，Jev 只用 0.114 秒，费用也只有前者的 1/171。**
- **Jev 不生成文字**：调用方提交一段状态（例如一张工单）和若干问题，每个问题的选项事先给定，模型返回各选项的概率。回到 3.1.1 节的调用链，这类请求**只有 prefill，没有 decode**。状态和所有问题拼在一起做一次前向，**每个问题末位置的输出分布就是答案**，好比图 3-13 中从同一前缀分出的几条分支，每条只走一步就停下。问题之间互不依赖，请求结束后也不必保留 KV。
- **概率能否当置信度靠训练**：TypeSafe 称其方法为 **RLCD**，思路与学术界的 **RLCR** 相同，都在奖励中加入 **Brier 分数**，让模型给出的概率与实际正确率相符。

> 🔎 检索确认：原文脚注 18 引用的论文《Beyond Binary Rewards: Training LMs to Reason About Their Uncertainty》确实存在（arXiv 2507.16806），标题与原文脚注一致，主题即"训练语言模型对自身不确定性进行推理"。（来源：[Paper page - Beyond Binary Rewards: Training LMs to Reason About Their Uncertainty](https://huggingface.co/papers/2507.16806)）本次检索未逐条核实其奖励函数中 Brier 分数与 RLCR 的具体定义，该部分笔记按原文保留。
- **用本书的条件验证**：Jev 只按输入收费，每百万 token **0.042 美元**；演示中 Jev 花费 **0.000081 美元**，折算下来输入约 **1929 个 token**。把这条请求放到 Qwen3-8B 上，一次前向约 **28 TFLOPs**，H100 SXM 按 **40% 的算力效率**计算约需 **70 ms**，与演示中的 0.114 秒相当。换成 DeepSeek V4.1 Flash 并走 CED 路径，运算量也只多出约四分之一。
- **对比普通 LLM**：如果交给普通 LLM，prefill 之后还要逐个生成 token，每一步受内存带宽限制，约需 **9 ms**。生成 64 个 token，延迟就增至 **0.65 秒，是决策请求的 9 倍**；由于 decode 可以合批，**GPU 时间却只多 28%**。图 3-15 把两种执行方式画在同一条时间轴上：**一眨眼给出答案，靠的是省掉了串行生成。**

> 图 3-15（原文插图）：同一条 1929 个 token 的请求在 H100 SXM 上的两种执行方式。上图为决策请求：prefill 1929 个 token（受算力限制），8 个位置的输出分布一次读出，一次前向 70.5 ms 后同时得到 8 个答案，时间轴标出 0、71 ms。下图为普通 LLM：同样的 prefill 之后逐 token 生成 64 个 token，即 63 步 decode，每步 9.2 ms（受带宽限制、依次执行）；时间轴标出 0、71、200、400、651 ms，末尾到 651 ms。模型为 Qwen3-8B，算力效率取 40%，带宽效率取 50%。

- **价格的算术**：按 DeepSeek 推理系统报告的口径，每 GPU 小时租金取 **2 美元**，则 8B 稠密模型或 V4.1 Flash 每处理一百万个输入 token，算力成本约为 **0.02 至 0.025 美元**，**Jev 的价格是这一成本的 1.7 至 2 倍**。也就是说，这一档模型只靠普通的 prefill 就能做到这个价格；反过来，**若价格要覆盖成本，Jev 每个 token 的运算量大致不会超过 8B 稠密模型的两倍**。
- **171 倍差距从哪来**：演示中 171 倍的费用差距，只有一小部分来自省去生成：在同一模型上，**省去 64 至 512 个输出 token，GPU 时间只减少到原来的 1/1.3 至 1/3.4**。其余差距来自**前沿模型本身的价格**，以及**推理时生成的大量 token**。
- **转交成本**：实际使用时，决策模型没有把握的请求还要转交 LLM 重新处理。设转交比例为 $e$，每条请求的平均费用为 $c_{\text{dec}} + e\,c_{\text{LLM}}$。按演示中的两个费用计算，**$e$ 只要超过约 0.58%，转交 LLM 的费用就会超过决策模型本身的费用**。因此，3.2.2 节成功任务成本中的 $c$ 也要计入转交费用。**决策模型是否更省钱，要看有多少请求需要转交，以及接手的 LLM 价格多高。**

**辅导讲解**

- **关键路径是 Agent 性能优化的指南针**。原文那个 2/6/10/3 秒的例子把两件事讲透了：(1) 任务总时间由最长路径决定，不是由总工作量决定——两个工具总工作 16 秒，但并行后关键路径上只算 10 秒；(2) 并行不减少工作量，只减少**等待**。所以在做优化时，第一件事是画依赖图、找关键路径，然后问"关键路径上最长的那一段是什么"。如果最长的一段是 10 秒的工具，那么把模型加速 4 倍对总时间几乎没用。
- 例题 3-2 的算法拆解（笔记复算）：

$$S_{\text{total}} = \frac{1}{(1-f) + f/s},\quad f = \frac{36.375}{76.510} \approx 0.4754,\ s = 2$$

  $S = 1/(0.5246 + 0.2377) = 1/0.7623 \approx 1.31$，总时间 $76.510 \times 0.7623 \approx 58.32$ s，与原文的 58.323 s 一致；节省 $18.19$ s，占 $18.19/76.510 \approx 23.8\%$。注意原文的"总时间 76.510 秒"比表中模型 76.294 + 工具 0.078 = 76.372 秒多出约 **0.138 秒**，这 0.138 秒即原文所说的**控制与交接时间**（原文只说明整任务"另含控制与交接时间"，未给出该数值，0.138 秒是笔记由总时间反推；图 3-10 的图注也提到"整任务另含控制与交接时间"）。做复算时要记得把这部分算进去，否则对不上。
- **思考模式的数据怎么读**（笔记整理）：关闭时 12 轮、765 个输出 token、模型耗时 13.156 s；开启后 4 轮、2,733 个输出 token、模型耗时 76.294 s。**轮数只有原来的三分之一，模型时间却多了 5.8 倍**——因为思考模式下每一轮生成了大量的思考 token（2,553 个在结束符之前，占 2,733 的 93.4%）。这正是 3.2.2 讲的"延长思考会增加串行生成时间与上下文状态"的实测量化：思考 token 是**串行**生成的，$G$ 变大就等比例地拉长单轮 wall clock。
- **"两组检查"为什么重要**：原定检查（返回值正确 + 输入不变）开启思考后 1013/1013 全通过；额外的"无别名"检查却只有 710/1013。这两组检查都"对"，但衡量的是不同的程序性质。工程含义很直接：**你的完成标准写到多细，你的评测就能看到多深**。如果只写了"返回值正确"，你会以为 1013/1013 已经完美；再加上"返回的子列表与原输入相互独立"（即返回的是拷贝而不是共享的引用），才暴露出 303 个用例仍共享子列表。这直接呼应 3.1.2 的"先写出什么算完成，再决定统计什么"，也说明了为什么原文在 3.2.2 要求把"接口格式"和"内容正确性"分开。
- **公共前缀与分支的状态公式**：$c_{\text{KV}}(H_0 + \sum_i h_i)$ 说明了两件事。第一，共享前缀**只算一份**——这是 KV 复用在多分支（比如并行采样 $k$ 条、或者 beam search）场景下的核心收益。第二，各分支的尾部**各算各的**，所以分支越多，总状态越大。把 $k$ 条并行采样的状态和"串行采 3 次"的状态比：串行的峰值状态是 $c_{\text{KV}}(H_0+h)$（一份），并行的峰值是 $c_{\text{KV}}(H_0 + \sum_{i=1}^{k} h_i)$（前缀一份 + $k$ 份尾部）。**用时间换空间，还是用空间换时间，这里就是那个开关。**
- **Jev 这个算例的教学价值**：它把本章的好几个概念串起来了。(1) 它的调用链只有 prefill，没有 decode——所以 3.1.1 的 $n_d = G - 1 = 0$；(2) 它的多个问题共享同一段状态前缀，等价于图 3-13 的多分支，但每条分支只走一步；(3) 它的"快"不是因为算法神奇，而是**省掉了串行生成**：普通 LLM 要跑 63 步 decode，每步都受带宽限制（约 9 ms），串起来就是 0.65 秒；而决策请求一次前向 70 ms 就把 8 个答案一起读出。(4) 它的"便宜"也不是因为推理便宜，而是因为它只处理**输入**（每百万 token 0.042 美元），一次请求只花输入的钱。
- 复算几个数（笔记补充）：$0.000081/0.042 \times 10^6 = 1928.6 \approx 1929$ 个输入 token；$989.4 \times 40\% = 395.76$ TFLOP/s，$28/395.76 \approx 70.7$ ms（原文正文写"约 70 ms"，图 3-15 标 70.5 ms，属同一量级的取整差异）；$0.000081/0.013880 = 0.005836$，即 **0.5836% ≈ 0.58%**，正是原文那个转交阈值；$0.042/0.025 = 1.68$、$0.042/0.02 = 2.1$，与"1.7 至 2 倍"一致。
- 原文"换成 DeepSeek V4.1 Flash 并走 CED 路径，运算量也只多出约四分之一"这句话，**原文没有明说这个"四分之一"是相对谁**。按上下文，最自然的读法是相对同一请求在 Qwen3-8B 上的那约 28 TFLOPs（即 CED 让更大的模型也能把 prefill 成本压到只高约 25%）。笔记在此如实指出原文表述简略，不做进一步推断。至于原文说"由于 decode 可以合批，GPU 时间却只多 28%"，**原文也没有给出这个 28% 的推导过程**；读者可以从"省去 64 至 512 个输出 token，GPU 时间只减少到原来的 1/1.3 至 1/3.4"这一句看出它与输出 token 数有关，但具体口径原文未展开。
- **工程上怎么用这些结论**：
  1. 优化前先算占比。任何"加速 $k$ 倍"的方案，先问它覆盖了总时间的百分之几。
  2. 能并行的工具就并行。注意并行的前提是**互不依赖**；有依赖关系的工具串行是必须的，硬并行会得到错误的中间结果。
  3. 工具等待期间的状态要做换出/放弃。如果下一轮还要用这段上下文，就保留（占容量）；如果要从头重算，就释放（占计算）。第 8、9 章讲的就是这个取舍。
  4. 如果有大量同构的短输出决策请求（如工单分类、选项打分），值得按 Jev 的思路重新设计接口：**一次前向、多个读出位置、不做自回归生成**。

**易混点**

- **关键路径与总工作量**：两个工具总工作 16 秒，但关键路径上只有 10 秒。**减少工作量（比如工具加速）和缩短关键路径（比如并行）是两件不同的事**：前者不改变依赖结构，后者不减少总工作量。
- **思考模式下的"模型时间"与"轮数"**：开启思考后轮数从 12 降到 4（更少的往返），但模型总时间从 13.156 s 涨到 76.294 s。**更少的轮次不等于更少的时间**，因为每轮的生成量差了好几倍。
- **"快"的来源**：Jev 的快来自"省掉 decode 的串行步数"，不是来自"更快的模型"。对照 3.1.1：decode 每步都受带宽限制且必须串行，而 prefill 可以并行处理大量 token。所以只要能把任务改造成"只 prefill"，就能拿到量级的速度差异。
- **$e$（转交比例）与成功率**：$e$ 只影响**平均费用**（$c_{\text{dec}} + e\,c_{\text{LLM}}$），而能不能省钱还要看转交带来的成功率提升，即 3.2.2 里的 $p_2/p_1$。两个条件要一起满足。

**一句话记住**

> 任务时间由关键路径决定：并行换时间、状态换空间；首轮加速 4 倍能省 27 秒，工具加速 2 倍只省 0.039 秒——因为前者占 47.5%、后者占 0.1%。Jev 的"眨眼回答"则是把 decode 整段砍掉换来的。

## 3.3 多模态与实时交互

**原文引言（本节的路线）**：Agent 的工具结果通常以文本进入下一轮输入。若输入换成图片或连续语音，调用模型之前还需要**编码输入**，输出端也可能需要**持续播放**。本节先分析**数据在阶段之间如何改变形状**（3.3.1、3.3.2），再分析**各阶段必须在何时完成**（3.3.3）。

### 3.3.1 视觉编码、语言生成与状态

**原文要点**

- **三阶段基本依赖**：图片进入语言模型之前，还要经过预处理、视觉编码和投影。用 $E$ 表示视觉编码，$P$ 表示语言 prefill，$D$ 表示后续 decode，一次视觉问答便有 $E \to P \to D$ 这条基本依赖。**图片大小影响 $E$ 的工作量，编码后的视觉 token 数影响语言部分的工作量；这两项工作应分别计算。**
- **视觉 token 数公式**：先数视觉 token，再数每个向量的特征维度。设预处理后的图片高、宽为 $H_{\text{img}}, W_{\text{img}}$，将图片分成方形图像块（patch），每块边长为 $p_{\text{patch}}$，每边再合并 $r$ 个 patch，则

$$n_v = \frac{H_{\text{img}} W_{\text{img}}}{p_{\text{patch}}^2\, r^2}$$

  其中 $n_v$ 是视觉 token 数（无量纲），$H_{\text{img}}, W_{\text{img}}, p_{\text{patch}}$ 单位都是像素，$r$ 是每边的合并倍数。
- **具体配置算例（Qwen3-VL-4B）**：640×640 的图片，按 16×16 patch 划分得到 $40 \times 40 = 1600$ 个 patch，再作 $2 \times 2$ 合并，得到 **400 个视觉 token**。最终特征宽度为 **2560**，每元素占两字节的 BF16 张量 $[400, 2560]$ 占

$$400 \times 2560 \times 2 = 2{,}048{,}000\ \text{字节}$$

> 图 3-16（原文插图）：图像从像素网格变为视觉 token。640 × 640 像素图像 → 16 × 16 像素一块 → 40 × 40 个块 → 相邻 2 × 2 块合并 → 20 × 20 个 token。图中用网格表示像素被切块、再被两两合并的过程。

- **编码结果不止一份（DeepStack）**：为向语言模型提供不同深度的视觉信息，**DeepStack 将视觉编码器中间层的特征送入相应语言层**。模型还取三个中间视觉层的这类特征，将它们与最终层特征拼接，完整张量为 $[400, 10240]$，占

$$400 \times 10240 \times 2 = 8{,}192{,}000\ \text{bytes} = 7.8125\ \text{MiB}$$

  **四组特征对应同一组 400 个视觉 token：特征宽度变为四倍，语言序列仍增加 400 个视觉 token。** 视觉编码的矩阵运算量约为 **1.310 TFLOPs**；图片解码与缩放发生在编码之前，语言计算则在编码之后。

> 图 3-17（原文插图）：视觉 token 数与每 token 特征宽度分别计量。图中"400 个视觉 token，各对应一个特征向量"，"四组视觉特征：每组宽 2560"，"编码结果：400 × 4 × 2560 × 2 bytes"；并注明"进入语言主干后，另产生各层 KV"。四组 2560 维 BF16 编码特征占 7.8125 MiB；这些视觉 token 进入语言模型后，另产生各层的 KV 状态。

- **两种缓存要分清**：图 3-16 与图 3-17 中，视觉编码改变了**视觉 token 数**和**特征宽度**；进入语言模型后，还会产生另一种表示。**编码缓存（encoder cache，EC）保存视觉编码器的输出，语言主干则产生 KV 缓存。** 该配置的语言 KV 每 token 占 **144 KiB**，400 个视觉 token 对应 **56.25 MiB**。
- **同一张教学截图的三个不同数据量**：**原始压缩文件 0.8 MB、完整 BF16 EC 7.8125 MiB、视觉 token 的逻辑 KV 56.25 MiB。**

| 对象 | 本例大小 | 决定它能否复用的条件 |
| --- | --- | --- |
| 压缩截图 | 0.8 MB，给定输入 | 同一文件内容 |
| 完整编码结果 EC | 7.8125 MiB | 图片、预处理、编码器与输出格式一致 |
| 视觉 token 的语言 KV | 56.25 MiB | 还依赖先前上下文、顺序、位置与模型状态 |

  （表格按原文语义还原。）
- **图片位置决定 KV 能否复用**：图片及编码配置相同时，EC 可以复用。语言 KV 还依赖图片之前的上下文：**问题放在图片之前时，更换问题会改变视觉 token 的 KV；问题放在图片之后时，因果注意力使此前视觉 token 的 KV 保持不变。**
- **多模态输入的编码状态与 KV 容量预算**：设输入包含四张图片与 400 个文本 token，计算这些输入 token 的 EC 与逻辑 KV。四张相同规格图片的 **EC 为 31.25 MiB**，**视觉 token KV 为 225 MiB**；再加 400 个文本 token，**输入逻辑 KV 为 281.25 MiB**。
- **三个不同的交接位置**：原图、EC 和 KV 这三种数据表示，对应三个不同的交接位置。**发送原图，接收方还要执行视觉编码；发送 EC，接收方从语言 prefill 开始；发送 KV，则交接已经完成的语言上下文。** 第 8 章安排同卡执行，第 9 章比较阶段交接，第 12 章把相同数据流放到端、边、云链路上。
- **分辨率加倍的效果**：保持 patch 与合并方式不变，把图片的高度和宽度都加倍，**视觉 token 数变为四倍**。因此 EC 和视觉 token 的语言 KV 都变为四倍；**视觉编码内部 token 之间的交互则还要按注意力结构计算**。原文的区分很关键：**特征拼接增加的是宽度，图片变大增加的是视觉 token 数，二者在语言主干中产生不同后果。**

**辅导讲解**

- **公式 $n_v = H W/(p^2 r^2)$ 的两个因子要分开看**。$p_{\text{patch}}$ 决定"切多细"，$r$ 决定"再压多狠"。640×640、$p=16$、$r=2$ 得到 400 个 token，意味着**每个视觉 token 概括了 $32 \times 32 = 1024$ 个像素**。复算一下：$640 \times 640 = 409{,}600$ 像素；$409600/1024 = 400$ ✓。这个"每 token 概括多少像素"的比值，决定了视觉信息被压缩的程度，也就决定了模型能"看清"多少细节。
- **为什么要把"token 数"和"特征宽度"分开算**：它们在系统里的后果完全不同（笔记整理）：
  - **token 数**决定语言主干的**序列长度**：它进入注意力，产生 $O(n^2)$ 的注意力交互，也决定语言 KV 的条数（400 个 token × 每 token 144 KiB = 56.25 MiB）。
  - **特征宽度**决定**张量有多大、要传多少字节**：四组特征把宽度从 2560 拉到 10240，EC 从 1.953 MiB 涨到 7.8125 MiB（×4），但语言序列长度仍然是 400。
  所以在做多模态部署时，一个常见的错误是把 7.8125 MiB 当成"语言侧要处理的数据量"。语言侧真正扛的是那 400 个 token 的 KV（56.25 MiB），EC 是**交接**时才关心的数据量。
- 复算几个数字（笔记补充）：$400 \times 2560 \times 2 = 2{,}048{,}000$ B $= 1.953$ MiB；$\times 4 = 8{,}192{,}000$ B $= 7.8125$ MiB；$400 \times 144\ \text{KiB} = 57{,}600\ \text{KiB} = 56.25$ MiB；四张图片 EC $= 4 \times 7.8125 = 31.25$ MiB；四张图片的视觉 token KV $= 4 \times 56.25 = 225$ MiB；再加 400 个文本 token 的 KV $= 400 \times 144\ \text{KiB} = 56.25$ MiB，合计 $225 + 56.25 = 281.25$ MiB ✓。三个数据量之间的倍数关系很说明问题：**原图 0.8 MB → EC 7.8125 MiB（约 10 倍）→ 语言 KV 56.25 MiB（约 70 倍）**。同一张图，越往"模型内部"走，占的空间越大。
- **"问题放在图片之前还是之后"这个细节非常值得记**。因果注意力意味着每个位置只能看到它左边的内容。如果提示是"这张图里有什么？<图片>"，那么图片 token 的左边包含问题，**换一个问题，图片 token 的 KV 就得重算**；如果提示是"<图片>这张图里有什么？"，图片 token 左边什么都没有（或只有固定前缀），**换问题时图片的 KV 完全不用动**。工程含义：**把大而稳定的模态内容放前面、把多变的问题放后面**，就能让昂贵的视觉 KV 复用起来。这和 3.2.1 讲的"末尾追加最便宜"是同一个道理。
- **EC 与 KV 的可复用条件差别**：EC 只依赖"图片 + 预处理 + 编码器 + 输出格式"——只要这几项不变，同一张图在任何上下文里都能复用 EC。KV 还依赖**先前上下文、顺序、位置与模型状态**——换一个模型版本、换一种位置编码、甚至前面挂的提示不同，KV 就用不了。这就解释了为什么表里 EC 的复用条件比 KV 短得多：**EC 更"通用"，KV 更"贴身"**。
- **三个交接位置的经济学**（笔记整理，依据原文"发送原图／EC／KV"的划分）：发送原图最省带宽（0.8 MB）但接收方最费算力（要做 $E$）；发送 KV 最费带宽（56.25 MiB/张图）但接收方最省算力（已经算完语言上下文）。**中间方案是发送 EC**（7.8125 MiB，接收方从 prefill 开始）。选哪个取决于链路带宽和两端算力的相对价格——第 9、12 章展开。
- **不适用的情况**：分辨率加倍得到"token 数四倍"这个结论，前提是 **patch 大小与合并方式不变**。如果同时把 patch 也放大一倍（即降低采样密度），token 数可以保持不变——但代价是每个 token 概括的像素更多、细节更糊。原文明确写了这个前提，别把结论用过头。

**易混点**

- **EC 与 KV**：EC 是**视觉编码器**的输出（编码缓存）；KV 是**语言主干**各层的键值状态。前者只依赖图片与编码配置，后者还依赖上下文与位置。大小上，本例 EC 是 7.8125 MiB，而视觉 token 的 KV 是 56.25 MiB——**KV 是 EC 的 7.2 倍**。
- **视觉 token 数与特征宽度**：前者是"序列有多长"（进注意力，$O(n^2)$），后者是"每个位置的向量有多宽"（进张量体积与传输量）。原文那句"特征拼接增加的是宽度，图片变大增加的是视觉 token 数"就是这个区分。
- **$n_v$ 里的 $r^2$ 与 patch 数**：1600 个 patch 除以 $r^2 = 4$ 得到 400 个 token。忘记平方（只除以 $r$）会把结果算成 800，这是最常见的手算错误。

**一句话记住**

> $n_v = H_{\text{img}}W_{\text{img}}/(p_{\text{patch}}^2 r^2)$ 数 token（进语言序列、决定 KV），四组 DeepStack 特征拼宽度（决定 EC 与传输量）；同一张图在三个阶段是 0.8 MB → 7.8125 MiB → 56.25 MiB。

### 3.3.2 音频与图像生成的计算过程

**原文要点**

- **视觉问答仍是自回归文本**：视觉问答仍通过语言模型逐 token 生成文本。**若输出本身是声音或图像，一次迭代处理的数据和迭代次数也会改变。**
- **音频输出：帧内还有循环**。以 Fish Audio 的语音生成模型 **S2 Pro** 为例：
  - **慢速（slow）路径**每次推进**一个音频帧**；
  - **快速（fast）路径**在帧内补齐**多个码本**的编号；
  - **码本**是离散声音表示的候选向量集合，**编解码器（codec）**把这些编号还原为波形；
  - **每帧先用一次快速路径前向建立状态，再用九次预测补齐码本，因此生成一帧需要十次快速路径前向计算。**
  原文由此得出结论：**语言 token/s、声学帧/s 与每秒生成的音频时长，衡量的是不同的生成速度。**
- **图像生成：换了一种循环**。相关概念：**潜在表示（latent）**是压缩后的连续图像表示；**去噪**逐步把含噪表示变为目标图像；**扩散 Transformer（DiT）**执行每步变换；**无分类器引导（CFG）**组合带条件与无条件两路预测；**变分自编码器（VAE）**负责像素与压缩表示之间的转换。
- **具体算例（Qwen-Image-2512）**：1024 × 1024 图像形成 **4096 个 latent 位置**，执行 **50 个去噪步**，**true CFG 路径每步有两支 DiT 前向**，总共执行 **100 次 DiT 前向计算**。**去噪矩阵运算量约 $7.830 \times 10^{15}$ FLOPs**；文本编码器与 VAE 还有各自的工作。**latent 的位置集合在去噪期间保持固定，各步持续更新其内容，累计工作随去噪步数增加。**
- **总运算量公式**：把每步去噪的运算量记为 $F_{\text{step}}(n_v)$，去噪步数为 $n_s$，每步引导分支数为 $n_b$，则

$$F_{\text{total}} = n_s\, n_b\, F_{\text{step}}(n_v)$$

  **步数加倍，运算量也加倍**；分辨率提高会增加图像潜在表示中的空间位置数，单步内部的矩阵行数和位置间交互也随之增加。原文的最后对比是本节的核心：**文本生成不断追加上下文，每步访问量随之增长；图像去噪反复更新同一组 latent，在固定分辨率下，累计运算量随去噪步数线性增长。**

**辅导讲解**

- 这一小节要建立的是一个**生成循环的分类学**（笔记整理）：
  - **文本生成**：迭代次数 $= G$，每步只产出 1 个 token，但**状态（KV）单调增长**，所以第 $t$ 步的成本随 $t$ 上升。
  - **音频生成**：迭代次数 $= $ 帧数，每帧内部还有 $1 + 9 = 10$ 次 fast 前向，即"**外层按帧、内层按码本**"两层循环。这解释了为什么"语言 token/s"和"声学帧/s"不是一回事：一个语言 token 可能对应不到一帧，一帧里又要跑 10 次前向。要比较不同语音系统的速度，必须说清是哪个单位的速度。
  - **图像生成**：迭代次数 $= n_s \times n_b$（去噪步 × 引导分支），而且**每一步处理的数据形状完全相同**（latent 的位置集合固定），所以累计运算量对步数是**线性**的，不含"上下文越长越贵"那项。
- 为什么图像去噪是线性的而文本生成不是？关键在**状态是否增长**。文本生成把新 token 追加进上下文，第 $t$ 步要 attend 到 $t$ 个位置，成本随 $t$ 增长（3.4.2 里那个 $O(L^2)$ 的注意力配对就是这个现象的定量版本）。图像去噪反复"擦同一块画布"：位置数是 $n_v$ 固定，每步都在这 $n_v$ 个位置上做同样的变换，所以成本恒定。**"上下文累加"与"固定画布反复迭代"是两种根本不同的负载形状。**
- 复算与量级（笔记补充）：
  - $n_s = 50$、$n_b = 2$（true CFG 的两支），所以 DiT 前向次数 $= 50 \times 2 = 100$ ✓。
  - 去噪矩阵运算量 $7.830 \times 10^{15}$ FLOPs $= 7830$ TFLOPs。如果按一次 DiT 前向分摊，约 $7830/100 = 78.3$ TFLOPs/次。这个量级与 3.4.3 单次 8K 训练前反向的数百 TFLOPs 相比不算大，但**它要跑 100 次串行**，所以延迟是主要问题（第 4 章会算这个时间）。
  - 音频（S2 Pro）：每帧 10 次 fast 前向。如果音频帧率是每秒 25 帧（常见设定，原文未给帧率），那么生成 1 秒音频需要 $25 \times 10 = 250$ 次前向——**这是一个非常高的串行迭代密度**，也解释了为什么实时语音生成对推理速度的要求比文本生成苛刻得多。注意：帧率是笔记为说明量级而假设的，原文未给出具体帧率。
- **工程上的启示**：
  1. 做容量规划时，先问"这个模态的迭代循环长什么样"。文本看 $G$ 和 KV 增长；音频看帧率 × 每帧前向数；图像看去噪步数 × 引导分支数。
  2. **减少迭代次数往往比提高单步效率更有效**，因为这些循环是严格串行的。例如图像生成把 CFG 从"每步两支"改成"少步蒸馏"，是把 $n_b$ 或 $n_s$ 直接砍一半；语音把 fast 路径的 9 次补齐减少，是把每帧的 10 次降下来。
  3. 分辨率对图像生成的影响是**双重**的：$n_v$（latent 位置数）变大，同时 $F_{\text{step}}$ 内部的位置间交互也变大。原文特意指出这一点，因为它不满足"线性放大"的直觉。

**易混点**

- **语言 token/s、声学帧/s、音频秒/s**：三者是不同单位。原文明确说它们"衡量的是不同的生成速度"，比较系统时务必对齐口径。
- **$n_s$（去噪步）与 $n_b$（引导分支数）**：$n_s$ 是"擦几遍"，$n_b$ 是"每遍同时算几支"。两者都乘进总运算量，但**$n_b$ 支是可以并行算的**（同一份 latent、两份条件），而 $n_s$ 步必须串行（后一步依赖前一步的结果）。所以它们对**延迟**的影响完全不同。
- **latent 的"位置集合固定"与文本的"上下文增长"**：前者让累计运算量对步数线性，后者让它超线性。原文对举这两句，正是为了说明"同一套硬件参数，两类负载的时间曲线不一样"。
- **EC 与 VAE latent**：两者都是"压缩表示"，但 EC 来自视觉编码器（进语言模型前），latent 是扩散模型的中间画布（在扩散循环内部）。位置完全不同，别混。

**一句话记住**

> 生成任务的成本 = 迭代次数 × 单步成本：文本的迭代次数是 $G$ 且每步访问量随上下文增长；音频是"帧 × 10 次 fast 前向"；图像是 $n_s n_b F_{\text{step}}(n_v)$，位置固定、对步数线性。

### 3.3.3 连续感知、首段响应与打断

**原文要点**

- **缓冲模型**：工作总量决定平均处理需求，**实时播放还要求每块数据都按时到达**。令 $A(t)$ 表示截至时刻 $t$ 已到达的可播放音频时长，$P(t)$ 表示已播放的音频时长，则缓冲中剩余音频为

$$B_{\text{audio}}(t) = A(t) - P(t)$$

  连续播放期间，每经过一秒，已播放音频时长 $P(t)$ 就增加一秒，$A(t)$ 则随数据块到达**跳跃增加**。两条曲线之间的距离就是**缓冲余量**；**余量降到零而下一块尚未到达，声音就会中断**。**预缓冲增加初始余量，同时推迟开始播放。**
- **输入端的时间约束**：在输入端，截图 Agent 如果只在动作结束后观察屏幕，就可能**漏掉中途出现又消失的弹窗**。持续观察与交互研究 **AOI** 针对的正是这类场景：它把**屏幕观测与动作执行分开**，持续收集图像、音频和事件，再筛选出供模型使用的记录。**增加观测频率可以发现更多短暂事件，但保存更多关键帧也会占用上下文；过多关键帧还可能挤占重要信息，使任务效果下降。** 因此，持续观测还要**配合筛选**，决定哪些内容值得保留并交给模型处理。
- **语音的时间约束更直接**：用户停止说话后，系统要采集或确认输入，经过识别／编码、推理、语音生成和播放。**开始播放后，后续音频还必须及时到达，才能避免中断。**
- **实测数据**：音频块到达应用之后，还要经过解码、排队和播放。两次语音交互测量中，**用户停止说话到首块音频到达的时间分别约为 400 ms、370 ms，后续音频块的到达间隔中位数均约为 94 ms**。原文的结论：**到达时间说明数据何时可用，播放时钟则决定音频何时播出。**
- **缓冲教学算例（逐项）**：输入每 20 ms 形成一块，24 kHz、单声道、每样本 2 bytes，每块数据量为

$$24{,}000 \times 0.020 \times 1 \times 2 = 960\ \text{bytes}$$

  每块采集结束后，**模型处理耗时 12 ms、发送耗时 1 ms，网络传播通常再需 5 ms**。第一块在 $20 + 12 + 1 + 5 = 38$ ms 到达，在**抖动缓冲区**（先暂存到达的音频、吸收到达时间波动的缓冲区）中等待 **40 ms** 后，于采集开始后的第 $38 + 40 = 78$ ms 播放。**第三块的传播延迟设为 50 ms**，直到 123 ms 才到，**错过 118 ms 的播放计划，造成额外 5 ms 的停顿**。后续块虽已到达，也要按声音顺序等待。
- **缓冲改为 60 ms**：这次停顿消失，**首播却推迟到 98 ms**。**增加缓冲可以避免这次到达时间波动造成的播放中断，代价是更晚开始；若音频的平均到达速度长期低于播放速度，有限缓冲终究会耗尽。**
- **打断要单独检查**：播放连续性之外，还要单独检查打断响应。图 3-20 从用户发出打断计时，追踪本地播放何时真正停止；**远端生成是否停止需要沿另一条控制路径判断。**
- **打断涉及的几项操作**：应用发出取消指令，播放设备静音，后端停止生成，并释放缓冲与状态。教学时序在 **123 ms 发出打断，控制延迟 5 ms，设备每 10 ms 检查并执行一次控制指令，于是 130 ms 静音，用户感受到的打断延迟为 7 ms**。原文强调要把三件事分开：**设备静音、后端停止生成和释放缓冲与状态，分别对应停止播放、停止计算和释放存储三个时刻**——后端停止生成决定**后续计算何时结束**，缓冲释放决定**容量何时可供其他任务使用**。
- **并非所有任务都要求连续输出**：**RAW** 是保留相机传感器原始采样信息的图像表示。RAW 图片精修关注的是**何时能得到完整成片**，无需像语音那样连续输出。精修还需要保留原始图像信息，**视觉理解使用的 EC 无法替代原图**。由此可见，**任务不同，时间要求也不同：有的要尽快开始，有的要持续流畅，有的要尽早全部完成。**

> 图 3-18（原文插图）：可组合的多模态阶段。自上而下四个阶段：视觉或音频编码（形成模型输入）→ 语言模型（理解并生成回复）→ 声学生成与解码（产生音频采样）→ 接收缓冲与播放设备（输出声音）。图注说明"编码形成模型输入，语言模型生成回复，声学模块将回复转成音频，接收方的缓冲与播放设备决定何时真正发声"。

> 图 3-19（原文插图）：八块音频的教学播放时间线。横轴为从采集起点计时（0–250 ms 量级），纵轴列出块 1 至块 8。每块长 20 ms；圆点标"到达"时刻，短竖线标"原定播放"时刻，色条标"实际播放"区间。第三块晚到 5 ms，其后的播放随之顺延。

**练习 3-5〔延伸〕：图像分辨率与音频缓冲如何影响资源需求**

**题干（原文）**：将 Qwen3-VL-4B 输入图片的分辨率从 640 × 640 改为 1280 × 1280，保持图像块大小、合并方式和特征精度不变，求视觉 token 数、完整编码缓存 EC 的大小，以及这些视觉 token 对应的 KV 大小。再根据本节音频时间线，比较初始缓冲为 40 ms 和 60 ms 时的首次播放时刻与停顿情况。如果每秒收到的音频只能播放 0.9 秒，开始播放时已缓存 0.3 秒音频，求连续播放多久后会耗尽缓冲，并解释增加有限缓冲能解决什么问题。

**参考解答（笔记补充，非原文）**

1. 分辨率加倍（$640 \to 1280$，保持 $p_{\text{patch}} = 16$、$r = 2$）：
   - 视觉 token 数 $n_v = 1280 \times 1280/(16^2 \times 2^2) = 1{,}638{,}400/1024 = 1600$ 个（正好是 400 的 4 倍）。
   - 完整 EC：$1600 \times 4 \times 2560 \times 2 = 32{,}768{,}000$ bytes $= 31.25$ MiB（4 倍）。
   - 视觉 token 的 KV：$1600 \times 144\ \text{KiB} = 230{,}400\ \text{KiB} = 225$ MiB（4 倍）。
2. 缓冲对比（沿用原文时间线：每块采集 20 ms，处理 12 ms、发送 1 ms、传播 5 ms，故第 1 块 38 ms 到达；第 3 块因传播 50 ms 而 123 ms 到达）：
   - 40 ms 缓冲：首播 $38 + 40 = 78$ ms；第 3 块原定播放时刻 $78 + 40 = 118$ ms，实际 123 ms 才到，**造成约 5 ms 停顿**。
   - 60 ms 缓冲：首播 $38 + 60 = 98$ ms；第 3 块原定播放时刻 $98 + 40 = 138$ ms $> 123$ ms，**不停顿**，代价是首播晚 20 ms。
3. 缓冲耗尽：净消耗速率 $1 - 0.9 = 0.1$ 秒音频／秒（即每播放 1 秒音频，缓冲净减少 0.1 秒），初始余量 0.3 秒，故 $0.3/0.1 = 3$ 秒后耗尽。
4. 有限缓冲能解决什么：它能**吸收到达时间的抖动**——只要"平均到达速度 ≥ 播放速度"，个别块晚到就不会导致中断。但它解决不了**平均速度不足**：如果到达长期慢于播放（本例的 0.9 倍），无论缓冲多大，终究会耗尽。所以缓冲是"抗抖动"手段，不是"补产能"手段。

**辅导讲解**

- $B_{\text{audio}}(t) = A(t) - P(t)$ 是一个**生产者—消费者**模型。$A(t)$ 是阶梯函数（每块到达就跳一下），$P(t)$ 是斜率恒为 1 的斜线（播放时钟永远匀速走）。两条线的间隙就是"还能撑多久"。这个模型的关键在于：**播放时钟不受网络控制**——音频一旦开始播，就必须按真实时间连续输出，快不了也慢不了。这就是实时任务与服务请求最大的区别：请求可以排队等，声音不能等。
- **预缓冲是个纯粹的权衡**：多等 20 ms 开始播，换来 20 ms 的额外余量。原文的算例把这一点量化得很干净：40 ms → 78 ms 首播 + 5 ms 停顿；60 ms → 98 ms 首播 + 无停顿。**要"更快开始"就更容易断，要"不停"就得更晚开始**，没有免费的选择。
- **三个时刻必须分开计**（这是原文特别强调的，也是工程上最常被合并的）：以打断为例——123 ms 用户发出打断，130 ms 设备静音（用户感知延迟 7 ms），而"后端停止生成"和"释放缓冲与状态"又是另外两个更晚的时刻。收益完全不同：静音只改善**体验**；停止生成节省**算力**；释放缓冲节省**容量**（第 8、9 章要用这个时刻做调度）。如果系统只上报一个"打断耗时"，你无法知道算力是否真的停了、容量是否真的还回来了。
- **AOI 的负载含义**：持续观测意味着**输入产生的速率与动作执行解耦**。Agent 不再是"做一步看一眼"，而是"眼睛一直睁着"。这带来两个新问题：(1) 观测帧会产生输入 token（每帧都要过视觉编码，按 3.3.1 算，一张 640×640 图就是 400 个 token、56.25 MiB 的 KV）；(2) 观测频率越高，"看到的"越多，但上下文装不下，于是必须**筛选**。原文那句"过多关键帧还可能挤占重要信息，使任务效果下降"提醒我们：这不是单纯的容量问题，而是**效果问题**——塞太多，模型反而抓不住重点。
- **实测数字的意义**：首块音频到达约 400 ms／370 ms，后续块间隔中位数约 94 ms。这两个数放在一起说明：**首块有 300–400 ms 的"起步成本"（识别 + 推理 + 生成 + 传输），但一旦跑起来，节奏就稳定在约 94 ms 一块**。所以优化实时语音对话，主要是压那 400 ms 的起步（TTFT 在这里变成了 TTFB，time to first byte/block），而断续问题则看后续 94 ms 的稳定性（抖动）。
- 复算（笔记补充）：$24{,}000\ \text{Hz} \times 0.020\ \text{s} = 480$ 个样本，$\times 2$ bytes = 960 bytes ✓。这个数字很小（不到 1 KB），说明**音频的带宽压力远小于算力压力**——真正的成本在每块数据背后的模型推理（见 3.3.2 的"每帧 10 次 fast 前向"）。
- **任务类型决定时间目标**（原文最后一段的提炼）：语音要"持续流畅"（看抖动与缓冲），截图 Agent 要"不漏事件"（看观测频率），RAW 精修要"尽早全部完成"（看总吞吐，不需要连续输出）。**把三类任务用同一套指标去考核，一定会得出错误的优化方向。** 顺带一提，RAW 精修还有一个数据量上的细节：它必须保留原图（原文："视觉理解使用的 EC 无法替代原图"），所以它既不能像语音那样"边生成边丢"，也不能像纯视觉问答那样只留 EC。
- **不适用的情况**：$B_{\text{audio}}(t)$ 模型假设播放设备按恒定速率消费、且不主动跳帧。如果系统支持"落后就丢弃中间块、直接跳到最新"（语音对话里常见），$P(t)$ 会出现跳变，这个连续缓冲模型就要改成"追赶"模型。原文未讨论这种策略。

**易混点**

- **到达时间与播放时间**：一块音频 123 ms 到达，不代表它 123 ms 被播放——"原定播放"时刻才是播放计划（40 ms 缓冲下第 3 块的原定播放时刻是 118 ms），实际播放还要看缓冲策略。原文明确说"到达时间说明数据何时可用，播放时钟则决定音频何时播出"。
- **抗抖动（缓冲）与补产能（带宽/算力）**：缓冲只能把"某块晚到"摊平，改变不了平均到达率。练习 3-5 第 3 问（0.9 倍速率）就是用来区分这两者的。
- **设备静音、停止生成、释放状态**：三个不同时刻、三种不同收益（体验／算力／容量）。
- **RAW 与 EC**：RAW 是传感器原始信息，EC 是视觉编码结果，**后者不能替代前者**，因为在 RAW 精修里需要的是没被压缩过的信息。

**一句话记住**

> 实时任务多了一条"播放时钟"的硬约束：$B_{\text{audio}}(t)=A(t)-P(t)$ 归零就断音；预缓冲是用"晚开始"换"不断音"，而打断的 7 ms（静音）≠ 后端停止生成 ≠ 状态释放。

## 3.4 训练的计算与状态需求

### 3.4.1 前向计算、反向传播与参数更新

**原文要点**

- **为什么训练要留中间结果**：推理用权重求输出，训练还要利用输出与目标的差异来调整权重。以最简单的一次乘法为例：输入 $x$ 乘以权重 $w$ 得到 $y$。后一层传回损失对 $y$ 的敏感度后，要算损失对 $w$ 的敏感度，**就还需要当时的 $x$**；要把敏感度传给前一步，**则需要 $w$**。因此，**前向把结果交给下一层以后，某些输入还要保留，等反向用完才能释放。**
- **线性层的前向与反向**：对线性层 $Y = XW$，输入 $X$ 为 $[m, k]$，权重 $W$ 为 $[k, n]$。定义如下：**损失 $\mathcal{L}$** 是衡量模型输出与训练目标差异的数值，训练的目标是降低损失；**梯度**描述损失对某个输入或参数的小变化有多敏感。反向传播从输出端沿依赖逆向传递这些敏感度。设后一层反向传来 $\partial \mathcal{L}/\partial Y$，当前层需要计算两种梯度：

$$\frac{\partial \mathcal{L}}{\partial X} = \frac{\partial \mathcal{L}}{\partial Y} W^{\mathsf T},\qquad \frac{\partial \mathcal{L}}{\partial W} = X^{\mathsf T}\frac{\partial \mathcal{L}}{\partial Y}$$

- **三倍关系**：前向计算输出，反向分别计算输入梯度和权重梯度。**三次矩阵乘法的运算量相同，因此这一线性层的训练矩阵运算量约为前向的三倍。** 下表将一次乘加计为两个 FLOPs：

| 操作 | 要解决的问题 | 左、右输入的形状 | 输出形状 | 矩阵 FLOPs |
| --- | --- | --- | --- | --- |
| 前向 $Y = XW$ | 根据输入求输出 | $[m, k]$ 与 $[k, n]$ | $[m, n]$ | $2mkn$ |
| 输入梯度 $\mathrm{d}X = \mathrm{d}Y W^{\mathsf T}$ | 将误差传回前一层 | $[m, n]$ 与 $[n, k]$ | $[m, k]$ | $2mkn$ |
| 权重梯度 $\mathrm{d}W = X^{\mathsf T}\mathrm{d}Y$ | 求这层权重的调整方向 | $[k, m]$ 与 $[m, n]$ | $[k, n]$ | $2mkn$ |

  （表格按原文语义还原。）
- **$6ND$ 的来源**：输入梯度把误差信号传给前一层，权重梯度决定本层参数的调整。观察三组矩阵尺寸：**虽然乘法顺序不同，三次运算都含有相同的 $mkn$ 个乘加**，因此合计约为 $6mkn$ FLOPs。**若所有训练 token 都经过同一组主要参数矩阵，累计便得到常见近似**

$$F_{\text{train}} \approx 6ND$$

  其中 $N$ 为参数量（个），$D$ 为训练 token 总数（个），系数 6 来自"前向 2 + 反向 4（输入梯度 2 + 权重梯度 2）"。
- **结构变化同样可推**：冻结某个权重矩阵后，可省去它的权重梯度计算；**若更早的层仍需要梯度，则仍要计算输入梯度**。**MoE 按选中专家累计两类梯度，注意力则按查询—键配对累计。** 沿反向依赖逐项累加，就得到各训练方法需要执行的计算量。
- **训练带来的新状态**：除计算量外，训练还带来新的状态保存需求。除了计算 $\mathrm{d}W$ 要用的 $X$，**对非线性运算求梯度也需要相应的中间结果**。参数梯度在反向传播中产生，再由优化器用来计算参数更新量。**优化器的状态记录多次更新积累的信息，因此需要保留到下一次更新。** 原文的关键判据：**每类数据的保留期限取决于最后一次使用它的操作**——某层激活通常在该层反向计算用完后释放，优化器动量则需要跨越多次更新持续保留。

> 图 3-21（原文插图）：激活的生命周期：一层激活从前向完成后保留到相应反向用完。横轴按事件排列（开始 → 前向完成 → 反向开始 → 反向完成），间距仅表示过程顺序；纵轴示意"该层计算"与"该层激活"两条状态带：激活带从"前向完成"开始，一直延续到该层反向用完，随后即可释放其占用的空间。

**例题 3-3：梯度与优化器状态为何使训练内存需求成倍增加？**

**解（原文给出）**：以 Qwen3-8B 的 **8,190,735,360 个参数**为例，保存 **BF16 权重、FP32 梯度、一份独立的 FP32 主权重（master weight），以及 Adam 的两个 FP32 矩估计**。Adam 是根据梯度及梯度平方的移动平均调节更新幅度的优化器，**两个矩估计分别保存这两种平均量**。不做分片（把这些状态切开，分给多张卡保存）时，每参数需要

$$2 + 4 + 4 + 4 + 4 = 18\ \text{bytes}$$

  共 $8{,}190{,}735{,}360 \times 18 = 147{,}433{,}236{,}480$ bytes $= 147.433$ GB，约 **137.308 GiB**。**尚未计入激活，这些状态就已超过一张 H100 SXM（80 GB）、RTX PRO 6000 Blackwell Workstation Edition（96 GB）乃至 H200（141 GB）的标称显存。**
- 原文的逐项解释：**BF16 权重用于前向和反向计算，梯度用于计算更新量，FP32 主权重用于高精度更新，Adam 的两个矩估计则累计梯度及其平方的统计量。** 这些数据合计占用的空间，**是推理 BF16 权重的九倍**。

> 图 3-22（原文插图）：训练沿前向依赖计算输出，再沿反向依赖传递梯度。图中三个方框依次为"前层、当前层、后层"；上排箭头表示"前向：输入 → 输出"，下排箭头表示"反向：后一层梯度 → 前一层的梯度"；图注说明"当前层另算权重梯度，用于更新"。

> 图 3-23（原文插图）：Qwen3-8B 全参数训练的参数相关状态。横轴为参数相关状态（GB，0–40 量级），五根柱依次是：BF16 权重 16.381、FP32 梯度 32.763、FP32 主权重 32.763、Adam 一阶矩 32.763、Adam 二阶矩 32.763。图注说明：每参数包括 2 字节计算权重和 4 组 4 字节状态，共 18 字节；激活和工作区的容量需求按各自的生命周期单独计算。

- **micro-batch 与参数更新要区分**：明确状态需求之后，再分析数据如何分批进入训练。**micro-batch（微批次）是一次前向和反向实际处理的数据子集**；完整的训练 batch 可以由多个 micro-batch 组成。显存无法容纳完整的训练 batch 时，可以**分多个 micro-batch 累计梯度，最后再更新一次参数**。**保持目标、有效标签和归一化一致时，将同一训练 batch 拆成更多 micro-batch，会改变执行顺序与激活的生命周期，而总训练数据量保持不变。** 第 10 章将据此讨论分片和流水。
- **数据准备与双缓冲**：训练过程中还要不断准备下一批输入。CPU 读取、解码、分词并组成 batch，再把张量送到加速器。**双缓冲**可以在计算当前 batch 时准备下一个 batch：**一个缓冲供计算读取，另一个接收新数据，交替使用**。计算用完已准备的数据后，就必须等待新输入；取回加速器结果时又会等待相应计算完成。第 5 章将结合前向、反向和参数更新的执行顺序，分析数据准备与计算如何重叠。

**辅导讲解**

- 为什么"训练 ≈ 前向的三倍"这句话要落在**矩阵尺寸**上才站得住？因为三次乘法的 $mkn$ 完全一样（笔记整理）：前向是 $[m,k]\times[k,n]$，输入梯度是 $[m,n]\times[n,k]$，权重梯度是 $[k,m]\times[m,n]$——**三个形状循环移位，乘加次数都是 $mkn$**。每次乘加算 2 FLOPs，所以三次合计 $6mkn$。这个推导是本章最值得亲手写一遍的地方，因为后面所有的训练预算（$6ND$、8K 训练矩阵的 402.591 TFLOPs、RL 各阶段运算量）都建立在它上面。
- $F_{\text{train}} \approx 6ND$ 的**前提条件**原文写得很清楚："若所有训练 token 都经过同一组主要参数矩阵"。这有两层意思：(1) $D$ 是**参与计算的 token 总数**（含为监督 token 提供上下文的那些），不是标签数；(2) $N$ 是**每个 token 都要过一遍的参数量**——所以嵌入层、MoE 里没被选中的专家都不满足这个条件。3.4.3 节那句"词嵌入等模块虽然包含参数，但并不对每个 token 执行完整矩阵乘法，不能一律按 $6ND$ 计入"说的就是这个。
- 例题 3-3 值得算两遍（笔记复算）：$8{,}190{,}735{,}360 \times 2 = 16{,}381{,}470{,}720$ B $= 16.381$ GB（BF16 权重）；$\times 4 = 32{,}762{,}941{,}440$ B $= 32.763$ GB（每一组 FP32 状态）。五项相加 $16.381 + 4\times 32.763 = 147.433$ GB ✓。换算成 GiB 要除以 $1024^3$：$147{,}433{,}236{,}480/1{,}073{,}741{,}824 = 137.308$ GiB ✓。**GB 与 GiB 差 7.4%，在"卡够不够装"的判断上足以改变结论**，原文两种单位都给了，读者自己算的时候要对齐口径。
- 为什么要有独立的 **FP32 主权重**？原文只给了"用于高精度更新"这一句。可以这样理解（笔记补充）：参数本身以 BF16 保存是为了省显存和跑得快，但如果每次更新都在 BF16 上累加，很小的更新量会被舍入吃掉（BF16 只有 8 位尾数）。所以训练保留一份 FP32 的参数副本，更新在 FP32 上做，算完再转回 BF16 给前向用。这就是"2 字节计算权重 + 4 字节主权重"并存的原因。
- **优化器状态为什么必须跨更新保留**：Adam 的两个矩估计是**梯度及其平方的移动平均**，它们天然是"跨步"的量——第 $t$ 步的估计依赖第 $t-1$ 步的估计。所以激活可以在反向用完后立刻释放（生命周期 = 一次前反向），而优化器状态必须活到训练结束。**"保留期限取决于最后一次使用它的操作"** 这句话就是判断所有训练状态大小的总纲：把每个张量的"最后一次被读"标出来，它从产生到那次读取之间占的空间就是它的容量需求。
- **micro-batch 是"显存换时间"的旋钮**：把一个大 batch 拆成 $a$ 个 micro-batch，峰值激活从"整个 batch 的量"降到"一个 micro-batch 的量"（因为每个 micro-batch 的激活在它自己的反向完成后就能释放），代价是前反向要执行 $a$ 次、每次都要重新读一遍权重。**注意原文的限定：保持目标、有效标签和归一化一致时，总训练数据量不变**——也就是说，拆分本身不改变"学了什么"，只改变"怎么算"。3.5.2 会给出一个反例：如果各 micro-batch 分别求均值再平均，归一化就变了，有效 token 少的 micro-batch 反而权重更大。
- **双缓冲的意义**：GPU 算的时候 CPU 在准备下一批数据，这样数据准备时间被"藏"在计算时间里。如果只有单缓冲，GPU 算完就得干等 CPU 分词。第 5 章会把这条流水线画全（前向、反向、参数更新与数据准备如何重叠）。
- **工程上的四条**：
  1. 训练显存要先算"参数相关状态"这一项（$18N$ 字节），它跟 batch 大小无关，是**地板**。以 8B 模型为例，地板就是 137.3 GiB，一张 80 GB 卡根本放不下。
  2. 激活是**随 batch 与序列长度增长**的那部分，可以用 micro-batch 和重计算压。
  3. 冻结参数能省的是**权重梯度与对应优化器状态**，但**省不掉输入梯度**——因为更早的可训练层还要靠它传误差。这是初学者最常见的误算。
  4. 记容量要按"峰值"记，而不是"平均"。激活的峰值出现在前向刚做完、反向还没开始的时刻（图 3-21 的中间段），这是训练最容易 OOM 的时刻。

**易混点**

- **$N$（参数量）与 $D$（训练 token 数）**：$N$ 决定**状态地板**（$18N$ 字节）和每 token 的计算量；$D$ 决定**总计算量**（$6ND$）和训练时长。3.6.2 里那个 $D/N$（每参数多少个 token）正是把两者放在一起比较的指标。
- **梯度（gradient）与优化器状态（optimizer state）**：梯度是"这一次反向算出来的敏感度"，每次迭代都可重算；优化器状态是"跨迭代累积的统计量"，必须持久保存。所以梯度在很多方案里可以省（例如用 BF16 存、或者用分片摊掉），优化器状态却很难省。
- **micro-batch 与 batch**：micro-batch 是**一次前反向**处理的数据量（硬件执行单位），batch 是**一次参数更新**累计的数据量（学习语义单位）。两者之间差一个"累计次数"。
- **"训练矩阵运算量约为前向三倍"与"训练总运算量约为前向三倍"**：前者只对**矩阵乘**成立。训练还有归一化、激活、损失、优化器更新等非矩阵运算，序列越短，这些部分占比越高（3.4.3 会讲）。

**一句话记住**

> 训练要留 $x$ 算 $\mathrm{d}W$、留 $w$ 传 $\mathrm{d}X$，三次矩阵乘各 $2mkn$，合计 $6mkn$ 即 $F_{\text{train}}\approx 6ND$；而状态上每参数要 18 字节（2 权重 + 4 梯度 + 4 主权重 + 4+4 两个 Adam 矩），8B 模型就是约 137.3 GiB，还没算激活。

### 3.4.2 预训练、中期训练与 SFT

**原文要点**

- **三个阶段名称不同，系统问题相同**：训练阶段的名称不同，系统仍要回答同样的问题：**输入有多少 token，哪些 token 参与损失，多少个 micro-batch 后更新一次参数。**
- **三个阶段的差别**：
  - **预训练**通常对连续文本做**下一 token 预测**；
  - **中期训练**调整**数据组成或上下文长度**；
  - **监督微调（SFT）**使用给定输入与目标回答继续训练模型，**常把指令与回答放在一起输入，只对回答计算损失**。
  估算资源时，要把这些差异落实为**输入形状、参与监督的 token 数和更新频率**。
- **Qwen3 的训练过程体现这些变化**：通用阶段使用**长度为 4096 的序列训练超过 30 万亿 token**，随后增加**科学、技术、工程与数学（STEM）、代码、reasoning 与合成数据，再训练约 5 万亿 token**；**长上下文阶段将长度扩至 32768**。原文的结论：**数据组成改变学习内容，序列长度还直接改变每个 token 可以访问多少前文，因此需要分别观察。**
- **序列分布如何改变注意力工作量**：假设两组独立文档都含 8192 个 token，一组为 $4096 + 4096$，另一组为 $7168 + 1024$。
  - 参数投影的行数相同（都是 8192 行）；
  - 但**因果注意力的有效查询—键配对数**分别为 **16,781,312** 和 **26,218,496**；
  - 在 Qwen3-8B 一层上，$QK^{\mathsf T}$ 与 $AV$ 前向工作约从 **0.275 增到 0.430 TFLOPs，增加约 56%**。
  原文的解释：**较长文档中的 token 可以看到更多前文，所以在总行数不变时，上下文交互增加；投影与 FFN 仍处理同样的 8192 个 token 表示。整层运算量的增幅取决于这部分新增交互占原有工作量的比例。**
- **SFT 中"读的 token"与"算损失的 token"不同**：一条样本可以包含系统提示、用户问题、工具结果和回答，但**训练只对回答部分计算损失**。其余 token 仍要经过主干网络，为回答提供上下文。实现还可以**只对参与监督的 token 计算词表投影**；**如果只在计算损失时屏蔽不参与监督的 token，却没有跳过这些 token 的词表投影，这部分矩阵乘法仍会照常执行。**
- **只训练部分参数的情形**：微调还可以只训练部分参数，这时**需要保存梯度和优化器状态的参数也相应减少**。**冻结模块的权重保持不变，但梯度仍需穿过它们传到较早的可训练模块，因此仍须计算相应的输入梯度。** 沿反向图逐层判断**是否求输入梯度、是否求权重梯度**，就能把训练状态与计算分别算出。
- **micro-batch 与更新数的定量关系**：设每个 micro-batch 有 $B_\mu$ 条长度为 $P$ 的序列，累计 $a$ 个 micro-batch 后更新一次，则

$$D_{\text{update}} = a\,B_\mu P\ \text{（每次更新读取的输入 token 数）}$$

  若每条只有 $P_{\text{label}}$ 个参与监督的 token，**损失归一化使用的有效 token 数**为

$$D_{\text{label}} = a\,B_\mu P_{\text{label}}$$

  **增大累计次数可以扩大每次更新的 batch，同时让一次更新分多次前反向执行；参数状态一直保留，每个 micro-batch 的激活可以在反向完成后释放。**

**辅导讲解**

- 这一小节最重要的一句话是"**SFT 中，模型读取的 token 与参与损失计算的 token 往往不同**"。把它想成一次考试：题目全文（系统提示、用户问题、工具结果）都得读，但只有你写的那部分答案会被打分。系统上这意味着**两个数量要分别记**：$D$（读取的 token，进 $6ND$ 的分子）和 $D_{\text{label}}$（打分的 token，决定损失归一化的分母）。原文在 3.4.3 会给出这个区别的实际后果：标签减半但词表投影照做，运算量一点不变。
- **序列分布那个算例值得亲手验一遍**（笔记复算）。因果注意力下，长度 $L$ 的序列的有效查询—键配对数（含自身）是 $\sum_{i=1}^{L} i = L(L+1)/2$：
  - $4096$：$4096 \times 4097/2 = 8{,}390{,}656$，两条相加 $= 16{,}781{,}312$ ✓
  - $7168$：$7168 \times 7169/2 = 25{,}693{,}696$；$1024$：$1024 \times 1025/2 = 524{,}800$；合计 $= 26{,}218{,}496$ ✓
  - 比值 $26{,}218{,}496/16{,}781{,}312 \approx 1.5624$，与"约增加 56%"一致 ✓（注意：这个配对数的比值是 56%，而实际一层运算量从 0.275 增到 0.430 TFLOPs，比值 $0.430/0.275 \approx 1.564$，也约 56%——两者吻合，说明这一项在 Qwen3-8B 的注意力里占主导。）
  - **同样的 8192 个 token，一行代码没改，总运算量却能差出 56%**。这就是"训练 token 总数相同，系统工作量就相同"这个误区（见章末"谬误与陷阱"）的定量反例。
- **SFT 实现里的那个"坑"值得单独说清**：词表头（LM head）是一次 $[\text{batch}\times L, h] \times [h, V]$ 的大矩阵乘，$V$ 通常是十几万。如果只在算损失时把非监督位置 mask 掉，这个矩阵乘**照样要为所有位置算一遍**——因为在标准实现里，mask 发生在 softmax/损失阶段，而矩阵乘发生在它之前。要真正省掉这份计算，必须在**进入词表头之前**先把监督位置挑出来（原文的"先取出参与监督的 token 的隐藏向量"）。3.4.3 里 431.368 → 416.074 TFLOPs 的那 15.294 TFLOPs 就是这部分的省法。
- **冻结模块为什么还费计算**：很多人以为"冻结 = 免费"。实际上冻结只免掉了**权重梯度**（以及对应的优化器状态），**输入梯度必须照算**，因为要靠它把误差继续往前传。用一个比方：一条传送带上，即使中间某个齿轮不调整，误差信号仍然要经过它传到上游。这就是原文"冻结模块的权重保持不变，但梯度仍需穿过它们"的含义。
- **Qwen3 的三个阶段**（笔记整理）：4096 长度 × 30 万亿 token（通用）→ 增加 STEM/代码/reasoning/合成数据的约 5 万亿 token（中期训练）→ 长度扩到 32768（长上下文）。注意"长度扩到 32768"不是简单地把序列拉长：按上面的配对公式，长度翻 8 倍，注意力配对数涨约 64 倍。这就是长上下文训练特别贵的原因，也解释了为什么它被单独列为一个阶段。
- **什么时候需要"中期训练"这个阶段**：它的作用是**在不重新跑完整预训练的前提下，改变数据的配方或长度**。数据配方（STEM、代码比例）改变的是"学什么"；上下文长度改变的是"能看到多远的依赖"和"注意力有多贵"。系统上它对应一次小规模的"重新配平"，成本远低于预训练但效果导向明确。

**易混点**

- **读取的 token 数与参与损失的 token 数**：前者进 $6ND$（决定算力），后者决定损失归一化与梯度尺度（决定学得对不对）。两者混用会出现"运算量估少了"或"梯度尺度错了"两类不同的问题。
- **"屏蔽损失"与"跳过词表投影"**：前者只影响损失数值，省不了矩阵乘；后者才是真正的计算量优化。原文特意把这两者并列，就是为了防止读者误以为 mask 等于省算。
- **冻结参数与冻结梯度**：冻结的是**权重更新**，不是梯度传播。输入梯度仍要算，除非后面的层完全不需要梯度（比如它之后没有任何可训练参数）。
- **序列长度 $P$ 与总 token 数**：总 token 数相同时，序列越"长而少"，注意力越贵。$6ND$ 用的是总 token 数，会把这一差异抹平——这正是它只是"粗算"的原因。

**一句话记住**

> 训练估算要回答三件事：读了多少 token（$6ND$）、多少 token 参与损失（$D_{\text{label}} = aB_\mu P_{\text{label}}$）、多少个 micro-batch 更新一次（$a$）；而同样 8192 个 token 分成 $4096+4096$ 与 $7168+1024$，注意力配对数是 16,781,312 对 26,218,496，差 56%。

### 3.4.3 从 $6ND$ 估算到逐项计算训练开销

**原文要点**

- **两步走的方法**：确定训练数据和有效 token 数之后，就可以累计总运算量。**先用线性层"训练约为前向三倍"的关系作粗算，再把注意力、词表头和状态更新逐项补回，便能看出粗算与完整模型之间的差距。**
- **基准设置**：以一次完整训练前向和反向为例：**Qwen3-8B，$B = 1$，$P = 8192$，全参数训练，所有输入 token 执行词表头，没有重计算**（重计算指为少保存激活，在反向时重新执行部分前向）。逐层累计投影、FFN、$QK^{\mathsf T}$、$AV$ 和输出头，矩阵运算量如下（表格按原文语义还原）：

| 矩阵计算 | TFLOPs |
| --- | --- |
| 前向矩阵 | 143.789 |
| 反向矩阵 | 287.579 |
| 前向加反向 | 431.368 |
| 其中因果注意力 $QK^{\mathsf T}$ 与 $AV$ 前反向 | 59.381 |
| 总参数代入 $6ND$ | 402.591 |

- **哪些漏算了、哪些多算了**：把 402.591 TFLOPs 的粗算修正到 431.368 TFLOPs，需要先说明两件事：
  1. **漏算**：查询与上下文之间的矩阵乘法不对应一份模型参数，却在前反向中贡献 **59.381 TFLOPs**；
  2. **多算**：词嵌入等模块虽然包含参数，但**并不对每个 token 执行完整矩阵乘法，不能一律按 $6ND$ 计入**。
  两项修正相抵后，**矩阵运算总量比粗算高约 7.15%**（笔记复算：$431.368/402.591 - 1 = 7.148\%$）。
- **属于哪一类差距**：原文明确指出这属于**第 1.3.4 节所说的第一类差距**：**粗算漏掉了注意力的二次项，又多算了不参与完整矩阵乘法的参数，要改的是模型本身，与实现无关。只有修正后的下界，才能用来衡量系统的利用率。**
- **有效标签减半的两种做法**：将有效标签数减到 **4096**，
  - 如果**仍对全部 token 计算词表投影**，矩阵运算量**就不变**；
  - 如果**先取出参与监督的 token 的隐藏向量，再只对它们执行词表投影**，总量则降到 **416.074 TFLOPs**。主干网络仍处理全部输入，**节省的是不参与监督的 token 的词表投影；反向时再把梯度放回对应位置。**

> 图 3-24（原文插图）：Qwen3-8B、8192 个 token 输入的全参数训练。横轴为矩阵运算量（TFLOPs，0–500 量级），四组柱依次为"前向"143.789、"反向"287.579、"前向加反向"431.368，以及"按总参数估算：$6ND$"402.591。图注说明：全部输入 token 执行词表头、没有重计算；按矩阵逐项累计，前向加反向为 431.368 TFLOPs。

- **非矩阵运算也要算**：归一化、激活、损失与优化器也需要计算和读写。以参数更新为例，**即使序列较短，仍要读写权重、梯度和优化器状态；序列越短，这部分成本在总量中的占比往往越高。** 因此，**训练预算既要考虑随 token 数增长的矩阵计算，也要考虑由参数量决定的更新开销。**
- **新增的前向操作会带来对应的反向**：模型新增的前向操作，也会增加对应的反向计算。**上下文压缩需要对投影、池化和状态更新求梯度，mHC 需要向各残差通路传播梯度，MoE 则要对实际选中的专家求梯度。** 第 2 章的计算图因而也能用于判断：**训练时要保存哪些中间结果，反向又要执行哪些运算。**
- **序列长度变化时的趋势判断**：序列长度变化时可以先判断各项开销的变化趋势：**参数投影随输入行数增长，注意力随查询—键配对数增长，优化器更新随参数量和更新次数增长**。若采用重计算，**容量需求下降，但重做的前向运算还要加回 $F_{\text{train}}$**。这些变化都能沿同一张前向—反向图逐项解释。

**练习 3-6〔延伸〕：一次参数更新需要多少计算、训练状态和监督 token**

**题干（原文）**：从 $Y = XW$ 推导输入梯度和权重梯度的尺寸，说明三次矩阵乘法的运算量为何相同。对 Qwen3-8B，按每参数 18 字节计算长期训练状态的总容量，再将梯度改为 BF16，求节省的容量。设每个 micro-batch 含 2 条序列，每条有 4096 个输入 token，其中 1024 个 token 参与监督。累计 8 个 micro-batch 后更新一次参数，求每次更新处理的输入 token 总数和有效监督 token 总数。解释仅屏蔽不参与监督的 token 的损失，与只对参与监督的 token 执行词表投影，在计算量上有何区别。

**参考解答（笔记补充，非原文）**

1. 梯度尺寸。$X$ 是 $[m,k]$，$W$ 是 $[k,n]$，$Y$ 是 $[m,n]$；反向传来的 $\mathrm{d}Y$ 也是 $[m,n]$。
   - $\mathrm{d}X = \mathrm{d}Y\,W^{\mathsf T}$：$[m,n] \times [n,k] \to [m,k]$，与 $X$ 同形 ✓
   - $\mathrm{d}W = X^{\mathsf T}\mathrm{d}Y$：$[k,m] \times [m,n] \to [k,n]$，与 $W$ 同形 ✓
   - 三次乘法的"乘加次数"都是 $m \times k \times n$（形状循环移位不改变乘加规模），每次乘加记 2 FLOPs，所以各为 $2mkn$ FLOPs，合计 $6mkn$。
2. 长期训练状态容量（每参数 18 字节）：
   - $8{,}190{,}735{,}360 \times 18 = 147{,}433{,}236{,}480$ bytes $= 147.433$ GB $= 137.308$ GiB。
   - 梯度改为 BF16 后，每参数 $2 + 2 + 4 + 4 + 4 = 16$ bytes，总容量 $= 131{,}051{,}765{,}760$ bytes $= 131.052$ GB $= 122.052$ GiB，**节省 16.381 GB（约 15.256 GiB，减少 11.1%）**。
3. 一次更新（$a = 8$，$B_\mu = 2$，$P = 4096$，$P_{\text{label}} = 1024$）：
   - 输入 token 总数 $= aB_\mu P = 8 \times 2 \times 4096 = 65{,}536$；
   - 有效监督 token 总数 $= aB_\mu P_{\text{label}} = 8 \times 2 \times 1024 = 16{,}384$。
4. 两种做法的计算量区别：
   - **仅屏蔽损失**：词表投影的矩阵乘仍按**全部 65,536 个位置**执行（$[\text{token}, h]\times[h, V]$），只是 softmax/损失阶段把非监督位置排除。省不了矩阵计算。
   - **只对监督 token 执行词表投影**：先把 16,384 个监督位置挑出来再算，词表头部分的矩阵乘按 16,384 个位置执行，比例是原来的 $1/4$。这就是 3.4.3 中 431.368 → 416.074 TFLOPs 的来源（该算例里有效标签从 8192 减到 4096，即减半）。

**辅导讲解**

- 这一小节是"**粗算 → 逐项修正**"的完整示范，方法是通用的：
  1. 用 $F \approx 6ND$ 得到第一版数字（402.591 TFLOPs）；
  2. 找出**不满足"所有 token 都过同一组参数矩阵"这个前提**的部分——注意力（有计算但不对应参数）和词嵌入（有参数但不做完整矩阵乘）；
  3. 把注意力加上、把嵌入扣掉，得到 431.368 TFLOPs。
  两处修正方向相反、量级接近（净 +7.15%），但**不能因为"相抵"就忽略它们**：原文指出这属于"第一类差距"（改模型本身才能消除，与实现优劣无关），**只有修正后的数字才能当作下界用来衡量系统的利用率（MFU）**。拿 402.591 当分母去算 MFU，会算出大于真实值的利用率，误以为实现非常好。
- 复算（笔记补充）：反向矩阵 $287.579 = 2 \times 143.789$ 精确成立，这与 3.4.1 的"反向是前向的两倍矩阵运算（输入梯度 + 权重梯度）"完全一致。所以"训练 ≈ 前向三倍"在**矩阵层面**是精确的（$143.789 \times 3 = 431.367$，与 431.368 只差取整）。真正与 $6ND$ 有偏差的原因不是"三倍关系"错了，而是"$N$ 的构成"与"注意力项"没被 $6ND$ 涵盖。
- **为什么"有效标签减半但运算量不变"是个重要结论**：它说明**优化了数据（减少监督 token）不等于优化了计算**。训练算力的大头在"让全部输入 token 过一遍主干"，词表头只是其中最"宽"的一层。这也解释了为什么"只对监督 token 算损失"这种 SFT 常规做法，对训练速度几乎没影响——它改变的是学习信号，不是计算量。
- **"序列越短，非矩阵开销占比越高"**这句话非常实用。当序列很短（例如 $P=512$）时，矩阵乘的规模按 $P$ 缩小，但**优化器更新部分的读写（权重、梯度、优化器状态，按参数量 $N$ 计）不缩**。所以小序列训练时，训练会从"算力受限"滑向"显存带宽受限"——这和第 2 章推理侧的算术强度问题是同一种物理。3.5.3 里 RL 的"策略更新"阶段运算量高达 952.416 TFLOPs（比 rollout 的 prefill 465.143 还大），正是这个效应的体现：更新阶段要读全部权重的梯度与优化器状态。
- **重计算的取舍**：原文一句"若采用重计算，容量需求下降，但重做的前向运算还要加回 $F_{\text{train}}$"概括了它的本质——**用计算换显存**。什么时候划算？当显存是瓶颈、而算力还有余量时（例如 batch 很大但要保 OOM 边界）。什么时候不划算？当训练已经是算力受限时，重计算会让每一步都变慢。
- **MoE / 上下文压缩 / mHC 的统一判断法**：原文列举这三种结构，给出的方法却是同一句——**"沿反向依赖逐项累加"**。具体做法（笔记整理）：
  1. 列前向图里每个算子；
  2. 对每个算子问两个问题：它有没有参数（要不要算权重梯度）、它之后的层要不要梯度（要不要算输入梯度）；
  3. 两项都要算的算子按 $6mkn$ 计，只算输入梯度的按 $4mkn$ 计（前向 2 + 输入梯度 2），只做前向的按 $2mkn$ 计。
  这个"按需计费"的方法能覆盖冻结层、MoE 未选中专家、被压缩掉的上下文等各种情况，比死记 $6ND$ 可靠得多。
- **工程上怎么用这一节**：
  1. 做容量/算力预算时，先按 $6ND$ 出一版，再用本文的修正率（本例 +7.15%）做敏感性分析。注意这个修正率**依模型结构而变**：注意力占比重的小模型修正率低，长上下文模型修正率高。
  2. 报 MFU 时要写清分母是"逐项计算的理论量"还是"$6ND$ 粗算"，否则不同团队的数字不可比。
  3. 训练短序列任务时，别只盯 FLOPs——优化器读写很可能才是真瓶颈。

**易混点**

- **$6ND$ 粗算 与 逐项计算**：前者是"参数量 × token 数 × 6"的快速估计，后者是把每个矩阵（投影、FFN、$QK^{\mathsf T}$、$AV$、输出头）分别算出来再相加。前者便于口算，后者才配当利用率的分母（原文："只有修正后的下界，才能用来衡量系统的利用率"）。
- **漏算的注意力与多算的嵌入**：两者方向相反。别因为"最后只差 7.15%"就以为两处可以互相抵消而随便忽略——它们在不同的模型结构下比例完全不同。
- **减少监督 token 与减少计算**：前者改变学习目标，后者改变算力开销，两者不等价（4096 标签 + 全量词表投影 = 运算量不变）。
- **重计算（recomputation）与"没有重计算"这个前提**：表里的 431.368 TFLOPs 是在"没有重计算"下算出来的。如果启用重计算，这个数还要往上加。

**一句话记住**

> 粗算 $6ND = 402.591$ TFLOPs，逐项补上注意力 59.381、扣掉不做完整矩阵乘的嵌入参数，得到 431.368 TFLOPs（高 7.15%）；只有这个修正后的下界才配当 MFU 的分母——而有效标签减半、词表投影照做时，运算量一点都不变。

## 3.5 强化学习（RL）

### 3.5.1 Rollout、奖励与环境验证

**原文要点**

- **RL 与"推理""预训练"的起点不同**：**推理从外部请求开始，预训练从已有文本开始。强化学习（RL）用行动得到的反馈来改进后续行动。** 在语言模型中，**策略（policy）是给定上下文时选择下一个 token 的概率分布**。RL 把两条路径连接起来：**当前策略先生成回答，再由反馈决定如何更新参数，更新后的策略继续产生下一批数据。生成过程通常称为 rollout。**
- **公开实践**：这条训练路线已有公开实践：**DeepSeek-R1 给出了从 reasoning 任务和可验证奖励出发的做法**。对代码、数学等容易检查的任务，**反馈可以来自规则或测试**；对需要实际操作的任务，**则要运行工具与环境**。**奖励**是用来评价一次回答或行动效果的数值。**奖励若由另一个模型生成，还会产生额外推理。** 因此，**一次"训练迭代"可能包含多个模型、CPU 测试、沙箱等待和梯度更新。**
- **更近的模型把 RL 与其他训练阶段组合起来**：**DeepSeek V4-Flash 先通过 SFT 和 RL 训练领域专家，再以多教师的同策略蒸馏（on-policy distillation，OPD）将多个专家的能力整合到同一个模型中。**
  - **蒸馏**让学生模型学习教师模型给出的输出信息；
  - **OPD** 由**当前学生自己生成轨迹**，**教师在这些 token 位置提供候选输出的概率分布**，学生据此学习。
  - 因此，**教师前向成为生成与更新之间的一项模型工作**；**规则验证则以测试或程序执行提供反馈，需要另一组计算资源**。
- **沿循环分析资源的方法**：沿这一循环分析资源时，**先找数据的生产者和消费者**：
  - **策略生成 token**；
  - **奖励函数或教师读取回答**；
  - **学习器读取训练样本并产生新权重**；
  - **负责生成的模型副本再使用新权重**。
  **某一角色变慢，后继角色就要等待；增加教师模型则需要额外的前向计算和权重存储空间。后续的并行安排都必须建立在这张依赖图上。**

**辅导讲解**

- 把 RL 与前面几节对照，可以看出它为什么"更难算"（笔记整理）：
  - 推理：一次请求一次前反向（只有前向），负载形状由请求决定。
  - 预训练：数据是现成的，一次前反向 + 一次更新，负载形状由 batch 决定。
  - RL：**数据要自己造**（rollout），**质量要自己评**（奖励 / 教师 / 测试），**权重还要发回去**（同步）。所以它的负载形状由"生成 → 反馈 → 学习 → 同步"这条环决定，而且**环上有多个异构组件**（模型、CPU、沙箱）。
- 原文那句"先找数据的生产者和消费者"是一个非常实用的排障方法。举例：如果 rollout 很慢，要问"是策略模型慢，还是沙箱排队，还是工具环境慢"？如果更新很慢，要问"是不是在等 rollout 的样本凑够一个 batch"？把每个角色的**产出**和**消耗**列出来，就能看到谁在等谁——这正是第 10 章要排的调度问题。
- **"奖励由模型生成会产生额外推理"这一句值得放大**：如果奖励来自规则或单元测试，成本是 CPU 与沙箱时间（便宜、可并行、但可能排队）；如果奖励来自一个 reward model 或教师模型，成本就是**一份前向计算 + 一份权重存储**。3.5.3 的例题 3-4 里"教师评分设为零次"，正是把这个变量显式地归零，方便先看清另外几项。
- **OPD 与普通蒸馏的区别**（笔记整理，依据原文"OPD 由当前学生自己生成轨迹"）：
  - 普通（离线）蒸馏：用教师自己生成的（或已有的）数据训练学生——学生学的是"教师走的路"。
  - 同策略蒸馏：学生自己走，教师只在学生走过的那些位置上给出概率分布——学生学的是"在我会走到的位置上，教师会怎么选"。后者的分布更贴近学生实际遇到的上下文，代价是**每一步都要请教师做一次前向**。
- **为什么 RL 的"一次迭代"可能很贵**：原文说一次迭代"可能包含多个模型、CPU 测试、沙箱等待和梯度更新"。这四类的资源完全不同（GPU 算力、CPU、I/O 与排队、GPU 算力），且**不能互相替代**。所以在规划容量时，RL 需要的是一张"每类资源各自多大"的表，而不是一个总算力数字。
- **不适用的情况**：RL 需要"可验证"或"可评分"的反馈信号。对没有可靠反馈信号的任务（例如纯开放式写作），奖励本身就是噪声，此时"增加生成计算"不一定带来能力提升——这与 3.2.2 讲的"延长生成仍未提高成功率"是同一个陷阱。

**易混点**

- **rollout 与推理服务**：两者都在跑生成，但 rollout 是**训练的一环**，它产生的样本要进更新；推理服务产生的 token 直接给用户。因此 rollout 可以（也应该）为了训练效率做特殊安排（例如等长样本、组内比较），而推理服务不行。
- **奖励（reward）与损失（loss）**：奖励是**环境或规则给这一条回答的评分**（外部信号）；损失是**学习器为了让策略朝高奖励方向走而构造的可微目标**。3.5.2 的"组内相对优势为零"就发生在从奖励到损失这一步。
- **教师前向与参考模型前向**：两者都是"为了别的目的跑一遍模型"，但目的不同——**参考模型**用来约束策略偏离程度（3.5.3 详述），**教师**用来提供学习目标。两者都要额外的计算与权重存储。

**一句话记住**

> RL = "生成（rollout）→ 反馈（规则/测试/教师/环境）→ 更新 → 权重回传"的闭环；先画清数据的生产者与消费者，再逐阶段配资源，因为一次迭代里同时有 GPU、CPU 和沙箱在排队。

### 3.5.2 有效样本、策略更新与权重同步

**原文要点**

- **两类样本要分清**：生成回答和计算奖励之后，还要决定哪些样本用于学习。**关键是区分已经生成的样本与最终进入更新的样本**：**前者决定生成开销，后者决定训练 batch，两者的数量未必相同。**
- **生成数的期望**：设一轮需要保留 $n_{\text{keep}}$ 条样本，生成样本的平均保留比例为 $a$，则所需生成数的期望为

$$n_{\text{generate}} \approx \frac{n_{\text{keep}}}{a}$$

  **保留 16 条样本，比例为一半时平均需要生成 32 条，降为四分之一时平均需要生成 64 条。** 原文的三阶段分工：**生成和评分处理全部回答，参数更新只处理保留样本；保留比例下降会增加前两个阶段的工作，而不会按同样比例扩大更新 batch。**
- **什么决定保留**：是否保留一条样本，由**训练方法及筛选规则**决定。**有的方法把失败回答作为负反馈，有的方法排除截断或奖励无效的回答。** **优势**表示某个回答相对于比较基准更好或更差的程度。**采用组内相对优势时，还要比较同一道题多份回答的奖励。** 因此：**保留样本数决定更新时处理多少数据，奖励和损失函数则决定这些数据产生何种梯度。**
- **例子：相同奖励如何消除组内学习信号。** 在使用组内相对奖励的策略更新中，**如果同组回答得到相同奖励，减去组内平均奖励后，每条回答的优势都为零，相应的策略梯度也为零**。**回答全部正确就可能出现这种情况。** 模型完成了生成、评分和更新流程，却没有从这一组回答中获得区分优劣的信号。**只有奖励差异提供了非零优势，策略损失才会推动参数沿相应方向调整。**
- **损失的求平均方式也会影响训练**：若目标是**对整个 batch 的有效 token 求平均**，累计各 micro-batch 梯度时就要使用**整个 batch 的有效 token 总数作为分母**。若**先分别计算每个 micro-batch 的均值，再对这些均值求平均**，**有效 token 较少的 micro-batch 里，token 就可能获得更大权重**。第 10 章将用具体训练方法解释这种差别。
- **权重必须回到生成端**：更新后还要把策略权重送给生成端。**若生成端继续使用旧版本，下一批数据就仍由旧策略产生。** 同步循环可以等权重就绪后再生成；**异步方案允许部分阶段重叠，却要处理样本版本与滞后**。第 10 章再讨论交接、抢占、恢复和资源配比。

**辅导讲解**

- $n_{\text{generate}} \approx n_{\text{keep}}/a$ 是一个很容易被低估的式子。举例：要 16 条保留样本，如果只有 1/4 的回答能通过筛选，就得生成 64 条——**生成是 4 倍，评分也是 4 倍，但更新还是 16 条**。所以"筛选变严"这件事的成本**不对称地压在生成和评分阶段**上，而这两个阶段恰好是最贵、最难并行的部分（生成是自回归串行的，3.5.3 会量化）。这也是 3.5.3 例题 3-4 的主题。
- **"组内相对优势全为零"这个例子，是 RL 工程里最常见的"空转"**：某道题的所有回答都对（或都错），减去组均值后每条的优势都是 0，于是这一组样本**跑了完整流程却贡献了零梯度**。它提醒我们两件事：
  1. **数据配比很重要**：题目太简单或太难，都产生不了学习信号。所以很多 RL 流程会做难度筛选，把"全对"和"全错"的组剔除或降权。
  2. **算力会浪费在零梯度样本上**：即便你剔除了它们，生成它们的成本已经花掉了（这也是 $n_{\text{generate}}$ 与 $n_{\text{keep}}$ 的差）。
- **损失归一化的两种做法为什么不同**（笔记整理）：
  - **全局归一化**（用整个 batch 的有效 token 总数作分母）：每个 token 的权重都一样，与它落在哪个 micro-batch 无关。数学上等价于"把所有 micro-batch 的有效 token 拼成一个大 batch 求平均"。
  - **先各自求均值再平均**：等价于**给每个 micro-batch 相同的权重**，而不是给每个 token 相同的权重。如果各 micro-batch 的有效 token 数不同（例如长度不一、或有效标签比例不同），那么有效 token 少的那个 micro-batch 里的**单个 token**就会获得更大的权重。
  这与 3.4.1 讲的 micro-batch "保持归一化一致"是同一个话题的两面：前者说"拆 micro-batch 不改变什么，前提是归一化一致"；这里说"归一化不一致时会怎样"。
- **权重同步的同步 vs 异步**（笔记整理，依据原文两句）：
  - **同步**：等新权重就绪，再开始下一批生成。**样本一定来自当前策略，没有滞后**，但生成端在等更新的那段时间是空闲的。
  - **异步**：生成端继续跑，不等更新。**吞吐更高**，但生成的样本可能来自**旧版本策略**，于是要处理"样本版本"和"滞后"（off-policy 程度）。
  这和 3.3.3 的"缓冲"是两类问题：那里是时间轴上的连续性，这里是**数据一致性**。第 10 章会讲怎么在两者之间选。
- **工程上的三条**：
  1. 规划 RL 容量时，把"生成数"和"更新数"分开报。只报"训练 batch = 16"会漏掉 4 倍的生成与评分开销。
  2. 监控"零优势样本占比"。如果这个比例长期很高，说明题库难度不合适，算力在被浪费。
  3. 权重同步是**一次集体通信 + 一次全量写入**。以 3.5.3 的数为例，8B 模型 BF16 一份权重 16.381 GB，4 个副本就是 65.526 GB 的传输量——如果同步频率高，这会成为网络瓶颈。

**易混点**

- **$n_{\text{generate}}$ 与 $n_{\text{keep}}$**：前者决定**生成与评分**的开销，后者决定**参数更新**的开销。保留比例 $a$ 只影响前者。
- **优势（advantage）与奖励（reward）**：奖励是原始评分，优势是"相对于基准"的差值。**奖励相同不代表优势为零**（如果基准也不同）；但在组内相对优势下，**同组奖励相同时优势必然为零**。
- **"屏蔽样本"与"不生成样本"**：屏蔽（不进更新）省的是更新开销；不生成省的是生成开销。前者便宜，后者要看筛选能否提前预测（通常不能，因为要先有回答才知道它好不好）。
- **同步循环中的"闲置"与异步循环中的"滞后"**：前者损失吞吐但数据干净，后者提升吞吐但数据陈旧。二者不是对错问题，而是取舍。

**一句话记住**

> 生成数 $\approx n_{\text{keep}}/a$：筛选越严，越多的成本压在生成与评分上，而更新 batch 不变；同组奖励相同则优势为零、梯度为零；更新完必须把新权重送回生成端，否则下一批数据还是旧策略产的。

### 3.5.3 有效样本数固定时，各阶段需要多少计算

**原文要点**

- **用固定目标来量化**：这种区分可以用固定目标量化：**每轮都要保留 16 条样本用于更新**。如果回答更难通过筛选，就必须先生成更多回答。

**例题 3-4：样本保留比例下降时，为保持更新样本数需要增加多少计算？**

**解（原文给出）**：以 Qwen3-8B 为例，设有**八道题，每题生成四份回答**，$P = 1024$，$G = 256$，共**保留 16 条样本用于一次策略更新**。
- **参考模型**（reference model，**权重保持固定、用来约束策略偏离程度的模型**）与策略模型结构相同，分别保存权重；**参考模型对全部 32 份回答各执行一次前向**，**本例不调用教师模型**。
- **各样本长度相同，生成时不提前停止，也不共享前缀。**
- **生成时每条先做一次 prefill，再做 255 次 decode。**
- **训练与评分时，轨迹已经确定，可以采用教师强制（teacher forcing）执行前向**：每个预测步骤使用轨迹中已经确定的前一个 token，而不是等待模型重新生成它。**因此，这些已知 token 可以一同计算。输入长度 $P + G - 1 = 1279$，256 个输出标签位于相应位置。**
- **16 条保留样本每轮更新的输入 token 共 20,464，监督输出共 4096。** 原文的结论：**输入 token 决定上下文计算，参与监督的 token 决定损失作用于哪些输出，二者分别进入训练预算。**

| 阶段 | 处理样本 | 矩阵运算量（TFLOPs） |
| --- | --- | --- |
| Rollout prefill | 32 | 465.143 |
| Rollout decode，255 步／条 | 32 | 129.056 |
| 参考模型，一次前向 | 32 | 634.944 |
| 教师评分，设为零次 | 0 | 0 |
| 策略更新，一次遍历 | 16 | 952.416 |
| 合计 | 保留 16 条 | 2,181.559 |

  （表格按原文语义还原。）
- **周期运算量公式**：将**一条回答的生成与参考模型前向合计运算量记为 $f_g + f_r$**，**一次固定更新 batch 的运算量记为 $F_u$**，则

$$F_{\text{cycle}}(n) = n\,(f_g + f_r) + F_u$$

  原文的限定：**参考模型读取完整回答，可以一次处理多个已知 token；生成则逐 token 推进。上式虽然把运算量相加，仍需分别记录各阶段的矩阵形状，才能根据对应的执行效率估算时间。**
- **保留比例从 $1/2$ 降到 $1/4$**：如果样本保留比例从 $1/2$ 降到 $1/4$，但仍要求得到 16 条保留样本，**教学对照改为生成 64 条**。生成与参考模型计算翻倍，更新量不变，**总矩阵运算量增到 3,410.701 TFLOPs，约增加 56.3%**。**每个保留样本分摊的矩阵运算量从 136.347 增到 213.169 TFLOPs。** 增加的 **1229.142 TFLOPs 全部来自额外回答的生成与参考模型计算**；进入更新的 16 条样本保持不变。
- **权重同步的传输量**：更新完成后，生成副本需要获得新权重。设有 $r$ 个副本，逐个独立发送大小为 $M_W$ 的完整权重，则

$$V_{\text{sync}} = r\,M_W$$

  **Qwen3-8B BF16 的一份权重约为 16.381 GB，四个副本共需约 65.526 GB。** **优化器状态留在学习器**，用于下一次更新；**生成副本只需要执行前向所需的权重**。**广播或分层分发则可以让多个副本共用部分传输路径，减少重复发送。**

> 图 3-25（原文插图）：强化学习中的角色和数据流。生成端产生回答 → 反馈环节评价结果（规则、模型或环境给出反馈）→ 筛选样本、组织训练输入 → 学习器计算梯度、更新策略；图中"左侧返回路径：新权重交给下一批生成"，形成闭环。图注强调"生成、反馈和学习使用同一批轨迹"。

> 图 3-26（原文插图）：保持 16 条有效样本的目标，生成数由 32 增到 64。横轴为矩阵运算量（TFLOPs，0–1600 量级），纵轴分四类阶段：生成输入、后续生成、参考评分、策略更新。生成 32 时四类分别约 465.143、129.056、634.944、952.416；生成 64 时前三类翻倍（约 930.286、258.112、1269.888），策略更新仍为 952.416。图注说明生成时的输入处理、后续 decode 和参考模型评分随回答总数增加，策略更新处理的样本数保持相同。

- **为各阶段分配资源时，既要看运算量，也要看计算方式**：**生成阶段的 decode 每步通常只处理各请求的一个新 token，在小 batch 下同时处理的 token 较少；评分和训练则能一起处理已知回答中的多个 token，工具验证还需要 CPU 和运行环境。** 原文的收尾：**分别估算各阶段的耗时，再按生成、反馈、更新和权重同步的顺序排列，才能得到完整周期。** 第 4 至 10 章将逐步介绍相应的硬件和调度方法。

**练习 3-7〔核心〕：更新样本数不变时，多生成回答会增加多少 RL 开销**

**题干（原文）**：保持一次更新使用 16 条等长样本。利用例题 3-4 中分别生成 32 条和 64 条回答时的周期总运算量，求每多生成一条回答所增加的生成与参考模型运算量，以及一次更新所需的固定运算量。保持更新样本数不变，据此预测生成 48 条回答时的周期总运算量。再用与生成模型结构相同的教师模型，对全部 48 条回答各执行一次前向计算，求新增的运算量。若将更新后的 BF16 权重分别发送给四个副本，每个副本独立接收一份，求总传输量。最后画出生成、反馈、更新与同步的依赖，指出哪些阶段可以在不同 batch 之间重叠。

**参考解答（笔记补充，非原文）**

1. 每多生成一条回答的边际运算量（生成 + 参考模型前向）：

$$\frac{3410.701 - 2181.559}{64 - 32} = \frac{1229.142}{32} \approx 38.4107\ \text{TFLOPs/条}$$

  也就是 $f_g + f_r \approx 38.4107$ TFLOPs。可交叉验算：生成部分 $(465.143 + 129.056)/32 = 18.5687$ TFLOPs/条，参考模型部分 $634.944/32 = 19.842$ TFLOPs/条，两者相加 $38.4107$ ✓。
2. 一次更新的固定运算量：$F_u = 2181.559 - 32 \times 38.4107 = 952.417 \approx 952.416$ TFLOPs ✓（与表中"策略更新，一次遍历"一致）。
3. 生成 48 条时的周期总运算量：

$$F_{\text{cycle}}(48) = 48 \times 38.4107 + 952.416 \approx 2796.13\ \text{TFLOPs}$$

4. 教师对全部 48 条各执行一次前向：教师与生成模型结构相同，故单条前向运算量与参考模型一致（19.842 TFLOPs/条），新增

$$48 \times 19.842 \approx 952.42\ \text{TFLOPs}$$

  （若沿用原文"参考模型一次前向 32 条 = 634.944 TFLOPs"的口径，等价于再叠一份与 32 条参考模型同规模的量并按 48/32 放大。）
5. 权重传输量：$V_{\text{sync}} = 4 \times 16.3815 = 65.526$ GB（每个副本独立接收一份完整权重）。
6. 依赖与可重叠性（笔记整理）：
   - **串行依赖**：生成 → 反馈（评分）→ 更新 → 同步。前一步的产物是后一步的输入，同一个 batch 内不能颠倒。
   - **可重叠**：**不同 batch 之间**，第 $k+1$ 批的生成（用的是第 $k$ 次更新后的权重，或按异步方案用更旧的权重）可以与第 $k$ 批的反馈/更新重叠；**同步一台副本的同时**可以继续用未更新的副本生成（代价是样本版本滞后）。这正是 3.5.2 里"异步方案允许部分阶段重叠，却要处理样本版本与滞后"的具体含义。
   - **不可重叠的反例**：同一批样本的"更新"不能在"生成"之前——更新要等这批样本；"同步"不能在"更新"之前——没有新权重可发。

**辅导讲解**

- 例题 3-4 的表把 RL 的"漏斗"画得很清楚（笔记整理）：
  - 32 条回答**全部**要走 rollout prefill（465.143）和 255 步 decode（129.056），还要**全部**过一遍参考模型（634.944）；
  - 但只有 **16 条**进入策略更新（952.416）。
  - 合计 2,181.559 TFLOPs，其中**只有 43.7%（952.416/2181.559）直接作用于被保留的样本**，其余都花在"生成了但不一定用"的回答上。
- **保留比例下降的放大效应**：从 1/2 降到 1/4，生成数从 32 涨到 64，总运算量 +56.3%。这里的 56.3% 值得算一下来源（笔记复算）：总运算量 = $n(f_g+f_r) + F_u$，$n$ 从 32 到 64 时，可变部分从 1229.142 翻倍到 2458.284（$+1229.142$），固定部分 952.416 不变。所以比例 $= 1229.142/2181.559 = 56.34\%$ ✓。**固定部分 $F_u$ 越大、可变部分占比越小，这个"放松筛选税"就越轻**——这也意味着：当模型很大（更新很贵）时，筛选变严带来的相对开销反而没那么可怕。
- **为什么参考模型要跑全部回答，而不是只跑保留的 16 条？** 因为参考模型的作用是"约束策略偏离程度"，而策略更新的损失里需要对每条参与优化的样本计算 KL/比值项。原文写得很明确："参考模型对全部 32 份回答各执行一次前向"。这是很多人第一次算 RL 预算时最容易漏的一项——**它和 rollout 一样是 32 份的工作量，而不是 16 份。**
- **教师评分"设为零次"是一个刻意的简化**：原文那句"教师评分，设为零次"说明这个算例先把教师前向排除，让读者看清其余四项。练习 3-7 第 4 问正是把这个变量加回来（48 条 × 19.842 ≈ 952 TFLOPs）。加回来之后，教师前向的成本与策略更新本身相当——**这解释了为什么"多教师 OPD"是昂贵的**（3.5.1 提到 V4-Flash 用了多教师）。
- **权重同步的传输量为什么值得单列**：$r M_W$ 是**一次全量传输**，不是增量。4 个副本、8B BF16 就是 65.526 GB；如果每几十步就同步一次，网络很快就成为瓶颈。原文给的两条缓解方向是：**优化器状态不必发送**（生成副本只要前向权重）、**广播/分层分发**（多个副本共用部分路径）。这两个都是"减少传输量"而不是"提高带宽"的思路，工程上更划算。
- **"既要看运算量，也要看计算方式"这句是本节的方法论落脚点**（笔记整理）：同样一 TFLOP，在不同阶段花的时间不同。
  - **生成阶段**：小 batch、逐 token、受带宽限制（回到 3.1.1）。所以它的"TFLOPs/s"很低。
  - **评分/训练阶段**：teacher forcing 让 1279 个已知 token 一起算，是大矩阵、受算力限制。所以它的"TFLOPs/s"接近峰值。
  - **工具验证**：不消耗 FLOPs，消耗 CPU 与排队时间。
  因此，**不能把 2,181.559 TFLOPs 直接除以 989.4 TFLOP/s 来估时间**——那会严重低估生成阶段、高估更新阶段。正确的做法是分阶段用各自的效率，再按依赖顺序相加。
- **复算提示**：$16 \times 1279 = 20{,}464$ ✓；$16 \times 256 = 4096$ ✓；$2181.559/16 = 136.347$ ✓；$3410.701/16 = 213.169$ ✓；$16.381 \times 4 = 65.524$（原文 65.526，差异来自权重体积取更多有效位，如 $16.3815$ GB × 4）。

**易混点**

- **生成数 $n$ 与保留数 16**：$n$ 是 $F_{\text{cycle}}$ 的自变量（决定可变部分），16 是固定的更新 batch（决定 $F_u$）。保留比例 $a$ 只通过 $n \approx 16/a$ 进入公式。
- **参考模型前向与教师前向**：两者都是"对已生成的回答再过一遍模型"，但**参考模型用同一份固定权重约束偏离**，**教师是另一个模型（或另一个专家）提供学习目标**。练习 3-7 里两者恰好同结构、同成本，但语义不同。
- **$f_g + f_r$ 与 $F_u$**：前者是"每条回答"的可变成本（乘 $n$），后者是"每次更新"的固定成本（与 $n$ 无关）。判断"筛选变严划不划算"，就是看可变部分与固定部分的比值。
- **运算量与耗时**：本节的表是**运算量**（TFLOPs），不是时间。要转成时间必须知道每个阶段的执行效率（精度受限于计算方式），原文明确提醒"仍需分别记录各阶段的矩阵形状"。

**一句话记住**

> RL 周期运算量 $F_{\text{cycle}}(n) = n(f_g+f_r) + F_u$：生成 32 条时共 2,181.559 TFLOPs，其中只有 952.416 直接作用于保留的 16 条；保留比例减半到 1/4 就要多生成一倍，总量涨 56.3%；更新完还要按 $rM_W$ 把权重发给每个副本（4 个副本 = 65.526 GB）。

## 3.6 从负载需求到训练与服务预算

### 3.6.1 Scaling Law：模型规模与数据量的关系

**原文要点**

- **问题的提出**：单次更新的计算可以逐项求出，**训练多少参数、使用多少数据则需要另行决定**。设总训练计算预算为 $C$，参数量为 $N$，训练 token 数为 $D$，主要计算近似满足 $C = 6ND$。**增加 $N$ 就必须减少 $D$。** 要在两者之间作选择，就要知道**参数与数据分别如何影响质量**。**Scaling Law（规模规律）用实验拟合模型规模、训练数据和损失之间的关系。**
- **拟合模型（幂律）**：下面采用幂律模型，其中参数与数据两项都为正，训练配置和损失评估方式固定：

$$L(N, D) = E + \frac{A}{N^{\alpha}} + \frac{B}{D^{\beta}}$$

  $L$ 是**验证损失**，$E$ 是**渐近损失**，$A/N^{\alpha}$ 描述**参数规模不足**的影响，$B/D^{\beta}$ 描述**数据量不足**的影响。这里的 $A, B, \alpha, \beta$ 都是**拟合系数**。**单独增加参数或数据会降低对应项；固定计算预算时，两项却向相反方向变化。**
- **求最优**：用 $D = C/(6N)$ 消去数据量，再对 $N$ 求导，最优点满足

$$\alpha A N^{-\alpha-1} = \beta B \left(\frac{6}{C}\right)^{\beta} N^{\beta-1}$$

  原文对两侧含义的解释：**左侧是增加参数带来的损失下降，右侧是减少数据造成的损失上升；两者相等时，再小幅改变参数量已经没有净收益。** 整理得到

$$N_{\text{opt}} = \left(\frac{\alpha A}{\beta B}\right)^{1/(\alpha+\beta)} \left(\frac{C}{6}\right)^{\beta/(\alpha+\beta)}$$

- **最优解的适用边界**：由此得到的 $N_{\text{opt}}$ 是**连续取值的结果**，实际设计时可在它附近选择合适的层数和宽度。**这一最优解只在固定训练计算预算下最小化验证损失，不含部署后的推理成本，也不考虑数据供给是否充足。** 模型上线后还要服务大量请求时，**最优选择可能偏向更小、训练更充分的配置**；3.6.2 节将用公开模型的训练记录，检查实际投入与这里的预测相差多少。
- **不同研究的分配指数并不一致**：**Kaplan 等人的早期研究给出约 $N \propto C^{0.73},\ D \propto C^{0.27}$ 的分配关系**；**Chinchilla 研究用不同的实验和拟合得出：模型规模与数据量应随预算更接近等比例增长。** 原文的评价：**前一种分配更快增加模型参数，后一种把更多新增预算分给训练数据；曲线及其拟合指数因此直接改变参数与数据的选择。**

**例题 3-5：训练规模拟合关系能否预测更大模型的损失？**（从公开训练记录中选定六个较小模型的观测值用于拟合，另将两个较大模型的观测留出。先选定拟合方法，再比较留出模型的预测值与实际观测值。）

**解（原文给出）**：**datablations** 是研究模型与数据规模变化的公开实验记录，**C4** 是这些记录使用的一套文本语料。以其中八个模型为例，**用六个较小模型拟合曲线，将 $N \ge 2 \times 10^9$ 的两个模型留作检验**。两个大模型的**实际损失分别约为 2.574、2.337，拟合曲线预测为 2.583、2.363**。**预测略高于实际值，均方根误差约为 0.0193 nats/token。**
- **单位与含义**：**nat 是使用自然对数时的信息量单位，nats/token 表示每个 token 的平均损失。** 图 3-27 用不同标记区分拟合点与检验点。

- **从损失到任务**：预测出验证损失之后，还要判断模型能否完成实际任务。**Llama 3 报告先根据训练计算量预测损失，再建立损失与任务表现的关系。** 这样，**代码、检索和工具使用等任务的质量要求，才能进一步转化为训练规模与计算量的选择。**
- **训练本身也有波动**：拟合和预测都建立在**单次训练**的观测上，而训练本身也有波动。**同样的数据与模型规模，改变随机初始化就可能得到不同的学习曲线；较大模型在训练尚未充分时，也未必优于较小模型。** **使用多个随机种子重复训练，可以区分规模变化带来的趋势与单次训练的偶然波动。**
- **长期服务会改变最优**：长期服务会把每次调用的成本累积到训练预算之上。**较小模型可以靠更长的训练达到目标质量：前期投入更多，之后每次调用读取的权重更少、执行的运算也更少。** **Beyond Chinchilla-Optimal** 将这种推理需求纳入分析，**47 个模型覆盖 150M–6B；其中 150M 模型的训练量最高达到每个参数 10,000 个 token，较大模型最高达到 1,000 个。** **训练预算与服务次数共同决定较小模型何时能收回额外训练的成本。**
- **固定目标损失下的训练投入与累计服务成本（原文算例）**：

- **分配指数的意义**：回到参数与数据的分配，还可以直接预测预算增加后的结果。由最优解表达式可得

$$N_{\text{opt}} \propto C^{\beta/(\alpha+\beta)},\qquad D_{\text{opt}} \propto C^{\alpha/(\alpha+\beta)}$$

  **若两个指数相等，预算增至四倍，参数和训练数据各增至两倍。** 原文的总结：**拟合指数的意义由此变得具体：指数决定新增计算应如何分给模型与数据。**

**练习 3-8〔延伸〕：如何在模型参数与训练数据之间分配计算预算**

**题干（原文）**：采用损失模型 $L = E + A/N^{\alpha} + B/D^{\beta}$ 和计算预算约束 $C = 6ND$，推导使损失最小的参数量 $N$ 与数据量 $D$ 分别如何随计算预算 $C$ 增长。取 $\alpha = \beta$，当计算预算分别增至原来的四倍和九倍时，最优参数量和数据量应各增至原来的多少倍？再使用例题 3-5 的八个 C4 观测点，用其中六个拟合、另外两个检验，计算两个检验点的预测误差，并解释为什么拟合点上的误差不能替代留出检验的误差。

**参考解答（笔记补充，非原文）**

1. 推导（与原书正文同路，这里写全步骤）：
   - 约束代入：$D = C/(6N)$，于是

$$L(N) = E + \frac{A}{N^{\alpha}} + B\left(\frac{6N}{C}\right)^{\beta}$$

   - 对 $N$ 求导并令其为零：

$$\frac{\mathrm{d}L}{\mathrm{d}N} = -\frac{\alpha A}{N^{\alpha+1}} + \frac{6^{\beta}\beta B}{C^{\beta}}N^{\beta-1} = 0$$

     即 $\alpha A N^{-\alpha-1} = \beta B (6/C)^{\beta} N^{\beta-1}$（与原文一致）。
   - 解出

$$N_{\text{opt}} = \left(\frac{\alpha A}{\beta B}\right)^{1/(\alpha+\beta)}\left(\frac{C}{6}\right)^{\beta/(\alpha+\beta)},\qquad D_{\text{opt}} = \frac{C}{6N_{\text{opt}}} \propto C^{\alpha/(\alpha+\beta)}$$

2. 指数关系：$N_{\text{opt}} \propto C^{\beta/(\alpha+\beta)}$，$D_{\text{opt}} \propto C^{\alpha/(\alpha+\beta)}$。
   - 取 $\alpha = \beta$，则两个指数都是 $1/2$：$N \propto C^{1/2}$、$D \propto C^{1/2}$。
   - 预算 $\times 4$：$N$ 和 $D$ 各 $\times \sqrt{4} = 2$ 倍。
   - 预算 $\times 9$：$N$ 和 $D$ 各 $\times \sqrt{9} = 3$ 倍。
3. 两个检验点的预测误差：预测减观测分别为 $2.583 - 2.574 = 0.009$ 与 $2.363 - 2.337 = 0.026$（nats/token）。均方根误差

$$\text{RMSE} = \sqrt{\frac{0.009^2 + 0.026^2}{2}} = \sqrt{\frac{0.000081 + 0.000676}{2}} \approx 0.01946$$

   原文给出的是"约 0.0193 nats/token"；笔记按四舍五入到三位小数的两个误差复算得约 0.0195，差异在末位（约 $2\times10^{-4}$），应来自原文用更高精度的中间值参与计算。
4. 为什么拟合点误差不能替代留出检验：
   - 拟合的目标函数就是"让曲线尽量贴近这六个点"，**拟合点上的误差是训练目标本身，必然偏小**（增加拟合参数或换更灵活的拟合形式，几乎总能让它更小）。
   - 留出点**完全没有参与求系数**，它衡量的是**对未见过的规模的外推能力**。原文的实验现象正好说明这一点：两个留出点的误差（0.009、0.026）一大一小，且**预测都略高于实际**，这种系统性偏差在拟合点上通常看不出来。
   - 所以报告 Scaling Law 时必须说明"哪些点参与拟合、哪些点留出检验"，否则数字不可比。

**辅导讲解**

- **Scaling Law 的推导其实就是一个"约束极值"问题**（笔记整理）：预算固定 $\Rightarrow$ 多给参数就少给数据 $\Rightarrow$ 损失函数里一项下降、另一项上升 $\Rightarrow$ 在导数为零处取最小。这就是原文那两句"左侧是增加参数带来的损失下降，右侧是减少数据造成的损失上升"的全部数学内容。理解了这个结构，也就理解了为什么**最优解依赖拟合出的指数**——指数决定了两项的"弹性"，也就决定了预算该往哪边倾斜。
- 复算一下那几个关键数字（笔记补充）：
  - 每 GPU 秒算力：$989.4 \times 40\% = 395.76$ TFLOP/s ✓（原文"折算后每 GPU 秒完成 395.76 TFLOP"）。
  - 单次请求运算量：$P=512, G=128 \Rightarrow 2N[512 + 127] = 1278N$。0.5B 时 $1278 \times 5\times10^8 = 6.39\times10^{11}$ FLOPs $= 0.639$ TFLOPs，除以 395.76 TFLOP/s $= 1.615\times10^{-3}$ GPU·s；0.1B 时 $= 3.23\times10^{-4}$ GPU·s；两者之差 $1.29\times10^{-3} \approx 0.00129$ GPU 秒 ✓，与原文一致。
  - 训练成本：$6ND$ 对 0.1B、$D = 298.6\times10^9$ 得 $6\times10^8\times2.986\times10^{11} = 1.792\times10^{20}$ FLOPs，除以 $395.76\times10^{12}$ 得 $4.53\times10^5$ GPU·s $= 125.8$ GPU 小时 ✓（原文 125.7）。
  - 交点：$73.5$ GPU 小时 $\times 3600 = 264{,}600$ GPU·s，除以 $0.00129$ GPU·s/次 $\approx 2.05\times10^8$ 次 $= 2.05$ 亿次 ✓（原文约 2.048 亿次）。
  这一串数字全都自洽，说明原文这个算例是实打实算出来的，读者可以放心当作复算练习。
- **"交点与 MFU 无关"这句话值得多想一秒**：因为训练成本和服务成本**都**乘以同一个 $1/\text{MFU}$ 系数，所以令两者相等时这个系数被约掉了。这是一个很好的方法论示例：**当你只关心"哪边更划算"时，共有的比例因子可以忽略；但要回答"总共多少小时/多少钱"，就必须知道 MFU。**
- **Kaplan 与 Chinchilla 的差别为什么重要**（笔记整理）：$N \propto C^{0.73}$ 意味着预算翻倍时参数增加约 1.66 倍、数据只增加约 1.21 倍；而等比例分配（指数各 0.5）意味着预算翻倍时参数与数据各增加约 1.41 倍。**前者的处方是"把新算力主要给参数"，后者是"参数和数据一起长"。** 在同样的算力下，这两种处方会给出完全不同的模型尺寸，也直接影响推理成本（更大模型 = 更贵的每次调用）。这就是为什么 3.6.1 结尾要强调"最优解不含部署后的推理成本"。
- **Beyond Chinchilla-Optimal 的那组数字怎么读**：47 个模型覆盖 150M–6B，其中**最小的 150M 模型训练量高达每参数 10,000 个 token，而较大的模型最高只有 1,000 个**。也就是说，**越小的模型被训练得越"充分"**。这正与"服务量大时选择更小、训练更充分的模型"这一结论相呼应：小模型每次调用省下的算力，可以支撑它多训一个数量级的 token。原文给的 0.1B vs 0.5B 算例就是这个逻辑的具体版本（2.048 亿次是回本点）。
- **任务的"转换链"**：训练计算量 $\to$ 验证损失（Scaling Law）$\to$ 下游任务表现（Llama 3 的做法）$\to$ 质量门槛 $\to$ 训练规模。这条链条意味着：**如果你只知道损失，还不能决定模型能不能用**——必须建立"损失—任务"的映射。原文提到"代码、检索和工具使用等任务的质量要求"能据此转化为训练规模，正是指这条链。
- **工程上的四条**：
  1. 报 Scaling Law 必须同时报**拟合点、留出点、拟合形式**（幂律还是别的）和**损失口径**（nats/token？哪个语料？），否则不同报告的数字不可比。
  2. 拿拟合曲线外推时要标注（原文就用虚线标出 0.1B 和 2.81B 这两条超范围曲线）。**外推范围之外的预测不能当结论。**
  3. 训练有随机性：**多 seed 重复**才能区分趋势与噪声。这一条在做"小模型先行"的实验设计时尤其重要。
  4. 做模型选型时，把"训练一次要多少 GPU 小时"和"每个请求要多少 GPU 秒"放到同一条成本曲线上看交点（图 3-29 的做法），而不是只看其中一头。

**易混点**

- **$E$（渐近损失）与 $L$（验证损失）**：$L$ 是当前配置下的损失，$E$ 是这个模型族在数据、参数都趋向无穷时损失的极限（不可达下界）。所以 $L - E$ 才是"还差多少"。
- **$\alpha, \beta$（拟合指数）与 $A, B$（拟合系数）**：指数决定**尺度的弹性**（预算乘 $k$ 倍时最优规模怎么变），系数决定**绝对量级**（在给定规模下损失有多高）。例题 3-8 问的"预算增至 4 倍/9 倍"只依赖指数，与 $A, B$ 无关。
- **计算最优（compute-optimal）与全生命周期最优**：前者在固定训练预算下最小化验证损失；后者把推理成本也算进去。原文明确说实际投入"超出前者并不表示前者算错了"——只是目标函数不同。
- **nats 与 bits**：nat 用自然对数，bit 用底 2 的对数；$1\ \text{nat} = 1/\ln 2 \approx 1.4427$ bit。比较不同报告的损失数字前先看单位。

**一句话记住**

> $L = E + A/N^{\alpha} + B/D^{\beta}$，在 $C=6ND$ 下求导得 $N_{\text{opt}} \propto C^{\beta/(\alpha+\beta)}$、$D_{\text{opt}} \propto C^{\alpha/(\alpha+\beta)}$；$\alpha=\beta$ 时预算翻 4 倍两者各翻 2 倍；而这个"计算最优"不含推理成本——把服务成本加进来，答案往往偏向更小、训练更充分的模型。

  - **DeepSeek V4-Flash 的主干专家约 45.4495 GFLOPs/token，按 32T 累计约 $1.45438 \times 10^{24}$ FLOPs**；
  - **DeepSeek V4-Pro 约 169.2465 GFLOPs/token，按 33T 累计约 $5.58513 \times 10^{24}$ FLOPs**。
- **整步训练计算的组成与一个易错点**：**整步训练计算由这些专家矩阵与注意力、路由、MTP、优化器和重计算共同组成。报告的损失权重也不是执行比例，例如 MTP 权重为 0.3，不表示只执行 30% 的辅助计算。**

> 图 3-30（原文插图）：相近参数规模的模型投入不同数量的训练 token。横轴按模型排列，纵轴为"报告训练 token 数／参数数"（0–5000）。柱值依次为：Llama 1 6.7B = 149.254、Llama 2 7B = 285.714、Llama 3.1 8B = 1,875.000、Qwen2.5 7B = 2,571.429、Qwen3 8B = 4,500.000。图注说明柱值为报告训练数据量除以参数量，Qwen 采用模型系列披露的数据预算。

- **训练投入也常用 GPU 小时计量**：若持续使用 $n_{\text{GPU}}$ 张卡，总 GPU 小时为 $H_{\text{GPU}}$，实际历时为

$$T_{\text{calendar}} = \frac{H_{\text{GPU}}}{n_{\text{GPU}}}$$

- **Llama 1 65B 的算例**：**训练消耗 1,022,362 A100 GPU 小时**。**持续使用 2048 张卡，对应约 499.2 小时，即 20.80 天；在相同加速器效率下只使用一半卡数，则需要约 41.60 天。** 原文的总结：**GPU 小时体现总投入，卡数决定完成这些工作需要多少实际时间。**
- **DeepSeek-V3 的算例**：报告**预训练 2.664M H800 GPU 小时；14.8T token 只对应预训练阶段；按持续使用 2048 卡计算，约需 54.20 天**。**后续的上下文扩展与后训练另有用量，但各阶段统计范围不同，不能一并除以预训练 token 数。**
- **Llama 3.1 405B 的算例**：用 GPU 小时换算实际历时，要除以同期使用的卡数。对 Llama 3.1 405B，取公开的 **30.84M H100 GPU 小时**，并假设这项工作全部使用最大规模 **16,384 卡**，实际历时约为 $30.84 \times 10^{6}/(16384 \times 24) \approx 78.43$ 天。**某个阶段使用的卡数更少时，相同 GPU 小时需要更长的实际时间；训练资源的分配时序因此决定训练完成时间。**
- **跨设备折算**：上述用量来自三种加速器，**GPU 小时不能直接跨设备比较投入规模**。按 BF16 稠密峰值算力折算：**A100 80GB 为 312 TFLOP/s，H100 与 H800 同为 989.4 TFLOP/s（H800 只是互联带宽更低）**，一个 H100 或 H800 GPU 小时约相当于 $989.4/312 \approx 3.17$ 个 A100 GPU 小时。

> 图 3-31（原文插图）：Llama 与 DeepSeek-V3 的公开训练用量统一折算为 A100 80GB 等效 GPU 小时。横轴为 A100 等效训练用量（百万 GPU 小时，0.1–100，对数尺度）。柱值依次为：Llama 1 6.7B（A100）0.08、Llama 1 65B（A100）1.02、Llama 2 7B（A100）0.18、Llama 2 70B（A100）1.72、Llama 3.1 8B（H100）4.63、Llama 3.1 70B（H100）22.20、Llama 3.1 405B（H100）97.80、DeepSeek-V3 预训练（H800）8.45。图例区分"原设备 A100（实测）"、"原设备 H100（×3.17）"、"原设备 H800（×3.17）"。图注强调：Llama 1／Llama 2 为 A100 实测小时；H100 与 H800 小时按 BF16 稠密峰值之比 $989.4/312 \approx 3.17$ 折算，DeepSeek-V3 只计预训练阶段；折算假定各设备实际利用率相近，**不表示效率或成本差异**。
- **后训练的投入**：以上几组用量都**属于预训练**，后训练的投入同样可以用 GPU 小时比较。**Qwen3 技术报告的表 21 把同一个 8B 模型的 RL 与 OPD 两条后训练路线并列，投入分别为 17,920 与 1,800 GPU 小时。** **两条路线可以二选一，各自包含生成、反馈与学习工作。** 把 GPU 小时对应到具体阶段和加速器，再结合各阶段的执行过程，就能解释训练投入主要消耗在哪里。

**练习 3-9〔延伸〕：增加训练数据或专家数量会改变哪些资源需求**

**题干（原文）**：根据 Llama／Qwen 表重算 $D/N$ 与 $6ND$。若参数量保持不变、训练数据量增至四倍，预测训练计算与上线后的纯权重容量分别如何变化。对 MoE，说明总专家数加倍、每 token 选中数不变时，参数容量与专家训练计算能否都按两倍估算。

**参考解答（笔记补充，非原文）**

1. 重算 $D/N$ 与 $6ND$（用表中的参数量与 token 数）：
   - Llama 1 6.7B：$D/N = 1\times10^{12}/(6.7\times10^9) = 149.254$；$6ND = 6 \times 6.7\times10^9 \times 1\times10^{12} = 4.02\times10^{22}$ FLOPs。
   - Llama 2 约 7B：$2\times10^{12}/(7\times10^9) = 285.714$；$6ND = 8.40\times10^{22}$ FLOPs。
   - Llama 3.1 约 8B：$15\times10^{12}/(8\times10^9) = 1875.0$；$6ND = 7.20\times10^{23}$ FLOPs。
   - Qwen2.5 约 7B：$18\times10^{12}/(7\times10^9) = 2571.429$；$6ND = 7.56\times10^{23}$ FLOPs。
   - Qwen3 约 8B：$36\times10^{12}/(8\times10^9) = 4500.0$；$6ND = 1.728\times10^{24}$ FLOPs。
2. 参数量不变、训练数据量增至四倍：
   - **训练计算 $6ND$ 增至四倍**（对 $D$ 线性）。
   - **上线后的纯权重容量不变**：它只由参数量 $N$ 决定（每参数 2 字节 BF16），与训练数据量无关。
   - 这正是"更充分训练的小模型"策略的代价结构：**多花一次性训练算力，换不变（甚至更小）的部署容量与读取量**。
3. MoE 在"总专家数加倍、每 token 选中数不变"时：
   - **参数容量约按两倍估算**（总权重翻倍）。
   - **专家训练计算一般不能按两倍估算**：每 token 只经过被选中的那些专家，选中数不变则**每个 token 的专家计算量不变**；若总 token 数也不变，专家部分的训练计算量基本不变（还要注意路由、共享专家等旁路的开销）。
   - 所以"参数容量"与"训练计算"在 MoE 上是两个维度：前者随总专家数线性增长，后者主要随**每 token 激活的参数量**增长。

**辅导讲解**

- **这张表最值得记的不是五个数字，而是那个趋势**：**参数规模差不多（7–8B），训练数据量从 1T 涨到 36T，$D/N$ 从 149 涨到 4,500——30 倍**。它说明"7B 模型"这个标签在 2023 年和 2025 年意味着完全不同的东西：同样大的一坨权重，一个只读了 1 万亿 token，一个读了 36 万亿。
- **为什么 $D/N$ 是个好指标**（笔记整理）：$6ND = 6 \cdot D/N \cdot N^2$。也就是说，在参数量相近的模型之间，**训练算力基本正比于 $D/N$**；而在 $D/N$ 相近的模型之间，**训练算力正比于 $N^2$**。所以 $D/N$ 是"每个参数被喂了多少数据"的密度指标，也是横向比较"训练投入强度"的最直观刻度。图 3-30 用它作纵轴正是这个道理。
- **MoE 的两套参数是这一节最容易混的地方**（笔记整理）：
  - **总参数量**（671B、284B、1.6T）：决定**权重存储容量**和**权重读取量**（每步 decode 要把用到的专家权重读进来）。它是"仓库有多大"。
  - **激活参数量**（37B、13B、49B）：决定**每 token 的计算量**（FLOPs）。它是"每次取货取多少"。
  - 所以"DeepSeek V4-Flash 是 284B 模型"和"它每 token 只激活约 13B"这两句话并不矛盾，而是描述了两个不同的资源。原文那句"总权重影响容量，激活参数只提供计算量的粗略估计"就是这两者的分工。
- 复算 $C_{\text{expert/token}}$ 的系数 18（笔记拆解）：公式 $18\,n_L h f (k_{\text{routed}} + k_{\text{shared}})$ 里的 $18 = 3 \times 2 \times 3$：
  - **3**：每个专家有三个投影（如 gate／up／down 三个权重矩阵）；
  - **2**：一次乘加计 2 FLOPs；
  - **3**：前反向合计约为前向的三倍（3.4.1 的结论）。
  这也说明这个公式算的是**训练**计算量。若只算推理前向，系数应改为 $3 \times 2 = 6$。
- **GPU 小时的三个用处**（笔记整理）：
  1. **比较投入规模**：必须先折算到同一设备（$3.17$ 这个系数就是干这个的）。原文特意强调"不表示效率或成本差异"——它只统一了算力口径。
  2. **估算日历时间**：$T_{\text{calendar}} = H_{\text{GPU}}/n_{\text{GPU}}$。这里是**线性**关系：卡数减半，时间翻倍。
  3. **核对统计口径**：原文特别提醒 DeepSeek-V3 的 14.8T token"只对应预训练阶段"，**不能把总的 GPU 小时除以预训练 token 数**，因为后训练和上下文扩展的用量也在总数里、但不在这 14.8T 里。这是读模型报告时最常见的口径错误。
- 复算（笔记补充）：$1{,}022{,}362/2048 = 499.20$ h $= 20.80$ 天 ✓；$1{,}022{,}362/1024 = 998.40$ h $= 41.60$ 天 ✓；$2.664\times10^6/2048 = 1300.78$ h $= 54.20$ 天 ✓；$30.84\times10^6/(16384\times24) = 78.43$ 天 ✓；$45.4495 \times 32 \times 10^{12} = 1.45438\times10^{24}$ ✓；$169.2465 \times 33 \times 10^{12} = 5.58513\times10^{24}$ ✓。全部与原文一致。
- **"MTP 权重 0.3 不等于只执行 30%"** 这句话值得单独记：报告里的权重系数是**损失函数里的加权**（训练时多个预测头按权重组合损失），不是"只跑 30% 的层"或"只算 30% 的计算量"。做预算时把损失权重当成执行比例，会把辅助头的计算量漏掉一大块。
- **Qwen3 后训练的两条路线（17,920 与 1,800 GPU 小时）** 给出了一个重要对比：**RL 比 OPD 贵一个数量级**（约 10 倍）。这与 3.5 节的分析一致：RL 要为"生成—反馈—更新—同步"整条环付费，而 OPD 主要是教师前向 + 学生训练。当然，两者**可以二选一**，说明它们追求的效果有重叠，选哪条是效果与成本的权衡。

**易混点**

- **总参数量与激活参数量（MoE）**：前者定容量与读取量，后者定每 token 计算量。混用会同时错估显存和算力。
- **训练计算与部署容量**：$D$ 只影响前者，$N$ 同时影响两者。所以"多训数据"和"换大模型"这两种提升手段的资源后果完全不同。
- **GPU 小时与日历时间**：前者是总投入（与卡数无关），后者 = 前者 ÷ 卡数（线性依赖同步使用的卡数）。
- **A100 等效小时与实际小时**：折算系数（H100/H800 ×3.17）只统一算力口径，**不代表效率或成本差异**。
- **$D/N$（每参数 token 数）与"每参数 20 token"的 Chinchilla 基准**：前者是实际观测，后者是理论的计算最优基准；实际值高出一两个数量级并不表示理论错了（目标函数不同）。

**一句话记住**

> 相近的 7–8B 模型，$D/N$ 从约 149（Llama 1 6.7B）涨到约 4,500（Qwen3 8B）；$T_{\text{calendar}} = H_{\text{GPU}}/n_{\text{GPU}}$ 把总投入换成日历时间（Llama 1 65B 的 1,022,362 A100 小时 ÷ 2048 卡 = 20.80 天）；跨设备比较要先按 BF16 峰值折算（H100/H800 ≈ 3.17 个 A100）。

### 3.6.3 满足质量要求的全生命周期成本

**原文要点**

- **把三部分合起来**：现在把第 2 章与本章的分析合在一起。**模型结构决定每次调用所需的存储容量、运算量和读取量，负载决定调用次数与等待，训练决定上线前的投入。** 设模型 $m$ 的前期成本为 $C_0(m)$，未来有 $Q$ 个任务，第 $j$ 类占比为 $w_j$、完成一个任务的平均成本为 $c_j(m)$，则

$$C_{\text{life}}(m) = C_0(m) + Q\sum_j w_j c_j(m)$$

  其中 $C_0(m)$ 是**前期（训练等）成本**（单位：成本，如 GPU 小时或美元），$Q$ 是**未来任务总数**（个），$w_j$ 是**第 $j$ 类任务的占比**（$\sum_j w_j = 1$），$c_j(m)$ 是**完成一个第 $j$ 类任务的平均成本**（成本/任务）。
- **比较之前要先对齐条件**：**比较之前，各模型都要满足相同质量、时限与完成条件。若任务成功率不同，$c_j$ 中还需包含失败和重试；价格变化、模型寿命、维护与贴现等假设也应在给出预算时说明。专用硬件若需要较长部署周期，模型版本能使用多久也会成为这一选择的条件。**
- **成本交点**：考虑都满足任务质量和时限的两个模型。若**较小模型需要额外训练成本 $\Delta C_0$，但每个成功任务能节省 $\Delta c > 0$**，累计成本相等的调用量为

$$Q^{*} = \frac{\Delta C_0}{\Delta c}$$

- **数值算例**：**若较小模型额外训练 10 万 H100 GPU 小时，即 $3.6 \times 10^8$ GPU 秒，每个任务节省 0.72 H100 GPU 秒，则 $Q^{*} = 3.6\times10^8/0.72 = 5\times10^8$，即五亿次任务。** **预期需求低于此数，额外训练成本尚未收回；高于此数，较小模型累计节省更多。** 原文的结论：**容量、延迟、质量和调用量共同决定选择，单看模型大小或 token 单价无法完成这一判断。**
- **后续章节如何使用本章信息**：后续章节将使用本章整理出的**三类负载信息**。下表列出各类负载需要记录的内容，以及这些信息将用于哪些系统设计问题（表格按原文语义还原）：

| 负载 | 必须保留的字段 | 后续使用 |
| --- | --- | --- |
| Chat／Agent | 任务检查、模型与版本、每轮输入／命中／输出、到达、工具依赖、分支与复用间隔 | 第 8 章安排批处理与状态；第 9 章交接与路由；第 11 章管理工具环境 |
| 视觉／实时 | 原图字节、E/P/D、EC/KV、帧或块到达、首响应／连续播放要求、打断后不再需要的计算 | 第 8、9 章安排编码和交接；第 12 章加入链路与执行位置 |
| 训练／RL | 数据与质量、长度和标签、micro-batch／更新、生成样本数／保留样本数、奖励计算与模型调用、权重版本、完成期限 | 第 4–7 章分析算力、存储与通信需求；第 10 章安排学习；第 11 章配置环境与资源池 |

- **三类例子的共同结论**：**这三类例子都说明，描述负载需要记录具体的执行过程。** 两分钟请求中，各时段的输入输出比例决定积压何时出现；代码 Agent 中，工具依赖决定等待时间，以及状态需要保存多久；RL 中，筛选前后的样本数决定生成与更新阶段各处理多少数据。**掌握这些信息，才能为各阶段安排资源。**
- **对下一章的过渡**：**第 4 章将结合芯片的算力、存储容量与带宽，分析这些负载如何在加速器上执行。** 本章算出的矩阵尺寸、状态大小和访问次数，将用于判断计算需要多久、数据能否容纳，以及读写能否及时完成。**各阶段的依赖关系则决定哪些工作可以重叠，哪些必须等待。**

**练习 3-10〔延伸〕：训练完成时间与累计服务成本**

**题干（原文）**：假设完成训练共需 1,022,362 A100 GPU 小时，即 Llama 1 65B 的公开用量。分别持续使用 2048 张和 1024 张 A100，并假设加速器数量改变后总 GPU 小时不变，求两种配置下完成训练所需的天数。再比较两个满足相同质量与时限的模型：小模型多投入 10 万 H100 GPU 小时训练，每个成功任务节省 0.72 H100 GPU 秒。预计完成两亿项和十亿项成功任务时，分别应选择哪个模型？计算总成本差，并说明若实际任务量发生变化，选择会在何处反转。

**参考解答（笔记补充，非原文）**

1. 训练历时（$T_{\text{calendar}} = H_{\text{GPU}}/n_{\text{GPU}}$）：
   - 2048 张：$1{,}022{,}362/2048 = 499.20$ 小时 $= 499.20/24 \approx 20.80$ 天。
   - 1024 张：$1{,}022{,}362/1024 = 998.40$ 小时 $\approx 41.60$ 天。
2. 两个模型的比较（小模型额外训练 $\Delta C_0 = 10$ 万 H100 GPU 小时 $= 10^5 \times 3600 = 3.6\times10^8$ GPU 秒；每成功任务节省 $\Delta c = 0.72$ GPU 秒）：
   - 两亿项（$Q = 2\times10^8$）：累计节省 $= 2\times10^8 \times 0.72 = 1.44\times10^8$ GPU 秒 $= 40{,}000$ GPU 小时 $< 100{,}000$ GPU 小时，**额外训练成本尚未收回，应选大模型（不做这笔额外训练）**；小模型多付 $100{,}000 - 40{,}000 = 60{,}000$ GPU 小时。
   - 十亿项（$Q = 1\times10^9$）：累计节省 $= 1\times10^9 \times 0.72 = 7.2\times10^8$ GPU 秒 $= 200{,}000$ GPU 小时 $> 100{,}000$ GPU 小时，**应选小模型**；相对大模型净省 $200{,}000 - 100{,}000 = 100{,}000$ GPU 小时。
   - 反转点：$Q^{*} = \Delta C_0/\Delta c = 3.6\times10^8/0.72 = 5\times10^8 = $ **五亿项成功任务**。低于它选大模型，高于它选小模型。

**辅导讲解**

- $C_{\text{life}}(m) = C_0(m) + Q\sum_j w_j c_j(m)$ 是本章的"总账公式"。它把前面所有小节的成果串了起来：
  - $C_0(m)$ 来自 **3.4、3.5**（训练与 RL 的算力与状态）和 **3.6.2**（GPU 小时）；
  - $c_j(m)$ 来自 **3.1、3.2、3.3**（每次调用的算力、排队、状态、工具等待）以及 **3.2.2**（成功任务成本）；
  - $Q$ 与 $w_j$ 来自**负载预测**（3.1.3 的请求分布）。
  **只有这三块都填上，才能回答"该用哪个模型"** —— 这正是原文"单看模型大小或 token 单价无法完成这一判断"的意思。
- **为什么必须先对齐质量与时限**：如果两个模型的成功率不同，比较就毫无意义——便宜的模型可能只是因为你把失败的尝试排除在分母之外。原文的处方是**把失败和重试都算进 $c_j$**，也就是用 3.2.2 的成功任务成本口径。这是一个"比较的公允性"问题，不是技术细节。
- **$Q^* = \Delta C_0/\Delta c$ 的经济学含义**（笔记整理）：这是最典型的**固定投入 vs 边际节省**的盈亏平衡分析。$\Delta C_0$ 是"多花的定金"，$\Delta c$ 是"每次省下的钱"，两者相除就是**回本所需的最小次数**。
  - 复算：10 万 GPU 小时 = $10^5 \times 3600 = 3.6\times10^8$ GPU 秒 ✓；除以 0.72 得 $5\times10^8$ ✓。
  - 与 3.6.1 的 0.1B vs 0.5B 算例（2.048 亿次）相比，两者是同一个思想，只是参数不同（那里 $\Delta C_0 = 73.5$ GPU 小时、$\Delta c = 0.00129$ GPU 秒）。**看到"某个更小的模型要更多训练"，就应该立刻想到问：它要服务多少次才回本？**
- **"专用硬件部署周期"为什么会影响模型选择**：如果为了部署某个模型要定制硬件、而硬件上线要一年，那么"模型版本能用多久"就变成了关键变量——如果这个模型半年后就被新版本取代，这笔硬件投入就收不回来。这是 $C_{\text{life}}$ 里"模型寿命、维护与贴现等假设"的现实来源。原文提醒这些假设要在给出预算时说明，因为**换了假设，结论可能完全反过来**。
- **三类负载表的用法**（笔记整理）：它不是"参考信息"，而是**一份采集清单**：
  - **Chat／Agent** 要采：每轮的输入／命中／输出 token 数（对应 3.2.1 的 $I_i, K_i$）、到达时间（3.1 的排队）、工具依赖图（3.2.4 的关键路径）、分支与复用间隔（缓存策略）。
  - **视觉／实时** 要采：原图字节、E/P/D 各阶段耗时（3.3.1）、EC/KV 大小、帧或块到达（3.3.3 的 $A(t)$）、首响应与连续播放要求、**打断后不再需要的计算**（这一项很特别：它是"可以取消的工作"，能直接省算力）。
  - **训练／RL** 要采：数据与质量、长度和标签（3.4.2 的 $P$ 与 $P_{\text{label}}$）、micro-batch／更新次数（3.4.2 的 $a$）、生成样本数／保留样本数（3.5.2 的 $n_{\text{generate}}$ 与 $n_{\text{keep}}$）、奖励计算与模型调用、权重版本（3.5.2 的同步）、完成期限。
  你会发现**这张表的每一栏都能追到本章前面某一节的一个公式**。如果一栏填不上，对应的那个公式就没法算。
- **工程上的四条**：
  1. 做模型选型时，先固定"质量门槛 + 时限"，再比成本；否则比出来的结论不可信。
  2. 把"失败与重试"计入 $c_j$，并保留失败原因字段（3.1.2 的要求）。
  3. 报预算时把假设写清（价格、寿命、贴现、硬件周期），因为 $Q^*$ 对 $\Delta c$ 非常敏感：$\Delta c$ 减半，$Q^*$ 翻倍。
  4. 采数据要按表来，**"记录具体的执行过程"** 是本章反复强调的一句话——负载不是一个数字，而是一条时间线加一组依赖关系。

**易混点**

- **$C_0$ 与 $c_j$**：前者是**一次性**前期投入（与 $Q$ 无关），后者是**每次**的边际成本（乘 $Q$ 与 $w_j$）。图 3-29 的"截距是训练投入、斜率是单次调用成本"说的就是这个结构。
- **$Q$（任务数）与调用次数**：一个任务可能包含多次模型调用（多轮对话、多次尝试）。原文的 $c_j$ 是"完成一个任务的平均成本"，已经包含了该任务内部的所有调用——所以 $Q$ 是**任务**数，别和调用次数搞混。
- **"额外训练成本 $\Delta C_0$"与"总训练成本 $C_0$"**：$Q^*$ 公式里的 $\Delta$ 是**两个方案之差**，不是任何一方的绝对值。
- **质量相同 ≠ 成功率相同**：原文说"各模型都要满足相同质量、时限与完成条件"，同时又要求"若任务成功率不同，$c_j$ 中还需包含失败和重试"。前者是**门槛**（都达标），后者是**代价**（达标过程花了多少）。

**一句话记住**

> $C_{\text{life}}(m) = C_0(m) + Q\sum_j w_j c_j(m)$，回本点 $Q^{*} = \Delta C_0/\Delta c$（多训 10 万 H100 小时、每任务省 0.72 GPU 秒 → 五亿次）；三类负载各有必采字段，而这些字段正好一一对应本章的公式。

## 谬误与陷阱

**原文要点**

- **误区一：平均请求率和长度相同，负载就相同。**
  少量超长请求、输入与输出长度的组合、请求到达顺序，都会影响短时间内的资源需求。例题 3-1 中，处理能力足以应付平均到达量，后一分钟却仍会积压。
- **误区二：token 单价降低，成功任务成本就会降低。**
  额外思考、未通过检查的回答、工具与环境都应进入分子，合格任务数进入分母。**零成功的 batch 只能报告消耗与失败，不能估计成功成本。**
- **误区三：训练 token 总数相同，系统工作量就相同。**
  序列分布改变注意力查询—键配对的数量，标签与词表头策略改变输出工作，更新次数改变优化器成本；RL 还要为没有采用的回答付出生成与反馈的开销。
- **误区四：Scaling Law 拟合出的计算最优规模，就是应该采用的训练规模。**
  计算最优只在固定训练预算、不计推理成本时成立。公开模型的每参数训练 token 数超出这一基准一至两个数量级，是把长期服务成本计入目标后的选择；**目标函数不同，不表示拟合结果被推翻。**

**辅导讲解**

- 这四个误区分别对应本章的四条主线，可以看成一份"考试易错点清单"（笔记整理）：
  - 误区一 → **3.1 排队**。破除工具是 $Q_{k+1} = \max(0, Q_k + A_k - \mu_k\Delta t)$：平均值相等，逐窗口的差额可以完全不同。
  - 误区二 → **3.2.2 成功任务成本**。破除工具是 $C_{\text{success}} = c/p$：分子含全部尝试（含失败、工具、环境），分母只数合格任务。
  - 误区三 → **3.4.2 序列分布 / 3.4.3 逐项计算 / 3.5.2 生成样本**。破除工具是：同样的 8192 token 分成 $4096+4096$ 或 $7168+1024$，注意力配对数是 16,781,312 对 26,218,496；标签减半但词表投影照做则运算量不变；RL 的生成数 $\approx n_{\text{keep}}/a$ 会随筛选变严而放大。
  - 误区四 → **3.6.1 / 3.6.3**。破除工具是 $Q^* = \Delta C_0/\Delta c$ 与 $C_{\text{life}}$：把推理成本纳入目标后，"计算最优"不再是"总成本最优"。
- 这四个误区有一个共同结构：**它们都是把"平均值"或"单一指标"当成了"完整负载"**。平均值丢了时间分布（误区一），单价丢了成功率（误区二），总 token 数丢了结构（误区三），计算预算丢了服务量（误区四）。所以本章的方法论可以用一句话概括：**负载 = 工作量的时间分布 + 完成标准 + 依赖关系 + 生命周期内的调用次数。**

**易混点**

- **"平均值够用"与"任何时刻都够用"**：前者是容量规划的起点，后者才是不积压的条件。
- **"单价下降"与"成本下降"**：中间还隔着用量与成功率两道关。
- **"计算最优"与"业务最优"**：前者是给定预算下的损失最小点，后者还要加上部署与调用成本。

**一句话记住**

> 四个误区都在犯同一个错——拿单个平均值/单价/总数/预算去代表整个负载；正确的做法是把时间分布、完成标准、结构差异和服务次数全都算进来。

## 代码任务轨迹

**原文要点**

- **任务定义**：任务是**修复区间合并函数，使嵌套区间和端点相接的区间正确合并，同时不修改输入及其嵌套列表**。
- **模型的能力边界**：模型**可以读取指定文件、改写它、运行固定测试并结束任务**，**控制器不替模型修改代码**。
- **两条轨迹**：
  - **关闭思考模式时，模型在 12 轮内读文件一次、改写五次、运行测试六次，仍未完成**；
  - **开启后，四轮分别是输出截断、写文件、运行测试和结束**。
- **首轮截断的代价**：**首轮截断产生的等待同样计入任务总时间。**

**辅导讲解**

- 这一段是 3.2.4 那张实测表的"题面"。把它和 3.2.4 的数据对起来看（笔记整理）：
  - 关闭思考：12 轮 = 读文件 1 + 改写 5 + 运行测试 6 = 12 ✓；总输出 765 token；模型耗时 13.156 s；工具耗时 0.476 s；原定检查只有 315/1013 通过，无别名检查 1/1013 ——**完全没修好**。
  - 开启思考：4 轮 = 输出截断 → 写文件 → 运行测试 → 结束 ✓；总输出 2,733 token（其中思考 2,553、结束符 3、之后 177）；模型耗时 76.294 s；工具耗时 0.078 s；原定检查 1013/1013 通过，无别名检查 710/1013 ——**原定目标达成，但额外性质只达成 70%**。
- **"控制器不替模型修改代码"这句很关键**：它保证了这个任务测的是**模型能力**，而不是"控制器兜底的能力"。如果控制器会自动修一下语法错误，那么"任务成功"就不能归功于模型。这与 3.1.2 的"先写出什么算完成"是同一件事的两面：**评测的可信度取决于你有没有偷偷替被测对象干活。**
- **"首轮截断的等待同样计入任务总时间"**：首轮 36.375 秒（图 3-10 中最大的一根柱）并不是"模型在思考"，而是**输出被截断后等待**。这种时间在传统指标里很容易被漏记（因为它既不是模型计算也不是工具执行），但它实实在在占掉了总时间的 47.5%。原文特意点出这一点，是在提醒：**统计任务时间要把"控制与交接"和"异常等待"都算上**（这也是 76.510 s 比 76.294 + 0.078 多出 0.138 s 的原因之一）。
- **两条轨迹的对照价值**：同样一个任务、同一个模型、同一个控制器，只改变"是否先生成思考内容"这一个开关，就从 12 轮失败变成 4 轮成功。这说明**在 Agent 场景里，影响最大的往往不是基础设施，而是"模型有没有想清楚再动手"**。对系统工程师来说，这意味着一件事：**负载的形状（轮数、token 数、时间分布）会随模型行为大幅变化，做容量规划时不能只按一种行为模式估算。**

**易混点**

- **"12 轮 vs 4 轮"与"13.156 s vs 76.294 s"**：轮数少不等于时间少。关闭思考时轮数多但每轮快，开启后轮数少但每轮慢（生成大量思考 token）。
- **"运行测试 6 次"与"修好了"**：跑了 6 次测试仍未通过；工具调用的**次数**衡量的是尝试量，不是成功。这与 3.2.2"生成已经消耗资源，任务却没有完成"是同一句话的实例。
- **"原定检查通过"与"任务真正完成"**：原定检查 1013/1013，但额外检查只有 710/1013。完成标准写到哪一层，决定了你能看到多深的问题。

**一句话记住**

> 关闭思考：12 轮、765 token、13.156 s、未修好；开启思考：4 轮、2,733 token、76.294 s、原定检查全过——而首轮那 36.375 秒的截断等待，占了整任务 47.5% 的时间。

## 本章小结

**原文要点（忠实整理原文"本章小结"）**

- **负载的两个维度**：持续服务的负载**既取决于每次请求要做多少工作，也取决于请求何时到达、各步骤之间有哪些依赖**。
- **平均值与短时压力**：**用平均速率可以粗略估算所需资源；分析短时间内的积压和状态驻留时间，则能发现平均值未体现的资源压力。**
- **任务类型的差异**：**多轮任务还包含工具等待与失败尝试，实时任务要保证数据及时到达，训练则增加反向、参数更新和权重同步。**
- **比较的前提**：**比较不同方案的资源与成本时，应采用相同的质量要求和任务完成标准。**
- **两套工具**：**Scaling Law 为训练分配提供可检验的统计模型，长期服务需求又可能改变前期投入的选择。**
- **三个核心练习**：**核心练习 3-2、3-4、3-7 分别把这些方法用于持续请求、交互任务和 RL 循环。**

**辅导讲解**

- 这段小结只用了五句话，但它精确地把整章分成了"**负载的形状**"和"**成本的账本**"两半（笔记整理）：
  - 前半：工作量的时间分布（3.1）、依赖与等待（3.2、3.3.3）、训练的状态与更新（3.4、3.5）。
  - 后半：质量的统一口径（3.2.2 的成功任务成本、3.1.2 的完成标准）、训练的分配（3.6.1、3.6.2）、全生命周期成本（3.6.3）。
- **"平均值未体现的资源压力"是本章的题眼**。整章至少有四处用到这个思想：排队积压（3.1.3）、工具等待的状态占用（3.1.2 的 $\lambda M_0\tau$）、TTFT 与完整请求时间的 p95 差异（3.1.3 的实测）、RL 里"生成了但没被保留"的样本（3.5.2）。**凡是只报平均值的监控面板，都会漏掉这四类问题。**
- **三个核心练习的分工**值得单独记：练习 3-2（持续请求：突发积压与工具等待的状态占用）、练习 3-4（交互任务：工具并行与局部加速的收益）、练习 3-7（RL 循环：保留比例变化对生成与更新开销的影响）。它们分别对应本章三条最实用的计算路径，如果时间有限，优先把这三个练习做熟。

**一句话记住**

> 负载 = 工作量 × 到达时间 × 依赖关系；平均值只够粗估，短时积压与状态驻留才是真压力；比较任何方案前，先把质量与完成标准统一。

## 原文本章小结

> 持续服务的负载既取决于每次请求要做多少工作，也取决于请求何时到达、各步骤之间有哪些依赖。用平均速率可以粗略估算所需资源；分析短时间内的积压和状态驻留时间，则能发现平均值未体现的资源压力。多轮任务还包含工具等待与失败尝试，实时任务要保证数据及时到达，训练则增加反向、参数更新和权重同步。
>
> 比较不同方案的资源与成本时，应采用相同的质量要求和任务完成标准。Scaling Law 为训练分配提供可检验的统计模型，长期服务需求又可能改变前期投入的选择。核心练习 3-2、3-4、3-7 分别把这些方法用于持续请求、交互任务和 RL 循环。
